# Backtrader 职责边界审查与重构建议

> 状态：**审查与重构建议，不是新的已实施合同或验收结论**。审查时间：2026-11-01；Backtrader 既有 `dev` 工作区，HEAD 为 `0933dadd64ccf75b281e435df2dd085e6d05e789`。工作区包含大量未提交的迭代 53 修改和新文件，下文明确区分工作树与 HEAD；行号和内容可能随工作区继续变化。未运行行为测试、构建或真实账户操作。

## 1. 目的和范围

本文以[仓库目录与文件职责规范](repository-responsibilities_zh.md)和[交易系统架构与项目职责](../../TRADING_SYSTEM_ARCHITECTURE.md)为起点，抽查引擎、数据、交易接入、研究、打包和入口。重点判断状态与生命周期属于谁、调用是否穿过合理的边界、现有兼容性如何保留，并提出可单独验收的小步重构。这里不是对整个仓库所有文件的逐行审计；未逐一核实的文件必须保持“待核查”，不能因为本文列出目标职责就认定实际实现已经符合。

现行指南提供目录分类与关键文件规则，但不构成逐文件清单。本文里的“应”是建议的目标，已有源代码、公开 API、发布包及策略行为才是迁移时需要核对的现实。未提交迭代 53 代码是候选实现，不视作已完成结构、导入、发行或行为验收。

## 2. 判断原则

1. **一个状态、一处权威**：明确状态的创建者、读写者、生命周期及失败后的归属；其他组件通过窄接口协作。必要的边界校验可以多层保留，不能机械删除。
2. **核心与适配器分工**：Cerebro 决定框架调度；Strategy/Line/Feed/Broker 表达 Backtrader 语义；Store 负责框架接入和生命周期协调；交易所原生协议、provider session 与账户权威属于对应 SDK/provider。
3. **接口先于移动**：先列当前调用者、公开入口、类身份、序列化、可选依赖、安装包和替身，再定义接口与迁移路径。私有命名不意味着外部没有调用者；兼容方式及退役期限须由具体轮次决定。
4. **区分数据与证明**：回放时间、模拟结果、配置及类型名称不自动证明实时来源、账户状态或交易权限；未知或不支持的能力要显式拒绝。
5. **性能和语义同等重要**：大文件、重复代码和多分支是审查线索，不自动等于缺陷；引擎热路径的时钟、通知、运行顺序和性能合同必须先建立比较基线。
6. **文件按职责而非数量拆分**：优先围绕独立状态、稳定合同和变更原因分离；简单公式模块可按同一规则批量描述，不为每个文件创造空泛包装层。
7. **证据按等级表述**：静态检查、模拟、安装包、性能和真实账户分别记录；当前审查只支持静态结论。

## 3. 建议的职责归属

| 范围 | 应承担 | 不应承担或需要边界 |
| --- | --- | --- |
| `cerebro.py`、`_cerebro/` | 公共装配入口、引擎调度、策略运行、通知顺序和有界生命周期；具体循环留在现有内部实现 | 不拥有 provider 连接、账户真值或独立于引擎的第二个策略调度器 |
| `metabase.py`、`parameters.py` | 显式对象构造、参数、owner 发现及兼容合同 | 不把交易所或业务策略逻辑放进通用构造流程 |
| `lineroot.py`、`linebuffer.py`、`lineseries.py`、`lineiterator.py`、`dataseries.py` | 线接口、数据存储及运算、线组合、时钟/迭代和数据类型；保持已有多数据语义 | 不让某一研究场景无条件改变普通线计算语义 |
| `strategy.py`、`indicator.py`、`observer.py`、`analyzer.py`、`sizer.py`、`signal.py` | 框架组件公共合同及其生命周期；Strategy 保留用户入口、订单 API 和回调顺序 | 不把 SDK 通用 journal、provider 原生协议或账户权威变成框架实现 |
| `feed.py`、`feeds/`、`filters/`、`resamplerfilter.py` | Feed 生命周期、数据映射、时间语义、过滤和聚合；不同数据时钟须有明确合同 | 不以回放/接收时间冒充实盘来源时钟，不自行决定真实交易权限 |
| `broker.py`、`brokers/`、`order.py`、`position.py`、`trade.py`、`comminfo.py`、`commissions/`、`fillers.py` | Broker 接口、框架订单/持仓/交易对象、成交投影、费用和回测撮合语义 | 不凭模拟成交、配置名或本地缓存宣称真实账户已确认 |
| `store.py`、`stores/` | 单实例 Store 合同；框架连接、订阅和通知协调；中立 DTO 向 BT 对象映射；由具体组件拥有明确的本地队列/代次状态 | 不复制 SDK 的 provider session、原生字段解析、账户授权或 durable journal 真值 |
| `execution/`、`factor_execution/`、`service/` | 当前为迭代 53 候选位置：BT 订单/因子事实投影与框架生命周期桥接；每个文件须进一步确定状态归属 | 不因搬入新目录而声称 SDK 通用能力、provider 权威或生产行为已迁移完成 |
| `research/`、`research/alpha101/` | 因子与面板研究框架、公式定义及与框架时钟的绑定；公式实现按目录规则归类 | 不另建与 Cerebro 冲突的隐式引擎；数据、时钟和缺失值合同不可凭名称替代 |
| `indicators/`、`observers/`、`analyzers/`、`sizers/`、`signals/` | 各自可复用组件；指标公式、观察、分析和仓位计算按具体模块说明 | 不暗中变更账户权威；`contrib/` 的来源和支持状态须单独标注 |
| `plot/`、`bokeh/`、包内 `reports/` | 数据展示、图形后端和报告表达；明确可选依赖 | 不成为核心包导入的无条件前提，不承载策略或执行真值 |
| `channels/`、`channel.py`、`events.py`、`notifications/`、`timer.py` | 按实际公开合同处理事件、通道、通知和定时，明确运行模式差异 | 不把不同运行模式的存在直接认定为错误，也不新增无合同的平行调度权威 |
| `configs/`、`profiles.py`、`live_trading/`、`btrun/` | 凭据外的配置模板、运行配置投影、实盘抽象和已确认支持的运行入口 | 不存真实凭据；历史命令须标明状态，不能因文件存在即认定可用 |
| `mixins/`、`utils/`、`functions.py` 等辅助模块 | 稳定且确有复用的通用机制；领域投影应有可辨认的 owner | 不用 `utils`/`common` 把不同生命周期的状态聚合为杂项 |
| `tests/`、`examples/`、`scripts/`、`tools/`、`docs/`、`archive/` | 测试合同、示例装配、仓库工具、文档和退役历史；分别标记支持及证据状态 | 生产包不能隐式依赖这些目录；历史证据不因整理而改写、删除或重跑 |

跨项目边界仍以现有交易系统架构和适用 SDK 规范为准。特别是 SDK 中立合同、provider 真值和 durable state 与 BT 类型投影不能只根据相似名称合并。

## 4. 有证据的优先重构项

### P0：先关闭迁移与发行缺口

**事实**：当前工作树已删除多个 `backtrader/stores/service_*.py`，同时新增未跟踪的 `backtrader/service/`；但 [`test_service_strategy_account_book.py`](../../../tests/unit/stores/test_service_strategy_account_book.py) 和 [`test_service_refresh_loop.py`](../../../tests/unit/stores/test_service_refresh_loop.py) 仍导入旧路径。这里是静态路径不一致，尚未运行测试确认报错。`setup.py` 的 `find_packages()` 会发现包含 `__init__.py` 的候选包，而这些包还未完成验收；这不代表已发布工件含有它们。

**建议**：先列出旧/新模块、公开和内部调用者、真实外部兼容需求及分发清单；逐项选择迁移调用点或保留有意的兼容入口。不要批量恢复退役包，也不要为让测试导入通过而掩盖未完成的迁移。对每个已接受的小范围分别做焦点导入/行为测试，再从明确的已接受源码构建隔离 wheel，核查内容、依赖和安装后导入来源。

**验收**：迁移清单中每个旧入口都有保留、迁移或退役结论；相关测试实际收集并通过；安装包与源码各自验证；无意外新包或敏感资源进入发行物。当前并无这些验收结果。

### P1：因子执行的无 I/O 合同和持久状态

**事实**：未跟踪的 [`factor_execution.py`](../../../backtrader/factor_execution/factor_execution.py) 中 `execution_position_snapshot()` 声明只读取缓存且不调用 Store，但实际调用 Broker 的 `getposition()`；当前 [`btapibroker.py`](../../../backtrader/brokers/btapibroker.py) 的该方法在非异步命令路径会调用 `_sync_positions()`，可能进一步刷新外部状态。由源码不能断言某次实际发生了外部调用，但该通用调用不保证文档声称的无 I/O 合同。`factor_execution_facts.py` 也调用同一 Broker 方法。

[`factor_position_book.py`](../../../backtrader/factor_execution/factor_position_book.py) 既有 BT Order 派生的归属计算，又定义 SQLite 表和写入，BT 侧 journal port 依赖这些操作；这与“durable state 归 SDK”目标的具体边界需要进一步确认，不能仅凭有 SQLite 就断定现有设计错误。

**建议**：先定义明确无 Store/provider I/O 的缓存持仓快照接口及其可用性和新鲜度语义；不满足时显式失败，而不是悄悄查询。分别核对 position book 的 schema、事务、重放和游标 owner；保留 BT 对 Order 的归属投影，如确认其为耐久账本则迁至 SDK journal owner，如仅为受控派生缓存则记录例外和事务边界。迁移前不改变订单或持仓的权威语义。

**验收**：以会记录调用的 Store/provider 替身证明快照路径零调用，并覆盖缓存缺失、并发变化与旧数据；持久化归属另验事务原子性、重复事件、恢复和兼容迁移。真实账户能力需另行验收。

### P1：Store、Broker 和 Feed 的协作合同

**事实**：[`BtApiStore`](../../../backtrader/stores/btapistore.py) 同时协调启停、行情、命令、对账、风险和 API 装配；[`BtApiBroker`](../../../backtrader/brokers/btapibroker.py) 启动及 session 接入处访问 Store 的私有模式和生命周期状态；[`BtApiFeed`](../../../backtrader/feeds/btapifeed.py) 依赖订阅、poll、历史数据和 raw bar 等具体行为。现有队列、投影和 SDK 适配模块已有部分拆分，因此大文件本身不是证明设计失败的理由。

**建议**：按调用场景先写两个窄合同：Broker 所需能力（模式、账户投影、命令、对账、生命周期）和 Feed 所需行情能力（订阅、历史、poll、raw bar、watermark 与结束语义）。Store 保留现有公开 facade、实例及生命周期权威；无状态投影和独立状态组件按现有 owner 渐进下沉。账户有效性、provider session 与授权保持 SDK 权威，Store 边界上的写路由校验继续保留。新协议不得因类型抽象而自动扩大写权限。

**验收**：先以原有行为建立基线，再覆盖普通和只读 Store、自定义 Store、实例隔离、命令与行情并发、断线代次、刷新时关闭、异常与超时清理；如涉及真实接入，单独按已授权的账户验收程序验证。

### P1：引擎与 live cohort 的职责边界

**事实**：[`cerebro.py`](../../../backtrader/cerebro.py) 中 live cohort 配置与验证直接检查研究层 `LiveBarCohort` 和精确 `BtApiFeed` 类型；[`_cerebro/runnext.py`](../../../backtrader/_cerebro/runnext.py) 同时处理常规多 Feed 推进以及 cohort 等待、批次和 winddown；[`research/live_cohort.py`](../../../backtrader/research/live_cohort.py) 拥有 cohort 状态。这是已观察到的跨层耦合，不单独证明行为错误。

**建议**：先整理成员身份、批次准备/提交、时钟、水位和退出的责任表；再考虑将 cohort 专属协调放进私有协作组件，由 Cerebro 保留唯一调度、生命周期和对外 API。第一步保留当前精确类型、成员身份及其他安全校验，不能为了抽象接口而放宽；是否允许更多实现需独立设计及验收。

**验收**：覆盖普通运行、cohort 批次、等待唤醒、关闭/超时、异常、无 cohort 路径和多数据时钟；对比 Broker、timer、策略和通知顺序，不只验证接口可导入。

### P1：Strategy 恢复投影与通知顺序

**事实**：[`strategy.py`](../../../backtrader/strategy.py) 同时承担用户策略 API、时钟推进、通知，以及与 Broker 协作的 Trade 状态恢复和 receipt 确认。恢复中的 BT `Trade` 构造确属框架投影，并不意味着通用 journal 应搬回 BT。

**建议**：在列出原有回调顺序、对象身份及失败路径后，考虑把 BT Trade 重建和校验收敛到私有投影协作者；Strategy 保留公共 API、生命周期和通知入口，SDK 保留其恢复协议与持久状态。不可将通知与 receipt 确认拆成失去顺序保证的两个独立异步流程。

**验收**：覆盖恢复事件重放、重复/失败通知、确认时机、Order/Trade 对象身份及 Strategy 子类兼容；结合现有恢复测试和普通策略回归分别验证。

### P2：时钟热路径与研究严格计算

**事实**：[`lineiterator.py`](../../../backtrader/lineiterator.py)、[`strategy.py`](../../../backtrader/strategy.py) 与 runonce/runnext 存在多条时钟和快路径；[`linebuffer.py`](../../../backtrader/linebuffer.py) 中可观察到对 `research.strict` 的条件依赖。不同路径服务于真实模式和性能需求，尚无证据表明应合并。

**建议**：先建立多 Feed、次级时钟、最小周期、runonce/runnext、replay、缺失值和通知的行为矩阵。再评估是否以窄的严格计算策略消除低层对研究包的直接依赖；默认行为和热路径成本必须保留。避免一次性重写线系统、取消快路径或仅为目录整齐迁移文件。

**验收**：对比时间序列、指标值、订单/通知顺序与策略输出，并运行相关性能合同；性能结果单独报告。

### P2：绘图后端和可选依赖隔离

**事实**：[`presentation.py`](../../../backtrader/_cerebro/presentation.py) 在默认 Bokeh 不可用时提供 Matplotlib 回退；但 [`plot/__init__.py`](../../../backtrader/plot/__init__.py) 导入 Plotly 后端，而 [`plot/plot.py`](../../../backtrader/plot/plot.py) 还在模块级导入 Plotly、Dash 和 pyecharts。这些库列在 `setup.py` 的绘图 extra，而非基础依赖。因此基础依赖环境下，其他绘图后端缺包可能阻断 Matplotlib 路径；这是静态依赖分析，尚未在隔离环境复现。

**建议**：按具体 backend 推迟加载其专属依赖；缺少被选后端时给明确错误，其他后端不受影响。保留现有 `backtrader.plot` 导出、默认回退行为及图表语义。普通 `reports/` 和研究用 factor report 有不同用途，继续分别维护而不因都生成图表而合并。

**验收**：在基础依赖、仅安装单个后端、安装全部后端的隔离环境分别验证导入和绘图选择；检查原有公共导入和默认回退。不能只在开发机完整依赖环境验证。

### P2：会话与刷新组件的 owner

**事实**：`service_execution_session.py` 和 `managed_runtime_host.py` 均涉及运行、poll、Broker 接入和清理，但各自的 API ownership 与授权语义可能不同；`service/funding_refresh.py` 存在队列、worker 与读取入口，须核对其是否符合 `service/` 仅保留框架桥接的目标。

**建议**：先画出 owned/borrowed API、启动/失败/关闭责任与权限矩阵，再决定能否共用小型生命周期协议；不得仅因方法名相同而合并会话。对 funding refresh 逐函数核查调用者与状态，决定属于 BT Store 内部协作还是 SDK 通用 owner，未核实前不移动。

**验收**：覆盖互斥绑定、只读/执行模式、借用 API 不被错误关闭、启动失败、重复关闭与清理失败；不把本地模拟当成账户证明。

### P2：文档、历史入口和发行声明

**事实**：职责规范第 6 节仍描述 Feed 从 Store 导入两个私有 helper；当前未提交的 `btapifeed.py` 已改从 `utils.bar_projection` 导入 `normalize_bar`。该观察仅适用于当前工作树，不能声称相关迁移已验收。另有历史示例和脚本引用已退役的 `backtrader_runtime`，`setup.py` 的 MIT classifier 与仓库 GPLv3 声明不一致；README 与 AGENTS 对 PyPI 安装的说明也不同。发行实际状态与许可结论不在此次静态审查范围。

**建议**：在对应迁移轮次验收后，同步修正职责指南；建立入口清单，给每个示例/脚本标注当前支持、历史或待核查，并提供经验证的替代入口。由项目负责人核实许可与发布事实，再同步发行元数据和文档；不据此猜测许可或恢复退役运行时。

**验收**：检查示例命令的来源、导航和目标文件，必要时在无账户隔离环境验证；中英文相关内容及发行元数据保持一致，冻结历史材料保持原样。

## 5. 文件级职责清单的维护方式

先按目录建立可复核的清单，而不是从文件名自动生成断言。每一行至少包含：`路径`、`当前实际职责与证据`、`建议职责/owner`、`公开入口及调用者`、`状态/副作用`、`打包与兼容`、`测试或验收状态`、`处置（保留/重构/退役/待核查）`。对无状态的同类公式，可以按目录共用合同并列出例外；关键生命周期与状态组件应逐文件列出，必要时细到函数。

建议顺序：① 迭代 53 的 `stores/`、`execution/`、`factor_execution/`、`service/` 和其 SDK 边界；② `cerebro.py`/`_cerebro/`、Feed、Broker 和 Strategy；③ 研究与因子；④ 用户入口、发行和历史脚本；⑤ 常规指标、展示及剩余辅助目录。每次按一个明确行为边界完成梳理、实现、相称验证与 scoped commit，再开始下一轮；不要按文件数量拆分，也不要要求一次性改完全部目录。

## 6. 实施与交付约束

- 保留当前工作区已有未提交修改和冻结证据；任何代码迁移前先对照当前 HEAD、工作树及调用者，避免覆盖并行工作。
- 当前文档只提出建议，不授权真实账户、provider、交易、宿主退出或历史证据重跑；需要的操作应遵循既有授权与保护约束。
- 对每轮写明精确范围、候选与既有接口、验证命令及结果、未覆盖风险、仓库/分支和提交。SDK 子包先提交，再更新其父仓库 gitlink。
- 结构变化时同步现行职责指南、`AGENTS.md` 和相关用户文档；本文保留审查时点，后续不得把提议改写成历史上已验收的事实。
