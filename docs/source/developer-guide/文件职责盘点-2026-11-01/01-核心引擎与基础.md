## 重点发现与建议顺序

1. **两套参数/兼容设施需要有调用图。** parameters.py 同时有 descriptor 新系统和旧 params bridge；metabase.py 仍含 ParamsMixin/AutoInfoClass/ParameterManager。下一步按实际继承者和 p/params 访问调用点登记保留、迁移或兼容，不以模块标题判断新旧系统已收敛。
2. **Strategy 是最明显的边界审查点。** 当前源码将标准 Strategy 生命周期与 managed-paper Trade projection/recovery 和 group-order Broker call-through 放在同一超大模块。迭代 53 的目标是 SDK 持久化与 provider authority 留在 SDK、BT 保持框架状态投影/窄调用桥；应按每个方法的调用者与 DTO 边界逐步分类，保持公开 Strategy API 和 Trade 通知语义。当前文件有未提交修改，本清单不代表这些改动已验收。
3. **channel 是另一种调度方式，不仅是数据容器。** backtrader/channel.py 提供队列与排序；_cerebro/channel.py 实际推进 Strategy。需维护其与普通 Feed 引擎之间明确的模式、时间/排序和生命周期合同。模式名或队列成功不等于实时/provider/成交能力。
4. **事件时钟需要维持两个边界。** events.py 的 EventData 会补本进程 receive wall/monotonic clock；SDK MarketOrderBookEnvelope 则保留 source/cursor/clock 并关闭 execution eligibility。应保留这一区分，不能为方便把本地 receive 时间推成 provider 时间或交易资格。
5. **行/时钟核心应优先查调用关系而非按行数重排。** linebuffer.py、lineiterator.py、lineseries.py 与 lineroot.py 互相依赖数据缓冲、minperiod、表达式、source clock 和动态行定义。先画出唯一推进者及 next/once 两条路径，再决定 strict factor guard 或 clock helper 的最窄所有者。
6. **Strategy._clk_update 存在多处运行时 patch attempt。** LineIterator 在 lineiterator.py:1790 定义基线方法；lineroot.py:919、lineseries.py:2408、metabase.py:169 各定义替代 safe_clk_update，并分别在 :1106、:2564、:1802 的模块级调用点尝试赋值。源码导入链可提供静态线索，但循环导入和各自异常分支影响是否完成赋值；必须进一步验证三者的执行顺序、Strategy._clk_update 最终函数身份/代码来源及真实调用路径，不能从任一个 helper 单独断定最终 owner 或已生效实现。
7. **Cerebro 拆分本身有明确收益，也有 MRO 成本。** 八个 mixin 把公共入口缩小、职责大体可区分；保留拆分，不建议继续无目标碎片化。跨 mixin 私有调用、类属性由谁初始化、方法重名/MRO 顺序和导出兼容应成为改动审阅项目。
8. **兼容文件与公共命名空间须查使用者。** test_helpers.py 随产品包存在；store.py 保留 SingletonMixin 导入但 Store 非 singleton；mixins 提供 StoreBase 旧别名；talib 通过惰性入口隔离依赖。可以提出逐步退役/收敛，但先查内部/外部调用及发行合同。
9. **装配 API 不代表环境或权限验收。** profiles.py 的 live 分支只完成 profile 驱动的对象装配并默认 BtApiStore；Cerebro live 标志、data feed 的 islive 或 Store 对象构造均不能证明账户/session ready，也不授予写能力。
