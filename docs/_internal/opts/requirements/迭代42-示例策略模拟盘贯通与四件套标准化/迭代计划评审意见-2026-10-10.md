## 1. 总体结论

**方向合理，8个示例的范围可以保留；建议补齐验收定义、授权接口集成和迁移顺序后再执行。**

1. 将认证案例已通过的直接API能力，推定为示例的Store/Broker完整链路已经可复用。
2. “报单终态”“成交往返”“自然信号”和“drill”没有形成足够明确的验收边界。
3. 四件套整理、旧入口删除、清单刷新和真实验收的顺序，可能使验收代码与最终提交不一致。

优化重点应是尽快交付一个完整示例并复用其工作路径。前置工作只解决明确的接口和验收缺口，不扩展新的通用场景引擎、拓扑矩阵或多层审计框架。

### RV42-01：先验证SimNow授权接口如何接入原生链路

计划§5.1拟复用`arm_execution_for_registered_sim`。当前SDK该接口面向直接CTP调用，返回的capability需要随`submit_order_insert`和`submit_order_action`传递；现有013_3则通过Store配置授权并创建Broker，Store的arming路径调用`arm_execution_from_preflight`。

核对位置：

- SDK：`D:/bt_api_py/bt_api/bt_api_ctp/src/bt_api_ctp/ctp/client.py:7055`。
- 示例：`examples/013_3_sa_midfreq_simnow/run.py:6029`及`:6228`。
- Store：`backtrader/stores/btapistore.py:13922`。

这说明存在必须明确的接口集成决策，尚不能把直接API准入与Store/Broker路径视为已经兼容；也不能仅凭这项差异断言整条路径必然不可实现。

建议在R1真实写入前，选择并验证一条路径：沿用现有Store可消费的授权接口，或补充必要的SDK公开接口。验证授权范围、交易日和连接代次绑定、每次报撤单的授权传递、失效及重放拒绝，以及启动失败后的有界关闭。避免示例通过私有属性绕过Store，也避免同时维护两套真实执行链。

如需要SDK改动，先完成该窄范围源码验收与提交，再集成到示例；源码验收本身不计为真实账户通过。

### RV42-02：完整贯通必须证明实际成交与对应平仓

当前§2将“成交/拒绝/撤销”并列为终态。若所有订单被拒绝或撤销，账户仍为空，按现有文字也可能被解释为贯通PASS。

建议将验收拆成两个维度：

- **订单生命周期**：请求身份明确、受理或拒绝可确认、终态可查询。
- **成交往返**：存在交易所确认的正成交量；每腿成交暴露均有对应平仓；最终持仓、挂单和成交对账通过。

本迭代完整技术贯通要求第二项。纯拒单或纯撤单只能作为单独的生命周期证据，不能证明成交往返。

自然信号与drill均可产生技术贯通结果，但证据必须记录触发来源。Drill只替代信号来源，不能绕过原有风险与执行状态机；双所、双腿或C/P/F三腿示例，需要覆盖自身对应的完整腿组合，不能用任意单腿交易替代。

只有自然信号观察窗口结束、尚无自然订单尝试、无未决订单或UNKNOWN且预检通过时，才进入drill。自然交易已经拒单、部分成交或超时后，不应再用drill覆盖其失败结果。Drill通过不产生策略有效性或盈利准入结论。

### RV42-03：多腿失败、清理预算与UNKNOWN需要可执行规则

“补偿撤单、强制平仓、UNKNOWN冻结”不足以确定双所或三腿失败后的行为。建议至少覆盖以下受控测试：

- 第一腿成交，第二腿或第三腿拒绝、超时或UNKNOWN。
- 部分成交、撤单与迟到成交竞态。
- 补偿单部分成交、拒绝或结果不确定。
- 运行超时、异常退出及重启后仍存在未决订单。
- 重复回报和重复启动，不得导致重复开仓或清理。

预算应明确区分逐腿数量、整轮名义金额、最大未对冲敞口及其持续时间。报单尝试、撤单和补偿均计数；给撤单及已确认持仓的减仓预留额度，不能因开仓耗尽预算而无法清理。预留清理额度也必须有上限。

UNKNOWN时停止新增风险，使用稳定订单身份查询与对账；只有确认活动订单后才撤单，只有确认剩余持仓后才减仓，不盲目重发或发送猜测数量的反向单。冻结与未决记录应持久化，并通过账户及环境范围的锁阻止另一个示例或重启进程绕过冻结。

试点可要求相关账户初始空仓、无活动单，以简化所有权和对账。清理仅覆盖本轮授权订单与持仓，不能扩大为清空账户其他业务。

上述异常分支使用实际策略和执行代码、受控外部叶子的测试验证。真实模拟账户完成有界的正向成交往返，无需为制造异常而扩大交易规模。

### RV42-04：统一写重试与客户端订单ID规则

§5.2允许OKX使用相同`clOrdId`重试，§5.3却规定写操作不重试，应消除冲突。

OKX官方文档说明，`clOrdId`只要求当前活动订单唯一，订单进入终态后可以复用，历史查询在重复ID下只返回最新匹配。因此相同ID不能单独证明永久幂等。

建议按以下类别确定行为：

| 请求结果 | 行为 |
| --- | --- |
| 确定拒绝 | 记录拒绝及原因；只有符合明确重试条件时才允许再次尝试 |
| 明确允许重试的错误 | 使用固定逻辑订单身份、有限次数和总期限；每次请求消耗预算 |
| 超时、断连或受理结果不确定 | 先查询与对账；未确认前禁止盲目重发 |

一次查询未找到订单不等于订单未受理。明确受理后的订单以场所订单身份跟踪；本地逻辑订单ID在整个运行和恢复周期内保持唯一。

参考：[OKX订单接口文档](https://www.okx.com/docs-v5/en/)。本建议不要求修改000已交付certlib，而是明确012示例使用的SDK路径必须具备什么语义。

### RV42-05：自动择优保留，但环境能力不可混用

TCP探测可用于候选筛选，最终运行前仍须验证登录、交易日、所需合约可交易、行情到达及新鲜度。排名最快的前置不一定具备本轮验收所需能力。

SimNow官方环境说明对第二套环境列有服务窗口，并说明不提供结算等服务；迭代41最新交付记录还区分了标准环境与7×24环境的资金校验行为。因此不能仅凭“7×24”名称或TCP连通就认为与标准环境等价，具体能力应以本次运行的事实确认。

建议：

- 证据记录所选front组、环境类型、交易日、连接代次及能力检查结果。
- 标准环境与7×24均可提供其实际覆盖范围内的技术证据，但资金、保证金及结算结论分别标注。
- 自动选择或回退仅发生在首次写入之前；存在订单、持仓或UNKNOWN后，不自动换环境重新运行。
- 期权可用性检查提前进行，核对C/P/F的标的对应、到期日、行权价、交易状态、乘数、最小数量和盘口。以规格确定可行的最小腿组合，不能只取每腿各自的最小下单量。

参考：[SimNow环境说明](https://www.simnow.com.cn/product.action)。官方网站说明和历史现场观察均不能替代本轮就绪检查。

### RV42-06：四件套统一使用方式，不强制把逻辑压成四个文件

§3.2允许本目录模块，§3.3又容易被理解为最终只能保留四个文件，需统一表述。

建议定义为：`README.md`、`config.yaml`、策略文件和`run.py`构成标准公开使用契约，`run.py`为唯一运行入口；允许必要内部模块、fixture和审批资产，没有第二套独立运行面。

现有013_3的锁、风控、报告模块，以及012的签名审批、公钥和清单，都有实际职责。不能为了目录外观删除必要能力，或把全部逻辑塞进庞大的`run.py`。若某项能力确实适合SDK，应按需要迁移并独立验收，不为本次整理新增通用框架。

清理前逐目录登记依赖与替代位置，只删除已被替代的入口、失效候选和模板。保留字节绑定的历史证据；其保留不意味着仍存在可执行旧入口。

### RV42-07：真实验收绑定最终运行代码，每目录独立提交

当前每轮先live验收，再删除旧文件并更新测试。后续清理若改变运行依赖、清单或审批哈希，验收代码可能与最终提交不同。

建议改成：

**实现与迁移 → 行为回归和失败路径检查 → 清单/审批刷新 → 冻结运行代码 → dry → live → 精确范围提交。**

新入口可在开发时与旧文件暂时共存，但旧入口退役、runtime登记迁移、测试更新和运行依赖裁剪应在本例最终live验收前完成。验收后只补充结果归档；若再次改变运行代码，按实际影响重新验收，不重复无变化的已通过套件来增加交付工作。

§4中的offset、缺盘口和超时修复会改变行为，应分别登记预期差异。其余信号、参数与订单意图使用冻结回放输入比较，避免以“标准化”名义无意改变策略。

013_1与013_2、014_1与014_2分别验收、分别提交；共享SDK改动先独立提交。013_3的private与managed replay路由逐项决定迁移或退役，不能随通用目录清理一起删除。R7只做全局残留检查、干跑与交付汇总。

### RV42-08：回放、预热、期限与证据格式在试点时确定

`--replay`不宜到R7才决定。它是保持策略行为、验证安全修复与降低后续开发成本的基础，应从R1起与dry/live并存。

Dry只验证公开配置结构和凭据环境变量名格式，不读取`.env`值，不要求真实凭据已经存在，不构造provider、不联网；真实凭据的有界读取和可用性检查放在显式live路径。目录外的dry/replay检查使用公开测试输入，不能意外依赖checkout根目录的私有文件。

每例定义最小预热数据量、真实历史数据来源或预热等待方式、自然信号截止条件、最大运行期限、订单确认期限和清理期限。超时使用单调时钟；行情不再更新时也必须能结束。不得用虚构行情填充真实验收所需的预热。014_1现有40根bar窗口是需要明确处理的实例。

保留`test_examples_self_contained`作为导入边界检查，但不能把它等同于复制目录后可运行：该测试明确不覆盖数据独立性，并对核心SDK模块名作了放行。补充一次有明确依赖和测试数据的目录外dry/replay运行检查即可，无需新增复杂验证体系。

建议最小证据格式包括：

| 层级 | 必要字段 |
| --- | --- |
| 运行 | schema版本、run_id、示例ID、开始/结束、状态与失败阶段、natural/drill/none |
| 运行来源 | 策略和配置哈希、Backtrader/SDK提交与实际加载版本、验收命令 |
| 环境 | 场所、demo/simnow类型、所选front组、交易日和连接代次 |
| 每腿 | 合约及规格、方向/offset/position side、逻辑与场所订单身份、请求量、累计成交、剩余量、终态及补偿关联 |
| 对账与清理 | 本轮最终持仓、活动单、快照时间与代次、预算消耗、UNKNOWN是否存在、资源关闭结果 |
| 归档 | 脱敏证据路径与SHA-256、验收代码来源、本轮交付提交引用 |

Tracker汇总各维度，不只记录报单/成交计数。现场原始证据保存在git-ignored目录；将足以复核结果的脱敏摘要与证据哈希归档到迭代42文档目录，避免换机器后只剩不可访问的路径。

## 5. 建议直接补入计划的验收条款

> 完整技术贯通PASS要求本示例对应的全部交易腿存在可确认的正成交量，完成相应平仓，并通过远端持仓和活动订单对账。纯拒单或纯撤单仅证明订单生命周期，不构成成交往返PASS。
>
> 自然信号与drill分别标注。Drill仅替代信号来源，使用同一风险及执行链；不得在自然交易已经失败或状态不确定后，用drill覆盖原结果。
>
> UNKNOWN停止新增风险，并保留持久化冻结与未决订单记录。恢复只能基于权威订单、成交和持仓事实；不得盲目重发或根据猜测数量平仓。
>
> 自动前置选择仅发生在首次写入之前。不同SimNow环境的证据覆盖范围分别记录；存在订单、持仓或UNKNOWN后不自动换环境重跑。
>
> 本例迁移、回归、运行依赖裁剪和清单刷新完成后冻结运行代码，再进行真实验收。每目录独立验收和提交，最终汇总不重复无变化的已通过验收。

## 6. 文字与交付口径修正

- §2的BLOCKED保留给已证明的外部能力、授权输入或运行环境限制。自身接口误用、装载错误和不忠实fixture属于实现或测试缺陷，应继续修复，不归因于交易所。
- “零改动翻转路径”不适用于所有阻塞。例如替代期权合约可能需要配置或映射调整，应如实写明所需变更与复验范围。
