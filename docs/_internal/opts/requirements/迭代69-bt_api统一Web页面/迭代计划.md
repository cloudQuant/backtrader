## 1. 背景与现状（STATIC，2026-11-11）

### 1.1 为什么有本迭代

按 D63-47，五个服务的页面原本分散在五个迭代里：Gateway 在 63.14，Risk 在 64.13，Execution 在 65.09a，Runtime 在 66.12，Monitor 在 68.06a。迭代 63 收尾时，63.14 的页面没有交付。用户决定不把它放进某一个现有迭代，而是新开一个迭代，把五个服务的功能放进同一个页面，由 bt_api_py 维护，能单独使用，AFI 只做集成（[需求原文](需求原文.md)）。

### 1.2 现在源码里有什么

### 1.3 冲突与不足

1. **D63-47 写的是五套可分别启动的页面，U69-2 要一个页面。** 各迭代计划里的页面步骤（64.13、65.09a、66.12、68.06a 以及 63.14）都是按“各自独立”写的。
2. **五个服务不一定同时部署。** Risk、Execution、Monitor 是可选组件，开启的前提是 Gateway 开启；Runtime 是独立的。一个页面必须能在只开了其中一部分服务时正常使用。
3. **维护归属。** 共同合同 §2.13.1 写的是“未来 AFI 通过显式路由/组件及 API 适配集成”，没有说页面源码放在哪个仓。U69-5 明确放在 bt_api_py 一侧，AFI 不保留自己的一份。
4. **现有雏形在 Gateway 仓里。** 如果统一页面放在 bt_api_py 主仓，雏形要迁移；如果留在 Gateway 仓，Gateway 包就要装着其他四个服务的页面。
5. **AFI 里已有一套 Gateway 操作入口和策略进程监督的实现**（共同合同 §2.13.1 表格末行）。集成时不能同时存在两个下命令的入口。

## 2. 目标、非目标与规则

### 2.1 目标

1. **一个页面。** 一个前端应用，里面有 Gateway、Risk、Execution、Runtime、Monitor 五个功能区；每个区能做的事按 D63-47 的表（共同合同 §2.13）。
2. **能单独使用。** 在 bt_api_py 一侧有可独立启动的本机 Web 入口，不依赖 AFI，运行时不依赖 Node。
3. **部分部署可用。** 没有部署或没有开启的服务，对应功能区明确显示“未启用”，不报错，也不显示看起来正常的假数据。
4. **AFI 只集成。** 提供宿主适配合同（接口地址、认证回调、路由前缀、主题由宿主注入）和集成说明；源码与发行都在 bt_api_py 一侧，AFI 使用带版本的构建产物。
5. **承接各迭代的页面部分。** 63.14 的页面，以及 64.13、65.09a、66.12、68.06a 的页面部分，由本迭代交付；各服务的版本化接口仍由各自的迭代交付。

### 2.2 非目标

- 不给任何服务增加新的业务能力：页面只调用所属服务已经提供的操作。不新增绕过 Risk 的人工下单入口。
- Monitor 区没有任何写操作。
- 本迭代不修改、不部署 AFI；不做 AFI 的单点登录。
- 默认只在本机监听；不默认对外开放。
- 不替代命令行：命令行和页面调用同一组应用操作。

### 2.3 沿用的规则（D63-47，共同合同 §2.13）

- 浏览器不是会话、账本或命令的持有者。刷新、断开、多个标签页不能造成重复执行。
- 写操作由所属服务按可信操作者、目标范围和当前权限校验并持久审计；隐藏按钮不算权限控制。
- 命令带稳定编号和内容摘要；回复丢失时按原编号查询，不由浏览器换一个编号重发。不照搬通用的自动重试。
- 受理、执行中、部分完成、未知、拒绝、已确认分别显示；解除一个原因和“可以交易”分别显示。
- 页面关闭或崩溃不改变交易准入，不连带启停任何服务。
- 浏览器拿不到场所凭据、服务私钥或通用运营凭据。

## 3. 架构（候选，69.01 冻结）

### 3.1 总览

```
浏览器 ──HTTP──> 统一 Web 宿主（bt_api_py，可选组件，本机）
                   ├─ Gateway 区  ──> Gateway 的 Web 适配 ──> Gateway 服务
                   ├─ Risk 区     ──> Risk 的 Web 适配    ──> Risk 服务（可选）
                   ├─ Execution 区──> Execution 的 Web 适配──> Execution 服务（可选）
                   ├─ Runtime 区  ──> Runtime 的 Web 适配 ──> Runtime 服务
                   └─ Monitor 区  ──> Monitor 的 Web 适配 ──> Monitor 服务（可选，只读）
```

- 每个服务的 Web 适配仍属于该服务（由它的迭代交付），只把 HTTP 请求映射到该服务已有的操作；统一宿主把已选用的适配挂在同一个来源下，并提供“哪些功能区可用”的查询。
- 统一宿主不持有任何服务的会话，不直接读写任何 journal，不导入没有选用的服务。
- 前端分四层：功能区的视图与组件、类型与接口客户端、宿主适配、独立运行外壳。AFI 集成时替换的只是宿主适配和外壳。

### 3.2 技术栈

沿用共同合同 §2.13.1 的选型：Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus、Axios，有图表时按需用 ECharts；Web 适配用 FastAPI 的可选模块。版本在 69.01 的兼容矩阵和锁文件里固定。预构建的静态资源随可选的 Web 发行交付。

### 3.3 仓库归属（候选）

| 内容 | 候选位置 | 说明 |
| --- | --- | --- |
| 统一页面的源码与构建产物、统一 Web 宿主 | `bt_api_py` 主仓（推荐） | 符合 U69-5“维护都在 bt_api_py”；主仓本来就依赖各服务包。现有 Gateway 雏形迁入 |
| 各服务的 Web 适配（HTTP → 该服务的操作） | 各服务包 | 适配只认识自己的服务；不随页面搬家 |
| 备选：新建一个只放页面的子仓 | `bt_api/` 下新包 | 页面可以单独发版；多一个仓要维护 |

### 3.4 认证与授权

独立使用时，统一宿主负责浏览器会话，并把会话主体映射到各服务的主体与授权；每个服务仍按自己的登记核验，统一宿主不能替任何服务放行。撤权后下一次调用即被拒绝。具体的登录方式、会话保存、来源限制和防伪造在 69.01 冻结。

### 3.5 与 AFI 的集成

AFI 引入带版本的页面构建产物，实现宿主适配（接口地址、认证回调、路由前缀、主题）。AFI 里现有的 Gateway 操作入口和策略进程监督要列迁移清单，集成后只保留一个下命令的入口。本迭代只交付合同、替身宿主测试和说明，不改 AFI。

## 6. 风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 五个服务的接口进度不一 | Risk、Execution、Runtime、Monitor 的接口都还没有实现 | 功能区各自验收，缺的记 GAP；外壳与 Gateway 区可以先发 |
| “一个页面”被做成耦合 | 一个功能区的故障拖垮其他区；或者统一宿主变成各服务之间的运行依赖 | 功能区之间不共享业务状态；统一宿主不持有服务会话；逐区故障注入 |
| 认证映射出错 | 统一宿主替服务放行，或者把一个服务的权限用到另一个服务 | 每个服务仍自己核验；撤权和跨目标拒绝逐区测试 |
| AFI 侧保留第二个命令入口 | 同一个操作从两处下发 | 迁移清单；集成前不启用 AFI 侧入口 |
| 现有雏形被误当成已交付 | 仓库里已有构建产物 | 本计划 §1.2 已写明它没有验收；69.01 决定迁移还是重写 |

### 7.1 待用户确认（确认前不生效）

1. **“一个页面”的具体形态。** 主会话的理解是：一个前端应用，里面分五个功能区（导航切换）。如果用户的意思是所有内容放在同一屏上，范围会不同。
2. **仓库归属。** §3.3 推荐把页面和统一宿主放在 bt_api_py 主仓；备选是新建只放页面的子仓。
3. **63.14 接口的三处缺口由谁补。** 内置宿主的账户快照、解除者写进 journal、明确的拒绝代码。页面的 Gateway 区需要前两项。候选：随页面转入本迭代（改 Gateway 仓），或者留在迭代 63。
4. **其他迭代的页面步骤是否全部由本迭代取代。** 主会话的理解是页面部分全部转入本迭代，64.13、65.09a、66.12、68.06a 只保留各自的接口部分；这些计划里目前只加了指向本迭代的说明，原文没有删改。
5. **与其他迭代的先后。** 外壳和 Gateway 区只依赖迭代 63 的接口，可以先做；其余功能区要等各自的服务。
