## 1. 背景与现状（STATIC，2026-11-06）

### 1.1 为什么有本迭代

- 用户问启停按钮放在 Gateway、monitor 还是 runtime（原话 1）。控制面分析把三件事分开：进程生命周期、运维控制面与按钮、下单流控制（控制面分析:160-166），建议生命周期由 runtime 的进程监督执行，下单栅栏由 Gateway 执行。
- 用户决定由 runtime 负责启停（U66-1），按钮放在 runtime，提供本地操作命令，以后集成到 ai-for-investor，runtime 作为微服务运行（U66-2）。
- 控制面分析发现：runtime 现在没有进程监督、远程接口和鉴权；BT 示例不处理 SIGTERM，外部停止不走优雅路径（控制面分析:48、:143、:345-346）。本迭代补齐前一部分；后一部分的 SIGTERM 处理已由迭代 62 实施（S-23，U66-15，`56bacb32b`），本迭代只补 runtime 还需要的 BT 侧部分（§5）。
- 用户 2026-11-06 晚又决定了 S-16～S-25（U66-8～U66-17）：runtime 在 direct 部署中也可用；暂停/恢复只在有 Gateway 时提供；不响应时按 DRAIN → SIGTERM → SIGKILL 升级；急停状态归 Gateway，runtime 只经 63.12 的控制端口下达命令；monitor 只观察。

### 1.5 缺口与冲突

1. **没有外部停止通道。** 对策略进程发 SIGTERM 会直接终止，不撤单、不写最终快照、不打印摘要；强杀后活动单留在场所（控制面分析:203）。（更新：迭代 62 `56bacb32b` 已补 SIGTERM/SIGBREAK 入口，§1.3。仍缺：Windows 上没有控制台或 runtime 接管的进程能否收到 CTRL_BREAK 未知，没有不依赖信号的停止通道，D66-05。）
2. **停止请求可能丢失。** `cerebro.run()` 激活之前的 `runstop` 被忽略（§1.3）；启动对账期间的停止要等启动结束。（更新：前半已由迭代 62 的锁存解决；后半仍在，§1.3“启动耗时”，由 B4 处理。）
3. **停止结果拿不到。** 摘要只打印在标准输出里，退出码分不清“干净停止”和“留有活动单”。runtime 重启后接管的进程不是它的子进程，拿不到退出码。（迭代 62 只在标准输出的汇总中加了 `stop_signal`，本项仍在，由 B3 处理。）
4. **Ctrl+C 与停止过程交错。** 第二次 Ctrl+C 会在 `_direct_stop` 等待撤单时抛出 `KeyboardInterrupt`；`_direct_stopping` 已置位，重入只返回旧摘要（STATIC 推断，66.02 用测试确认）。（更新：迭代 62 对 SIGTERM 已做到“重复信号只重复请求”，SIGINT 有意保持不变。runtime 不发 SIGINT，所以本项只影响手工 Ctrl+C，不在本迭代范围，登记给迭代 62 后续。）
5. **runtime 现有代码不是启动路径。** `DirectBacktraderSession` 不进入迭代 62 的 direct 写入模式（§1.2 第 4 项），`validate`/`doctor` 也不认 007 的配置格式。新的进程监督应直接拉起策略目录的 `run.py`，不复用进程内装配（D66-17）。
6. **接口传输与 INV-01 冲突。** 见 §1.4；需要 D66-03。
7. **运行锁不能用来探测。** runtime 若为了判断“是否在运行”去尝试加锁，会和手工启动的策略争锁，使其以 `live_run_active` 失败（INV66-03）。
8. **ai-for-investor 已有一套强杀式启停。** 两个监督者管理同一目录时，运行锁能防止双开，但停止仍会被 AFI 强杀（§10）。
9. **命令行名称。** 迭代 53 已从 BT 移除旧的 `bt-runtime` 入口（`TRADING_SYSTEM_ARCHITECTURE.md:98`）；用户示例里的 `bt-runtime start` 与现有入口 `bt-api-runtime` 不同（D66-16）。

## 2. 目标、非目标与新增规则

### 2.1 目标

1. **进程监督。** runtime 作为常驻服务，登记策略目录，按命令启动、停止、重启策略进程，报告状态与健康，查看日志（U66-1）。
2. **本地操作命令。** 命令行 `bt-api-runtime <子命令>`（名称见 D66-16），在本机操作（U66-2）。
3. **适合集成的服务接口。** 受鉴权的本机接口，命令带幂等号、先审计后执行、结果为有限码；以后由 ai-for-investor 作为客户端调用（U66-2，§4.2）。
4. **优雅停止可达。** BT 策略进程把外部停止请求转为 `cerebro.runstop()` 的入口由迭代 62 提供（S-23，U66-15）；本迭代补 runtime 还需要的部分：启动中途可停、心跳与最终摘要文件、区分结果的退出码、公布停止预算（§5）。
5. **不响应时升级（S-18，U66-10）。** 进程判定为不响应后，Gateway 部署按 DRAIN（经 Gateway 控制端口，该策略范围）→ SIGTERM → SIGKILL 升级；direct 部署没有 Gateway，从 SIGTERM 开始：SIGTERM → SIGKILL。SIGKILL 不早于 BT 公布的停止预算（INV66-10）。进程有响应时的普通停止只是 SIGTERM（优雅停止），不是升级（§3.5）。
6. **暂停/恢复（S-17，U66-9）。** 暂停 = 策略范围 STOP_NEW 或 FREEZE，恢复 = 指定原因号的 RESUME，进程不停；只在有 Gateway 时提供，direct 部署拒绝（D66-06 已定）。
7. **runtime 重启不影响策略。** runtime 退出或崩溃不终止策略进程，重启后核对身份再接管（D66-10）。
8. **跨平台。** Windows 11、Ubuntu、macOS 三个平台行为一致或明确报告差异。
9. **验收。** INTEGRATION_SIM（真实子进程）三平台，SimNow 上用 direct 示例走通启动、停止、重启和 runtime 重启接管。

### 2.2 非目标

- runtime 不在下单路径上：不发送、不撤销、不修改订单，不持有凭据值或 provider 会话（INV66-01）。
- 不做急停状态与执行：它们归 Gateway（S-19，U66-11；63 §3.17）。不做 Gateway 控制端口与 runtime principal 的权限：它们在 63.12 实现（原话 7、U63-4），本迭代只做控制端口的客户端，不改 `bt_api_gateway`。
- 不做 Gateway 租约过期自动 DRAIN（S-25，U66-17，归 63.12，依赖 63.11）；runtime 不配置、不触发，只显示。
- 不接收 monitor 的命令，不以 monitor 控制台为命令前端（S-20，U66-12）。不增加“策略 × 合约”范围（S-22，U66-14）；runtime 只用策略范围。
- 不做 SIGTERM 处理器本身（迭代 62 已做，S-23）；不改 SIGINT 行为（§1.5 第 4 项）。
- 不做自成交、风控检查（U66-7、S-01）；不做平仓按钮（D66-20）。
- 不做图形界面；ai-for-investor 的集成本身不在本迭代（D66-19）。
- 不做远程（跨主机）控制、集群或高可用；一台主机一个 runtime 实例。
- 不做定时启停、交易日历驱动的自动开机（以后另议）。
- 本迭代缺省不监督 Gateway、risk、execution、monitor 等服务进程（D66-02）。
- 不改 direct 停止语义（D62-19）；不为 direct 增加急停状态（S-23）。
- 不改迭代 52 的装配模块（D66-17）；不做生产账户验证。

## 3. 设计

### 3.1 总览

```text
操作者 ──CLI──┐                        bt_api_runtime 服务（每主机一个）
以后 AFI ──API─┼──▶ 鉴权 ─▶ 命令台账 ─▶ 监督器 ──spawn/信号/停止请求──▶ 策略进程 ×N（run.py，BT）
              │       （SQLite）        │  ▲                               ├ 写 state/run_status.json（心跳）
              │                         │  └──── 读状态文件、PID 身份 ───────┤ 写 state/last_run.json（最终摘要）
              │                         │                                   └ SIGTERM/停止请求 → cerebro.runstop()（迭代 62 stop_on_terminate）→ _direct_stop
              │                         ├─（仅 Gateway 部署，66.07）Gateway 控制端口（63.12）：策略范围 STOP_NEW/FREEZE/DRAIN/RESUME
              │                         └─（可选）事件 → monitor 遥测（仅 Gateway 部署，S-09；monitor 只观察，S-20）
```

文件名与字段在 66.01 冻结。runtime 进程本身不连交易所、不连 Gateway 的交易端口。

### 3.2 策略单元与登记

- 一个策略单元 = 一个策略目录（`config.yaml` + `run.py` + `state/` + `logs/`），由 runtime 配置登记（§6），不从目录名推断。
- 身份取自 `state/identity.json` 的 UUID（经 `backtrader.live_state` 的只读接口，不自行解析）。没有该文件时状态为 `NOT_INITIALIZED`，只能经 D66-12 的首次初始化入口启动。主机或目录与身份不符时报告 `identity_mismatch`，提示运营执行 `live_state rebind`（INV66-08）。
- 两个登记指向同一目录、或两个目录有相同 UUID（复制目录）时，登记失败（`duplicate_strategy_dir`、`duplicate_strategy_uuid`）。
- 模式 `access: direct | gateway` 写在登记里。direct 策略按 D66-13 检查同账户哈希的并发；该检查只覆盖本 runtime 管理的进程，不证明没有其他写者（INV-08）。

### 3.3 单元状态机（runtime 视角）

`NOT_INITIALIZED` / `STOPPED` → `STARTING`（已拉起，等待 BT 报告 run_id）→ `RUNNING`（BT 心跳正常；子阶段 RECONCILING、WARMUP、LIVE 由 BT 报告）→ `STOPPING`（已发停止请求，按 §3.5 升级）→ 终态之一：`STOPPED`（BT 摘要 STOPPED）、`STOPPED_WITH_WORKING_ORDERS`、`STOPPED_WITH_WRITE_IN_FLIGHT`、`BLOCKED`（启动被 BT 拒绝，带 BT 的有限码）、`CRASHED`（非零退出且无摘要）、`KILLED`（runtime 强杀）、`LOST`（接管的进程消失且无摘要）。另有 `UNMANAGED_RUNNING`：BT 状态文件显示在运行、PID 存活，但不是本 runtime 拉起的（例如手工运行）；对它只允许 `status`，停止需显式 `--adopt`（D66-10 一并决定）。

“暂停”不是进程状态：它是 Gateway 中策略范围的急停原因，runtime 只显示从 Gateway 读到的原因列表（66.07）。

### 3.4 启动

1. 鉴权与授权；写命令台账。
2. 检查（全部只是提示，INV66-07）：单元未在运行；`state/identity.json` 可读且与目录一致；direct 同账户并发（D66-13）；策略自己的 `run.py --dry-run` 通过（子进程，离线）；Gateway 部署时读取 Gateway 状态（就绪、该策略 principal 已登记，D63-13）；Gateway 若声明启用了 risk 或 execution，则只报告它们的就绪状态，查不到时标 `NOT_CHECKED`，不阻止启动（BT/SDK 在组件不可用时自己 fail-closed，INV-02）。
3. 拉起：工作目录为策略目录；参数来自登记（缺省追加 `--run-seconds 0`，见 §6）；传入 `--run-id` 与 BT 状态文件路径约定；标准输出与错误写到 runtime 的运行目录文件（不用管道，见 §3.10）；环境变量按白名单构造（D66-11）。
4. 记录 PID、创建时间、命令行摘要、run_id；等待 BT 状态文件出现该 run_id。BT 进入 RECONCILING 之后，`start` 命令记为 `APPLIED`；进程以退出码 2 结束则记为 `BLOCKED` 并附 BT 的有限码。超过 `start_timeout_s` 仍无状态文件时记为 `UNKNOWN`，进程不被自动杀掉。
5. 不自动加 `--first-init`（INV66-08）。

### 3.5 停止与不响应时的升级（S-18 已由用户决定，U66-10）

用户决定的次序只针对**不响应**的进程：Gateway 部署 DRAIN → SIGTERM → SIGKILL；direct 部署从 SIGTERM 开始。进程有响应时，停止就是迭代 62 的优雅停止（一次 SIGTERM），不经过升级。所以一次停止命令分两段：A 普通停止，E 升级；“怎样判定不响应”是本计划的设计（待审阅）。

**A. 普通停止**

| 步骤 | direct 部署 | Gateway 部署 | 记录 |
| --- | --- | --- | --- |
| A0 判定 | PID 身份吻合且心跳新鲜（不超过 3 个 `heartbeat_interval_s`）→ 进入 A1；心跳已过期（`STALE`）→ 直接进入 E 段。`STARTING` 阶段尚无状态文件时，在 `start_timeout_s` 内按有响应处理 | 同左 | 命令 CLAIMED；记录判定依据 |
| A1 | 发优雅停止请求：POSIX 只对主进程 PID 发 SIGTERM（不发给进程组，避免 62.08 示例的 Gateway 子进程被同时终止）；Windows 发 CTRL_BREAK_EVENT 或写停止请求文件（D66-05）。迭代 62 的 `stop_on_terminate` 把它转为 `runstop()` | 同左 | 记录 `t_term`（本次停止第一次发出 SIGTERM 或停止请求的时刻，INV66-10 的起算点） |
| A1～A2 | BT：`runstop` → `_direct_stop`：停写，撤本策略活动单，等待，写最终快照与摘要 | 同左（撤单经 Gateway） | 读心跳中的 `STOPPING` 与进度 |
| A2 = `t_term` + max(`graceful_timeout_s`, BT 公布的预算 + 余量) | 进程已退出 → 结束；仍未退出 → 判定为不响应，进入 E 段 | 同左 | 记录“停止超时” |

**E. 不响应时的升级（S-18）**

| 步骤 | Gateway 部署 | direct 部署 | 记录 |
| --- | --- | --- | --- |
| E1 DRAIN | 经 Gateway 控制端口（63.12），以 runtime principal（D66-08）对该策略 UUID 下达 DRAIN；Gateway 拒新单，按归属账本撤该策略的活动单，不需要策略进程配合（63 §3.17）。等到 Gateway 返回 APPLIED、PARTIAL（附清单）、REJECTED 或 UNKNOWN，最长 `drain_timeout_s`。Gateway 状态显示该策略已有生效的 DRAIN 原因（例如 S-25 的租约过期 DRAIN）时不再新增原因，记录已有原因号并等其进度 | 跳过：没有 Gateway，没有急停状态（S-23 a） | 原因号、结果写入台账。runtime 下达的原因须运营 RESUME（63 §3.17“解除”；S-21 的自动解除只适用于 Gateway 自身触发的原因） |
| E2 SIGTERM | 对主进程发 SIGTERM（Windows 同 A1）。A1 已发过时，这是重复请求：迭代 62 的处理器只重复请求，不打断进行中的停止 | 从这里开始；A1 已发过时同左 | 如为本次第一次 SIGTERM，记 `t_term` |
| E3 SIGKILL | 不早于 max(E2 + `kill_timeout_s`，`t_term` + BT 公布的预算)（INV66-10）：强制终止进程树（POSIX：对进程组 SIGKILL；Windows：Job Object 或 `taskkill /T /F`，D66-05） | 同左 | `KILLED` |
| 进程退出后 | 读最终摘要；没有摘要按 INV66-04 报告。DRAIN 原因保留在 Gateway：策略重启后可以启动、对账和撤单，但新单要等运营 RESUME | 读最终摘要；强杀后活动单可能留在场所，下次启动按 D62-16 接管后再撤 | 命令结果 |

- E1 失败（控制端口不可达、拒绝、超时或结果不明）时，以有限码记入台账（如 `kill_switch_owner_unavailable`、`kill_switch_rejected:<码>`、`kill_switch_unknown`），升级继续到 E2，不因 Gateway 不可用而卡住停止，也不静默跳过。Gateway 不可用时本来就不能经 Gateway 撤单（63 §3.12“Gateway 宕机且有活动委托”行）。
- 迭代 62 的在途写入栅栏：`_direct_stop` 对已提交的结算确认最多等 `direct_stop_write_timeout`（35 秒），在此之前强杀可能中断一笔已提交的写入，结果要靠下次启动对账（`_btapi_direct_mode.py:3264-3275`）。所以 E3 不得早于 BT 公布的预算（INV66-10）；摘要为 `STOPPED_WITH_WRITE_IN_FLIGHT` 时如实报告，不当作干净停止。
- 卡住的 `next()`：`runstop` 只置停止事件，主循环要等 `next()` 返回才检查（`runnext.py:380-383`）。心跳线程独立于主循环，所以这种进程在 A0 仍判为有响应，A2 超时后进入 E 段：Gateway 部署由 E1 的 DRAIN 撤单，不需要进程配合；direct 部署只能在 E3 强杀。整个进程停住（心跳也不再更新）时，A0 直接进入 E 段。
- 启动对账期间收到停止：迭代 62 的锁存使 `runstop` 在运行作用域打开后立即生效，但 `_direct_start` 仍要跑完全部启动步骤（§1.3“启动耗时”）；BT 应在启动步骤之间检查停止请求并放弃启动（§5.2 B4）。
- `stop --force`：跳过 A 段与各段等待，要求 operator 以上角色并写明理由。Gateway 部署仍先下达 E1 的 DRAIN（只等“已受理”，不等撤完），随即 E3；direct 部署直接 E3。它是 INV66-10 唯一的例外。`stop --all`：对所有运行单元并行执行。
- 幂等：重复的停止命令返回同一结果；BT 侧 `_direct_stop` 重入返回原摘要（`:3136-3137`）；runtime 重启后按持久化的步骤与时刻继续，不重复下达已受理的 DRAIN（§3.9）。
- runtime 只在停止类命令中升级（INV66-12）；心跳过期只报告 `STALE`。策略失联时的自动排空是 Gateway 的租约过期 DRAIN（S-25，缺省关闭，63.12），不是 runtime 的功能。

### 3.6 重启、暂停与恢复

- **重启** = 完整停止（§3.5）+ 启动（§3.4），同一命令号下两步各有记录。上一轮为 `STOPPED_WITH_WORKING_ORDERS` 时照常重启（BT 按 D62-16 接管）；上一轮为 `BLOCKED` 时不自动重试。停止经过 E1 的 DRAIN 时，重启照常拉起进程，但命令结果附 `kill_switch_cause_active:<原因号>`，提示新单要等运营 RESUME；runtime 不自动 RESUME（INV66-08）。
- **暂停/恢复**（S-17 已定，U66-9；D66-06 已定）：只在 `access: gateway` 时提供，经 Gateway 控制端口（63.12）提交策略范围的 STOP_NEW（暂停开仓）或 FREEZE（`--freeze`，冻结），恢复时提交指定原因号的 RESUME；进程不停。动作、范围、原因号与结果（APPLIED、PARTIAL、REJECTED、UNKNOWN）只用 63.02 在 `bt_api_base` 定义的统一急停词汇（63 §3.19 第一行；64.02 的 `KillSwitchCommand` 引用同一词汇；S-24，INV66-11）。direct 部署返回 `pause_requires_gateway`。控制端口不可达、runtime principal 未登记或无权时，返回 `kill_switch_owner_unavailable` 或 Gateway 的拒绝码，不静默跳过。
- **恢复的权限**：按 63 §3.17，RESUME 只能由运营执行，一次解除一个原因号，在哪个范围下达就在哪个范围解除。runtime 的 `resume` 怎样满足“只能由运营执行”见 D66-08（候选）；在它决定之前，66.07 只实现暂停与升级 DRAIN，`resume` 返回 `resume_requires_operator_principal`。
- runtime 不持有急停状态；`status` 显示的急停原因（范围、模式、来源、原因号、DRAIN 进度、是否会在条件恢复后自动解除）是从 Gateway 读来的，读不到时显示 `UNKNOWN`（控制面分析:279、:311）。来源为 Gateway 自身的原因（`monitor_required` 下的存活丢失、S-25 的租约过期 DRAIN）照样显示；哪些自动解除由 Gateway 账户配置决定（S-21，63 D63-33），runtime 不改变。

### 3.7 状态、健康与日志

- **心跳与健康**：BT 每 `heartbeat_interval_s` 原子写一次状态文件（§5.2 B2）。runtime 计算：心跳超过 3 个间隔未更新为 `STALE`；PID 不存在为进程消失；心跳只说明进程活着，不说明可交易、订单完成或账户齐全（控制面分析 §2.1；架构文档:88）。
- **主循环进度**：状态文件另有主循环最后推进时间。休市时没有行情，主循环不推进是正常的，所以它只用于展示，不触发自动升级。
- **行情 LIVE**：取自 BT 报告的各数据 `trade_qualification()` 与预热状态；runtime 自己不连行情。
- **最后错误**：只显示 BT 写出的有限码与时间；详细文本留在本地日志。
- **日志**：`logs <单元>` 显示 runtime 捕获的标准输出/错误尾部（有界），并列出 TradeLogger 目录（`logs/<配置名>/<时间戳>/`）的路径；接口返回的日志有大小上限，只对 viewer 以上角色开放（D66-14）。runtime 对捕获文件做大小轮转。

### 3.8 鉴权、授权、审计与幂等

- 身份：命令行与接口客户端都映射到一个操作者身份（D66-14 的角色：viewer、operator、admin，按单元授权）。本机命令行的身份来源与接口令牌的发放方式随 D66-03 一起冻结。
- 危险动作（首次初始化、`--force`、`--adopt`、`stop --all`）需要二次确认：服务先返回确认令牌，客户端在有效期内带令牌重发（参照控制面分析:185-188 的 QuantConnect 两次点击）。
- 命令台账（SQLite，`synchronous=FULL`）：命令号（客户端生成，UUID）、操作者、客户端类型、动作、目标单元 UUID 与目录、参数摘要、理由、状态 PENDING→CLAIMED→APPLIED/REJECTED/UNKNOWN、结果（BT 摘要或有限码）、时间；状态机参照 `mon: control.py:60-76`。
- 每个单元同时只有一个进行中的生命周期命令；`stop` 可以抢占尚未拉起进程的 `start`。
- 审计只追加，不记录凭据、账号和令牌；`audit` 子命令按单元和时间查询。

### 3.9 runtime 自身的持久化与重启

- runtime 的家目录（§6）保存：单元登记快照、运行记录（PID、创建时间、命令行摘要、run_id、日志路径）、命令台账、升级时间线进度。单实例：家目录上的独占锁，第二个 runtime 拒绝启动。
- runtime 退出（正常或崩溃）不停止策略（D66-10，INV66-05）。重启时逐个核对运行记录：身份全部吻合才接管；处于 STOPPING 的单元按持久化的步骤（A1、A2、E1～E3）与 `t_term` 等时刻继续，不重复已执行的步骤（已受理的 DRAIN 不再下达）；CLAIMED 的命令无法判断结果时记为 UNKNOWN，等运营处理。
- 接管的进程不是 runtime 的子进程，拿不到退出码，所以终态只能来自 BT 的最终摘要文件（§5.2 B3）。

### 9.2 未决问题（UNKNOWN）

1. Windows 11 上，`CREATE_NEW_PROCESS_GROUP` 与 `CREATE_NO_WINDOW`/`DETACHED_PROCESS` 组合时 CTRL_BREAK_EVENT 能否送达；runtime 作为服务运行（无控制台）时呢。
2. BT 主线程阻塞在 C 调用（如等待行情的阻塞读）时，信号处理器多久能运行；`next()` 卡住时停止的实际延迟。
3. 启动对账期间的停止延迟（§1.3 推断）在 SimNow 交易时段的实际值。
4. 断线或进程被杀后，CTP 是否保留活动委托（63 计划:233、控制面分析:347）。
5. 状态文件在 Windows 上被杀毒软件占用时 `os.replace` 的失败率与重试策略。
6. ai-for-investor 希望用 HTTP 还是 SDK 客户端调用 runtime（迭代 10 规格之后未核对）。
7. 一台主机上要管理的策略数量上限；runtime 的心跳轮询开销。
8. Windows 上令牌文件权限的检查方式（与 65 计划 §8.2 第 6 项相同问题）。
9. 迭代 62 的 SIGTERM 处理只有 UNIT/FAKE 证据（子进程测试在 win32 上跳过），没有在 SimNow 上发送过 SIGTERM（`56bacb32b` 提交说明；007 README:203）；Windows 上 CTRL_BREAK 经该处理器的实际效果未知。
10. 63.12 的控制端口对 DRAIN 的“已受理”与“撤完”的返回时机、PARTIAL 的清单格式（E1 的等待依据），在 63.01 冻结前未知。

SimNow 场景（66.10，需用户授权，结果只说明 SimNow 行为）：

1. `serve` 启动 runtime；`register` 一个 direct 示例（已初始化的目录）；`start`：状态依次为 STARTING → RUNNING（RECONCILING → WARMUP → LIVE）。
2. 策略挂出一笔远价限价单后 `stop`：BT 撤本策略的单，摘要 STOPPED，runtime 记 APPLIED；账户无该策略的活动单。
3. 再 `start`，运行中 `kill -9` runtime，确认策略照常运行；重启 runtime，单元被接管，`status` 正常。
4. `restart`：完整停止后重新启动，启动对账通过。
5. 用一个故意卡住 `next()` 的测试策略（只在 SimNow 账户、远价单）验证 direct 升级（SIGTERM → SIGKILL）、E3 强杀与 `KILLED` 报告；下次启动按 D62-16 接管并撤单。
6. 同一账户哈希的第二个 direct 单元启动被拒（D66-13）。
7. Gateway 场景（63.09 与 66.07 之后）：`pause` → Gateway 拒绝该策略开仓、放行撤单；恢复按 D66-08（`resume --cause` 或运营工具 RESUME）；卡住 `next()` 的策略按 DRAIN → SIGTERM → SIGKILL 停止，DRAIN 撤销它的远价单而不碰同账户其他策略；重启后在运营 RESUME 之前不能下新单。
