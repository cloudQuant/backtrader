## 1. 背景与现状（STATIC，2026-11-06）

### 1.1 为什么有本迭代

- 用户问启停按钮放在 Gateway、monitor 还是 runtime（原话 1）。控制面分析把三件事分开：进程生命周期、运维控制面与按钮、下单流控制（控制面分析:160-166），建议生命周期由 runtime 的进程监督执行，下单栅栏由 Gateway 执行。
- 用户决定由 runtime 负责启停（U66-1），按钮放在 runtime，提供本地操作命令，以后集成到 ai-for-investor，runtime 作为微服务运行（U66-2）。
- 控制面分析发现：runtime 现在没有进程监督、远程接口和鉴权；BT 示例不处理 SIGTERM，外部停止不走优雅路径（控制面分析:48、:143、:345-346）。本迭代补齐前一部分；后一部分的 SIGTERM 处理已由迭代 62 实施（S-23，U66-15，`56bacb32b`），本迭代只补 runtime 还需要的 BT 侧部分（§5）。
- 用户 2026-11-06 晚又决定了 S-16～S-25（U66-8～U66-17）：runtime 在 direct 部署中也可用；暂停/恢复只在有 Gateway 时提供；不响应时按 DRAIN → SIGTERM → SIGKILL 升级；急停状态归 Gateway，runtime 只经 63.12 的控制端口下达命令；monitor 只观察。

### 1.5 缺口与冲突

1. **没有外部停止通道。** 对策略进程发 SIGTERM 会直接终止，不撤单、不写最终快照、不打印摘要；强杀后活动单留在场所（控制面分析:203）。（更新：迭代 62 `56bacb32b` 已补 SIGTERM/SIGBREAK 入口，§1.3。仍缺：Windows 上没有控制台或 runtime 接管的进程能否收到 CTRL_BREAK 未知，没有不依赖信号的停止通道，D66-05。）
2. **停止请求可能丢失。** `cerebro.run()` 激活之前的 `runstop` 被忽略（§1.3）；启动对账期间的停止要等启动结束。（更新：前半已由迭代 62 的锁存解决；后半仍在，§1.3“启动耗时”，由 B4 处理。）
3. **停止结果拿不到。** 摘要只打印在标准输出里，退出码分不清“干净停止”和“留有活动单”。runtime 重启后接管的进程不是它的子进程，拿不到退出码。（迭代 62 只在标准输出的汇总中加了 `stop_signal`，本项仍在，由 B3 处理。）
4. **Ctrl+C 与停止过程交错。** 第二次 Ctrl+C 会在 `_direct_stop` 等待撤单时抛出 `KeyboardInterrupt`；`_direct_stopping` 已置位，重入只返回旧摘要（STATIC 推断，66.02 用测试确认）。（更新：迭代 62 对 SIGTERM 已做到“重复信号只重复请求”，SIGINT 有意保持不变。runtime 不发 SIGINT，所以本项只影响手工 Ctrl+C，不在本迭代范围，登记给迭代 62 后续。）
5. **runtime 现有代码不是启动路径。** `DirectBacktraderSession` 不进入迭代 62 的 direct 写入模式（§1.2 第 4 项），`validate`/`doctor` 也不认 007 的配置格式。新的进程监督应直接拉起策略目录的 `run.py`，不复用进程内装配（D66-17）。
6. **接口传输与 INV-01 冲突。** 见 §1.4；需要 D66-03。
7. **运行锁不能用来探测。** runtime 若为了判断“是否在运行”去尝试加锁，会和手工启动的策略争锁，使其以 `live_run_active` 失败（INV66-03）。
8. **ai-for-investor 已有一套强杀式启停。** 两个监督者管理同一目录时，运行锁能防止双开，但停止仍会被 AFI 强杀（§10）。
9. **命令行名称。** 迭代 53 已从 BT 移除旧的 `bt-runtime` 入口（`TRADING_SYSTEM_ARCHITECTURE.md:98`）；用户示例里的 `bt-runtime start` 与现有入口 `bt-api-runtime` 不同（D66-16）。

## 2. 目标、非目标与新增规则

### 2.1 目标

1. **进程监督。** runtime 作为常驻服务，登记策略目录，按命令启动、停止、重启策略进程，报告状态与健康，查看日志（U66-1）。
2. **本地操作命令。** 命令行 `bt-api-runtime <子命令>`（名称见 D66-16），在本机操作（U66-2）。
3. **适合集成的服务接口和独立前端。** 首期交付 runtime 独立前端（D66-19、D63-47）；CLI、前端及未来 ai-for-investor 复用同一受鉴权的本机服务合同，命令带幂等号、先审计后执行、结果为有限码。技术栈按跨迭代合同 §2.13.1 选用，D66-03 传输仍待决定（§4.2）。
4. **优雅停止可达。** BT 策略进程把外部停止请求转为 `cerebro.runstop()` 的入口由迭代 62 提供（S-23，U66-15）；本迭代补 runtime 还需要的部分：启动中途可停、心跳与最终摘要文件、区分结果的退出码、公布停止预算（§5）。
5. **不响应时升级（S-18，U66-10）。** 进程判定为不响应后，Gateway 部署按 DRAIN（经 Gateway 控制端口，该策略范围）→ SIGTERM → SIGKILL 升级；direct 部署没有 Gateway，从 SIGTERM 开始：SIGTERM → SIGKILL。SIGKILL 不早于 BT 公布的停止预算（INV66-10）。进程有响应时的普通停止只是 SIGTERM（优雅停止），不是升级（§3.5）。
6. **暂停/恢复（S-17，U66-9）。** 暂停 = 策略范围 STOP_NEW 或 FREEZE，恢复 = 指定原因号的 RESUME，进程不停；只在有 Gateway 时提供，direct 部署拒绝（D66-06 已定）。
7. **runtime 重启不影响策略。** runtime 退出或崩溃不终止策略进程，重启后核对身份再接管（D66-10）。
8. **跨平台。** Windows 11、Ubuntu、macOS 三个平台行为一致或明确报告差异。
9. **验收。** INTEGRATION_SIM（真实子进程）三平台，SimNow 上用 direct 示例走通启动、停止、重启和 runtime 重启接管。

### 2.2 非目标

- runtime 不在下单路径上：不发送、不撤销、不修改订单，不持有凭据值或 provider 会话（INV66-01）。
- 不做急停状态与执行：它们归 Gateway（S-19，U66-11；63 §3.17）。不做 Gateway 控制端口与 runtime principal 的权限：它们在 63.12 实现（原话 7、U63-4），本迭代只做控制端口的客户端，不改 `bt_api_gateway`。
- 不做 Gateway 租约过期自动 DRAIN（S-25，U66-17，归 63.12，依赖 63.11）；runtime 不配置、不触发，只显示。
- 不接收 monitor 的命令，不以 monitor 控制台为命令前端（S-20，U66-12）。不增加“策略 × 合约”范围（S-22，U66-14）；runtime 只用策略范围。
- 不做 SIGTERM 处理器本身（迭代 62 已做，S-23）；不改 SIGINT 行为（§1.5 第 4 项）。
- 不做自成交、风控检查（U66-7、S-01）；不做平仓按钮（D66-20）。
- 本迭代交付 runtime 独立前端；与 ai-for-investor 的实际集成本身不在本迭代（D66-19、D63-47）。历史需求原文对“以后才有界面”的理解由本次用户新决定覆盖，原文保留。
- 不做远程（跨主机）控制、集群或高可用；一台主机一个 runtime 实例。
- 不做定时启停、交易日历驱动的自动开机（以后另议）。
- 本迭代只监督策略进程，不监督 Gateway、Risk、Execution、Monitor 等服务进程（D66-02，用户选 c）。这些服务由各自入口或系统服务管理器运行；仅预留未来服务类型的扩展接口和配置版本，不实现服务单元注册、启停或自动发现启动。服务管理另立需求。
- 不改 direct 停止语义（D62-19）；不为 direct 增加急停状态（S-23）。
- 不改迭代 52 的装配模块（D66-17）；不做生产账户验证。

## 3. 设计

### 3.1 总览

```text
操作者 ──CLI──┐                        bt_api_runtime 服务（每主机一个）
以后 AFI ──API─┼──▶ 鉴权 ─▶ 命令台账 ─▶ 监督器 ──spawn/信号/停止请求──▶ 策略进程 ×N（run.py，BT）
              │       （SQLite）        │  ▲                               ├ 写 state/run_status.json（心跳）
              │                         │  └──── 读状态文件、PID 身份 ───────┤ 写 state/last_run.json（最终摘要）
              │                         │                                   └ SIGTERM/停止请求 → cerebro.runstop()（迭代 62 stop_on_terminate）→ _direct_stop
              │                         ├─（仅 Gateway 部署，66.07）Gateway 控制端口（63.12）：策略范围 STOP_NEW/FREEZE/DRAIN/RESUME
              │                         └─（可选）事件 → monitor 遥测（仅 Gateway 部署，S-09；monitor 只观察，S-20）
```

文件名与字段在 66.01 冻结。runtime 进程本身不连交易所、不连 Gateway 的交易端口。

独立前端与 CLI、未来 AFI 均为 runtime 服务客户端，复用同一版本化接口、身份鉴别、权限、命令台账和审计；页面不自行启动或直接操控策略，也不能绕过后端。前端首期只查看和管理策略生命周期、状态和授权操作；Gateway 暂停/恢复仍经 D66-08/63.12，Monitor 不作控制入口。关闭页面不停止 runtime 或策略，不自动启动其他服务，不自动 RESUME。

前端统一采用 Vue 3、TypeScript、Vite、Vue Router、Pinia、Element Plus 和 Axios，图表按需 ECharts；Web 适配优先 FastAPI，作为可选 Web 依赖，复用 runtime 现有应用操作和中立服务客户端，不另写进程或交易 owner。Node 仅为构建/开发依赖，交付可选安装的预构建静态资源。[跨迭代合同 §2.13.1](../迭代63-Gateway统一转发与多策略共享会话/跨迭代合同与决策.md)记录 ai-for-investor 源码事实和技术选型：复用技术栈并不整包复制其全局 store、路由或认证，也不声称已有通用插件/微前端；后续通过显式路由、组件和 API 适配集成。FastAPI 可选 Web 层不决定 D66-03 的 CLI/本机控制传输，也不将全部控制调用静默改为 HTTP。

AFI 现有 Axios 客户端具备自动重试，不能直接照搬到停止、恢复等命令；超时后的原命令 ID 查询及幂等重试按 runtime 和 Gateway 的已冻结服务语义执行。AFI 的 JWT/RBAC 不自动等于 runtime 或 Gateway 的授权，前端主体和各服务 grant 须有独立可信映射，不共享超权密钥。

### 3.2 策略单元与登记

- 一个策略单元 = 一个策略目录（`config.yaml` + `run.py` + `state/` + `logs/`），由 runtime 配置登记（§6），不从目录名推断。
- 首期的登记、start、stop、status、adopt 等生命周期操作对象仅为策略进程。可在授权范围内读取已选服务状态、通过 Gateway 控制端口请求策略范围暂停或排空；这不是对共享服务的启停管理。策略停止不联动停止共享服务；所选前置服务不可用时按既有 fail-closed/所选组件故障合同报告，不由 runtime 代启动或回退。Risk 保持可选，不建立固定 Gateway → Risk → Execution 启动硬依赖。
- 监督配置与接口只预留未来服务类型的版本化扩展位置；未知或首期不支持的单元类型在登记、校验和操作时明确返回有限拒绝码，不得作为策略解释或自动启动。
- 身份取自 `state/identity.json` 的 UUID（经 `backtrader.live_state` 的只读接口，不自行解析）。没有该文件时状态为 `NOT_INITIALIZED`，只能经 D66-12 的首次初始化入口启动。主机或目录与身份不符时报告 `identity_mismatch`，提示运营执行 `live_state rebind`（INV66-08）。
- 两个登记指向同一目录、或两个目录有相同 UUID（复制目录）时，登记失败（`duplicate_strategy_dir`、`duplicate_strategy_uuid`）。
- 模式 `access: direct | gateway` 写在登记里。direct 策略按 D66-13 检查同账户哈希的并发；该检查只覆盖本 runtime 管理的进程，不证明没有其他写者（INV-08）。

### 3.3 单元状态机（runtime 视角）

`NOT_INITIALIZED`（确认尚未初始化）或 `INITIALIZED_NO_RUN`（身份有效且已核实没有该单元历史 run）或干净 `STOPPED` → `STARTING` → `RUNNING`（BT 心跳正常；RECONCILING、WARMUP、LIVE 为 BT 自报子阶段）→ `STOPPING` → 终态。已有历史但记录缺失、损坏或旧摘要不能匹配时为 UNKNOWN，而非 `INITIALIZED_NO_RUN` 或干净 `STOPPED`；存在未决事项的停止结果分别展示。`BLOCKED` 仅由可核验且匹配本 run 的启动拒绝记录支持，不能单凭退出码 2；无有效摘要时按 INV66-04 报告进程结局及撤单未知。`UNMANAGED_RUNNING` 的接管仍按 D66-10 决定。单元进程状态、命令受理/结果和上次停止结论是独立维度；`RUNNING` 或命令 APPLIED 均不证明账户、对账或交易就绪。

“暂停”不是进程状态：它是 Gateway 中策略范围的急停原因，runtime 只显示从 Gateway 读到的原因列表（66.07）。D65-27/28 的虚拟平仓转换及 STOP_NEW 专门例外由 Gateway 等 owner 按跨迭代合同执行；runtime 只显示 Gateway 权威原因和其公开的转换可用性，缺事实显示 UNKNOWN，不自行判断放行或把普通 OPEN 视作例外。D63-41 的公开默认 getter 查询账户、显式策略 getter 查询策略；下单辅助按策略范围隔离。runtime/监控查询不因此需要重复配置策略资金，策略资金视图未配置仍明确不可用。

**Gateway 断连（D63-03、Q35 已决定）**：策略进程继续运行并等待连接恢复，相关写入不可用且不回退 direct；runtime 在 CLI/前端分别呈现 Gateway 连接、写入可用性与策略进程状态，不能仅因连接断开认定进程退出、自动 stop 或重启。显式用户 stop/restart 及确实发生异常退出时的 D66-09 资格判定不变。场所在途或已有委托在断连期间仍可能成交；不能因失联宣称策略已停止、订单已撤或订单终态。断连时用户请求停止、撤单或状态查询若结果不可证明，保留相应 UNKNOWN/PARTIAL，不宣称撤单完成。连接恢复后展示 Gateway 当前会话的对账、回报补齐与准入结果；runtime 不自行证明已恢复交易、不自动 RESUME、不盲目重发。

### 3.4 启动

1. 鉴权与授权；写命令台账。
2. 硬门禁：目录和身份可用且匹配、没有同单元活动启动或运行；若 D66-13 选 a，还须在本 runtime 管理范围内对同账户哈希做原子检查并预留，连同并发启动、失败释放和崩溃恢复一并冻结，不能仅作提示。首次初始化前身份/账户哈希不可用时只能走经授权的 D66-12 特例，如何防止并发初始化须冻结，不能假定外部手工写者不存在。预检提示：策略自己的 `run.py --dry-run`（子进程，离线）及 Gateway 状态；Gateway 声明的 risk/execution 就绪状态查不到时标 `NOT_CHECKED`。这些提示不代替 BT/SDK/Gateway 的 fail-closed 准入，不授予写权限（INV66-07、INV-02）。
3. 拉起：工作目录为策略目录；参数来自登记（缺省追加 `--run-seconds 0`，见 §6）；传入 `--run-id` 与 BT 状态文件路径约定；标准输出与错误写到 runtime 的运行目录文件（不用管道，见 §3.10）；环境变量按白名单构造（D66-11）。
4. 记录 PID、创建时间、命令行摘要、run_id；等待 BT 状态文件出现该 run_id。BT 进入 RECONCILING 后 `start` 的 `APPLIED` 只表示启动请求已落实及进程已被观察，不代表对账完成或可交易；进程状态与写入阻断原因另行报告。退出码 2 只是观察；只有匹配 run 的可信拒绝记录才可报告受证 `BLOCKED`，无摘要按 INV66-04 报告。超过 `start_timeout_s` 仍无状态文件时记为 `UNKNOWN`，进程不被自动杀掉。
5. 不自动加 `--first-init`（INV66-08）。

### 3.5 停止与不响应时的升级（S-18 已由用户决定，U66-10）

用户决定的次序只针对**不响应**的进程：Gateway 部署 DRAIN → SIGTERM → SIGKILL；direct 部署从 SIGTERM 开始。进程有响应时，停止就是迭代 62 的优雅停止（一次 SIGTERM），不经过升级。所以一次停止命令分两段：A 普通停止，E 升级；“怎样判定不响应”是本计划的设计（待审阅）。

**A. 普通停止**

| 步骤 | direct 部署 | Gateway 部署 | 记录 |
| --- | --- | --- | --- |
| A0 判定 | PID 身份吻合且心跳新鲜（不超过 3 个 `heartbeat_interval_s`）→ 进入 A1；心跳已过期（`STALE`）→ 直接进入 E 段。`STARTING` 阶段尚无状态文件时，在 `start_timeout_s` 内按有响应处理 | 同左 | 命令 CLAIMED；记录判定依据 |
| A1 | 发优雅停止请求：POSIX 只对主进程 PID 发 SIGTERM（不发给进程组，避免 62.08 示例的 Gateway 子进程被同时终止）；Windows 发 CTRL_BREAK_EVENT 或写停止请求文件（D66-05）。迭代 62 的 `stop_on_terminate` 把它转为 `runstop()` | 同左 | 记录 `t_term`（本次停止第一次发出 SIGTERM 或停止请求的时刻，INV66-10 的起算点） |
| A1～A2 | BT：`runstop` → `_direct_stop`：停写，撤本策略活动单，等待，写最终快照与摘要 | 同左（撤单经 Gateway） | 读心跳中的 `STOPPING` 与进度 |
| A2 = `t_term` + max(`graceful_timeout_s`, 已证明预算 + 余量) | 进程已退出 → 结束进程停止阶段，交易清理按实际结果单列；仍未退出 → 判定为不响应，进入 E 段。预算无法证明时可按停止命令的观察超时进入 E1/E2，但不自动执行 E3 | 同左 | 记录“停止超时”与预算证明状态 |

**E. 不响应时的升级（S-18）**

| 步骤 | Gateway 部署 | direct 部署 | 记录 |
| --- | --- | --- | --- |
| E1 DRAIN | 经 Gateway 控制端口（63.12），以 runtime principal（D66-08）对该策略 UUID 下达 DRAIN；Gateway 拒新单，按归属账本撤该策略的活动单，不需要策略进程配合（63 §3.17）。等到 Gateway 返回 APPLIED、PARTIAL（附清单）、REJECTED 或 UNKNOWN，最长 `drain_timeout_s`。已有其他来源的 DRAIN 时记录其原因与进度，但不能把可自动解除的原因当作覆盖整个停止意图的持久屏障；停止专属原因/等效受权屏障的身份、建立、解除和竞争由 63/66 冻结 | 跳过：没有 Gateway，没有急停状态（S-23 a） | 原因号、结果写入台账。runtime 下达的原因须运营 RESUME（63 §3.17“解除”；S-21 的自动解除适用范围以 63 D63-33 及各原因独立合同为准） |
| E2 SIGTERM | 对主进程发 SIGTERM（Windows 同 A1）。A1 已发过时，这是重复请求：迭代 62 的处理器只重复请求，不打断进行中的停止 | 从这里开始；A1 已发过时同左 | 如为本次第一次 SIGTERM，记 `t_term` |
| E3 SIGKILL | 不早于 max(E2 + `kill_timeout_s`，`t_term` + 已证明的完整停止预算)；依 INV66-05/10 验证稳定目标身份、范围与预算。无证明不自动强杀，显式 `--force` 仅按 §3.5 授权例外，不豁免目标身份与范围核验 | 同左 | 成功确认强杀才为 `KILLED`；否则 `UNKNOWN` |
| 进程退出后 | 读最终摘要；没有摘要按 INV66-04 报告。Gateway 按原因和版本保留/解除 DRAIN：策略重启后可以启动、对账和撤单，新单仍受所有适用原因约束；Runtime 自己原因按授权解除，租约原因按 D63-33 | 读最终摘要；强杀后活动单可能留在场所，下次启动按 D62-16 接管后再撤 | 命令结果 |

- E1 失败（控制端口不可达、拒绝、超时或结果不明）时，以有限码记入台账（如 `kill_switch_owner_unavailable`、`kill_switch_rejected:<码>`、`kill_switch_unknown`），升级继续到 E2，不因 Gateway 不可用而卡住停止，也不静默跳过；DRAIN 的结果不明时继续向进程请求停止不等于确认 DRAIN 已生效。Gateway 不可用时本来就不能经 Gateway 撤单（63 §3.12“Gateway 宕机且有活动委托”行）。
- 迭代 62 的在途写入栅栏：`_direct_stop` 对已提交的结算确认最多等 `direct_stop_write_timeout`（35 秒），在此之前强杀可能中断一笔已提交的写入，结果要靠下次启动对账（`_btapi_direct_mode.py:3264-3275`）。所以 E3 不得早于 BT 公布的预算（INV66-10）；摘要为 `STOPPED_WITH_WRITE_IN_FLIGHT` 时如实报告，不当作干净停止。
- 卡住的 `next()`：`runstop` 只置停止事件，主循环要等 `next()` 返回才检查（`runnext.py:380-383`）。心跳线程独立于主循环，所以这种进程在 A0 仍判为有响应，A2 超时后进入 E 段：Gateway 部署由 E1 的 DRAIN 撤单，不需要进程配合；direct 部署只能在 E3 强杀。整个进程停住（心跳也不再更新）时，A0 直接进入 E 段。
- 启动对账期间收到停止：迭代 62 的锁存使 `runstop` 在运行作用域打开后立即生效，但 `_direct_start` 仍要跑完全部启动步骤（§1.3“启动耗时”）；BT 应在启动步骤之间检查停止请求并放弃启动（§5.2 B4）。
- `stop --force`：跳过 A 段与各段等待，要求 operator 以上角色并写明理由。Gateway 部署仍先下达 E1 的 DRAIN（只等“已受理”，不等撤完），随即 E3；direct 部署直接 E3。它是 INV66-10 唯一的例外。`stop --all`：对所有运行单元并行执行。
- 幂等：重复的停止命令返回同一结果；BT 侧 `_direct_stop` 重入返回原摘要（`:3136-3137`）；runtime 重启后按持久化的步骤与时刻继续，不重复下达已受理的 DRAIN（§3.9）。
- runtime 只在停止类命令中升级（INV66-12）；心跳过期只报告 `STALE`。策略失联时的自动排空是 Gateway 的租约过期 DRAIN（S-25，缺省关闭，63.12），不是 runtime 的功能。

**正常停止的 Execution 母单（2026-11-08 用户决定）：** 受权停止该策略时取消其未完成母单余量并尝试撤销场内子单；须经受权合同建立对新切片/内部转移的停止屏障，按原身份跟踪请求；屏障建立失败或不可证时禁止声称交易侧已停止，但仍按进程停止合同请求优雅退出，并继续按原身份处理在途状态、部分撤单、迟到成交和 UNKNOWN。只有权威终态与累计成交对齐后才能报告母单结束；Gateway 不可达或结果未知时如实报告部分完成/UNKNOWN，不因进程退出宣称成功。策略进程退出与交易侧清理分别报告，不联动停止共享服务。用户后续取消了本期重启后提示或操作原母单余量重新下单的功能；重启不复活已取消母单，原订单和实际成交继续按权威事实对账，见共同合同 §2.33、65 计划 §3.8a。

### 3.6 重启、暂停与恢复

- **重启** = 完整停止（§3.5）+ 启动（§3.4），同一命令号下两步各有记录。上一轮为 `STOPPED_WITH_WORKING_ORDERS` 时进程启动与订单对账、可交易分别报告（BT 按 D62-16 接管）；已选 Execution 时按 §3.5 保持取消与未决跟踪，不因启动成功重新下单；上一轮为 `BLOCKED` 时不自动重试。停止经过 E1 的 DRAIN 时，重启照常拉起进程，但命令结果附 `kill_switch_cause_active:<原因号>`，提示新单要等运营 RESUME；runtime 不自动 RESUME（INV66-08）。
- **策略异常退出自动重启（D66-09，Q31 已决定）**：缺省关闭；可按策略显式开启有限次数、带退避间隔的重启。仅在旧目标策略进程身份及实际退出已被可靠确认、相关未决写入和 UNKNOWN 均不存在或已按各 owner 的合同解决、启动硬门禁满足时才允许自动尝试；无足够证据则不重启并展示原因，不能把异常退出本身视作无未决的证明。`BLOCKED`、相关在途写入/UNKNOWN、无法确认旧进程已退出或资格不可证明均禁止自动重启；心跳 `STALE`、PID 复用、控制超时不能充作退出证据，也不能拉起第二实例。自动资格按目标策略的相关作用域检查，不因其他策略的无关 UNKNOWN 扩大成全账户自动阻断；独立的账户级硬门禁仍按原合同执行。
- 生命周期记录区分异常退出、用户正常停止、显式 `restart` 与 `--force` 退出；用户正常停止不触发自动重启，显式停止须撤销尚待执行的自动尝试，停止与自动启动竞争须原子裁决、校验当前生命周期代际，旧定时回调和旧进程结果不能在停止后重新拉起。自动尝试前再次验证退出、权限、门禁、代际及预算；持久记录次数和退避计划，runtime 重启不能无限重置次数；时钟/boot 不可比较时不得缩短退避或推断已到期，按已冻结恢复合同报告 UNKNOWN。有限次数、间隔和计数窗口的具体字段/边界由 66.01/66.04 冻结；无配置 `never`，开启但缺少或非法的参数明确拒绝，不能静默关闭或无界重启。
- **存在急停时自动启动（2026-11-08 用户已决定）**：策略已启用异常自动重启且旧进程退出、相关未决/UNKNOWN、授权及其他硬门禁均满足时，即使 Gateway 仍有适用 DRAIN、FREEZE 或 STOP_NEW，也允许启动策略进程并展示阻断原因；原因继续按 Gateway 自身规则生效，不能绕过限制下单，不自动 RESUME。急停本身不能一概当成禁止进程启动的 BLOCKED；其他真正的启动硬门禁不受影响。
- 自动重启资格与手动启动/恢复合同分别判断；自动重启是新一轮策略进程启动，按原身份执行 BT/SDK 对账，不证明可交易，也不自动 RESUME 或解除 Gateway 急停/UNKNOWN。D66-02 只管理策略进程，不代启 Gateway、Risk、Execution 或 Monitor；该策略进程政策与迭代 65 Q29 的 Execution 服务已重启后母单恢复政策不同。
- **暂停/恢复**（S-17 已定，U66-9；D66-06 已定）：只在 `access: gateway` 时提供，经 Gateway 控制端口（63.12）提交策略范围的 STOP_NEW（暂停开仓）或 FREEZE（`--freeze`，冻结），恢复时提交指定原因号的 RESUME；进程不停。动作、范围、原因号与结果（APPLIED、PARTIAL、REJECTED、UNKNOWN）只用 63.02 在 `bt_api_base` 定义的统一急停词汇（63 §3.19 第一行；64.02 的 `KillSwitchCommand` 引用同一词汇；S-24，INV66-11）。direct 部署返回 `pause_requires_gateway`。控制端口不可达、runtime principal 未登记或无权时，返回 `kill_switch_owner_unavailable` 或 Gateway 的拒绝码，不静默跳过。
- **恢复的权限（D66-08，Q20 已决定）**：由已授权运营人员主动请求，runtime 专用 principal 以有限代理身份转达；Gateway 验证可信操作者、代理授权及该目标策略和指定原因的作用域，审计为“运营经 Runtime”。只可逐项解除该 runtime principal 为目标策略设置的原因，不解除其他来源原因、UNKNOWN 或系统阻断；不持有完整运营 principal，不自动 RESUME，也不在启动或重启时自动恢复交易。具体身份凭证、代理证明、令牌、授权衰减与撤权机制由 63/66 冻结，不能只信 payload 中操作者字符串；D66-14 的具体角色映射仍待定。权限/接口未就绪时返回明确不可用或拒绝，不能虚报恢复。
- **恢复请求与结果**：原因归属绑定受信的稳定 runtime principal、目标策略和不可复用 cause_id；提交时 Gateway 校验当前有效授权及原因状态版本。同一 RESUME 重试或响应丢失按原命令 ID 和原内容查询/幂等处理；pending 不显示已恢复。权限缺失、原因不属于该 principal、过期授权/旧请求重放或原因状态失配等由 Gateway 明确拒绝或保持 UNKNOWN；多原因逐项核验，某个原因解除不等于其他原因解除或策略可交易。runtime 重启不会自动 RESUME；重启后，合法运营新发起并通过当前认证授权的命令可解除同一稳定 principal 此前留下且仍有效的原因，不能仅因原因创建于旧进程 boot 而拒绝。
- runtime 不持有急停状态；`status` 显示的急停原因（范围、模式、来源、原因号、DRAIN 进度、是否会在条件恢复后自动解除）是从 Gateway 读来的，读不到时显示 `UNKNOWN`（控制面分析:279、:311）。来源为 Gateway 自身的原因（`monitor_required` 下的存活丢失、S-25 的租约过期 DRAIN）照样显示；Q34 已定 Monitor 有效心跳恢复后默认由 Gateway 自动解除对应失联原因，可配置运营人工恢复；租约过期 DRAIN 在策略重连并完成恢复核对后默认只解除该原因及版本，可配置人工（后续用户决定，63 D63-33）。runtime 按原因号和版本显示 Gateway 结果，不代清 Gateway 原因，也不把单项解除显示成全部可交易；其他原因及 UNKNOWN 保留。

- D63-04（Q28 已决定）的订单 UNKNOWN 范围由 Gateway 持有：所属策略该合约全部新订单暂停，其他策略仅同合约同持仓方向可平容量无法证明时暂拒平仓；撤单/查询仍按权限可请求，连接不可达如实报告。Runtime 展示受权的命令、范围、原因及版本，不因此停止整个策略进程，也不能通过重启或有限代理 RESUME 清除它；多个 UNKNOWN 逐项解决由 Gateway 处理，其他急停原因仍保留。验证页面/状态不会把局部阻断显示为全账户停机，不把单项解决显示为全面恢复；不改变 direct 的迭代 62 合同。

### 3.7 状态、健康与日志

- **心跳与健康**：BT 每 `heartbeat_interval_s` 原子写一次状态文件（§5.2 B2）。runtime 计算：心跳超过 3 个间隔未更新为 `STALE`；PID 不存在为进程消失；心跳只说明进程活着，不说明可交易、订单完成或账户齐全（控制面分析 §2.1；架构文档:88）。
- **主循环进度**：状态文件另有主循环最后推进时间。休市时没有行情，主循环不推进是正常的，所以它只用于展示，不触发自动升级。
- **行情 LIVE**：取自 BT 报告的各数据 `trade_qualification()` 与预热状态；runtime 自己不连行情。
- **最后错误**：只显示 BT 写出的有限码与时间；详细文本留在本地日志。
- **日志**：`logs <单元>` 显示 runtime 捕获的标准输出/错误尾部（有界），并列出 TradeLogger 目录（`logs/<配置名>/<时间戳>/`）的路径；接口返回的日志有大小上限，只对 viewer 以上角色开放（D66-14）。捕获输出的轮转机制与单文件/总量上限须在 66.01 冻结：子进程直接持有文件描述符，单靠重命名不能让其转写新文件；不依赖 runtime 存活的方式须在实际子进程和 runtime 重启后验证。未证明有界写入与不中断子进程前，该项为 GAP。

### 3.8 鉴权、授权、审计与幂等

- 身份：命令行与接口客户端都须经可信认证映射到操作者身份（D66-14 的候选角色：viewer、operator、admin，按单元授权）；请求正文自报的姓名不作为身份。单个共享令牌无法证明多个不同操作者：66.01 随 D66-03/D66-14 冻结逐主体凭据或可验证的操作系统主体映射、发放、权限变更/撤销与审计身份绑定。不能实现可靠映射时，须如实降级为单主体而非声称多角色可审计；跨到 Gateway 的主体与权限另依 D66-08/63.12。
- 危险动作（首次初始化、`--force`、`--adopt`、`stop --all`）需要二次确认：服务先返回确认令牌，客户端在有效期内带令牌重发（参照控制面分析:185-188 的 QuantConnect 两次点击）。
- 命令台账（SQLite，`synchronous=FULL`）：命令号（客户端生成，UUID）、操作者、客户端类型、动作、目标单元 UUID 与目录、参数摘要、理由、状态 PENDING→CLAIMED→APPLIED/REJECTED/UNKNOWN、结果（BT 摘要或有限码）、时间；状态机参照 `mon: control.py:60-76`。
- 每个单元同时只有一个进行中的生命周期命令；`stop` 可以抢占尚未拉起进程的 `start`。
- 审计只追加，不记录凭据、账号和令牌；`audit` 子命令按单元和时间查询。

### 3.9 runtime 自身的持久化与重启

- runtime 的家目录（§6）保存：单元登记快照、运行记录（PID、创建时间、命令行摘要、run_id、日志路径）、命令台账、升级时间线进度。单实例：家目录上的独占锁，第二个 runtime 拒绝启动。
- runtime 退出（正常或崩溃）不停止策略（D66-10，INV66-05）。重启时逐个核对运行记录：身份全部吻合才接管；处于 STOPPING 的单元按持久化步骤（A1、A2、E1～E3）恢复：记录 boot 身份、单调时刻及证据；仅在同一 boot 且时钟与进程身份可验证时计算剩余预算。跨 boot、boot 身份缺失或时钟不可比较时不得自动推断等待完成或自动强杀，结果标 UNKNOWN 并等待运营；显式 `--force` 仍受 §3.5 授权、理由和审计约束。外部调用已发出但受理结果不明时保持 UNKNOWN，按冻结的 Gateway 幂等合同查询或安全重试，不凭本地步骤号认定未执行或盲目重复 DRAIN。CLAIMED 的命令无法判断结果时记为 UNKNOWN，等运营处理。
- 接管的进程不是 runtime 的子进程，拿不到退出码，所以终态只能来自 BT 的最终摘要文件（§5.2 B3）。

### 3.12 可执行重构清单与跨迭代边界

### 9.2 未决问题（UNKNOWN）

1. Windows 11 上，`CREATE_NEW_PROCESS_GROUP` 与 `CREATE_NO_WINDOW`/`DETACHED_PROCESS` 组合时 CTRL_BREAK_EVENT 能否送达；runtime 作为服务运行（无控制台）时呢。
2. BT 主线程阻塞在 C 调用（如等待行情的阻塞读）时，信号处理器多久能运行；`next()` 卡住时停止的实际延迟。
3. 启动对账期间的停止延迟（§1.3 推断）在 SimNow 交易时段的实际值。
4. 断线或进程被杀后，CTP 是否保留活动委托（63 计划:233、控制面分析:347）。
5. 状态文件在 Windows 上被杀毒软件占用时 `os.replace` 的失败率与重试策略。
6. ai-for-investor 希望用 HTTP 还是 SDK 客户端调用 runtime（迭代 10 规格之后未核对）。
7. 一台主机上要管理的策略数量上限；runtime 的心跳轮询开销。
8. Windows 上令牌文件权限的检查方式（与 65 计划 §8.2 第 6 项相同问题）。
9. 迭代 62 的 SIGTERM 处理最初只有 UNIT/FAKE（子进程测试在 win32 上跳过）；后续交易时段带挂单的单次 SimNow 停止已报告 PASS（[§2j D3](../迭代62-问题修复/SimNow实测记录-2026-11-05.md)），§2j F 另有收盘后连接保持、无挂单的单次观察。它们均不证明 runtime 端到端或 Windows 上 CTRL_BREAK 的实际效果，后者仍未知。
10. 63.12 的控制端口对 DRAIN 的“已受理”与“撤完”的返回时机、PARTIAL 的清单格式（E1 的等待依据），在 63.01 冻结前未知。

SimNow 场景（66.10，需用户授权，结果只说明 SimNow 行为）：

1. `serve` 启动 runtime；`register` 一个 direct 示例（已初始化的目录）；`start`：状态依次为 STARTING → RUNNING（RECONCILING → WARMUP → LIVE）。
2. 策略挂出一笔远价限价单后 `stop`：BT 撤本策略的单，摘要 STOPPED，runtime 记 APPLIED；账户无该策略的活动单。
3. 再 `start`，运行中 `kill -9` runtime，确认策略照常运行；重启 runtime，单元被接管，`status` 正常。
4. `restart`：完整停止后重新启动，启动对账通过。
5. 用一个故意卡住 `next()` 的测试策略（只在 SimNow 账户、远价单）验证 direct 升级（SIGTERM → SIGKILL）、E3 强杀与 `KILLED` 报告；下次启动按 D62-16 接管并撤单。
6. 同一账户哈希的第二个 direct 单元启动被拒（D66-13）。
7. Gateway 场景（63.09 与 66.07 之后）：`pause` → Gateway 拒绝该策略普通开仓、放行撤单；受权运营经 runtime `resume --cause` 按 D66-08 有限代理解除指定原因并验证审计；卡住 `next()` 的策略按 DRAIN → SIGTERM → SIGKILL 停止，DRAIN 撤销它的远价单而不碰同账户其他策略；重启不自动 RESUME，解除指定原因不代表其他阻断已解除或策略可交易。
