## 0. 结论

- 计划和设计已经写清这些内容：
  - BT 与 runtime 之间的进程合同：状态文件、最终摘要、退出码、停止预算、启动中途可停；
  - Windows 上的信号差异（CTRL_BREAK、TerminateProcess 无法捕获）；
  - PID 复用与 TOCTOU；
  - 不探测 `run.lock`；
  - 停止与升级的两段式（A 普通停止、E 升级）。
  S-14～S-25 的用户决定都已正确落实。
- 本轮共 9 条：P1 2 条，P2 5 条，P3 2 条。最主要的两点：
  - 自研进程监督器的范围很大，建议把“进程后端”抽象出来，Linux 上可交给 systemd（RV66-01）；
  - Gateway、risk、execution、monitor 四类服务没有人按依赖顺序启停（RV66-02）。

## 2. 发现与建议

### RV66-01（P1）自研进程监督器的范围过大：建议抽象“进程后端”，允许交给系统服务管理器

- **定位**：设计 §4（PID、创建时间、boot 身份、命令行摘要、TOCTOU、进程组竞态）和 §7（systemd cgroup、launchd、Windows Job 的 `KILL_ON_JOB_CLOSE`、日志轮转）；计划 §3.10、D66-05、D66-15、66.05、66.09。
- **问题**：设计自己也承认，`start_new_session`、进程组、Job Object 都不能保证“runtime 退出时不终止策略”和“只终止本次 run 的进程”，并要求在每种服务管理器和每个操作系统上实测证明。自研需要同时解决这些问题：
  - 进程身份的稳定绑定，以及组成员范围；
  - 脱离进程组的后代进程；
  - 日志轮转（子进程直接持有文件描述符）；
  - 跨 boot 的计时；
  - runtime 自身被托管时，所在的 cgroup 或 Job 的归属。
  在 Linux 上，systemd 已经处理好了其中大部分：按 cgroup 识别进程、`KillMode=control-group`、`Restart=`、journald [S24]。
- **方案**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| a | 自研一套实现，覆盖三个平台（现状） | 一套代码 | 范围大；每个平台、每种管理器都要实测；最难的一项是 runtime 被 systemd/launchd 托管时策略能否独立存活 |
| **b** | 定义 `ProcessBackend` 接口。native 后端（subprocess + psutil，Windows 上用 Job Object）用于开发机和 Windows；systemd 后端（为每个策略单元生成 `systemctl --user` 的临时单元或模板单元）用于 Linux 生产。runtime 只负责控制面、命令台账和状态推导 | Linux 上的可靠性交给 systemd；native 后端可以只承诺“同一会话内”的能力 | 两个后端都要测试；systemd 后端只能用于 Linux |
| c | 全部交给系统服务管理器（systemd、launchd、Windows 服务），runtime 只下发命令 | 自研最少 | Windows、macOS 的能力差异大；需要与 S-15“runtime 是微服务、按钮在 runtime”重新对齐 |

- **建议**：选 b。66.01 先冻结 `ProcessBackend` 的最小能力集（start、signal、status、wait、identity）；各后端逐项声明支持哪些能力，不支持的操作返回有限码。作为新增候选 D66-21。（问题 Q66-01）

### RV66-02（P1）D66-02：建议 runtime 至少按依赖顺序启停服务进程（仍不读凭据）

- **定位**：D66-02（建议 c：本迭代只监督策略进程）；§2.2 非目标中的“缺省不监督 Gateway、risk、execution、monitor”。
- **问题**：63～68 落地后，一个账户最多有 4 类常驻服务（Gateway、risk、execution、monitor）加 N 个策略，而且启动有先后：
  - Gateway 先就绪；
  - 选了 risk 的策略要等 risk；
  - execution 要等 Gateway 和 risk。
  63.09、64.09、65.11 的 SimNow 验收都要按这个顺序拉起进程，现在只能靠一次性脚本。
- **方案**：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| a / c | 只监督策略（计划建议的 c 与 a 在本迭代效果相同） | 范围最小；服务启停全靠人工或脚本 |
| **b-lite** | 新增“服务单元”，只登记入口、依赖和就绪探针（如 Gateway 的 `session_status` 就绪、risk 的 `risk.status`）；按依赖顺序启动，按相反顺序停止。runtime 不读凭据：Gateway 按自己的配置读取 env 文件路径，与 D66-11 a 做法相同。服务单元不提供暂停和 DRAIN | 解决验收和日常运维的启停顺序；多一种单元类型；停 Gateway 时要等它的 SIGTERM 优雅停止完成（63 §3.12） |
| b | 完整监督服务，含重启策略和依赖失败处理 | 功能完整，范围大 |

- **建议**：b-lite。（问题 Q66-02）

### RV66-03（P2）定时启停与交易日历：建议纳入单元模型，可以另立步骤

- **定位**：§2.2 非目标中的“不做定时启停、交易日历驱动的自动开机（以后另议）”；§3.12 第 5 项（67 的日历更新由操作系统计划任务负责）。
- **问题**：CTP 分日盘和夜盘，节假日前一晚没有夜盘。常见的运维方式是开盘前 N 分钟启动、收盘后停止。WonderTrader 的 WtMonSvr 就用 WatchDog 自动调度任务 [S5]。迭代 67 提供日历文件之后，runtime 是最自然的调度位置；否则只能用 cron 调 CLI，节假日判断还要另写一套。
- **方案**：

| 方案 | 做法 |
| --- | --- |
| a | 维持非目标 |
| **b** | 本迭代在单元模型中加入 `schedule`（时间窗 + 交易日过滤，日历来自 67 的公开接口；67 未交付时只支持固定时间窗，并如实标明），新增可选步骤 66.12 |
| c | 另立迭代 |

- **建议**：b（或 c）。作为新增候选 D66-22。（问题 Q66-03）

### RV66-04（P2）本机控制接口的安全与身份：HTTP 要防 DNS 重绑定和跨站请求；CLI 改走本地套接字，取对端的操作系统身份

- **定位**：D66-03（建议 a：回环 HTTP/JSON + 令牌文件）、D66-14（三级角色）、INV66-09、§3.8。
- **问题**：
  1. 回环 HTTP 服务可以被本机浏览器里的网页借 DNS 重绑定或跨站请求访问，只校验 Host 头还不够。
  2. D66-14 要求“逐主体凭据或可验证的 OS 主体映射”；共享令牌只能代表一个主体，设计 §6 已经指出这一点。
- **建议**：
  1. **HTTP**：同时校验 Host 和 Origin，拒绝 Origin 不在预期内的请求；不开 CORS；凭据只放在 `Authorization` 头里，不用 cookie；限制请求体大小和超时；令牌按主体发放、短期有效（freqtrade 在 127.0.0.1 上用短期 JWT [S8]）。
  2. **CLI**：改走 Unix 域套接字（POSIX）或命名管道（Windows），由服务端读取对端凭据（Linux 用 `SO_PEERCRED`，macOS 用 `getpeereid`，Windows 取命名管道客户端的身份），把操作系统用户映射为 viewer、operator 或 admin。这正是 D66-14 要的“可信 OS 主体映射”，不需要分发令牌。
  3. **AFI**：以后经 HTTP 加每主体令牌接入。
  也就是说，D66-03 采用“a + c”的组合。（问题 Q66-04）

### RV66-05（P2）D66-08 补选项 d：runtime 作为运营代理转达 RESUME

- **定位**：D66-08。现有选项：a，runtime principal 可以转达 RESUME，但需确认这算不算“由运营执行”；b，runtime 没有 RESUME 权限；c，runtime 持有完整的运营 principal。另见 63 INV63-06（代理 principal 只能在被代表者的范围内行事）。
- **建议新增 d**：
  - 每位运营在 Gateway 中有自己的 principal 和 grant；
  - runtime 作为“运营代理”转达 RESUME 时，带上 `on_behalf_of=<运营 principal>`；
  - Gateway 同时核对两件事：runtime 有代理 grant，且这位运营本人有 RESUME 权限；审计记为“运营 X 经 runtime”。

  这与 63 为 risk、execution 设计的代理模型相同，既满足“只能由运营执行”，又不必把完整的运营权限交给 runtime。运营在 runtime 中的身份来自 RV66-04 的操作系统主体映射。
- **相关**：RV63-03（主体热加载）。运营 principal 的增减也不应该要求重启 Gateway。（问题 Q66-05）

### RV66-06（P2）direct 部署没有任何告警出口

- **定位**：S-09（monitor 只能在 Gateway 部署中启用）；§4.3（只有在 Gateway 部署且选了 monitor 时才转发事件）。
- **问题**：direct 部署中，策略崩溃、心跳过期（STALE）、被强杀、停止时仍有活动委托（`STOPPED_WITH_WORKING_ORDERS`）等事件只写在 runtime 本地，没有人会收到通知。
- **方案**：

| 方案 | 做法 |
| --- | --- |
| a | 不做 |
| **b** | runtime 提供一个可选的推送出口（通用 webhook，或 BT `backtrader/notifications` 已支持的某个通道），只发送 runtime 自己的事件，按事件级别过滤并限速 |
| c | 只依靠策略内的 BT 通知（`Strategy.send_message`） |

- **建议**：b；策略内的事件仍用 c。（问题 Q66-06）

### RV66-07（P2）主循环停滞只展示、不告警

- **定位**：§3.7（主循环进度只用于展示）；§3.5“卡住的 `next()`”一段；INV66-12（心跳过期只报 STALE，不自动升级）。
- **问题**：心跳线程独立于主循环，所以 `next()` 卡住时进程看起来仍然“活着”。交易时段内主循环长时间不推进是严重问题（既不下单也不撤单），但现在不会产生任何信号。
- **建议**：保留 INV66-12，不自动处置；但在交易时段内（依据交易日历或 provider 的 `trading_session_schedule`），主循环停滞超过阈值时产生 `LOOP_STALLED` 事件，送到 RV66-06 的推送出口或 monitor；休市时不做判断。

### RV66-08（P3）AFI 集成的部署约束要写明

- 控制接口只开放在本机（INV66-09），因此 AFI 必须与 runtime 部署在同一台主机上，或者经运营自建的安全隧道访问。建议在 §10 和 AFI 的集成说明中写明这一点。跨主机访问需要另行设计（TLS + 认证），不在本迭代范围内。

### RV66-09（P3）外部佐证：暂停的语义

- freqtrade 的 `stopentry`（原名 `stopbuy`）会停止开新仓，并按规则继续处理已有持仓 [S8]，与 D66-06 的“暂停 = STOP_NEW”一致。FREEZE（连平仓也拒）在同类产品中比较少见，是更严格的选项。按钮文案应写清两者的差别：是否仍放行平仓。
