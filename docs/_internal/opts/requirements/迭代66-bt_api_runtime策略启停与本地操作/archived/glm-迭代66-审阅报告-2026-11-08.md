### GL66-04(边界)[新发现] `BLOCKED` 的“可核验启动拒绝记录”没有产物定义,状态不可达

- **定位**:迭代计划.md:165(§3.3“`BLOCKED` 仅由可核验且匹配本 run 的启动拒绝记录支持,不能单凭退出码 2”)、:122(INV66-04 以最终摘要为准)、:176(§3.4 第 4 条同一要求)、:328(B3“停止后原子写 `state/last_run.json`”)、:400(门禁“退出码 2 但摘要缺失”)、:53(现状摘要只在 stdout)。
- **问题**:B3 明确只在“停止后”写最终摘要;启动被拒时 `run.py` 在 :391 `return EXIT_BLOCKED`、:415 置 `status, code = "BLOCKED", EXIT_BLOCKED`,只经 :359-361 的 `report()` 打印一行 JSON 到 stdout,不写任何状态文件。于是 §3.3 要求的“匹配本 run 的可信拒绝记录”在本迭代不存在:B3 的 schema 也没定义拒绝码/拒绝阶段;INV66-04 又会因“没有摘要”把进程结局归为 `CRASHED`/`KILLED`/`LOST`。状态机中的 `BLOCKED` 因此不可达,而测试门禁还要求覆盖“退出码 2 但摘要缺失”的负例。
- **证据**:`run.py:391` 引文 `return EXIT_BLOCKED`;`:415` 引文 `status, code = "BLOCKED", EXIT_BLOCKED`;`:359-361` 引文 `def report(status, **fields): ... print(json.dumps(...))`;B3 引文“停止后原子写 `state/last_run.json`”。
- **建议**:B3 拆成两类原子记录:(a) run 最终摘要;(b) 启动拒绝摘要(建议同文件、不同 `kind`/`exit_reason`,或独立 `state/start_refused.json`),在包括拒绝在内的所有退出路径写 run_id、进程身份、拒绝码、阶段与来源;INV66-04 明确识别两类 schema。若不扩展,则从状态机删除 `BLOCKED` 或只显示 `EXIT_2_NO_RECORD`,不能保留现状。
- **影响**:T2 已经正确地否定了“退出码 2 即 BLOCKED”,但没有给出替代证据,导致状态机留了一个永远无法进入的终态;前端会把受证拒绝显示成 CRASHED/LOST 或永远 UNKNOWN。
