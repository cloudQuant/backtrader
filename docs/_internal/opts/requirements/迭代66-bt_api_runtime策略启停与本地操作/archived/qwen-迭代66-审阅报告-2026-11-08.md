## 3. 发现与建议

### QW66-01（P1）STARTING 超过 start_timeout_s 后，stop 的判定分支缺失

- **定位**：计划 §3.5 A0（“STARTING 阶段尚无状态文件时，在 `start_timeout_s` 内按有响应处理”）与 §3.4 第 4 条（“超过 `start_timeout_s` 仍无状态文件时记为 UNKNOWN，进程不被自动杀掉”）；设计 §4 STARTING 行、§5。
- **问题**：A0 只定义“心跳新鲜→A1”“STALE→E 段”两条入口，STARTING 的例外只覆盖 `start_timeout_s` 之内。当启动观察已超时（单元记 UNKNOWN、进程仍存活、从未有心跳）而用户下达 `stop` 时，走 A1、直接 E 段还是拒绝，两份文档都没有定义；该场景 E3 的预算依据（B5 的启动中途分量是否单独可用）也未写明。实现者只能自行取舍，结果是“停止悬挂”或“任意强杀”二选一，均属误杀/漏杀风险。
- **建议**：66.01 在 A0 补第三分支：STARTING 且已超过 `start_timeout_s`（PID 身份吻合、无状态文件）→ 按不响应进入 E 段；E3 仅允许使用经证明覆盖启动阶段的预算分量，预算不可证明时保持 UNKNOWN、只走显式 `--force`。同时写明此时原 `start` 命令的台账结局（UNKNOWN 收尾还是继续观察）与 `stop` 抢占关系（§3.8 只覆盖“尚未拉起”的抢占）。
- **理由**：INV66-10 已把“可证明预算”作为自动强杀的唯一门槛，本分支只是把该规则接到一个已承认存在（§3.4）却无消费路径的状态上；不补则该状态的停止行为不可判定。
- **验收**：UNIT 假时钟 + INTEGRATION_SIM 真实慢启动子进程（不写状态文件）断言：stop 按冻结分支执行；预算缺失时进程不被自动杀、命令结果 UNKNOWN；`--force` 路径仍受授权与审计约束。

### QW66-02（P2）spawn 到 stop_on_terminate 安装之间的窗口未入合同

- **定位**：计划 §5.2 B1/B4、§3.5 A1；`BT: examples/live/007_ctp/bbroker_5s_single_symbol_direct/run.py:395-411`（当前 dev）。
- **问题**：迭代 62 的锁存覆盖“处理器安装后、运行激活前”。但 run.py 在 `create_store`/`create_broker`（:395、:397）之后才安装 `stop_on_terminate`（:411）；spawn 到安装之间收到 SIGTERM 走 Python 默认动作立即终止：无摘要、无清理、退出由信号决定。A0/A1 对 STARTING 进程正是直接发 SIGTERM。“安装前无账户副作用”目前只是 STATIC 推断（Store/Broker 构造是否有连接或写入副作用未在 66 文档中要求证明），B4 的测试矩阵从 run 作用域打开后才开始。
- **建议**：66.01/66.02 明确三点：(1) 合同要求“处理器安装前无账户副作用”并给出测试，或把安装点前移到 run.py 入口（属 BT 侧改动，纳入 B1/B6 范围）；(2) runtime 对该窗口内死亡的进程按 INV66-04 报 `CRASHED`/`KILLED` + 撤单 UNKNOWN，若 (1) 的证明成立可另给更干净的有限码；(3) B5 的预算说明包含该窗口的处置。
- **理由**：不补合同则“启动中途停止”（B4）的覆盖有盲区：最早的停止请求恰好落在保护最弱的阶段；INV66-04 保证不谎报，但不能代替对副作用边界的证明（计划 §3.12 第 2 条自己要求“每个有副作用边界”）。
- **验收**：INTEGRATION_SIM 在 spawn 后、安装前发 SIGTERM：进程终止、runtime 报告符合冻结合同、无残留写入或如实 UNKNOWN；若安装点前移，迭代 62 的 `tests/unit/test_live_trading_graceful_stop.py` 全部仍通过。

### QW66-03（P2）平台能力矩阵不是明确交付物；macOS 的稳定身份绑定候选缺位

- **定位**：计划 §3.10 表、66.01（只有 Windows 探针）、66.05/66.09 补充门禁；设计 §4（“该平台可验证、与目标身份稳定绑定的句柄或等效能力”）、§7；复核清单 §5 T1。
- **问题**：T1 要求“实际支持的平台、进程/组句柄能力、systemd/launchd/Windows Job 配置须逐组合证明”。现行文本写清了不可证明时的兜底（拒绝/UNKNOWN）和门禁，但没有任何一步交付“平台能力矩阵”文档：POSIX 侧稳定绑定的候选机制未列——Linux 有 `pidfd_open(2)` [N2]，macOS 没有 pidfd 等价物；D66-15 推荐的 psutil 只提供创建时间等时点事实，属 check-then-act，不满足设计 §4 的“稳定绑定”。逐平台候选缺位的后果是：macOS 上 E3 自动强杀可能整体不可用（只剩显式 force），这一行为差异到 66.05/66.09 门禁才会暴露，且 66.01 探针只列了 Windows 项。
- **建议**：66.01 增加“平台能力矩阵”交付物（文档，非安装器）：行 = Ubuntu/macOS/Windows 11 ×（稳定绑定、组范围证明、优雅信号送达、解耦存活、runtime 托管组合），列 = 候选机制（Linux pidfd、Windows 进程句柄/嵌套 Job [N3]、macOS 替代方案如“操作前即时复核创建时间 + 操作限定单主进程 PID”及其残余 TOCTOU 等级）、证明方法、不可证明时的降级。POSIX 补一个与 Windows 探针对称的探针步骤（66.01 或 66.05）。
- **理由**：这是 T1“哪个平台能做到什么、做不到时怎么办”的直接落实；先列候选再进门禁，避免把“macOS 无法自动 E3”留到验收阶段才发现。
- **验收**：矩阵覆盖全部组合并各给 PASS/GAP/NOT_RUN 判定方法；macOS 的 E3 能力有明确结论（自动或仅显式 force）并回写 §3.10；探针脚本按 66.01 约定放 scratch 不入库。

### QW66-04（P2）D66-03 选项文本未随 D63-47/66.12 更新；双北向通道的主体映射待冻结（同步缺口）

- **定位**：计划 §8.1 D66-03（选项 c“本地套接字/命名管道，只供命令行，AFI 适配以后再做”）、§3.1 第 3 段（FastAPI 可选 Web 层“不决定 D66-03”）、§4.2；设计 §6。
- **问题**：66.12 已定交付独立前端，浏览器只能经 HTTP 到达服务（FastAPI Web 适配已写入 §3.1/设计 §6），因此选项 c“避免 HTTP、AFI 以后再说”的前提已不成立——无论 D66-03 选什么，HTTP 入口都会存在。三个选项的实际差异已经改变，但选项文本仍是 D63-47 之前的写法；用户按失真描述做决定会影响决定质量。同时 CLI 通道（令牌文件或套接字对端凭据）与 Web 通道（会话/JWT 类）并存后，“复用同一受鉴权合同”需要单一主体身份与角色映射的冻结稿，现文只有原则句（§3.1“前端主体和各服务 grant 须有独立可信映射”）。
- **建议**：在用户确认 D66-03 前更新选项描述：写明 Web 适配层与 D66-03 传输并存、c 不再免除 HTTP、a 与 Web 适配层天然合并为同一回环 HTTP 面；66.01 冻结两通道的单一主体模型（认证方式、角色、审计字段、映射失败拒绝码）。这是同步缺口登记，不是重开 D63-47 或 D66-03 的决定。
- **理由**：纪律要求已定决定不重问，但选项表是待决事项的唯一决策依据，须与已定事实一致；复核清单 M5 也把“Web 身份映射/操作合同”列为剩余交付。
- **验收**：D66-03 选项文本与 §3.1/66.12 一致、无“AFI 适配以后再做”类失效前提；66.01 冻结稿含双通道主体映射表与不一致时的拒绝行为。

### QW66-05（P2）INITIALIZED_NO_RUN 的“没有历史 run”判定来源未冻结

- **定位**：计划 §3.3（“身份有效且已核实没有该单元历史 run”）、INV66-03（runtime 只读 `state/identity.json` 和 BT 为它写的状态文件）；设计 §4 状态映射；66.05/66.09 门禁（“测试已初始化无历史、历史丢失”）。
- **问题**：`identity.json` 不含运行历史；`run_status.json`/`last_run.json` 只覆盖本次/最近 run。目录曾手工运行过、而 runtime 台账全新时，“已核实没有历史 run”没有权威数据来源——按现文它只能退化为 UNKNOWN，或者靠“`last_run.json` 不存在”推断，而后者正是 T2 禁止的伪造干净状态。BT `backtrader/live_state/` 有 audit/sequence/snapshot 等记录（`audit.py`、`sequence.py`、`snapshot.py`），但计划未写 runtime 是否经只读接口消费它们。
- **建议**：66.01 冻结判定来源，候选：a. BT live_state 增加只读投影“该目录是否存在任何历史 run/未决标记”（与 identity 只读接口同类，符合 INV66-02/03）；b. runtime 台账 + BT 状态文件联合判定，不可核实时一律 UNKNOWN。补对应 UNIT 分支（手工历史 + 新台账、历史损坏、真首启）。
- **理由**：T2 的落实只差这最后一环：状态定义有了，产生该状态的事实来源没有；没有来源，`INITIALIZED_NO_RUN` 是不可验证的宣称。
- **验收**：三种场景（有手工历史、历史损坏、真首启）的状态输出与冻结来源一致；不得以 `last_run.json` 缺失单独得出 `INITIALIZED_NO_RUN`。

### QW66-06（P2）62.08 式策略自带 Gateway 子进程在 E3/异常退出后的归属未定义

- **定位**：计划 §1.3 第 61 行（`multiprocessing` spawn 非 daemon、孤儿为 STATIC 推断）、§3.5 A1（“只对主进程发 SIGTERM，避免 Gateway 子进程被同时终止”）、66.01 探针（只测子进程是否同时收到信号）；设计 §4（“脱组后代不能假称已清理”）。
- **问题**：A1 刻意保护 Gateway 子进程，但主进程被 E3 SIGKILL 或异常退出后，这个持有 CTP 行情会话的子进程由谁发现、报告、收尾没有定义：runtime 状态模型没有“已知直接后代仍存活/未覆盖”字段，§9.1 风险表没有“孤儿持有场所会话”行，下次启动的会话/资源冲突也未列入启动预检。63.08 会把 Gateway 重写为独立服务（D66-02 下由其自身入口运行），但在 63.08 交付前 62.08 形态是现存的真实部署，且 66.10 场景 5 恰好要强杀这类进程。
- **建议**：66.01 明确过渡形态合同：a. 示例侧（run.py/B6 或 63.08）负责在 finally 中终止自己 spawn 的子进程；b. runtime 状态把“已知直接后代仍存活”作为未覆盖项如实报告，不自动杀（杀它等于 runtime 干预服务进程，越过 D66-02 边界）；c. §9.1 增加孤儿会话风险行。66.10 场景 5 补后代检查断言。
- **理由**：设计 §4 的“保留未覆盖项”原则需要落到这个已知的具体场景，否则漏清理留下无归属的场所会话，属于 T1 关注的“组成员范围”问题的现实实例。
- **验收**：INTEGRATION_SIM：强杀主进程后后代存活被报告为未覆盖、接管与重启不被静默放行；007 gateway 示例改造后正常停止无孤儿（无环境则 NOT_RUN）。
