## 0. 结论

- 两处设计判断成立：
  - **§1.4 的投影要求表很好。** 它逐条列出 BT 对订单身份的假设，以及母单投影各自要满足什么条件。
  - **派发归属合理。** execution 只做 Gateway 的客户端，Gateway 是唯一派发点，这与同类系统一致：NautilusTrader 的执行算法产生的订单同样要经过 RiskEngine 和 ExecutionEngine（63 控制面分析 [R1]）；WonderTrader 的执行单元位于策略层之下 [S4]。
- 本轮共 9 条：P1 4 条，P2 4 条，P3 1 条。最重要的有三条：
  - **配置结构不一致（RV65-01）**：设计和计划的配置写法不同，而且合并、轧差在逻辑上不能按策略选择。
  - **轧差应从 65 拆出（RV65-02）**：它同时要改 63、64 和 BT 的合同，建议另立迭代。
  - **期货双边持仓下的轧差限制（RV65-03）**：两笔开仓互相抵消（“开对开”）会在策略账本里造成场所并不存在的仓位，只有“平对开”的持仓转让能保持一致。

## 2. 发现与建议

### RV65-01（P1）配置分层不一致：设计 §3 与计划 §5 写法不同，且合并、轧差不能按策略选择

- **定位**：
  - 设计 §3：只给了一个 `gateway.execution` 块，里面同时有 `scheme`、`merge`、`netting`、`algorithm` 和 `constraints`，看不出它属于账户、服务还是策略。正文另有一句“账户配置声明允许…策略配置只在允许范围内收窄”。
  - 计划 §5：分三处。账户级 `components.execution.allow[]`；execution 服务级 `scheme`（含 `class`、`merge`、`netting`、`algorithm`）；策略级 `gateway.execution.routes[]`（匹配条件 → 算法和参数）。
- **问题**：
  - 合并和轧差要同时处理多个策略的母单，只能在服务级或账户级选择。两个策略选了不同的轧差方案，就无法互相轧差，所以“按策略选择轧差”没有意义。
  - 算法可以按路由选择。
- **建议**：统一为三层，以合同注册表（RVX-02）为唯一出处，并改正设计 §3 的 YAML：
  1. **账户层**（运营维护，放在 Gateway 账户目录）：
     - 可以委托给哪个 execution principal；
     - 允许的合约、算法类和方案类版本；
     - 母单数量上限、子单预算和撤单预算；
     - 每个策略是否允许参与合并或轧差（按策略 opt-in）。
  2. **execution 服务层**（运营维护）：
     - 方案类，合并类、轧差类及其参数；
     - 全局约束：最大子单数、撤单预算、重试上限；
     - 注册表白名单。
  3. **策略层**（策略作者维护）：
     - 路由规则（匹配条件 → 算法和参数），只能在账户层范围内收窄；
     - 合并或轧差只能选择退出，不能开启账户层没有允许的内容。
- 问题 Q65-01。

### RV65-02（P1）轧差和内部转移的范围与排期：建议从 65 拆出，或放到最后一个里程碑

- **背景**：用户已决定 D65-25（本迭代提供可配置方案）和 D65-26（允许内部转移）。计划已把它们隔离到 65.05b，并允许标记为 GAP。
- **问题**：内部转移同时要求四件事：
  1. 修改 63 的权威账本合同（INV63-04、§3.11），并新增 Gateway 的双边原子提交接口；
  2. 选了 risk 时，64 要新增转移前的风控协议（`risk.transfer.*`）；
  3. BT 要能表达非场所来源的转移（D65-03 可能做不到）；
  4. 经济政策（D65-09：价格、公平、费用、今昨桶、保证金）尚未决定。
  这是 63～65 中风险最高的一块。留在 65 内，65 的验收就要等 63 和 64 的改动；三方合同还让每份计划都变长（63 设计 §5.1、64 设计 §7、65 设计 §5）。
- **方案**：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| a | 保持在 65（现状），允许标 GAP | 65 难以整体完成；三份计划都要继续承载这份合同 |
| **b** | 另立迭代（例如“跨策略轧差与内部转移”），在 63/64/65 核心验收之后开始 | 范围清楚，不阻塞核心；D65-26 的决定不变，只调整排期 |
| c | 65 只做同向合并，轧差以后再做 | 与 b 接近，只是不单独立项 |

- **建议**：b（或 c）。（问题 Q65-02）

### RV65-03（P1）轧差的几种可行模型、双边持仓下的限制，以及内部转移的定价（供 D65-09）

**一、模型选择**

| 模型 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **1 内部转移**（现方案） | 反向母单先在两个策略的账本之间按内部价格转移，只把净额发到场所；每个策略的账本仍代表真实、可平的仓位 | 策略账本与可平容量一致，符合 D62-26 显式开平 | 要定价格、公平、费用和今昨桶规则；63、64 都要改；BT 要能表达非场所来源 |
| 2 目标仓位 / 理论持仓（WonderTrader 组合盘一类 [S4]） | 策略只给出目标仓位，执行层按“账户净目标 − 实际持仓”下单；各策略的仓位和盈亏是理论值（按信号参考价计），执行滑点和费用归到组合 | 报撤单和手续费最省，也不需要转移记录 | 策略账本不再是可平仓位，与 63 的按策略可平容量、显式 offset 以及 BT 的订单语义冲突；需要另一套目标仓位接口，与 S-08“BT 不处理”冲突 |
| 3 不轧差，只做同向合并 | 反向母单各自发到场所，靠 risk 的 R-05 拒绝可能自成交的子单，或由 execution 暂缓会与本账户反向挂单相交的子单 | 账本语义最简单，没有定价争议 | 报撤单和手续费更多 |

**二、双边持仓（CTP，D62-25）下模型 1 的必要限制。** 这是本条最重要的一点。

- **“开对开”不能轧差。** 设想 A 要买开 5 手（多），B 要卖开 5 手（空）。如果轧掉，场所上不下单，但 A 的账本记多 5、B 的账本记空 5，而场所上的多空都是 0。按方向做的账户合计对账（63 §3.11：Σ 多 = 场所多，Σ 空 = 场所空）会立即失衡。之后 A 想卖平这 5 手多头时，场所上根本没有可平的多头。
- **“平对开”可以轧差，本质是持仓转让。** 设想 A 持有场所多头 5 手、要卖平，B 要买开 5 手多。把 A 的多头转给 B：场所多头 5 手不变，A 的账本变 0，B 的账本变多 5。按方向对账仍成立，B 以后也能在场所卖平。今昨桶随仓位一起转移：A 的昨仓转给 B 后仍是昨仓，这会影响 SHFE 的平今、平昨及手续费。账户层的保证金不变。
- **建议**：双边持仓的场所只允许“持仓转让”式轧差，即一方平掉自己已有的场所仓位（带显式的今昨桶），另一方开同一持仓方向的新仓；其余组合一律不轧差。净持仓模式的场所（例如 OKX 单向持仓）可以另行允许“开对开”，但本迭代不涉及 OKX/Binance（D63-10）。

**三、定价（模型 1）**

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| **i** | 匹配时刻的独立市价：有双边盘口时取中间价（按价格网格取整），没有时取最新价；行情过期就不转移 | 与 SEC 17a-7 的“独立当前市价”原则一致 [S14]，双方都不吃亏；需要新鲜行情，并要定取整方向 |
| ii | 最新成交价 | 简单；买卖价差大时对其中一方不利 |
| iii | 双方限价的中点 | 不依赖行情；但价格会受策略自己报价的影响，不公平 |

- **建议**：选 i，取整规则须明确，例如四舍五入到最近的价位，正好居中时取被动方有利的一侧。

**四、费用与分配**

- **费用**：内部转移没有场所手续费，按 0 记录并标注来源。是否收内部费用属于政策，建议缺省不收。
- **分配**：当一方数量大于另一方时，可以按母单受理时间先后（FIFO，确定、易审计），也可以按剩余量比例分配（用最大余数法取整）。建议 FIFO。

- 问题 Q65-03。

### RV65-04（P1）把“BT 产品代码零改动”的可行性验证提前到 65.01

- **定位**：§1.4 的结论（“BT 产品代码能否保持不变尚未证明”）；65.07 依赖 63.06 和 65.06。
- **问题**：§1.4 列出了很多 BT 假设：身份键、交易日绑定、去重键、启动时按 `exchange_order_id` 归组、UNKNOWN 只对强身份做恢复等。这些假设要到 65.07 才验证，那时 65.02～65.06 都已做完。如果做不到，就要改选 D65-03 b（改 BT），连 63.06 的设计也要跟着变，前面的工作可能白做。
- **建议**：
  - 65.01 先做一个小型验证：在 BT direct 模式（或 63.06 的 Gateway 分支）上接一个替身 SDK，按 §1.4 的 7 行逐条发出母单投影，跑一遍 BT 的对账、去重和重启路径，尽早决定 D65-03。
  - 同时评估在 base 中加一个明确的“母单身份类型”，代替借用 `client_order_id` 兜底，因为 BT 的兜底路径本来不是为母单设计的。这需要很小的 BT 改动，即 D65-03 b，由用户决定。
- 问题 Q65-04。

### RV65-05（P2）MVP 算法：在 D65-08 a 之外，考虑加入限价追单

- **背景**：CTA 期货一笔单常在 1～20 手之间，几手的 TWAP 意义不大。更常用的是限价追单：先挂对价或排队价，未成交时按规则追价，最多追 N 次，且不越过母单限价。VeighNa 提供了 BestLimit 和 Sniper [S9]。
- **方案**：

| 方案 | 内容 |
| --- | --- |
| a | PASS + SLICE + TWAP（计划） |
| b | PASS + SLICE + 限价追单 |
| c | PASS + SLICE + TWAP + 限价追单 |

- **注意**：每追一次价就是一次撤单加一次新单，会计入 R-04，所以撤单预算必须填写。
- **建议**：范围允许就选 c，否则选 b，TWAP 以后再做。（问题 Q65-05）

### RV65-06（P2）插件注册表用 Python entry points 加账户白名单，接口可参照 executor 模式

- **定位**：设计 §2（“受控注册表…只加载所选类，不 `eval` 配置或任意导入路径”），计划 §4.3。
- **建议**：
  - **注册机制**：用 entry point 组登记插件（如 `bt_api_execution.schemes`、`.algorithms`、`.merge`、`.netting`），与现有的 `bt_api.direct_write_providers` 用同一机制（63 §1.1）。
  - **选择方式**：配置按“登记名 + 版本”选类，再经账户白名单过滤。
  - **类声明**：每个类声明协议版本和参数 JSON Schema。schema 还可以直接用来给 AFI 生成表单（§3.12）。
- **接口**：设计中的 `AlgorithmV1.next(residual, ctx) -> ChildProposal | Wait | Done` 加上 `on_event` 是合适的。建议补两点：
  - 明确的结束策略，即剩余未成交部分是保留还是撤销，可参照 Hummingbot 的 `keep_position` [S7]；
  - 确定性回放：固定随机种子、使用假时钟（设计已提到）。

### RV65-07（P2）D65-14 与 INV65-08 冲突：重试次数应必填、无缺省

- **定位**：计划 §5 的注释写“`max_child_retries: <运营填写>  # 缺失即 0 次（D65-14）`”；INV65-08 要求“必填且无缺省”；设计 §3 写“`child_retry_limit: <required>  # D65-14 待决`”。
- **建议**：设为必填，0 也必须显式写出；缺失即拒绝该配置。同时统一这两个键名。

### RV65-08（P2）采用 RVX-01 之后，65 的简化

- **A′（补 abandon 与 epoch）**：§3.8 第 5、7、8 行，即 `risk.parent.reserve` 前后崩溃、`CHILD_PLANNED` 之后崩溃、子单预留之后崩溃，都可以用 Gateway 上的 `abandon(child_id)` 加上 risk 侧凭这份证明做的释放得到确定结论。INV65-03 中“释放未成交余量”也就有了可证明的依据。
- **B（单阶段）**：子单流程变成 `CHILD_PLANNED` → `place`（一次 RPC）→ 结果，§3.5 的第 1～3 步合并为一步。
