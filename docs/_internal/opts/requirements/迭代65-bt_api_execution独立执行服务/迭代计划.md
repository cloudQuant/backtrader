## 1. 背景与现状（STATIC，2026-11-06）

### 1.1 为什么有本迭代

- 63 分析把 execution 放在唯一派发点之前：execution 把母单拆成子单，交给派发点，自己不碰交易所会话（63 分析:15-19、:27-28、:44）；Gateway 模式下的派发点是每账户一个的 Gateway 交易 owner（:29-33）。
- 63 计划把执行算法、拆单和聚合列为非目标（63 计划 §2.2、§3.15）；64 计划只在 risk 一侧提供母单预留合同，不接入 execution（64 计划 §2.2、64.10）。execution 本身的开发没有归属，用户要求放到迭代 65（原话 1）。
- 用户限定 execution、risk、monitor 只能在开启 Gateway 时启用（原话 2、U65-4）。所以本迭代只设计“Gateway + execution（± risk ± monitor）”，不存在 direct + execution。
- 同日晚上用户又决定（U65-5～U65-9）：risk 是 Gateway 之前的独立服务，开启时 BT 的订单先经 risk 再到 Gateway；Gateway 也接受没有风控批准的订单；急停状态由 Gateway 持有；monitor 只观察、不发控制命令；现有急停词汇改名统一；Gateway 相关的开发都在迭代 63。因此：子单在开 risk 时走 execution → risk 服务 → Gateway；`reserve_parent` 由 execution 经 risk 服务调用（原 D65-12 消解）；本迭代需要的 Gateway 侧能力（母单委托信封、代理 principal、租约、子单幂等键、行情 principal）由 63.13 实现，本迭代不修改 `bt_api_gateway`。

### 1.4 “BT 不处理”的边界（原话 1）

BT direct 模式（63.06 起也是 Gateway 模式的基础）对订单身份有以下假设。要让母单在 BT 看来是“一笔普通订单”，SDK 的投影必须满足每一行：

| BT 的假设 | 位置（`BT: backtrader/brokers/_btapi_direct_mode.py`） | 对母单投影的要求 |
| --- | --- | --- |
| 订单键：有 FrontID/SessionID/OrderRef 用会话三元组；有 ExchangeID/OrderSysID 用场所号；都没有时退回 `client_order_id` | `:194-211` | 母单身份只带 `client_order_id`（母单号）和 `trading_day`，不带任何子单的原生字段，否则母单会和子单回报串号 |
| 按交易日绑定的键只用于非 `client_order_id` 键 | `:1834-1845` | 母单不得跨交易日（D65-04），否则无法区分不同交易日的同号 |
| 一次 `make_order` 返回一个 `DirectWriteOutcome`（sent 为 True/False/None）和一个身份；None 时该合约置 `pending_unknown` | `:1568-1628` | sent=True 定义为“母单已被 Gateway 和 execution 耐久受理”；受理结果不明时返回 None |
| 回报按身份键找订单；成交按（exchange_id、trade_id、side、order_sys_id）拼成的键去重；`cancelled` 先于成交到达时等待成交 | `:1864-1880`、`:1941-1990`、`:2016-2024` | 子单成交投影为带母单身份的成交事件，`trade_id` 用场所成交号；去重键必须仍然唯一（65.01 核对 CTP TradeID 的唯一范围） |
| 启动对账：`orders`/`active_orders` 按身份键匹配未决标记；不匹配的活动委托计为外部（`foreign_working_orders`）；成交按场所订单号归组 | `:577-600`、`:671-681` | 账户事实中本策略的子单必须折叠为母单；否则子单会被当成外部委托，或在 63.06 中被当成本策略可接管的委托而重复计算 |

| 撤单把身份交给 `cancel_order(target_identity=)` | `:1703-1748`、`:1778-1792` | SDK 按母单号把撤单路由为母单撤单 |

### 1.6 冲突与不足

1. **派发归属的文档冲突。** `BT: docs/TRADING_SYSTEM_ARCHITECTURE.md:84` 把“本地订单意图、派发、恢复与 UNKNOWN”归给 execution；迭代 10 的 AFI 规格把“最终派发”和“策略/人工 book 归属”也归给 execution（`bt_api_py/docs/迭代计划/迭代10-可选组件与可配置通信/ai-for-investor接入与组合风控职责迁移.md:16`、`:23`、`:124`）。按 63 方案 A 与原话 3，派发与每策略归属在 Gateway；execution 只负责母单、子单计划、算法进度和成交到母单的分配（63 分析:126）。
2. **现有 execution 是派发 owner 形态。** `account_owner` 直接持有 provider 端口（§1.2 第 6 项）。新服务需要的是 Gateway 的客户端，而不是又一个派发 owner。
3. **配置键冲突。** 若把执行路由写进 `execution_config` 或 §1.3 的 12 个键，BT 会离开 direct/Gateway 路径（`btapistore.py:410-418`），等于让 BT 感知 execution。
4. **委托只有字段，没有授权语义。** `WireIdentity` 有 `actor_ref`、`delegate_ref`，注释写明是 untrusted sender claims（`base: service_protocol.py:194-206`）；ServiceHost 只在行情身份上拒绝 `delegate_ref`（`SDK: service_host.py:738`），非行情端口是否核验委托没有核实。线上声明不能作为“代表策略 X”的授权（INV-05）。已列入 63.13：代理 principal 的授权以 Gateway 的登记为准。
5. **没有母单信封。** Gateway（63 草案初稿）只有逐单预留，没有记录母单总量、方向、开平、价格上限和期限的耐久信封。execution 有缺陷时可以发出超过母单的子单，而 Gateway 无从发现。按 D65-01 a 由 63.13 实现；开 risk 时 risk 的母单预留另行约束数量（64 计划 §3.3）。
6. **子单幂等需要调用方键。** 已纳入 63 计划 §3.4、§3.5 的 `request_key`；子单以 `child_id` 作为该键，经 risk 转发时沿用。
7. **行情。** 算法需要盘口和成交量；execution 目前没有任何行情入口，而 MarketHub 的 principal 和键集合是静态给定的（63 计划 §3.3、D63-13）。execution 的行情 principal 已列入 63.13。
8. **原话 2 的文档影响。** 62 计划目标 3、63 分析 §5.2/§5.3 的 direct + risk、direct + execution 条目需随 U65-4 修改；63、64 计划已在 2026-11-06 晚修订，其余见 §9。

## 2. 目标、非目标与新增规则

### 2.1 目标

1. **独立进程。** execution 作为独立的服务进程运行（ServiceHost + CURVE，同主机 loopback），有自己的日志、配置和生命周期；它崩溃不影响 Gateway 和策略进程（U65-1）。
2. **以 Gateway 为前提。** 只有开启 Gateway 时才可以启用；Gateway 未开启而配置了 execution 时以有限错误码拒绝启动；未选择时任何进程都不导入 `bt_api_execution`（U65-4、INV-01）。
3. **BT 不感知。** BT 产品代码不改；`bt_api_py` 按配置把命中规则的 BT 订单作为母单交给 execution，其余订单按 63 方案直通 Gateway；母单对 BT 投影为一笔普通订单（§1.4）。
4. **子单只经 Gateway 派发。** 子单走 Gateway 唯一派发点，受同样的授权、归属、流控与急停约束；开 risk 时子单先经 risk 服务（execution → risk → Gateway，与普通订单同一路径，64 计划 §4.2）；Gateway 用母单委托信封限制子单（D65-01 a）。
5. **母子两级风控。** execution 受理母单后经 risk 服务整笔预留（`risk.parent.reserve`），子单在 risk 服务逐单 claim（64 合同）；未开 risk 时没有这两级风控。
6. **崩溃安全与幂等。** 每个崩溃点都能按身份恢复；子单结果不明保持 UNKNOWN，不重发；execution 崩溃只冻结母单（U65-1）。
7. **算法 MVP。** SLICE（按最大子单量拆分）与 TWAP（§4.1）。
8. **适合以后集成 ai-for-investor。** 母单接口与 BT 无关，其他已认证主体（如人工 book）也能使用（§3.12）。
9. **验收。** 回环集成（INTEGRATION_SIM），以及 SimNow 上 1 个 Gateway + 1 个 execution + 2 个策略。

### 2.2 非目标

- 基础转发（归 Gateway，迭代 63）；风控政策（归 risk，迭代 64）；急停（状态与执行在 Gateway，U65-7，迭代 63）。
- 修改 `bt_api_gateway`：本迭代需要的 Gateway 侧能力都在迭代 63 的 63.13（U65-9）；发现缺口时提回 63。
- 合并执行（同向合并或跨策略轧差）的实现：本迭代只给出可行性和记账分析（§4.3），实现需 D65-09 之后另行安排。
- VWAP、POV、冰山、盯价的实现（§4.2，后续阶段）。
- 母单改单（amend）：64 计划把“CTP 无改单”记为 provider 事实（64 计划 §3.2 R-04），本仓库未另行核实；母单只能撤销后重下。
- 跨交易日母单；跨主机部署；execution 高可用或主备；多个 execution 实例服务同一账户。
- direct + execution（U65-4）；修改 direct 路径；退役迭代 60 托管 execution 路径（D65-11）。
- 集成 ai-for-investor；OKX/Binance（同 D63-10 a）；生产账户验证。

### 2.3 本迭代新增规则

| ID | 规则 |
| --- | --- |
| INV65-01 | execution 只在开启 Gateway 时可选：策略进程在任何模式下都不导入 `bt_api_execution`；未选择时 Gateway 进程也不导入；Gateway 未开启而配置了 execution 时以有限码拒绝启动，不忽略该配置。以隔离进程的全生命周期导入观测为证。 |
| INV65-02 | execution 进程不持有 provider 会话、凭据或原生库，不导入 `bt_api_ctp.ctp.client`，也不导入 `bt_api_risk`（经 bt_api_py 的 risk 服务客户端调用）；子单只经 Gateway 派发，开 risk 时先经 risk 服务（INV63-01、INV63-02 推广到 execution）。 |
| INV65-03 | 子单不得超出母单信封：合约、方向、开平、交易日一致，价格不越母单限价，时间不超过母单期限；Σ（已派发 + 在途 + UNKNOWN 子单数量）≤ 母单数量。按 D65-01 a 由 Gateway 强制（63.13），不依赖 execution 自律；开 risk 时 risk 的母单预留另行约束（64 计划 §3.3）。 |
| INV65-04 | execution 只能代表把母单委托给它的策略行事，委托以 Gateway 自己的母单记录为准，不以线上 `delegate_ref` 声明为准（INV-05）；它不能撤销、查询或平掉不属于其子单的委托和持仓。开 risk 时子单由 risk 服务转发，Gateway 核对 risk 服务可代表该策略、母单属于该策略且处于 ACTIVE；“由 execution 发起”的声明只作审计。 |
| INV65-05 | 成交归属到哪个策略以 Gateway 归属账本为准（INV63-04）；execution 只记录子单成交到母单的分配，不另立持仓权威。 |
| INV65-06 | 被路由到 execution 的订单，在 execution 不可用、母单被拒或结果不明时，不降级为直通单（INV-02；63 分析:259）。 |
| INV65-07 | BT 产品代码不因 execution 而改动，母单对 BT 的投影由 SDK 完成；做不到时停止并请用户决定（D65-03）。 |
| INV65-08 | 必填的限额和算法参数没有缺省值；缺失即该路由不可用，启动时以有限码拒绝。 |

## 3. 架构

### 3.1 总览

进程：策略进程 ×N（BT 不变）；Gateway（每账户一个，63）；risk 服务（每账户一个，可选，64）；execution 服务（每账户一个，D65-13）。execution 是 Gateway 的客户端（execution principal），开 risk 时也是 risk 服务的客户端；它不连 CTP。

```text
命中执行路由的 BT 订单（按推荐的 D65-01 a）：
① 策略 SDK ── parent.authorize（母单委托信封，只是授权记录，不发往场所）──▶ Gateway   → PARENT_AUTHORIZED
② BT 写 PREPARED（含 parent_ref）
③ 策略 SDK ── parent.submit ──▶ execution ──[开 risk]── risk.parent.reserve ──▶ risk 服务
                                execution ── parent.accept ──▶ Gateway                  → PARENT_ACTIVE
④ 子单：execution ──[开 risk]── risk.order.reserve / dispatch ──▶ risk 服务 ── 转发 ──▶ Gateway ──▶ CTP
         execution ──[未开 risk]──────── direct.reserve / dispatch ──────────────────▶ Gateway ──▶ CTP
         子单撤单：execution ── direct.cancel ──▶ Gateway（不经 risk）
⑤ 回报：Gateway ──▶ 本策略流（带 parent_ref，SDK 投影为母单）、execution 流、risk 观察流
未命中执行路由的 BT 订单：按 63 计划 §3.18 直通（开 risk 时经 risk）。
```

该图表达职责分层，名称在 65.01 冻结。这条路径与 63 计划 §3.18、64 计划 §3.3 和 §4.5 一致：Gateway 不调用 risk；risk 位于所有到达 Gateway 的下单请求之前（开启时）；母单的整笔风控由 execution 经 risk 服务申请。推荐 D65-01 a 的理由：信封由 Gateway 强制，不依赖 execution 自律，也不依赖是否开启 risk；母单与子单的记录都能在 Gateway 日志里核对；BT 订单按 S-08 由 bt_api_py 交给 execution（第③步）。在 Gateway 登记的只是授权记录，不是发往场所的订单，所以不违反“订单先经 risk 再到 Gateway”（U65-5）；若用户不这样理解，见 D65-01 b。

### 3.2 BT 订单怎样被路由（SDK）

- 路由在策略进程的 `bt_api_py` Gateway route 内进行，位于 63.05 远端 `DirectWriteProvider` 之前：`make_order(OrderRequest, pre_dispatch_commit, host_scope)` 先按规则匹配，未命中走 63 的直通路径（开 risk 时经 risk 服务），命中走 §3.1 的①～③。
- 规则分两层（D65-02 c）：账户级（运营，Gateway 账户配置）给出每个策略可用的算法、合约、单个母单的数量上限、子单与撤单预算；策略级（策略作者，策略 `config.yaml` 的 `gateway.execution` 段）在这个范围内选择。生效规则 = 策略规则 ∩ 账户允许；策略规则超出账户允许时启动失败（P5，63 分析:71）。
- 匹配维度：合约、方向、开平、订单类型（MVP 只有限价，D65-07）、数量阈值（如 ≥ N 手）。自上而下取第一条命中；没有命中就直通。不按信号或指标匹配，因为 BT 不传执行指令（原话 1）。
- 规则在启动时校验并冻结。Gateway 对未授权的 `parent.authorize`（策略无权委托给该 execution、合约不在白名单）拒 `execution_not_authorized`，这是 Gateway 的授权。Gateway 是否还要拒绝“命中规则却走直通”的订单（`execution_route_required`），见 D65-15：与 Gateway 不检查风控批准（U65-6）同理，推荐不做，执行路由由 bt_api_py 的配置决定，配置漂移造成的绕过是已接受的性质。
- 配置键必须位于 SDK 解析的 Gateway route 选项内，不得使用 `execution_config` 或 `DIRECT_EXECUTION_CONFIG_KEYS`（§1.6 第 3 项）；BT 只透传，不解析。
- 命中规则但 execution 不可用（未启动、租约失效、母单被拒）：该订单以有限码拒绝（确定未发送），不降级为直通（INV65-06）；未命中的订单照常直通（D65-10）。

### 3.3 母单接口（按 D65-01 a；名称在 65.01 冻结）

Gateway 一侧的操作由迭代 63 的 63.13 实现（U65-9），本迭代只使用；execution 一侧的操作由本迭代实现。

| 操作 | 所在 | 调用方 | 语义 |
| --- | --- | --- | --- |
| `parent.authorize` | Gateway | 策略 SDK（以后也可以是人工 book 主体） | Gateway 校验授权（该策略可委托给 execution principal E、合约白名单）、信封参数与急停（63 计划 §3.17；开仓母单遇 STOP_NEW、任何母单遇 FREEZE/DRAIN 即拒）；平仓母单按整笔预留本策略可平容量（归属，63 计划 §3.11）；写 PARENT_AUTHORIZED（Gateway 生成的母单号 `parent_ref`、请求摘要、到期时间）。不调用 risk。拒绝即确定未开始 |
| `parent.release` | Gateway | 策略 SDK、execution | 释放尚未 accept 的授权 |
| `parent.submit(parent_ref, 算法与参数)` | execution | 策略 SDK（BT 未决标记 PREPARED 之后） | execution 读取 Gateway 上的信封并核对自己是委托方 → 写日志 PARENT_RECEIVED → 开 risk 时调 `risk.parent.reserve` → 调 Gateway `parent.accept`；任一步拒绝即确定未开始，并 `parent.release`；同号幂等 |
| `parent.accept`、`parent.complete(parent_ref, 原因)` | Gateway | execution | accept：PARENT_AUTHORIZED → PARENT_ACTIVE，信封开始受理子单；complete：所有子单终态且没有 UNKNOWN 之后宣布母单结束（FILLED、CANCELLED_REMAINDER、EXPIRED） |
| `parent.cancel(parent_ref)` | Gateway | 策略 SDK、运营 | 立即冻结信封（不再受理子单预留）；按 D65-06 由 Gateway 直接撤销该母单的活动子单；经 execution 流通知 execution |
| `parent.status`、`parent.list` | Gateway；execution 提供算法进度 | 策略 SDK、运营、以后的 AFI | 母单状态、累计成交、在途与 UNKNOWN 子单数、冻结原因 |
| 子单 `direct.reserve(…, origin, on_behalf_of, parent_ref, child_id)`，以及 `direct.dispatch`、`direct.command_status` | Gateway | 未开 risk：execution；开 risk：risk 服务转发 execution 的子单（64 计划 §4.2） | 63 的逐单操作；`child_id` 是调用方幂等键（63 计划 §3.4 的 `request_key`） |
| 子单 `direct.cancel` | Gateway | execution（不经 risk） | 只能撤它自己母单的子单 |
| `execution.lease` | Gateway | execution | 心跳续租；租约失效 → 冻结其全部母单（U65-1 a1） |

母单状态：PARENT_AUTHORIZED → PARENT_ACTIVE（⇄ FROZEN，恢复规则见 D65-05）→ ENDING → FILLED / CANCELLED_REMAINDER / EXPIRED；PARENT_AUTHORIZED 到期或被释放 → EXPIRED_NOT_STARTED。母单的 FROZEN 是母单状态，语义与统一词汇的 FREEZE 一致（拒新子单、放行撤单），但它不是急停范围，不写入 Gateway 急停状态（63 计划 §3.19）。没有改单操作（§2.2）。

### 3.4 母子身份

- 身份链：BT（策略 UUID、局部序号、`Order.ref`）→ 母单号 `parent_ref`（Gateway 生成的 UUID4）→ 子单号 `child_id`（execution 生成，= `parent_ref` + 序号，先写入 execution 日志再发请求）→ Gateway `reservation_id` → 原生身份（交易日、FrontID、SessionID、OrderRef，派发时分配，63 计划 §3.4）→ 场所身份（ExchangeID、OrderSysID）。
- `origin` 取值为 `self`、`execution:<execution principal>`，经 risk 转发时为 `risk:<risk principal>`（63 计划 §3.5），同时带 `on_behalf_of`（母单所属策略）与 `parent_ref`；记入归属账本的策略是母单的策略，不是 execution 或 risk（INV65-05）。
- 母单对 BT 的身份：`NativeOrderIdentity(exchange_name, client_order_id=<由 parent_ref 派生的母单号>, fields={parent_ref, trading_day})`，不含任何子单原生字段（§1.4）。
- MVP 中每个子单只属于一个母单；`FillAllocation`（`exec: contracts.py:758`）在一对一时就是恒等分配。

### 3.5 子单怎样到达唯一派发点

1. execution 写 CHILD_PLANNED（child_id、数量、价格规则），再发出子单预留：开 risk 时调 `risk.order.reserve`（带 `parent_ref`、`child_id`），由 risk 预留并从母单预留中扣减后转发 Gateway `direct.reserve`；未开 risk 时直接调 Gateway `direct.reserve(origin=execution:<E>, on_behalf_of, parent_ref, child_id)`。
2. Gateway 在预留时核对信封（INV65-03）、母单处于 ACTIVE、代理关系（INV65-04）、母单所属策略和代理两级流控份额、急停，以及 63 的其余逐单检查（63 计划 §3.5）。
3. execution 写 CHILD_RESERVED（reservation_id），再发出派发：开 risk 时调 `risk.order.dispatch`，risk 在自己的事务内 claim（自成交、计数等）并提交后转发 Gateway `direct.dispatch`；未开 risk 时直接调 Gateway `direct.dispatch`。Gateway 在派发锁内复查急停 → 写 DISPATCHING → grant → 原生调用。execution 不直接操作 risk 账本。
4. 确定未发送（`gateway_rate_limited`、`kill_switch_*`、`risk_*`、`risk_self_trade` 等）：execution 可在 D65-14 的重试预算内用新的 child_id 重试；预算用尽即冻结母单并报告。结果不明（包括调用 `risk.order.dispatch` 超时，64 计划 INV64-08）：该子单 UNKNOWN，母单停止切片，不补发（63 分析:135）。
5. 子单撤单（时间片结束、未成余量）：execution 直接调 Gateway `direct.cancel`，不经 risk（64 计划 INV64-11）；Gateway 核对目标是该 execution 母单的子单；risk 从观察流把撤单计入 R-04。

### 3.6 成交归属与对 BT 的投影

- Gateway 收到子单回报后按身份路由（63 计划 §3.7），在同一事务里记入母单所属策略的归属账本，并写入该策略的回报流（带 `origin`、`parent_ref`、`child_id`）和 execution 回报流。
- 策略 SDK 把带 `parent_ref` 的子单事件投影为母单事件：成交事件 = 母单身份 + 场所成交号、价格、数量、开平；订单事件 = 母单累计值（order_qty = 母单量，filled_qty = Σ 子单成交，remaining_qty = 两者之差）；母单 ACTIVE 时投影 `accepted`；收到 `parent.complete` 后投影终态（`filled`，或带累计成交的 `cancelled`）。子单自己的 accepted、cancelled、rejected 不投影给 BT。
- 账户事实（63 的 `direct.account_facts`）：本策略带 `parent_ref` 的子单委托和成交折叠为母单（§1.4）；其他策略的子单按 63 的“其他策略”标签计数（D63-01）。
- execution 只用 execution 回报流推进算法，不读策略流；子单成交到母单的分配写在 execution 日志里，只用于算法和报告。

### 3.7 风控（迭代 64 的 API）

调用路径与 64 计划 §3.3、§4.2 一致（原 D65-12 已由 U65-5 消解：Gateway 不调用 risk，所以 `reserve_parent` 不可能由 Gateway 调用）：

| 层级 | 调用 | 调用方 | 依据 |
| --- | --- | --- | --- |
| 母单 | `risk.parent.reserve`（即 `reserve_parent`）：整笔检查 R-03 持仓、R-07 亏损、策略额度，记录母单范围；R-01 单笔上限、R-02 价格带不按母单查 | execution，在 `parent.submit` 受理之后、`parent.accept` 之前 | 64 计划 §3.3 |
| 子单 | `risk.order.reserve`（带 `parent_ref`，从母单扣减，超出母单即拒 `risk_parent_envelope_exceeded`）→ `risk.order.dispatch`（risk 内 claim，提交后转发 Gateway） | execution | 64 计划 §3.3、§4.2 |
| 子单结算 | risk 按 Gateway 结果与观察流结算 | risk 服务自身 | 64 计划 §4.2 第 6、8 行 |
| 母单结束 | `risk.parent.release` 释放未用部分；有 UNKNOWN 子单的母单保持占用 | execution（risk 另从观察流核对） | 64 计划 §3.3 |

- 未选 risk 时，母单只受 Gateway 的信封、授权、归属、流控与急停约束（S-02 选 B 后，单笔上限等不在 Gateway）；execution 不因此获得额外控制，也不另做风控。
- 选中 risk 但不可用时按 D64-02（拒 OPEN 与 CLOSE）：母单受理（`risk.parent.reserve`）和子单预留都拒绝，不改为直达 Gateway；撤单（包括撤母单时撤销子单）直达 Gateway，不受影响。
- Gateway 不检查风控批准（U65-6）：若 execution 在开 risk 的配置下被误配为直达 Gateway，子单照常受理，risk 只能事后从观察流看到（64 计划 INV64-10）。这是已接受的性质；Gateway 的母单信封仍然约束子单。

### 3.8 持久化、崩溃恢复与幂等

BT `live_state`、Gateway 日志、execution 日志、risk 账本四个存储彼此不原子。次序规则沿用 63 分析:142：原生调用只发生在所有相关耐久记录之后；恢复按身份查询，不按时间推测。

| 序 | 步骤 | 耐久位置 | 在此之后崩溃 | 恢复 |
| --- | --- | --- | --- | --- |
| 1 | BT 分配局部序号 | `live_state` | — | 63 不变 |
| 2 | `parent.authorize` → PARENT_AUTHORIZED | Gateway | 策略崩溃 | 到期转 EXPIRED_NOT_STARTED，释放本策略可平容量；确定未开始 |
| 3 | BT 标记 PREPARED（含母单号） | `live_state` | execution 未收到 submit | 同上；策略重启后按母单号查 Gateway `parent.status` |
| 4 | SDK → execution `parent.submit` → PARENT_RECEIVED | execution 日志 | 回复丢失 | 同号重发幂等；SDK 以 Gateway `parent.status` 判定；仍为 AUTHORIZED 时等到期或重发 |
| 5 | （开 risk）execution → `risk.parent.reserve` | risk | execution 在 accept 前崩溃 | execution 重启读日志：未 accept 的母单一律 `risk.parent.release` 并 `parent.release`，确定未开始；risk 预留另有 TTL 兜底 |
| 6 | execution → Gateway `parent.accept` → PARENT_ACTIVE | Gateway | 回复丢失 | 同号重发幂等；SDK 收到 execution 的受理回复后 BT 记 DISPATCHED（sent 的含义见 §1.4）；回复丢失时 SDK 报告结果不明，按 `parent.status` 解决 |
| 7 | CHILD_PLANNED | execution | execution 崩溃 | 重启后按 `child_id`（= `request_key`）查 Gateway，开 risk 时也查 risk：没有预留 → 确定未预留；有 → 继续使用 |
| 8 | 子单预留：risk 预留与母单扣减（开 risk）→ Gateway RESERVED 与信封扣减 | risk、Gateway | execution 或 risk 崩溃 | 预留到期 → 确定未发送，信封与 risk 回补（64 计划 §4.3） |
| 9 | 子单派发：risk claim（开 risk）→ Gateway DISPATCHING → 原生调用 → SENT / NOT_SENT / UNKNOWN | risk、Gateway | 任一方崩溃 | 64 计划 §4.3；63 计划 §3.6 第 5–7 行 |
| 10 | 子单回报 → 策略流 + execution 流 + 归属账本（同一事务）；risk 观察流 | Gateway | 消费方崩溃 | 游标重放，按成交键去重 |
| 11 | `parent.complete` → `risk.parent.release` | Gateway、execution、risk | — | 只在所有子单终态且无 UNKNOWN 后接受 |

- **execution 崩溃（U65-1）。** 租约失效 → Gateway 冻结它的全部母单（不再受理子单预留，在途预留到期作废）；活动子单留在场所，照常回报；BT 订单保持活动；risk 对这些母单的预留保持。重启后 execution 读日志，按 child_id 和 reservation_id 向 Gateway（开 risk 时也向 risk）查询；是否恢复切片按 D65-05。
- **risk 崩溃（开 risk 时）。** 子单预留与派发按 64 计划 §4.3 处理；risk 不可用期间 execution 不切片（子单预留被拒，不改为直达 Gateway，INV65-06），撤子单不受影响。
- **Gateway 崩溃。** 按 63 计划 §3.12 恢复，先解决 DISPATCHING。期间 execution 看到 `gateway_unavailable`，不切片。
- **策略崩溃。** 母单已被 Gateway 和 execution 受理，照常执行；BT 重启后按母单号恢复订单（§1.4 第 6 行）。
- **幂等键。** `parent_ref`（Gateway 生成）、`parent.authorize` 的调用方请求号（由 BT 局部序号派生，即 63 的 `request_key`）、`child_id`、`reservation_id`、撤单命令号；同号同内容返回已记录的结果，同号不同内容拒绝（沿用 63 计划 §3.5）。
- **分工。** 母单信封和母子映射在 Gateway 日志；母单进度和算法状态在 execution 日志；母单与子单的风控占用在 risk 账本。execution 日志损坏 → execution 拒绝启动，Gateway 侧母单保持冻结，策略仍可撤母单（D65-06）。

### 3.9 日切、结算、交易时段与流控

- 母单绑定受理时的交易日（D65-04）。Gateway 处于 `trading_day_switch_pending`（63 计划 §3.9）时拒绝新的子单预留；交易日最后一个交易时段结束前，execution 停止切片，未成部分在所有子单终态后以 EXPIRED 结束。
- 时段：只在合约的交易时段内下子单，午休、夜盘与日盘之间暂停。时段表取 provider 声明（`bt_api_ctp.trading_session_schedule`，只依赖 base 协议，63 计划 §3.16）；execution 进程直接导入该模块还是由 Gateway 发布时段表，65.01 决定，前者不得引入原生库（INV65-02）。
- 结算确认只由 Gateway 做（D63-14）；execution 在 `day_ready` 之前不切片。
- 流控：子单占用母单所属策略的份额，另设 execution 总份额上限（运营填写）；撤单使用保留容量（63 计划 §3.10）。遇 `gateway_rate_limited` 时退避，不自旋。
- 查询：execution 不触发原生账户查询；子单状态来自 execution 回报流和 `direct.command_status`（63 计划 §3.6），不额外占用单查询槽（63 计划 §3.8）。

### 3.10 安全

- execution 进程不持有 CTP 凭据（INV65-02）。它与 Gateway 之间用 CURVE；私钥文件权限 0600，由运营工具生成，不经 argv 或日志（沿用 63 计划 §3.13 与 D63-13 a 的静态登记）。
- 委托：策略 principal 的 grant 增加“允许委托给 execution principal E”；Gateway 在 `parent.authorize` 时把母单绑定到 E，`parent.accept` 只接受 E；子单请求（E 直达，或经 risk 服务转发）都按 Gateway 自己的母单记录核对（INV65-04），线上 `delegate_ref` 只作审计。
- E 的 grant 只含：读取委托给它的母单信封、`parent.accept`/`complete`、子单预留、派发、撤单（限其母单）；子单状态；execution 回报流；所需合约的行情。不含账户全量事实、其他策略的回报流、结算、急停命令。开 risk 时，E 另有 risk 服务的客户端身份（64 计划 §6.1）。
- 运营可以只冻结 E（冻结 E 的全部母单）；FREEZE、STOP_NEW、DRAIN 对子单的作用与对普通订单相同，按子单所属策略匹配范围；急停状态由 Gateway 持有并执行（U65-7，63 计划 §3.17）。

### 3.11 可观测性

- execution 日志 → monitor：复用 `service_execution_monitor` 的中继模式（只读游标、owner 线程 poll、不在下单路径上，`SDK: service_execution_monitor.py:1-12`）。事件：母单受理、冻结、结束；子单拒绝码分布；UNKNOWN 子单；调度滞后；撤单预算消耗；滑点（`ExecutionQualityRecord`，须有到达价与成交证据）。
- Gateway 状态（63 计划 §3.14）增加：每个 execution principal 的租约、活动母单数、冻结母单数（由 63.13 实现）。
- monitor 缺省可选，只观察，不发控制命令（U65-8）。`monitor_required`（U65-2）是 Gateway 根据自己观察到的 monitor 存活作出的判定，与 execution 租约无关：execution 租约失效只冻结它的母单，不触发账户级 STOP_NEW。
- BT 订单看不到“母单冻结”和“子单 UNKNOWN”（§1.4 结论）；SDK 在 Gateway route 的状态报告里提供这两项，monitor 告警。按 D65-03 a，不为此改 BT。

### 3.12 面向 ai-for-investor 的接口约束（不实现集成）

- 母单接口只依赖 base 中立类型（Decimal 数量、显式开平、限价、期限、算法名与版本化参数），不出现 BT 类型。主体可以是策略（`WireScope.strategy_ref`），也可以是人工 book（`manual_book_ref`，`base: service_protocol.py:211-219` 已有该字段）。
- 状态、撤单、列表和事件游标都经同一服务协议读取；AFI 的 HTTP/WS 适配归 AFI（迭代 10 AFI 规格:16 的分工）。但该规格中“execution 负责最终派发与策略归属”的表述需随本计划修改（§9）。
- 算法参数 schema 带版本号，拒绝未知键，便于前端生成表单。

## 4. 算法目录与分期

### 4.1 MVP（迭代 65）

| 算法 | 行为 | 参数（必填，无缺省） | 需要的事实 |
| --- | --- | --- | --- |
| PASS | 整笔作为一个子单；只在规则显式选择时使用，用于打通链路和测试。与直通的区别是它经过母单与信封 | — | — |
| SLICE | 按最大子单量顺序拆分；前一子单终态后再发下一笔 | `max_child_qty`；`child_price`（`limit` = 母单价、`passive`、`cross`，都不越母单限价）；`child_timeout_s` | `passive`、`cross` 需要一档行情 |
| TWAP | 在[开始, 结束]内按时间片均分，时段外暂停；每片未成余量撤销并滚入下一片；结束后未成部分不追单 | `duration_s` 或 `end_time`；`slices`；`child_price`；`max_cancels_per_parent` | 时段表；`passive`、`cross` 需要一档行情 |

共同约束：子单只用限价，不越母单限价；平仓母单的子单与母单开平相同（SHFE/INE 的平今、平昨由 BT 显式给出，D62-26）；母单只接受限价（D65-07）；子单数和撤单数受预算限制；行情过期时暂停切片，不按旧价下单；每个调度决定都能在测试中用假时钟和假行情重放。

### 4.2 后续阶段

| 阶段 | 算法 | 前置与限制 |
| --- | --- | --- |
| E2 | 冰山（显示量 + 补单） | CTP 是否有原生冰山未核实（65.01 核对 provider）；每次补单都是新子单，报单与撤单计数上升 |
| E2 | 盯价（smart limit pegging） | 改价 = 撤单 + 新单（64 计划 §3.2 R-04）；必须有撤单预算和 R-04 阈值；行情快照粒度未实测（UNKNOWN） |
| E3 | POV（按成交量比例） | 需要实时成交量：可用行情累计成交量的差分，但快照粒度和丢包的影响未知 |
| E3 | VWAP | 需要日内成交量分布，本仓库没有数据来源（UNKNOWN），需另定来源 |
| E3 以后 | 合并执行 | 见 §4.3 与 D65-09 |

### 4.3 合并执行（跨策略）的可行性与记账影响

| 方式 | 做法 | 与 63 每策略账本的关系 | 判断 |
| --- | --- | --- | --- |
| 同向合并 | 同账户、同合约、同方向、同开平的多个母单合成一个子单流 | 一笔场所成交要分给多个策略，需要确定的分配规则（按比例、按到达顺序等），期货整手分配会有余数；这改变了 63 “一个预留对应一个策略”的归属模型，INV63-04 需改为“按分配记录归属” | 可行，但需要新的分配合同；只有在子单数或撤单数受限时收益才明显 |
| 跨策略轧差 | A 买 5、B 卖 3 → 只发净买 2，内部转移 3 | 那 3 手没有场所成交：A、B 账本的变化没有场所证据，违反 INV-09 和 INV63-04“由已归属成交更新”；CTP 显式开平下，B 的卖可能是平仓、A 的买是开仓，场所持仓的今昨结构不变而策略账本变了，SHFE/INE 平今平昨的归属随之失真；内部转移价格是策略之间的利益分配；BT 会收到没有场所成交号的成交 | **不建议用于 CTP**；需要用户另行决定，并需要新的账本与对账模型 |
| 顺序协调（不合并） | 不合成订单，只避免两个策略的子单互相成交（如反向挂单存在时暂停切片） | 归属不变 | 可作为自成交拒绝的缓解，放在 E2 |

结论：迭代 65 不实现合并执行，只交付本节分析，由用户决定是否、以哪种方式进入后续迭代（D65-09）。

## 5. 配置（`config.yaml`，跨平台）

键名在 65.01 冻结；尖括号表示运营或策略作者必须填写的值，不提供缺省。

```yaml
# 账户级 Gateway 配置（运营；63 D63-08 a 的账户文件夹；Gateway 读取这些授权由 63.13 实现）
components:
  execution:
    enabled: true                      # 需要 Gateway；false 或缺失 → 不登记 execution principal
    principals:
      - name: exec-a
        public_key_file: keys/exec-a.pub
        lease_seconds: <运营填写>
        max_child_rate_per_second: <运营填写>   # execution 总份额，计入账户流控
    allow:                             # 每个策略可用的上限；策略配置只能更窄
      - strategy_uuid: <策略目录 state/identity.json 中的 UUID>
        delegate_to: exec-a
        algorithms: [slice, twap]
        instruments: [rb2701]
        max_parent_qty: {rb2701: <运营填写>}
        max_children_per_parent: <运营填写>
        max_cancels_per_parent: <运营填写>
        max_child_retries: <运营填写>  # 缺失即 0 次（D65-14）
```

```yaml
# execution 服务目录 config.yaml（运营）
gateway:
  connection_file: state/gateway_connection.json
  client_key_file: state/exec-a.key   # 0600；不经 argv 或日志
journal: state/execution.sqlite3      # 本地磁盘；不放网络盘
session_schedule: provider            # 或 gateway；65.01 决定
risk:                                 # none，或 risk 服务连接（开 risk 时母单与子单经 risk，64 计划 §3.3）
  connection_file: state/risk_connection.json
listen: {bind: 127.0.0.1, port: <运营填写>}   # 供策略 SDK 调 parent.submit；只在本机
monitor: {enabled: false}
```

```yaml
# 策略目录 config.yaml（策略作者；BT 只透传给 SDK，不解析）
access: gateway
gateway:
  connection_file: state/gateway_connection.json
  client_key_file: state/gateway_client.key
  execution:                           # 缺失 = 全部直通
    connection_file: state/execution_connection.json   # SDK 把命中路由的订单交给 execution（S-08）
    routes:                            # 自上而下，取第一条命中
      - match: {instruments: [rb2701], order_types: [limit], min_qty: <策略填写>}
        algorithm: twap
        params: {duration_s: <策略填写>, slices: <策略填写>, child_price: passive, max_cancels_per_parent: <策略填写>}
```

跨平台规则：

- 相对路径一律相对于该 `config.yaml` 所在目录，用 `pathlib` 解析；不展开 `~` 或环境变量，不依赖当前工作目录。
- 传输用 loopback TCP 上的 CURVE ZMQ，不用 `ipc://`（Windows 上没有同样语义）。
- SQLite 只放本地磁盘，网络盘上的文件锁不可靠。
- 私钥文件权限：POSIX 检查 0600；Windows 的 ACL 检查方式未定（UNKNOWN，65.01 与 63 一并决定）；不能检查时拒绝启动，而不是忽略。
- 时间：调度用交易所时区（CTP 为 Asia/Shanghai）和 provider 时段表，不用本机时区；时钟质量沿用 D62-21/27/28。
- 未知键、类型错误、策略规则超出账户允许、执行路由写在 `execution_config` 等 BT 选择键下，都在启动时以有限码拒绝。
