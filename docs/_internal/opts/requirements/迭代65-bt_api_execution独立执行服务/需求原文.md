## 3. 解读说明（起草人注，非用户原话）

- 原话 1 与 63 分析 S-08 的两个候选（a：仍用 `make_order`，加可选执行指令；b：新的母单 API，63 分析:321）都不完全相同：BT 既不加执行指令，也不调用新 API，由 `bt_api_py` 按配置决定哪些订单交给 execution。计划按“BT 产品代码不改”理解，并在计划 §1.4、D65-03 中说明这一理解的边界和未证明之处。
- 原话 1 中的“继承到ai-for-investor”，按上下文理解为“集成到 ai-for-investor”；原文照录不改。集成本身不在迭代 65 范围内，迭代 65 只要求接口适合以后集成。
- 原话 1 中的“合并执行”可能指（i）把同方向订单合成一笔发出，或（ii）跨策略轧差（买卖相抵后只发净额）。两者的记账后果不同（计划 §4.3），本迭代不擅自选定，作为 D65-09 提出。
- 原话 1 中的“拆单”与迭代 62 的 D62-18“不自动拆单”不冲突：D62-18 约束 direct 路径和 Gateway 直通路径上框架与 SDK 的行为；execution 的拆单只在运营和策略显式配置了执行路由时发生。
- 原话 2 中的“修改一下相关的文档吧”：需要修改的文档列在计划 §9，由主会话记入各迭代的计划修改记录；本文件和计划不直接改其他迭代的正文。
- 迭代 64 需求原文的原话 4 截至“放到迭代65中”；本文件第 1 条按主会话转来的全文（含“写一个新的迭代文档，后续会集中进行开发”）记录。
- U65-1、U65-2 由主会话以英文转述后译出，措辞以用户原意为准；如有出入，以用户更正为准。
- U65-5 与计划初稿的 D65-12 建议（由 Gateway 在母单预留时调用 `reserve_parent`）不相容：Gateway 不调用 risk。计划改为由 execution 经 risk 服务调用，并按 U65-5 重拟母单入口（D65-01）。原话 1 的“bt_api_py会负责这个处理，把bt的订单交给bt_api_execution”在重拟后按字面落实：SDK 直接把母单交给 execution；推荐方案另在 Gateway 登记一份母单委托信封，它只是授权记录，不是发往场所的订单。
- U65-6 之后，计划初稿中“Gateway 拒绝命中执行路由却走直通的订单（`execution_route_required`）”与“Gateway 不检查风控批准”同属让 Gateway 核对上游组件的路由；计划把它改为候选 D65-15，推荐不做。

## 4. 主会话归纳的目标（非用户原话，供审阅核对）

- `bt_api_execution` 作为独立进程（微服务形态）运行，承担拆单和算法执行；合并执行视 D65-09 的决定在以后进行。
- 只有开启 `bt_api_gateway` 时才能启用 execution；没有开启 Gateway 时不加载、不启动 execution。
- BT 不感知 execution：`bt_api_py` 按配置把 BT 订单交给 execution，没有命中规则的订单直接经 Gateway 转发。
- execution 的子单经 Gateway 唯一派发点发出，不另开交易所会话；开启 risk 时子单先经 risk 服务。
- execution 崩溃时只冻结母单，已经发出的子单保留。
- 本迭代需要的 Gateway 侧能力在迭代 63 实现，本迭代不改 `bt_api_gateway`。
- 以后集成到 ai-for-investor；迭代 65 只保证接口适合集成。
