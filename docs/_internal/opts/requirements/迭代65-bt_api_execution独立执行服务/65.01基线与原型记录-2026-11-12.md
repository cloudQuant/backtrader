## 7. 停止与双租约审阅草案（未冻结）

已决定的正常 stop/restart 停止阶段取消该策略未完成母单余量并尝试撤其场内子单；仅权威终态和成交水位一致才报告结束，迟到成交和 UNKNOWN 按原身份及最坏占用处理，其他策略不受影响，重启不复活已取消母单。策略租约和 Execution 租约相互独立：前者默认不自动 DRAIN、显式选择时按其原因处理；后者失效冻结相关母单，不因此释放活动或 UNKNOWN 子单。恢复只解除经核对的对应原因和版本，不清除其他阻断。

当前 Gateway 有多原因控制、条件解除和单母单 `CANCEL_REQUESTED` 的本地源码路径；这些不证明 Runtime 的持久批量停止意图、Execution 服务租约、跨日恢复或内转屏障已接通。特别是既有 parent register 与停止屏障的同事务竞争未证明，不能将单个 DRAIN 操作视为完整停止合同。

待 63/65/66 联合冻结的候选是：以带主体、范围、稳定操作 ID 和版本的 Gateway 权威停止屏障，和母单登记、子单预留/派发及内转预留在同一权威事务建立明确先后；持久屏障后按原身份逐一取消并记录各母子单状态。丢回复只按原 ID 查询，旧版本不能解除新原因，租约恢复不能自动清除独立停止原因。此段为审阅候选，不是当前 wire 接口或已实现行为。

故障验证至少覆盖屏障与登记/预留/派发/内转的先后竞争；双租约分别及同时失效、不同原因叠加和旧版本解除；母单 10 手已成 4、挂 2、未发 4 的部分撤成/迟到/UNKNOWN；持久前后崩溃、丢回复、撤权、原计划到期及不相关策略并发。真实组件、替身和选用 Risk 的证据分别登记。

## 8. 母单期限兼容方案候选（未冻结）

按照用户对 D65-03 的选择，首期接受 Gateway 当前可提交的 `Order.valid is None` 订单；带非空 BT `valid` 的订单保留现有明确拒绝。策略选中的 Execution 路由须由配置显式提供母单有效期政策，SDK 命中路由后在首次远端副作用之前，将政策版本、来源、时区、受理基准及一次算定的绝对期限与母单原请求身份一起持久化。具体字段名、配置层级、允许的政策组合和受理基准尚需联合冻结；不能仅在内存计算或将子单的原生 `time_in_force` 当作母单期限。

候选政策包含交易日内到期与显式截止时间。交易日边界、截止时刻和日历来源必须可证明，期限缺失、非法、已过期、时钟或交易日不可证明时拒绝受理或暂停，不能默认为无限期。若实现允许由持续时长计算截止，必须绑定一次明确的受理基准，重放及重启只读取原截止，不从当前时间重新起算。账户授权上限与策略选项如何比较由 65.01 完整 schema 冻结；不允许策略通过更宽期限越过账户授权。

跨日的母单在原截止内才可继续，子单仍遵循实际 provider 的交易日、有效期与会话规则。截止后停止新增子单，活动/在途/UNKNOWN 子单及迟到成交继续按 Gateway 权威事实追踪，不能用到期替代撤成或释放证明。配置变更不回写已受理母单；若无法读取原政策或原截止，保持冻结而不是创建新的期限或母单。

待证明：命中与未命中路由各自的行为；无/坏配置及非空 BT `valid` 无写副作用；交易日截止和跨午夜、夏令时、节假日及缺日历；受理前后崩溃、丢回复和重复同 ID；配置变更、重启、跨日、已截止和 UNKNOWN；确保策略可观察的订单语义和配置期限一致。以上仍是候选设计，不声称当前 SDK 或 Gateway 已提供这些能力。

## 10. Gateway 母单投影待验证边界

现有 Gateway BT 提交为一笔 BT 订单分配一个 request key，持久化该 key、订单 intent 与框架快照，然后调用 SDK 的 reserve/dispatch。Gateway 返回流与该请求的 reservation、摘要、主体、来源身份、合约、方向及数量绑定；现有 Risk 委托分支有专门的持久化绑定，不是通用 Execution 母子单合同。多个真实子单各自的 reservation、原生订单身份和数量不能直接当作母单的原生事实，也不能把某个子单的终态直接当母单终态。

现行 provider-normalized 回报及 Gateway stream 类型没有已验证的内部转移事件入口。内部转移不是交易所成交，不能为了让现有 BT 消费而编造交易所成交、原生身份、来源证明或 ACK。已登记单命令的多笔合成成交及 checkpoint 原型通过，不能外推为多子单或双边内部转移已支持。

`tests/unit/test_iter65_gateway_transfer_prototype.py` 在两个独立真实 BT Gateway 消费者及本地 checkpoint 上验证当前合同边界，**4 passed**：当前 SDK observation 对 `internal_transfer` 类型拒绝，现有事件信封要求命令关联；空流重开不影响各自 checkpoint。该实验没有投递有效内部转移，也没有测成双侧 Position/Order/Trade、通知、原子提交或崩溃重放；这些仍为 GAP/NOT_RUN。协议后续扩展时须相应更新此基线实验，不能把其拒绝断言当成本期最终功能要求。

继续研究的候选是 SDK/Execution 显式持有经过授权的母单到各子单映射，逐笔保留 provider 来源，Gateway/SDK 对策略分配和内部转移建立独立的版本化身份、账本、水位和证据，再验证是否能由现有 BT 消费器合法表达与恢复。这是尚未证明可行的合同探索，不允许改写来源以满足旧校验；当前 BT 回报结构及来源校验能否在零产品改动下满足本期完整要求仍是 GAP。若证明不能，应记录具体不可表达项并按用户选择重新讨论，不擅自削减本期目标。

进一步静态核对：当前 `BtApiBroker` 的 Gateway 消费器绑定精确 SDK client/host 与已登记请求，通知事务也要求下一条已登记事件；不能仅凭 SDK 持有 Broker 引用或调用通知队列就合法注入非场所事件。SDK 现有策略持仓只读接口可能消费将来的 Gateway 权威账本快照，但仅能作为读取方向研究，不能自动证明母单 Order/Trade、通知及重放已更新。用户已确认必须复用现有 `BtApiBroker` 且不修改其源码，故独立替换 Broker 的实验不作为交付方案；不能把 BT 依赖塞入 SDK 中立核心或声称恢复已解决。双边账本事务、来源、顺序/去重、checkpoint、回调及崩溃恢复仍需证明。

现有 `GatewayPendingHost` 的 checkpoint 对事件类型、请求原生身份和已存事件水位有严格约束，不能将内部转移硬塞进现有 native fill 合同。用户要求继续复用现有 Broker，SDK/服务侧需寻找不伪造场所事实且兼容现有校验的机制；测试内独立 Broker 的逐腿内存循环不是双边耐久原子提交，也不是本期交付方案。

按这一约束的源码复核：原 Broker 为一笔 BT 订单持久化一个 request key，要求 event 的 reservation、摘要、主体、数量和原生身份或已验证别名与该请求匹配；普通命令 checkpoint 还要求非空 `NativeOrderIdentity`。现有 Risk 委托分支要求实际 Risk 路由及已持久的委托记录，不能用虚假 Risk 标志代替 Execution。Broker 只处理现有 ORDER/TRADE/ORDER_ERROR/CANCEL_ERROR，直接回报合同将 ORDER/TRADE 定义为场所/provider 来源；普通 `notify()` 也不能绕过已登记事件的通知事务。母单及内部转移本身没有对应原生场所订单，不能凭空填原生身份或将内转伪装为场所成交。SDK 即使扩展其类型和服务事实，也尚须证明这些不变的 Broker 检查可合法满足，及逐笔来源能保真；当前方案为 GAP，不声称理论上所有 SDK 合同重设计都不可能。

另一套旧 execution event 表允许多个外部订单关联同一 client ID，但会直接把子单状态和累计成交投影到 BT 订单，尚不证明母单聚合正确；该旧流与当前 Gateway stream 互斥，Gateway 模式的正常 `next` 也不消费该旧通道。策略持仓只读接口有望读取扩展后的权威虚拟账本，但当前非零 `Position.price` 为 NaN，且不产生 Order/Trade/通知；普通 Gateway `getposition()`/`self.position` 仍不可用。以上不能作为本期完整投影的替代验收。

继续检查发现公开策略账本钩子可投递 `LedgerEvent` 到策略的专门回调，但不会自动推进标准 BT Order/Trade 或其通知；其 `account_book` 绑定还与 Gateway 的策略持仓读取分支冲突。旧 `ServiceExecutionSession` 与 Gateway 通知绑定互斥，且已按用户决定列入退役。直接调用公开的 Broker 通知队列也会在 Gateway 的 armed-event 校验处被拒绝，不能以此绕过来源与持久化合同。这些是当前实现边界，不是对所有未来 SDK 合同的理论不可能证明；继续探索须保留同一 `BtApiBroker`、原有源码及真实来源。

补充源码核对：Gateway 的 `GatewayTradeAttribution` 是同一场内订单真实身份的别名桥，绑定原命令和 reservation，不能当成多个独立子单或内部转移的关联凭证；Broker 同时要求订单大小对应原 intent，成交开平与 intent 一致，因而平今转平昨也须另证明合法投影。普通 Store 更新入口在 Gateway/direct 模式的正常 `next()` 中不消费，旧 managed 路径又不提供此处所需的 Gateway 耐久回放与双边事务，不能作为替代。现阶段未找到满足全部约束的 SDK 单侧实现，不排除未来存在尚未证明的合同设计。

`tests/unit/test_iter65_broker_public_notification_prototype.py` 用真实 `BtApiBroker`、本地 GatewayPendingHost 与既有合成命令验证另一个公开入口，**2 passed**：对内存订单调用公开 `Order.execute` 会改变订单自身成交量，但在没有已登记并 arm 的 Gateway 事件时，再调用公开 `Broker.notify` 并经框架通知入口投递会被 `NOT_ARMED` 拒绝；策略 Trade、Broker Position、持久 checkpoint 和订单快照未推进，重开后 checkpoint/快照保持。该尝试有内存订单副作用，不是可用于真实内转的方案；测试未伪造新的场所事件。`add_order_history` 当前亦未实现。另按源码核对，公开 group 接口依赖已决定退役的旧 `ServiceExecutionSession`，与当前 Gateway stream 绑定互斥；只读策略持仓 getter 不能推进标准订单与 Trade 通知。以上只排除所测现有入口，不证明所有未来 SDK 合同重设计在理论上均不可行。

`tests/unit/test_iter65_gateway_parent_prototype.py` 补充单场所命令的合成旧日迟到向量：先应用 11 月 9 日成交 0.4，取消回报累计 0.7 时等待缺失成交，重开 checkpoint 后收到 11 月 7 日的 0.3 成交，订单转为取消，Position/Trade 均为 0.7；重复事实不重复增加成交或持仓，ACK 推进至序号 9。两个 execution bit 及来源事实保留各自成交日期，但取消使累计 `order.executed.dt` 变为测试数据线时间 11 月 3 日；此差异须纳入时间语义审阅，不能把累计时间当作最后一笔场内成交时间。事件、RPC 和身份均为受控替身，只覆盖一个已绑定命令，不证明真实 CTP 或跨日母子单。

Store 的公开通知队列理论上可携带明确标识来源的自定义消息，但当前是进程内广播，不提供完整的策略隔离、持久 ACK 和重放，也不推进标准 BT Order/Trade；尚未有 Gateway 内转流接线，不能把它作为标准订单或成交投影的替代。

恢复候选应由权威 owner 对双边分录原子提交，消费侧持久保存稳定事件 ID、顺序、来源 sidecar、BT 对象投影、待通知与 cursor 后再 ACK；跨进程/库不假设原子。现有 Strategy 的通知恢复使用框架内部钩子，单凭公开 Broker 接口尚不能证明回调前 Trade 状态及通知批次原子持久化，需逐版本验证或明确新合同。回调已执行但确认前崩溃可能重投，外部策略副作用不能由本地快照保证恰好一次，须由消费方基于稳定 ID 幂等处理或保留明确的不确定状态。该段是设计候选，不是已实现保证。

`tests/unit/test_iter65_broker_adapter_prototype.py` 用测试内最小 `BrokerBase` 子类、合成中立转移和真实 Cerebro 双策略生命周期作候选实验，**3 passed**：两个策略分别看到 +2/−2 虚拟仓、母单完成和 Order/Trade 通知，重复事实在内存内去重。第二个实验让同一母单先内转再处理另一种合成策略分配，回调时 Order 的 `info` 可显示当次来源和 ID，但保留的两次 `Order.clone()` 通知共享 `info`，第一次对象之后显示了第二次来源；execution bit 本身没有来源或事件 ID 字段。测试适配器对通知的 `info` 深拷贝后可在内存中保留每次来源；动态给 execution bit 增加属性也可在内存观察，但当前 Gateway framework snapshot 会明确拒绝增加字段的 bit，移除后才可捕获，不能视为持久恢复方案。该路径只在首次开仓产生 Trade 通知，同一 Trade 后续加仓没有单独的 Trade 通知。测试描述当前普通框架路径，不证明不存在其他来源表达方式。该替身没有实现真实 Gateway/SDK 接线、账户资金、权限、持久化、双腿原子提交和重启恢复；用户已明确不采用独立替换 Broker 方案；该实验不能代替现有 `BtApiBroker` 的行为。

## 13. Execution 母单基础的复用候选（未冻结）

当前 `ManagedExecutionFacade` 面向单 intent 的准入与一次派发，包含 CTP account-family lease 路径；`ParentAuthority` 则在 Execution SQLite 和外部传入的 writer lease 上维护母单、子单与 Gateway 委派。两者不是可直接等价互换的完整独立服务；`ExecutionGatewaySession` 是按策略 scope 装配的客户端，也不是本期的账户级服务。现有 `ParentAuthority` 的选 Risk 子单仍明确受阻，不能把无 Risk 合成联调推广到该路径。

## 14. 内部转移补充范围（待细化）

用户已确认策略不需要额外同意内部轧差；受账户配置范围及适用服务权限约束的匹配产生对应策略虚拟仓位，不能在 schema 中增加逐策略或逐订单的参与同意门槛。订单正常的策略归属、账户/服务主体权限、母单期限、价格和数量检查仍须保留，且与参与同意是不同概念。

1. 原始请求的账户/策略、母单与各操作 ID、规范摘要、原期限、配置版本及 writer 世代先在对应本地事务中持久；同身份同内容重放按接口明确返回原操作回执或当前观察，异摘要/错范围/不匹配主体冲突。不得因超时、空查询、断连或重启换号再发。
2. 已选 Risk 按所选规则模式形成可靠决定后才登记 Gateway；R-08 为 deny 时还须证明整笔母单的有效预留，off/warn 不因此新增 deny 级预留，也不能清除已有未决占用。Gateway 历史 ACCEPTED 必须与当前可用观察、版本、原期限、授权、租约、时段和全部适用阻断一起检查。最终预约/派发仍由 Gateway 在自己的权威事务中重验；旧 ACTIVE 回执不能覆盖更新后的 CANCEL_REQUESTED。
3. 取消先持久原取消 ID、预期版本及停止新增动作的屏障；仅能证明尚未越过发送/claim 栅栏的准备项可按合同终止。按 D65-06，Execution 离线时，已登记母单的获授权策略仍须能请求 Gateway 独立持久取消及屏障并尝试逐笔撤活动子单，不能依赖 Execution 本地事务或其在线；仅因 Execution 故障不自动撤单。已派发、结果 UNKNOWN 与迟到成交保留原身份及最坏占用，不能把撤单受理或到期当作撤成。到期须由可信时间及持久不可逆栅栏证明，继续允许适用的回报核对和受授权撤单。
4. 重启先核对原方案与期限、writer 租约、授权、各 owner 未决集合、交易日和回报水位。D65-05 默认 AUTO_CONTINUE 只可在证据充分时解除相应 Execution 故障原因及版本；取消或到期锁存、其他原因及旧日未知子单不随之消失。确定的操作结果不能因重启倒退，迟到权威成交可补记而不恢复新增下单权利。
5. 各原因按动作计算而非一律全停：STOP_NEW 阻断普通 OPEN；虚拟平仓造成真实 OPEN 的例外仅限用户决定的账户、策略、合约与数量预配置范围，提交前重验，FREEZE/DRAIN 和其他独立阻断仍适用。真实子单 UNKNOWN 的同策略同合约新单阻断及其他策略平仓容量规则按 D63-04；查询和受授权撤单入口保留，但不能保证远端送达。

候选的迟到登记 fence、可信到期锁存、独立原因与 Gateway/Risk 的真实接口均未交付；BT 标准受理及转移投影仍未证明。该表不替代用户验收或跨 owner 冻结。

## 21. 母单数量与内转占用候选（未冻结）

在同一母单、单位、权威 journal 版本和可比切点下，候选把原始核准数量 `Q` 分为互斥的：已权威完成量 `F`、已有子单仍可能成交的最坏余量 `C`、尚可能生效的内转在途量 `T`、如设计选择持久预留的计划量 `P` 与账面未占用量 `A`，满足 `Q = F + C + T + P + A` 且各项非负。`A` 不单独授予调度资格：母单取消、到期或其他阻断时，即使 `A` 大于零也不能新增动作。`F` 中场内成交与已提交内转按唯一来源和经济事实分别计入，同一数量不能因转换及其后续关联重复计算；转换在何时可归入完成量须另行冻结。若最终不设权威计划预留，`P` 为零，普通调度意图不能冒称已占用。

新增子单或转移只有在各自需要量不超过账面 `A`、母单具备调度资格且真实账户、合约、方向、今昨及占用等额外约束可证时才可预留。若设权威计划量 `P`，必须绑定母单、用途、owner、窗口及版本；仅同一窗口持有的有效队列预留可以转换成该窗口的转移占用，未匹配量按冻结合同释放或转为该母单子单占用，其他窗口或子单的预留不得挪用。上述转换在权威事务或可证明的串行栅栏下把相应 `P` 移入 `C` 或 `T`，不能二次扣减。权威子单成交将对应 `C` 转入 `F`；双边内转确定提交时，各母单对应 `T` 转入 `F`，同一转移 ID/摘要重复只能返回原结果。每个实际子单只归唯一母单和策略，内转另以双方身份和独立转移 ID 表达，external 不参与匹配。

Gateway 候选以 writer fence 保护同一权威事务，重验两方母单、期限、账户和服务权限、原订单归属、交易日及独立阻断，并校验预先取得的可信行情/持仓证据及版本；可变来源须在提交边界有可证明 fence/version，无法证明则冻结，不能假设外部来源和 SQLite 原子一致。该事务与子单预留、取消及停止屏障串行竞争；双边分录及转移身份必须原子提交。若拆为准备和提交，准备阶段先耐久占用双方 `T`，提交阶段原子转换；跨服务 UNKNOWN 不因空查询或超时释放。此处不要求策略或每张订单额外同意轧差；真实行情和授权来源仍须证明。Execution、Gateway 与已选 Risk 各自数据库不可假设同一事务，必须逐原操作身份恢复并分别证明占用释放。

普通子单撤余只有在原身份权威终态、完整成交水位和迟到请求 fence 均可证后，才可将确证余量返还 `A` 并按既定规则重新匹配；母单取消或到期后返还的数量不得重新用于新增动作。租约失效、撤单受理、TTL 或空查询都不构成释放证明。迟到的可信成交应按原事实身份和版本化摘要幂等入账；若与已释放或已用数量冲突，保留事实、冻结并对账，不能丢弃成交来维持公式。多个对手方按每个转移 ID 分开记录已完成与 UNKNOWN，不重新随机配对或释放未决腿。

上述桶、事务与时点尚未实现；计划预留是否权威、转换归集时点、费用成本及可信切点仍待 63/65 和适用 owner 冻结。尤其不能把现有 `transfer_completed` 回调或 §14 的测试替身当作在途预留已交付。

## 23. 密钥文件读取与 Windows ACL 候选（STATIC / UNIT，未冻结）

当前 007 示例的 `examples/live/007_ctp/gateway_local_resources.py` 使用目录文件描述符和不跟随链接的本地读取，检查所有者、权限位、链接数及读前后文件属性；非 POSIX 或缺少所需原语时拒绝。它是示例装配，不证明独立 Execution 服务已实现密钥读取。SDK Gateway 本地 profile 与 Web 宿主还有各自独立的 POSIX-only 读取器，检查内容不完全相同；SDK 策略会话接收调用方已解析的密钥，不能据此认定其已完成文件权限校验。

`tests/unit/test_iter65_key_loader_prototype.py` 用临时合成数据验证当前 007 示例，**9 passed**：本机可读的 `0600`、`0400`、`0700` 均被接受，`0640`、`0660` 及末端软/硬链接被拒；示例实际检查私钥没有 group/other 权限位，未严格要求模式等于 `0600`。策略文件路径的现有校验会展开 `~`，与 65 计划的“不展开 `~`”不同；本期是否复用该示例及迁移方式尚未决定，不能把现状当作满足 65 合同。模拟非 POSIX 分支只用模块局部替身，实际 Windows、NTFS 和 ACL 未运行；这些断言是当前基线而非期望保留的最终政策。

Windows 候选须先冻结允许主体及服务账户、文件读取/修改/控制权、管理员和备份特权、受信文件系统及目录/链接的威胁边界；不能将 POSIX `0600` 直接当成 Windows ACL。微软文档说明，[GetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo) 可从已打开对象句柄读取安全描述符，但读取与并发修改存在竞态；[AccessCheck](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-accesscheck) 针对传入的单个 token 判断指定权限，单次成功不能证明所有其他主体均无权访问。空 DACL 与 null DACL 的效果相反，不能混淆。 [微软文档：Null DACL 与空 DACL](https://learn.microsoft.com/en-us/windows/win32/secauthz/null-dacls-and-empty-dacls)

待审候选是对实际读取的同一文件句柄获取并验证身份、安全描述符和内容，明确拒绝或受限处理重解析点、权限继承及不受信卷；仅凭文件 ID、一次权限检查或不共享写/删除都不能证明安全描述符与内容不会并发变化。安全描述符不可读、未知 ACE 或无法证明政策和文件一致时失败关闭。上述 API 和策略组合尚未实现，允许的 SID、目录信任、控制权和特权例外亦未由用户决定。

Windows 原生验收须使用临时无真实密钥文件覆盖允许/拒绝主体和组、继承与 inherit-only、空/null DACL、owner 和修改 ACL 权限、读取错误/未知 ACE、服务 token 与适用特权、目标及中间重解析点、硬链接、文件或 ACL 并发替换和不可检查文件系统；并证明失败发生于读取密钥及启动服务/套接字的相应边界。此处尚无 Windows 原生或 PowerShell 5.1 实测，§8.2 第 6 项仍为 OPEN。

## 24. 算法事实流与迟到成交容量（未冻结）

算法只消费经过核验的视图和原方案/截止版本，宿主持久生成原子计划与子单身份后，Gateway 在其自身事务中再次核验权限、数量、期限和服务世代。UNKNOWN、缺失事实/来源或未对齐撤单不能释放余量；重启保留原子单、挂单和未决身份，TWAP 错过的时间点不得默认集中补发。PASS、SLICE、TWAP 与轧差开关独立；立即/窗口轧差调度不是 TWAP。事件端口、独立 cursor、跨服务可比切点、费用更正、Risk 和时段接线均未冻结或实现，替身原型不能代替真实组件验收。

## 25. Execution 离线时的策略撤母单（D65-06，GAP）

用户已决定：已授权策略主动撤母单时，即使 Execution 不在线，Gateway 仍须冻结该母单并尝试撤其活动子单、逐笔报告实际结果；Execution 故障本身不自动撤单，受理不等于撤成，未知结果保留原身份及占用。现有 `GatewayParentGrant` 类型允许策略角色被授予母单查询/取消，但当前 CTP 本地 profile 只为 Execution 服务主体构造 parent grant；现有 `GatewayParentServiceClient` 使用仅接受 SERVICE 的 `GatewayDelegateRoute`，不能直接视为现成的策略母单取消客户端。

`tests/unit/test_iter65_offline_parent_cancel_prototype.py` 使用真实本地 Registry、Gateway parent/delegation service、owner 和临时 SQLite，手工提供合成策略 parent grant；合成 Execution 先登记母单、经 Gateway sealed claim 和测试回调使子单记为 SENT，随后撤销该合成服务主体并关闭其临时 Store。测试中未伪造 Registry 上下文或绕过授权，**1 passed**：策略首次合并注册普通写操作和 parent 操作返回 `SCOPE_DENIED`；先注册普通写操作成功后，再独立注册 parent 操作返回 `DUPLICATE_ACTIVE_RUN`；使用已存在的普通写注册调用 parent.cancel 同样 `SCOPE_DENIED`。在 Gateway owner 队列屏障的观测截点，母单仍 ACTIVE、子单仍 SENT，已装配的合成撤单回调没有执行。

该实验只覆盖指定合成注册组合，并未取得有效策略 parent.cancel，故不能验证其 targets、取消重放或最终撤成，也不证明其他部署组合或真实账户的行为。当前源码中的 parent cancel 事务负责持久化 `CANCEL_REQUESTED` 和冻结目标列表；所查逐目标推进逻辑位于 Execution 的 `advance_cancel_children`。策略另有在具备原子单身份与权限时撤销单个委派子单的入口，但单笔撤单不等于持久冻结母单、自动枚举及尝试所有目标。CTP 装配、策略 SDK 入口、Registry 策略注册与 Gateway 独立耐久驱动须分别交付和验收，不能以冻结回执冒充完成 D65-06。

待冻结的恢复合同需绑定原母单及登记身份、策略主体、稳定母单取消 ID、请求摘要和版本；Gateway 自身持久推进逐子单目标，并与 Execution 同时撤单、迟到成交、撤权和重启竞争。对尚未发出的预约只能凭权威证据释放，对已发或 UNKNOWN 目标分别尝试撤单并按原身份跟踪；原母单登记尚 UNKNOWN 时，空查询不证明旧登记不会迟到。Gateway 的冻结及逐项尝试不能依赖 Execution 进程在线，也不能误撤其他策略或提前释放未决占用。以上为候选，服务接口与线性化细节均未实现或冻结。

**策略注册待审方向。** 可考虑让同一策略注册在一个 Registry 写事务内竞争唯一策略写 claim，并建立同时包含普通写、获授权的 parent 查询和取消的同一 session；parent.cancel 仍是写操作，仍逐项核验实际策略 principal/actor、账户/策略/domain/run、实例、port/scope_ref、操作以及精确匹配的 ResourceGrant 和 GatewayParentGrant。仅对通过上述预检的 STRATEGY_CLIENT 自身合并写注册，可考虑把“已有当前 claim”的核验推迟到该事务内：建立 claim/session 后复核同一注册 ID、授权及当前版本，事务外与提交前均须防止撤权竞态，任何后置失败必须回滚，不能以普通失败返回留下半成品。同一注册键及规范摘要重放返回原注册，异内容冲突；Execution SERVICE 仍需既有受权策略 owner，不能获得自举例外，普通只读注册也不扩大权限。此为候选，不能将查询权限升级为取消权限，也不能凭自报 run ID 证明 claim；是否支持不含普通写操作的取消专用注册仍待冻结。

既有只读注册、直接写注册和未选择 Execution 的策略须保持各自合同；同 registration key/摘要重放、不同内容冲突、同策略并发注册、注册后撤权/过期/Registry 重启和旧 epoch 必须分别验证。CTP 策略 parent grant 的实际装配及可持久保存原母单/取消操作身份的策略 SDK 客户端仍需交付，不能把此注册候选当成完整 D65-06。

**Gateway 目标推进待审方向。** 母单取消事务应将受认证的请求和稳定取消身份与冻结目标集绑定；后续由 Gateway 自己的受信 owner/epoch 耐久恢复推进，而不冒用离线 Execution 或策略身份。对 `RELEASE_PENDING`，仅在原预约、摘要、版本和未发送证据均成立时释放；`WAIT_DISPATCH` 继续核对原预约，不猜测已发或可释放；`CANCEL_PENDING` 按原子单和真实身份持久记录取消尝试，受理/排队/发送不等于场所撤成。终态仍需真实订单事实及成交水位，UNKNOWN 和迟到事实保留最坏占用；Risk 占用由 Risk 自己核验和释放。

Gateway 的现有内存取消队列及 live admission 不能在进程重启后自动构成可恢复授权证明；已受理请求在撤权、进程崩溃和恢复后的继续权限需明确持久证明与政策。策略直接撤单、Execution actor 撤单和母单取消驱动可能针对同一原预约使用不同操作 ID，须定义原预约/真实身份上的竞争和 UNKNOWN 恢复；由 Gateway 权威事务进行目标级合并是待审候选，不得仅凭各自 ID 幂等推断不会重复派发。完成所需 schema、owner、证据和服务操作均尚未实现或冻结。

`tests/unit/test_iter65_cross_actor_cancel_prototype.py` 用真实本地 Registry、Gateway parent/delegation/actor 服务、Execution 组件及 SQLite，配合合成身份、授权、provider 回调和测试专用 coverage seal，**2 passed**。在指定顺序下，合成子单标为 SENT、母单取消形成该子单的 `CANCEL_PENDING` 目标后，策略经 `direct.delegated_cancel` 发起自己的取消操作，Execution 随后按冻结目标 ID 推进取消；同一 request key、reservation、摘要和 native 目标产生两条不同操作的 SENT attempt，合成撤单回调执行两次，测试回调使用两个不同的合成 provider strong key。策略和 Execution 各自按原操作重放均未再次调用；母单仍为 `CANCEL_REQUESTED`，原子单仍为 SENT。

另一向量中，首次合成回调在派发 marker 持久化后抛出超时，Gateway 将策略操作记为 `UNKNOWN`；Execution 随后对同一目标使用另一冻结操作 ID，第二次合成回调执行并记为 `SENT`。各自重放原操作没有第三次回调。该向量展示的是结果未知后另一操作仍能进入派发路径，不表示第一次或第二次在真实场所已生效。

该 UNKNOWN 向量进一步验证同进程内的**干净关闭与重建**：测试 owner 关闭后以同一临时 guard 目录、原 journal ID/最小 revision 和新 generation 重建，随后新建内存 Registry 并重新注册合成主体。两条撤单记录的受检操作 ID、主体、目标、prepared、marker、attempt、版本和状态不变，重建及原操作重放没有新的合成撤单回调。策略以原 ID 查询和重放仍得到 UNKNOWN 与 OBSERVED；Execution 以原 ID 查询时 Gateway 返回原 SENT，但客户端得到 `UNKNOWN / INVALID_OR_UNAVAILABLE_REPLY`。测试确认新响应与原 Execution observation 除当前 `owner_generation` 不同外相同：Execution 的同版本 observation 全内容一致性检查拒绝该变化，旧 observation 未改变。SENT 仍仅是合成回调结果，不是场所撤成。

同一测试先经受权 `actor_status` 保存子单的 SENT v3 观察，再做上述干净重建。重建后的 Gateway 子单应答保留原预约代际和同一版本、摘要及原生身份摘要，仅当前 owner generation 变化；Execution 客户端同样返回 `UNKNOWN / INVALID_OR_UNAVAILABLE_REPLY`，原持久观察和合成回调计数不变。因此该受控组合中的同版本冲突不仅影响撤单观察，也影响已派发子单观察；测试没有证明所有子单状态或其他客户端均如此。

`tests/unit/test_iter65_release_epoch_prototype.py` 用真实本地 Registry、Gateway 服务/owner、Execution SQLite 及合成身份和 provider，**2 passed**：Gateway 实际受理子单 RESERVED v1 后，测试传输丢弃回复，Execution 没有保存预约观察。第一种顺序中，母单取消先将预约冻结为 `RELEASE_PENDING`；干净重建时测试工厂在 owner ready 前显式过期唯一已知旧预约，得到 EXPIRED v2。重新注册后，Execution 查询得到 `OBSERVED / EXPIRED`，但子单仍为 UNKNOWN、冻结操作不变；重复推进只查询，不创建 release intent 或新的下单、撤单回调。第二种顺序中，测试先按同样方式重建并过期预约，再经重新注册的客户端冻结母单；返回的冻结目标为空，Execution 仍保留该 UNKNOWN 子单及其 3 手数量，重复取消和推进无新增调用。两个向量没有调用 release status，不能据此判断该接口跨代结果；单条测试过期不是生产启动全量扫描，Execution 进程及 lease 未重建，崩溃恢复和真实账户均未验证，不能推广至预约仍为 RESERVED 的时序。

**旧预约的未发送证明与收敛候选。** 当前 Gateway 日志中 `EXPIRED v2` 从 `RESERVED v1` 经事务条件转换；日志完整性约束及相关数量检查要求其无原生身份、无强身份键，且不存在矛盾的订单/成交事实。若同一可信 journal 的防回滚锚、独占 owner 和所有 native 派发必须先提交 marker 等前提均已证明，过期提交与 marker 提交在数据库写事务中竞争：过期先提交则后续旧预约不能开始派发；marker 先提交则该行不再是可过期的 RESERVED。这个条件性本地结论不能推广到绕过 journal 的 provider、未关闭的旧 owner 或不可信快照；空查询和超时也不能替代证明。

Gateway 当前冻结前会先检查 RELEASED、EXPIRED、NOT_SENT 的矛盾事实并跳过这些子单；冻结后才过期的目标仍为 `RELEASE_PENDING`，Execution 当前仅在读到原 RESERVED 时创建 release intent。Gateway 的目标核验及 journal release 对符合条件的已过期目标可记录原 release 操作，但现有 Execution 推进路径遇到已过期观察时不会进入该调用；现有跨代 release status 还要求当前 owner generation 等于原预约 generation。Gateway 的剩余量与 Execution 保守保留的 UNKNOWN 占用因而可能暂时不同，不能据此认定任何一方已完成端到端释放。

待审候选是由 Gateway 的母单冻结事务提供可核验的完整子单清单，并为冻结前后已终结且确证未发送的原预约提供稳定、可重放、带主体与版本的终结事实；事实绑定母子单、原请求/预约、摘要、主体、旧代际及无派发 marker 和无矛盾事实的证据，并经当前 owner、注册及账本来源核验。Execution 在自身 writer fence 下以原事件身份幂等写入证据和零成交终态、更新本地占用，再确认消费；Gateway 与 Execution 之间通过可恢复消息或原 ID 查询衔接，不假定跨库原子。选用 Risk 时由 Risk 按自己的合同独立核验及处理其占用。此为设计候选，不是已实现接口；证明缺失、身份冲突、迟到事实或旧 owner 无法排除时保持 UNKNOWN。

验收需覆盖冻结前/后过期、已有或缺失 release intent、真实 journal 中过期和 marker 两种先后、同 ID 重放与异内容冲突、跨代来源及防回滚、撤权和调用中换 owner、矛盾订单/成交、Gateway 与 Execution 各自提交前后崩溃及 ACK 丢失；冻结目标缺席本身不能证明未知子单未发送，也不能直接释放。不同主体的取消如何合并仍是待审合同，不把该候选作为已定策略。

该实验没有重建 Execution Store、进程或 lease，也没有模拟异常崩溃和真实 CTP 会话；不能据此声称完整恢复。当前 `LocalAccountSessionGuard` 对崩溃遗留的 active 记录拒绝直接接管，专用 abandoned-session 对账还会检查未决派发；干净关闭不等同上述崩溃接管。恢复合同需区分原 attempt generation 和当前应答 owner generation，在验证新 owner 来源、授权与原 attempt 全部身份后处理代际变化，并继续拒绝同版本事实冲突；不能简单忽略 generation 或无证明地接受任意新 owner。具体协议、持久审计和迁移尚待设计与验证。

**跨代应答可信绑定候选。** Registry 的 service epoch 和 Gateway journal 的 owner generation 分别产生；当前查到的客户端注册及前后栅栏不能单独证明二者与同一受信 journal owner 绑定。journal 的预期 ID 和最小 revision 可检查身份及下界，但外部锚本身须可信，滞后的下界不能排除同 ID 且 revision 不低于该下界的旧快照或分叉。可考虑由受信宿主在持有本机 guard、确认旧会话已安全关闭或按正式流程完成对账、验证 journal 及外部锚后，绑定服务实例、Registry epoch、账户、journal ID 和当前 owner generation，并使认证应答与原请求及作用域关联；跨进程证明和密钥、撤销、继承机制仍须设计。guard 只约束共享可信目录的本机参与方，不证明跨主机排他或场所旧连接已终止。

消费侧可考虑把原 attempt 的事实和已验证的当前应答元数据分开保存：同版本的原身份、原 generation、状态及其他事实仍严格一致，响应来源变化须另有受信证明并保留审计；更高版本仍须验证合法状态迁移。测试须覆盖旧 epoch、错账户/策略/目标/attempt、同版本篡改、撤权及 RPC 期间 owner 变化、错误或滞后的 journal 锚、同 ID 分叉、异常崩溃和未确认旧会话关闭；证据不足时保持 UNKNOWN。这些均为候选，不是当前已经实现的认证或恢复协议。

`tests/unit/test_iter65_ctp_cancel_key_journal_prototype.py` 将真实 CTP `prepare_cancel_order` 和真实 Gateway 撤单 journal 在隔离环境中组合，**1 passed**：内存合成登录及原订单 marker 下，同一合成目标的两次准备产生不同 RequestID、request key 和 reservation ID；两个操作分别写入独立 `DISPATCHING` marker，各自重放不新建 marker。测试禁止连接及 native 请求，没有经过 dispatcher 或发送撤单，且未验证实际授权；该结果只说明本地准备键及 journal 的组合，不证明真实会话、并发、交易所送达或撤成。请求计数器的跨进程持久性也未证明。

上述跨主体向量只覆盖受控顺序和合成 provider key；CTP 组合向量则直接调用 journal，没有覆盖跨主体授权路径。与已存在的单 journal 测试一样，同一操作幂等或相同 strong key 冲突不能自动证明跨主体、不同操作 ID 对同一目标的去重。目标级合并是待审候选而非已冻结的用户规则；Gateway 自主驱动需要明确该竞争及 UNKNOWN 的恢复合同。

候选实现可以在 Gateway 日志事务中以账户、策略、原预约、请求摘要、原主体、交易日及原生目标身份绑定目标记录，同时单独保存各获授权主体的操作 ID 和每次派发事实；不同操作关联同一未决目标时不自动制造新派发。恢复时逐条保留已有 attempt 和 marker，旧库若已有多个可能在途的 attempt 不能择一覆盖。目标记录并不取代逐请求授权、结果查询授权或完整成交对账，也不能将 SENT 当作撤成。这些状态和迁移均未实现或验收。

迭代 63 的 DRAIN 专项要求撤单结果不明时不盲目重发，查询确认仍活动后才可再撤；它不能自动扩大为所有主体竞争场景的已定策略。查询的身份、完整性、时点与旧请求迟到风险，以及哪些证据和政策允许新的 attempt，仍待冻结。单次仍活动快照本身不能证明先前未决撤单将不会迟到。
