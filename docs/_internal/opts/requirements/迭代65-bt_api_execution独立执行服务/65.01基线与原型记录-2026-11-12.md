## 7. 停止与双租约审阅草案（未冻结）

已决定的正常 stop/restart 停止阶段取消该策略未完成母单余量并尝试撤其场内子单；仅权威终态和成交水位一致才报告结束，迟到成交和 UNKNOWN 按原身份及最坏占用处理，其他策略不受影响，重启不复活已取消母单。策略租约和 Execution 租约相互独立：前者默认不自动 DRAIN、显式选择时按其原因处理；后者失效冻结相关母单，不因此释放活动或 UNKNOWN 子单。恢复只解除经核对的对应原因和版本，不清除其他阻断。

当前 Gateway 有多原因控制、条件解除和单母单 `CANCEL_REQUESTED` 的本地源码路径；这些不证明 Runtime 的持久批量停止意图、Execution 服务租约、跨日恢复或内转屏障已接通。特别是既有 parent register 与停止屏障的同事务竞争未证明，不能将单个 DRAIN 操作视为完整停止合同。

待 63/65/66 联合冻结的候选是：以带主体、范围、稳定操作 ID 和版本的 Gateway 权威停止屏障，和母单登记、子单预留/派发及内转预留在同一权威事务建立明确先后；持久屏障后按原身份逐一取消并记录各母子单状态。丢回复只按原 ID 查询，旧版本不能解除新原因，租约恢复不能自动清除独立停止原因。此段为审阅候选，不是当前 wire 接口或已实现行为。

故障验证至少覆盖屏障与登记/预留/派发/内转的先后竞争；双租约分别及同时失效、不同原因叠加和旧版本解除；母单 10 手已成 4、挂 2、未发 4 的部分撤成/迟到/UNKNOWN；持久前后崩溃、丢回复、撤权、原计划到期及不相关策略并发。真实组件、替身和选用 Risk 的证据分别登记。

## 8. 母单期限兼容方案候选（未冻结）

按照用户对 D65-03 的选择，首期接受 Gateway 当前可提交的 `Order.valid is None` 订单；带非空 BT `valid` 的订单保留现有明确拒绝。策略选中的 Execution 路由须由配置显式提供母单有效期政策，SDK 命中路由后在首次远端副作用之前，将政策版本、来源、时区、受理基准及一次算定的绝对期限与母单原请求身份一起持久化。具体字段名、配置层级、允许的政策组合和受理基准尚需联合冻结；不能仅在内存计算或将子单的原生 `time_in_force` 当作母单期限。

候选政策包含交易日内到期与显式截止时间。交易日边界、截止时刻和日历来源必须可证明，期限缺失、非法、已过期、时钟或交易日不可证明时拒绝受理或暂停，不能默认为无限期。若实现允许由持续时长计算截止，必须绑定一次明确的受理基准，重放及重启只读取原截止，不从当前时间重新起算。账户授权上限与策略选项如何比较由 65.01 完整 schema 冻结；不允许策略通过更宽期限越过账户授权。

跨日的母单在原截止内才可继续，子单仍遵循实际 provider 的交易日、有效期与会话规则。截止后停止新增子单，活动/在途/UNKNOWN 子单及迟到成交继续按 Gateway 权威事实追踪，不能用到期替代撤成或释放证明。配置变更不回写已受理母单；若无法读取原政策或原截止，保持冻结而不是创建新的期限或母单。

待证明：命中与未命中路由各自的行为；无/坏配置及非空 BT `valid` 无写副作用；交易日截止和跨午夜、夏令时、节假日及缺日历；受理前后崩溃、丢回复和重复同 ID；配置变更、重启、跨日、已截止和 UNKNOWN；确保策略可观察的订单语义和配置期限一致。以上仍是候选设计，不声称当前 SDK 或 Gateway 已提供这些能力。

## 10. Gateway 母单投影待验证边界

现有 Gateway BT 提交为一笔 BT 订单分配一个 request key，持久化该 key、订单 intent 与框架快照，然后调用 SDK 的 reserve/dispatch。Gateway 返回流与该请求的 reservation、摘要、主体、来源身份、合约、方向及数量绑定；现有 Risk 委托分支有专门的持久化绑定，不是通用 Execution 母子单合同。多个真实子单各自的 reservation、原生订单身份和数量不能直接当作母单的原生事实，也不能把某个子单的终态直接当母单终态。

现行 provider-normalized 回报及 Gateway stream 类型没有已验证的内部转移事件入口。内部转移不是交易所成交，不能为了让现有 BT 消费而编造交易所成交、原生身份、来源证明或 ACK。已登记单命令的多笔合成成交及 checkpoint 原型通过，不能外推为多子单或双边内部转移已支持。

`tests/unit/test_iter65_gateway_transfer_prototype.py` 在两个独立真实 BT Gateway 消费者及本地 checkpoint 上验证当前合同边界，**4 passed**：当前 SDK observation 对 `internal_transfer` 类型拒绝，现有事件信封要求命令关联；空流重开不影响各自 checkpoint。该实验没有投递有效内部转移，也没有测成双侧 Position/Order/Trade、通知、原子提交或崩溃重放；这些仍为 GAP/NOT_RUN。协议后续扩展时须相应更新此基线实验，不能把其拒绝断言当成本期最终功能要求。

继续研究的候选是 SDK/Execution 显式持有经过授权的母单到各子单映射，逐笔保留 provider 来源，Gateway/SDK 对策略分配和内部转移建立独立的版本化身份、账本、水位和证据，再验证是否能由现有 BT 消费器合法表达与恢复。这是尚未证明可行的合同探索，不允许改写来源以满足旧校验；当前 BT 回报结构及来源校验能否在零产品改动下满足本期完整要求仍是 GAP。若证明不能，应记录具体不可表达项并按用户选择重新讨论，不擅自削减本期目标。

进一步静态核对：当前 `BtApiBroker` 的 Gateway 消费器绑定精确 SDK client/host 与已登记请求，通知事务也要求下一条已登记事件；不能仅凭 SDK 持有 Broker 引用或调用通知队列就合法注入非场所事件。SDK 现有策略持仓只读接口可能消费将来的 Gateway 权威账本快照，但仅能作为读取方向研究，不能自动证明母单 Order/Trade、通知及重放已更新。用户已确认必须复用现有 `BtApiBroker` 且不修改其源码，故独立替换 Broker 的实验不作为交付方案；不能把 BT 依赖塞入 SDK 中立核心或声称恢复已解决。双边账本事务、来源、顺序/去重、checkpoint、回调及崩溃恢复仍需证明。

现有 `GatewayPendingHost` 的 checkpoint 对事件类型、请求原生身份和已存事件水位有严格约束，不能将内部转移硬塞进现有 native fill 合同。用户要求继续复用现有 Broker，SDK/服务侧需寻找不伪造场所事实且兼容现有校验的机制；测试内独立 Broker 的逐腿内存循环不是双边耐久原子提交，也不是本期交付方案。

按这一约束的源码复核：原 Broker 为一笔 BT 订单持久化一个 request key，要求 event 的 reservation、摘要、主体、数量和原生身份或已验证别名与该请求匹配；普通命令 checkpoint 还要求非空 `NativeOrderIdentity`。现有 Risk 委托分支要求实际 Risk 路由及已持久的委托记录，不能用虚假 Risk 标志代替 Execution。Broker 只处理现有 ORDER/TRADE/ORDER_ERROR/CANCEL_ERROR，直接回报合同将 ORDER/TRADE 定义为场所/provider 来源；普通 `notify()` 也不能绕过已登记事件的通知事务。母单及内部转移本身没有对应原生场所订单，不能凭空填原生身份或将内转伪装为场所成交。SDK 即使扩展其类型和服务事实，也尚须证明这些不变的 Broker 检查可合法满足，及逐笔来源能保真；当前方案为 GAP，不声称理论上所有 SDK 合同重设计都不可能。

另一套旧 execution event 表允许多个外部订单关联同一 client ID，但会直接把子单状态和累计成交投影到 BT 订单，尚不证明母单聚合正确；该旧流与当前 Gateway stream 互斥，Gateway 模式的正常 `next` 也不消费该旧通道。策略持仓只读接口有望读取扩展后的权威虚拟账本，但当前非零 `Position.price` 为 NaN，且不产生 Order/Trade/通知；普通 Gateway `getposition()`/`self.position` 仍不可用。以上不能作为本期完整投影的替代验收。

恢复候选应由权威 owner 对双边分录原子提交，消费侧持久保存稳定事件 ID、顺序、来源 sidecar、BT 对象投影、待通知与 cursor 后再 ACK；跨进程/库不假设原子。现有 Strategy 的通知恢复使用框架内部钩子，单凭公开 Broker 接口尚不能证明回调前 Trade 状态及通知批次原子持久化，需逐版本验证或明确新合同。回调已执行但确认前崩溃可能重投，外部策略副作用不能由本地快照保证恰好一次，须由消费方基于稳定 ID 幂等处理或保留明确的不确定状态。该段是设计候选，不是已实现保证。

`tests/unit/test_iter65_broker_adapter_prototype.py` 用测试内最小 `BrokerBase` 子类、合成中立转移和真实 Cerebro 双策略生命周期作候选实验，**3 passed**：两个策略分别看到 +2/−2 虚拟仓、母单完成和 Order/Trade 通知，重复事实在内存内去重。第二个实验让同一母单先内转再处理另一种合成策略分配，回调时 Order 的 `info` 可显示当次来源和 ID，但保留的两次 `Order.clone()` 通知共享 `info`，第一次对象之后显示了第二次来源；execution bit 本身没有来源或事件 ID 字段。测试适配器对通知的 `info` 深拷贝后可在内存中保留每次来源；动态给 execution bit 增加属性也可在内存观察，但当前 Gateway framework snapshot 会明确拒绝增加字段的 bit，移除后才可捕获，不能视为持久恢复方案。该路径只在首次开仓产生 Trade 通知，同一 Trade 后续加仓没有单独的 Trade 通知。测试描述当前普通框架路径，不证明不存在其他来源表达方式。该替身没有实现真实 Gateway/SDK 接线、账户资金、权限、持久化、双腿原子提交和重启恢复；用户已明确不采用独立替换 Broker 方案；该实验不能代替现有 `BtApiBroker` 的行为。

## 11. Execution 服务接口审阅草案（未冻结）

65 提供统一页面所需的版本化服务接口，页面和浏览器联调归 69。Gateway 和 Risk 已有各自的本机 Web 适配与可信宿主，可参考其认证、范围检查和审计模式；它们的 grant、撤单操作或收据不能直接视为 Execution 权限或母单撤销接口。现有 Execution `parent_authority` 有本地母单同 ID 冲突及取消原 ID 查询基础，但不是对外服务 API，尚未证明操作者授权、审计或独立进程能力。

候选接口区分受权读取与状态更改：读取返回账户/策略/对象作用域、事实来源、水位、版本、完整性和 UNKNOWN，列表有界；母单撤销及适用授权管理须按具体操作声明。可信宿主把认证主体映射到 Execution 自身的 principal 和按账户、策略、对象、操作限定的 grant；服务使用时重验有效性和撤权，不以浏览器自报身份授权。

写请求在远端副作用前持久记录原命令 ID、规范摘要、目标与期望版本；同 ID 同内容查询已有结果，异内容冲突；审计关联操作主体、授权版本、目标及实际结果。超时或丢回复按原 ID 查询，无法证明时为 UNKNOWN，不自动换 ID 重试。母单撤销受理、子单终态及迟到成交分别表达；各服务各自的本地事务和审计不假装跨库原子。主体到 grant 的具体映射、操作枚举、撤权与已在途 claim 的线性化点和持久收据恢复仍待冻结。

验收应覆盖无 UI 启动、版本和数据陈旧、跨账户/策略/目标拒绝、撤权与提交竞争、并发重复、崩溃及丢回复、原 ID 异内容冲突、受理不等于终态与 UNKNOWN 保留。真实 Execution/Gateway 联调和选 Risk 路径分别记录；替身及静态源码不代替服务或账户验收。

## 13. Execution 母单基础的复用候选（未冻结）

当前 `ManagedExecutionFacade` 面向单 intent 的准入与一次派发，包含 CTP account-family lease 路径；`ParentAuthority` 则在 Execution SQLite 和外部传入的 writer lease 上维护母单、子单与 Gateway 委派。两者不是可直接等价互换的完整独立服务；`ExecutionGatewaySession` 是按策略 scope 装配的客户端，也不是本期的账户级服务。现有 `ParentAuthority` 的选 Risk 子单仍明确受阻，不能把无 Risk 合成联调推广到该路径。

目前 CTP account-family owner 是该 SQLite 内的持久状态，重开后失去进程内 handle 的接管与 release/handoff 未证明；单库 lease 不代表交易账户在全部进程上天然唯一。应分别验证 Execution 服务和 Gateway owner 的职责、续租/过期/旧 owner fence、跨进程及崩溃接管、同键异内容、UNKNOWN、Gateway 原生派发和选 Risk 路径。真实账户、跨平台及发行包验收另记。

## 14. 内部转移补充范围（待细化）
