## 7. 停止与双租约审阅草案（未冻结）

已决定的正常 stop/restart 停止阶段取消该策略未完成母单余量并尝试撤其场内子单；仅权威终态和成交水位一致才报告结束，迟到成交和 UNKNOWN 按原身份及最坏占用处理，其他策略不受影响，重启不复活已取消母单。策略租约和 Execution 租约相互独立：前者默认不自动 DRAIN、显式选择时按其原因处理；后者失效冻结相关母单，不因此释放活动或 UNKNOWN 子单。恢复只解除经核对的对应原因和版本，不清除其他阻断。

当前 Gateway 有多原因控制、条件解除和单母单 `CANCEL_REQUESTED` 的本地源码路径；这些不证明 Runtime 的持久批量停止意图、Execution 服务租约、跨日恢复或内转屏障已接通。特别是既有 parent register 与停止屏障的同事务竞争未证明，不能将单个 DRAIN 操作视为完整停止合同。

待 63/65/66 联合冻结的候选是：以带主体、范围、稳定操作 ID 和版本的 Gateway 权威停止屏障，和母单登记、子单预留/派发及内转预留在同一权威事务建立明确先后；持久屏障后按原身份逐一取消并记录各母子单状态。丢回复只按原 ID 查询，旧版本不能解除新原因，租约恢复不能自动清除独立停止原因。此段为审阅候选，不是当前 wire 接口或已实现行为。

故障验证至少覆盖屏障与登记/预留/派发/内转的先后竞争；双租约分别及同时失效、不同原因叠加和旧版本解除；母单 10 手已成 4、挂 2、未发 4 的部分撤成/迟到/UNKNOWN；持久前后崩溃、丢回复、撤权、原计划到期及不相关策略并发。真实组件、替身和选用 Risk 的证据分别登记。

2026-11-12 补充的 `tests/unit/test_iter65_stop_barrier_prototype.py` 使用真实 Gateway journal、母单 authority 与控制入口及合成身份/授权替身，**6 passed**：策略级 STOP_NEW、FREEZE、DRAIN 生效时，当前母单登记仍可返回 ACTIVE，但该策略新开仓子单的预约被拒，另一策略可预约；解除单个原因不解除其他原因，已取消母单不因解除原因复活，原因生效前已预约的子单在解除后仍受既有阻断。上述是顺序离线观察，不证明独立 Runtime 停止屏障、双租约、并发线性化、内转或真实授权；不能把当前 DRAIN 当成已交付的正常停止屏障。

按照用户对 D65-03 的选择，首期接受 Gateway 当前可提交的 `Order.valid is None` 订单；带非空 BT `valid` 的订单保留现有明确拒绝。策略选中的 Execution 路由须由配置显式提供母单有效期政策，SDK 命中路由后在首次远端副作用之前，将政策版本、来源、时区、受理基准及一次算定的绝对期限与母单原请求身份一起持久化。具体字段名、配置层级、允许的政策组合和受理基准尚需联合冻结；不能仅在内存计算或将子单的原生 `time_in_force` 当作母单期限。

候选政策包含交易日内到期与显式截止时间。交易日边界、截止时刻和日历来源必须可证明，期限缺失、非法、已过期、时钟或交易日不可证明时拒绝受理或暂停，不能默认为无限期。若实现允许由持续时长计算截止，必须绑定一次明确的受理基准，重放及重启只读取原截止，不从当前时间重新起算。账户授权上限与策略选项如何比较由 65.01 完整 schema 冻结；不允许策略通过更宽期限越过账户授权。

跨日的母单在原截止内才可继续，子单仍遵循实际 provider 的交易日、有效期与会话规则。截止后停止新增子单，活动/在途/UNKNOWN 子单及迟到成交继续按 Gateway 权威事实追踪，不能用到期替代撤成或释放证明。配置变更不回写已受理母单；若无法读取原政策或原截止，保持冻结而不是创建新的期限或母单。

## 10. Gateway 母单投影待验证边界

现有 Gateway BT 提交为一笔 BT 订单分配一个 request key，持久化该 key、订单 intent 与框架快照，然后调用 SDK 的 reserve/dispatch。Gateway 返回流与该请求的 reservation、摘要、主体、来源身份、合约、方向及数量绑定；现有 Risk 委托分支有专门的持久化绑定，不是通用 Execution 母子单合同。多个真实子单各自的 reservation、原生订单身份和数量不能直接当作母单的原生事实，也不能把某个子单的终态直接当母单终态。

现行 provider-normalized 回报及 Gateway stream 类型没有已验证的内部转移事件入口。内部转移不是交易所成交，不能为了让现有 BT 消费而编造交易所成交、原生身份、来源证明或 ACK。已登记单命令的多笔合成成交及 checkpoint 原型通过，不能外推为多子单或双边内部转移已支持。

`tests/unit/test_iter65_gateway_transfer_prototype.py` 在两个独立真实 BT Gateway 消费者及本地 checkpoint 上验证当前合同边界，**4 passed**：当前 SDK observation 对 `internal_transfer` 类型拒绝，现有事件信封要求命令关联；空流重开不影响各自 checkpoint。该实验没有投递有效内部转移，也没有测成双侧 Position/Order/Trade、通知、原子提交或崩溃重放；这些仍为 GAP/NOT_RUN。协议后续扩展时须相应更新此基线实验，不能把其拒绝断言当成本期最终功能要求。

继续研究的候选是 SDK/Execution 显式持有经过授权的母单到各子单映射，逐笔保留 provider 来源，Gateway/SDK 对策略分配和内部转移建立独立的版本化身份、账本、水位和证据，再验证是否能由现有 BT 消费器合法表达与恢复。这是尚未证明可行的合同探索，不允许改写来源以满足旧校验；当前 BT 回报结构及来源校验能否在零产品改动下满足本期完整要求仍是 GAP。若证明不能，应记录具体不可表达项并按用户选择重新讨论，不擅自削减本期目标。

进一步静态核对：当前 `BtApiBroker` 的 Gateway 消费器绑定精确 SDK client/host 与已登记请求，通知事务也要求下一条已登记事件；不能仅凭 SDK 持有 Broker 引用或调用通知队列就合法注入非场所事件。SDK 现有策略持仓只读接口可能消费将来的 Gateway 权威账本快照，但仅能作为读取方向研究，不能自动证明母单 Order/Trade、通知及重放已更新。用户已确认必须复用现有 `BtApiBroker` 且不修改其源码，故独立替换 Broker 的实验不作为交付方案；不能把 BT 依赖塞入 SDK 中立核心或声称恢复已解决。双边账本事务、来源、顺序/去重、checkpoint、回调及崩溃恢复仍需证明。

现有 `GatewayPendingHost` 的 checkpoint 对事件类型、请求原生身份和已存事件水位有严格约束，不能将内部转移硬塞进现有 native fill 合同。用户要求继续复用现有 Broker，SDK/服务侧需寻找不伪造场所事实且兼容现有校验的机制；测试内独立 Broker 的逐腿内存循环不是双边耐久原子提交，也不是本期交付方案。

按这一约束的源码复核：原 Broker 为一笔 BT 订单持久化一个 request key，要求 event 的 reservation、摘要、主体、数量和原生身份或已验证别名与该请求匹配；普通命令 checkpoint 还要求非空 `NativeOrderIdentity`。现有 Risk 委托分支要求实际 Risk 路由及已持久的委托记录，不能用虚假 Risk 标志代替 Execution。Broker 只处理现有 ORDER/TRADE/ORDER_ERROR/CANCEL_ERROR，直接回报合同将 ORDER/TRADE 定义为场所/provider 来源；普通 `notify()` 也不能绕过已登记事件的通知事务。母单及内部转移本身没有对应原生场所订单，不能凭空填原生身份或将内转伪装为场所成交。SDK 即使扩展其类型和服务事实，也尚须证明这些不变的 Broker 检查可合法满足，及逐笔来源能保真；当前方案为 GAP，不声称理论上所有 SDK 合同重设计都不可能。

另一套旧 execution event 表允许多个外部订单关联同一 client ID，但会直接把子单状态和累计成交投影到 BT 订单，尚不证明母单聚合正确；该旧流与当前 Gateway stream 互斥，Gateway 模式的正常 `next` 也不消费该旧通道。策略持仓只读接口有望读取扩展后的权威虚拟账本，但当前非零 `Position.price` 为 NaN，且不产生 Order/Trade/通知；普通 Gateway `getposition()`/`self.position` 仍不可用。以上不能作为本期完整投影的替代验收。

继续检查发现公开策略账本钩子可投递 `LedgerEvent` 到策略的专门回调，但不会自动推进标准 BT Order/Trade 或其通知；其 `account_book` 绑定还与 Gateway 的策略持仓读取分支冲突。旧 `ServiceExecutionSession` 与 Gateway 通知绑定互斥，且已按用户决定列入退役。直接调用公开的 Broker 通知队列也会在 Gateway 的 armed-event 校验处被拒绝，不能以此绕过来源与持久化合同。这些是当前实现边界，不是对所有未来 SDK 合同的理论不可能证明；继续探索须保留同一 `BtApiBroker`、原有源码及真实来源。

补充源码核对：Gateway 的 `GatewayTradeAttribution` 是同一场内订单真实身份的别名桥，绑定原命令和 reservation，不能当成多个独立子单或内部转移的关联凭证；Broker 同时要求订单大小对应原 intent，成交开平与 intent 一致，因而平今转平昨也须另证明合法投影。普通 Store 更新入口在 Gateway/direct 模式的正常 `next()` 中不消费，旧 managed 路径又不提供此处所需的 Gateway 耐久回放与双边事务，不能作为替代。现阶段未找到满足全部约束的 SDK 单侧实现，不排除未来存在尚未证明的合同设计。

Store 的公开通知队列理论上可携带明确标识来源的自定义消息，但当前是进程内广播，不提供完整的策略隔离、持久 ACK 和重放，也不推进标准 BT Order/Trade；尚未有 Gateway 内转流接线，不能把它作为标准订单或成交投影的替代。

恢复候选应由权威 owner 对双边分录原子提交，消费侧持久保存稳定事件 ID、顺序、来源 sidecar、BT 对象投影、待通知与 cursor 后再 ACK；跨进程/库不假设原子。现有 Strategy 的通知恢复使用框架内部钩子，单凭公开 Broker 接口尚不能证明回调前 Trade 状态及通知批次原子持久化，需逐版本验证或明确新合同。回调已执行但确认前崩溃可能重投，外部策略副作用不能由本地快照保证恰好一次，须由消费方基于稳定 ID 幂等处理或保留明确的不确定状态。该段是设计候选，不是已实现保证。

`tests/unit/test_iter65_broker_adapter_prototype.py` 用测试内最小 `BrokerBase` 子类、合成中立转移和真实 Cerebro 双策略生命周期作候选实验，**3 passed**：两个策略分别看到 +2/−2 虚拟仓、母单完成和 Order/Trade 通知，重复事实在内存内去重。第二个实验让同一母单先内转再处理另一种合成策略分配，回调时 Order 的 `info` 可显示当次来源和 ID，但保留的两次 `Order.clone()` 通知共享 `info`，第一次对象之后显示了第二次来源；execution bit 本身没有来源或事件 ID 字段。测试适配器对通知的 `info` 深拷贝后可在内存中保留每次来源；动态给 execution bit 增加属性也可在内存观察，但当前 Gateway framework snapshot 会明确拒绝增加字段的 bit，移除后才可捕获，不能视为持久恢复方案。该路径只在首次开仓产生 Trade 通知，同一 Trade 后续加仓没有单独的 Trade 通知。测试描述当前普通框架路径，不证明不存在其他来源表达方式。该替身没有实现真实 Gateway/SDK 接线、账户资金、权限、持久化、双腿原子提交和重启恢复；用户已明确不采用独立替换 Broker 方案；该实验不能代替现有 `BtApiBroker` 的行为。

## 11. Execution 服务接口审阅草案（未冻结）

## 13. Execution 母单基础的复用候选（未冻结）

当前 `ManagedExecutionFacade` 面向单 intent 的准入与一次派发，包含 CTP account-family lease 路径；`ParentAuthority` 则在 Execution SQLite 和外部传入的 writer lease 上维护母单、子单与 Gateway 委派。两者不是可直接等价互换的完整独立服务；`ExecutionGatewaySession` 是按策略 scope 装配的客户端，也不是本期的账户级服务。现有 `ParentAuthority` 的选 Risk 子单仍明确受阻，不能把无 Risk 合成联调推广到该路径。

技术候选是优先评估复用 `ParentAuthority` 的母单 journal 和明确的 Gateway 委派端口，在此基础上实现账户级服务、持久状态和算法；Gateway 保持既有唯一实际派发职责。旧 `execution/account_owner` 服务角色和 BT Session 仍按 D65-11 退役；仅按实际调用者复用中立持久化或准入部件，不把旧单单 Facade 的 provider dispatcher 并入新服务，也不启用旧 CTP OrderRef/outbox 作为第二派发点。此候选尚未证明租约可组合或恢复可靠，不能据现有类名、日志或局部测试冻结。

目前 CTP account-family owner 是该 SQLite 内的持久状态，重开后失去进程内 handle 的接管与 release/handoff 未证明；单库 lease 不代表交易账户在全部进程上天然唯一。应分别验证 Execution 服务和 Gateway owner 的职责、续租/过期/旧 owner fence、跨进程及崩溃接管、同键异内容、UNKNOWN、Gateway 原生派发和选 Risk 路径。真实账户、跨平台及发行包验收另记。

## 14. 内部转移补充范围（待细化）

用户已确认策略不需要额外同意内部轧差；受账户配置范围及适用服务权限约束的匹配产生对应策略虚拟仓位，不能在 schema 中增加逐策略或逐订单的参与同意门槛。订单正常的策略归属、账户/服务主体权限、母单期限、价格和数量检查仍须保留，且与参与同意是不同概念。

STOP_NEW 下，用户选择按账户、策略、合约及数量范围预先显式配置虚拟平仓转换例外，提交前重新验证；缺配置拒绝，普通 OPEN 不获豁免，FREEZE/DRAIN 及其他独立阻断仍适用。选 Risk 时按实际动作执行相应检查。具体配置及身份授权在 63/65、选 Risk 时与 64 联合冻结。

`tests/unit/test_iter65_transfer_reservation_prototype.py` 使用真实 Gateway 本地 journal、parent authority 与委派预约，配合合成授权和测试内的待决状态，**4 passed**：母单 10 手时，测试替身标记 6 手 PREPARED 或 UNKNOWN、而传给 authority 的已完成量为 0，另一个 6 手子单仍可预约；在独立干净 journal 中传入已完成量 6 后，6 手子单被拒且无预约，4 手子单可预约。测试中的待决状态只在内存，不存在真实 Gateway 内转记录或并发，不证明生产发生超量；它说明仅输入完成量不能表达未传入的在途占用。未来须在 Gateway 权威事务中统一竞争内转与子单数量，并对 PREPARED、UNKNOWN、完成、取消及崩溃恢复分别验证；不可将该基线当作目标行为。

当前 Gateway 母单登记的表和结果没有公开账户级受理序号，单母单 `version` 不能比较跨策略顺序。候选是在受 writer fence 的账户权威登记事务中分配不可变序号，同身份重放返回原值，并为 journal/代际、迁移和缺失旧记录定义处理；不能以客户端时钟或未经合同保证的 SQLite rowid 充当权威顺序。

待审的抽象顺序向量：按 A、B、C、D 受理，A/B 各买 1 手、C/D 各卖 1 手，兼容边仅 A–C、A–D、B–C。如果最终冻结的 FIFO 配对规则明确先取 A–C，则本窗口只匹配 1 手；不能为了匹配 2 手而改配 A–D、B–C。此例依赖先定义双方扫描顺序，兼容图是合成输入，并不证明具体开平场景存在这些关系；比例法的兼容组与取整仍待定义，不能从该例推定。

## 21. 母单数量与内转占用候选（未冻结）

在同一母单、单位、权威 journal 版本和可比切点下，候选把原始核准数量 `Q` 分为互斥的：已权威完成量 `F`、已有子单仍可能成交的最坏余量 `C`、尚可能生效的内转在途量 `T`、如设计选择持久预留的计划量 `P` 与账面未占用量 `A`，满足 `Q = F + C + T + P + A` 且各项非负。`A` 不单独授予调度资格：母单取消、到期或其他阻断时，即使 `A` 大于零也不能新增动作。`F` 中场内成交与已提交内转按唯一来源和经济事实分别计入，同一数量不能因转换及其后续关联重复计算；转换在何时可归入完成量须另行冻结。若最终不设权威计划预留，`P` 为零，普通调度意图不能冒称已占用。

新增子单或转移只有在各自需要量不超过账面 `A`、母单具备调度资格且真实账户、合约、方向、今昨及占用等额外约束可证时才可预留。若设权威计划量 `P`，必须绑定母单、用途、owner、窗口及版本；仅同一窗口持有的有效队列预留可以转换成该窗口的转移占用，未匹配量按冻结合同释放或转为该母单子单占用，其他窗口或子单的预留不得挪用。上述转换在权威事务或可证明的串行栅栏下把相应 `P` 移入 `C` 或 `T`，不能二次扣减。权威子单成交将对应 `C` 转入 `F`；双边内转确定提交时，各母单对应 `T` 转入 `F`，同一转移 ID/摘要重复只能返回原结果。每个实际子单只归唯一母单和策略，内转另以双方身份和独立转移 ID 表达，external 不参与匹配。

Gateway 候选以 writer fence 保护同一权威事务，重验两方母单、期限、账户和服务权限、原订单归属、交易日及独立阻断，并校验预先取得的可信行情/持仓证据及版本；可变来源须在提交边界有可证明 fence/version，无法证明则冻结，不能假设外部来源和 SQLite 原子一致。该事务与子单预留、取消及停止屏障串行竞争；双边分录及转移身份必须原子提交。若拆为准备和提交，准备阶段先耐久占用双方 `T`，提交阶段原子转换；跨服务 UNKNOWN 不因空查询或超时释放。此处不要求策略或每张订单额外同意轧差；真实行情和授权来源仍须证明。Execution、Gateway 与已选 Risk 各自数据库不可假设同一事务，必须逐原操作身份恢复并分别证明占用释放。

普通子单撤余只有在原身份权威终态、完整成交水位和迟到请求 fence 均可证后，才可将确证余量返还 `A` 并按既定规则重新匹配；母单取消或到期后返还的数量不得重新用于新增动作。租约失效、撤单受理、TTL 或空查询都不构成释放证明。迟到的可信成交应按原事实身份和版本化摘要幂等入账；若与已释放或已用数量冲突，保留事实、冻结并对账，不能丢弃成交来维持公式。多个对手方按每个转移 ID 分开记录已完成与 UNKNOWN，不重新随机配对或释放未决腿。

上述桶、事务与时点尚未实现；计划预留是否权威、转换归集时点、费用成本及可信切点仍待 63/65 和适用 owner 冻结。尤其不能把现有 `transfer_completed` 回调或 §14 的测试替身当作在途预留已交付。

| 崩溃或丢回复切点 | 恢复时能确定什么，以及必须保留什么 | 应补的针对性证据 |
| --- | --- | --- |
| SDK 身份持久提交之前 | 仅在能证明本地未提交且没有远端调用时可重新准备；内存丢失本身不证明没有远端副作用。 | 写失败、提交前后终止；下游调用计数、同键同摘要恢复及异摘要冲突。 |
| SDK 身份已提交，Execution 收录前后 | 原身份可恢复；远端可能未收录，也可能已收录而回包丢失。查原操作，空查询须结合迟到请求 fence，不能换键补发。 | 发送前、Execution 提交后回包前终止；原请求迟到与重放竞争。 |
| Execution 母单落库前后 | 落库只证明本地收录，不证明 Risk、Gateway 或 BT 已确定受理；原配置、期限及授权须按本 owner 版本核对。 | 提交前后与并发重放；原 spec/操作 ID 恢复、不同主体或内容冲突。 |
| 已选 Risk 请求前 UNKNOWN 持久后、Risk 提交前后 | 请求可能在途时按原风险操作查询并保留未决；R-08 deny 才要求整笔最坏预留，off/warn 不新增该级预留。Gateway 缺行不能证明 Risk 无占用；未选 Risk 不引入该依赖。 | 各模式的未到达、提交后丢回复、撤权及重启；deny 不双占，off/warn 不误增整笔预留。 |
| Gateway 登记 UNKNOWN 已持久、发送和提交前后 | 登记可能未达、在队列或已提交；原操作回执与当前观察分开核对。取消先到 NOT_FOUND 后原登记仍可能迟到，缺少可靠 fence 时不能释放相应占用。 | claim、发送栅栏、提交和回包前后终止；迟到登记与取消、重启、撤权和同号重放。§6 现有原型只证明缺口。 |
| Gateway 已登记，BT 受理投影前后 | Execution 与 Gateway 可信持久受理均绑定原身份才是确定投影前提；旧 ACTIVE 回执不能覆盖当前取消。BT 标准投影及恢复合同仍未证明。 | 页重复、通知前后终止、当前版本变化及重启；逐来源证明不重复通知与入账。 |
| 子单 PREPARED、claim 及 Gateway reserve 前后 | 本地计划不等于权威预约。claim 后未得回执可能已预约，保留原 child ID、请求键及占用；只有实际 fence 证明旧请求不可生效才可认定未发送。 | 本地 claim 前后、payload 校验失败、intent 写入、预约提交后丢回复及旧 owner 竞争；核对各库状态和无重复预约。当前 `ParentAuthority` claim 后仍可能因校验失败留下 UNKNOWN，不能把异常一概当无副作用。 |
| 已预约，dispatch marker、服务提交或原生调用前后 | marker、QUEUED 或回复丢失不证明场所已接单或未发送。按原预约、摘要、版本及实际来源查询，保留 UNKNOWN；不得凭空查询推断确定未发送。 | 各 durable marker、Gateway claim 和替身 provider 调用前后终止；真实来源身份与会话绑定、不重复派发。 |
| 确定未发送后的后续处理 | 仅权威证明 NOT_SENT 且旧请求不再生效、原母单仍有效并重新通过准入时，才可按 D65-14 的账户显式次数以新 child ID 重试；次数为零或耗尽冻结。`not_found_at_venue` 不改写为 NOT_SENT，也不自动重发。 | 迟到 fence、次数 0/用尽、期限/权限/急停/选 Risk 重验，UNKNOWN 不换身份补发。 |
| 策略主动取消，屏障或逐子单撤单回包前后 | D65-06 要求已登记母单的获授权策略在 Execution 离线时仍能由 Gateway 冻结并尝试逐笔撤销；故障本身不自动撤单。受理、超时和 TTL 不是撤成，按原身份跟踪且不影响其他母单。 | Gateway 屏障与每笔撤单提交前后重启、撤权、部分成功和迟到成交；登记未知时不得盲目释放。 |
| Gateway 回报落库，SDK checkpoint/ACK 或 Risk 释放前后 | 事实可能只落在部分 owner；按可信事实身份、摘要和各自水位恢复。原期限到达或本地完成不释放仍未知的子单。 | 成交与撤单乱序、重复回放、各水位前后终止；数量、费用及通知去重，Risk 释放独立核验。 |

当前 SDK parent client 对未验证回包返回 `None`；Execution 有本地 UNKNOWN claim，Gateway 有本地授权和预约校验，但这些都不证明完整跨服务迟到 fence、风险释放或零改动 Broker 投影。该表须与 63、适用的 64 和后续故障注入共同冻结与验证。
