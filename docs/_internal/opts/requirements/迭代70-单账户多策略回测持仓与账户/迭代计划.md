# 迭代 70（opts 线）：单账户多策略回测持仓与账户

状态：**规划草案，待后续启动**。本次只记录计划，不修改回测或实盘代码，不表示任何功能已经开发或验收。

本计划与 `docs/source/reference/optimization-docs/requirements/迭代70-基于Backtesting优化.md` 属于不同文档线，仅编号相同。现有实盘重构以[迭代 60 计划](../迭代60-统一行情容器与低转换数据链路/迭代计划.md)及其实际交付和验收状态为准；迭代 53 已废弃，不作为本计划的前置或设计依据。

## 1. 启动条件与目标

**启动时机**：用户希望先完成实盘，再优化本功能。本计划先保存；实盘相关工作完成且用户确认进入本迭代后，再核对迭代 60 的实际合同、验收和遗留项，确定回测所需的稳定基线。本文不预设迭代 60 已经完成或已获得真实账户验收。

目标是在一个 `Cerebro`、一个模拟账户和多个策略的回测中，让策略交易同一合约时，能够明确区分：

1. 每个策略自己的持仓、订单、成交及已声明支持的策略账户视图。
2. `BackBroker` 管理的整个模拟账户持仓、资金及撮合结果。
3. 策略范围和账户范围的统计差异，使同一策略源码尽可能在回测与受支持的实盘模式下复用，且作用域差异可见。

首要场景：策略 A 买入 SA 2 手，策略 B 买入同一 SA 3 手，分别查询到 2 手和 3 手，模拟账户查询到 5 手；A 的平仓不会错误使用 B 的策略持仓。资金、费用、盈亏和保证金按本迭代确认的合同分别展示，不凭持仓数量推断。

## 2. 已核对的现状

以下是 2026-11-03 的源码和本地小样本观察，开工时必须按实际 checkout、提交和未提交工作重新核对，不作为未来状态保证。

- `Cerebro` 默认创建一个 `BackBroker`；同一次运行中多个策略共用该 Broker。Broker 默认按 Data Feed 保存账户持仓，并非按策略保存；订单有 owner、通知可按 owner 分发，但这本身不构成策略持仓账本。
- 策略未绑定 `account_book` 时，`getposition()` 和 `position` 读取 Broker 的持仓。一次三根 Bar 的合成示例中，A 买入 2 手后，未交易的 B 观察到 `[0, 2, 2]`。这是单个本地样本，不代表完整回归通过。
- 策略绑定账本后已有策略范围持仓查询分支；现有 direct 账本绑定属于 `BtApiBroker` 路径，并未自动接入 `BackBroker` 的模拟成交。已有账本读视图不能单独完成模拟成交记账或撮合隔离。
- 普通 Sizer 使用 Broker 现金；部分目标价值及百分比接口使用 Broker 估值。绑定持仓视图不会自动产生策略资金或权益。反向交易时，现有账户级执行信息及 `Trade` 投影的策略归属需真实框架集成测试确认。
- 十个策略分别使用十个 `Cerebro` 可得到彼此独立的模拟资金和持仓，但不能等同于十个策略共享一个账户的回测；同一个 `Cerebro` 的默认行为则是共享账户，并非开箱即用的策略隔离。

## 3. 范围与原则

### 3.1 本迭代范围

- 在保持既有默认回测兼容的前提下，设计并实现**显式启用**的单进程、单 `Cerebro`、单模拟账户、多策略回测能力。最终配置项和 API 以设计评审为准；本文不声称相关开关已存在。
- 复用 Cerebro 现有策略调度及 `BackBroker` 模拟撮合和账户记账；模拟成交有明确策略 owner，策略账本只按约定的已成交事实更新，提供策略视图和独立账户视图。
- 在确认支持的范围内处理持仓、订单归属、部分成交、费用、平仓、资金/预算、估值、盈亏及框架回调；未实现的字段和组合明确不可用，不以账户值冒充策略值。
- 基于实盘完成后的实际合同，盘点并复用可共享的策略视图协议和语义；回测适配器以 Backtrader 为主，具体可复用代码归属以开工盘点及设计决定为准。允许内存账本；不为普通回测强制引入 Gateway、ZMQ、provider、实盘持久化服务或可选 Risk/Execution/Monitor。
- 设计、实现及验收区分现货/期货、净持仓/双向持仓以及不同策略方向；首期支持矩阵必须经设计审阅确定。当前没有证据支持宣称所有组合均可用。

### 3.2 非目标

- 本迭代不重做交易所接入、实盘账本或 Gateway，不把回测结果当作实盘或账户授权证据。
- 不创建第二个策略调度器，也不因为策略账本绕过 Broker 撮合或直接篡改账户持仓。
- 不预先承诺多进程共享回测账户、分布式撮合、交易所级市场冲击模型、自动策略订单聚合或跨策略内部撮合；如后续需要，另行设计。
- 不默认改变未启用此能力的既有回测语义；如盘点发现必须变更，先列破坏性影响和迁移方案，再由用户决策。

## 4. 目标职责和数据流

```text
历史 Feed ──> Cerebro 依次驱动多个 Strategy
                         │  带策略归属的订单
                         ▼
                  BackBroker 模拟撮合
                         │  已成交事实、订单状态、费用
            ┌────────────┴────────────┐
            ▼                         ▼
     模拟账户持仓与资金          回测策略账本
     （账户级视图）              （逐策略视图）
            └────────────┬────────────┘
                         ▼
       一致性检查 → 框架通知 / Trade / Analyzer / Observer
```

该图表达目标，不规定最终类名或调用栈。设计需明确：成交由谁产生，账户和策略账本谁拥有写入权，更新顺序、可观察时点及失败行为是什么；不得让回测账本和 Broker 各自独立撮合。策略账本的更新必须与当前执行模型一致，避免在通知前后多次消费同一成交；如无法维持一致性，停止当前模拟并报告错误，不能继续输出看似完整的结果。

建议策略使用统一的策略作用域接口；账户总持仓、总资金和账户权益通过清晰的账户级入口访问。回测只读快照与可变 Broker 对象的隔离方式、性能成本，以及与迭代 60 实际接口的兼容，需要开工后确定。

## 8. 风险与回退

- 最大风险是账户净仓与策略虚拟敞口不一致时，误判开平、盈亏和保证金。先冻结支持矩阵；不支持时拒绝，不通过重写账户持仓掩盖差异。
- 新策略视图可能影响已有 Sizer、目标仓位、分析器与通知；默认关闭、建立旧行为基线，审定破坏性变化后再迁移。
- 内存账本只服务本次模拟运行；是否需要中断恢复或持久化由后续需求单独决定，不沿用实盘恢复语义作默认承诺。
- 回退路径为关闭显式启用的回测策略账本并恢复旧默认行为；保留测试数据、结果和差异说明。若涉及持久化格式或公开 API 迁移，另提供版本化迁移与回退步骤。
