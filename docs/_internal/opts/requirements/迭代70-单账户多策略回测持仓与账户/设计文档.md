## 2. 接口与绑定

63.01 与70.01冻结共同签名，以下是主架构接口提案，必须在两个 Broker 实现与真实 Strategy 调用中一起核对：

| 层 | 提案 | 合同 |
| --- | --- | --- |
| Strategy | `get_strategy_cash()`、`get_strategy_value()` | 自动传入自身已绑定身份，返回策略可用资金/权益。 |
| Strategy | `get_strategy_position(data=None, broker=None, side=None)` | 默认本策略首个 Data/当前 Broker；显式其他 Broker 必须已有对应策略绑定；side 仅支持已声明模型。 |
| BrokerBase / BackBroker / BtApiBroker | `get_strategy_cash(*, strategy)`、`get_strategy_value(*, strategy)` | strategy 必填，接受已注册策略实例并解析其稳定 ID；不使用进程全局的“当前策略”。 |
| BrokerBase / BackBroker / BtApiBroker | `get_strategy_position(data, *, strategy, clone=True, side=None)` | 返回隔离的 BT Position 视图；未知策略/资产、未支持方向明确失败，读取不能制造账本条目。 |

三个公开方法在受支持 Broker 中始终存在，账户默认语义不受账本开关改变。首期默认保持旧回测撮合及策略账本关闭，显式策略预算配置或显式启用策略账户视图时创建账本；单策略启用时可按 D63-45 使用显式账户初资。账本未启用/未绑定时新 getter 明确不可用，不能静默返回账户值；close/target/Sizer 的策略隔离作用于已启用的策略账户模式，旧模式兼容单列验收，不称为新策略隔离通过。

返回数值沿用 BT 公开数值习惯；中间计算精度、浮点转换及误差容差在70.01固定。不可用应有稳定原因，如未绑定、未分配、缺价格/费率、币种不可比、未支持资产模型；不能用0、NaN、账户值掩盖。资金未分配不妨碍有合法绑定的持仓查询；已证明空仓可返回零仓。

账户旧名、`getaccountposition(s)` 及 position/positions、按名称/集合查询的迁移按 D63-41 逐项登记。自动交易消费者必须显式转向策略接口；普通未启用模式的旧行为保留基线，显式策略模式不能静默回退。是否增加 Strategy 的账户现金便捷委托不影响已有 `strategy.broker.getcash/getvalue` 的账户含义。

## 3. 初始化与本地状态

BackBroker 拥有模拟账户事实和本次运行的策略账本；允许内存存储，不启动 Gateway、ZMQ、Risk、Execution、Monitor 或实盘 provider，不建立第二套撮合器。Cerebro 仍是唯一策略调度器。实盘策略账本权威仍由63提供；两种模式共享合同与测试向量，不把内存回测账本称为实盘权威。

候选状态由当前运行 ID、策略稳定 ID、账户/资产/币种标识、事件序号、预算版本、持仓成本、费用及占用记录构成。策略 ID 区分同类多实例及重复名称，不使用展示名、订单 tradeid 或 Data 对象地址作为跨运行业务身份。Feed→资产的映射由显式元数据确定；同合约多个 Feed 的归并规则在70.01冻结，不能凭同名自动合并。

D63-45 初始化顺序：解析并校验完整运行策略清单和预算配置 → 登记显式账户初资来源 → 生成运行/策略身份 → 绑定对应预算与资产模型 → 发布初始快照 → 开始允许依赖策略资金的计算。当前 Broker 在策略构造之前启动，不能仅在 Broker.start 时猜测最终策略数。70.01原型需确定工厂绑定钩子；若某构造阶段尚未绑定，必须明确返回未初始化，至少在 Strategy.start/首次交易回调前完成。不得在首个 getter 调用时懒猜唯一策略。

单策略仅在明确通过 `BackBroker(cash=...)` 或运行前 `setcash(...)` 设置账户初资时，允许将其登记为唯一策略预算；已有显式策略预算优先，不重复相加。库内默认现金不自动获得该身份；配置解析/参数工厂必须保留调用者是否显式设置及覆盖来源标志，不能看金额是否等于10000来猜测。显式配置恰好等于库默认值仍是显式来源。多策略不复制账户初资；缺预算时策略资金接口不可用。StrategySkip、重复运行、优化进程、策略数改变须重新核验清单与绑定，不继承上次状态。运行中 setcash/add_cash 与策略预算调整分开，未定义的组合明确拒绝或报告不可用，不静默把账户入金分给所有策略。D63-46 已允许显式预算超配；预算比例基准、运行中调整和未分配余额的具体配置流程仍须冻结。

**D63-46 已确认：允许显式预算超配，账户资金约束另查。** 账户初始权益100万、A/B预算各60万可接受，不拒绝该预算配置、不自动缩成50万，不改变provider/模拟账户真实资金。各策略getter仍按自己的预算计算，不能要求策略权益合计等于账户；同币种可比切点下单列初始预算调节项100−120=−20万，仅解释配置差额，不进入资金池或记作实际借款、亏损、外部残差成交。显式预算调整与真实入出金各有事件/版本，调节项不能掩盖未知交易事实。

实际资金约束按职责保留：BackBroker检查模拟账户购买力，实盘provider/柜台决定实际可承接能力；选择Risk且R-08 deny时另作账户原子预留及适用策略预算检查，不强制安装Risk、不把资金政策迁入Gateway；D64-10 已确认 R-08 缺省 off，仍可显式配置 warn/deny，策略虚拟保证金记账和 BackBroker 账户购买力检查不因 off 停止。账户100万、两笔各需新增资金60万，即使各策略预算满足，也不能在有账户资金预检的路径同时认定足额；验收第一笔预留后40万、第二笔不足、重复/恢复不虚增资金。配置字段、比例基准及预算调整流程仍按共享合同冻结。

## 4. 统一会计模型

同一策略、币种与估值切点上：

```text
E = B0 + B_delta + R_gross + U - F
C = E - M - H
```

E 对应 get_strategy_value，C 对应 get_strategy_cash；B0 是初始预算，B_delta 是已生效预算调整，R_gross 是费用前已实现盈亏，U 是尚未实现浮动盈亏，F 是已确认费用，M 是已定义的虚拟持仓保证金/资产资金占用，H 是尚未被 M/F 等前项覆盖的在途预留。对期货按 D65-36，各策略虚拟仓独立计提 M，跨策略抵消不减该占用；账户真实/模拟保证金另列，不要求各策略 M 求和等于账户保证金。

技术设计约束：

- Getter 原样返回负值。Sizer 根据非正可用资金拒绝或不下单属于自己的政策，不在 getter 内截零，不自动授权强平或启用 Risk。
- 持仓使用策略自身成交成本计算 R/U，不把账户净仓的 opened/closed/pnl 直接归给当前订单 owner。A 开空可能在账户上平掉 A/B 的净多，策略自身仍是开空；两层分别记账并核对映射。
- 对已验证的线性期货模型，采用开仓成本基准计算累计策略 R/U；账户逐 bar 的 cashadjust 是账户现金结算/调整，不作为第二笔策略盈亏复制进 R。若改用结算基准分段法，必须同步成本并用模型测试证明收益守恒，不得混用。`ComminfoFuturesInverse` 的逐段价格比公式不保证与开仓到终值的一次计算相同；须单列多段反例、成本/结算/费用模型和可比性，未适配标记不可用，不能声称所有现有期货类天然等价。
- 开/平手续费与利息各有唯一经济事件。check_submitted/pseudoexec 试算不写成交或费用账；实际模拟成交使用 `_execute` 对开/平角色计入账户的手续费源，不能将当前返回值被忽略的 `confirmexec()` 再当一笔费用。账户已扣的 credit interest 若又出现在 int2pnl/closedcomm 的通知字段中，不再次扣 F。利息须按对应策略承担的持仓/借款、时间及费率模型明确归属，不能把按 Data/腿累计的全部利息记给第一个平单 owner；模型不能分解时列未归属项并令相关策略费用/权益不可用。估计费用可作为 H 的一部分，确认后转换而非双扣。
- 现货买入后资金占用必须有资产模型。例如预算1000，买5股于100、现价110、无费用，E=1050；若声明无融资现金交易模型，应有可解释的已投资资金占用与余额，不能用 M=0 得出1050全部可买。以成本500还是市值550计占用、融资本金及空头规则会改变 C，需在支持矩阵冻结，不伪称现有 spot 估值已解决。
- 缺价格、乘数、费率、币种或费用依据时，对应 E/C 不可用。不能用最后任意缓存或账户余额补足；单币种先交付，其他组合按支持矩阵声明。
- 预算、资金占用、状态版本、费率和估值切点必须可复现。查询不推进账本，不做隐藏资金调整；标记价格只取当前模拟时间已可见数据，不能读取未来 Bar。

## 5. 模拟成交、预留与发布时点

由现有 BackBroker 撮合产生真实模拟成交，策略账本消费已确定的增量；不能再撮合一次，也不能在通知消费端重复记账。候选事件身份为运行 ID＋账户＋订单 ref＋成交增量序号；费用更正另带修订版本。同键异内容报一致性错误；重复同内容不改变账户或策略。

受理阶段对订单固定 owner、资产、策略/账户意图、数量/价格约束及预算版本；策略模式缺 owner 不自动归到第一策略。历史订单导入和旧通知 owner 回退的兼容行为只留在旧模式；策略模式必须有显式归属映射，否则拒绝对应输入。

每笔已确认成交先更新本地一致单元：核验数量和状态 → 原账户撮合/费用事实 → 策略成本及持仓增量 → 映射/预留状态 → 不可变成交事件及序号。当前通知会等待整个 `broker.next()` 完成；该轮全部成交、cashadjust和估值完成后才发布一致的账户/策略周期快照并分发通知。采用周期最终可见快照语义：通知保留自身订单事件序号，getter读取最新已发布快照，不冒充该笔成交瞬间的资金历史值。预检或暂存保证中间失败时停止并报告不完整；不让通知看到半边账或继续输出完整绩效。具体内存事务布局由70.02原型验证，不宣称与实盘跨库有共同原子事务。

在途 H 要区分已受理未成交、部分成交、取消/拒绝及终态：提交预留，实际成交将对应预留转换为持仓 M/实际 F，取消只释放未成部分，同一份占用不重复计算。多笔请求即使同 Bar 也按冻结受理顺序和当前占用核验，不复用旧余额放行。普通账户购买力检查保持；策略超预算的具体准入政策与查询负值是不同合同。

订单事件切点与getter最新快照切点分别记录，快照包含运行/周期、估值时刻及账本序号；同一批通知通常读取周期最终资金，不要求第一笔通知对应第一笔资金值。回调内新提交产生的H变更要先原子发布新的预留版本，再供后续查询使用，不重新撮合。quicknotify、同Bar多笔/多策略、bar结算均验证这一规则；若需历史逐笔资金则读取绑定事件的快照，不用无版本getter回推。Trade按自身事件序列处理，Analyzer/Observer按声明的估值切点统计。账户execution bit与策略开平可能不同，70.05不能直接用账户closed/opened位更新策略Trade；各策略消费进度不得互相覆盖。

## 6. 回测与实盘对照及迭代分工

63拥有实盘账户/策略 API、授权账本和事实投影；64选用时消费统一资金视图作业务风险控制；65提出内部转移/转换，处理 D65-35 手续费及 D65-36 保证金；70实现 BackBroker本地接口/策略账本和框架消费者。63.01与70.01协调共同签名和向量，不以70尚未实施阻塞63独立基础路径，也不以63替身验收替代回测。

统一接口不自动扩展70为完整 Execution 算法或内部撮合引擎。BackBroker自身模拟成交和反向策略持仓映射属于70范围；若要模拟65的未下场内部抵消，需要显式可复用事件适配与范围设计，不能把两次实际模拟成交伪装成无场所转移。已支持相同来源语义的组合才作逐项对照，其他项记 GAP，不宣称“全部模式统一”已完成。

## 7. 必需验收向量

- A持仓2/B持仓3/账户5；两个旧getposition都取账户5，新策略getter分别2/3；A close只处理2。查询结果修改不能改变底层账户或B持仓。
- D63-44数值：B0=100000、R=2000、U=3000、F=100、M=20000、H=10000得到E104900/C74900；U=-3000得到E98900/C68900；释放H10000只增加C。H使C为负时如实返回；重复成交/费用/释放均不再次改变结果。
- 单策略显式cash/setcash预算别名、显式策略预算优先、库默认金额不自动分配、多策略未配不可用；重复运行/优化/跳过策略、构造和start回调查询、同类多实例不串账。
- 现货开/加/部分平/全平及浮盈亏；线性期货多Bar cashadjust后部分平/反手/支持的双侧，inverse多段非可比反例及明确拒绝，手续费和利息各计一次且不误归第一平单策略。缺参数/估值/费用明确不可用。
- 受理、部分成交、撤单、拒单、重复输入与未决占用，账户及策略资金竞争；历史无主订单不能默归第一策略。覆盖runonce两模式、同Bar不同策略顺序和支持的cheat配置。
- 账户100万、显式策略预算60万/60万合法；策略初始E/C各60万而账户仍100万，预算调节−20万只供对账。账户购买力不足不因策略预算合计更大而放行；重复、恢复及预算调整不创造账户资金，未能对账的交易差异不能用预算调节吞掉。
- 同预算、资产模型、价格、费率、映射及受控事件，回测与实盘策略投影的E/C/Position、完成量、费用和原因码一致；真实撮合差异单列，不把受控输入对照称为真实账户接受。

文档静态检查不替代上述产品测试。实际检查记录命令、环境、输入、输出及证据等级；未实施/未运行项为 NOT_RUN，不能由接口名称存在推出完成。
