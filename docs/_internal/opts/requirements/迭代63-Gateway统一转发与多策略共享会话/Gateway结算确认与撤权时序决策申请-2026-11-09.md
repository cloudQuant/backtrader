# Gateway 结算确认与撤权时序决策申请

日期：2026-11-09。状态：用户已于 2026-11-09 选择 A；相关合同已同步，实现和验收尚未完成。

## 需要决定的情形

用户已决定 Gateway 每交易日自动确认 CTP 结算，并选择订单最终核对后视为已在途。订单的决定没有自动规定**结算确认**的撤权时序。

当前 CTP 结算确认和部分查询会持内部锁等待原生接口；如果原生调用长期不返回，账户会话或控制操作可能被拖慢。释放锁前需要同时解决单次票据、交易日、账户、连接代际与 SDK grant 的最终复核。原生调用后失联时不得将结果当成未确认或自动重复发送。

## 选择 A：结算也使用已准入在途语义（建议）

在同账户、交易日、会话、结算未确认观察和当前授权均经过最终核对后，先耐久记录原确认意图及唯一身份；短临界区原子确认调用许可后视为在途，释放控制锁再调用 CTP。撤权/停机先于许可则不得确认；许可先于撤权时，**结算确认可能在撤权完成后才到达柜台**。丢回复、超时或崩溃保持 UNKNOWN，只按原身份查询/回读，不重复发送；只有可信回读证明该账户当日已确认才视为成功。权限或来源缺证时失败关闭。

该选择不允许撤权后的新结算意图获取许可，不意味着任何交易订单被授权，也不将成功提交当作结算确认成功。日切、换账户/前置、旧 grant、重复调用及并发读回须按同一会话和交易日隔离。

## 选择 B：保持严格撤权时序

保持既有严格解释：撤权完成后，尚未进入厂商调用的结算确认不得进入；如需跨调用入口持锁，原生调用长期挂起时，撤权完成或其他控制可能长时间等待。等待超时不能证明确认未发送，仍按原身份回读且不得盲目重发。

## 后续验证

需要对 Registry grant、SDK coordinator、CTP provider/session 做共同版本与最终门槛设计，覆盖撤权先后、原生阻塞、结算观察与日切竞争、确认前后崩溃、重复回调和重启；只使用合成 provider，真实账户另需授权。此方案不自动开放当前仍缺全域证明的 Gateway 新单。
