# Gateway 原生派发与撤权时序决策申请

日期：2026-11-09。状态：用户已于 2026-11-09 选择 B；相关合同已同步，代码实现与验收尚未完成。

## 场景

Gateway 在发送原生 CTP 报单前，需要核对主体授权、急停、行情有效性以及订单身份。当前普通订单实现为保持最终检查与原生调用之间的约束，在原生调用期间持有 Registry 和行情门禁锁；若原生调用长时间不返回，同一进程中的部分授权变化和行情状态更新可能被阻塞。母单还需读取账本，存在与 CTP 会话锁的反向顺序风险，当前 market + parent 在派发标记前拒绝。

独立探针复现了反向锁机制；尚未证明默认受信 owner 下存在合法的跨线程反向执行。真实 CTP 下原生函数是否可能长期阻塞尚无测量。不能通过增加超时推断请求未发送，也不能移除母单、授权或行情校验。

## 选择 A：保持严格撤权时序

保持既有解释：撤权或急停完成后不能有新的原生调用；为避免穿越检查与调用窗口，必要时让撤权等待已进入临界区的原生调用返回。若调用无界阻塞，撤权完成和部分状态更新也可能长时间等待；母单仍保持拒绝，直到实现可证明的有界场所栅栏。请求状态不明时保留 UNKNOWN。

## 选择 B：明确已准入派发的线性化点（建议）

在短临界区内完成当前授权、急停、行情、账户/策略/订单和母单证据检查，原子确认派发许可后即认定该原请求已在途，并持久记录可恢复身份；释放 Registry、行情和账本锁后调用原生 API。撤权或急停先于该确认时不得发送；确认先于撤权时，撤权可立即完成，但这笔已在途的报单**可能在撤权完成后才到达柜台**。该笔订单按原身份报告在途或 UNKNOWN，对账或 DRAIN 撤单，不宣称撤单成功，也不盲重发。所有可以影响母单、行情、主体、会话和风险证据的写者必须参与同一版本/失效协议；未接入的来源继续 fail-closed。即使选 B，也不能保证原生调用立即返回或控制柜台行为。

B 改变的是“撤权完成”与已准入但未进入原生 API 的请求之间的可观察时序；它不允许撤权后的新请求取得派发许可，也不替代券商实时账户与交易事实。若已批准风险服务，Gateway 仍不代替风险策略或伪造风控审批。

## 验证范围

分别测试撤权/急停先于许可与许可先于撤权、行情和母单并发变化、provider 挂起/退出、迟到回报、崩溃和原键恢复；检查 Registry、行情和 SQLite 不因原生阻塞被无限占用；真实账户另需明确授权。方案 B 对现行“任一侧关闭都不能写”的影响需用户明确接受后才修改代码和合同。
