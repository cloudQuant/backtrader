# 迭代 63 需求原文：Gateway 统一转发与多策略共享会话

记录日期：2026-11-06。
背景：迭代 62 的 62.08 交付中，`examples/live/007_ctp` 的 11 个 `*_gateway` 示例采用混合方式：行情经 Gateway CTP MarketHub，下单与账户事实经策略进程自己的 SDK direct CTP 交易会话；经 Gateway 托管执行运行时的下单因 6 项生产缺口返回 `managed_gateway_execution_unavailable`（见[迭代 62 计划修改记录](../迭代62-问题修复/计划修改记录.md) 2026-11-06 01:10 行）。用户在迭代 62 实施与 SimNow 验收期间的同日讨论中提出以下要求。

本文件只保存用户原话和同一讨论中的决定，不包含设计结论；设计见[迭代计划](迭代计划.md)。2026-11-06 晚用户就两份分析（[信号与订单链路组件顺序](分析-信号与订单链路组件顺序.md) 的 S-01～S-12、[风控位置与控制面归属](分析-风控位置与控制面归属.md) 的 S-13～S-25）逐条作出的决定补记在原话 4～10 与 U63-4～U63-27；计划据此的修改见[计划修改记录](计划修改记录.md)。

1. “现在下单不是要通过bt_api_py，然后通过bt_api_py的统一接口进行下单，当参数配置是ctp的时候，会通过ctp进行下单，是这样进行的吧？现在gateway只是做行情和账户信息的转发，后续的托管下单是要进去到bt_api_risk, bt_api_execution中负责，需要按照这个意图来，如果当前迭代计划有问题，可以修复一下当前的迭代计划”
2. “本次需要把gateway也负责转发订单等账户信息，也负责转发下单信息，因为可能就只使用了bt_api_gateway这个组件，所以希望使用这个组件的时候，直接建立了一个多个策略共用的session, 下单也通过gateway, 这样可以避免多个策略使用一个ctp账号，创建太多的session导致session超了，按照这个去修复；当使用了gateway的组件之后，基本上应该是不需要bt那边直接连接交易所的session这种了。”

以下原话 4～10 为 2026-11-06 晚就两份分析逐条讨论时所说，由主会话转来（逐字）：

## 3. 解读说明（起草人注，非用户原话）

- 原话 1 后半句（“现在gateway只是做行情和账户信息的转发，后续的托管下单是要进去到bt_api_risk, bt_api_execution中负责”）已由原话 3 更正（“我弄错了，bt_api_gateway是需要有转发订单的功能的”）。本迭代以原话 2、3 为准：Gateway 转发行情、账户信息和订单；`bt_api_execution` 负责执行功能与算法交易；`bt_api_risk` 提供风控。
- 原话 1 前半句是一个提问（现在下单是否经 bt_api_py 统一接口、配置为 CTP 时经 CTP 下单），回答见[迭代计划](迭代计划.md) §1.1。
- 原话 1 末句“如果当前迭代计划有问题，可以修复一下当前的迭代计划”针对迭代 62 计划；62.08 的相应改动由主会话记入迭代 62 的计划修改记录，本迭代只引用。
- 原话 5 与 63 控制面分析 S-01 的建议（选项 a：risk 作为库运行在 Gateway 进程内）不同，以原话 5 为准。原话 6 更正的是原话 5 之后讨论中的一句话：Gateway 并不要求订单带有风控批准。两句合起来理解为：risk 是 Gateway 之前的可选独立服务，经不经过它由 bt_api_py 的部署配置决定，Gateway 不检查。由此，配置错误的客户端可以绕过 risk；计划把这一点记为已知并已接受的性质，不作为要求。
- 原话 9 表明，不选 risk 时没有跨策略自成交保护，这是已知的功能缺失；计划不在 Gateway 中补这项检查，也不因此限制写 principal 的数量（63 控制面分析 S-13 的 b、c、d 都不采用）。
- 原话 10 与 U63-14 合起来理解为：monitor 不发出任何控制命令；`monitor_required` 打开时，由 Gateway 根据自己观察到的 monitor 存活情况施加 STOP_NEW，不等 monitor 发命令。
- U63-26 与 63 控制面分析 S-24 的建议（选项 a：中立词汇 + 对照表，现有名字不改）不同，以用户决定为准：现有代码改名为同一套词汇。
- U63-25 记的是用户的说明。截至 backtrader `74c48c7e3`，`backtrader/` 与 `examples/live/007_ctp/*/run.py` 中检索不到 SIGTERM 处理（STATIC）；是否已在迭代 62 的其他提交或未提交改动中完成，由主会话核对。

## 4. 主会话归纳的目标（非用户原话，供审阅核对）

- `bt_api_gateway` 转发行情、账户信息（持仓、活动委托、成交、资金、权限、回报）以及下单/撤单命令。
- 每个账户一个 CTP 交易会话，由多个策略进程共享，以免超过 CTP 会话数限制。
- 使用 Gateway 时，BT 不打开任何直连交易所会话。
- `bt_api_execution` 仍负责执行功能和算法交易，不负责基础转发；它是 Gateway 之后才能启用的独立服务（迭代 65）。
- `bt_api_risk` 提供风控，作为 Gateway 之前的可选独立服务（迭代 64）；Gateway 自身只做授权、归属、流控，并持有急停状态。
- Gateway 相关的开发（包括为 64、65、66 提供的 Gateway 侧能力）都在迭代 63。
- monitor 只观察，不发控制命令。
- 确认程序化交易报告事项之前，Gateway 写入只用于 SimNow。
