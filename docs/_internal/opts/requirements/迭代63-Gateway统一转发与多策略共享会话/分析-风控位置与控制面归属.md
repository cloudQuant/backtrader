## 0. 结论速览

| 问题 | 建议 | 主要理由 |
| --- | --- | --- |
| S-01 risk 在哪里运行 | **a**：作为库运行在 Gateway 交易 owner 进程内，在每账户派发锁内同步调用 | 共享会话的唯一出口是 Gateway。S-02 b 已把自成交、报撤单计数划给 risk，这两项必须看到账户上全部策略的活动单，并且与派发同锁 |
| 启停按钮 | **生命周期**由 `bt_api_runtime` 执行（进程监督）；**下单栅栏**由 Gateway 执行；**按钮界面**先做 runtime 的本机运维入口，Gateway 部署下 monitor 控制台可作为可选前端 | “启停”是进程生命周期，不是下单控制。Gateway 持有 CTP 凭据，不宜再负责拉起进程。monitor 按 S-09/S-10 是可选组件，不能做唯一入口 |
| S-04 急停 | **状态与执行**放在每账户唯一的派发点，Gateway 模式下是 Gateway 交易 owner，与预留、派发记录存在同一个库；**命令**可来自运营界面、monitor 告警、risk、runtime，以及 Gateway 自身 | 只有在出口执行才不可绕过，也才能覆盖 execution 子单（S-07）；同库同锁才没有“检查与发送之间”的竞态 |
| direct 模式 | 按 S-09 不设计 risk/monitor。现有的停止手段：SDK 写入准入（部署期开关，不是急停）、策略自身停止（`runstop` → `_direct_stop`）、操作系统终止 | direct 是单策略独占账户（D62-05），“停止策略”就等于“停止该账户的写入并撤单” |

关键发现（STATIC）：

1. **同名不同义。** 现有三处实现对同一组词的理解各不相同（§3.1）：
   - risk 的冻结只拦“增加风险”的预留，相当于用户定义的 STOP_NEW；
   - SDK `ServiceRegistry` 的 STOP_NEW 拦全部提交类操作（含平仓），接近用户定义的 FREEZE；
   - monitor 的 DRAIN 在现有执行者里直接返回 unsupported。

   急停需要在 `bt_api_base` 定义一份中立语义，不能沿用现有名字。
2. **risk 冻结只有账户一级。** 它的范围类型是 `AccountScope`，表达不了策略或合约范围，所以急停不能建在 risk 冻结上。
3. **启停的基础设施缺失。** `bt_api_runtime` 只有进程内装配和离线 `validate`/`doctor`，没有进程监督、远程接口和鉴权。BT 示例不处理 SIGTERM，收到 SIGTERM 会直接终止，不走优雅停止。
4. **S-02 b 与 S-09 叠加后的空档。** Gateway 部署如果不选 risk，同一账户上的多个策略之间就没有自成交和报撤单计数保护；而交易所正是按客户合并统计这两项（§1.2）。需要一个决定（§4 S-13）。
5. **更正链路分析 §4.1。** risk 并非完全没有自成交门禁：它有一个粗粒度的预留级互斥，不看价格和方向，只覆盖经过 risk 的预留（`risk: core/admission.py:12750-12790`）。它不能替代派发时的相交判断（C-5）。

## 1. 问题一（S-01）：Gateway 模式下 risk 运行在哪里

### 1.1 行业平台的做法

| 平台 | 交易前风控在哪里运行 | 管什么 | 对本项目的含义 |
| --- | --- | --- | --- |
| VeighNa | RiskManager 在主引擎进程内替换 `MainEngine.send_order`：每笔委托先 `check_allowed`，通过后才交给网关（引用 [R6]）。规则包括活动委托上限、单笔数量/价值上限、合约撤单上限等，每条规则可单独启停（引用 [R7]） | 账户/网关级，不区分策略 | 风控在唯一下单出口，与网关同进程 |
| VeighNa RpcService | 一个服务端进程作为“统一的行情和交易路由通道，允许多客户端同时连接”（引用 [R9]）。文档另称可在服务端加载 RiskManagerApp，做多交易员共享通道下的产品级风控（检索摘要） | 多个进程共享一个账户通道 | 与迭代 63 的共享 Gateway 结构相同；风控放在服务端 |
| NautilusTrader | RiskEngine 在内核中，位于策略/执行算法与 ExecutionEngine 之间的提交、改单路径上，撤单与查询不经过它。交易状态有 ACTIVE、REDUCING、HALTED（引用 [R1]）。一个进程一个节点，生产上建议把多个策略放在同一节点（引用 [R2]） | 节点级，覆盖同节点全部策略 | 风控与执行同进程、同线程，没有跨进程检查 |
| QuantConnect LEAN | 算法内的风险模型调整组合目标后才交给执行模型（引用 [R14]）；券商模型在 LEAN 把订单发往真实券商之前校验（引用 [R14]）；之后是券商自身风控 | 单个算法 | 策略内风控、平台出口校验、券商三层 |
| WonderTrader | 有“通道流量风控”（合规风险：总撤单笔数、短时间内下单和撤单次数）、账户资金风控、组合盘资金风控，以及在策略或组合出风险时“直接断开信号执行”的离合器；策略只设置目标仓位，执行在独立线程（引用 [R10]） | 通道、账户、组合三级 | 合规类计数放在通道层；“离合器”就是急停 |
| TqSdk（天勤） | SDK 内的本地规则：交易日内开仓次数、开仓手数、累计开仓手数、每秒报撤单次数，违规抛出 `TqRiskRuleError`；多账户时须指定账户（引用 [R11]） | 账户 × 合约/交易所 | 规则只统计本进程的委托；多个进程共用一个账户时能否合计，文档未说明（UNKNOWN） |
| Hummingbot | `kill_switch_rate`：收益率达到阈值即停止机器人，属于策略级盈亏止损（引用 [R12]）。多个机器人共用一个账户时，用 `rate_limits_share_pct` 静态切分交易所限频，接近份额时只告警（引用 [R12]） | 单个机器人 | 策略级止损放在策略进程；跨机器人只有静态切分，没有统一仲裁 |

规律：

- 单进程平台（VeighNa 主引擎、NautilusTrader 节点、LEAN）中，策略进程就是出口进程，所以“风控在策略进程内”与“风控在出口”是同一件事。
- 一旦多个进程共享一个账户（VeighNa RpcService），风控就跟着网关移到服务端。
- 留在策略进程里的，是策略自身的止损和额度（Hummingbot、LEAN 风险模型），它们不承担账户级检查。

### 1.3 四层分工：什么放在哪一层

行业实践可以归纳为四条：

1. 纵深防御，每层都不假设其他层存在。
2. 规则放在“拥有判断所需信息的最早位置”做早拒，同时在“不可绕过的最后出口”做权威检查。
3. 最后一道检查由对账户负责的一方控制，独立于下单方（15c3-5 (d)）。
4. 急停在出口执行，撤单不受阻。

| 层 | 典型内容 | 谁的信息足够 | Gateway 模式下的对应 | direct 模式下的对应 |
| --- | --- | --- | --- | --- |
| ① 策略自查 | 信号合理性；本策略的仓位、额度和亏损止损（如 Hummingbot kill switch、LEAN 风险模型） | 本策略 | BT 策略代码 + BT 预检（早拒，不作为权威：`BT: backtrader/brokers/_btapi_direct_mode.py:1464-1523`） | 同左，而且这也是唯一的平台层 |
| ② 平台出口 | 授权、归属、可平量、流控与保留容量、急停；单笔上限、价格带、自成交、报撤单计数（后四项按 S-02 b 归 risk） | 只有出口能看到全部策略的活动单和共享配额 | Gateway 交易 owner + 进程内 risk 库 | SDK 协调器只有写入准入（S-09：不加 risk） |
| ③ 券商柜台 | 验资验仓、报单流控、会话数、交易权限 | 账户合计 | CTP 柜台（由经纪商配置，数值 UNKNOWN） | 同左 |
| ④ 交易所 | 涨跌停、单笔最大下单量、持仓限额、异常交易监控 | 全市场，按客户合并 | 交易所 | 同左 |

策略进程里的风控（用户说的“这个策略在做”）应当保留：凡是只与本策略逻辑有关的检查都放在 ①，越早拒越省配额。但 ① 只能比 ② 更严，不能放宽，也不承担账户级检查（链路分析 P5）。

### 1.4 共享会话与同合约多策略带来的约束

1. **统计口径是账户（客户），不是策略。** 交易所按客户和实控组统计自成交与撤单；柜台按账户和会话限流。N 个策略各自“合规”，合计后仍可能超限，只有 Gateway 能做合计。
2. **自成交只能在派发时判断。** 链路分析 C-5 已说明预留时检查有竞态。判断需要“其他策略已派发、派发中或 UNKNOWN 的反向单”，这些状态都在 Gateway 日志里。
3. **检查与发送必须同锁**（链路分析 P2）。如果 risk 不在 Gateway 进程，派发锁就要跨一次网络往返。迭代计划 §3.1 正是因此否决了方案 C：持锁跨网络时，一方慢就会阻塞整个账户。
4. **配额共享。** 一个策略被限频不应挤占他人；撤单和平仓要有保留容量（`gw: quota_admission.py:10-14`、`:41`、`:232`，STATIC）。
5. **execution 子单也经 Gateway（S-07）。** 放在 Gateway 的检查天然覆盖子单；放在策略进程的检查覆盖不到。

### 1.5 选项比较

| 选项 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **a** Gateway 进程内的库 | Gateway 交易 owner 在预留时调 `reserve`，在派发锁内调 `claim`，派发后 `settle` 或 `release`（调用点见链路分析 C-1） | 与派发同锁，没有竞态；不增加故障点；与 VeighNa RiskManager/RpcService、NautilusTrader RiskEngine 同一模式；自然覆盖 execution 子单 | risk 的缺陷或卡顿会拖住该账户的 Gateway；两者发布节奏耦合；Python 进程内每笔多一次 SQLite 事务，时延未知（UNKNOWN，需实测）；必须先解决账户级 dispatch latch（S-06） | **推荐** |
| b 独立 risk 服务，Gateway 同步调用 | 每笔经一次 RPC | 可独立部署和升级；将来能跨账户（多个 Gateway）合计；进程隔离 | 派发锁内多一次网络往返，放到锁外又有竞态；RPC 超时时预留是否生效不明，需要幂等预留号和 TTL；自成交检查要把全部活动单同步给服务；服务宕机时按 S-05 a 所有账户同时停写 | 不建议用于逐单路径 |
| c 各策略进程内 | 每个策略自带 risk | 早拒，无网络开销 | 看不到其他策略，做不了账户合计、自成交和报撤单计数；策略可以绕过；违反链路分析 P1 和 15c3-5 (d) 的独立控制原则；S-09 下 risk 只随 Gateway 存在，放进策略进程没有意义 | 否 |
| a′（a 的远期扩展） | 逐单检查仍在 Gateway 内；跨账户或产品级额度由独立服务定期分配给各 Gateway，Gateway 在本地扣减 | 逐单路径没有网络调用；满足将来的多账户合计 | 需要设计额度分配和回收协议；不在迭代 63 范围 | 远期选项 |

### 1.6 建议与配套条件

建议选 **a**。配套条件如下：

- **钩子只在 Gateway 实现。** S-09 之后不再需要“direct + risk”，链路分析 C-1 中协调器钩子的 direct 部分可以撤回。中立的钩子协议仍放在 `bt_api_base`，由 Gateway 交易 owner 调用。
- **选中而不可用即拒。** 拒绝开仓和平仓，放行撤单（S-05 a）。未选 risk 时，Gateway 进程不导入 `bt_api_risk`（C-7）。
- **先改 S-06。** 账户级 dispatch latch 不改，同一账户的开仓就是串行的：claim 时安装账户级冻结（`risk: core/admission.py:7346-7347`、`:7408`），只能由注入的日志权威解除（`bt_api_risk/README.md:52-64`）。
- **旧分析类不进入关键路径。** `risk: core/risk_manager.py:252` 默认 `approved: True`；`core/order_limits.py:30`、`:76` 内置缺省值 1 000 000 和每分钟 60 笔。
- **派发时相交判断要新写。** risk 现有的自成交互斥只看经 risk 的预留，不看价格和方向（`risk: core/admission.py:12750-12790`）。派发时的相交判断（C-5）按 S-02 b 归 risk 实现，由 Gateway 在派发锁内提供“其他策略活动单”的视图。
- **策略进程保留自查。** BT 预检和策略自己的止损继续做，只能更严，不作为账户风控。
- **空档提示。** risk 的单笔上限、价格带和计数实现之前，Gateway 部署在 ② 层只有授权、归属、流控和急停，其余靠 ③④ 层兜底。见 §4 S-13。

共同点：

1. “停止”默认撤销本策略的活动单、不平仓；平仓是另一个需要确认的动作。
2. 控制面（按钮或 API）与被控进程分离时，控制面负责鉴权、审计和编排，被控进程负责自己的优雅停止。
3. 都区分“停止策略”与“停止下单”，例如 NautilusTrader 的 HALTED、CME 的 kill switch。

### 2.3 三件事要分开

| 事项 | 含义 | 状态归谁 | 建议归属 |
| --- | --- | --- | --- |
| 策略生命周期 | 启动、停止、重启一个策略进程（一个策略目录就是一个实例） | 进程是否在运行：看 OS 进程和 `state/run.lock`；停止过程：由 BT 自己执行 | 执行者是 `bt_api_runtime` 的进程监督；停止语义由 BT 执行（迭代 62：只撤本策略活动单） |
| 运维控制面与按钮 | 鉴权、确认、审计、展示状态，把命令送到执行者 | 命令台账 | 先在 runtime 提供本机运维入口（CLI，加一个只在本机可达的接口，可复用 SDK `ServiceHost`/CURVE 或 Unix 域套接字）。任何界面（网页、桌面、将来的 ai-for-investor）都只是这个入口的客户端。Gateway 部署且选了 monitor 时，monitor 控制台可以作为另一个前端，复用它的 HMAC 校验和持久台账，命令仍转给 runtime 或 Gateway 执行 |
| 下单流控制 | 暂停或恢复下单、急停、排空 | Gateway 交易 owner（§3） | Gateway。“暂停/恢复”按钮应映射为策略范围的 STOP_NEW 或 FREEZE 与 RESUME，它们不是生命周期动作 |

为什么不放 Gateway：

- Gateway 持有 CTP 凭据（迭代计划 §3.13），再让它拉起任意策略进程会扩大攻击面；
- Gateway 宕机时（D63-03）仍然要能停止策略进程；
- Gateway 是账户级进程，策略进程的生命周期不是账户状态。

但 Gateway 必须提供“策略范围停写/排空”，作为进程停不下来时的兜底（§2.4 第 4 条）。

为什么不只放 monitor：

- 按 S-09/S-10，monitor 只在 Gateway 部署中存在，而且缺省不选，按钮不能依赖可选组件；
- monitor 现有的控制动作只有四种下单控制，没有启停进程，它也不执行命令（README）。

runtime 是否也受 S-09 约束：S-09 只点名 execution、risk、monitor。runtime 不在下单路径上，不增加组合复杂度，建议 direct 与 Gateway 两种模式都可用（§4 S-16）。

### 2.4 按钮如何安全地到达运行中的 BT 进程（建议）

1. **鉴权与授权。**
   - 运营 principal 与策略 principal 分开（迭代计划 §3.13）。
   - 运维界面以 application_client 身份接入。base 协议只定义了 strategy_client、application_client、service 三种角色（`bt_api_py/bt_api/bt_api_base/src/bt_api_base/service_protocol.py:53-58`）。
   - 按策略目录授权。危险动作（带 `--first-init` 启动、平仓）需要二次确认，参照 QuantConnect 的两次点击。
2. **先审计，后执行。**
   - 命令先持久记录：命令号、操作者、目标策略 UUID、动作、时间、原因。执行后再记录结果。
   - 结果是 BT 的停止报告（`STOPPED`、`STOPPED_WITH_WORKING_ORDERS` 或 `STOPPED_WITH_WRITE_IN_FLIGHT`，`BT: _btapi_direct_mode.py:3177-3188`），不是“按钮已点击”。
   - 可复用 monitor 台账的状态机：PENDING→CLAIMED→ACKNOWLEDGED/REJECTED/UNKNOWN（`mon: control.py:60-76`）。
3. **幂等。**
   - 命令号唯一：同号同内容返回原结果，同号不同内容拒绝。monitor 用 `ControlConflictError` 处理这一点，签发序号单调递增（`mon: control.py:489-493`）。
   - 停止天然幂等：`_direct_stop` 重入时返回原摘要（`:3136-3137`）。
   - 启动靠 `state/run.lock` 防止重复；Gateway 侧每个策略 principal 只允许一个活动租约。
4. **送达与升级（Gateway 模式）。**
   1. runtime 发 SIGTERM（前提是 BT 运行入口把 SIGTERM 映射为 `cerebro.runstop()`），或经本地控制通道请求优雅停止。
   2. BT 走 `_direct_stop`：停写，撤本策略活动单，在 `stop_cancel_timeout` 内等待，输出报告。
   3. 超时仍无报告：runtime 以运营身份请求 Gateway 对该策略施加 STOP_NEW，再施加 DRAIN。Gateway 用撤单保留容量按身份撤销该策略的活动单，这一步不需要策略进程配合。
   4. 再超时：先 SIGTERM，再 SIGKILL。
   5. 进程退出后，UNKNOWN 标记和 Gateway 日志都保留。重启时按迭代 62/63 的规则对账，对账通过前该策略写入关闭。策略范围的 DRAIN/FREEZE 原因保留，直到运营执行 RESUME。
5. **direct 模式。** 没有外部栅栏。进程无响应时只能 SIGKILL，活动单会留在场所；CTP 断线后是否撤单未知（UNKNOWN，迭代计划 §6.2 第 3 项）。重启后按 D62-16 接管，再撤单。所以 direct 模式更需要“SIGTERM → `runstop`”这一处小改动。
6. **启动按钮。**
   - 只做启动前检查：runtime 已有离线的 `validate`/`doctor`；Gateway 已就绪且该 principal 已登记（D63-13）；`run.lock` 空闲；不自动加 `--first-init`。
   - 检查通过后拉起 `run.py`。启动对账仍由 BT 完成，按钮不替 BT 做判断。

## 3. 问题三（S-04）：急停放在哪里

### 3.1 现状：同名不同义（STATIC）

| 位置 | 名称 | 实际效果 | 范围 | 撤单 | 持久化 | 依据 |
| --- | --- | --- | --- | --- | --- | --- |

结论：现有实现没有一处能直接用作 S-04 的急停。

- risk 冻结的效果相当于 STOP_NEW，范围只有账户，而且 risk 可以不选；
- ServiceRegistry 的 STOP_NEW 属于迭代 60 的托管服务路径；
- 写入准入会把撤单一起拦掉；
- monitor 只记录命令，不执行。

### 3.2 行业参照

- **NautilusTrader**（引用 [R1]）：交易状态放在出口处的 RiskEngine。HALTED 只放行撤单和查询，REDUCING 只放行减仓，分别对应用户定义的 FREEZE 和 STOP_NEW。开启 `bypass` 时不执行交易状态，同时关闭交易前检查和下单限速（引用 [R5]，检索摘要）。
- **CME Kill Switch**（引用 [R20]，检索摘要）：阻止新单并撤销活动单，接近 DRAIN；分三级独立执行，上级覆盖下级；在哪一级下达就在哪一级解除。
- **RTS 6 第 12 条**（引用 [R17]）：能紧急撤销任一或全部未执行订单，并能识别每笔订单对应的算法、交易员或客户。按范围排空的前提是订单归属可靠。
- **WonderTrader 离合器**（引用 [R10]）：策略或组合出风险时，直接断开信号执行。
- **注意名不副实的“kill switch”**：LEAN 的 Liquidate 是“平仓后停止”，Hummingbot 的 kill switch 是“亏损达到阈值后停止”（引用 [R15]、[R12]），都不同于 S-04 的“停新单/排空”。S-04 不含自动平仓，这与 D62-19 一致。

### 3.3 状态与执行放在派发点，命令可以来自多处

**状态与执行：Gateway 交易 owner。** 急停原因写在 Gateway 日志里，与预留、派发记录在同一个 SQLite 中，并检查两次：

- 预留时（`direct.reserve`）：命中即拒，结果为确定未发送；
- 派发锁内、写 DISPATCHING 之前：再查一次，处理“预留之后才下达急停”的情况。命中则释放预留，结果同样是确定未发送。

| 命令来源 | 怎样到达 Gateway | 可下达的动作 | 说明 |
| --- | --- | --- | --- |
| 运营界面（runtime 本机入口或 monitor 控制台） | Gateway 新增的运营端口，只接受运营 principal（迭代计划 §3.13） | 全部，含 RESUME | RESUME 必须指明原因号 |
| monitor 告警或规则 | monitor 台账 → 新的 SDK 执行者适配器（仿照 `MonitorRiskControlOwner`，以 Gateway 为执行者）→ Gateway 运营端口 | FREEZE、STOP_NEW、DRAIN | 阈值规则目前只观察（`mon: threshold_rules.py:1-20`），自动下达需另行授权 |
| `monitor_required` 下的心跳丢失（S-10） | 由 Gateway 自己判定：监视 monitor 的存活租约，不等 monitor 发命令 | STOP_NEW（账户） | 被监视的一方宕机时无法自报，所以判定必须在执行点；该租约机制现在不存在，需新做 |
| risk 越限 | risk 库在 Gateway 进程内，越限时登记一个原因 | STOP_NEW 或 FREEZE | risk 自身的冻结继续用于 risk 内部的拒单，但不作为急停状态 |
| runtime 停止无响应的进程 | 经运营端口（runtime 持有运营身份或得到委托） | 策略范围 STOP_NEW → DRAIN | 见 §2.4 |
| Gateway 自身的 fail-closed 阻断（回报中断、日切、会话断开、UNKNOWN） | 内部 | — | 这些是系统阻断，条件消除后自动解除（迭代计划 §3.7、§3.9），不是急停原因。两类状态分开存放，避免“恢复急停”误解除系统阻断 |

execution 子单（S-07）经 Gateway 下单，按来源策略匹配范围（链路分析 C-6 的 `origin` 字段），所以策略范围的急停同样拦住代该策略下的子单。execution 崩溃后冻结母单，属于 execution 自己的状态，不写进 Gateway 的急停。

### 3.4 语义与范围解析

- **原因记录**包括：`cause_id`；范围（`account`、`strategy:<UUID>` 或 `instrument:<合约>`）；模式；来源（运营、monitor 命令号、risk、runtime 或 Gateway）；理由；生效时间；DRAIN 进度；解除者与解除时间。
- **适用原因与有效模式。** 一笔新单（策略 s、合约 i、开或平）适用的原因 = 账户级原因 ∪ 策略 s 的原因 ∪ 合约 i 的原因。有效模式取最严的一个：DRAIN ≈ FREEZE > STOP_NEW。DRAIN 撤完单后仍按 FREEZE 拒绝新单，直到 RESUME。
- **开仓**：命中任何一种模式都拒绝。
- **平仓**：FREEZE、DRAIN 下拒绝。STOP_NEW 下放行，但仍要通过本策略可平量和账户可平量检查（INV63-06）。开平以显式 offset（D62-26）和 Gateway 归属账本为准，不信任客户端自报；这与 risk“REDUCE 必须由 owner 推导”一致（`risk: core/admission.py:421-425`）。
- **撤单**：任何急停都不拦。但仍要核对归属（INV63-06），并沿用 R-3 的跨交易日拒撤规则（同类规则见 `BT: _btapi_direct_mode.py:1750-1776`）。
- **RESUME**：一次只解除一个原因；同一范围内还有其他原因时继续生效。这对应 risk 的 `has_other_active_freezes`，也对应 monitor v2 RESUME 必须指明目标原因（`mon: control.py:245-246`）。在哪个范围下达，就在哪个范围解除（CME 做法）。
- **拒单码**带有效模式和原因号，例如 `kill_switch_freeze:<cause>`，归类为确定未发送。
- **“策略 × 合约”组合范围**：用户只列了三种范围，建议迭代 63 不增加（§4 S-22）。

**DRAIN 的执行步骤：**

1. 在同一事务里登记原因，然后才返回“已受理”。
2. 按 Gateway 归属账本列出范围内的活动单：包括已发送和部分成交的单；DISPATCHING 和 UNKNOWN 的单视为可能仍在场所。
3. 对每笔单按原身份发一次撤单（会话三元组，或 ExchangeID + OrderSysID，`ctp: direct_write_provider.py:982-1043`），使用撤单保留容量；配额不够就排队，不丢弃。
4. 撤单结果不明时不盲目重发；查询确认仍是活动单后，才再发撤单。
5. 结果：全部终结记为 APPLIED；仍有未终结或 UNKNOWN 的单，报告“部分完成”并附清单。monitor 的执行结果只有 APPLIED、REJECTED、UNKNOWN 三种（`mon: control.py:71-76`）。“部分完成”可以记为 UNKNOWN 并在 `effect_result` 中给出明细，也可以扩展结果类型（§4 S-24）。

### 3.5 持久化与重启

- **Gateway 重启。** 原因保存在 Gateway 日志中，交易 owner 宣布就绪前先加载；进行中的 DRAIN 继续执行（重新列出仍活动的单）。日志不可读时不就绪（迭代计划 §3.12），也就是全部写入关闭。
- **急停库写入失败。** 命令结果记为 UNKNOWN 或拒绝，Gateway 对该账户按 FREEZE 处理（fail-closed）。
- **策略重启。** 策略范围的原因按策略 UUID 记录，不按 run 号，所以策略重启后仍然有效。BT 启动后从 `direct.session_status` 读到急停状态，写进对账报告，预检据此早拒；但急停不阻止 BT 启动、对账和撤单。
- **monitor 重启。** 台账持久；处于 CLAIMED 或 UNKNOWN 的命令由原执行者恢复（`mon: control.py:545-566`）。
- **runtime 重启。** runtime 不保存急停状态，不受影响。

### 3.6 与迭代 62 fail-closed 规则的关系

- **急停只加阻断，不解除任何阻断。** RESUME 不解除 UNKNOWN，也不解除回报中断和日切阻断；这与 D62-29“结算确认不解除 UNKNOWN”同理。
- **UNKNOWN 照旧处理。** UNKNOWN 继续阻断相关写入，只按原身份查询，不换身份重发（INV62-05，`迭代62-问题修复/迭代计划.md:104`）。DRAIN 对 UNKNOWN 的单发撤单不算重发订单；但撤单本身的结果不明时，同样不盲目重试。
- **计数与撤单。** 撤单永远放行，S-11 的计数阈值只拦新单、不拦撤单。一次大范围 DRAIN 可能让撤单数接近交易所的异常交易标准；安全优先，这个代价可以接受，但要告警。
- **撤单保留容量。** 现有配额已允许撤单、平仓、对账使用保留份额（`gw: quota_admission.py:41`、`:232`）。急停期间普通开仓本来就被拒，保留份额足够撤单优先使用。
- **Gateway 单点。** Gateway 宕机时，急停和撤单都不可用。应急只能经期货公司柜台或其他终端处理，这属于运维规程，不是代码。

### 3.7 direct 模式（无 Gateway）

按 S-09，不为 direct 设计 risk/monitor，也不新增急停状态。现有手段：

| 手段 | 作用 | 局限 |
| --- | --- | --- |
| SDK 写入准入 | 部署时按 route 开启 | 运行中不能切换；关闭会连撤单一起拒绝（§3.1），所以它是能力开关，不是急停 |
| 策略自身停止 | `runstop` → `_direct_stop`：停写，只撤本策略活动单，不平仓 | 需要进程能响应 |
| BT 内部自动阻断 | 结算未确认、日切、核对不一致、UNKNOWN 时 fail-closed | 运营不能手动下达 |
| 操作系统终止 | SIGKILL 一定能停下进程 | 活动单留在场所 |

direct 是单策略独占账户（D62-05），“停止策略”就是该账户的“停写 + 撤单”。建议只做一处小改动：在 BT 运行入口（示例 `run.py` 或 runtime）把 SIGTERM 映射为 `cerebro.runstop()`，让外部停止走优雅路径（§4 S-23）。不增加 STOP_NEW/FREEZE 状态。

### 3.8 各包分工

| 包 | 在急停中的职责 | 不负责 |
| --- | --- | --- |
| bt_api_base | 中立类型：动作、范围、原因号、拒单码、命令结果（含“部分完成”） | 状态与执行 |
| bt_api_gateway | 原因状态机；与预留、派发同库的持久化；两处检查；DRAIN 执行；撤单保留容量；运营端口；`monitor_required` 的存活判定；状态查询 | 判断该不该急停（这是策略逻辑和风控政策的事） |
| bt_api_py | Gateway 组合：运营 principal、端口注册；`MonitorGatewayControlOwner` 适配器；远端 provider 把急停拒单码映射为确定未发送 | 持有状态 |
| bt_api_monitor | 命令入口、HMAC 校验、台账、告警规则，可选的控制台 | 执行命令；也不成为交易前置（S-10 的 `monitor_required` 由 Gateway 执行） |
| bt_api_risk | 越限时登记原因；自身冻结只用于 risk 拒单 | 急停状态的权威 |
| bt_api_runtime | 停止无响应进程时请求策略范围的 STOP_NEW/DRAIN；提供运营本机入口 | 急停状态 |
| backtrader | 把急停状态投影到预检和报告，用于早拒；本地 fail-closed 阻断照旧 | 急停的权威 |

## 5. 风险与未知

| 项 | 说明 | 状态 |
| --- | --- | --- |
| Gateway 单点 | Gateway 宕机时急停和撤单都不可用 | 设计约束；需要运维规程（期货公司柜台、其他终端） |
| risk 进程内时延 | 每笔派发锁内多一次 SQLite 事务，吞吐量未知 | UNKNOWN；在 63.03 或 R 阶段实测 |
| 账户级 latch | 原样接入会让同账户全部开仓串行 | 已证实（STATIC）；S-06 |
| 同名不同义 | 见 §3.1 | 已证实（STATIC）；S-24 |
| 链路分析 §4.1 需更正 | risk 有粗粒度的自成交互斥 | 已证实（STATIC）；不改变 C-5 |
| monitor 不能执行 DRAIN | 现有执行者直接拒绝 | 已证实（STATIC）；S-20 |
| runtime 没有进程监督 | 启停要新做进程监督、鉴权和审计 | 已证实（STATIC）；S-14、S-15 |
| SIGTERM 不走优雅停止 | 示例未处理 SIGTERM（Python 默认行为见 [R25]） | 已证实（STATIC）；S-23 |
| 断线后活动单是否保留 | 进程被杀或 Gateway 宕机后，CTP 是否撤单 | UNKNOWN（迭代计划 §6.2 第 3 项） |
| 交易所阈值 | 文中数字来自 2020 年期货公司手册；2026-10 的修订尚在征求意见 | UNKNOWN；以交易所现行规则和期货公司通知为准 |
| 柜台流控与会话上限 | 由经纪商配置，数值未知 | UNKNOWN |
| 程序化交易规定第十四条 | 交易者系统须具备异常监测、阈值管理、错误防范、应急处置；本设计是否满足报备要求 | UNKNOWN；随 S-12 向期货公司确认 |
| DRAIN 与撤单计数 | 大范围排空可能触发交易所的频繁报撤单统计 | 设计取舍；需告警 |
| `monitor_required` 的存活判定 | 现在没有 monitor 向 Gateway 续期的心跳租约 | 新工作；S-10 |
| 引用受限 | FIA 2024 原文未能读取；CME、RpcService 的风控部分、NautilusTrader Controller 只见检索摘要；RTS 6 条文取自英国保留版本页面，欧盟原文未直接核对 | 结论只依赖已读到的部分 |
