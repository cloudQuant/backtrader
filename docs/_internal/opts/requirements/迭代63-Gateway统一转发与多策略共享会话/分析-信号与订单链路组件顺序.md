## 0. 结论速览

**先纠正一个前提。** 这四个组件里，真正把订单送到交易所的只有一个“派发点”：direct 模式下是 SDK 的 `DirectWriteCoordinator`（经 provider），Gateway 模式下是 Gateway 的交易 owner。

- `bt_api_execution` 把母单拆成子单，再把子单交给派发点，自己不碰交易所会话；
- `bt_api_risk` 只做批准、拒绝、预留和冻结，从不发单；
- `bt_api_monitor` 只观察和告警，最多发出控制命令，由派发点执行。

所以问题的核心是：谁在关键路径上，以什么顺序；谁是旁路。

```text
同步关键路径（自上而下；任一层拒绝都是“确定未发送”，结果不明则记为 UNKNOWN，不重试）
① 策略：信号 → 订单意图（合约、方向、显式开平、数量、价格）
② BT Broker 本地预检（框架层，非权威，只用于尽早拒绝）
③ [可选] execution：母单受理 ──→ [可选] risk 母单级预留（整笔敞口、策略额度）
          └→ 算法切片：子单（每个子单都按普通订单走 ④，并带母单号和代理身份）
④ 唯一派发点（direct：SDK 协调器；Gateway：每账户一个交易 owner）
   a 写入准入、急停/冻结   b 会话、结算、日切   c principal 授权、合约白名单、单笔上限
   d 本策略/账户可平容量、跨策略自成交   e 场所静态规则（由 provider 声明）
   f 会话流控、撤单计数   g [可选] risk 逐单 claim
   h 耐久派发记录 → 一次性 grant → 原生调用
⑤ provider（CTP 字段、OrderRef）→ CTP 柜台（资金、保证金、限仓）→ 交易所

回流（同步写账本，异步通知）：成交 → ④ 的归属账本（Gateway 模式下是权威）→ risk 敞口 / BT 投影
旁路（不阻塞）：③④⑤ 的订单、成交、拒单原因、风控决定、会话与行情健康、流控计数 ──→ monitor
控制（在路径上，但由 ④ 自己执行）：monitor 或运营 → 控制命令 → ④ 执行 FREEZE / STOP_NEW / DRAIN / RESUME
```

要点：

1. **risk 检查两次。** 逻辑上，一次在 execution 切片之前（母单，按整笔），一次在派发之前（逐单，按账户）。物理上，risk 以库的形式在 execution 或派发点**进程内**同步调用，并与派发持同一把锁，不单独占一跳。现有代码也是这样接的（§4.2）。
2. **execution 在派发点之前，不另开会话。** 有 Gateway 时，子单和普通策略订单走同一个 Gateway 出口，受同样的账户级检查和流控。
3. **monitor 永远是旁路**，挂掉不影响下单。**急停在路径上**，但急停状态归派发点持有；monitor 只是可以发命令的来源之一。
4. **迭代 63** 先做 Gateway 基础转发，加上“共享会话本身就需要”的基础控制：急停、授权、归属容量、自成交、流控、撤单计数。risk 和 execution 只留接口，被选中而不可用时一律拒绝。monitor 可选。业务风控政策和执行算法放到后续阶段（§6）。

## 1. 行业通行分层与本项目的对应

### 1.1 分层与原则

行业没有唯一标准。下表参照 [FIA 自动交易风控白皮书](https://www.fia.org/sites/default/files/2024-07/FIA_WP_AUTOMATED%20TRADING%20RISK%20CONTROLS_FINAL_0.pdf)（`BT: docs/TRADING_SYSTEM_ARCHITECTURE.md:5` 已引用）、SEC Rule 15c3-5（Market Access Rule）、MiFID II RTS 6（Delegated Regulation (EU) 2017/589，第 12、15–17 条），以及 CME Globex 的 Kill Switch、Cancel on Disconnect、Self-Match Prevention 和消息限频工具。这些都是对照材料，不构成本项目的合规结论。

| 层 | 典型职责 | 本项目对应 |
| --- | --- | --- |
| 策略 | 信号、目标仓位、订单意图 | BT Strategy |
| 策略级交易前控制 | 本策略额度、可平量、合约白名单 | BT 预检（早拒）；Gateway 按 principal 强制 |
| 执行 / OMS / 算法 | 母子单、算法调度、成交回分配 | `bt_api_execution`（算法尚未实现，§4.1） |
| 账户/会话级交易前控制（最后一道） | 单笔上限、价格偏离带、资金/信用、重复单、限频、急停、自成交 | Gateway 交易 owner，可选 risk 钩子 |
| 网关 / 连接 | 会话、协议、流控、路由 | Gateway 内的 CTP provider 会话 |
| 场所 | 撮合；柜台检查资金、保证金和限仓 | CTP 柜台、交易所 |
| 实时监控 | 告警、急停入口、健康 | `bt_api_monitor` |
| 交易后 | 对账、持仓限额、独立回报副本 | Gateway 账户合计对账、BT 审计、risk 敞口 |

由此得到五条原则，后文都以它们为据：

- **P1 最后一道检查位于唯一出口，且不可绕过。** 15c3-5 要求市场接入风控由接入方“直接且排他地控制”。共享账户的唯一出口就是 Gateway，所以账户级检查必须放在 Gateway，不能放在策略进程。
- **P2 检查紧挨发送，同进程，同锁。** 先检查再发送之间如果有间隔，状态可能已经变化（TOCTOU）。`DurableRiskGate` 自己的注释也指出，单纯 `validate_permit` 挡不住两个进程并发，必须在同一事务里 `claim_for_dispatch`（`risk: core/admission.py:7270-7288`）。
- **P3 依次做无状态拒绝、预留、耐久记录、claim 并发送。** 前面任何一步拒绝都是确定未发送；预留在后续拒绝时释放；耐久记录之后结果不明就是 UNKNOWN。
- **P4 监控是旁路，控制在路径上。** 监控事件不是订单或账户事实的权威（`bt_api_monitor/README.md:10-15`）；急停必须由派发点执行，才不可绕过。
- **P5 额度由账户 owner（运营）配置，不由策略自报。** 策略配置不能放宽账户级限额；策略进程只能比账户更严格。

### 1.2 risk 看信号还是看订单

**看订单意图，不看信号。** 风控需要知道效果（开或平、方向、数量、价格），才能算出敞口和可平量；信号（指标值、因子分数）本身没有敞口。

BT 实盘边界的输出本来就是 BT `Order`，带合约、方向、显式 `offset`、数量和价格。所谓“信号日志”是对 buy/sell 调用的记录，属于信息：`Strategy._notify_signal_to_observers`（`BT: backtrader/strategy.py:542`），TradeLogger `log_signal`（`BT: backtrader/observers/trade_logger.py:2482`）。

risk 的中立意图类型也是效果语义：`IntentAction` = INCREASE / REDUCE / CANCEL / UNKNOWN_EFFECT（`risk: core/admission.py:99-105`）。它的注释明确说，REDUCE 必须由账户 owner 推导，不信任客户端的 reduce-only 声明（`:421-425`）。因此开平效果由派发点根据归属账本判定，不是策略说了算（与计划 INV63-06 一致）。

信号可以送给 monitor 或 TradeLogger 作审计和复盘，但不进入风控判定。目标仓位类输入（因子策略）先在 BT 里换算成订单，再送出；只有将来 execution 做跨策略聚合时，才需要接收目标仓位意图（§6.2）。

### 1.3 母单与子单：两级都要检查

| 层级 | 检查 | 目的 |
| --- | --- | --- |
| 母单（execution 受理时） | 策略授权、整笔敞口与额度预留、本策略可平量（按整笔）、价格带 | 防止“化整为零”：每个子单都过，合计却超限；也避免执行到一半被拒，留下半成品仓位或腿风险 |
| 子单 / 逐单（派发前） | 急停、会话、单笔上限、场所规则、账户级可平、自成交、限频、risk claim | 防止算法缺陷导致子单失控；账户状态（其他策略的活动单、流控、急停）只有在派发那一刻才确定 |

没有 execution 时，一笔策略订单既是母单也是子单：在 Gateway 的预留步骤做一次 risk 预留，在派发步骤做一次 claim（§6.3 C-1）。

现有 risk 只有“单意图预留/claim”和多腿 group vector（`risk: core/admission.py:4734`、`5648`、`6230`），**没有“母单整笔预留、子单从中分摊 claim”的合同**。这是后续 execution 接入时的缺口。

### 1.4 中国期货的特殊约束

- **程序化交易报告。** 证监会 2025 年发布的期货市场程序化交易管理规定（试行）及各交易所实施细则，对报告和异常交易监控有要求。本文未逐条核对原文，具体义务和阈值以期货公司通知为准（UNKNOWN）。
- **穿透式监管。** CTP 用 AppID/AuthCode 认证终端（示例模板 `ctp.app_id/auth_code`，`BT: examples/live/007_ctp/tickbroker_single_symbol_direct/config.yaml:16-17`）。Gateway 模式下，柜台看到的终端只有 Gateway 一个。多个策略共用一个认证终端是否满足报备要求，需要期货公司确认（UNKNOWN，见 §6.4 S-12）。
- **自成交与报撤单。** 异常交易按客户（以及实际控制关系账户）计算，同一账户两个策略反向成交就是自成交。交易所撮合是否替客户拦截，本仓库没有证据，按“不会拦截”保守设计。只有 Gateway 能看到全部策略的活动单，所以跨策略自成交检查只能放在 Gateway（与计划 D63-11 a 一致；补充见 §6.3 C-5）。报单、撤单次数也只有 Gateway 能完整计数。
- **会话流控。** CTP 对每个会话的报单和查询有流控，阈值由经纪商设定（UNKNOWN，计划 §6.2 第 4 项）。原生请求返回非零时，provider 记为确定未发送 `ctp_native_insert_returned_nonzero`（`ctp: direct_write_provider.py:973-980`）。共享会话之后，N 个策略共用同一份流控配额，需要按策略分份额，并给撤单和平仓预留容量（`gw: quota_admission.py:10-14` 已有保留容量的设计）。
- **资金、保证金、限仓。** 按 CTP 的一般行为，柜台在报单时检查，不足即拒单（本仓库未逐项实测）。所以基础层不做可负担性预检不会造成透支（D62-23），代价是浪费配额并留下拒单记录。可负担性预检属于可选 risk。
- **今昨仓。** SHFE/INE 必须显式平今或平昨，按策略精确记账（计划 §3.11 已覆盖）。

## 2. 两两之间为什么是这个顺序，反过来会怎样

| 顺序 | 理由 | 反过来或缺失时的后果 |
| --- | --- | --- |
| 策略 → risk（risk 看订单意图） | 有效果和数量才能计算敞口 | risk 看信号：算不出敞口，只能放行或误拒 |
| risk 母单预留 → execution 切片 | 整笔敞口一次占住；拒绝发生在任何子单发出之前 | 只查子单：合计超限，或执行到一半被拒，留下腿风险 |
| execution → Gateway | 子单仍经唯一出口，受账户级检查、流控和自成交约束（P1） | execution 自连 provider：每账户出现第二个 TD 会话，违反 INV63-02，并绕过账户级检查 |
| Gateway 账户级检查 → risk 逐单 claim → 发送 | 先做便宜、确定的拒绝（急停、授权、会话），再做有状态的预留和 claim，最后紧挨发送（P2、P3） | claim 过早：持有 latch 的时间变长；claim 在发送之后：风控形同事后记账 |
| 派发点持有急停状态 | 急停只有在出口执行才不可绕过（P4） | 急停只在 risk：没选 risk 的部署就没有急停。这正是现状：monitor 控制只对接 Risk gate，`SDK: service_monitor_control.py:61` |
| monitor 作旁路 | monitor 不是权威，故障时不应停止交易 | monitor 放进路径：monitor 宕机或变慢会让整个账户停摆，监控结论还可能被当成授权 |
| 成交回流 → 账本 → risk / BT | 下一次预检依据的是已验证成交，而不是估计 | 不回流：风控敞口靠估计，账本漂移，可平量错误 |
| BT 预检在 Gateway 之前（重复检查） | 尽早拒绝，节省往返 | 只靠 BT：策略缺陷或越权无人兜底；只靠 Gateway：可以接受，但无效请求会占用配额 |

## 3. 状态归属与崩溃处理

### 3.1 谁对什么权威

| 状态 | 权威所在 | 其他组件的角色 |
| --- | --- | --- |
| 订单、成交、持仓、资金的场所事实 | CTP 柜台、交易所（经 provider 观察） | 其余各层都是投影；没有结果不等于零或失败 |
| 策略身份 UUID、局部序号、策略侧未决标记、待发单 | BT `live_state`（`BT: backtrader/live_state/pending.py:1-30`） | Gateway 按 UUID 授权；标记只证明“本策略打算或曾经发出” |
| 预留、派发记录、OrderRef 分配、身份路由、每策略归属账本、账户合计对账、结算确认记录 | Gateway 日志（迭代 63 新建，INV63-04） | BT 快照是可重建的投影；risk 从这里取持仓和成交事实 |
| 风控许可、预留占用、风控冻结 | `bt_api_risk` 的 SQLite（`risk: core/admission.py:2662`） | 由派发点调用；它不自行取得或核实账户事实（`bt_api_risk/README.md:18`） |
| 母单、子单计划、算法进度、成交到母单的分配 | `bt_api_execution` 日志（选用时） | 成交归属到哪个策略仍以 Gateway 为准 |
| 急停状态（当前是否冻结） | 派发点（Gateway 或 SDK 协调器） | monitor 或运营的命令只证明“命令已发出”（`mon: control.py:51-57`；`bt_api_monitor/README.md:12-14`） |
| 遥测、告警、事件副本 | `bt_api_monitor` | 不作为任何交易判定的依据 |

### 3.2 各组件崩溃时（与迭代 62 的 fail-closed 一致：UNKNOWN 阻断相关写入，不盲目重试）

| 崩溃对象 | 立即影响 | 恢复规则 | 写入 |
| --- | --- | --- | --- |
| 策略进程 | Gateway 照常管理该策略的活动单；未派发的预留到期，按确定未发送处理 | 按预留号或原生身份查询命令状态；从上次 ACK 重放回报（计划 §3.6、§3.12） | 本策略对账通过前关闭；其他策略不受影响 |
| execution 进程（后续） | 母单暂停；已经交给 Gateway 的子单照常管理和回报 | 读自身日志和 Gateway 命令状态；有 UNKNOWN 子单的母单不再切片，也不补发 | 该母单关闭；是否自动撤销其活动子单见 S-07 |
| risk 作为 Gateway 内的库 | 随 Gateway 一起崩溃 | 许可按 TTL 过期；有 claim 而无 DISPATCHING 记录，可证明未发送（前提是 DISPATCHING 先于发送，§6.3 C-1）；有 DISPATCHING 的按 UNKNOWN 处理 | 同 Gateway |
| risk 库或数据库不可用（Gateway 存活） | 选中而不可用 | 拒绝开仓和平仓，放行撤单（S-05）；不静默绕过（D62-23） | 部分关闭 |
| Gateway | 所有策略都不能写，也不能撤单 | 按计划 §3.12：DISPATCHING 按原身份查询解决；用当日完整成交补齐账本；账户合计对账后再宣布就绪 | 全部关闭，不回退直连（INV63-05） |
| monitor | 交易不受影响，告警缺失或延迟 | 持久事件从游标重放；尽力而为的遥测丢失并计数（`bt_api_monitor/README.md:143-152`） | 默认不受影响（S-10） |
| BT 投影与 Gateway 账本不一致 | — | 以 Gateway 为准，阻断本策略该合约并报告 | 本策略该合约关闭 |

各存储之间没有原子性（risk、Gateway 日志、`live_state` 是三个 SQLite 或文件存储）。安全依赖一条次序规则：**原生调用只发生在所有相关耐久记录之后。** 恢复时按身份查询解决，不按时间推测。

## 4. 现状盘点（STATIC）

### 4.1 四个组件现在是什么

### 4.2 SDK 接线现状：risk 是在 execution 之前、在 Gateway 处，还是都不是？

- **direct（迭代 62）：没有 risk，也没有 monitor 钩子。** `DirectWriteCoordinator.place` 的顺序是：准入 → provider 预留 → 宿主耐久提交 → 复核会话代际 → 一次性 grant → 发送（`SDK: direct_write.py:207-276`；`BtApi.make_order` 的 direct 分支 `SDK: bt_api.py:10434-10449`）。没有可插入 risk 的位置，所以“direct + risk”在迭代 62 的路径上目前做不到。
- **托管（迭代 60）：risk 在 dispatch owner 进程内被调用，不在 Gateway。**
  - 服务组件 `risk/account_owner` 构造 `RiskOrderEntryService`，经 `BtApi.make_order` 派发（`SDK: service_components.py:2330`；`service_risk_order_entry.py:1-7`、`741`、`3102`）。
  - `execution/account_owner` 构造 `ExecutionOrderEntryService`；order_gate、cancel_gate、basic gate 都没有时拒绝构造（`service_components.py:2878-2920`）。
  - 两者都通过 `provider_session_ref` 引用 Gateway `account_session_worker` 的会话（`service_components.py:1364-1376`；`service_config.py:1224-1263`）。
  - 在这条路径上，Gateway 只提供会话和读模型，不做风控；Gateway 路由器虽然有准入回调接口，但没有 risk 实现（`bt_api_gateway/README.md:11-18`）。
- **62.08 托管 CTP：** 在 Gateway 主机组合 execution 的 basic admission 与 risk gate，单合约，因 6 项缺口不可用（`SDK: ctp_gateway_execution.py:1-24`；计划 §7）。
- **monitor：** 执行日志中继是可选的，只在 owner 线程 `poll` 时运行，不在下单路径上（`SDK: service_execution_monitor.py:1-12`）。这个模式适合复用给 Gateway 日志。

### 4.3 BT 订单路径现状

- **Store 选择。** 写入准入开启且没有 execution 配置时进入 direct 模式（`BT: backtrader/stores/btapistore.py:398-418`）。旧的 `backend=gateway/forwarding`、`provider=gateway` 写法被显式拒绝（`:217-237`），迭代 63 的选择键不能复用这些名字。
- **BT 预检**（`BT: backtrader/brokers/_btapi_direct_mode.py:1464-1523`）：停止中、准入、日切、全局阻断或 UNKNOWN 阻断、交易权限否定、订单类型、数量、限价大于 0、有效期、显式开平、持仓侧、可平量。之后 `_direct_route` 判断行情资格和交易时段（`:1525-1551`）。
  - 没有：单笔上限、价格偏离带、限频、自成交（direct 是单策略独占账户，D62-05，后两项原本也不需要）。
- **BT 不直接导入这四个包。** 对 `backtrader/` 检索 `bt_api_risk|bt_api_execution|bt_api_gateway|bt_api_monitor` 没有结果，选择全部经 SDK，符合职责规范。BT 与 monitor 也没有任何接线；`notifications/` 是尽力而为、不持久化的消息推送（`BT: backtrader/notifications/__init__.py:21-29`），不能当监控使用。

### 5.3 BT 如何经配置选择（草图；名称在 63.01 冻结）

原则：

- 策略的 `config.yaml` 只声明接入方式、对组件的要求和本策略的连接材料；
- 账户级限额、principal 和组件实例在 Gateway 的账户配置中，由运营维护（P5）；
- 两边都不写凭据值，凭据只经环境变量进入 Gateway 进程（INV63-01）；
- 尖括号表示必须由运营按经纪商要求填写的值，不提供缺省值。

```yaml
# 策略目录 config.yaml（Gateway 模式草图）
access: gateway            # direct（迭代 62，缺省）| gateway；不可用时 fail-closed，不自动回退
direct:
  write_admission: true    # 策略侧 SDK 准入；两种接入都需要
  market_clock_verification: true
gateway:                   # 仅 access: gateway 时读取；出现 ctp 凭据键即拒绝
  connection_file: state/gateway_connection.json   # 运营工具生成：地址与服务端公钥
  client_key_file: state/gateway_client.key        # 0600；不经 argv 或日志
components:                # 不写即不启用、不导入
  risk: {require: false}       # true：Gateway 报告 risk 未生效时，本策略不写
  execution: {enabled: false}  # true 而包或服务不可用：启动失败，不当普通单发送
  monitor: {enabled: false, heartbeat_seconds: 10}
```

```yaml
# 账户级 Gateway 配置（运营；对应计划 D63-08 a 的账户文件夹）
route: CTP___FUTURE
write_admission: true
principals:                       # 静态登记（D63-13 a）
  - strategy_uuid: <策略目录 state/identity.json 中的 UUID>
    public_key_file: keys/<名称>.pub
    commands: [read, submit, cancel]
    instruments: [rb2701]
    max_order_qty: {rb2701: <运营填写>}   # 缺失时该 principal 不可写（S-03）
controls:
  operator_principal: ops
  rate: {orders_per_second: <经纪商确认>, reserved_for_cancel_close: <运营填写>}
  cancel_count: {warn: <运营填写>, block: <运营填写>}    # 按账户、合约、交易日（S-11）
```

direct 模式下，`components.risk.enabled: true` 表示在策略进程内启用 risk（单策略即账户 owner），政策文件也写在策略目录。这需要先完成 C-1 的协调器钩子。

### 5.4 可选组件规则（迭代 62 `修复相应的问题.md:13`、62-R3）

1. **未选择：** 不导入、不启动、不要求，与迭代 62 计划 :584 的验收行一致。Gateway 基础转发的进程也不得导入 `bt_api_execution` 或 `bt_api_risk`。现有托管组合会强制导入它们（`SDK: ctp_gateway_execution.py:275-387`），所以不能把它当作转发路径（C-7）。

3. **BT 只经 SDK 选择组件，** 不直接导入这些包（现状已满足，§4.3）。
4. **策略侧配置只能比账户侧更严格，** 不能放宽或关闭账户级控制。
5. **execution 不是硬依赖。** 没有 execution 时，带算法指令的订单以 `execution_component_not_selected` 拒绝，不降级为普通单（S-08）。

## 6. 建议与分阶段路径

### 6.1 迭代 63 内做（Gateway 基础转发）

- 计划现有的 63.01–63.10 不变（两阶段派发、归属账本、回报路由、查询调度、结算、日切）。
- 在 Gateway 交易 owner 内置**共享会话必需的基础控制**。这些不属于 `bt_api_risk` 的业务政策，原因是共享会话把单个策略的失误放大到整个账户：
  - 急停（S-04）；
  - principal 授权与合约白名单；
  - 单笔数量上限（S-03）；
  - 本策略与账户可平容量；
  - 跨策略自成交（C-5）；
  - 会话流控与按策略份额；
  - 撤单和报单计数（S-11）。
- 场所静态规则（价位、数量步长、单笔最大量、涨跌停）由 provider 声明检查函数，Gateway 调用（职责规范：场所事实归 provider）。CTP direct provider 现在不做这些检查（`ctp: direct_write_provider.py:857-980`），超出时由柜台拒单，代价是浪费配额。这一项优先级较低，可后移。
- 定义中立 risk 钩子并固定调用点（C-1），实现“选中而不可用即拒”；不实现政策。
- 在线协议预留代理身份和母单字段（C-6）。
- monitor 仍不是前置；Gateway 状态查询按计划 §3.14 做。

### 6.3 对迭代 63 计划的修改建议（需用户同意后由主会话写入计划修改记录）

- **C-1（§3.5、§3.6、§3.15、63.02）：** risk 钩子以中立协议定义在 `bt_api_base`，让 SDK 协调器（direct + risk）和 Gateway 交易 owner 共用一份合同。调用点固定如下：
  - 预留时 `reserve`：拒绝即确定未发送；许可号记入 RESERVED。
  - 派发锁内依次为：risk `claim` → 写 DISPATCHING → grant → 原生调用。这样，有 claim 而无 DISPATCHING 的记录可以证明未发送。
  - RESERVED 到期、确定未发送时，`release`。
  - 已发送时随成交 `settle`；UNKNOWN 时保留占用，直到解决。
  - 计划目前只写“可选 risk 钩子”，没有规定调用点和次序。
- **C-2（§3.5）：** 在 Gateway 派发前检查清单中补上单笔上限和场所静态规则（provider 声明），并写明检查次序：无状态拒绝 → 预留 → 耐久记录 → claim → 发送（P3）。
- **C-3（§3.5、63.03）：** 写明急停语义：
  - FREEZE：拒绝新预留，撤单照常放行；
  - STOP_NEW：只拒开仓；
  - DRAIN：拒绝新预留，并按身份撤销范围内的活动单；
  - RESUME：只允许运营 principal 执行。
  - 范围分账户、策略、合约三级；撤单使用配额中的保留容量。
  - 计划现在只说“可沿用路由器的 FREEZE/DRAIN/RESUME”。
- **C-4（§3.10）：** 撤单计数从“只记录并告警”改为“警告阈值告警，硬阈值阻断该合约的新报单”，阈值由运营填写，不给缺省值（S-11）。
- **C-5（D63-11）：** 自成交检查放在派发锁内，在派发时进行。比较对象是其他策略处于 RESERVED-已派发、DISPATCHING、在场所活动、UNKNOWN 状态的反向订单；UNKNOWN 按可能仍在活动处理；市价单视为与全部反向挂单相交。原因是：预留时检查有竞态（A 已预留未派发，B 来检查时看不到），而派发锁本来就串行化了同一会话的派发（§3.4）。处理方式是拒绝新来的一笔：撤销他人挂单违反 INV63-06。
- **C-6（63.01 冻结载荷）：** `direct.reserve` 的载荷预留两个字段：`origin`（principal 本身，或“execution 代理策略 X”）和 `parent_ref`（母单号）。迭代 63 只接受“本人”，其他值拒绝。这样 E 阶段不需要改线协议。Gateway 的 `WireIdentity` 已含 actor 与 delegation（`bt_api_gateway/README.md:102`）。
- **C-7（63.05 测试）：** 在“策略进程未加载 `bt_api_ctp.ctp.client`”的模块探测之外，再加一条：未选用时，Gateway 进程不加载 `bt_api_execution` 和 `bt_api_risk`。
- **C-8（§3.14）：** 写明 Gateway 日志是 monitor 的事件源（中继模式），monitor 缺失不影响交易；列出要中继的事件类型。
- **C-9（文档漂移）：** 计划写明的核对基线是 backtrader `8b87173d3`，但其中 `_btapi_direct_mode.py` 的行号与 `74c48c7e3` 一致。例如 `_direct_submit` 在 `8b87173d3` 位于 :1179，在 HEAD 位于 :1428；该文件在两次提交之间改动了 +479 行。63.01 重核时以 HEAD 为准，并更正基线说明。

| S-01 | Gateway 模式下 risk 运行在哪里 | a Gateway 进程内的库；b 独立 risk 服务，Gateway 同步 RPC；c 策略进程内 | a：与派发同锁（P2），不多一个故障点；c 违反 P1 |
| S-02 | Gateway 内置基础控制的范围 | a §6.1 全部内置；b 只做授权、归属和流控，其余交给 risk | a：不选 risk 的部署也需要这些控制（共享会话放大风险） |
| S-03 | 单笔上限和价格偏离带 | a 每个写 principal 必须配置单笔上限（无缺省，缺失不可写），价格带可选；b 都可选；c 都强制 | a；价格带需要行情参考价，参考价过期时拒绝，可能在快市中拒掉平仓，所以暂作可选 |
| S-04 | 急停语义与范围 | 按 C-3；撤单是否永远放行 | 按 C-3，撤单永远放行 |
| S-05 | risk 被选中但不可用 | a 拒开仓与平仓，放行撤单；b 全拒，包括撤单；c 只拒开仓 | a：符合 D62-23 的“不静默绕过”，同时保留撤单能力；c 等于平仓绕过 risk，需要用户明确授权 |
| S-06 | `DurableRiskGate` 的账户级 dispatch latch | a 接入 Gateway 前改为按（策略、合约）范围，或由 Gateway 日志权威在回报确认后自动解除；b 照原样使用（全账户开仓串行）；c 另写 Gateway 专用的轻量 risk | a；b 会重现计划 §1.4 第 3 项写者权威的串行问题 |
| S-07 | execution 的位置；崩溃时是否撤销其子单 | a 独立可选进程，作为 Gateway 代理 principal；b 内嵌在 Gateway 进程；c 嵌入策略进程。崩溃时：a1 只冻结母单；a2 租约到期后由 Gateway 撤销其活动子单 | a + a1：进程隔离，不扩大 Gateway 的故障面；a2 留作以后的可配置项 |
| S-08 | BT 对 execution 的接口 | a 仍用 `make_order`，加可选执行指令（算法名与参数）；b 新的母单 API | a：BT 改动最小，没有 execution 时按 §5.4 第 5 条拒绝 |
| S-09 | 是否支持 direct + execution | a 暂不支持，execution 只在 Gateway 后面；b 进程内组合，派发端口为协调器 | a：先把一条链做实 |
| S-10 | monitor 能否成为交易前置 | a 永远可选，缺失不影响交易；b 运营可声明 `monitor_required`：心跳中断时 Gateway 执行 STOP_NEW | 缺省 a，b 作为显式选项 |
| S-11 | 撤单和报单计数达到阈值后的行为 | a 警告加硬阈值阻断该合约新单；b 只告警（计划现状） | a，阈值由运营按期货公司要求填写 |
| S-12 | 程序化交易报告与穿透式信息 | 不是设计选项：需要用户向期货公司确认多策略共用一个 Gateway 认证终端的报备方式，以及适用的阈值 | 63.09 之前确认；确认前，SimNow 之外的账户不启用 Gateway 写入 |

## 7. 风险与未决问题

| 项 | 说明 | 状态 |
| --- | --- | --- |
| risk latch 串行 | 原样接入 `DurableRiskGate`：账户上任一开仓 claim 未解决，所有策略都不能再开仓（§4.1） | 已证实（STATIC）；S-06 |
| 母子分摊合同缺失 | risk 只有单意图和多腿 group，没有“母单预留、子单分摊” | 缺口；E 阶段 |
| 旧 risk 类放行 | `check_order_risk` 默认放行，`OrderLimits` 有内置缺省值；误接入就是 fail-open | 已证实（STATIC）；规定不进入关键路径 |
| 急停依赖 risk | 现有 monitor 控制只能冻结 Risk gate；不选 risk 的部署没有远程急停 | 已证实（STATIC）；C-3、M 阶段 |
| direct + risk 不可用 | 协调器没有钩子 | 已证实（STATIC）；C-1 |
| 自成交竞态 | 只在预留时检查会漏掉“已预留未派发”的对手单 | 设计风险；C-5 |
| Gateway 单点 | Gateway 宕机后不能撤单；会话断开后活动单是否保留在场所未知 | UNKNOWN（计划 §6.2 第 3 项） |
| 流控与监管阈值 | 经纪商流控、交易所自成交和报撤单阈值、程序化报告条款 | UNKNOWN（计划 §6.2 第 4、5 项；S-12） |
| 交易所是否拦截同客户对敲 | 本仓库无证据 | UNKNOWN；按不拦截设计 |
| 柜台资金和保证金检查 | 按 CTP 一般行为由柜台拒单，本仓库未逐项实测 | UNKNOWN；不影响基础层安全结论，只影响拒单可观察性 |
| 三个存储不原子 | risk、Gateway 日志、`live_state` | 设计约束；靠次序规则和按身份恢复（§3.2）；需故障注入测试 |
| 价格带依赖行情 | 参考价过期时只能拒绝，可能挡住平仓 | 设计取舍；S-03 |
| execution 成交归属 | 跨策略聚合（轧差）以后，成交先归入 execution 资金池再分配，会改变 INV63-04 的权威归属 | 未决；E 阶段之后，届时需新的用户决定 |
