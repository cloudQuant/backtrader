# 迭代 63 分轮合同冻结稿

日期：2026-11-08。状态：分段冻结、实现中，**不代表 63.01 或整期验收完成**。本文件将当前实施边界写到可检验的接口；未覆盖的总体合同仍见计划、设计和实施合同补充。

## 1. 第二轮原生派发组合

Gateway 的 `direct.reserve` 与 provider 的 `reserve_order` 是不同阶段。前者仅写账户、策略、认证 principal、request_key、摘要、预留 UUID、TTL、owner generation；它不调用 CTP，不分配 OrderRef。收到 `direct.dispatch` 后，Gateway 在唯一 owner 线程检查原记录、范围、期限、权限及门槛，再调用 SDK 已有 `DirectWriteCoordinator.place`。其中 provider.reserve_order 才分配原生身份；注入的 Gateway commit port 将该身份与强键写为 DISPATCHING，事务成功才返回原预留号作为 marker，SDK 随后复核会话、签发并消费一次性 grant、发送。

这一组合保留两阶段的耐久次序，复用已实现的 SDK 原生流程，不必为了远端 reserve 而提前拆开 provider 原生 reservation。原计划要求拆分 coordinator 的机械改造因此调整；远端策略 SDK 的 PREPARED 与延后 attach 原生身份仍须单独实现，不能用带 Gateway 标签的假 NativeOrderIdentity 填空。

内部 `GatewayDirectDispatcher` 绑定真实 LocalAccountSessionGuard、账户及同一 generation，所有操作在 guard owner 的进程和线程。已 DISPATCHING/SENT/NOT_SENT/UNKNOWN、RELEASED 或 EXPIRED 的同身份重放只读原记录；不再分配原生身份或发送。最终结果写入失败保留 DISPATCHING，后续只能查原记录。它尚不是完整交易 owner，不自动建立身份授权、会话就绪、结算、急停、账本或未知解决。

SDK 组合层显式绑定 expected_local_provider 对象与 coordinator route，按需加载 Gateway。该实例绑定不是原生来源证明；受信装配必须提供本地 native provider，不能接远端 Gateway provider 形成递归。Gateway 包不反向导入 SDK。

## 2. 订单载荷与请求绑定

首个派发切片只接受 SDK 现有 OrderRequest.to_dict 的完整规范标量映射。quantity/price 是规范十进制字符串，布尔与整数保持精确类型；不接受二进制浮点、遗漏字段后隐式补默认、额外字段或嵌套 instrument/ctp_order_identity。account_id 必须等于配置的 Gateway 账户 scope；运行时、执行周期、托管意图等 authority 标签不允许由该普通下单载荷提供。

SDK 通过统一 decode_gateway_order_request 校验 from_dict/to_dict 的完整规范往返。RPC reserve 与原生 dispatch 共用该校验；dispatch 从原持久载荷构造请求，并在耐久 commit 前再核对请求未变化。不能只比较独立的 request_summary，因为它不能证明实际请求的方向、数量、价格、开平或有效期。后续若支持嵌套中立合约或母单扩展，须升级明确 schema 和验收向量，不以任意 factory 绕过本合同。

SDK strong_identity_keys 复用选定 provider 的关联规则，仅输出 strong 键的排序、去重、ASCII 规范 JSON 字符串，每键最多 256 字符。拒绝错 route、缺失所需交易日、不可规范化键和无强键；不会注册身份、消费事件或签发 grant。强键投影不证明原生来源，CTP 仍由受信 provider 返回完整会话/交易日身份，弱日/ref 候选不能单独认领。

## 3. 首个 RPC 切片

端口 `service.direct_write`，显式 Gateway `trading_owner` 角色；本轮 capability 仅声明已实现的 `direct.reserve`、`direct.release`、`direct.command_status`。mount 为 broker.direct_write、application.direct_write、upstream.direct_write。该角色名不是已经具备完整交易 owner 的证明；未实现的 dispatch、cancel、结算与事实接口不发布。

reserve/release 是持久写操作，遵循 registry 的认证、scope、epoch、grant、撤权和活动 strategy run claim。reserve 遵循现有 STOP_NEW；release 和原记录查询保留。绑定从可信 ServiceCallContext 取得账户、策略、principal，wire 自报字段不能覆盖。此切片拒绝 SERVICE 代理，代理关系与观察流由 63.13 继续交付。

command_status 按账户＋策略＋principal 读取原请求，允许获权的新 run 恢复自己的历史记录，不以旧 run 作为读取前置。写入仍要求当前有效 run claim。订单 idempotency_key 必须等于外层 request_key。TTL 是首次创建选项，不参与订单 payload 摘要，同键重试不延长原窗口；成功回执提供 journal_id、记录 generation、是否当前代、相对剩余秒数与 expiry_pending。过期观察不写 EXPIRED，也不证明 NOT_SENT。

STOP_NEW 后默认包含 reserve 的完整注册仍被拒，SDK 提供 release＋command_status 的最小恢复注册配置；release 保留写 claim，不能把它降为只读来绕过授权。

成功业务结果为 status=OK；明确未执行本次操作的验证拒绝为 REQUEST_REJECTED＋有限码。这不是订单 Rejected 或原命令 NOT_SENT 证明。提交后不确定、损坏和无法分类的异常保留 HANDLER_FAILED/ServiceCallOutcomeUnknownError，禁止换 key 盲重发。

## 4. CTP flow 与结算

provider 客户端新增成对的 trusted_flow_root/flow_account_scope，根必须已存在且为绝对真实目录；账户路径用 scope SHA256 下分 td/md。构造时绑定目录身份，native factory 前再次验证；借用 Trader 必须匹配同一绑定。普通 direct 未配置时保留既有临时目录，一次性 MD 诊断保留自己的临时生命周期。Gateway 完整装配后必须强制配置，不允许验证失败后回退临时目录。

当前 POSIX 实现要求 0700，因此只覆盖同一 OS 用户。计划中的跨 OS 用户共根部署及 Windows ACL 验证仍为 GAP，不能把“同机锁根”误读为已支持任何用户组合。native API 最终只接受路径字符串，最后检查至 native 打开之间仍依赖受信权限；目录不是互斥或跨主机 fence。

D63-14 的每日自动确认由 Gateway 调度 SDK ensure_settlement：先读当日状态，仅明确 UNCONFIRMED 且账户写准入有效时写耐久标记并确认，UNKNOWN 先回读、不能无限重试。原生 auto_settlement_confirm 继续关闭。账户/交易日状态、重启、日切和确认故障的完整持久状态机尚未交付。

## 6. 默认传输与破坏式重构授权

D63-50冻结默认transport为bt_api_transport_zmq。SDK gateway extra默认包含该包，现有ZmqTransportFactory和ServiceHost继续经该包通信；原R02“ZMQ另选”的安装方案由此更新。未来其他中间件归新传输包；当前不新增backend。用户授权Gateway及ZMQ包必要破坏式调整，仍需维护同版接口、错误/UNKNOWN语义、主体范围、socket线程归属及独立进程验证。

## 7. R04 派发排队与授权复核合同

本节冻结 R04 的实施约束，测试和交付状态另见分轮记录。现有 ServiceHost 在 ZMQ owner 线程同步调用 handler，poll timeout 不限制 handler 耗时。派发 handler 不得等待原生调用完成：网络线程继续持有 socket，另一个账户 owner 线程创建并独占 dispatcher、guard 和原生资源。该线程不是策略调度器；Cerebro 的策略生命周期不变。

`direct.dispatch` 使用原 request_key、reservation_id、digest、expected_version。有界内存队列接纳后只报告排队状态，不能称为耐久派发成功。重复排队按完整身份核对；队列满、关闭、排队超时或回复丢失均不能证明原命令 NOT_SENT。客户端通过原键查询 journal；原生身份仅在 DISPATCHING 的耐久事务中建立，不用队列编号伪造。该路径不自动重发、不切回 direct。

Registry 为当前已认证的 direct.dispatch 签发绑定原注册、epoch、身份、作用域、操作和完整参数的进程内能力。能力可移交给单一账户 owner 线程，不能并发、重入或在任务结束后继续使用。初检与耐久派发前分别复核；固定锁序为 Registry → Gateway journal，短临界区中只做本地授权与持久状态变更，不执行 provider 或网络 I/O。取得 journal 写锁后须再次检查当前时间和租约，避免锁等待期间过期的请求取得 marker。此合同定义本地授权检查与状态转换的线性化边界，不把进程锁或已通过的检查当成跨主机 fencing，也不声称能撤回已到 provider 的请求。

Gateway 的 owner admission 只接受字面 True，漏写返回值、异常和其他值均拒绝。每请求 fence 单独传递，不能使用共享可变的“当前请求上下文”。只有明确接入 owner 队列且核对其 journal/账户/代际绑定的服务才发布 dispatch capability；纯 storage 服务继续只发布三项已实现操作。原有 registry STOP_NEW 是旧 run 写入栅栏，不等同于后续仅约束普通开仓的 Gateway 业务急停政策。

服务配置显式设置 `dispatch_enabled: true` 才计划发布第四项操作；默认 false 保留 storage 切片。配置开启而受信资源未提供匹配 owner 时启动失败，不在运行时补成伪能力。状态回执中的 native_identity 来自原耐久记录，解析身份字段后再次做有界与敏感字段校验；不硬编码交易所专有身份字段。strong_identity_key_digests 仅是强键摘要的一致性投影，不是原生查单键或权限、来源证明。

permit.close 是非阻塞的任务清理，阻止后续 scope 和重新校验，不撤回已经通过最后复核的本次短临界区提交。权限撤销、STOP_NEW 和 Registry 关闭仍通过 Registry 的锁串行化。固定 SQLite read snapshot 与进程锁仅保护遵循同一 Registry owner 的操作，不保护绕过锁直接修改数据库的外部写者。

owner 原生调用阻塞时，关闭等待有上限，但不能假定 native 已取消、释放账户锁或另起 owner。资源关闭始终在原 owner 线程；启动中途失败也须保留明确的清理句柄，未知清理状态不能报告关闭成功。停止接纳、丢弃未运行队列项与在途责任分别处理，原 journal 保留恢复依据。该切片不保证磁盘故障或不释放 Python GIL 的 native 阻塞下控制面的硬实时性；真实 native、进程隔离、完整 TD/MD 生命周期仍需后续验证。

本轮队列为有界 FIFO，不承诺策略间公平配额。排队期限只表示过期任务不得开始派发；无独立清扫线程，过期项在下一次出队或显式 close 时清理。状态查询仍同步访问 SQLite，锁等待或存储阻塞可影响网络线程；native 替身阻塞时仍可服务的证据不能推广为全链路无阻塞。最小 UNKNOWN 作用域阻断仍由后续 owner admission 与账本接线，队列 failure_category 本身不代替订单真值。

## 8. R05 策略侧逻辑预留与持久宿主端口

中立 `GatewayCommandBinding` 和 schema_version=1 的 `GatewayCommandRecord` 归 Base。成功回复显式携带 journal_id、账户、策略、principal，全部来自 Gateway 耐久记录；客户端必须与可信配置精确核对，不从首次回执自动接受新 journal。run_id 不在 Gateway 命令记录中，不伪装为耐久字段；它由客户端原意图和实际注册作用域绑定。

RESERVED 没有原生身份；DISPATCHING/SENT/NOT_SENT/UNKNOWN 必须携带已持久的原生身份和强键摘要。原生身份在派发提交前和回执解析时使用同一有界校验，避免先发送、随后发现身份无法传输。规范载荷编码/摘要由 Base 共享，必须保持旧 journal 的字节与摘要；秘密字段检查仍由相应入口承担，规范编码本身不授权或脱敏。

策略 SDK 客户端复用 `ThreadedServiceClientRuntime`，按 owner 线程产生的不可变 identity、原 run、mount/service/instance/scope/operations 快照核对唯一路由。客户端不创建 provider、原生会话或本进程写 grant。共享 OrderRequest decoder 位于中立 SDK 模块，与服务器 dispatcher 装配分开。显式 Gateway 失败不会切回 direct。

客户端必须注入持久宿主端口：reserve 前保存完整意图、稳定 request_key、账户/策略/journal、摘要和原 run 并回读；dispatch 前耐久记录原预留；release 前保存稳定 operation_id 与 expected_version。保存失败不发送对应 RPC。宿主负责原子冲突和跨进程单调观察，回读一致性不等于物理 fsync 证明；BT 的具体 pending 适配仍需后续交付，本轮测试适配器不是生产存储实现。

客户端结果区分观察、易失排队、请求拒绝、本次 RPC 未启动和结果未知，不直接投影为订单 Rejected 或 NOT_SENT。任何丢回复、无效写回执或提交后存储失败均保留原意图，按原键恢复；不自动重发。release 成功须与本次持久操作 ID/版本匹配。请求状态可在回复前已前进，合法重复派发应接受原命令的新状态，不能仅因回复版本大于请求版本就否定它，也不据此再次发送。

相同记录版本下，剩余 TTL、expiry_pending、当前 owner 代际和代际匹配可以变化；它们是观察字段。EXPIRED 可以在同一版本上首次补充成对的 release 元数据，既有 pair 不得移除或更换。原生身份和其他稳定字段矛盾、版本倒退仍拒绝。新 run 可在当前 Registry 授权下读取或释放旧意图，不能自动重新派发旧 run 的意图；正常重连保留原 run。

## 9. R06 结算观察绑定与每日耐久尝试

本节依据计划 §3.9“每账户每交易日确认一次”，修复 I63-S002 并接续 D63-14，不增加账户操作授权。具体实现和检查见分轮记录，不能据接口合同宣称真实自动结算已通过。

Base 提供不可变 SettlementObservation（route、provider 账户绑定、交易日、原生 generation、状态、observation_id）和 SettlementWriteBinding（同一观察、耐久 marker）。DTO 只是值；provider 以实际同次查询来源、issuer、Trader/API/SPI、账户/日/代际及期限验证原对象，复制/伪造 DTO 不授予确认。诊断字典或当前 ready 标志不能重新制造查询证明。CTP 同一会话后续结算观察/状态改变也使旧票据失效。

provider 显式声明 settlement_required：False 才表示无需该步骤；缺失或错误声明为 UNKNOWN。CTP 声明 True，OKX/Binance 显式声明 False。SDK ensure_settlement 保留对宿主的枚举结果接口，可接受受信 owner 传入的同一观察；必需步骤不再凭裸状态枚举、随后独立采样的 day/generation 写 marker。观察在提交前、耐久提交后再次校验；marker 使用原观察的账户/日/代际/观察 ID，grant 再绑定该观察和 marker。提交后的准入失败和调用结果不明为 UNKNOWN，不因缺少返回值推断未提交。

CTP 的 SDK direct/Gateway 确认入口要求原 UNCONFIRMED 观察，通过同一 SDK grant 校验后，将账户、交易日、代际、API/SPI 和期限复核传至最终 native 入口。旧 ingress 分支之外也必须检查原生结算授权，不把内部锁当成外部硬 fence；Registry、journal 事务和 CTP 会话状态锁不跨阻塞 native 调用，provider/coordinator 的串行化锁保持明确的原有职责。成功只由同一账户/交易日的来源绑定新回读确认。SDK_ADMITTED_PROFILE 不允许空观察校验/消费入口；原非 SDK typed managed/core 路径保留独立受控授权，不能据此宣称全部旧通路已迁为新观察合同。所有原生结算入口仍统一检查账户/日/代际/API/SPI 和单次进入。原生 auto_settlement_confirm 保持关闭，R05 对可信空/合法旧日回读的既有本地政策不变，I63-S003 的真实日期与覆盖语义仍是 GAP。

Gateway 在现有账户 journal 同一 SQLite DB 内加入每日结算记录，复用 journal_id、修订锚点、FULL/WAL、文件身份和容量控制。键为账户/route/交易日，原生账户绑定在同 route 跨日保持一致；初始 observation、attempt/marker、owner/native generation 不覆盖。ATTEMPTING 必须在原生确认前耐久写入；UNKNOWN 保留尝试；CONFIRMED 只由受信 owner 提交的新鲜确认观察推进。storage 不自行证明来源。任何已有同日尝试均不再返回一个可发送的 marker，重启、回复丢失和提交结果不明只能先回读；后续交易日另建该日记录，旧记录保留。确认已经存在时可只记录只读观察，不造一次实际发送。

schema v2→v3 为显式、受当前账户 guard 约束的加表事务，检查已保存 journal_id、修订和容量，保留原命令/释放/强键；不通过删除数据库或静默创建空库升级。失败必须回滚，旧代码/旧对象不得忽略新版 schema 继续写。迁移不解决外部绕锁写者或恢复旧备份的权威问题。

SDK GatewaySettlementController 绑定精确本地 provider、coordinator、现有 dispatcher/journal，以及由受信装配提供的预期 provider 账户绑定。tick 在账户 owner 线程先回读；只有原观察可信、准入开启、当日无尝试时才经 SDK 写确认。journal 取得写锁后及提交前复核当前 owner、观察与准入，等待磁盘锁不延长观察有效期。确认或未知都不能解除订单 UNKNOWN/急停等独立原因；ready 只能来自仍有效的当前观察，不能从旧持久 CONFIRMED 自行恢复。

GatewayDirectOwner 可注入同线程周期维护回调，在空闲和队列任务之间执行，不在网络线程或第二个原生线程调用；持续任务不能饿死维护。关闭后不再开始新维护，在途阻塞继续遵循保留清理责任的合同。实际交易工厂必须把结算 ready 接入派发准入；提供 hook 和合成联调不等于完整单 TD/MD 部署完成。

本轮验证必须覆盖：状态读取后/marker 等待中/提交后/最终 native 前的会话变化、伪造或复制观察、错误账户/日期/来源、一次性授权；同日重复 tick、确认回复丢失、进程重开、次日一次、只读已确认、写准入关闭、迁移回滚/数据保留、周期维护与关闭。源码、安装包、替身 native 和真实账户证据分别报告。

SDK verifier 与 commit port 是受信装配依赖；DTO、marker 字符串和类型相等不自行证明 fsync 或阻止任意进程内 Python 代码伪造权限。真实来源核验归 provider，耐久责任归注入的宿主。controller 只接收 settlement_required 精确为 True 的 provider，并在每次实时 gate 复核；无需结算的路由不通过此 controller 伪造观察。ready 仅允许 owner 线程读取并验证，status.observed_ready 是无 provider 调用的缓存诊断，不能用于网络线程授权。维护间隔为 0.001–3600 秒，队列任务与到期维护均须获得执行机会。

## 10. R07 单一 CTP 会话与交易 operator 装配

本轮接续真实资源工厂和独立进程服务入口，目标范围不缩减为 fake-only 服务。当前生产源码没有 CTP trading_owner 工厂；现有 operator 只接账户只读 worker 或 market_hub，直接同时启动旧两类 profile 会分别创建 TD/MD。下述合同在实现前冻结，验收结果另记。

### 10.1 规范账户和启动前提

本轮显式支持现有 CTP SimNow provider 范围，AccountKey 的 provider/venue/environment 精确为 ctp/simnow/simnow；其他环境不假装可用，完整目标与真实环境验收仍保留。broker（subaccount_id）与 user（account_id）必填、拒绝首尾空白，保留大小写及前导零。前置地址、策略、显示别名和 API 密钥不参与账户锁键。settings.account_scope、journal.account_scope、WireScope 账户和 flow_account_scope 必须一致，且等于既有 AccountKey.account_key_id 的规范 JSON 摘要；不得用任意显示别名创建新锁域。

Gateway 选择 LocalAccountSessionGuard，不另起 HostAccountRegistry 锁体系。锁根与 flow 根均显式提供受信既有目录；不同根、direct、其他 OS 用户/主机的限制沿用 INV63-02 / I63-G001，不宣称跨主机 fencing。旧 label 库拒绝不匹配，不静默改名/迁移。交易工厂只打开显式 journal_id/revision 锚定的 schema v3 现存库；初始化与 v2 升级仍是显式操作，不因服务启动自动建空库。

### 10.2 Provider 单一会话

CTP 新 CtpGatewaySession 是原组件的资源组合：CtpReadOnlyAccountSessionProvider 唯一创建和持有 TD、复用其来源绑定账户查询和确证关闭；CtpDirectWriteProvider 借用同一个精确 request feed/Trader；一个 CtpQuoteV2MarketProvider 为多个 symbol 复用一个惰性 MD。禁止另建 CtpTradeStream、第二 TD 或将旧子进程只读 worker 接到同一账户。

构造不连接 native，connect 前已保留可关闭句柄。受信 installed-code factories 返回精确、新建且未连接的 feed/stream；native 前核对账户、front 绑定、flow 根与规范 scope。发现外来已连接资源须拒绝，不能将它当本组件拥有的资源停止。credentials 仅在受信工厂闭包内，错误为有限码；YAML 不提供任意 Python factory 导入。

同一 Trader 原生重连后可刷新来源绑定的查询 scope，但必须仍是相同 feed/Trader 与原账户，不能重建第二会话或给旧查询补上新 scope。Gateway direct provider 禁止 implicit connect，关闭后台结算 readback；结算维护由 R06 controller 在唯一账户 owner 线程调用。普通 direct 的既有后台模式保留。共享会话及其已取出的 provider 引用在公共请求入口先检查构造 PID 和适用的 owner thread 对象，避免 fork 或线程 ID 重用绕过；native 回报 listener 仍按其原跨线程投递职责运行。

关闭先停止接受新工作，保留未确认 MD/TD 对象。market.close 或账户的 typed startup/native stop receipt 不完整时返回 False，可重试，不丢引用；stop/disconnect 的返回、coordinator 吞掉的异常和 guard.release 都不是 native 已关闭证明。重连后的停止必须核对同一 Trader 当前原生代际及实际 receipt，不让初始代际永久阻止合法清理，也不以任意新代际掩盖对象替换。只有全部关闭确认后才能释放 guard。

### 10.3 SDK operator 与资源所有权

GatewayOperatorProfile/Deployment 增加 trading_owner 角色，复用已存在的 service.direct_write、GatewayDirectServiceBinding 和 ServiceHost。该角色拒绝旧 account_session/market_binding/session_owner 注入；资源由显式受信 resource_provider 提供，不误入旧 account worker 装配，不自动创建第二原生资源。

新 build_ctp_gateway_trading_profile 只注册工厂，不立即启动。Host 获取该 component 资源时才创建 GatewayDirectOwner；后者在自己的线程取得 guard、打开 journal、创建/连接 CtpGatewaySession、绑定 coordinator/dispatcher/settlement controller。dispatcher 是该 guard 的唯一 consumer。

派发准入必须同时满足 controller.ready 的实时验证与应用显式提供的 assert_admitted(record) 字面 True；不提供默认业务放行，不把 cached observed_ready 或 owner 队列可接纳状态当成交易授权。后续最小 UNKNOWN、账户/策略账本及恢复的完整接线仍须交付，必需回调不得以恒 True 冒充生产门禁。write_enabled 缺省 False；每日结算确认继续使用 SDK 写准入和 R06 耐久尝试。

ServiceHost 的 ComponentResources.owned 接管精确 binding 与关闭回调；回调必须把 owner.close(timeout) False 转成有限异常，让 Host 保留 close_failed/custody 并可重试。部分构造失败通过 ServiceResourceConstructionError 交出 owned 句柄；owner 工厂内部失败通过 GatewayOwnerStartupCleanupError 保留原 session/guard 清理。不得因尚未发布 binding 而遗失已启动线程。Host 基础 ready 表示基础 RPC/owner 可服务，不证明账户可交易；实际提交仍检查实时结算和业务准入。

本轮不将惰性市场 provider 的存在写成行情网络端口已接好。后续须把行情与账户读取接入同一 owner/read model，不能让网络线程直接调用线程绑定的 provider，或为复用旧 MarketHub 再建一套 MD。

### 10.4 验证与剩余范围

覆盖真实 Python TraderClient 配合 fake native 的单 TD/单 MD、多 symbol、读写同对象、账户/front/flow 错配、来源刷新、启动失败、关闭失败/重试、错线程/fork；SDK operator 使用真实 ServiceHost/CURVE 和独立进程合成资源验证配置、注册、原键 reserve/dispatch/status 与完整资源责任。组件替身检查与真实 CTP 接线检查分列。真实账户操作、实际原生跨平台停止、完整行情/账户网络接线、BT 及整期验收仍不因本轮通过而完成。

### 10.5 审阅补充与明确缺口

市场订阅的公开 handle 不得暴露 stream、queue 或 owner token；返回不可变、不透明身份，资源和源状态由 provider 内部持有，并按精确句柄对象核验。伪造或复制句柄不继承订阅所有权；不保留旧公开资源字段别名。Python 私有反射不在隔离承诺范围内。

R07 真实 Python CTP 工厂联调暴露显式前置 profile 错误进入 managed 分支的 I63-C001：修复须依现有 direct SDK admission 与最终 native 校验分流，不将 profile 字符串当权限，也不删除旧 managed verifier。短暂 TD 不可用导致 owner 停止、未自动恢复的 I63-C002 仍须继续实施。记录缺口不缩减本期目标；本轮只接受已实测的会话组合、资源保管和服务装配切片，不能将外部准入 callback 或 synthetic provider 代替尚未实现的账本与恢复能力。
