# 迭代 63 分轮合同冻结稿

日期：2026-11-08。状态：分段冻结、实现中，**不代表 63.01 或整期验收完成**。本文件将当前实施边界写到可检验的接口；未覆盖的总体合同仍见计划、设计和实施合同补充。

## 1. 第二轮原生派发组合

Gateway 的 `direct.reserve` 与 provider 的 `reserve_order` 是不同阶段。前者仅写账户、策略、认证 principal、request_key、摘要、预留 UUID、TTL、owner generation；它不调用 CTP，不分配 OrderRef。收到 `direct.dispatch` 后，Gateway 在唯一 owner 线程检查原记录、范围、期限、权限及门槛，再调用 SDK 已有 `DirectWriteCoordinator.place`。其中 provider.reserve_order 才分配原生身份；注入的 Gateway commit port 将该身份与强键写为 DISPATCHING，事务成功才返回原预留号作为 marker，SDK 随后复核会话、签发并消费一次性 grant、发送。

这一组合保留两阶段的耐久次序，复用已实现的 SDK 原生流程，不必为了远端 reserve 而提前拆开 provider 原生 reservation。原计划要求拆分 coordinator 的机械改造因此调整；远端策略 SDK 的 PREPARED 与延后 attach 原生身份仍须单独实现，不能用带 Gateway 标签的假 NativeOrderIdentity 填空。

内部 `GatewayDirectDispatcher` 绑定真实 LocalAccountSessionGuard、账户及同一 generation，所有操作在 guard owner 的进程和线程。已 DISPATCHING/SENT/NOT_SENT/UNKNOWN、RELEASED 或 EXPIRED 的同身份重放只读原记录；不再分配原生身份或发送。最终结果写入失败保留 DISPATCHING，后续只能查原记录。它尚不是完整交易 owner，不自动建立身份授权、会话就绪、结算、急停、账本或未知解决。

SDK 组合层显式绑定 expected_local_provider 对象与 coordinator route，按需加载 Gateway。该实例绑定不是原生来源证明；受信装配必须提供本地 native provider，不能接远端 Gateway provider 形成递归。Gateway 包不反向导入 SDK。

## 2. 订单载荷与请求绑定

首个派发切片只接受 SDK 现有 OrderRequest.to_dict 的完整规范标量映射。quantity/price 是规范十进制字符串，布尔与整数保持精确类型；不接受二进制浮点、遗漏字段后隐式补默认、额外字段或嵌套 instrument/ctp_order_identity。account_id 必须等于配置的 Gateway 账户 scope；运行时、执行周期、托管意图等 authority 标签不允许由该普通下单载荷提供。

SDK 通过统一 decode_gateway_order_request 校验 from_dict/to_dict 的完整规范往返。RPC reserve 与原生 dispatch 共用该校验；dispatch 从原持久载荷构造请求，并在耐久 commit 前再核对请求未变化。不能只比较独立的 request_summary，因为它不能证明实际请求的方向、数量、价格、开平或有效期。后续若支持嵌套中立合约或母单扩展，须升级明确 schema 和验收向量，不以任意 factory 绕过本合同。

SDK strong_identity_keys 复用选定 provider 的关联规则，仅输出 strong 键的排序、去重、ASCII 规范 JSON 字符串，每键最多 256 字符。拒绝错 route、缺失所需交易日、不可规范化键和无强键；不会注册身份、消费事件或签发 grant。强键投影不证明原生来源，CTP 仍由受信 provider 返回完整会话/交易日身份，弱日/ref 候选不能单独认领。

## 3. 首个 RPC 切片

端口 `service.direct_write`，显式 Gateway `trading_owner` 角色；本轮 capability 仅声明已实现的 `direct.reserve`、`direct.release`、`direct.command_status`。mount 为 broker.direct_write、application.direct_write、upstream.direct_write。该角色名不是已经具备完整交易 owner 的证明；未实现的 dispatch、cancel、结算与事实接口不发布。

reserve/release 是持久写操作，遵循 registry 的认证、scope、epoch、grant、撤权和活动 strategy run claim。reserve 遵循现有 STOP_NEW；release 和原记录查询保留。绑定从可信 ServiceCallContext 取得账户、策略、principal，wire 自报字段不能覆盖。此切片拒绝 SERVICE 代理，代理关系与观察流由 63.13 继续交付。

command_status 按账户＋策略＋principal 读取原请求，允许获权的新 run 恢复自己的历史记录，不以旧 run 作为读取前置。写入仍要求当前有效 run claim。订单 idempotency_key 必须等于外层 request_key。TTL 是首次创建选项，不参与订单 payload 摘要，同键重试不延长原窗口；成功回执提供 journal_id、记录 generation、是否当前代、相对剩余秒数与 expiry_pending。过期观察不写 EXPIRED，也不证明 NOT_SENT。

STOP_NEW 后默认包含 reserve 的完整注册仍被拒，SDK 提供 release＋command_status 的最小恢复注册配置；release 保留写 claim，不能把它降为只读来绕过授权。

成功业务结果为 status=OK；明确未执行本次操作的验证拒绝为 REQUEST_REJECTED＋有限码。这不是订单 Rejected 或原命令 NOT_SENT 证明。提交后不确定、损坏和无法分类的异常保留 HANDLER_FAILED/ServiceCallOutcomeUnknownError，禁止换 key 盲重发。

## 4. CTP flow 与结算

provider 客户端新增成对的 trusted_flow_root/flow_account_scope，根必须已存在且为绝对真实目录；账户路径用 scope SHA256 下分 td/md。构造时绑定目录身份，native factory 前再次验证；借用 Trader 必须匹配同一绑定。普通 direct 未配置时保留既有临时目录，一次性 MD 诊断保留自己的临时生命周期。Gateway 完整装配后必须强制配置，不允许验证失败后回退临时目录。

当前 POSIX 实现要求 0700，因此只覆盖同一 OS 用户。计划中的跨 OS 用户共根部署及 Windows ACL 验证仍为 GAP，不能把“同机锁根”误读为已支持任何用户组合。native API 最终只接受路径字符串，最后检查至 native 打开之间仍依赖受信权限；目录不是互斥或跨主机 fence。

D63-14 的每日自动确认由 Gateway 调度 SDK ensure_settlement：先读当日状态，仅明确 UNCONFIRMED 且账户写准入有效时写耐久标记并确认，UNKNOWN 先回读、不能无限重试。原生 auto_settlement_confirm 继续关闭。账户/交易日状态、重启、日切和确认故障的完整持久状态机尚未交付。

## 6. 默认传输与破坏式重构授权

D63-50冻结默认transport为bt_api_transport_zmq。SDK gateway extra默认包含该包，现有ZmqTransportFactory和ServiceHost继续经该包通信；原R02“ZMQ另选”的安装方案由此更新。未来其他中间件归新传输包；当前不新增backend。用户授权Gateway及ZMQ包必要破坏式调整，仍需维护同版接口、错误/UNKNOWN语义、主体范围、socket线程归属及独立进程验证。

## 7. R04 派发排队与授权复核合同

本节冻结 R04 的实施约束，测试和交付状态另见分轮记录。现有 ServiceHost 在 ZMQ owner 线程同步调用 handler，poll timeout 不限制 handler 耗时。派发 handler 不得等待原生调用完成：网络线程继续持有 socket，另一个账户 owner 线程创建并独占 dispatcher、guard 和原生资源。该线程不是策略调度器；Cerebro 的策略生命周期不变。

`direct.dispatch` 使用原 request_key、reservation_id、digest、expected_version。有界内存队列接纳后只报告排队状态，不能称为耐久派发成功。重复排队按完整身份核对；队列满、关闭、排队超时或回复丢失均不能证明原命令 NOT_SENT。客户端通过原键查询 journal；原生身份仅在 DISPATCHING 的耐久事务中建立，不用队列编号伪造。该路径不自动重发、不切回 direct。

Registry 为当前已认证的 direct.dispatch 签发绑定原注册、epoch、身份、作用域、操作和完整参数的进程内能力。能力可移交给单一账户 owner 线程，不能并发、重入或在任务结束后继续使用。初检与耐久派发前分别复核；固定锁序为 Registry → Gateway journal，短临界区中只做本地授权与持久状态变更，不执行 provider 或网络 I/O。取得 journal 写锁后须再次检查当前时间和租约，避免锁等待期间过期的请求取得 marker。此合同定义本地授权检查与状态转换的线性化边界，不把进程锁或已通过的检查当成跨主机 fencing，也不声称能撤回已到 provider 的请求。

Gateway 的 owner admission 只接受字面 True，漏写返回值、异常和其他值均拒绝。每请求 fence 单独传递，不能使用共享可变的“当前请求上下文”。只有明确接入 owner 队列且核对其 journal/账户/代际绑定的服务才发布 dispatch capability；纯 storage 服务继续只发布三项已实现操作。原有 registry STOP_NEW 是旧 run 写入栅栏，不等同于后续仅约束普通开仓的 Gateway 业务急停政策。

服务配置显式设置 `dispatch_enabled: true` 才计划发布第四项操作；默认 false 保留 storage 切片。配置开启而受信资源未提供匹配 owner 时启动失败，不在运行时补成伪能力。状态回执中的 native_identity 来自原耐久记录，解析身份字段后再次做有界与敏感字段校验；不硬编码交易所专有身份字段。strong_identity_key_digests 仅是强键摘要的一致性投影，不是原生查单键或权限、来源证明。

permit.close 是非阻塞的任务清理，阻止后续 scope 和重新校验，不撤回已经通过最后复核的本次短临界区提交。权限撤销、STOP_NEW 和 Registry 关闭仍通过 Registry 的锁串行化。固定 SQLite read snapshot 与进程锁仅保护遵循同一 Registry owner 的操作，不保护绕过锁直接修改数据库的外部写者。

owner 原生调用阻塞时，关闭等待有上限，但不能假定 native 已取消、释放账户锁或另起 owner。资源关闭始终在原 owner 线程；启动中途失败也须保留明确的清理句柄，未知清理状态不能报告关闭成功。停止接纳、丢弃未运行队列项与在途责任分别处理，原 journal 保留恢复依据。该切片不保证磁盘故障或不释放 Python GIL 的 native 阻塞下控制面的硬实时性；真实 native、进程隔离、完整 TD/MD 生命周期仍需后续验证。

本轮队列为有界 FIFO，不承诺策略间公平配额。排队期限只表示过期任务不得开始派发；无独立清扫线程，过期项在下一次出队或显式 close 时清理。状态查询仍同步访问 SQLite，锁等待或存储阻塞可影响网络线程；native 替身阻塞时仍可服务的证据不能推广为全链路无阻塞。最小 UNKNOWN 作用域阻断仍由后续 owner admission 与账本接线，队列 failure_category 本身不代替订单真值。

## 8. R05 策略侧逻辑预留与持久宿主端口

中立 `GatewayCommandBinding` 和 schema_version=1 的 `GatewayCommandRecord` 归 Base。成功回复显式携带 journal_id、账户、策略、principal，全部来自 Gateway 耐久记录；客户端必须与可信配置精确核对，不从首次回执自动接受新 journal。run_id 不在 Gateway 命令记录中，不伪装为耐久字段；它由客户端原意图和实际注册作用域绑定。

RESERVED 没有原生身份；DISPATCHING/SENT/NOT_SENT/UNKNOWN 必须携带已持久的原生身份和强键摘要。原生身份在派发提交前和回执解析时使用同一有界校验，避免先发送、随后发现身份无法传输。规范载荷编码/摘要由 Base 共享，必须保持旧 journal 的字节与摘要；秘密字段检查仍由相应入口承担，规范编码本身不授权或脱敏。

策略 SDK 客户端复用 `ThreadedServiceClientRuntime`，按 owner 线程产生的不可变 identity、原 run、mount/service/instance/scope/operations 快照核对唯一路由。客户端不创建 provider、原生会话或本进程写 grant。共享 OrderRequest decoder 位于中立 SDK 模块，与服务器 dispatcher 装配分开。显式 Gateway 失败不会切回 direct。

客户端必须注入持久宿主端口：reserve 前保存完整意图、稳定 request_key、账户/策略/journal、摘要和原 run 并回读；dispatch 前耐久记录原预留；release 前保存稳定 operation_id 与 expected_version。保存失败不发送对应 RPC。宿主负责原子冲突和跨进程单调观察，回读一致性不等于物理 fsync 证明；BT 的具体 pending 适配仍需后续交付，本轮测试适配器不是生产存储实现。

客户端结果区分观察、易失排队、请求拒绝、本次 RPC 未启动和结果未知，不直接投影为订单 Rejected 或 NOT_SENT。任何丢回复、无效写回执或提交后存储失败均保留原意图，按原键恢复；不自动重发。release 成功须与本次持久操作 ID/版本匹配。请求状态可在回复前已前进，合法重复派发应接受原命令的新状态，不能仅因回复版本大于请求版本就否定它，也不据此再次发送。

相同记录版本下，剩余 TTL、expiry_pending、当前 owner 代际和代际匹配可以变化；它们是观察字段。EXPIRED 可以在同一版本上首次补充成对的 release 元数据，既有 pair 不得移除或更换。原生身份和其他稳定字段矛盾、版本倒退仍拒绝。新 run 可在当前 Registry 授权下读取或释放旧意图，不能自动重新派发旧 run 的意图；正常重连保留原 run。

## 9. R06 结算观察绑定与每日耐久尝试

本节依据计划 §3.9“每账户每交易日确认一次”，修复 I63-S002 并接续 D63-14，不增加账户操作授权。具体实现和检查见分轮记录，不能据接口合同宣称真实自动结算已通过。

Base 提供不可变 SettlementObservation（route、provider 账户绑定、交易日、原生 generation、状态、observation_id）和 SettlementWriteBinding（同一观察、耐久 marker）。DTO 只是值；provider 以实际同次查询来源、issuer、Trader/API/SPI、账户/日/代际及期限验证原对象，复制/伪造 DTO 不授予确认。诊断字典或当前 ready 标志不能重新制造查询证明。CTP 同一会话后续结算观察/状态改变也使旧票据失效。

provider 显式声明 settlement_required：False 才表示无需该步骤；缺失或错误声明为 UNKNOWN。CTP 声明 True，OKX/Binance 显式声明 False。SDK ensure_settlement 保留对宿主的枚举结果接口，可接受受信 owner 传入的同一观察；必需步骤不再凭裸状态枚举、随后独立采样的 day/generation 写 marker。观察在提交前、耐久提交后再次校验；marker 使用原观察的账户/日/代际/观察 ID，grant 再绑定该观察和 marker。提交后的准入失败和调用结果不明为 UNKNOWN，不因缺少返回值推断未提交。

CTP 的 SDK direct/Gateway 确认入口要求原 UNCONFIRMED 观察，通过同一 SDK grant 校验后，将账户、交易日、代际、API/SPI 和期限复核传至最终 native 入口。旧 ingress 分支之外也必须检查原生结算授权，不把内部锁当成外部硬 fence；Registry、journal 事务和 CTP 会话状态锁不跨阻塞 native 调用，provider/coordinator 的串行化锁保持明确的原有职责。成功只由同一账户/交易日的来源绑定新回读确认。SDK_ADMITTED_PROFILE 不允许空观察校验/消费入口；原非 SDK typed managed/core 路径保留独立受控授权，不能据此宣称全部旧通路已迁为新观察合同。所有原生结算入口仍统一检查账户/日/代际/API/SPI 和单次进入。原生 auto_settlement_confirm 保持关闭，R05 对可信空/合法旧日回读的既有本地政策不变，I63-S003 的真实日期与覆盖语义仍是 GAP。

Gateway 在现有账户 journal 同一 SQLite DB 内加入每日结算记录，复用 journal_id、修订锚点、FULL/WAL、文件身份和容量控制。键为账户/route/交易日，原生账户绑定在同 route 跨日保持一致；初始 observation、attempt/marker、owner/native generation 不覆盖。ATTEMPTING 必须在原生确认前耐久写入；UNKNOWN 保留尝试；CONFIRMED 只由受信 owner 提交的新鲜确认观察推进。storage 不自行证明来源。任何已有同日尝试均不再返回一个可发送的 marker，重启、回复丢失和提交结果不明只能先回读；后续交易日另建该日记录，旧记录保留。确认已经存在时可只记录只读观察，不造一次实际发送。

schema v2→v3 为显式、受当前账户 guard 约束的加表事务，检查已保存 journal_id、修订和容量，保留原命令/释放/强键；不通过删除数据库或静默创建空库升级。失败必须回滚，旧代码/旧对象不得忽略新版 schema 继续写。迁移不解决外部绕锁写者或恢复旧备份的权威问题。

SDK GatewaySettlementController 绑定精确本地 provider、coordinator、现有 dispatcher/journal，以及由受信装配提供的预期 provider 账户绑定。tick 在账户 owner 线程先回读；只有原观察可信、准入开启、当日无尝试时才经 SDK 写确认。journal 取得写锁后及提交前复核当前 owner、观察与准入，等待磁盘锁不延长观察有效期。确认或未知都不能解除订单 UNKNOWN/急停等独立原因；ready 只能来自仍有效的当前观察，不能从旧持久 CONFIRMED 自行恢复。

GatewayDirectOwner 可注入同线程周期维护回调，在空闲和队列任务之间执行，不在网络线程或第二个原生线程调用；持续任务不能饿死维护。关闭后不再开始新维护，在途阻塞继续遵循保留清理责任的合同。实际交易工厂必须把结算 ready 接入派发准入；提供 hook 和合成联调不等于完整单 TD/MD 部署完成。

本轮验证必须覆盖：状态读取后/marker 等待中/提交后/最终 native 前的会话变化、伪造或复制观察、错误账户/日期/来源、一次性授权；同日重复 tick、确认回复丢失、进程重开、次日一次、只读已确认、写准入关闭、迁移回滚/数据保留、周期维护与关闭。源码、安装包、替身 native 和真实账户证据分别报告。

SDK verifier 与 commit port 是受信装配依赖；DTO、marker 字符串和类型相等不自行证明 fsync 或阻止任意进程内 Python 代码伪造权限。真实来源核验归 provider，耐久责任归注入的宿主。controller 只接收 settlement_required 精确为 True 的 provider，并在每次实时 gate 复核；无需结算的路由不通过此 controller 伪造观察。ready 仅允许 owner 线程读取并验证，status.observed_ready 是无 provider 调用的缓存诊断，不能用于网络线程授权。维护间隔为 0.001–3600 秒，队列任务与到期维护均须获得执行机会。

## 10. R07 单一 CTP 会话与交易 operator 装配

### 10.1 规范账户和启动前提

本轮显式支持现有 CTP SimNow provider 范围，AccountKey 的 provider/venue/environment 精确为 ctp/simnow/simnow；其他环境不假装可用，完整目标与真实环境验收仍保留。broker（subaccount_id）与 user（account_id）必填、拒绝首尾空白，保留大小写及前导零。前置地址、策略、显示别名和 API 密钥不参与账户锁键。settings.account_scope、journal.account_scope、WireScope 账户和 flow_account_scope 必须一致，且等于既有 AccountKey.account_key_id 的规范 JSON 摘要；不得用任意显示别名创建新锁域。

### 10.2 Provider 单一会话

CTP 新 CtpGatewaySession 是原组件的资源组合：CtpReadOnlyAccountSessionProvider 唯一创建和持有 TD、复用其来源绑定账户查询和确证关闭；CtpDirectWriteProvider 借用同一个精确 request feed/Trader；一个 CtpQuoteV2MarketProvider 为多个 symbol 复用一个惰性 MD。禁止另建 CtpTradeStream、第二 TD 或将旧子进程只读 worker 接到同一账户。

同一 Trader 原生重连后可刷新来源绑定的查询 scope，但必须仍是相同 feed/Trader 与原账户，不能重建第二会话或给旧查询补上新 scope。Gateway direct provider 禁止 implicit connect，关闭后台结算 readback；结算维护由 R06 controller 在唯一账户 owner 线程调用。普通 direct 的既有后台模式保留。共享会话及其已取出的 provider 引用在公共请求入口先检查构造 PID 和适用的 owner thread 对象，避免 fork 或线程 ID 重用绕过；native 回报 listener 仍按其原跨线程投递职责运行。

### 10.3 SDK operator 与资源所有权

GatewayOperatorProfile/Deployment 增加 trading_owner 角色，复用已存在的 service.direct_write、GatewayDirectServiceBinding 和 ServiceHost。该角色拒绝旧 account_session/market_binding/session_owner 注入；资源由显式受信 resource_provider 提供，不误入旧 account worker 装配，不自动创建第二原生资源。

派发准入必须同时满足 controller.ready 的实时验证与应用显式提供的 assert_admitted(record) 字面 True；不提供默认业务放行，不把 cached observed_ready 或 owner 队列可接纳状态当成交易授权。后续最小 UNKNOWN、账户/策略账本及恢复的完整接线仍须交付，必需回调不得以恒 True 冒充生产门禁。write_enabled 缺省 False；每日结算确认继续使用 SDK 写准入和 R06 耐久尝试。

ServiceHost 的 ComponentResources.owned 接管精确 binding 与关闭回调；回调必须把 owner.close(timeout) False 转成有限异常，让 Host 保留 close_failed/custody 并可重试。部分构造失败通过 ServiceResourceConstructionError 交出 owned 句柄；owner 工厂内部失败通过 GatewayOwnerStartupCleanupError 保留原 session/guard 清理。不得因尚未发布 binding 而遗失已启动线程。Host 基础 ready 表示基础 RPC/owner 可服务，不证明账户可交易；实际提交仍检查实时结算和业务准入。

本轮不将惰性市场 provider 的存在写成行情网络端口已接好。后续须把行情与账户读取接入同一 owner/read model，不能让网络线程直接调用线程绑定的 provider，或为复用旧 MarketHub 再建一套 MD。

## 11. R08 BT Gateway 持久宿主与 pending 扩展

本轮依据用户已批准的 BT 有限调整，先实现独立于 Broker/Store 运行接线的存储切片。它落实 SDK GatewayClientHostPort，不能据此称策略已能连 Gateway 或交易。框架调度、Order/Position/Trade 核心、只读接入和普通 direct 语义不改。

### 11.1 共同中立合同与格式

SDK 在现有 gateway_direct_client 模块提供受检 intent/release 映射编解码、intent 构造及 record 单调进展校验；客户端和 BT 宿主复用同一合同，不把 DTO 校验复制到 BT。持久映射带独立 schema_version，拒绝多余/缺失字段、非规范 payload/digest、账户/route/strategy/principal 不一致和非有限 TTL。canonical_payload 只来自既有 decode_gateway_order_request 的全字段规范请求，account_id 必须等于受信 account_scope；不存原生账户凭据、密钥或任意原始配置。标签和 DTO 本身不授予账户权限。

普通新建 pending.json 仍为 v1。新增明确 upgrade_for_gateway 操作，在 pending.lock 下验证完整 v1（含 UUID、active/history），原子改写为 v2 并原样保留旧标记；不在读取、Host 构造或 direct 启动时自动迁移。v2 增加 gateway 段，其绑定固定为一个 journal/account/strategy/principal 组合，和本策略本地 UUID 分别存放；原始绑定不同必须拒绝，不靠显示名自动重绑。已有旧标记保持原字段；Gateway 标记增加明确 gateway 引用字段，不借未知 extra 字段伪装类型。

v2 的 gateway 段包含规范绑定、持久容量上限及以 request_key 为键的意图集合。每项保存规范 intent、最新观察、可空 marker_id、第一份 release plan、可空 local_seq/bt_ref。所有意图、观察、标记和原生身份同在 pending.json，同一 pending.lock 内核对并一次原子替换，消除跨文件提交窗；不引入第二个数据库/journal。v1/v2 明确验证，未知版本/损坏/错 UUID 拒绝，未选择 Gateway 的 v1 路径不要求导入可选 Gateway 合同。

### 11.2 幂等、补写与保留

GatewayPendingHost 的七个 SDK 宿主方法分别保存/读取 intent、record、release 和 commit_pre_dispatch。save_intent 可由 BT 在首次 RPC 前额外传 local_seq/bt_ref，SDK 普通调用不覆盖已有宿主事实；已知值冲突拒绝。首个 intent（含首个 TTL）与绑定不可覆盖，同键异请求/route/run/digest 拒绝，跨进程同值重复幂等。无标记意图也须能枚举恢复，不能因尚无原生身份或 PREPARED 标记而遗漏。

commit_pre_dispatch 只接受该意图已持久的 RESERVED 观察，锁内要求已存及请求观察同为 RESERVED、版本相同，并通过共享进展校验，才可重复返回同一 marker_id；已有本地标记须仍为 active PREPARED。动态 TTL/owner 观察不生成第二份标记。远端已推进或本地已变 UNKNOWN/已派发/终态时，旧 RESERVED 快照不再取得派发准入，既有标记仍可读取。逻辑标记可没有原生身份，去重使用 request_key 与固定绑定，不把两个空 native 元组当重复；普通 direct 仍拒绝没有身份的 place。不同意图不得复用活动 local_seq。

save_record 在锁内重验规范 DTO、完整绑定/摘要/预留身份及单调版本，复用 SDK 允许的动态观察字段和 EXPIRED release 补充规则。已存在 Gateway 标记时，在同一次写入中将首次真实 native identity/client id/generation/day 补入顶层标记并保存观察；同值幂等，任何换绑/退版本/强键冲突/其他标记占用身份拒绝且磁盘不变。身份补写本身不自动宣告 BT Accepted/Terminal，不解除 UNKNOWN；若仅有 intent 而无标记，观察仍可保管，但不能据此补造曾经成功提交的标记或重发。

release 首计划稳定保存；同键、reservation、digest、operation/version 冲突拒绝。容量默认 10000、显式上限 100000，升级时固定；满时拒绝新增，不自动清理去重键。Gateway 意图及其终态标记不受普通 direct 的最近 500 history 淘汰影响，旧直接标记仍按原规则裁剪。后续压缩须另行定义可恢复去重保留合同。

identity 初始化的 pristine 判断纳入 gateway 内容；new_instance rebind 必须拒绝未决 intent（含尚无 marker 的项）。有 active marker、无终态依据的 intent 或 SENT/UNKNOWN 观察仍未决；已在本地 history 有 TERMINAL marker，或无 marker 且可信观察已是 NOT_SENT/RELEASED/EXPIRED，才不因该项阻止重建。不删除旧账本，仍沿用原显式归档重建流程。运行时的 run.lock 所有权和本地文件系统限制仍适用，不宣称防绕锁外部写入或跨主机一致性。

### 11.3 验证和后续

验证非空 v1 迁移/中断重试、损坏/错策略拒绝；两个空身份意图并存；跨进程/重启幂等及冲突零写入；原生身份首绑/重复/冲突和原子写失败；旧 run 只查询/释放、原 marker 重用；未决意图阻止 rebind；全套既有 live_state direct/identity/CLI 回归。另用真实 GatewayDirectClient 和本地 synthetic 服务接宿主，不用测试宿主替身代替新持久层。只验证本地持久协议，不称 fsync 证明场所状态、断电保证或账户验收；Broker/Store 和租约线程在下一切片接续。

### 11.4 审阅补充：身份冲突、恢复路由与本地关联

v2 所有写入（包括既有 PendingCommandStore 的 commit/attach/mark）在原子替换前共用完整 validator；加载时同样核对双向关联、顶层原生身份与不可变 facts，采用精确类型比较，不允许 bool/int 相等掩盖换绑。普通 v1 的裁剪不应用到 Gateway 意图及其历史标记；显式升级不裁剪原 history。空 v2 的固定 binding 也是持久状态，不因尚无意图而视作 pristine。

SDK 提供 project_direct_strong_identity_keys 纯投影，与 DirectWriteCoordinator 共用既有相关性算法。BT 对旧 direct 标记分别产生按日和非按日的合法候选摘要，与 Gateway 观察内实际强键摘要比较，识别相同强身份但额外字段不同的情况；不从摘要反推身份，也不凭交易所名猜测 provider 声明。不同日的真实按日摘要不相交；真实非按日摘要仍按原声明跨日查重。字段畸形须明确拒绝，缺日仅使按日候选不适用。正向 Gateway 补写、反向旧 direct commit 及损坏文件加载采用相同防线。纯投影候选字段收紧为合法精确类型；不完整畸形字段由 unavailable 改为 invalid，不改变合法身份的 key。

Registry 可能在旧租约已释放后，将新的客户端会话绑定到原 durable run。Gateway 客户端只为 status/release 接受与持久原意图 run 完全匹配的已授权 binding，同时要求 runtime 的当前 run、principal、账户、策略、服务、端口及其他 scope 精确匹配；不允许任意第三 run，也不允许借恢复路由 reserve/dispatch。当前 run 的正常完整路由校验保留，不改通用 Registry 的归属和停机合同。

BT 提供只读、不可变 GatewayPendingContext，load_context(request_key) 在锁内返回 marker_id/local_seq/bt_ref，便于 Broker 在原生身份和标记尚不存在时恢复原本地关联；不据此补造 BT Order 或场所事实。


## 12. R09 单一 owner 的账户读模型与同服务只读端口

接续 R08（BT 552cc563e、SDK 3354cfd3）。本轮实现账户观测网络链路并补强 CTP 查询范围证据，完整策略账本、行情、执行回报、场所撤单及 Broker/Store 接线仍继续实施，不能把本切片作为全期完成标准。

### 12.1 复用观测与持久投影

从 GatewayAccountSessionWorker 提取 GatewayAccountReadModel，保留原 AccountObservation、coverage/complete、观测顺序、同 ID 内容、wall/monotonic 时钟、保留期限和 journal 原子快照校验。旧 worker 组合使用同一个实现，不复制一套宽松验证。read model 不拥有 provider、native 会话、guard 获取/释放或线程，构造和写入属于唯一账户 owner；原 worker 的连接、关闭、完整持仓来源和其他真实能力仍由原 owner 保持。

模型提供 start_generation、begin_refresh、finish_refresh、fail_refresh、close；begin 在原生查询前使缓存失效，并返回同代、单次使用的精确 attempt token。注入受信 assert_current_generation(generation) 回调，发布/持久化前后在 owner 线程复核；回调不创造外部账户授权。旧日志载入仅诊断，须本代新读取才就绪；同一观测重放不延长原新鲜度。旧 token、失败、关闭、代际切换均不能把旧值称为当前。

latest_snapshot/read_status 跨线程只读不可变内存及可信时钟，按剩余期限递减，不调用 provider、guard 或磁盘；PID 在锁前检查，写路径检查精确线程对象。网络读取期间 owner 的原生查询可以仍在等待，typed snapshot 此时明确不可用；不临时复制旧值冒充完整。多次原生查询保持 multi_query 语义，不能称账户原子切点或策略归属。

### 12.2 同一 ServiceHost 的显式双端口

trading_owner 可明确绑定 service.direct_write 与 service.account_read，现有单命令端口继续有效。账户读资源为精确 GatewayReadService + GatewayAccountReadModel，不伪装 provider_session；同 journal/账户/scope/身份验证保留。只广告 account.snapshot、account.snapshot.typed、account.head、account.read_after、account.ack、account.progress，且 read model 不提供 execution stream。configuration、server_time、metadata、reconciliation 等同步原生能力不得凭配置宣告可用。读端口 write_operations 为空，Registry 授权和 Gateway journal/principal ACL 均须通过；ACK 只是消费者本地持久处理进度。

SDK 显式提供 CtpGatewayAccountReadSettings（账户读 journal、state scope、required coverage、刷新/过期/超时）及 account_read_principals。无显式读授权时，direct 权限不会扩大成账户全览；应用主体与策略主体按已注册精确身份分别验证。策略账户只读只列明确获权的 strategy_ref，不能读出他人交易流或获得提交权。两个 journal 各保留原合同并拒绝同文件别名，不宣称读取快照与交易归属账本具有跨库原子性。

### 12.3 CTP 请求范围与行归属证明

## 13. R10 账户活动委托投影与持久观察身份

### 13.5 审阅补强

全部订单行在终态分流前核验同一交易日和可证实的状态/数量规则。全部成交必须成交量等于原量，部分成交不在队列必须为严格部分成交，未成交不在队列必须为零成交；取消仅应用明确的通用数量约束，不猜额外场所语义。条件单 b/c 或非 Immediately/缺少触发条件字段的活动行不能降为普通限价单；当前账户 DTO 未完整表达触发合同，本轮明确拒绝。

issuer 正常关闭的任何失败先禁止业务操作，保留原连接供重试，只有实际 close 成功才清空引用和标为 closed。初始化错误后若清理也失败，OrderCorrelationIssuerCleanupError 以有限错误和 close() 端口保留精确部分资源；profile 接入同一 owner 清理链，确认身份库已关闭前不释放 guard。初始化清理成功时维持原初始化错误。该错误不提供可用业务 issuer，不把失败重开变为可交易状态。

关闭失败标志必须在事务持锁后再次复核；不得用初始化特例放过已被失败关闭的对象。新 issuer_id 和 partial cleanup.close 的 PID 检查先于任何继承锁；这一新增入口限制不扩大为旧 issuer 全方法 fork 验收。

## 14. R11 同库回报归属与净数量账本

本轮实现 63.03 的持久核心，继续朝完整回报/账本/恢复链路推进。不能顺序调用三个独立 journal 代替同一事务。BT 产品本轮不调整；费用、成本/盈亏、external 基线及事实授权、网络事件端口/ACK、原生轮询与完整补查在后续接线完成，不能由本轮存储通过关闭对应要求。

### 14.1 中立回报事实

Base 新增 gateway_execution_protocol.py，定义冻结的 GatewayReturnFact（schema_version=1）。这是受信本地适配器提供的中立事实，不是网络提交端口，不认证来源或授权。显式字段：account_scope、route、instrument（MarketInstrumentKey）、trading_day（合法 YYYYMMDD）、kind（DirectExecutionEventKind）、identity（可空 NativeOrderIdentity）、identity_keys（有界、排序、唯一强键 tuple）、binding_keys（identity_keys 子集，表示必须已经绑定的会话/客户端锚点）、venue_key（可空且为 identity_keys 成员，仅订单回报可学习的新场所键）、trade_key（可空的有界字符串 tuple）、status（可空 DirectOrderStatus）、side、offset、order_quantity、filled_quantity、remaining_quantity、limit_price、trade_quantity、trade_price、trade_time、error_code、source_ref、session_generation。

side 只可为 buy/sell/None，offset 只可为 open/close/close_today/close_yesterday/None。数量/价格以规范十进制字符串或 None 保存，禁止浮点数、非有限值、bool、负数量；order/trade quantity 与提供的价格须大于零，filled/remaining 可为零。decimal 字符串最多 128 字符、最多 36 位整数与 18 位小数、无指数/多余前导零/尾随小数零；零统一为 0。类型与边界错误在落库前拒绝，不将缺失改为零。trade_time 仅有界文本诊断，不推导交易日。identity 若存在必须 route 一致，内部 trading_day 若存在须一致；沿用 Base 的敏感字段与深度/体积限制，不存任意 raw payload 或错误原文。source_ref 和 session_generation 仅来源标签，不是权限或真实性证明。

提供严格 to_mapping/from_mapping、fact_digest 与 trade_content_digest：fact_digest 排除 source_ref/session_generation 这两个接收诊断字段，其余事实字段保留；trade_content_digest 仅对逐笔成交经济事实计算，包含 account/route/instrument/day/trade_key/venue_key/side/offset/trade_quantity/trade_price，排除迟到的客户端身份/接收代际和诊断时间。同成交键的来源/身份补全不能制造第二笔成交，但其关联仍须重新检查。该摘要不证明内容真实。None 与空集合严格区分；缺 trade_key/venue_key/side/quantity/price 的成交可以保留为未归属事实，不得进入净仓。

### 14.2 v4 与同一事务域

GatewayDirectCommandJournal 创建 v4，新构造明确拒绝 v2/v3；提供受既有精确 LocalAccountSessionGuard 约束的 upgrade_v3，保留 upgrade_v2 的显式入口并使其在单一事务直接升级至 v4。验证账户/generation/journal_id/minimum_revision、精确旧 DDL/索引/触发器、命令/原强键/release 双向关系、settlement 行与共享容量，之后创建扩展表并一次更新 schema/revision；中断回滚，旧对象因锚点版本不同拒绝继续读写，不自动修表或重建身份。不得 executescript 隐式提交。

新增 direct_execution_journal.py 承载 GatewayDirectExecutionLedger；该对象接收精确 journal 和已持有 guard，复用原 _connection/_transaction 与文件身份/锚点，不开第二库、不导入 SDK。扩展表存规范事实、归属/未归属原因、成交唯一键及经济摘要/应用状态、追加的场所别名、每策略/规范合约的带符号净数量、不可变策略事件，以及同成交冲突审计。每次真实持久变更在同一事务 bump 一次 journal revision；重复无变化不 bump。所有 mutation 先查构造 PID/owner thread，再校验 guard；取得事务后及提交前复核 guard。只读查询不调用 native，也不把 scope 参数当授权。

原命令 native_identity_json、strong_keys_json、dispatch 状态和 version 不因回报重写。后来学习的 venue_key 进入独立 alias 表，与全账户唯一 strong-key 索引同事务登记；v4 校验区分初始键与 learned alias 的双向对应。原 begin_dispatch/finish 精确身份合同不变，DISPATCHING 期间学习 venue key 后，原 finish 仍必须成功。

### 14.3 关联与原子应用

公开内部接口 ingest(fact)、reconcile_pending(limit=...)、position(strategy_scope, instrument)、read_events(strategy_scope, after_sequence, limit)、pending(limit)，返回冻结结果或不可变副本。返回包含 disposition（ATTRIBUTED/UNATTRIBUTED/CONFLICT）、fact_digest、strategy_scope/事件 sequence（可空）、applied（仅本次新增成交是否入账）、reason（有限码）；不报告权限、场所终态或解阻成功。读取只体现该库已知投影，不宣称初始账户基线已建立或真实可平容量。

关联只查询耐久 strong-key 索引：命中多个 reservation、原命令 native route/请求 symbol 不匹配或提供的 binding_keys 未全部属于该命令时，不按某一首命中猜归属，记录有限冲突/未归属原因。binding_keys 不能从已知场所键反向学习。只允许已强匹配的 ORDER 追加未绑定 venue_key；已属其他命令的别名不能覆盖。只有原命令已有派发身份（DISPATCHING/SENT/UNKNOWN/NOT_SENT）才可归属，NOT_SENT 后出现实际回报保留矛盾并不自动重发。缺强键或尚未学习场所键的成交持久为 UNATTRIBUTED，不能自动归 external。

成交唯一键为 account+route+规范 trade_key。trade_key 必须由 provider/SDK 按原生作用域提供；本轮不把旧 DirectExecutionEvent.dedup_key 当此合同，不在 Gateway 硬编码交易所字段。强归属且经济字段完整、与命令 symbol/side/明确 offset 一致的成交，以买为正、卖为负更新所属策略/合约净数量；同一事务写原事实、成交唯一记录/应用标记、净数量和策略事件。累计订单 filled 数量只保存观察历史，绝不代替逐笔成交增加净仓。请求量本身不入仓；不借账本净额推断可平、费用或成本。超出请求量的真实逐笔成交不裁剪，保留异常诊断并按实际数量记录。

同成交键和相同经济摘要重复不得再次入仓/发策略成交事件。相同键但不同经济摘要先保留冲突审计，既有已应用数量不改写，新增矛盾量不自动叠加，返回 CONFLICT；原内容重放不能清除冲突。首次未归属后可在 reconcile_pending 的有界单事务批次中重新按已学习强键关联，并且只应用一次；原未归属事实仍保留追踪。一批最多 256 项，容量满先拒绝新事实且不淘汰幂等记录；重复已知事实应仍可读取/识别。

策略事件只由确定归属生成；ORDER/ERROR 保留不可变状态观察，不宣称最后接收就是真实最终状态。迟到成交和相互矛盾终态不得因既有终态而丢弃。完整状态归并、独立 UNKNOWN 原因解除和 BT 修订通知仍按后续合同接线，本轮不更新派发结果来伪造它们。读事件按全账户单调序号过滤指定策略且有界；此内部存储接口未提供 RPC/认证或 ACK，不表示跨策略网络可见。

v4 重开须检查完整 sqlite_master 白名单及 DDL，拒绝额外触发器、表或索引；并校验事实规范映射/摘要/容量、成交与事件引用、别名的强匹配订单来源，以及策略合约净增量与已应用逐笔成交的精确重算相等。损坏拒绝而不自动修表、改量或消除冲突。该启动审计不等同于外部备份真伪或恶意外部写者防护。

归属一致性补充：已归属 fact 的全部 identity_keys 必须在耐久索引属于同一 reservation；只有 ORDER 当前准备同事务学习的 venue_key 可是唯一未绑定键。非 ORDER 含未绑定键（包括尚未学习的 venue），或 ORDER 含其他未绑定键，先保留 UNATTRIBUTED，不入仓、不发归属事件；学习后再核对全部键并归属。避免先以会话 A 入仓、之后将同一未知场所键学给 B，形成有效写入但无法重开的矛盾。

容量与累计量补充：执行 meta 同事务维护 fact_count，重开再与实际行数/上限核对；新增事实加一，重复不加。每 reservation 的累计绝对成交量独立存为同库投影，与逐笔应用原子更新，overfill 比较不逐笔重扫历史；重开按已应用成交重算相等。单笔仍最多 36 位整数，累计量允许 42 位整数（最多 100 万事实），策略净量上限仍 36 位；均使用精确 Decimal，不用 SQLite REAL 求和。

binding_keys 限定为原派发强键中的会话/客户端锚点；不能将后来学习的 venue 当作新的原始会话绑定来使用。


## 15. R12：原生回报查询、精确投影与预留事务准入

本轮并行范围由主代理冻结；仍不代表完整启动恢复、实时回报或策略消费已接通。

1. CTP 成交回调在进入 Python 栅栏后捕获接收来源，拍摄字段时在同一锁内复验精确 API/SPI 和会话字段，原生 getter 重入后再核验。监听器在锁外执行。此机制不证明进入 Python 之前的原生延迟来源；原生 TradingDay 与接收连接代际分开保存，旧无来源私有 helper 只保留原 synthetic 用途。
2. 新查询 reader 只能借用同一个已登录 TD，在固定 owner 线程读取 orders/trades；不自动连接。每一查询独立核对封印、issuer、账户/日/代际、API/SPI 来源、完整无过滤请求意图与原生回读、成功终包、无超时/迟到/截断、TTL 和整批行摘要。未知合约保留给投影层显式失败，外账户/外日或不可冻结行使整批失败，不静默删行。
3. 查询成功后保存一个有界、不可变本地 batch ticket。assert_current 只检查精确 ticket、来源、当前会话和 TTL，不逐笔重扫整批；合法 owner 的失败新读取撤销旧 ticket，错误线程不修改 owner 状态。两次顺序查询不宣称原子账户快照或场所历史完整。
4. CTP 纯投影只解释原生字段，来源由调用者先核验。原生 TradingDay 必须明确，禁止用当前登录日补写；原生 Order 的 FrontID/SessionID/OrderRef 形成绑定身份，交易所/OrderSysID/日形成场所身份。Trade 缺少会话身份时不把 OrderRef 升格为强键；SDK 使用已有统一强键编码，provider 不依赖 SDK/Gateway。CTP trade_key 明确包含原生交易日、交易所、合约及成交号，不能只把交易日放到事实摘要。数量保留整数精度，价格按收到的 CTP double 规范十进制化，不声称恢复收到 double 前的精度。
5. SDK 接受统一 AccountKey；其账户/经纪商/环境须匹配已验证 reader，account_key_id 须精确等于 ledger.account_scope，合约场所须属于该账户 realm，空批也不能绕过。SDK 在入账前验证整批投影与合约目录，再逐条写入 R11 同库 ledger；写入前后核对来源。逐条事务失败允许存在已提交前缀，调用整体失败，重读幂等，不宣称整批单事务。未知归属仍保留 pending；成功处理查询不自动解除 UNKNOWN 或开放账户写入。
6. journal 新预留可注入只在本地执行的 reservation_fence。新记录在同一 SQLite 写事务中进入 fence，并保持到提交/回滚结束；原 principal/摘要/载荷一致的幂等记录先返回且不续 TTL。准入进入前的精确拒绝可映射 ADMISSION_DENIED；提交后或退出异常保持不确定，不能回复“未预留”。锁顺序为 journal 写事务后进入本地 gate；持 gate 的更新者不反向获取 journal，也不得在 fence 内进行 native/network 调用。
7. 本轮不改变 service 的默认交易能力，不把挂点当成已接好的启动恢复 gate；BT、实时 callback 持久来源、external 基线、完整事件 ACK/撤单/控制面及真实账户验收继续保持各自未完成状态。

## 16. R13：回报接收、owner 入账与策略消费进度

本节冻结本轮实现合同；完成情况以随后归档的审阅和实际测试为准。沿用单账户、单交易 owner、同一个原生 TD 和原命令 SQLite，不增加策略调度器。

1. CTP 在 GatewaySession 所有的全新 request feed 创建 Trader 后、start 前安装有界回报缓冲。普通 direct 未选择此来源时保持原路径。订单、成交和报单/撤单错误由原生回调在同锁内核对精确 API/SPI、进入 Python 时的接收会话，并在 getter 拍字段后再次核对。接收交易日、代际和原生行的 TradingDay 分开保存；不借当前登录信息补写原订单身份。无来源的 synthetic helper 不得成为此原生入口。
2. 缓冲的生产者可来自回调线程，消费由构造 owner/PID 执行。记录冻结、有字段/字符串/总字节/条数上限；溢出或来源/快照失败保留已有记录并设置不能由 ACK 消除的 gap。offer 只发行一个精确批次 ticket，追加不使其失效；未 ACK 重取同一前缀，ACK 只移除全部已确认前缀。不得使用先弹出再入库的语义，不声明内存缓冲具备进程崩溃耐久性。
3. Session 公开受检的同 Trader 查询 reader 工厂和回报缓冲入口，SDK 不直接借用私有 Trader 或创建第二 TD。reader 换代须显式重建，旧 ticket 不跨代复用；来源标签和 DTO 本身仍不是网络认证或账户权限。
4. SDK trading owner 在原 guard/journal 上构造执行账本。显式配置可信合约目录和有界查询预算；启用写入必须配置回报维护。订单/成交批次先完整投影，再逐笔耐久入账，全部成功后才 ACK；失败保留整批，重放依靠同库去重处理已提交前缀。未实现解释合同的错误回报保留待处理并阻止新派发，不伪装为订单拒绝或丢弃。
5. 查询维护逐次执行同代完整 orders/trades，失败与换代撤销本轮查询完成状态；只读重查有间隔，不自动重报订单。每个维护 tick 最多一个重查询阶段，账户读与回报查询公平轮换；回调消费和 pending 关联分别有界。查询不得在 SQLite 事务内进行。
6. 新预留使用 R12 本地事务 fence，在首次维护前关闭；缓存的维护状态不等于实时原生截面。派发 owner 再核验当前会话、回报缓冲和完整查询状态，同时保留既有结算与调用方准入检查。查询成功不建立 external 初始基线、不单独证明可平/资金、不解除业务 UNKNOWN，也不把其他组件的风险批准强加为 Gateway 的默认职责。缓冲 gap 不得因空查询或 ACK 自动消除。
7. 执行事件消费进度与事实留在原命令库，schema 显式升级至 v5，新增按 account/principal/consumer/strategy 隔离的有界消费者表。v4 普通打开拒绝，显式升级先严格验证旧 DDL、对象、锚点、全部原内容及 guard，在同一事务升级；v2/v3 显式入口直接到新版本，中断回滚，原事件/命令/事实不丢失。
8. 流 epoch 由原 journal_id、账户和策略稳定派生；事件仍使用原全账户 sequence，各策略序号允许间隔。正向 resume 必须属于该消费者已经 offer 的本策略事件，ACK 不得超过已 offer 范围，旧 ACK 幂等且不倒退。分页计算完整响应大小后才能提交 offered 进度，首条放不下不得创建/推进消费者。丢回复允许重读，不以服务器准备回复作为客户端已持久处理的证据。
9. 消费进度写入不改变命令/事实 revision，也不删除历史或伪造快照。消费者接口是同进程受信存储 API，不能据此声称 RPC 已认证、guard 当前有效或 BT 已持久消费。网络 ACL、客户端本地投影与游标原子保存、ACK RPC 接线仍须分别交付验证。

审阅补充：消费页必须显式传入可信 result_fits 回调，不能缺省视为通过。纯本地调用方可以明确选择不设序列化预算，网络装配则必须检查完整响应封装。空页不创建消费者，也不要求 ACK。OnErrRtnOrderInsert/Action 的错误对象缺失或 ErrorID 为零是未知/矛盾信息，应保留 gap，不能套用正常 OnRsp 的成功省略规则。

来源与日切补充：reader 的当前会话校验可独立于查询 ticket 执行，只证明当前精确来源。当前已验证回调源携带的合法历史原生 TradingDay 可按历史日期入账，不得换成接收日；未来日拒绝并保留待处理。旧来源的未 ACK ticket 不因此获准跨代消费。已验证同 Trader、同账户的重连可先失效账户读模型，再重新绑定并重查；无法证明来源、账户或 Trader 一致时仍拒绝，查询成功不替代完整日切恢复。维护异常及清理开始时先关闭新预留 fence，清理失败保留资源也不能留下开放的缓存准入。

同 native 重绑定须由 provider 在原 Trader 同一状态锁内完成旧 API/SPI 核对、新 reader 构造及最终复核；SDK 不能用两个分开的调用替代该原子工厂。reader 当前 scope 同时绑定 FrontID/SessionID 和原生会话对象，数值 generation 不变不表示登录身份不变。普通暂时断线尚未形成可信新登录时仍可能沿原路径停止 owner，不能把受检登录更新称为完整网络重连恢复。


## 17. R14：同库策略事件的认证网络读取与 ACK

本轮主代理冻结以下合同并划分互不重叠的实现范围。目标是将 R13 的账户 owner 账本接到现有独立 Gateway/ZMQ 服务和 SDK 客户端；不把 RPC 通过当作 BT 投影持久化或完整恢复验收。

1. 复用 service.direct_write / broker.direct_write，新增独立操作 direct.events.read_after、direct.events.progress、direct.events.ack；这是策略事实消费，不授予下单、撤单、业务风控或账户全量读取权限。新操作必须显式 requested_operations 选择，旧客户端缺省注册集合不扩大。静态资源 operation grant 和每次 Registry 身份、scope、lease 检查继续执行；可显式用于停止 run 的只读恢复，ACK 不加入交易 WRITE_OPERATIONS。
2. 认证只接受无 delegate 的 STRATEGY_CLIENT，principal 与 Registry context 一致，actor 等于静态策略，完整 execution_domain/account/strategy 与服务端配置一致，run 非空且其他组合 scope 为空。策略从服务端授权表确定，不接受客户端传 principal、strategy 或 consumer。consumer_ref 稳定绑定协议版本、角色、principal、actor、空 delegate、execution_domain、account、strategy，不含 run/registration；不同主体独立，重注册同主体保留消费身份。算法由 Base 唯一共享 helper 提供。
3. 同一账户 owner 只构造一个 ledger。读取事件时在原 SQLite 事务内取得每项归属的 request_key、reservation_id、command digest 和原 command principal，不在响应阶段另查猜测绑定。Gateway 的内部事件返回增加这些元数据；同 PID 的精确 journal 绑定检查不表示 guard 权威或网络授权。旧 ingest/净量/同库游标合同不变，不新增事件数据库。
4. Base 新增 gateway_execution_stream_protocol，提供严格有界公开 DTO：GatewayExecutionObservation、GatewayExecutionStreamEvent、GatewayExecutionStreamPage 和 GatewayExecutionStreamProgress，页与进度绑定既有 GatewayCommandBinding（principal 指消费者）及 consumer_ref/epoch/offered/ack。事件携带 sequence、原请求键、预留号、命令摘要、原命令主体、fact_digest 与 observation。observation 只含中立交易字段；native identity 仅公开其规范 JSON（ensure_ascii=True、sort_keys=True、紧凑分隔符）的 native_identity_digest，不转发可含任意字段的 identity.fields；identity_keys、binding_keys、venue_key 和 trade_key 只公开 SHA-256 摘要，字段明确命名为 identity_key_digests、binding_key_digests、venue_key_digest、trade_key_digest；不公开原强键、原逐笔键、source_ref 或接收 session_generation。数量/价格复用原 Base 严格合同，公开摘要不重建原生身份；框架可按原 request_key 从既有 command_status 获取原派发身份，本事件元数据足以关联原订单意图。不输出原始 provider payload 或错误文本。所有确定性摘要仅作关联标签，不承诺匿名化或抗枚举。fact_digest 是原服务端事实的标签，不能由删减后的公开 observation 反算或视为来源证明。
5. page/progress schema_version=1，from_mapping 拒绝未知字段/非精确类型/非法摘要/超限；最多 256 项，sequence 严格递增但允许间隔，事件 account 必须匹配 binding，ack <= offered 且每项 sequence <= offered。历史重放页的最后 sequence 可小于已有 offered。原命令 principal 可能与消费者不同，不据此扩展授权，仍只返回确定归属本策略事件。
6. read_after 参数精确为 after_sequence、expected_epoch、limit；progress 参数为空；ack 参数精确为 sequence、expected_epoch。after_sequence=0 可无 epoch，正向 resume 要求已 offer 的本策略原序号和正确 epoch，沿用 R13。回复为 status=OK 加 page 或 progress，明确的请求前置拒绝为 REQUEST_REJECTED 加有限 code；提交后错误和传输不确定不得伪装为未推进或 ACK 成功。
7. 服务端将候选页转换为最终公开回复后，在原 cursor 事务内调用 Registry context.result_fits；检查必须存在，覆盖完整 envelope 和传输封装及客户端/服务端最小字节预算。首条超限不创建/推进消费者，适配为 REPLY_TOO_LARGE；SDK runtime 为新读取自动传本地接收上限。进度/ACK 的有界回复也检查预算；任何提交后最终发送失败仍允许按原 cursor 重读/查进度，不自动推断客户端消费完成。
8. SDK 使用独立 GatewayExecutionStreamClient，复用精确 ThreadedServiceClientRuntime 与 GatewayClientRoute；不创建 native、第二运行时或 direct fallback。read/progress/ack 返回受检 DTO，验证绑定、稳定 consumer、epoch、序号和页范围；不假定策略内连续序号，不自动 ACK，不自己建立 BT 状态或另建游标库。调用方须先持久保存投影和 cursor 再显式 ACK；本轮仅客户端端口，不宣称调用方已完成该事务。
9. 事件读取拥有独立于交易准入的服务生命周期：未配置 return_settings 不广告事件能力，不能借旧 account read 冒充。owner 构造并注入受限 stream service；关闭先永久关闭 stream 入口再清理 journal/guard。读请求与 close 在进程内锁下线性化，fork/PID 检查先于锁，不在该锁内调用 native，也不使 owner 的入账锁序反转。允许读取当前服务已保存的历史事实，不将连接/查询健康当作其交易可用保证。
10. 必需检查包括严格 DTO/脱敏、两主体两策略隔离、夹杂序号 1/3、显式授权/恢复注册、实际 CURVE/Registry 跨进程读取与 ACK、完整回复字节上限及首项超限无进度、提交后丢回复重放、换 run 同 consumer、epoch/非法 ACK、owner 关闭竞争、原 direct/account read 回归。CTP 错误的原生 RequestID 当前在派发标记后产生、撤单尝试无耐久绑定，继续保留错误 ticket/UNKNOWN；不使用接收日/会话补原始订单身份。本轮不新增 BT 架构改动。


R14 审阅修正：新事件 read_after/ack 分别会持久推进 offered/ack，必须进入既有 MIG03 的 cursor 写入栅栏；它们仍不属于交易 WRITE_OPERATIONS。progress 不触发持久变更。停止 run 的事件恢复提供显式 events-only 操作集，不强行携带 release，避免读取另一个 run 的历史时误争用交易写 claim。

生命周期修正：短锁只标记关闭和登记在途读取；关闭后永久拒绝新请求，并在总关闭预算内等待在途 drain。无法及时 drain 时保留 journal/guard 和准确资源句柄、报告关闭未确认，后续可重试；不得为满足超时先释放 guard。读事务不持生命周期锁执行 SQLite/预算回调，完成时通知 drain；维护入账不反向申请读取生命周期锁。


## 18. R15：原生撤单尝试先准备再持久派发

目标是闭合远端真实撤单，继续复用原交易 owner、同账户命令库、SDK 写入准入和 CTP 原生栅栏。`direct.release` 仍只释放未派发预留，绝不解释为场内撤单。先交付下述前置合同及实现，再接同 owner RPC、客户端和回报；前置通过不能宣布远端撤单或 BT 交易入口可用。BT 产品边界仍按已批准限定申请。

1. Base 新增 `direct_cancel_protocol.PreparedCancelRequest`，字段固定为 `reservation_id`、`target_identity`（精确 NativeOrderIdentity）、`symbol`、`trading_day`（本次派发日）、`session_generation`（本次派发代际）、`request_fields`（有界不可变扁平 str/int/bool/None 映射）和 `request_keys`（有界、非空、无重复的 provider 强尝试键元组）。提供严格版本 1 mapping 往返与规范摘要；DTO 不证明来源或权限。目标原订单日只来自 target_identity，本次派发日不能覆盖它。字段/条目/字节/数字边界与现有 Base 合同一致，拒绝 bool 冒充整数、非规范键、额外 wire 字段或构造后篡改。
2. 现有 `PreDispatchRecord` 仅增加末尾可选 `prepared_cancel`，缺省保持原格式；存在时必须是 CANCEL、目标/symbol/route/当前 generation 与准备记录完全一致。`to_dict` 仅在非空时增加该字段。SDK 新增显式 `DirectWriteCoordinator.cancel_prepared`；仅调用 provider 的 `prepare_cancel_order(target, symbol)`、`submit_prepared_cancel(prepared, grant, verifier)`、`release_cancel_reservation(prepared)`。不按对象碰巧有方法改变旧 cancel 路径，不回退未准备的 cancel。流程为 prepare → 验证 → host durable commit → 代际复核/issue grant → 单次 submit；commit/授权前失败释放未发准备项，进入 native 后异常保持 UNKNOWN。原 target/symbol、准备项及持久 marker 必须一一对应。
3. ## 19. R16：远端取消的独立授权、持久请求和客户端恢复

7. 来源重置检查、描述与 epoch ACK 仍由原 provider 判断。Hub 维护调用的 reset、ACK 和 unsubscribe 均为非阻塞：沿用同一 retained future，pending reset/ACK 报明确 pending，unsubscribe 返回 False 并保留原 handle；不能在每 key/每次维护内分别等待 native owner。ACK 保留原 epoch，下一次 reset 检查先解决该次 ACK，再查询当前 provider，不能在旧 ACK 未决时令 Hub 重复生成新 epoch。异步 reset 的完成结果消费一次；零等待探测不等于正等待超时，完成结果超过 call_timeout_seconds 未被消费则重新查询，原 provider 的 poll 仍逐次检查真实 source scope。pending 控制或出队无法安全解决时 Hub 不继续 poll；确认 source reset 时丢弃旧源缓存，再允许新 epoch 数据。describe 的正等待超时结果须解决后重新查询当前 owner，不据旧结果延长来源有效性。单独订阅/描述请求仍有原有限等待；本节不承诺抢占任何运行中的 native 调用。

## 25. R23：异步行情引导与同线程续办（本轮局部验证通过，整期未验收）

本节关闭目标为 E043 的默认 CTP Gateway 初始化阻塞；R22 已在真实回环 Host 上复现单项 bootstrap 等待 native MD start 会使另一主体的状态查询超时。以下为本轮已确定的实现合同，不能作为已通过证据。BT 产品不在本轮改动范围。

### 25.1 原生 owner 的非阻塞取得接口

SDK 的既有 GatewayOwnerMarketProvider 新增 begin_subscribe、subscription_ready、probe_source。begin 仅在原 native owner 有界队列提交一次并立即返回逻辑 handle；ready 和 probe 的 future 检查均不正等待。pending、active 与不确定的同 key 不得重复创建。probe 保留原 key/generation/stream/epoch 和完成时刻，None 表示尚未就绪，不能据此 release 后重建。旧 epoch、已过期或旧同步等待超时结果先解决再重新查询，不能重标来源。

其他数据维护不得偷取并丢失 descriptor，也不得因一个已取消的订阅消费者留下 descriptor 而永久挡住仍在共享的消费者。需有界保留原结果及其参数；reset/ACK 的事实与消费边界保持原合同。最后一个 ref 的释放仍依原 nonblocking unsubscribe；未确认就保留原 handle。只有已确认 whole-provider close 可以清除未知取得。

Gateway 仅在三个可信方法全部可调用时发布异步能力；部分实现拒绝。普通同步 provider 保留原合同，但不得被称作非阻塞 provider。异步实例的旧 market.subscribe 和 market.bootstrap_many RPC 在 provider 副作用前明确拒绝 ASYNC_BOOTSTRAP_REQUIRED，不能留下生产同步旁路。低层 Python 旧同步接口不作为默认服务入口。

### 25.2 注册范围的稳定操作身份

新增 market.bootstrap_begin、market.bootstrap_status、market.bootstrap_cancel。begin 参数为 operation_id（32 位小写十六进制）、subscriptions（1–20 个唯一 key，可逐项要求 source descriptor）及可选 refresh_existing 布尔值（默认 False，并入规范 payload）；status/cancel 仅接受 operation_id。身份键是认证 registration_id 与 operation_id，不能由请求伪造主体。

同 ID、同规范 payload 重取原任务；同 ID 不同 payload 拒绝。status 的 not_found 不证明请求未发送，客户端仅能在原绑定下以原 ID/内容恢复查询或重试。cancel 未知 ID 创建取消墓碑，拒绝晚到 begin 重新取得。服务重启/注册变化按现有 service epoch 与恢复合同处理，不能把内存任务表当作跨代持久日志。

状态及字段为：pending / not_found 含 operation_id、status；active 另含旧 batch 的 items；cancelling / cancelled / rejected 另含有限 code；unknown 另含 code、uncertain_stream_ids。cancelled 需要本任务独占资源已确认释放或共享资源中本任务已无 ref；不确定清理不得伪装成已取消。

### 25.3 有界任务与 ref 生命周期

默认每注册最多 16 个任务、全服务 128 个；pending 与终态均计入，不能为接纳新请求静默驱逐旧 ID。仅注册退出且相关清理确认后才移除。默认 startup deadline 为 30 秒，查询和重试不延长；期限检查先于 readiness 暂停，发布暂停不无限延长任务。每次维护最多推进 32 个有界步骤并轮转各任务。结果缓存总上限 32 MiB、单结果受已有 wire 上界限制；没有容量必须取消本任务，不能无限缓存。

取得前完成整批 ACL、重复 key、既有 active/pending 重叠及容量预检。pending refs 必须计入容量、防止提前释放上游，但不代表可投递或已完成的订阅。共享 key 复用同一 handle/generation。取得有效且请求了来源描述时 descriptor 有效才转 active；未请求时不强制 probe 或伪造 descriptor。每个 ref 需本任务唯一 owner token，旧任务取消不得删除同注册/key 的后来订阅。

恢复或重授权刷新可显式 refresh_existing=True，借用同主体/注册的已有 active ref 原 token 来取得新的 snapshot/head 及按请求取得 descriptor；不增加 refcount、不换 token、不建立或释放上游。pending refs 与没有 async token 的旧 ref 不可借用。新任务取消/回滚只清理自身新取得项，不清理借用项。单 client 的 active close 仍只 unsubscribe 原注册/key，不能取消其原多 key batch 来恢复或关闭一个成员。

active 结果已通过完整回复预算并准备返回（offered，不证明客户端收到）后，其中一个 key 退出/变代不能因重读状态而自动释放其它成员。旧缓存不可重发时保守返回 BOOTSTRAP_STALE 的 unknown，保留仍持有的相关 refs；确认无本任务资源后才可 cancelled。显式 cancel 原任务才清理其自有剩余 refs。尚未 offered 的原子 batch 保持整体回滚。

撤权、注册从真实 active 集合消失、超时、部分批次失败和 close 均取消原 refs；失败清理保留原 handle 与不确定状态。已 active 缓存每次输出前复验当前 ACL、ref token、epoch，撤权再授权不复活旧任务或旧缓存。快照继续传认证 principal_ref，保留 E044 授权水位。fresh begin 在任务、ref 或 provider 副作用前必须提供可调用 result_fits，否则有限拒绝 REPLY_BUDGET_REQUIRED；受信无 wire 的本地调用者也须显式选择检查器。任何 active 输出都必须经过完整检查；缺失检查器不设置 offered、不丢弃原任务。初次 active 必须通过含外层字段的完整 result_fits 与缓存预算，失败回滚；后来较小回复预算只拒绝当次回复，不重做已完成任务。

### 25.4 客户端状态机与续办

SDK 在第一次发送前固定操作 ID、原绑定及完整 payload，先创建全部 SUB，再发送 begin。一次 step 最多一个控制 RPC及有界验证；pending 保留原任务，丢回复不换 ID、不回退旧路径。来源校验必须先于任何 snapshot 消费。可能发送后的绑定/代际变化保留原注册清理不确定态并进入恢复；明确未发送时仅回滚新本地资源，不能虚构远端 UNKNOWN 或退订旧引用。关闭/取消沿原 ID 推进，未确认仍 close_failed；不能通过无限等待 native 来关闭。

恢复用的新 SUB 先创建，旧 SUB 的关闭尝试和确认按实际对象保留唯一清理责任；仅未发送且从未尝试关闭的旧 SUB 可原样恢复。已尝试关闭的对象不可恢复为可用，确认关闭后不得重复关闭。明确授权拒绝仍锁存授权中断，须重新授权并按水位恢复；清理后允许同一客户端创建新 SUB 重试，不复活已关闭对象。

原始 ServiceMarketClient 的同步便利方法可使用同一状态机并在等待间维护 runtime；策略 Gateway owner 必须使用 step 续办，不可在 owner 内循环 sleep 等待。start、恢复和重授权重新订阅需复用这个机制；尚未闭合的恢复分支保持明确不可用，不得经被禁止的同步 subscribe 旁路假称成功。

ThreadedServiceClientRuntime 支持可信本地 OwnerOperationContinuation(resume, delay_seconds=0.01)。回调不是 wire/JSON 参数，仅 extension.invoke 或前次 resume 可返回。原 handle 保持 running；所有步骤在原线程执行，每步间维护租约并公平处理其他请求。continuation 的形状/回调/有限正延迟每次都重新核验。所有 deferred 项计入等待队列容量；沿用旧语义，最多是 queue_size 加唯一运行项的有界总数。超时重取原 handle，取消只适用于尚未开始的 queued 项。

关闭/维护故障将已 yield 未完任务终结为 OWNER_OUTCOME_UNKNOWN；初次 invoke 在 stop 后才返回 continuation 也同样处理。旧同步 invoke 直接返回已获得的最终 JSON 结果语义保留，不能概括为所有已开始调用关闭时均丢弃结果。extension 原资源清理与失败保留合同不变。

### 25.5 能力、授权和验证边界

所有 SDK/Host 静态市场词汇及实例能力声明同步新三项。普通 raw runtime 在 requested_operations=None 时不默认增加新三项；Gateway 市场设置默认显式请求它们；显式选择旧同步五项时原样保留，新异步三项若被选择必须齐全，不得自动补入显式操作集。旧显式 grant 不被自动扩大，新请求缺授权由 Registry 明确拒绝。new fresh begin 在 Hub not ready 时创建有界 rejected 任务并保留规范 payload，不调用 provider；同 ID 重复和冲突检查仍稳定。同 ID 旧任务的 begin/status/cancel 仍由原任务处理，外层不得以无 operation_id 的 MARKET_NOT_READY 假称原资源未发生或阻断清理。非异步实例不得虚假广告新能力。

验收必须包含：原生订阅/descriptor 被事件阻塞时 Host 状态和租约可前进；策略同 owner 中其他请求可前进；同 ID 丢回复、共享取得、取消在 begin 前到达、部分回滚、过期/撤权/重授权、旧任务不删新 ref、来源未来消费交错、容量/公平、完整响应预算和清理不确定。源码、合成进程与隔离安装分别记录；原生账户与整期验收不由本轮通过替代。

### 26.1 单文件升级与水位

GatewayPendingHost.upgrade_for_execution 显式将已有 v3 无损升级为 v4，保留意图、原生身份、取消计划与旧标记。执行区记录 consumer_ref、首次固定的 epoch、单调 revision、stored_sequence、applied_sequence、acknowledged_sequence、原始事件和投影快照。三个水位必须满足 acknowledged <= applied <= stored；接收成功不能等同应用成功或发送 ACK。旧 v1/v2/v3 路径保持原行为，不自动升级或降级。

默认最多 10000 条事件、事件内容 32 MiB、投影 16 MiB；显式上限分别不得超过 100000、64 MiB、32 MiB，均拒绝 bool 和非正整数。旧事件、成交去重内容及终态关联不自动淘汰。容量不足拒绝整次变更，磁盘保持原状。所有状态变更复用现有锁内重读与原子替换；不新增数据库、锁协议、策略调度器或后台 ACK。

检查点读取返回脱离磁盘对象的快照。ingest_execution_page(page, expected_revision, after_sequence) 的低层调用方必须保证 after_sequence 来自这次实际读取；stored 只推进到最后实际收到并持久保存的事件，不能推进到服务端 offered 水位，允许策略事件序号稀疏。空页不越过任何事件。原页精确重试幂等；非已知重试必须从当前 stored 读取并匹配 revision。epoch、主体、账户或 ACK 超过本地 applied 时整页拒绝。

### 26.2 SDK 实际读取上下文

SDK 新增不可变 GatewayExecutionReadContext(binding, consumer_ref, after_sequence, expected_epoch, limit)，仅成功校验的 read_after OBSERVED 页面结果携带 request_context。字段来自实际客户端和调用参数，不从回复猜测。after 必须为非 bool 的 [0, 2**63) 整数，limit 为 1–256，非零 after 要求明确 epoch；epoch 与 consumer 复用当前合法格式。progress、ack、未发送、拒绝和 UNKNOWN 结果不携带该上下文。

BT 的 ingest_execution_result(result, expected_revision) 使用此上下文，拒绝错误类型、非 OBSERVED、缺失上下文、夹带 progress/code、绑定/consumer/epoch/limit 不匹配及错起点。此生产接入入口不接受另传 after，防止实际读取 after=100 后被调用方错当成 after=0 的稀疏页。上下文是 SDK 受信调用链的请求关联数据，可构造的 DTO 本身不是密码学证明或 provider 授权。

### 26.3 原命令关联与去重

每条事件必须关联宿主已持久化的原意图和命令观察，精确核对 request_key、reservation_id、command_digest、principal、account、合约；合约按服务端既有合同以 instrument.native_symbol 匹配请求 symbol，不假定规范 instrument_id 与原生符号相同。交易所 route 取自 record.native_identity.exchange_name，不能拿 RPC route 替代。原生身份尚未落盘时整页拒绝，调用方先按原请求身份查询并保存 status，再重读原页，不提前移动游标。

binding_key_digests 必须是原命令 strong_identity_key_digests 的子集，复用 Gateway 原始绑定键的语义。完整 native_identity_digest 可以因原生字段补全而变化，identity_key_digests 可以包含已学习的场所别名，故不能要求它们与最初准备身份完全相等。公开摘要仅为关联标签；本地没有 prepared 原文时不假造其验证。

相同序号必须有完全相同的规范事件内容；相同 fact_digest 不得改变关联或内容。成交键按 account、route、trade_key_digest 定域，同键不可归属另一请求或 reservation；数量、价格、方向、开平、合约、交易日及 venue_key 的经济内容冲突整页拒绝。相同原命令、相同经济内容的另一个事件序号可保存，后续真实投影须按成交键去重。缺失经济字段不补零，不假设费用为零。取消归属必须匹配本地原取消计划及目标；已保存取消回执时 attempt_id 也须一致，缺失回执不证明取消结果。

### 26.4 投影提交、ACK 与恢复边界

commit_execution_projection(through_sequence, projection, expected_revision, expected_applied_sequence) 同一次原子替换保存快照和 applied。through 必须为已存事件序号，不能回退；双重 CAS 防止并发旧投影覆盖。同水位重试以规范 JSON 字节判等，不能用 Python 的 1 == True 或 1 == 1.0 语义。快照严格为有限 JSON 的 {schema_version: 1, state: {...}}，有深度、容量与敏感键限制；state 是后续 BT 投影者拥有的版本化内容，不证明完整框架状态。

只有调用方完成上述耐久提交后才可显式调用 SDK ACK；record_execution_ack 仅记录精确 binding、consumer、epoch 的服务端进度，不允许超过本地 applied。ACK 丢回复按原 epoch/sequence 重取，不生成新事件或重复应用。写入前失败、替换后报错、重开与两个宿主交错必须保留幂等和水位关系。

identity.py 仅扩展已有归档前状态检查以识别 v4 意图、取消及 stored > applied 或 applied > acknowledged，不从不透明快照推断空仓。跨目录状态归档并发 E020 仍按独立调整申请待定，本轮不修改其锁协议。现有 managed paper 恢复器依赖专用 manifest、receipt、来源时钟及成交合同，不能把 Gateway 回报包装为模拟成交证明。

验收包括旧 live_state/direct 回归、明确升级、稀疏与空页、关联拒绝、原页重试、冲突/容量、严格 JSON 类型、原子失败恢复、CAS，以及独立 Gateway 进程和真实 ZMQ/CURVE/SDK 的合成事实联调。源码和隔离安装分别记录。真实 Broker 投影、三策略进程、账户、跨平台和整期验收继续保持各自未完成状态。

## 27. R25：真实框架对象快照与恢复

状态：2026-11-09，本轮局部源码及隔离安装验证通过，整期 IN_PROGRESS。本节在已批准的 Broker/pending 接线范围内实现真实 BT 对象的编码和恢复，不修改核心 Order、Position、Trade 算法。Strategy 通知前后的新钩子另见[限定调整申请](Backtrader-Gateway通知持久化钩子调整申请-2026-11-09.md)，批准前不实施。快照编解码本身不等于完整事件消费者或 E023 已关闭。

### 27.1 显式对象集合与稳定关联

Broker 私有模块提供 capture_framework_state，输入为稳定 key 到真实 Order、Position、Trade 的映射，以及受信 data_by_ref、owner、broker；输出有精确 schema 版本的有限 JSON。restore_framework_state 接收快照及新进程的受信 data_by_ref、owner、broker、commission_for_data，返回 GatewayFrameworkObjects（orders、positions、trades、order_refs、trade_refs）。它不加载 provider、不执行网络、不推进游标/ACK，也不直接修改 Strategy 的交易集合。

所有框架对象引用须显式包含在集合中。Trade 历史中的 Order 可能是某次通知副本，与当前原订单同 ref 但具有不同状态及执行片段窗口；不能按 ref 偷换成当前原订单。缺失引用拒绝，调用方须把该准确副本以独立稳定 key 纳入集合。

同一业务 Order 或 Trade 的原对象与通知副本保持同组 ref，彼此仍是不同对象；恢复时为每组分配新的运行时 ref，并返回旧→新映射，不重置全局计数器。组内数据、方向、owner、tradeid 等不可变绑定必须一致。原框架 p、info、created、执行片段 deque 及 Trade history 的受限共享关系需显式保存并重建，不能以数值相等代替引用一致。

这里的“新 ref”指由当前运行时正常分配，不保证独立重启进程中数字与旧值永不相同。别名按真实对象图保存：普通 Order.clone 共享 info，而 BtApiBroker.notify 对 info 做顶层浅复制，内部容器仍可能共享。不同顶层 info、独立执行片段 deque 及其共享片段不因同 ref 被强行合并；也不把实际共享对象拆成相同数值的副本。info 支持有限 dict/list/tuple、AutoDict/AutoOrderedDict，以及显式集合内准确 Order 对象的受限引用；循环、集合外引用和任意对象仍拒绝。已存在的 fee_correction_ids 按可选 tuple 保留；order.broker 原为 None 时仍恢复为 None。同 ref Trade 已知 long=True/False 不可互相矛盾，尚未开仓副本的 None 可保留。

### 27.2 复用真实对象，避免重放旧成交

Order 保留参数、生命周期状态、created、executed、完整 OrderExecutionBit 及 p1/p2。捕获不能调用 clone 改变 pending 边界；恢复不能调用 execute、addbit 重新累计旧成交。BuyOrder/SellOrder 由已绑定且有 bar 的 Feed 正常构造，再按已验证字段恢复；owner、data、broker 和 commission 对象只从受信参数取得。parent/oco 通过同集合稳定引用解析，不从 JSON 反序列化任意对象。

Position 保留数量、价格、原价、adjbase、开平变化、datetime/updt 等实际状态，不调用 update 重算。Trade 保留开闭状态、方向、数量、价格、价值、费用、盈亏、开闭 bar/时间、复合 tradeid、historyon 和完整 TradeHistory；历史 event.order 指向正确恢复对象。不能限制为 managed paper 的单 FOK 开仓，也不能复用其 receipt 作为 Gateway 来源证明。所有 provider/费用/时间真实性仍由上游合同负责。

TradeHistory 时区取自相应受信 Feed，校验保存描述；Position datetime/updt 支持 naive、标准 datetime.timezone 固定偏移，或恰为受信 Feed 所持有的时区对象。后者保存 data 引用并核对偏移/fold；其他无法无损恢复的时区明确拒绝，不默默降为固定偏移。整数、bool、float、None 区分，有限 float 精确往返；不重算或修正已经保存的经济字段。

info 与其他允许扩展只保存明确支持的有限数据，非法对象或敏感键拒绝，不能静默忽略后声称完整恢复。无 pickle、动态类名导入或任意属性字典恢复。schema、对象/引用/共享组、枚举、数值和容量先验证，再返回完整新对象集合；失败不安装部分恢复状态。总 JSON 上限 16 MiB、节点 100000、深度 16，清单亦有有限上界；R24 外层投影限制继续生效。

手续费对象不从 JSON 构造。捕获时，非 None 的 order.comminfo 必须是当前受信 broker 对该 Feed 查得的实际对象；按对象身份记录共享组、具体内置类型、已规范化参数和影响经济计算的有效缓存。恢复先解析 commission_for_data，核对它仍是新 broker 的当前对象，再逐项比较参数、缓存和跨 Feed 共享关系，之后才创建框架对象。不得把同 Feed 的不同旧模型合并，或把 percabs=False 的已规范化费率再次换算。源码内显式支持 CommInfoBase 及现有标量型内置佣金类；OptionPremiumCommInfo 的规则快照/来源和任意自定义模型需要另外的绑定合同，当前明确拒绝，不能声称通用支持。后续完整 Gateway 若使用这些模型，须补齐相应合同及验证，不能以此局部端口的限制缩减整期目标。

### 28.1 查询源与原生生命周期

复用 CtpGatewaySession 的同一 TraderClient、API/SPI 与受信账户会话。新增静态合约规则查询不依赖 MD，也不修改旧的 MD 绑定 metadata reader。只接受明确的 MarketInstrumentKey、InstrumentID 和 ExchangeID，不退化为全市场查询。

本地 timeout/cancel 不等于 vendor 撤销；已提交查询的 native 槽须等自己的终包或会话失效，不能为下一查询提前释放。完成的 QueryResult 是原请求的历史终包证据，可幂等读取；complete 不证明来源现在仍有效。release 只释放终态本地句柄，不静默驱逐在途项。错误实例、伪造句柄、跨进程/线程均拒绝；待完成查询遇到失效会话不得继续派发，Gateway reader 在消费包括历史成功结果时仍复核当前来源与有效期。既有来源与 native gate 的状态锁临界区仍可能等待竞争线程，本节不承诺无锁或硬性单步耗时上界。

CtpGatewayInstrumentQueryReader 复核同一查询来源、过滤字段读回、完整终包、原始行摘要、会话和精确合约。不要求 instrument 行携带账户字段，账户绑定来自受信查询来源。拒绝零行、多行、错误合约、字段缺失与冲突。有效期保留现有查询证据从回调完成起最多 35 秒，不在 poll 或网络回复时续期。

### 28.2 限价合约规格和中立编解码

当前 Gateway CTP 提交支持限价单。本轮数量规则使用原生 MinLimitOrderVolume/MaxLimitOrderVolume，不能用固定 1 或市价限值替代。整数 lots 的 step=1、contract_multiplier=1、CNY 结算币种是既有 CTP 期货 provider 规则；VolumeMultiple、PriceTick、ProductID、ProductClass、IsTrading 等事实来自该次完整查询。这里只支持期货，其他产品明确拒绝。市价订单支持不由读取其限值而产生。

provider 返回封印观察及规范规则；SDK 构造既有 InstrumentSpec 和 Freshness，不把它包装为 ExecutionRulesSnapshot receipt 或写入就绪证明。保留真实回调 observed_at、disabled 状态、未知和失败，不补造实际费用、保证金或价格。原始私密行不传给策略。

SDK codec 使用精确版本化结构 {schema_version:1, order_type:limit, spec:{...}}，复用 InstrumentSpec 字段但 raw 必须为空。Decimal 用有界精确字符串，UTC 时间保留来源，严格拒绝 bool 冒充数值、非有限值、未知字段及超过 64 KiB 的结果。available=True 要求既有 InstrumentSpec 的完整核心数值规则与 64 位摘要；通用 DTO 的 max_quantity 可为 None，存在时须合法且不小于 min_quantity。CTP reader 则始终要求本次原生限价上下限齐全且有效，不能用通用可选字段绕过 provider 校验。unavailable 保留现有模型的空未知字段及明确 reason，不伪造 fingerprint。策略端解码不导入 CTP/native。

### 28.3 服务任务、授权和预算

在既有 account read 端口显式添加 account.instrument_spec.begin/status/cancel 三项，旧六项读取合同及旧请求权限不变。只有实际装配 source/service 的实例发布能力；新三项须显式完整授权和请求。默认联合 CTP profile 在配置账户读取时装配同一会话的 source，查询范围限于配置的 observation_instruments，且主体已有明确 account-read grant。

begin 参数仅 operation_id（32 位小写十六进制）和完整 instrument key；status/cancel 仅 operation_id。任务按 registration 与 operation_id 隔离，绑定不可变身份、scope 和合约；同 ID 不同 payload 拒绝，提前 cancel 保存 tombstone。pending 全局最多 64 个、每注册最多 8 个；包括终态和 tombstone 的总保留量全局最多 256 个、每注册最多 64 个。原生查询默认 5 秒，终态保留从第一次完成时刻起最多 60 秒，查询状态不续期；到期仍有未清理资源时保留清理责任，过期来源不能再次 ready。重启不承诺恢复这些只读任务。

每次 RPC 经真实 Registry 的操作、租约、epoch、身份与范围检查，再通过现有 GatewayReadService 的账户读取 ACL。维护使用真实活动注册集合取消失效任务，关闭和撤权保留已开始任务的清理责任。已准入的只读 native 请求可能在撤权清理前完成，不声称原子中断；失效注册不能取得结果。

统一回复为 operation_id/status/code/snapshot。ready snapshot 包含 instrument、精确 spec、session_generation、connection_generation、trading_day、remaining_seconds。每次 ready 交付周期在原 owner 上复核源观察，排队/传输耗时只扣减期限；周期可以跨若干 pending/status RPC。交付后的再次读取重新复核，不无限复用旧缓存。ready 释放前还调用 provider 的无 I/O 来源探测：True 只代表当前时点有效，False 拒绝，None 表示锁忙并返回 pending、安排新 owner 校验。异步快照不证明 socket 发出瞬间的账户状态，也不提供交易授权。新任务、提前取消和已有任务取消均须在状态变化前检查完整回复预算；预算失败明确拒绝，不截断数据或取消未知 native 事实。

### 28.4 策略线程和验证

## 30. R28：Broker 与 Strategy 的通知事务接线

### 30.1 显式绑定与事务范围

### 30.2 原回调前后挂点

### 30.3 对象保存与失败恢复

Broker 收集注册原 Order、策略历史/待发订单、实际 quick 通知、真实 Trade 容器与通知副本、历史引用 Order、parent/OCO 和 Position 关联；对象 key 使用逻辑请求、Feed 引用、事件序号和明确容器角色/序号，进程内 id 仅用于去重，不能成为耐久身份。复用原 codec 保存真实对象并保留 alias；额外 _gateway_strategy 元数据描述容器安装与 fee applied/lastTrade 映射。恢复先完整校验元数据与 codec，再安装，不能半途替换框架状态。

Trade/费用已在内存应用后、耐久写入之前可能失败。完整 candidate 必须在 store 前固定，失败保留 active/fault 并禁止下一事件或 ACK；显式恢复可用同一 candidate 重试持久写入，替换后报错也须幂等。candidate 尚未完整形成的错误必须锁定并要求从旧检查点重开，不能因 applied 标记跳过费用回调而假装成功。重开后未落盘事件仍未 applied，按旧检查点处理；已落盘批次只重投回调，不再次执行成交或费用。

pending 重投走原 Strategy._notify 和费用 inner，沿保存顺序、原稳定 ID，replayed=True；callback/confirm 失败继续保留。confirmed 批次不重投，通过原 Strategy.clear 整理已通知队列。先完成本地通知确认，再向后续消费者暴露可 ACK 水位；本切片不自行发送网络 ACK，不承诺任意外部副作用恰好一次，也不声称分析器任意内部状态已持久化。

### 32.2 同库日期与明确补充事件

Gateway 日志显式升级 v9，在原数据库增加 direct_execution_trade_dates 表，记录账户、route、trade_key_json、日期、提供该日期的 fact_digest 和原始计量事实 original_fact_digest。原 direct_execution_trades.fact_digest 仍指向计入数量的事实，不能因补日期而替换。

首次入账成交已有日期时，同事务保存日期。已入账成交原日期未知、后续同归属同经济内容的事实给出已知日期时，原子保存日期并追加 TRADE_DATE_ENRICHED 策略事件，applied=False，公开标记 trade_metadata_only=True；持仓、累计成交数量和原计量事实均不改变。相同日期或后来仍未知的重复回报不追加事件。不同已知日期保留为 TRADE_DATE_CONFLICT，既有日期与数量不覆盖，已有冲突不因后续回报自动消失。

补充必须经过原账户、命令、强身份、合约、方向及经济内容检查。不能凭同一个 trade key 越过归属验证。日期补充事件和水位遵循原事务、容量、回复预算与显式 ACK 规则。

### 32.3 显式迁移与重开核验

新建日志为 v9；旧 v8 通过独立 upgrade_from_v8 显式升级，先完整核对旧命令、执行、消费者和 place/cancel 关联，再添加空日期表。早期已支持版本继续通过既有显式迁移流程到 v9。构造器不得静默升级；不修改真实账户历史文件。

重开要验证日期表的精确 DDL、每条日期的事实/原计量事实/成交归属、补充事件顺序和只计量一次；缺行、多行、替换日期、孤立或错挂关联均拒绝。旧 JSON、旧摘要、已消费水位和数量在迁移前后保持。日期冲突即便经济摘要相同也必须可核验，不能删除冲突记录来让审计通过。

### 32.4 BT pending 的有限扩展

沿用获批 pending 文件与 v4 格式，不新增锁协议或生命周期。既有观察解码保存新嵌套版本，旧页收据摘要与通知批次保持可重开。跨事件检查保留原身份/经济约束，并拒绝不同已知日期；metadata-only 必须有同键原成交，新增已知日期不能由另一个普通成交标记偷换成新的数量。读取/保存并不自动更新框架对象或 ACK。

### 32.5 验证要求

旧版本规范字节及摘要、闰日和非法值、自然日期不同于交易日、callback/query 同源传递、首次已知与先未知后已知、重复/冲突、事务失败、容量、显式升级与损坏重开，均须有对应检查。独立进程 CURVE 回环验证原请求归属、补充标记、策略隔离、回复预算和显式 ACK；BT 用真实 pending 文件验证保存/重开而非假宿主。源码与隔离安装证据分开记录，不代替实际日期语义、账户或整期验收。

## 33. R31：稀疏执行流消费、原调度恢复与首事件前订单状态

本轮实施中，尚未验收。复用原Broker订单/持仓计算、Cerebro/Strategy通知时点、R25对象codec及同一pending文件。Gateway继续独立进程、默认ZMQ；不新增策略调度器、对象账本或通知数据库，不触及E020锁协议。首期显式消费者入口不等于最终config装配或完整下单链，剩余提交接线和恢复必须继续交付。

### 33.1 显式时间解释与完整合约绑定

SDK GatewayExecutionTimePolicy为不可变、版本化的调用方解释规则，显式route、IANA timezone、date_hms_seconds_v1格式；没有默认时区，不根据provider名称或系统环境推断。完整合法自然日期和HH:MM:SS按该规则转换为aware UTC；缺值保持未知，已提供非法字段及DST不存在/歧义时刻拒绝。解释不宣称原生时钟、时区或freshness已验证，摘要绑定配置字段但不固定运行环境tzdb版本。

BT消费者接受显式instrument_by_ref，键与data_by_ref完全对应；事件规范MarketInstrumentKey须精确相等，并核对route、持久请求symbol/side/offset及原请求归属。请求本身允许instrument=None的既有合同保持，不能从收到的事件反填缺失预期合约。该预期key与时间规则一并进入Order的持久info并在恢复后比较，缺失或不一致拒绝；调用方声明本身不构成provider来源证明。

普通成交的自然日期缺失时，可查找同一pending中已验证关联的后续metadata-only日期事实，并保存所采用事实引用；不能使用交易日、本机今天或Feed当前bar。使用原BT date2num，真实事件上下文限定Order执行时间；不能凭用户info自报verified取得该路径，也不复用managed-paper证明标志。

### 33.2 执行消费与确认顺序

真实Gateway执行流read_after按stored_sequence/epoch读取，有界页经SDK实际请求context及原host校验落盘。逐条取下一未applied稀疏事件，绑定原request/order并arm原通知事务，再用现有成交/状态/错误函数投影。quantity_unit和position_side若取自持久意图，标记为请求派生的本地归属，不能冒充远端回报字段。缺实际fee使用原SDK费用未知路径，不强填实际零费用，不偷偷打开本地估算；已有Trade数值的费用完整性仍按来源及未完成状态解释。

每轮最多推进一条待投影事件；用户回调、持久化或恢复未完成时不投影下一条。请求级ORDER_ERROR/CANCEL_ERROR无终态证明不投影成Rejected/Canceled或释放UNKNOWN。无法安全解释的输入保持未应用；缺必要时间/身份不吞为成功。真实订单状态观察可以产生通知，但日期补充不能产生额外成交。

原Strategy通知提交并成功确认后，Broker才可请求远端ACK；只有OBSERVED进度通过host校验才记录本地acknowledged_sequence。超时、UNKNOWN、丢回复不推进、不改原请求键。新消费者启用时不能落回原direct/managed账户同步、重试或写路径；最终Gateway写adapter未装配时明确拒绝该尚未接通能力，该临时边界不作为整期完成。

### 33.3 无通知日期补充与原Strategy恢复调度

commit_gateway_trade_metadata只接受已持久、已arm的精确TRADE metadata-only事件和绑定原Order；空闲通知状态下只更新Order.info.gateway_trade_dates，不改成交数量、持仓、Trade、费用或已有执行时间。复用capture_framework_state和commit_execution_projection保存图。_gateway_strategy metadata v2增加delivery=none与原event_fact_digest；没有假的空/confirmed通知batch。普通通知metadata v1保持。

ACK检查分别验证confirmed通知批次或严格v2无通知投影、对应sequence/fact/date和原事件，且不存在活动/未决/fault；普通v1缺batch不可被视为完成。恢复v2重建原对象但不投递通知。写失败保留不确定状态，原子替换后抛错必须按重开事实判断，不能提前ACK。

生产消费者不从Broker.next直接调用用户回调。Strategy._notify入口在已获批私有钩子范围内委托可选_gateway_resume_notifications；仅精确True表示本次由原replay入口完成。无绑定/无待恢复或递归中的replaying返回False走原逻辑；活动重入、新通知混入或restart_required拒绝。现有fee/普通/quick重放在这个原Strategy通知时点执行，复用原计算和通知ID，回调仍至少一次，失败不确认。

### 33.4 首事件前订单描述的原子保存

当前intent/local_seq/bt_ref不能完整恢复原Order。pending显式schema5在v4 gateway中增加order_snapshots及总字节上限，旧v1–v4保持；upgrade_for_order_state只从完整验证的v4加空映射，v5同配置幂等，不给历史意图伪造快照。原execution projection的seq0限制不放松，原markers、取消、事件和收据保持。

save_order_intent在同一原锁/原子文件更新中写入规范intent、正整数local_seq/bt_ref与R25 codec快照，须发生在reserve/dispatch之前。当前快照限一个尚未执行的原订单，orders键精确为request_key，原ref匹配bt_ref，positions/trades为空；不藉此声称任意parent/OCO或provider订单类型已支持。按request索引的envelope包含schema_version/local_seq/bt_ref/snapshot，原描述只写一次，相同内容幂等，冲突拒绝，SDK旧save_intent不能擦除它。

live_state检查JSON、容量、索引和意图/context关联；Broker恢复继续使用原codec并验证受信Feed/owner/commission和请求字段。恢复对象是新进程真实Order，原ref到新runtime ref的映射须保留，不强行重写旧context。身份rebind和marker安全检查识别v5，但不改变E020锁语义。首条回报前的完整提交/状态重取/恢复消费者仍须接入这些端口并联调，不以端口存在宣称完成。

### 33.5 验证与未交付边界

检查真实对象数量一次、普通/quick/fee恢复、用户回调与原子写失败、ACK未知/重试、日期晚到、完整instrument不符、时区规则恢复不符、v4到v5迁移及首事件前崩溃。独立Gateway/CURVE合成进程与源码/安装分别验证。CTP Gateway当前声明仅Limit，direct允许Market不扩展该能力；真实账户、来源时区及日切另按正式矩阵。config-only启动、完整资金/经济账本、控制/代理/Web/综合验收仍须继续，正式14步不得按本轮局部测试关闭。
