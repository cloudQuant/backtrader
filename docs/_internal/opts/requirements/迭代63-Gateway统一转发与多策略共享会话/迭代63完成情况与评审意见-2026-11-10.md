## 3. 主要评审发现

### P0-1：可开仓而策略账本不可用，平仓闭环受阻（E111、63.07/09）

- **依据**：SDK 的 Gateway 子仓 `src/bt_api_gateway/direct_command_journal.py:2010` 定义 `install_strategy_ledger_ports`；本次检索 SDK 与 Gateway 生产 Python 源码只找到定义，未发现调用。该文件 `:2132` 起在开仓时跳过策略可平量检查，平仓缺端口报 `STRATEGY_LEDGER_UNAVAILABLE`。R38 记录了实际持仓读取失败及平仓未完成。
- **影响**：开启 `strategy_ledger_enabled` 或 journal v11 不等于策略账本已可用。开仓和退出风险不对称，不能用挂撤成功替代开平仓往返及隔离验收。
- **建议**：由 Gateway/SDK/CTP owner 按现行边界实现并接入可信、非阻塞的合约绑定、交易日、日切与连续性检查；在用户授权的适用环境中验证开仓、部分成交、并发平仓、撤单和拒单的账本与账户对账，包含异常和重启。不得以账户总仓冒充某策略可平量或通过放宽失败关闭绕过缺口。

### P0-2：首次账本基线和既有交易历史不能只靠接端口修复（63.03/07）

- **依据**：同一 journal 的 `:2038`、`:2066` 定义空仓和外部基线初始化；本次对 SDK/Gateway 生产源码检索未发现调用。`strategy_position_ledger.py:265`、`:309` 在已有命令或成交历史时拒绝首次建立基线；`:469` 的持仓读取要求已有基线。空仓初始化注释还说明当前未安装可提供所需证明的 provider verifier。
- **影响**：完成 P0-1 的四个端口不自动建立可信的账户初始状态。历史 SimNow 场景已经发生交易；具体账户和 journal 当前内容未审查，不能断言其可直接初始化，尤其不能清空历史或把当前总仓推定为策略仓。
- **建议**：分别设计空仓无活动单初始化、受权外部基线、已存在命令/成交的历史恢复或迁移路径；核对原始身份、完整性、同一可比较切点、授权与 owner fence，并覆盖崩溃重试和冲突。历史账户如何处理应依实际证据和适用授权单独确定，禁止凭空建基线、覆盖或丢弃记录。

### P1-1：Gateway 重启时策略退出，与已确认 D63-03 存在合同差异（63.05/06/09）

- **依据**：[计划 D63-03 及 §3.12](迭代计划.md)要求 Gateway 不可用和重启后策略继续等待、重新注册、回补及对账；[设计 §4.0a](设计文档.md)要求不因断连自动停止。R38/交接记录：租约内短暂暂停可在同进程恢复；租约失效或新 service epoch 时以 `GATEWAY_STREAM_SESSION_LOST` 退出，需外部重启。源码中 `backtrader/stores/btapistore.py:772` 与 `backtrader/brokers/_btapi_gateway_stream.py:645` 区分这两种状态。
- **影响**：E112 对短时中断的修复有局部证据，但不能认定整个 D63-03 已满足；外部重启和原进程等待恢复会影响策略生命周期和运行状态。
- **建议**：按现行决定实现安全等待、重注册、按原身份续读及对账后再准入，并验证长断连、租约到期、Gateway 新 epoch、在途 UNKNOWN 与策略主动停止。若需把退出作为允许行为，应先明确提出合同差异和取舍，由用户决定，不能将已有实现自行解释成合同变更。

### P1-2：策略在线时首次停止 Gateway 失败（E107、63.03/09）

- **依据**：R38 两次重启场景首次 SIGTERM 均记录 `CLOSE_FAILED` 和 `component_close:gateway:gateway-a`，后续再次 SIGTERM 才关闭。SDK `bt_api_py/service_host.py:1463`、`:3307` 说明关闭失败的汇总路径，`gateway_direct_owner.py:559` 对 owner 完成有界等待；这些位置不能单独证明超时的根因。
- **影响**：正常停止无法稳定完成，旧 owner 的退出与后续接管需以实际关闭结果为准，不能把第一次失败视作已释放。
- **建议**：在不处置保留进程或重放历史实际调用的前提下，用可控替身和有界日志定位各资源关闭阶段、预算和在途状态；验证单次停止、部分失败后的可重试清理、活动订单保留、旧 owner fence 和重启恢复。

### P1-3：策略资金、权益与账本范围尚未闭合（E080、63.06/07）

- **依据**：`backtrader/brokers/btapibroker.py:1972` 附近 Gateway 路径对资金/权益返回 NaN，对不具备依据的持仓读取失败关闭；状态矩阵和问题记录也保留策略经济账本、费用及 getter 隔离缺口。
- **影响**：当前失败关闭是缺少可信范围时的保护，不代表策略资金、Sizer、目标仓位、手续费和权益已可使用；不得用账户级数据填补策略级事实。
- **建议**：按 D63-41/44/45、迭代 60 的策略作用域合同补齐数据来源与经济模型，验证多个策略、缺报价/费用、部分成交、迟到费用、UNKNOWN 和重启；与开平仓及账户对账一并验证。

### P1-4：控制、代理、Web 和扩展合同仍有正式交付缺口（63.12–14）

FREEZE、STOP_NEW 的有限 SimNow 记录不能推断 DRAIN、撤单保留容量、租约过期策略、Monitor required 心跳与授权撤销已经通过。代理 principal、`on_behalf_of`、账户观察流及跨日母子单和数量守恒仍需按 63.13 分层交付；独立 Web 的真实适配、授权、幂等、审计、浏览器联调与故障隔离仍缺交付/验收证据。日历扩展与其他迭代的依赖应按计划单列，不能用静态页面、接口存在或替身代替完整验收。

### P1-5：最终发行、性能与回归证据未锁定（63.10，T020–T022）

冻结全部适用仓库源码、子仓 gitlink、依赖和构建输入后，重建包括 CTP 原生包的 wheel，在仓库外隔离环境确认实际导入与包来源，再执行计划要求的回归和安装矩阵。T020 的双会话发送与撤单组合仍缺覆盖；T021 的同版本包来源和测试镜像问题仍须处理；LOAD01 需整体重跑并重钉关联输入。交接记载 T022 的基线豁免决定；执行时仍须逐类记录新旧集合与版本，单列 LOAD01 和实际涉及本期改动的用例，不把任何新增失败自动算作旧基线。性能、平台、长期运行和 §6.3 各适用场景按实测记 PASS/GAP/NOT_RUN；目标规模或门槛未定时只报告测量值。

[I63-ENV001](开发问题记录.md) 记录 SQLite WAL 并发风险和修复版本；本次只读检查 conda base 仍报告 SQLite `3.46.0`。这不能证明最终 Gateway 环境使用相同库，也未复现损坏；发行验收应核对实际解释器加载的 SQLite、适用的部署并发模式和供应商修复状态，并在目标环境重跑相关持久化检查。

### P2：可用性和运维改进

owner 上回报查询和结算回读仍可能阻塞其他任务；E110 将部分等待由 10 秒缩短到 2 秒，不证明共享 owner 的最坏等待、排队公平性及 claim 时效已满足。应在不改变已确认在途与 UNKNOWN 语义的前提下，评估分步/异步查询、优先级及有界队列，测量 p95/p99、超时与恢复。交接还记录 SimNow 行情延迟、对象形式客户端时钟刷新问题和会话丢失后的注册清理待改进；先补确定性复现和指标，区分可用性优化与交易安全门槛。
