## I63-C002：交易 owner 在 TD 暂时不可用后不自动恢复（GAP）

## I63-E002：未登记场所键提前归属可造成重开矛盾（R11 本地修复）

R16 最终证据：E017/E018 纳入主代理源码与隔离安装 Base285 / Gateway756 / CTP918 / SDK771 集合；BT 真实持久取消宿主仍未交付。SDK 两条既有 F401 在 HEAD 对照复现，继续记录为既有 lint 缺口，不把本轮检查写成全仓 lint PASS。详见[第十六轮审阅](archived/实施第十六轮远程撤单与独立授权审阅-2026-11-09.md)。


## I63-E019：相同原单的多次取消错误会碰撞旧事实摘要（R17 本地修复已验证）

源码核对：GatewayReturnFact v1 fact_digest 排除 source_ref/session_generation。仅以新来源标签区分同订单、同错误码的两次取消，仍会产生相同摘要；以原摘要唯一关联取消尝试会吞掉第二个观察或形成冲突。R17 改用显式 CANCEL_ERROR 事实 v2，把 cancel_request_key 纳入摘要，保留历史 v1 形状及摘要。分别投递、重复幂等及重开验证已纳入最终源码与隔离安装回归，真实账户仍未验证。

## I63-E020：new_instance 状态归档与独立 Store 写入存在并发窗口（OPEN）

源码和调用图确认：rebind 的 run/identity 锁与 pending/waiting 独立写锁没有贯穿同一归档事务；state 内锁还存在 rename 后旧 inode/Windows 句柄边界。当前 GatewayPendingHost 没有生产接线且不要求 run token，不能假设 direct 的运行锁已保护它。R17 v3 首写/单调 CAS 只证明同一现存状态目录内的合作写入，顺序 rebind 拒绝不证明归档并发安全。所需更广 BT 锁协议见[限定调整申请](Backtrader-状态归档并发调整申请-2026-11-09.md)，尚待确认和确定性交错复现。


## I63-E021：取消事件的运行中读取需交叉核对原单和策略（R17 本地修复已验证）

R17 初稿的侧表校验能验证事实与取消 attempt，但运行中的事件读取还必须把该 attempt 的 target_reservation_id/strategy_scope 与正在读取事件的原单和策略交叉核对，不能只依赖下次重开审计。现已在同一读取事务增加比较，并补充同/异策略双原单篡改测试。主代理另要求错误事实的 trading_day/session_generation 与准备记录精确一致，包括代际变化但摘要不变的情况；不得以 DTO 可解码代替关联完整性。

## I63-T004：全量验证 harness 改变导入语义（R17 验证环境已修正并复跑）

扩大 Base 到全量时，测试 namespace 被其他仓库的 tests 包遮蔽，先发生一项收集失败；修正显式测试 namespace 并加载原套件需要的 asyncio 插件后，来源 guard 又把不存在模块的 ModuleNotFoundError 改为 ImportError，使 14 个退役模块检查失败（1772 passed、3 skipped）。这些失败来自验证环境，未据此修改产品或删除测试。另一次初跑期间 guard 文件被修改，不作为固定版本最终证据。原始失败、旧 harness 快照及摘要均须保留；使用固定脚本重新执行后再记录最终结果，不能用新脚本的摘要代替旧日志实际使用版本。
