## I63-G001：trusted flow跨用户/Windows权限未覆盖（GAP）

当前POSIX根、账户及TD/MD子目录强制0700，只支持同OS用户。计划涉及多个OS用户共享可信根，仍需明确共享组/ACL合同及平台测试；Windows仅检查非reparse真实目录，未验证ACL。不能把单用户POSIX用例提升为跨用户/跨平台支持，native最终字符串路径打开也仍依赖受信权限。Gateway必须先持有owner锁再创建会话，目录本身不提供fence。

## I63-G002：完整 owner 控制面与排队能力尚未覆盖（GAP）

## I63-S001：结算完整回读的来源错误被当作未确认

状态：**R05 本地修复已验证 / UNIT-FAKE，真实账户未验收**。CTP 基线 5e22b2e。真实 TraderClient 配合合成 native 查询，错误账户的完整终包可使旧 settlement_status 返回 UNCONFIRMED；client 虽清理内部证明，原 QueryResult 仍完整，provider 只检查 complete/error 会误分类。修复要求完整校验同一 Trader、账户、交易日、generation、查询来源/过滤/终包及记录摘要；缺失、混杂、不匹配或竞态为 UNKNOWN，不能据此自动确认。可信空和严格旧日回读的服务器真实语义尚未账户验收。

## I63-S002：SDK 结算状态与提交日/会话未绑定（OPEN）

状态：**OPEN / STATIC**。SDK 基线 9a762e67，DirectWriteCoordinator.ensure_settlement 先读 status，再分别读取 session_generation/trading_day 构造 marker。状态读取后重连或跨日时，旧日 UNCONFIRMED 可能被用于新会话的标记；原生 grant 拒绝旧代不能替代 read-first 证据绑定。后续须使用 provider 绑定的结算观察与提交/发送前复核，并以稳定账户/交易日/attempt 恢复持久 marker。R05 只修 provider 的回读分类，不据此关闭本项或宣称 Gateway 每日自动确认已交付。

R06 前置源码核对进一步确认：WriteGrant 目前只含 route/operation/generation，不含账户、交易日或观察绑定；grant.issue 在 marker 提交后执行。CTP 普通 confirm 路径未传递 _request_settlement_confirmation 已有的 expected_generation，最终 native 入口的 settlement authorization 会话核对位于 callback-ingress 分支。后续须复用 provider 查询来源/issuer，把一份不可变观察贯穿 marker 与原生调用前复核；持久化进程无关的账户/日/attempt，不能把 issuer 对象当作重启身份，也不能以加锁声称网络发送原子化。进入 native 或提交结果不明仍按 UNKNOWN 恢复。

## I63-S003：结算确认日期与交易日、空查询覆盖语义（GAP）

本地 CTP 6.7.7 SettlementInfoConfirmField 只有 ConfirmDate，头文件注释为“确认日期”，没有 TradingDay。夜盘/跨日映射以及完整空查询能否排除当日已确认尚未验证。R05 保留既有本地策略：可信完整空结果或全部合法旧日期为 UNCONFIRMED；错误来源、账户、混杂/矛盾、非法/未来日期为 UNKNOWN。该保留不新增场所真实性主张；完整 Gateway 每日自动确认验收须给出目标环境的日期与覆盖依据。原生自动确认继续关闭，仅 SDK 准入路径可确认。见[第五轮审阅](archived/实施第五轮客户端与结算回读审阅-2026-11-08.md)。
