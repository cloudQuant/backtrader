## I63-E002：未登记场所键提前归属可造成重开矛盾（R11 本地修复）

原 profile 先 Hub.close，再 proxy.close，最后才开始 owner 的关闭预算；两次逐 handle 清理各自等待 pending/release，退出时间可按 N×timeout 累积。修复为 begin_close 无等待停止新操作、先在原总预算内关闭 owner、确认后清逻辑态；桥独立 close 的全部 handle 共享一个预算，未确认资源保留并可重试。多 handle 加阻塞 owner 的有界行为测试负责验证，不能以单 handle 正常关闭证明整体预算。

## I63-E040：联合 profile 的 fake key 不符合真实 CTP 行情合同（R21 / 本轮局部验证通过）

profile 原测试使用 ticker，宽松 fake 接受，但真实 CTP provider 要求 tick、无 depth/timeframe 且 instrument_id 与 native_symbol 一致。真实路径会拒绝并可能进入 Hub 订阅不确定态；fake 通过不是可订阅证据。CTP 提取轻量纯规则到 market_key_contract，provider 保留原异常类型，SDK 构造前调用同一规则；测试改为真实支持 key 并分别验证非法输入。独立进程联合测试使用真实 Python session/provider 加合成 TD/MD，仍不代表实际 native 或 SimNow 验收。

## I63-E041：行情维护同步等待 native owner 阻塞 Host RPC（R21 / 本轮局部验证通过）

ServiceHost 在接收 RPC 前同步维护 Hub；桥的 reset 检查与到期 unsubscribe 原先逐 key 等待 call_timeout_seconds，多个 stream 可把一次维护放大为 N×timeout。native owner 不可抢占，并不要求网络 Host 同步等待。独立 Gateway 进程中阻塞已出队 poll，再让维护进入等待，独立 direct-only 客户端的既有命令状态 RPC 在 0.5 秒超时为 UNKNOWN；原始失败 `/tmp/iter63-r21-poll-host-liveness-maintain.log`。早期立刻发 RPC 可抢在维护前而成功，不能作为阻塞期间持续活性证据，保留 `/tmp/iter63-r21-poll-host-liveness.log` 说明该窗口。

按冻结合同 §24.7 将维护使用的 reset/ACK/unsubscribe 改为非阻塞推进同一 retained future；旧 ACK 的 epoch、已出队批次、gap 和不确定资源不丢弃。不得通过缩小测试 timeout、停用维护、重新 native poll 或替换 session 掩盖问题；修复后需原失败场景转通过并检查多 stream 维护与清理预算。

## I63-E042：reset=False 不足以允许缓存行情交付（R21 / 本轮局部验证通过）

CTP 的 source_epoch_reset_required 在断线恢复尚未进入 reset_pending 时也返回 False；原 poll 另行检查 recovery、当前 scope、symbol readiness 和 pending reset，并在不可用时不出队。桥若直接返回此前缓存，便跳过这些 provider 事实检查。

CTP 将原 poll 前检查提取为共享 helper，并提供不出队、不 ACK 的 retained_events_ready；SDK 在原 native owner 的异步控制调用中同时核对 reset 和缓存交付条件。许可只能对当前已核对批次使用一次，过期重查；恢复未就绪不交付缓存，确认 reset 清旧批次，ACK 后不得把旧批次改标新源。新增 provider/Hub 合成回归和原独立进程活性向量共同验证。

证据边界：owner 在 T0 核验并交出的原源观察，可能在 T1 发生断线后、T2 才到达 Host/网络接收者；本轮没有跨线程/native/网络原子撤回机制，不能声称 T2 当前源或 live 真值。保留原 observed_at、source 和 epoch，消费者原有来源与时效校验仍必须执行。T0 后才注入断线的向量不能写成已证明零旧帧；它与“检查时已经断线，却因 reset=False 仍交付”的可修缺陷分别记录。

## I63-E043：批量订阅入口的有限等待仍会累积（R21 STATIC / OPEN）

Gateway market.bootstrap_many 最多 20 项，逐项调用 hub.subscribe；桥 subscribe/describe_source 各自仍有有限等待，默认 5 秒、profile 最大 30 秒。因此一次已授权批量订阅可在 native owner 阻塞时长时间占用 Host，后台维护非阻塞并不证明所有请求入口均有总延迟上界。当前仅静态核对，尚未独立复现批量倍率，不能引用 E041 的后台场景作为本项测试。

下一轮优先明确异步 acquisition/descriptor、同 registration/key 的唯一 pending 身份、幂等查询、部分 batch 回滚及客户端不确定态。当前 Hub 在 descriptor 未就绪时尝试 release；直接把桥等待改为零可能取消尚未开始的申请并反复饥饿，不能据此假修复。SDK 已发送 batch 的失败不回退旧路径，丢回复和不完整响应须保留 uncertainty。具体入口为 Gateway market_hub 的 bootstrap_many、subscribe 和 rollback，以及 SDK service_market 的 batch/单项启动。此缺口保留在 63.05/综合验收，不阻止已授权的本地实现与验证，但阻止宣称完整 Gateway 响应性或整期完成。
