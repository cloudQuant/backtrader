## 2. E111：策略账本端口与基线

### 2.1 原因

Gateway journal 的策略持仓账本要由可信的 owner 代码安装四个本地端口，并且要先有基线，才提供持仓读取和平仓容量。生产代码里没有任何地方安装端口或建立基线，所以打开 `strategy_ledger_enabled` 后：开仓照常受理，持仓读取和所有平仓一律返回 `STRATEGY_LEDGER_UNAVAILABLE`。此外，两个已有的基线入口（空仓、外部基线）都拒绝已有命令或成交的 journal，因此先交易、后启用账本的 journal 永远无法建立基线。

### 2.2 实现

新模块 `bt_api_py/ctp_gateway_strategy_ledger.py`（`CtpGatewayStrategyLedger`），只在账户 owner 线程上运行，RPC 对端接触不到。

**四个端口**（都不做网络或柜台 I/O）：

| 端口 | 依据 |
|---|---|
| `resolve_binding` | profile 配置的回报合约清单确定完整合约；是否必须区分今昨由 `bt_api_ctp.close_offset_policy` 声明 |
| `current_trading_day` | 已登录 TD 会话的交易日 |
| `verify_day_transition` | 两个日期格式有效，且 `旧日 < 新日 <= 当前会话交易日` |
| `verify_current_continuity` | 请求的是当前会话交易日；回报来源在当前原生会话内已完成委托、成交两次整日查询，且之后没有缺口、来源过期或写入失败的回调批次；该合约上没有更早交易日的、可能到达过柜台而未了结的命令 |

最后一条的理由：柜台查询只覆盖当前交易日。更早交易日可能到达过柜台的订单，如果 journal 里没有“终态且累计成交与已记成交相等”的证据，其成交永远无法由之后的查询补齐，该合约的账本就不连续。

回报“连续”与“可派发”是两个判断：`CtpGatewayReturnMaintenance.ledger_continuous()` 允许缓冲区里还有待处理的回调（账本只是滞后，滞后时平仓容量偏保守），不允许丢失；`dispatch_ready()` 仍要求缓冲区为空。

**基线**（owner 线程，在 journal 事务之外读取账户，事务内再核对一次）：

| 情形 | 处理 |
|---|---|
| journal 无历史，账户无持仓、无活动委托 | 建立空基线 |
| journal 已有历史 | 建立回放基线：全部命令已了结、没有未归属成交、无活动委托，且 journal 自己的已归属成交从第一笔成交的交易日回放，结果与柜台完整持仓逐项相等（SHFE/INE 按今昨分桶，其余按方向合计） |
| journal 无历史，账户已有持仓，且运营在受保护资源包中声明（`strategy_ledger.external_baseline`） | 声明与柜台完整持仓完全相等时，建立外部基线；这些持仓记入 external，不属于任何策略，策略不能平掉（D63-06） |
| 其余情形（未声明的既有持仓、有历史又有既有持仓、有活动委托、有未了结命令） | 不建立基线，账本保持不可用 |

任何差额都拒绝建立基线，不会把快照里的持仓分给策略或记作外部。

“一次账户读取是可比较切点”的判定：读取前后，私有回报缓冲区没有待处理记录、末序号相同、无缺口，且原生会话代际和交易日不变。账户的任何委托或成交（包括手工的）都会出现在这条私有流上。同样的条件在 journal 事务内、提交前再核对一次，并带 5 s 有效期。

**预约门**：启用账本后，基线建立之前，profile 拒绝全部新预约（`STRATEGY_LEDGER_UNAVAILABLE`），包括开仓。这样不会再出现“能开仓、不能平仓”。

### 2.3 需要用户知晓的设计取舍

1. **回放基线是新增的第三种基线**，证据以 `schema_version` 2 保存（记录历史起始交易日和被核对的柜台持仓）。版本 1 的证据字节和摘要不变。旧版代码读到版本 2 会拒绝打开 journal（不可降级）。
2. **CFFEX、GFEX 的平仓规则尚未确定**（计划 §6.2 第 6 项），provider 不声明，这两个交易所的合约在账本里不可解析，经 Gateway 无法平仓。待规则核实后在 `close_offset_policy` 补充。
3. **有历史的 journal 同时存在既有持仓**时不支持（回放结果与柜台不等，拒绝）。需要先由其他途径处理既有持仓，或另行设计“回放 + 外部”组合基线。
4. 外部基线由资源包声明授权，没有做成网络控制命令。资源包本身是 0600 的运营信任根；若 63.14 页面要提供该操作，仍须走受权 API。

## 3. E107：策略在线时第一次停止失败

owner 清理只调用一次 `session.close()`。原生停止若在一次等待内未确认，清理即抛错，owner 线程随后等待下一次关闭请求，所以第一次 SIGTERM 以 `CLOSE_FAILED` 结束，第二次才完成。

修改：

- owner 清理在本次关闭预算内重试 `session.close()`（会话本来就为 owner 线程重试保留了未确认的停止）；预算用尽后不再重试，等下一次关闭请求。
- 清理未完成时写出停在哪一步（如 `CTP_SESSION_CLOSE_UNCONFIRMED`）；会话关闭未确认时写出是行情、交易还是账户部分。

**尚未确认的部分**：SimNow 上到底是哪一步超时（推测是策略在线时才存在的原生行情流停止）还没有实测证据。新增的日志会在下一次运行中指明。结论见 §6。

测试：新增 2 例（旧代码在第一例失败），3 处变异全部检出；profile 套件 51 passed、3 xfailed。

## 4. D63-03：断连后在原进程内重新注册

### 4.1 与用户决定的差距

E112 修复后，短暂不可用（租约内）时策略在原进程恢复；但租约过期或 Gateway 重启（新的 service epoch）后，策略以 `GATEWAY_STREAM_SESSION_LOST` 退出，要靠外部重启。用户决定 D63-03 要求：策略继续运行、等待 Gateway 恢复、重新注册并回补，不因断连自动停止，也不回退 direct。

### 4.2 实现（backtrader）

| 部件 | 行为 |
|---|---|
| `BtApiStore.gateway_reconnect()` | 关闭已丢失的 SDK 会话，在同一进程内用同一个 pending host、密钥和运行锁注册新会话。旧运行时未关闭、Gateway 不可达或注册被拒时返回 False，调用方继续等待；重试按退避间隔（0、1、2、5、10、30 s），等待原因每种只记一次日志 |
| Broker 每步 | 发起上述重连；成功后把绑定换到新会话（订单对象、耐久游标不变），从已保存的序号之后续读 |
| 旧会话已确认排队的派发 | 不再当作“已排队”（重启的 Gateway 丢了队列）：逐笔按原身份读回，由 Gateway 决定撤回还是继续，不重发 |
| 重连完成前 | 提交与撤单被拒（`GATEWAY_STREAM_GATEWAY_UNAVAILABLE`） |
| 行情适配器 | 跟随 Store 换到新会话，从订阅的 bootstrap 重新开始；在新的实时行情到达前不可交易 |
| 何时结束策略 | 只有 Store 自己被停止或失去运行锁时才以 `SESSION_LOST` 结束 |

旧会话没能告知旧 Gateway 的事项（注销、退订）不阻止重连：那份注册随旧租约或旧 Gateway 结束。只有旧运行时的线程未结束或本地关闭未完成时才等待，避免同时存在两个运行时。

断连本身不新增需要运营 RESUME 的原因；重连后是否可下单仍由原有的恢复与准入检查决定（未解决的旧单阻止同一数据上的新单，行情须重新合格）。

### 4.3 时序事实（合成进程测试测得）

Gateway 停止后的前约 30 s（租约期内），SDK 会话仍视为有效，BT 状态为 `READ_UNAVAILABLE`；租约到期后会话才判为丢失，状态变为 `GATEWAY_UNAVAILABLE` 并开始重连。Gateway 恢复后的下一次尝试即注册成功。

### 4.4 测试

- 进程级：真实独立 Gateway（真实 ServiceHost、CURVE、SQLite journal 与 Registry，原生边界为替身）正常停止后在同一 journal 上重新启动；同一个 BT 进程持续步进。重启前收到第一笔成交，重启后收到第二笔成交，其间已确认游标不变、无重放无丢失。约 40 s。
- 单元：Store 重连状态机、Broker 绑定切换、行情适配器跟随，共 12 例。
- 变异检查 22 处全部检出。BT iter63/Gateway 选择回归 550 passed、1 xfailed。

## 4a. Gateway 模式的停止撤单（D62-19）

准备 SimNow 场景 6 时发现：Gateway 模式下 `BtApiBroker.stop()` 只关闭会话，不撤销本策略的活动委托（R38 中策略正常停止后挂单仍在、重启后才撤销，即此原因）。计划 63.06 与 §6.3“停止只撤本策略委托”要求正常停止只撤本策略的委托。

BT `ba0e94431`：停止时先按原身份请求撤销本策略的每笔活动委托（尚未派发的预约改为释放），在 `stop_cancel_timeout` 内等待柜台答复，再照旧关闭会话。不平仓；该会话只能触及本策略自己的命令。

停止摘要（`gateway_working_orders`）不把未观察到的结果报成已撤：

| 字段 | 含义 |
|---|---|
| `confirmed_terminal` | 本进程已观察到结束的委托 |
| `awaiting_confirmation` | 已请求撤单，但答复在停止结束前尚未应用；下次启动由耐久回报流送达 |
| `refused` | 撤单请求没能发出（例如 Gateway 不可达），按原因计数 |
| `unresolved_working_orders` | 停止结束时仍为活动状态的委托数 |

测试：新增 5 例，7 处变异全部检出；BT iter63/Gateway 选择 555 passed、1 xfailed。

## 4b. 账户合计对账端口（D63-48；本节为当时状态，接线见 §6.7）

SDK `79aebbf1`：账本模块可保留一次账户读取作为对账切点（证明方式与基线相同），并安装 journal 的对账端口。切点只在仍是账户的最新状态、且不超过 `comparison_max_age`（默认 120 s）时作答，否则对账结果为不可用，不把缺失当作零。运营声明的外部基线持仓计入 external。基线之后记录的外部成交没有外部分类器担保，存在时对账不可用。

默认关闭（需给出 `comparison_refresh_seconds`）。**尚未接入交易 profile 和运营资源包**：已安装的运营入口目前不支持账户只读设置（account read），对账服务依附于它，这是下一步的装配工作。测试：新增 10 例；9 处变异中 5 处检出，4 处是账本连续性端口会再次执行的冗余保护。

| a（已列出）与 b（未列出）在线 40 秒后同时 `kill -9` | Registry 记录 a 的一条过期事件，状态 `APPLIED`；journal 中出现一条原因：策略范围 `strategy-a`、模式 `DRAIN`、来源 `system:lease:…`、生效。b 没有事件，也没有原因 |
| 运营端口读取 | 策略 a 范围的 `list`、`status` 返回该原因；账户范围和策略 b 范围的 `list` 为空；`targets` 为空（a 没有在途委托） |
| a 重新启动并注册，运行 45 秒后正常停止 | 原因仍然生效：重连本身不解除 |
| 运营对该原因执行 `resume` | 被拒绝，`RECOVERY_REQUIRED`；原因仍然生效 |
| Gateway 一次 SIGTERM | 正常停止，无残留进程 |

结论有两条。第一，桥在真实 owner 下无法启动的缺陷已修复（`e95fd88b`），修复后“只对已列出的策略、在租约过期时施加 DRAIN、重连不解除”在已安装组合上成立。第二，这种原因在已安装组合里**没有任何解除途径**：自动解除和运营解除都要求已安装的恢复证明来源，而目前没有任何 provider 提供，资源包也无法指定。因此资源包选项已撤回（`131017c9`），桥只对受信的进程内组合保留。计划 D63-28 还要求“开启时过期时长必填”，现有实现是租约一过期就施加，没有这个时长。两项缺口记为 I63-E128。

预演还暴露一个 QA 问题：源码快照 `frozen-f` 没有包含 SDK 的 `examples/`，QA 策略启动即失败；已补上，否则 09:00 的实盘会在第一步失败。
