# 迭代 63 第六轮：结算观察、每日尝试与日志升级审阅

日期：2026-11-08。范围：Base、SDK、CTP、Gateway 和 OKX/Binance 的最小能力声明。结论：本轮局部实现通过所列源码检查；整期仍 IN_PROGRESS / 未验收。默认传输仍为 bt_api_transport_zmq，本轮没有新增中间件或改动其源码。

## 本轮修改

- Base 的 SettlementObservation 表示同次查询的 route、账户绑定、交易日、原生 generation、状态与观察 ID；SettlementWriteBinding 将原 UNCONFIRMED 观察和耐久 marker 绑定。DTO 不自行证明来源。
- SDK 对 settlement_required 使用精确布尔声明。CTP 为 True，OKX/Binance 为 False；声明缺失、非法或验证期间改变时为 UNKNOWN。marker 和 grant 使用同一观察，提交前后复核。提交后准入、调用或 grant 清理异常均保留 UNKNOWN。
- CTP 验证实际封印查询结果、原 Trader/API/SPI、账户、日、代际、PID、期限和观察 epoch，拒绝复制票据。SDK profile 的最终原生入口必须检查和一次性消费原观察；原非 SDK typed managed/core 路径仍有独立授权。统一原生账户 fingerprint 的 acct_ 格式，消除旧 ingress 格式不一致，并将最终会话校验覆盖到非 ingress 路径。
- Gateway journal schema v3 在原 SQLite 库保存每日 ATTEMPTING/UNKNOWN/CONFIRMED，保留首次 marker、观察与代际。已有同日记录不再授予发送 marker；重开后按新鲜回读核对，次日独立建行。旧记录保留并与命令共用容量。
- 显式 upgrade_v2 在匹配账户 guard 和保存锚点下核对旧 DDL、索引、历史命令/释放/强键关系，拒绝额外触发器，事务加表并递增修订，失败回滚。没有删库或自动建空库的升级分支。
- GatewaySettlementController 复用原 dispatcher/guard，在现有 owner 线程回读、记录尝试与确认。ready 是 owner 线程实时 gate，status.observed_ready 只是缓存诊断。维护回调与命令轮流获得机会，关闭后不开始新维护；原生阻塞仍可能延迟二者并保留清理责任。

## 审阅发现与处理

| 发现 | 处理与证据边界 |
| --- | --- |
| grant 清理异常覆盖已提交后的有限结果 | 捕获并返回 UNKNOWN；定向负向测试已纳入 SDK 回归 |
| 观察生成后 provider 的结算声明改变仍可能通过 | SDK 与 controller 在验证前后持续要求字面 True，getter 异常拒绝；包含提交、grant 发放和确认返回边界 |
| 日志迁移只看字段不足以保护旧记录 | 增加精确旧结构、关系和容量校验，拒绝额外触发器；数据保留、篡改和 DDL 后故障回滚用例通过 |
| 等待 SQLite 写锁可能使原观察/准入过期 | 取得锁后与提交前复核；独立 SQLite 连接实际持写锁期间改变 generation 或 admission，放锁后无尝试、无发送 |
| fork 继承被其他线程持有的锁可能阻塞 | CTP 和 controller 公共入口先检查 PID；合成 fork/持锁向量覆盖 |
| 极小维护间隔可能使命令永久不出队 | 最小间隔 0.001 秒，并保留维护与排队任务相互让出执行机会的规则 |
| 网络线程读取 ready 会进入 provider 锁 | ready 限 owner 线程；跨线程只读不可变缓存诊断，不以缓存授予派发 |
| 计划将 Gateway 复用 direct 启动恢复写成已实现 | 改为待接线目标；无原生身份先按原 request_key 查询，不使用场所 not-found 结论 |
