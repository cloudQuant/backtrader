## 3. 跨迭代发现

严重度定义：**P1** = 建议在 63.01/64.01/65.01/66.01/68.01 冻结前处理；**P2** = 建议在实施中补上；**P3** = 文档一致性。

### RVX-01（P1）用“按幂等键放弃 + owner epoch 栅栏”证明 NOT_SENT；评估把两阶段合并为单阶段

**问题。**

- 63 设计 §4.1 设想让 `command_status` 返回“日志保留区间与连续覆盖水位”和 fence 结果，用来证明 NOT_SENT。这个合同还是提案，而且要证明的命题很难：此前所有可能到达的 reserve/dispatch 都已处理，或已被永久排除。
- 64 计划 §4.3 第 1～3 行、§4.3“risk 不可用（SDK 已写 PREPARED 之后）”行、设计 §6，以及 65 计划 §3.8 第 5、7、8 行都依赖它。合同没交付时，这些情形只能 UNKNOWN 并长期保留占用。
- 有一种情形，现有设计根本没有可用的 fence：risk 已提交本地预留，`direct.reserve` 可能还在路上，Gateway 侧没有任何记录（64 §4.3 第 1 行）。这时没有 RESERVED 行可以转 EXPIRED。65 §3.8 第 5 行（`risk.parent.reserve` 前后崩溃）也是同样的结构。

**建议的两个原语**（名称待 63.01 冻结）：

1. **放弃（墓碑）**，例如 `direct.abandon(account_scope, request_key, digest)`。它在 Gateway 派发锁内、一个 SQLite 事务里执行：
   - 没有该键的记录：写入 TOMBSTONE，返回权威的 NOT_SENT；
   - 状态为 RESERVED：转 ABANDONED（等同 EXPIRED），返回 NOT_SENT；
   - 状态为 DISPATCHING、SENT、UNKNOWN 或已终态：返回已记录的状态，不能放弃。
   之后凡是带这个键的 reserve、dispatch 或 place 一律以有限码拒绝。可以调用的有原 principal、Gateway 登记的它的代理（risk、execution）和运营。幂等键本身“同键同内容返回原结果、同键异内容拒绝”的语义与 Stripe 等系统一致 [S21]；墓碑是在此之上加的“先占位、后到者一律拒绝”操作。
2. **owner epoch 栅栏。** 每个写请求都带上客户端最近一次从 `session_status` 读到的 Gateway owner epoch，Gateway 拒绝与当前 epoch 不符的写请求。Gateway 重启后，旧 epoch 发出的所有在途请求，包括 ZMQ 在重连后才投递的排队消息，都不可能生效。这就是 Kleppmann 所说的 fencing token [S20]，可以直接替代“旧 owner、旧代际、迟到请求不能生效”的那一整段证明。

**效果。** 64、65 里上述 UNKNOWN 都能用 `abandon` 得到确定结论后释放占用，不必实现覆盖水位。墓碑按交易日保留（`request_key` 由策略 UUID 加单调局部序号派生，`child_id` 按母单派生），交易日结束加一段余量后清理；有 epoch 栅栏，旧 epoch 的请求本来也到不了。

**进一步的选项：单阶段 `place`。** INV63-03 已经承认 Gateway 无法核验策略侧的 PREPARED，而 `request_key` 可以在任何 RPC 之前写进 PREPARED。这样两次 RPC 可以合并成一次 `direct.place(request_key, digest, epoch)`，在一把派发锁内完成准入、DISPATCHING、分配 OrderRef、grant 和原生调用。

- 在 Gateway 内部，这就是现有的 `DirectWriteCoordinator.place`：provider `reserve_order` → `PreDispatchCommitPort.commit` → grant → `submit_order`，只是提交端口换成 Gateway 日志。
- 策略侧的远端 provider 本地实现 `reserve_order`（只分配 `request_key`，不发 RPC），`submit_order` 才发 RPC。`bt_api_base.direct_write_protocol` 的 `DirectWriteProvider`/`PreDispatchCommitPort` 合同不用改（`direct_write_protocol.py:231-239`、`:413-447`）。

这样一来，以下工作都不再需要：

- 63.02 拆分协调器；
- 63.04 的“预留不含 OrderRef、提交时分配”新入口；
- 63 §3.4 的 OrderRef 次序问题；
- 63 §3.6 的“到期与派发原子竞争”整套规则；
- 急停“预留时一次、派发锁内再一次”的双重检查。

64 的 `risk.order.reserve/dispatch` 合并成一个 `risk.order.place`（L1～L3 加 claim 在一个事务里，提交后再转发），65 的子单也只走一次。

| 方案 | 内容 | 优点 | 代价 |
| --- | --- | --- | --- |
| A 现状 | 两阶段 + 预留到期 + 覆盖水位/fence 提案 | 已经过两轮审阅，文本最完整 | NOT_SENT 证明复杂且未冻结；64、65 有多处只能长期 UNKNOWN |
| **A′** | 保留两阶段，补 `abandon` 与 epoch 两个原语 | 改动最小；立即消除 64、65 的长期 UNKNOWN；不用实现覆盖水位 | 两阶段的状态和竞态规则仍在 |
| **B** | 单阶段 `place` + `abandon` + epoch | 协议最简单；Gateway 内复用现有协调器；63.02、63.04 范围缩小；64、65 同步简化 | 三份计划的协议与崩溃表要重写，与已审阅文本差异大；失去“写 PREPARED 之前先被确定性拒绝”的小优化，只是多出一些很快解决的 PREPARED 标记 |

### RVX-06（P2）写明目标运行规模，再量性能和恢复时间

没有任何文档写明目标规模：每账户几个策略、几个合约、峰值下单速率、能接受多少附加时延。现状是：64.11 只量 risk 的时延；63 的测试矩阵没有性能行；迭代 62 观察到每个实盘进程忙轮询约占一个 CPU 核（63 §1.5 第 12 项）。一台主机上跑 Gateway、risk、execution、monitor 再加 N 个策略，CPU 争用会推迟行情处理，引发新鲜度拒单（63 §6.1 已登记该风险）。

**建议**：

- 63.01 把目标规模写成“假设”，例如“每账户 ≤ 10 个策略、≤ 40 个合约、≤ 5 笔/秒；回环下每笔附加 p99 ≤ 20 ms”。这些数值只是示例，由用户定。
- 63.09、64.11、65.08 按 INV-12 只记录实测值，不设门槛。
- 把“忙轮询”列为 63.09 之前必须先查清的事项。不改的话，“多策略共享一台主机”的目标撑不过几个进程。

### RVX-08（P1）把 S-12/D63-22 写成要问期货公司的具体问题清单

依据见 §2 的监控中心规范、程序化交易管理规定和交易所异常交易标准。建议写进 63 §6.2，并在 64 的 R-04/R-05 和 65（算法会增加报撤单）中引用：

1. **终端类型。** Gateway 是单进程、单 AppID，在同一主机上服务 N 个策略进程。它是否按“直连终端”认证？如果以后策略进程放到其他主机，是否必须改成中继（RelayAppID，逐终端采集并上报）？
2. **AppID 与版本。** AppID 含版本号。Gateway 每次升级是否要重新申请 AppID/授权码，或重新做接入认证测试？
3. **程序化交易报告。** 一个账户上有多个策略时，“交易策略类型及主要内容”是否要按策略分别报告？新增、停用策略或改参数时要不要变更报告？报告的时点是什么？
4. **高频认定。** 交易所现行的高频交易标准是什么？“最高报撤单频率”和“单日最高报撤单笔数”是否按账户上 N 个策略的合计填写？
5. **异常交易口径。** 自成交、频繁报撤单、大额报撤单的计数是否包括被柜台拒绝的报单？实际控制关系账户怎样合并？期货公司是否另设更严的阈值？
6. **柜台参数。** 本账户的报单、撤单、查询流控值和最大在线会话数各是多少？
7. **应急撤单。** 期货公司能否提供断线撤单、紧急撤单服务或接口？CTP 本身没有 Cancel-on-Disconnect（63 §6.2 第 3 项记为未知）。

另一点：按施行日和过渡期推算，过渡期已于 2026 年 4 月前后结束。如果用户已经用真实账户做程序化交易（不论是否经 Gateway），报告义务可能已经适用。这一点也要一并确认。（问题 QX-07）
