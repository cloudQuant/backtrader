## 1. 用户已决定事项的实施

### 1.1 存储信任：OS 强制隔离（SDK `02b2d08a`）

新增 `bt_api_py/gateway_storage_trust.py`。CTP 交易 profile 在两个时点运行 `assert_gateway_storage_isolated()`：部署工厂中 Registry 打开之前，以及 owner 启动时守护锁与 journal 打开之前。拒绝条件（错误码只有类别，不含路径）：

- 存储目录（守护根、journal、CTP flow、Registry、账户读取与身份库所在目录）或其中任一条目不属于 Gateway 有效用户、对组或其他用户可写，或为符号链接。
- SQLite 主库或其 WAL/SHM/journal 文件不满足同一条件。
- 配置路径或其真实路径的任一祖先目录属于 root 和 Gateway 用户以外的用户，或对他人可写而无 sticky 位。
- 非 POSIX 平台一律拒绝。

它不能发现以 Gateway 同一用户运行的其他进程或特权主体，这两点作为部署要求写入 SDK 运营示例。账户对比候选仍为 `NOT_COMPARABLE`：它还需要 CTP 全账户覆盖与共同切点证明，存储信任只解决其中一项前提。本机 SimNow harness 以单一 OS 用户运行 Gateway 与策略，可通过检查，但不演示隔离部署本身。

### 1.2 E020 状态归档协调锁（BT `47f12e588`）

先以确定性交错复现（旧代码上 4 例全部失败）：

- 检查后写入被静默归档；
- 进行中的写入不被等待；
- waiting 写入同理；
- 重绑前构造的实例取得新运行锁。

实现：策略根目录持久协调锁 `.state-coordination.lock`，归档不会移动它。它是 pending、waiting、sequence 写入、审计追加、身份初始化/绑定/重绑及运行锁获取的最外层锁。锁序为协调锁 → 运行锁（仍不等待）→ identity → 各存储锁；同一线程可重入，按解析后的根路径区分，路径别名共享同一锁。new_instance 的检查、归档与重新初始化在同一协调临界区完成；持旧身份的写者随后在既有 `strategy_uuid` 校验处失败。运行锁获取在协调锁下重新核对身份。

覆盖项：两种交错、跨进程持锁及持锁崩溃、锁超时、符号链接根目录。未覆盖：Windows（未运行）、旧版本独立写者（升级前须停止）、网络文件系统、跨主机与恶意写者。
