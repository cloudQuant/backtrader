## 1. 交付范围

### 1.1 订单派发（决定 B）

- **Base `claim_fence`**：新增 `ClaimFence.with_sealer()`，返回生产核心与一次性 `CoverageSealer`。封印只由组合根持有；`seal(coverage, not_selected=...)` 要求每个被选域列出已接入的写者，可选域固定为 NOT_SELECTED。封印后被覆盖写者才可发布 READY，未封印核心与此前一样失败关闭。新增 `retire(claim)` / `abandon(candidate)`：在耐久 journal 已使同一命令不可再准备后释放内存去重项，解决 4096 次派发后命令容量耗尽的问题。封印是对已审阅接线的组合声明，不是对不合作写者的运行时证明。
- **覆盖的域与写者**（`bt_api_py.gateway_dispatch_claim.GATEWAY_DISPATCH_COVERAGE`）：registry（ServiceRegistry 事务及持锁变更）、market（`GatewayMarketDispatchGate.market_change`）、parent_facts 与 control（Gateway 命令 journal 的 SQLite authorizer：任一主表写入在 COMMIT 前同时开启两个域的变更；`install_dispatch_change_port` 此前没有生产调用方，本轮接入）、session_source（CTP TD 连接/登录钩子、MD 流来源钩子，以及配置时的 SNTP 时钟刷新器）。risk 为 NOT_SELECTED。CTP TD 结算状态写者未挂钩；provider 在原生调用前于自身会话锁内复核会话、就绪和来源，无法被绕过。
- **派发顺序**：首次准入检查 → 在写 DISPATCHING marker **之前**取得单次 claim（capture → 最终校验：请求 fence/Registry、owner、准入、委托、带 250 ms 窗口的行情原生复核、只读 journal 控制与 required monitor 复核 → capture → prepare → 在叶子锁内 try_claim）→ marker 事务（再次复核授权，可拒绝）→ provider。provider 侧最终检查只核对 claim 年龄（≤2 s），Registry/行情/journal 锁都不跨原生调用持有。为覆盖 claim 窗口，`direct.dispatch` 租约及行情注册要求剩余有效期 >0.5 s。
- **忙则让出**：被覆盖写者正处于变更中时返回 `DISPATCH_CLAIM_BUSY`，不写 marker，命令保持 RESERVED；`GatewayDirectOwner` 在原任务期限内把任务放回队尾，先处理排队的 owner 服务任务（例如行情 Hub 正在等待的原生操作）再重试。
- SDK 直连服务与委托服务只在 owner 报告已封印 claim 时才把新派发入队，否则仍返回原 `DISPATCH_CLAIM_UNAVAILABLE`。provider 未经 claim 就报告发送时，dispatcher 记录真实结果并对后续派发失败关闭。SDK 组合中原 `CheckedCommitPort` 漏传 native fence 的问题已补上。

### 1.2 结算确认（决定 A）

- 账户级授权 = 路由写入准入 + 当前 owner 代际 + 无账户级 FREEZE；STOP_NEW/DRAIN 与订单 UNKNOWN 不阻止结算确认。
- 流程：核对 → 持久化当日 ATTEMPTING marker → 在 owner 线程上以同一核对作为单次 claim（控制类写者均经 owner 服务调用在该线程执行）→ CTP 原生确认 → 仅当可信回读证明同账户同交易日已确认才记成功。claim 失败时 provider 从未被调用，删除该未发送 marker（`settlement_abandon_unsent`）；结果不明或 marker 提交回复丢失均保持原身份 UNKNOWN，只回读、不重发。
- CTP provider 的 Gateway 分支在 provider 锁内核验并消耗 grant，随后释放锁再调用原生确认与回读；trader 侧回调读取固定票据而不取 provider 锁（避免与后台回读线程 provider→trader 状态锁的顺序反转），在途令牌排斥并发结算操作。
