## 2. 发现与建议

### RV63-01（P1）Gateway 宕机或 TD 会话长时间中断时，没有应急撤单通道

- **定位**：§6.1“单点故障”行的缓解措施写了“运营撤单工具”，但 §5 没有任何步骤交付它，§6.3 也没有验收项；§3.12“Gateway 宕机且有活动委托”行；§6.2 第 3 项（会话断开后委托是否仍在场所，未知）。
- **问题**：Gateway 是账户唯一的 TD owner。它宕机、起不来或登录失败时，所有策略都无法撤单。CTP 没有交易所层的断线撤单，活动委托会一直挂着。
- **依据**：FIA 把 Kill Switch、Cancel on Disconnect 列为交易所层最佳实践 [S13]；CME 的 kill switch 独立于交易系统（63 控制面分析 [R20]）。
- **方案**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| a | 独立的运营 CLI：取得账户锁后另登一个临时 TD 会话，查询并撤销全部活动委托（或按 Gateway 日志里的身份映射只撤某个策略的），写审计后退出 | 与 Gateway 代码解耦 | 绕过 Gateway 日志，Gateway 重启后要额外对账；身份映射要再实现一遍 |
| **b** | Gateway 以“仅撤单模式”启动（如 `--cancel-only`）：同一份日志、身份映射和账户锁；登录 → 完整查询 → 按范围（账户/策略）撤单 → 写日志 → 退出，或停在只撤单状态 | 复用全部不变量与审计；之后正常重启 Gateway 能自然衔接 | 前提是 Gateway 本身能启动（日志损坏时不可用） |
| c | 只写运维规程：用期货公司提供的终端（如快期）手工撤单，或致电期货公司 | 不写代码 | 慢、没有审计、全靠人工 |

- **建议**：以 b 为主；把 c 写进 Gateway/007 README，作为日志损坏等极端情况的兜底；不推荐 a。另把“期货公司是否提供紧急撤单服务”加入 RVX-08 清单。
- **影响**：63.12（或新增 63.14）；63.09 场景 7 增加“停 Gateway 后经仅撤单模式撤单”；63.10 文档。（问题 Q63-01）

### RV63-02（P1）D63-38 在 Gateway 下的实施参数：静默期、重复确认、查不到之后原单又出现

本条**不改变** D63-38 的决定（完整、同交易日、强身份的查询查不到 → `not_found_at_venue`，以 Rejected 通知策略，不自动重发），只补实施参数。

- **定位**：§3.6 第 5 行与“查不到”分支表、INV63-13、§3.12 的 Gateway 重启行与 CTP 前置重连行、§6.2 第 11 项。
- **问题 1：没有最小等待。** Gateway 崩溃后几秒内重启时，原单可能还在柜台处理中。如果一次查询查不到就宣布 Rejected，策略据此重下，原单随后又出现，就会形成重复敞口。
  - 迭代 62 direct 在运行中补账时，要等最后一笔发单之后的 `direct_return_gap_quiet_period`（2 s）过去才做完整读取（`backtrader/brokers/_btapi_direct_mode.py` :3118-3140 的回报缺口说明）。Gateway 计划没有对应的参数。
  - NautilusTrader 的做法：订单最近一次事件落在阈值窗口（默认 5 s）内时先不判；缺失计数到重试上限（默认 5）后先做一次定向查询，再判 REJECTED。它的理由是避免“场所还在处理”造成的误判 [S1][S3]。
- **问题 2：没有规定判定之后原单又出现时怎么办。** 62 direct 的注释写了“场所确认过的单出现矛盾时阻断该合约”，63 的分支表没有对应行。
- **建议**（写进 §3.6 分支表和 63.01 冻结清单）：
  1. **静默期**：从原单最近一次 DISPATCHING 或事件时间起，至少过 T 秒才能下“查不到”的结论。T 可配置，缺省值由 63.01 冻结，可参照 62 的 2 s 和 Nautilus 的 5 s。
  2. **重复确认**：至少连续 N 次（建议 2 次，间隔 Δ）完整同日查询都查不到，或者一次完整查询加一次按强身份的定向查询（如 provider 支持）。
  3. **迟到出现**：判定之后又按强身份看到原单的回报或查询行，仍归属原策略（不当作外部单）；该合约阻断，记为“矛盾”，通知策略和 monitor，由运营处置；不自动撤单、不自动平仓；账户合计对账要计入。
  4. **测试**：静默期内重启；两次查询之间原单出现；判定之后原单出现。
- **关于迭代 62**：同样的问题也存在于 62 direct 的启动对账——启动时一次完整查询即判（`_direct_resolve_unknown_marker` :958-978）。是否回改 62 由用户决定。
- **方案**：a 按上面三条补参数（推荐）；b 只加静默期；c 维持现状。（问题 Q63-02）

### RV63-03（P1）D63-13 静态登记会让“新增一个策略”中断整个账户

- **定位**：§4.1 D63-13（建议 a：静态登记，新增主体须重启 Gateway）；§3.12 “Gateway 重启”行（宣布就绪前全部写入关闭）；§3.13。
- **代码事实**：`TrustedServiceAuthority.principals` 与 `grants` 在构造时给定，之后不可变（SDK `bt_api_py/service_host.py:301-323`）；运行时吊销目前只覆盖行情流 grant（迭代 60 G2，`service_host.py:2319` 附近）。
- **问题**：新增或替换策略、轮换某个策略的密钥、撤销被盗的密钥，都要重启 Gateway。重启意味着新的 TD/MD 会话、全量查询与对账（SimNow 整日委托/成交约 14 行/秒，§3.8），全部策略的写入关闭到就绪为止。交易时段内实际上做不了。
- **方案**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| a | 静态登记 + 重启（计划建议） | 最简单 | 运维代价高，交易时段内无法变更，撤权也要重启 |
| **b** | 版本化的主体文件 + 运营命令热加载（如 `gateway principals reload`）。只允许新增和撤销（含收窄 grant），每次形成新的授权代际并审计；被撤销 principal 的现有连接立即断开，其在途请求按代际拒绝 | 不中断其他策略；撤权即时生效；与 64 的“授权代际”一致 | 需要在 SDK ServiceHost 加一张可变授权表（属 63.05 范围），并测试并发与撤权竞态 |
| c | 完整的运行时登记 API（任意增删改） | 最灵活 | 范围大，攻击面大 |

- **建议**：b。
- **影响**：63.05（SDK 授权表可变）；63.12、63.13（代理和 runtime principal 用同一机制）；66 的 D66-08。（问题 Q63-03）

### RV63-04（P1）S-12/D63-22：补具体问题清单，并登记 INV63-08 的解除条件

- 通用问题清单见 RVX-08。63 特有两点：
  1. **Gateway 的认证终端身份。** 监控中心规范区分直连和中继代理，AppID 含版本号 [S15]。同主机服务多个策略进程时，Gateway 是否仍算直连终端，要期货公司确认；跨主机部署（现为非目标）时可能必须走中继（RelayAppID，逐终端上报信息；社区资料 [S16]）。Gateway 升级是否要更换 AppID 或重新认证，也要确认。
  2. **INV63-08 的解除条件。** 目前以“SDK 环境标签 demo”判定 SimNow。建议同时规定解除条件：用户登记期货公司的确认记录（谁确认、确认了什么、日期）并作出决定，而不是只改配置。
- **建议**：把清单写进 §6.2 第 9 项；INV63-08 补上解除条件。（问题 QX-07）

### RV63-05（P1）D63-05 策略资金：建议沿用迭代 60 的“策略账户簿”，而不是让 getcash/getvalue 报错

- **定位**：§4.1 D63-05（建议 a：未配置分配时 `getcash/getvalue` 不可用）；§3.11 资金行；INV63-07；§3.16 `_direct_apply_balance` 行。
- **代码事实**：
  - BT 通用 Sizer 用 `self.broker.getcash()` 计算下单量（`backtrader/sizer.py:90`）。选 a，所有用缺省 sizer 的策略在 Gateway 模式下都会直接失败。
  - BT 已有迭代 60 的策略账户簿：`BtApiBroker.bind_direct_strategy_account_book`（`backtrader/brokers/btapibroker.py:1829-1880`，docstring 写明 “Ordinary Broker getters keep their account-level semantics”）、`DirectStrategyAccountBookView`、`StrategyAccountBookPercentSizer`（`backtrader/sizers/strategy_account_book.py`，按策略账户簿的现金定量，未绑定即 fail-closed），以及 `Strategy._strategy_valuation`。
- **方案**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| a | 计划建议：未配置分配时 `getcash/getvalue` 报错 | 严格符合 INV-10 | 破坏现有策略和 sizer；与迭代 60 已接受的语义不同 |
| b | Broker getters 直接返回按配置分配的策略资金与权益 | 策略代码不用改 | 改变 Broker getter 的语义；账户值和策略值走同一入口，容易误用 |
| **d** | 沿用迭代 60：Broker getters 保持账户级（文档写明）；策略级资金和权益由 `strategy.account_book` 提供，来源是 Gateway 本策略账本加配置的策略资金分配（如 `gateway.strategy_capital`，填了才启用），估值标“估计”；要按策略定量的策略改用 `StrategyAccountBookPercentSizer` 等 | 复用已有抽象和测试；不破坏现有策略；“分开入口”就满足了 INV-10 | 缺省 sizer 仍按账户现金定量，必须在 README 和启动日志中提示 |

- **建议**：d。如果用户要求更严，可以在 d 之上加一个开关：Gateway 多策略模式下，用读 broker 现金的 sizer 就拒绝启动。（问题 Q63-04）

### RV63-07（P2）账户观察流改成“流内快照 + 序号增量”；外部订单归属可参照 Nautilus

- **定位**：§3.7 账户观察流、§3.8 一致切点、§3.11 账户合计对账；64 设计 §5 的“同一切点”要求。
- **建议**：
  1. **流内快照**：Gateway 是归属账本的唯一写者，可以在写账本的同一个 SQLite 事务里，往观察流写一条带流序号 N 的“账本快照事件”；消费者从快照 N 起按序号应用增量。对 Gateway 自有的事实（策略账本、在途、急停），一致切点由构造保证；64 risk 和 BT 对这部分事实的“共同切点”问题就解决了。
  2. **场所事实**（CTP 持仓、成交查询）仍按 §3.8 的 NOT_COMPARABLE 规则只用于对账，不进入“一致切点”的承诺。
  3. **外部订单归属**：D63-09 a 可参照 NautilusTrader 的 external order claim [S1]：运营可以把某合约的外部单显式认领给某个策略（留审计），否则一律记外部残差。
  4. **说明取舍**：Kungfu 在本地与柜台不一致时会自动同步重置 [S6]；63 选择阻断后由运营分类，更保守。建议在 §3.11 写明不采用自动重置的理由。

### RV63-08（P2）Gateway 日志：持久性、备份和丢失后的重建流程

- **定位**：§3.12 末行“Gateway 日志损坏或丢失：拒绝启动交易 owner，需人工”；设计 §8 只提到迁移前备份。
- **问题**：日志是多策略归属的唯一权威，但丢失后“需人工”没有可执行的方法。
- **建议**：
  1. SQLite 用 WAL 与 `synchronous=FULL`，并写明磁盘故障时 fail-closed 的行为；
  2. 用 SQLite backup API 在线备份到另一个目录或磁盘：日切完成、`day_ready` 之后各一次，另加运营命令；
  3. 按交易日归档；
  4. 写出重建规程：用各策略 `live_state` 中已 attach 的原生身份（§3.6 第 8 行）、完整当日委托和成交查询、最近一次备份重建当日归属；运营逐项确认后才开放写入；不能证明的部分记外部残差。
- **方案**：a 备份 + 重建规程（推荐）；b 流式复制（类似 Litestream），超出本迭代；c 维持现状。（问题 Q63-05）

### RV63-10（P2）D63-36 的 ACK 文字冲突：建议的解法

- **冲突**：§3.14 写 monitor“经中继的消费确认通道回传 ACK”；§4.0 D63-36 写 monitor“不向 Gateway 发任何东西”。设计 §6 和 68 §3.4 都登记为未裁决。
- **建议**（与 RV68-01 一致）：把 ACK 定义为 **monitor 持久入口对中继推送请求的响应**。中继向 monitor 发请求，monitor 只回响应，从不主动连接或发送。这样两处文字可以同时成立：monitor 不发起任何消息，Gateway 又能从响应中得到“该心跳已被 monitor 持久接收”的证据。存活的判据是：最近一条被持久接收的心跳，其发出时间在配置时长内。
- **补充**：即使不开 `monitor_required`，也在 `session_status` 中公布“monitor 最近一次确认距今多久”，供运营和 runtime 显示，解决“谁来监控监控”的问题。

### RV63-11（P3）一致性与小项

1. **D65-26 没有回写正文。** §2.2“Gateway 不做任何轧差，每个策略的订单原样转发”、INV63-04、§3.11“由已归属成交增量更新”与 D65-26 冲突；计划正文和计划修改记录都没登记（只有设计 §5.1 登记了）。建议：

   - 63.03 的账本表从一开始就用带来源类型的分录（场所成交 / 分配 / 内部转移 / 运营调整 / 日切），扩展启用前只写场所成交，免得以后迁移。

3. **平今平昨规则。** VeighNa 的开平转换器同样把 SHFE/INE（必须指明平今平昨）与其他交易所分开处理 [S10]。社区资料称其他交易所自动优先平今，但没有经交易所原文核实，与 §6.2 第 6 项一致：仍按“provider 事实，须核实”处理。
4. **统一 D63-36 的文字**：§3.14 与 §4.0 按 RV63-10 统一。（问题 Q63-07）

### RV63-12（P2）不开 risk 时的自成交风险：只建议加观察计数，不改 D63-23

- D63-23 已决定：不选 risk 时不考虑自成交，属已知功能缺失。本条不建议在 Gateway 拦截。
- **事实提醒**：交易所把单日单合约自成交 ≥ 5 次列为异常交易，实际控制关系账户合并计算（第三方整理 [S18][S19]）。同一账户上多个策略交易同一合约时，一方的挂单被另一方的反向单成交，就构成自成交。
- **方案**：

| 方案 | 做法 |
| --- | --- |
| a | 只在 007 README 和 Gateway 启动日志中明确提示“未选 risk 时没有自成交保护” |
| **b** | Gateway 已按账户、合约、交易日公布原始报撤单计数（§3.10），可以再公布“同账户反向可成交挂单”和“已发生的同账户双方成交”两项观察计数，只观察、不拒单，供 monitor 告警（属可观测性，不属风控） |
| c | 维持现状 |

- **建议**：b。（问题 Q63-06）
