## 3. 租约过期 DRAIN 的完整实现（D63-52，I63-E128）

第三十九轮的结论是：这种原因一旦施加就无法解除（没有恢复证明来源），计划要求的过期时长也没有实现，资源包选项因此撤回。本轮补齐三部分。

### 3.1 过期时长（D63-28：必填，无缺省值）

Registry 在策略租约过期时记录一条事件，状态为 `WAITING`，并记下“过期时刻＋配置时长”。到这个时刻事件才变为 `PENDING`，之后的行为与原来相同：拦住该策略的新委托，直到 owner 把 DRAIN 原因写入 journal。策略在此之前重新注册，事件变为 `RETURNED`，不施加任何原因。时长为 0 时与原来的行为一致。

- 时长由受信的 owner 配置传入，没有缺省值；缺失、非数值、负数、超过 86400 秒都被拒绝；运行中不能换成另一个值。
- 旧版本写下的事件表没有这一列，配置时补上；旧事件保持原状态。
- 只有同一策略的注册能撤回等待中的事件；其他策略注册不影响它。已经 `PENDING` 的事件不会因为策略回来而撤回。

这里把计划中的“过期满配置的秒数后自动对该策略施加 DRAIN”理解为：从租约过期时刻起算，策略在这段时间内回来就不施加。这是开发侧的理解，没有另外向用户确认。

### 3.2 CTP 恢复证明来源

`GatewayLeaseRecovery` 原有的本地条件不变：策略已有新的注册（同一主体、同一策略、同一 run id）、它的回报流已经确认到最新一条事件、它没有未决的命令和撤单。新增的 `CtpGatewayLeaseRecoverySource` 在 owner 线程上给出只有 provider 一侧才能说明的事实，不做任何柜台或网络调用：

- 完整：当前原生会话的回报维护是连续的（当日两类全量查询都已完成，此后没有断档、过期来源或失败批次）。
- 同一切点：回报缓冲里没有等待处理的回调；缓冲的最后序号、原生会话代际和交易日共同标识这个切点。提交前再核对一次，期间有回调到达就放弃。
- 该策略的回报没有遗漏：当日在该策略可交易的合约上，没有任何回报仍处于未归属或冲突状态。这一条是偏保守的：同一合约上的手工交易也会让原因保持不解除（当前 profile 没有安装能区分外部交易的分类器）。

来源在 owner 构建回报维护时绑定；未绑定、不在 owner 线程、或任何一条说明不了，都不给出证明，原因保持。

### 3.3 自动解除与人工解除（D63-33）

- 缺省自动：桥在每个维护周期对仍然有效的租约原因尝试一次解除，同一原因两次尝试至少间隔 1 秒。证明不成立是常态（策略还没回来或还在恢复），不记为组件故障。owner 忙时这一步推迟，不排队、不阻塞 host。
- 可配置人工：`automatic_resume` 为 false 时桥不尝试，由运营执行 `resume`，使用同一份证明；证明不成立时返回 `RECOVERY_REQUIRED`。
- 两种方式都只解除这一条原因的这一版本，其他原因（运营施加的、UNKNOWN 等）不受影响。

`controls.lease_drain`：`{"strategies": [...], "expiry_seconds": <数值>, "automatic_resume": <布尔，可省略，缺省 true>}`。不写这一节就是关闭。`expiry_seconds` 缺失时资源包被拒绝。说明见 SDK `examples/services/ctp-gateway-simnow-trading.example.md`。

## 5a. Gateway 仅撤单启动（D63-58）

命令：`bt-gateway-operator --config <启动配置> --cancel-only --operator <运营标识> --reason "<原因>"`。

做法：

1. 与正常启动使用同一套存储检查、账户会话锁、身份和 journal。上一个 Gateway 还活着时被锁拒绝；异常退出之后要先做会话核对（`--reconcile-session`）。
2. 在 host 开始服务之前，先在 owner 线程把一条账户级 DRAIN 原因（`cancel-only:<本次运行号>`）写入 journal。此后所有策略的新委托都被 `CONTROL_DRAIN` 拒绝；策略仍可撤自己的单。写入失败则启动失败。
3. 等当前会话的回报连续之后才开始撤单，这样已经结束的委托不会再被撤。
4. 每个维护周期撤一笔仍在途的委托，走已有的“控制原因撤单”路径（journal v17）；撤单凭证里记录运营标识和本次运行号。发送结果未知的委托不盲撤，已经发出的撤单不重发。
5. 全部目标都观察到终态时为 `COMPLETE`，退出码 0；120 秒内没有做到为 `INCOMPLETE`，journal 低于 v17 为 `UNAVAILABLE`，退出码 3。结束时打印一行计数，然后像普通停止一样退出。
6. 这条原因在运行结束后保持有效，重启也不会消失；之后正常启动仍不接受新委托，直到运营在账户范围 `resume`。

命令不覆盖的情形（拒绝启动、`UNAVAILABLE`、`INCOMPLETE`、journal 损坏、委托不是经本 Gateway 下的）按书面规程由人工在期货公司客户端撤单，规程写在 SDK `examples/services/ctp-gateway-simnow-trading.example.md` 的“Emergency”一节。

测试：`tests/unit/test_iter63_gateway_cancel_only.py`（运行本身，19 条）与 `test_iter63_gateway_cancel_only_start.py`（命令行、应用、工厂、profile、host，22 条）；变异检查 33 项全部被发现；SDK “iter63、lease、registry、operator、host、cancel”选择 2003 passed、59 failed、8 errors，失败集合与修改前的快照逐项比较没有新增。

Gateway 的 journal（schema 14 起）本来就能保存并对外提供"策略资金快照"，BT 的 `broker.get_strategy_cash(strategy)` / `get_strategy_value(strategy)` 也已经会读，但一直没有东西生成快照。本轮补上了 CTP 的生成方：

| 部分 | 文件 | 内容 |
|---|---|---|
| 费率文件 | `bt_api_py/strategy_rates.py`，模板 `examples/services/strategy-rates.example.yaml` | 一个账户一个本地 YAML：按品种（可按合约覆盖）给出合约乘数、多空保证金率、开仓/平仓/平今手续费（每手金额＋成交额比例）。文件里没有的品种没有费率，不按 0 处理 |
| 计算模型 | `bt_api_py/strategy_financial_model.py` | 只用本策略自己的成交逐笔计算：多空分开，平仓对本方向持仓均价结算已实现盈亏；持仓按最新价算浮动盈亏和保证金；在途的开仓委托按限价预留保证金和开仓手续费，平仓委托不预留 |
| 生成方 | `bt_api_py/ctp_gateway_strategy_financial.py` | 在账户线程上运行；每次只读 journal 里新增的委托和回报；金额变化时写一条快照，有持仓时至少每 `refresh_seconds` 刷新一次 |
| 最新价 | `bt_api_py/gateway_owner_market.py` 新增 `event_observer` | 用 Gateway 自己行情连接收到的最新价，所以只有某个策略经 Gateway 订阅了的合约才有价格 |
| 配置 | `bt_api_py/ctp_gateway_local_profile.py` | 资源包新增可选段 `strategy_financial`（见 5b.2） |

权益 = 初始金额 + 调整 + 已实现盈亏 + 浮动盈亏 − 手续费；可用资金 = 权益 − 持仓保证金 − 在途开仓委托的预留。

### 5b.2 三项决定怎样落到配置上

```json
"strategy_financial": {
  "rates_file": "/绝对路径/strategy-rates.yaml",
  "currency": "CNY",
  "budgets": {"<策略标识>": "600000.00"},
  "adjustments": [{"id": "2026-11-12-a", "strategy": "<策略标识>", "amount": "-100000.00"}],
  "refresh_seconds": 60,
  "price_max_age_seconds": 180

```

- D63-53（固定金额）：`budgets`。没有列出的策略没有资金数字，没有缺省值，也不按账户余额分摊。每个键必须是本资源包里某个策略客户端的策略标识，写错在启动时报错。初始金额一旦写入某策略的记录就不能再改，改了该策略报 `INITIAL_BUDGET_CHANGED`、不给数字。
- D63-54（改配置、重启生效）：`adjustments`，每条有自己的 `id` 和带符号的金额，重启 Gateway 后生效；没有运行时命令。条目要一直保留在列表里，删掉一条等于下次启动时把这笔钱收回。
- D63-55（共用费率文件）：`rates_file`，启动时读一次，改了要重启才生效。

**与提问时的说法不一致的地方（需要用户知道）：** 提问 D63-55 时选项文字写的是"每个策略的 config.yaml 只写费率文件路径"。实际实现里资金是在 Gateway 进程里统一计算的，所以费率文件路径、初始金额、调整记录都只写在 Gateway 的资源包里（一处）；策略的 config.yaml 不写路径，只需要 `strategy_finance_currency: CNY` 并申请 `direct.strategy_financial`。原因：成交和在途委托的完整记录在 Gateway 的 journal 里，由各策略进程各算各的会出现几份不一致的数字。

**没有问过用户、由我定的三点：** 合约乘数也从这个费率文件读；最新价超过 180 秒不再使用（`price_max_age_seconds`，可配）；有持仓时至少每 60 秒刷新一次（`refresh_seconds`，可配）。

### 5b.3 什么时候不给数字

缺任何一项输入都不给数字（策略一侧 `get_strategy_cash` 抛 `GATEWAY_STRATEGY_CASH_UNAVAILABLE`），不用 0 或旧值顶替；Gateway 日志在原因变化时写一次：

| 日志里的原因 | 含义 |
|---|---|
| `RATES_UNAVAILABLE` | 成交或在途委托的品种不在费率文件里 |
| `VALUATION_PRICE_UNAVAILABLE` | 持有的合约没有可用的最新价（没人订阅，或价格超过最长时限） |
| `UNATTRIBUTED_TRADE_ON_INSTRUMENT` | 本策略交易过的合约上有一笔成交还没有归属到任何策略 |
| `RETURNS_NOT_CONTINUOUS` | 回报流不完整（启动初期、断线重连期间） |
| `WORKING_ORDER_PRICE_UNAVAILABLE` | 在途的开仓委托没有限价 |
| `TRADE_ATTRIBUTION_NOT_MATCHED` | 成交的归属不是普通匹配（例如记录为"未发出"的委托后来出现成交），与策略持仓台账同一条规则 |
| `POSITION_UNDERFLOW` | 平掉了本策略成交记录里没有开过的仓 |
| `INITIAL_BUDGET_CHANGED` | 资源包里的初始金额与已有记录不一致 |
| `HISTORY_LOADING` | 启动后正在分页读取历史 |

### 5b.4 已知限制

1. 手续费和保证金是按费率文件估算的，不读柜台，数字的准确程度取决于费率文件。
2. 持仓如果来自策略台账的"基线声明"（不是 journal 里的成交记录），没有成本价，该策略没有资金数字（表现为 `POSITION_UNDERFLOW`）。
3. 每次因价格刷新产生的变化都会在 journal 里写一行快照；`refresh_seconds` 不宜设得比策略需要的更小。
4. 公开示例还没有用到策略资金（示例下单仍是固定手数）。
5. 资金数字目前只用于策略读取，Gateway 接受委托时不按它拦截。

## 5c. 来源不明的回报只阻断该合约（D63-59）

状态：源码完成并有测试（gateway 仓 `0e0e495`、SDK `cbe88b4d` 和 `b07e832c`，均仅本地）；剩余限制见 5c.3。按计划 §6.3，外部账本相关场景在 SimNow 上不新增实际账户调用，所以本项没有 SimNow 下单验证；下午盘的 Gateway 带着这项功能运行，用来确认正常交易时不会误阻断。未标记 ACCEPTED。

### 5c.1 做了什么

此前，一笔 Gateway 无法归属到任何委托的成交只会让该合约的"策略可平量"不可用（平仓被拒），开仓照常放行。按决定改为：

1. **急停原因增加"合约"范围**（gateway 仓 `direct_control.py`）。原来只有账户、策略两种范围；新增的合约范围写作 `<交易所>:<合约>`，只能是 FREEZE：该合约上所有策略的新委托（开仓、平仓）在预留和派发两处都被拒绝（`CONTROL_FREEZE`），其他合约不受影响；撤单不是新委托，不受影响。没有改 journal 表结构（范围类型和范围值本来就是文本列）。旧版本 Gateway 打不开含有合约原因的 journal（journal 不降级）。
2. **自动检测**（SDK `bt_api_py/gateway_instrument_block.py`）。账户线程上约每秒检查一次：某合约上有归属不明或冲突的成交/委托回报、且还没有对应的原因时，写入该合约的 FREEZE 原因并打一条警告日志（写明合约和原因编号）。原因写在 journal 里，重启后仍然有效。
3. **自动解除**。如果这些回报后来被 journal 归属了（例如成交回报比委托回报先到），检测器自己解除并写日志。
4. **运营解除**。有全账户权限的运营在 `direct.control.list` 里能看到合约原因（与账户自己的原因在同一页），用原有的 `direct.control.resume` 解除，解除记录带运营身份；只有某个策略权限的运营看不到也解除不了。如果该合约上还有 Gateway 自己发出的、结果未知的委托（派发中或 UNKNOWN），解除被拒（`CONTRACT_ORDERS_UNDECIDED`），因为那些回报可能正是这张委托的。
5. 原因编号里包含"当时那批回报"的摘要：运营解除后，同一批回报不会再次触发；该合约再出现一笔新的不明回报，会重新阻断。

只要配置了急停（`controls`），这项功能就自动开启，没有单独的开关。

### 5c.3 解除之后：把这批成交记为外部成交（SDK `b07e832c`）

第一版（`cbe88b4d`）里，运营解除后只有新开仓恢复，策略在该合约上的持仓和可平量仍然不可用，平仓继续被拒。午休后半段补齐：

- 运营解除后约一秒内，检测器把"当时那批回报"里的成交交给策略账本，记入 journal 的外部账本；每条记录写明是哪一个原因、哪一次运营解除。
- 策略账本只为这样的记录作保（必须是本检测器的合约原因、合约一致、由运营解除而不是检测器自己解除）。此后各策略在该合约上自己的持仓和可平量恢复可用，平仓放行；账户对账把这些成交算作外部持仓（账户 = 各策略 + 外部）。
- 该合约上还有 Gateway 自己发出的、结果未知的委托时，不记录（那些成交可能正是这张委托的），日志写明原因。
- 策略资金（5b）同样把已记为外部的成交视为已了结，不再因此不给数字。

测试 `tests/unit/test_iter63_instrument_release_external.py`（8 个用例，真实 journal 加策略账本夹具）：阻断 → 运营解除 → 记为外部 → 可平量恢复 → 对账 MATCH（策略 1 手、外部 1 手、账户 2 手）；再来一笔不明成交重新阻断且不算外部；不明委托不需要记录；没有运营解除作依据的外部记录不被承认；有结果未知的自有委托时拒绝记录；策略资金先不给数字、记录后恢复。变异检查 18 个被检出，另有 6 个存活变异指向被其他检查覆盖的多余判断，已删除这些判断。相关测试合计 158 通过。

仍然存在的限制：

1. 冲突类回报（同一成交编号内容不同）不能记为外部成交，解除后该合约的策略持仓仍不可用，需要人工排查。
2. 记录外部成交需要策略账本和账户扩展（journal schema 12 及以上）。没有时，解除只恢复开仓，Gateway 日志说明原因。
3. 没有 SimNow 下单验证（计划 §6.3：外部账本场景在 SimNow 上不新增实际账户调用）。
