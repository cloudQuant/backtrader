1. **建立可证明的派发与撤权栅栏。** 审计 Registry、账户 journal、母子单、市场数据、时钟、CTP TD/MD、控制、所选 Risk 和 session 的全部可达写者；在每个状态可见改变前使同一 Base core 的相应域失效。签发后绑定应使用带活动 token 的 `attach_writer_handle`，绑定失败 poison，绑定完成发布 `UNAVAILABLE`。同一短锁中完成版本复核、唯一 claim 与撤权次序；原生调用放锁外。已 claim 的请求保留在途身份。
2. **接通账户级结算授权，而不是策略级授权。** `WriteAdmission.revoke()` 只撤已有 grant，不会永久禁用后续发放；账户确认不经过某个策略的 Registry permit。先持久化当日唯一 marker，再 capture、核验、capture、claim；确认丢失、崩溃或结果不明按 marker 原身份回读。订单 `UNKNOWN` 本身不解除，也不自动阻止结算。应覆盖 route、账户、owner/session generation、provider/Trader/API/SPI、交易日、grant、观察和全部 marker 写者。
3. **解决存储与账户事实来源。** 已用隔离数据库复现：有目录替换能力的本地进程可在连接打开时替换同 anchor 的 SQLite 文件并在复核前复原，路径与 anchor 检查不能证明 SQLite 实际打开的文件。该复现不证明远程攻击。当前候选对账接口故意返回 `UNAVAILABLE`。需确定并实现可信 VFS/句柄证明或具有明确 OS 强制隔离的部署信任模型，覆盖主库、WAL、SHM、恢复和其他 journal 写者；不要以 0700、同 UID 的独立进程或自报配置代替证明。CTP 全账户覆盖、合约来源及共同切点仍须证明；缺失时保持 `NOT_COMPARABLE`，不能自动解除对应 DRAIN。
4. **恢复与运行维护。** 订单/结算 marker 崩溃切点、owner 原生调用长期阻塞、重启去重、close 未确认时资源保留、控制请求可用性、容量与告警、事实流自动压缩和规模压力均待完成。claim 的命令及 writer 记录目前有容量上限但没有已证明安全的运行期回收；清理失败成功闭锁时首次诊断可能不显示该故障。
