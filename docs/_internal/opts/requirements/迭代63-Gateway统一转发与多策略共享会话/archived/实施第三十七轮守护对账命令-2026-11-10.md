## 2. 实现（本地 dev，未推送）

- Gateway 子仓 `9fd9199`：
  - `reconcile_abandoned_account_session` 以非阻塞方式取得守护文件的 OS 锁，证明旧 owner 已不存在，且期间无 owner 可启动。
  - 阻塞证据任一项非零即拒绝（`SESSION_RECONCILIATION_BLOCKED`，并附计数）。
  - 先追加 0600 审计记录（操作者、原因、时间、被放弃的 generation、证据计数），再把记录改为 closed。
  - `inspect_unresolved_dispatch` 以只读方式统计 journal 中三类未决条目：DISPATCHING/UNKNOWN 的下单命令、同状态的撤单，以及 ATTEMPTING/UNKNOWN 的结算确认。journal 不属于该账户时拒绝。
- SDK `91d5ded4`：
  - CTP 交易 profile 工厂提供 `reconcile_session` 钩子，先做与启动相同的存储隔离检查。
  - 新增命令 `bt-gateway-operator --reconcile-session --operator <id> --reason <text>`，只输出状态、证据计数与账户摘要前缀。退出码：成功 0、拒绝 3、配置错误 2。
- SDK `a66276b9`：异常退出后重启原先只报 `RESOURCE_CONSTRUCTION_FAILED`（经 Host 时为 `RESOURCE_RESOLUTION_FAILED`），运营者无从得知下一步。原因是守护拒绝发生在 owner 线程，owner 只记 `factory_failed`。现在 owner 工厂保留该有限码，启动以此报错；构造错误与组件解析按允许清单透出 `SESSION_RECONCILIATION_REQUIRED`、`SESSION_ALREADY_OWNED` 与原有的 `MONITOR_INCOMPATIBLE`。
- SDK `906f25ca`：运营示例文档补充异常退出后的对账步骤。
- 测试：`tests/unit/test_iter63_session_reconciliation.py`（30 例），`tests/integration/test_iter63_session_reconciliation_owner.py`（真实交易 profile 子进程：异常退出后启动报对账码，对账后启动就绪）。
- 变异检查：以下改动均使测试失败：
  - 去掉证据检查；
  - 不取锁；
  - 不写审计；
  - closed 也视为需对账；
  - journal 不计 DISPATCHING；
  - 三处错误码透出任一处还原。

## 4. 限制

- journal 若有 DISPATCHING/UNKNOWN 命令或在途结算，命令按决定拒绝且不提供覆盖选项。Gateway 也无法启动以进行常规恢复，运营者须先在交易所核对账户。是否需要“已人工核对”的后续路径，须由用户决定。
- 只检查本机同一守护目录，不是分布式锁。
