### 1.2 Gateway 现在转发什么

- **只转发行情。** `ctp_gateway_composition` 组装的 Gateway 角色是 `market_hub`，授权操作只有 `market.*`（`bt_api_py/ctp_gateway_composition.py:52-58`），账户引用固定为 `account:bt-ctp-gateway-market-only`（`:49`），且只登记一个客户端 principal（`:226`、`:242`）。
- **每个策略各起一个 Gateway。** 每个 `_gateway` 示例的 `run.py` 在每次运行时以子进程启动本目录的 `gateway_host.py`，经管道取得本次生成的 CURVE 连接（`examples/live/007_ctp/*_gateway/run.py:137-157`）。N 个策略即 N 个 Gateway、N 个 CTP 行情会话。
- **策略进程仍自己连 CTP。** `create_store` 把 SimNow 账号、密码放进 `exchange_kwargs`（`run.py:176-212`，`:185`）；`BtApi` 在注册 route 时据此构造本地 CTP feed（`bt_api.py:5879-5894`），direct provider 首次使用时经该 feed 打开 TD 会话（`direct_write_provider.py:524-534`）。即使行情来自 Gateway，`BtApi.market_tick_projector` 仍要求本地 provider feed 作为 route 客户端（`bt_api.py:4135-4142`，`_selected_provider_route` 在 `:4449-4458`）。
- **托管下单关闭。** `--orders managed` 在读取凭据前返回 `managed_gateway_execution_unavailable`（`run.py:50-55`、`302-311`）；`gateway_host.py --managed-boot-check` 只启动/关闭托管运行时（`gateway_host.py:255`）。
- 结果：每个策略至少 1 个 TD 会话（策略进程自己）+ 1 个 MD 会话（它自己的 Gateway 子进程）；同一账户 N 个策略 = N 个 TD 会话。策略进程本地 feed 是否另开 MD 会话未逐行核实（63.01 核对）。这正是原话 2 所说的会话数问题。007 README 也要求不要让 `_direct` 与 `_gateway` 文件夹同时交易同一账户同一合约（`examples/live/007_ctp/README.md:194`）。

### 1.4 与用户意图冲突或不足之处

1. **62.08 的目标表述与原话 3 冲突。** 迭代 62 计划 §3.1 与 62.08 写“BT 通过 Gateway 使用 CTP 行情与托管执行运行时”（`迭代62-问题修复/迭代计划.md:86`、`:570`）。托管运行时组合强制依赖 `bt_api_execution` 的执行库和 `bt_api_risk` 的 `DurableRiskGate`（`bt_api_py/ctp_gateway_execution.py:275-387`），且只服务一个账户的一个合约（`:19-23`）。按原话 3，基础转发归 Gateway，execution 只负责执行功能与算法。62.08 的修改由主会话记入迭代 62 计划修改记录，本计划只引用。
2. **架构文档把派发和 UNKNOWN 归给 execution。** `docs/TRADING_SYSTEM_ARCHITECTURE.md:84` 把“本地订单意图、派发、恢复与 UNKNOWN”的权威归 `bt_api_execution`；SDK README 写明“this SDK does not provide a separate forwarding runtime”（`bt_api_py/README.md:44`）。按本迭代设计，经 Gateway 的基础转发的派发记录归 Gateway，需在 63.10 随用户决定更新。
3. **现有 Gateway 命令路由按账户串行。** `GatewayCommandRouter` 的非 READ 命令必须有 `GatewayAccountWriterAuthority`（`bt_api_gateway/router.py:325`）；后者在账户上**任一**先前动作未解决时拒绝新动作（`writer_authority.py:335-351`），而执行器返回一律记为 `returned_unverified`、属于未解决（`:100-105`）；只有经 provider 查询验证器记录解决才能继续，但包内“no real provider verifier or registered runtime is shipped”（`bt_api_gateway/README.md:189`）。原样复用会让同一账户的所有策略一次只能有一笔命令。
4. **Gateway 读模型不做策略归属。** 账户视图策略“does not filter by strategy order ownership or allocate virtual positions”（`bt_api_gateway/README.md:142`）；执行观察的策略路由依赖客户端号前缀（见 §1.3）。

## 2. 目标、非目标与新增规则

### 2.1 目标

1. **一账户一会话。** 每个 CTP 账户由一个 Gateway 进程持有唯一的 TD 会话（交易与全部账户查询）和一个 MD 会话；同一账户上的多个策略进程共享它们。
2. **Gateway 统一转发。** Gateway 转发行情、账户信息（持仓、活动委托、当日成交、资金、交易权限、会话与结算状态、回报）和下单/撤单命令；BT 的进出信息先经 Gateway（原话 3）。
3. **策略进程不连交易所。** 选 Gateway 时，策略进程不构造 CTP feed、不加载 CTP 原生库、不持有 CTP 凭据（原话 2）。
4. **复用 direct 合同。** BT 仍经 `BtApi.make_order/cancel_order` 下单，SDK 为该 route 提供经 Gateway 的 provider；BT direct 模式尽量少改。
5. **同合约多策略。** 同一账户的多个策略可交易同一合约（U63-1），按策略记账，并做账户级合计对账。
6. **崩溃安全。** 策略侧与 Gateway 侧各有派发前耐久记录，任何崩溃点都可按原身份恢复，结果不明保持 UNKNOWN（INV-06）。
7. **示例。** 11 个 `_gateway` 示例去掉混合方式和 `--orders managed`，全部经共享 Gateway（U63-2）。
8. **验收。** SimNow 上 1 个 Gateway、2–3 个策略进程共用一个账户（含同一合约），并提供会话数证据。在 S-12 确认之前只用 SimNow（D63-22，INV63-08）。
9. **急停。** Gateway 持有并执行急停状态（D63-19、D63-24）：FREEZE、STOP_NEW、DRAIN、RESUME，范围为账户、策略、合约；撤单永远放行并保留容量；按 D63-25 区分自动解除与须由运营 RESUME 的原因；按 D63-28 提供可按策略开启的“租约过期自动 DRAIN”（§3.17）。
10. **为迭代 64、65、66 提供 Gateway 侧能力**（D63-15：Gateway 相关的开发都在本迭代）：代理 principal（risk 服务、execution 服务代表策略行事）、调用方幂等键、`origin`/`parent_ref`/`child_id` 字段与回报标签、供 risk 服务使用的账户观察流与行情 principal、控制端口（运营、runtime、risk 服务提交急停命令）、母单委托信封（D65-01 已定登记顺序，身份与授权合同待冻结）、monitor 事件中继与 `monitor_required` 存活判定（§3.14、§3.18）。64、65、66 不再修改 `bt_api_gateway`。
11. **词汇统一。** 按 D63-27 把现有代码中的急停词汇改名为同一套（§3.19）；本迭代负责 `bt_api_base` 的中立词汇与 `bt_api_gateway` 的部分，其余部分由迭代 64、65 负责。

12. **独立前端（D63-47）。** 提供可独立启用的 Gateway 页面，展示会话、账户/策略、订单和急停原因，支持服务端授权的既有运营管理；与未来 ai-for-investor 复用版本化 API。页面关闭不停止 Gateway，不把 Monitor 变成控制入口（§3.21、63.14）。

### 2.2 非目标

- 反向轧差、拆单与算法调度：归 `bt_api_execution`（迭代 65）；Gateway 不计算轧差或算法，转发经基础授权和归属/映射校验的真实账户订单。D65-31 明确同向母单及轧差后余量分别下场，实际子单唯一绑定发起母单/策略；本期不提供跨母单共同场所子单、真实成交份额分配或共同撤单。按 D65-26/27，本迭代提供反向转移双方/多方授权、虚拟策略账本、内部转移及转换映射的权威原子提交；抵消部分不送场所。经济算法归 65，Gateway 侧全部归本迭代（目标 10）。
- 业务风控政策与风控检查：单笔上限、价格带、自成交、报单/撤单计数阈值、超出归属的可平容量、资金/保证金可负担性（D63-18、U63-8），归独立的 `bt_api_risk` 服务（迭代 64）。Gateway 不调用 risk，也不检查订单是否带有风控批准（D63-16、D63-17）。不选 risk 时没有这些控制，跨策略自成交保护缺失是已知的功能缺失（D63-23）。
- direct + risk、direct + execution、direct + monitor：不存在（D63-20）。
- monitor 发出的控制命令：monitor 只观察（D63-21）。Gateway 自己的授权管理页面按 D63-47 交付；当前不实施 ai-for-investor 集成。
- SimNow 之外账户的 Gateway 写入（D63-22）。
- 托管执行运行时的六项生产缺口：不再作为本路径的前置（映射见 §7）。
- OKX/Binance 的 Gateway 共享会话与交易转发留待后续（D63-10）；不取消已有 direct 路径，也不由此宣称其行为已通过。跨主机部署（策略与 Gateway 不在同一主机）、Gateway 高可用/主备、同一账户多个 Gateway 不在本期。统一 SDK 与 Base 中立合同保留 provider 扩展点，CTP 原生字段及语义归 CTP provider。
- 生产账户验证；改变 direct 账户写入规则；迭代 70 的回测多策略。D63-41 明确改变公共查询默认作用域，相关 direct 框架投影和调用者须同步迁移/回归，不改变原生写入授权。

## 3. 方案比较与推荐设计

### 3.1 方案比较

| 方案 | 做法 | 会话数 | 复用与改动 | 依赖 | 主要问题 |

### 3.3 会话归属

- **已确认：每账户一个 Gateway 进程**（D63-02，2026-11-08），持有该账户唯一的 TD 会话（交易、持仓/委托/成交/资金查询、结算、权限）和一个 MD 会话。策略进程只连 Gateway。R07 按[单一会话与 operator 装配合同](分轮合同冻结稿-2026-11-08.md#10-r07-单一-ctp-会话与交易-operator-装配)推进工厂，不表示完整服务已验收。
- **同主机互斥**：交易 owner 启动时取得按账户的主机级锁（复用 `account_coordination.HostAccountRegistry` 或 `session_guard` 的 OS 锁），第二个 owner 拒绝启动（INV63-02）。跨主机、其他终端和仍以 direct 模式运行的 BT 进程不受此锁约束，只能经未归属回报被发现（§3.7）。
  2026-11-07 补充（审阅发现 5；现状见 §1.5 第 6 项），63.01 冻结三点：
  1. **规范账户身份**：provider、环境、broker 与 user 规范化后的哈希。写明规范化规则（大小写、空白、前导零等）并测试别名。与 `HostAccountRegistry` 二选一或统一为同一个键，避免两套机制互不排斥。
  2. **受信根目录**：Gateway 配置的必填项，不用每用户家目录或系统临时目录作缺省。多个 OS 用户运行 Gateway 时须共用该目录及其权限，否则不保证互斥。
  3. **CTP 交易流文件目录**：现按（broker、user）放在系统临时目录，改为随账户放到受信根目录下，不与其他进程共用流文件。
  测试：不同根目录、不同 OS 用户、账户别名、残留锁（`SESSION_RECONCILIATION_REQUIRED`）与崩溃后接管。
- **进程边界（D63-08，2026-11-08）**：Gateway 作为独立服务进程启动；策略仅由自身 config.yaml 连接远端服务，不内嵌交易 owner，也不在失败后回退本地 TD。
- **部署形态**：按每账户独立进程决定，由一个 `trading_owner` 角色逐步整合命令、账户读取和行情服务；SDK 的 operator/Host 网络线程与账户原生 owner 线程分工。R07 首先接命令资源工厂和共享会话，完整账户/行情端口仍待交付。复用迭代 60 的查询与行情组件，但不启动其另建 TD 的只读账户 worker/profile；网络线程不能直接调用线程绑定的 native provider，不能用两个各自创建会话的部署替代共享账户 owner。
- **行情键集合**：MarketHub 的键全集和每 principal 允许的键在构建时给定（`ctp_gateway_composition.py:256-257`）；本迭代取所有已登记策略合约的并集，静态配置（与 D63-13 一致）。

### 3.4 OrderRef 与订单身份

- **OrderRef 在派发时分配，不在预留时分配。** CTP 要求同一会话内 OrderRef 唯一且递增（provider 注释 `ctp/client.py:11661-11664`）。两阶段派发下，策略 A 先预留、策略 B 后预留但先派发是常态；若在预留时分配，派发次序与 OrderRef 次序会不一致。CTP 是否拒绝乱序 OrderRef **未在本仓库实测（UNKNOWN）**，设计不依赖这一未知：Gateway 在每会话的派发锁内分配 OrderRef、写入耐久记录、再发送，因此派发次序与 OrderRef 次序一致。这要求 provider 增加“预留不含 OrderRef、提交时分配”的入口（63.04），direct 路径的现有行为保持不变。
- **身份链**：策略（UUID、局部序号、`Order.ref`）→ 调用方幂等键 `request_key`（策略直连时由策略 UUID 与局部序号派生；risk 服务转发时沿用同一键；execution 子单为 `child_id`）→ 预留号 `reservation_id`（Gateway 生成的 UUID4，预留时即持久）→ 原生身份（交易日、FrontID、SessionID、OrderRef；派发时持久）→ 场所身份（ExchangeID、OrderSysID，按交易日绑定，见 R-3 F1）。`request_key` 让转发方（risk 服务、execution 服务）在请求发出后、回复到达前崩溃时，仍能按键查询该预留（迭代 65 计划 §1.6 第 6 项；迭代 64 计划 §4.3）。
- **不按策略划分 OrderRef 号段**：号段前缀会破坏会话内递增。BT 生成的 `client_order_id`（`bt{uuid12}s{seq}`，`_btapi_direct_mode.py:1630-1656`）只作请求摘要；CTP 的客户端号就是 OrderRef，归属靠 Gateway 的登记表，不靠前缀。
- **Gateway 重启或重新登录**后是新的会话三元组，OrderRef 从新会话登录返回的 `MaxOrderRef` 继续（`ctp/client.py:4794-4796`）；旧会话的订单在同一交易日内仍可按原三元组查询和撤单（`direct_write_provider.py:1003-1005` 注释）。
- **强身份与弱键**（INV63-14，2026-11-07，审阅发现 3）：
  - 归属只认（交易日、FrontID、SessionID、OrderRef）与（交易日、ExchangeID、OrderSysID）。
  - 成交回报不带会话字段，只能经委托回报学到的 OrderSysID 归属。成交先于委托回报到达时，按迭代 62 的做法缓冲（`b56b6f8c6`：5 s，有条数上限），超时写入未归属流，并把该预留标为待核。
  - `OnErrRtnOrderInsert` 不带会话字段（私有流广播给账户的所有会话），只作候选证据；Gateway 自己请求的报单错误以带本会话身份的 `OnRspOrderInsert` 为准。
  - 迭代 62 SDK 关联器的弱键回退（§1.5 第 2 项）不得被 Gateway 沿用。（2026-11-07：迭代 62 已去掉该回退，CTP 路由的强键带交易日，bt_api_py `71547da7`、`148c7b4b`；Gateway 复用 SDK 协调器时即沿用这一行为。）
- **63.01 冻结的格式**（2026-11-07，审阅结构建议）：
  - `request_key`：字符集、长度、作用域（账户 + 策略 UUID + 局部序号，或代理子单号）、保存期限、跨交易日规则。
  - 请求摘要：参与字段与规范序列化。
  - 预留号与身份映射：持久化表结构与唯一约束。
  - 分页游标与快照号、grant 的作用域与有效期、会话代际，以及各状态的迁移表。
  静态声明、替身、账户名都不能当作来源、场所受理或授权的证明。

### 3.5 命令转发与授权

- **新端口与操作**（名称 63.01 冻结）：端口 `service.direct_write`，操作 `direct.session_status`、`direct.reserve`、`direct.dispatch`、`direct.release`、`direct.cancel`、`direct.command_status`、`direct.account_facts`、`direct.strategy_book`、`direct.instrument_positions`、`direct.trading_permissions`；回报经 `account.read_after`（`track_delivery=True`）与 `account.ack` 读取本策略的流。另有控制端口（§3.17：`control.kill_switch`、`control.status`）与账户观察流（§3.18）。不复用托管路径的 `service.order_entry`/`orders.submit`，避免与 typed 托管合同混淆。
- **`direct.reserve` 载荷**（63.01 冻结，链路分析 C-6）：`request_key`（§3.4）、`origin`（`self`，或代理：`risk:<principal>`、`execution:<principal>`）、`on_behalf_of`（被代表的策略 UUID）、`parent_ref`、`child_id`（无母单时为空）。母单字段须在 D65-01 已决定顺序下，Gateway 已成功登记且验证对应权威母单信封后才有效（§3.18）；不得以字段存在代替授权或登记。
- **principal**：每个策略一个 CURVE 客户端密钥；服务端把公钥映射到 principal，grant 绑定账户作用域、策略作用域（= 策略目录 `state/identity.json` 的 UUID）、允许的命令（READ/SUBMIT/CANCEL）、合约白名单。单笔数量上限不在 Gateway（D63-18；迭代 64 R-01）。principal 种类：策略 principal；代理 principal（risk 服务、execution 服务，grant 列出可代表的策略 UUID 与命令，D63-31）；账户观察 principal（只读全账户回报与事实，供 risk 服务使用）；运营 principal；runtime principal（迭代 66 D66-08 决定其权限）。principal 与 grant 在 `TrustedServiceAuthority` 中静态给定（`service_host.py:322-323`），新增主体见 D63-13；剔除可用迭代 60 的运行时吊销。
- **两侧准入**：策略侧 `write_admission`（BT 配置，SDK 判定）关闭时根本不发 RPC；Gateway 侧由运营配置该账户 route 的 `WriteAdmission`（S-12 之前只对 SimNow，INV63-08），并按以下次序核对（无状态、确定的拒绝在前，链路分析 C-2 按 D63-18 收窄）：principal 授权（含代理关系与合约白名单）→ 会话已登录且当前交易日结算已确认 → 无账户级日切待定 → 急停（§3.17；预留时与派发锁内各查一次）→ 配额与按策略份额（§3.10）→ 本策略平仓容量（归属，§3.11）。grant 在 Gateway 进程签发并消耗。任一侧关闭后不得签发新的派发许可。2026-11-09 用户选择已准入订单视为在途：在最终核对及原子派发许可先于关闭完成时，该原请求可能在关闭后才到达柜台，按原身份保持在途或 UNKNOWN、对账并按授权撤单，不盲重发；关闭先于许可时不得派发。版本化失效协议及所有写者覆盖完成并验收前，缺证明的路径继续拒绝。详见 [派发与撤权时序决定](Gateway原生派发与撤权时序决策申请-2026-11-09.md)。Gateway 不调用 risk，也不检查风控批准（INV63-10）；单笔上限、价格带、自成交、报撤单计数阈值、超出归属的可平容量都不在 Gateway（D63-18）。
- **释放预留**：`direct.release` 只作用于未派发 RESERVED，不等于撤单或 Risk 占用释放；状态、授权、墓碑、保留及与 dispatch/expire 的竞争按[实施合同补充 §1](实施合同补充.md)冻结和验收。
- **幂等**：`request_key`、`reservation_id` 与撤单命令号在 Gateway 日志中唯一；同号不同内容拒绝，同号同内容返回已记录结果，不重发（沿用 `router.py:225-239` 的语义）。2026-11-07 补充（审阅发现 11）：预留号绑定到发起预留的 principal 与请求摘要。`direct.dispatch` 只接受该 principal（或 Gateway 登记的其代理，INV63-06）对本预留号、同一摘要的调用；其他 principal 即使持有预留号，也不能派发或查询该预留。
- **不经 `GatewayCommandRouter` + 账户写者权威**：其“账户上任一未解决动作即阻断全部写入”（§1.4 第 3 项）与多策略并发不符。交易 owner 使用自己的日志，未解决范围按 D63-04。急停由交易 owner 自己的状态机执行（§3.17），路由器的命令种类按 §3.19 统一词汇。
- **审计**：Gateway 对每次预留、派发、撤单、结算、人工解决记录 principal、策略、身份、请求摘要与结果，不记录凭据；策略侧沿用 `live_state` 审计。

  **判定后迟到回报**：同一强身份的委托/成交随后到达时仍保留原命令及策略归属，记录矛盾/修订事件并重新核对相关范围，不丢弃真实成交、不自动补单或重复记账。BT 的原 Rejected 通知与后续事实更正、母单影响、占用恢复在 63.03/06 冻结并用迟到场景验证；不改变 D63-38 的查询判定，也不自行加额外等待轮次。

  “查不到”不证明请求从未发出（可能被前置拒绝，§6.2 第 11 项）；策略自行重下时仍可能形成重复的业务意图，由策略负责。迭代 62 计划 §5.3 原有的“查询不到保持 UNKNOWN”对完整同交易日、强身份的情形已被 D63-38 取代，其余情形不变。
- **到期与派发的原子竞争**（2026-11-07，审阅发现 6）：
  - 到期判定只在该账户的派发锁内、同一个 SQLite 事务里做：派发事务检查“状态为 RESERVED 且未到期”后直接转 DISPATCHING；到期清理在同一把锁内检查“状态仍为 RESERVED 且已到期”后转 EXPIRED。
  - EXPIRED 提交是必要条件；同时核对原命令 scope/身份、受信单 owner 与全部适用派发入口的栅栏、保留和迟到请求约束（设计 §4.1），成立才报告“确定未发送”（`reservation_expired`），否则 UNKNOWN。
  - 到期按 Gateway 进程内的单调时钟计时，日志另记墙钟时间只作审计。Gateway 重启时，在交易 owner 就绪之前、同一事务内把上一进程代际的全部 RESERVED 转 EXPIRED，所以墙钟跳变不会延长预留。

  - 测试：到期边界上并发派发与清理、每个提交点注入崩溃、墙钟回拨。
- 撤单不需要两阶段：BT 先提交撤单标记，再 `direct.cancel(目标身份)`；Gateway 核对目标归属本策略（INV63-06），写撤单 DISPATCHING，签发 grant 后原生撤单。结果不明时按原单终态解决，与迭代 62 相同。
- SDK 协调器改为由 provider 声明“结果不明”的错误码（修正 §1.4 第 9 项）：派发或撤单请求发出后的传输超时、连接中断声明为结果不明；预留阶段失败、请求未能发出（本地即可证明）才是确定未发送。
- 结算确认只由 Gateway 写，Gateway 侧提交端口是 Gateway 日志（§3.9）。
- 开 risk 时，第 2 行与第 4 行的请求由 risk 服务转发（第 2 行之前 risk 先完成预留，第 4 行之前 risk 先耐久提交 claim），Gateway 侧的次序、记录与恢复不变；risk 一侧的次序与崩溃恢复见迭代 64 计划 §4.2、§4.3。Gateway 对转发来的请求与直达的请求一视同仁（INV63-10），只多核对代理关系（INV63-06）。

### 3.6a 本系统订单 UNKNOWN 的影响范围（D63-04，Q28 已决定）

本系统订单 UNKNOWN 时，暂停所属策略在该合约的全部新订单（OPEN/CLOSE、新子单及新内部转移提交），不自动撤已有活动单或停止策略进程。对其他策略，仅同账户同合约同持仓方向的真实可平容量因该 UNKNOWN 无法证明时暂拒相应平仓；容量可证明则继续其余准入检查。其他合约或无此依赖的操作不因该项一概阻断；撤单和查询保留，但连接不可达不能虚报成功。方向指被平多/空仓，按适用今昨桶、占用和 UNKNOWN 最坏影响验证，不凭净量相等或陈旧观察认定可平。

Gateway 持有该系统范围栅栏，预留、派发及内部转移提交在一致状态版本下复核；不能换请求身份或执行方案绕过。它不依赖 Risk，且不替代 D63-18 下所选 Risk 的一般账户可平业务检查；选 Risk 时未决最坏占用仍保留。命令身份、范围、容量依赖、版本、产生/解决证据持久关联；多个 UNKNOWN 各自维护，一项解决只解除其影响并重算依赖，重启/旧消息不得全清。实际成交及费用照常按原身份投影。D63-38 的完整同日强身份查询解决、通知及不自动重发继续适用，解除阻断不等于证明未发或释放风险占用；其他独立急停、会话等条件保留。

验收按共同合同 §2.19：A 未知平多2，A 同合约新开/平被挡；B 同合约平多容量不可证暂拒，可证时仍经其余门槛；B 平空及其他合约不被该项一概停机；覆盖两个以上 UNKNOWN、逐项解决、旧消息重放、派发竞态、今昨桶、所选/未选 Risk、原有活动单、撤单/查询及迟到成交。确认 external 交易及 D63-48 单纯数量差额不冒充本系统 UNKNOWN。63.03/06/07 实施，65/64 消费，66/68 只按权限观察；尚未运行的用例保持 NOT_RUN。

### 3.7 回报路由

- **单一消费者**：Gateway 交易 owner 是 provider 回报队列的唯一消费者（协调器 `poll_events` 本来就是单次取出，`direct_write.py:376-412`）。
- **按身份路由**：路由键为（交易日、会话三元组、OrderRef）、~~（交易日、OrderRef）~~、（交易日、ExchangeID、OrderSysID）；在派发时登记，获知场所号时追加并持久，Gateway 重启后可恢复。只指向其他交易日的键不路由到当日订单（迭代 62 R-3 F1 的同一问题）。2026-11-07（INV63-14，审阅发现 3）：（交易日、OrderRef）降为只用于候选检索的弱键，不能单独归属；回报带会话字段却与登记三元组不同时不归属；成交先于委托回报到达时缓冲到学到 OrderSysID 为止（§3.4），超时写入未归属流。
- **写入与记账同事务**：归属到运行策略的回报写入其流，并在同一 SQLite 事务内更新归属账本；先按强身份关联、缓冲及核对，未决本系统订单不得自动认作外部。可确认属于本账户外部来源的订单与成交以原始身份、来源和真实费用归集到专用 external 策略账本，并在同一事务持久事件/审计（§3.11c）；来源或身份不足的仍为未归属，不以倒算余额伪造外部事实。
- **消费与 ACK**：策略按游标读取，在 BT 投影和快照持久化之后才 ACK（沿用 `_btapi_gateway_events.py:14-22` 的提交次序）；在保留区间内从上次 ACK 重放，按成交键去重。超过保留/压缩水位须显式报缺口，经有证明的快照与增量恢复，不能静默跳游标；策略、代理和观察者分别验收，见[实施合同补充 §3](实施合同补充.md)。
- **丢失与缺口**：provider 队列满会丢最旧事件并计数（`direct_write_provider.py:1105-1119`）。Gateway 发现计数增加、会话重连或私有流 QUICK 模式下的重连空窗时，把账户标为“回报中断”，暂停新预留，用完整当日委托/成交查询补齐并发布补齐事件，再恢复；策略侧看到 `stream_gap` 时同样阻断写入直至 Gateway 宣布恢复。

- **策略侧 R-3**：保留迭代 62 的日切阻断（迭代 62 文档与代码注释称“冻结”，它是系统阻断，不是急停，§3.19）与 FIFO 等待队列（I62-15），核验步骤改为读 Gateway 状态与本策略账本，在 `day_ready` 之后应用；旧日未决标记经 Gateway 按交易日绑定的身份查询解决，否则保持 UNKNOWN（`previous_day_pending_unknown`）。

### 3.11b 首次接入与外部基线（D63-06，2026-11-08）

### 3.11c 运行中 external 策略账本（D63-09，2026-11-08）

Gateway 为每个账户维护专用 external 策略账本，以归集经核验属于该账户、来源为系统外部的订单和成交；这是账本作用域，不是运行策略进程，也不自动获得普通策略的下单或撤单权限。运行中出现此类外部订单/成交本身不触发全账户或该合约暂停；Gateway、已有策略按正常流程继续，也不自动撤这些外部订单。账户原有授权、急停、时钟、写入准入和其他独立系统/账户规则继续适用，不能因本条消除其原因。

外部订单/成交是已发生事实的归集，不要求它事先获得普通策略授权、经过 Risk 或配置策略预算才能记录；不得因 external 未配置策略预算而自动停机整个账户。外部事实归属、资金 getter 的可用性与已选 Risk 的实际账户政策分别判断。

分类顺序先以强身份关联本系统订单；成交先于委托按既有有界缓冲和查询核对，未决或迟到的本系统订单不能仅因未匹配即标外部。可确认的外部事件保留账户/交易日、原始订单与成交身份、来源、状态、数量、价格及真实费用和费用来源；同一成交及迟到费用更正按身份幂等记入 external 账本、相关事件流和审计，并参与账户对账。真实费用未知时为未知、不填零；对重复、乱序、缺口和重启须按身份恢复。来源或身份尚不能确认的事件保留未归属及证据，不通过倒算账户残差记为外部成交；不能因为一条记录未归属就把它冒充已解释事实。账户视图可展示 external 状态，是否及哪些数据对具体 principal 可见依 D63-01 与授权合同。

D63-06 的受权外部基线可作为 external 账本期初分录，标记 BASELINE、事实及切点来源，不是场所成交，不分给运行策略；运行中外部成交单独为后续事实，不修改既有基线。首次接入仍须无活动委托，运行中外部订单不受此首启条件约束。账本只承接可证明的外部变化，不能通过任意调整、剩余倒算或重做基线隐藏真实差异。账户事实和账本缺口/独立阻断按 D63-04/07 及既有合同处理，但不得因“有外部订单或成交”本身自动暂停。

**D63-48（Q26 已确认）：理论净持仓与账户核对。** 在同账户、规范合约及可比较切点，以带符号净数量计算：普通策略理论持仓之和 + external 账本持仓 = provider 账户持仓；多为正、空为负，买成交增加、卖成交减少。策略理论账只由该策略已确认成交、内部转移及转换增量形成；未完成订单的请求量不计入已形成持仓，pending 单独记录。A 理论多 5、B 理论空 5 可以对应真实净仓 0，不能要求多空逐腿相加；账户真实多空、今昨及各策略明细仍用于可平与准入，净额一致不证明 gross 风险或全部映射正确。 普通策略汇总包含已停止、离线但理论持仓尚未清零的策略，不按当前运行进程列表过滤。

external 初值只来自已核准的 BASELINE，之后按可证明来源的真实外部成交增量更新，不能每次倒算 `账户−Σ策略` 强行填平差额；external 不参与策略内部匹配、转移或虚拟转换。例：A 理论 +5，账户被手工 SELL CLOSE 5 后为 0；A 保持 +5，external 因真实卖出记录净 −5，数量恒等式仍为 0。这里的 external −5 是带来源的净账本分录，不伪造真实开空，也不成为虚拟转换对手方。数量恒等式不自动推导预算、费用或盈亏公式。

Gateway 以同一可比较切点发布含账户/合约、来源、版本、水位、完整性、理论汇总、external 净额、账户净额及差额的只读观察；Monitor 消费该观察并告警：相等不报不匹配，差额非零报告不匹配，事实不足或切点不可比较报告未能核对，不将缺失填零或报健康。Monitor 不修改账本、不发控制命令；仅有外部订单/成交不触发自动停机，本系统 UNKNOWN 按已定 D63-04，D63-07 其余独立阻断仍待明确。63 先以替身验证观察合同，不等待 Monitor 综合验收；68 实际接入以自己的步骤记录联调。

**D63-49（Q27 用户已决定）：外部成交造成无真实可平量时拒单。** A 理论 +5、external −5、账户 0，A 请求平多 5 时拒绝该平仓，理论仓暂不变，拒单后仍为 A +5 / external −5 / 账户 0；不自动改发 `SELL OPEN 5`，也不改 external 或其他策略的理论仓凑平。external 不能提供 D65-28 的转换参与方、映射或 STOP_NEW 例外证明。普通策略 A/B 已确认的内部虚拟转换仍按 D65-27/28 单独处理，不受此拒单规则撤销。

职责仍遵循 D63-18：已选择 Risk 时由 R-03b 按完整可信的账户实际可平事实检查；未选择 Risk 时保持 Gateway/SDK 基础校验及 provider 原生 CLOSE 语义，明确柜台拒绝按原命令投影，不强制引入 Risk 或把账户业务风控移入 Gateway。Execution 不得通过自动改 OPEN 绕过失败。本条零可平量拒单须来自具备相应职责的交易前拒绝或原生明确拒绝；D63-38 完整同日强身份查询未找到时的 Rejected 投影另按已定合同，不改写为“确定未发”。尚未按既定规则解决的派发结果不明仍为 UNKNOWN，保留身份和未决占用，不能以账户净仓为零推断请求未成交。无成交的拒单不减少理论仓、不记平仓盈亏/虚构费用或释放该仓位保证金；仅按既有规则释放可证明未使用的订单预留。

63.03 在 Gateway 中交付账户专用 external 账本、来源与权限、幂等事件和替身测试；63.06 只投影账户/本策略/其他运行策略/已确认 external/未归属，运行策略不能代 external 下单撤单；63.07 在可比较切点按 D63-48 核对理论净仓、external 与账户；D63-49 的拒单及账本不变须独立验证，不能以设计决定代替实现证据。synthetic + 真实服务回环验证外部挂单与成交后策略正常继续、状态和费用幂等、不同策略/外部权限隔离、先成交后订单、丢包/重启和未归属恢复；不新增实际账户操作。

### 3.11d direct → Gateway 空仓迁移（D63-12，Q40）

首期仅迁移已证明空仓的策略，带仓迁移留待后续；Q40 只约束 direct → Gateway，Gateway → direct 仍按其独立准入和虚拟仓问题处理，不由本决定代选。

先停止该策略的旧 direct 写入并核验原账户、策略身份与来源，使用完整、可信且可比较的事实证明该策略归属持仓为空，且没有属于它的活动委托、在途/UNKNOWN 命令或未决账本动作。未确认来源、缺失日志、无法证明归属或切点时不视为空，也不能把该策略仓通过改名或重记为 external 绕过。不得自动下单平仓、抹账，或将旧原生日内订单复用作新母单。

在经证明的旧 writer 退出及防迟到 fence 和新 Gateway owner 权威接管之间建立互斥，验证当前授权与身份；若无法证明互斥，不能启用该策略的 Gateway 写入，不能仅以本机锁推断所有旧 writer 已退出。记录迁移命令身份、事实来源及版本、双方 owner 代际、旧身份和审计；幂等恢复应能识别提交后丢回复及失败，不能造成旧 direct 与新路径双跑。Gateway 中该策略从空账本接入，不凭本地快照创建策略持仓。

账户其余无关的外部持仓不要求清空：首次接入仍需满足 D63-06/Q24 外部基线的受权事实、对账与全账户无活动委托前提；已有 Gateway 则沿用其经确认的 external 账本。外部基线始终归 external，不分配为迁移策略仓。synthetic 与真实 Gateway 回环覆盖成功迁移、带仓/活动单/在途/UNKNOWN/未决/来源不明拒绝、原身份错配、旧 writer 存活或迟到、进程崩溃与重试、外部持仓及基线前提；验收不新增账户操作授权。

### 3.13 安全边界

- **凭据只在 Gateway**：CTP 账号、密码、AppID/AuthCode 只在 Gateway 进程环境中；策略配置与 `BtApi` 的 Gateway route 拒绝凭据字段（INV63-01）。
- **CURVE**：每策略一个客户端密钥对；本迭代只支持同主机 loopback。密钥分发方式见 D63-13（推荐：运营工具为策略目录生成密钥，私钥写入该目录 `state/` 下权限 0600 的文件，公钥登记到 Gateway；不经 argv、日志或公共文件）。现有“每次运行子进程管道传密钥”（`run.py:137-157`）只适用于父子进程，不适用于长期运行的共享 Gateway。
- **运营 principal** 与策略 principal 分开：急停 RESUME、人工解决 UNKNOWN、声明外部基线只允许运营 principal。急停命令的来源与各自可下达的动作见 §3.17；monitor 没有控制权限（INV63-11）。
- **代理 principal**（risk 服务、execution 服务）各有自己的密钥，不共享策略的私钥；grant 只列出可代表的策略与命令，不含结算、急停解除和其他策略的流（execution 的范围见迭代 65 §3.10）。
- 日志、审计、错误详情不含凭据和原始账号；账户只以 provider 的哈希引用出现（`direct_write_provider.py:1582-1586`）。

### 3.14 可观测性

- **Gateway 状态**（`direct.session_status` 与运营查询）：TD/MD 会话数与登录次数、会话代际、交易日、结算状态、已连接 principal、每策略的预留/派发中/UNKNOWN/活动委托数、账本版本、账户合计对账状态与残差、查询队列深度与等待时间、限频拒绝数、已路由/未归属/丢失的回报数、生效中的急停原因（范围、模式、来源、DRAIN 进度）、代理 principal 及其租约、各策略租约年龄。策略经 `direct.session_status` 读到本策略适用的急停原因，BT 据此在预检中尽早拒绝并写入对账报告（控制面分析 §3.5），急停不阻止 BT 启动、对账和撤单。
- **策略侧**：`get_direct_reconcile_report()` 增加 Gateway 字段（账户作用域、账本版本、对账状态、其他策略/未归属委托数、`gateway_unavailable` 次数）。
- **会话数证据**（63.09）：Gateway 状态与 provider 登录计数；按进程统计到 CTP 前置的 TCP 连接（Gateway 进程应为 TD+MD，策略进程为 0）；策略进程未加载 CTP 原生库的模块探测；策略配置不含凭据（只检查键是否存在，不读取值）。
- **monitor 中继**（链路分析 C-8）：Gateway 日志是 monitor 的事件源，按 `service_execution_monitor` 的只读游标模式中继到 monitor 的持久入口，不在下单路径上；~~monitor 缺失或变慢不影响交易~~（2026-11-07 复审更正：未开启 `monitor_required` 时，monitor 缺失或变慢不影响交易；开启时按下一条的存活判定施加 STOP_NEW），中继积压有界并计数。monitor 不发控制命令；D63-43 采用 Gateway 中继主动请求、Monitor 仅在同一受认证请求响应中返回心跳 ACK，不增加主动上报接口。ACK 必须绑定 monitor 的 principal 与当前中继代际，过期或重放的 ACK 不刷新存活；Gateway 重启后存活从启动宽限重新计算（63.01 冻结 ACK 的来源与格式）。中继的事件类型（63.01 冻结）：预留/派发/撤单结果与拒绝码、UNKNOWN 的产生与解决、回报中断与补齐、急停原因的生效/解除与 DRAIN 进度、流控拒绝与份额使用、原始报撤单计数、会话与结算、日切、账户合计对账状态、D63-48 带可比较切点与来源的理论净仓/external/账户净仓及差额、代理租约状态；事实不足标未能核对。
- **monitor 只观察**（D63-21）：缺省可选；monitor 不向 Gateway 发任何控制命令。显式打开 `monitor_required`（D63-21 中的 S-10）时，Gateway 根据自己观察到的 monitor 存活（判定方式见 D63-36）在丢失超过配置时长后施加账户范围 STOP_NEW。D63-36 已于 2026-11-07 决定（审阅发现 9）：
  - Gateway 每隔固定秒数向 monitor 中继写一条心跳事件。心跳走独立通道或优先位，不被业务事件积压挡住。
  - Gateway 记录每条心跳的发出时间与 monitor 的 ACK 时间；现有进度表没有时间列（§1.5 第 7 项），63.12 增加。
  - “最近一条已 ACK 的心跳是在配置时长之内发出的”即视为存活。开启后有启动宽限。重放的旧 ACK 只推进到它对应的心跳，不能刷新存活。积压只影响业务事件，不影响心跳通道。
  - 测试：正常空闲、monitor 停止、慢消费积压、旧 ACK 重放、Gateway 重启。

  **D68-02 启动兼容性（2026-11-08 用户已决定）**：账户开启 `monitor_required` 时，启动阶段若确认配置的 Monitor 是不支持当前协议身份和心跳绑定确认能力的旧版，Gateway 拒绝启动并明确提示版本不兼容、升级或更换；不发布交易就绪、不派发新命令，不伪造 ACK、关闭 required 或用启动宽限掩盖已确认不兼容。认证与能力证明、检查时点、有限码和失败清理由 63.01/68.01 冻结；已存在的在途身份和 UNKNOWN 保留。暂时不可达、超时或认证失败不等同已确认旧版，按原初始化及宽限/失活合同如实报告；已运行后失联仍按 D63-36/Q34 处理，不据该启动决定擅自退出服务。非 required 兼容/降级仍遵守既有只观察授权。

  该 STOP_NEW 是 Gateway 自己的判定，不是 monitor 的命令。D63-33 的 Monitor 部分已由 Q34 决定：仅显式启用 `monitor_required` 时因 Monitor 存活丢失产生账户 STOP_NEW；Gateway 收到可信认证、当前中继代际、对应请求且发出时间仍符合 D63-36 新鲜度判定的心跳响应后，默认自动解除该 Monitor 失联原因，账户配置可改为等待受权运营人工 RESUME。Monitor 只响应 Gateway 中继主动请求的 ACK，不发送控制命令。

D68-08 已确认 Monitor 本地持久告警及可选通用 Webhook；该通知只发往受信配置的告警接收端，不向 Gateway 发控制命令。持久事件接收 ACK 及心跳处理不等待 Webhook，通知慢/失败不反向撤销 ACK，也不由 Monitor 改变交易状态；monitor_required 继续按本节的服务存活证据判定。

### 3.17 急停（D63-19、D63-24、D63-25、D63-26、D63-28；链路分析 C-3）

- **状态与执行在 Gateway**（D63-24）：急停原因写在 Gateway 日志，与预留、派发记录在同一个 SQLite；交易 owner 宣布就绪前先加载；急停记录写入失败时，该账户按 FREEZE 处理（fail-closed）。
- **语义**（D63-19）：

  | 模式 | 新开仓 | 新平仓 | 撤单 | 说明 |
  | --- | --- | --- | --- | --- |
  | FREEZE | 拒 | 拒 | 放行 | — |
  | STOP_NEW | 普通开仓拒绝；虚拟平仓引起的实际 OPEN 按 D63-42/D65-28 的独立转换准入配置判断 | 放行，仍须通过本策略归属可平容量（INV63-06）；虚拟平仓另校验转换映射 | 放行 | 区分策略意图与实际 offset；Gateway 校验权威账本和转换身份，不信任客户端自报 |
  | DRAIN | 拒 | 拒 | 放行 | 受理后按身份撤销范围内的活动单；撤完仍按 FREEZE 拒新单，直到 RESUME |
  | RESUME | — | — | — | 运营直接执行，或按D66-08经Runtime有限代理；一次解除一个原因号；代理仅限该Runtime对目标策略设置的原因 |

- **范围**：账户、策略（策略 UUID）、合约（中立合约键）；不增加“策略 × 合约”（D63-26）。一笔新单适用的原因 = 账户级 ∪ 该策略 ∪ 该合约；有效模式取最严（DRAIN ≈ FREEZE > STOP_NEW）。代理 principal 提交的订单按被代表的策略匹配范围，所以策略范围的急停同样拦住 risk 服务转发的订单与 execution 子单。
- **两处检查**：`direct.reserve` 时命中即拒；派发锁内、写 DISPATCHING 之前再查一次（处理“预留之后才下达急停”），命中则拒绝本次调用，并按实施合同补充 §1 的同锁同事务规则处理尚未派发预留。该次拒绝不单独证明同身份命令从未派发；只有完整日志覆盖及有效旧 owner/迟到请求 fence 可证明时才返回命令级 NOT_SENT，否则保留 UNKNOWN 及适用 Risk 占用。拒单码带模式和原因号，如 `kill_switch_freeze:<cause>`。
- **撤单**：任何模式都不拦，仍核对归属（INV63-06）与跨交易日拒撤规则；使用配额中的撤单保留容量，容量不够时排队，不丢弃。
- **DRAIN 步骤**：在同一事务里登记原因后才回复“已受理”；按归属账本列出范围内的活动单（含已发送、部分成交；DISPATCHING 与 UNKNOWN 视为可能仍在场所）；每笔按原身份撤一次；撤单结果不明时不盲目重发，查询确认仍活动后才再撤；全部终结记 APPLIED，否则记“部分完成”并附清单（结果类型见 §3.19）。大范围 DRAIN 会增加撤单数，按“安全优先”接受，并经 monitor 中继告警。
  2026-11-07 补充（审阅发现 8；D63-40 已决定）：
  - **目标清单在受理时冻结**：DRAIN 受理时，把目标订单清单（按身份）与原因号一起持久化。之后只撤这份清单内仍活动的单；Gateway 重启后按这份清单继续，不重新按范围列出。这样不会撤到受理之后、或 RESUME 之后新建的订单。
  - **撤单任务带原因号与代际**：执行前核对原因仍生效、代际一致。
  - **DRAIN 未完成时允许 RESUME**（D63-40）：尚未发出的撤单任务取消，已发出的撤单跟踪到结果（结果不明按上文处理），该次 DRAIN 记为“部分完成”并附清单。RESUME 之后，旧任务一律不执行。
  - **再次 DRAIN**：同一范围再次 DRAIN 是新原因号、新清单。
  - 测试：DRAIN 中途 RESUME、DRAIN 中途 Gateway 重启、重复 DRAIN、RESUME 之后新建的订单不被撤。
- **命令来源**（控制面分析 §3.3，按 D63-21 去掉 monitor）：

  | 来源 | 途径 | 可下达 |
  | --- | --- | --- |
  | 运营 | 控制端口，运营 principal | 全部，含 RESUME |
  | runtime（迭代 66） | 控制端口，专用runtime principal；RESUME另核受权运营及委托证明（D66-08已确认） | 策略范围STOP_NEW/FREEZE及DRAIN；受权运营主动发起时，可代理RESUME该principal对目标策略设置的指定原因，不解除其他来源原因 |
  | risk 服务（迭代 64） | 控制端口，risk 服务 principal | STOP_NEW、FREEZE（迭代 64 D64-11） |
  | Gateway 自身：`monitor_required` 下 monitor 存活丢失（D63-21） | 内部判定 | 账户范围 STOP_NEW |
  | Gateway 自身：策略租约过期（D63-28，按策略开启，缺省关闭） | 内部判定 | 该策略 DRAIN |
  | monitor | — | 无（D63-21、INV63-11） |

- **D66-08运营有限代理恢复（2026-11-08已决定）**：Gateway核验Runtime主体、可信操作者/代理授权、目标策略、原因号及状态版本，不凭载荷名字放权。只解除该Runtime principal对目标策略设置的原因；多原因逐项核验，其他来源与系统阻断保留。Runtime启动/重启不自动恢复；相同稳定主体在重启后可经当前授权的运营新请求解除自己的旧有效原因。持久化命令身份、丢回复查询原结果，不以受理/UNKNOWN宣称已恢复；原因解除不等于全部交易条件就绪。63.01/12与66.06/07冻结证明/撤权/重放和审计合同，覆盖DRAIN中途恢复、错来源、并发、重启及多阻断。
- **解除**（D63-25、D63-33）：Q34 已决定 Monitor 存活丢失的账户 STOP_NEW 默认在有效心跳恢复后由 Gateway 自动解除该失联原因，可配置为仅受权运营人工 RESUME；租约过期 DRAIN 已由 2026-11-08 实施追问确认：策略重连且完成恢复核对后默认自动解除本次原因，可配置人工恢复；仅匹配 cause/version，不清除其他原因和 UNKNOWN。运营、runtime、risk 下达的原因一律须按既有权限 RESUME（risk 原因的锁存另见迭代 64 D64-09）。
  - 恢复依据是认证通过、绑定当前中继代际和原心跳请求且该心跳**发出时间**满足 D63-36 新鲜度的响应；仅 Monitor 进程启动、网页打开、积压旧 ACK、刚收到但对应旧心跳的响应均不构成恢复。Q34 不增加额外等待轮数。
  - 恢复判定与解除须在 Gateway 以失联 `cause_id` 和状态版本作条件提交；解除前再次失联、原因/版本变化或重启后，旧恢复不得清掉新原因。只解除对应的 Monitor 失联原因，不解除 Risk、人工、Runtime、另一 Monitor 新失联原因、UNKNOWN 或任何其他系统阻断；原因解除不等于账户可交易。
  - Gateway 重启仍按 D63-36 的新代际启动宽限与重新验证执行，不能凭旧持久健康或旧代际 ACK 自动解除。人工模式只由既有受权运营 RESUME；D66-08 的 Runtime 有限代理不得解除 Gateway 自身产生的 Monitor 原因。
- **系统阻断不是急停原因**：回报中断、日切、会话断开、UNKNOWN、结算未确认等 fail-closed 阻断在条件消除后自动解除，与急停原因分开存放，RESUME 不会解除它们（INV63-09；同 D62-29“结算确认不解除 UNKNOWN”）。
- **租约过期自动 DRAIN 的前提**（D63-28）：只有在 63.11 完成、客户端租约维护不再依赖 Cerebro 线程之后才允许开启，否则 `next()` 长时间占用会误触发（迭代 62 缺陷 19；R-3 F2 最坏约 31 s）；开启时过期时长必填，无缺省值。
- **重启**：Gateway 重启时先加载原因，进行中的 DRAIN ~~重新列出仍活动的单继续执行~~ 按受理时持久化的目标清单继续执行（2026-11-07，不重新按范围列出）；策略范围的原因按 UUID 记录，策略重启后仍有效；BT 启动后从 `direct.session_status` 读到原因并写入对账报告（§3.14）。

### 3.18 与 risk、execution、monitor、runtime 的关系（D63-15～D63-17、D63-20、D63-23、D63-29、D63-31）

- **前提**：risk、execution、monitor 只能在开启 Gateway 时启用（D63-20）；它们都是独立进程，Gateway 与策略进程都不导入这些包（INV63-12）。runtime 不受此限（D63-29 中的 S-16）。D66-02已定Runtime首期仅监督策略进程，服务进程由各自入口或系统服务管理器运行；状态检查和策略控制端口对接不等于服务启停，停止某策略不能停止共享Gateway/Risk/Execution/Monitor。
- **调用路径**（迭代 64 §4.5、迭代 65 §3.1 与此一致）：

  | 部署 | PLACE（下单） | 撤单、状态、事实、回报 | 风控所在 |
  | --- | --- | --- | --- |
  | Gateway | SDK → Gateway | SDK → Gateway | Gateway 的授权、归属、流控、急停；柜台 |
  | Gateway + risk | SDK → risk 服务（预留、claim）→ Gateway | SDK → Gateway（撤单不经 risk，不受 risk 可用性影响） | 另加 risk 服务；Gateway 不变 |
  | Gateway + execution | 未命中执行路由：同第一行；命中：母单交给 execution（入口按迭代 65 D65-01），子单 execution → Gateway | SDK → Gateway；撤母单见迭代 65 D65-06 | 同第一行，另加母单委托信封（D65-01 顺序已定，操作与身份待冻结） |
  | Gateway + execution + risk | 未命中：同第二行；命中：execution 受理母单时经 risk 服务 `reserve_parent`，子单 execution → risk 服务 → Gateway | 同上 | 母单预留与子单 claim 都在 risk 服务 |

- **Gateway 不检查风控批准**（D63-17、INV63-10）：经不经过 risk 由 bt_api_py 的配置决定（迭代 64 §6.1）。已知并已接受的性质：配置错误或未配置 risk 的客户端，以自己的 SUBMIT 授权直达 Gateway 时，risk 不会生效，Gateway 也无从区分。仍然适用于所有订单的是 Gateway 自己的授权、归属、流控与急停；risk 只能从账户观察流事后看到这些订单，把它们计入计数、自成交视图和持仓，但不能阻止。D63-37 已确认提供运营可选授权：可把某策略的 SUBMIT 只授给 Risk principal，默认保持原权限；这是普通授权，不是风控批准检查。
- **竞态的如实说明**：risk 在 Gateway 之前，Gateway 的派发次序可能与 risk 的 claim 次序不同；这不影响 risk 的判断，因为 risk 把已 claim 未结的订单按在途计入。绕过 risk 的订单要等 Gateway 回报后 risk 才看到，在此之前 risk 的自成交与计数视图缺这部分（迭代 64 §4.2）。急停在 Gateway 执行，不受这类竞态影响。
- **Execution 故障后的母单恢复（D65-05，Q29 已决定）**：65 按账户可配置保持冻结/自动继续，默认核对完成后按原计划继续。63.13 需提供受权、版本化、幂等的母单故障冻结恢复边界：原母单/方案版本、当前代理租约/授权和未决集合核对通过，只解除该服务故障导致的母单冻结，保留其他急停与系统阻断；不等同运营 RESUME。原窗口无效或事实不全不恢复，已有子单继续按原身份处理。用替身及真实 Gateway 回环覆盖 10=已成4+活动2+未下4、恢复/成交/取消竞态、旧版本/撤权、多个原因、提交后丢回复和幂等查询；协议由 63/65.01 冻结，本体无需导入 Execution 包。详见共同合同 §2.20，具体继续计划由65持有。
- **跨日母单 owner 合同（D65-04，Q38）**：63.13 提供持久化稳定母单/信封及子单关联、交易日、账本与可平桶映射、状态及完整性版本，支持原有归属和显式有效期跨日；日切、派发、撤单、回报、到期与恢复必须串行或版本条件更新，不能因计数日更换重建总量、重复提交或释放未决占用。D65-01 已决定先 Execution、选 Risk 时先母单风控、之后向 Gateway 登记；稳定身份、授权、映射及具体端口由 63/64/65 冻结，不能假定现有能力已交付，也不使 63 基础验收等待 65 综合验收。
- **本迭代为 64、65、66 提供的 Gateway 侧能力**（63.12、63.13；D63-15）：代理 principal 的授权与 `on_behalf_of` 归属；`request_key` 幂等；`origin`/`parent_ref`/`child_id` 字段与回报标签；账户观察流；risk、execution 服务的 MarketHub 行情 principal；控制端口及运营、runtime、risk 服务的权限；D65-01 已决定的母单委托信封、Execution 受权登记与 execution 租约；monitor 中继与 `monitor_required`。Gateway 在选用 Risk 的母单风控后独立验证策略和代理授权并登记自己的权威数量边界，不调用 Risk 或检查其批准；稳定请求身份、幂等、异常恢复及登记前取消按[共同合同 §2.32](跨迭代合同与决策.md)冻结。64、65、66 发现 Gateway 侧缺口时提回本迭代处理，不在各自迭代修改 `bt_api_gateway`。

### 3.20 Gateway 行情路径的健康与恢复（D62-38 在 Gateway 下的对应；2026-11-07 新增）

迭代 62 的 D62-38 与缺陷 23 的修复只覆盖 direct 行情路径；D62-38 的 LIVE 定义要求断线或恢复中为 DELAYED（§1.5 第 10、12 项）。Gateway 行情路径需要同样的语义：

- **断线期间**：从 provider 源丢失到重启，MarketHub 向每个客户端订阅报告“恢复中”（新的健康信号或非 ACTIVE 状态，名称在 63.01 冻结）。客户端 SDK 把它投影为不可 resync 的 RECOVERY_REQUIRED，BT Store 记录原因，Feed 转 DELAYED（沿用 backtrader `b5fd3ea18` 的 `tick_stream_recovery_reason`）。不再出现“ACTIVE 而无数据”。provider 侧已有 `source_recovery_state`（bt_api_ctp `8585334`），Hub 可直接读取。
- **断线期间的新订阅**：修复 `start_uncertain` 置位后永不复位（§1.5 第 10 项）。恢复中的新订阅返回可重试的有限码，不把 Hub 留在无法关闭的状态。
- **源重启之后**：Hub 轮换 epoch 并确认 provider（现状）。客户端得到 `PROVIDER_RESYNC_REQUIRED` 后，按 D63-39（2026-11-07 已决定，选 a）由 BT Store 自动确认数据丢失并 resync，退避与 direct 相同（0/1/2/5/10/30 s），取消 backtrader `afecc2617` 中“Gateway 行情不自动 resync”的排除；resync 后第一笔健康 tick 使 Feed 回到 LIVE。
- **首笔 tick**：resync 后第一笔新鲜、有效的 tick 可交易（D62-38 第 2 点），与 direct 相同。
- **时钟资格**：tick 的时钟与新鲜度资格在客户端判定（SDK `ServiceMarketStream` 的 `_qualified`，迭代 62 `66515f62`）。`direct.market_clock_verification` 与按合约延迟上限等配置在策略侧生效。接收时间是 Gateway 转发后客户端的接收时间，只在同主机有意义（§6.1“时钟域”）。
- **会话数**：Hub 用一个 CTP 行情会话服务全部合约（§1.5 第 10 项），配对策略不再像 direct 那样每个合约一个会话。
- **长时间断线**（2026-11-08 新增，迭代 62 缺陷 25）：provider 在源丢失后持续恢复（退避重试，bt_api_ctp `5fa57e5`），Hub 在整个恢复期间保持“恢复中”信号；合同违规导致的最终失败（provider 记 ERROR，不再自动恢复）须作为不同的健康状态报告给客户端与运维，不能与“恢复中”混为一谈。
- **长时间中断告警**：按用户 2026-11-08 的决定移到迭代 68（bt_api_monitor 观察与告警）；迭代 62/63 只保留日志与 DELAYED 状态。
- **测试**：
  - UNIT/FAKE：Hub 恢复中的健康信号、`start_uncertain` 复位、resync 后首笔可交易。
  - INTEGRATION_SIM：回环 Gateway 中 provider 源断开再恢复，3 个客户端的 Feed 都 DELAYED，再回到 LIVE。
  - SIMNOW：挂起 Gateway 进程超过心跳超时，观察各策略的 Feed 状态与恢复。
  - SIMNOW（2026-11-08 新增）：前置长时间不可达（超过连接超时；拒绝连接与静默丢包两种）之后服务恢复，Hub 的行情自动恢复，各策略 Feed 由 DELAYED 回到 LIVE（迭代 62 缺陷 25 的同一场景，direct 路径的 SimNow 复核见迭代 62 SimNow 记录 §2j H）。

SimNow 场景（63.09，需用户授权，结果只说明 SimNow 行为）：

1. Gateway 账户默认首次接入：全账户空仓、无活动委托（D63-06）；运营外部基线路径另以 synthetic + 回环验证，本场景不额外授权账户操作。
2. 启动策略 A（`bbroker_5s_single_symbol_gateway`，rb2701）、B（`mixbroker_single_symbol_gateway`，rb2701）、C（`sa_dual_ma_gateway`，SA701），各自首启；记录会话数证据。
3. A、B 各开多 1 手 rb2701：账户 2 手，账本 1/1，账户对账 BALANCED；A `close_today` 1 手后账本 0/1、账户 1 手。
4. B 挂远价单后 `kill -9`，重启 B：恢复并交给策略，A、C 不受影响。
5. 在 A 有活动委托、B 有持仓时重启 Gateway：身份、账本恢复，无重复成交，策略恢复写入。
6. 正常停止 A：只撤 A 的委托（D62-19）。
7. 停 Gateway：三个策略进程继续等待，无法可靠提交的请求暂停并报告断连，不回退直连；恢复后先回补、对账及检查准入，再恢复适用交易；不得把撤单未送达报告为成功。
8. 可行时跨夜盘交易日：Gateway 只确认一次结算，三个策略依次恢复。
9. 运营对 B 施加策略范围 STOP_NEW：B 的开仓被本地拒绝，B 的平仓与撤单照常，A、C 不受影响；再对 B 施加 DRAIN：只撤 B 的活动单；运营 RESUME 两个原因后 B 恢复。

10. （2026-11-07 新增）用进程挂起（SIGSTOP 超过心跳超时再 SIGCONT，不需要 sudo，迭代 62 SimNow 记录 §2j D 的方法）模拟 Gateway 与前置断开：三个策略的 Feed 转 DELAYED、写入关闭；恢复后按 D63-39 resync，回到 LIVE。断线期间有活动委托时，恢复后按 §3.7 补齐成交。
11. （2026-11-07 新增）用一笔资金不足或价格越界的报单，验证“前置拒单不出现在委托查询中”（§6.2 第 11 项）。
