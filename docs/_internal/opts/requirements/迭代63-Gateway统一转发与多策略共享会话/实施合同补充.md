# 迭代 63：实施合同补充

2026-11-08 文档审阅补充，状态 **REVIEW_PENDING**。本文是[设计文档](设计文档.md)的实施补充；以下技术方案供 63.01 冻结并接受，尚未实现或行为验收。已决定的 D63/D65/D66 语义保持，产品选项仍见[实施准备与待决事项](实施准备与待决事项.md)。不改变两阶段派发为单阶段，也不增加 D63-38 的等待轮次。

## 1. release、到期与未发送证明

`direct.release` 仅放弃尚未派发的预留，不是撤单、强制终止 UNKNOWN 或释放 Risk 资金的指令。使用与 reserve 相同的账户/策略/request_key、reservation_id 和订单摘要，另带 release 操作 ID、预期版本；服务端以当前认证主体及已登记代理授权检查，不能凭持有句柄授权。

建议新增持久状态 `RELEASED`，与 `EXPIRED` 区分主动放弃和到期。命名可在 63.01 调整，以下转换语义不可省略：

| 当前状态/输入 | 同锁同事务处理 | 结果和恢复 |
| --- | --- | --- |
| RESERVED，release 授权/摘要/版本有效 | 条件更新为 RELEASED；同事务记录原因、操作 ID、原请求身份及审计 | 提交后原 request_key 不得重新预留或派发；丢回复查询原操作 |
| RESERVED，dispatch 或 expire 先提交 | release 不覆盖胜出状态 | 若 DISPATCHING 或后续状态，报告已经进入派发路径；若 EXPIRED，返回既有到期状态 |
| RELEASED/EXPIRED，相同 release 重试 | 返回原记录，不删除命令、重置 TTL 或创建新预留 | 仍须当前查询授权；同操作 ID 不同摘要拒绝 |
| DISPATCHING/SENT/UNKNOWN/已观察场所结果 | 拒绝 release 的状态变更 | 保留原身份及占用，按原单查询/撤单合同处理；不能伪报 NOT_SENT |
| 找不到 request_key/reservation_id、日志覆盖不足或越权 | 不创建猜测的成功结果 | 有限错误/UNKNOWN，不能因“无行”断言未发 |

RELEASED/EXPIRED 只有在完整权威日志、原身份和旧 owner/迟到请求 fence 满足设计 §4.1 时，才构成 NOT_SENT 的证据。release 自身超时也可能已经提交；调用方只能查原身份，不能换键重下。`not_found_at_venue` 始终是场所查询判定，不能自动转换成 RELEASED 或 NOT_SENT。

持久拒绝重放记录（墓碑）按账户、策略和 request_key 保存原摘要及终态；不得简单按交易日清除跨日母单/命令。63.01 把保留期、客户端可恢复期、最大消息迟到期与旧 epoch 拒绝条件共同冻结：清理后若旧键仍可能被接受为新请求，就不能删除其拒绝重放依据。owner epoch 只能拒绝新到达入口的旧请求，不能撤回已到 provider 的请求；旧 writer 未被实际 fence 时不签发确定未发证明。未知请求的显式 abandon 是独立候选，当前 release 不隐式提供。

验收：release/dispatch/expire 两两竞争与三方交错；每个事务提交点崩溃；release 成功后迟到 reserve/dispatch；同键异摘要、越权、旧 epoch、保留期边界、日志缺页、回复丢失。断言同一预留最多一次进入原生发送边界，终态不复活；未证 NOT_SENT 时 Risk 占用不释放。采用状态序列测试覆盖竞争，不要求固定测试数或变异率。

## 2. 单查询槽与调用者超时

调用者的期限与 provider 原生查询的生命周期分开。每个原生查询绑定账户、查询种类、原生请求 ID、会话代际和交易日；共享等待者各自超时，不因某一等待者离开而取消其他等待者或释放原生槽。

原生槽仅在 provider 确认本请求终包、确认原生查询实际终止且不再占槽（仅取消请求被受理不够，迟到回调仍须隔离），或旧会话已隔离且其回调不能污染新会话时释放。RPC 超时、队列超时、局部取消和仅停止等待均不是释放证据。旧请求的迟到行/终包只属于旧请求，不能补全下一查询；缺终包时保持占用/隔离状态、报告不可用，由有界恢复流程处理，不能无限启动并发查询。若 provider 现有入口不能提供这一合同，63.04 补足，63.03 先用明确标记的替身验证。

返回结果分开记录等待者超时、原生查询未终结和数据完整性。一次查询各分区不自动具有原子账户切点；仍执行计划 §3.8 的 NOT_COMPARABLE 分支，完整终包不等于持仓/成交查询发生在同一时点。

验收：A 超时后 B 排队；合并等待者中仅一人超时；A 迟到数据/终包；缺终包后重连、旧代际同请求号、跨交易日；分页被替换、队列满、恢复后公平调度。不得把 A 的行计入 B，也不得仅因当前回报序号没变报 BALANCED。

## 3. 观察流、压缩与离线消费者

Gateway 自有账本、命令和原因状态可在同一本地事务产生不可变快照及对应日志水位，后续增量严格从该水位之后衔接。该水位只证明 Gateway 自有状态一致，不赋予 provider 账户查询共同水位。流和快照携带账户/授权 scope、stream epoch、schema、账本版本、序号和完整性；账户观察 principal、策略与 Execution 分别有独立消费进度，不能 ACK 他人流。

消费者旧 ACK 落在已保留范围内时正常重放；落在压缩/过期范围外时返回明确 `recovery_required` 和受权恢复描述，不静默推进游标、不把空列表当追平。客户端先耐久安装已核验快照，再从其衔接水位应用增量并 ACK。快照缺订单身份、已应用成交/费用版本、未决占用或所需历史时，相关投影仍不完整；不能用只有当前净持仓的快照恢复 Trade/Analyzer 历史。

63.01 冻结各流的保留和容量、离线消费者处理、快照覆盖、旧键墓碑与 ACK 的关系；事件正文可压缩不等于命令幂等身份可删除。Monitor 的心跳 ACK 也不表示业务流已追平。磁盘不足不能静默丢交易权威数据；日志无法提交时沿用已有拒绝新增派发规则，观察中继缓冲则保持有界并报告缺口。

验收：策略/Execution 离线超过保留期、压缩与 ACK 并发、快照与首条增量重叠/缺口、安装快照前后崩溃、撤权、跨 stream epoch、未知版本及费用迟到。状态、成交和费用只应用一次；缺覆盖不能宣布恢复完成。63.03/05 验证策略路径，63.13 验证代理/观察路径，68 联调另记。

## 4. 数量、金额与策略资金证据

Gateway 权威账本采用规范十进制数或按声明单位的定标整数；wire 使用与 Base 合同一致的规范十进制字符串，持久化不经过二进制 float 往返。数量单位/步长、价格网格、合约乘数、币种、费用与舍入规则均绑定来源和版本。CTP 手数按 provider 声明的整手网格检查，不能因通用十进制支持而接受分数手。

数量守恒在规范单位上精确比较，不借用 BT 浮点投影的 `1e-9` 容差掩盖一手/一步长短缺。金额及费用先按其有版本的计价/舍入规则处理，再比较；费用未知和未确认估计分列，不能填零。实际费率、币种精度或经济舍入政策缺失时，对应金额结果不可用，63.01 不能替 provider 或用户猜默认。BT 数据线/Order 的 float 投影属于边界适配，必须记录量化和误差处理，不反向覆盖权威账本。

资金调节项以独立的 `budget_reconciliation` 视图（名称待冻结）承载账户/币种/切点、账户初始权益、各策略预算、调节项、来源及版本；它不是 D63-48 数量对账差额、可用资金池或 external 成交。D63-46 的 100−60−60=−20 万只解释预算配置。策略权益总和不强制等于账户权益；getter 与 close/target/Sizer 的作用域仍按 D63-41。

验收向量：

- 通用分数量模型下 `0.1+0.2=0.3`、大量增量重放、非整网格拒绝；CTP 模型下分数手明确拒绝，合法 1/2/3 手守恒。
- 同一真实成交、内部转移、转换映射不可重复计完成量；真实/理论/external 与四桶守恒分别检查；一个真实最小数量单位的差额不可被容差吞掉。
- 资金输入 100000、已实现 2000、浮盈 3000、费用 100、保证金 20000、在途 10000，得到 value=104900、cash=74900；浮亏 3000 时为 98900/68900；释放在途只增加 cash。
- 迟到费用更正、负 cash、缺预算/估值/币种、100 万账户与两份 60 万预算；Risk deny 的 60 万预留后仅剩 40 万由 64 验证，63 不能据自身账本宣称 Risk 资金预检通过。

63.03/06/07 验证本期账本及 BT 接口；70 实现 BackBroker 并运行相同向量，D63-45 单策略回测兼容由 70 接受，63 只冻结和对照合同。具体资产经济政策仍按待决表处理。

## 5. Rejected 后迟到事实的框架投影

D63-38 的普通单和休市待发单均通知 Rejected；“取消待发”指停止本地待发及禁止自动重排，不是另发场所撤单或改用 BT Canceled。判定时点不添加静默期/多轮确认。后续同一强身份的真实成交必须保留原归属，持久记录原判定、矛盾/更正版本和来源事件，不另造策略意图或自动补单。

当前源码 `Order.execute` 会依据剩余量写 Partial/Completed；`_direct_process_matched` 对成交调用 `_direct_apply_trade`，后者执行订单、记持仓并通知。因此旧报告“Rejected 在框架层绝对不能转出”的前提不成立；这也不证明新 Gateway 的恢复、Trade/Analyzer 或母单投影已经正确。

63.01 须用真实 BT 框架与替身来源做最小可行性验证，再冻结一种表达。推荐保留原 Rejected 通知的历史，绑定原 Order 身份处理迟到成交增量并明确标识事实更正；不要另建不相关订单、只改报告而漏掉持仓/成交，或重复发送原 Rejected 通知。具体回调字段与终态修订兼容性须由原型证明；若需要改变对外回调合同，应先展示具体差异供用户审阅。

63.06/07 覆盖原单仍在内存、已重启、成交先于委托、更正事件与 ACK 之间崩溃、同一成交重放、费用迟到及策略已据 Rejected 发起新意图的场景。断言原命令与新意图不被合并；真实成交/Position/Trade/费用各记一次；原历史通知可追溯；Analyzer 明确覆盖/不可恢复范围；不能因订单不 alive 丢弃来源真实成交。63.13/65 按同一更正事件校正原母单完成/占用，不回滚真实成交或伪造转移。

## 6. 交易日志、备份与恢复

普通诊断日志只输出有限码、去标识引用及必要状态，不输出凭据、认证材料、原始账号或完整订单载荷。受保护的交易 journal 则必须保存恢复需要的规范订单摘要、原生强身份、数量/价格/来源、账本分录、费用版本、授权版本、急停原因、操作结果及消费进度；其访问权限、导出脱敏和保留独立配置。禁止凭据进入任何一种日志。对外文档或审阅仍只用脱敏快照。

63.03 交付一致备份与离线恢复的技术路径，63.01 冻结落盘/提交成功定义、备份元数据和保留约束。备份须覆盖同一权威时点的数据库与适用日志内容，不能简单复制正在写入的主文件就声称一致。备份记录账户去标识引用、schema、owner epoch、交易日、账本/事件水位、创建时间和完整性信息；运营手动备份和定时策略是独立配置，不因设计而立即触碰现有账户日志。

恢复到隔离位置，先验证来源、完整性和 schema，再证明旧 writer 已退出与迟到 fence；按最后可信备份水位和可证来源补齐后，才能核对归属、未决、急停及消费进度。场所查询、各策略 live_state 都只是补充输入，不能重建缺失的内部转移、虚拟成本或全部历史授权。不得从“账户−Σ策略”重建 external，也不得仅凭最新持仓或未找到命令重置账本/序号。缺证明保持待核/UNKNOWN；来源不明只记未归属，不能记 external。恢复旧备份不能回退幂等高水位或使已派发键再次可用。

用新建 synthetic 库演练备份、备份后有派发、恢复旧副本、重复回报、缺失转移记录、schema 不匹配、只读/满盘和旧 owner 存活；本轮及未来测试均不得处置 retained host 或重跑已消费调用。63.10 文档只发布已验证的恢复步骤；应急撤单工具仍按 RV63-OP01 待决，不由备份功能自动获得授权。

## 7. Gateway 日历与合约状态接线（承接迭代 67）

承接 [67 计划 §3.10](../迭代67-交易日历数据文件化与每日更新/迭代计划.md)与 [65 计划 §3.9](../迭代65-bt_api_execution独立执行服务/迭代计划.md)：Gateway 运营配置接收日历根引用（候选键 `calendars.root`，最终与 67 schema 对齐），SDK 向 provider 组合版本化日历；Gateway 在自己的日切流程读取/重读，并转发中立的日历状态和合约状态观察。客户端取得版本/覆盖、来源时间、合约/品种范围、会话代际、交易日、完整性及有限错误，不取得服务器文件路径、凭据或原生客户端。

67 拥有文件发布、版本选择、中立类型、provider 状态投影和 SDK 合成；63 拥有 Gateway 配置接线、服务转发和消费者恢复。策略本地日历投影可保留，但不得假设与 Gateway 自动同版，须比较 calendar_ref 与覆盖；缺失、冲突、过期或旧代际观察不得扩大可交易范围。文件日历是预期安排，不能替代 provider 当前交易日、结算、实际合约状态或来源时钟证明。

63.01 与 67.01 冻结接口；63.05 提供组合/读取路径，63.13 提供 Execution/观察 principal 的版本化状态。先用明确替身推进；真实文件日历接入依赖 67.04，实时状态转发依赖 67.06 的实际交付，不能要求 67 综合验收先完成。67.06 的本体不反向依赖 Gateway 转发验收；两边独立本体通过后联合回环。67 未交付时基础 Gateway 继续使用迭代 62 已有且仍有效的日历合同，不以替身宣称文件化接入完成；需要新日历覆盖的算法/扩展保持 GAP。

验收：日内版本固定与日切换版、加载失败、覆盖不足、版本不一致、旧会话/旧日状态、状态范围不匹配、仅收紧不凭观察放宽、客户端不读服务器路径及不加载 CTP 原生库。记录 63/67 版本和共用联调回执，63.10 分别汇总基础与文件化扩展。
