## 1. 用户需求与完成定义

目标场景是回测约十年的期权、期货或股票数据，历史累计可能有 **100,000** 个不同证券或合约，而同一时点需要处理的合约约为 **1,000** 个。

本轮交付应当做到：

1. 尚未到达上市或显式激活时间的合约只登记轻量元数据；不创建完整 Feed/指标、不打开行情源、不读取行情记录。
2. 到达激活时间后才创建 Feed、建立普通 Backtrader Indicator 依赖并预热；其他合约继续运行。
3. 引擎行情读取、指标推进和策略活动集合查询只涉及当前需要处理的对象，不逐 bar 扫描全部历史合约。
4. 停止交易后退出新交易信号集合；在订单、持仓、结算、依赖和历史保存完成后退出调度、关闭资源并释放大缓存。
5. 合约身份保持稳定，历史订单、成交、持仓归属和分析结果不因退出而改变。
6. 通过静态小样本基准、独立经济事件参考和完整规模运行证明正确性与资源边界。不能只用“策略少循环了”作为引擎优化验收。
7. 同一长期活跃 Feed 上大量下单时，终态订单、通知、成交片段和已平仓交易不在内存中无限累计；不必等 Feed 退市才归档历史。
8. 在不改变撮合、回调、资金和持仓结果的前提下，完整历史可以按稳定身份、时间和游标查询；归档不能以丢记录或破坏历史查询换取低内存。

这里的“从 datas 移除”定义为**从受管活动集合及实际调度集合退出**。不让策略直接执行 `self.datas.remove()`，也不把旧 Feed 改名复用为新合约。

## 3. 范围与兼容合同

### 3.1 必须交付

- 显式启用的动态 Data 模式，接入现有 Cerebro/runnext、普通 Indicator 和 BackBroker。
- 历史、已闭合 bar 的日线和分钟线；同一次运行中的动态合约采用一致 timeframe/compression。固定标的或基准 Feed 作为明确依赖。
- 单 Strategy 下多合约组合交易；单合约指标及对固定标的的显式依赖。多腿分别下单沿用已有撮合语义，不新增原子成交承诺。
- 合约目录、事件驱动的激活/退出、按需数据工厂、独立指标预热、活动集合和期权链索引。
- 不持仓退出、提前平仓退出、存在挂单/部分成交的退出，以及显式结算事件的处理合同。
- 一个有限、明确的现金结算期权示例模型和独立参考；覆盖多空、乘数、费用、缺结算价及重复结算事件。它不代表所有交易所期权规则。
- 有界行情缓存、历史事件落盘、资源观测、真实文件读取的规模测试，以及股票/期货生命周期样例。
- 订单、成交片段、Trade/TradeHistory 的有界留存及独立归档，覆盖仍活跃的合约和少量长寿命订单；本地持久历史读取不依赖存活的 Cerebro/Strategy/Feed。

### 3.2 初版明确不支持

动态模式不支持 `runonce=True`、`preload=True`、优化多进程、多个 Strategy 共享动态集合、live/SDK 执行、channel 模式、replay/resample、混合动态周期、cheat-on-open/close。不兼容组合须在启动行情源前报错，不静默回退。普通静态模式的既有能力继续按原路径工作。

订单历史归档通过显式 `history_policy` 启用：动态模式必须配置持久归档策略；固定 Feed 的普通历史逐 bar 回测也可单独启用，以解决同一品种高频下单的内存增长。未配置的静态模式保持原有历史行为。归档模式初版采用与上段一致的逐 bar、单 Strategy、历史回测能力边界；不支持组合须明确拒绝。正常下单、查询未完成订单及回调的语义保持一致；直接把私有 `_orders/_trades` 或 Broker.orders 当全量历史库的用法，在显式归档模式下须迁移到公开历史查询接口，不能承诺旧容器仍无限保存对象。

本轮不承诺任意第三方 Analyzer、依赖全历史 `.array` 的自定义指标、运行时自动拼接多个动态合约的指标图，以及 FactorStrategy/Alpha101 截面研究的动态成员语义。这些组合须有明确的能力检查；不支持时拒绝，不能输出貌似完整的结果。原有静态研究路径属于回归范围。

美式提前行权、实物交割、标的交付后的完整账户处理、各交易所规则全集、数据采购、实盘、发布和部署不在本轮完成声明中。未注册相应终止处理模型的持仓不能被强制清零或标成已归档。进程崩溃后的恢复另行规划，本轮只保证同一运行内的事件幂等和失败留痕。

## 4. 数据结构与拟议接口

以下名称是拟议接口，R0 冻结最终命名并同步全部样例；行为合同不因改名降低。

### 4.1 四类集合

| 结构 | 内容与生命周期 | 访问约束 |
|---|---|---|
| `InstrumentCatalog` | 全部合约的轻量、可版本化元数据和源定位符 | 允许一次性 O(N) 建索引；不保存 DataFrame、Feed、指标或全部行情 |
| 受管调度集合 | WARMING、ACTIVE，以及仍需处理事件的 DRAINING 对象 | 引擎只推进必要对象；不能退化为遍历全目录判断状态 |
| `Strategy.active_datas` | 已上市、预热完成、允许新交易的动态 Data 只读视图 | 支持正常迭代；成员只在事件边界改变，顺序稳定 |
| 历史存储 | 不可变身份、状态、订单/成交/结算和可选行情输出 | 按 ID 分页读取，不在运行内累积全部历史对象图 |

`self.datas/data0/data1` 在初版动态模式中仍表示启动时固定注册的标的、基准或时钟 Feed，不把十万个动态合约追加进去。动态合约通过显式视图和查询 API 访问；不改变静态模式的公开编号语义。文档必须清楚区分两种集合，不能宣称所有旧策略零修改支持动态模式。

动态 Feed 不调用普通 `Cerebro.adddata()`，不追加到 `Cerebro.datas/feeds/datasbyname`；其创建、启动、ID 查询和停止由独立的受管注册表负责，再接入现有事件循环。既有 `getdatabyname()` 继续查询固定 Data，动态 ID 查询使用受管注册表，不混用名称与身份索引。

目录至少包含 `instrument_id`、交易场所/代码、资产类别、标的、期权方向/行权价/乘数、上市时间、停止接收新订单时间、最后可成交时间、经济到期与结算规则引用、时区/交易日历、源位置和输入版本。字段按资产类别校验；股票可没有预先确定的退市时间。

- `instrument_id` 在运行内唯一且不可复用；显示代码可以按场所和生效区间解析，歧义必须报错。
- 区分记录的 `effective_at` 与 `known_at`。策略不能查询当时未知的上市、退市或条款变化；目录离线建立不授予未来信息的使用权。
- 源 EOF、临时无 bar、停牌、停止交易、到期和完成结算是不同事件。禁止用“最后一行日期”自动证明经济到期。
- 查单一合约使用 ID 映射；按标的/到期月份/认购认沽建立活动桶，行权价可用有序索引。查询不能扫描全部历史合约；结果按固定键排序，同一输入重排不得改变交易顺序。
- 目录自身 O(N) 的成本单列统计，不能把它声称为 O(1) 内存。

## 5. 生命周期、时钟与执行顺序

### 5.1 状态机

```text
REGISTERED ──上市/激活──> WARMING ──所需指标就绪──> ACTIVE
                              │                     │
                              └──停止交易───────────┤
                                                    v
                                                DRAINING
                                                    │
                          订单/持仓/结算/依赖/存储全部满足退出条件
                                                    v
                                                ARCHIVED

任何阶段的不可恢复错误 → FAILED（保留原因、终止本次运行，不假装正常退出）
```

REGISTERED 未激活时 Feed factory/open/read 计数必须为零。WARMING 只有已真实到达且允许使用的历史样本，不能用未来数据、复制报价或补零缩短预热；合约寿命不足所需窗口时允许从 WARMING 直接进入 DRAINING，记录始终未就绪。

ACTIVE 缺少本时点新行情时，保留明确的新鲜度/更新时间，不能伪造一次新 bar；现有持仓估值是否允许使用最后报价由明确估值策略决定。缺行情不能变成自动退市，也不能用过期报价撮合新订单。

DRAINING 立即退出新交易集合。普通行情源可在完成最后需要的读取后关闭；结算事件可来自独立、有界的事件源。仍需保留的对象、依赖和期限必须可观测，不能无限累计却仍宣称内存有界。

ARCHIVED 是该运行内的终态；重复退出请求不得重复关闭、重复记账或重新读取行情。回调失败、打开失败、输入损坏、存储失败和停止运行均有确定的清理路径。

### 5.2 时间边界

1. 使用明确的时区、交易日历和 bar 时间含义；内部排序采用统一时间基准，夜盘交易日不由自然日粗略推断。
2. `activation_at` 决定允许创建数据源的最早时间；受管预热不能早于该时间。如果回测从合约中途开始，历史回补必须显式限定在当时已知、已发生的区间，且不能把回补时段当作本次可成交时段。
3. `order_cutoff_at` 起拒绝新普通交易订单；已有订单能否在 `last_trade_at` 的最终报价成交由冻结的执行规则判断。到期、最后交易和结算时间不可混用。
4. 至少有一个覆盖回测区间的固定时钟来源：标的/基准 Feed，或受管的有界日历 Feed。首个短命期权不能充当唯一时间来源。无活跃期权时仍能推进到下一上市/结算事件。
5. 上市、停止交易和结算按排序事件队列推进；启动排序成本与逐步调度成本分开。每根 bar 不重新筛选整个目录。

### 5.3 同一时间戳的固定顺序

在现有 Cerebro 事件循环内扩展阶段，不建立另一个独立时间循环：

1. 应用截至该时点已知且生效的目录变更，激活新对象，设置停止接收新订单的状态。
2. 读取本时点各个到期应更新的 bar，完成时间对齐；对本时点输入形成一致视图，再按原生依赖顺序推进指标。
3. Broker 按既有普通回测语义处理之前提交的订单，检查合约交易时间和报价时效，发出订单/成交通知。
4. 处理退出、撤单终态及符合条件的结算事件；发布不可变生命周期通知。重复结算事件只产生一次经济影响。
5. 调用策略，策略遍历本步稳定的活动集合；新订单仍遵守普通的后续可成交事件规则，不能因动态加载引入同 bar 未来成交。
6. 保存本步记录，并在回调和迭代结束后执行满足条件的释放。禁止在正在遍历的容器中即时增删对象。

同一阶段多合约使用稳定 ID 顺序；文件枚举顺序、目录行重排和分块大小变化不能改变结果。没有行情而只有结算/生命周期事件时也必须处理该事件，不能伪造交易 bar。

## 6. 原生指标、持仓和结果的集成

### 6.1 指标所有权与预热

- 每个动态 Data 有受管的指标作用域；框架在正确的 `OwnerContext` 中调用构建钩子一次，收集整棵普通 Indicator/LineActions 子图并绑定真实源时钟。
- 新图构建完成后，对该作用域计算依赖窗口并执行 stage2 切换，再注册到引擎的受管指标调度入口。不能只设置 OwnerContext，也不能重新执行全 Strategy 的 `_periodset()`/`_stage2()`。每个节点仅由一个 owner 路径推进；归档时从同一注册入口完整解除。
- 复用现有构造和 `prenext/nextstart/next` 生命周期；策略不手动调用指标的 `_next()`，不复制指标数学实现。
- 合约就绪条件由该作用域的实际依赖与最小周期决定；新合约不能重置全局 Strategy、其他合约或固定标的的阶段。
- 中途开始回测的历史回补采用有界读取和按时间顺序的作用域内预热回放：每根允许使用的历史 bar 推进一次完整子图，追平后才接入当前调度。回放不推进全局账户时钟，不调用交易决策或重放订单/结算；跨固定标的的依赖必须取得对应历史时点的值，无法取得时明确拒绝，不能代入当前值。
- 保留 QBuffer 的实际窗口需求，包括子指标累积窗口、递归输出 `[-1]` 和显式历史访问。不能通过提高 minperiod 掩盖缓存问题，或忽略窗口溢出返回零值。
- 对固定标的的依赖只订阅既有已推进数据，不重复计算标的指标。自动跨多个动态合约构图暂不支持；显式依赖检查须在交易前完成。
- 退场时解除 owner 注册、绑定和缓存引用；仍存在消费者时保留明确的引用占用记录。不得清空共享标的缓存来释放单个合约。

### 6.2 Broker 与经济退出

- 不改变既有持仓的证券归属；动态数据对象即使被历史订单引用，其稳定身份也不改名、不换绑。
- DRAINING 不代表已平仓。撤单请求、撤单确认、部分成交、剩余数量、OCO/bracket 子单必须逐项达到终态。
- 默认终止策略为“必须已经无仓、无未完成订单”；不满足时明确失败，禁止隐式强平、丢仓或抹掉保证金。提前平仓由策略在可成交窗口内完成，不能在 EOF 后按旧报价制造成交。
- 本轮另提供显式现金结算示例模型：条款、乘数、方向、费用、结算时点、结算标的价格及来源均固定；用独立小样本账本核对现金、持仓和损益。缺价格、未知条款、重复且冲突的事件必须失败。
- 已归档合约不得继续匹配订单；新交易针对过期 Data 引用须拒绝。Broker 估值/待执行订单索引不能每步扫描全部历史零持仓和全部终态订单。
- 不新增“所有期权结算已经支持”的声明；不适用的实物交割或提前行权请求按能力边界拒绝。

### 6.3 释放条件和分析器

合约进入 ARCHIVED 必须同时具备：行情终止原因明确、无未完成订单、无剩余持仓或已完成明确结算、无需要继续推进的消费者、通知已处理、历史存储确认成功、资源关闭成功。

释放检查覆盖 Feed 数组、源文件/游标、DataFrame/读取块、指标子图、owner 注册、别名索引、观察器和历史订单间接引用。可以保留轻量身份/最终快照，不得让十万个终态订单对象继续保留十万个大 Feed 缓存。仅观察 RSS 下降或调用 GC 不算释放证明。

初版保留已发出 `order.data` 的对象身份：**合约归档**时将该 Data 封存为仅含身份和终态元数据的对象，清除其行情缓存、源句柄和指标依赖；通过旧引用读取行情应明确报已归档，不能返回别的合约或旧价格。**订单归档**不改变仍活跃 Feed 的状态，也不要求对应持仓已经平仓。订单创建/成交快照须在释放前持久化；满足第6.4节条件后，框架移除终态对象强引用，历史 API 从快照回读。运行索引只保留未完成对象、未消费通知和仍有交易依赖的关联对象，各自计入预算。

动态模式提供明确的分析器支持清单和生命周期钩子。至少接受账户资金/价值、收益/回撤、订单/成交明细，以及按合约 ID 的持仓长表；动态成员不采用一开始固定十万列的宽表。未适配分析器在运行前拒绝。全历史查询按分页读取，需要全量物化的用户请求单独说明内存成本。

初版支持账户级 Analyzer 和基于不可变事件的明细收集器：Analyzer 只启动/停止一次，按固定账户时钟推进，不依赖动态 `dataN` 别名，也不因某个合约预热重置全局 minperiod。按 ID 的事件订阅在激活时建立，最终通知落盘确认后解除。任意按合约动态创建 Analyzer、独立 Analyzer 预热及旧宽表分析器的自动适配不在初版范围，能力检查明确拒绝。

行情与结果写出采用有界批次，记录缓冲上限、写出确认及失败行为。不能用现有 `research.CsvSink` 的完整内存收集冒充流式落盘。完整图表使用落盘历史重建；动态内存窗口不承诺直接支持原来的全历史 `cerebro.plot()`，初版明确报不支持。

### 6.4 订单、成交与交易历史的内存合同

#### 6.4.1 三类记录分别推进

| 对象 | 保留运行对象的条件 | 可归档的时点 |
|---|---|---|
| Order | Created/Submitted/Accepted/Partial，或仍被 bracket/OCO、激活队列和消费者实际需要 | 明确进入 Completed/Canceled/Expired/Margin/Rejected，且通过下述归档检查；`not alive()` 只说明不再可成交，不能代替依赖、消费和持久化检查 |
| OrderExecutionBit / 状态通知 | 尚未被全部同步消费者消费，或尚未持久化确认 | 每个已消费区间可增量归档，即使订单仍 Partial；保留当前累计成交标量及未消费片段 |
| Trade / TradeHistory | 当前仍未闭合的交易及未消费更新；同 tradeid 再开仓视为新的交易实例 | Trade 闭合且通过归档检查后释放运行对象；未平仓 Trade 的已消费历史也持续归档，不能等平仓才释放明细 |

订单已成交不等于 Trade 已平仓，Trade 已平仓也不等于合约退市。三者使用独立状态和完成检查；开仓单归档后，持仓、后续平仓、收益归因必须继续正确。

订单/Trade 归档顺序固定为：终态判定 → 关联依赖确认 → 本轮同步消费者完成 → 不可变快照及明细持久化确认 → 从运行容器移除。同步消费者包括 Strategy 的 `notify_order/notify_trade`、Analyzer/Observer 通知及本 bar 的 `next`；只清空 Broker.notifs 还不够。回调期间原单、参数和执行片段保持可读；归档不得额外触发交易通知，失败重试也不能重复成交或重复回调。

bracket 初版按关联组完成后释放有依赖的原始对象：父单终态不能导致子单丢失，须检查 `_pchildren`、`_toactivate`、`parent` 引用和撤单收尾。OCO 在组内所有后续取消/撮合动作完成后清理 `_ocol/_ocos`，包括只含数字的历史映射。组未完成时可先落盘已发生记录，但保留必要对象并报告占用原因和数量。

#### 6.4.2 持久记录与历史查询

初版交付一个本地持久后端，优先复用合适的现有组件；若无可复用后端，采用版本化 SQLite schema、事务提交、磁盘索引和有界页缓存。不得以 pickle 整个 Order/Trade/Strategy 对象图作为归档，也不同时建设多套历史后端。`history_policy` 统一管理 sink 和配额，合约与订单复用同一运行身份及事务提交边界。

历史至少保存以下值类型信息：

- `schema_version/run_id/strategy_id/instrument_id/order_ref/tradeid/trade_instance_id`、事件序号和事件时间；`order_ref` 只在相应运行内解析，复用 tradeid 不覆盖过去交易。
- 下单时的 created 字段、执行方式/有效期、方向/数量/价格、父子/OCO 关系 ID，以及每次状态转移的 executed 标量快照、拒绝/撤销原因和费用配置身份。
- 每个成交片段的稳定 ID、先后顺序、时间、数量、价格、value/comm/pnl、开平数量和执行后的仓位；归档保留完整明细，不能仅存最终平均成交价。
- Trade 的开闭时间、状态、数量、价格、累计费用、毛/净损益和关联成交；`tradehistory=True` 时保留每次原有历史更新，将 event.order 表达为稳定 ID/不可变订单快照。关闭该选项时不伪造原本不存在的 TradeHistory，但基础订单、成交和闭合 Trade 记录仍齐全。
- 用户扩展 info 仅通过明确的值类型编码或注册适配器保存，编码大小有上限；不能悄悄丢字段或把 DataFrame/Feed/回调闭包写入历史。可预检的非法输入在提交前拒绝，运行中才出现的不可归档字段明确报错并保留未提交记录状态。

数值按原始可表示精度保存，时间含时区/交易日语义，不因展示格式、JSON 小数截断或单位转换改变结果。归档是提交后的不可变记录；同一事件 ID 的重复写入可幂等确认，内容冲突必须报错。仅成功入队不算持久化确认；记录及其查询索引须在同一原子提交中变得可见。

拟议公开接口为 `history.get_order(run_id, order_ref)` 和按过滤条件/游标分页的 `history.iter_orders(...)`、`iter_order_events(...)`、`iter_fills(...)`、`iter_trades(...)`、`iter_trade_history(...)`。get_order/iter_orders 返回读快照水位下每张订单的最新状态；iter_order_events 保留每次原始状态通知的独立记录，不合并 Submitted/Accepted/Partial/Completed。返回值都是不可变记录，不返回带 owner/broker 的运行对象；可通过父子、OCO、成交和交易 ID 继续追溯。常用过滤至少包括运行、策略、合约、时间、订单状态和 trade_instance_id，索引不能全量装入 Python 字典。

运行中查询须统一当前运行状态、已终态待提交尾部和已提交历史，明确 pending/durable 状态，按稳定事件序号去重且不漏记录；分页游标绑定固定查询条件和读快照水位，查询期间新增提交不能让翻页重复或跳过记录。只能查询当时已发生的事件，不能暴露未来行情。运行结束后可用独立只读 reader 在新进程打开历史，无需恢复 Cerebro、Strategy、Feed 或行情文件；查询不重新创建 Feed、不下单、不触发回调。全量导出使用迭代批次，主动 `list(...)` 全量物化属于调用者成本。

#### 6.4.3 引用清理与有界缓存

- 清理清单覆盖 Broker 的 orders/submitted/pending/notifs、bracket/OCO/激活关系，以及 Strategy 的 `_orders/_orderspending/_trades/_tradespending`、Trade.history、Analyzer/Observer 缓存、历史写入队列、序列化中间对象和查询缓存。零持仓键/空交易桶只能在无依赖时删除，不能删除当前持仓或活动订单。
- 采用“移除框架对已消费对象的强引用 + 保存独立值快照”，不以直接赋 `order.p.data=None`、`order.owner=None` 或修改共享 `p/created/exbits` 作为清理捷径。原单和通知浅拷贝共享的对象仍有消费者时不能被改写。历史记录不得包含 Order→owner→Strategy→Cerebro、TradeHistory→Order 或 Feed→源 DataFrame 的引用链。
- 正常交易期间保留当前 `created/executed` 标量语义、订单身份和 `iterpending()` 的精确增量消费语义。已消费执行片段采用绝对序号及有界窗口/历史读取适配，不得直接从共享 deque 左侧删除造成 p1/p2 错位。完整 exbits/TradeHistory 的读取可采用只读分页适配器，保留原有顺序、数量和字段；自定义代码若要求直接修改历史 deque/list，归档模式明确不支持，不能默默截断。
- 每个关闭 Trade 及历史更新按独立交易实例归档；只保留当前开放 Trade 的必要累计状态，不保留过去所有 Trade 作为下一次开仓的前置条件。Analyzer 的累计统计可常驻，逐笔明细须消费后写出或受配额限制。
- 不以无限增长的 ref→offset、去重 set、已完成 ID 集合、日志列表或 weakref 探针列表替代原始对象。完整索引和历史幂等判断使用磁盘后端；基准诊断也只能抽样保留有界探针。
- 用户自行保留原始 Order/Trade 或复制全部历史属于显式外部引用，须说明它可能经 owner/data 保留运行图，不能声称框架能强制回收。推荐保留历史 ID/不可变记录；验收分别覆盖“只保留历史记录仍可回收”和“保留原始订单形成可解释引用、释放后可回收”。已完成合约的行情缓存清理仍遵守第6.3节。

写入队列、批次、未确认明细、查询页及历史缓存同时设置条数和字节上限。达到上限时停止接受新的工作，并在历史回测事件边界等待已提交任务；不得丢弃记录、跳过撮合或跳过模拟时间。写出超时、磁盘满、事务失败、查询损坏必须给出明确错误、最后已提交水位及未持久化记录范围，运行标记 INCOMPLETE；不能先释放原记录再报告丢失。正常 runstop/结束须处理在途通知、提交可归档历史并关闭资源；仍有未完成订单或未闭合交易的快照标记为未完成，不能为了退出伪造 Completed/Closed。

### 8.1 正确性参考

小样本静态基准使用同一原生引擎逐 bar 路径、同一排序、同一可交易时间和同一策略规则，显式处理迟上市的 `prenext`，不能因静态基准本身不交易而得到空结果相等。另设简短、独立的经济事件账本，不用新动态实现生成自己的 golden。

配对包含实际非零持仓、成交、费用和结算见证。原始事件完整保存；不同运行产生的 order.ref 可通过稳定逻辑订单键建立一一映射，但不得合并重复订单、删去失败事件或重排输出掩盖顺序差异。日期、身份、数量、状态、分支和以货币最小单位表达的 fixture 现金结果精确一致；连续指标的容差在 R0 冻结，并对同运算顺序优先要求精确配对。不能通过只比较最终收益、NaN 交集或降低比较范围验收。

历史归档配对在可承载的小样本上使用相同策略/行情/执行规则，分别运行原有内存历史和新持久归档路径；动态路径则在测试配置中保留同样生命周期、仅切换历史策略。覆盖 Market/Close/Limit/Stop/StopLimit/跟踪单、所有终态、部分成交、反转仓位、OCO/bracket、同 tradeid 重开、`tradehistory=True/False`。按原始发出顺序比较全部订单和交易通知，包含未成交、撤销及拒绝，不能只比成功成交。用户回调读取 created/executed/iterpending、支持的 Analyzer/Observer 当轮读取及之后分页回读都要实际执行；查询有无、分页大小不同不应改变交易结果。归档关闭的大样本不要求强行跑到内存耗尽，百万单使用独立预期计数/账本摘要及完整流式回读。

### 9.2 冻结门槛

以下为本计划设定的验收目标，尚无实测结果。实施 R0 固定机器、解释器、日历、数据布局、策略、指标数量和读取块配置；若改变目标，先修订计划并保留原失败证据，不能跑完后放宽阈值。

- 常规计时在单进程 Anaconda base Python 3.11 上串行运行，不同时运行 xdist/coverage/其他性能任务。B1 三轮配对并交换顺序，单列启动与稳态、冷读与热读；不能混算。
- B1 的100,000对10,000目录场景，稳态单步中位数比值 **≤1.20**，p95比值 **≤1.25**；同时输出实际操作计数，不能仅凭计时掩盖 O(N) 扫描。预先建目录和终态离线汇总允许 O(N)，逐事件全目录扫描计数必须为零。
- B2 的行情配置固定为每合约7条数据线、SMA5/EMA5、声明窗口预算64格和有界结果批次；峰值进程树 RSS **≤2 GiB**。这个预算不适用于任意自定义指标数量或全历史结果物化。
- 存活的重型 Feed 数量不得超过 `固定Feed + WARMING + ACTIVE + DRAINING中仍需Feed者 + 有原因的依赖保留者`；不得把 ARCHIVED 身份壳计作重型 Feed 隐藏缓存。基准的待收尾/依赖保留上限另固定为128，达到上限须明确失败，不能无限排队。
- 同时打开的行情资源不得超过受管预算；以一合约一文件配置时，上限为当前需读取 Feed 数加16个固定余量。每次归档后资源计数回到应有水平，运行完成后恢复启动前基线。
- 缓存格数按各实际依赖窗口及明确额外格计算；未激活与已归档合约的大行情缓存均为零。记录 Python对象/数组/读取块的存量及引用见证，不能只用逻辑列表长度证明释放。
- 扣除可测的元数据和有界输出缓存差异后，B2稳态后段相对前段的残留存量不得随归档合约数线性增长；RSS区间中位数增量目标 **≤max(64 MiB, 前段中位数的20%)**。须同时检查对象引用，区分分配器保留与实际泄漏。
- B1/B3 使用与B2相同的每合约7条数据线、SMA5/EMA5、64格窗口和有界输出配置；B3沿用2 GiB进程树RSS及128个待收尾/依赖保留上限，报告完整吞吐、p50/p95/p99和同样的资源计数。没有既定策略吞吐基线时不虚构“提速100倍”，也不以日线结果代替分钟运行。

B1 的比值是本轮明确的时间开销门槛；B3 的吞吐和延迟分布作为诊断记录，PASS 只表示其资源及正确性要求满足，不表示达到某个未定义的绝对吞吐或时延目标。

全程区分目录 N、WARMING/ACTIVE/DRAINING 数量、实际调度数、实际读取数和实际交易数。至少记录文件打开/读取字节、bar计数、指标调用、逐步集合访问、查询候选数、订单/成交/结算/输出条数、错误及关闭结果。按交易日采样并在激活/归档边界记录峰值；进程树 RSS 另以固定间隔采样。

### 9.3 大量下单的资源门槛与历史回读

B4–B6 使用真实 Cerebro、BackBroker 和 Strategy 下单，不以直接构造 Order 或数据库插入代替；启用 `preload=False/runonce=False/exactbars=1`、有界文件输入与历史归档。关闭默认全历史绘图观察器，保留已适配的账户统计和事件收集器。B4 固定全部 OHLC=100、初始现金100,000,000、乘数1、股票式现金记账、Market 订单和 checksubmit=True，至少提供 Q+2 根 bar；每档应有 Q 张原单、Q 次成交、3Q 条 Submitted/Accepted/Completed 通知及 Q/2 个闭合 Trade。这些是磁盘历史的预期计数，不是允许常驻内存的对象数；费用应为 Q×0.01，最终净仓位零，现金按独立账本核对。B5 同样令 OHLC=100、每 bar volume≥1，用确定的 filler 产生真实部分成交，并在买单全部完成后才提交卖单；B6 沿用原有撮合/关联单逻辑，不绕过父子单激活或 OCO 取消。

B4 的三档在独立进程完整运行；B5/B6 单独运行。每种配置固定配额、后端缓存、输入块和输出字段，单列初始化/结束刷盘/查询成本；输入离线生成，不在回测进程持有整个输入 DataFrame。以下是待验收目标，并非实测结果：

| 维度 | B4–B6 冻结门槛 |
|---|---|
| 进程树 RSS | 每次完整运行峰值≤2 GiB，包含写入端/子进程；不把历史服务内存移到旁路后排除统计 |
| 写入批次 | 每批最多1,024条或4 MiB，先达到者生效；待写/未确认值记录合计最多8,192条或32 MiB，二者同时约束 |

| 稳态增长 | B4 在相同批次水位、开放订单/交易数及缓存状态下，从100,000到1,000,000单的稳态 RSS 中位数增量≤max(64 MiB, 前段中位数的20%)；对象计数不得随累计订单量增长 |
