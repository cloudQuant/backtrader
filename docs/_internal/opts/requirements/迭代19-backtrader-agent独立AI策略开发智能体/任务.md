## 0. 立项结论

本迭代建设第三个可单独安装和使用的产品 `backtrader-agent`。用户显式选择该 Agent
后，宿主 AI 必须在不安装、不启动、不读取 `backtrader-mcp` 和
`backtrader-skills` 的条件下独立完成：

```text
理解需求
  -> 检查、登记并加载本地数据
  -> 形成 StrategySpec
  -> 检索策略语料与当前 fork 模板
  -> 生成 single_test 或 python_bundle
  -> 静态/API/安全校验
  -> 预览并批准受限文件变更
  -> apply 后复核目标 hash
  -> 单独批准受控回测和测试
  -> runonce/runnext 与必要的 master/dev 比较
  -> 诊断失败并最小修复
  -> 输出指标、报告和完整 provenance
```

这里的 `Agent` 不是新起一个模型服务，也不是 MCP/Skills 的代理壳。它是宿主 AI 可发现、
可显式激活的 Backtrader 专家 Agent 包，拥有自己的 persona、菜单、工作流编排、契约、
语料目录、模板、确定性脚本、校验器、runner、报告和验收。

用户可获得三个入口，但每个入口都是完整产品：

| 产品 | 主要交互形态 | 独立性要求 |
| --- | --- | --- |
| `backtrader-skills` | 按意图触发的多个聚焦技能 | 无 MCP、无 Agent 仍完整 |
| `backtrader-mcp` | resources/prompts/typed tools | 无 Skills、无 Agent 仍完整 |
| `backtrader-agent` | 显式选择的专家 persona、菜单和工作流状态 | 无 MCP、无 Skills 仍完整 |

三者可以读写格式兼容的公开 v1 契约，但不能共享运行库作为必需依赖，不能互相调用来
补齐缺失能力，也不能把“组合使用可完成”作为验收结论。

### 1.2 Agent 形态决策

P0 采用：

```text
stateless host Agent
  + explicit AgentSessionManifest
  + append-only local event journal
  + deterministic product-owned scripts
```

解释：

- `stateless` 指 Agent 不依赖隐藏模型记忆、BMad memory sidecar、First Breath 或
  PULSE 才能正确工作；
- 会话阶段、artifact、hash、审批、run ID 和修复历史写入明确的产品产物，因此崩溃后
  可恢复，但不保存模型隐藏推理；
- 新激活默认从当前请求开始，只有用户显式选择 `session_id` 才读取旧任务产物；
- 宿主 AI 负责理解、生成和解释；所有索引、数据解析、hash、写入、校验、运行、比较
  和报告由确定性脚本执行；
- P0 不嵌入 OpenAI Agents SDK、模型 API key 或远程推理客户端；
- 若未来需要 headless/autonomous、长期语义记忆或 SDK adapter，进入 P1，不能成为
  首版完整闭环的前置。

### 1.3 为什么不能直接复制现有 BMad Agent

当前部分 `bmad-agent-*` 菜单通过 `skill = "bmad-*"` 调用外部技能。若
`backtrader-agent` 通过相同方式调用 `backtrader-strategy-author/test/review`，将形成
对 `backtrader-skills` 的隐藏运行依赖，违反用户要求。

本 Agent 的菜单必须：

- 路由到包内 `references/` 的工作流说明和包内 `scripts/`；
- 不声明 `skill = "backtrader-*"`；
- 不调用 MCP tool/resource/prompt；
- 不依赖 `_bmad` runtime、Builder 或 roster 注册才能完成 P0；
- 可以在兼容宿主中可选注册，但注册只是发现便利，不是运行前置。

## 2. 用户场景

### 2.1 核心场景

1. 用户激活 `backtrader-agent`，执行 doctor，确认实际 Backtrader 源码、数据根和能力。
2. 用户给出本地 CSV、Pandas/仓库 fixture，Agent 检查字段、时间、质量、时区和 feed
   映射，生成 `DatasetManifest`。
3. 用户描述策略意图，Agent 澄清数据、信号、交易方向、仓位、退出和风险，生成
   `StrategySpec`。
4. Agent 检索两套语料，只返回当前任务相关模板和 2–3 个有 provenance 的参考。
5. Agent 为七类策略生成一个功能测试，或完整 Python 三件套。
6. Agent 先把文件写入产品私有 draft，审查生命周期、时钟、参数、API、安全、
   look-ahead 和数据泄漏。
7. 校验通过后，Agent 展示精确文件清单和 diff；用户批准后才写入目标根并复核 hash。
8. Agent 经第二次批准后运行固定回测/测试，比较 runonce/runnext。
9. 失败时 Agent 根据稳定 Diagnostic 生成最小 patch，重新校验和运行。
10. Agent 解释指标、限制和来源，并输出可复现 JSON/Markdown/HTML 报告。
11. 会话中断后，Agent 从显式 session manifest 恢复到合法阶段，不依赖聊天记忆猜测。

### 2.2 P0 不覆盖

- 实盘 broker/store、实盘下单或真实交易账户；
- 网络行情下载、数据库连接、WebSocket、API key 和凭据管理；
- HTTP/远程 Agent 服务、多租户、OAuth；
- 任意 shell、任意模块、任意 pytest target、任意 cwd；
- 自动寻优、自动追求最高收益或收益承诺；
- 未批准第三方代码的动态 import/执行；
- 多 Agent 自主协作、后台 PULSE、定时运行；
- 把子进程控制描述为完整 OS 沙箱或可靠断网。

## 3. 强制独立性与产品边界

```text
[强制] 不安装 backtrader-mcp 和 backtrader-skills 时，全部 P0 能力仍可用
[强制] Agent 不 import、启动、探测或调用 MCP server
[强制] Agent 不读取、import 或执行 .agents/skills/backtrader-* 的实现
[强制] Agent 自带七份公共契约、ComparisonProfile、Catalog、14 份模板、
       Dataset loader、Validator、Runner、Tests 和 Reporter
[强制] Agent 不内嵌模型 SDK、模型 key 或远程推理调用
[强制] Persona/菜单不是安全边界，所有高风险动作由脚本和 action policy 强制
[强制] 不使用 exec/eval，不在宿主进程 import 未校验候选
[强制] 数据、写入和运行只能引用 opaque ID 与 hash-bound manifest
[强制] 写入批准和执行批准互不复用
[强制] P0 只使用受控本地离线数据，不连接实盘或网络 Provider
[强制] Agent 未安装时，Backtrader 核心仍保持原有 Python 支持和行为
```

允许的跨产品关系只有：

1. 公开 Schema 和 golden fixture 兼容；
2. 用户可手工把一个产品生成的合规 artifact 交给另一个产品重新登记和验证；
3. 三产品都存在后的额外 compatibility scoreboard。

这些都不是任一产品的发布前置。

## 5. 交互模型、角色和菜单

### 5.1 单 Agent、多工作模式

首版只建设一个 Agent，内部使用受限模式，不自动创建多个子 Agent：

| 模式 | 责任 |
| --- | --- |
| Coordinator | 路由、阶段、审批、恢复和下一合法动作 |
| Data Engineer | 本地数据检查、映射、质量和 DatasetManifest |
| Librarian | 语料检索、provenance 和模板选择 |
| Specifier | 澄清需求并形成 StrategySpec |
| Author | 生成两种产物 |
| Reviewer | 生命周期、API、路径、安全、数据泄漏和 look-ahead |
| Test Engineer | 固定 runner、双模式、目标测试和 baseline |
| Repairer | 根据结构化诊断做最小修复 |
| Analyst | 指标、限制和报告解释 |

模式只是 persona 的责任切换；确定性动作仍由脚本执行。

### 5.2 菜单

| Code | 菜单 | 路由与结果 |
| --- | --- | --- |
| `DR` | 环境诊断 | doctor action；返回实际环境和阻断项 |
| `DI` | 数据接入 | DataSpec → inspect/optional materialize → register → preview |
| `CS` | 检索语料 | catalog search/inspect，只读 |
| `NW` | 新建策略 | Data → Spec → Search → Author → Validate → Apply → Run → Report |
| `RV` | 审查策略 | 登记 draft/artifact → static/security review |
| `BT` | 回测与测试 | revalidate → execute approval → run/test/compare |
| `FX` | 修复失败 | diagnostics → minimal patch → revalidate |
| `RP` | 查看/解释报告 | RunResult → report/limitations/provenance |
| `ST` | 状态与恢复 | session status、next actions、resume/cancel/archive |
| `HE` | 帮助 | 能力、数据支持、边界和示例 |

当用户已经明确说“加载这份数据并写一个策略回测”，Agent 可直接进入 `NW`，无需先
展示菜单；但仍必须经过数据登记、写入批准和执行批准。

### 5.3 菜单实现约束

- P0 的 `customize.toml` 只保存当前 Builder 要求的 metadata（至少
  `code/name/title/icon/description/agent_type=stateless`），不启用 `_bmad`
  customization resolver；
- persona、边界、菜单和内部路由完整定义在 `SKILL.md`；
- 每个菜单项使用内部 prompt/reference 或枚举 action，禁止指向外部 Backtrader skill；
- `SKILL.md` 完整定义激活、路由、状态、批准和错误处理；
- workflow Markdown 放入 `references/`，不把大量 prompt 文件散放 skill root；
- 所有脚本提供明确 `--help` 和 typed/allowlisted 参数，不提供 `--command`/`--shell`；
- 实施时以当前 Builder scanner/TOML schema 为准，不能盲抄旧 agent example。

## 7. 公共契约与 Agent 专用状态

### 7.1 七份跨产品兼容契约

Agent 必须独立携带并实现：

1. `StrategySpec v1`
2. `DatasetManifest v1`
3. `CorpusManifest v1`
4. `StrategyArtifactManifest v1`
5. `ValidationReport v1`，内含稳定 `Diagnostic`
6. `RunManifest v1`
7. `RunResult v1`

以及被七份契约引用的 `ComparisonProfile v1`。Schema 兼容只用于 artifact
互操作；Agent 不从 Skills/MCP 的安装目录加载 Schema。

public import/export 的核心字段、`ds_<64hex>` dataset ID、七类 archetype 枚举和
canonical-json-v1 与迭代17第 6.8 节逐字兼容；session/journal/action/token 等 Agent
专有状态只能放入 AgentSessionManifest 或版本化 `extensions`。仓库级 parity fixture
可比较 vendored schemas/golden artifacts，但 Agent distribution 的独立测试不得读取
sibling 实现。

### 7.2 `StrategySpec v1`

至少包含：

- 名称、slug、category、archetype 和目标 profile；
- 已登记 `dataset_id`，feed 名称/角色/周期/custom lines 需求；
- 指标/特征、类型化参数、默认值和约束；
- entry/add/reduce/exit/stop/take-profit/risk；
- order、Sizer、commission、cash；
- Analyzer、期望输出和 runonce/runnext；
- 允许依赖/import；
- 非目标和未决项。

数据、方向、仓位和退出规则未澄清时，Agent 不得把 spec 标为可生成。

### 7.3 `DatasetManifest v1`

严格区分用户 `DataSpec` 与实际解析后的事实：

`DataSpec` 是
`dataset-manifest-v1.schema.json#/$defs/DataSpec` 中的 typed request，不是第八份
公共 Schema。它继承 DatasetManifest v1 版本，拥有独立 `spec_hash` 和正反 fixture；
Agent 对话只负责澄清该对象，登记脚本负责生成 resolved manifest。

- `dataset_id`、schema/spec/semantic-manifest hash 和 provenance；semantic hash
  排除产品名/版本、创建时间和本机显示路径等非数据语义字段；
- feed ID/name/symbol、execution/signal/benchmark/hedge/cash_proxy 角色；
- local file/materialized DataFrame、opaque root ID、相对路径、format、size、SHA-256；
- allowlisted parser/feed class 和冻结的列/datetime/null/dtype 参数；
- datetime/OHLCV/openinterest/custom lines 映射；
- timeframe、compression、from/to、timezone、session、calendar 和 bar 时间语义；
- 按顺序记录的 sort/date clip/feature/resample/replay transform 与实现 hash；
- row count、首末时间、normalized SHA-256、重复/空值/非有限值/OHLC 检查；
- master feed、`intersection | left | explicit_asof` alignment、resample 和最低重叠；
- validation status、diagnostics 和 policy version。

源文件、映射、时间范围、transform、环境或 Backtrader revision 变化时，旧 validation
和 run approval 失效。

### 7.4 其余公共契约

- `CorpusManifest`：canonical path ID、runner import 主策略、版本/hash、数据、指标、
  订单、风险、依赖、cross-link 和质量状态；
- `StrategyArtifactManifest`：profile、文件角色/相对路径/hash、diff、目标根和批准；
- `ValidationReport`：schema/AST/current-fork/security/import/smoke/parity/test/baseline；
- `RunManifest`：固定 profile、source/data/config/env/engine hash、审批、命令和产物；

### 7.5 `ComparisonProfile v1`

- 整数计数、状态、布尔、枚举、ID、hash：精确；
- 浮点：`math.isclose(rel_tol=1e-7, abs_tol=1e-9)`；

- runonce/runnext 的交易事件按规范化字段比较；
- master/dev 默认同规则，不能临时放宽后宣称通过。

## 8. 状态机与 Action Gateway

### 8.1 状态机

```text
NEW
  -> DATA_READY
  -> SPEC_DRAFT
  -> SPEC_APPROVED
  -> SOURCES_SELECTED
  -> DRAFT_READY
  -> VALIDATED
  -> APPLY_PREPARED
  -> APPLIED
  -> RUN_APPROVED
  -> RUNNING
  -> PASSED | FAILED

FAILED -> REPAIRING -> DRAFT_READY
PASSED -> REPORTED -> COMPLETED
nonterminal state -> CANCELLED
RUNNING interrupted -> PAUSED
PAUSED -> NEEDS_REVALIDATION
COMPLETED | CANCELLED -> ARCHIVED
active nonterminal state | PAUSED + hash/revision/environment change
  -> NEEDS_REVALIDATION(resume_state, invalidated_evidence)
NEEDS_REVALIDATION -> DATA_READY | DRAFT_READY | APPLIED
```

允许只读子流程，例如未生成策略时直接 `CS` 检索；但 write/execute 状态不得跳跃。
生命周期阶段与证据有效性分开记录：manifest 始终保留 `draft_revision`、
`applied_revision` 和 `resume_state`，并分别记录 spec、validation、change approval、
run approval 的 validity。数据变化可失效 spec 及其下游，候选变化失效 validation
及其下游，目标 preimage 变化失效 change approval，engine/environment 变化至少失效
validation/run approval；不得因为失效而丢失已应用版本事实。完成重新验证后回到
`resume_state` 的合法阶段。`session-resume` 不复用旧 run approval。

`COMPLETED/CANCELLED` 是 closed state，只允许幂等 archive；`ARCHIVED` 是 absorbing
terminal。三者均不可 resume/revalidate，继续工作必须新建带 `parent_session_id` 的
session。它们之后发生 hash/revision/environment 变化不改变原 session。

`RV/BT/RP` 使用显式 session type（`review_existing/run_existing/report_existing`）
和登记动作进入状态机：`artifact-register` 生成受控 draft/applied artifact 事实，
`run-result-register` 只登记并验证不可变 RunResult；不允许靠菜单路由私自跳状态。

### 8.2 不变量

- action 只接受枚举类型和 Schema-valid 参数；
- `idempotency_key = sha256(session_id + action_type + state_revision +
  normalized_input_hashes + approval/token_id)`；相同 key 的重复 apply/run 不产生第二次
  副作用；
- candidate/config/dataset/environment/engine hash 任一变化使 token 失效；
- apply approval 和 execute approval 不可复用；
- crash 后只从 session manifest/journal 恢复；
- state transition 以 append-only event 记录，失败也留下最小审计；
- 私有 draft 写入不等于授权写入用户目标根；
- cancel 不删除已产生的审计证据；
- 并发 session/run 有固定上限。

事件日志使用版本化 `AgentEvent` 定义，至少包含：session ID、严格递增 sequence、
event/action type、from/to state、normalized input hashes、idempotency key、approval/
token ID、effect/result references、previous event hash、event hash、status 和时间。
执行副作用前先持久化 `ACTION_PREPARED`，完成后写 `ACTION_COMMITTED`；checkpoint 由
已验证的 hash chain 物化，并记录 last sequence/event hash。

写入采用临时文件、flush/fsync 和同文件系统原子 replace；JSONL 尾部不完整、sequence
跳号、hash chain 断裂或 checkpoint 不匹配时，恢复必须安全停止并隔离损坏后缀，不能
猜测状态。若恢复时只有 PREPARED 没有 COMMITTED，先核对目标 effect manifest/hash：
副作用已存在则补记 commit；不存在时仅允许以相同 idempotency key 安全重试。


或任意文件浏览 action。

### 9.1 P0 adapters

`dataset-materialize` 只接受已批准的产品内 tabular artifact/仓库 fixture ID，不接受

hash。将该文件重新加载后必须与物化前的规范化 DataFrame 语义等价。

### 9.2 数据门禁

- 路径必须属于登记 root，`realpath` 后仍在 allowlist 内；
- 只接受相对路径，拒绝 `..`、absolute、symlink escape、设备文件；
- 读取前后核对 stat 与 SHA-256，防止 TOCTOU；
- mtime/size 只用于缓存，不作为 provenance；
- 限制文件大小、总大小、行数、feed/列/transform 数；
- timestamp 可解析、单调，重复策略显式；
- timezone、session、bar open/close、bar shift 明确；
- OHLC 与 finite 校验，volume/openinterest 补值策略明确；
- 多数据默认严格 intersection，不静默 forward-fill；
- resample/replay 只能传播已完成高周期 bar；
- custom feature 记录 transform 顺序、实现 hash、依赖版本；
- ML 固定 seed、模型 artifact hash 和训练/评估窗口，检查目标泄漏；
- manifest/日志不写完整 DataFrame、凭据或 token。

### 9.3 七种策略 Archetype 的数据场景矩阵

| Archetype | 数据重点 |
| --- | --- |
| 单数据指标 | 显式 OHLCV、日期窗口、bars、首末时间和 normalized hash |
| 多指标 | 单调 DataFrame、列顺序、warm-up 覆盖最大 minperiod |
| 多资产 | feed name/role、共同日期、严格对齐、禁止静默补齐 |
| 多周期 | 源/目标周期、aggregation/label/closed、已完成 bar、双时钟 |
| 配对/价差 | 两腿周期、交集、顺序、hedge 角色和各自 hash |
| 订单/风险 | OHLC、session、bar 时间语义和 gap 对成交的影响 |
| 预计算/ML | custom lines、dtype、warm-up、transform/model hash、无泄漏 |

## 11. 生成、写入、校验与执行

### 11.1 草稿和写入

P0 冻结以下 root registry；所有 action 只接受 opaque root ID 和相对路径：


9. draft/目标/数据/环境变化使批准失效；执行另需独立 run approval。

- reports 可解释指标、限制、来源和未覆盖能力；
- snapshot/source-attached 都符合各自声明。

### 14.2 负向

- 菜单、prompt、脚本或 import 尝试指向/访问 MCP 或 Backtrader Skills；
- Agent 未激活时误触发不相关 Python/投资问题；
- raw source/command/shell/任意 pytest target 交给 run；
- 未登记或已改变数据、空交集、非法 OHLC、未来聚合 bar；
- `../`、绝对路径、编码绕过、symlink escape；
- dynamic import、subprocess、socket、network/live/secret；
- apply/run 共用审批、token 过期或 hash/revision 改变；
- session 状态损坏、非法跳转、重复 action、并发超限；
- 错误输出包含 absolute path、环境变量、secret 或完整 traceback。

以上必须安全失败并返回稳定、脱敏、可修复的 Diagnostic。

## 17. 风险与控制

| 风险 | 控制 |
| --- | --- |
| Agent 退化为 persona/prompt | 自带 Action Gateway、脚本、状态、runner 和 Agent-only 端到端门禁 |
| 菜单暗中调用 Skills/MCP | 内部 route allowlist + 无 sibling 产品环境 + file/import/process audit |
| 把宿主 adapter 当唯一源码 | canonical tracked `backtrader-agent` + distribution 安装验收 |
| 产品资源静默漏包 | resources check-ignore/ls-files + manifest hash |
| 隐藏记忆导致状态漂移 | stateless Agent + 显式 session manifest/journal |
| 崩溃或重复请求造成双写/双跑 | 状态机、幂等 key、append-only events 和 hash token |
| Host adapter 锁定 | 内部 Agent manifest + 首版明确 adapter；更多 adapter 放 P1 |
| 三产品重复实现发生漂移 | 同一公开 contract fixtures/parity scoreboard，不共享必需 runtime |
| 旧语料生命周期不兼容 | 14 份当前 fork 模板 + 分对象初始化/clock 校验 |
| 数据路径泄漏或漂移 | opaque root、relative path、source/normalized hash、TOCTOU 检查 |
| 多数据/多周期未来信息 | 明确 alignment/resample/bar 语义和双模式验收 |
| AI 编造 expected metrics | fresh master baseline + 人工批准 + dev 验证 |
| Persona 被误当安全边界 | 高风险动作只能通过 typed deterministic scripts |
| 子进程仍能访问主机 | P0 披露边界；强隔离 container 进入 P1 |
| “禁网”承诺不可验证 | 无网络 action + 已知 API 拒绝；OS 级断网只有验证后声明 |
| 多角色使流程复杂 | 单 Agent、多模式；不自动创建自主子 Agent |
