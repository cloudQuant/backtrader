## 1. 结论与目标

**值得有选择地尝试，但不能预先承诺整个 Backtrader 内存显著下降。** 优先评估大量创建、字段稳定、没有复杂继承的 `OrderExecutionBit`、`OrderData` 和 `OrderParams`。事件队列包装 `channel.Event` 也值得优先测量；`Position`、`Trade`、参数辅助对象和封闭的行情证据记录作为有条件的后续候选。通用行情事件、Strategy、Indicator、Feed 及 Line 基类不在本轮改造范围。

`__slots__` 减少属性存储开销，不压缩字段引用的 float、字符串、deque、DataFrame 或 Line 数组，也不减少历史对象数量。它不会自动切断 Order → Feed / owner → Strategy → Cerebro 的强引用。大行情缓存场景的收益可能很小；成交片段、通知和订单状态对象占比高的场景更有机会受益。

两类内存工作应分别推进：

- 本迭代：减少每个仍需存活的对象的属性布局开销，保持对象数量与业务结果一致。
- [迭代52](../迭代52-动态Data生命周期管理/迭代计划.md)：通过动态 Data 生命周期、消费完成后的历史归档及引用清理，控制对象存量和缓存。该计划仍未实现，不能作为本迭代的既有能力。

近似估算为 `节省量 = Σ(各类同时存活实例数 × 每实例实际节省字节)`，共享对象只能按身份计一次。这里使用同时存活数而非累计创建数；不能把通知共享的参数、created 和成交 deque 重复计费。整个进程的收益必须再用独立 RSS 测量验证。

完成定义：得到逐类采用/拒绝结论，至少一个候选通过兼容与实测收益门禁；输出明确的适用场景。若只有局部收益，则只能报告“对象布局优化通过”，不能报告“Backtrader 整体显著降内存”。如果没有候选满足门禁，保留测量结论并停止生产改造也是有效的调研结论，不虚构优化成果。

### 2.1 首批字段清单

清单是实施核对起点，必须与所有外部写入、延迟分支和序列化状态复核，不能只从 `__init__` 自动生成后直接合入。

- `OrderExecutionBit`：`dt, size, price, closed, opened, closedvalue, openedvalue, closedcomm, openedcomm, value, comm, pnl, psize, pprice`。
- `OrderData`：`pclose, exbits, p1, p2, dt, size, remsize, price, pricelimit, trailamount, trailpercent, _plimit, value, comm, margin, pnl, psize, pprice`。保留 `plimit` 的 property getter/setter。
- `OrderParams`：`owner, data, size, price, pricelimit, exectype, valid, tradeid, oco, trailamount, trailpercent, parent, transmit, simulated, histnotify`。
- `Position`：`datetime, size, price, price_orig, adjbase, upopened, upclosed, updt`。

`__weakref__` 和是否保留 `__dict__` 属于布局合同，另外列出，不计入业务字段数。slots 槽名不得与 property、类默认值或父类槽冲突；未初始化字段仍需保持原有 AttributeError/hasattr 语义。

已知阻断点：`btapibroker.py:9814` 用 `position.__dict__.update(preview.__dict__)` 原地同步；`strategy.py:2238` 起写入Trade的 `service_execution_recovery_*` 字段；`parameters.py:1089` 的Accessor state读取实例字典；`btapifeed.py:1579` 为队列Event附加 `_source_feed`。这些都是本轮源码发现，不是对第三方使用方式的穷尽证明。

## 3. 隔离布局诊断与证据边界

本次诊断见 [evidence/README.md](evidence/README.md)，脚本和原始 JSON 随计划保存。脚本从公开源码重建隔离类，保留方法，仅改变布局，不替换正在运行的 Backtrader 类。

测量方案：Anaconda base 中的实际解释器；每类每布局新进程；先构造并释放128个预热对象；每轮保留100,000个默认构造对象；三轮交替顺序。比较原布局、固定槽加弱引用的 strict 原型，以及保留 `__dict__` 的 hybrid 原型。测量前不读取实例字典，避免字典物化改变结果。

实际环境为 **CPython 3.11.8 / macOS arm64**。每类分别对strict/hybrid各做三轮配对，合计36个子进程。以下为配对组的tracemalloc存活分配中位数差；百分比的分母包含对象列表和默认构造时实际分配的负载，不是单个对象壳：

| 类 | strict节省/实例 | strict分配下降 | hybrid节省/实例 | hybrid分配下降 |
|---|---:|---:|---:|---:|
| OrderExecutionBit | 48 bytes | 18.75% | 16 bytes | 6.25% |
| OrderData | 48 bytes | 4.80% | 16 bytes | 1.60% |
| Position | 40 bytes | 26.31% | 8 bytes | 5.26% |

这说明保留扩展能力后节省明显收窄，不能统一套用“省30%–50%”之类经验值。按本样本线性估算，100万个同时存活的bit严格槽约少45.8 MiB、hybrid约少15.3 MiB的Python分配；这是同布局同负载的算术外推，不是百万bit或进程RSS实测。`OrderParams`、参数类和事件包装本次未做布局实验。

**诊断中OrderData的RSS增量中位数反而升高**：baseline/strict约95.5/121.5 MiB，另一配对组baseline/hybrid约94.0/99.4 MiB。不能只挑tracemalloc下降来证明进程收益；R0必须查清无tracing场景下的分配器行为。原因尚未定位，当前不能把它归为正常噪声或生产回退结论。

报告同时给出 tracemalloc 存活分配、峰值、进程 RSS 前后值及构造耗时。构造耗时在 tracing 下，仅诊断使用；RSS 也包含 tracer 的开销，不能作为生产内存验收。对象壳加实例字典的 shallow size 在采样后读取，单列展示，不能当对象图大小。

这些样本未运行真实 Cerebro、撮合、复制、恢复或多进程优化；默认构造也没有真实历史负载。只证明候选布局有节省潜力。正式实现还需运行第6节的实际场景与第7节全部适用验收项。

## 4. 兼容性与实施约束

### 4.1 三种布局不能混为一谈

| 布局 | 自定义属性 | 反射/状态差异 | 本轮用途 |
|---|---|---|---|
| 原有普通类 | 支持 | 当前语义 | 冻结基线 |
| strict：固定槽 + `__weakref__` | 直接实例拒绝未知字段；未声明 slots 的用户子类通常仍有字典 | 没有实例字典，`vars()` 不再适用 | 估计布局收益；仅可用于确认封闭的内部记录，不能直接默认替换现有公共类 |
| hybrid：固定槽 + `__dict__` + `__weakref__` | 保留动态赋值 | `__dict__` 仅反映扩展属性，固定槽字段不在其中 | **现有公共记录的优先兼容候选**，仍需迁移仓库内部直接字典读写，并明确反射边界 |

保留字典不意味着完全兼容；特别是 `obj.__dict__.update(...)` 不会更新同名 slot 的值。不能用“能 setattr”或单元测试通过推导第三方反射兼容。R0 必须记录逐类扩展与序列化合同；若调用者必须保留原始字典作为完整状态的语义而没有可接受迁移，则该类保持原样。不得用丢弃字段、兜底吞异常或隐藏新类替换来制造兼容。

公共对象的严格封闭是单独的 API 决策，不作为本轮默认方案；不额外引入全局 `use_slots` 开关、第二套订单模型或新调度器。不能在类创建后赋值 `Class.__slots__` 并声称实例布局已改变。

### 4.2 复制、持有关系与序列化

1. 保持现有 copy/clone 行为：Order 通知共享 `p/created`，executed 为独立浅拷贝，成交 deque 仍按既有规则共享；`p1/p2` 的消费区间不能重发或丢失。
2. deepcopy 必须保留原有值、别名和循环关系语义；不能为 slots 额外深拷贝 Feed、行情或成交历史。
3. 全部被改造的原可弱引用类继续支持 weakref；子类不重复声明已有 `__weakref__`。测试释放后的回收，诊断列表自身不能无限持有弱引用或原对象。
4. 如调整 state 协议，显式保存槽字段和扩展字段，定义 state 版本；覆盖基线旧字典 state → 新类恢复、当前 copy/pickle 往返和跨进程 spawn。须保留协议0等既有低协议能力，不能只测协议4/5；参数系统已有协议0/最高协议测试。新版本产生的状态是否能被旧版本读取要单独声明，不能默认为双向兼容；禁止实例字典中的同名键遮蔽真实槽状态。
5. 保持现有类模块路径、可导入性、参数名、公开字段、可变性、相等/哈希及 repr 行为。slots 本身不应带来 frozen 或 dataclass 自动 eq 等语义变化。
6. 不修改成交数量/价格/费用的数值类型与精度，不删除 exbits、TradeHistory、通知或分析器结果，不变更 `exactbars/preload/runonce` 的默认配置。

### 4.3 Python 与继承合同

基础包仍支持当前声明的 Python 3.8–3.13，不为 slots 抬高最低版本。普通记录类优先手写 slots；`dataclass(slots=True)` 从3.10才支持，`weakref_slot` 从3.11才支持，不能无条件用于基础包。

队列包装/校验结果/行情证据dataclass若纳入实施，须单独冻结版本方案。可以保持3.8/3.9原有布局、仅在支持的版本采用优化，但必须逐版本报告实际是否具有字典和节省量，不能把3.11测量外推为全版本。验证dataclass排序/eq/hash、asdict、默认工厂、继承、显式/无参super和用户子类；增加 `_source_feed` 存储不能悄悄将其加入比较或自动序列化为整条Feed图。不得为了消除祖先字典改动不在范围内的框架基类。

## 6. 测量方法与收益门禁

### 6.1 正式场景

### 6.2 可复现测量

- 正式基线与候选必须绑定代码提交、相关文件哈希、输入哈希、实际 import 路径、Python/OS/架构、依赖和配置。基线不包含 unrelated dirty 源码；保留已有工作区修改，必要时从固定提交导出只读测量源码，不移动当前 dev。
- 每个 profile 独立新进程，串行运行；至少5对基线/候选，交替先后顺序。每轮保留原始值，报告中位数、范围与配对差异；禁止在并发 pytest、coverage、tracemalloc 下进行正式时间/RSS门禁。
- 两条测量通道：不带 tracing 的进程树 peak RSS/持有阶段 RSS/墙钟时间；另跑带 tracing 的 Python 存活分配与对象归因。50ms RSS采样需配合阶段边界/进程高水位记录，不能漏掉短暂构造峰值；记录具体平台采集方式与单位。
- 计数、字段审计、`vars()`/`__dict__` 访问在独立诊断进程完成；不要因统计而让基线字典物化。构造耗时和属性读写微基准只作为辅助，最终看实际回测耗时。
- 区分峰值、稳态存活和释放后 RSS。分配器缓存可能使 RSS 不立即下降；回收证明须结合弱引用、对象存量与 traced current，不以“RSS 没降”单独判断泄漏。
- 内存不足或平台缺失时记录 `INCOMPLETE/NOT_RUN`，保留失败与退出码；不缩小样本后继续沿用原规模标签，不把超时/OOM作为通过。先预估内存预算，在资源允许的机器上运行固定规模。

### 6.3 预设接受标准

1. **正确性是硬门禁**：订单事件、成交、资金/持仓、Trade/历史、Analyzer 与报告输出保持基线语义；无新缺字段、pickle/weakref 或子类故障。数值运算未变的路径要求逐值一致，不新增宽容误差预算。
2. **单类采用门禁**：R0依据实际布局冻结每类的字节目标及成本收益决定。当前首批hybrid的诊断参考目标是bit/OrderData至少16 bytes/实例，Position仅8 bytes且优先级更低；未经测量的类不能照搬这些数值。正式S0至少4/5配对同方向改善，并且适用实际场景的无tracing RSS应有可复现改善。按对象集合及各自拥有的负载计量、共享部分只计一次；扩展/已物化字典组不得出现不可解释膨胀。为节省少数字节却需要广泛API迁移时保持原实现；不以局部字节目标替代下一条的显著收益门槛。
3. **“显著降低”口径**：至少一个预先冻结的实际 Cerebro 目标场景 S1/S2，在不带 tracing 的5对测量中 peak RSS 中位数下降 **≥10% 且 ≥32 MiB**，并且至少4对同方向改善；必须点名场景、规模与配置。S0达到该比例不等于整个 Backtrader 达标。
4. **回退限制**：实际S1/S2/S3及本轮适用的S4/S5，耗时中位数回退≤5%，peak RSS回退≤3%且≤16 MiB；超出则调查并修复/撤回相关类，不能把 tracing 或并发噪声结果当正式判定。
5. **报告分级**：功能/局部布局门禁通过但端到端门槛不达标，标记“局部优化 PASS / 显著收益 GAP”；任一正确性失败为 NO-GO。正式目标是待验证的接受条件，不是本次测量已经达到的结果。

## 8. 风险、回退与交付

最主要风险不是漏写一个slots声明，而是漏掉延迟属性、让直接字典更新悄悄失效、改变copy/pickle和用户子类行为。每个类别保留独立提交和基线结果；不合格时回退该类并保留其他已经验收的改动，不用全局异常处理掩盖失败。

内存分析不得递归读取或序列化整个 live Broker/账户对象图；只使用公开源码、合成数据和明确字段计数。报告不包含 `.env`、真实config、凭据或私有行情捕获。

最终交付：逐类决定表、必要的局部源码改动、兼容/状态迁移说明、复现脚本和输入、原始配对数据、验收矩阵及每轮提交。源码PASS、安装PASS、跨版本PASS、账户/实盘、发布/部署分别报告。本次不进行账户连接、推送或发布。
