## 0. 一句话结论

**计划的事实边界、失败语义和所有权意识很强，但当前更像“设计原则汇编”，还不是一份可排期、可验收、可交付的迭代计划。** 建议先关闭 4 个 P0 问题和 4 个高优先级设计决策，再进入 60.01 实施；否则后续每一步都会在“合同未冻结、范围未收敛”的状态下反复返工。

结论评级：**有条件通过（Conditional Pass）**。

## 1. 总体评价

### 1.1 做得好的地方

1. **证据分级意识突出**：反复区分静态源码、隔离模拟、安装包、真实来源和真实账户，明确“路径存在不等于能力验收”。这在同类重构计划中很少见。
2. **UNKNOWN / 不可用 / 不可比较语义完整**：没有把未知默认为零，没有把 ACK 当成交，没有把快照差额伪造成交，方向正确。
3. **所有权边界清楚**：Base 管合同、provider 管原生解析、SDK 管绑定与账本、BT 管投影、Gateway 只管路由与授权视图，避免了“第二套账本”。
4. **恢复与接管要求严谨**：QUIESCE → FENCE → RESTORE → SYNC → RECONCILE → READY 状态机，以及“仅存储 fence 不足以接管”的判断，是正确的安全底线。
5. **链接质量好**：42 份文档内部相对链接全部可解析，未发现断链。
6. **验收矩阵可观察**：A/B 2/3 → 账户 5、重复 fill、先成交后订单、超时/UNKNOWN、缺口与水位等场景，具备可执行雏形。

### 1.2 主要差距（优先级总览）

| 级别 | 问题 | 后果 |
| --- | --- | --- |
| P0 | 计划目录未纳入 Git | 无评审基线、无法跨仓引用、存在丢失风险 |
| P0 | 60.01 明确不读旧 Gateway/transport 源码，却要在 60.09 重构它 | 无法做迁移、兼容、回滚和工时评估 |
| P0 | 范围横跨 10 个顺序子迭代，无 MVP、里程碑和迭代完成定义 | 无法排期，容易长期悬空 |
| P0 | Base 3.8 / SDK 3.11 / codec 3.10 / numpy 1.26 冲突未决策 | 发行可能直接阻塞 |
| P1 | 缺集中决策、假设、风险登记 | “待决”散落在 42 份文档，无法追踪 |
| P1 | 需求/验收 ID 不统一，无追溯矩阵 | 无法证明每条需求都被验证 |
| P1 | 容器与 wire 合同是散文，不是规范字段字典/Schema | 实现时仍有大量二次设计 |

| P1 | 安全模型、测试策略、可观测性、跨仓矩阵缺失 | 上线与运维准备不足 |

## 2. P0：开工前必须修正

### P0-1 计划目录尚未纳入版本控制

**现象**：`git status` 显示整个迭代 60 目录为未跟踪（`??`），`git ls-files` 计数为 **0**。

**影响**：
- 没有 commit 基线，用户审阅的到底是哪个版本无法追溯。
- 跨仓（Base/SDK/provider/Gateway/transport）评审无法用 commit 引用同一份合同。
- 与 AGENTS.md 的“记录范围/结果/仓库/分支/commit”要求不一致。
- 目录一旦被清理或切换分支，计划可能丢失。

**建议**：
1. 在 `dev` 上单独提交计划文档，提交信息记录“计划评审稿、未实施、验证 NOT_RUN”。
2. 在目录内增加 `README.md`，列出文档地图、状态、当前决策和审阅记录。
3. 在 `AGENTS.md` 或内部计划索引中增加一行入口链接。
4. 后续每次修订计划都单独提交，保留可追溯的评审历史。

### P0-2 60.01 排除旧 Gateway/transport 源码，与 60.09 重构目标冲突

**证据**：
- 主计划第 343 行：“本次未读取这两个仓库现有源码，不据此推断具体文件迁移或能力状态。”
- 60.01 需求规划：不读取旧 Gateway 实现。
- Gateway 调研设计第 3 行：“本次按用户要求不研究现有 Gateway/transport 源码，不把旧实现作为设计依据。”

**问题**：不把旧实现当作**设计依据**是合理的；但 60.01 的职责是“基线盘点与合同决策”，60.09 又要替换这些组件。完全不读旧代码会导致：
- 无法列出公开入口、配置键、消息格式、调用者、部署方式和测试。
- 无法制定迁移表、兼容期、回滚方案和废弃顺序。
- 无法评估工作量与风险，60.09-A 的“保留待核实公开接口和数据迁移清单”被推迟到设计冻结之后。

**建议**（二选一，并写入 60.01）：
- **方案 A（推荐）**：允许只读、黑盒式的“迁移盘点”，不把旧代码当设计依据，但必须记录：包结构、公开 API、配置、wire 格式、消费者、测试、部署假设、依赖图、已知缺陷。产出“保留/替换/退役”决策表。
- **方案 B**：如果用户明确禁止读取，则在 60.01 把它登记为**显式假设/阻塞项**，并规定 60.09-A 开工前必须补一次只读盘点，否则 60.09 不得冻结设计。

### P0-3 范围过大，缺少 MVP、里程碑和“迭代完成”定义

**现象**：10 个顺序子迭代覆盖统一容器、3 个场所、Tick/Bar、订单/成交/账户、多策略归属账本、策略账户 API、MessagePack、Gateway/ZMQ、多进程恢复、可选 Risk/Execution/Monitor。没有工时、日期、关键路径、并行机会和整体完成标准。

**影响**：
- 60.01–60.10 每步都要用户审阅，实际周期可能以月计；中途任何一步阻塞都会拖住后续全部步骤。
- 没有 MVP，无法尽早验证“低转换数据链路”是否真的带来收益。
- 没有“不做什么”的边界，可选组件和未来能力持续膨胀。

**建议**：
1. 明确 **MVP = 60.01–60.05**：Base 容器 + CTP Tick 纵切 + 三场所 Bar + direct 订单/成交/账户，单策略优先；60.06–60.10 作为后续阶段（例如 60B/61）。
2. 增加“里程碑表”：每步结束时**可演示什么、可测量什么、哪些能力仍不可用**。
3. 增加“非目标（Non-goals）”清单：本迭代不实现多进程安全交易、不实现 Risk/Execution/Monitor 业务、不做策略调度器、不做完整 Gateway 集群等。
4. 给出整体 **Definition of Done**：哪些合同冻结、哪些测试通过、哪些证据等级达到、哪些能力仍标 UNKNOWN。
5. 标注可并行分支：例如 60.04 与 60.05 在 60.02 后可以部分并行；60.08 的 schema 设计可在 60.02 后启动，最终冻结再等 60.07。

### P0-4 Python/依赖版本冲突未形成决策

**证据**：主计划第 314 行已识别：BT/Base 声明 `>=3.8`，SDK 声明 `>=3.11`，`msgspec` 要求 `>=3.10`，Base 现有 `numpy>=1.26` 与 3.8 依赖求解冲突。

**问题**：计划只说“记录矩阵、未解决列为阻塞”，但没有决策期限、候选方案和 owner。这是发行级阻塞，不应留到 60.08 才发现。

**建议**：
1. 在 60.01 增加 P0 决策：Base 是否放弃 Python 3.8？若保留，codec 是否改用支持 3.8 的 `msgpack-python`？numpy 下限如何调整？
2. 列出候选矩阵：Python 版本 × Base/SDK/provider/Gateway/codec × wheel/平台。
3. 在 CI 中增加相应的构建/导入矩阵，并把未通过项标为阻塞。
4. 明确“声明支持”与“实际验证支持”的区别，避免 README/元数据继续夸大。

## 3. P1：重要改进

### P1-1 缺集中决策、假设与风险登记

**现象**：42 份文档里散落着“待决”“需在步骤 01 确定”“未决项”，但没有一张统一表；风险只以散文出现，没有概率/影响/缓解/owner。

**建议**：新增 3 份短文档，并在每步更新：
- `决策登记.md`：`D-01 | 决策 | 候选 | 决定 | owner | 截止步骤 | 关闭条件 | 证据`。
- `假设登记.md`：`A-01 | 假设 | 若不成立的影响 | 验证方式 | 截止步骤`。
- `风险登记.md`：`R-01 | 风险 | 概率 | 影响 | 缓解 | owner | 触发条件`。

至少应包含：Python 版本、数值表示、API 兼容、单写者/fencing、旧 Gateway 迁移、provider 能力、存储引擎、安全机制、性能阈值。

### P1-2 需求/验收 ID 不统一，无追溯矩阵

**现象**：ID 格式混杂：`01-A`、`02-A`、`03-A`、`04-R1`、`05-R1`、`06-R1`、`07-R1`、`M08-1`、`G09-1`、`R10-1`、`A08-01`、`A09-01`、`A10-01`。

**建议**：
1. 统一为 `60.SS-Rn`（需求）与 `60.SS-An`（验收），例如 `60.04-R1`、`60.04-A1`。
2. 增加追溯矩阵：`需求 ID | 设计章节 | 验收用例 | 证据路径 | 状态`。
3. 每条验收用例必须能链接到实际命令、夹具、样本或证据文件；没有证据的用例保持 `NOT_RUN`。
4. 把“计划检查”“可执行案例”“验收矩阵”三种叫法统一。

### P1-3 容器与 wire 合同缺少规范字段字典和 Schema 单一真源

**现象**：主计划 §8 和 60.02/60.08 用大量散文描述字段语义，但没有一张可实现的字段表；`schema_id`、`kind`、版本、扩展命名空间、缺失值编码都还是示意。

**建议**：
1. 增加 `contract/` 附录，包含机器可读 schema（JSON Schema、IDL 或 Python dataclass 定义三者择一为真源），文档从它生成或链接，避免文档、codec、容器类三处漂移。
2. 字段字典至少包含：`name | type | unit | nullable | missing encoding | scope | source | version | notes`。
3. 明确统一缺失值模型：缺席、显式 null、已知零、未知、不可用，各自如何编码。
4. 明确数值表示：十进制字符串的规范形式（尾零、指数、NaN/Inf、负数零）、精度元数据、与 BT float 的转换边界和舍入规则。
5. 明确 Bar 时间戳约定：开始时间还是结束时间、交易所时区还是 UTC、形成中/已完成如何区分。
6. 明确订单/成交去重键：账户、route、交易日、订单 ID、成交 ID、会话代际的复合规则。
7. 提供最小 golden samples（每种 kind 至少 1 条正常 + 1 条缺失 + 1 条畸形）。

### P1-4 性能目标未量化

**现象**：迭代名称强调“低转换数据链路”，但全文没有 baseline 数值、目标数值或 go/no-go 阈值；只写“预先登记阈值”。

**建议**：
1. 在 60.01 固定一个可复现基准：CTP Tick 路径、三场所 Bar 路径、direct 订单路径；记录机器、Python、依赖、样本 hash、预热、轮次。
2. 给出**临时目标**（即使后续调整）：例如每 tick 的对象构造/深拷贝次数下降 X%、p99 处理延迟、吞吐、RSS、队列深度。
3. 为每步定义“本步应改善哪个指标、允许恶化多少”；没有测量的步骤不得声称性能收益。
4. 把“减少 deepcopy”作为假设而非结论；先用分配计数和端到端基准证明，再决定移除。
5. 明确性能验收的 NO-GO 条件：如果目标未达成，是否回退到旧路径、是否缩小范围。

### P1-5 多策略账本与 BT API 兼容方案未定

**现象**：§7.5–7.6 对“一个账户 10 个策略”描述很细，但把关键决策全部推到 60.01：`getposition()`、`close()`、目标仓位、`getcash()`、`getvalue()`、Sizer/Analyzer/Observer 的作用域和兼容方式都没有候选方案。

**建议**：
1. 在 60.01 之前给出至少 3 个候选：
   - **A**：保留账户级 API 语义不变，新增显式 `strategy_view` / 绑定代理，策略通过新入口访问策略范围。
   - **B**：在 `Strategy` 上下文注入策略身份，让现有 API 自动切换作用域（兼容风险最高）。
   - **C**：每个策略独立 Broker/账本视图（与现有共享 Broker 现实冲突，需说明代价）。
2. 明确默认行为：单策略、回测、外部调用、无策略上下文时分别返回什么；不得静默退回账户总额。
3. 明确破坏性变更清单、版本号、废弃期和迁移指南。
4. 区分“因子归属账本”和“策略归属账本”：是否同一存储、同一 schema、同一 owner？如果复用，给出迁移/兼容方案；如果不复用，说明为何不是“第二套权威账本”。
5. 给出完整的 A/B 2/3 → 5 状态转移示例，包含订单、预留、成交、费用、对账和 BT 通知的字段级变化。

### P1-6 单写者/fencing 的场所可行性未评估

**现象**：计划要求“证明旧 owner/provider 会话失效，或每次实际派发都经过可验证 fence”，否则拒绝接管。这是正确的安全底线，但没有评估 CTP/OKX/Binance 是否支持会话撤销、客户端订单 ID、按客户端 ID 查询、幂等键或派发栅栏。

**建议**：
1. 增加 `provider 能力矩阵`：会话撤销、按 client order ID 查询、幂等、订单标签、重连恢复、账户快照原子性、成交去重 ID。
2. 对每个场所标注：支持 / 部分支持 / 不支持 / 未验证。
3. 定义降级策略：不支持 fencing 的场所，是否限制为单进程、只读、人工接管，或需要外部网关/终端证明。
4. 明确“fence”的实现位置：存储 token 在派发前检查，还是独立授权服务，还是 provider 原生机制。
5. 在 60.10 增加“故意保留旧会话”的故障注入用例（已有 A10-10，但需要可执行工具）。

### P1-7 安全模型与 ZMQ 隔离机制不具体

**现象**：计划正确指出“topic 不是权限”，但“确保无权客户端不能接收或解密”没有具体机制；没有威胁模型、密钥管理、审计日志和供应链要求。

**建议**：
1. 增加简短威胁模型：网络窃听、恶意客户端、越权订阅、重放、凭据泄露、内部人员、供应链 codec。
2. 明确默认安全部署：CURVE / mTLS / 每 scope 独立 socket / XPUB 认证代理，至少选一种并说明适用条件。
3. 明确密钥来源、轮换、存储和日志脱敏规则。
4. 明确审计事件：认证、授权、订阅、命令、拒绝、撤权、重放。
5. 对 codec 增加供应链验证：版本固定、hash、许可证、已知 CVE 检查。

### P1-8 测试策略、夹具与工具链缺失

**现象**：验收矩阵是场景化散文，没有测试金字塔、夹具目录、golden 文件、属性测试、模糊测试、恢复状态机测试、多进程故障注入和跨仓 contract test。

**建议**：
1. 按层定义测试：
   - **合同测试**：Base 容器与编解码，跨 provider 共享。
   - **单元测试**：字段映射、缺失值、精度、去重键。
   - **属性测试**：round-trip、精度保持、边界值。
   - **模糊测试**：解码器、畸形/超限消息。
   - **状态机测试**：订单/成交/恢复/预留的确定性模拟。
   - **集成测试**：direct/Gateway 对等、多进程、断线、慢消费者。
   - **chaos 测试**：崩溃点、ACK 前后、日志过期、epoch 变化。
   - **provider 一致性测试**：每场所能力矩阵。
   - **性能基准**：固定样本、机器、阈值。
2. 建立 `tests/fixtures/iter60/` 或等价目录，存放 golden 消息、样本数据、期望输出和 hash。
3. 把验收矩阵转成 pytest 用例或可执行脚本，而不是只写在 Markdown 里。
4. 增加跨仓 contract test：Base/SDK/provider/Gateway 各自 CI 跑同一组合同。

### P1-9 可观测性与运维要求缺失

**现象**：Monitor 是可选组件，但计划没有定义核心指标、日志字段、健康状态、告警阈值和 runbook。

**建议**：
1. 必须指标：队列深度、丢弃/缺口、epoch/序号、重连次数、UNKNOWN 数量、对账差异、预留占用、账本水位、延迟分位数。
2. 必须日志：订单/成交关联、拒绝原因、UNKNOWN、权限拒绝、恢复状态转换；不得泄露凭据或越权账户数据。
3. 健康语义：`HEALTHY / DEGRADED / INCOMPLETE / UNAVAILABLE`，并说明每种状态下允许哪些操作。
4. Runbook：UNKNOWN 处理、缺口恢复、对账差异、切换接管、日志过期。
5. SLO：行情延迟、命令延迟、恢复时间、对账频率；没有 SLO 就无法验收“可运营”。

### P1-10 跨仓版本、提交与集成矩阵缺失

**现象**：计划跨 BT、Base、SDK、provider、Gateway、transport，但只有“子仓先提交、父仓 gitlink”一句；没有版本兼容矩阵、分支策略、集成测试环境和发布顺序。

**建议**：
1. 增加 `仓库/版本矩阵`：仓库、分支、commit、Python、依赖、发布包名、兼容范围。
2. 明确每个阶段的“最小可集成组合”，以及哪些组合必须一起升级。
3. 增加跨仓 CI：contract tests、wheel 安装、gitlink 一致性检查。
4. 明确 gitlink 更新顺序、回滚方式和发布 tag 规则。
5. 记录“源码可导入”与“发行包可用”两种证据，分别验证。

## 4. P2：文档工程与可读性

### 4.1 模板去重
