## 0. 结论

既有三份报告主要从**计划自身的一致性、治理和环境基线**入手。本报告从**源码侧**补充：计划 §4 对现状的描述在几处**低估了已有实现**，导致 60.01–60.04 容易按“从零设计合同”的假设展开，而真实问题是“如何把已存在的、分散的 provider 专有语义收编进 Base 合同”。最重要的四点：

1. CTP Tick 已有一整套成交量语义与质量字段，Base 合同要决定**收编还是排除**它们（N1）。
2. CTP 行情对象在发布前要经过一条**有状态、有顺序**的变异流水线，计划所说“发布后可变性”缺少明确的冻结点（N2）。
3. Backtrader 已实现净持仓/双向持仓与按腿读取，但相关代码在工作区中处于**未提交的合并状态**，计划把持仓模式写成“待选择”，且没有把这份 dirty 变更登记为 60.01 基线（N3）。
4. `BtApiStore` 对每个 Tick 实际有**两次** `deepcopy`（写入时和读取快照时），而 Feed 里有 67 处 `_tick_value()` 鸭子类型访问；“低转换”的成本模型需要同时覆盖这两类（N4）。

## 1. 已核对的发现

### N1 计划 §4.2 对 CTP 成交量语义的描述过时：CTP Tick 已有显式的累计/增量机制，Base 合同必须决定如何收编

**计划原文（§4 第 2 条）**：CTP 的 `get_last_volume()` 在没有增量时可返回累计量；不能将累计量、24 小时量和逐笔增量视为同一字段。

**源码事实（已核对）**：`bt_api_ctp/containers/ctp/ctp_ticker.py` 中：

- `get_last_volume()` 在 `volume_semantics == "delta"` 且 `delta_volume` 非空时返回增量，否则返回 `volume_val`（累计量）。
- 同时存在 `get_cumulative_volume()`、`get_delta_volume()`、`apply_volume_delta(delta, complete=, quality=)`，以及 `volume_complete`、`volume_quality`、`continuity_status`、`execution_eligible`、`quality_flags`、`event_time_source` 等字段。
- 事件时间由 `resolve_event_time()` 用 ActionDay + UpdateTime（+08:00）折算 UTC，失败时回退到接收时间并写入 `quality_flags`。
- OKX 的 `get_last_volume()` 只返回 `lastSz`（`okx_ticker.py:59,145`），没有累计/增量/完整性字段。

**问题**：计划把问题定义为“同名 getter 语义不一致”，但实际更深一层：**CTP 有一套显式的语义与质量字段，OKX 没有**。60.02 如果只统一 getter 名称，会出现两种坏结果之一：

- 把 CTP 的 `execution_eligible`、`continuity_status`、`volume_complete` 视为 CTP 私有扩展，则 `btapifeed.py` 中现有对这些字段的使用（如 `getattr(orderbook, "execution_eligible", None) is False`，第 713、1076 行）在 Gateway 解码为“公开标准实现”后会静默失效，而计划 §8.1 允许“只消费公共字段时解码成公开标准实现”。
- 把它们提升进 Base 合同，则 OKX、Binance 必须给出等价语义或显式“未知”，计划没有规定缺失时的取值。

**建议**：

- 60.01 的字段盘点表增加“质量/资格字段”一类，列出每个字段的 provider、消费者（Feed 内行号）和缺失语义。
- 60.02 明确决策：质量与资格字段是否属于 Base 公共合同；若是，缺失值为“未知”而不是 `True`/`False`。
- §8.1 的“解码为公开标准实现”增加一条：**会影响资格判断的字段不得被丢弃**，否则 direct 与 Gateway 的资格结果不一致，违反 §10 的对等要求。

### N2 CTP 行情对象在发布前经过有顺序的变异流水线，计划缺少“冻结点”定义

**源码事实（已核对）**：`bt_api_ctp/feeds/live_ctp_feed.py` 约 3376–3384 行，一条 Tick 的处理顺序是：

`row.init_data()` → `row.resolve_event_time()` → `_validate_ctp_quote(row)` → 通过则 `self._volume_tracker.apply(row)`，否则 `row.apply_volume_delta(0, complete=False, quality="INVALID_QUOTE")` → 可选 `_attach_managed_quote_v2_receipt(row)` → `self.push_data(row)`。

其中 `_volume_tracker` 是**有状态**对象（依赖上一条 Tick），`apply_volume_delta()` 还会写 `continuity_status`、`execution_eligible` 等派生字段。

**问题**：计划 §4.3 和 §5.3 要求“明确解析完成时点、发布后的可变性”，但没有指出：

- 现实中的“发布”点就是 `push_data(row)`，此前至少有 4 次变异，且变异顺序依赖 Feed 内的有状态跟踪器。Base 容器若要求构造即不可变，这条流水线要整体重写；若允许发布前变异，就要在合同里写明“冻结点”。
- `apply_volume_delta()` 是**唯一权威的累计转增量转换**（其 docstring 如此声明），因此 Gateway 路径必须在服务端完成这一步再编码，接收端不能重做；否则两种路径对增量的结果会因跟踪器状态不同而不一致。计划没有写这条约束。
- `apply_volume_delta()` 的实现里无条件写 `execution_eligible = False`。我只核对了这一处赋值，**未核对**之后谁把它置为可交易；60.03 应把它列入必须追踪的问题，否则无法判断资格字段在 direct 与 Gateway 中的最终值是否一致。

**建议**：

- 60.02 增加“发布冻结点”定义：容器在 provider Feed 的 `push_data` 之前完成全部变异；之后只读。
- 60.03 的单 Tick 纵切把“有状态的累计转增量”明确归属到服务端/provider 侧，并写一条对等测试：同一串累计量输入分别经 direct 与 MessagePack 往返，增量序列一致，包括首条 Tick、乱序和日切。
- 增加 `push_data` 之后检测变异的测试，用于验证“共享引用”的安全性（可用冻结代理或比较前后字段哈希，不要求改变生产类型）。

### N3 Backtrader 持仓模式已实现，但处于未提交的合并状态；计划把它写成“待选择”，且没有登记该 dirty 变更

**事实（已核对）**：

- `strategy.py:3851–3856` 的 `close()` 已支持 `position_side` 参数和 `net`/`dual_side` 模式；双向模式下两腿都有仓位且未指定方向时抛 `ValueError`。`getposition(data, broker, side=...)`（`strategy.py:4264`）已有 `side` 参数。
- `strategy.py` 从 `.position` 导入 `normalize_position_mode`、`normalize_position_side`、`POSITION_MODE_DUAL_SIDE` 等。`git status` 显示 `backtrader/position.py` 为 `M`（`+134` 行，新增 `POSITION_MODE_NET`、`normalize_position_mode`、`normalize_position_side`、`normalize_position_offset`），`backtrader/position_modes.py` 为 `D`（删除）。也就是说，**持仓模式辅助函数正在从独立模块合并进 `position.py`，尚未提交**。
- 计划 §7.5.4 第 4 条和 60.01 要求“选择并记录实际支持的模式、映射”，但没有提到 BT 侧已有这套 API 以及上述合并变更。

**问题**：

- 60.01 的 dirty 基线登记如果只看子模块，会漏掉 BT 主仓里这个会改变 `close()`/`getposition()` 行为面的未提交变更；计划引用的 `strategy.py:4264` 等行号都是相对这个 dirty 工作区的。
- 策略范围化的 `close()`（§7.5.3 第 5 条）必须与现有 `position_side` 参数、双向模式下的 `ValueError` 协调：在策略账本中，“同时持有多空两腿”时 `close()` 抛错的行为是否保留，计划没有说明。
- `position_modes.py` 被删除后，任何从该模块导入的外部代码会失败。我在 `backtrader` 与 `tests` 中没有找到对它的引用，但**未检查其他仓库**（SDK、examples）。

**建议**：

- 60.01 把 `position.py`/`position_modes.py` 的合并变更登记为基线项，说明其所属迭代，并在其提交或明确搁置之前不要引用相关行号。
- §7.5.4 第 4 条改写为：“在 BT 现有 `net`/`dual_side` 模式和 `side`/`position_side` 参数的基础上，确定策略账本如何映射；不重新设计模式枚举。”
- 60.07 的兼容矩阵增加“双向模式 + 两腿均有仓位 + 策略范围 `close()`”一行。

### N4 `BtApiStore` 每个 Tick 实际有两次 `deepcopy`，Feed 里还有 67 处鸭子类型访问；成本模型需要覆盖这两类

**事实（已核对）**：

- `btapistore.py:1915`：`poll_tick()` 每取到一条 Tick 就 `deepcopy(tick)` 写入 `_latest_ticks`。
- `btapistore.py:1928`：`get_latest_tick_snapshot()` 每次读取再 `deepcopy(tick)` 返回。计划 §4.5 只提到“保存最近行情时使用 deepcopy”，没有提读取侧的这一次。
- `btapifeed.py` 共 2003 行，`_tick_value(` 出现 67 次，`getattr(` 出现 50 次。`_tick_value()` 同时处理字典和对象两种形态（待核对其精确实现，我只确认了调用次数，没有逐处阅读）。
- 引用 `btapifeed`/`BtApiFeed` 的测试文件有 8 个；引用 `market_tick_adapter` 的测试文件为 0（与独立审阅报告 B3 一致）。

**问题**：

- “低转换”如果只统计 `deepcopy`，会漏掉 Feed 内部大量的字典/对象双形态访问；统一成标准容器后，这些访问是否能简化为直接 getter，取决于 `_tick_value()` 的语义，而该函数是 60.03 要改动的核心。
- `deepcopy` 对一个带 `quality_flags` 列表和多个时间字段的 CTP 容器并非常数成本（待测量）；写入侧复制是为了隔离后续变异，读取侧复制是为了隔离调用者变异。若 N2 的“冻结点”被采纳，这两处复制的必要性才能逐个判断，而不是笼统地“消除”。

**建议**：

- 60.01 的性能基线分别记录：写入侧复制次数/耗时、读取侧复制次数/耗时、`_tick_value()` 每条 Tick 的调用次数（可用计数器注入或 `cProfile`）。
- 60.03 的验收增加：`get_latest_tick_snapshot()` 的调用者清单，以及去掉读取侧复制后调用者是否会修改返回值（必须先证明不修改或返回只读视图）。
- 在没有这三项基线之前，计划不应使用“减少复制”作为已确认的收益。

### N5 numpy 约束比独立审阅报告 A5 所述更细：Python 3.13 已走 numpy 2.x

**事实（已核对）**：`requirements.txt` 与 `setup.py` 的约束是 `numpy>=1.20.0,<2.0.0; python_version < "3.13"` 和 `numpy>=2.1.0; python_version >= "3.13"`，注释说明 3.13 没有 numpy 1.x wheel。

**意义**：A5 提醒容器数值表示变更可能触发策略回归测试的计数漂移，这一点成立。补充一点：BT 声明支持 3.8–3.13，所以**在 3.13 上 BT 已经是 numpy 2.x**，回归基线在 3.13 上并非 numpy 1.x 标定。60.02/60.08 的数值表示评估应把“3.11（numpy 1.x）与 3.13（numpy 2.x）各跑一次策略回归”列为出口门，而不是只在一个解释器上验证。

## 2. 待核对的疑点（我没有足够证据下结论）

1. `apply_volume_delta()` 无条件置 `execution_eligible = False` 后，是谁、在什么条件下把它改回可交易？（N2）
2. `_tick_value()` 在对象形态与字典形态下对缺失字段返回什么默认值？是否会把“未知”变成 `None`/`0`？（N4）
3. `position_modes.py` 被删除后，SDK、examples 与 `docs` 是否还有引用？（N3）
4. OKX 的 `lastSz` 是否能区分“本次成交量”与“数据缺失”（`from_dict_get_float` 对缺失键的返回值）？（N1）
