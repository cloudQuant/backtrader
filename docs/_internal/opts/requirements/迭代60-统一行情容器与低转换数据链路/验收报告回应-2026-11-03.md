## 2. 修复明细

### F3 预算缺省（SDK `bt_api_py/strategy_ledger.py`）

- 开仓默认必须有预算，否则 `BUDGET_UNCONFIGURED`；这恢复了 60.07 交付说明写明的“没配预算一律拒绝”。原 SDK 测试曾断言“无预算策略不受限”，与交付说明矛盾，已改。
- **需要你确认的政策**：保留了显式开关 `require_budget=False`（只限平仓容量，不限开仓）。如不希望提供这个开关，告诉我即删除。
- 合约乘数改为 `InstrumentTerms(multiplier, quote_currency, product_model)`；预算币种与标的计价币种不同则拒绝 `BUDGET_CURRENCY_MISMATCH`，存量持仓或挂单有其他币种也拒绝，不再把不同币种直接相加。
- 平仓不需要预算。

### F4 手续费（SDK + BT）

- 手续费身份为 (intent, 币种)，值为 provider 报告的**累计**手续费，保存在 `execution_fees` 表，重启后保留。
- 数量不变、只是手续费变高的回报（迟到手续费）会入账，返回数量增量 0；重复投递幂等；同币种累计值变小则拒绝 `EXECUTION_FEE_REGRESSED`；数量更小的旧回报整体忽略。
- **新发现的缺陷（报告未列出）**：原实现从“上一条成交事件”读取手续费基线；一条不带手续费的回报会把基线清成 0，下一条累计手续费就被重复计入（例：2 → 无 → 5 记成 7）。已修复并加测试。
- BT：`BtApiBroker` 在每笔已应用成交上按币种记录 provider 报告的手续费累计（只记录有明确币种的），账本同步时逐币种传给 `apply_execution`。

### F5 对账（SDK + BT）

- `reconcile()` 只接受 `AccountPositionReport(account_ref, source, observed_ns, complete, positions)`；普通 dict 直接拒绝。
- 结果：`BALANCED`（完整、新鲜、账户一致且数量相等）、`RESIDUAL`、`IN_FLIGHT`（有差异且相关标的有在途订单）、`UNVERIFIED`（不完整、过期、观测时刻在未来）。账户不一致直接报错。默认新鲜度 30 秒，可配置。
- Reader 每次读取都在**同一事务**内对账并取快照；只有 `BALANCED` 才返回。
- BT `bind_direct_strategy_ledger`：必须有对账来源。默认是 Store 的持仓订阅（见下节“订阅式对账来源”）；也可传 `account_positions`（例如 Gateway 流）；只用账本需显式 `unreconciled=True`，此时永远没有策略现金和估值。基线快照的观测时刻取最旧一行的 provider 时间，避免旧数据看起来新鲜。
- 在途与真实分歧的区分：差异出现在“有挂单的标的”，或“本地成交晚于报告观测时刻且仍在结算窗口内”时为 `IN_FLIGHT`，此时 Reader 只给出账本持仓、不给财务数据；其余差异为 `RESIDUAL`，读取失败关闭。

### F5 补充：订阅式对账来源（用户 2026-11-03 决定）

- SDK 新增 `bt_api_py/account_position_stream.py`：
  - `StreamedAccountPositions`：由订阅维护的账户持仓，线程安全，`report()` 不做任何 I/O。必须先有一次完整快照；之后按 (标的, 方向) 应用绝对持仓推送；断线、序号跳号、未知数量都会使其变为不完整，直到下一次完整快照。
  - `GatewayAccountPositionStream`：在自己的线程里持有 `ServiceClientRuntime` 与 `ServiceAccountConsumer`（ZMQ `account.read_after`，游标 + ACK + 崩溃重放），用 Gateway 视图的 `sdk.account.view` 快照与 delta 维护持仓；只有页面到达流头且 `state_status.ready` 时才算证据，`fresh_for_seconds` 作为存活证明（`valid_until_ns`）。
  - `ServiceAccountConsumer` 新增只读属性 `last_state_status`、`last_page_at_head`（原先 `state_status` 被校验后丢弃）。
- 对账规则补充：报告带 `valid_until_ns` 时，用“当前时刻 ≤ valid_until_ns”判断新鲜度，代替观测时刻年龄；`IN_FLIGHT` 的宽限只覆盖结算窗口（默认 30 秒）内、晚于报告观测时刻的本地成交，超出窗口即为 `RESIDUAL`，真实分歧不会被长期掩盖。
- BT direct：`BtApiStore.subscribe_account_positions()`。订阅时做一次完整 SDK 持仓快照作为基线，之后由 Store 已在消费的 SDK `position` 推送更新，`disconnect` 推送标记中断；基线最多每 10 秒（可配置）以及中断后才重读一次，**不再每次读持仓都调 provider**。`bind_direct_strategy_ledger` 默认使用该订阅；Gateway 模式传 `GatewayAccountPositionStream(...).report`；每次查询读快照只在显式 `account_positions="store_snapshot"` 时使用。
- 证据：SDK 单元 10 项；**真实子进程 Gateway**（会话 worker、journal、CURVE ROUTER）→ ZMQ → 流 → 账本，依次验证 `BALANCED` → provider 被外部改动后在结算窗口内 `IN_FLIGHT`、窗口过后 `RESIDUAL` → 账本补记后恢复 `BALANCED`；BT 6 项（默认订阅、读持仓不调 provider、推送与断线、基线失败关闭、Store 事件分发路由、显式快照模式）。
- **残留**：CTP 没有持仓推送通道，direct CTP 只能靠周期基线（默认 10 秒）；OKX/Binance 的持仓推送已由 provider 解码，但是否全量到达 Store 未在真实连接上验证。

### G1 策略资金（SDK + BT）

- SDK：`StrategyCapital(amount, currency)` 是分配给策略的现金，**不是预算**。现金随本策略自己的现货成交和手续费变化；首次使用时持久化，重开时配置不同拒绝 `LEDGER_CAPITAL_MISMATCH`，已有交易历史后再配置拒绝 `LEDGER_CAPITAL_LATE`。
- 现货买入必须满足“现金 − 在途买单占用 ≥ 本单金额”，否则 `STRATEGY_CASH_INSUFFICIENT`；跨实例并发也只放行一笔（测试 6 实例争用）。
- 只建模**现货多头、计价币种等于资金币种**；期货、空头、其他币种在下单前拒绝 `STRATEGY_CAPITAL_MODEL_UNSUPPORTED`。成交缺价格后现金变为不可知 `STRATEGY_CASH_UNKNOWN`，此后需现金的买单被拒，平仓仍可用。**现金不可知后没有恢复接口**（需要人工重建基线），列为残留。
- 其他币种的手续费记在该币种现金下，不做汇率换算。
- 快照只有在同一事务内对账 `BALANCED` 时才发布现金、持仓成本和财务切点（三个水位：执行事件、账户事实=对账报告、账户活动=成交应用），否则 `financial_available=False` 并给出原因码。
- BT Sizer：现金型 Sizer（`PercentSizer`、`AllInSizer` 及两个 Int 版本、自定义 Sizer）在绑定账本后收到**本策略现金**；需要单一现金币种、stocklike 佣金模型，否则下单前拒绝，不回退账户现金。`FixedSize` 等不读现金的 Sizer 不受影响。Sizer 只是建议，账本准入仍是原子约束。

### F6 / 60.11 目标价值与百分比（BT）

- 新增 `value_strategy_book()`（`backtrader/service/service_strategy_account_book.py`），政策 `strategy_spot_equity.v1`：权益 = 资金币种现金 + Σ 现货多头 × 行情价 × 乘数。
- 同一次调用只读**一次**快照（测试断言读取次数为 1），持仓、现金、估值都来自同一版本。
- 行情价：持仓标的按 feed 名称找数据，取当前 bar 收盘价，必须有限且为正；各行情价的 bar 时间差不得超过 `Strategy.strategy_mark_max_age`（默认 0，即同一 bar 时间）。

### 关于 `type(x) is` 与 `isinstance`

- 冻结容器切换到只读子类后，`type(x) is 容器类` 不再成立。本仓库与 SDK 中对**容器类**的精确类型判断只有 CTP 三处，都在“只接受原生行情”的信任边界上，已改用 `container_class(x) is CtpTickerData`。
- 不建议改成单纯的 `isinstance`：它会接受任何子类，而子类可以覆盖 getter 冒充原生行情，削弱这三处原本的防护。`container_class` 只通过 Base 私有注册表把冻结实例映射回原类，既兼容冻结又保持精确。
- 其他大量 `type(x) is ...` 判断针对的是冻结 dataclass 合同（不会被切换类），属于有意的加固，不受冻结影响，不需要修改。普通（非信任边界）的类型判断今后建议用 `isinstance`。
