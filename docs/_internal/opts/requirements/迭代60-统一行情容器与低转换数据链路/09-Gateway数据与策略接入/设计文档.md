## 职责与实现设计

- 宿主注入 provider、身份、SDK 账本与写入准入；Gateway 路由与授权视图，共享可选 codec 编解码，transport 调用 codec 并负责连接和帧收发。
- 行情按 topic + MessagePack 经 PUB/SUB；HWM、慢消费者和丢帧显式可见，最新快照不能补回逐笔历史。
- 账户事件、命令与快照使用认证 ROUTER/DEALER；按账户/授权视图隔离并提供持久日志、快照切点和重放，ACK 只代表消费进度。

## 请求和事件流

```text
策略 → BT Broker → SDK 客户端 → Gateway 命令路由 → SDK 账户协调器 → provider
策略 ← BT 投影 ← SDK 客户端 ← 授权策略视图 ← SDK 账本 ← 已确认订单/成交
策略 ← Feed ← SDK 客户端 ← 行情 PUB/SUB ← 已规范化 provider 行情
```

账户协调器和账本由服务宿主装配，Gateway 不凭连接或 topic 授权，也不复制账本算法。接收端先建立缓冲，再取得完整快照及一致切点、重放切点后事件并按身份去重；缓冲溢出、日志过期或切点不可证明时停止可信推进。provider 多次查询并非天然原子，多进程接管和切换在步骤 10 单独验收。

## 消息和订阅

按经授权的 provider、venue、具体合约、频道、粒度和可见范围构建订阅键；完全兼容时共享上游并引用计数，每个消费者独立队列、epoch、序号、退出和质量状态。PUB/SUB 两帧分别为带终止分隔的 topic 与 08 MessagePack envelope，序号在可见分区内连续。topic 不是权限：服务端按可信授权范围分区并确保无权客户端无法接收或解密，无法保证时改用认证点对点流。HWM、慢消费者、断线及丢帧通过序列和控制通道周期水位发现并标记缺口；水位过期保持不完整，不假定发送端可获悉每次丢帧。最新快照只恢复当前值，不能补齐逐笔或盘口；无可靠重放/补数则对应完整消费不可用。

账户通道采用认证 ROUTER/DEALER，宿主验证账户、策略及操作授权，跨机/跨用户配置认证和加密。快照含范围、完整性、观察时间、日志 epoch 和切点；事件含事件 ID、游标、范围及载荷；命令含稳定 ID、账户/策略绑定、操作和参数，结果区分接收、拒绝、观察与 UNKNOWN。客户端自报身份、topic 或消息来源字段不是授权凭据。

## 本步最小可靠闭环

1. 客户端认证、绑定范围并建立有界订阅缓冲；取得授权完整快照和本地事件日志一致切点 `c`。交易所多次查询并非天然原子，来源质量须明示。
2. 从 `c` 后重放到明确水位 `h`，按范围和事件身份去重，与缓冲的实时事件合并并持续核对水位。切点和连续性、完整性及来源满足合同后才将视图标记可用。
3. 消费者将投影状态、去重信息与游标一致持久化后 ACK；ACK 仅代表消费进度。缓冲溢出、日志过期、epoch 变化、缺口或持久化失败停止可信推进，重新快照/对账；无法证明一致保持不可用。
4. 命令按账户范围稳定 ID 持久登记，同 ID 不同内容拒绝。派发后超时或结果缺失为 UNKNOWN，按原身份查询及对账，不换 ID 重发；传输 ACK 不证明交易所受理。

接收 SDK 对每进程每条实际消息解码一次并按容器合同复用，Store、Feed、Broker 保留框架投影。本步骤实现上述可靠事件闭环；步骤 10 再验证崩溃边界、多进程接管和模式切换，不代替本步交付。

## 可选组件装配和观察范围

所选 Risk/Execution 的命令决策、预留与实际派发接点在服务端账户协调器一侧；客户端传递绑定上下文，不能自己再执行第二条并行派发。provider 返回的行情、订单、成交及账户观察由服务端 SDK 验证和关联后进入业务链，Monitor 可在服务端或客户端按授权订阅对应只读观察，须标明来源、账户/策略范围和观察位置。同一事实的多处遥测不重复更新账本，不把序列化字段或监控记录当来源证明。组件未选时不依赖其发行包；故障政策见[总计划 §3.1](../迭代计划.md#31-可选-riskexecutionmonitor-的扩展边界)。

Gateway、共享 codec、ZMQ transport、SDK 与宿主的目标依赖方向、生命周期、存储端口及重构方案见[架构调研及重构设计](Gateway与ZMQ架构调研及重构设计.md)。特别地，日志、读视图及快照切点必须来自同一事务或可证明的一致机制；如无法证明，恢复视图保持不可用。ZMQ 路由身份不是业务 principal，订阅、撤权、重放、快照及命令均须分别检查授权。
