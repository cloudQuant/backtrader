# Gateway 与 ZMQ：目标架构及重构设计

状态：**设计提案；实施 NOT_STARTED，验证 NOT_RUN**。适用范围为迭代 60；入口见[总计划](../迭代计划.md)、[60.09 计划](迭代计划.md)、[需求](需求规划.md)、[设计](设计文档.md)和[验收](验收文档.md)。本次按用户要求不研究现有 Gateway/transport 源码，不把旧实现作为设计依据；因此不能断言旧实现的具体问题、需要修改的文件或现有能力。本文是建议，不表示任何仓库或真实账户已通过验证。

## 1. 选择与依据

**建议采用领域 Gateway + 可注入的 ZMQ transport**，不要求 Gateway 依赖具体 socket；transport 也不反向依赖 Gateway 的账户、策略或 provider 逻辑。Gateway 通过最小业务端口接收宿主提供的身份上下文、SDK 服务、存储和传输；独立宿主显式组装 provider、SDK、Gateway、可选组件及 transport。与 Gateway 内直接硬编码 ZMQ 相比，该方案需要少量装配与端口代码，但可以独立验证业务授权和传输、复用 direct 路径与中立合同。只定义 60.09 所需端口，暂不引入通用插件框架、服务发现或复杂集群系统。

ZeroMQ 是带不同排队语义的异步消息抽象：PUB 达到高水位时可能丢弃消息，发送成功不代表订阅者已接收；ROUTER/DEALER 本身不提供持久日志、业务重放或交易所 exactly-once。[libzmq socket 说明](https://libzmq.readthedocs.io/en/latest/zmq_socket.html) 和 [socket 选项](https://libzmq.readthedocs.io/en/latest/zmq_setsockopt.html)。MessagePack 只提供编码格式，账户语义、兼容、授权、游标和恢复合同需由应用定义：[MessagePack 规范](https://github.com/msgpack/msgpack/blob/master/spec.md)。

## 2. 分包和单向依赖

| 层/包 | 建议职责 | 不持有 |
| --- | --- | --- |
| `bt_api_base` | 标准业务容器、中立命令/事件、身份范围、版本及存储/服务端口合同；字段缺失、精度和生命周期。 | provider 真值、账户权限决定、socket 或账本实例。 |
| 共享可选 MessagePack codec | 受控 schema 注册、版本检查、有界编解码；供 SDK 客户端与 transport 组合复用。 | 业务权限、交易所授权或第二份业务模型；具体发行位置在 60.08 确定。 |
| `bt_api_py` + provider | SDK 路由、身份和请求关联、统一工作流、策略归属与账户协调；provider 管原生会话、事实和映射。 | Gateway 网络通信或向 BT 暴露场所专属 adapter。 |
| `bt_api_gateway` | 消费可信上下文；账户命令/查询路由、可见范围与授权、兼容订阅协调、读取视图、事件流服务合同。 | 自行加载凭据/provider、实现 ZMQ socket、复制 SDK 策略账本或自动获得授权。 |
| `bt_api_transport_zmq` | 使用注入 codec 的 ZMQ 连接/认证握手、消息帧、socket 生命周期、容量/背压、超时和连接状态。 | 账户业务授权政策、账本、对账、事件重放语义或 provider 回报事实。 |
| 宿主 | 选择 provider、账户身份/权限、存储实现，显式组合 SDK、Gateway、codec、transport 和选中的 Risk/Execution/Monitor；负责启动/关闭与容量。 | 不以配置自报身份、连接成功或本地日志直接证明交易所权限。 |
| Backtrader | Store/Feed/Broker 生命周期、数据线、BT Order/Position/Trade 及策略回调投影。 | 原生交易所协议与跨策略权威账本。 |

依赖方向：宿主组合各层；Gateway 只依赖 Base/SDK 的中立端口；transport 依赖消息合同和可选 codec，不依赖 Gateway；Base 不依赖任一可选运行组件。建议按职责组织 Gateway 的账户命令路由、订阅协调、授权读视图、事件日志/游标接口，transport 的连接、安全配置、帧、收发及生命周期；**这些是职责划分，不是强制增加文件或已存在模块名**。

可作为实施时的最小包内组织参考：

```text
bt_api_gateway/
  ports / contracts       # 业务端口和注入，不重复 Base 业务容器
  commands                # 账户/策略范围命令和授权路由
  market                  # 订阅去重、消费者与授权范围
  views / events          # 快照、事件游标和读视图服务

bt_api_transport_zmq/
  connection / lifecycle  # 上下文、socket、启动、关闭和健康
  channel                 # 请求响应、发布订阅、帧与背压
  security                # 认证/加密所需的传输配置与挂接
  codec integration       # 使用注入的共享 MessagePack codec
```

斜线分隔表示职责集合而非指定源码文件数量；实施时可以按现有清晰职责合并。宿主组合入口可放在恰当的 SDK/服务宿主中，不因 Gateway 可选而让它加载 provider 或凭据。`views / events` 负责服务契约和协调，不暗示其自行拥有 SDK 账本或必然实现特定数据库。

## 3. 部署、通路和所有权

```text
交易所 ↔ provider ↔ SDK 账户协调 / 策略账本 ← 宿主：身份、存储、可选组件
                              ↕ 中立端口
                       Gateway 业务路由
                              ↕ 中立消息
                   codec ↔ ZMQ transport ↔ codec
                              ↕
                   SDK 客户端 → BT Store / Feed / Broker
```

未选择 Gateway 时，BT → SDK → provider 同进程直连，**不要求安装或加载** Gateway、ZMQ、codec、Risk、Execution、Monitor。显式选择 Gateway 时，transport 故障、认证失败或事件不可用不得静默直连。服务端的账户 owner 对一个账户/route 有一个逻辑权威账本和选定派发 owner；Gateway 只提供经授权的视图和入口。命令、订单观察、逐笔成交、账户快照及策略投影分开表达；MessagePack 跨进程每次接收构造容器，同进程可复用不可变观察。

行情订阅按 provider、venue、具体合约、频道、粒度和可见范围合并；兼容时一个上游订阅、多消费者独立生命周期。消息按**授权范围**隔离后再发布：ZMQ topic 的订阅过滤不是访问控制；未获授权的客户端不能接收或解密不属于自己的行情。若无法在发布端按可信 scope 隔离或提供各自受保护通道，应使用认证的点对点流。不要把敏感账户/订单事件广播给无权客户端。

## 4. 命令、账户事件和恢复

- **命令与幂等**：认证上下文经 Gateway 验证账户、策略和操作权限，再交 SDK 绑定稳定命令/订单 ID、账户/route、内容和派发 owner。持久存储按合同作用域记录 ID 与规范化内容；同 ID 同内容返回已有状态，同 ID 不同内容拒绝。provider 能否查询/幂等按场所证据决定。发送可能已发生、响应丢失或会话中断时保持 `UNKNOWN`，按原身份查询/对账，不能自动换 ID 重发。接受请求、传输 ACK 和本地登记均不是交易所受理。可选 Execution 接管时不允许 SDK 直发再派一遍；每笔实际派发的 Risk 决策按显式配置绑定命令与有效期。
- **账户日志与快照**：Gateway 的事件流服务通过宿主注入的存储端口查询作用域化的事件日志与读视图，SDK 账户协调器拥有策略账本及事实投影。明确日志的唯一写入 owner、epoch、可见序号、水位、容量、保留期和权限；账户范围与策略授权不能只靠 topic 实现。状态/日志切点必须由存储提供一致事务或可证明的等价机制，若做不到就不提供可信恢复视图，不以多次 provider 查询冒充原子快照。
- **同步顺序**：认证 → 建立有界缓冲 → 获取经授权的快照及其本地一致切点 → 从切点后重放到明确水位 → 去重合并实时事件并继续检查水位。需要持久恢复的消费者在状态、去重和游标一致持久化后 ACK；崩溃后按已提交游标重放。缓冲溢出、断线、权限变化、日志过期、epoch 变化或水位过期时标不完整，停止可信推进并重新同步或对账。多次 provider 查询不天然原子；本地切点不证明交易所事实完整。
- **接管边界**：共享存储 fencing 只约束实际检查该 fence 的写入；不能证明持有 provider 会话的旧进程已无法下单。每次实际派发必须经过可验证、对新旧 owner 都强制生效的派发栅栏，或能证明旧 owner/其 provider 会话已失效；两者都无法证明时禁止自动接管。锁和租约也不能阻止其他未受约束的手工终端，仍需账户对账。

## 5. 传输机制和生命周期

- 行情采用授权分区内的 PUB/SUB 与按该分区定义的 epoch/sequence；每个可见分区由认证控制通道提供有界且及时的水位。序号缺口、水位过期及启动/慢消费者/重连均影响完整性；不能假定发送端能观察到所有丢失。需要完整逐笔而来源无可用补数时明确不可用。
- 命令、快照、重放和 ACK 采用受认证 ROUTER/DEALER 及关联请求 ID；规定请求/响应帧、版本/能力协商、可见错误类别、payload 上限、超时与一致性。路由 ID 不是账户身份，用户自报字段不是权限。入站解码使用上限和受控类型注册；错误消息不得泄露跨账户内容。
- 定义可信 principal 到账户/策略/订阅及操作 scope 的映射、撤权和过期处理；认证、加密、密钥来源和轮换由可信宿主/传输装配明确，不把密钥存入仓库或写日志。CURVE 或其他机制须按部署验证，不能仅凭开启某个 socket 选项宣称业务授权完成。
- 为每个 socket 明确线程/事件循环 owner、队列边界、取消与关闭顺序；Context 与 socket 的线程安全规则不同，优先每线程独立 socket，避免跨线程共享。[PyZMQ 线程安全说明](https://pyzmq.readthedocs.io/en/latest/howto/morethanbindings.html)。定义停止接收、排空或标记未处理、关闭连接、释放资源的有界行为；关闭不确定不伪造成订单终态。

## 7. 可执行验收与证据

- **隔离与缺省**：未安装、已安装未选择、显式选择缺包/故障；direct 不强制依赖组件，选中 Gateway 失败不回退；单账户 10 策略兼容共享订阅与单策略退出。
- **权限**：错误身份、越权账户/策略、直接订阅其他 topic、撤权与重连、重放/游标越权和权限变化；无权连接不能获得可解密业务数据，记录拒绝而不泄露内容。
- **wire 与生命周期**：不支持版本、畸形/超限帧、重复键、请求 ID 冲突、连接半关闭、队列满、慢消费者和有界停止；每个 socket 的并发 owner 可验证。
- **事件与命令**：快照并发追加、重放去重、ACK 前后崩溃、持久化失败、epoch 变化、日志过期、水位过期、同 ID 不同内容、发送后响应丢失；分别断言状态、拒绝/UNKNOWN 和持久水位，不增加第二笔派发。
- **接管**：故意保留旧 provider 会话，证明仅存储 fence 不授权新 owner；只有实际派发强制栅栏生效或旧会话已失效且已对账时才能继续。无法证实时 NO-GO。
- **证据**：源码/隔离 fake、跨进程、wheel、可复现性能和经另行授权的真实来源/账户分别记录；隔离替身不证明 provider、授权、交易或真实性能。所有尚未执行项为 NOT_RUN。
