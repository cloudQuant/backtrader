## 职责与实现设计

- Base 持有业务合同和与实现无关的端口；原生解析归 provider，身份来源、信任和消费游标分别由实际 owner 维护。
- 定义 Tick 累计/增量、Bar 完成状态、订单与逐笔 fill、持仓模式、策略预算/账户事实的最小字段和未知值。
- 约定发布后稳定性、惰性解析和可变嵌套对象所有权；不放宽现有精确类型及来源检查以凑通路。

## 状态及故障边界

- 实施前核对工作区和现有调用者；确定唯一状态 owner、生命周期及与相邻步骤的接口。
- 本步涉及的来源、授权、时间、账户事实或结果不确定时保持 UNKNOWN/不可用；显式启用的可选组件失败不得静默回退。
- 设计更改、破坏性迁移和未关闭风险记录在本步交付说明中，提交用户审阅。

## 对象和兼容设计

以步骤 01 审定的现有 Base 接口为起点，形成规范字段表及 DTO 对照表，按复用、兼容适配或迁移逐项实施，避免另造平行事实模型。每种对象定义必填/可选字段、可区分零的显式缺失、非法类型和非有限数值处理。时间、价格、数量的规范类型与精度先冻结，原生单位转换归 provider；不凭系统时间补来源时间。

构造时隔离外部可变输入；发布后属性、getter、嵌套扩展对消费者稳定。若保留惰性解析，须证明并发初始化确定、无副作用且输入不再可变。对象引用可复用；route、订阅、来源证明、会话代际、消费游标及 Feed 本地状态独立管理。自报字段不证明来源。标准字段与扩展同名必须按合同拒绝；未知扩展版本、是否保留字段均须明确。

Base 定义模型与端口，provider 负责场所字段，SDK 负责绑定与工作流，BT 保留投影；账本实现和 codec 不在本步。盘点 `TickerData`、`BarData`、`OrderData`、`TradeData`、`PositionData` 与 SDK DTO 的构造/继承/getter、公开导出、调用方和映射；核对 CTP `get_position_direction` 与 Base `get_position_side`、惰性 getter 和 `get_all_data` 覆盖，不预设兼容。
