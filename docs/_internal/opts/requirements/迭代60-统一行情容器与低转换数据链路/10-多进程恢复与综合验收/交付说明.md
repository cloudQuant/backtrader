## 6. 第三阶段收尾（2026-11-03）

### 6.1 性能：NO-GO → 有条件 GO

在隔离的 venv 里安装带 C 扩展的 `msgpack` 1.2.4（未改动共享的 anaconda 环境）后重测（[原始输出](evidence/perf_wire_msgpack_c_2026-11-03.txt)）：

| 指标 | MessagePack v1（严格） | JSON → 同一冻结容器（无严格检查） |
| --- | --- | --- |
| 编码 | 15.8 µs | 34.9 µs |
| 解码为冻结容器 | 40.7 µs | 29.8 µs |
| 往返合计 | **56.4 µs** | 64.7 µs |

**判定：有条件 GO**。前提是使用带 C 扩展的 msgpack（≥1.1，主流平台都有 wheel；`codec_backend()` 可检查）。此时 v1 往返比 JSON 快约 13%，而且多做了十进制文法、重复键、拒绝浮点等检查。纯 Python 的 msgpack（例如 anaconda 自带的 1.0.3）下仍不达标。msgspec 在有类型和无类型两种模式下**都会静默接受重复键**，不能替代。

### 6.2 多进程接管 / direct↔Gateway 切换：NO-GO → 已实现（需部署提供证据）

SDK 新增 `AccountOwnerHandoff`（`bt_api_py` `56106631`）。它把 QUIESCE → FENCE → RESTORE → SYNC → RECONCILE → READY 持久化到 SQLite，并保留只追加的审计记录：
- **FENCE**：必须提供与账户、旧 owner 代际绑定的 `OwnerRevocationProof`（provider 会话已撤销，或派发栅栏已生效）；存储租约不被接受。没有证据就是 NO-GO。
- **派发权**：从 QUIESCE 到 READY 期间任何一方都不能派单；READY 后代际加 1，旧代际永远不能再派单。
- **对账**：只接受 `BALANCED`。
- **其他约束**：阶段不可跳过，同时只允许一个切换；任一阶段后崩溃都能从断点恢复，且审计中没有重复阶段。

19 项测试，变异检查有效。**限制**：证据的真实性（例如 provider 的登出回执）由部署方提供，本模块只校验绑定关系。真实环境下的接管仍为 NOT_RUN。

## 9. owner fence：派发租约、协调库身份绑定、旧会话撤销（复验 G1；用户审阅 PENDING）

本节只描述 owner fence，与上文 §6.2、§8 中 owner fence 的描述冲突时以本节为准。**G1 仍为 NO-GO**：本机（同主机）范围内已能本地证明，跨主机单写仍无法在本地证明。

| 项 | 当前实现 | 证据等级 | 状态 |
| --- | --- | --- | --- |
| 原子派发出口 | 原来的“先检查、后调用”改为 SDK `DispatchLease`：每次 provider 写入在 SQLite `BEGIN IMMEDIATE` 内登记一行 `IN_FLIGHT`（绑定账户、owner、代际、intent），整个 provider 调用期间持有，结束时记 ACKNOWLEDGED / REJECTED / NOT_SENT / UNKNOWN。QUIESCE 与租约在同一串行事务域内，是排他一侧：提交后旧代际拿不到新租约，并记录租约高水位与在途数；FENCE 有界等待在途租约，超时就记为 UNKNOWN。BT 侧：同步 Store 由 Broker 在 `submit_order`/`cancel_order` 外层持有租约；队列 Store 由 `SdkCorrelatedOrderAdapter.dispatch_command` 在派发前最后一步取租约，provider 调用返回后再结束租约。不能发租约的 fence 在认领前被拒绝 | UNIT/FAKE + INTEGRATION_SIM（线程屏障交错；两个进程共享协调库，含旧 owner 进程在写入中被杀） | 本机范围 PASS |
| 协调库身份绑定 | `AccountCoordinationBinding(account_ref, provider_route)` 的摘要决定规范协调库位置（`canonical_coordination_path` / `open_canonical`）；库内记录绑定摘要，路由不符时拒绝打开。主机注册表（`HostAccountRegistry`，默认按用户放在 `~/.bt_api_py/account-owner-host`）以原子硬链接登记“绑定 → 唯一库路径”，同一账户在本机的第二个库被拒（`COORDINATION_STORE_CONFLICT`）。owner 进程在整个生命周期持有 OS 建议锁（POSIX 用 `flock`，Windows 用 `msvcrt.locking`），租约必须由持锁实例发出；重新取锁时，前一个持锁者遗留的 `IN_FLIGHT` 记为 UNKNOWN。未绑定的 handoff 只用于诊断，永不放行派发 | UNIT/FAKE + INTEGRATION_SIM | 同主机 PASS：原 xfail 改为真实通过（`test_same_host_second_database_for_the_account_cannot_dispatch`） |
| 跨主机单写 | 两台主机或两个 OS 用户的注册表互相独立，本地无法协调 | 严格 xfail（`test_cross_host_databases_do_not_prove_account_exclusivity`） | **NO-GO**：部署须提供 provider 会话登出回执，或交易所侧会话撤销/单会话限制的证明 |
| 旧会话撤销 | 新增中性接口 `bt_api_py.provider_session_revocation`：`ProviderSessionRevocationEvidence`（账户、路由、被撤销代际、旧 owner 取锁时登记的 provider 会话引用、类型、观测时间、回执引用）和 `ProviderSessionRevocationVerifier` 协议。FENCE 要求证据与账户、路由、代际、会话全部一致，且观测时间不早于 QUIESCE，并经部署方 verifier 确认；没有证据、没有 verifier、确认失败或 verifier 抛异常时一律拒绝接管。旧的 `OwnerRevocationProof` 与 `proof_verifier` 已删除（破坏性变更） | UNIT/FAKE（仅 fake provider） | 接口与拒绝路径 PASS；真实 provider 证据 NOT_RUN |
| 在途 UNKNOWN 传给新 owner | UNKNOWN（包括 FENCE 超时、owner 崩溃遗留，以及旧 owner 晚到的回报，后者只记 `late_outcome`）一直保持未决：RESTORE 审计中带 `carried_unknown_intents`，存在未决项时 RECONCILE 拒绝（`HANDOFF_NO_GO_UNKNOWN_INFLIGHT`）。同一 submit intent（SDK client_order_id 或账本 intent id）对任何 owner 都不再发租约 | UNIT/FAKE + INTEGRATION_SIM | PASS |

**残余风险**：拿到租约的旧进程如果在调用 provider 之前长时间停顿，FENCE 超时后会把它记为 UNKNOWN，但它恢复后仍可能把请求发出去。这一点只能靠旧会话撤销证据兜底，因此 FENCE 一定要求撤销证据。SQLite 写锁不保证公平：派发极其频繁时，QUIESCE 可能要等到忙等超时（10 s）。
