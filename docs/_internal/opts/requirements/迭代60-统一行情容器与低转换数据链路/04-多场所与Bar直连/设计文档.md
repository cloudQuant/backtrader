## 职责与实现设计

- provider 完成各自原生解析，SDK 保留订阅/序列/质量状态，BT 保留数据线、聚合及回调顺序。
- 完成 Bar 以完成标记与时间为合同；历史重叠、重复、乱序、重连或缺失分别处理，不能假装补齐历史。
- 复用步骤 02 容器，登记 MarketBar 及旧适配器的活跃消费者和退役条件。

## 状态及故障边界

- 实施前核对工作区和现有调用者；确定唯一状态 owner、生命周期及与相邻步骤的接口。
- 本步涉及的来源、授权、时间、账户事实或结果不确定时保持 UNKNOWN/不可用；显式启用的可选组件失败不得静默回退。
- 设计更改、破坏性迁移和未关闭风险记录在本步交付说明中，提交用户审阅。

## 接口与所有权

| 边界 | 输入 | 输出和 owner |
| --- | --- | --- |
| provider → SDK | venue、route、合约、频道/周期、原生事件、接收时间及单位 | 02 标准容器含时间精度、缺失原因与 Bar 起止/完成状态；扩展不覆盖标准字段。 |
| SDK → Store | 容器及独立来源、session/epoch、序列和质量元数据 | SDK 按订阅检查并维护消费者游标与缺口，容器不签发证明。 |
| Store → Feed | route 绑定、容器、历史与实时窗口 | BT 数值线和回调；局部质量与聚合状态不能改写共享事实。 |

仅兼容的 provider、合约、频道、周期和来源要求允许共享订阅；每消费者独立生命周期。发布前完成初始化并限制嵌套可变输入，历史快照不被后续回调改变。本地 Tick 聚合与交易所 Bar 各自标识来源。

## 历史与实时衔接

1. 先订阅实时并有界缓冲，记录 epoch 和可用水位；读取有边界历史及其完成状态。
2. 合约、周期、时间边界、来源和完成语义一致时才判重；相同身份内容冲突记录并阻止可信推进。
3. 以可证明切点衔接；缓冲溢出、缺口、代际变化或不可证明切点标记不完整并重建，不伪造补齐。形成中和完成 Bar 分别交付。
4. 沿用框架多 Feed 调度；重复、乱序、旧 epoch、慢消费及消费者退出均可观察。

事件与接收时间及原生精度分别保留，不能以接收时钟冒充事件时钟。BT 浮点投影记录精度损失，量未知不变零。
