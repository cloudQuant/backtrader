## 1. 目标、范围与非目标

### 1.1 目标

- 使用 `bt_api_base.containers` 梳理统一的 Tick/Ticker、Bar、订单、逐笔成交和持仓数据合同；CTP、OKX、Binance 等 provider 按合同实现自己的容器子类与原生解析。
- `bt_api_gateway` 是**可选组件**。未启用时，Backtrader 通过 `bt_api_py` 直接连接 provider（direct）；显式启用时，数据由 `bt_api_py` 经 Gateway 转发给 Backtrader。两条路径共享 Base 容器语义，配置 Gateway 不改变业务字段或策略接口。
- 同一进程内尽量共享已规范化、已冻结的对象；Gateway 跨进程转发使用版本化 MessagePack 合同，接收端解码为标准容器后在本进程复用（INV-03）。direct 不要求安装或连接 Gateway、ZMQ 或 MessagePack codec（INV-01）。
- 保留 Backtrader `Order`、`Trade`、`Position` 的框架生命周期与状态投影；provider 数据、账户快照或 Gateway 事件不自动替代这些框架对象。
- 支持目标场景：一个账户内多个策略交易同一具体合约，订单和成交分别归属到各策略，维护可恢复的策略持仓和策略账户视图，并与真实账户核对。该场景是目标设计，当前未实现或验收；真实多策略交易的解锁规则见公约 §5。
- 交易所原始消息仍需解析，Backtrader 数据线仍需写入数值。序列化、跨进程传输和必要的快照隔离不可笼统描述为零拷贝。

### 1.2 非目标（本迭代不做）

- 不实现 Risk、Execution、Monitor 的业务功能，只预留中立端口（§3.1）。
- 不实现多进程 direct 共享账户；不做 Gateway 集群或高可用。
- 不新增第二套策略调度器；不做策略订单净额合并、拆单或算法执行。
- 不宣称任何真实账户、provider 或性能能力已验收；真实账户操作另需授权。
- 不在没有基线测量的前提下删除已有的复制或校验（INV-12）。

## 2. 可选 Gateway 与目标数据流

### 2.1 未启用 Gateway：SDK 直接接入（默认）

```text
交易所 → provider / Base 容器 → bt_api_py → Backtrader Store
                                           ├→ Feed → 策略行情回调 / 数据线
                                           └→ Broker → 订单、成交、持仓与通知

下单/撤单：Strategy / Broker → bt_api_py → provider → 交易所
```

SDK 与 Backtrader 同进程时，尽量传递同一个**已冻结**的标准数据对象，不经过序列化。同进程引用复用不等于省略 Backtrader 数据线、订单状态或本地聚合。

### 2.2 显式启用 Gateway：经 Gateway 转发

```text
交易所 → provider / Base 容器 → bt_api_py（服务端）→ bt_api_gateway
    → MessagePack 编码 / ZMQ（跨进程）
    → bt_api_py（接收端）→ Backtrader Store → Feed / Broker → 策略

下单/撤单：Strategy / Broker → bt_api_py（接收端）→ Gateway 命令接口
    → bt_api_py（服务端）/ provider → 交易所
```

服务端和接收端指相应进程中的 SDK 职责。账户快照、订单观察与逐笔成交事件必须区分；下单和撤单是反向命令，不是行情或账户数据广播。

### 2.3 选择与故障边界

- 未配置或未选择 Gateway 时走 direct；是否安装 Gateway 不能隐式改变路径（INV-01）。
- 显式选择 Gateway 后，其缺失、连接失败、认证失败或事件不完整必须明确报告，不静默切回 direct（INV-02）。
- 两条路径对同一事实使用相同容器字段、单位、缺失值及语义。**对等的含义是业务字段和决策结果一致**；服务端已验证的 provider 来源证明，经编码传到客户端后，其证明强度由“服务端声明 + 受认证通道”构成，不等同于客户端直接验证原始 provider 证明。60.08/60.09 须定义接收端可依赖的证明等级和不可用条件。
- SDK 与 Feed 继续维护各自的来源、会话、路由、序号、新鲜度、消费状态和必要校验。容器类型、字段自报或对象共享不证明来源可信，也不授予交易权限（INV-05）。

## 3. 职责划分

| 组件 | 目标职责 |
| --- | --- |
| `bt_api_base.containers` / 中立协议 | 定义共享行情、订单、成交、真实账户与策略持仓/账户视图合同及存储端口：字段或 getter、作用域、单位、缺失值、事件/接收时间、数量语义、**发布冻结点**及生命周期。对照现有 Base 协议和中立 DTO 收敛重复结构；数据合同不持有账本，不签发来源或授权证明。 |
| `bt_api_ctp`、`bt_api_okx`、`bt_api_binance` 等 provider | 实现 Base 合同，解析各自原生字段并填充规范数据；**有状态的原生转换（如 CTP 累计量转增量）在 provider 侧且只做一次**；维护场所专有字段、原生连接及回调语义，不猜测未知事实。 |
| `bt_api_py` | direct 模式直接向 Backtrader 提供 provider 容器；Gateway 模式由服务端 SDK 提供数据、接收端 SDK 消费转发。统一 provider 发现、订阅、route、会话和来源绑定；负责与框架无关的策略订单归属、成交去重、账本更新、账户视图投影及对账，通过存储端口由宿主装配。业务风控政策归显式选择的 Risk。 |
| `bt_api_gateway` | 可选；仅显式启用时转发 SDK 数据，提供账户范围命令路由、行情订阅协调及授权读视图；不复制第二套记账算法。 |
| 独立服务与 transport | 可信宿主注入 provider、身份和写入准入；共享可选 codec 负责编码，transport 调用 codec 并负责认证和数据传递。广播 topic、连接成功或 ACK 不是账户授权或交易所事实。 |
| Backtrader Store / Feed / Broker | Store 管理实例、路由和生命周期；Feed 保留数据线和本地 Bar 聚合；账户级 Broker 根据 SDK 账本及已验证事实投影 BT 订单、成交、策略持仓/账户视图和通知，并在权限允许时提供真实账户视图。逐项消除经测量确认的重复展开和不必要复制。 |
| Backtrader Strategy | 消费行情、自身持仓、预算/盈亏和订单通知；不需要感知 SDK 账本在本地还是 Gateway 服务端。真实账户视图是独立且受权限约束的接口；既有 API 变更按 §7.6.4 处理。 |

### 3.1 可选 Risk、Execution、Monitor 的扩展边界

本节是**预留架构合同**：本迭代不实现三个组件的业务功能，只在各步骤盘点可复用的中立合同，在适当边界预留最小可注入端口，并用隔离替身验证调用和失败语义。接口名称和是否复用现有合同在 60.01–60.02 确定；不为预留能力引入通用插件框架，也不增加 direct 的强制依赖。组件是否安装不决定是否启用；未选择时不要求安装或加载。

```text
下单/撤单：Strategy → BT Broker → SDK 身份/账户/命令绑定
         → [可选 Execution：接管意图、派发与恢复；或 SDK direct 派发]
         → 每笔实际派发前执行所选 Risk 决策和必要预留 → provider → 交易所

行情与回报：provider → Base 容器 / SDK 来源和会话验证 → Feed / Broker
                                         └→ [可选 Monitor 只读观察]
Gateway：以上账户协调、可选决策与派发在服务端宿主组合；客户端经认证路由访问。
```

`[ ]` 表示显式选择后的目标接点。未选择 Risk 时仍保留身份、会话、基础请求校验、关联和 UNKNOWN 处理。行情和回报不必都经过 Risk 或 Execution，相关消费组件可依权限读取所需的有效事实；Monitor 从明示观察点取得事件，不成为事实处理链的必经中转。若未来由 Execution 修改、拆分或聚合意图，每笔实际派发都要重新满足授权、账户/策略绑定和所选 Risk 决策。

| 可选组件 | 未来接口输入与输出边界 | 失败、所有权及本次范围 |
| --- | --- | --- |
| Risk | 在账户 owner 侧接收经绑定的命令、策略/账户范围及所需的已验证行情、持仓与预算事实；返回允许/拒绝/不可判定及必要预留。策略、账户、时效和所批准的命令参数必须绑定。 | 选中后缺包、超时、决策过期、事实不完整或服务失败不得绕过；拒绝/不可判定不派单。取消请求的准入规则单独定义。 |
| Execution | 按显式装配接收带稳定身份的策略意图或命令，与账户 owner、provider 和 Risk 以中立端口协作。 | 同一账户/命令只有一个派发 owner，直发与 Execution 不双发；不创建双权威账本或凭回执认定成交。当前 `bt_api_execution` 不可导入（§4 G-12）。 |
| Monitor | 按授权接收只读行情质量、命令状态、订单/成交、账户/策略状态与健康事件。 | 只观察，不修改共享容器、路由或账本；普通遥测有界隔离，丢失/延迟显式告警，不阻塞核心链路；若部署声明监控为交易前必需门槛，其不可用时停止相应操作。日志不泄露凭据或越权账户数据。 |

最小中立端口：**命令与身份上下文、决策/预留结果、单一派发与结果、只读观察、账本持久化**；优先复用 `bt_api_base` 已有 DTO/协议。各步落点：60.01 登记组件选择、owner 和失败矩阵；60.02 决定端口和兼容；60.03–04 预留行情观察；60.05–07 预留订单决策、单一派发、只读回报及单一账本边界；60.08–09 界定跨进程视图和权限；60.10 用隔离替身验证组合与故障。替身只证明接口合同。

### 6.2 Broker 状态与回调

- 数据容器表达观察；Broker 持有本地订单引用、框架关联、执行 bit、BT 持仓投影及通知时序；多策略权威归属账本的 owner 见 §7.5（INV-07）。
- 按账户、route、会话/代际、品种和订单/成交身份匹配；重复、乱序、部分成交、成交先于订单及未知身份要有明确处理。**成交先于订单的暂存区有界**：满时持久化隔离并停止相关游标推进、触发对账，不丢弃、不 ACK。
- 既有 startup 持仓策略在首次快照后由确认成交维护本地账本；不能无条件用远端快照覆盖本地持仓。

## 7. Gateway 行情与账户数据转发方案

### 7.1 目标分层

| 层次 | 职责与交付 |
| --- | --- |
| Provider | 一次解析原生数据为 Base 合同并完成有状态转换；区分真实来源和未确认字段。 |
| Gateway 市场域 | 按 provider、venue、品种、频道、订阅及授权协调行情源；保留流身份、代际、序号、时间及质量语义。 |
| Gateway 账户域 | 按可信账户和授权视图提供完整快照、可恢复变更及有来源绑定的订单/成交事实；区分账户事实与策略归属。 |
| 服务宿主和 transport | 宿主提供已认证身份、资源和服务装配；共享 codec 编解码，transport 负责协议帧、客户端认证及传输。 |
| SDK 客户端 | 统一 direct 与 Gateway 的业务消费接口；负责订阅、路由、解码、来源绑定、连续性与错误投影。 |
| BT Store / Feed / Broker | 分别消费行情和账户/订单事实，保留框架对象、状态和回调。 |

### 7.2 行情：订阅与接收

1. 客户端按明确的品种、频道、粒度和权限范围订阅；Gateway 聚合可共享的上游订阅，为独立消费者提供流身份、代际与序号。
2. 跨进程行情使用版本化 MessagePack 合同，携带最小必要的来源、时间、游标及质量信息（含 D60-11 的资格字段）；接收端只解码一次形成标准容器，再在本进程传递引用。
3. 队列容量、慢消费者、合并、丢帧、乱序和断线重连必须有可观察的合同；缺口或来源时钟不足时不得将行情升级为完整、实时或可交易。
4. ZMQ PUB/SUB 不保证送达或重放；最新行情快照不能当完整逐笔历史或完整盘口。

### 7.3 订单、成交和持仓：快照与事件

1. 初始读取使用经授权的账户快照，明确完整性、观察时间和一致性；不完整或来源未知不得解释为零仓、空订单或已确认终态。
2. 订单状态和逐笔成交如需实时推送，应有明确的 provider 事件来源、关联、事件 ID、流 epoch/序号和重放或对账合同。
3. 接收端先建立快照基线，再按游标处理后续事件；重复按可信 ID 幂等，缺口、代际变化或无法关联时暂停推进并查询/对账。需持久恢复的消费者在本地状态与游标持久化后再 ACK（INV-05）。
4. 行情流、账户视图和订单/成交可靠事件可采用不同的容量、持久性与恢复策略；不得把可覆盖的最新行情语义套用于成交事件。

### 7.4 订单命令反向路径

```text
Strategy → BT Order / Broker → SDK 命令与关联 → 已认证 Gateway 命令路由
         → 服务端准入 / 账户 owner → provider → 交易所
         ← 回执与订单/成交观察，经各自的验证及事件路径返回
```

- 提交和撤单携带账户、route、客户端命令/订单身份及必要关联。服务端本地回执、客户端 ACK 或网络超时都不能证明交易所受理、拒绝或未发送（INV-05、INV-06）。
- **同 ID 内容一致性按语义指纹判断**：指纹覆盖账户、route、策略、命令类型及全部业务参数的规范化值；等价表示（map 顺序、可选字段缺省、等价十进制写法）不视为冲突，同 ID 改账户、策略或数量必须拒绝。
- **命令入口有界**：定义命令队列容量、准入前持久化、过载拒绝或延迟、客户端重试和 UNKNOWN 分类；持久化不可用时不得继续实际派发。
- 本地锁、日志或 lease 不证明其他主机及交易所侧的单写者或原子性。

### 7.5 一个账户、多个策略交易同一合约

**场景**：一个账户下 10 个策略交易同一具体合约（例如 `SA2701`；`SA` 是品种名，订阅、下单和对账使用已确认的具体合约）。图示为 Gateway 路径；direct 复用同一账户协调及账本合同（§7.6）。首个切片先覆盖单进程多策略。BT 引擎已支持同一 Cerebro 多策略共享一个 Broker（G-16）。

```text
CTP / provider → SDK → 服务宿主 + Gateway → 行情编码 / 发布
                                                ↓
                               SDK 接收并解码 → BT Feed → 策略 1 … 10

策略 i → BT Broker / SDK → Gateway 账户命令路由 → 账户协调器 → provider
                                                     ↓
                           订单归属 + 成交去重 + 策略账本 + 账户对账
                                                     ↓
                        可恢复的账户事件 / 策略视图 → 策略 i 的 BT 通知
```

账户协调器是服务宿主组合的逻辑职责，不表示 Gateway 包内已提供 provider 客户端、凭据加载器或持久化实现。

#### 7.5.1 行情共享

1. Gateway 按 provider、venue、具体合约、频道、频率/深度和授权范围匹配上游订阅；合同兼容才共用。订阅用消费者引用计数，单个策略退出、重订阅或变更配置不得中断其他消费者。
2. **孤儿订阅回收**：每个消费者有 lease/heartbeat；断线只暂停该消费者，租约到期后幂等回收其引用；重连使用新消费代际，不影响其他订阅。
3. 跨进程在发布端编码一次，每个接收进程对每条实际收到的消息解码一次；同进程 10 个策略复用同一已冻结容器引用（INV-11）。
4. 每个接收端保留自己的生命周期、消费进度、积压和缺口状态；需要完整逐笔而来源不能补回时，该消费流明确不可用或不完整。

#### 7.5.2 订单、成交和策略归属

1. 每个策略有在账户/route 下稳定、唯一的 `strategy_id`（来源按 D60-06），另有每次启动的 `run_id` 与受认证调用者绑定。**同一 `strategy_id` 只能有一个当前 run**（D60-17）：接管时持久化单调代际，旧 run 的 submit、cancel、订阅、ACK 和恢复请求被拒绝。
2. BT 创建订单时，把本地订单引用映射到稳定的命令 ID、客户端订单 ID、策略和运行实例；账户协调器在派发前**在同一持久事务中**写入绑定、派发状态和全部预留，恢复时拒绝孤立记录。ID 规则按各 provider 原生约束定义。
3. 下单、撤单和回报先按已认证账户和可信订单关联校验；订单状态及逐笔成交定向投递给所属策略。不得仅凭同一合约推断归属。
4. 成交以 provider 可验证的成交身份及其实际作用域去重；**去重记录保留期覆盖最大重放和迟到窗口**，不足时拒绝旧游标重放并先对账。身份缺失、冲突或外部订单进入未归属/待核查队列。派发超时保持 UNKNOWN（INV-06）。

#### 7.5.3 策略持仓账本

1. 首期由 direct 进程或 Gateway 服务宿主为每个账户/route 装配**一个逻辑账户协调器和一个持久策略归属账本**（INV-07）。`bt_api_py` 持有中立归属、记账与对账工作流，宿主注入持久化端口；BT Broker 保留订单引用、策略关联、框架投影与通知。实现前按 D60-07、D60-08 决定 BT 既有策略账本子系统和 Execution journal 的复用关系，不得同时维护两个独立的权威账本。
2. 账本以账户、route、策略、具体合约和持仓维度为键；保存绑定订单、确认的逐笔成交、去重身份、数量/单位、均价、费用及币种、今昨仓或多空腿、日志水位和未决状态。同一账户的状态变更串行化；持久存储以事务原子提交成交去重、账本变化及消费进度。
3. **账本存储有 schema 版本**：迁移原子且幂等，覆盖既有 journal、迁移中崩溃、旧版本 reader/writer 拒绝、不可降级和备份恢复演练；迁移失败不得进入 READY。
4. 新账户的策略账本以确认的零基线或明确审批的初始归属为起点；已有账户持仓先作为未归属持仓，经可审计的人工认领或明确策略后才允许依赖该仓位的操作。禁止把账户快照复制成各策略持仓（INV-09）。
5. 例：A 确认开多 2 手，B 确认开多 3 手，基线为零且无其他变动，则账本为 A 多 2、B 多 3，账户观察应为多 5。A 平仓以其可平量为上限，未决平仓单计入预留；并发平仓在账户协调器中原子检查和预留。
6. BT 侧多策略模式下，`getposition()`、`close()`、目标仓位及其他依赖持仓的 API 统一使用策略范围数据，或明确拒绝；账户总仓通过独立且标明范围的接口读取。策略范围的 `close()` 须与现有 `position_side` 参数和双向模式“两腿均有仓位时抛错”的行为协调（G-17）。SDK 把每笔命令的可信策略身份传入，而非沿用 Store 单一身份配置（G-19）。
7. 账户资金和保证金是账户事实，不因 10 个策略复制 10 份可用余额（INV-10）。

#### 7.5.4 账户级对账与异常处理

1. 对账以 provider 返回的经验证账户持仓、订单和逐笔成交为外部事实，以策略账本和已记录的未归属部分为内部事实，按账户、route、具体合约、单位、持仓模式、多空腿、今昨仓和交易日比较。仅在维度可直接相加且来源完整时使用“各策略已归属量 + 已确认未归属量 = 账户实际量”。
2. 启动、重连、缺口、日切和定期触发对账。先固定账本与事件日志切点，再读取账户观察并衔接切点后的回报；无法建立可靠比较切点时标记不确定（`NOT_COMPARABLE`），不宣布一致。
3. 发现差异、外部成交、身份冲突或无法核实的持仓时，保留证据，暂停受影响账户/合约上依赖仓位的操作；人工调整记录原因、依据、操作者与前后水位。不静默覆盖、不自动分摊。
4. 持仓模式在 BT 现有 `net`/`dual_side` 与 `side`/`position_side` 之上映射，不重新设计枚举（G-17）。60.01 记录实际支持的模式映射和自成交防范方案；不支持的组合明确拒绝。

**实施顺序**：先明确身份、持仓模式和既有账本复用决策，再完成单账户单进程的共享行情、独立命令归属、持久策略账本和账户对账；随后按同一合同扩展多进程。

### 7.6 策略账户信息与两种模式统一

本节是跨仓**目标设计**。策略账户是按归属规则构造的内部视图，不是交易所子账户；无初始分配或计算依据时字段保持未知/不可用（INV-10）。

#### 7.6.1 视图、字段及计算口径

| 视图或字段 | 目标语义与来源 |
| --- | --- |
| 真实账户视图 | provider 的余额、可用资金、权益、保证金、持仓及开放订单，附账户/route、币种、来源、时间和完整性；有权限时单独访问。 |
| 策略持仓 | 由已可信关联并去重的逐笔成交、明确初始归属及经审计调整计算。 |
| 资金分配与调拨 | 按账户、策略、币种记录初始预算、追加、划回及有效时间；是内部额度。 |
| 已实现/未实现盈亏 | 由归属成交、合约乘数、方向、结算规则和有效价格按明确方法计算，标注估值来源、价格时间、精度和完整性；依据缺失时标记未知或过期。 |
| 费用及其他收支 | 已确认且能归属的手续费、返佣、资金费逐项记录；迟到费用以可追溯调整入账，未知费用不设为零；共同费用先列入未分配。 |
| 策略权益、占用与可用预算 | 依据版本化的分配、盈亏、费用、预留和估值政策计算，注明币种、时点与完整性；多币种不擅自加总。 |

示例：账户可用资金 100 万元，A、B 内部预算分别为 20 万元和 30 万元，仅为示例，且预算是内部分配而非账户余额。策略权益或可用预算不能简单等同于预算初值。策略级预算和预留的业务政策须显式配置，在账户协调器内原子检查和更新；所选 Risk 组件故障不得被绕过。

#### 7.6.2 共享合同与读写流程

1. Base 定义与传输无关的策略/账户身份、策略持仓视图、策略账户视图、分配及调整、账本状态、存储/查询端口；先与现有容器、中立 DTO 和 BT 既有策略账本子系统（G-14）盘点收敛。
2. SDK 实现可信订单绑定、成交去重、仓位和策略账户投影、资金调整及对账；同一持久化事务提交事件去重、相关仓位/账户变更及消费进度。持久化后向 Broker 提供同一版本的策略视图。
3. 分配、调拨、纠错及手工归属有稳定操作 ID、权限、原因、依据、前后版本与审计记录；重复操作幂等。
4. 策略视图通过已绑定策略身份和账户授权查询；账户级数据不默认广播给所有策略；客户端接收的是受控视图，不作为服务端账本的另一写入源。

#### 7.6.3 direct 与 Gateway 的装配、恢复和切换

| 项目 | direct：未选择 Gateway | Gateway：显式选择 |
| --- | --- | --- |
| 账户与账本 owner | 同一进程内由 SDK 与本地宿主装配一个协调器及持久账本。 | 服务端宿主装配同一个 SDK 协调器和账本；Gateway 提供命令路由和读视图。 |
| 策略访问 | BT Broker 通过 SDK 本地端口查询和订阅。 | BT Broker 通过接收端 SDK 与 Gateway 访问相同合同。 |
| 规则与结果 | 与 Gateway 使用相同规则；无可选组件强制依赖（INV-01）。 | 服务端为权威写入位置；连接故障不静默改用 direct（INV-02）。 |
| 重启恢复 | 从本地持久账本恢复关联、去重、预留和游标，核对账户与未决订单后恢复。 | 服务端按相同规则恢复；客户端重新取得快照及事件切点。 |

- 独立 direct 进程各自维护本地账本时不能互相感知预留；首期不支持把它们当成一个安全的多策略账户，相关多进程交易拒绝。
- 同一真实账户通过不同 route 或宿主别名同时接入时，以 provider 验证的账户及环境身份建立唯一协调/派发 fence；别名无法确定唯一时拒绝。
- direct 与 Gateway 互相切换时，**不能让两个 owner 同时处理同一账户**。先停止新命令并处理未决/UNKNOWN，保留身份、关联、去重、账本、预留、水位和审计历史，受控导入后与 provider 对账。存储 fencing 不能单独证明旧 owner 无法派单（INV-08）：必须证明旧 owner 及其 provider 会话失效，或每次实际派发都受对新旧 owner 强制生效的栅栏约束；否则 `NO-GO`。**切换状态机本身持久化**，每个提交点（QUIESCE、FENCE、RESTORE、SYNC、RECONCILE）前后崩溃都可幂等恢复。

#### 7.6.4 Backtrader 接口与兼容

- 策略侧的持仓、`close()`、目标仓位、策略资金/权益、Sizer、Analyzer、Observer 和相关通知使用同一策略作用域。`getposition()`、`getcash()`、`getvalue()` 的兼容方式在 60.01 盘点后确定；**以 BT 既有 `StrategyAccountBookPercentSizer`、`bind_strategy_account_book()` 为起点**（D60-07），不另建平行机制。
- BT Broker 提供区分清楚的策略视图和真实账户视图；策略身份由框架和 SDK 绑定（D60-06）。无策略上下文的调用、无预算或估值依据的字段返回不可用/错误，不静默退回账户总额——既有 Sizer 已是 fail-closed，可作为参照。
- 现有单策略、回测及外部调用的默认值和迁移影响在 60.01 单独决策；目标是切换 direct/Gateway 不需要重写策略。

## 8. Base 容器和 MessagePack v1 合同

### 8.1 唯一业务合同与对象边界

- `bt_api_base.containers` 是 Tick/Ticker、Bar、订单、逐笔成交和持仓的公共语义入口。优先重构现有容器或收敛现有中立类型（含 G-13 的多副本合同），保留场所子类扩展，不建立 Gateway 专用的平行业务对象。
- provider 从原生消息一次解析/归一化，在**发布冻结点**（D60-12）前完成全部变异；容器在构造期或冻结点前完成初始化（D60-13）。SDK 和 BT 同进程消费同一已冻结对象；来源、消费游标、Feed 本地质量和策略状态按各自 owner 保存。
- Gateway 跨进程将同一合同编码为 MessagePack，接收端一次解码为对应 Base 标准容器；不复制第二份业务字段。数据线写入、Feed 聚合和 Broker 状态/通知快照仍是必要投影。
- 标准字段及场所扩展有明确命名空间；扩展不能覆盖标准字段或冒充可信身份。子类是否在接收端保留，由受控的消息类型与 provider 注册决定，不根据消息里的模块名动态导入。只消费公共字段时可解码为公开标准实现，但**影响资格判断的字段（D60-11）不得丢弃**。

落点：Base `containers/` 持有业务字段和类型合同；Base 可定义不绑定具体库的序列化协议及 schema；MessagePack 具体 codec 由共享的可选实现提供，SDK 客户端和 Gateway 复用同一实现；ZMQ 连接、认证和收发由 transport 持有。实际路径及是否独立发行在 60.01/60.02 确定。

### 8.2 MessagePack 数据格式

v1 使用**具名字段 map**；`schema_id`、`major`、`minor`、`kind`、流元数据及业务数据的键名和类型在 Base 合同中集中定义。结构示意（非现有 API）：

```text
{
  schema_id, major, minor, kind,
  stream: {stream_id, epoch, sequence},
  source: {provider, venue, route 或授权视图引用},
  event_time, receive_time, time_quality,
  data: 标准容器字段及显式场所扩展
}
```

| 项目 | v1 约定与待定项 |
| --- | --- |
| 消息类别 | Tick/Ticker、Bar、Order、单笔 Fill、Position，以及区分的账户快照/变更和命令/回执；报价、逐笔成交和 Bar 不混为同一类型。 |
| 数值 | 价格、数量和费用用规范十进制字符串。**文法冻结**：拒绝 NaN/Infinity；规定负零、指数形式、前导零、尾零的规范化和等价关系；逐字段规定范围和最大有效位，超大精度/指数在解析前即拒绝。原生只提供二进制浮点时不声称恢复十进制精度。BT 数据线按合同投影，并评估对策略回归计数的影响（G-24）。 |
| 时间 | UTC 事件时间与接收时间分别表达；推荐 UTC epoch 纳秒整数，原始精度不足时标明精度，不凭默认值补造时间。 |
| 缺失和未知 | 缺失、已知空值及明确的零可区分（INV-04）。BT 侧读取须避免 `_tick_value` 把未知替换为默认值（G-08）。 |
| 严格解码 | 只接受恰好一个完整对象（拒绝尾随字节和拼接对象）；拒绝重复 map 键、非字符串键、非法 UTF-8 和未登记的 ext 类型。 |
| 进化 | major 不兼容时拒绝；minor 新增字段的忽略/保留/拒绝规则明确，影响订单、授权或解释的未知字段不得静默忽略。连接握手校验 schema 版本、扩展注册表和关键字段表的摘要，不一致则拒绝。 |
| 序号 | `sequence` 固定位宽和初值；耗尽前原子切换 epoch 并重新同步，禁止同代回绕。 |
| 安全和容量 | 限制消息字节、嵌套深度、字段/数组长度和整数范围；按已认证客户端与账户/订阅权限处理，topic 只用于过滤。禁止 pickle 或按消息声明的类路径反序列化。 |

编码器只编码已冻结的容器；解码器用受控的 `schema_id`/版本/类型注册直接构建标准容器。是否能省去中间字典取决于所选实现，须用分配计数和端到端基准证明。

**Python 与依赖约束**：不在计划中写死版本字面量（G-23）。60.01 分别记录 Base/SDK/provider/Gateway/transport/BT 的源码声明、已安装元数据和实际可导入解释器，以及平台、wheel 和依赖求解（含 numpy、pandas、pyarrow）；任何不一致为阻塞。codec 候选按其**实际版本的发行元数据**评估，不得使声明支持更低版本的 Base 核心无条件依赖它。

### 8.3 ZMQ 通道与恢复合同

- **行情**：ZMQ PUB/SUB，两帧分别承载有终止分隔的 topic 和 MessagePack 消息。topic 不是授权机制：按授权范围分区，确保无权客户端不能收到或解密；无法证明时用认证的点对点流。按可见订阅分区维护 `stream_id`、`epoch` 和连续 `sequence`。**接收端重算 topic、授权 scope 与 stream 绑定，不匹配即拒绝并重新同步**。每个 stream 强制发布者 fence，发布者接管时更换 epoch，订阅端拒绝旧代际。慢消费者、HWM、断线、丢帧和代际变化通过序列和认证控制通道水位发现。
- **账户观察与命令**：受认证的 ROUTER/DEALER 请求/响应；账户事件按账户及授权视图有界持久化，支持快照、按游标重放及消费者进度。命令和结果不依赖不可靠广播作为唯一来源。
- **快照衔接**：先建立订阅缓冲，取得完整快照及一致切点，按游标重放到明确水位，与实时事件合并去重。缓冲溢出、日志过期、epoch 改变或无法建立切点时停止可信推进并重新快照/对账。
- **日志保留与慢消费者**：逐消费者跟踪未确认游标；长期不 ACK 的消费者被隔离并停止推进，不静默删除其未确认事件，也不阻塞其他消费者。
- **ACK**：在自身状态、去重信息和游标一致持久化后 ACK。ACK 绑定消费者、run、epoch 和游标；服务端只持久化单调进度，拒绝旧代际的迟到 ACK。
- **命令**：稳定 ID、语义指纹一致性检查（§7.4）和持久化派发状态；异常或超时保持 UNKNOWN。不承诺全链 exactly-once。
- **滚动升级**：新旧 client/server 共存时按能力协商；不兼容组合在写命令前拒绝；升级不改变稳定命令身份，恢复后按原身份查询并保持单一派发 owner。
- **依赖和认证**：ZMQ 是可选传输（INV-01）；跨机/跨用户采用明确的认证、加密及账户/频道授权方案。
- **授权负例矩阵**：通配符订阅、跨账户快照/重放、越权策略视图、伪造 route/strategy 命令、撤权后重连，逐接口断言无权端收不到且无法解密，错误与日志不泄露内容。
