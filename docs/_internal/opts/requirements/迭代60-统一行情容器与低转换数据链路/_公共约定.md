## 1. 状态术语

| 术语 | 含义 | 谁可以宣告 | 之后的流程 |
| --- | --- | --- | --- |
| `NOT_STARTED` | 步骤或检查尚未开始。 | 执行者 | 开始实施后改为 `IN_PROGRESS`。 |
| `IN_PROGRESS` | 正在实施；不代表任何检查通过。 | 执行者 | 完成后进入 `REVIEW_PENDING`，受阻时进入 `BLOCKED`。 |
| `BLOCKED` | 必需前置、决策、环境或证据缺失，无法继续。必须写明阻塞项 ID、owner 和解除条件。 | 执行者 | 解除后回到 `IN_PROGRESS`；不得跳过阻塞进入下一步。 |
| `NOT_RUN` | 检查已计划但未执行（含环境不可用、无授权）。不是失败，也不是通过。 | 执行者 | 必需检查为 `NOT_RUN` 时，步骤不得标记完成。 |
| `PASS` / `FAIL` | 检查已执行，并附证据等级、版本和环境。 | 执行者 | `FAIL` 须修复或登记为已接受的偏差（需用户确认）。 |
| `NOT_COMPARABLE` | 两组结果的合同、精度、校验强度或输入不同，不能比较。 | 执行者提出，用户审阅确认 | 不得据此宣称提速、对等或一致。 |
| `UNKNOWN` | 运行时事实不可证明（订单结果、来源、账户状态等）。属于数据和状态语义，不是文档状态。 | 系统运行时 | 按原身份查询或对账；不得默认为零、成功或失败。 |
| `NO-GO` | 关键安全条件（如旧 owner 失效、阈值）无法证明，决定不继续该能力。 | 执行者提出，用户确认 | 保持原路径或能力不可用，并记录理由。 |
| `REVIEW_PENDING` | 步骤交付已提交，等待用户审阅。 | 执行者 | 用户明确同意后为 `ACCEPTED`；否则返回 `IN_PROGRESS`。 |
| `ACCEPTED` | 用户已明确同意该步骤交付，仅限其声明范围。 | **仅用户** | 才允许进入下一步。 |
| `REOPENED` | 已接受的步骤或决策因后续变化需要重做。须列出失效的需求、设计、代码、测试和性能证据。 | 执行者提出，用户确认 | 回到 `IN_PROGRESS`，后续依赖步骤同时标注受影响。 |

步骤状态流转：`NOT_STARTED → IN_PROGRESS → (BLOCKED ↔ IN_PROGRESS) → REVIEW_PENDING → ACCEPTED`；任意已接受步骤可进入 `REOPENED`。

## 4. 证据等级

每条检查结果必须标明以下之一，且不得以低等级替代高等级：

1. `STATIC`：源码/文档静态核对（附 commit 与文件:行）。
2. `UNIT` / `FAKE`：单元或隔离替身。
3. `INTEGRATION_SIM`：多组件模拟集成。
4. `PACKAGE`：隔离安装的 wheel/sdist。必须附当次“逐包导入落点表”快照（包名 → `__file__` → 所属源码树 → 分支/HEAD → 安装版本），否则降级为 `STATIC`。
5. `PERF`：按预先登记口径的性能测量。
6. `REAL_SOURCE`：真实行情来源（需授权）。
7. `REAL_ACCOUNT`：真实账户读取或交易（需另行明确授权）。

## 5. 能力解锁状态

不以“某步骤完成”推断能力可用。以下能力分别维护状态，解锁证据须绑定 provider、账户环境、版本、部署形态和授权范围；`FAKE`/`INTEGRATION_SIM` 证据不能解锁 `REAL_ACCOUNT` 能力。

| 能力 | 可能状态 |
| --- | --- |
| direct 行情（逐场所） | `PLANNED` → `CONTROLLED_ONLY` → `READY_FOR_AUTHORIZED_VALIDATION` → `ACCEPTED_FOR_DECLARED_SCOPE` |
| direct 单策略订单/成交 | 同上 |
| 策略归属账本 | 同上 |
| 策略预算/账户视图 | 同上 |
| Gateway 行情 | 同上 |
| Gateway 命令 | 同上 |
| 多进程接管/模式切换 | 同上 |
| 真实多策略交易 | 60.01–60.09 期间固定为 `CONTROLLED_ONLY`；只有 60.10 综合恢复/切换验收、对应 provider 能力和另行账户授权全部具备后才可提升。 |

## 6. 通用执行规则

1. 每步开始前核对各仓 checkout、HEAD、dirty 和调用者，确定唯一状态 owner、生命周期和相邻步骤接口。
2. 来源、授权、时间、账户事实或结果不确定时保持 `UNKNOWN`/不可用（INV-04、INV-06）。
3. 每步只交付本步范围；不提前宣称后续能力完成。
4. 每步交付说明包括：范围、仓库/分支/commit、diff 摘要、追踪表、检查结果与证据等级、兼容和破坏性变化、未决项；状态为 `REVIEW_PENDING`，用户 `ACCEPTED` 后才进入下一步。
5. 必需检查为 `NOT_RUN`/`BLOCKED` 时不得标记完成。
6. 真实账户读写须另有有效明确授权；本计划不授权真实账户操作、重跑已消费调用或处置 retained host。
7. 故障注入只用受控进程崩溃、持久化/文件系统/网络故障模拟；不对真实主机断电，不 kill retained host。
8. **性能 NO-GO**：若移除复制或改变路径后，按预登记口径的端到端指标未改善或恶化，保留原路径并记录“该环节不是瓶颈”，不得为完成计划删除已验证安全的隔离。
9. **决策变更**：已 `DECIDED` 的 `D60-nn` 或步骤合同发生变化时，标记受影响步骤为 `REOPENED`，重做相应 direct、codec、兼容和对等验收。
10. **文档同步**：改变职责、公开 API 或依赖的步骤，同时交付 AGENTS.md、职责规范、相关 README、迁移说明和导航的更新（或说明为何不需要）。
11. **跨仓提交**：在各子模块 `dev` 上开发（D60-03），先子仓提交，再更新父仓 gitlink；不得在 detached HEAD 上提交。
12. **策略回归**：涉及 Feed、数值表示、多 Feed 时钟、minperiod 或策略接口的步骤，出口门包含 `make test-strategies`，并在 Python 3.11（numpy 1.x）和 3.13（numpy 2.x）各运行一次。
