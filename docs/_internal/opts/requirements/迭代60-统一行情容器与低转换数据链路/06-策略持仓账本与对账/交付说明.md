## 2. 新增能力：按策略的可平量准入（真实缺口）

既有实现把“平仓数量不能超过持仓”交给可注入的 Risk 准入门，但没有一个中立的、按策略计算的实现。缺少它时，策略 A 可以平掉策略 B 的持仓，两个并发平仓也可能超卖。

| 仓库 / 提交 | 变更 |
| --- | --- |
| `bt_api_execution` `5afdf6c` | 新增 `StrategyCloseCapacityGate`（`strategy_close_capacity.py`）：平仓意图（`CLOSE*` 或 `reduce_only`）的数量必须 ≤ `基线 + 本策略已确认成交 − 本策略未终结平仓单的剩余量（含 UNKNOWN）− 本进程已授予但未落库的预留`。每次都从持久事实重算，因此重启后结果一致；开仓不在此限制，可选的 `inner` 门（如共享 Risk）照常调用。`SqliteExecutionStore.list_scope_intents()` 提供它所需的只读投影。 |

## 7. 2026-11-03 续：标准通知恢复（G3）与迟到手续费修正（F5）（用户审阅 PENDING）

本节为当前工作树（未提交）的实现记录，不是验收结论；与上文冲突处以本节为准。

**G3 标准 `notify_order`/`notify_trade` 恢复**

- 新增 `backtrader.execution.strategy_notification_outbox.StrategyNotificationJournal`：每个策略一个有序 SQLite 日志（WAL + `synchronous=FULL`），追加和 ACK 均为 O(1) 单行操作，每行带 digest（读取时校验）；已 ACK 行超过 `retain_acked`（默认 1024）后分批压缩，文件行数上界约为 `max_pending + retain_acked + 256`。旧 `StrategyNotificationOutbox`（全历史审计）保留但不再用于通知路径。本机记录：追加+ACK 每对约 200–400 µs（单元测试打印，非性能门槛）。
- `BtApiBroker.bind_strategy_notification_recovery(strategy, directory, deployment_ref=..., generation=None, resync=False)`（显式 opt-in）：订单通知在 Broker `notify` 入队时先写日志；Trade 在 Strategy 由成交生成时（`_addnotification` 返回后）写日志；迟到手续费修正在派发前写日志；均在策略回调正常返回后才 ACK。重启后按日志顺序重放未 ACK 项。
- 稳定 ID：由日志 generation + 账本 intent id（否则 SDK client/external order id，否则进程内本地 ref）+ 状态 + 累计成交量/价/手续费 + 修正次数派生；Trade ID 由产生它的订单通知 ID 派生；修正 ID 由订单身份 + 修正序号派生。投递对象带 `notification_id` 与 `replayed`（该 ID 此前已写入过：重放或重复），策略按 `notification_id` 去重。至少一次，不是恰好一次。
- generation：direct 绑定 SDK 账本的 journal generation；其他路径须显式传 `generation`。不同 generation 抛 `StrategyNotificationRecoveryError("RESYNC_REQUIRED")`，状态 `strategy_notification_recovery_state()` 为 `RESYNC_REQUIRED`，不重放；`resync=True` 把旧日志改名为 `*.resync-N` 保留后重新开始。
- 重建对象：`RecoveredOrder`/`RecoveredTrade` 只读，含状态、方向、数量、价格、exectype、executed size/price/value/comm、ref、intent/provider id、`recovered = replayed = True`。**不重建**：data feed（仅 `data_name`）、comminfo、`executed.exbits`、`created`、父子/OCO 关联、Trade history/barlen；重放订单不可撤单；旧进程 ref 可能与新订单 ref 相同，须按 `notification_id` 或 intent id 关联。修正只重放给 Strategy 的 `notify_fee_correction`（analyzer/observer 重启为空）。订单已写日志而 Trade 未写日志即崩溃时，只重放订单（含成交），不重放 Trade。

**F5 迟到手续费 fee-only 修正**

- 选择专用钩子 `notify_fee_correction(order, trade, delta, currency)`（Strategy、其 analyzers、observers），不重复 `notify_trade`，避免 TradeAnalyzer 等对已关闭 Trade 重复计数。

## 8. 验收后修复：重启后才到达的迟到手续费（2026-11-04）

本节只记录源码与本地测试进展，不是验收结论，不改变任何步骤的验收状态。证据等级：UNIT/FAKE 与 INTEGRATION_SIM（临时 SQLite、spawn 子进程 `os._exit`、同进程 co-located Gateway 读服务）；真实 provider、账户与 Gateway 部署 NOT_RUN。

**缺口**：§7 的 fee-only 修正依赖进程内存（`_applied_fill_fees`、`_seen_trade_ids`、活订单）。进程重启后，上一进程已应用成交的迟到手续费：direct 模式找不到订单，按 unmatched 延迟（实际丢失）；Gateway 模式终态订单计为 orphaned；Gateway 重建的未终态订单收到上一进程成交的更正时，被当成第二笔成交（伪造成交、持仓错误），且重建订单未恢复 `provider_fee_totals`。

**修复**

- **已应用成交索引（`StrategyNotificationJournal` schema v3，v2 文件打开时原地升级）**：新表 `journal_order`（订单身份 → 最近一次写日志的订单记录与按币种的 provider 累计手续费）、`journal_fill`（成交事实 → 订单身份、数量、价格、已记手续费与币种）、`journal_link`/`journal_trade`（订单 → 它最后更新的 Trade 快照）。与所属通知在**同一事务**写入；索引行带摘要，读取时校验（篡改为 `STORE_CORRUPT`）。有界：保留 `retain_fee_orders`（默认 10 000）个最近更新的订单及其成交，摊销压缩；被压缩订单的更正不再被识别。只索引带 provider/client order id 的成交（进程内 ref 重启后不能识别成交）。
- **写入顺序**：Broker 在 `notify` 时（Strategy 交接之前）把自上次通知以来记下的手续费更正、订单通知和索引更新写在一个事务里（原来更正在 Strategy 交接时才写日志）；更正条目的 id 即更正身份，重复追加时保留首次快照（`keep_existing`）；Strategy 交接后写 Trade 快照与订单关联。
- **重启后的入口 `_apply_durable_fill_fee`**（direct：`_lookup_order` 找不到订单时；Gateway：终态订单的成交事件）：数量/价格不同或无手续费→忽略（绝不伪造成交）；同一费用→忽略（幂等）；更低、换币种或原成交无费用→`fee_fenced`：禁止交易、`freeze_openings("fill_fee_correction_unprojectable")`，原因见 `BtApiBroker.fee_correction_fence()`。有效更正：**先账本**——用 SDK 新增只读 `SqliteStrategyLedger.execution_totals(intent_id)` 比较：账本已等于目标值→跳过（上次崩溃已入账）；等于日志记录→以不变数量做 fee-only `apply_execution`；其他→`ledger_fee_diverged` fail-closed；**再**一个日志事务写更正、修正后的订单通知与索引。Cerebro 交接时投递：Strategy `notify_fee_correction(order, trade, delta, currency)` 一次，`order` 为只读 `RecoveredOrder`（原 ref、intent id、最后状态、executed size/price、修正后佣金，`recovered=True`、`replayed=False`），`trade` 为该订单最后更新的 Trade 的只读 `RecoveredTrade`（commission/pnlcomm 已修正），没有记录时为 `None`；随后 `notify_order(同一订单快照)`。各自在回调返回后 ACK，崩溃后按原 id 重放。
- **只调用 Strategy**：analyzer/observer 重启后为空，从未计入上一进程的 Trade，且 Trade ref 按进程重新计数（TradeAnalyzer 按 ref 记桶，传入旧 Trade 会改错桶），因此不调用它们；进程内（不重启）路径不变，仍调用 Strategy、analyzer、observer。
- **direct 模式未终态订单**：重启后不重建订单，其更正同样走此路径（订单快照状态为 `Partial`）；该订单之后的新成交仍为 unmatched（既有限制，未改）。
- **service 模式核对**：终态（`FILLED`）订单的 `provider_commission_evidence` 恢复回执经 `_apply_service_execution_recovery_event` → `_apply_fee_only_correction` → `notify` → Strategy `_addnotification` 调用 `notify_fee_correction`（新增单元测试证明，回执在投递后 ACK）。前提是该 intent 的订单已绑定到 `_recovery_orders_by_intent`；V1 重启后未重新绑定的终态订单，其回执保持 pending（不丢、不认领），宿主侧账本由执行日志投影，已含该费用。
- **SDK 改动（最小）**：`bt_api_py.strategy_ledger.SqliteStrategyLedger.execution_totals`（只读，返回累计成交量与按币种累计手续费），不改变既有写路径。
