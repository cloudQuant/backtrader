## 2. 新增能力：按策略的可平量准入（真实缺口）

既有实现把“平仓数量不能超过持仓”交给可注入的 Risk 准入门，但没有一个中立的、按策略计算的实现。缺少它时，策略 A 可以平掉策略 B 的持仓，两个并发平仓也可能超卖。

| 仓库 / 提交 | 变更 |
| --- | --- |
| `bt_api_execution` `5afdf6c` | 新增 `StrategyCloseCapacityGate`（`strategy_close_capacity.py`）：平仓意图（`CLOSE*` 或 `reduce_only`）的数量必须 ≤ `基线 + 本策略已确认成交 − 本策略未终结平仓单的剩余量（含 UNKNOWN）− 本进程已授予但未落库的预留`。每次都从持久事实重算，因此重启后结果一致；开仓不在此限制，可选的 `inner` 门（如共享 Risk）照常调用。`SqliteExecutionStore.list_scope_intents()` 提供它所需的只读投影。 |

## 7. 2026-11-03 续：标准通知恢复（G3）与迟到手续费修正（F5）（用户审阅 PENDING）

本节为当前工作树（未提交）的实现记录，不是验收结论；与上文冲突处以本节为准。

**G3 标准 `notify_order`/`notify_trade` 恢复**

- 新增 `backtrader.execution.strategy_notification_outbox.StrategyNotificationJournal`：每个策略一个有序 SQLite 日志（WAL + `synchronous=FULL`），追加和 ACK 均为 O(1) 单行操作，每行带 digest（读取时校验）；已 ACK 行超过 `retain_acked`（默认 1024）后分批压缩，文件行数上界约为 `max_pending + retain_acked + 256`。旧 `StrategyNotificationOutbox`（全历史审计）保留但不再用于通知路径。本机记录：追加+ACK 每对约 200–400 µs（单元测试打印，非性能门槛）。
- `BtApiBroker.bind_strategy_notification_recovery(strategy, directory, deployment_ref=..., generation=None, resync=False)`（显式 opt-in）：订单通知在 Broker `notify` 入队时先写日志；Trade 在 Strategy 由成交生成时（`_addnotification` 返回后）写日志；迟到手续费修正在派发前写日志；均在策略回调正常返回后才 ACK。重启后按日志顺序重放未 ACK 项。
- 稳定 ID：由日志 generation + 账本 intent id（否则 SDK client/external order id，否则进程内本地 ref）+ 状态 + 累计成交量/价/手续费 + 修正次数派生；Trade ID 由产生它的订单通知 ID 派生；修正 ID 由订单身份 + 修正序号派生。投递对象带 `notification_id` 与 `replayed`（该 ID 此前已写入过：重放或重复），策略按 `notification_id` 去重。至少一次，不是恰好一次。
- generation：direct 绑定 SDK 账本的 journal generation；其他路径须显式传 `generation`。不同 generation 抛 `StrategyNotificationRecoveryError("RESYNC_REQUIRED")`，状态 `strategy_notification_recovery_state()` 为 `RESYNC_REQUIRED`，不重放；`resync=True` 把旧日志改名为 `*.resync-N` 保留后重新开始。
- 重建对象：`RecoveredOrder`/`RecoveredTrade` 只读，含状态、方向、数量、价格、exectype、executed size/price/value/comm、ref、intent/provider id、`recovered = replayed = True`。**不重建**：data feed（仅 `data_name`）、comminfo、`executed.exbits`、`created`、父子/OCO 关联、Trade history/barlen；重放订单不可撤单；旧进程 ref 可能与新订单 ref 相同，须按 `notification_id` 或 intent id 关联。修正只重放给 Strategy 的 `notify_fee_correction`（analyzer/observer 重启为空）。订单已写日志而 Trade 未写日志即崩溃时，只重放订单（含成交），不重放 Trade。

**F5 迟到手续费 fee-only 修正**

- 选择专用钩子 `notify_fee_correction(order, trade, delta, currency)`（Strategy、其 analyzers、observers），不重复 `notify_trade`，避免 TradeAnalyzer 等对已关闭 Trade 重复计数。
- service-recovery 累计回报：沿用 `_apply_fee_only_correction`，入账逻辑抽为 `_book_fee_correction`。
- 新增 direct 入口：provider 以相同 fill id、相同数量和价格重报已应用成交且手续费更高（同币种）时，按差额修正订单佣金、账本手续费（持久化）、Trade `commission/pnlcomm` 并调用钩子；相同手续费幂等忽略；更低、币种不同或原成交无手续费时标记 `PNL_INCOMPLETE`、`fee_correction_error`，冻结开仓并停止交易（`fee_fenced`）；数量/价格不同的重复仍忽略，不伪造零量成交。
- 修复缺陷：`_execution_commissions` 两处调用位置参数颠倒，纯开仓成交的 SDK 手续费被记为平仓佣金，Trade 佣金为 0。现改为关键字参数。
- Analyzer：内置 analyzer **均未实现** `notify_fee_correction`（TradeAnalyzer、Returns 等已计入的数值不随修正变化）；测试演示 TradeAnalyzer 子类通过钩子修正 `pnl.net.total`。内置 analyzer 的修正处理仍 OPEN（不在本工作包可改文件范围）。

**Gateway**：`generation=` 显式路径让经 `BtApiBroker.notify` 到达的 Gateway/service 订单通知走同一日志（INTEGRATION_SIM，fake Store，无 Gateway 进程）。SDK `ServiceAccountConsumer` 的游标提交与 BT 通知日志之间的“先落盘再 ACK”链路 **OPEN**：BT 当前没有消费 Gateway 账户事件的组件，也没有把 Gateway 账户事件映射为 BT Order 的投影，需另行设计。
