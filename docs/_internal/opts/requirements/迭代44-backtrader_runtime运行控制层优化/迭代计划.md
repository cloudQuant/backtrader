状态：**需求与行为设计已定，待开发**

范围修订：2026-10-13，按用户要求收敛为参数与配置校验。

定稿决策：2026-10-13，用户确认以下三项：使用相关组件的旧配置必须迁移到 v5；必需组件缺少配置块时报错；覆盖已登记 runtime 的策略参数类型和已确定的范围约束。具体规则见第 4、5 节。R1 负责将现有字段与接口整理为开发规格，不重新决定这些行为。

本轮是独立的迭代 44，承接当前 runtime 和迭代 43 的示例入口。迭代 41 的历史合同与证据仅作参考；本轮任务、验收和提交记录归入本目录。

## 1. 目标与范围

让用户在运行前发现配置错误，并获得明确的字段位置、原因和修改提示。校验覆盖 runtime 自身参数，以及 `bt_api_py` 的四个子包：`bt_api_risk`、`bt_api_monitor`、`bt_api_execution`、`bt_api_gateway`。

本轮交付限定为：

1. 字段、类型、必填项、默认值、枚举、取值范围和组合约束校验。
2. 配置与已登记 runtime、mode、preset、组件的兼容性校验。
3. 四个子包各自的配置校验，以及已选组件之间的配置一致性校验。
4. 在现有 `validate`、`doctor` 和 `run` 启动前接入相同的校验逻辑，输出稳定、脱敏的错误信息。

风控实现仍归 `bt_api_risk`。本轮只检查其配置及配置引用，不开发风险算法，不调整风险决策行为。原草案中的下单链路改造、并发风险预留、runner 生命周期扩展和进程监督开发已移出本轮范围。

**配置校验通过只表示配置满足约束。** 它不证明服务已连接、账户状态有效、订单风控已生效或当前运行入口可以交易；现有运行准入与 live 限制继续生效。

## 2. 公开源码核对与当前缺口

本节依据公开源码和公开配置定义整理，未读取真实私有配置，也未执行账户或服务连接。

| 当前情况 | 本轮需要解决的配置问题 |
|---|---|
| `backtrader_runtime/config.py` 使用 schema v4，`runtime` 子块只接受 `mode`、`preset`，根字段严格受限 | 明确新增组件配置的版本和兼容方式；不能直接往 v4 中添加 `components` 或 `risk_profile_id` |
| runtime 已检查 capability 声明、包可发现性及可信来源 | 这些检查不能替代四个包的参数语义校验，需要接入各包的纯校验接口 |
| `bt_api_risk` 已有 `RiskPolicy` 等类型及字段约束 | 复用现有约束，补齐从配置到这些约束的校验入口，避免复制风险规则 |
| `bt_api_monitor/config.py` 的 `MonitoringConfig` 当前按已知键读取 kwargs，未知键会被忽略；缺少完整类型和范围校验 | 明确拒绝拼错字段和非法值；将校验与 `setup_monitoring()` 的服务启动、日志初始化等行为分离 |
| execution、gateway 已有构造参数和合同，但不能假定四个包已有统一的配置 API | 逐包盘点现有公开接口；缺失时仅补必要的配置类型与纯校验函数 |
| 示例 `entry.tier` 与 runtime `mode/preset` 分别控制不同入口 | 保留各自配置边界，明确合法组合；不把 `entry.tier` 当作 runtime 模式或授权字段 |

当前公开源码入口：Backtrader 的 `config.py`、`policy.py`、`registry.py`、`capability_imports.py`；SDK 的 `bt_api_risk/core/admission.py`、`bt_api_monitor/config.py`，以及 execution、gateway 的公开接口与 README。实施时以各仓已提交版本重新确认字段清单。

## 3. 校验职责

| 组件 | 本轮职责 |
|---|---|
| `backtrader_runtime` | 校验 runtime 配置外层结构和策略参数；根据登记的 profile 选择允许且需要的组件；调用校验接口；汇总错误；在启动前拒绝无效配置 |
| `bt_api_risk` | 拥有风险配置的字段定义、默认值、类型、取值范围及配置内约束；继续独立负责风险实现 |
| `bt_api_monitor` | 拥有监控配置的字段定义、类型、范围和组合约束 |
| `bt_api_execution` | 拥有执行组件配置的字段定义、类型、范围和组合约束 |
| `bt_api_gateway` | 拥有网关配置的字段定义、类型、范围和组合约束 |
| `bt_api_py` 配置集成层 | 复用各包校验结果，检查已装配组件之间的配置引用和兼容关系；runtime 调用该集成接口 |

字段规则由所属包维护。runtime 不维护另一份风险限额规则、监控默认值或执行参数范围。集成层只增加跨包配置比较，不增加交易服务、运行状态管理或新执行框架。

## 4. 具体校验内容

以下是字段盘点和验收的范围。已有字段直接复用；对已有功能，仅补充表达其现有公开配置或装配参数所必需的字段。R1 必须列明字段与现有消费者的对应关系，不开放新业务功能，也不把内部实现参数全部变成用户配置。

| 范围 | 参数与配置检查 | 典型错误 |
|---|---|---|
| Runtime / 策略参数 | schema 版本、strategy/runtime 登记、mode 与 preset 组合、允许的参数名、参数类型、默认值和策略声明的范围 | 不支持的版本、未知字段、模式冲突、整数被写成布尔值、拼错策略参数 |
| `bt_api_risk` | 现有 `RiskPolicy` 的 `policy_id`、`max_increase_notional`、`max_increase_count`、`permit_ttl_seconds`、`require_strategy_allocation`、`notional_unit` 等配置约束；策略引用格式及本地可解析性 | 空策略标识、负限额、非有限数值、非正 TTL、单位不符合包合同、引用无法解析 |
| `bt_api_monitor` | 采集/健康检查间隔与超时、端口范围、日志级别、日志容量/备份数、传输枚举、ELK 等可选功能的必填项、路径和凭据引用格式 | 间隔为零或负数、端口越界、错误日志级别、未知字段、开启可选项后缺少必要配置 |
| `bt_api_execution` | 已公开的执行模式、身份和风险策略引用、journal/outbox 配置、超时/租约参数及其现有组合约束 | 缺少必要引用、配置类型错误、非法超时、普通受管配置使用仅供测试的 `allow_unprotected` 选项 |
| `bt_api_gateway` | 已公开的路由/作用域配置、协议版本、writer authority 与 journal 配置关联、租约参数；启用配套 transport 时检查其配置引用 | 协议不兼容、作用域引用冲突、缺失所需配置、router 与 authority 未指向合同要求的同一存储 |

`bt_api_gateway` 核心包不启动 socket 服务。本轮检查 gateway 对已有 transport 的配置引用及兼容关系；可复用 transport 已有纯校验接口，但不新增 transport 配置体系或网络服务。未实际检查的 transport 内部设置不得报告为已通过四包校验。

### 4.1 跨包一致性

仅检查配置中能够静态确定、且已有合同要求的关系：

- risk 与 execution 引用的策略、账户作用域、环境和计价单位是否兼容。
- gateway 与 execution 的路由、作用域和协议配置是否匹配。
- execution 与 monitor 的事件/outbox 引用、schema 版本和读写角色是否兼容。
- 当前 profile 允许的组件与所提供配置是否一致；只读 profile 不得因组件配置获得写权限。
- 对确实要求共用存储的组件检查路径与可确定的文件身份；不将要求隔离的存储强行合并。重复声明的监听地址和端口可以报告静态冲突，但不探测端口是否被占用。
- 超时、TTL、租约之间仅执行所属包已定义的约束，不凭 runtime 自行设定比例或风险阈值。

缺少账户实时数据、服务连接状态、余额、持仓、行情等，均不在本轮配置校验范围内。外部策略服务中的引用只检查格式与必要配置，不宣称远端对象存在。

### 4.2 按需校验

- 所选 profile 必需的组件：必须显式提供配置块、可用校验器和兼容版本；缺少整个块即报错，不能用默认值生成该块。
- 配置块存在时，仅省略的可选字段使用所属包默认值。省略必填字段仍报错；空映射不能绕过必填项，`null` 也不代表使用默认值。
- profile 允许且用户明确配置的可选组件：完整校验，错误不能被静默忽略。
- profile 不允许的组件配置：报告配置冲突，不通过配置自动扩大 capability。
- 未使用且未配置的组件：标记 `NOT_REQUIRED`，不要求安装。例如普通本地回测不应强制安装 gateway。
- `paper` 与 `sandbox` 分别按现有 policy 校验；sandbox 的特殊审批合同继续由登记项约束，不因配置校验通过新增写能力。

组件是否实际需要或已启用，由所选 profile 和代码登记的装配信息决定。仅安装了某个包，或登记项允许但未使用该能力，不等于启用了该组件；配置中的 `enabled` 或任意模块路径不能自行授予能力。

### 4.3 策略参数声明

本轮覆盖实施基线中所有已登记 runtime 的策略参数。R1 建立逐项清单，在代码登记项中绑定静态参数 schema，声明字段类型、是否必填、默认值及已有的枚举/范围/组合约束。类型依据实际参数消费者的公开合同确定，不能仅按默认值猜测；没有业务依据的范围不自行添加。

校验时读取该静态声明，不实例化策略、不导入策略模块来探测参数。未知参数拒绝；必填字段缺失拒绝；仅声明了默认值的可选参数可以补默认值。未提供声明的已登记参数属于开发缺口，不能以跳过检查完成验收。任意未登记策略不纳入本轮。

v4 与 v5 均执行这些参数约束。保留 v4 文件格式不意味着继续接受过去未被发现的类型或范围错误。

## 5. 配置与接口兼容

### 5.1 配置版本

新版采用 `config_schema_version: 5`。在单份 runtime `config.yaml` 中增加 `components` 映射，键限于 `risk`、`monitor`、`execution`、`gateway`；每个组件块只包含必填的整数 `config_schema_version` 和映射 `settings`。本轮新增包级配置合同的初始版本为 1，后续不支持的版本明确拒绝。根层其他字段沿用原有归属与限制，新组件设置不能放入策略 `parameters`。

例如 `components.monitor.config_schema_version` 标识监控配置版本，`components.monitor.settings.prometheus_port` 存放端口。此处定义的是开发目标，当前代码尚未支持 v5。没有组件需要配置时可省略 `components` 或使用空映射；它不覆盖必需组件必须显式存在的规则。现有密钥引用和受保护配置读取规则继续适用，不因新增 `settings` 允许嵌入任意凭据。

兼容规则已由用户确定：

| 配置情况 | 升级后的处理 |
|---|---|
| v4，所选 profile 实际需要或已启用四包中的任一组件 | 拒绝并提示 `component_config_migration_required`，退出 2；必须迁移 v5 后完成新校验，不能降级为旧检查 |
| v4，不涉及这四类组件 | 保留 v4 文件格式，执行现有 runtime 校验及本轮增加的已登记策略参数校验；四包为 `NOT_REQUIRED` |
| v4 中加入 `components` 等 v5 字段 | 拒绝未知字段，提示采用正确版本；不静默当作 v5 解析 |
| v5 | 按实际所需和明确配置的组件完成全部适用检查；任一检查失败或无法完成都不能以部分通过继续启动 |

迁移只调整配置表示，不能自动改变 mode/preset、启用新组件或取得写权限。R1/R4 提供公开迁移样例和字段对照；校验命令不修改用户文件，开发和验收不读取真实私有配置。既有更早阶段的入口拒绝仍然有效。

示例 `entry.tier` 保持其独立入口职责，v4/v5 均不直接接受额外的 `entry` 根字段。R1 按实际入口登记记录合法组合；不新增模式映射或自动升降级规则。

### 5.2 默认值与覆盖

包级默认值由所属包统一提供，校验报告可展示允许公开的最终有效值及来源。保留当前 mode/preset 的控制权和 CLI 限制；本轮不增加任意环境变量覆盖、配置叠加或插件导入能力。密钥引用沿用既有机制。

字段规格必须区分缺失、`null`、空字符串和空映射；仅声明可空的字段接受 `null`。整数不接受布尔值，数值字段不隐式接受字符串，所有数值必须有限。金额等 Decimal 字段可显式声明十进制字符串表示，以保留精度；这是字段合同允许的格式，不是任意字符串转数值。具体允许表示和规范化方式必须列入字段表。

v5 新组件设置中的相对文件路径以 `config.yaml` 所在目录为基准，不随启动工作目录变化；v4 既有字段沿用其已定义路径语义。校验不创建目录、文件或数据库，也不通过试写探测权限。

### 5.3 包级纯校验接口

四个包应提供独立于服务启动的 `validate_config(settings, *, schema_version)` 入口，语义统一为返回是否有效、配置版本、标准化配置和结构化错误。这是待实现的接口合同，不是现有统一 API。可包装包内已有校验函数；内部类型由各包选择，通过 SDK 配置集成层适配为统一报告，子包不反向依赖 `backtrader_runtime`。

实现要求：

- 包括包初始化和依赖导入在内，不连接 provider、不启动线程/进程或 native SDK、不绑定端口、不创建或迁移数据库、不初始化生产日志。
- 不用 `setup_monitoring()`、创建执行服务或连接 gateway 来代替校验。
- runtime 通过代码登记的适配器选择校验器；配置不能指定任意模块或函数路径。
- 所需校验器不存在、版本不兼容或执行失败时，返回可区分的错误，不以“包能 import”代替通过。
- 标准化配置作为内部结果传递；公开输出采用字段允许列表，不能直接序列化完整配置对象。

新增严格规则应用于该配置校验入口和 runtime 的调用路径。本轮不顺带改变 SDK 其他直接调用者的构造行为。若包初始化本身妨碍纯校验，只做建立纯校验路径所必需的导入分离，并单独验收该边界。

## 6. 接入现有命令

```text
读取已允许的配置输入
  → runtime schema / 参数 / profile 校验
  → 确定所需组件及校验器版本
  → 各包配置校验
  → 跨包配置一致性校验
  → 返回配置校验报告
```

- `validate`：给出上述校验结果；任何必须完成的检查失败或无法完成时，不报告整体通过。
- `doctor`：复用结果，并结合现有依赖诊断显示缺失的包、校验器和兼容问题；在线就绪保持未检查。
- `run`：在现有 runner 启动前调用同一校验流程，使用这次通过的有效配置；不能因为之前运行过 `doctor` 就跳过当前校验。后续运行仍服从现有准入逻辑。

现有 `bootstrap` 的模板版本也须匹配所选 profile：需要四包组件时生成 v5 配置骨架，不再生成必定要求迁移的 v4 文件。无安全既有默认值的必填设置保留为明确的待填项，并报告配置尚未就绪；文件创建成功不等于配置校验通过。不自动填写账户或风险限额，不覆盖已有文件；这仅是配置生成兼容修正，不新增命令。

校验与后续配置消费必须共用同一份规范化结果，包括补齐的默认值。新增组件设置须进入已有配置封装、传递和一致性检查，不能出现“校验 A、实际使用 B”。R1 标明每个字段的实际消费位置；R3 只完成必要的配置传递接线，不修改订单业务或新增组件启动流程。集成验收用假 runner/配置消费者核对收到的值，无须启动真实服务。

不新增 run/status/stop 等生命周期协议。保留现有 CLI 退出码与已公开结果字段；新增组件诊断采用明确的报告版本，不静默改变旧字段含义。

### 结果与失败规则

新增校验报告版本固定为 1，并在现有 JSON 载荷中通过独立的 `validation` 字段提供；保留已有错误投影。组件/检查项状态采用：

| 状态 | 含义 | 对校验结果的影响 |
|---|---|---|
| `VALID` | 适用检查全部完成且通过 | 可计入整体通过 |
| `INVALID` | 字段、配置 schema 版本、迁移要求或跨包关系不合法 | 整体失败，退出 2 |
| `UNAVAILABLE` | 所需包/校验器不可用、不兼容或异常，未完成检查 | 整体失败，退出 2，不伪装成字段合法 |
| `NOT_REQUIRED` | 组件未使用且未配置 | 不要求安装，不阻断 |
| `NOT_CHECKED` | 前置结构错误等原因导致后续检查未执行 | 必需检查未完成，整体失败，退出 2 |

所有适用检查通过时，`validate`/`doctor` 退出 0；`run` 才能继续既有准入与运行流程，其最终结果仍取决于后续阶段。`doctor` 可以继续汇总诊断，但不能把必需检查失败降为退出 0。已经配置的可选组件缺包也不能整体通过；本轮不增加“只检查格式即可启动”的降级选项。

### 错误报告

错误至少包括 `component`、`field_path`、`reason_code` 和不含输入值的修改提示。可在解析成功后一次汇总多个独立字段错误，按组件、字段路径和原因码稳定排序；最多返回 100 条，截断时给出 `truncated=true`。结构不合法时停止依赖它的后续校验。

目标提示示例：

```text
component: monitor
field_path: components.monitor.settings.prometheus_port
reason_code: out_of_range
message: 端口必须是 1–65535 之间的整数。
```

该路径属于已确定的 v5 目标结构，当前实现尚不支持。报告可以解释合法范围，但不得回显密钥、账户标识、私有配置值、含凭据的 URL 或完整配置摘要。对现有允许读取的受保护配置，继续使用既有受限读取机制；离线校验不额外解析外部凭据或探测服务。公开字段也须明确列入输出允许列表。

### R1 必须形成的开发规格

1. **字段表**：字段路径、所属包、schema 版本、适用 profile、类型/单位、必填性、可空性、默认值、枚举/范围/组合约束、敏感级别、约束来源与实际消费者。包括全部已登记策略参数，不能用“等”代替实施清单。

3. **接口与用例映射**：包级返回类型到统一报告的映射、稳定原因码、每条约束的有效/无效/边界样例、v4→v5 迁移样例。所有样例使用公开合成值。

## 9. 参考原则与本轮排除项

Freqtrade 文档提供了启动时校验配置和查看有效配置的实践，可借鉴字段错误与有效值的可见性；本项目保留自身更严格的 mode/preset 控制规则，不直接照搬覆盖顺序。[Freqtrade Configuration](https://www.freqtrade.io/en/stable/configuration/)

NautilusTrader 的运行配置按组件组织，并显式声明连接、对账等超时参数。本轮只借鉴配置结构和参数合同；不引入其节点生命周期或连接流程。[NautilusTrader Live Configuration](https://nautilustrader.io/docs/latest/how_to/configure_live_trading/)

以下内容不属于迭代 44 的交付：风险算法与限额引擎开发、订单/改单/撤单链路调整、Broker/Store 改造、生命周期协议、进程监督、服务健康探测、自动连接重试、真实账户或交易验收。相关架构背景不再作为本轮实现任务。
