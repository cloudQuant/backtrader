## 实现要点

- 仅从当前、完整且未过期的无品种过滤 `orders_result` 查询建立已知 CTP 委托的 `OrderSysID` 绑定。绑定关联完整查询的 request ID、查询行摘要、匹配行摘要、账户/交易日、会话与连接代次，并在事务内复核查询收据、grant 和 expiry。
- 查询补全的 SysID 写入独立、追加式的已知委托绑定记录；保留 submit 时原始的 `provider_identity`，不把查询值回写或改写成原始 provider 证据。未知归属的委托不获得该绑定。
- CTP 撤单 `Action` 按完整目标构造，核对 `OrderSysID`、`FrontID`、`SessionID` 及合约、交易所、`OrderRef`、Broker/Investor 等目标字段；会话身份和连接代次必须匹配，且查询授权仍在有效期内。
- 真实 SDK 的单合约授权按 `Exchange.Instrument` 校验；会话 scope 与登录状态在同一 SDK 可重入锁下读取。授权发布被中断时冻结写入并尽力撤销授权。此快照当前依赖 SDK 私有锁，后续宜由 SDK 提供公开的原子 typed session scope。
- 已绑定因子协调器的 Store 在协调器丢失后阻止按 OrderRef、SysID 或无标记订单绕过 Journal。该标记只在当前 Store 生命周期内有效；028 启动先绑定 Journal 和协调器，再 arm 并运行策略，跨进程直接绕过此启动路径不在本轮证明范围。
- SDK 截止时间与会话终检依赖 `bt_api_ctp` dev `427d71a02ce78c79d3399623302fa81d623485a9` 和父仓库 dev `918eba76`。原生调用前的最后检查与原生入口之间仍可能被操作系统调度打断，不声称硬实时原子性。
- v22 使用事务化的一次性撤单 dispatch claim。迁移时把旧版本中结果不明的 `DISPATCHING` 撤单写入不可变 tombstone，阻止重放；不把含糊状态当成未发送而再次派发。
- 迁移分批处理时覆盖每一条旧撤单并跳过 submit；tombstone 与 durable capacity 记账保持原子一致。批次或容量不足等失败会回滚，不留下部分 tombstone、计数或 schema 升级。
- 撤单身份查找使用无品种过滤的完整账户订单查询，避免按合约查询产生不完整身份集合。
