## 2. Runtime 应包含什么

Runtime 是策略运行的**控制与编排层**，覆盖运行前、运行中、恢复和停止，而不是策略公式、交易所 API 或一次性检查脚本。借鉴 [NautilusTrader 架构](https://nautilustrader.io/docs/latest/concepts/architecture/)、[QuantConnect 部署与状态恢复](https://www.quantconnect.com/docs/v2/cloud-platform/live-trading/deployment) 和 [FIA 自动交易系统指南](https://www.fia.org/sites/default/files/2019-09/FIA-Guide-to-the-Development-and-Operation-of-Automated-Trading-Systems.pdf) 的职责分离；这些资料是设计参考，不声称其特定司法辖区规则自动适用于本项目。

| 阶段/能力 | Runtime 的职责 | 事实权威与边界 |
|---|---|---|
| 配置与身份 | 解析版本化配置、合法性/模式/插件依赖检查、形成脱敏有效配置和运行身份；凭据按现有受保护合同获取 | 不把密钥写入配置模板、日志或证据；不通过普通检查授予写权限 |
| 启动前检查 | 策略装载和参数、环境/依赖/版本、日历、数据、账户连接权限、路由和资源可用性；分别输出可执行、阻断、未观察 | 离线检查可在无凭据及不连接 provider 时运行；在线只读探测单列，检查通过不是资金或订单授权 |
| 装配与生命周期 | 按配置选择组件、注入依赖、受控启动、ready、降级、停机、资源收尾；报告明确状态及失败原因 | Backtrader 仍由 Cerebro 管 feed/indicator/Strategy；不新增第二个调度器 |
| 持续健康与控制 | 心跳、组件与行情新鲜度、容量、连接、运行模式和停止请求；触发对应保护动作 | Runtime 汇总健康事实，监控插件负责观测/告警；它不伪造账户事实或吞掉异常 |
| 恢复与对账 | 协调预热、持久化状态加载、断线与进程重启后的顺序和准入 | execution/Broker/交易源是订单和成交的权威；UNKNOWN 不自动重发；指标历史与账户状态分别验证，不能以本地快照替代交易源 |
| 可观测与证据 | 生成结构化状态、关联 ID、版本和脱敏运行清单；调用现有 journal/tape/monitor 能力 | 不承诺 exactly-once；异常时保留真实、不确定和未观察状态，证据不包含凭据/原始私密回包 |
| 安全与权限 | 默认只读、显式模式和授权、受信任插件来源、密钥生命周期、受控关闭 | 风险限制在每次订单决策/派发时仍须执行；预检不能代替运行中风控 |
| 运维体验 | `validate/doctor`、dry/replay/shadow/live 状态、版本诊断和可读错误；按能力逐项实现 | 健康、就绪、许可与可写是不同状态；不会自动开仓、平仓或强制清理不明资源 |

建议优先级：P0 为旧功能完整迁移、配置/依赖检查、现有身份与生命周期及新 CLI；P1 为组合与恢复、可观察性和简洁入口；P2 为可选增强，如更丰富的健康聚合、指标导出、部署适配。P2 不得延迟 028 简化或 50/51 已有验收。交易控制参考 [FIA 风控实践](https://www.cftc.gov/media/2746/TAC100319_FIA/download)：订单大小/价格、重复、限速、行情合理性和紧急控制需要在恰当的交易环节执行，而非只在启动时检查一次。

## 3. 所属边界与全部迁移

### 3.1 目标依赖关系

```text
xx_strategy.py + config.yaml + run.py
        ↓ 选用现有 Backtrader 公开 API / 薄装配入口
Backtrader：Cerebro、Strategy、Feed、Broker、因子、cohort
        ↕ 受控 adapter（位于 bt_api_runtime 项目内，可选安装）
bt_api_runtime：配置、预检、装配、生命周期、恢复协调
        ↓ 稳定 contracts；按配置显式装配已有服务或 direct 路径
bt_api_py / bt_api_base  ── gateway / risk / execution / monitor / provider
```

所有现有 `backtrader_runtime` 功能最终归新仓库，包括 Backtrader 专用桥接、fixture 和 CTP 能力；新项目内部按通用核心、Backtrader 可选适配、provider/CTP 适配及历史 fixtures 分层。**新 runtime 核心本身不依赖 Backtrader**；选择 BT 适配时才加载相应可选依赖。是否采用 extras、独立分发或其他包装由兼容性和循环依赖验证确定；本计划不假定当前父 wheel 已包含新子模块。

发行约束需先核清：Backtrader 当前声明 Python >=3.8，而 `bt_api_py` 当前要求 >=3.11；新 runtime 应作为独立 distribution 验证各能力的 Python 支持范围，并让需要新版本 SDK 的能力按各自要求选择性启用。新包应保留惰性导入、错误语义与对象一致性，不在基础导入时意外加载 native/provider。原 `inventory`/`runner` 对源码根、固定注册和 fixtures 有路径绑定，新包不得简单把新安装目录当成 Backtrader 源根。

| 现有能力 | 迁入新仓库后的归属与处理 |
|---|---|
| `config`、`registry`、`policy`、`cli`、`runner`、`legacy`、`inventory` | 全部保留；通用配置/协议与 Backtrader/示例绑定拆层。原 registry 中固定示例、固定源路径和 import 规则必须逐项迁移，不把任意插件默认为可信 |
| `credential_resolver`、`capability_imports`、provider provenance/deployment/preflight、review/evidence | 全部保留原安全和证据语义，区分纯离线与在线只读；敏感内容仅使用现有受保护接口 |
| `test_execution_profile` | 迁移公开的版本化 profile 解析、规范字节、摘要、verifier 与失败关闭校验；这是运行能力而非仅测试工具，保持 profile v2 语义，不把 profile 结论当作账户或下单授权 |
| `managed_execution`、`framework_projection` | 整体纳入新仓库的 Backtrader adapter；保持 Order/Store/Broker 与线程、身份合同，不要求 SDK 核心导入 Backtrader |
| `service_observation`、`cross_exchange_orderbook_observation` | 整体迁入；将 SDK 通用观察与 BT Store/事件适配分层，保持原有对外行为 |
| `ctp_*` 系列，包括预检、只读、profile、front、operator 和 private setup | 全部迁入 provider/CTP 适配层，保留私有输入规则、来源验证和现有受控调用，不把诊断等同于账户验收 |
| `_iteration41_*`、内置资源及旧 CLI 功能 | 源文件、资源和测试整体清点并迁移；以新包入口提供相应命令功能，旧模块入口取消，命令名称是否复用由新发行方案决定 |

先建立旧包每个公开/被调用模块、CLI、资源、符号、异常、序列化字段、配置及测试的迁移清单；对每项记录新位置、调用方变更和验证。新仓库成为实现的唯一权威来源后，删除 Backtrader 里的 `backtrader_runtime` 与 `backtrader.runtime` 旧实现/门面，并更新当前源码、活跃示例、测试、文档和发行入口，直接使用 `bt_api_runtime`。固定来源身份与序列化合同须同步迁移，不以关闭校验解决；历史冻结证据仅作历史记录，不全局改写。

特别阻塞：`bt_api_py/_ctp_credential_binding.py` 当前依赖旧模块名、源码位置与 `backtrader_runtime_sha256` 等绑定语义，且它所声明的 `backtrader_runtime._ctp_credential_binding` 并不在当前 Backtrader tracked 包中。R0 需从已批准的公开历史/实现来源定位并审查该 adapter，确认其实际使用条件；不能假设旧实现就在当前目录。然后将 SDK binder、source identity、字段和所有当前消费者切换到新协议并进行正反例验证，保持受保护数据不外泄；不能直接把同名代码复制后认定身份等价。固定证据、已消费调用及历史 source pins 保留原样。

## 4. 三文件目标与启用模型

三文件是**用户交付界面**，不是把内部实现复制到三个大文件。`xx_strategy.py` 只声明因子与目标决策，继续是普通 `bt.Strategy` 或经确认的薄封装；`config.yaml` 声明品种、模式、参数、组件和限额；`run.py` 只调用公开组合入口。理想示意（下列 API 仅为拟议）：

```python
# run.py — 拟议，当前不可运行
from backtrader.live import run_from_config
from alpha003_strategy import Alpha003Strategy

if __name__ == "__main__":
    run_from_config(Alpha003Strategy, "config.yaml")
```

这里假定 Backtrader 提供轻量组合门面：只有配置启用 runtime 时才惰性加载新包；这也是需要验证的设计选项。用户策略的目标形态是声明 Alpha003、读取已就绪的因子截面并返回多空目标，系统负责把目标和限额交给现有 Broker/执行链；是否用普通 `next()`、薄辅助函数或声明式策略由 R1 原型确定。它们都必须沿用 Cerebro 生命周期。具体方法名尚未决定，不把一个虚构 API 当成现有功能。

```yaml
# 拟议结构，不是当前 schema，也不包含凭据
mode: shadow                 # dry / replay / shadow / live
strategy:
  factor: alpha003
  rebalance_grids: 5
plugins:
  runtime: {enabled: true}
  gateway: {enabled: false}
  risk: {enabled: false}
  execution: {enabled: false}
  monitor: {enabled: false}
```

上面的键名只表达意图，不能直接映射为当前 ServiceHost schema。R1 应设计一个到现有 `components`、`clients.bindings`、direct 模式的显式编译/验证层，避免配置看似启用但实际未接线。配置版本化、拒绝未知项、可列出最终组件和来源；仅加载已配置且被允许的组件，组件启用但缺失/版本不兼容/启动失败明确阻断，不静默切换。插件关闭时保持当前经验证的 direct/backtest 行为，**不因此取消该路径已有的授权、风控和保护**；`live` 与实际写入授权仍是独立门槛，禁止通过缺省值升级模式。`runtime` 本身关闭时由已有 Backtrader 启动路径运行；启用才调用它。

负责解释用户配置的最小入口必须属于无 runtime 插件也可安装的基础层：即使 `runtime.enabled: false`，也要验证组件开关键及其模式兼容性，对其余已启用组件进行实际装配或明确拒绝，不得无声忽略。这个基础解析层可复用现有配置合同，最终归属在 R1 定稿；不要求离线 dry 配置连接网络或读取凭据。

先固定并验收安装矩阵：① 仅安装新版 Backtrader 且不启用 runtime 时，backtest/direct 基础功能正常，旧 runtime 模块不再作为新版本能力发布；② 安装新 runtime 核心但无 Backtrader 时，核心/离线检查可导入，BT 专用能力给出明确缺依赖结果；③ 新 runtime 与新版 Backtrader 共装时，当前调用方全部使用新路径；④ 各 SDK 插件独立/组合安装时按已启用能力逐项检查。实施过程以已提交旧版本作为对照，完成新功能与调用方切换后删除旧包，不发布旧 import shim，也不添加循环依赖。已有用户需要按迁移说明更新安装和导入。

优先使用现有静态 manifest/注册能力，确有需要才引入 [PyPA entry points](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/)；发现已安装插件与授权加载代码是两回事。避免全盘自动扫描和配置触发任意 import。安装、发现、启用、ready、授权分别记录；不把 Git submodule 等同于已安装 distribution。

简洁目标以可理解性验收：示例默认 `run.py` 仅入口和参数传递，目标不超过 20 个非空行；028 策略文件目标不超过 150 个非空行，包含声明、目标和必要的策略自定义逻辑。以上是设计目标而非以删功能换取的硬门槛：超出时记录具体原因和可复用边界，由验收评估。复杂的通用机制不得以大段复制、全局变量、隐式默认或无验证的黑盒转嫁；配置项数和必填项也要计入体验评估。

## 5. 分轮实施与接受门槛

每轮直接在现有 `dev` 工作区实施，完成该轮约定验收后仅提交明确范围，再进入下一轮。SDK 子模块先提交，父仓库最后更新对应 gitlink；保留其他 dirty/untracked 文件。每轮记录仓库、父提交、范围、结果、证据级别、提交和遗留问题；不创建额外开发 worktree。下列是拟议轮次，可按依赖再切小，但不得跳过验收。

R1 必须先确定并验证上一节的安装矩阵、关闭 runtime 时的配置解析责任及新入口切换方案；这些没有解决前，R2/R4 不得移除旧实现或切换发行入口。R0 可以先行清点，迁移实现以冻结后的合同为准。

| 轮次 | 交付与依赖 | 接受条件 |
|---|---|---|
| R0 清单与迁移基线 | 完整枚举旧 runtime 所有功能/模块/资产、入口、引用、配置和身份绑定；建立新旧符号映射与实测基线 | 每项有新归属和测试；列出无法迁移项及阻塞；历史证据与 50/51 状态不被重写 |
| R1 组件配置与生命周期合同 | 基于现有 ServiceHost/direct 拟定统一用户配置与编译映射，定义插件依赖、模式、错误和关闭顺序 | 各组件独立开关与合理组合矩阵；缺失/错误/部分启动失败无静默降级；直连与回测保持既有行为 |
| R2 新 runtime 包与通用能力迁移 | 独立可安装 distribution，迁配置/注册/策略/诊断与资源；调用方改用新入口 | 新旧能力结果、异常、脱敏字段、默认值对照；基础安装不导入 Backtrader/SDK；wheel、RECORD、仓外导入验证 |

| R4 BT adapter 与托管功能迁移 | `managed_execution`、观察、Store/Order 和 fixture 迁至新项目可选 BT 适配，删除旧 import 门面并改造调用方 | 已装/未装 BT 两组隔离环境；普通 Cerebro 生命周期、同一 Store/client、路由/线程/guard 和 CLI 功能保持；无循环依赖 |
| R5 精简策略与装配 | 对 028 提取已证实可复用的策略无关机制，保留普通 Strategy、回放与实盘路径 | 三文件用户界面；排序平局、授权集、目标决策、风控及故障行为与旧版逐事件对比，先 source/真实组件+fake 叶子，再安装包 |

| R7 恢复、故障与多模式 | 断线、缺格、重复事件、持久化故障、进程重启和优雅停机端到端 | 不重发 UNKNOWN；保留撤单/减险独立通道；journal/tape 先后顺序、来源链、线程 join、资源不确定性均可验证 |

## 6. 验收矩阵与非退化合同

1. **功能完整性**：旧包全部已公开和生产引用功能、CLI、资源、配置及结果都有迁移行；旧/新版本用同一合法/非法输入比较返回值、异常和副作用。无测试覆盖的入口先补表征测试；生产调用方、安装依赖及新路径均明确，旧包和门面从新版本删除。
2. **三文件体验**：新用户只编辑三文件即可在干净环境完成 dry 和离线 replay；使用普通策略 API，失败提示可定位配置/插件/运行阶段。目录可以有依赖包，但不要求用户维护它们。实际行数及配置项数记录前后对照。
3. **因子及交易语义**：同一公式/因子定义、完整成员集合、预热与可用时间、目标和决策顺序不变；回放不得使用决策前不可得信息。`LIVE_READY` 只意味着计算就绪，不等于可交易。
4. **安全与风险**：read-only 默认、显式写许可、价格/数量/资金及身份检查依旧存在；过期/缺失/来源不明的事实阻断增险，不应无故阻断已验证的撤单或减险。禁用插件不形成绕过已有控制的新入口。
5. **运行与恢复**：旧新系统对同一公开回放事实产生相同决定、下单计划和因果顺序；测部分成交、断线、UNKNOWN、重复回报、缺格、重启、tape/journal 失败、shutdown/join 失败和外部仓位变化。恢复权威以实际 provider 与已验证日志为准。
6. **分发和迁移**：各独立 wheel 的版本范围、extras、依赖图、许可证和 Python 版本有明确矩阵；验证 base-only、BT adapter、各插件分别安装和组合安装；CLI 功能由新包入口提供，旧模块路径不再发布。源码搜索及隔离 wheel 检查要证明活跃生产引用、安装清单和入口已全部切到新包；冻结历史记录允许保留旧名字。无效/缺字段配置、离线 doctor 和新包基础导入不得提前加载 runner、provider、native CTP 或未选插件，也不得触发 provider I/O；profile v2/verifier 正反例、固定 identity、数据字段迁移与回滚单独检验。
7. **性能与资源**：同配置同数据测旧新 CPU、RSS、延迟、队列/对象边界与停机耗时，报告测量环境、样本和回归阈值；不得以源码测试替代长时间真实行情覆盖。
8. **证据分级**：分别报告 SOURCE、真实组件 + FAKE 叶子、INSTALLED、LIVE_SHADOW、DEMO_ACCOUNT；任何一级不能推断后一级。生产资金账户不在本计划授权内。

## 7. 依赖、发布与回滚

- 顺序为 contracts/切换方案 → 新 runtime 包 → provider 与 BT adapters → SDK 组合及调用方切换 → 删除 Backtrader 旧包/门面 → 三文件示例。各 repo 先按接受结果提交，再更新父 gitlink；发布顺序和最小版本矩阵先证明后推广。
- 新实现和调用方完成验证后直接删除旧 runtime/门面；不保留兼容 shim 或让两套运行时同时成为写入权威。回滚以回退已提交的发行版本和匹配依赖为单位，不能重放不明订单或破坏已有运行状态。旧历史工件及冻结 source pins 不改写。
- 审查依赖许可与版权：Backtrader GPLv3，新仓库公开并不自动决定其许可证；迁移前核实所有源与资源许可证、依赖版本和发布义务，不假设新包可重新许可。
- 不把 runtime 变成第二个执行引擎或调度器；不新增实际账户测试作为源码重构的隐含授权。已知无法观测的旧 retained host 不因迁移而被释放、退出或重试。

## 8. 未决设计问题

1. 独立发行物、父包 extras 与 SDK provider 依赖的最终版本策略；新包安装组合及旧路径删除后用户迁移方式。
2. 既有 ServiceHost schema 与三文件用户配置如何一一映射；是否需要新的公开 session factory，先做最小可运行原型再定 API。
3. 通用风险和 CTP 平今昨/费用政策的实际归属，以现有 `bt_api_risk` / `bt_api_execution` / `bt_api_py` 实现和契约核对为准；禁止复制第二套权威实现。
4. 现有运行中证据、凭据 source binding、历史 fixtures 的稳定身份与新 namespace 如何共存；需先通过 R0/R3。
5. runtime 拓扑：单进程与可选独立服务的能力及失败传播分别列清；不假设全部插件必须启动服务进程。
6. 028 的真实行情及模拟账户未完验收如何在迁移前后复用一次证据；按 50/51 当前正式验收清单执行，不以这份计划改写状态。
