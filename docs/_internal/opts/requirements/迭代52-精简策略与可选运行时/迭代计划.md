## 2. Runtime 应包含什么

Runtime 是策略运行的**控制与编排层**，覆盖运行前、运行中、恢复和停止，而不是策略公式、交易所 API 或一次性检查脚本。借鉴 [NautilusTrader 架构](https://nautilustrader.io/docs/latest/concepts/architecture/)、[QuantConnect 部署与状态恢复](https://www.quantconnect.com/docs/v2/cloud-platform/live-trading/deployment) 和 [FIA 自动交易系统指南](https://www.fia.org/sites/default/files/2019-09/FIA-Guide-to-the-Development-and-Operation-of-Automated-Trading-Systems.pdf) 的职责分离；这些资料是设计参考，不声称其特定司法辖区规则自动适用于本项目。

| 阶段/能力 | Runtime 的职责 | 事实权威与边界 |
|---|---|---|
| 配置与身份 | 解析版本化配置、合法性/模式/插件依赖检查、形成脱敏有效配置和运行身份；凭据按现有受保护合同获取 | 不把密钥写入配置模板、日志或证据；不通过普通检查授予写权限 |
| 启动前检查 | 策略装载和参数、环境/依赖/版本、日历、数据、账户连接权限、路由和资源可用性；分别输出可执行、阻断、未观察 | 离线检查可在无凭据及不连接 provider 时运行；在线只读探测单列，检查通过不是资金或订单授权 |
| 装配与生命周期 | 按配置选择组件、注入依赖、受控启动、ready、降级、停机、资源收尾；报告明确状态及失败原因 | Backtrader 仍由 Cerebro 管 feed/indicator/Strategy；不新增第二个调度器 |
| 持续健康与控制 | 心跳、组件与行情新鲜度、容量、连接、运行模式和停止请求；触发对应保护动作 | Runtime 汇总健康事实，监控插件负责观测/告警；它不伪造账户事实或吞掉异常 |
| 恢复与对账 | 协调预热、持久化状态加载、断线与进程重启后的顺序和准入 | execution/Broker/交易源是订单和成交的权威；UNKNOWN 不自动重发；指标历史与账户状态分别验证，不能以本地快照替代交易源 |
| 可观测与证据 | 生成结构化状态、关联 ID、版本和脱敏运行清单；调用现有 journal/tape/monitor 能力 | 不承诺 exactly-once；异常时保留真实、不确定和未观察状态，证据不包含凭据/原始私密回包 |
| 安全与权限 | 默认只读、显式模式和授权、受信任插件来源、密钥生命周期、受控关闭 | 风险限制在每次订单决策/派发时仍须执行；预检不能代替运行中风控 |
| 运维体验 | `validate/doctor`、dry/replay/shadow/live 状态、版本诊断和可读错误；按能力逐项实现 | 健康、就绪、许可与可写是不同状态；不会自动开仓、平仓或强制清理不明资源 |

建议优先级：P0 为旧功能完整迁移、配置/依赖检查、现有身份与生命周期及新 CLI；P1 为组合与恢复、可观察性和简洁入口；P2 为可选增强，如更丰富的健康聚合、指标导出、部署适配。P2 不得延迟 028 简化或 50/51 已有验收。交易控制参考 [FIA 风控实践](https://www.cftc.gov/media/2746/TAC100319_FIA/download)：订单大小/价格、重复、限速、行情合理性和紧急控制需要在恰当的交易环节执行，而非只在启动时检查一次。

## 3. 所属边界与全部迁移

### 3.1 目标依赖关系

```text
xx_strategy.py + config.yaml + run.py
        ↓ 选用现有 Backtrader 公开 API / 薄装配入口
Backtrader：Cerebro、Strategy、Feed、Broker、因子、cohort、框架适配与投影
        ↕ 以显式协议连接，runtime 不成为框架内部状态的所有者
bt_api_runtime：配置、预检、装配、生命周期、恢复协调
        ↓ 按配置显式装配已有服务或 direct 路径
bt_api_base：共享合同；bt_api_py：SDK 服务和安全组合
        ↓
bt_api_gateway / bt_api_risk / bt_api_execution / bt_api_monitor / bt_api_ctp 等 provider
```

按**状态和职责归属**拆分，旧 runtime 功能全部保留，但实现分别由下表对应项目负责；`bt_api_runtime` 不复制其他组件的交易权威状态。**新 runtime 核心本身不依赖 Backtrader**；Backtrader 特定适配与投影在 Backtrader，CTP provider 逻辑在 `bt_api_ctp`，认证专用资产在测试/认证工具。各组件通过稳定协议组合；选择 Backtrader 功能时才按需要加载 Backtrader。是否采用 extras、独立分发或其他包装由依赖和安装矩阵验证确定；当前父 wheel 并未因此自动包含新子模块。下表是目标归属而非现状宣称：新 runtime 目前仍是占位仓库，已有插件的源码能力、实际接线和真实账户验收必须分别确认，缺口由对应项目实施。

发行约束需先核清：Backtrader 当前声明 Python >=3.8，而 `bt_api_py` 当前要求 >=3.11；新 runtime 应作为独立 distribution 验证各能力的 Python 支持范围，并让需要新版本 SDK 的能力按各自要求选择性启用。新包应保留惰性导入、错误语义与对象一致性，不在基础导入时意外加载 native/provider。原 `inventory`/`runner` 对源码根、固定注册和 fixtures 有路径绑定，新包不得简单把新安装目录当成 Backtrader 源根。

| 现有能力/模块 | 新的职责归属与处理 |
|---|---|
| `config`、`registry`、`policy`、`cli`、`runner`、`legacy`、`inventory` | 严格配置、运行模式、组件注册、可信加载、preflight 调度和生命周期编排归 `bt_api_runtime`；Backtrader 策略注册、Cerebro/Store 绑定和框架特定 runner 归 Backtrader。逐项迁移固定示例、来源和 import 校验；新设计无需保留旧示例入口或旧模块门面 |
| `capability_imports`、`provider_deployment`、`provider_preflight` | 通用可信加载及预检编排归 `bt_api_runtime`，可共享的 receipt/wire 合同评估复用 `bt_api_base`；provider 特定来源与部署事实由相应 provider/部署组件提供。受信 verifier 由权威方注入，默认拒绝语义不得放宽 |
| `credential_resolver` 和私有配置 | runtime 处理秘密引用、授权范围及调用时机；通用受保护凭据接口/实现优先评估归 `bt_api_py` 安全基础模块，CTP 专属字段和协议由 `bt_api_ctp` 解释。保留现有权限、来源、scope seal 和有限释放约束；不在示例或各插件复制秘密读取器 |
| `test_execution_profile` | 通用 profile/wire 合同评估复用 `bt_api_base`，解析、校验和 preflight 绑定由 `bt_api_runtime` 协调，可信 verifier 由权威方注入。保留 profile v2 及失败关闭语义；这是运行能力，不代表账户或下单授权 |
| `managed_execution`、`framework_projection` | Backtrader Order/Broker/Store 绑定、成交到持仓/观察器投影及其 session projection journal 归 **Backtrader**；provider-neutral 订单意图、派发、持久 journal 和 UNKNOWN 对账归 **`bt_api_execution`**。二者属于不同状态所有权，不合并成单个日志 |
| `service_observation`、`cross_exchange_orderbook_observation` | SDK 服务客户端及会话组合归 `bt_api_py`，账户/行情共享服务归 `bt_api_gateway`，Backtrader `ServiceReadProxy`/Store/事件适配归 Backtrader；runtime 只编排。跨交易所示例政策及验证留示例/测试 |
| `ctp_*` 系列 | CTP 原生连接、front、行情/账户回调、查询和协议归 `bt_api_ctp`；runtime 只调用和汇总检查，`bt_api_py` 负责 SDK 服务装配，Backtrader 专属绑定归 Backtrader。私有配置、admission、provider provenance 和来源 pins 按实际信任所有权逐项分解，不假定整文件可搬入 CTP |
| 策略外风控和监控 | 资金/价格/订单许可及风险限额归 `bt_api_risk`；telemetry、可观察事件、只读监控和告警归 `bt_api_monitor`。runtime 汇总状态并协调策略，monitor 不作为账户事实、ready 或订单状态的权威 |
| `review_evidence`、`evidence_bundle`、`_iteration41_*`、资源与旧 CLI 功能 | iteration41 专属证据/fixture 归认证或测试工具；可复用的 wire 合同评估归 `bt_api_base`，与运行配置绑定的检查由 runtime 协调。源文件、资源及功能逐项清点，新 CLI 提供相应能力；旧入口取消，命令名称由新发行方案决定 |

先建立旧包每个公开/被调用模块、CLI、资源、符号、异常、序列化字段、配置及测试的迁移清单；对每项记录其唯一功能所有者、新位置、调用方变更和验证。各目标项目的替代功能和组合路径均验收后，删除 Backtrader 里的 `backtrader_runtime` 与 `backtrader.runtime` 旧实现/门面，并更新当前源码、活跃示例、测试、文档和发行入口，直接调用新归属。固定来源身份与序列化合同须同步迁移，不以关闭校验解决；历史冻结证据仅作历史记录，不全局改写。

特别阻塞：`bt_api_py/_ctp_credential_binding.py` 当前依赖旧模块名、源码位置与 `backtrader_runtime_sha256` 等绑定语义，且它所声明的 `backtrader_runtime._ctp_credential_binding` 并不在当前 Backtrader tracked 包中。R0 需从已批准的公开历史/实现来源定位并审查该 adapter，确认其实际使用条件；不能假设旧实现就在当前目录。然后将 SDK binder、source identity、字段和所有当前消费者切换到新协议并进行正反例验证，保持受保护数据不外泄；不能直接把同名代码复制后认定身份等价。固定证据、已消费调用及历史 source pins 保留原样。

## 4. 三文件目标与启用模型

三文件是**用户交付界面**，不是把内部实现复制到三个大文件。`xx_strategy.py` 只声明因子与目标决策，继续是普通 `bt.Strategy` 或经确认的薄封装；`config.yaml` 声明品种、模式、参数、组件和限额；`run.py` 只调用公开组合入口。理想示意（下列 API 仅为拟议）：

```python
# run.py — 拟议，当前不可运行
from backtrader.live import run_from_config
from alpha003_strategy import Alpha003Strategy

if __name__ == "__main__":
    run_from_config(Alpha003Strategy, "config.yaml")
```

这里假定 Backtrader 提供轻量组合门面：只有配置启用 runtime 时才惰性加载新包；这也是需要验证的设计选项。用户策略的目标形态是声明 Alpha003、读取已就绪的因子截面并返回多空目标，系统负责把目标和限额交给现有 Broker/执行链；是否用普通 `next()`、薄辅助函数或声明式策略由 R1 原型确定。它们都必须沿用 Cerebro 生命周期。具体方法名尚未决定，不把一个虚构 API 当成现有功能。

```yaml
# 拟议结构，不是当前 schema，也不包含凭据
mode: shadow                 # dry / replay / shadow / live
strategy:
  factor: alpha003
  rebalance_grids: 5
plugins:
  runtime: {enabled: true}
  gateway: {enabled: false}
  risk: {enabled: false}
  execution: {enabled: false}
  monitor: {enabled: false}
```

上面的键名只表达意图，不能直接映射为当前 ServiceHost schema。R1 应设计并冻结一个到现有 `components`、`clients.bindings`、direct 模式的显式编译/验证层，避免配置看似启用但实际未接线；目标示例统一使用新 schema 和新装配入口，不回退旧示例入口。配置版本化、拒绝未知项、可列出最终组件和来源；仅加载已配置且被允许的组件，组件启用但缺失/版本不兼容/启动失败明确阻断，不静默切换。插件关闭时按新合同使用所选 direct/backtest 路径，**不因此取消该路径已有的授权、风控和保护**；`live` 与实际写入授权仍是独立门槛，禁止通过缺省值升级模式。`runtime` 本身关闭时由新入口明确装配无需该插件的 Backtrader 路径；启用才加载它。

负责解释用户配置的最小入口必须属于无 runtime 插件也可安装的基础层：即使 `runtime.enabled: false`，也要验证组件开关键及其模式兼容性，对其余已启用组件进行实际装配或明确拒绝，不得无声忽略。这个基础解析层可复用现有配置合同，最终归属在 R1 定稿；不要求离线 dry 配置连接网络或读取凭据。

先固定并验收安装矩阵：① 仅安装新版 Backtrader 且不启用 runtime 时，backtest/direct 基础功能正常，旧 runtime 模块不再作为新版本能力发布；② 安装新 runtime 核心但无 Backtrader 时，核心/离线检查可导入，需要 Backtrader 的装配给出明确缺依赖结果；③ 新 runtime 与新版 Backtrader 共装时，框架适配由 Backtrader 提供，当前调用方使用各功能的新路径；④ 各 SDK 插件独立/组合安装时按已启用能力逐项检查。实施过程以已提交旧版本作为对照，完成所有目标项目的替代功能与调用方切换后删除旧包，不发布旧 import shim，也不添加循环依赖。已有用户需要按迁移说明更新安装和导入。

优先使用现有静态 manifest/注册能力，确有需要才引入 [PyPA entry points](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/)；发现已安装插件与授权加载代码是两回事。避免全盘自动扫描和配置触发任意 import。安装、发现、启用、ready、授权分别记录；不把 Git submodule 等同于已安装 distribution。

简洁目标以可理解性验收：`xx_strategy.py`、`config.yaml` 和 `run.py` 各不超过 800 个非空行。统计时逐个文件计算，剔除仅含空白字符的行，注释、文档字符串和配置说明都计入；配置使用可公开的交付模板，不读取用户私密配置。`run.py` 仍应尽量只负责入口和参数传递，策略仅保留声明、目标和必要的自定义逻辑。复杂的通用机制不得以大段复制、全局变量、隐式默认或无验证的黑盒转嫁；配置项数和必填项也要计入体验评估。不得为了满足行数限制而删除已要求的功能或降低验收标准。

## 6. 验收矩阵与非退化合同

1. **功能完整性**：旧包全部已公开和生产引用功能、CLI、资源、配置及结果都有迁移行，每行列出目标仓库、状态所有者、调用链、依赖与测试；必要时旧/新实现用同一合法/非法输入比较返回值、异常和副作用。无测试覆盖的入口先补表征测试；生产调用方、安装依赖及新路径均明确，所有目标组件与组合验收后旧包和门面从新版本删除。
2. **三文件体验**：对 live/unified 清单中每个目标策略，用户只编辑三文件即可在干净环境运行该示例支持的 dry 或离线模拟模式；使用普通策略 API，失败提示可定位配置/插件/运行阶段。目录可以有共享依赖包，但不要求用户维护它们。分别统计策略、公开配置模板和入口脚本，三者各须不超过 800 非空行；认证矩阵公共基础设施按实际职责单独验收。
3. **因子及交易语义**：每个示例按明确的新业务规格测试公式、资产集合、预热、可用时间和决策规则；示例行为不要求与旧版一致。仍称为 Alpha003 时使用真实已注册的 Alpha003 公式；回放不得使用决策前不可得信息。`LIVE_READY` 只意味着计算就绪，不等于可交易。
4. **安全与风险**：read-only 默认、显式写许可、价格/数量/资金及身份检查依旧存在；过期/缺失/来源不明的事实阻断增险，不应无故阻断已验证的撤单或减险。禁用插件不形成绕过已有控制的新入口。
5. **运行与恢复**：各新示例依据新规格验证决定、下单计划和因果顺序，无需与旧示例结果相同；测部分成交、断线、UNKNOWN、重复回报、缺格、重启、持久化失败、shutdown/join 失败和外部仓位变化。恢复权威以实际 provider 与已验证日志为准。
6. **分发和迁移**：各独立 wheel 的版本范围、extras、依赖图、许可证和 Python 版本有明确矩阵；验证 base-only、Backtrader 桥接、各插件分别安装和组合安装；runtime CLI、CTP 操作命令、插件运维及认证/证据工具的命令分别由所属项目提供，旧模块路径不再发布。源码搜索及隔离 wheel 检查要证明活跃生产引用、安装清单和入口已全部切到各自的新归属；冻结历史记录允许保留旧名字。无效/缺字段配置、离线 doctor 和新包基础导入不得提前加载 runner、provider、native CTP 或未选插件，也不得触发 provider I/O；profile v2/verifier 正反例、固定 identity、数据字段迁移与回滚单独检验。
7. **性能与资源**：按新示例合同测 CPU、RSS、延迟、队列/对象边界与停机耗时，报告测量环境、样本和验收阈值；旧数据仅在场景可比时作为参考，不要求旧行为一致；不得以源码测试替代长时间真实行情覆盖。
8. **证据分级**：分别报告 SOURCE、真实组件 + FAKE 叶子、INSTALLED、LIVE_SHADOW、DEMO_ACCOUNT；任何一级不能推断后一级。生产资金账户不在本计划授权内。
9. **组件权威与跨仓库组合**：运行时只编排并汇总预检，执行订单及 UNKNOWN 由 execution/交易源负责，风险许可由 risk 负责，monitor 不充当交易事实权威，Backtrader 投影 journal 只记录自身 session 的消费状态。验证各组件单独安装/缺失、启停与失败传播、身份绑定、事件一致性、重启顺序及完整装配；不能因功能分散就漏迁或重复维护两套权威。

## 7. 依赖、发布与回滚

- 顺序为 contracts/所有权清单 → 新 runtime 与 base 合同 → 各 provider/安全模块、Backtrader 桥接和相关插件按小轮验收 → SDK 组合及调用方切换 → 删除 Backtrader 旧包/门面 → 028 样板和 live/unified 全量交易示例分批重构。各 repo 先按接受结果提交，再更新父 gitlink；发布顺序、安装依赖和最小版本矩阵先证明后推广。
- 新实现和调用方完成验证后直接删除旧 runtime/门面；不保留兼容 shim 或让两套运行时同时成为写入权威。回滚以回退已提交的发行版本和匹配依赖为单位，不能重放不明订单或破坏已有运行状态。旧历史工件及冻结 source pins 不改写。
- 审查依赖许可与版权：Backtrader GPLv3，新仓库公开并不自动决定其许可证；迁移前核实所有源与资源许可证、依赖版本和发布义务，不假设新包可重新许可。
- 不把 runtime 变成第二个执行引擎或调度器；不新增实际账户测试作为源码重构的隐含授权。已知无法观测的旧 retained host 不因迁移而被释放、退出或重试。

## 8. 未决设计问题

1. 独立发行物、父包 extras 与 SDK provider 依赖的最终版本策略；新包安装组合及旧路径删除后用户迁移方式。
2. 既有 ServiceHost schema 与三文件用户配置如何一一映射；是否需要新的公开 session factory，先做最小可运行原型再定 API。
3. 高层归属已确定：CTP 协议与交易所特有平今昨细节归 `bt_api_ctp`，通用风险许可归 `bt_api_risk`，订单状态与执行归 `bt_api_execution`。具体费用、持仓桶及 provider 事实的合同边界仍须按现有实现和信任来源逐项核对；禁止复制第二套权威实现。
4. 现有运行中证据、凭据 source binding、历史 fixtures 的稳定身份与新 namespace 如何共存；需先通过 R0/R3。
5. runtime 拓扑：单进程与可选独立服务的能力及失败传播分别列清；不假设全部插件必须启动服务进程。
6. 028 的真实行情及模拟账户未完验收如何在迁移前后复用一次证据；按 50/51 当前正式验收清单执行，不以这份计划改写状态。
