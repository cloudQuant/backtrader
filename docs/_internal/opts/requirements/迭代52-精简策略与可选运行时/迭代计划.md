# 迭代 52：精简策略与可选运行时插件

日期：2026-10-30。状态：**规划，尚未实施或验收**。

本迭代面向 Backtrader、`bt_api_py` 和其独立插件仓库。用户模式统一为 `replay`、`shadow`、`paper`（外部模拟账户）和 `live`（生产账户）；迭代 52 本轮只实现、使用和验收 `paper` / `live`。`paper` 不是本地撮合：它连接 provider 的外部模拟/测试账户；在 provider 支持时，`paper` 与 `live` 通常复用同一条实际交易链路，但必须隔离账户引用、凭据引用、endpoint、路由 scope 和权限，并逐 provider 处理接口与产品差异。`replay`、`shadow` 及旧本地模拟能力先盘点、划分归属并拆出保留源码与冻结证据，留待后续；本轮不运行、不做本地验收，也不作为 `FRAMEWORK_COMPLETE` 门槛。旧 `backtrader_runtime` 的功能须完整清点并标明本轮迁移或延期；延期能力不视为已迁移或已交付。仅迁移本轮范围内及当前 paper/live 生产调用链所需的功能，先将当前生产引用适配到新归属；只有这些迁移完成、无活跃生产引用留在旧包且延期源码/证据已分离留存后，才可删除旧 runtime 实现和门面。这里的类型、配置和命令示例均为设计草案，不表示现有 API 已实现。

对 `examples/live` 和 `examples/unified` 中的文件先逐项分类；本轮只重构所需的 `paper` / `live` 策略与调用链。旧目录、入口、schema 和逐事件行为不作为兼容目标。属于 `replay`、`shadow` 或旧本地模拟的示例先保留源码/冻结证据并登记为延期，本轮不运行、不本地验收，也不计入完成门槛。该范围调整不改变原有认证、实际账户、授权/风控、受保留运行实例和冻结证据约束。

本计划不改写 [迭代 50 验收方案](../迭代50-因子实盘运行与交易接入/验收方案.md)及 [迭代 51 验收方案](../迭代51-因子流批一体与Alpha003-SimNow实盘示例/验收方案.md)中的历史事实；未完成的真实行情、外部模拟账户、重启与正式验收仍按原编号及既有规则跟踪。迁移不得把源码、fake 叶子或本地旧模拟结果改记为实际账户通过。保留原有认证范围、逐项实际账户授权与 freshness/guard/private-input 规则；禁止重复已接受调用、读取晚到私密捕获，或绕过受保留运行实例和冻结证据约束。

### 本迭代的最终交付：完整交易框架，而不只是文件瘦身

迭代 52 需要交付一套可配置、可运行、可恢复、可扩展的模拟与实盘交易框架：从策略和组件配置，经过环境检查、行情、策略、风险、订单、回报、账户状态、记录、故障恢复和有界停机，形成完整闭环。三文件、每文件不超过 800 非空行是用户体验验收，不代替框架或真实环境验收。所有范围内的交易示例都按新框架重构；其旧业务行为不要求兼容。历史记录、已消费调用和受保留的实例不能因此被改写或重试。

“后续只需优化细节”的具体含义是：本迭代先冻结版本化边界、状态所有权、组合和失败合同，交付相应实现与可复现实证；后续新增同类策略、接入符合合同的新 provider、调整风控规则、替换兼容 transport 或改进性能时，原则上不必修改 Cerebro、共享合同或其他组件的核心流程。用两个不同策略、两个不同 provider 测试适配器和两种组合拓扑证明这一扩展性；不得通过复制引擎、修改内部源码或硬编码已有 provider 才能完成。新资产类别、交易所不提供的功能及未来重大版本可能需要新增适配或版本化接口；本迭代不作“以后任何需求绝不改框架”的无法验证承诺。

迭代 52 的 `FRAMEWORK_COMPLETE` 只覆盖本轮限定的 `paper` / `live` 范围及第 5、6、6.1 节列明的必需门槛；`replay`、`shadow` 和旧本地模拟明确延期，不是本轮使用/本地验收项目，也不是完成门槛。小轮可独立接受并按仓库提交；任何必需接口、现场环境或已获授权的外部模拟账户条件不可用时，具体项保持 NOT_RUN/BLOCKED，不能以源码、fake、旧本地模拟或文档结论补成 PASS。`live` 表示生产账户配置/路径，不代表获得生产资金、生产写入或追加实际操作的许可；本计划不授权这些操作。

## 2. Runtime 应包含什么

Runtime 是策略运行的**控制与编排层**，覆盖运行前、运行中、恢复和停止，而不是策略公式、交易所 API 或一次性检查脚本。借鉴 [NautilusTrader 架构](https://nautilustrader.io/docs/latest/concepts/architecture/)、[QuantConnect 部署与状态恢复](https://www.quantconnect.com/docs/v2/cloud-platform/live-trading/deployment) 和 [FIA 自动交易系统指南](https://www.fia.org/sites/default/files/2019-09/FIA-Guide-to-the-Development-and-Operation-of-Automated-Trading-Systems.pdf) 的职责分离；这些资料是设计参考，不声称其特定司法辖区规则自动适用于本项目。

| 阶段/能力 | Runtime 的职责 | 事实权威与边界 |
|---|---|---|
| 配置与身份 | 解析版本化配置、合法性/模式/插件依赖检查、形成脱敏有效配置和运行身份；凭据按现有受保护合同获取 | 不把密钥写入配置模板、日志或证据；不通过普通检查授予写权限 |
| 启动前检查 | 策略装载和参数、环境/依赖/版本、日历、数据、账户连接权限、路由和资源可用性；分别输出可执行、阻断、未观察 | 离线检查可在无凭据及不连接 provider 时运行；在线只读探测单列，检查通过不是资金或订单授权 |
| 装配与生命周期 | 按配置选择组件、注入依赖、受控启动、ready、降级、停机、资源收尾；报告明确状态及失败原因 | Backtrader 仍由 Cerebro 管 feed/indicator/Strategy；不新增第二个调度器 |
| 持续健康与控制 | 心跳、组件与行情新鲜度、容量、连接、运行模式和停止请求；触发对应保护动作 | Runtime 汇总健康事实，监控插件负责观测/告警；它不伪造账户事实或吞掉异常 |
| 恢复与对账 | 协调预热、持久化状态加载、断线与进程重启后的顺序和准入 | execution/Broker/交易源是订单和成交的权威；UNKNOWN 不自动重发；指标历史与账户状态分别验证，不能以本地快照替代交易源 |
| 可观测与证据 | 生成结构化状态、关联 ID、版本和脱敏运行清单；调用现有 journal/tape/monitor 能力 | 不承诺 exactly-once；异常时保留真实、不确定和未观察状态，证据不包含凭据/原始私密回包 |
| 安全与权限 | 默认只读、显式模式和授权、受信任插件来源、密钥生命周期、受控关闭 | 风险限制在每次订单决策/派发时仍须执行；预检不能代替运行中风控 |
| 运维体验 | `validate/doctor` 诊断操作，以及 `paper/live` 的状态、版本诊断和可读错误；按本轮能力逐项实现 | `validate/doctor` 不是运行模式；健康、就绪、许可与可写是不同状态；不会自动开仓、平仓或强制清理不明资源。replay/shadow 留待后续 |

本轮必需范围覆盖 `paper/live` 所需的配置、运行、市场数据、持续风险、执行、对账、恢复、可观测、停机和三文件示例；这些核心保障不能被推迟为可选增强。旧 runtime 中仅供 replay、shadow 或本地模拟使用的功能在 R0 清点后归档/分离，列为后续范围，不宣称迁移完成；任何同时被 paper/live 生产调用的共享能力仍须本轮适配和验收。更丰富的可视化、额外 provider、分析指标和性能优化可在已通过的接口上后续增加。交易控制参考 [FIA 2024 风控实践](https://www.fia.org/sites/default/files/2024-07/FIA_WP_AUTOMATED%20TRADING%20RISK%20CONTROLS_FINAL_0.pdf)：订单大小/价格、重复、限速、行情合理性和紧急控制需要在恰当的交易环节执行，而非只在启动时检查一次。

## 3. 所属边界、延期能力与迁移范围

### 3.1 目标依赖关系

```text
xx_strategy.py + config.yaml + run.py
        ↓ 选用现有 Backtrader 公开 API / 薄装配入口
Backtrader：Cerebro、Strategy、Feed、Broker、因子、cohort、框架适配与投影
        ↕ 以显式协议连接，runtime 不成为框架内部状态的所有者
bt_api_runtime：配置、预检、装配、生命周期、恢复协调
        ↓ 按配置显式装配已有服务或 direct 路径
bt_api_base：共享合同；bt_api_py：SDK 服务和安全组合
        ↓
bt_api_gateway / bt_api_risk / bt_api_execution / bt_api_monitor / bt_api_ctp 等 provider
```

按**状态和职责归属**清点并拆分旧 runtime。只有 `paper/live` 生产链路所需能力属于本轮迁移范围；`replay`、`shadow` 和旧本地模拟能力逐项列为延期，分离保留源码、测试输入与冻结证据，不宣称已由新仓库交付。`bt_api_runtime` 不复制其他组件的交易权威状态。**新 runtime 核心本身不依赖 Backtrader**；Backtrader 特定适配与投影在 Backtrader，CTP provider 逻辑在 `bt_api_ctp`，认证专用资产在测试/认证工具。各组件通过稳定协议组合；选择 Backtrader 功能时才按需要加载 Backtrader。是否采用 extras、独立分发或其他包装由依赖和安装矩阵验证确定；当前父 wheel 并未因此自动包含新子模块。下表是目标归属而非现状宣称：新 runtime 目前仍是占位仓库，已有插件的源码能力、实际接线和真实账户验收必须分别确认，缺口由对应项目实施。

发行约束需先核清：Backtrader 当前声明 Python >=3.8，而 `bt_api_py` 当前要求 >=3.11；新 runtime 应作为独立 distribution 验证各能力的 Python 支持范围，并让需要新版本 SDK 的能力按各自要求选择性启用。新包应保留惰性导入、错误语义与对象一致性，不在基础导入时意外加载 native/provider。原 `inventory`/`runner` 对源码根、固定注册和 fixtures 有路径绑定，新包不得简单把新安装目录当成 Backtrader 源根。

## 4. 三文件目标与启用模型

三文件是**用户交付界面**，不是把内部实现复制到三个大文件。`xx_strategy.py` 只声明因子与目标决策，继续是普通 `bt.Strategy` 或经确认的薄封装；`config.yaml` 声明品种、模式、参数、组件和限额；`run.py` 只调用公开组合入口。理想示意（下列 API 仅为拟议）：

```python
# run.py — 拟议，当前不可运行
from backtrader.live import run_from_config
from alpha003_strategy import Alpha003Strategy

if __name__ == "__main__":
    run_from_config(Alpha003Strategy, "config.yaml")
```

这里假定 Backtrader 提供轻量组合门面：只有配置启用 runtime 时才惰性加载新包；这也是需要验证的设计选项。用户策略的目标形态是声明 Alpha003、读取已就绪的因子截面并返回多空目标，系统负责把目标和限额交给现有 Broker/执行链；是否用普通 `next()`、薄辅助函数或声明式策略由 R1 原型确定。它们都必须沿用 Cerebro 生命周期。具体方法名尚未决定，不把一个虚构 API 当成现有功能。

```yaml

mode: paper                  # 本轮启用 paper/live；切换 live 必须使用独立生产账户引用
```

### 4.1 统一模式、身份与配置合同

R1 先冻结**版本化合同**，再写目标示例。`mode` 只有 `replay`、`shadow`、`paper`、`live` 四个值，不增加 `dry`、`demo` 或 `simnow` 别名；迭代 52 只启用 paper/live，replay/shadow 明确返回延期/不支持状态，不执行其运行路径。模式名不代替实际权限：配置还须分开验证账户环境、provider endpoint、账户/凭据引用、路由 scope、数据来源、组件版本和写入权限。paper 必须绑定外部模拟账户；live 必须绑定生产账户。任意交叉绑定、未知键、版本或能力不匹配均拒绝。YAML 不直接注入可信代码、密钥或授权。

同一用户配置只能有**一个权威 schema 和解析/编译实现**，不能在 Backtrader 与 runtime 各维护一套可能漂移的 YAML parser。R1 确定可独立加载的纯数据 schema、解析器、只读 `ResolvedPlan` 和诊断的唯一发行所有者：runtime 关闭或未安装时仍可检查配置，runtime 启用时复用同一结果并负责组件编排，Backtrader 只负责 Cerebro/Feed/Broker 对象适配。该合同需要满足 Backtrader 现有 Python 版本与 SDK 不同版本的安装矩阵；只有验证通过才选择 `bt_api_base` 或其他轻量合同分发方案，不能通过强制安装全部 SDK 绕过。可信 factory/authority 由部署代码注入，用户 YAML 仅表达可验证引用。

| 面向用户的唯一模式 | 市场数据与执行 | 预期边界 |
|---|---|---|
| `replay` | 历史数据；旧本地撮合路径 | 后续范围；迭代 52 不运行、不本地验收、不作为完成门槛 |
| `shadow` | 实时数据及只读账户观察 | 后续范围；迭代 52 不运行、不本地验收、不作为完成门槛 |
| `paper` | provider 实时数据 + provider 外部模拟账户执行 | 本轮实现并验收；使用实际 provider/account/route 和正常订单回报/对账链，不是本地撮合，也不等同生产账户 |
| `live` | provider 实时数据 + provider 生产账户执行路径 | 本轮实现并验收配置、装配、权限隔离及安全拒绝；本计划不授权生产资金或生产写入 |

四个名字构成唯一模式枚举；本轮可运行范围只有 paper/live。paper 和 live 在 provider 支持时共享真实连接、Feed、Cerebro/Broker、风险、执行、回报和对账链路，区别由隔离的账户环境配置表达：账户引用、凭据引用、endpoint、路由 scope、权限以及 provider-specific 产品/单位/规则必须分别验证，任何跨环境或错配均拒绝。paper 指外部模拟账户，不使用本地撮合器；provider 可能将其 endpoint 标为 Demo、测试环境或 SimNow，这些是环境/产品名称而非模式。live 路径的实现与本地安全测试不授权生产资金或真实写入。replay、shadow 与旧本地撮合仍只列入清点和后续设计，不在本轮启动或验收。

部分旧示例的 `--live` 曾指 SimNow 或 provider Demo endpoint；新配置必须把 paper 模拟账户与 live 生产账户明确分开，不能把旧 flag 静默解释成任一新模式或用作兼容别名。缺少适用授权/正式入口的实际账户场景仍为 `NOT_AUTHORIZED` / `UNSUPPORTED` / `NOT_RUN`，不能自行启动。

版本化 `SimulationProfile`、随机撮合/本地成交模型及历史事件回放属于 replay/旧本地模拟的延期能力：本轮不实现、不运行、不本地验收，也不用于 paper/live 订单事实。paper 的成交、拒绝、费用、保证金和回报必须来自对应 provider 的外部模拟账户；live 的账户/订单事实必须来自授权 scope 内的 production provider。测试中的 fake provider 只用于隔离的源码/组合验证，不能冒充本地 paper 或实际账户结果。

SDK 现有 `ServiceReadProxy` 是只读、`ServiceExecutionSession` 当前只支持普通 bar 模式；本轮要补齐 paper/live 共用的受支持组合合同、账户环境隔离、资源所有权、失败传播和可复用装配入口，并在真实 Backtrader Feed/Broker、SDK client/host 及现有组件上验证。不能把只读 proxy 作为写 Broker，也不能以 fake composition 宣称真实账户通过。显式 managed 路径配置缺失或失败时不能回退直连。当前 `run_configured_cerebro` 的受限接口与拟议的三文件入口不是同一个现成 API。

### 4.2 全生命周期与单一权威合同

以下是各组件协作的目标流程，名称与状态必须在 R1 定稿并有机器可读错误分类，而不是强制复制某个第三方引擎：

1. **解析和预检**：以版本化配置构造脱敏运行清单；验证策略、组件与分发版本、scope、capability、数据/执行模式、权限和资源。离线检查不隐式访问网络或私密输入；在线只读检查须明确启用。就绪、健康、交易许可和已连接分别表示。
2. **装配**：组合根负责选择 direct 或 service、注入真实资源和可信 authority，确定账户/策略/逻辑运行/连接代次与所有权；按依赖顺序启动，启动中途失败按已获得资源的真实状态逆序收尾。账户与写入 scope 的冲突须在派发前拒绝；同一 scope 不得同时有两个未协调的派发 owner。
3. **恢复与同步**：加载经过版本校验的执行和框架状态，获取授权范围内的账户、持仓、活动委托及必要成交事实，按可证明覆盖完成对账；缺失、过期、范围不明、查询未完成或本地/远端冲突不是零仓或成功。无法判定时阻断新增风险并保留 UNKNOWN；不得仅凭一次重启就重发未知订单。
4. **行情与预热**：数据经 provider→Gateway/Feed→Cerebro 正常生命周期进入策略；标明源、合约、时区/交易日、事件时间、接收/可用时间、连接代次、序列及数据质量。重复、缺口、乱序、迟到、断线重连、会话切换、预热和 cohort 缺格按显式合同处理，不静默前填、缩池或把历史预热当作新开仓信号。事件处理与资源队列须有上界和可观察的背压/丢失策略。
5. **信号与下单**：策略根据明确可用的事实生成信号或目标；Backtrader 负责框架订单和回调，组合层调用风险许可、执行记录和 provider adapter。开仓、撤单、减仓在各自授权/数据前提下分别评估：无法证明可增险时拒绝新增风险，但不得仅因开仓所需资金不可用就压制已独立验证的撤单或减险。provider 的价格、数量、单位、精度、产品和权限规则在适配边界检查，不把一个市场的语义套给所有场所。
6. **异步回报与持续运行**：提交、确认、拒绝、部分/全部成交、撤单及超时按来源身份和顺序推进；执行记录、风险许可、Gateway 读模型、Backtrader 投影和 Monitor 事件各自有权威与版本，不假装跨 SQLite/provider 的操作自动原子。对重复/晚到/冲突回报、断线恢复、消息/磁盘故障和外部订单/持仓变化必须定义幂等、对账或阻断结果。订阅恢复不等于账户或订单已对齐。
7. **控制和停机**：操作员暂停增险、撤单、减险、策略停止和紧急停止是不同意图，作用域和权限必须明确；紧急控制不能伪装为自动平仓成功。按既定顺序停止新决策，处理已授权风险动作，等待有界回报、核对并持久化、停止/合并线程、关闭组件；超时、句柄/线程/订单状态未确认时返回未决，不以进程退出冒充清理或账户归零。

可扩展合同至少覆盖：运行/账户/策略与请求身份，版本化配置和 capability，行情及账户事实（含单位、币种、时间、来源、完整性），订单意图、执行事件、结果与 UNKNOWN，风险许可及拒绝，恢复游标、运行状态与关闭结果。旧字段/序列化与新 schema 的迁移要有明确版本、转换和拒绝规则；provider-specific 扩展不得把敏感数据或原始回报泄露给通用日志。

### 4.3 框架完成边界与代表性闭环

本轮完整 profile 仅覆盖 paper/live 在既有普通 bar、实时 tick/cohort 支持边界内的实际 provider 链路，及经验证的策略/账户 scope 隔离；多腿或跨场所时每条腿的身份、部分成交、风险及非原子性必须可表达。行业极低延迟 HFT、全部交易所产品和跨交易所原子成交不会因框架完成而自动成立。Replay/本地机械成交或 Demo endpoint 也不证明 HFT，且前者不属于本轮运行/验收范围；HFT 资格需另行定义和证明真实行情→决策→原生发送/回报/成交→对账链、时钟/队列、尾延迟/吞吐/丢失/资源阈值与长时真实样本。无合格证据的场景仍标 `HFT_NOT_ADMITTED` / `NOT_RUN`。生产账户写入许可是独立门槛，本计划不授予。

本轮代表性闭环包括：① 不依赖 provider/私密输入的配置校验操作（它不是运行模式）；② 真实组件、真实 Cerebro/Feed/Broker、fake provider 叶子的受控源码/组合测试，覆盖 paper/live 配置隔离、单因子/多腿策略及 direct/已支持的 service 拓扑，但不把 fake 结果计为账户验收；③ 隔离安装环境中的 paper/live 配置、启动、恢复与安全拒绝；④ 按既有正式入口和授权逐项完成 CTP/SimNow、Binance paper/Demo、OKX paper/Demo 外部模拟账户的适用实际订单、回报、撤单/减险、对账和正常收尾。live 生产账户路径用安全的 fake/拒绝/配置边界验证；没有单独授权不得执行生产写入。本轮不运行 replay/shadow 或旧本地撮合，也不以一次订单替代正式 case。外部条件不足时记录 BLOCKED/NOT_RUN，不降低既有验收要求。

这些代表性路径必须复用已可工作的正式验收入口和既有 guard；优先修复当前共用 runner/loader/fixture 问题，分别归类为本方 harness/配置、候选业务或已证明的外部依赖，不为每个场所另造一套框架。保留所需的全部历史 frozen source/证据和任何 retained host；无 unchanged actual retry、手工 release 或 host exit 授权。新实现需要自己的源码、安装和实际证据；旧实现曾成功的账户调用只证明旧实现，不能重复原调用或直接算新实现通过。

## 6. 验收矩阵与非退化合同

1. **功能完整性与旧 runtime 清点**：旧包全部公开/生产引用能力、CLI、资源、配置、字段和测试均逐项盘点，标记为 paper/live 本轮迁移、replay/shadow/旧本地模拟延期，或退役/历史保留。记录归属、调用链和证据；当前 paper/live 生产引用全部适配并验收。延期源码与冻结证据拆出并保留，不宣称新实现已交付。仅在范围内迁移完成且无活跃旧包引用后删除运行时包/门面。
2. **三文件体验**：对 R0 标记为本轮的 paper/live 策略，三文件可在干净环境配置并接入各自实际 provider 链路；source/fake 测试清楚标注，不伪装成账户验收。普通策略 API 与错误定位要求不变。策略、公开配置模板和入口脚本各 ≤800 非空行；延期 replay/shadow/旧本地模拟不作为运行或验收目标。
3. **因子及交易语义**：每个本轮 paper/live 示例按明确新规格测试公式、资产集合、预热、可用时间和决策规则；示例行为不要求与旧版一致。仍称 Alpha003 时使用真实注册公式；`LIVE_READY` 只表示计算就绪，不等于交易许可。
4. **安全与风险**：read-only 默认、显式写许可、价格/数量/资金及身份检查依旧存在；过期/缺失/来源不明的事实阻断增险，不应无故阻断已验证的撤单或减险。禁用插件不形成绕过已有控制的新入口。
5. **运行与恢复**：各新示例依据新规格验证决定、下单计划和因果顺序，无需与旧示例结果相同；测部分成交、断线、UNKNOWN、重复回报、缺格、重启、持久化失败、shutdown/join 失败和外部仓位变化。恢复权威以实际 provider 与已验证日志为准。
6. **分发和迁移**：明确 wheel 版本、依赖、许可证和 Python 矩阵；验证 paper/live 所需的基础、Backtrader 桥接及 SDK 插件独立/组合安装。新路径接管全部当前 paper/live 生产引用，旧运行时模块不再发布且没有活跃导入；延期 replay/shadow/local-simulation 源码与冻结证据另行保留，不能列为已迁移功能。离线 validate/doctor 与基础导入不得触发 provider I/O 或提前加载未选插件；profile/binder/identity 的既有安全合同及正反例保持。
7. **性能与资源**：按 paper/live 真实 provider 链路及新示例合同测 CPU、RSS、延迟、队列/对象边界、对账/恢复和停机耗时，冻结环境、样本与阈值；不得用旧本地模拟或 smoke 代替真实行情/账户覆盖。
8. **证据分级**：分别报告 SOURCE、真实组件 + FAKE 叶子、INSTALLED、PAPER_ACCOUNT 和 live 配置/权限边界验证；各级不能推断后一级。Fake 不是 paper account 通过；live 路径验证不代表生产资金或生产写入已获授权，本计划不授予该许可。
9. **组件权威与跨仓库组合**：运行时只编排并汇总预检，执行订单及 UNKNOWN 由 execution/交易源负责，风险许可由 risk 负责，monitor 不充当交易事实权威，Backtrader 投影 journal 只记录自身 session 的消费状态。验证各组件单独安装/缺失、启停与失败传播、身份绑定、事件一致性、重启顺序及完整装配；不能因功能分散就漏迁或重复维护两套权威。

## 7. 依赖、发布与回滚

- 顺序为完整清点/分类及所有权 → 新 runtime/base 合同 → paper/live 所需 provider、安全模块、Backtrader 桥接与插件小轮验收 → SDK 组合及当前生产调用方适配 → 028 与其他 paper/live 示例分批重构和相应实际账户证据 → 满足本轮门槛后移除旧可安装 runtime。Replay/shadow/旧本地模拟源码与冻结证据先从活跃包拆出留存，另列后续范围；不本地运行或验收。迁移期间新入口不得 fallback 旧入口，两条链不得同时控制同一写入 scope。子仓库先 scoped commit，再更新父 gitlink。
- 只有 paper/live 本轮功能迁移完成、全部当前生产引用适配且不存在活跃旧包导入，并将 replay/shadow/旧本地模拟源码、测试与冻结证据拆分到明确的非运行时保留位置后，才删除旧 runtime/门面。此删除仅表示本轮限定范围已退役旧运行时，不表示延期能力迁移/交付；不保留旧 API shim，也不允许双重写入权威。回滚按已提交发行版本和匹配依赖进行，不重放 UNKNOWN。历史工件与冻结 source pins 不改写。
- 审查依赖许可与版权：Backtrader GPLv3，新仓库公开并不自动决定其许可证；迁移前核实所有源与资源许可证、依赖版本和发布义务，不假设新包可重新许可。
- 不把 runtime 变成第二个执行引擎或调度器；不新增实际账户测试作为源码重构的隐含授权。已知无法观测的旧 retained host 不因迁移而被释放、退出或重试。

## 8. 未决设计问题

1. 独立发行物、父包 extras 与 SDK provider 依赖的最终版本策略；新包安装组合及旧路径删除后用户迁移方式。
2. 既有 ServiceHost schema 与三文件用户配置如何一一映射；是否需要新的公开 session factory，先做最小可运行原型再定 API。
3. 高层归属已确定：CTP 协议与交易所特有平今昨细节归 `bt_api_ctp`，通用风险许可归 `bt_api_risk`，订单状态与执行归 `bt_api_execution`。具体费用、持仓桶及 provider 事实的合同边界仍须按现有实现和信任来源逐项核对；禁止复制第二套权威实现。
4. 现有运行中证据、凭据 source binding、历史 fixtures 的稳定身份与新 namespace 如何共存；需先通过 R0/R3。
5. runtime 拓扑：单进程与可选独立服务的能力及失败传播分别列清；不假设全部插件必须启动服务进程。
6. 028 的真实行情及模拟账户未完验收如何在迁移前后复用一次证据；按 50/51 当前正式验收清单执行，不以这份计划改写状态。
