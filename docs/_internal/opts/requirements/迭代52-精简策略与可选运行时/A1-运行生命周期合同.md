## NORMATIVE CONTRACT：后续实现必须达到的目标

### 1. 唯一调度与写入派发边界

1. 每次 run 只能有一个策略与市场事件调度 owner：Backtrader `Cerebro`。运行时 facade、session、Store、Feed 和 Broker adapter 可验证计划、持有资源、请求停止或转译接口，但不得另建 Strategy `next` 调用循环、第二套 Feed 时钟或平行订单调度器。
2. 每次可写 run 只能选定一条 Broker → 明确 writer route → provider 的写入派发链。Strategy 只通过其 Broker 提交/撤销；配置/运行时不得另行直接写 provider。`ServiceReadProxy` 永远是观察接口，不能提升成 writer。
3. direct 与 managed/service 是显式选择的装配边界。选定 managed/service 后，解析、启动、health、route 或权限失败都必须 fail closed；禁止静默回退到 direct、mock、`BackBroker` 或旧路径。未发送与结果未知必须区别处理；结果未知时不得自动重发可能已产生副作用的请求。
4. 适用的 `Strategy` 源码在 `paper` 与 `live` 间保持相同。模式、账户环境、provider/product、endpoint、账户引用、credential reference、数据源、策略/路由身份与写入权限分别绑定、验证；不以代码复制或 mode 别名切换策略行为。

### 2. 分维度状态，不以一个 `running` / `connected` 布尔代替

下列五个维度必须分别可读、可审计。它们不是互相推导的别名；报告至少包含 run ID、每一维当前值、最近变更阶段、有限原因码和观察时间。

| 维度 | 规范状态 | 约束 |
|---|---|---|
| `phase` | `new`、`validating`、`prepared`、`starting`、`running`、`stopping`、`stopped`、`failed` | 只描述 run 生命周期；`running` 不表示健康或获准写入。 |
| `ready` | `not_ready`、`ready`、`revoked`、`unknown` | `not_ready` 是初始/尚未满足门槛；`revoked` 表示曾满足的必要条件已失效；`unknown` 表示无法观察。只有 `ready=ready` 可满足 readiness 门，另外三态均不可派发写入。 |
| `health` | `unknown`、`healthy`、`degraded`、`failed` | 按 Feed、账户、执行路由、控制租约、worker 等必需子系统分项记录；局部 `healthy` 不能代表整次 run 健康。 |
| `permit` | `none`、`read_only`、`paper_write`、`live_write`、`revoked` | 初始值必须是 `none`。`none` 不授权 provider/account I/O；`read_only` 只授权绑定清单内的只读操作及该读路径明确列出的最小控制面调用，不授权 submit/cancel 或其他业务写入。模式名、配置成功、`is_connected`、静态 capability、mock/fake 或“未观察到写调用”均不授予许可。 |
| `cleanup` | `not_started`、`in_progress`、`complete`、`partial`、`unresolved` | `not_started` 仅适用于 cleanup 尚未进入且无 provider 副作用/资源获取；`partial` 表示状态均已知、但存在确定失败或未完成的必需清理项；`unresolved` 表示远端结果、资源状态、开放订单处置或责任移交未确认。`closed`/`disconnected` 单一字段不能证明未决订单或远端注册已结束。 |

聚合优先级（互斥）：cleanup 尚未进入且无 provider 副作用/资源获取时为 `not_started`；否则只要任一远端结果、资源状态、已知开放订单处置或责任移交未确认，或必需动作正在等待人工/外部确认，就为 `unresolved`；否则存在确定失败项或已知未完成且当前未执行的必需项时为 `partial`，即使其他步骤仍在执行；否则至少有一个必需步骤正在实际执行时为 `in_progress`；否则仅当所有责任均得到确认时为 `complete`。因此等待操作员/外部确认不是 `in_progress`；若一项失败而另一项仍在执行，聚合为 `partial`，并分别保留失败项与执行中项；未知/待确认项优先聚合为 `unresolved`，但不得覆盖其他项的失败记录。聚合态只是摘要：必须保留每个清理项的稳定 ID、状态、有限原因码、attempted/confirmed、owner 与观察时间；任一失败或未决项不得因汇总或重试被清除或覆盖。

### 3. 许可和 readiness 的独立前置条件

- 静态校验和 trusted route 选择须先于会触发 provider I/O 的 factory。schema 只提供符号化选择，不提供可导入类、任意 factory、endpoint 或隐式账户写权。
- 进入 `prepared` 前，必须绑定且复核 mode/environment、provider/product、account、endpoint、credential reference、strategy identity、feed/source/clock、Store/Broker、订单 writer/query route 和资源 owner。真实身份、授权和静态声明要分别验证；symbol 相等不等于身份或 grant。
- 默认 `permit=none`，它只允许 provider-free 的本地配置/源码校验，不允许调用 provider factory、账户/行情 facade 或执行注册/订阅 I/O。读取账户/行情必须先取得 `read_only`，且只能调用该 permit 明确列出的读取操作与其必要的最小控制面操作；任何 `submit`、`cancel` 或其他业务写 RPC 均须在唯一派发边界拒绝。`paper_write` 只可绑定已验证的外部模拟账户；`live_write` 必须是独立、可撤销、限账户/endpoint/route/strategy/run/能力与有效期的明确授权。live 许可不得由 paper 许可推导。
- 写派发仅可在 `phase=running` 且 `ready=ready`、permit、必需子系统 `health`、route/account/run identity 与有效期复核通过时发生；dispatch boundary 每次重新检查。失败先阻断该次派发，再把许可置为 `revoked` 或 `none`，并令 `ready=revoked` 或 `ready=unknown`。授权状态与命令提交结果分别记录。
- `ready=ready` 不代表 `permit` 允许写入；`permit=read_only` 不能提交/撤销订单；`health=healthy` 不代表账户/行情真实或许可有效。即使其他门满足，只要 `phase` 不等于 `running` 就不得开始写派发。

### 4. Phase 转移与失败门

| 转移 | 必需条件 | 失败结果 |
|---|---|---|
| `new → validating` | 新 run 唯一 ID；没有共享上一次 run 的 mutable session/资源。 | 拒绝复用，保持 `failed` 或 `stopped` 终态。 |
| `validating → prepared` | 完成纯数据校验、plan/route 选择、环境/账户匹配、组件能力与 ownership 声明；I/O 前校验全部通过。 | `phase=failed`、`ready=not_ready`、`permit=none`；若尚无资源且未发生 provider I/O，`cleanup=not_started`。不尝试 provider 连接。 |
| `prepared → starting` | 建立本次 run 的获取账本；每个资源的 owner、借用关系、thread affinity、启动步骤和可观察关闭条件已知。 | 不允许部分资源进入未登记状态；已发生获取则进入 cleanup。 |
| `starting → running` | 必需 Store/Broker/Feed/facade 和控制组件已启动；完整账户快照及必要市场 bootstrap/source/clock 检查成功；required health 为 `healthy`；若该计划需要下单，已取得相符且有效的 permit。 | 任何门失败都不启动 Strategy 主循环；进入 `failed` 并按账本清理。 |
| `running → stopping` | 正常数据结束、已接受的 stop request、permit 撤销、required readiness/health 丢失、内部错误或控制中断。 | **先关闭 admission，再发布 `phase=stopping`**；两者必须原子化或由同一锁/门保护。写 dispatcher 必须在执行前检查 `phase==running`，因此状态转移后不得开始新派发。已开始请求仍须跟踪；停止请求不表示 Strategy、provider 或 worker 已停止。 |
| `stopping → stopped` | Strategy/调度已停止；不存在已知未决订单，或每笔已知仍开放订单均由持久化 reconciliation owner 明确接受接管并留下可关联记录；所有 run-owned 资源关闭已确认；borrowed 资源责任已归还/确认；`cleanup=complete`。 | 远端结果未知、接管未确认、或本 owner 资源未完成收尾时，保持 `phase=failed` 且 `cleanup=unresolved`/`partial`，不得报告 `stopped`。 |
| 任一非终态 → `failed` | 校验、启动、Strategy、Feed、Broker、transport、permit、健康或 cleanup 失败。 | 若此前已 ready 则转为 `ready=revoked`；未达门槛保持 `not_ready`，无法观察则为 `unknown`。`permit` 置 `revoked`（若曾授权）；保留原始主错误和单独 cleanup 报告。状态不明时禁止自动重新启动或改走另一条路径。 |

required 子系统健康丢失时，必须先阻断该能力的下一次派发，再将 readiness/permit 置为不可用；是否仅降级只读观察，必须是 route 明示且不依赖缺失能力，不能由通用 runtime 猜测。跨线程 stop 只可发出受限停止信号；资源关闭由声明的 owner thread 完成。

调用幂等和终态约束（**NORMATIVE CONTRACT；属于未来实现要求，不表示当前实现已具备**）：每个 invocation 使用唯一 `attempt_id`。若同一 attempt 已存在，重复调用只能返回该 attempt 的当前状态，或用有限原因码明确拒绝；必须幂等，不得再次启动、创建 Strategy、分配新 `run_id` 或重复派发。该 attempt 已关联终态 session 时，返回同一 attempt/run 已记录的终态结果。`run_id` 进入 `stopped` 或 `failed` 后不可重开或改写。携带旧终态 `run_id` 的新 attempt 必须拒绝，记录新 attempt 为 `failed` 并给出有限校验原因码，旧 run 的 phase、cleanup、primary error 与结果保持不变；不得为拒绝这次调用而伪造新 `run_id`。若新 attempt 在 run 建立前因校验失败，只记录该 attempt 为 `failed`，不虚构 run；只有显式新 run 请求配有新 `attempt_id` 和新 `run_id` 才能建立独立 run，且该新 run 的校验失败只会将新 attempt/新 run 标为 `failed`，不得重写任何旧 run 终态。attempt 记录与五维 run 状态分开保存。

### 5. 资源 ownership 与清理协议

1. 每项资源必须标成 `run_owned`、`borrowed` 或 `external_owner`，注明唯一 owner、创建/关闭 thread、显式 handoff 点、依赖边、stop/close 的返回条件与可读取的终态。创建者在 handoff 成功前负责已取得资源；handoff 失败时由创建者回滚或将资源保留并报告不确定，不可把 unknown 对象交给通用清理器猜测。
2. 进入 stopping 的第一步关闭新的写入 admission，并冻结新的 Strategy 派发；dispatch gate 同时要求 `phase==running`。不得自动假定 cancel、flatten、断线或本地 close 能撤销 provider 已接受的命令。对在途 RPC/订单按已审查的 provider 策略等待、查询或标记未决，不能默默重放。
3. 对本次 run 所拥有的资源，后续实现须基于实际 dependency/ownership ledger 做依赖逆序收尾：先停使用者，再关被使用的资源；共享 facade/runtime 由其实际 owner 收尾。禁止对 borrowed/external-owner 资源做 double-stop/close。跨所有 adapter 的固定类别顺序尚未确定；本段是目标约束，不表示当前 Cerebro 顺序已符合。
4. cleanup 中每项操作须单独记录稳定 ID、状态（`not_started`、`in_progress`、`confirmed`、`failed` 或 `pending`）、`attempted`、`confirmed`、有限原因码、owner 与观察时间；`pending` 必须说明是在等依赖、人工/外部确认还是重试条件，等待人工/外部确认归入聚合 `unresolved`，不得伪报为正在执行。`cleanup=complete` 仅当本 owner 所有资源已收尾，且每笔已知仍开放订单已完成对账或由持久化 reconciliation owner 明确接受接管并留下记录时成立。若 provider 结果未知、接管未确认、public state 不可读、进程/线程状态不可观测、注销/订阅结果未知、关闭结果无法确认资源终态，或证据只说明本地断开，则聚合为 `unresolved`，保留 owner 引用并禁止丢弃状态；若资源仍活动或必需项已确定失败/未完成、当前没有对应清理步骤正在执行，且无未知项/待确认项，则聚合为 `partial`；若对应清理步骤正在实际执行且无更高优先级的 unresolved/partial 项，则为 `in_progress`。其他步骤仍可继续，但不得清除或覆盖失败记录。
5. 启动错误或运行错误始终是 primary error；cleanup 错误作为有限附加结果，不覆盖原错误。诊断只输出固定原因码、phase、组件类别、异常类型、attempted/confirmed/pending、允许的源码位置和关联 ID；不得把 credential、配置值、provider 原始响应、异常 message、locals 或晚到 private capture 写入日志/报告。区分“请求未发送”和“已发送但结果未知”。
6. 只有明确声明可幂等、同 owner thread、同 run 的补偿清理允许重试；不得自动重试可能有远端副作用的业务请求。`cleanup=unresolved` 必须保留为单独状态供 owner/operator 对账，不得改写成 `stopped`、`complete`、零计数或成功。

### 6. 停止、未决和外部确认

- `stop_requested`、Strategy `stop()` 已返回、Cerebro loop 已返回、Store `is_connected=False`、facade 本地 `close()` 返回和 SDK runtime `closed` 是不同观察。它们不能单独证明开放订单已完成或已移交给持久 reconciliation owner，也不能单独推出 `cleanup=complete` / `phase=stopped`。
- provider 对命令的响应缺失、timeout、worker 未退出、市场 unsubscribe/register 不确定、账户/路由观测不完整、清理 owner 不可访问或状态 getter 失败时，记录对应 `unknown/unresolved`；停止新写入，保留可恢复的本地 owner/context，并要求按已授权正式流程对账。
- 完成状态不得从 fake、源码类存在、配置标签或源测试数量推导；异常从 `paper` 切换到 `live`（或 direct 与 managed 切换）不是恢复策略。

## PRESENT：当前公开源码可证实的局部行为

### Backtrader / Cerebro / Strategy

- `backtrader/_cerebro/execution.py` 的 `_prepare_run` 先启动 Store、Broker、Feed，再启动 data；`runstrategies` 构造 Strategy、随后调用 `_start()`，之后启动 writer/timer 并选 `_runonce` 或 `_runnext`。因此现有策略/数据推进由 Cerebro 编排，存在一个普通 run loop（源码 L282-L335、L337-L427、L468-L528）。
- 正常结束的可见 teardown 路径先调用 Strategy `_stop()`，再停止 writer、Broker；仅 `not predata` 时才逐项调用 data.stop()，之后停止 Feed 与 managed Store（L529-L564）。普通启动失败协调器目前按 Strategy、writer、Broker、直接 data、Feed、managed Store 尝试清理（L78-L236）；这是现有实现顺序，**不是**通用依赖逆序契约。主循环异常先保存在 `run_exception`，但 `finally` 内 Strategy `_stop()` 没有逐个异常保护：若其抛错，可能掩盖已保存的 loop 异常并跳过后续 writer/Broker/data/Feed/Store 收尾；startup coordinator 保留原启动异常的保证不能推广到这条正常 teardown 路径（L529-L564）。
- 启动失败协调器按触及资源记录 attempt，尽量保留原异常，并附有限的 cleanup exception type/traceback location（不含异常 message/locals）；data ownership 不确定时跳过可能重复的 stop；不完整启动的 Strategy 不调用 `_stop()`，timer 没有对应 stop 步骤，外部/非 managed Store 由外部 owner 负责（`execution.py` L78-L101、L132-L170、L173-L250）。
- Strategy `_start()` 会依序启动 analyzers、observers，转 stage 后调用用户 `start()`；Cerebro 仅在 `_start()` 正常返回后把它记入 `started_strategies`。Strategy `_stop()` 的用户 `stop()`/analyzer 异常可以中断后续，observer `stop()` 异常则在现有实现中记录日志并抑制；当前没有覆盖所有 child resource 的完整启动账本（`strategy.py` L1842-L1905、L2049-L2122；[Cerebro 启动清理记录](./A1-Cerebro启动失败清理记录.md#L5-L10)；[Observer 清理记录](./A1-Observer启动清理记录.md#L5-L9)）。

### Backtrader managed session、service read proxy 与 SDK runtime candidate

- `ServiceExecutionSession.run()` 做 preflight、绑定 managed adapter/owned runtimes，最后调用 `cerebro.run()`；它不是第二个 Strategy event loop。其 preflight 拒绝 read-only Store、`market_data_only` Broker、已启动资源以及 channel 与优化模式（`backtrader/stores/service_execution_session.py` L417-L530、L712-L753）。这条 managed execution 入口有 writer/query route 检查；接口存在不等于授权给具体账户或 provider。
- `ServiceReadProxy` 明确声明 `service_read_only=True`、`read_only=True`；`connect()`/`disconnect()` 与经 `_assert_connected()` 保护的读取/市场操作检查创建线程，关闭时关闭注入的 account/market facade，但共享 runtime 属调用方。不能把该约束扩大为所有属性 getter：例如 `is_connected` 属性本身不调用 `_assert_owner()`（`backtrader/stores/service_read_proxy.py` L326-L378、L1345-L1352）。
- 子仓 `bt_api_runtime` 的 `RunSession` 在 assembly thread 单次调用 `Cerebro.run()`，可用 `request_stop()` 调用 Cerebro 的线程安全 `runstop()`；它关 per-run proxy，不自动拥有/关闭共享 SDK runtime（`D:/bt_api_py/bt_api/bt_api_runtime/runtime/src/bt_api_runtime/assembly.py` L505-L588、L811-L913）。其 `RuntimeCleanupReport` 是 fixed step codes/confirmed/pending 的局部报告，不是全系统 phase/ready/health/permit（同文件 L85-L103、L571-L579）。
