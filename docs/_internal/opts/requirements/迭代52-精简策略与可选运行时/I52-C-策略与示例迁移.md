# I52-C：策略与示例迁移

状态：规划；对应总纲 R5、R8。本文是迭代 52 的独立子计划，依赖 [I52-A](./I52-A-清点与统一合同.md) 的完整清单/合同和 [I52-B](./I52-B-运行时与首条交易链路.md) 中已接受的入口及第一条 provider 链路的源码/组合/安装基础。B 的外部 paper 账户若因授权或外部条件受阻，可记录 BLOCKED/NOT_RUN 并继续独立的 C 小轮；实际账户和最终完成门槛不能因此降低。

## 目标与边界

先用 `028_alpha003_simnow_minute` 做一条精简、可理解的 paper/live 策略示例，再从 R0 清单按小组或独立 case 迁移其余所有属于 paper/live 的调用链，最后用一个不同的既有 provider 适配证明合同可扩展。每轮均复用已提交公共入口与组件；不拓展 provider 清单、managed/service 拓扑或产品支持范围。

跨模式共用适用策略代码仍是长期目标。本轮以同一份策略源码在 paper/live 配置装配为验收点，不要求已有全部策略自动兼容，也不运行/验收 replay、shadow、旧本地撮合。旧目录与旧 schema 不作为兼容目标。`paper` 只能指真实 provider 外部模拟账户；示例中的 Demo/SimNow 是环境/endpoint 标识，不是 mode。

## 小轮

### C1 / R5：028 首个精简策略

- 先将 028 原职责拆为策略政策、通用机制、provider/CTP 规则、Backtrader 生命周期和配置/资源编排；依据 A 的职责表分别复用既有所有者。`plan_alpha003_orders` 逐段审计后再决定归属，不把整段业务政策塞进 runtime。
- 复用 Backtrader 已有 Alpha003 公式/调度（包括适用的 `get_alpha(3)`、`LiveFactorSet`）；不复制公式或创建第二调度器。选标、tie-break、调仓频率、多空目标和风险/权限是明确的策略/配置合同；`LIVE_READY` 不代表交易许可。
- 交付 `xx_strategy.py`、`config.yaml`、`run.py` 三个文件，每个 ≤800 非空行。`run.py` 只调用已接受的公开组合入口；策略保持普通 Backtrader Strategy/Cerebro 生命周期。paper/live 可复用一份策略/API，但配置必须隔离账户/凭据引用、endpoint、路由 scope 和权限。
- 先 source 与真实框架/组件 + fake provider leaf；再隔离安装和仓外运行。以同一策略对象/源码检查两种 ResolvedPlan 的选择与错配拒绝；不以 local simulation 替代 paper。

### C2 / R8：其余 paper/live 示例和调用链

- 以 R0 的逐文件/逐 case 清单为唯一依据，按一组或单独 case 分轮处理 `007`、`012_1/012_2`、`013_1–013_3`、`014_1/014_2`、`015`、`000_live_certification`/Optional16 及其实际 paper/live 共享 helper。清单发现范围变化时先更新清单，不凭本文目录列表推定所有项目都可写或可运行。
- 每轮只迁移明确归属的 paper/live 项及其共享活跃 helper；分离保存 replay/shadow/旧本地撮合源码、测试样本和冻结证据，标记 `DEFERRED` 且不执行。当前 paper/live 生产共用 helper 不能仅因文件位于延期示例目录而漏迁。
- 每个策略入口复核三文件与各自 800 非空行上限、统一配置、Feed/Broker/Store 接线、provider/product/clock、风险/权限、安装依赖、case ID 与证据映射。旧策略输出/逐事件行为不要求等价，但任何语义变化须在新规格与测试明确说明。
- 认证驱动、断言、测试工具和专用 fixture 归测试/认证支持，不冒充用户策略。99 个正式条目及 Optional16 的身份、前置和历史结果保持原样；迁移不自动通过 formal case，也不重排授权。

### C3：第二个既有 provider 适配证明

- 从 R0 确认的第二种 provider/product 中选择已有公共 adapter/SDK 接口，使用 C1/C2 已接受的稳定合同做独立适配示范；与第一条链路使用同一份未经修改的 Strategy 源码，核对源码身份和数据、订单及通知的公共合同。Source/fake 覆盖身份、数据/订单字段映射、显式不支持能力和失败边界；隔离安装验证其分发和无核心源码复制。
- 不自行添加 provider、endpoint、产品或 topology；若清单无法证明第二 provider 接口已存在/可受支持，则将 C3 记为 `BLOCKED` 并提交缺口，不用两个 fake 名称冒充两个 provider，也不把单 provider 纵切算成扩展性通过。
- 第二 provider 的实际 paper 证据仍须按该 venue 原有授权和 formal entry 单独登记；某一 venue 的通过不可代替另一 venue。每个 venue 同时最多一个实际 case/集成 blocker。

## 复用、依赖与验收

复用 A 的能力/文件/case 清单、B 的 parser/ResolvedPlan/assembly/provider contract、现有 Backtrader research/Cerebro/Feed/Broker/Store、SDK 公开插件接口及 50/51 正式测试/guard。对每个小轮分别记录 source、真实组件 + fake leaf、installed、paper-account 或 live 边界等证据级别；测试成功、旧脚本可运行或目录覆盖均不能推断实际账户 PASS。

每轮在当前相关仓库 `dev` 直接实施，验收后 scoped commit，之后再开始下一轮。SDK 子仓先提交、父仓后更新 gitlink；保留其他改动，不创建开发 worktree。交付对应策略三文件、其源码/配置测试和安装/装配结果、旧条目→新合同/测试/evidence 映射、延期保留清单、commit 与未完成项。不得把 replay/shadow/本地撮合纳入 I52 的通过数。

所有真实账户步骤必须重新遵循旧 case 的逐项授权、freshness、guard、private-input、consumed-call 与 retained-host 控制；不能重复已接受成功调用、unchanged retry、读取晚到私密捕获或手工释放/退出受保留 host。live production-write 未授权。
