交接日期：2026-10-31。用途：交给接手开发者完成迭代 52，并在交付后由验收方独立核对。本文记录交接时观察到的状态；实施前应重新核对各仓库和工作区，不能把本文中的候选设计、历史状态或测试结果当成当前已完成的能力。

## 1. 目标和用户要求

迭代 52 的目标是搭好一套可配置、可运行、可恢复、可扩展的模拟与实盘交易框架，覆盖配置、行情、策略、风险、订单及回报、账户状态、监控、故障恢复和有界停机。它不是单纯压缩文件，也不是另外实现一个交易引擎。

- 标准在线模式只有 `replay`、`shadow`、`paper`、`live` 四种；本迭代只实现、使用和验收 `paper` 与 `live`。`paper` 是交易服务商提供的外部模拟账户，`live` 是生产账户路径。回测是独立的历史研究/回测场景。
- 同一份**适用的策略代码**应能用于回测及上述模式，通过对应 Feed、Broker、Store 和配置装配切换，不要求为每种模式改写策略。此为长期合同；本轮只以 paper/live 的适用策略和能力作为实现与验收范围。
- `replay`、`shadow` 和旧本地撮合相关代码、测试输入及历史证据要清点、确定归属并安全保留；本轮不运行、不做本地行为验收，也不因保留而声称已实现。
- paper 与 live 通常应复用同一交易链路，但账户环境、账户/凭据引用、endpoint、路由 scope 和权限必须分别校验隔离；具体差异按 provider/product 明确处理。模式名不授予权限，Demo/SimNow 是环境或 endpoint 标识，不是新模式。
- 用户原先希望示例仅需 `xx_strategy.py`、`config.yaml`、`run.py`，随后明确表示严格限定三个文件的目标过高，要求控制在 **800 非空行以内**。因此应优先保持入口简洁、复用项目已有能力；示例交付文件包括策略、入口、配置及必要辅助脚本，每个分别控制在 800 非空行以内，不是把所有文件的行数相加。三个文件是优先的简洁形式，不应因确有合理职责需要的小型辅助文件就违背用户后续指令。现有总计划及 C 计划把“三文件”写成硬条件，实施者应在冻结 C/D 验收规格前，同步修订总计划及相关子计划中的硬条件，按用户最新要求消除这一冲突。
- 旧示例行为不要求保持兼容。旧 `backtrader_runtime` 的功能应完整清点，逐项确定归属以及迁移、延期或退役；本轮迁移 paper/live 所需功能，延期功能安全保留。最终取消旧可安装包及 `backtrader.runtime` 旧门面，直接使用 `bt_api_runtime`；不保留旧包作为长期备用。删除必须在本轮活跃调用方完成替代、验收通过且延期材料安全保留后进行，不能提前删除造成断链。

## 2. 权威计划与职责边界

请先阅读 [迭代 52 总计划](./迭代计划.md) 和四个子计划：[A：清点与统一合同](./I52-A-清点与统一合同.md)、[B：运行时与首条交易链路](./I52-B-运行时与首条交易链路.md)、[C：策略与示例迁移](./I52-C-策略与示例迁移.md)、[D：验收与发行切换](./I52-D-验收与发行切换.md)。总计划的 52-F01–F20 为逐项验收清单。计划里标为“拟议”的 API、字段或拓扑不是已实现能力。若计划文字与用户后续明确指令不一致，以用户指令为准，并及时修订验收规格。

- **Backtrader**：Cerebro/Strategy、Feed/Broker/Store 接线、框架订单和通知投影及其生命周期；不复制 SDK 的交易事实权威。
- **bt_api_py 与 provider adapter**：统一 SDK 公共接口、provider/产品适配、来源与账户边界；按实际代码确定归属。

- **可选插件**：`bt_api_gateway`、`bt_api_risk`、`bt_api_monitor`、`bt_api_execution` 与 `bt_api_runtime` 按各自接口承担连接、风险、监控、执行及运行编排职责，由统一配置和能力合同决定装配。不得把启用开关、静态 capability 或连接成功等同于交易授权；缺失依赖或 managed 路径失败不得静默回退 direct/mock/旧路径。
- 完整架构和更细职责见 [交易系统架构](../../../../TRADING_SYSTEM_ARCHITECTURE.md)、[运行模式说明](../../../../source/advanced/architecture/trading-modes_zh.md) 及总计划第 2–4 节；以各仓库当前源码与公开接口核实可用性。
