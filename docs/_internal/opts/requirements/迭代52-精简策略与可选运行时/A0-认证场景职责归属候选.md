# A0：认证场景职责归属候选

状态：**只读源码候选映射；尚未逐 venue / 逐 case 核准，也不是迁移决定、功能验收或正式认证状态变更。** 本文供 A0 逐案评审使用。只依据公开源码和非证据类 A0 规划文档。未读取真实 `config.yaml`、`.env`、evidence、captures、results、日志或账号资料；未运行案例、测试、provider、交易或旧 replay/shadow。

## 1. 判定原则

### 1.1 原始身份不合并

认证身份是不可变键 `(venue, case_id)`：SimNow、Binance、OKX 各自保留 B01–B02、C01、E01–E03、EM01–EM03、L01–L04、M01–M05、O01–O03、T01–T03、TH01–TH06、V01–V03，合计 99 个独立条目。相同 ID 的场景描述可作为候选行为模板，但不能共享正式状态、来源记录、授权前置或 owner 决定。EM03 已能从公开策略源码看出三个 venue 的动作不同，证明仅按 ID 合并会丢失语义。

本表只给出 **33 类行为的候选归属**。实际决策时须把它展开为 99 行，对每个 venue 的策略和 runner 源码重新核对，并分别记录路径、源码快照及 `owner_basis`。不得更改原 case ID、原 tracker 状态、原授权条件或历史证据引用；`RISK` 原值另列，不能覆写成组件名。

### 1.2 先拆行为义务，再定 owner

对每个 case，从公开源码抽取一个或多个行为义务，每个义务至少写清：

- 触发与前置事实；
- 被观察或断言的结果；
- 必须保持的副作用边界（例如是否派发、订单是否残留）；
- 事实来源（venue response、订单回报、monitor event、session generation、operator command 等）；
- 当前源码位置和目标契约 owner。

一个 case 可以有多个义务和多个 supporting owners。候选 `primary_owner` 指负责该义务 oracle 的权威组件；若一项行为同时验证两个不同 oracle，应拆成两个子义务，不强行归给一个组件。owner 冲突或来源不清时标为 `UNRESOLVED` 并列出缺少的源码/合同，不按 ID、文件夹名或 `RISK` 猜测。

### 1.3 `RISK` 不等于 Risk owner、mode 或授权

三个旧 runner 的 `READ` / `WRITE` / `DANGEROUS` 是认证入口中的本地风险等级和旗标门槛。它不说明行为由 `bt_api_risk` 实现，不说明新系统的 `paper`/`live` mode、账户权限、endpoint 或真实批准。

清单保留独立字段：`legacy_risk_label`、`mode_candidate`、`account_environment`、`permission`、`formal_status_ref`。不得把旧 `--live`、`--allow-write`、`--allow-dangerous` 自动迁成 I52 permit。正式状态只从授权核验后的原逐案 tracker 读取；在未核前仍为待核，不从源码或测试推 PASS/FAIL。

## 2. 目标职责边界

| 候选 owner | 应负责的权威事实 | 不应据此推导 |
|---|---|---|
| SimNow / Binance / OKX adapter（各自独立） | 场所 API 与协议；产品/合约元数据；venue tick、volume 等规则来源；连接/session generation；场所状态、错误、订单和成交字段规范化；数据时钟/来源映射。 | 账户身份、授权、策略选择或通用风控策略。不能把一个 venue 的具体协议直接复制为另一个 venue 的通过证明。 |
| Risk | 账户/组合级限额、允许的风险增量、价格/数量/频率等政策限制及每次派发前的风险准入。 | 场所 API 的错误解释、session 状态、订单事实。venue 合约规则先由 adapter 提供；是否还需 Risk 政策由规则来源决定。 |
| Gateway | 实际 Gateway 路由下的传输、服务端命令路由、身份/ACL、请求关联和服务端控制边界。 | venue 协议映射，或任何仅写有 `service` 的调用。只有真实调用链进入 Gateway 才归 Gateway。 |
| Execution | 有效命令的 dispatch / no-dispatch 边界，订单提交和撤销状态，幂等、成交、UNKNOWN、对账与恢复事实。 | 自行伪造 venue 订单/账户事实或替代策略。 |
| Monitor | 只读事件采集与关联、session/运行观测、阈值快照和告警。 | 订单/账户事实权威、派发授权或运行 ready 的最终决定。 |
| Runtime | 配置与 mode 解析、授权 permit、组件装配、资源所有权、ready/暂停/停止/恢复和健康汇总。 | 交易策略、第二个订单调度器、provider 协议或 Risk 决策本身。 |
| Certification harness | 原 case ID、认证前置与 CLI gate、场景步骤、结果 oracle、案例专用报告/捕获边界。 | 产品 runtime 或用户策略；case 通过也不等同 I52 mode/权限可用。 |
| 策略（产品层） | 用户可复用的市场/领域决策和目标意图。 | 认证脚本的账户/操作员控制、provider API、资源生命周期、交易执行状态和底层权限实现。 |

当前认证源码观察与目标职责要分栏记录：三套 `cases/<ID>/run.py` 进入各自的 `certlib.runner.main_case`，runner 动态加载 `Strategy.run(ctx)` 并注入 case client/context；A0 调用链清单指出这 99 个策略文件没有导入 Backtrader，当前链路没有组装 Backtrader `Cerebro`、Feed 或 Broker。因此，文件名中的 `strategy` 是认证场景驱动，不能据此断定它就是目标 Backtrader 用户策略。

## 3. 33 类行为的候选归属

“候选主责”仅供逐案 review 起步；`+` 表示该行为还需要该 owner 的独立义务或事实。实际三 venue 结果必须分别填写。

| Case ID | 公开源码描述的行为 | 候选主责与协作 | `RISK` 的正确用途 / 注意事项 |
|---|---|---|---|
| B01 | crossing fill 加 resting order 生命周期 | Execution；venue adapter 负责成交/队列语义和状态映射 | `DANGEROUS` 仅保留旧入口门槛；不代表 Risk 是场景主责。 |
| B02 | 多个 resting orders 接受后批量撤销 | Execution + venue adapter | `WRITE` 不能据此认定目标账户已获写权。 |
| C01 | 登录、session ready、基线账户/持仓/订单读取 | venue adapter + Runtime session 生命周期；harness 保留认证前置 | `READ` 不证明凭据、账户或 endpoint 的实际权限。Binance 可选 service 路径单独记录。 |
| E01 | 资金不足导致 venue 拒绝；SimNow 有界多次 resting 探测并清理，Binance/OKX 为单次超额下单且各自核查残单或持仓 | venue adapter 拒绝规范化 + Execution 订单/清理状态 | `WRITE` 是旧 runner gate；本场景要观察 venue 拒绝，不能由 Risk 预先吞掉目标拒绝 oracle。 |
| E02 | 在确认无持仓后，故意提交 close 方向单以观察 venue 拒绝 | venue adapter 拒绝规范化 + Execution 状态/残单处理 | `WRITE`；源码明确意图是 venue rejection，不应按“Risk 风险控制测试”简化。 |
| E03 | 故意越出 venue 价格带，观察 venue reject 并确认无残留 | venue adapter 价格带响应 + Execution 状态/残单处理 | `WRITE`；源码明确绕过 local validation。 |
| EM01 | 操作员撤销 execution admission，验证拒绝后恢复并完成有限订单周期 | Runtime/授权边界 + Execution no-dispatch；若命令走 Gateway 则增加 Gateway 义务 | `WRITE` 表示旧入口的控制/写门槛，不是通用 Risk 限额。 |
| EM02 | pause 时拒绝请求，resume 后完成订单周期 | Runtime 控制状态 + Execution 派发门 | `WRITE`；pause/resume 与市场风险政策分开。 |
| EM03 | 强制 logout、key/session loss 后建立新 session | venue adapter 识别失效 + Runtime 恢复 + Monitor 记录；三 venue 分别描述 | 标签跨 venue 不同，且行为机制不同；不可用同一 RISK 或模板覆盖。 |
| L01 | fill 与 trade row / OrderRef 关联、最终持仓回平 | Execution 交易/订单关联 + adapter ID 映射；Monitor/TradeLogger 作日志投影 | `WRITE`；日志不能成为交易事实的唯一来源。 |
| L02 | session system log 的 login/query 代次一致性 | Monitor 日志/关联 + adapter session 事件；harness 保留日志 oracle | `READ`；Binance service read 变体另行核实，不等同 Gateway。 |
| L03 | monitor event-hook 捕获账户查询事件 | Monitor + adapter event source；harness 检查 snapshot | `READ`；event hook 连接存在不等于产品 monitor 已装配。 |
| L04 | 基于 venue 下限价与半 tick 的本地价格校验拒绝，确认不派发 | adapter instrument rule + Execution no-dispatch；若另有组合限制才加 Risk | `READ` 是有意在发送前拒绝的用例，不能推成“没有写意图”。 |
| M01 | monitor readiness、session generation 和账户事件 | Runtime ready/session 判定 + adapter 事实 + Monitor 输出 | `READ`；monitor 观测值不独自授权运行。 |
| M02 | 外部 stop/disconnect 被观察，且不提交订单 | venue adapter 的中断/stop 事实 + Runtime 状态转换 + Monitor 记录 | `READ`；不要把本地断开伪造成 venue 事件。 |
| M03 | 仅一个 fresh session 恢复并绑定同代次的账户基线 | Runtime 恢复顺序 + venue adapter 新 session/query | `READ`；连接成功不是完整恢复证明。 |
| M04 | monitor 对 submit 事件记录一次，随后订单可撤销并到终态 | Monitor 主 oracle + Execution 事件 + adapter 状态 | `WRITE`；submit 是触发，monitor 是主要断言对象。 |
| M05 | monitor 对 submit/cancel 两类事件记录，随后订单到终态 | Monitor + Execution 事件 + adapter 状态 | `WRITE`；同上。 |
| O01 | 多次 open submission 每单观察到一个 monitor insert event，最终清理 | Monitor 去重/关联主 oracle + Execution 生命周期 + adapter 状态 | `DANGEROUS` 不等于 Risk 主责；避免重复采集和订单副作用是不同义务。 |
| O02 | 开仓成交后提交 reduce order，验证 resting、撤单和最终 flatten | Execution 生命周期 + adapter close/offset 语义；Risk reduce-only 另列 | `DANGEROUS` 是旧 gate；将“减仓政策”和“场所 offset/订单状态”拆开。 |
| O03 | 重复 cancel 的结果被记录且订单仍保持终态 | Execution 幂等/终态 + adapter 重复撤单结果映射；若有事件要求则加 Monitor | `DANGEROUS` 只表示旧用例门槛，不是组件归属。 |
| T01 | resting LIMIT 接受、可见、撤销至终态 | Execution + venue adapter | `WRITE` 不是 I52 授权。 |
| T02 | 开仓 fill、观察持仓、reduce close fill、最终回到零 | Execution + adapter fill/close/position 字段；Risk 检查单独列 | `WRITE`；场所今昨仓或 close-offset 语义不能塞进通用 Risk。 |
| T03 | 在授权前置下接受 resting order 并撤销至终态 | Runtime/授权 scope + Execution + venue adapter | `WRITE`；授权判定和订单语义是两条义务。 |
| TH01 | submit threshold 有效配置快照 | Monitor；Runtime 提供已解析配置/版本 | `READ`；不代表实际账户交易阈值生效。 |
| TH02 | submit-count threshold alert 恰好一次并清理 orders | Monitor 告警主 oracle + Execution submit 事件 + adapter 状态 | `DANGEROUS` 是旧入口 gate；alert 行为归 Monitor。 |
| TH03 | combined submit/cancel threshold 配置快照 | Monitor + Runtime 配置绑定 | `READ`。 |
| TH04 | submit+cancel 次数触发一次 combined alert | Monitor + Execution 事件 + adapter 状态 | `DANGEROUS`；不能据标签认定 Risk 是告警实现。 |
| TH05 | repeated-submit threshold 与 window 的配置快照 | Monitor + Runtime 配置绑定 | `READ`。 |
| TH06 | repeated-submit window 告警恰好一次并清理 orders | Monitor + Execution submit 事件 + adapter 状态 | `DANGEROUS`；告警 oracle 归 Monitor。 |
| V01 | 未知 instrument 被本地拒绝，dispatch 不存在 | venue adapter 的产品/合约查询 + instrument rule + Execution no-dispatch | `READ`；这是本地数据/规则校验，不是场所下单拒绝。 |
| V02 | 用 venue `PriceTick` 构造错位价格并本地拒绝 | adapter tick 来源/rule + Execution no-dispatch | `READ`；Risk 只管独立的账户/组合政策限制。 |
| V03 | 超限量本地拒绝：SimNow 使用 `MaxLimitOrderVolume`，OKX 使用 `maxLmtSz` 或套件 fallback，Binance 使用场景配置上限 | 场所元数据或场景上限按来源分别归属 + Execution no-dispatch；不得把配置上限当作 adapter 权威事实 | `READ`；不得仅按名称猜成账户 Risk 限额。 |

## 4. 关键源码样本及其分类理由

以下是分类依据示例，不代表其他 venue 的行为已得到逐案确认：

- SimNow `V01_strategy.py` 描述 unknown instrument 本地拒绝，并检查 `order_insert` 和 `order_action` 均未调用；`V02_strategy.py` 从 `PriceTick` 派生半 tick；`V03_strategy.py` 从 `MaxLimitOrderVolume` 派生超限量。`L04_strategy.py` 也是 half-tick local reject。四者均表明本地 instrument rule、dispatch guard 和 harness oracle 应分栏，不能让一个 `READ` 标签决定 owner。
- SimNow `E01_strategy.py` 描述多次 bounded resting probes 直到 venue insufficient-funds rejection；`E02_strategy.py` 和 `E03_strategy.py` 明确称为 genuine venue rejection 并有意绕过 local validation。分类重点是 adapter 把拒绝事实规范化、Execution 保持终态/清理；Risk 不应改变认证场景所测的拒绝来源。
- SimNow `TH02_strategy.py` 将 `client.event_hook` 连接到 `monitor.record`，验证 submit threshold 告警恰好一次；`O01_strategy.py` 也验证重复 submit 的 monitor insert 事件数与提交数一致。两者的 `DANGEROUS` 不是 Monitor 的 owner 判据。
- 三个 `EM03_strategy.py` 描述不同的操作：SimNow native `ReqUserLogout` / session 恢复；Binance listenKey 被删除后 renew 失败再创建新 key；OKX revoke credential 并用新 credential context 恢复。应保留三行独立义务，分别按 adapter 协议和 Runtime 恢复顺序核准。
- SimNow `EM01_strategy.py` 验证 disarm execution admission 后 write 被拒绝、恢复后可完成有界订单周期；`EM02_strategy.py` 验证 pause/resume。前者主要是运行授权，后者是控制生命周期，两者均需 Execution no-dispatch 保证，但不是相同的 Risk 规则。
- `T02` / `O02` 的行为包括成交、平仓、reduce/order offset 和持仓终态：Execution 负责订单/成交生命周期，venue adapter 负责各场所 close 语义，Risk 如需限制风险增量则作为独立子义务。不能因为 RISK 值较高就把所有逻辑塞给 Risk。

## 5. 可执行的只读分类规则

先以 Git 跟踪源码枚举目录，校验每个 venue 33 个 case 和两条源码路径，再执行静态 AST/文本解析；分类结果为**候选**，由 reviewer 核对后才能写入正式 A0 表。

1. 每条记录生成 immutable `case_key = venue + ':' + case_id`，另存当前源码 commit/path/hash。`CASE_ID` 与目录不一致、缺文件、解析失败或路径未跟踪，直接报错进入人工核验，不自动修复身份。
2. 分开静态提取 strategy 行为与 runner/harness 行为。允许读取 `.py` 源码和公开模板；不得导入/运行案例代码。真实配置只允许在另一个受授权流程中确认存在性或按批准边界核验，本规则不读取其内容。
3. 从 case docstring、`client`/`ctx` 的方法调用、局部 validator、事件 hook、结果 artifacts 和断言提取 `behavior_atoms`。仅抽取源码中实际出现的触发、结果和 no-dispatch/终态等副作用，不用 ID 前缀推断。
4. 根据规则来源分配 owner：
   - 读取/规范化 venue response、session event、product metadata → 对应 venue adapter；
   - 账户/组合策略限额或 permit → Risk；venue 产品规则需标注其 metadata 来源；
   - 订单/撤单/成交事实、dispatch/no-dispatch、UNKNOWN 或终态 → Execution；
   - threshold/config snapshot/告警/event capture → Monitor；
   - 实际 Gateway route、ACL 或远程控制命令 → Gateway；只有明确 route call edge 才分配；
   - mode/config/装配/ready/pause/recovery/resource lifecycle → Runtime；
   - 原 CaseResult、认证前置、case 安排与验收 oracle → Certification harness；
   - 产品信号与业务订单意图 → Strategy。若证据只证明 harness 顺序而不证明产品策略，Strategy owner 留空。
5. 对规则优先使用“事实来源 + oracle”两列。venue metadata 驱动的 `PriceTick`/`MaxLimitOrderVolume` 属 adapter instrument rule；Binance V03 的场景配置上限和 OKX 的套件 fallback 要单独标明来源，不能视作 venue 元数据；账户额度属于 Risk；二者都可能要求 Execution 在派发边界作 no-dispatch。超出以上规则或多义调用都标 `UNRESOLVED`，禁止回退为 Risk。
6. 迁移处置与组件 owner 分开决策：可复用 paper/live 机制，只有在发现活跃 paper/live caller 并确认其契约后才提议迁移；认证专用 operator 触发和断言先归 harness；replay/shadow/旧本地撮合按 I52 既定范围延后保留。任何保留、延期或退役都要记来源与保全路径，不能删除原 case 身份。
7. 自动一致性检查要求：99 个唯一 tuple；各 venue 恰有该 venue 33 个源码闭包；每个 tuple 都有候选或明确 `UNRESOLVED`；源文件中的 `CASE_ID` 匹配 tuple；`legacy_risk_label` 单独存储；所有 owner 均有 `owner_basis`；Formal status、mode 和 permission 不从源码生成。

建议的附加清单字段：

```text
case_key, original_case_id, venue, source_commit, run_path, strategy_path,
legacy_risk_label, harness_owner, behavior_atoms[], primary_owner,
supporting_owners[], owner_basis[], candidate_disposition,
mode_candidate, account_environment, permission, test_map,
formal_status_ref, review_state
```

`candidate_disposition` 和 `review_state` 是 I52 工作状态；它们不得改写正式认证状态。正式状态应保留原 tracker 值及来源引用，未核到 tracker 时仍为 `PENDING_TRACKER_REVIEW`。

## 6. 不能从本轮源码决定的事项

1. 各 case 当前有效 endpoint、账户、credential、direct/service 选择及真实权限；真实配置未读取。
2. 99 个正式逐案状态、时间、授权条件和 evidence 引用；本轮没有读取正式 tracker 或任何 evidence。
3. 哪些 case 已有当前活跃 paper/live 用户调用方、目标是否是产品 `Strategy`，或只能留在认证 harness；源文件本身不能证明运行态调用关系。
4. 当前哪些策略应映射为 I52 `paper` 或 `live`，以及 live-write 是否受支持。旧 `--live`、provider “Demo” 和 RISK 标签均不足为证。
5. 每个规则在新产品中最终属于 adapter instrument constraints、Risk policy 还是 Backtrader order validation API；需要 A1 冻结统一订单合同和明确来源字段。
6. 任一认证 case 是否能通过新的 Gateway。A0 公开源码称现有认证后端拒绝 `gateway_zmq`；Binance C01/L02 的 `service` 分支不能未经调用链确认而改称 Gateway。
7. 这份候选表不改变历史 `12 PASS / 3 BLOCKED / 84 NOT_RUN` 或 Optional16 状态，也不构成 case 迁移接受、真实账户接受或任何权限授权。
