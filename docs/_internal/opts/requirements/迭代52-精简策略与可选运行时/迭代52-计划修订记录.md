# 迭代 52 计划修订记录

本文件记录对 [迭代计划.md](./迭代计划.md) 及 A/B/C/D 子计划的修订。修订不等于降低原验收门槛；未完成项仍按 `BLOCKED` / `NOT_RUN` 记录。历史事实和已提交证据不因修订改写。

## R1（2026-10-31）

### 背景

- A2 双 Host 只读控制面测试已修正并通过（5 passed），A0 总清单与 A1 合同已完成事实重基线（commit `cdd2e35cd`）。
- 现状核对：`bt_api_run_contract 0.1.5` / `bt_api_runtime 0.1.12` 已提供严格 YAML 解析、ResolvedPlan、只读 direct/service 装配；尚无 CLI、permit、topology 选择、managed 或写路径。
- 旧 `backtrader_runtime` 仍被 38 个示例、40 个测试、3 个脚本引用；其延期/证据专属能力尚未拆分。

### 修订项

#### R1-1 首条 paper 竖切改选 Binance Demo（原：028/SimNow）

原计划 C1 以 028 Alpha003 + SimNow 作为首个端到端样板。修订为：**先以 Binance Demo（USD-M）直接写链路完成第一条真实 paper 竖切**，随后再迁移 028。

理由：028 `alpha003_strategy.py` 约 7,853 行、`run.py` 约 11,948 行且依赖 SimNow 原生 SDK/CPython 3.11/origin fence/arm-once/私有前置；Binance Demo 使用标准库 REST 与现有 `BtApiStore`/`BtApiBroker` 执行链，已有真实 T01/T03 前置与授权规则，能最快验证“配置→装配→Cerebro/Broker→provider→回报/对账→停机”的完整闭环。该调整只改变顺序，不取消 028 的 C1 义务。

#### R1-2 新 runtime 的 Backtrader 适配采用惰性模块

`bt_api_runtime` 基础导入必须不加载 Backtrader/SDK/provider（计划 §4、§5）。为此：

- `bt_api_runtime.__init__` 改为 PEP 562 惰性导出；
- 新增的可选 `bt_api_runtime.direct_backtrader` 模块在首次访问时才导入 Backtrader；
- `bt-api-runtime` 发行物把 Backtrader 适配声明为可选 extra（验证安装矩阵后确定具体 extra 名）。

该模块只负责 Backtrader Store/Broker/Cerebro 装配与生命周期，不成为第二调度器、撮合器或订单事实权威。

#### R1-3 F20 的“逐场所”解释

原计划 52-F20 要求“按原有正式入口和权限逐场所验收外部 paper/simulated account 的适用订单、回报、撤单/减险、对账及正常收尾”。修订明确：**每个 venue 至少一条经新运行时入口的真实 paper-account 代表性流程**即满足 F20 的“逐场所”范围；99 个正式 case 的逐案状态仍由原 tracker 管理，不因代表性流程通过而升级，也不得用旧实现成功调用代替新入口证据。

三场所均须有独立真实证据（Binance Demo、OKX Demo、SimNow），venue 之间不可互相替代。

#### R1-4 配置 schema 版本策略

v2 合同保持冻结，不回填字段。拓扑、run identity、permissions 等新增概念以 **schema v3** 引入，并保留 v2 的冻结测试与拒绝规则；v3 必须复用同一 parser 所有权，不在 Backtrader 另建 YAML parser。

#### R1-5 旧 runtime 退役（R10）前置

R10 按原计划执行，但明确：

- 当前 paper/live 活跃调用方全部迁移并通过后，才删除旧包；
- 延期/iteration-41 证据专属测试与 fixture 移入非安装保留位置，并给出 wheel 内容排除证明；
- 若仍有活跃调用方，R10 保持 `BLOCKED`，不得声明 `FRAMEWORK_COMPLETE`。

#### R1-6 三文件/行数口径

沿用交接说明：用户已将硬性三文件目标放宽为“每个交付文件 ≤800 非空行”。计划中“三文件硬条件”的表述按此口径执行：优先三文件；确有职责需要的小型辅助文件允许存在，但每个文件分别计数。

## R2（2026-10-31）

### 背景与结果

- 同一策略源码通过两个公开配置模板完成 **Binance USD-M Demo**（GTC 挂/撤）与 **OKX SWAP Demo**（IOC 开/平）真实 paper 往返；见
  `evidence/iteration52-c1-two-provider-paper-2026-10-31.md`。
- 过程中发现：OKX 订单事件能让 Broker 得到 Completed，但 SDK journal 未写入终态，导致后续写被 `unresolved_or_undurable_journal` 拒绝。
- 另发现 Broker 市价平仓价格未对齐 OKX tick，且单场所会话无法读取多场所共享 journal。

### 修订项

#### R2-1 同一策略、两个公开模板

052 示例泛化为 `052_provider_demo_roundtrip`：策略文件保持一份；`config.yaml`（Binance）与
`config.okx.yaml`（OKX）分别声明 venue/product/数量单位/订单风格；代码拥有的 profile 负责 SDK venue
key、币种、凭据变量名与 ledger 场所映射。该做法替代“每个场所复制一份策略”的方案。

#### R2-2 运行时 provider-confirmed unknown 恢复

在 SDK 增加 `reconcile_unknown_order_from_query`（journal 身份 + provider 终态事实），runtime 在
idle pump 与 shutdown 前调用；OKX IOC 路径增加有界 `close_delay_seconds` / `recovery_grace_seconds`，
让 journal 在后续写和停机前完成确认。该恢复只写 journal，不提交/重试/撤销订单。

#### R2-3 已知 SDK 缺口保持显式

OKX 事件流的终态确认缺口尚未在 SDK 根因层修复；当前以 provider 查询补偿。该补偿是运行时恢复能力，
不改变“provider 终态才算完成”的原则。其他策略/场所若遇到同类缺口，必须 fail closed 或显式恢复，
不得把 unknown 映射为成功。

#### R2-4 F20 覆盖状态

本轮新增 Binance 与 OKX 两个真实 paper 场所；SimNow 仍未执行，F20 保持 **PARTIAL (2/3 venues)**。
installed wheel、028 迁移、R10 旧 runtime 退役仍 OPEN；不得声明整体 `FRAMEWORK_COMPLETE`。



## R3（2026-10-31）

- SimNow 采用 **同一策略源码 + checkout-bound registered-sim 适配**（052 leaf：`simnow_paper.py`/`simnow_runner.py`/`paper_common.py`，按路径复用 013_3 `simnow_direct`，未复制 846 行模块）；真实 SA701 1 手 marketable 开仓 + reduce-only 平仓 PASS，disarm 0/0。
- 发现 registered-sim **撤单身份**限制：SDK 的会话内递增 OrderRef 与交易所跨会话订单历史冲突，legacy cancel 仅按 OrderRef、不带 typed OrderSysID/Front/Session；typed cancel 需要 managed decision journal。一次真实挂/撤尝试因此留下 OrderStatus 3 的排队订单，适配器正确 freeze，随后由独立 000 certlib 以 OrderSysID 撤销到 OrderStatus 5；账户 flat。
- 因此 F20 保持 **PARTIAL**：三场所 representative 流程已具备，但 SimNow 撤单路径与 CTP fee 未验收；最终接受运行使用开/平仓而非撤单。
- 下一修复：registered-sim 唯一 OrderRef 或 typed cancel target/journal 接线；之后 028 迁移与 R10。
