# 迭代 52 计划修订记录

本文件记录对 [迭代计划.md](./迭代计划.md) 及 A/B/C/D 子计划的修订。修订不等于降低原验收门槛；未完成项仍按 `BLOCKED` / `NOT_RUN` 记录。历史事实和已提交证据不因修订改写。

## R1（2026-10-31）

### 背景

- A2 双 Host 只读控制面测试已修正并通过（5 passed），A0 总清单与 A1 合同已完成事实重基线（commit `cdd2e35cd`）。
- 现状核对：`bt_api_run_contract 0.1.5` / `bt_api_runtime 0.1.12` 已提供严格 YAML 解析、ResolvedPlan、只读 direct/service 装配；尚无 CLI、permit、topology 选择、managed 或写路径。
- 旧 `backtrader_runtime` 仍被 38 个示例、40 个测试、3 个脚本引用；其延期/证据专属能力尚未拆分。

### 修订项

#### R1-1 首条 paper 竖切改选 Binance Demo（原：028/SimNow）

原计划 C1 以 028 Alpha003 + SimNow 作为首个端到端样板。修订为：**先以 Binance Demo（USD-M）直接写链路完成第一条真实 paper 竖切**，随后再迁移 028。

理由：028 `alpha003_strategy.py` 约 7,853 行、`run.py` 约 11,948 行且依赖 SimNow 原生 SDK/CPython 3.11/origin fence/arm-once/私有前置；Binance Demo 使用标准库 REST 与现有 `BtApiStore`/`BtApiBroker` 执行链，已有真实 T01/T03 前置与授权规则，能最快验证“配置→装配→Cerebro/Broker→provider→回报/对账→停机”的完整闭环。该调整只改变顺序，不取消 028 的 C1 义务。

#### R1-2 新 runtime 的 Backtrader 适配采用惰性模块

`bt_api_runtime` 基础导入必须不加载 Backtrader/SDK/provider（计划 §4、§5）。为此：

- `bt_api_runtime.__init__` 改为 PEP 562 惰性导出；
- 新增的可选 `bt_api_runtime.direct_backtrader` 模块在首次访问时才导入 Backtrader；
- `bt-api-runtime` 发行物把 Backtrader 适配声明为可选 extra（验证安装矩阵后确定具体 extra 名）。

该模块只负责 Backtrader Store/Broker/Cerebro 装配与生命周期，不成为第二调度器、撮合器或订单事实权威。

#### R1-3 F20 的“逐场所”解释

原计划 52-F20 要求“按原有正式入口和权限逐场所验收外部 paper/simulated account 的适用订单、回报、撤单/减险、对账及正常收尾”。修订明确：**每个 venue 至少一条经新运行时入口的真实 paper-account 代表性流程**即满足 F20 的“逐场所”范围；99 个正式 case 的逐案状态仍由原 tracker 管理，不因代表性流程通过而升级，也不得用旧实现成功调用代替新入口证据。

三场所均须有独立真实证据（Binance Demo、OKX Demo、SimNow），venue 之间不可互相替代。

#### R1-4 配置 schema 版本策略

v2 合同保持冻结，不回填字段。拓扑、run identity、permissions 等新增概念以 **schema v3** 引入，并保留 v2 的冻结测试与拒绝规则；v3 必须复用同一 parser 所有权，不在 Backtrader 另建 YAML parser。

#### R1-5 旧 runtime 退役（R10）前置

R10 按原计划执行，但明确：

- 当前 paper/live 活跃调用方全部迁移并通过后，才删除旧包；
- 延期/iteration-41 证据专属测试与 fixture 移入非安装保留位置，并给出 wheel 内容排除证明；
- 若仍有活跃调用方，R10 保持 `BLOCKED`，不得声明 `FRAMEWORK_COMPLETE`。

#### R1-6 三文件/行数口径

沿用交接说明：用户已将硬性三文件目标放宽为“每个交付文件 ≤800 非空行”。计划中“三文件硬条件”的表述按此口径执行：优先三文件；确有职责需要的小型辅助文件允许存在，但每个文件分别计数。**（本句的“小型辅助文件允许存在”已由 R5-1 撤回；机制代码必须按职责归位，不得留在示例目录当本地副本。）**

## R2（2026-10-31）

### 背景与结果

- 同一策略源码通过两个公开配置模板完成 **Binance USD-M Demo**（GTC 挂/撤）与 **OKX SWAP Demo**（IOC 开/平）真实 paper 往返；见
  `evidence/iteration52-c1-two-provider-paper-2026-10-31.md`。
- 过程中发现：OKX 订单事件能让 Broker 得到 Completed，但 SDK journal 未写入终态，导致后续写被 `unresolved_or_undurable_journal` 拒绝。
- 另发现 Broker 市价平仓价格未对齐 OKX tick，且单场所会话无法读取多场所共享 journal。

### 修订项

#### R2-1 同一策略、两个公开模板

052 示例泛化为 `052_provider_demo_roundtrip`：策略文件保持一份；`config.yaml`（Binance）与
`config.okx.yaml`（OKX）分别声明 venue/product/数量单位/订单风格；代码拥有的 profile 负责 SDK venue
key、币种、凭据变量名与 ledger 场所映射。该做法替代“每个场所复制一份策略”的方案。

#### R2-2 运行时 provider-confirmed unknown 恢复

在 SDK 增加 `reconcile_unknown_order_from_query`（journal 身份 + provider 终态事实），runtime 在
idle pump 与 shutdown 前调用；OKX IOC 路径增加有界 `close_delay_seconds` / `recovery_grace_seconds`，
让 journal 在后续写和停机前完成确认。该恢复只写 journal，不提交/重试/撤销订单。

#### R2-3 已知 SDK 缺口保持显式

OKX 事件流的终态确认缺口尚未在 SDK 根因层修复；当前以 provider 查询补偿。该补偿是运行时恢复能力，
不改变“provider 终态才算完成”的原则。其他策略/场所若遇到同类缺口，必须 fail closed 或显式恢复，
不得把 unknown 映射为成功。

#### R2-4 F20 覆盖状态

本轮新增 Binance 与 OKX 两个真实 paper 场所；SimNow 仍未执行，F20 保持 **PARTIAL (2/3 venues)**。
installed wheel、028 迁移、R10 旧 runtime 退役仍 OPEN；不得声明整体 `FRAMEWORK_COMPLETE`。

- SimNow 采用 **同一策略源码 + checkout-bound registered-sim 适配**（052 leaf：`simnow_paper.py`/`simnow_runner.py`/`paper_common.py`，按路径复用 013_3 `simnow_direct`，未复制 846 行模块）；真实 SA701 1 手 marketable 开仓 + reduce-only 平仓 PASS，disarm 0/0。

## R4（2026-10-31）

### 背景与结果

- runtime `0.1.15`：`DirectBacktraderSession` 在构造期拒绝任何 enabled 插件（`plugin_composition_unavailable`），与离线 `doctor` 的判定一致；disabled 插件条目仍接受。该措施关闭“CLI 报 blocked、程序化会话却静默回退 direct”的不一致。
- 052 增加 production 绑定模板 `config.live.yaml`，其 provider/endpoint/account/credential/scope、凭据变量名和写能力与 Demo 模板完全分离；grant 的 `allow_live_write` 在本示例固定 false。三条 live 路径分别停在写授权、凭据解析和 live 写授权，Store/Broker/传输均未启动；证据见 `evidence/iteration52-f06-live-boundary-2026-10-31.md`。
- 运行时新增 11 项隔离测试，覆盖 endpoint/account/credential/scope 引用错配、paper+production、live+demo、grant 环境/模式/品种绑定，以及 parser 的未知能力与 deferred 模式拒绝。

### 修订项

#### R4-1 F06 的判定口径

F06 验证的是“配置、装配和隔离合同”，不要求真实生产会话。因此 F06 可在 **LIVE-BOUNDARY** 层级判 PASS：paper 只绑定 Demo；production 模板引用/凭据/endpoint 与 Demo 分离；live 需 production profile + 显式 `allow_live_write`，未授权在传输前拒绝。真实生产账户、真实生产凭据仍不提供、不连接、不授权（F14/F20 的相应边界不变）。

#### R4-2 插件与 topology 的支持声明

本轮 direct 是唯一受支持的 paper/live 装配 topology；`plugins` 中任何 enabled 条目都被显式拒绝，不在本轮提供插件组合。schema v2 的未知字段（含 `topology`/`permissions` 等）由 parser 以 `unknown_field` 拒绝，因此不存在“请求 managed 后静默回退 direct”的路径。若后续需要 service/managed topology，须按 R1-4 以 schema v3 引入并单独验收；本轮不得用 fake 或旧 `ServiceExecutionSession` 冒充新 topology 通过。

#### R4-3 示例 live 通道的授权锚点

示例的 live 写授权只来自调用方注入的 `DirectWriteGrant`，且 `paper_common.build_grant` 固定 `allow_live_write=False`。这只证明示例不会自发写入生产，不构成生产准入；生产 permit/issuer 属 F14，仍未实现。（`paper_common` 本身按 R5 归位到 runtime，该固定值随迁。）

## R5（2026-10-31）

### 背景

用户复核指出 `examples/unified/052_provider_demo_roundtrip/` 存在示例目录内的机制副本：
`simnow_paper.py` 1016 非空行、`simnow_runner.py` 429、`paper_common.py` 113。计划原文
（`迭代计划.md` §“三文件目标与启用模型”与 R8 行）要求「三文件是**用户交付界面**，不是把内部实现复制到三个大文件」
「所有本轮活跃 helper 按职责迁入 Backtrader、`bt_api_runtime`、对应 SDK 插件或测试支持」，并明确
「不得以…整套本地 adapter 副本」充作完成。`simnow_paper.py` 还直接突破每个交付文件 ≤800 非空行上限。

### 修订项

#### R5-1 撤回 R1-6 的放宽口径

R1-6 中「确有职责需要的小型辅助文件允许存在」一句**没有计划依据，现予撤回**；R1-6 的其余内容
（逐文件分别计数、≤800 非空行）继续有效。恢复计划原口径：优先三文件；机制代码必须按职责归位到
Backtrader / `bt_api_runtime` / 对应 SDK 插件 / 测试支持，而不是留在示例目录里当本地副本。
不得为了满足行数或文件数限制而删除已要求的功能或降低验收门槛。

`entry_tier.py` 不属机制 helper：它是迭代 43 规定的**每目录逐字副本**（目录可移植性合同，
由 `tests/unit/test_iteration43_example_layout_boundaries.py` 固定），本轮保持原位。

#### R5-2 052 helper 归位映射

| 现有示例内代码 | 归位目标 | 依据 |
| --- | --- | --- |
| `paper_common.py`：grant 构造、证据写出与摘要 | `bt_api_runtime` 公开装配/证据 API | 生命周期与配置装配归 runtime |
| `simnow_paper.py`：CTP 专有映射（原生字段、`OrderRef`/`OrderSysID`/`FrontID`/`SessionID` 撤单身份、registered-sim arm/disarm/freeze、查询行核实） | SDK CTP adapter 层（`bt_api_ctp` / registered-sim 适配） | CTP 专有映射归 CTP adapter |
| `simnow_runner.py`：会话装配与停机编排 | runtime direct 会话的 CTP 支持路径 | 实际订单执行归 Execution，装配归 runtime |
| `run.py`、`provider_demo_roundtrip_strategy.py`、`config*.yaml`、`README.md` | 保持 052 用户界面 | 三文件/四件套交付界面 |

#### R5-3 归位后的验收要求

归位是**接线变更**：必须在新的 runtime/SDK 接线处重跑受影响场所的真实 paper 流程
（Binance Demo、OKX Demo、SimNow registered-sim）。既有 PASS 只作为历史证据保留，
不得自动升级为新接线的账户验收；重跑前矩阵相应行标注「接线变更待重验收」。

#### R5-4 实施顺序与提交

1. runtime/SDK 源码 + source/fake 合同先行，各自提交对应 `dev`，SDK 子包先提交再更新父 gitlink；
2. 再把 052 入口改为只调用公开入口，删除示例内机制副本；
3. 最后重跑真实 paper 竖切并按场所登记证据。
每轮独立验收、独立提交；不以「文件已删除」代替「能力已归位并被验收」。

#### R5-5 归属修正（同日，R5-2 表的落点澄清）

核对源码后修正 R5-2 的落点表述：core 早已存在框架自有的注册模拟盘适配器
`backtrader/stores/registered_sim.py`（4,930 非空行；`RegisteredSimWrapper`、`RegisteredSimStore`、
`RegisteredSimCancelTarget` 等合同），并以类属性 `registered_sim_route_id = "simnow-registered-v1"`
作为 Store/Broker 行为门的判据。由于 `RegisteredSimStore` 必须继承 `BtApiStore`，而 SDK 包不得
import Backtrader，**这份框架侧代码不能落进 `bt_api_ctp`**；R5-2 中「CTP 专有映射归 CTP adapter」
只适用于不需要 Backtrader 的原生语义（SDK 已有的 `arm_execution_for_registered_sim`、
`order_action`、查询过滤），那些保持原位。

因此 052 的归位目标改为：**消费 core 的 `registered_sim` 路由**，而不是新建第三个平行实现。
由此暴露并被登记为独立风险项的事实是：示例内 `simnow_direct.RegisteredSimStore` 与 core 同名类
互不 import、且**不带 route id**，导致 btapistore/btapibroker 中 6 处 `simnow-registered-v1` 门
（原生订单身份捕获、派发证据核验、`registered_sim_execution_unknown` 归类、因子 tick 源）
在所有既有真实 SimNow 运行中从未执行；core 路由此前只由 028 的 isinstance 门与测试承载，
无账户级证据。切换后这些门首次被真实行使，故必须逐场所重跑并重新取证，
示例副本的历史 PASS 一律不得转记为 core 路由的验收。

B 类执行基底（`execution_decision_journal` 等）向 `bt_api_execution`/`bt_api_ctp` 合并属于独立立项，
且必须排在「core `registered_sim` 收敛」之前或之后有依赖约束：core `registered_sim` 现在引用
`execution_decision_journal`，若先把它下沉 SDK 会让 SDK 反向依赖 Backtrader，顺序不可颠倒。
