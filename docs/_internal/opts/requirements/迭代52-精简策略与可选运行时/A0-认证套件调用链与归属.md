## 共享调用链

```text
cases/<ID>/run.py
  → 加入 case 目录和 venue 根到 sys.path；导入 certlib.runner.main_case
  → 解析 CLI，按案例目录定位并读取 config.yaml，计算 topology，执行 backend fail-closed 检查
  → 动态加载 <ID>_strategy.py，实例化 <ID>Strategy 并取得 RISK
  → 读取所需 env 名称；--live 分支再经过凭据、风险等级和本地写入 flag 门槛
  → certlib.make_client(...) 创建 venue client；构造 CaseContext(client=...)
  → client.connect() → strategy.run(ctx) → CaseResult → client.close() → 生成运行时结果/evidence
```

代表性 wrapper 路径：`examples/live/000_live_certification/simnow_penetration/cases/C01/run.py:12-21`、`binance_penetration/cases/C01/run.py:12-21`、`okx_penetration/cases/C01/run.py:12-21`。三者均添加 case/venue 路径、从对应 venue root 导入 `certlib.runner.main_case` 并调用；每个套件 33 个 wrapper 的静态 AST 结构一致。

三个 runner 都是独立 case harness：动态创建策略对象并传入 `CaseContext`，没有组装 Backtrader `Cerebro`、`DataFeed` 或 `Broker`；99 个 tracked strategy 文件也均未导入 `backtrader`。因此这些 certification case 不是当前统一 Feed/Broker/Store 策略装配入口。Binance 的 SDK 服务分支使用名为 `store.account` 的 service mount；这是 SDK account facade，不是 Backtrader `Store`。

## 本地风险等级与写入 gate

三个 runner 都把 RISK 映射为 `READ=0`、`WRITE=1`、`DANGEROUS=2`；未带 `--live` 时返回 DRY plan，不执行 strategy 的 live 链。进入 live 链后，WRITE 级至少需要 `--allow-write`；DANGEROUS 级先经过同一 write gate、再要求 `--allow-dangerous`。READ 不经过本地写 flag gate。凭据/env 是否实际满足、真实 API key 是否只读、账号是否 paper、审批 owner 是否已授权都不能由这个 CLI 逻辑推出。

源码还有需要迁移时修复的风险标签边界：三个 runner 将缺失或 falsey 的 `RISK` 回退为 `READ`，`RISK_LEVEL.get(risk, 0)` 对未知标签也按最低级处理；本次 99 个已清点标签均为已知值，不能因此将这条回退视为安全的通用规则。新入口应拒绝未知或缺失风险标签，而不是延用该行为。

Binance 的部分 docstring 只提及 C01；当前实现白名单和 runner 允许 C01/L02，L02 仅有静态接口对应，不代表端到端或账户验收通过。

`topology.execution`、`topology.risk`、`topology.monitor` 是独立的可选组件开关，与 strategy 的 `RISK` 常量不是同一字段；本 HEAD 的三套 backend 对这些开关均 fail-closed。`RISK=WRITE` 仅说明策略代码标签及 runner 本地门槛，不表示 I52 execution mount 已实现或授权写入。
