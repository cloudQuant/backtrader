# I52-B：运行时与首条交易链路

状态：规划；对应总纲 R2–R4、R6–R7。本文是迭代 52 的独立子计划，依赖 [I52-A](./I52-A-清点与统一合同.md) 与 [迭代计划.md](./迭代计划.md)。各轮可继续拆小并局部重叠，但每轮独立验收、记录和提交。

## 目标与边界

基于已接受的 A 合同，把本轮必要的配置编排、共享协议、身份/provider 边界、Backtrader 桥接和故障恢复能力迁到正确仓库；再用一个 A0 已盘点、正式验收入口可复用的既有 provider，打通单条 paper/live 交易链。先 source/fake，再真实组件组合和隔离安装；满足条件后才可申请并单独执行外部 paper-account 验收。

`bt_api_runtime` 当前基线在母计划中记录为占位仓库；实施前仍须核实当前 checkout，不把规划当成能力。paper 使用外部模拟账户。本轮实现 live 生产账户所需的交易路径及其授权检查，使用受控 fake 叶子验证订单、回报和恢复合同，同时验证配置、装配、权限隔离与安全拒绝；没有独立授权不得对生产账户做实际写入。replay/shadow/本地撮合不运行、不验收。

## 小轮顺序

### B0：选择一个现有 provider 和真实入口

从 A0 清单中选一个已有 provider/组件组合，条件是有可复用的公共接口及既有 formal paper-account 入口、case 身份和 guard。选择理由、产品/endpoints、direct 或已支持 service 拓扑、缺口与授权条件写入记录。不得为了做演示临时加 provider、endpoint、拓扑或新认证框架。此阶段每个 venue 最多维护一个当前实际 case/集成 blocker；共用 runner 的问题共修一次。连续两次 pre-case harness 失败，先诊断公共 runner，不再叠加 ad hoc harness。

### B1 / R2：Runtime 与共享合同

- 让 `bt_api_runtime` 只负责版本化配置/注册、预检、装配、生命周期/诊断及恢复协调；复用 A 的唯一解析结果。
- 跨组件 wire/schema 合同只有在版本、Python 矩阵、依赖与共享性被验证后才放入 `bt_api_base`；Backtrader 私有状态和认证专用 fixture 不外移到 base。
- 基础 runtime 导入不得强制加载 Backtrader、SDK 服务或 provider；选择框架/provider 功能时再按明示依赖装载。wheel、依赖和仓外导入均用隔离环境验证。

### B2 / R3：身份和 provider 边界

按实际引用迁移公共凭据引用解析、provider 来源绑定和 CTP 专有能力至其确认的所有者。保留受保护 source identity、authority 注入、DACL/ACL、scope seal、权限范围和失败关闭；先审计旧绑定消费者与不在当前 checkout 的依赖来源，不能通过复制同名代码或关闭校验假定身份等价。密钥/原始敏感回包不得进入日志或证据；离线验证与在线只读探测分开。

### B3 / R4：Backtrader 桥接与状态拆分

Backtrader 持有 Cerebro、Strategy、Feed/Store/Broker 绑定、Order 投影和自己的 session projection journal；`bt_api_execution` 持有 provider-neutral 派发/订单状态与 UNKNOWN 对账；runtime 编排；Gateway 和 Monitor 保持各自事实职责。分别核对现有 API 与真实生命周期，不复制执行权威或第二个 scheduler。验证普通 Cerebro、已选 Store/client、线程/路由、journal 语义和 CLI 的 paper/live 相关行为；明确缺依赖错误及无循环依赖。旧 runtime 在 D/R10 前不得删除。

### B4 / R6：单 provider 组合

只组合 B0 选择的既有 provider 和 A 已验证的 direct / managed 拓扑。分别覆盖插件启停、缺包、版本不符、重复装载/写 owner、部分启动失败与收尾、账户环境错配；显式 managed 不得 fallback。若两种拓扑中有一种当前未支持，则保留拒绝结果，不在本轮扩展拓扑。

### B5 / R7：单 provider 恢复与故障

对所选 provider 的 paper 与 live 配置边界验证断线、缺格/过期、重复或迟到事件、UNKNOWN、持久化失败、重启对账和有界停机。验证先对账再新增风险、不重发 UNKNOWN、撤单/经证明的减险与新增风险分开、来源/因果顺序可查、join/资源不确定性不伪报关闭。provider 特有的 endpoint、产品和恢复差异逐项标出；不外推成所有 provider 已支持。

## 验收顺序和接受条件

每个小轮按 `source → 真实框架/组件 + fake 外部叶子 → 隔离安装/仓外消费` 验收；Source 或 fake 不推断为真实 provider 账户通过。至少检查 schema/错误合同、导入边界、wheel/RECORD/依赖、组件来源和版本、direct/managed 明确状态、启动/失败/停止资源事实、两个 journal 的分工及订单/风险/监控权威。隔离安装不依赖仓内 `tests/datas` 或 `.codex-tmp`。

只有 B1–B5 达到相应层级后，才按既有授权规则安排单 provider 的真实外部 paper-account 验收；授权不是由本计划或 fake 测试赋予。实际调用只走对应既有 formal entry 和原 guards，重新确认当前 source pins、账户 scope、freshness、权限、私有输入和 retained-host/consumed-generation 状态。不得重复成功调用或 unchanged retry，不读取晚到私密捕获。不可用/未授权的条目保持 `BLOCKED` / `NOT_RUN`，Fake 不是 paper PASS。live 交易路径的本地组件验证与未授权拒绝证明不等于生产账户验收。

## 复用与交付

复用 A 的配置/能力合同、母计划第 2–4、6 节状态所有权与错误语义、现有 50/51 runner、各组件的现有公开接口和已有测试。交付每个包的迁移映射、接口/版本/依赖清单、focused QA 与 installed consumer 记录、paper/live 故障矩阵、证据等级和未观察项；每轮标明 provider/product/topology 与所覆盖 case。

各仓库在现有 `dev` checkout 按小轮修改；验收后仅提交本轮明确路径，子包先于 `bt_api_py` gitlink，父仓最后按需更新。保留任何既有差异、历史测试和冻结证据，不创建额外开发 worktree。每轮记录父提交、repo/branch、范围、结果、证据级别、commit 和下一 blocker。生产账户写入不授权。
