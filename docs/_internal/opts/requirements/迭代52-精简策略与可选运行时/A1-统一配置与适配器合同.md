## 4. 当前合同：bt_api_run_contract schema v1/v2

本节按 bt_api_run_contract 0.1.5 的 README 和公开源码定义唯一有效字段/API；0.1.5 的 schema_version 1/2 字段表与公共入口经本轮源码核对未变。A1 仍未完整验收，但 schema 示例与 resolver 调用不再另拟一套字段名、DTO 或部署参数。

### 4.1 公共 API 与版本字段

公开 import 名为 bt_api_run_contract。当前实际入口和返回类型为：

    parse_config(source: Union[str, bytes]) -> Union[ValidatedRunConfig, ValidatedRunConfigV2]
    resolve_plan(
        config: Union[ValidatedRunConfig, ValidatedRunConfigV2],
        registry: Union[TrustedRegistry, TrustedRegistryV2],
    ) -> Union[ResolvedPlan, ResolvedPlanV2]
    validate_plan(
        plan: Union[ResolvedPlan, ResolvedPlanV2],
        config: Union[ValidatedRunConfig, ValidatedRunConfigV2],
        registry: Union[TrustedRegistry, TrustedRegistryV2],
    ) -> Union[ResolvedPlan, ResolvedPlanV2]

parse_config 只接收调用方已持有的 str 或 UTF-8 bytes，不接收 Mapping，不读文件、环境、registry 或网络。它按顶层 schema_version 分派，返回对应的不可变 DTO；resolve_plan 只接收 config 与 registry 两个位置参数。不存在 parse_config_text、parse_config_mapping 或带 deployment 参数的 resolve_plan 公共入口。

| schema_version | 必需顶层字段 | references 必需字段 | 当前含义 |
|---|---|---|---|
| 1 | schema_version、mode、environment、references、plugins | strategy、provider、endpoint、account、credential、scope | 兼容的六 ref 静态合同；没有 strategy_parameters 或 requested_capabilities 字段。 |
| 2 | schema_version、mode、environment、references、plugins、strategy_parameters、requested_capabilities | strategy、provider、endpoint、account、credential、scope、product、data_source、clock | 九 ref 静态合同；另校验有界纯数据策略参数和能力请求。 |

两个版本都拒绝未知字段，并要求 mode 与 environment 分别为 paper 或 live 且相等。replay 和 shadow 是已识别但 deferred 的 mode：parse_config 抛出 RunConfigError，code 为 mode_deferred，不返回 DTO。backtest、simulation、dry、demo、simnow 不是本合同的 mode；旧 schema v4 的本地 simulation/paper 不会自动迁移。

references 每个字段的值均匹配 字段名/[a-z][a-z0-9_-]{0,63}，例如 endpoint/paper_demo；它是符号引用，不是 URL、对象导入路径或凭据值。v1 plugins 是符合 [a-z][a-z0-9_-]{0,63} 名称到严格 YAML 布尔值的映射；v2 也使用此映射，最多 64 项。插件开关可通过 parser，但任何 enabled=true 都使 resolver 抛出 code=plugin_resolution_deferred。v1 没有 capability 请求字段。v2 的 strategy_parameters 必须是映射，最多 64 项；每个名称须为非关键字 Python 标识符，最多 64 字符、128 UTF-8 字节。值只允许 null、bool、32 位整数、绝对值不超过 1e12 的有限 float、最多 256 字符/512 字节且不含控制字符的字符串，以及列表和字符串键映射。每层 list/map 最多 64 项，嵌套最多 8 层，总节点最多 512；解析器将 list/map 转成不可变包装值。requested_capabilities 必须是至多四个唯一值，范围为 market.read、account.read、orders.paper.write、orders.live.write；写请求还必须与 mode 匹配。

### 4.3 静态解析、runtime 组装与明确延后项

v1 resolver 将一个完整六 ref route 与 environment 原子匹配。v2 将一个完整九 ref route 与 environment 原子匹配，并按 route 的 available_capabilities 检查只读 capability 请求，再用 code-owned strategy_parameter_contract 校验参数名称、required 项和顶层 exact 类型。部署方通过代码对象构造 TrustedRoute / TrustedRegistry，或其 V2 类型；这些类表示调用方的 trust assertion，不建立来源证明。resolve_plan 及再次调用的 validate_plan 只给出静态匹配结果，不解析 secret、不访问真实资源、不加载策略或插件，也不签发许可。

v2 parser 对 mode 匹配的 write 请求进行结构校验，但 resolver 对任一 orders.*.write 请求都返回 capability_resolution_deferred，即使 route 声明了它。v1/v2 中启用插件都会在 resolver 处 deferred。runtime README 0.1.12 描述的当前 source candidate 要求 v2 只读组装显式请求 market.read 与 account.read；静态 resolver 本身只做请求子集检查，并不强制这两个 read 项。运行时 source candidate 使用代码注册的 RuntimeBindings / RuntimeBindingsV2、普通 Backtrader Cerebro 及 market_data_only Broker，不能下单；它不是授权服务，也不验证 factory 后面的真实 provider/account 身份。

当前公开 source/fake 证据不证明 provider/account 的真实身份和权限、source descriptor 的真实性、clock 校准、远端清理或生产部署。permit issuer、authorize、DeploymentBinding、PreparedRun、write 执行及 replay/shadow 装配都不是当前合同包的 API；当前 runtime 0.1.12 同样没有 permit 对象、CLI 入口、拓扑选择或写路径。这些是未来需求，须另有实现与验收，不能作为当前 schema 或函数签名书写。

### 5.2 状态与启动/停止

候选状态序列为 `UNPARSED → VALIDATED → RESOLVED → AUTHORIZED → PREPARING → READY → RUNNING → STOPPING → STOPPED`；任一阶段失败进入带稳定错误码的 `FAILED` 或 `BLOCKED` 并保留失败阶段。`READY` 仅说明已绑定所需组件且相应的连接/订阅、数据源与 clock preflight 成功；它不是交易许可、账户健康保证或下单承诺。Permit/许可是单独状态事实。

启动原则：schema v1/v2 可静态校验并由 resolver 按完整 route 匹配；runtime 0.1.12 source candidate 提供 v1/v2 paper/live 只读组装，v2 显式要求 market.read+account.read。source/fake 证据不是真实 provider/account 启动，也不验证真实资源身份/权限。写 capability 与插件启用仍 deferred；生产授权、资源身份、ready 和失败收尾证据未完成。当前没有 permit 对象、CLI 或拓扑选择，schema v1 的有限只读装配证据也不证明完整 Strategy startup 或失败清理。

停止原则：先阻止新策略订单意图，再按明确的策略/许可 policy 处理未决订单；不默默假定所有订单已撤销或已成交。完成 provider reconciliation/尾部事件处理后，仅关闭本 handle owned 的 Feed、Broker、Store、session、thread/transport；borrowed facade 不擅自关闭。关闭失败、回报缺口或未知在途订单使最终状态保持未决/受限，禁止静默 fallback。关停协议和每个 provider 的 close/readiness 证据目前均 NOT_PROVEN。Backtrader 历史快照 df0e0b887（2026-10-30）的一次启动失败后尝试 best-effort 清理，但清理完整性未确认；observer 通知与部分 Strategy 状态未确认，不能据此声称启动/清理生命周期已验收。

### 5.3 三类配置不得互相冒充

1. I52 user run config 由 bt_api_run_contract schema_version 1/2 解析：v1 有六个 references；v2 增加 product、data_source、clock，并包含 strategy_parameters 与 requested_capabilities。当前格式没有 adapter_ref 或嵌套 runtime/strategy 对象；应用代码通过 RuntimeBindings / RuntimeBindingsV2 将符号 route 绑定到策略类、feed names 和 provider factory。
2. SDK service_config.py 描述 service/client process role、binding、transport/service/scope；由 bt_api_py 自己解析和版本化。
3. SDK exchange config 描述 provider venue、HTTP/WebSocket/SPI connection、endpoint、authentication 和资产类型；由 bt_api_base/exchange adapter 自己解析。

当前 resolver 仅以 environment 与六个/九个 refs 匹配调用方提供的 route；v2 还校验 route 声明的只读 capability 子集和 code-owned 参数契约。bt_api_runtime 0.1.12 source candidate 提供 v1/v2 paper/live 只读组装；写 capability、插件执行仍 deferred，且当前无 permit 对象、CLI 与拓扑选择。source/fake 不验证真实资源身份、权限或账户。服务 schema v6、service schema v1、exchange Pydantic model 不能拼接成一个 YAML 大 schema。
