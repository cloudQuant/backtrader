## 4. 新合同 v1 候选（未冻结）

### 4.1 版本、字段与 mode

本节以下 YAML/API 为完整合同的候选，不等于 `0e9ba072` 已实现的 schema：该源码小轮当前暴露 `parse_config`，使用根字段 `schema_version`、`mode`、`environment`、`references` 和 `plugins`。策略参数、产品/时钟、可信引用解析和许可尚未实现；最终 schema 需在 A1 后续小轮确定，不得把下列示意当作已运行接口。

建议使用新根字段 `contract_schema_version: 1`，不沿用旧 `config_schema_version: 4`。新 `mode` 的公共枚举仅为 `replay`、`shadow`、`paper`、`live`。I52 实现和验收集合只有 `paper`/`live`；`replay`/`shadow` 明确标为 **FUTURE**。`backtest`、`simulation`、`dry`、`demo`、`simnow` 均不是 mode 别名；provider/environment 名可以单独引用，但不改变 mode。

候选 YAML 结构（ref 全部是假标识；不是可运行账户配置）：

```yaml
contract_schema_version: 1
strategy:
  ref: "registered:alpha003-v1"
  parameters: {}
runtime:
  mode: paper
  environment: paper
  adapter_ref: "registered:provider-product-adapter"
  product_ref: "registered:product-family"
  endpoint_ref: "registered:paper-endpoint"
  account_ref: "registered:paper-account"
  credential_ref: "secret-ref:paper-account"
  route_scope_ref: "registered:paper-order-route"
  data_source_ref: "registered:paper-market-data"
  clock_ref: "registered:provider-event-clock"
  requested_capabilities:
    - market.read
    - account.read
    - orders.paper.write
```

静态 schema 校验 mode 与 environment 必须独立且匹配：`paper` 只能配注册的外部 paper environment；`live` 只能配 production environment。`endpoint_ref` 必须是有名 ref，schema 不接受任意 URL；`account_ref`、`credential_ref`、`route_scope_ref` 必须来自同一个 trusted adapter/product/environment 的绑定关系。`credential_ref` 是引用，不含 key/token/password；只有在获得后续许可后，凭据 authority 才能解析该 ref，不能跨 environment fallback。

`requested_capabilities` 是请求集合而非授权集合；registry profile 与许可 authority 必须分别收窄、匹配并签发明确授权。至少检查 `(mode, environment, provider, product, endpoint, account, credential, route, data_source, clock, strategy_ref)` 全组绑定一致。未知字段/ref、字段错位、缺省 endpoint/account/credential/route、交叉 paper/live 凭据、production endpoint 配 paper、provider/product 不匹配、路由超出该账户权限、能力请求超授权集合，均 fail closed。schema 本身的有效性不意味着许可、可交易或 ready。

具体 production-live permit 的签发者、有效期/一次性策略与撤销语义仍为 **NOT_PROVEN**；live write 在本轮无授权且不运行。Paper 的 `orders.paper.write` 若未来接受，只能指向 provider 的外部 paper/simulated account，绝不能映射到 Backtrader 本地 hypothetical-fill Broker。`simnow` 是 CTP 环境标识，不是 mode。

### 4.2 纯 parser / DTO 候选 API

合同包候选 API：

```python
parse_config_text(text: str) -> RunConfig
parse_config_mapping(value: Mapping[str, object]) -> RunConfig
resolve_plan(
    config: RunConfig,
    *,
    registry: TrustedRegistrySnapshot,
    deployment: DeploymentBinding,
) -> ResolvedPlan
```

以上仅为候选签名，不代表已实现。前两个函数只处理已提供的内存文本/对象，不打开文件、不读取进程环境、不访问网络/账户/secret store、不加载模块/插件、不调用 Backtrader 或 SDK。建议复用严格 YAML 原则：SafeLoader、只允许字符串键、拒绝重复键/anchor/alias/tag、拒绝未知字段、拒绝 NaN/Inf、设有输入和嵌套深度上限、错误不包含原始值或 YAML 行文本。`parameters` 仅接受受限、可规范化的纯数据；策略参数的名字/取值范围再由可信策略描述校验。DTO 使用不可变映射/tuple；脱敏 `to_public_dict()` 只输出 mode、ref 名称、参数 key、digest 和安全错误代码。

这些是格式与纯数据约束，不证明原始文件来源可信。v4 的 file descriptor identity、private CTP block、loader weakref seal 不属于新 DTO。若运行入口需要配置来源审计，由 loader 在独立的 `ConfigSourceEvidence` 外层绑定 canonical path、文件摘要、读取策略与 registry 版本；该审计对象也不代表交易许可。

### 4.3 Plan 与启动 API 候选

建议将纯解析/解析计划与具副作用启动分层：

1. `parse_config_text` 产生 `RunConfig`；`resolve_plan` 仅在可信 registry snapshot 与 deployment binding 对应完整时返回不可变 `ResolvedPlan`。两步都不访问 provider 或 filesystem。
2. 单独的 `authorize(plan, permit)`（属于许可 authority，不属于 parser）验证 mode、account/environment、route、能力、策略和有效期，返回不能从 YAML 构造的 `AuthorizedPlan`。无 permit 时只可检查，不能 prepare。
3. runtime/adapter 层的候选 `prepare_cerebro(authorized_plan, adapter_factories, cerebro_factory)` 构造实际组件并返回生命周期 handle。配置不持有可调用对象或 Python import path；工厂必须来自与 plan/permit 同一可信 registry 与 deployment binding，准备阶段核验具体实现身份和绑定，不得以调用方另传的未绑定工厂替换获准组件。该工厂绑定合同及证据尚未实现，是 A1 纵切的阻断项。
4. 唯一执行入口 `PreparedRun.run(**kwargs)` 只调用一次普通 `Cerebro.run(**kwargs)` 并委托其策略/数据事件调度；它不是第二 scheduler。任何解析、解析计划、授权、factory、启动或 ready 失败都传播为有类型的 fail-closed 结果，不回退到 direct/mock/local-sim 路径。

第 2–4 步的包 owner、是否将 `PreparedRun` 放入未来 `bt_api_runtime`，以及它与现有 `run_configured_cerebro()` 的组合关系均 **NOT_PROVEN**。在选择 owner 前必须避免 dependency cycle：contract 不依赖 BT/SDK；BT 不依赖 runtime assembly；adapter/runtime 只能向 contract 和实际的 BT/SDK 边界依赖。`bt_api_runtime` 为空，因此目前不能声称这条方向可安装。

### 5.2 状态与启动/停止

候选状态序列为 `UNPARSED → VALIDATED → RESOLVED → AUTHORIZED → PREPARING → READY → RUNNING → STOPPING → STOPPED`；任一阶段失败进入带稳定错误码的 `FAILED` 或 `BLOCKED` 并保留失败阶段。`READY` 仅说明已绑定所需组件且相应的连接/订阅、数据源与 clock preflight 成功；它不是交易许可、账户健康保证或下单承诺。Permit/许可是单独状态事实。

启动原则：在任何 provider I/O 前完成纯 schema/registry/environment/route/permit 校验；开始后逐项记录创建/启动资源及 borrowed/owned；所有 required Feed/Broker/Store preflight 成功后才能 ready；strategy 只由 Cerebro 执行。由于 Cerebro 会启动/停止自己的 Feed/Broker，具体 adapter 必须声明哪些 hook 由 Cerebro 拥有，外层不得重复调用 start/stop。失败按反向创建顺序收尾，且每项记录结果；清理结果不确定时保留可见状态并阻止第二次启动。

停止原则：先阻止新策略订单意图，再按明确的策略/许可 policy 处理未决订单；不默默假定所有订单已撤销或已成交。完成 provider reconciliation/尾部事件处理后，仅关闭本 handle owned 的 Feed、Broker、Store、session、thread/transport；borrowed facade 不擅自关闭。关闭失败、回报缺口或未知在途订单使最终状态保持未决/受限，禁止静默 fallback。关停协议和每个 provider 的 close/readiness 证据目前均 **NOT_PROVEN**。

### 5.3 三类配置不得互相冒充

1. I52 user run config 描述“要运行哪个可信策略、希望哪个 mode、引用哪组可信 provider/product/account/endpoint/credential/route/data/clock profile”——schema 版本由合同 wheel 管。
2. SDK `service_config.py` 描述 service/client process role、binding、transport/service/scope；由 `bt_api_py` 自己解析和版本化。
3. SDK exchange config 描述 provider venue、HTTP/WebSocket/SPI connection、endpoint、authentication 和资产类型；由 `bt_api_base`/exchange adapter 自己解析。

统一 resolver 只能从第一种配置的 opaque refs 找到受信 registry 条目，再调用相应 SDK/parser/factory。服务 schema v6、service schema v1、exchange Pydantic model 不能拼接成一个 YAML 大 schema；同名的 `account_ref`、`environment` 或 `endpoint` 也必须在转换处重新核对身份和 scope。
