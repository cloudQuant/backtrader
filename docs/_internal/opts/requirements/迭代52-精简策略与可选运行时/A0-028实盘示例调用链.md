## 结论

1. 028 当前 `--mode live` 路径将连接地址限制为官方 SimNow CTP 配对。按交易模式标准，这属于外部模拟账户 `paper`，不是生产账户 `live`。CLI/tier 中没有 `paper`，也没有生产 endpoint/账户的装配路径。
2. 这是直连适配：`run.py` 以 `backend="direct"` 创建 `RegisteredSimStore`，然后使用 `BtApiBroker` 和 `BtApiFeed`。它没有用 `ServiceExecutionSession` 或 `ServiceReadProxy` 替代这条链。
3. `Alpha003TargetStrategy` 复用 Backtrader 的 `LiveFactorSet`、`LiveBarCohort` 和注册的 Alpha003 计算图，但其写执行校验明确要求 `BtApiBroker`、`RegisteredSimStore` 和 `simnow-registered-v1` 路由。因此目前还不是可直接切换生产 broker/store 的环境中立策略。
4. 代码和公开测试源覆盖了不少本地契约、合成 Store/provider 以及真实 Backtrader 对象的组合；README 明确说这些测试不调用真实 provider/account。本文不证明 SimNow `paper` 账户或生产 `live` 账户已连接、下单或验收。

## 调用链

```mermaid
flowchart TD
    A[run.py: run / mode + entry tier] --> B[run_live_epochs]
    B --> C[run_live:  profile + selection + journal]
    C --> D[RegisteredSimStore: CTP / direct]
    D --> E[CTP raw tick source]
    E --> F[BtApiFeed: 1-minute cohort feeds]
    F --> G[LiveBarCohort: complete planned batch]
    G --> H[Cerebro: ordinary runnext loop]
    H --> I[Alpha003TargetStrategy]
    I --> J[LiveFactorSet.snapshot]
    J --> K[get_alpha(3): registered FactorIndicator]
    I --> L[typed facts + target/risk/order plan]
    L --> M[ExecutionDecisionJournal + FactorExecutionCoordinator]
    M --> N[BtApiBroker]
    N --> D
    C --> Q[QueryRefreshLoop: serialized background refresh]
    Q --> D
    R[RunnerWallClock: UTC + monotonic + wait] --> G
```

`run.py:11791` 只接受 `dry`、`research`、`replay`、`live`；`entry_tier.py:15,73` 只定义 `dry`、`replay`、`live`（另有 `backtest` 到 `replay` 的别名）。tier 决策允许 CLI 保持或降低配置 tier，不能提升。`dry` 只做配置检查；`research` 读取已保存的分钟带并通过 `FactorStrategy`/普通 Cerebro 计算；`replay` 走 `CausalReplayBroker` 的本地因果撮合；`live` 进入 `run_live_epochs`，再由 `run_live` 装配 Store、Broker、Feed、cohort 和策略。Research/replay 不会创建 provider Store；它们不是 `paper` 账户证据。

### Live 组装顺序

`run.py:10282` 的 `run_live` 首先验证写入请求、风险预算、范围标识、时钟新鲜度、查询时限、journal/tape 和 SimNow profile。配置来自已选 `live` 运行所指向的环境变量，或仅供可信同进程调用者使用的 `_live_store_config_override`；此分支不读 `.env`。Profile 检查将有效 TD/MD 地址与 SDK 注册的官方 SimNow 配对比较，拒绝其他环境。

`run.py:10413` 的本地 `create_store()` 建立 `RegisteredSimStore(provider="ctp", backend="direct", allow_writes=write_enabled, preserve_raw_bars=True, ...)`，并检查固定 route id `simnow-registered-v1`。查询选品路径先等 Store ready、读取当前登录事实，在同一 Store/会话上收集 CTP 可见的合约目录和当前深度，再固定本 epoch 的产品、合约路由和授权目标。这个范围表示该连接可见的数据，不构成交易所全品种覆盖证明；未知分类或缺少选中合约的可用行情会阻断选择。后续 epoch 只有在前一 epoch 的退出检查通过后才开始新 Store。

分钟 Feed 使用 `store.getdata()` 取得 `BtApiFeed`，设置 `timeframe=Minutes`、`compression=1`、`backfill_start=False`、显式时钟、cohort source 模式、raw-event binding 和 bar watermark；随后每个 target Feed 都以精确名称注册到同一个 `LiveBarCohort`。CTP 因子源 binding 同时固定 calendar、target、产品/合约、交易日与预期 MD generation。cohort 密封后交给 Cerebro；Cerebro 使用 `exactbars=1, runonce=False, preload=False`，并用 ordinary feed mode 驱动完整分钟 cohort。

`BtApiBroker` 接收该 Store、精确 target→合约元数据、`require_complete_ctp_evidence=True`、`flatten_on_stop=False`；只读时 `market_data_only=True`。`FactorExecutionCoordinator` 将 Broker、durable `ExecutionDecisionJournal` 与 account/strategy/logical-run 范围绑定。Live 启动前先执行一轮 query refresh，再安装 `Alpha003TargetStrategy`，启动 refresh thread，最后同步调用 `cerebro.run(runonce=False, preload=False)`。

### 策略、因子、账户事实与指令

`alpha003_strategy.py:2664` 的 `make_alpha003_factor_spec` 以 `get_alpha(3)` 建 `FactorSpec`，field binding 为每个 target Feed 的 `open` 和 `volume`。注册公式在 `backtrader/research/alpha101/alpha003.py`：`-correlation(rank(open), rank(volume), 10)`；native/build 是同一公式的两种构图路径，不是第二套策略公式。

`Alpha003TargetStrategy.__init__`（`alpha003_strategy.py:3713` 起）按 Cerebro Feed 名称建立 target map，构造一因子 `LiveFactorPlan`，再调用 `LiveFactorSet.bind(plan, data_by_name, cohort=...)`。`LiveFactorSet`（`backtrader/research/live.py:412` 起）只接受精确的 `BtApiFeed` cohort 成员、同一 Cerebro 安装时钟、完整目标池和 cohort 发行的字段/source receipt；它在 Strategy owner 内创建普通 `FactorIndicator` 图。`snapshot()` 读取 cohort 最近发布的完整 batch，不推进或另建一个调度器。策略随后把该批次与因子快照送给 target 选择和 order planner。

Live 输入事实由控制刷新路径提供：登录/交易日、账户、持仓、未结订单、成交、合约/费用事实及针对执行目标的保证金/行情查询。查询按受限顺序进行，策略按 source/session/新鲜度和完整性消费快照；策略本身不直接调用 SDK 写 API。决策 tape 在可下单前记录完整 batch、来源、因子值/状态、目标决定和 order plan；协调器负责把经批准的意图送到 Broker。`notify_order`/`notify_trade` 回调把 Broker 通知投影到策略的有界事件记录。

写权限由多道条件组成：旧 `mode=live`、有效 tier `live`、`live.allow_writes`、显式 `--allow-write`、完整非空风险预算、持久 journal/范围以及精确每合约 arm template。Store 的 `allow_writes` 默认为 false 且构造后不可变；即使设为 true，实际 dispatch 仍需 SDK 发放的 scoped native capability。仅配置模板不会 arm，mode 名也不授予生产写权限。read-only 路径用 `market_data_only=True`；关闭 Broker 时禁止依靠自动 flatten。

## 时钟、线程、启动与关闭

### 时钟与执行线程

`RunnerWallClock`（`run.py:2309`）分别提供 host UTC、`monotonic_ns()` 和等待接口；`wait_interruptibly` 通过 Cerebro cohort waker 等待事件。它用于调度、deadline 和 freshness 检查，不改写交易所 tick/bar 时间、TradingDay、source clock domain 或 generation。Feed 侧将原始 CTP tick 映射成 minute bucket；cohort 对全目标计划时刻、完整性、source-age/future-skew 和 generation 作联合验证，缺腿或来源失效时不应被压成较小的目标池。

Cerebro 在 `run.py` 中以普通 `run()` 同步运行策略回调；本示例另起一个 `QueryRefreshLoop` 工作线程（`run.py:7697,8757`）串行刷新 account/order/trade/instrument/quote/margin facts。其查询有每轮和总时限、唤醒/停止边界；正常退出必须 `stop_and_join()` 成功。CTP SDK 内部回调/客户端线程具体由 SDK 管理，本次只审了调用方源码，没有实际运行或测量线程延迟/竞态。

### 生命周期顺序与证据缺口

- 启动：验证输入与 endpoint profile → 构造 journal/Store → readiness/login → 选品/网格 → source tick binding → Broker/cohort/Feed → 初始 query set → Strategy → refresh thread → Cerebro。
- 停止：SIGINT/SIGTERM/SIGBREAK 将有限 winddown 请求交给控制 loop；策略在 engine thread 使用刷新事实处理自己拥有的订单及 `run_end_policy`，并等待目标范围/回执满足 shutdown 条件。cohort waker 只唤醒引擎等待，不制造行情。
- 收尾：Cerebro 已运行时由 Broker 拥有 Store lifecycle，runner 先停止并 join refresh thread，再关闭 decision tape，检查 Broker/Store 与 CTP factor source shutdown 事实，最后关闭 journal；若 refresh 未 join，Store/journal 关闭会被跳过。setup 在 Cerebro 启动前失败时走有限 Store stop。每项清理结果附在返回/错误上；“不知道是否关闭”保持为未确认，不等于账户已平仓。
- Feed 停止会清除未完成 minute builder，不合成最后一根 bar。有限 cohort EOF 只接受策略已 ready 的 winddown；若撤单/平仓需要后续 Broker poll 或市场 bar，则本轮被报告为 blocked，而不是把进程退出当作已结清。
- `run_live_epochs` 对后续日历 bundle/CTP query epoch 要求前一轮 Strategy post-join、Broker/Store/journal/tape 清理证据完成，再读取/启动下一 epoch。这个是源码定义的闸门，不证明实际账户已完成一轮正常收尾。
- `discovery_lifecycle.close_discovery_store()` 是另一条只读发现连接的关闭 helper，只用于尚未启动 Feed/Broker/Cerebro 的零写 Store；它不在 `run_live` 的一般 Broker/Store 收尾中，也不能替代 live session 关闭证据。README 还指出 MD generation 0 的普通回执不足以证明 startup resource 已处置。

## I52 的模式映射、复用项与 owner 建议

交易模式标准（`docs/source/advanced/architecture/trading-modes_zh.md`）把外部模拟账户定义为 `paper`，把真实生产账户定义为 `live`；架构文档也明确这些语义不表示相应模式已实现。

| 028 旧路径 | 按 I52 语义分类 | 当前缺口 |
|---|---|---|
| `dry` / `research` | 验证或离线研究，既非 paper 也非 live | 保持为准备/分析入口，不当成交易模式。 |
| `replay` | 本地 `CausalReplayBroker` 仿真；I52 不做、不运行、不验收 | 之后单独决定 owner 与历史时钟/撮合边界。 |
| `live` + SimNow + read-only | 外部 SimNow 账户上的只读旧用法；endpoint 归类是 paper。它不是目标 shadow 定义的自动实现。 | I52 不应把旧 selector 或 tier 直接复用为 `shadow`。 |
| `live` + SimNow + 所有写闸门通过 | 外部模拟账户写入，归类为 paper 写路径，不是生产 live。 | 需以 paper mode 显式固定环境、凭据、账户、route 和 capability。 |
| 生产账户 | 当前代码没有该路径；`validate_official_simnow_store_profile` 会拒绝非官方 SimNow 配对。 | 必须单独实现并接受生产 endpoint、账户身份、写能力、订单/撤单/状态对账和 shutdown 生命周期。不得回退到 SimNow。 |

**建议的目标 owner（属设计建议，需 I52 决策确认）：**

- **模式选择、环境/账户校验、能力授予与组合入口：**由一个受信任的 I52 application/composition owner 统一负责；当前没有证据表明这应由每个示例单独负责，也不应让 `Alpha003TargetStrategy` 持有生产 endpoint/凭据逻辑。
- **策略/研究语义：**由 Backtrader 的策略与 research API 负责，包括 Alpha003 factor spec/registry、`LiveFactorSet`、cohort 输入要求和 Broker 的公共交易语义。
- **Provider adapter：**Backtrader 负责 Feed/Broker/Store 公共合同及其源事件规范化；`bt_api_py`/`bt_api_ctp` 负责对应 provider 的 SDK client、native callback、连接 generation 与 provider 特有命令/回报合同。生产 live 不能复用 `RegisteredSimStore` 的 SimNow 身份。
- **Secret/config 解析：**由 I52 确定的可信 runtime/composition owner 持有。旧 `backtrader_runtime` 的 013_3 zero-write 读取逻辑可作为 SimNow paper 配置来源，但它不应隐式成为生产 live 授权。

**可复用：** Alpha003 注册 class 和 factor spec；`LiveFactorSet`/`LiveBarCohort` 的完整 batch 与来源 receipt 约束；显式时钟/age gate；typed account/position/order/quote facts；决策 tape、durable journal、`FactorExecutionCoordinator` 和策略内风险语义（前提是 Broker 能力合同保持一致）。

**需迁移或拆分：** `run.py` 将 CLI/tier、SimNow profile、CTP query catalog、账户 refresh、journal/restart、order loop、shutdown 和日切全放在 example runner；不要整体复制为框架运行时。先拆出公共 mode/composition contract，再按 `paper` 和 production `live` 注入各自 Store/Broker/Feed。`Alpha003TargetStrategy._validate_live_execution_binding()` 对当前 Store 类和 route id 的硬校验应迁入 adapter capability/admission 边界，或被一个经过验证的通用执行能力合同替换。`protected_simnow.py` 保持 paper-only credential bootstrap，或由选定的可信配置 owner 替换；不能包装成 live grant。
