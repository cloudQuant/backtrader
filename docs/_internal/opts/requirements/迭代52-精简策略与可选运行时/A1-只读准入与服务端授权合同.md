# I52-A 只读准入与服务端授权合同

> 状态：**重新撰写的合同草案 / NORMATIVE CANDIDATE**。这不是已实现或已验收的能力，也不声称逐字恢复先前丢失的草稿。源码与合同层级分别标为 PRESENT、NORMATIVE CANDIDATE、NOT_PROVEN。

## 1. 目标与边界

同一份普通 Strategy 源码可以在受支持的运行环境中复用；paper/live 的账户、endpoint、scope、授权与 runtime 由部署和装配提供，不要求 Strategy 分支判断账户 mode、读取 key 或直接调用 provider。名称、配置、preflight、read_only 标记、capability 清单、健康状态及调用方自报 boolean 都不授予权限。

本合同只定义：本地可信部署如何预先授权一次有限的控制面 bootstrap；如何把远端已认证、已授权且仍有效的单个 registration binding 变为单 run、单 issuer 的只读 permit；以及不确定、过期、恢复和写路径如何 fail closed。它不宣称真实 endpoint、provider、账户、paper/live 写入或正式验收已通过。

## 3. NORMATIVE CANDIDATE：bootstrap 与 permit 阶段

### 阶段 0：本地解析，不连线

Parser、ResolvedPlan、静态 deployment/preflight 只检查结构与路由；不得创建 socket/transport、发 RPC、读取账户、创建 subscriber 或订阅。输入中的 trusted=true、principal 字符串、合成 receipt 或 capability 名称均不可制造 authority。

### 阶段 1：受信部署明确授权的控制面 bootstrap

Bootstrap 是本地受信部署授予的一次有限“尝试控制面连接/注册”权限，必须在创建 SDK Runtime/transport 前已存在，并绑定预期 service/endpoint、server peer key/transport profile、client credential/key reference、run owner/run_id、精确 binding/scope 和每个 mount 的显式 operation allowlist。它不声称远端已经认证，且本地应用门在阶段 2 前不允许读取 provider 账户或订阅市场。Registry 一旦接受注册，所授 operations 在服务端已可用；阶段 2 仅是受信客户端的本地 gate，不是远端二阶段 activation，不能阻止绕过该门的直接 RPC。若要求服务端独立激活，则现有边界为 GAP，必须 fail closed。

取得该本地 bootstrap authority 后，代码才可建立 transport 并调用 discover/register；远端身份仍须经真实 CURVE/ZAP principal 与 pinned peer/reply identity 验证，远端 grant 仍由当前 Host/Registry 判断。若现有 API 无法保证 bootstrap 只触及认证控制面、无法在 Runtime 构造前锁定 exact operations，或会自动触发账户/市场数据面动作，则该阶段标 GAP 并 fail closed，不得宣称 API 已安全隔离。此合同不要求臆造新的 authority service。

### 阶段 2：逐 binding 产生 read-only permit

Registry 成功 receipt 只作为核验输入，不自动变成本地 permit。受信 run owner 对每个 binding 独立核对：客户端预期 principal（服务端按 ZAP 映射并在 grant 中检查；未证明 receipt 含该认证结果）、客户端验证的 server peer/service identity 与 key、registration ID、service epoch、完整 typed scope、唯一活动 run_id、mount/instance/port/scope_ref、policy/requirements、逐 binding operations、lease expiry 和本地 route。每个 binding 的 receipt operations 必须与构造前显式 mount allowlist 按该 port 派生的投影完全相等，且全部 binding 的操作并集须无遗漏地等于 mount allowlist；缺项、多项或不符均拒发 permit。自签 boolean、preflight、config 或 synthetic receipt 不能替代真实受信 reply。

permit 至少绑定 schema/revision、run_id、issuer/service、peer profile/key reference、registration ID、epoch、mount、scope、exact operations、policy version 和 monotonic expiry；每个 issuer/binding/epoch 各一份，不合并宽权限。单次账户 snapshot 只能经对应 account permit；market stream 必须有单独明确的 stream lifecycle 权限，且只有进入阶段 2 后才能创建 subscriber 或 subscribe。market.subscribe/unsubscribe 不是无副作用的数据读取。Market 注册 RPC scope 包含 strategy/run 等受控维度，而 subscriber/event 使用不含 account、strategy、run 的 public stream scope；必须证明该 run 的注册 binding 与 public stream scope、subscription key、source 及 epoch 的映射一致，不能把两种 scope 当作相同。若当前接口或可信预期不能证明该映射，market permit 为 GAP 并拒绝数据交付。

### 阶段 3：每次业务调用前本地 gate 与服务端复核

Facade、Backtrader read proxy 和 I52 RunSession 的每次业务读前都检查 permit 未撤销、同一 run 仍活动、binding 唯一且 active、issuer/peer/epoch/scope/operation 精确匹配、deadline 尚未到期、没有 renewal-unknown latch。任何一项失败都不得调用 facade/Registry，也不得 direct/mock fallback。通过本地 gate 后，服务端仍必须逐请求复核 principal、registration、grant、capability、scope、policy、epoch 与 lease。

### 失效、unknown、恢复和写隔离

- 只凭在旧 deadline 前成功且字段全匹配的 renewal 可延长 deadline。renewal OutcomeUnknown 必须立即设置 per-binding unknown/revoked latch，停止之后所有业务读，即使 Runtime.healthy() 仍为 true、旧 deadline 尚未到，也不得让 maintain()/refresh() 绕过 gate。当前 SDK 未证明实现这个 latch；未实现即 fail closed。
- Expiry、NOT_REGISTERED、STALE_EPOCH、identity/scope/policy/capability 变化、peer/key 变化、revoke、Runtime close/failed 或 lease 无法观察都立即撤销相应 permit。
- register 已发送但 reply unknown 时，不签发 permit、不读账户、不订阅市场、不用新 key/session 令 run ready。服务端相同 principal/key/digest 幂等 primitive 已有，但 Runtime 没有证明暴露原 key/session/digest reconciliation；在原注册对账成功或可信 owner 确认旧 run 终止前保持关闭。不自动重放业务读或旧 subscribe。
- paper_write 与 live_write 使用各自受信部署 grant、Risk/Execution admission、精确账户/endpoint/route/run 与期限。paper 不推导 live；read-only permit 不授权写。risk README 中本地 permit/fake 不是账户审批；execution README 的 journal/outbox 与 UNKNOWN 不是 provider acknowledgement。引用：D:\bt_api_py\bt_api\bt_api_risk\README.md（约 L30-L56）；D:\bt_api_py\bt_api\bt_api_execution\README.md（约 L1-L33、L104-L139）。

## 4. NOT_PROVEN / GAP

1. 尚无统一 per-binding read_only permit 在 ServiceAccountClient、ServiceMarketClient、Backtrader ServiceReadProxy、I52 RunSession 的 enforcement proof。
2. I52 当前未证明在 Runtime 构造前强制显式 requested_operations allowlist，也未证明最终 receipt 与该清单按 port 的投影逐 binding 完全相等且并集无遗漏；默认推导可能把 order_entry 写操作纳入。
3. required renewal OutcomeUnknown 下的立即停读 latch 尚未实现；healthy/maintain 不能作为替代。
4. Registry 接受非空 run_id 不等于强制唯一；唯一活动 run_id 目前依赖可信 run owner，服务端强制 NOT_PROVEN。
5. 服务端幂等 register primitive PRESENT；客户端原 session/key/digest reconciliation orchestration NOT_PROVEN。
6. 本轮未重新读取计划、旧生命周期合同或任何源码文件；丢失草稿中的精确来源 hash/pin 表不可恢复，本重写不伪造或复用该表。下列路径及行段仅标识先前核对过的公开源码事实；本次未重新计算来源文件 hash。必须由后续 reviewer 重新绑定来源版本后才能把本合同用于实现验收。
7. SdkReadOnlySpec/preflight/config/read_only marker、local fake grant、合成 receipt 与本地测试均不能证明真实部署的 ZAP principal/key map、真实 server key pin、provider 身份或账户读权限。真实 endpoint acceptance 另行授权，不在本文证据范围。
8. 本文没有验收任何 replay/shadow/旧本地模拟模式，也没有验证 paper/live 写路径或真实账户。

## 5. 具体验收场景

| 场景 | 动作 | 必须观察的结果 |
|---|---|---|
| A0 无 bootstrap authority | 输入可信样式 boolean、错误 route 或合成 receipt，不给可信本地 credential/peer/allowlist | 在 transport/socket 前拒绝；RPC、账户读、subscriber、subscribe、permit 均为 0。 |
| A1 默认操作不可用 | 只读构造省略 requested_operations 或 receipt 含 allowlist 外操作 | Runtime/transport 构造前拒绝默认补集；receipt 多/少任一项均拒发 permit；order submit/cancel 为 0。 |
| A2 受控本地合成 bootstrap | 在受控本地 endpoint 使用真实 SDK transport/server/Host/Registry 源码、合成 CURVE keys、synthetic principal/grant、fake provider leaves；仅做 discover/register，先显式 allowlist | ZAP principal 由该受控 server key map 导出，Registry grant 精确接受，每个 binding 的 receipt 与其 port 投影完全相等、并集无遗漏；account/provider GET、subscriber/subscribe、order submit/cancel 均为 0。成功只证明这组源码与受控本地合成控制流；不证明外部部署、真实 principal/key/grant、真实 endpoint 或真实账户授权。 |
| A3 错 peer、身份、scope 或 grant | 使用错误 server key、未知 client key、principal mismatch、错误 scope_ref、stale epoch 或过宽 operations | 由对应认证/Registry 层拒绝；不得根据 capability/reply 合成 permit，无业务 handler 执行，无 fallback。 |
| A4 运行身份唯一性 | 在受信 run owner 创建唯一活动 run，再尝试第二或重用 run_id | owner 在 bootstrap 前拒绝重复/重用；服务端非空 run_id 接受不能代替该断言。 |
| A5 permit 隔离 | 对 exact account binding 发 snapshot；跨 binding 请求 snapshot/order write；market 没有 stream permit 时 start | 只有 permit 对应的 read 被允许；跨 scope/read/write 拒绝；未授权 market subscriber/subscribe 为 0。 |
| A6 renewal unknown | 在旧 deadline 前丢失 required renewal reply，观察 Runtime 仍 healthy 的可能路径，再调用 refresh | candidate permit gate 立即 latch 并令 account.snapshot 请求数保持不变；若仅凭 healthy/maintain 仍发请求则 FAIL。 |
| A7 register unknown/recovery | register 已发送后丢 reply；用 Registry 同 principal/key/digest 检查 active 幂等回读，另用相同 key 不同 digest 检查 CONFLICT | 当前服务端 primitive 应如源码所述；若 client 未用原 session/key/digest 对账，run 保持 closed，不用新 key/session 发业务读或订阅。 |
| A8 paper/live write | 同一策略源码加载不同装配，分别给出或不给出独立 writer grant | 策略源码无 mode 分支；read-only permit 无写权，paper grant 不可供 live 使用；缺权限则拒绝且无副作用。 |
