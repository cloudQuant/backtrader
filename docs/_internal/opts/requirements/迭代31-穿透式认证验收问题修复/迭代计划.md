## 二、问题清单

### P0（不修则整个验收无法完成）

#### F1 持仓模式不可配置：net 模式对双向持仓账户硬失败

- 现象：出厂配置下 `C01 / T01 / V01` 全部在 `cerebro.run()` 的 `broker.start()` 阶段抛出
  `ValueError: net mode received opposing position rows for one instrument`，用例连日志都没生成。
- 根因：
  - [btapibroker.py:485](../../../../../backtrader/brokers/btapibroker.py:485) `start()` 调用
    `_sync_positions(force=True, raise_errors=True)`，无降级路径；
  - [btapibroker.py:4025](../../../../../backtrader/brokers/btapibroker.py:4025) net 模式下同一合约出现多空两行即抛错；
  - 本地实测账户确实**同时持有 rb2610 多 6 手 + 空 6 手**（SHFE 双向持仓），
    这是交易所/柜台合法状态，不是脏数据。
- 用例侧同样缺失：`hongyuan_penetration/common/config.py:59` 的 `create_config()` 不产出
  `position_mode`，全目录 `grep position_mode` 无任何命中。
- 影响：**30/33 用例无法开始**（仅 M03、EM03 这类不启动 broker 的用例例外）。
- 修复方向（择一或组合）：
  1. `common/config.py` 的 `create_config()` 增加 `position_mode`（默认 `dual_side`，可用环境变量覆盖），
     `BtApiStore._config` 中的 `position_mode` 已被
     [btapistore.py:5318](../../../../../backtrader/stores/btapistore.py:5318) 用于
     `supports_position_mode()` 判定，改动最小；
  2. 框架侧：net 模式遇到方向相反的行时，选择**净额合并**或**自动识别为双向**，而不是直接抛错；
     至少要在异常信息中给出可执行的处置建议；
  3. 明确"认证账户前置条件"：若坚持 net 模式，则必须先手工把账户持仓调成单向/空仓，
     并在用例里做前置断言（`preflight`）后给出明确 BLOCKED 原因。

#### F2 用例的报单调用不满足 dual_side 契约（缺 `position_side`）

- 现象：注入 `dual_side` 后，14 个用例以
  `ValueError: dual_side mode requires both position_side and offset to be specified` 失败。
- 根因：[position_modes.py:77](../../../../../backtrader/position_modes.py:77) 规定
  dual_side 下 `position_side` 与 `offset` 必须同时给定；
  而用例只写了 `offset`（`T01/T02/L03/M04`）或两者都没写（`T03/M05/O01/O03/V01/V02/V03/E01/EM01/TH02/TH04/TH06/L01`）。
  T01 也失败，说明连"买单只给 `offset='open'`"这种下意识写法都过不了。
- 影响：所有涉及真实报撤单的用例（2、3、4、9、10、12、14、18、19、20、21、22、25、30）全部 FAIL。
- 修复方向：用例统一通过一个 `send_order()` 帮助函数报单，
  按 `position_mode` 自动补齐 `position_side`（`infer_position_side(isbuy, offset)` 已有现成实现）。

#### F3 行情通道只有偶发快照 tick，无法形成实时 bar

- 现象：33 个用例总计约 40 分钟连接期内，单个用例最多只记录到 6 个 tick；
  `B01/B02/O02/TH04/L04` 直接 BLOCKED "未收到行情数据"，
  `EM02/B01/B02` BLOCKED "未能通过种子 bar 触发"。
- 实测（独立最小复现，非用例问题）：
  ```text
  store.subscribe("rb2610")            -> supports_live_ticks=True
  60 秒内 store.poll_tick() 返回值个数 -> 1   （价格 4876，成交量 0）
  另一次 60 秒探测                      -> 0
  ```
  `md_client.is_ready = True`，说明不是登录问题；`_handle_md_tick`
  （[btapistore.py:2759](../../../../../backtrader/stores/btapistore.py:2759)）无去重/过滤逻辑。
- 影响：一切依赖"多根 bar / 真实成交 / 部分成交"的用例（8、16、28、29、33，以及 26）无法取证。
- 需要先分清责任方：
  1. 宏源仿真 MD 前置是否只推快照、不推连续 tick（需与柜台/机房确认，或换 simnow 7×24 环境对照）；
  2. 若环境正常，则检查 `bt_api_py` MD 回调注册与 `BtApiStore` 订阅时序
     （是否存在"订阅发出后 MD 才登录完成，订阅被丢弃"的竞态）。
- 修复方向：先做一次**独立的行情通道基线测试**（订阅 N 个合约 × 若干分钟，统计 tick 速率），
  把结论固化为证据，再决定是改环境用法还是改代码。

#### F4 用例超时与"首个 tick 到达延迟"竞争

- 现象：EM02 使用 `run_with_timeout(cerebro, timeout_seconds=20)`，
  实际首个 bar 在用例开始后约 28 秒才落盘（`EM02/logs/bar.log` 时间戳 09:41:24，
  用例 09:40:56 启动），于是 `bar_count == 0` → BLOCKED。
- 根因：用例超时值（20/25/30/45 秒）普遍小于"首次订阅到首个 tick/bar"的实际延迟。
- 修复方向：统一"等待首根 bar"的显式等待函数（轮询到 bar 或超时），
  并把超时收到 ≥90 秒；不要用固定的短超时赌首 tick 到达。

#### F5 本地校验在 dual_side 下永远走不到校验分支

- 现象：V01/V02/V03（错误防范三个必做点）在 dual_side 下失败于 F2 的报错，而不是本地拒单。
- 根因：调用顺序是
  [btapibroker.py:3542](../../../../../backtrader/brokers/btapibroker.py:3542) `buy()` 先
  `_normalize_order_meta()`（dual_side 缺 `position_side` 即抛错），
  而真正的本地校验 [btapibroker.py:2629](../../../../../backtrader/brokers/btapibroker.py:2629)
  `_validate_order()` 在 `submit()` 之后才执行。
- 影响：即便补齐 `position_side`，"参数非法的报单"是否仍会先被 meta 校验拦截，需要回归确认。
- 修复方向：明确 `position_side` 归一化与合约/价格/数量校验的先后契约。
  建议：**结构性参数（position_side）缺失属于调用错误，应抛错；但业务校验（合约/步长/手数）应在抛错之前**
  或至少在异常中携带可区分的错误码，避免"非法报单"被报成"持仓模式配置错误"。

### P1（会导致结论不可信或验收材料不达标）

#### F6 `account_position_unchanged` 用浮动盈亏整条记录比较 → 误判 FAIL

- 现象：TH01/TH03/TH05（纯阈值设置用例，不应有任何交易）被判
  `Strict reconciliation failed: account_position_unchanged`。
- 证据（TH01 两次快照，同一位置）：
  ```text
  before_action            current_price=4785.0  profit=5760.0
  after_action_before_stop current_price=4873.0  profit=11040.0
  ```
- 根因：[evidence.py:519](../../../../../examples/007_ctp/live_certification/hongyuan_penetration/common/evidence.py:519)
  `_stable_positions()` 把整条持仓 dict（含 `current_price / mark_price / profit / use_margin`）
  序列化后比较，任何行情跳动都会让"持仓未变化"判定失败。
- 影响：M01/M02/M03 同样是 `account_position_change: none`，本次只是没踩到 tick 才 PASS →
  **同一用例在不同时点结果不同，验收结论不可复现**。
- 修复方向：比较只保留"结构性字段"（`instrument/direction/volume/yd_position/today_position`），
  剔除盯市字段；或改为"成交/委托事件 + 持仓手数变化"判定。

#### F7 证据模型允许用例"自证"（自造 required event / evidence field）

- 现象：`EM02_force_logout` 类用例在 `pass_result(details={"events": ["strategy_trading_paused"], ...})`
  中**硬编码**所需事件（[EM02_pause_strategy.py:110](../../../../../examples/007_ctp/live_certification/hongyuan_penetration/cases/EM02_pause_strategy.py:110)）；
  EM03 的 `reason` 也来自用例自带 details。
- 根因：`details` 中的 `events` / 任意键都会被当成"已观测证据"：
  [result.py:209](../../../../../examples/007_ctp/live_certification/hongyuan_penetration/common/result.py:209)、
  [evidence.py:269](../../../../../examples/007_ctp/live_certification/hongyuan_penetration/common/evidence.py:269)。
- 影响：用例可以在**功能缺失**的情况下依然满足 required_events。
  EM02 的真实场景就是：即使 `broker.pause_strategy()` 不存在（用例用 `hasattr` 兜底、
  且不校验其存在），只要 `cerebro.runstop()` 能停引擎就会 PASS。
- 修复方向：
  1. `required_events` 只允许来自 **日志文件 / store 通知**；`details.events` 一律不参与判定；
  2. 用例禁止自带 required 同名事件，加一条离线单测守住这条约束（现有
     `tests/unit/live_certification/test_simnow_penetration_certification.py` 可扩展）；
  3. `evidence_fields` 只允许来自"本次事件 payload"，不接受 state_snapshots.json
     里的通用字段名（见 F10）。

#### F8 两个必做测试点是"恒定 BLOCKED"的桩

- E03（市场状态错误码）：`E03_market_state_error.py` 连上柜台后**无条件**返回
  `blocked_result("未观察到真实柜台市场状态远端拒单")`，既不尝试下单，也不区分时段 —— 永远不会 PASS。
- E02（持仓不足）：用例第一步查持仓，账户有多仓就直接
  `blocked_result("账户已有 rb2610 多仓 6.0，为避免误平仓跳过")`。
  在本次账户状态下 100% BLOCKED。
- 影响：必做测试点 23、24 在本轮没有任何证据；而实施计划 §七 却标注"已覆盖"。
- 修复方向：
  - E03：给出可执行方案（非交易时段/停板合约/受限交易所），或明确降级为"环境受限、以集成测试替代"，
    并在验收材料里如实标注；
  - E02：设计不依赖"账户无持仓"的复现路径（例如对无持仓合约平仓、
    或用本地校验前置条件断言 + 柜台错误兜底）。

#### F9 用例自检标准与 certification 门禁不一致

- L03：用例认为 `monitor.log` 里出现 `monitoring_summary` 就算通过，
  但 [certification.py:66](../../../../../examples/007_ctp/live_certification/hongyuan_penetration/common/certification.py:66)
  要求 `risk_monitor_event` + `metric`；
  实际本次 `monitor.log` 只有 1 条零单量的 `monitoring_summary`，于是被门禁降级为 FAIL。
- V01：用例不是用"非法合约代码"，而是对**合法合约**注入
  `contract_metadata={symbol: {"valid": False}}` 来触发本地拒单
  （[V01_invalid_instrument.py:50](../../../../../examples/007_ctp/live_certification/hongyuan_penetration/cases/V01_invalid_instrument.py:50)）。
  这只能证明"broker 会读自己的 metadata 开关"，**证明不了"合约代码错误会被拒绝"**。
- 修复方向：把每个用例的自检条件与 `certification.py` 的 required_events/evidence_fields
  做一致性校验（离线单测），V01 改用真正不存在的合约或直接构造非法 underlier。

#### F10 `evidence_fields` 可被快照文件里的通用字段名满足

- 现象：M03 要求 `timestamp`，但 `certification_evidence` 里并没有事件时间戳；
  该字段名被 `state_snapshots.json` 自身的 `timestamp` 键满足。
- 根因：[evidence.py:278](../../../../../examples/007_ctp/live_certification/hongyuan_penetration/common/evidence.py:278)
  把快照的全部键名并入 `field_names`。
- 影响：`timestamp / account_id_masked / gateway_key / instrument / price` 等高频字段几乎"永远满足"。
- 修复方向：字段证据只从"满足 required_events 的那条事件 payload"中提取，
  或对每个字段声明其允许来源（事件/快照/对账）。

#### F11 M02 用"主动 stop"冒充"连接断开"

- 现象：M02 判 PASS 依据的是 `started_store` 退出时的 `store.stop()` 产生的
  `session_stopped`（[evidence.py:202](../../../../../examples/007_ctp/live_certification/hongyuan_penetration/common/evidence.py:202)
  把它别名为 `store_disconnected`）。
- 监管语义："连接断开时能正常显示连接断开"通常指**异常断链的检测与展示**（CONNBROKEN/重连前），
  而不是自主有序登出。
- 修复方向：区分 `store_disconnect_requested`（主动）与 `store_disconnected_unexpected`（异常），
  M02 使用后者；或在用例中通过断开网络/停止 MD 前置来制造真实断链。

### P2（工程质量与材料一致性）

#### F12 两份 33 点用例集重复且已漂移

- `examples/007_ctp/live_certification/` 下同时存在 `hongyuan_penetration` 与 `simnow_penetration`，
  33 个 case + `common/*` 逐文件重复，且已出现实质性差异：
  - `config.py`：hongyuan 默认合约仍是 **`rb2605`**，simnow 已是 `rb2610`；
  - 文案/命名差异遍布每个文件。
- 影响：同一缺陷要修两遍，且极易只修一份（本次 `rb2605` 过期就是漂移的后果）。
- 修复方向：抽公共 suite 基类 + 环境 profile，两个环境只保留差异配置。

#### F13 默认合约 `rb2605` 已过期

- 实测 `store.get_symbol_info("rb2605")` 返回 `{}`；`rb2610/rb2701/rb2705` 正常。
- 位置：`hongyuan_penetration/common/config.py:25-26`（`DEFAULT_ORDER_SYMBOL/TICK_SYMBOL`）。
- 影响：即使解决 F1，默认配置下所有报单/行情用例仍会失败。
- 修复方向：默认合约改为可配置且**启动时校验合约可查询**，不可用直接 FATAL 而不是静默失败。

#### F14 覆盖率指标会给出"33/33 covered"的误导性结论

#### F16 实施计划 §七 的"已覆盖"标注与实测不符

### 7.3 复验中新发现的问题（按发现顺序）

#### F17a（本轮已修）：用例从未执行 CTP 类型化准入前置

报单被本地拒绝：`ctp_query_evidence_incomplete — New CTP exposure is blocked
until typed startup queries complete`。框架要求报单前
`store.get_ctp_preflight_snapshot()` 产出绑定当前会话的完整证据，且
`ctp_query_max_age_seconds=30s`，连接时查一次没用，必须在**报单前**查。
实测该前置对 rb2701 可完成（7.3 秒，`evidence_complete=True`）。
修复即 7.2 的 `ensure_ctp_trading_admission()` + 23 处布线。

#### F17b（跨仓库阻塞，本轮不可修）：SDK 执行门禁封死了 legacy CTP 直连路径的报单

准入前置通过后，报单在 SDK 层被拒：

```text
ctp_execution_gate_native_write_blocked
```

- 调用链：[btapistore.py:2514](../../../../../backtrader/stores/btapistore.py:2514)
  `self.trader_client.api.ReqOrderInsert(field, req_id)`、撤单
  [btapistore.py:2581](../../../../../backtrader/stores/btapistore.py:2581) `ReqOrderAction` ——
  走的是“公共原生 API 视图”。
- 安装的 `bt_api_ctp` **2.0.2**（2026-09-16 升级）在该视图上**禁止一切非读请求**
  （`_invoke_public_api_request`：`ReqOrderInsert/ReqOrderAction` 属 native write）。
- SDK 提供的类型化写入口 `submit_order_insert / submit_order_action` 要求：
  1. `configure_execution_gate(capability)` —— capability 只由 SDK 核心签发
     （`_issue_execution_capability_for_core`，私有下划线，"used only by the owning SDK"）；
  2. `arm_execution_gate(capability, authorization)` —— 一次性授权，绑定
     账户指纹/交易日/合约清单/策略身份哈希/执行周期；
  3. 环境证明 `_execution_environment_proof` 要求 **verified demo 环境**。
- 即：legacy `provider="ctp"` 直连路径在新 SDK 下**合法地无法报撤单**。
  这解释了为什么迭代 1 当年能下单（旧版 SDK 无门禁），而现在全部被拦。

**修复方向（需要单独立项，涉及 bt_api_py 仓库协作）**：

1. 首选：把认证用例的 store 切到托管 SDK 路径（`provider="btapi"` + demo 准入流程，
   即迭代 22 SA 示例的模式：审批回执、观测门、策略身份绑定）；
2. 或：与 SDK 侧协商给 legacy 直连路径一个显式的、同样类型化的准入入口；
3. 任何“绕过/降级门禁”的方案都不接受——这正是本仓库安全姿态的一部分。

**两条路径的传输事实（2026-09-17 核实）**：

| 路径 | 下单通道 | 是否经 ZMQ |
| --- | --- | --- |
| 直连 `provider="ctp"` | 进程内 `bt_api_ctp` 的 `TraderClient` 直接持有 **CTP 原生 API**（`CThostFtdcTraderApi`，编译 `.so`），[btapistore.py:2514](../../../../../backtrader/stores/btapistore.py:2514) 的 `ReqOrderInsert` 即原生调用，由 CTP 库自身 TCP 连交易前置 | 否，无中间进程 |
| 托管 `provider="btapi"` | 经 `bt_api_py.BtApi` 的**统一准入/授权/审计层**；传输 `transport_mode` 二选一：`direct`（默认，进程内直接持有各所客户端）或 `zmq`（经转发网关进程，`forwarding_config` 配端点，见 bt_api.py 构造参数） | 可选（仅 `zmq` 模式） |

即“托管=ZMQ”不准确：ZMQ 只是托管路径的可选传输，本质区别是是否经过 SDK 的
准入/授权层（`bt_api_ctp` 自身无 zmq，zmq 在 `bt_api_py` 的 forwarding 层）。
另注意：backtrader 侧**已存在** SDK 审批臂装入口——
[btapistore.py:12605](../../../../../backtrader/stores/btapistore.py:12605)
`arm_execution_from_approval` + `CtpExecutionApprovalCapability`
（[btapistore.py:160](../../../../../backtrader/stores/btapistore.py:160)
`_is_ctp_approval_capability`），legacy 直连 wrapper 只是没有接它——
这为 T31-16 提供了现成挂点。

#### F18（观察项）：M03 断线重连偶发 `CTP market data login did not become ready within 20s`

重连后 MD 登录 20 秒未就绪，属环境时序抖动或 SDK 重连等待不足，复跑可过；
