## 当前源码观察

1. **本地 intent 和 claim。** Risk `pretrade/ledger.py` 的 `risk_pretrade_control_intents` 保存账户 scope、cause、mode、范围、latch、规则、状态和行版本，但没有持久保存经认证的 Gateway 来源与代际绑定。`PretradeEngine._apply_control` 在本地事务中检查 latch、CAS 将 PENDING 改为 UNKNOWN，再在事务外调用控制端口；`_record_control` 对即时 `REQUEST_DENIED` / `TRANSPORT_NOT_STARTED` 分别投影 REJECTED / PENDING，其他结果维持 UNKNOWN。`_record_control` 的 `status_only` 条件仅作字段诊断；当前内部调用路径没有传入 `status_only=True`，也没有对 UNKNOWN 自动调用 status 查询，因此不能将该比较视为正在核对来源；即使字段一致也不建立来源权威。这是当前 WIP 的静态观察，不是已验收的跨服务协议。
2. **恢复和依赖动作。** 采样时 `_retry_intents` 只扫描 PENDING 控制项，不自动重发 UNKNOWN；`_apply_control` 也只处理 PENDING。`_apply_cancel` 对带 `wait_cause_id` 的撤单意图，在控制项不存在、REJECTED 或 SUPERSEDED 时作相应保守处理；即使历史行显示 APPLIED，也因缺可信来源绑定而不放行等待中的撤单。因此当前 WIP 中依赖 STOP_NEW 的 `stop_new_and_cancel` 路径不可用；不能把单独运营撤单、已有控制请求或其他 Gateway 功能一概称为不可用。
3. **传输字段不是来源证明。** SDK `GatewayControlAdapter` 检查本地注册状态和返回字段形状；status 的 `NOT_FOUND` 是该次查询观察，既不证明从未执行，也不证明跨代未发送。Gateway `direct_control` 的记录含 account、origin、generation 等字段，但它们的存在或字符串相等本身不建立 Risk 与 Gateway 的共同授权、来源和跨代一致性。
4. **政策缓存和事务。** Risk `PretradeEngine.__init__` 从 `PolicyStore.load` 取得实例级 `_active`；`publish_policy` 在 ledger 事务内检查最新版本并插入政策，事务退出后才赋值本实例 `_active`。reserve / claim、parent reserve 和 R-04 等路径使用实例缓存；本次检索未发现这些决策在每次事务内将该缓存版本与 `latest_policy()` 统一比较。账本事务的本地 writer fence / CAS 约束不自动同步不同 engine 的内存缓存，也不证明跨主机栅栏。

最后一点是**静态风险推断**：若允许多个 engine 对同一政策作用域工作，旧实例可能继续使用旧 `_active`；即使单实例有并发，政策事务提交与本地赋值之间也存在需验证的窗口。当前未复现具体生产事故，也未证明现有部署允许该并发或确有错误放行。

## 需保持的安全边界

- UNKNOWN 是原身份下未决状态。查询 `NOT_FOUND`、超时、重连或新 generation 不证明旧请求 NOT_SENT；不得自动重发、换键、释放占用或用新来源覆盖旧事实。明确的本次 `TRANSPORT_NOT_STARTED` 只有在合同能证明其对应的那次请求未进入执行路径时才可按合同处理，不能倒推既有 UNKNOWN 的历史。
- claim 提交后到 Gateway 实际执行之间可能发生 latch 解除、权限撤销、代际更换或宿主失效。本地再查一次不能单独消除跨进程 TOCTOU；不能承诺已进入外部路径的调用可被本地撤销。已可能发出的调用保留原身份和 UNKNOWN，后续只按可信原身份对账。
- 缺失来源 / 授权时，依赖该证明的控制与撤单流程保持不可用或 UNKNOWN；本地 latch 只约束经过该 Risk 路径的请求，不证明 Gateway 已对全账户生效，也不推断撤单已送达或成功。不得以此移除未选择 Risk 时的基础身份、协议和 UNKNOWN 处理。

## 建议的实现门槛（待设计，不是已实现合同）

| 阶段 | 建议责任与验收点 |
| --- | --- |
| 1. 固定来源合同 | 由 Gateway / SDK / Risk 明确可验证的服务实例、账户与 scope、控制主体授权、cause / operation 语义、journal 身份及 generation / epoch。需要受信签发和校验、持久化与重新绑定规则；配置字符串、自报字段、DTO 或哈希不能自行授予权威。先定义生效、过期、撤权及跨代读取的证据和故障结果。 |
| 2. 状态与旧数据 | 为原控制和撤单意图保留不可变身份、语义与来源关联，严格冲突检测和条件更新。历史 UNKNOWN、APPLIED 或无绑定行不能直接升级为可信成功；给出只读核验、人工处置和迁移 / 回退方案。NOT_FOUND 只作为受限观察，任何自动重试须有独立、可信的原请求未发送证明。 |
| 3. claim 与撤权 | 在 Gateway 实际副作用边界设计共同授权 / 撤权栅栏和结果契约，明确 claim 前、claim 后调用前、执行中、回执丢失及重启各状态；跨数据库不得假定原子。不能证明未发送时维持 UNKNOWN；旧代调用尚在途时新代不得凭代号或缺行放行。STOP_NEW 与 cancel 的依赖只在可信的控制事实及仍有效授权下解除，不能用本地 APPLIED 文本代替。 |
| 4. 政策版本一致性 | 先确定是否只允许一个权威 engine / 写者以及可证明的生命周期；若支持多实例，决策事务内绑定并核验最新政策版本 / digest 与所用不可变政策对象，失配时拒绝或在安全边界外重载后重新进入事务并复核。还需覆盖发布提交后缓存赋值失败、并发发布 / reserve / claim、R-04 和 L4 的同一版本语义；版本号或 digest 本身不证明来源。真实共同事务和跨代授权另行证明。 |
| 5. 验证与交付 | 先纯内存 fake 验证同键异语义、不同账户 / 主体 / generation、NOT_FOUND、授权撤销及不可重发；再按授权在隔离持久存储与真实协议边界做受控并发 / 故障注入与重启回放。分别记录 SDK / Risk / Gateway 源码、wheel、日志、资源清理和真实账户证据等级；任何缺失保持 GAP / NOT_RUN，不将本地 fake 作为生产验收。 |

## 最小验证矩阵

| 场景 | 期望证据或保守结果 |
| --- | --- |
| 同 cause 不同 scope / mode / principal / Gateway 实例或 generation | 冲突或 UNKNOWN；不能凭同名 cause 合并成功。 |
| 原控制 UNKNOWN，当前端返回 NOT_FOUND / 超时 / 新代空状态 | 保留原身份与占用，不自动重发；查询本身不证明 NOT_SENT。 |
| claim 后、外部动作前撤权 / latch 解除 / owner 更代 | 用共同栅栏验证能否阻止动作；无法证明时保留 UNKNOWN，不声称已撤回在途调用。 |
| STOP_NEW 的可信结果缺失或旧 APPLIED 无来源 | 依赖撤单不放行；独立已授权撤单按自身合同另测，不放宽授权。 |
| 两 engine 共享同一作用域，A 缓存旧版、B 发布新版 | 发布后 A 的 reserve / claim / parent / R-04 / L4 不得静默以旧版当新版；事务版本失配须可观察且失败关闭或安全重载重验。 |
| 发布事务刚提交、缓存赋值前并发 / 崩溃 | 不得把旧缓存当当前政策；验证提交结果、重新加载与原身份恢复，记录失败和不可判定。 |
| 旧 binary 已持有连接、schema / generation 变更 | 验证可证明的隔离与在途处置；不能由新进程拒绝旧连接推断既存旧进程已退出。 |

上述矩阵是拟议验收要求，尚未在本轮运行。真实来源、账户、跨代撤权、持久恢复与完整服务保持 **GAP / NOT_RUN / NO-GO**。
