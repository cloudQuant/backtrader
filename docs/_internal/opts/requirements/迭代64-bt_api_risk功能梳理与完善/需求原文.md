## 3. 解读说明（起草人注，非用户原话）

- 原话 1 后半句关于“启动策略和停止策略的按钮”放在 `bt_api_gateway`、`bt_api_monitor` 还是 `bt_api_runtime` 的提问，由 U64-3 所述的另一份分析回答，不在本迭代决定。本迭代只在按钮最终映射为策略范围的 STOP_NEW / DRAIN 时，复用同一急停命令合同。
- U64-1 选 B 后，63 分析 §6.1 原建议在 Gateway 交易 owner 内置的单笔上限、自成交、报撤单计数改由 `bt_api_risk` 提供；迭代 63 计划中相应条目（§3.5 principal grant 的可选单笔上限、§3.10 计数、D63-11 自成交）需要修改，由主会话记入迭代 63 的计划修改记录，本迭代只引用。
- “risk 是可选组件、不是硬依赖”沿用迭代 62 的需求（[修复相应的问题](../迭代62-问题修复/修复相应的问题.md) 第 2、3 条及“可选组件”分层）；U64-5 在此之上加了前提：只有开启 Gateway 时才可选。
- U64-3 记录时的“派发点进程内（direct 协调器或 Gateway 交易 owner）”已被 U64-5 收窄：risk 只在 Gateway 交易 owner 进程内或独立服务两种形态运行，不再有 direct 协调器形态。
- U64-5 与迭代 60 INV-01（direct 不加载 Risk）一致；与迭代 62 计划目标 3 “配置 execution、risk、monitor、gateway 时按组件叠加”的表述不一致，后者的修改由主会话记入迭代 62/63 的计划修改记录。63 分析 §5.2 中的 “direct + risk” 部署行随之作废。
- U64-8 中由 Gateway 执行 STOP_NEW，与 S-04 急停状态归属的分析相关，由该分析一并处理；本迭代只说明 risk 与它的关系。
- U64-9 与 63 控制面分析 S-01 的建议（a：risk 作为库在 Gateway 进程内、在派发锁内调用）不同，以用户决定为准。U64-3 中“派发点进程内”的形态随之不再需要；计划 §4 按“risk 服务位于 Gateway 之前、先预留和 claim 再转发”重写，risk 与 Gateway 不能共用一把锁，计划如实写明由此产生的竞态与时延。
- U64-10 更正的是 U64-9 之后讨论中的一句话：Gateway 不要求订单带有风控批准。因此，配置错误的客户端可以绕过 risk；计划把这一点记为已知并已接受的性质，不作为要求。
- U64-14 与 63 控制面分析 S-24 的建议（a：现有名字不改，另写对照表）不同，以用户决定为准。改名总表与负责的迭代见迭代 63 计划 §3.19。

## 4. 主会话归纳的目标（非用户原话，供审阅核对）

- 把单笔上限、价格带、自成交、报撤单计数、超出归属的可平容量等控制放进 `bt_api_risk`，并梳理该包现有功能中哪些可用、哪些是桩或遗留。
- risk 是 Gateway 之前的独立服务：bt_api_py 与迭代 65 的 execution 微服务把下单交给它，它预留、claim 后转发 Gateway；Gateway 不调用 risk，也不检查风控批准。
- risk 越限可向 Gateway 发出急停命令；急停状态由 Gateway 持有。
- risk 保持可选，但只能在 Gateway 开启时启用：未选择不启动；选择而不可用时 fail-closed（不回退为直达 Gateway）；Gateway 未开启却配置了 risk 时拒绝启动。
- 现有 risk 的 freeze 等名称改为统一词汇。
