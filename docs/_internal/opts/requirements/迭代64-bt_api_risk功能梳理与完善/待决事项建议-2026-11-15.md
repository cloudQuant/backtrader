## 1. 阻塞 A：认证来源证明与 `_v1_source_quarantined()`

### 1.1 当前精确行为（fail-closed 保证）

- `bt_api/bt_api_risk/src/bt_api_risk/pretrade/engine.py:238-243`：`_v1_source_quarantined()` **无条件返回 `True`**，注释为 “Temporary unconditional guard until authenticated source proof exists”，并明确 “does not fence an older binary or host”。
- 该函数在 `engine.py` 中有 20 余处调用，效果是**整条 v1 决策链短路**：
  - `proves_not_sent()` 恒为 `False`（`engine.py:564-567`），因此任何 permit 都不能凭“确定未发送”释放。
  - `_gateway_call()` 对 `reserve/dispatch/status/release` 直接返回 `GatewayReply("UNKNOWN", code="RISK_SOURCE_UNVERIFIED")`，**根本不调用端口**（`engine.py:860-862`）。
  - `risk.order.reserve` 在鉴权/scope/origin 校验后返回 `RiskOrderResult(key, "UNKNOWN")`（`engine.py:2479-2480`）；`dispatch`/`release` 经 `_quarantined_order_write` 提前返回（`engine.py:984`、`2925`、`3410`）。
  - `recover()` 返回 `{"checked": 0, "source_unverified": 1, ...}`（`engine.py:4574-4578`）；`maintain()` 同（`engine.py:4600-4606`）。
  - `_status_fields()` 恒返回 `{}`（`engine.py:5598-5601`），Gateway status 回包永不推进 permit 状态。
  - `status_summary()["available"]` 因隔离恒为 `False`（`engine.py:5499-5506`）。
- **第二层同向隔离**：账本 schema 有不可变来源栅栏（`pretrade/ledger.py:375-386`，含禁止 UPDATE/DELETE/第二次 INSERT 的触发器）；`_source_unverified()` 只接受唯一的 `(1, 'SOURCE_UNVERIFIED')`（`ledger.py:726-735`）；v2/v4 写入原语在来源未证时抛 `PRETRADE_SOURCE_UNVERIFIED`（如 `ledger.py:1541`、`1650`、`1858`、`1939`、`2440`、`3573`、`3641`）。**因此即使只把 `_v1_source_quarantined()` 改成 `False`，写入仍会失败关闭。**
- “v1 来源绑定”在本快照只有两个落点：引擎的 `_v1_source_quarantined()`（决策入口）与账本的不可变 `risk_pretrade_source_guard` 行（写入入口）。二者都只有“来源未证”这一种状态，**没有可写入“已认证来源”的 schema 或入口**；这正是“认证来源证明”尚未存在的原因。
- 测试钉住现状：`tests/test_pretrade_fact_source_gate.py:8-21` 断言 `_v1_source_quarantined() is True`、reserve 返回 `UNKNOWN` 且 `gateway.calls == []`。

### 1.2 选项

**A-1 保持隔离，把 v1 明确降级为只读/历史路径**
- 实现范围：仅文档与测试期望调整（把“应产生真实决策”的用例改为期望 `UNKNOWN`/`RISK_SOURCE_UNVERIFIED`），**不改产品代码**。
- 安全影响：零变化，最保守。
- 证明方式：每个 v1 决策入口都返回有限码且不触达 Gateway；直接调用底层写入仍抛 `PRETRADE_SOURCE_UNVERIFIED`。
- 仍为 GAP：v1 永远不产生决策，迭代 64 不能声称 R-01～R-11 已实现行为。

**A-2 先冻结“认证来源合同”，再按新 schema 解除隔离**
- 实现范围：跨 Risk/SDK/Gateway——定义受信签发与校验（认证 principal、账户 scope、session/generation/epoch、覆盖水位、有效期与撤权）、新增账本 schema 状态记录“已认证来源”、把隔离谓词替换为“已验证来源快照”检查，并补负向矩阵。大工程。
- 安全影响：唯一能让 v1 真实决策的方向，但必须拒绝“配置字符串 / 自报字段 / DTO / 哈希 / 过期标志”作为授权（计划 §4.3、§64.01 已明令）。
- 证明方式：错误 principal/scope/epoch/过期/撤权/代际不符 → `UNKNOWN`；旧 binary/host 不能借新库写入；无证明时底层写入仍拒绝；提交后崩溃与重启恢复按原身份。
- 仍为 GAP：真实 Gateway/provider 来源、跨进程撤权、发送点 TOCTOU 仍未证。

**A-3 只解除只读/状态/摘要路径**
- 实现范围：小，仅改少量调用点。
- 安全影响：写路径仍关闭；但“状态可读”容易被误读为来源已证，且 permit 原始身份仍无法证明。
- 证明方式：只读端点仅用本地账本作答；任何 Gateway 端口仍短路；permit 不发生状态迁移。
- 仍为 GAP：不提供任何决策能力，且增加运营误解风险。**不建议。**

### 1.3 建议（proposal）

采用 **A-1 作为当前默认**，把 **A-2 作为唯一能开启决策的路径**；A-2 的**第一个交付物是冻结的来源合同文本**，不是代码。不要用 A-3。理由：`engine.py:241` 自己声明隔离不约束旧 binary/host，仅翻转布尔既不安全也不足以打开账本写入（1.1 第二层）。

### 1.4 最小用户决定措辞

> “A：本轮保持 `_v1_source_quarantined()` 为真，v1 只作只读/历史保留；仅当认证来源合同（签发方、账户 scope、generation/epoch、覆盖水位、有效期、撤权与旧 host 隔离）经我确认冻结后，才授权按新 schema 实现解除。授权实现新 schema 与负向测试，不授权以配置、布尔、DTO 或哈希打开隔离。”

如选择 A-2 先行，则改为：“A-2：同意按上述合同冻结并实现，先交合同文本与负向测试，再动 `_v1_source_quarantined()`。”

## 2. 阻塞 B：R-04/R-11 v2 政策激活/发布路径

### 2.1 当前精确行为（fail-closed 保证）

- 公共校验器只接受 v2：`pretrade/policy.py:1237-1244` 的 `validate_policy_document` 直接转 `validate_policy_v2_document`；v1 wire 文档得到 `policy_schema_unsupported`（本地探针确认）。
- `pretrade/policy_store.py:40-84` 的 `activate()`：
  - 非精确 `RiskPolicy`、缺 `r04_binding` 字段、digest/schema 不符 → `RULE_POLICY_INVALID`；
  - `r04_binding is not None` → `RULE_R04_V2_UNAVAILABLE`（`policy_store.py:53-54`）；
  - **无论是否带 counters，最后一行仍无条件抛 `RULE_R04_V2_UNAVAILABLE`**（`policy_store.py:84`）。本地探针：v2 无 counters 政策可被校验器接受，但 `activate()` 仍拒绝。
- 结论：**当前源码不存在任何可达的正式政策激活路径**（v1 wire 被校验器拒绝，v2 被 `activate()` 拒绝）。这与 [开发验收状态矩阵](开发验收状态矩阵.md) 第 8-9 行的登记一致。
- 连带效果：`PolicyStore.load()`（`policy_store.py:179-185`）吞掉错误、`load_error` 置位并返回 `None`，引擎无政策；`publish_policy()` 在 `engine.py:5060` 调 `activate()`，`RuleConfigError` 被映射为 `RiskAdminError("policy_rule_not_allowed")`（`engine.py:5061-5062`），**在 `txn.insert_policy` 之前失败**，不写任何政策行；`self._active = active` 只在事务提交后赋值（`engine.py:5087`）。
- SDK 宿主：`bt_api_py/risk_service_host.py:178-181` 在配置了 `r04_selection` 时直接 `RISK_SERVICE_R04_V2_UNAVAILABLE`；`bootstrap_policy()`（`risk_service_host.py:665-716`，启动时经 `:2063` 调用）在发布被拒时 `RISK_SERVICE_POLICY_PUBLISH_REFUSED`。因此依赖已发布政策的测试全部停在 setup。
- 引擎并未消费 v2：`ActivePolicy.r04_v2`（`policy_store.py:33`）只被赋值，`engine.py` 无任何 `r04_v2` 引用；claim 只用旧的 `active.r04`（`engine.py:3266`），且 breach 硬编码 `scope_kind="instrument"`、`modes=(("STOP_NEW","instrument"),)`（`engine.py:3284-3293`），**不投影受信规则返回的 action/scope**；外部订单/撤单观察计数直接读 `active.policy.counters.<kind>.block`（`engine.py:4555-4572`），不调用 v2 规则。这正是 [验收遗留](验收遗留-许可完整性与R04语义-2026-11-14.md) 记录的 breach 语义 GAP。
- 多 engine `_active`：`_require_policy_snapshot()`（`engine.py:1024-1044`）在决策事务内校验“实例缓存同一对象 + 账本最新 version/digest/policy_id 一致”，已用于 reserve（`engine.py:2569`、`2636`）、claim（`3037`、`3078`）、parent（`1472-1597`）、loss/L4（`4889-4900`）；失配 → `_PolicySnapshotChanged` → `RiskOrderResult(..., "UNKNOWN", code="risk_policy_unavailable")`（reserve `engine.py:2637-2638`、claim `3085-3086`、loss/L4 `4914`）。**当前行为是失败关闭，而不是静默使用旧版**；11-14 文档的静默旧版风险在本快照的上述路径已被收敛。仍待决定的是：(a) 发布事务提交到 `engine.py:5087` 赋值之间的窗口，同实例并发决策会得到 `UNKNOWN`（安全但可用性损失）；(b) 失配时是保持 `UNKNOWN` 还是允许“安全重载后重新进入事务”；(c) 这只是单进程内检查，不等于跨进程单写者证明。
- 来源/FX：`ExchangeRuleSet` 带 `source_id/source_version/obtained_at_ns/expires_at_ns`（`policy.py:623-633`），R-11 适用性会校验交易日与 obt/exp 窗口（`policy.py:1217-1233`），但 `policy.py:971` 明言“解析不是来源权威”；FX 可信绑定仍是独立 GAP。

### 2.2 选项

**B-1 最小解锁：允许“无 counters、无 r04_binding”的 v2 政策激活/发布**
- 实现范围：`policy_store.activate()` 对 `counters is None and r04_binding is None` 走原 v1 规则路径；`r04_binding` 非空继续拒绝；把 `engine.py:5061-5062` 的错误码改为如实的 `policy_r04_v2_unavailable`（而非 `policy_rule_not_allowed`）；保持 `_require_policy_snapshot` 与失配 `UNKNOWN`；补发布/加载/重启与多 engine 测试。中小工程。
- 安全影响：打开“政策可发布/可加载”，但**不打开 R-04 v2 规则**；不削弱现有决策失败关闭；来源/FX 仍是声明性输入。引擎只在 `active.policy.counters is not None` 时调用 `active.r04`（`engine.py:3264`），因此无 counters 路径不新增规则求值面。
- 证明方式：v2 无 counters 发布 → 加载 → 重启 → reserve 使用已发布版本；带 binding 的政策在任何状态写入前拒绝；B 发布后 A 的旧缓存 reserve 返回 `UNKNOWN/risk_policy_unavailable`；提交后赋值窗口返回 `UNKNOWN`。
- 仍为 GAP：R-04/R-11 v2 规则激活、breach 语义、来源/FX 权威。

**B-2 完整 v2：激活并接线 `BoundR04V2`，冻结 breach 与多 engine 语义**
- 实现范围：`ActivePolicy.r04_v2` 接入 `engine._evaluate_claim` 与观察路径；冻结 breach 投影（`EXISTING` vs `ON_CLAIM`、action/scope、被拒 claim 的处理）；持久化 wire 文档与 artifact 绑定；接通宿主 `r04_selection`；明确失配时保持 `UNKNOWN` 还是安全重载；保持异常/非法类 fail-closed（`run_r04_v2` 已返回 `DENY/RULE_FAILED`）。跨仓大工程。
- 安全影响：新增规则求值与越限意图路径，必须保留 allowlist/版本/精确类检查，且不得接受自报 artifact。
- 证明方式：伪造 artifact、版本/contract 不符、覆写关键方法、插件抛异常、上下文被改、错 instrument、被拒 claim 仍报 breach 等负向矩阵；重启后按持久绑定恢复；claim 与观察两个 basis；有/无 counters；无默认阈值。
- 仍为 GAP：来源/FX 权威、派发点跨进程原子性、真实期货公司规则。

**B-3 另开 `activate_v2` 而不动现有守卫**
- 实现范围：中等，但引擎在隔离下无法产生效果；转交说明 §9 记录该尝试已全部回退。
- 安全影响：重复激活面，难以统一守卫。
- **不建议**：既不能证明真实能力，又扩大未冻结设计面。

### 2.3 建议（proposal）

先做 **B-1**（解锁政策 bootstrap/加载与大部分 setup 失败，不假装 R-04 v2 已工作），再由用户单独授权 **B-2**。B-1 的边界必须写死：只接受 `counters is None and r04_binding is None`；任何 binding 仍在写入前拒绝；失配仍 `UNKNOWN`。

### 2.4 最小用户决定措辞

> “B：先授权 B-1——允许无 counters、无 `r04_binding` 的 v2 政策经 `activate()`/`publish_policy()` 生效并持久化，带 binding 的政策仍返回 `RULE_R04_V2_UNAVAILABLE`，多 engine 失配仍返回 `UNKNOWN/risk_policy_unavailable`；错误码改为如实名称。B-2（完整 R-04 v2 接线、breach 的 EXISTING/ON_CLAIM 投影、来源/FX 语义）另行授权，不在本次范围。”

## 3. 阻塞 C：CTP `FENCE_ENTRY_UNTRUSTED` 与受信子类边界

### 3.1 当前精确行为（fail-closed 保证）

- SDK 为了让 Risk 核心获得 provider 证据与 Gateway 来源校验，组合了一个**子类**：`bt_api_py/service_risk_order_journal.py:45` `class RiskOrderJournal(RiskExecutionJournalBridge, _RiskOrderJournal)`，并在 `:48-57` 覆写 `_risk_dispatch_profile` 与 `_verify_gateway_position_source_receipt`（核心基类版本只会抛不可用，见 `risk_order_journal.py:867-872`）。
- 核心侧是**精确类型门**：`_trusted_fence_context()` 要求 `type(journal) is RiskOrderJournal`（`risk_order_journal.py:574-601`）；`_borrow_identity_current()`（`:455`）、`_entry_scope_key()`（`:526`）、`_initialize_execution_composition_slot()`（`:793-795`）、`_bind_execution_composition()`（`:812-814`）、`_is_execution_composition_current()`（`:839-841`）同为精确类型；`__init__` 只为精确核心建立 composition slot（`:874-885`）。
- SDK 侧是**反向精确类型门**：`service_risk_order_entry.py:765` 要求精确 SDK 子类；`ctp_risk_dispatch_bridge.py:124`、`service_execution_risk_cancel.py:79`、`service_risk_position_snapshot.py:145/442`、`service_execution_group_proofs.py:946`、`service_strategy_ledger_host.py:466` 同；而 `service_execution_risk_composition.py:136/145` 又要求精确**核心**。**没有任何对象能同时满足两侧**，这是结构性矛盾。
- 失败路径（与转交说明 §10.2 “C 类”一致）：`CtpRiskDispatchBridge.__init__` 在 `ctp_risk_dispatch_bridge.py:153-157` 调 `journal.writer_fence(account_scope)`；`writer_fence()` 的信任判断见 `risk_order_journal.py:1174`，不信任时先 `_quarantine_fence_entry(key)` 再抛 `FENCE_ENTRY_UNTRUSTED`（`:1186`）；`_raise_fence_entry(..., complete=False)` 把它呈现为 `RiskFenceEntryError(code="FENCE_ENTRY_UNKNOWN", cleanup=UNKNOWN)`（`:609-626`）。CTP runtime 启动因此 `RISK_ADMISSION_FACTORY_FAILED`（`ctp_execution_runtime.py:2196-2202`）。
- 附带影响：`_quarantine_fence_entry` 会把该账户 scope key 写入进程级 `_FENCE_ENTRY_QUARANTINED_KEYS`（`risk_order_journal.py:543-558`），**同一进程内后续任何正确装配也会得到 `FENCE_ENTRY_QUARANTINED`，直到进程重启**。这扩大了单次装配错误的爆炸半径。
- 现状被测试刻意钉住：`tests/unit/test_iter64_execution_risk_composition_fake.py:364-372` 断言 SDK 子类 `_trusted_fence_context(...) is False` 且 composition 抛 `CORE_REQUIRED`。这是有意的信任边界，不是测试缺陷；转交说明与开发草案均写明“不能用 `isinstance` 或类名相同直接放宽”。

### 3.2 选项

**C-1 SDK 持有唯一精确核心实例，来源能力改为实例级端口（开发草案 §2-§3 的方向）**
- 实现范围：Risk 提供一个受支持的实例端口/槽位机制，把 `_risk_dispatch_profile`、`_verify_gateway_position_source_receipt` 与 Execution 撤单来源桥从继承改为实例绑定；SDK facade 固定引用该核心，并迁移全部装配点（entry、CTP bridge/cancel、group proofs、position snapshot、strategy ledger host）。中大工程，但已有设计草案。
- 安全影响：保留精确类型信任边界；端口必须拒绝缺失、替换、类型/身份变化，不接受通用 callable、可构造 DTO、`verified=True` 或字段格式作为授权。
- 证明方式：端口绑定正反例；未绑定/被替换/类型变化 → 操作不可用；子类仍被拒绝；两个核心实例互不串用；CTP bridge 能取得 fence 并写入命令；现有“无写能力”测试不变；对精确类型行做变异检查。
- 仍为 GAP：进程内 Python 不是沙箱；真实 CTP/Gateway 来源未证。

**C-2 Risk 提供显式“受信子类登记”入口**
- 实现范围：Risk 侧新增一次性、按精确类对象 + 模块身份 + 关键方法摘要的登记；`_trusted_fence_context` 接受“精确核心或已登记且未覆写 fence/lock/entry/borrow 方法的类”；已使用后登记、跨进程登记拒绝。SDK 基本不动。中等工程。
- 安全影响：把边界从“精确类”扩为“已登记类”；同进程代码可调用登记器，因此**只能作为装配期自检，不能宣称是恶意同进程代码的边界**。
- 证明方式：已登记接受、未登记拒绝；覆写 `writer_fence`/`_initialize`/`_assert_current`/锁助手即拒绝；重复登记/不同进程拒绝；对每个覆写点做变异检查。
- 仍为 GAP：登记是进程内策略，不建立真实来源或账户权威。

**C-3 把精确类型门换成结构性能力门**
- 实现范围：最小改动。
- 安全影响：与计划 §64.01“不得简单删除类型检查 / 不能为通过测试直接放宽”相冲突，绕过面最大。**不建议**。
- 证明方式：必需方法集被篡改即拒绝；但同形类可被接受。
- 仍为 GAP：信任边界实质弱化。

### 3.3 建议（proposal）

采用 **C-1**。它既保留“精确核心 + 精确 fence 上下文”的信任边界，又与既有开发草案的所有权模型一致；C-2 仅在用户希望保留“继承式组合”时作为退路。实现时须同时处理 3.1 的进程级 quarantine 语义（装配失败不得污染后续正确装配），并在文档中写明这不是恶意代码边界。

### 3.4 最小用户决定措辞

> “C：选择 C-1——SDK 组合改为持有唯一精确 Risk 核心实例，并以实例绑定方式提供 provider profile、Gateway 仓位来源、Execution 撤单来源三个端口；授权相应的破坏式调用点迁移。新增实例端口机制不得接受 callable、布尔或字段格式作为授权；端口缺失/替换/类型变化必须使相关路径不可用；装配失败不得把账户 scope 永久 quarantine 到进程结束。”
