## 1. “来源”的定义与授权边界

### 1.1 本合同的“来源”指什么

Risk 预交易引擎消费四类来源数据；本合同的“认证来源”只覆盖它们来自**经认证的 Gateway 服务会话**这件事：

| 编号 | 来源路径 | 现有落点（只读源码） | 本证明绑定的东西 |
| --- | --- | --- | --- |
| S1 | 账户事件观察流 | `upstream.account`；`account.events.read_after/progress/ack`；`GatewayAccountObserverClient`（SDK `gateway_account_observer_client.py:19-190`） | `epoch`、`consumer_ref`、`acknowledged_sequence`、观察注册 `registration_id` |
| S2 | 类型化账户快照 | `application.account`；`account.snapshot.typed`；`ServiceAccountClient` / `AccountStateView`（`bt_api_py/service_account.py:76-114`） | `account_key_id`、`snapshot_id`、`session_generation`、`cursor`、`fresh_until_monotonic` |
| S3 | 行情参考价 | `upstream.market`；live tick `receipt` + `clock_observation`（SDK `risk_service_gateway.py:1483-1543`） | 行情注册与 live attestation（当前已有逐 tick 证明） |
| S4 | Gateway 命令/控制回包 | `application.direct_write`；`reserve/dispatch/status/release`、`control.apply/status/cancel_scope` | 回包所属的认证会话身份；回包仍是 claim，不是事实 |

来源证明**只回答“这条会话和这份覆盖水位是否由受信主体在受信通道上给出”**。它不把 S4 的回包变成终态事实；S4 仍走现有 `proves_not_sent` / `_status_fields` / `_record_*` 证明规则（`engine.py:587-601`、`5785-5811`）。

### 1.2 明确拒绝作为授权的东西

以下任一单独出现，**不得**使 `_v1_source_quarantined()` 变为 `False`，也不得使账本写入被接受：

| 被拒绝项 | 现有落点/原因 |
| --- | --- |
| 配置字符串（`source_verified: true`、`source_mode: authenticated`、`trusted: yes`） | 不是身份；Risk 配置解析只接受已声明键（SDK `risk_service_config.py:98-169` 对未知/非法文档给 `RISK_SERVICE_CONFIG_INVALID_DOCUMENT`）。本证明**不新增**这类键。 |
| 请求/载荷自报字段（`view.source_*`、payload 中的 `verified`/`authenticated`/`proof`） | `RiskOrderView` 的字段是调用方声明；`CallerIdentity` 由 authority 派生（SDK `risk_service_component.py:194-268`），请求正文不构成身份。 |
| DTO / 对象属性（`verified=True`、`source_ok`、`trusted=True`） | 可构造的 DTO 不证明来源；与 C-1 对“可调用对象/布尔/字段冒充”的拒绝一致。 |
| 裸哈希（数据库文件哈希、证明行哈希、账户哈希单独） | 哈希只证明内容未被改动，不证明谁签发、绑定了哪个账户/代际/水位。 |
| 单独的过期标志（`expires_at`、`not_expired=true`） | 有效期是绑定字段之一，不是授权本身；无签发方/scope/代际时无效。 |
| `WireIdentity` 的声明字段 | `bt_api_base/service_protocol.py:194-197` 自述 “Untrusted sender claims; trusted transport/service state must verify them”。 |
| `CallerIdentity.role` / `principal_ref` 单独 | 它由 Registry/authority 派生，证明调用方已认证；不证明账户事实来源，也不证明覆盖完整。 |
| 行情 `receipt` 单独 | 只证明该 tick 的 live attestation（`risk_service_gateway.py:1519-1527`），不证明账户事件来源或覆盖。 |
| `FENCE_ENTRY_*` 本地进程隔离 | 只证明装配/类型边界，不证明来源。 |
| SQLite 本地事务 / writer token 单独 | 只证明单写者，不证明跨主机或来源。 |
| `schema_version` / 表存在 | 只证明书是哪个格式，不证明来源。 |

## 2. 合同之一：认证主体的签发与校验

### 2.1 信任锚与签发方（who signs）

**信任锚（out-of-band，操作员安装）**

- SDK 宿主把操作员安装的 principal 表转成 `TrustedServiceAuthority`（`bt_api_py/service_host.py:309-389`）：
  - `principals: Mapping[bytes, str]` 把 **40 字节 CURVE 公钥** 映射到 `principal_ref`；
  - `grants: Mapping[str, tuple[PrincipalGrant, ...]]` 给出每个 principal 的精确 `WireIdentity` 与 `ResourceGrant`（实例、端口、scope、operations）；
  - `curve_public_key` / `curve_secret_key` 是服务端 CURVE 凭据。
- 远端 TCP 由 ZMQ CURVE/ZAP 认证：服务端只承认 ACL 中的公钥，并以 ZAP 的 `User-Id` 元数据（**不是客户端自选的 ROUTER identity**）选择 `RemotePrincipalGrant`（`bt_api_transport_zmq/server.py:111-120`、`225-243`、`319-359`）。
- 本地 IPC / loopback 端点不启用 ZAP 的曲线公钥→principal 映射，而使用注入的 `PrincipalAuthenticator`（`server.py:158-179`、`235-240`）；即使设置了 CURVE 凭据，身份仍来自注入的认证器。因此**本机回环证据不能证明远端主机身份**，见 §5。

**签发方（issuer）**

- 来源证明的 issuer 是 **Gateway 的 `WireRole.SERVICE` principal**：`delegate_ref is None`，在 `upstream.account`（观察）、`upstream.market`（行情）、`application.direct_write`（命令/控制）、`application.account`（快照）四个挂载上由认证会话注册，且 operations 覆盖所需操作（SDK `risk_service_host.py:1721-1765`；`_granted` 检查见 `risk_service_host.py:940-951`）。
- 若只配置了部分来源（例如没有 `gateway.account_snapshot` 或没有 `gateway.market`），proof 对应字段为空，且只覆盖已配置的来源；不把未配置的来源算作“已验证”。

**转录者与验证者**

- **转录者**：Risk 服务宿主（受信组合代码）。它把已验证会话事实写入账本，本身不是授权来源。
- **验证者**：同一宿主在启动时按身份重新推导并比较；引擎在每次决策时只读进程内快照，不读账本行。
- **不声称**：本证明不是 per-message 签名，也不是 bearer token。CURVE 握手证明的是连接时刻的密钥占有；证明行只是受信宿主对该会话的转录。若未来要求逐消息签名/不可否认，须另立合同，本文不覆盖。

### 2.3 校验算法（启动时与每次使用时）

**启动时（宿主，恰好一次）**：

1. 打开 v7 书并持有 writer fence；读取 `risk_pretrade_source_proof_v7` 的**当前行**（`proof_sequence` 最大者）。无行 → 隔离。
2. 计算当前行 `proof_digest`，与行内值比较；比较 `proof_schema`、序列连续性、CHECK 形状；失败 → 隔离（`SOURCE_PROOF_INVALID`）。
3. 从**活体 authority** 重新推导：主体/签发方 principal、actor、service/instance、注册集合、`authorization_generation`。与当前行逐字段精确比较；失败 → 对应原因（`SOURCE_PRINCIPAL_MISMATCH` / `SOURCE_SCOPE_MISMATCH` / `SOURCE_GENERATION_MISMATCH` / `SOURCE_PROOF_REVOKED`）。
4. 重新建立认证会话（观察、控制、可选快照/行情），读取活体 `service_epoch`、观察 `epoch`、`consumer_ref`、`acknowledged_sequence`、`head_sequence`。要求：
   - 活体 `service_epoch` 与行内 `subject_service_epoch` 相等，否则 `SOURCE_EPOCH_MISMATCH`；
   - 观察 `epoch` 与 `coverage_epoch` 相等，否则 `SOURCE_EPOCH_MISMATCH`；
   - 活体 `acknowledged_sequence >= coverage_watermark_sequence`，否则 `SOURCE_WATERMARK_REGRESSION`；
   - 活体 `consumer_ref` 与行相等（由身份+scope 重算），否则 `SOURCE_SCOPE_MISMATCH`。
5. 校验账户快照组（如配置）：`account_key_id`、`snapshot_id`、`session_generation`、`cursor`、`fresh_until_monotonic` 与行一致且未过期；否则 `SOURCE_COVERAGE_UNVERIFIED`。
6. 校验 `host_ref` 与操作员安装的当前主机身份相等；否则 `SOURCE_HOST_MISMATCH`。
7. 校验窗口：`not_before_ns <= now <= expires_ns`；`now < not_before_ns` → `SOURCE_PROOF_NOT_YET_VALID`；`now > expires_ns` → `SOURCE_PROOF_EXPIRED`；`now < issued_at_ns`（时钟回拨）→ `SOURCE_CLOCK_INVALID`。
8. 全部通过后，构造 `VerifiedSourceSnapshot` 并**一次性安装**（§3.4）。任何一步失败：不安装，记录原因，保持隔离。

**每次使用时（引擎，无 I/O）**：

- `_v1_source_quarantined()` 只在“快照已安装 + 未被作废 + 未过期 + pid/线程一致”时返回 `False`。
- 每次决策**不重新读账本**、不重新认证、不调用端口之外的东西；这是热路径约束。
- 决策事务内仍由 `_source_unverified(connection)` 做结构层的第二道检查（§3.3）；两层必须同时成立。

### 2.4 有效期、撤权与失效

- **有效期**：以 §2.3 第 7 步的窗口为准。窗口内不因“长时间无事件”自动续期；**不在同一进程内续期或重新安装**。到期即隔离，恢复须重启并重新验证。
- **撤权**：
  - 操作员从 authority 移除/替换主体或签发方的 grant → 活体 `authorization_generation` 改变；已安装快照在下一次使用前的活体复核（宿主心跳/会话状态）失败，宿主调用 `invalidate_verified_source("grant_revoked")` → 永久隔离直到重启。
  - Gateway 注销/替换观察注册、关闭会话 → `invalidate_verified_source("registration_lost")`；旧 proof 的 `registration_id` 不再匹配 → 重启后 `SOURCE_GENERATION_MISMATCH`。
  - 操作员显式撤销：受信宿主发出撤销信号（不是请求正文），记为 append-only 审计事件，**不修改 proof 行**；进程保持隔离。
- **撤销不可回滚**：旧 proof 行永不被“恢复为当前”；只能追加新行并由重启后的完整验证使其成为当前。
- **不会自动解除**：任何“重新连接成功”“收到 status”“收到一条 Gateway 拒绝”都不恢复来源；必须重新走 §2.3。

### 2.5 旧 binary / 旧 host 隔离

- **旧 binary**：v7 书的 `schema_version=7` 不在旧二进制接受集合 `{1,2,3,4,5,6}` 中（`ledger.py:3514-3521`、`3780-3789`），旧进程打开即 `PRETRADE_SCHEMA_MISMATCH`，不会写入。该性质可在 UNIT 证明。
- **旧 host**：
  - proof 绑定 `host_ref` 与 `subject_registration_id`/`service_epoch`；不同 `host_ref` 无法通过 §2.3 第 4/6 步 → `SOURCE_HOST_MISMATCH`。
  - 复制到旧主机的书即使带着旧 proof，其 epoch/generation/watermark 也会失配 → 隔离；该路径可在 UNIT/FAKE 证明。
  - **跨主机互斥本身不由本证明建立**：两个活主机各持一份文件副本时，本地无法证明谁是唯一写者。该保证依赖 INV64-13 的“每账户至多一个有效 risk writer + 新 owner 先证明旧 owner 与在途请求不可再生效”与 Gateway 的注册互斥；真实实现与验证为 **GAP / NOT_RUN**。
  - 存储信任仍按迭代 63 的决定：**OS 隔离**；本文不把本地 Python 或 SQLite 当作沙箱（`risk_order_journal.py:456-470`、`806-814` 的边界声明同样适用）。

## 3. 合同之二：账本状态与切换

### 3.1 新 schema 版本 v7（DDL 草案，供实现包逐字实现）

- 该表 **append-only**；`proof_sequence` 严格递增且连续。**当前行 = `MAX(proof_sequence)`**；历史行只作审计，永不用于授权。
- 冻结 `risk_pretrade_source_guard`（v3 起已有）**保持原样**，在 v7 中只作为“这本书从无证明状态起步”的结构标记，**不参与授权**；授权只看证明表当前行。
- `_SCHEMA_V7 = _SCHEMA_V6 + _SOURCE_PROOF_V7_SCHEMA`；`SCHEMA_VERSION` 在实现包切到 7 之前保持 3。实现包未落地前，`PretradeLedger(..., schema_version=7)` 必须抛 `PRETRADE_V7_UNAVAILABLE`（与 `PRETRADE_V5_UNAVAILABLE`/`PRETRADE_V6_UNAVAILABLE` 同形，`ledger.py:3451-3458`）。

### 3.2 不可变规则

- `UPDATE` / `DELETE` 一律由触发器 abort；Python 侧映射为 `PRETRADE_SOURCE_PROOF_IMMUTABLE`。
- 第二次 `INSERT` 只能以 `proof_sequence = max+1` 追加；否则触发器 abort，映射为 `PRETRADE_SOURCE_PROOF_CONFLICT`。
- 一行一经写入，其 `proof_digest`、窗口、水位、身份、fence 全部不可变；**撤权/过期不是写入**，是活体校验失败（§2.4）。
- 不允许“删除旧行重置序列”；不允许把旧行重新设为当前；不允许用备份回滚证明历史。
- 审计：每次发布、每次安装、每次作废都写既有 append-only 审计表（`risk_pretrade_audit`），记录 `proof_sequence`、`proof_digest`、原因码与 writer fence；不写账户号、凭据或路径。

### 3.3 `_source_unverified()` 的新语义（结构层）

保留函数名以最小化调用点（`engine.py`/`ledger.py` 现有 10 余处），只改语义：

- **v3–v6**：恒返回 `True`（未验证）。旧书写路径继续抛 `PRETRADE_SOURCE_UNVERIFIED`，行为不变。
- **v7**：仅当“恰好一个连续序列 + 当前行结构自洽”时返回 `False`：
  - 当前行存在且 `proof_sequence` 从 1 连续到 max；
  - `proof_digest` 重算一致；
  - `coverage_ack_sequence == coverage_watermark_sequence`、`coverage_from_zero == 1`、`coverage_ack_sequence <= coverage_head_sequence`；
  - `expires_ns > not_before_ns`、`issued_at_ns >= not_before_ns`；
  - 所有 CHECK 形状有效。
- 结构异常 → `PRETRADE_SCHEMA_MISMATCH`；发布冲突 → `PRETRADE_SOURCE_PROOF_CONFLICT`。
- **该层不验证活体身份**；活体身份由 §2.3/§3.4 的进程快照负责。两层同时成立才允许决策/写入；任何一层失败都失败关闭。
- **直接账本调用**：v7 书 + 结构自洽的当前行时，账本层本身会允许写入；但引擎的全部决策入口仍被 `_v1_source_quarantined()` 挡住。宿主不得在未安装快照时调用 v2/v4 写入原语；实现包的测试必须覆盖“有 proof 行但未安装快照时，引擎不产生决策、宿主不写业务行”。这是合同不声称“库层单独可授权”的边界。
- 旧书（v3–v6）在新二进制中：不迁移、不加行、不删行；来源相关原语继续 `PRETRADE_SOURCE_UNVERIFIED`，宿主以 `RISK_SERVICE_STORAGE_SCHEMA_INVALID` 或显式的 `PRETRADE_SOURCE_MIGRATION_REQUIRED` 报告（§3.5）。

### 3.4 `_v1_source_quarantined()` → “已验证来源快照”（恰好一次）

**冻结的模块接口**（实现包新增，本文冻结语义）：

- `@dataclass(frozen=True) class VerifiedSourceSnapshot`：§2.2 元组的不可变副本，外加 `installed_at_ns`、`install_monotonic_ns`、`expires_monotonic_ns`、`pid`、`thread_id`、`proof_sequence`、`proof_digest`。**字段类型全部精确；不接受 callable、Mapping 代理、子类或可变容器。**
- `install_verified_source_snapshot(snapshot: object, *, ledger: object, fence: object) -> None`：
  - 精确类型检查（`type(snapshot) is VerifiedSourceSnapshot`、`type(ledger) is PretradeLedger`、`type(fence) is RiskOrderWriterFence`）；
  - 要求 `ledger.fence is fence`、`fence.scope.key` 与快照的账户 scope 一致、`fence.owner_id`/`fencing_token` 与快照记录的 writer 字段一致；不持当前 writer fence 不得安装；
  - 只能由宿主在 §2.3 全部通过后调用；
  - 每进程**恰好一次**：第二次调用抛 `RISK_SOURCE_ALREADY_INSTALLED`，不改变已安装状态；
  - 校验 pid/线程、窗口未过期、`not_before <= now`；失败不安装；
  - 用一次原子发布（与 `_initialize_execution_composition_slot` 的 `setdefault` + 身份复核同型，`risk_order_journal.py:838-855`）写入模块私有槽位。
  - **非恶意代码边界**：该接口是受信组合 API；同进程恶意代码可自行构造 DTO 或直接改私有状态，本文不声称能阻止。它防的是配置错误、旧 host/旧 binary、伪造请求与缺失证明，不是 Python 沙箱。
- `invalidate_verified_source(reason: str) -> None`：只接受有限原因集合；一次写入**永久**标记；重复调用幂等；**没有清除接口**。
- `_v1_source_quarantined() -> bool`：保留在 `bt_api_risk.pretrade.engine` 可导入；返回 `True`，除非快照已安装、未作废、未过期且 pid/线程一致。**它永远不读账本、不读配置、不接受参数。**
- 实现包不得逐点切换 30 余处调用；谓词仍是唯一开关。

**启动顺序（宿主，冻结）**：

1. `open_storage()`（现有）→ v7 书 + writer fence。
2. 若 v7 未实现或旧书 → 不安装，保持隔离。
3. `build_engine()`（现有）→ 引擎构造；此时谓词仍为 `True`。
4. 建立认证会话并验证 §2.3；发布 proof 行（同一 writer fence 事务）或验证既有当前行。
5. 仅在第 4 步全部通过后 `install_verified_source_snapshot(...)`。
6. 之后才启动服务/循环；`recover()`、`maintain()`、`status` 才可能返回非隔离结果。
7. 任何一步抛异常/返回 UNKNOWN → 不安装，宿主按既有 `RISK_SERVICE_STORAGE_*` 码失败关闭；不得“先安装后补证”。

**不变量**：

- 每个进程至多一个 `VerifiedSourceSnapshot`；没有“重新验证后重新安装”。
- 进程内没有“续期”路径；窗口到期或会话丢失即永久隔离，重启是唯一恢复。
- 快照不是 bearer token：它只在本进程、本 pid、本线程、本会话代际内有效；复制到别的进程不会自动生效（新进程必须重新走 §2.3）。

### 3.5 旧账本迁移：refuse-not-guess

- **新二进制打开 v3–v6 书**：拒绝就地升级。不执行 DDL、不插入 proof、不删除 guard 行；来源相关原语继续 `PRETRADE_SOURCE_UNVERIFIED`。宿主报告 `PRETRADE_SOURCE_MIGRATION_REQUIRED`（实现包新增有限码）。
- **v1/v2 旧书**：保持既有 `PRETRADE_LEGACY_QUIESCENCE_REQUIRED`（`ledger.py:3491-3499`），不因 A-2 放宽。
- **v7 书被 v3–v6 二进制打开**：`PRETRADE_SCHEMA_MISMATCH`（版本不在接受集合）。
- **回退**：不允许降级 schema、不允许删 proof 行、不允许用备份“回到”未隔离状态。旧 UNKNOWN、占用、latch、来源栅栏一律保留；不因迁移清零。
- **迁移工具**（若未来提供）：必须先证明无来源相关在途状态、必须持有活体已验证来源、必须操作员受权、必须 append-only；本文不授权该工具。

| N25 | 配置出现 `source_verified`/`source_mode` 等键 | 启动失败 | `SOURCE_CONFIG_NOT_AUTHORITY` | `RISK_SERVICE_CONFIG_INVALID_DOCUMENT` | UNIT |
| N26 | 裸哈希（DB/文件/账户哈希）作为证明 | UNKNOWN | `SOURCE_HASH_NOT_PROOF` | 不接受；不改变状态 | UNIT |
| N27 | 单独的过期/未过期标志 | UNKNOWN | `SOURCE_PROOF_INVALID` | 不接受 | UNIT |

| N29 | 发布事务 COMMIT/ROLLBACK 结果不明 | UNKNOWN | `SOURCE_PROOF_COMMIT_UNCERTAIN` | `PRETRADE_SOURCE_PROOF_COMMIT_UNCERTAIN`；保留隔离，不盲目重试 | UNIT（故障注入） |
| N30 | v7 尚未实现时请求 v7 | 不启动 | `SOURCE_V7_UNAVAILABLE` | `PRETRADE_V7_UNAVAILABLE` | UNIT |

矩阵规模：**30 项负向**。每项都要求“有限原因码 + 失败关闭 + 不改旧 UNKNOWN/占用”。

### 4.2 正向路径（9 项）

| # | 场景 | 期望 |
| --- | --- | --- |
| P01 | 新 v7 书创建 + guard 行 + 无 proof | 隔离；`_v1_source_quarantined() is True`；`status.available is False` |

## 5. 证据边界：什么能本地证明，什么仍是 GAP

### 5.1 本地可证明（实现包，UNIT/FAKE）

- `_v1_source_quarantined()` 的 True→False 只在一次性安装后发生；第二次安装被拒；作废后永久隔离。
- 账本 v7 DDL、append-only 触发器、连续序列、digest/CHECK、`_source_unverified` 的 v3–v6 恒 True 与 v7 结构判定。
- 30 项负向矩阵与 9 项正向路径，全部用合成 authority/Registry/观察客户端/时钟；不连真实 socket。
- 重启、提交崩溃、故障注入（用现有 `fault_point` 风格或内存 SQLite）；旧书拒绝迁移。
- 配置键不存在（解析拒绝）与请求自报字段被忽略/拒绝。
- 证明发布必须持 writer fence；旧 binary 打开 v7 失败。

**这只证明合同在受控替身上可实现，不证明真实来源。**

### 5.2 仍为 GAP / NOT_RUN

| 项目 | 原因 |
| --- | --- |
| 真实 CURVE/ZAP 握手、真实 Gateway principal 表与 grant | 需要真实服务与密钥；本地只测注入 authenticator/合成 ACL |
| 真实账户观察流/快照/行情与 provider 身份 | 需要真实 Gateway/provider；本地为 fake |
| 跨进程/跨主机撤权与注册互斥 | 依赖 Gateway 真实注册与 INV64-13 接管证据；本地无法证明 |
| 两个活主机各持一份书副本的唯一写者 | 需要 Gateway 侧单写者执行；本文不声称已解决 |
| `claim` 之后到 Gateway 实际副作用之间的 TOCTOU | 本地无法消除；保留原身份与 UNKNOWN |
| 真实 Windows/ACL/文件权限 | 未运行 |
| wheel/安装/发行与真实服务组合 | 未运行 |
| 本机 loopback 的 `PrincipalAuthenticator` 路径 | 不使用 CURVE，不能外推远端身份 |
| R-04 v2、breach、FX、provider 规则、五个 `*_verified` 占位 | 本证明不解锁，仍为独立 GAP |

任何本地通过都只能写 **UNIT/FAKE**；不得升级为真实账户或生产结论。
