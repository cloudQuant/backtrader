## 2. 目标、非目标与新增规则

### 2.1 目标

1. **独立风控服务与线协议**（U64-9；63 分析 C-1 按此调整）：risk 作为每账户一个的独立进程运行在 Gateway 之前（部署粒度见 D64-15）。bt_api_py（策略侧）与迭代 65 的 execution 服务按两段把下单交给它：`risk.order.reserve`（L1、L2 预留，并转发 Gateway `direct.reserve`）与 `risk.order.dispatch`（L3 claim 耐久提交后转发 Gateway `direct.dispatch`）；母单另有 `risk.parent.*`（U64-7）。risk 从 Gateway 账户观察流取得回报与持仓、从 MarketHub 取得参考价，据此结算占用与计数。协议的中立类型在 `bt_api_base`，次序与崩溃语义见 §4。没有 direct 钩子，Gateway 内也没有钩子。
2. **控制目录**：按 U64-1/U64-2 在 `bt_api_risk` 实现 §3 的控制，每项写明语义、事实来源、过期行为和有限错误码。
3. **修复现有问题**：账户级 dispatch latch（S-06）、遗留 `RiskManager` 默认放行、发明的缺省值、README 不实。
4. **配置**：运营维护的账户/策略/合约限额，必填项无缺省，跨平台路径；审计与可观测性。
5. **越限联动急停**：risk 向 Gateway 控制端口发出急停命令（STOP_NEW、FREEZE），急停状态由 Gateway 持有并执行（U64-12）。
6. **以 Gateway 为前提的可选组件**（U64-5）：只有开启 Gateway 时才能启用 risk；Gateway 未开启却配置了 risk 时拒绝启动；未选择不启动、不连接；选择而不可用即 fail-closed（SDK 不回退为直达 Gateway）。Gateway 不检查风控批准（U64-10），risk 只对经过它的订单生效。
7. **词汇改名**（U64-14）：risk 的 freeze 改为 STOP_NEW 一组名称、dispatch latch 改为在途占用的名称，SDK `ServiceRegistry.stop_strategy_new` 改为 FREEZE 一组名称，`MonitorRiskControlOwner` 按 63 计划 D63-35 处理（§5.7；改名总表见 63 计划 §3.19）。

### 2.2 非目标

- risk 不连 provider、不持有 provider 会话或凭据、不改订单字段（只原样转发或拒绝）、不发起撤单；它取得的账户事实全部来自 Gateway（账户观察流与只读事实），不自行向场所核实（`bt_api_risk/README.md:18` 的定位按此更新）。
- 场所事实不进 risk 配置；risk 只读 provider 声明、经 Gateway 转出的事实。
- 撤单：不经 risk 服务，SDK 直接发给 Gateway；risk 只经账户观察流计数（INV64-11）。
- 修改 `bt_api_gateway`：Gateway 侧能力全部在迭代 63（U64-15；63.12、63.13）；本迭代发现缺口时提回 63。
- execution 的开发，包括 `bt_api_py` 把 BT 订单交给 execution、拆单与合并执行、execution 进程与崩溃处理：迭代 65（U64-6、U64-7）。本迭代只在 risk 一侧提供母单预留合同并用替身测试（64.10），不接入 execution。
- monitor 中继与告警规则：Gateway 一侧的中继在迭代 63；本迭代只提供 risk 自身的审计、状态查询和指标。monitor 不发控制命令（U64-13）；`monitor_required` 下的 STOP_NEW 由 Gateway 自己判定（U64-8），不属 risk。
- 程序化交易报告（S-12）：只提供计数导出供运营使用；不宣称满足任何监管要求。
- 改进遗留分析类与 ML：只把它们隔离出关键路径。
- 生产账户验证；OKX/Binance demo 验收（D64-13）。

## 3. 风控目录

### 3.1 通用语义

- **判定**：PASS；DENY（有限码，确定未发送）；WARN（放行并告警）。
- **动作**：OPEN（INCREASE）、CLOSE（REDUCE）、CANCEL。撤单不经 risk（INV64-11），risk 只从观察流计数，永远不拒撤单（U64-4）。
- **检查层**（全部在 risk 服务内；BT 不调用、不导入 risk）：L1 无状态逐单（`risk.order.reserve` 受理时）；L2 预留（有状态：额度、持仓、亏损状态；与 L1 同一事务）；L3 claim（`risk.order.dispatch` 时，在按账户串行的事务内：自成交、计数消耗、范围锁存、参考价复核；提交后才转发 Gateway）；L4 交易后与实时（经 Gateway 账户观察流的成交、委托状态与账户事实，经 MarketHub 的参考价）。
- **在途**：本账户已过 L2 的预留、已 claim 未结、Gateway DISPATCHING、在场所活动、UNKNOWN；UNKNOWN 按最坏情况计（可能仍活动或已成交）。绕过 risk 的订单从观察流得知后也计入在途（INV64-10）。
- **范围键**：账户（route + provider 哈希账户引用）、策略（策略目录 UUID）、合约（中立合约键）。

### 3.3 母单级检查（供迭代 65 使用）

execution 是经 Gateway 下单的独立进程，`bt_api_py` 把 BT 订单交给它（U64-6、U64-7），其开发在迭代 65。risk 一侧的合同与调用路径如下（与迭代 65 计划 §3.7 一致；迭代 65 原 D65-12 “由 Gateway 调用 `reserve_parent`”的建议已由 U64-9 消解，因为 Gateway 不调用 risk）：

- `risk.parent.reserve`（即 `reserve_parent`）：**execution 服务**在受理母单之后、切片之前调用，按整笔预留 R-03、R-07 与策略额度，并记录母单范围（合约、方向、开平、限价、交易日、总量）。拒绝即母单确定未开始。R-01、R-02 不按母单查（母单没有单一价格），在子单上查。
- 子单走与普通订单相同的两段：execution → `risk.order.reserve`（带 `parent_ref`、`child_id` 作 `request_key`）→ risk 转发 Gateway `direct.reserve`；execution → `risk.order.dispatch` → risk 在 claim 事务内检查自成交与计数 → 转发 Gateway `direct.dispatch`。子单预留从母单预留中扣减，不重复占用；子单累计超过母单总量、或越出母单范围时拒绝 `risk_parent_envelope_exceeded`。execution 不直接操作 risk 账本，也不在开 risk 时直接向 Gateway 下子单。
- 母单完成或撤销时，execution 调 `risk.parent.release` 释放未用部分；risk 也从观察流核对子单终态，有 UNKNOWN 子单的母单保持占用。execution 崩溃时只冻结它的母单（不再切片、不再预留子单），已发出的子单保留并照常由 Gateway 管理和回报（U64-6）；risk 对该母单的预留在 execution 重启并处理之前保持。
- 现有 risk 只有单意图与多腿 group vector（`risk: core/admission.py:5648`、`6230`），没有母子分摊合同（63 分析 §1.3）。合同的字段与语义若与迭代 65 计划冲突，以两份计划协调后的冻结稿为准。

### 3.4 越限如何触发急停

- risk 产生 `RiskBreach`（控制 ID、范围、阈值版本、观测值、时间、证据摘要），按配置映射为急停命令：可自动发出 STOP_NEW 与 FREEZE（D64-11）；DRAIN 与 RESUME 只能由运营发出。
- 命令经中立 `KillSwitchCommandSink` 送往 Gateway 控制端口（U64-12；63 计划 §3.17、63.12），risk 服务以自己的 principal 提交，Gateway 只授予它 STOP_NEW 与 FREEZE；命令号由越限 ID 派生，重复发送幂等。
- Gateway 还会收到其他来源的命令：运营、runtime（迭代 66）。monitor 不发命令（U64-13）；运营声明 `monitor_required` 时，monitor 存活丢失由 Gateway 自己判定并施加 STOP_NEW（U64-8）。risk 不参与这条判定，也不把 monitor 存活丢失当作 risk 越限。
- risk 只记录“已发出”和 Gateway 回执，不把回执当作效果证明。
- Gateway 不可达或回执不明时，risk 在自己账本中对该范围保持本地拒绝锁存（OPEN 拒 `risk_breach_latched`），直到 Gateway 回执确认或运营解除。这个锁存只拦经过 risk 的订单（INV64-10）；Gateway 不可达时 risk 转发的订单本来也发不出去。
- 急停状态的权威不在 risk（INV64-01）；本地锁存只影响 risk 自己的判定。risk 原有的账户级 freeze（monitor FREEZE 落在这里）按 §5.7 改名为 STOP_NEW 一组名称；`MonitorRiskControlOwner` 按 63 计划 D63-35 处理。

## 4. 风控 API 与调用点

### 4.1 中立合同与服务操作（`bt_api_base` 与 bt_api_py 的 risk 服务客户端，名称在 64.01 冻结）

- `RiskOrderView`：route、账户引用（哈希）、写入主体（策略 UUID）、`origin`（本人 / execution 代理）、`parent_ref`、`child_id`（与 63 计划 §3.5 的 `direct.reserve` 载荷相同）、`request_key`（策略：UUID + 局部序号；execution 子单：`child_id`；risk 转发 Gateway 时原样沿用）、中立合约键、方向、显式开平（无开平的场所为空）、持仓侧、数量与单位、订单类型、限价（可空）、有效期、交易日、会话代际。效果 INCREASE/REDUCE 由 risk 按 INV64-04 推导，不由调用方给出。
- `RiskFacts`：risk 服务内部的事实快照，**不再由派发点传入**：参考价（MarketHub）、合约事实（乘数、价位，provider 声明经 Gateway 转出）、各策略归属持仓与在途、账户可平量与今昨、账户资金与费率摘要（经账户观察 principal 读取），以及各项年龄与完整性；字段可空，空即“未知”（INV-04）。
- 服务操作（调用方 → risk 服务；每个调用带截止时间；拒绝以有限码返回）：`risk.order.reserve(view)` → 许可号与 Gateway 预留号；`risk.order.dispatch(permit, reservation_id, 请求摘要)` → Gateway 派发结果；`risk.order.release(permit)`；`risk.order.status(request_key | permit)`；`risk.parent.reserve`、`risk.parent.release`、`risk.parent.status`（§3.3）；`risk.status`。没有 `check`/`claim`/`settle`/`observe` 的外部入口：L1 在 reserve 内，claim 在 dispatch 内，结算与观察由 risk 消费 Gateway 观察流完成。
- `RiskSettleOutcome`（risk 内部，按 Gateway 结果填写）：NOT_SENT（附证据类别：Gateway 拒绝、预留到期、无 DISPATCHING 记录）、ACCEPTED、FILL（逐笔，按成交键幂等）、TERMINAL（撤销/拒绝/全成，带累计成交）、UNKNOWN。
- `KillSwitchCommand`：使用迭代 63 在 `bt_api_base` 定义的统一急停词汇（63 计划 §3.19、63.02）：动作（FREEZE/STOP_NEW/DRAIN/RESUME）、范围（账户/策略/合约）、命令号、原因码；本迭代只使用，不另定义。
- 不进 base：政策数值、计数状态、存储格式（归 risk）；场所事实（归 provider）。

### 4.2 调用路径与次序（risk 服务位于 Gateway 之前）

初稿的“Gateway 在派发锁内调用 claim”不再成立：risk 与 Gateway 是两个进程，risk 的检查不能和 Gateway 的派发持同一把锁（63 分析 P2 的“同进程同锁”在此做不到）。改用以下规则：

- **原子性在 risk 内部**：每个账户一个 risk 服务、一个 SQLite 账本；`reserve`（L1+L2）与 claim（L3）各是一个 `BEGIN IMMEDIATE` 事务，同一账户的事务串行，所以经过 risk 的订单之间看到的是一致的额度、持仓与在途。
- **在途从 claim 开始计**：claim 一经提交，该订单就按最坏情况计入在途（持仓、额度、自成交反向集、计数），直到 risk 从 Gateway 得到确定结果。risk 不在 Gateway 往返期间持有写锁，claim 提交后才转发，所以 Gateway 的延迟不阻塞其他策略的 claim，代价是在途按最坏情况多计一段时间。
- **Gateway 的拒绝释放预留**：Gateway 在预留或派发时拒绝（授权、急停、流控、会话、日切、预留到期等），都是确定未发送，risk 在同一请求内 `settle(NOT_SENT)` 释放占用。

| 步 | 调用 | 执行者 | 拒绝或失败的含义 | 耐久要求 |
| --- | --- | --- | --- | --- |
| 1 | BT 分配局部序号 | 策略进程 | — | `live_state`（63 计划 §3.6 第 1 行） |
| 2 | SDK → `risk.order.reserve(view)` | risk 服务：L1 + L2，一个事务 | risk 拒绝：确定未发送 | risk 预留（ACTIVE，带到期，不长于 Gateway 预留到期）先提交 |
| 3 | risk → Gateway `direct.reserve(request_key, origin=risk, on_behalf_of=策略)` | Gateway：授权（含代理）、会话、日切、急停、流控、归属可平量（63 计划 §3.5） | Gateway 拒绝：risk 在同一请求内释放预留，回复确定未发送 | Gateway RESERVED；risk 记下 `reservation_id` |
| 4 | risk 回复（许可号、`reservation_id`）；BT 写 PREPARED（含二者） | 策略进程 | — | `live_state`（63 计划 §3.6 第 3 行） |
| 5 | SDK → `risk.order.dispatch(permit, reservation_id, 摘要)` | risk 服务：L3 claim，一个事务 | risk 拒绝：确定未发送；risk 释放占用，并尽力 `direct.release` Gateway 预留（失败则等到期） | claim 先耐久提交（INV64-08） |
| 6 | risk → Gateway `direct.dispatch` | Gateway 派发锁内：急停复查 → OrderRef → DISPATCHING → grant → 原生调用 | NOT_SENT：risk `settle(NOT_SENT)` 释放；SENT：保持占用；UNKNOWN：按最坏占用直到 Gateway 解决 | Gateway 日志（63 计划 §3.6 第 5–7 行） |
| 7 | risk 回复 SDK | — | SDK 超时：报告结果不明，按 Gateway `direct.command_status` 解决（INV64-08） | BT 标记 DISPATCHED/TERMINAL |
| 8 | risk 消费 Gateway 账户观察流 | risk 服务 | 从不授权 | 按身份与成交键幂等 `settle`；消费游标在 risk 持久化之后 ACK |
| 9 | 观察绕过 risk 的订单、撤单、外部委托 | risk 服务 | 从不授权，也不能阻止（INV64-10） | 计数、自成交视图、持仓 |

撤单：SDK 直接发给 Gateway（INV64-11），risk 从观察流计数（R-04）。结算确认只在 Gateway，不经过 risk。

**竞态与绕过（如实说明）**：

- 经过 risk 的订单之间没有检查与占用的竞态（claim 串行）。Gateway 的派发次序可能与 claim 次序不同，不影响判断，因为已 claim 的订单都已按在途计入。
- 绕过 risk 的订单（INV64-10）在 Gateway 回报之前 risk 看不到。在这段时间里，risk 可能放行一笔会与它相交的订单，或在计数上少算。这是 Gateway 接受未经风控的订单（U64-10）的直接后果，属于已接受的性质；如果同一账户的所有写入都经 risk，这一缺口就不存在。
- 急停在 Gateway 执行（U64-12），对所有订单生效，不受上述竞态影响。
- R-03b 的账户可平量依赖观察流的新鲜度；观察流中断或过期时，risk 按 D63-07 的 UNVERIFIED 处理（CLOSE 拒 `risk_closable_unverified`）。

**时延**：每笔下单在 reserve 与 dispatch 两段各多一跳（SDK → risk → Gateway），外加两次 risk 写事务；同一账户的 claim 吞吐受 SQLite 写事务速率限制。具体数值未知，按 INV-12 在 64.11 实测 p50/p99，不预设结论。

### 4.3 崩溃与超时语义

原则：risk 自己从不主动重发 `direct.dispatch`；一切不确定都按 Gateway 的记录解决（`direct.command_status` 按 `request_key` 或 `reservation_id` 查询，以及观察流重放）。幂等键：`request_key`（同键同内容返回原结果，同键不同内容拒绝）、许可号、`reservation_id`。

| 位置 | 现象 | 恢复 | 写入 |
| --- | --- | --- | --- |
| risk 预留提交后、转发 `direct.reserve` 前 risk 崩溃 | risk 有孤立预留；Gateway 无记录 | 重启后按 `request_key` 查 Gateway：无记录 → 释放；SDK 的 reserve 调用超时，按确定未发送处理（没有许可号就不可能派发） | 不受影响 |
| Gateway RESERVED 之后、回复 SDK 之前 risk 崩溃 | Gateway 有预留，SDK 没拿到许可号 | SDK 不会派发；Gateway 预留到期 → EXPIRED（确定未发送）；risk 重启后按 `request_key` 查到 EXPIRED 即释放。SDK 用同一 `request_key` 重试 reserve 时返回原结果 | 不受影响 |
| claim 提交后、转发 `direct.dispatch` 前 risk 崩溃 | 有 claim，Gateway 仍是 RESERVED | risk 重启后不补发；等 Gateway 预留到期 → `settle(NOT_SENT, evidence=reservation_expired)`；SDK 侧此前已报告结果不明，按 `direct.command_status` 得到 EXPIRED 后转为确定未发送 | 本单确定未发送；该合约在解决前按 D63-04 阻断 |
| 转发 `direct.dispatch` 后、收到结果前 risk 崩溃 | Gateway 有 DISPATCHING 或终态 | risk 重启后按 `reservation_id` 查 Gateway，并从上次 ACK 重放观察流；SENT/UNKNOWN 保持占用，终态按结果结算 | 同上 |
| Gateway 在 DISPATCHING 前后崩溃 | — | 按 63 计划 §3.6 第 5–7 行（无 DISPATCHING 即确定未发送；有则按原身份查询解决）；risk 保持最坏占用直到 Gateway 公布结果 | 同上 |
| 策略进程崩溃 | Gateway 与 risk 不受影响 | 按 63 计划 §3.6；未派发的预留在两处到期并释放；已派发的照常结算 | 只影响该策略 |
| execution 进程崩溃 | 同上 | 母单按 §3.3 冻结；子单同普通订单 | 只影响该母单 |
| SDK 或 execution 调 `risk.order.dispatch` 超时或断连 | 不知 risk 是否已转发 | 报告结果不明（INV64-08），按 Gateway `direct.command_status` 解决；不换 `request_key` 重发 | 该合约在解决前阻断 |
| risk 不可用（SDK 已写 PREPARED 之后） | 无法派发 | SDK 不得改为直达 Gateway（INV64-02）；Gateway 预留到期 → 确定未发送 | 本单确定未发送 |
| risk 存储损坏或丢失 | — | risk 拒绝启动；SDK 按 D64-02 拒 PLACE，撤单直达 Gateway 不受影响；人工核验后用 Gateway 账户事实重建基线（沿用 LIVE_GROSS 基线与 rebase 路径） | 经 risk 的 PLACE 全部关闭 |
| 四个存储不原子（`live_state`、risk、Gateway 日志，开 execution 时另有 execution 日志） | — | 次序规则：原生调用只发生在所有相关耐久记录之后（63 分析 §3.2）；risk 的 claim 先于转发，Gateway 的 DISPATCHING 先于原生调用 | — |

### 4.4 选中而不可用（S-05）

- “不可用”：risk 服务未启动或不可达、政策未绑定（`bind_policy`）、存储不可写、调用超过截止时间、`risk.status` 报告降级。
- 行为按 D64-02（建议 a）：SDK 拒绝 OPEN 与 CLOSE，码 `risk_unavailable:<原因>`；撤单直达 Gateway，不受影响；结算确认在 Gateway，不受影响；不回退为直达 Gateway（不回退到“没有 risk”）。
- 由策略配置 `gateway.risk`（§6.1）决定本策略的 PLACE 是否经 risk；配置为经 risk 时，risk 不可用即本策略不能下单。Gateway 不知道、也不检查这一配置（U64-10）。

### 4.5 部署与调用路径（与 63 计划 §3.18、65 计划 §3.1 一致）

risk 只在开启 Gateway 时可用（U64-5）；派发点始终是 Gateway 交易 owner。

| 部署 | PLACE 路径 | risk 的调用方 | 说明 |
| --- | --- | --- | --- |
| Gateway + risk | SDK → risk 服务 → Gateway | 策略进程内的 bt_api_py（`risk.order.*`） | 撤单与读取直达 Gateway |
| Gateway + execution 服务 + risk（迭代 65） | 未命中执行路由：同上；命中：母单交给 execution（入口见 65 D65-01），execution → `risk.parent.reserve`；子单 execution → risk 服务 → Gateway | bt_api_py（直通订单）；execution 服务（母单与子单） | risk 侧合同在 64.10；execution 接入在迭代 65 |
| Gateway（未开 risk） | SDK → Gateway；execution 子单 execution → Gateway | — | 没有本迭代的任何控制；自成交保护缺失属已知功能缺失（U64-11） |

只有一种形态（独立服务，U64-9），不再需要“进程内库与服务两种形态的一致性”；64.11 改为测量服务形态的时延、吞吐与故障行为。

## 6. 配置、审计与可观测性

### 6.1 配置位置与路径

- **前提（U64-5）**：risk 只在 Gateway 开启时有效。非 Gateway 的策略配置出现 risk 设置时以有限码拒绝启动（§5.3），不忽略、不降级为“没有 risk”。
- **risk 服务目录**（运营维护，与 63 D63-08 a 的账户级 Gateway 文件夹并列）：服务配置（Gateway 连接文件、risk 服务的客户端密钥、存储目录、监听地址）与政策文件 `risk_policy.yaml`。Gateway 的账户配置不配置 risk（Gateway 不调用 risk，U64-10），只登记 risk 服务的代理 principal、账户观察 principal 与控制端口权限（63 计划 §3.5、63.13）。
- **策略目录 `config.yaml`**（`access: gateway` 时）写 `gateway.risk`：`none`，或 risk 服务的连接文件（经 risk 下单）。是否必须显式写出见 D64-01。可另写更严的本策略限额，随会话登记交给 risk 服务，由 risk 校验“只能收紧”（64.01 冻结是否在本迭代支持）；策略进程不加载政策文件。
- 路径：相对路径相对于该配置文件所在目录；支持 `~` 与环境变量展开；用 `pathlib` 处理，Windows、macOS、Linux 一致；存储目录必须在本机文件系统（SQLite 锁的限制同 `gw: quota_admission.py:1-7`，不支持网络文件系统）；POSIX 下目录 0700、文件 0600；Windows ACL 尽力而为（未验证，UNKNOWN）。
- 配置不含凭据和原始账号；账户只用 provider 的哈希引用。

### 6.3 校验

- 未知键拒绝；数值为有限正 Decimal；启用的控制缺少阈值是配置错误，不等于“关闭”。
- 策略限额 ≤ 账户限额（只能收紧）；策略 UUID 必须是已登记的写入主体。
- 政策指纹绑定到 risk 账本（沿用 `bind_policy`）；改政策需新版本；运行中变更按 D64-12（建议本迭代只在 risk 服务重启时生效）。
- Gateway 未开启而出现 risk 配置：拒绝启动（U64-5，§5.3）。
- risk 服务启动时核对：Gateway 已为它登记代理、观察、行情与控制端口权限（63.13、63.12），缺任何一项即拒绝启动，不降级。
- 提供不连账户的离线校验入口，供运营开盘前检查。

### 6.4 审计

- 每次 check、reserve、claim、release、settle、拒绝、越限、急停命令各记一条：时间、主体、合约、效果、政策版本、命中的控制与有限码、输入摘要（不含账号与凭据）、耗时。
- 追加写入 risk 存储，不改写；按交易日导出计数报表（JSON/CSV）供运营按期货公司要求报告（S-12），不是监管报送。

### 6.5 可观测性

- `status`：可用性、政策版本、各范围的越限锁存与本地拒绝锁存、计数与阈值利用率、参考价过期次数、claim 延迟分位数；不输出完整路径与账号。
- 指标经 SDK 日志与 monitor 接口导出（可选）；monitor 只观察（U64-13），缺失不影响 risk 判定（63 分析 P4）。运营声明 `monitor_required` 时，monitor 存活丢失后的 STOP_NEW 由 Gateway 自己判定并执行（U64-8），risk 不参与该判定。
- `status` 另报告：观察流的游标与延迟、经观察流发现的绕过 risk 的订单数（INV64-10）。
- BT `get_direct_reconcile_report()`（Gateway 分支）增加 `risk` 摘要：本策略是否配置为经 risk、risk 服务是否可用、本策略最近的拒绝码计数。
