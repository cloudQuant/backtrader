## 1. 背景与现状（STATIC，2026-11-06）

### 1.1 为什么有本迭代

- 用户对 63 分析 §6.4 的回答：S-02 选 B，Gateway 只做授权、归属和流控，其余交给 `bt_api_risk`（U64-1）；S-03 的单笔上限与价格带都要，归 `bt_api_risk`（U64-2）；S-01 待定（U64-3）；S-04 语义采纳、归属待定（U64-4）。S-01 与急停归属当晚已决定，见下文第三条。
- 后果：63 分析 §6.1 原建议在 Gateway 内置的单笔上限、跨策略自成交、报撤单计数改由 risk 提供。**没选 risk 的 Gateway 部署就没有这三项控制**；用户已确认其中自成交保护的缺失是已知的功能缺失（U64-11）。63 计划中受影响的条目（§3.5 principal grant 的单笔上限、§3.10 的计数、D63-11 自成交）已在 2026-11-06 的修订中改掉，见 63 计划修改记录。
- 同日用户又决定（U64-5～U64-8）：execution、risk、monitor 只能在开启 Gateway 时启用（S-09），所以不存在 direct + risk，迭代 62 的 direct 路径保持没有 risk；execution 是经 Gateway 下单的独立进程（S-07），由 `bt_api_py` 把 BT 订单交给它，开发放在迭代 65（S-08）；monitor 缺省可选，运营声明 `monitor_required` 时心跳中断由 Gateway 执行 STOP_NEW（S-10）。
- 同日晚上用户决定（U64-9～U64-15）：S-01 选独立风控服务，放在 Gateway 前面，开启 risk 时 BT 的订单先经 risk 再到 Gateway（U64-9）；随即更正：Gateway 也接受没有风控批准的订单，是否经过 risk 由 bt_api_py 的部署配置决定（U64-10）；不选 risk 时不考虑自成交，属功能缺失（U64-11，S-13）；急停状态由 Gateway 持有并执行（U64-12，S-19）；monitor 只观察、不发控制命令（U64-13，S-20）；现有急停词汇改名统一（U64-14，S-24）；Gateway 相关的开发都在迭代 63（U64-15）。
- 因此，**risk 是一个位于 Gateway 之前的独立服务进程**：bt_api_py（策略进程内的 Gateway route）与迭代 65 的 execution 服务把下单请求交给 risk 服务，risk 在自己的账本里预留和 claim 之后再转发给 Gateway。Gateway 不调用 risk、不检查风控批准；本迭代需要的 Gateway 侧能力（代理 principal、账户观察流、行情 principal、控制端口、`request_key`）由迭代 63 的 63.12、63.13 提供，本迭代不修改 `bt_api_gateway`。初稿里“Gateway 交易 owner 在派发锁内调用 risk 库”的设计不再成立，§3、§4 已按服务形态重写。

## 2. 目标、非目标与新增规则

### 2.1 目标

1. **独立风控服务与线协议**（U64-9；63 分析 C-1 按此调整）：risk 作为独立进程运行在 Gateway 之前（每账户一个是 D64-15 的建议，部署粒度待用户决定）。bt_api_py（策略侧）与迭代 65 的 execution 服务按两段把下单交给它：`risk.order.reserve`（L1、L2 预留，并转发 Gateway `direct.reserve`）与 `risk.order.dispatch`（L3 claim 耐久提交后转发 Gateway `direct.dispatch`）；母单另有 `risk.parent.*`（U64-7）。risk 从 Gateway 账户观察流取得回报与持仓、从 MarketHub 取得参考价，据此结算占用与计数。协议的中立类型在 `bt_api_base`，次序与崩溃语义见 §4。没有 direct 钩子，Gateway 内也没有钩子。
2. **控制目录**：按 U64-1/U64-2 在 `bt_api_risk` 实现 §3 的控制，每项写明语义、事实来源、过期行为和有限错误码。
3. **修复现有问题**：账户级 dispatch latch（S-06）、遗留 `RiskManager` 默认放行、发明的缺省值、README 不实。
4. **配置**：运营维护的账户/策略/合约限额，必填项无缺省，跨平台路径；审计与可观测性。
5. **越限联动急停**：risk 向 Gateway 控制端口发出急停命令（STOP_NEW、FREEZE），急停状态由 Gateway 持有并执行（U64-12）。
6. **以 Gateway 为前提的可选组件**（U64-5）：只有开启 Gateway 时才能启用 risk；Gateway 未开启却配置了 risk 时拒绝启动；未选择不启动、不连接；选择而不可用即 fail-closed（SDK 不回退为直达 Gateway）。Gateway 不检查风控批准（U64-10），risk 只对经过它的订单生效。
7. **词汇改名**（U64-14）：risk 的 freeze 改为 STOP_NEW 一组名称、dispatch latch 改为在途占用的名称，SDK `ServiceRegistry.stop_strategy_new` 改为 FREEZE 一组名称，`MonitorRiskControlOwner` 按 63 计划 D63-35 处理（§5.7；改名总表见 63 计划 §3.19）。

8. **独立可选前端入口（D63-47）**：Risk 服务提供可独立启用的页面入口，页面与风控业务解耦；关闭页面不停止服务，不改变 risk 选用、失败关闭、预留和恢复合同。页面与未来 `ai-for-investor` 均通过同一版本化服务 API 接入；Risk 服务/API 不依赖页面或该系统运行。本迭代不实施 `ai-for-investor` 集成。用户已决定页面可查看规则、额度和风险状态，并经 Risk 自身受权管理 API 调整规则；具体角色/操作枚举、schema 及规则何时生效仍须冻结，不据此授权自动恢复或扩大权限。详见 §6.6、64.13。

### 2.2 非目标

- risk 不连 provider、不持有 provider 会话或凭据、不改订单字段（只原样转发或拒绝）、不发起撤单；它取得的账户事实全部来自 Gateway（账户观察流与只读事实），不自行向场所核实（`bt_api_risk/README.md:18` 的定位按此更新）。
- 场所事实不进 risk 配置；risk 只读 provider 声明、经 Gateway 转出的事实。
- 撤单：不经 risk 服务，SDK 直接发给 Gateway；risk 只经账户观察流计数（INV64-11）。
- 修改 `bt_api_gateway`：Gateway 侧能力全部在迭代 63（U64-15；63.12、63.13）；本迭代发现缺口时提回 63。
- execution 的开发，包括 `bt_api_py` 把 BT 订单交给 execution、拆单与反向轧差、execution 进程与崩溃处理：迭代 65（U64-6、U64-7）。本迭代只在 risk 一侧提供母单预留合同并用替身测试（64.10），不接入 execution。
- monitor 中继与告警规则：Gateway 一侧的中继在迭代 63；本迭代只提供 risk 自身的审计、状态查询和指标。monitor 不发控制命令（U64-13）；`monitor_required` 下的 STOP_NEW 由 Gateway 自己判定（U64-8），不属 risk。
- 程序化交易报告（S-12）：只提供计数导出供运营使用；不宣称满足任何监管要求。
- 改进遗留分析类与 ML：只把它们隔离出关键路径。
- 生产账户验证；OKX/Binance demo 验收（D64-13）。

## 3. 风控目录

### 3.1 通用语义

- **判定**：PASS；DENY（有限码，确定未发送）；WARN（放行并告警）。
- **动作**：OPEN（INCREASE）、CLOSE（REDUCE）、CANCEL。撤单不经 risk（INV64-11），risk 只从观察流计数，永远不拒撤单（U64-4）。
- **检查层**（全部在 risk 服务内；BT 不调用、不导入 risk）：L1 无状态逐单（`risk.order.reserve` 受理时）；L2 预留（有状态：额度、持仓、亏损状态；与 L1 同一事务）；L3 claim（`risk.order.dispatch` 时，在按账户串行的事务内：自成交、计数消耗、范围锁存、参考价复核；提交后才转发 Gateway）；L4 交易后与实时（经 Gateway 账户观察流的成交、委托状态与账户事实，经 MarketHub 的参考价）。
- **在途**：本账户已过 L2 的预留、已 claim 未结、Gateway DISPATCHING、在场所活动、UNKNOWN；UNKNOWN 按最坏情况计（可能仍活动或已成交）。绕过 risk 的订单从观察流得知后也计入在途（INV64-10）。
- **范围键**：账户（route + provider 哈希账户引用）、策略（策略目录 UUID）、合约（中立合约键）。

### 3.1a 账户、策略与虚拟转换（D63-41、D65-27/28，2026-11-08 已决定）

账户 `getcash/getvalue/getposition` 与策略 `get_strategy_cash/get_strategy_value/get_strategy_position` 的语义按共享合同；策略初始资金由金额或比例显式配置，未配置时策略资金接口不可用，不能用账户总额代替；`close`、`order_target_*` 与默认 Sizer 仍用策略范围。策略预算并非交易所隔离资金，策略可用资金、账户可用资金和两者各自占用单独计算；D63-46 已允许显式预算超配；预算比例基准、币种、配置字段及调整规则仍待冻结，不预设数值。

区分策略虚拟动作（方向、开平、今昨与归属）和实际账户动作（场所方向、开平、今昨与数量），并绑定 Gateway 权威虚拟账本、实际账户事实和两者映射的版本。首期须支持虚拟多空及其后续真实订单转换；旧逐方向“策略持仓合计等于账户持仓”仅对可证明的真实归属模式适用，虚拟模式必须核对映射、在途、桶与真实风险，净额相等本身不足。UNKNOWN 的虚拟转换不能视为完成或释放占用。

策略虚拟 CLOSE 可能产生实际账户 OPEN。D65-28 允许满足**单独配置的转换准入**时通过 Gateway 的 STOP_NEW；Gateway 根据自身授权、虚拟仓/映射和转换因果独立验证，不检查 risk 批准。普通 OPEN 不因自报 CLOSE 获例外，FREEZE、DRAIN 和其他阻断不变。选中 risk 时同时检查策略虚拟变化及真实账户新增敞口、保证金和资金；不得套用普通实际 CLOSE 的风控豁免。规则范围、限额、缺失配置与授权层级待冻结；未冻结/证据不足则对应转换不可用，未选 risk 不依赖 risk。下文 OPEN/CLOSE 除显式指策略虚拟动作外，均指**实际账户动作**；原 CLOSE 豁免不自动覆盖上述真实 OPEN。

**D65-35/36 已确认的转换经济与策略占用：** A 虚拟平多引起实际卖开以保留 B 的虚拟空仓时，真实 OPEN 手续费归 A，A 按实际成交价确认对应平仓盈亏，B 原虚拟成本保持；不另扣滑点或虚拟 CLOSE 费。按权威成交增量推进可证明的虚拟变化及映射，保留唯一发起母单及 conversion_id，不复制场所成交给 B。实际费用、估计费用占用和迟到修订分开，未知不填零，来源身份/版本幂等；部分/UNKNOWN 不预平剩余量。

各策略按自身虚拟仓位独立计提保证金、减少各自策略可用资金。A 多5/B 空5相抵而账户空仓时，两策略仍各计5手内部占用；该投影与 provider 实际保证金分列，不相加重复扣同一策略预算。母子预留、内转及转换是占用状态转换，未决量保留适用最坏占用。合约、费率、价格、币种、时点和来源版本必须明确可信，缺输入不可用而非零。A 仅平2时 A 剩3/B 仍5的虚拟占用与账户真实空2保证金分别核对；共同合同 §2.9/2.10 的全成5手、部分2/5和费用更正为联合验收输入。63 权威账本投影、65 提案、64 选用才作政策控制；不引入强制 Risk 或自动强平，策略 cash/value 核心公式按 D63-44 执行；同策略组合保证金算法仍待冻结。

**D63-44 已确认：策略资金核心口径（设计输入，未实现）。** `get_strategy_value = 显式初始预算 + 已生效预算调整 + 已实现盈亏（扣费用前） + 浮动盈亏 − 费用`；`get_strategy_cash = get_strategy_value − 策略虚拟保证金 − 尚未被前项覆盖的在途资金占用`。浮盈、浮亏均影响策略可用资金，虚拟保证金不减少权益；负 cash/value 如实返回，负数本身不等同拒单、自动强平或选择 R-08 deny。显式策略初始预算原则不变，未配置或必需事实缺失时接口不可用/UNKNOWN，不能借账户值或填零；已实现盈亏以 gross 口径配合费用单独扣一次。Risk 只消费 63 唯一权威策略账本的来源绑定、版本化投影，不另立资金账本权威；未选 Risk 仍能计算和查询。

期货结算及 `cashadjust` 的已结算变动须与盈亏、估值基准及结算事件去重，不能把已经转为已实现/结算调整的浮盈再次计入；重放、费用晚到和更正按来源身份幂等处理。现货购入本金、空头、利息等需先冻结适用资产模型，再按同一 cash/value 语义对照，不能把期货公式的保证金设零当成完整现货资金模型。来源、币种、估值切点、金额/比例基准、预算调整生效、配置字段及同策略组合保证金计算等仍待按职责细化；显式超配按 D63-46 允许，不改变已定核心公式。

BackBroker 回测也应提供 `get_strategy_cash`、`get_strategy_value`、`get_strategy_position` 并与实盘作用域及计算语义对照；仅使用本地已确认模拟成交、费用与估值来源，缺事实不可伪造。此处仅为设计要求，不代表回测已实现、账户已验收或依赖新 Risk 服务；单策略回测按 D63-45 允许复用显式账户初资，多策略仍分别分配；绑定与来源识别由70实现。

**验收向量：**预算 100000、调整 0、已实现 gross 2000、浮盈 3000、费用 100、虚拟保证金 20000、尚未覆盖在途占用 10000：value 为 104900、cash 为 74900；浮盈改浮亏 3000 时 value 为 98900、cash 为 68900。若随后取消并经确认释放 10000 在途占用，仅 cash 增加 10000（分别为 84900、78900），value 不变；重复事件结果不变。另验证负值原样、缺事实不可用、费用单扣、期货结算与浮盈不重算、现货仅在其资产模型确认后核对、未选 Risk 的查询，以及 BackBroker 和实盘在各自可信输入下语义一致。

**D63-46 已确认：允许显式策略预算超配。** 账户初始权益 100 万，策略 A、B 各自显式配置初始预算 60 万，配置可以接受，不能自动缩成 50 万/50 万，也不能因预算合计 120 万而增加真实账户资金。各策略 cash/value 仍按其预算和 D63-44 计算，不要求策略权益合计等于账户权益。可比较时单列已声明预算差额/调节项：初始化为账户初始权益减策略初始预算总和，本例为 −20 万；它仅用于预算对账，不进入任何可用资金池，不是外部真实借款、资金、盈亏或实际 SHORTFALL。后续预算调整及账户权益变化的对账规则由权威账本合同细化。

账户资金约束另行检查；仅在选用 Risk 且 R-08 模式为 deny 的合同下，策略预算检查通过不代表账户能够同时承接。无费用示例中账户可用资金 100 万，A、B 的每单新增保证金各需 60 万，且各自策略预算足够：两笔并发时账户层只能有一笔取得 60 万预留，另一笔不得因为配置允许超配而通过账户资金预留；两层占用均须按可信水位去重。此示例不把 D64-10 的 off/warn/deny 默认改为 deny，不强制选择 Risk，也不把该业务政策检查加到 Gateway；其他部署沿用既定职责：BackBroker 保留模拟账户购买力检查，实盘 provider/柜台决定实际承接；未选 Risk 或 off/warn 不据此声称已有 deny 级预检。各模式的实际实现与证据分别验收。

选用适用资金控制的 Risk 时，按所选模式分别检查各策略预算及账户资金，以来源/水位避免将虚拟持仓占用、母子及转换预留、真实保证金重复扣在同一策略预算；R-08 未配置模式时按已确认 D64-10 缺省 off；显式 warn/deny 仍按所选模式执行。费用未知仍保留适用预估占用，已确认费用晚到/更正按原身份更新损益及预留。

**D63-48：理论持仓与外部账本（Q25/Q26 已决定）。** 运行策略形成自身理论持仓，外部订单/成交归有来源的 `external` 策略账本，外部账本不是运行策略间轧差或虚拟转换的参与方。按同账户、同合约、同单位和可比较切点的带符号净数量核对（多为正、空为负）：Σ 普通策略理论持仓 + 外部持仓 = 账户持仓；两边数值不匹配由 Monitor 告警。多空 gross、今昨桶、实际可平及资金仍分别检查，净数相等不能证明这些维度一致；切点或来源不全则标不可比较，不能倒算残差作为外部事件补平。Risk 只消费 Gateway 的权威账本及 provider 账户事实：策略风险使用相应策略理论仓和在途，账户风险包含外部实际仓/活动及在途；不因 external 来源或未配其预算自动暂停全账户，亦不因此绕开已选择的 Risk 规则。外部来源和普通策略自己的订单归属、费用、身份及重放保持独立。 普通策略汇总包含已停止、离线但理论持仓尚未清零的策略，不按当前运行进程列表过滤。

**D63-49（Q27 用户已决定）：外部成交造成无真实可平量时拒单。** A 理论 +5、external −5、账户 0，A 请求平多 5 时拒绝该平仓，理论仓暂不变，拒单后仍为 A +5 / external −5 / 账户 0；不自动改发 `SELL OPEN 5`，也不改 external 或其他策略的理论仓凑平。external 不能提供 D65-28 的转换参与方、映射或 STOP_NEW 例外证明。普通策略 A/B 已确认的内部虚拟转换仍按 D65-27/28 单独处理，不受此拒单规则撤销。

职责仍遵循 D63-18：已选择 Risk 时由 R-03b 按完整可信的账户实际可平事实检查；未选择 Risk 时保持 Gateway/SDK 基础校验及 provider 原生 CLOSE 语义，明确柜台拒绝按原命令投影，不强制引入 Risk 或把账户业务风控移入 Gateway。Execution 不得通过自动改 OPEN 绕过失败。本条零可平量拒单须来自具备相应职责的交易前拒绝或原生明确拒绝；D63-38 完整同日强身份查询未找到时的 Rejected 投影另按已定合同，不改写为“确定未发”。尚未按既定规则解决的派发结果不明仍为 UNKNOWN，保留身份和未决占用，不能以账户净仓为零推断请求未成交。无成交的拒单不减少理论仓、不记平仓盈亏/虚构费用或释放该仓位保证金；仅按既有规则释放可证明未使用的订单预留。

### 3.2a 风控规则扩展合同（D64-08 / Q32）

用户确认 Risk 可继承重写，后续可按需设计不同规则。首期 Risk 提供 R-04 上述内置策略实现，同时提供版本化可继承基类/接口及真正的规则调用扩展点，允许未来经受信、合法的服务端配置选择自定义类；不得将内置行为写死在 Gateway/SDK，亦不得仅暴露空继承接口而忽略覆写结果。规则输入应包含身份与作用域、可信事实、交易日、政策版本和当前操作；输出为受限判定/越限意图与有限原因，具体 API/schema 由 64.01 冻结。组合时由 Risk 宿主独占授权、事务、计数、状态和副作用，结果不可伪造来源或放宽 SDK 准入、Gateway 授权/急停、现有 UNKNOWN 与恢复边界。

服务端只允许受信注册/配置的实现及版本，不接受请求方自报类名作为权威或任意远程代码加载；绑定可重放的实现身份、版本与配置摘要到相关持久状态，重启、变更和迁移按 D64-12 及对应合同处理；缺类、异常、未知结果或版本不符时选中规则 fail-closed，不静默退回内置或跳过。自定义规则能表达其他政策不等于本期承诺另交付内置 FREEZE/仅告警方案，也不能绕过 principal/grant、生命周期、审计、Gateway 控制权限和 UNKNOWN 约束。实际接口、隔离与部署/授权机制待冻结，不宣称现有 `core.policy_engine.Rule` 或 `PolicyCatalogService` 已是可安全用于该服务准入的扩展合同；其现有条件/动作与目录实现应在 64.01 核对复用边界。

**现有源码核对（STATIC）与落点。** Risk `core/policy_engine.py` 已有具体 `RuleCondition`、`Rule.evaluate` 与 `PolicyEngine.add_rule`（约 24、77、106、149、200 行），并非此服务经验证的抽象合同；`core/risk_manager.py:279-300` 不把政策结果的 approved 可靠合并到准入。现有 `order_admission.py:90-112,134-140` 对 gate 精确类型检查，SDK `service_risk_order_entry.py:792-795` 对 adapter 亦为精确类型，子类不能直接替换该链。须在 64.01 盘点并选择兼容/重构方案，不将现有类存在当作扩展已生效。新接口明确宿主装配、评估上下文和结构化结果、规则组合顺序及失败语义，实际接入 reserve/claim 而非只定义类型；在真实服务链用注册的测试子类验证覆写改变可配置决策，既有独立拒绝和安全栅栏不可被后来规则覆盖。重构必须保留当前 `DurableRiskAdmissionAdapter`/`DurableRiskGate` 及 SDK 入口的精确类型 guard 所承载的可信签发、来源绑定与权限安全合同，不通过简单删除类型检查或传入 adapter 子类冒充 authority；具体等价信任机制和迁移在 64.01 冻结，缺证明则关闭选中路径。此为公开源码 STATIC 核对，不代表发行或行为验证。

### 3.3 母单级检查（供迭代 65 使用）

execution 是经 Gateway 下单的独立进程，`bt_api_py` 把 BT 订单交给它（U64-6、U64-7），其开发在迭代 65。risk 一侧的合同与调用路径如下（与迭代 65 计划 §3.7 一致；迭代 65 原 D65-12 “由 Gateway 调用 `reserve_parent`”的建议已由 U64-9 消解，因为 Gateway 不调用 risk）：

- `risk.parent.reserve`（即 `reserve_parent`）：**execution 服务**收到母单意图后、切片之前调用，按整笔预留 R-03、R-07 与策略额度；选择 R-08 deny 时按整笔最坏资金及保证金预留，子单复用并划拨，不重复占用，并记录母单范围（稳定身份、合约、方向、开平、限价、创建交易日、有效期限和总量；依 Q38 可跨日）。只有证明同身份母单未受理、迟到请求不能再受理且相关预留按证据处理，才能判定确定未开始；否则按原身份保持 UNKNOWN 并核查。R-01、R-02 不按母单查（母单没有单一价格），在子单上查。
- **D65-01 后续用户决定**：BT 经 SDK 先交 Execution，选用 Risk 时 Execution 先以稳定原始请求/母单身份请求上述风控，之后由 Execution 向 Gateway 登记母单范围；Gateway 独立核验授权并持有权威数量桶，Risk 信封仅约束自身风控占用，不替代 Gateway 信封。Risk 的预留不能要求 Gateway 已登记该母单，身份分配、跨服务映射和授权在 63/64/65.01 冻结。Gateway 登记结果不明时按原身份核对三方；没有完整未受理与有效迟到请求 fence 证明不能释放 Risk 占用或重发。Gateway 不检查 Risk 批准；未选 Risk 的路径不依赖该服务。详见[共同合同 §2.32](../迭代63-Gateway统一转发与多策略共享会话/跨迭代合同与决策.md)。
- 子单走与普通订单相同的两段：execution → `risk.order.reserve`（带 `parent_ref`、`child_id` 作 `request_key`）→ risk 转发 Gateway `direct.reserve`；execution → `risk.order.dispatch` → risk 在 claim 事务内检查自成交与计数 → 转发 Gateway `direct.dispatch`。子单预留从母单预留中扣减，不重复占用；子单累计超过母单总量、或越出母单范围时拒绝 `risk_parent_envelope_exceeded`。execution 不直接操作 risk 账本，也不在开 risk 时直接向 Gateway 下子单。
- 母单完成或撤销时，execution 调 `risk.parent.release` 释放未用部分；risk 也从观察流核对子单终态，有 UNKNOWN 子单的母单保持占用。execution 崩溃时只冻结它的母单（不再切片、不再预留子单），已发出的子单保留并照常由 Gateway 管理和回报（U64-6）；risk 对该母单的预留在 execution 重启并处理之前保持。
- 现有 risk 只有单意图与多腿 group vector（`risk: core/admission.py:5648`、`6230`），没有母子分摊合同（63 分析 §1.3）。合同的字段与语义若与迭代 65 计划冲突，以两份计划协调后的冻结稿为准。
- **迭代 65 内部转移的风控依赖（2026-11-07 用户决定）**：execution 可配置反向轧差与算法或无算法，并允许轧差通过策略账本内部转移分配持仓和盈亏；依 D65-31，首期同向订单不合并为共同场所单，反向轧差后各母单剩余数量各自下场。内部转移须有独立事件身份、价格与定价依据、各参与策略及账户作用域，与场所订单和成交严格区分；不把它记作场所成交，也不凭内部转移创造或改变 provider 账户持仓事实。risk 按可信的 Gateway 策略归属账本分别更新策略暴露与盈亏，账户级暴露以账户事实及在途为准；真实归属模式按可证明的口径核对策略合计与账户，虚拟模式按 §3.1a 映射、双侧及未决转换对账，避免重复计入成交、费用或计数。定价、授权、原子性、事件顺序、幂等、恢复及对账合同须由迭代 63 修订归属合同并与 64、65 共同冻结；事实不完整或合同未就绪时，相关内部转移及依赖它的风险判定安全阻断，不宣称现有实现支持。

**D65-04（Q38 已决定）：原母单可跨交易日继续。** 母单稳定身份、所属账户/策略、总量、有效期限、方案及配置绑定跨日持久保留，不因交易日更换生成新母单或重置既有额度；跨日继续须在期限内并满足各步骤资格，不表示日切后自动可下单。选 Risk 时，原母单、子单、转换及在途占用须跨日恢复，已成、活动、待发、UNKNOWN 与已预留桶维持不重不漏；原交易日 UNKNOWN 按原账户、母单、子单及场所身份保留最坏占用，不能因新日查询缺失直接标为未发、释放或换身份重发。D63-38 的完整同日强身份查询规则不外推到旧日未知。

新日任何子单须重新绑定当前 session/交易日、有效授权、SDK 写入准入、完整新鲜账户/行情事实和适用 Risk 政策；原母单所绑定的方案/配置用于原计划恢复，Risk 规则实现和参数版本按既有变更合同校验，不因旧母单而永久豁免新日检查。平今/平昨、真实可平量、策略理论仓及映射须来自当前合格来源和 provider/Gateway 规则；不能仅由日历变化推断桶转换或可平容量。条件不足时相关子单等待或拒绝按既有合同，UNKNOWN 继续阻断适用范围。

**D65-37（Q39 已决定）：平今母单跨日的目标绑定。** 原平今母单及其原始意图、原目标持仓身份、原期限/数量不可改写；在原有效期限内跨日继续时，须先核对该原目标的持仓、可信日切映射版本及当前实际昨日可平事实，再以派生子单的当前 `CLOSE_YESTERDAY` 表达对应剩余；不得取次日新开的今仓替代原目标，不改成 OPEN。Risk 输入和来源证据分别绑定原母单 offset/目标、原创建交易日、日切映射及版本、当前交易日与会话、派生 child offset/数量、当前真实可平及已占用容量；Risk 按已验证映射和当前昨日桶执行适用检查，不能仅因父单原标签为 `CLOSE_TODAY` 而错误拒绝合法映射或绕过实际桶检查。64 不自己创造映射或场所事实；Gateway/provider 按各自职责提供和核验，联合字段/原子边界仍按上文冻结。

例如母单平今 5、前日已确认成交 2、余 3，若日切映射和当前真实可平均证明原目标对应昨日可平 3，才可在原期限内对这 3 派生平昨子单；次日新增今仓不能替代。旧日 UNKNOWN 的最坏占用按原身份保留，迟到真实成交以强身份幂等扣减原目标未完成量并重算当前可用，不能和新子单重复使用份额；未决或映射/事实缺失按既有安全门槛等待或拒绝、不猜测。真实可平量为零遵循 D63-49；已到期（包括原 DAY 期限已结束）的母单不借此延长或继续。策略间虚拟转换仍独立遵循 D65-27/28；是否选择 Risk 及 D64-10 缺省 off 不因本决定改变。

R-04 的账户 × 合约 × 交易日报撤计数按该事实发生的交易日及既有去重/未知定义归集；新日子单不因母单创建于旧日而计入旧日，迟到旧日事件按原事实日修订。日切不自动 RESUME 或全清任何 Risk 原因（D64-21/Q32）；Q34 的 Monitor 原因独立按其已确认规则处理。D64-10/Q30 的 R-08 缺省 off 不因跨日或恢复变成 deny；选 deny 时旧/新日资金快照覆盖及未决占用按来源、水位和身份去重，不因日切双扣、清零或盲释放；策略虚拟保证金仍按各自持仓独立计算。未选 Risk 路径不因此要求 Risk，Gateway/provider 职责保持。

**63/65 接口与原子边界**：联合冻结母单稳定 ID（含创建日如属于身份则保留原值）、配置/期限/总量版本、当前子单交易日/会话、原子母子/转移归属与占用版本、实际/理论今昨及映射事实、事件强身份/事实日/水位、规则和授权/准入版本、旧日未决与恢复结果。63 负责 Gateway 日切、权威账本、身份及条件提交，65 负责原母单计划/期限与调度，64 消费并记录自身占用，provider 负责原生规则及真实事实；各持久域各自原子、按原身份幂等恢复，不声称跨库原子。来源、切点、版本、桶或授权不足则适用路径保持 UNKNOWN/GAP，不凭日切自动补单。

### 3.3a 独立真实子单、反向转移及数量/资金守恒


**D65-31 已决定**：首期同向订单不合并下单，仅反向订单进行轧差；每个实际 child 绑定唯一母单及策略、原 child ID、账户、授权、方向/开平/桶、价限与信封版本，轧差剩余由各母单各自下场。risk 对该单独 child 一次预留与 claim，将其所属母单的未用额度原子划拨为在途占用；实际成交与费用按来源身份只投影到该母单，部分撤单、迟到成交、更正和 UNKNOWN 按原身份保守处理，不重复释放或越限。多母单向量仅用于反向内部转移及虚拟映射，不代表共同场所子单；D65-30 的共同实际成交两类分配被 D65-31 覆盖，不是首期目标，也不预设反向匹配策略。

D65-32 限定反向轧差只使用尚未下场且未被其他计划占用的可用数量，不为轧差主动撤单。活动场所单、派发中、撤单未确认和 UNKNOWN 的占用均排除；内部转移与真实子单竞争同一份数量时由 Gateway 权威预留原子裁定，不能只信 Execution 的本地池。用户后续决定：普通子单撤单获权威终态、成交完整对齐及占用确证释放后，原母单仍有效的未成交余量允许重新参与反向匹配；须重验双方授权、价格、可用数量、期限与其他适用条件。所选 Risk 按其原身份将额度按合同转换，Gateway 的权威数量桶决定竞争，不跨库假定原子。撤单未确认、UNKNOWN 或原母单已取消/到期不能入池，也不为轧差主动撤单。

选 risk 的内部转移候选接口为 `risk.transfer.reserve/dispatch/status/release`，以反向参与方的双边或多边 parent/strategy 向量、转移 ID、数量、桶、价格来源及策略/账户版本为输入；risk 同一事务将各参与母单的对应未用数量及适用预算划入待转移占用并同时校验各方最坏风险；与子单竞争同一母单份额时只有一个转换可成功。提交后按权威转移事件转为已确认，UNKNOWN 保留；只有证明未提交且旧请求不可生效时才能转回。实际账户资金与策略预算占用分别记账，母单、子单和转移只是同一份占用的状态转换，不双占或重复释放；D65-29 已决定内部转移支持买卖一档中间价和最新成交价两种定价类，须显式选择并验证有效行情及参与方限价，不得自动切换；Risk 消费权威来源分明的结果，不替 Execution 选择方案。D65-31 覆盖 D65-30 的共同实际成交分配安排；D65-33/34 另定两类调度和两类内部匹配，配置分别选择，Risk 不代选方案。D65-35/36 已定指定转换费用/盈亏及独立虚拟保证金原则；具体数值算法、定价输入、其他费用、虚拟映射及其余经济细则仍待用户和 63/65 按职责冻结。

64.10 的单母单替身出口独立。反向内部转移及虚拟转换分别保留扩展合同、替身和 63/64/65 真实组件联调共享回执；上游未就绪记 GAP/NOT_RUN，不阻塞 63/65 基础及未选 risk 的路径，也不等对方综合验收。

### 3.4 越限如何触发急停

- risk 产生 `RiskBreach`（控制 ID、范围、阈值版本、观测值、时间、证据摘要）。R-04 首期内置硬阈值固定请求账户 × 合约 STOP_NEW（D64-08）；其他越限的可自动命令范围仍依 D64-11，DRAIN 与 RESUME 只能由运营发出。Risk 发出的 Gateway 原因依 D64-21 须运营 RESUME，不因日切自动全清。
- 命令经中立 `KillSwitchCommandSink` 送往 Gateway 控制端口（U64-12；63 计划 §3.17、63.12），risk 服务以自己的 principal 提交，按最小权限授予已确认的命令范围；R-04 的 STOP_NEW 已决定，其他动作依 D64-11 待定。命令号由越限 ID 派生，重复发送幂等。
- Gateway 还会收到其他来源的命令：运营、runtime（迭代 66）。monitor 不发命令（U64-13）；运营声明 `monitor_required` 时，monitor 存活丢失由 Gateway 自己判定并施加 STOP_NEW（U64-8）。risk 不参与这条判定，也不把 monitor 存活丢失当作 risk 越限。
- risk 只记录“已发出”和 Gateway 回执，不把回执当作效果证明。
- Gateway 不可达或回执不明时，risk 在自己账本中对该范围保持本地拒绝锁存（OPEN 拒 `risk_breach_latched`）。本地锁存的解除和兜底交接由 D64-09/64.01 冻结；回执不证明 Gateway 原因生效，也不自动解除越限。Gateway 的 Risk 原因仍须运营 RESUME。本地锁存只拦经过 risk 的订单（INV64-10），不能据此声称 Gateway 全范围控制已生效。
- 急停状态的权威不在 risk（INV64-01）；本地锁存只影响 risk 自己的判定。risk 原有的账户级 freeze（monitor FREEZE 落在这里）按 §5.7 改名为 STOP_NEW 一组名称；`MonitorRiskControlOwner` 按 63 计划 D63-35 处理。

## 4. 风控 API 与调用点

### 4.1 中立合同与服务操作（`bt_api_base` 与 bt_api_py 的 risk 服务客户端，名称在 64.01 冻结）

- `RiskOrderView`：route、账户引用（哈希）、写入主体（策略 UUID）、`origin`（本人 / execution 代理）、`parent_ref`、`child_id`（与 63 计划 §3.5 的 `direct.reserve` 载荷相同）、`request_key`（策略：UUID + 局部序号；execution 子单：`child_id`；risk 转发 Gateway 时原样沿用）、中立合约键、方向、显式开平（无开平的场所为空）、持仓侧、数量与单位、订单类型、限价（可空）、有效期、交易日、会话代际。效果 INCREASE/REDUCE 由 risk 按 INV64-04 推导，不由调用方给出。
- `RiskFacts`：risk 服务内部的事实快照，**不再由派发点传入**：参考价（MarketHub）、合约事实（乘数、价位，provider 声明经 Gateway 转出）、各策略归属持仓与在途、账户可平量与今昨、账户资金与费率摘要（经账户观察 principal 读取），以及各项年龄与完整性；字段可空，空即“未知”（INV-04）。
- 服务操作（调用方 → risk 服务；每个调用带截止时间；拒绝以有限码返回）：`risk.order.reserve(view)` → 许可号与 Gateway 预留号；`risk.order.dispatch(permit, reservation_id, 请求摘要)` → Gateway 派发结果；`risk.order.release(permit)`；`risk.order.status(request_key | permit)`；`risk.parent.reserve`、`risk.parent.release`、`risk.parent.status`（§3.3）；`risk.status`。没有 `check`/`claim`/`settle`/`observe` 的外部入口：L1 在 reserve 内，claim 在 dispatch 内，结算与观察由 risk 消费 Gateway 观察流完成。
- `RiskSettleOutcome` 是 risk **内部**状态投影，按 Gateway 有权威且经绑定的结果填写：NOT_SENT（须满足 §4.3 的证明）、ACCEPTED、FILL（逐笔按成交键幂等）、TERMINAL（含累计成交）、UNKNOWN。它不作为 base 公共协议类型；跨进程只交换 63/64 冻结的中立命令结果及观察合同。
- `KillSwitchCommand`：使用迭代 63 在 `bt_api_base` 定义的统一急停词汇（63 计划 §3.19、63.02）：动作（FREEZE/STOP_NEW/DRAIN/RESUME）、范围（账户/策略/合约）、命令号、原因码；本迭代只使用，不另定义。
- 不进 base：政策数值、`RiskSettleOutcome`、计数状态、存储格式（归 risk）；场所事实（归 provider）。
- 调用方 → risk 的认证与授权合同由 64.01 冻结、64.02 表达中立请求和有限错误码、64.09 接线：将已认证身份、账户 scope、策略 UUID、允许的动作及 execution 代理授权绑定到请求摘要、会话/授权代际、request_key、permit 与 Gateway 预留；服务端不得采信自报身份。reserve 和 dispatch 分别检查时效与撤权；同键同语义的重试、异语义冲突、状态查询权限及重放保留期均须定义。传输认证、密钥轮换/撤销与审计不输出凭据。risk 到 Gateway 的代理 principal 只执行已认证且获授权调用者的范围，不能把任意来客请求转成它自身的代理权限。

### 4.2 调用路径与次序（risk 服务位于 Gateway 之前）

初稿的“Gateway 在派发锁内调用 claim”不再成立：risk 与 Gateway 是两个进程，risk 的检查不能和 Gateway 的派发持同一把锁（63 分析 P2 的“同进程同锁”在此做不到）。改用以下规则：

- **原子性在 risk 内部**：部署粒度待 D64-15 决定；在一个已获授权的账户单 writer、一个有效账本的前提下，`reserve`（L1+L2）与 claim（L3）分别用 `BEGIN IMMEDIATE` 串行更新 risk 自有预留和占用。SQLite 不能单独证明外部账户事实完整或跨主机单写；单 writer 的租约、代际、fence、失效与接管证明须由 64.01 与 63 冻结合适合同，缺失时拒绝接管。
- **在途从 claim 开始计**：claim 一经提交，该订单就按最坏情况计入在途（持仓、额度、自成交反向集、计数），直到 risk 从 Gateway 得到确定结果。risk 不在 Gateway 往返期间持有写锁，claim 提交后才转发，所以 Gateway 的延迟不阻塞其他策略的 claim，代价是在途按最坏情况多计一段时间。
- **Gateway 的拒绝释放预留**：只有 Gateway 对绑定的本次命令给出经验证、能证明未派发的确定拒绝，且不存在可生效的旧请求时，risk 才可 `settle(NOT_SENT)` 释放占用；泛化错误、超时、无法归属或证明不足按 UNKNOWN，参见 §4.3。

| 步 | 调用 | 执行者 | 拒绝或失败的含义 | 耐久要求 |
| --- | --- | --- | --- | --- |
| 1 | BT 分配局部序号 | 策略进程 | — | `live_state`（63 计划 §3.6 第 1 行） |
| 2 | SDK → `risk.order.reserve(view)` | risk 服务：L1 + L2，一个事务 | Risk 本次拒绝不单独证明同身份过去未受理或并发/迟到请求不能生效；仅在满足 §4.3 的绑定证明和 fence 时认定确定未发送，否则按原身份核查并保持 UNKNOWN | risk 预留（ACTIVE，带到期，不长于 Gateway 预留到期）先提交 |
| 3 | risk → Gateway `direct.reserve(request_key, origin=risk, on_behalf_of=策略)` | Gateway：授权（含代理）、会话、日切、急停、流控、归属可平量（63 计划 §3.5） | Gateway 对该命令给出符合 §4.3 的确定未发送证明时释放预留；否则 UNKNOWN | Gateway RESERVED；risk 记下 `reservation_id` |
| 4 | risk 回复（许可号、`reservation_id`）；BT 写 PREPARED（含二者） | 策略进程 | — | `live_state`（63 计划 §3.6 第 3 行） |
| 5 | SDK → `risk.order.dispatch(permit, reservation_id, 摘要)` | risk 服务：L3 claim，一个事务 | 同 permit 的拒绝/进入 RELEASING 与 CLAIMED 条件转换在同一事务互斥；仅在证明 claim 未提交、没有可生效并发/迟到派发且 Gateway 权威释放或终态满足 §4.3 后回收占用，否则 UNKNOWN | claim 先耐久提交（INV64-08） |
| 6 | risk → Gateway `direct.dispatch` | Gateway 派发锁内：急停复查 → OrderRef → DISPATCHING → grant → 原生调用 | NOT_SENT：risk `settle(NOT_SENT)` 释放；SENT：保持占用；UNKNOWN：按最坏占用直到 Gateway 解决 | Gateway 日志（63 计划 §3.6 第 5–7 行） |
| 7 | risk 回复 SDK | — | 超时按原身份核对 Risk 持久状态、Gateway 命令/观察及迟到请求 fence；证据不足保持 UNKNOWN 及占用 | BT 按经证实的状态投影，不凭超时认定终态 |
| 8 | risk 消费 Gateway 账户观察流 | risk 服务 | 从不授权 | 按身份与成交键幂等 `settle`；消费游标在 risk 持久化之后 ACK |
| 9 | 观察绕过 risk 的订单、撤单、外部委托 | risk 服务 | 从不授权，也不能阻止（INV64-10） | 计数、自成交视图、持仓 |

撤单：SDK 直接发给 Gateway（INV64-11），risk 从观察流计数（R-04）。结算确认只在 Gateway，不经过 risk。

**竞态与绕过（如实说明）**：

- 在单一有效 writer、同账本、同一已认证账户 scope、事实有效且无观察缺口的前提下，经 risk 的订单在 claim 事务内对 risk 已记录的占用串行检查；Gateway 派发顺序可与 claim 顺序不同。此结论不证明 risk 与 Gateway/provider 的事实或派发原子，也不覆盖账本外未知订单。
- 绕过 risk 的订单（INV64-10）在可验证观察之前 risk 看不到，可能出现相交或少计；即使配置要求经 risk，也不能单靠配置证明外部终端和其他主体均受约束。无证据时不得宣称账户全覆盖。D63-37 已决定可配置收紧策略 SUBMIT、默认保持原权限；覆盖以实际 grant 为准，不据此宣称账户全覆盖。
- 急停在 Gateway 执行（U64-12），对所有订单生效，不受上述竞态影响。
- 建立来源绑定的账户快照与观察流共同切点，并证明 scope/交易日/会话代际、连续序号与接收水位；先原子持久化事件和游标再 ACK，按事件身份去重；丢帧、过期、重连、换日、快照不完整或无法证明切点均进入 UNVERIFIED。不能把空集视为无活动订单；对所需事实不完整的控制执行相应 fail-closed 合同，R-03b 的 CLOSE 拒 `risk_closable_unverified`。账本丢失重建须核对在途/UNKNOWN、已占用额度及可回放区间，不以当前持仓快照单独证明恢复完成。
- R-04 以 request/order 身份关联本地 claim 与观察流，重复和重放不得双计；不能关联、迟到、UNKNOWN、终态修订与跨交易日时按待冻结口径保守处理并暴露差异，不能以估计替代外部报送口径。

**时延**：每笔下单在 reserve 与 dispatch 两段各多一跳（SDK → risk → Gateway），外加两次 risk 写事务；同一账户的 claim 吞吐受 SQLite 写事务速率限制。具体数值未知，按 INV-12 在 64.11 实测 p50/p99，不预设结论。

### 4.3 崩溃与超时语义

原则：risk 自己从不主动重发 `direct.dispatch`；超时、失联或查询结果缺失先记 UNKNOWN，按原身份查询和观察流恢复。幂等键绑定账户 scope、授权代际、`request_key`、请求语义摘要、许可号及 `reservation_id`；同键同内容返回原状态，同键异内容拒绝。

**D63-04 / Q28 已确认：本系统订单 UNKNOWN 的最小影响范围。** Gateway 拥有该系统未知范围栅栏，是否选择 Risk 不影响其执行；这项栅栏解决 UNKNOWN 影响范围，不把一般账户可平业务检查 R-03b 移入 Gateway。本系统订单 UNKNOWN 时，阻断其所属策略在该合约的**所有新订单**，包括 OPEN、CLOSE、后续子单及通过新内部转移提交执行的订单份额；不得更换母单或请求身份绕过。已提交转移按原身份核对，不自动撤销既有活动单，不停止策略进程。对其他策略，仅当同账户、同合约、同持仓方向的实际可平容量因该 UNKNOWN 无法证明时暂拒对应平仓；容量可以证明时该项不阻断，其他方向/合约亦不因本项一概阻断，仍须满足授权、会话、资金及所选 Risk 等独立规则。撤单和查询入口保留，断线时不承诺请求已经送达或撤单成功。

选用 Risk 时继续将 UNKNOWN 按最坏情况占用，影响范围缩小不等于释放占用、增加可平容量或解除 Risk 其他独立拒绝；不凭 UNKNOWN 本身把原订单标成拒绝或释放。多个 UNKNOWN 分别绑定原身份及相关栅栏，解决一个仅解除该订单可解除的影响，不全清其他未知或独立阻断。D63-38 的完整同交易日强身份查询未找到的既定解决与通知规则保持不变、不自动重发；该场所结果不单独证明 NOT_SENT 或替代 §4.3 的 Risk 占用释放证明。

**NOT_SENT 的必要证明**：Gateway 在正确账户、owner/session epoch、命令身份和持久日志完整覆盖范围内返回权威终态（如明确拒绝或失效），并提供单调水位/等价证据，证明所有此前可能到达的 reserve/dispatch 已处理或已被有效 fence 永久排除；旧 owner、旧代际和网络中迟到请求之后均不能成功派发。`NOT_FOUND`、无 DISPATCHING 行、本地 timeout 或没有许可号单独都不满足此证明。若 63 暂无上述合同，提回 63 并保持 UNKNOWN/占用；不得把缺口当做 NOT_SENT。64.01 与 63 冻结证据格式、保留期、查询权限和原子边界，64.09 验证。

**与 D63-38 的区别**：上述规则处理 Gateway 命令日志缺失及在途 reserve/dispatch 是否还能迟到；它不修改用户已决定的场所订单恢复规则。对完整、同交易日、强身份的场所委托查询查不到原身份，按 63 计划 INV63-13 和 D63-38 标 `not_found_at_venue`、通知所属策略并解除对应阻断，不自动重发；不完整查询或旧交易日保持 UNKNOWN。该场所查询结果不单独证明请求从未发送，也不能替代命令日志与迟到请求的 fence；64.01 明确两种证据如何各自作用于 risk 占用，64.09 覆盖两者交叉场景，不自行更改 D63-38。

### 4.4 选中而不可用（S-05）

- “不可用”：risk 服务未启动或不可达、政策未绑定（`bind_policy`）、关键存储不可写或调用超过截止时间。单一“降级”标签不足以判断服务整体不可用；观察流缺口按受影响范围、事实和控制标记 UNVERIFIED，映射与有限原因由 64.01 冻结，不能单凭标签推断所有平仓均通过或均被拒。
- D64-02 已由用户确认：Risk 整体不可用时 SDK 拒绝新的 OPEN 与 CLOSE，有限错误码待冻结；在途结果不明保持 UNKNOWN、原身份及占用。撤单仍经 Gateway 发起，是否送达按连接和权限结果报告；结算确认由 Gateway 处理，不回退为直接下单。
- 由策略配置 `gateway.risk`（§6.1）决定本策略的 PLACE 是否经 risk；配置为经 risk 时，risk 不可用即本策略不能下单。Gateway 不知道、也不检查这一配置（U64-10）。

### 4.5 部署与调用路径（与 63 计划 §3.18、65 计划 §3.1 一致）

risk 只在开启 Gateway 时可用（U64-5）；派发点始终是 Gateway 交易 owner。

| 部署 | PLACE 路径 | risk 的调用方 | 说明 |
| --- | --- | --- | --- |
| Gateway + risk | SDK → risk 服务 → Gateway | 策略进程内的 bt_api_py（`risk.order.*`） | 撤单与读取直达 Gateway |
| Gateway + execution 服务 + risk（迭代 65） | 未命中执行路由：同上；命中：母单交给 execution（入口见 65 D65-01），execution → `risk.parent.reserve`；子单 execution → risk 服务 → Gateway | bt_api_py（直通订单）；execution 服务（母单与子单） | risk 侧合同在 64.10；execution 接入在迭代 65 |
| Gateway（未开 risk） | SDK → Gateway；execution 子单 execution → Gateway | — | 没有本迭代的任何控制；自成交保护缺失属已知功能缺失（U64-11） |

只有一种形态（独立服务，U64-9），不再需要“进程内库与服务两种形态的一致性”；64.11 改为测量服务形态的时延、吞吐与故障行为。

## 5. 现有问题的修复

### 5.1 账户级 dispatch latch（S-06）

- 现状见 §1.2 第 2 项。原样用于共享账户时，任一策略一笔 claim 未经日志权威解决，全账户都不能开仓，重现 63 计划 §1.4 第 3 项的写者权威串行问题。
- **D63-04 / Q28 已确认的 Gateway UNKNOWN 影响范围**见 §4.3：所属策略该合约全部新订单阻断，其他策略同账户同合约同持仓方向的平仓仅在实际可平容量因该 UNKNOWN 不可证明时暂拒。无论是否选 Risk 均适用；不因范围缩小释放 Risk 最坏占用。D64-05 的 Risk 本地 latch/兼容模式、符合 §4.3 的 Gateway typed 结果如何供 `settle` 处理及账本迁移仍待冻结，不能将这些细节视为已由 Q28 选择。
- 新增测试（旧代码须失败）：A 的 rb2701 平多订单 UNKNOWN 时，A 在该合约新 OPEN、CLOSE、后续子单及通过新内部转移提交执行的份额均被 Gateway 栅栏阻断；同账户 B 在该合约平多如容量因 A UNKNOWN 不可证明则暂拒，可证明时本栅栏不拒；B 平空或其他合约不因本项一概阻断，仍受其他门槛约束。检查撤单和查询可发起但断线不承诺送达、不撤既有单、不停进程；两个 UNKNOWN 先解决一个时另一项仍生效，Risk 未决占用不释放。兼容模式的行为和迁移须符合已确认 D63-04，不以旧账户级阻断替代新合同。
- 额度：若 64.01 确认 §1.2 第 3 项的累计计数，新合同的额度改为按交易日窗口与“当前持仓 + 在途”计算（R-03），旧额度只留在兼容模式。

## 6. 配置、审计与可观测性

### 6.1 配置位置与路径

- **前提（U64-5）**：risk 只在 Gateway 开启时有效。非 Gateway 的策略配置出现 risk 设置时以有限码拒绝启动（§5.3），不忽略、不降级为“没有 risk”。
- **risk 服务目录**（运营维护，与 63 D63-08 a 的账户级 Gateway 文件夹并列）：服务配置（Gateway 连接文件、risk 服务的客户端密钥、存储目录、监听地址）与政策文件 `risk_policy.yaml`。Gateway 的账户配置不配置 risk（Gateway 不调用 risk，U64-10），只登记 risk 服务的代理 principal、账户观察 principal 与控制端口权限（63 计划 §3.5、63.13）。
- **策略目录 `config.yaml`**（`access: gateway` 时）写 `gateway.risk`：`none`，或 risk 服务的连接文件（经 risk 下单）。是否必须显式写出见 D64-01。可另写更严的本策略限额，随会话登记交给 risk 服务，由 risk 校验“只能收紧”（64.01 冻结是否在本迭代支持）；策略进程不加载政策文件。
- 路径：相对路径相对于该配置文件所在目录；支持 `~` 与环境变量展开；用 `pathlib` 处理，Windows、macOS、Linux 一致；存储目录必须在本机文件系统（SQLite 锁的限制同 `gw: quota_admission.py:1-7`，不支持网络文件系统）；POSIX 下目录 0700、文件 0600；Windows ACL 尽力而为（未验证，UNKNOWN）。
- 配置不含凭据和原始账号；账户只用 provider 的哈希引用。

### 6.3 校验

- 未知键拒绝；数值为有限正 Decimal；启用的控制缺少阈值是配置错误，不等于“关闭”。
- 策略限额 ≤ 账户限额（只能收紧）；策略 UUID 必须是已登记的写入主体。
- 政策指纹绑定到 risk 账本（沿用 `bind_policy`）；改政策需新版本；运行中变更按 D64-12（建议本迭代只在 risk 服务重启时生效）。
- Gateway 未开启而出现 risk 配置：拒绝启动（U64-5，§5.3）。
- risk 服务启动时核对：Gateway 已为它登记代理、观察、行情与控制端口权限（63.13、63.12），缺任何一项即拒绝启动，不降级。
- 提供不连账户的离线校验入口，供运营开盘前检查。

### 6.4 审计

- 每次 check、reserve、claim、release、settle、拒绝、越限、急停命令各记一条：时间、主体、合约、效果、政策版本、命中的控制与有限码、输入摘要（不含账号与凭据）、耗时。
- 追加写入 risk 存储，不改写；按交易日导出计数报表（JSON/CSV）供运营按期货公司要求报告（S-12），不是监管报送。

### 6.5 可观测性

- `status`：可用性、政策版本、各范围的越限锁存与本地拒绝锁存、计数与阈值利用率、参考价过期次数、claim 延迟分位数；不输出完整路径与账号。
- 指标经 SDK 日志与 monitor 接口导出（可选）；monitor 只观察（U64-13），缺失不影响 risk 判定（63 分析 P4）。运营声明 `monitor_required` 时，monitor 存活丢失后的 STOP_NEW 由 Gateway 自己判定并执行（U64-8），risk 不参与该判定。
- `status` 另报告：观察流的游标与延迟、经观察流发现的绕过 risk 的订单数（INV64-10）。
- BT `get_direct_reconcile_report()`（Gateway 分支）增加 `risk` 摘要：本策略是否配置为经 risk、risk 服务是否可用、本策略最近的拒绝码计数。

### 6.6 独立页面与服务 API（D63-47）

共同技术方案见[跨迭代合同与决策](../迭代63-Gateway统一转发与多策略共享会话/跨迭代合同与决策.md) §2.13.1：Vue 3＋TypeScript＋Vite、Vue Router、Pinia、Element Plus、Axios，图表按需 ECharts；可选 FastAPI Web 适配复用既有服务操作，不替换服务间传输。页面组件、API 客户端、宿主适配与独立壳分离，预构建静态资源可选交付；未来 AFI 显式集成，本期不改 AFI。认证/授权和命令重试遵循共同合同，不能照搬 AFI 通用 Axios 重试。Runtime 也提供独立前端，但首期仍只监督策略。

- 风控服务业务状态与可独立开启/关闭的页面解耦；页面关闭、异常或无客户端时，服务及其调用合同继续按自身状态运行。页面不可用不把已选 risk 改为直达 Gateway，也不以页面在线证明 risk 健康或账户权威。
- 页面使用的版本化服务 API 独立于页面定义，并可供未来 `ai-for-investor` 调用；服务、页面均不以该系统存在为运行前提，本迭代不实现或声称已经实现其集成。API 的身份、账户/策略范围、结果版本及错误、审计和安全边界在 64.01/02 与相关组件共同冻结；不通过页面直写 risk 账本或由页面维护权威状态。
- 用户已决定 Risk 页面可查看规则、额度与风险状态，并通过 Risk 自身受权管理 API 调整规则；鉴权、业务校验、执行和审计均由服务端负责，页面不扩大调用者 grant、不持有通用运营密钥，不绕过 Gateway 放行或解除其他原因。具体角色、操作枚举、schema 和规则生效方式（含 D64-12）仍待冻结；本决定不预设阈值或自动恢复。现有服务内部授权的订单协议不因页面存在而向浏览器开放；Monitor 仍是观察服务且不成为控制入口，Runtime 首期仍只监督策略。技术栈按共同合同 §2.13.1 采用，不宣称已有实现。
