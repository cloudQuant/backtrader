## 0. 结论

- 计划对 `bt_api_risk` 现状盘点扎实，已经查出：遗留 `RiskManager` 默认放行（fail-open）、账户级 dispatch latch、内置缺省值、README 描述与源码不符。控制目录与行业做法基本对得上：单笔数量/名义上限、价格带、持仓与可平、报撤单计数、自成交、重复单、亏损、保证金、越限联动急停，正好对应 VeighNa RiskManager、NautilusTrader RiskEngine 和 FIA 列出的交易前检查。
- 本轮共 10 条：P1 2 条，P2 5 条，P3 3 条。主要问题是：
  - “确定未发送”（NOT_SENT）的证明依赖一份尚未冻结的合同，导致多处只能长期 UNKNOWN（RV64-01）；
  - 选了 risk 的策略仍可能因配置漂移绕过 risk，建议 D63-37 改选 b（RV64-02）；
  - 是改造 1.46 万行的 `DurableRiskGate`，还是新建小核心，没有作为决定提出（RV64-03）；
  - 缺少期货特有的“交易所规则类”限额（RV64-04）。

## 2. 发现与建议

### RV64-01（P1）NOT_SENT 证明依赖未冻结的“覆盖水位 + fence”合同，§4.3 多行只能长期 UNKNOWN

- **定位**：§4.3 表第 1～3 行、“risk 不可用（SDK 已写 PREPARED 之后）”行、INV64-08；设计 §6；63 设计 §4.1。
- **问题**：最典型的情形是 risk 已提交本地预留，但 `direct.reserve` 是否到达 Gateway 不明，Gateway 上没有任何记录。按现设计，只有 Gateway 给出“完整覆盖水位 + 迟到请求 fence”的证明才能释放，否则一直 UNKNOWN 并保留占用；而 63 设计 §4.1 对这份合同只是“提案”。结果是：risk 崩溃一次，某策略的某合约就可能长期被占用或阻断，直到人工处理。
- **建议**：采用 RVX-01 的 `abandon(request_key)` 加 owner epoch。risk 重启后对每个未决的 `request_key` 调用 abandon：
  - 得到 NOT_SENT（含墓碑），释放占用；
  - 得到 DISPATCHING、SENT 或 UNKNOWN，按原身份跟踪。
  §4.3 表按此重写。“与 D63-38 的区别”一段保留：场所查不到，不等于命令未发送。
- **若选 RVX-01 的 B（单阶段）**：
  - `risk.order.reserve` 与 `risk.order.dispatch` 合并为 `risk.order.place`：L1～L3 与 claim 在一个事务里，提交后转发 `direct.place`；
  - §4.2 的 9 步缩为约 6 步；
  - `risk.order.release` 改为对 Gateway 调用 abandon。
- **影响**：64.01、64.02、64.09，须与 63.01 同步。（问题 QX-01）

### RV64-02（P1）选了 risk 的策略，建议缺省只把 SUBMIT 授给 risk 代理 principal（D63-37 改选 b）

- **定位**：INV64-10（绕过 risk 是已接受的性质）；§4.2“竞态与绕过”；D64-01；63 的 D63-37（计划建议 a）。
- **问题**：Gateway 不检查风控批准是用户已作的决定（D63-17、D64-17），本条不改它。但如果策略 principal 自己也持有 SUBMIT，任何配置漂移（`config.yaml` 写错、SDK 版本不一致等）都会让该策略的订单绕过 R-01、R-02、R-04、R-05，risk 只能事后计数。SEC 15c3-5 (d) 要求最后一道控制由负责方直接且排他地控制，FIA 也强调交易前控制的独立性（63 控制面分析 [R16][R18]）。D63-37 的 b 用的是 Gateway 的**普通授权**，不是“检查批准”，与 D63-17 不冲突。
- **方案**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| a | 计划建议：策略 principal 照常持有 SUBMIT | 与 D63-17 的字面最接近 | 配错即绕过；R-04、R-05 只能尽力而为 |
| **b** | 策略配置了 `gateway.risk: <连接>` 时，运营工具给该策略生成的 Gateway grant 不含 SUBMIT（只含 READ、CANCEL），SUBMIT 只授 risk 代理 principal；risk 的启动核对（§6.3 末条）扩展为“所覆盖的策略在 Gateway 上没有直接 SUBMIT” | 不改变 Gateway 的职责；配错会被授权挡住，而不是悄悄绕过 | 运营要维护两套 grant；risk 不可用时该策略无法下单（这与 D64-02 a 的行为本来一致） |
| c | 每个策略自选 a 或 b | 灵活 | 多一个配置面 |

- **建议**：以 b 为缺省，允许通过 c 显式放开个别策略。（问题 Q64-01）

### RV64-03（P2）新建服务核心还是改造 `DurableRiskGate`：计划和设计倾向不同，建议显式决定

- **定位**：计划 64.03 在 `core/admission.py` 上改 latch、扩展 `RiskIntent`、加交易日窗口、改名并迁移 schema；设计 §5 建议新的模块布局（`service/auth.py`、`orders.py`、`observations.py`、`control.py`、`store/ledger.py`、`policy/`）；§9.1 已登记“`admission.py` 体量与回归”风险。
- **问题**：`core/admission.py` 有 14 586 行，包含大量证明类型，同时服务迭代 60 的托管路径。在它上面扩展新服务的语义（方向、价格、自成交、范围占用、交易日窗口），会与托管路径的行为纠缠在一起，回归面很大。
- **方案**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| a | 改造（计划 64.03） | 复用现有的 SQLite 事务和 fail-closed 骨架 | 回归面大；兼容模式与新语义交织 |
| **b** | 新建小核心：请求状态机 + 版本化账本 + 纯函数政策，只复用 `instrument.py` 的名义值计算等纯函数；`DurableRiskGate` 冻结，只服务迭代 60 托管路径，再按 D65-11、D63-35 的处置逐步退役 | 新语义边界清楚，便于做 RVX-05 的状态机测试；不扰动托管路径 | 部分逻辑要重写；新旧两套会并存一段时间 |
| c | 混合：新的服务核心，复用 `DurableRiskGate` 的事务和 claim 原语 | 折中 | 依赖关系复杂 |

- **建议**：b，作为新增候选 D64-25。（问题 Q64-02）

### RV64-04（P2）缺少期货特有的“交易所规则类”限额：限仓、日内开仓限额、交割月持仓规定

- **定位**：§3.2 控制清单 R-01～R-10；§1.5 职责规范一行（价位、数量步长、交易所单笔最大量、涨跌停等归 provider）。
- **问题**：
  - 中国期货交易所对客户有持仓限额（一般月份宽，临近交割月逐步收紧），部分合约有日内开仓交易量限额，自然人客户通常不能持仓进入交割月。具体规定以交易所规则为准；本轮检索只拿到第三方资料，没有取得交易所原文。
  - 违反这些规定，会被交易所处理，或被期货公司强行平仓，换月的 CTA 策略尤其容易碰到。
  - 现有 R-03 是运营自填的仓位上限，不读交易所规则。
- **建议**：新增可选控制 R-11“交易所规则类限额”。
  - 只消费 provider 声明的中立事实：按合约、客户类型和月份阶段给出的限仓，日内开仓限额，交割月禁止持仓的日期；
  - 缺省关闭；事实缺失时按配置处理（缺省 WARN）；临近交割月前 N 个交易日发 WARN；
  - 这些事实要由 bt_api_ctp 声明，64.01 先核实能否取得。来源可能是需要人工维护的规则表，与迭代 67 的“数据文件化”做法类似。
- **方案**：a 新增 R-11（推荐，缺省关闭）；b 只做“临近交割月提醒”（WARN）；c 不做，列入非目标并在 README 提示。（问题 Q64-03）

### RV64-05（P2）R-04/R-05 的参考阈值，以及“实际控制关系账户”的合并口径

- **定位**：R-04（阈值由运营填写，无缺省）、R-05、D64-08、§9.2 第 1、3 项。
- **事实**：第三方整理的交易所标准为单日单合约自成交 ≥ 5 次、撤单 ≥ 500 次（股指 400 次）、大额撤单（单笔 ≥ 300 手）≥ 50 次，实际控制关系账户合并计算 [S18][S19]。
- **问题**：
  1. 运营填阈值时没有参考，容易填偏；
  2. 每账户一个 risk 服务（D64-15 a）无法合并多个账户的计数。如果用户有多个实际控制关系账户，可能各账户都低于阈值，合并后却超限。
- **建议**：
  1. 在政策文件说明和 README 中列出“交易所参考值（以原文为准）”；校验时若运营阈值高于参考值，给出 WARN。
  2. 合并口径按下表选择：

| 方案 | 做法 | 优缺点 |
| --- | --- | --- |
| a | 只按单账户计数，文档写明缺口 | 简单；多账户时可能超限 |
| b | 以后另设跨账户计数聚合（可先在 monitor 侧只做观察告警） | 覆盖合并口径；需要新组件 |
| c | 有多个账户时，把阈值按账户静态拆分 | 不用新组件；保守，浪费额度 |

- **建议**：a + c；有多账户需求时再做 b。（问题 Q64-04）

### RV64-06（P2）D64-09 亏损锁存：risk 下达的原因须运营 RESUME，会延续到下一个交易日

- **定位**：R-07；D64-09（建议 a：锁存到运营 RESUME）；63 §3.17“运营、runtime、risk 下达的原因一律须 RESUME”；D64-21。
- **问题**：日内亏损超限后，risk 向 Gateway 发 STOP_NEW。到了下一个交易日，亏损计数已按交易日清零，但 Gateway 上的原因还在，必须有人 RESUME 才能开仓。这可能正是用户想要的人工复核，也可能变成每天早上的固定手工操作。
- **方案**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| a | 计划建议：锁存到运营 RESUME | 强制人工复核 | 每次触发都要人工处理 |
| b | 亏损类原因带“新交易日 `day_ready` 时自动解除”的属性，作为 D63-33 自动解除类的一种 | 与“按交易日计”的语义一致，不需人工 | 需要 63.12 支持按交易日解除；与“risk 原因须 RESUME”的现行规则不同，需用户改决定 |
| c | risk 只在本地锁存，不发 Gateway 原因；新交易日自动清零；超限时另发 monitor 告警 | 不占用 Gateway 原因 | 只能拦住经过 risk 的订单（本来也是如此） |

- **建议**：由用户决定。重视人工复核选 a，重视无人值守选 b。（问题 Q64-05）

### RV64-07（P2）观察流的“共同切点”：采用 63 的流内快照，就能覆盖 Gateway 自有的事实

- **定位**：设计 §5“冷启动先获得受信账户快照及与观察流的同一切点”；§4.2“竞态与绕过”；63 §3.8。
- **建议**：见 RV63-07。risk 用到的策略暴露、在途和归属持仓都来自 Gateway 账本，而 Gateway 是唯一写者。如果 63 采用“流内快照 + 序号增量”，冷启动和重连时就不必再证明“同一切点”；只有账户级的场所事实（CTP 持仓和资金）仍按 UNVERIFIED/NOT_COMPARABLE 处理。这能明显缩小 64.09 的测试面。

### RV64-08（P3）政策文件需要“provider 哈希账户引用”，但没有获取途径

- **定位**：§6.2 中的 `account_ref: <provider 给出的哈希账户引用>`。
- **建议**：由 Gateway 状态或运营 CLI 提供一个只输出该哈希、不输出原始账号的命令；离线校验入口（§6.3 末条）核对它与 Gateway 是否一致。

### RV64-09（P3）一致性与溯源

1. 第 9 行引用“INV63-01～07”，应为“INV63-01～14”（RVX-02）。
2. §1.1a 写“用户本轮明确允许重构相关 SDK 子库”，需求原文中没有这条记录，建议补入（RVX-07）。
3. 设计 §10 第 2 条已经指出：计划中有些表格把 D64-02、05、08、09、11 的建议写成了确定行为或验收项。建议在 §3.2、§9.3 的相应行标注“（依 D64-xx）”，避免实施时当成已决定。

### RV64-10（P3）D64-04 的参考价：补上“最新价过期时的回退规则”

- **建议**写进 R-02 的语义列：
  - 参考价按 D64-04 a 取最新价；
  - 最新价超过 `max_reference_age` 时，若双边盘口存在且未过期，回退到中间价；否则 OPEN 拒绝（`risk_price_reference_stale`），CLOSE 按 `apply_to_close` 处理；
  - 涨跌停时只有一侧盘口（D62-38 已把它定义为有效报价），价格带按停板价截断。
