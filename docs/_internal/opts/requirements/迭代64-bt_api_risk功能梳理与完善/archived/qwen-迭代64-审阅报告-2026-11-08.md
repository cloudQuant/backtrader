## 3. 发现与建议

### QW64-01（P1）R-08a 资金守恒仍缺可执行公式、两层占用次序与多步手算向量

- **定位**：计划 §3.2 R-08a（204 行）、§3.1a（180–182 行）、§3.3（220–222 行）、§9.3 R-08 行（641 行）；设计 §4.1（108–114 行）。
- **问题**：复核清单 R1 的"原则 + 单步示例"已写入（100/70/70、水位去重、未知不填零），但三处仍不可实施：(a) "快照覆盖本地占用"的判定没有公式——`能证明覆盖的事件/冻结水位` 是什么字段、与本地占用记录如何比较，未写；(b) 账户层与策略预算层两段检查在同一事务内的次序与失败语义未写（策略预算足够而账户不足时，已做的策略层扣减是否回滚）；(c) 母单/转移层与 R-08a 的关系未定义——§3.3 写 `risk.parent.reserve` 整笔预留"R-03、R-07 与策略额度"，未说 R-08a deny 时母单是否整笔预留账户保证金、跨日母单（D65-04）资金占用是否随日切快照更新释放，`risk.transfer.reserve` 的"适用预算"（设计 §7）同样含糊。
- **建议**（公式与数值均为示例，供 64.01 冻结时具体化，不是阈值决定）：
  - 覆盖判定：每笔本地资金占用记录持久 `hold_seq`（Risk 账本单调序号）与来源事件引用；余额快照持久 `covered_seq`（该快照已反映到的 Risk 占用/柜台冻结事件水位）。判定式为：仅当 `hold.covered_by` 能绑定到快照声明的覆盖范围（`hold.hold_seq ≤ snapshot.covered_seq` 且同账户、同币种、同交易日）才视为已覆盖。
  - 有效可用资金：`effective_available = snapshot.available − Σ{hold.amount | hold 未被 snapshot 覆盖 ∧ hold 状态 ∈ {RESERVED, CLAIMED, UNKNOWN}}`；准入判定：`effective_available ≥ worst_margin(order) + worst_fees(order)`，否则 DENY（有限码），UNKNOWN 占用按最坏计。
  - 两层次序：同一 `BEGIN IMMEDIATE` 事务内先账户层后策略预算层（策略层按 D63-44 公式的 `strategy_cash`），任一层不足即整笔 DENY，事务回滚不留部分占用。
  - 母单层：明确选择"母单不预留账户保证金，账户层资金占用只在子单 dispatch（实际下场）时按子单最坏值预留"或"母单整笔预留"之一并写入 §3.3；两种选择给出跨日行为（日切快照更新时母单层占用如何修订）。
  - 三步手算向量（示例数值）：① 快照 available=100、covered_seq=10；单 A 需 70：无未覆盖占用，100≥70，预留成功（hold_seq=11）；② 单 B 需 70：effective=100−70=30<70，DENY；③ 新快照 available=30、covered_seq=11（柜台已含 A 冻结），单 C 需 30：effective=30−0=30，通过；④ A 被证明未派发（§4.3 fence）释放 hold 11，或 A 成交 3 手后未成交部分按终态证明释放；每步断言 `Σ未覆盖占用 + effective_available = snapshot.available`。
- **理由**：复核清单 §8 要求"各合同先有可手算样例和状态转换，再做实现"；R1 剩余项自认"可执行 schema/公式"未交付。没有比较规则，64.03–04 的实现者只能各自发明水位语义，deny 模式的资金事实错误会直接影响真实账户。
- **验收**：§9.3 R-08 行与设计 §4.1 出现字段级判定式与至少一条含"新快照到达 + 旧占用释放 + 部分成交"的多步向量；UNIT 断言守恒式在每一步、重复事件与重启恢复后成立。

### QW64-02（P1）母子单/转移的数量占用缺完整桶集合、守恒等式与裁定层级，R2/R3 验收不可机械判定

- **定位**：计划 §3.3（220–223 行）、§3.3a（238–247 行）、§9.3"独立子单与反向转移"行（644 行）；设计 §6.1（153–155 行）、§7（157–188 行）；对照合同 §2.6（D65-32）。
- **问题**：(a) permit 只写了 RESERVED→CLAIMED 与 RESERVED→DENIED/RELEASING 两分支互斥，CLAIMED 之后（转发、SENT、UNKNOWN、结算终态、到期）与 RELEASING 的终态没有枚举成完整状态集合与转换表；(b) 母单额度只说"已成交、活动、未用及 UNKNOWN 的账目必须分列"，没有桶定义与守恒等式，`risk.transfer` 引入的"待转移占用"桶与子单划拨桶的关系没有等式约束，"不双占、不提前释放"因此无法机械断言；(c) 竞争裁定层级两处表述并存——计划 §3.3a 引 D65-32 写"由 Gateway 权威预留原子裁定"，同节又写 Risk"同一事务将各参与母单的对应未用数量…划入待转移占用…只有一个转换可成功"；对经 Risk 的请求，Risk 单 writer 事务与 Gateway 版本比较各裁定什么、两层结论不一致时以谁为准并如何回滚，未写。
- **建议**：
  - 桶守恒等式（示例）：`parent_total = filled_confirmed + at_venue_active + dispatched_unknown + transfer_pending + child_reserved_unused + unused_releasable`，各桶 ≥ 0，任何事件只在同事务内做桶间原子搬移；UNKNOWN 只能进 `dispatched_unknown`/`transfer_pending`，释放必须绑定 §4.3 证明。

  - 裁定层级一句话写清：经 Risk 的请求由 Risk 单 writer 事务先行互斥（本地权威），Gateway 的版本比较/权威预留对绕过者与并发提交做最终裁定（账户权威）；Gateway 拒绝时 Risk 按绑定结果回滚对应桶并留审计。
  - 手算向量（示例）：母单 10；子单 3 reserve→claim→dispatch→成交 2→撤 1（fence 证明）；转移 reserve 4→UNKNOWN；断言每步等式成立且 `transfer_pending` 与 `child_reserved_unused` 不重叠同一份额；并加一条"转移与子单并发争用同一未用份额，只有一个成功"。
  - 测试手段：把上述等式作为属性测试不变量写入 §9.3（RVX-05 a 的状态机测试，工具由开发定稿）。
- **理由**：复核清单 R2/R3 的剩余项即"可执行 schema/公式"；65 侧 INV65-03 已给出母单信封不等式（65 计划 147 行），64 作为占用账本 owner 反而没有对应等式，两边无法互相校验。
- **验收**：设计 §6.1/§7 出现完整状态集合、转换表与守恒等式；§9.3 对应行的断言可直接翻译成属性测试不变量。
