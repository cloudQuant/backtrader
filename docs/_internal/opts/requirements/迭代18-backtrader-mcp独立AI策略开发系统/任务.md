## 0. 立项结论

本迭代建设一个可单独安装和运行的 `backtrader-mcp`。用户在已有 Backtrader
运行时上只安装 MCP 包、不安装任何 Backtrader Skills 或 `backtrader-agent` 时，
连接 MCP 的 AI 仍必须通过 resources、prompts 和 typed tools 完成完整闭环：

```text
策略需求规格化
  -> 检查、登记并加载本地数据
  -> 语料目录检索
  -> 选择当前 fork 模板和参考实现
  -> 生成两种策略产物
  -> 创建/更新受限 draft
  -> 静态和安全校验
  -> hash token 绑定
  -> 经批准受控回测/测试
  -> 诊断修复
  -> 比较、报告和产物读取
```

MCP Server 不内置 LLM，也不负责替代宿主 AI 写代码。宿主 AI 通过 MCP prompt 和
resource 获取规范与参考，通过 draft 工具提交生成的受限文件内容。MCP 自己必须拥有
语料索引、模板、校验、受控 runner、测试、结果和报告服务，不能把这些功能转交给
`backtrader-skills` 或 `backtrader-agent`。

### 1.2 参考 MCP 原型不可直接使用

参考项目当前实现存在以下根本问题：

- 工具接收裸 `strategy_code` 并在进程内 `exec()`；
- 动态选择 CCXT 交易所，没有严格能力和路径边界；
- 接收但没有可靠使用 `to_date`；
- 调用当前 fork 不存在的 `Cerebro.addnotifycallback()` 和
  `broker.get_value_history()`；
- 没有自动化测试；
- 将完整 traceback 返回客户端；
- README 中永续、杠杆和资金费等声明没有完整运行模型支撑。

本迭代是重新设计独立 MCP 产品，不是在该单文件原型上打补丁。

### 1.3 语料使用边界

- 唯一 canonical ID 是 `category/完整策略目录名`。
- 三件套主策略必须从 `run.py` import 解析，不能按 glob 猜测。
- 1,032 个映射只能标记 lineage；当前实现可能已经维护分叉。
- 当前 fork 的直接 `bt.Strategy` 由 `Strategy.__new__/Strategy.__init__` 先建立参数、
  data aliases 和 clock，再调用用户 `__init__`；不调用 `super().__init__()` 是合法
  主流写法。只有自定义父策略或 cooperative mixin 需要按 MRO 验证父类初始化。
- 检索必须包含必要的 preprocessing、feed lines、Strategy、runner 和 test 片段。
- 历史结果只能作为参考，不能作为新策略 fresh acceptance。

## 3. 运行时与打包边界

当前 Backtrader 支持 Python 3.8–3.13。2026-07-30 通过官方 GitHub Releases API
与 PyPI JSON 再次核验，MCP Python SDK v2.0.0 已于 2026-07-28 正式发布，要求
Python 3.10+。但其 release notes 明确说明 Tasks extension 未随 v2.0.0 发布，因此
协议稳定不等于已有长任务管理能力。MCP 必须独立分发：

实时证据：[MCP Python SDK v2.0.0 release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.0.0)、
[PyPI project metadata](https://pypi.org/project/mcp/2.0.0/)。

```text
backtrader-mcp/
  pyproject.toml
  README.md
  LICENSE
  NOTICE
  src/backtrader_mcp/
  resources/
  tests/
```

要求：

- `requires-python = ">=3.10"` 只存在于 MCP distribution；
- 首版使用 `mcp>=2.0,<2.1` 兼容范围并锁定验收版本；升级 minor 前先跑协议/宿主矩阵；
- 不依赖未发布的 Tasks extension；P0 自带持久 run registry、status 和 cancel tools；
- M0 必须核验官方 release、protocol 和目标 client，不能仅根据版本号假定兼容；
- Backtrader 核心不增加强制 MCP 依赖；
- MCP 通过明确的本地包/源码配置使用当前 Backtrader；
- 启动时 `doctor` 输出实际 `backtrader.__file__`、version、commit 和能力；
- 发布包必须包含自己的 schema、catalog snapshot、精选参考片段、模板和服务，
  不依赖仓库 Skills 文件或 sibling corpus checkout。

首版 transport：

```text
host AI/client <-> stdio MCP server <-> product-local services
                                      <-> local Backtrader
                                      <-> fixed local fixtures
                                      <-> isolated draft/artifact roots
```

### 3.1 四类宿主安装

`README.md` 与安装 smoke 必须覆盖：

- Claude Code：项目/用户 scope 的 stdio MCP 配置与 `claude mcp add`；
- Codex：`.codex/config.toml` 或 `codex mcp add`；
- OpenCode：项目 `opencode.json` 的 local MCP server 配置；
- OpenClaw：workspace MCP 配置或 `openclaw mcp add`。

四类 adapter 都只启动同一个 `backtrader-mcp` stdio entrypoint，显式传入受控
workspace/data/artifact roots；不得为某个宿主维护另一套业务实现。每个 adapter 至少
完成 initialize、tools/list、resources/list、prompts/list 和一次 typed tool smoke。

## 6. 版本化契约

MCP 包内 vendoring 并独立实现七份 Schema：

- `StrategySpec v1`
- `DatasetManifest v1`
- `CorpusManifest v1`
- `StrategyArtifactManifest v1`
- `ValidationReport v1`，内含 `Diagnostic`
- `RunManifest v1`
- `RunResult v1`

字段要求与迭代17保持格式兼容，但这是互操作协议，不是运行依赖。MCP 的独立发布
验收不要求迭代17已经完成。

public import/export 的核心字段、`ds_<64hex>` dataset ID、七类 archetype 枚举和
canonical-json-v1 必须与迭代17第 6.8 节逐字兼容；MCP 私有 CAS/job/change/token 状态
只能放入版本化 `extensions`。仓库级 parity fixture 可比较三份 vendored schema 与
golden artifact，但 MCP wheel 的自身测试不得 import 或读取 sibling 实现。

### 6.1 `StrategySpec`

包含策略 archetype、目标 profile、feeds/timeframes/lines、指标/特征、类型化参数、
交易/退出/风险规则、订单/Sizer/commission、Analyzer、依赖、验证要求，以及已登记
`dataset_id` 引用；不得直接携带任意本地路径或 Python loader。

### 6.2 `DatasetManifest v1`

把“用户请求的数据配置”和“实际解析后的数据事实”分开。Manifest 至少包含：

`DataSpec` 定义在
`dataset-manifest-v1.schema.json#/$defs/DataSpec`，是 inspect/register typed input，
不是第八份公共 Schema。它继承 DatasetManifest v1 版本，冻结 `spec_hash` 与正反
fixture；DatasetManifest 再加入解析后的数据事实、质量结果和 provenance。

- `dataset_id`、schema/spec/semantic-manifest hash、产品/Backtrader/parser
  provenance；semantic hash 排除产品名/版本、创建时间和本机显示路径等非数据语义字段；
- 每个 feed 的唯一名称、symbol、execution/signal/benchmark/hedge/cash_proxy 角色与
  tradable 标记；
- `source.kind`、opaque root ID、根内相对路径、format/media type、size 和 SHA-256；
- parser/feed class allowlist 以及冻结的列、datetime、separator、null、dtype 参数；
- datetime/OHLCV/openinterest/custom lines 映射；
- timeframe、compression、from/to、timezone、session、calendar、bar-open/close 语义；
- 按顺序记录的 date clip、sort、feature、resample/replay 等 transform 及实现 hash；
- 行数、首末时间、normalized data hash、重复/空值/非有限值/OHLC/频率检查；
- 多 feed master、角色、`intersection | left | explicit_asof` 对齐和最低重叠门禁；
- validation status、稳定 diagnostics 和 policy version。

首版支持 `generic_csv`、`backtrader_csv`、已下载 `yahoo_csv`、`mt5_csv`、显式
`PandasData` 和产品模板拥有的 custom-lines DataFrame。P0 不接受 pickle、任意
Python feed/transform、JSONL/NPZ/tick 通用加载、数据库、网络下载或实时流。
这里的 Pandas 支持是 runner 从 immutable canonical CSV/CAS 构造受控 DataFrame/
`PandasData`，不是跨进程接收任意内存对象；宿主 DataFrame 必须先变为有 hash 和配额
的 JSON records/columns 或登记 root 内 CSV/Arrow，再物化入 CAS。

### 6.3 Catalog

每条记录包含 canonical path key、别名、runner import 主策略、source/test 双路径、
revision/hash、配置、feeds、特征、指标、订单、风险、依赖、结果 shape、映射/质量状态。

### 6.4 Validation 和 Run

诊断必须稳定、结构化并脱敏。Run 结果必须记录源码/数据/配置/环境 hash、实际
Backtrader import、命令、超时、指标、比较、产物和审批。

### 6.5 `ComparisonProfile v1`

该 profile 是七份契约引用的版本化策略文件，不新增第八种产物 Schema。默认规则：

- 整数计数、状态、布尔、枚举、ID 和 hash 精确相等；
- 浮点指标使用 `math.isclose(rel_tol=1e-7, abs_tol=1e-9)`；
- 专属字段容差按 metric key 配置，禁止用全局大容差掩盖差异；
- schema 声明 nullable 的字段只允许 `null == null`；
- NaN、Infinity 或缺失必需字段直接失败；
- runonce/runnext 比较计数、浮点和规范化交易事件；
- master/dev 覆盖必须记录 metric、原/新容差、理由、批准人、时间和 profile hash。

M1 必须冻结 `comparison-profile-v1.json`、正反 fixture 和 structured diagnostics。

### 9.2 Spec 和 Draft

| Tool | 主要输入 | 结构化输出 |
| --- | --- | --- |
| `validate_strategy_spec` | StrategySpec + dataset ID | typed diagnostics、normalized spec |
| `render_strategy_scaffold` | normalized spec、profile、archetype | 模板文件、artifact manifest |
| `create_strategy_draft` | spec、profile、受限文件列表 | draft ID、manifest、preview |
| `update_strategy_draft` | draft ID、expected hashes、patches | 新 manifest、diff、旧 token 失效 |
| `prepare_strategy_changes` | draft ID、validation token、目标根 | pending change ID、路径/diff/覆盖状态和 manifest hash |
| `approve_strategy_changes` | pending change ID、expected manifest hash、可信 approval ID | 一次性 change token |
| `apply_strategy_changes` | pending change ID、change token | applied manifest |

`create/update` 可以接收宿主 AI 生成的文件内容，但只能保存到受限 draft。它们不能
执行代码，也不能接受任意文件名、任意数量或任意大小。

draft 是 MCP 产品私有、可丢弃的存储，不等于用户目标工作区。用户调用
`create/update` 即授权本次受限 draft 写；目标工作区写入必须在 validation token
有效时 prepare，再由一次独立 `approve_strategy_changes` 调用绑定精确 manifest
hash，最后消费一次性 change token。服务端只能强制“两阶段、精确内容、可审计”的
协议，不能声称自己能证明调用方背后一定是人；各宿主配置必须把 approve 调用映射为
显式用户确认。支持 MCP elicitation/MRTR 的宿主记录 accept/decline/cancel 证据；
不支持的宿主必须由产品自带本地 CLI/UI 签发 `approval_id`。模型提交
`approved=true`、复述确认文本或直接调用 approve tool 都不能单独成为可信批准。

### 9.3 Validate、Run、Test 和 Report

| Tool | 主要输入 | 结构化输出 |
| --- | --- | --- |
| `validate_strategy_draft` | draft ID、profile | ValidationReport、validation token |
| `prepare_strategy_run` | draft ID、validation token、固定 run/test profile | pending run ID、命令摘要和 input hash |
| `approve_strategy_run` | pending run ID、expected input hash、可信 approval ID | 一次性 run token |
| `start_strategy_run` | pending run ID、run token、idempotency key | job ID、run ID、status URI |
| `start_strategy_tests` | pending run ID、run token、idempotency key | job ID、test run ID、status URI |
| `get_run_status` | run ID | queued/running/terminal 状态、进度和诊断摘要 |
| `cancel_run` | run ID、expected state version | 取消结果和新状态 |
| `apply_strategy_repair` | draft ID、expected hashes、受限 patches | 新 draft manifest、旧 token 失效 |
| `compare_strategy_runs` | 两个 run ID、固定 profile ID、可选已批准 override ID | 规范化差异 |
| `get_run_result` | run ID、detail | manifest/metrics/diagnostics/resources |
| `render_strategy_report` | run ID、format allowlist | artifact resource link |

运行工具不接收源码、shell、任意 cwd、任意 pytest target、任意数据路径或任意输出路径；
只能引用已登记且 hash 未变化的 `dataset_id`。

P0 不依赖 SDK 的实验性 Tasks extension；长任务由产品内受限 worker、持久 run
registry、`get_run_status` 和 `cancel_run` 管理。未来采用协议 Tasks 必须保持这些
typed 语义和现有客户端兼容。

## 10. Draft、Token 与批准流程

```text
AI 生成受限文件
  -> create/update 产品私有 draft
  -> validate draft
  -> validation_token(source+config+DatasetManifest+env hashes)
  -> prepare exact draft run
  -> 用户通过可信 provider 单独批准执行
  -> durable fixed-runner job
  -> PASS + immutable tested artifact
  -> preview 精确测试过的字节对应的目标工作区变更
  -> 用户通过另一 approval 单独批准 apply
  -> atomic apply + target hash verification
  -> run_id + immutable evidence
```

默认先在产品私有 draft 上运行并验证，再 apply 完全相同的 tested hash。若部署选择先
apply，runner 必须只接受 `applied_artifact_id`，重新读取目标字节并签发新 validation
token；不得 apply 工作区后继续用旧 `draft_id` 代表已应用内容。

规则：

- draft 更新立即吊销全部旧 token；
- 私有 draft 写入与目标工作区 apply 是两个不同权限边界；
- token 有短期有效期、单 draft、单 validation profile；
- runner 启动前重新计算 hash；
- 数据、环境或 Backtrader revision 改变也必须重新验证；
- register 在一次受控读取中校验并写入 product-owned content-addressed immutable
  store；runner 只读 CAS artifact，原始文件 stat/hash 仅保留 provenance，避免
  check-open 间 TOCTOU；
- apply token 与 run token 不通用；
- 失败或取消均保留最小审计记录；
- 并发运行有上限，run ID 和 workspace ID 是不透明值。

## 11. 静态和安全门禁

### 11.1 Candidate 校验

- YAML/schema/扩展 namespace；
- runner import 唯一解析；
- Strategy subclass 与类名；
- 直接 Strategy 与自定义父策略/mixin 各自正确的初始化契约；
- config 参数与策略参数；
- AST/compile；
- import/dependency allowlist；
- 禁止 `exec/eval/compile/__import__/importlib`；
- 禁止 subprocess/shell/socket/任意网络；
- 禁止凭据、绝对路径、目录穿越和软链接逃逸；
- 禁止 live broker/store；
- data fixture 边界和 future-data/look-ahead 规则；
- datetime 单调/重复策略、timezone/session、OHLC 合法性、null/finite、时间范围；
- 多 feed 名称/角色/对齐/最小重叠与 resample/replay 已完成 bar 语义；
- 文件名、数量、单文件大小、总大小和输出配额。

### 11.2 Server/Protocol 校验

- typed input schema 和 output schema；
- deterministic tool/resource/prompt listing；
- 非法 URI、超长输入、未知字段和错误类型；
- tool 超时、取消、并发与速率限制；
- structuredContent 与文本摘要一致；
- 内部异常映射为稳定错误码；
- 绝对路径、环境变量、secret 和 traceback 脱敏；
- 高风险工具向客户端明确展示输入并要求确认；
- 运行产物只通过受控 Resource Link 暴露。
- stdio 协议 stdout 零业务日志，日志只到 stderr；候选 stdout/stderr 单独捕获；
  覆盖 UTF-8 framing、半包、断管、SIGTERM、客户端取消和子进程组清理。

### 11.3 执行边界

- 首版 local `stdio`；
- 固定 child-process runner；
- 使用参数数组，不拼 shell；
- 固定 cwd、清洗环境、固定本地 fixture、静态拒绝已知网络 API；
- 数据 parser/feed/transform 白名单，不执行用户 loader 或动态 callable；
- timeout、stdout/stderr、CPU/内存/文件大小限制；
- 不在 MCP Server 进程内 import/执行候选；
- 不把子进程控制误称为强沙箱或 OS 级断网；
- AI 生成代码仍是不可信输入；P0 只执行本产品辅助生成、验证且用户批准的候选，未知
  第三方代码仅静态校验；AST + child process 不是 OS sandbox，安全声明不得扩大。

## 12. 语料检索和生成

在检索策略前，MCP 必须先完成本地数据接入。数据服务只读已登记 root，路径经
`realpath` 后仍须位于 allowlist 内；输入文件不修改。相同文件、映射、时间范围和
transform 应得到相同 manifest hash。预览只返回受限样本与统计，不把整份行情放入
模型上下文。

DataFrame 物化只接受已批准的产品内 tabular artifact ID，不接受 pickle、任意对象

对齐、多周期 resample/replay、配对两腿、订单 OHLC/session、预计算 custom lines。

## 19. 风险与控制

| 风险 | 控制 |
| --- | --- |
| MCP 退化为薄工具壳 | 独立 catalog/validator/runner/report 和 MCP-only 端到端门禁 |
| 再现原型 raw exec | run tool 不收源码；draft → validate → hash token → run |
| SDK Python 版本污染核心 | 独立 distribution 和独立运行环境 |
| MCP URI 转成任意文件 API | opaque ID、路径归一化、root confinement、symlink 检查 |
| 服务端状态漂移 | 显式 draft/run ID、不可变 manifest、token hash |
| 语料选错主文件 | canonical path key + runner import 解析 |
| 旧模板生命周期不兼容 | 新写 14 份当前 fork 模板 + AST 门禁 |
| 历史收益被误当验收 | fresh master/dev baseline + 人工批准 |
| 子进程安全被夸大 | 文档披露边界，容器列为 P1 |
| MCP 暗中读取 Skills | 无 Skills 打包和文件访问审计 |
| MCP 暗中读取 Agent | 无 Agent 打包和文件访问审计 |
| 数据路径泄漏或数据漂移 | opaque root ID、相对路径、DatasetManifest、双 hash 和 token 失效 |
| 多数据/多周期产生未来信息 | 显式 alignment/resample 语义、已完成 bar 门禁和双模式验收 |
| clean install 暗中依赖 sibling corpus | 随包 snapshot/模板/精选片段 + 显式 source-attached 模式 |
| SDK/client 快速演进造成协议漂移 | M0 锁版本并以真实 stdio/Inspector/host 测试证明兼容 |
| “禁网”承诺不可验证 | P0 只承诺静态网络 API 拒绝和人工批准；强隔离留给容器后端 |
