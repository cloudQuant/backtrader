## 0. 审阅结论摘要

**这是一份工程质量很高、但"交易员视角"缺失的计划。**

它在"不出事"这个方向做得非常扎实：双路径显式归责、fail-closed、capability 不伪造、证据脱敏、
负向测试清单详尽、明确区分 replay/shadow/SimNow/production。这些是很多实盘系统出事故之后才补的
东西，计划一开始就写进去了，值得肯定。

但它回答的是"**怎么保证不越权写入**"，几乎没有回答"**我作为交易员，日常和出事后要知道什么、
要能做什么**"。具体地：

| 维度 | 评价 |
| --- | --- |
| 安全边界与归责 | 强。双路径、fail-closed、无自动回退，写得很清楚 |
| 执行正确性（journal/permit/对账） | 强。状态机、幂等、UNKNOWN→reconcile 都覆盖了 |
| 交易业务语义（CTP/期权/合约/口径） | **弱。这是最大缺口** |
| 可观测性（PnL/权益/成本/执行质量） | **弱。只监控"健康"，不监控"赚亏"** |
| 多策略共享账户的资金分配 | **缺失。架构级缺口** |
| 进程死亡后的兜底 | **缺失。架构级缺口，且与现有设计自相矛盾** |
| 简洁易用 | **不足。与初始需求第 1 条直接冲突** |

下面逐条展开。每条都给出文档中的具体位置和可验证证据，便于直接转成修订项。

## 1. 架构级缺口

### 1.1 【严重】策略进程死了以后，谁管我的仓位？

这是交易员在实盘里**最恐惧的场景**：周末/深夜，策略进程崩了，手上有 3 手 CTP 空头，
没人撤挂单，没人平仓，第二天开盘跳空。

计划里的相关表述是矛盾的：

- [需求文档](需求文档.md) 术语表：monitor 是"**独立于策略主循环**的控制面观察者"；
- FR41-08：monitor "**监控策略进程之外的运行状态**……检测进程/心跳失活"；
- 但 [设计文档](设计文档.md) D41-04 与 [迭代计划](迭代计划.md) WP41-D/D4：monitor 的
  freeze/drain 请求"**只能经 Broker control gate 生效**"；
- 而 Broker control gate 位于**策略进程内**（`BtApiBroker`）。

**结论：如果策略进程死了，Broker control gate 也死了，monitor 即使检测到心跳失活，
也无法执行任何 drain。** 这个"检测到但管不了"的窗口，恰恰是唯一真正需要兜底的窗口。

计划自己在 [插件与ZMQ架构](插件与ZMQ架构.md:187) 已经意识到同进程的洞：
> `enable_trading` 仅是 gateway command-channel 的默认拒写门：同进程若直接持有 provider adapter
> 仍可能绕过它，所以它不能替代 process isolation、ACL 或 server-side risk/execution admission。

但这条只写给了 gateway，没有写给它自己最需要它的 monitor。

更麻烦的是 CTP：计划明确 gateway 的 CTP 写入在独立验收前保持 `NOT_SUPPORTED`
（[插件与ZMQ架构](插件与ZMQ架构.md:190)、AC41-46）。那么在 CTP 上，**进程死亡后当前设计下
没有任何一层能撤单/平仓**——只能等期货公司强平。

**建议补充（必须落到合同和验收里，不能只在文档里说"monitor 独立"）：**

1. 明确 monitor 的**部署形态**：进程内 thread、独立进程、还是两者皆可。若是独立进程，
   定义它与策略进程的通信通道（它不能依赖已死的 Broker control gate）。
2. 定义 **`drain` 的执行主体（drain executor）** 与进程存活解耦：候选方案是
   (a) gateway server 持有账户会话并在 client 失联时代为撤单；
   (b) 独立 supervisor 进程持有受限 reduce-only 通道；
   (c) 明确声明"进程死亡后无自动兜底，依赖交易所/期货公司强平"并写进 README 已知限制。
   **三条里必须显式选一条**，不能留白。
3. 新增验收：**杀进程演练**。`kill -9` 策略进程后，证明 (a) 挂单被撤、风险敞口被降到预期状态，
   或 (b) 明确记录"无自动兜底"且 operator 收到可操作告警。现有 AC41-36 的
   "monitor restart/drain 演练"是重启演练，不是进程死亡演练，覆盖不到这个场景。
4. `freeze`/`drain` 的语义需要区分"**自愿停止**"与"**失联兜底**"。二者授权来源不同
   （前者 operator 主动，后者必须是预设的、不可被策略影响的策略）。

### 1.2 【严重】共享账户下，我的策略能下多大？

初始需求第 2 条要的是"账户级风险控制"。计划做到了账户级**硬上限**，但漏掉了
**账户级资金/保证金在策略之间的分配**。

文档里只有一处沾边——FR41-05 与 NFR41-04 提到 risk scope 包含"策略/候选分配"——
但：

- 没有任何 contract 让**策略自己知道**它的分配额度；
- `ExecutionIntent`/`RiskPermit` 里没有"本策略可用保证金"这类字段；
- Backtrader 的 `Sizer` 拿到的 `broker.getcash()` 是**整个账户**的现金，
  不是这个策略的那一份。

**后果：三个策略共用一个账户时，每个策略的 sizer 都会以为整个账户的钱是它的。**
策略 A 用 100% 账户保证金下单后，策略 B 的 sizer 仍然算出"我还有很多钱"，
直到 B 的订单被 risk 以"保证金不足"拒绝。表现是**策略行为随机、回测与实盘严重不一致**，
而且拒绝发生在下单时而不是 sizing 时，交易员看到的是莫名其妙的拒单。

**建议补充：**

1. 定义 `StrategyAllocation` contract：账户总权益 → 各策略/候选的分配额（名义/保证金/风险预算），
   并明确它是**由谁设定**（operator 部署配置？研究准入产出？）以及**如何调整**（能否盘中改？改了要不要 freeze？）。
2. 定义策略侧**读取分配额的公开接口**，并让 Backtrader adapter 把它接到 sizer 可见的位置
   （例如提供 allocation-aware 的 `getcash()`/`getvalue()` 语义，或至少提供只读查询 API）。
3. 明确"分配额用尽"与"账户级上限用尽"是**两种不同的拒绝**，原因码必须区分，
   否则交易员无法判断是该调策略还是该入金。
4. 新增验收：多策略共享账户下，sizer 决策不会越过各自分配额；分配额调整后旧 permit 失效。

### 1.3 【严重】`config.yaml` 命名与仓库现状冲突，会引发迁移事故

计划的配置根设计是：`<strategy-runtime-dir>/config.yaml` 是本地的、被 `.gitignore` 忽略的
凭据与插件组合入口，仓库只提交 `config.example.yaml`（[设计文档](设计文档.md) §3.1、
FR41-14、NFR41-08）。[README](README.md:54) 还特别强调：

> 现有被追踪的 `config.yaml` 不能只靠新增 ignore 变安全：迁移必须先将其无秘密结构迁到模板、
> 移除 Git index 中的真实文件……

**计划知道有"已跟踪的 config.yaml"这个问题，但没有盘点它们，也没有发现命名冲突。**
我实际盘点的结果：

```text
$ git ls-files | grep -E '(^|/)config\.yaml$'
examples/001_multi_extend_data/config.yaml
examples/012_1_midfreq_cross_exchange/config.yaml
examples/012_2_event_driven_cross_exchange/config.yaml
examples/013_1_midfreq_cross_arbitrage/config.yaml
examples/013_2_highfreq_calendar_arbitrage/config.yaml
examples/013_3_sa_midfreq_simnow/config.yaml
examples/014_1_ctp_options_lowfreq/config.yaml
examples/014_2_ctp_options_midfreq/config.yaml
examples/015_ctp_options_highfreq/config.yaml
examples/016_self_similarity/config.yaml
examples/017_fnn_embedding/config.yaml
```

**11 个文件**，其中至少 3 个**根本不在迁移矩阵范围内**：

- `examples/001_multi_extend_data/config.yaml` 的内容是**策略参数文件**：
  ```yaml
  strategy:
    name: "可转债双低因子多品种策略"
  params:
    first_factor_weight: 0.5
    hold_percent: 20
  data:
    symbol: "bond_index"
  ```
  这是**必须被版本控制**的、无秘密的策略参数——迁移矩阵第 3 节把 `001/` 归为 `NOT_APPLICABLE`，
  它压根不在迁移范围内。
- `examples/015_ctp_options_highfreq/config.yaml` 是 `schema_version: ctp-options-candidate.v1`
  的候选运行配置（`mode: replay`、`production_enabled: false`），同样无秘密。
- `examples/013_3_sa_midfreq_simnow/config.yaml` 是 SimNow 前置地址 + profile + 合约选择，
  **SimNow 前置地址是公开信息，不是凭据**。

**后果（这是我认为最可能立刻出事的一条）：**

1. 如果按计划给每个策略目录加 `.gitignore: /config.yaml`，会**误伤 001/016/017 这类
   纯参数文件**，把合法参数移出版本控制，破坏这些 example 的可复现性——而它们并不在
   迁移矩阵的授权范围内。
2. 同一个文件名 `config.yaml` 在仓库里同时表示"策略参数"和"运行时凭据+插件组合根"两种
   完全不同的东西。迁移期 operator 极易把凭据写进参数文件，或反过来把参数文件当模板删掉。
3. "凭据 vs 非秘密运行参数"被一刀切成"config.yaml 一律不跟踪"，会让 SimNow 前置地址、
   合约选择、profile 名这类**应该被版本控制的运行参数**失去追踪，这是可用性倒退。

**建议（优先级最高的修订项之一）：**

1. **改名**。把插件组合根换成一个语义无歧义的名字，例如 `runtime.yaml`、`live.yaml`
   或 `plugins.yaml`，与既有的"策略参数 `config.yaml`"彻底分开。改名成本在计划阶段是零，
   进入实施后是灾难。
2. 若坚持用 `config.yaml`，则必须限定作用域（例如只在 `<strategy-dir>/live/config.yaml`），
   并在 WP41-A 中**逐个列出这 11 个文件及其处置**（保留跟踪 / 迁为模板 / 移除索引 / 移入新名），
   每个都要有 `git ls-files` + `git check-ignore` 证据。
3. 明确区分**凭据字段**与**非秘密运行参数**：只有前者需要 untrack，后者应继续版本控制。
   当前 NFR41-05/NFR41-08 的表述是"整个 config.yaml 不能进 Git"，过于粗暴。
4. 新增验收：仓库级扫描证明不存在"含凭据且被跟踪"的文件，**同时**不存在
   "应被跟踪的参数文件被误 ignore" 的情况（双向断言，不能只查一边）。

### 1.4 【中】risk 与 monitor 都能 freeze，谁说了算？

FR41-05（risk 可冻结）与 FR41-07（monitor 可请求 freeze）都能阻断开仓，但计划**从未定义
两者同时生效时的合并语义**（全文检索"优先级/precedence/合并语义"：0 命中）。

需要回答的问题：

- risk 判定 `allow`、monitor 判定 `freeze`，最终能不能开仓？（直觉是"任一 freeze 即 freeze"，
  但要写死。）
- monitor 的 freeze 解除后，risk 的 freeze 是否仍然生效？
- 两者对**同一 scope** 的 freeze 是独立计数还是共享？
- `drain` 由谁发起、由谁确认完成？两个组件同时对同一账户发起 drain 会不会互相打架？
- `resume` 需要**哪些授权**？（计划说"必须重新 preflight/授权"，但没说是谁的授权、
  是否要求双方都同意。）

**建议：** 在 [设计文档](设计文档.md) 增加一节"控制面合并语义"，明确
**freeze 是 OR（任一即生效）、resume 是 AND（需全部解除且人工授权）**，
并给出 `ControlCommand` 的优先级与冲突裁决表。补一条负向测试：
risk 与 monitor 对同一 scope 同时 freeze，drain 不重复执行、不互相撤销。

## 2. 交易业务语义缺口（计划几乎没覆盖）

我按交易员日常真正依赖的概念做了一次全文检索，结果如下（命中数为 0 表示计划完全没提）：

| 概念 | 命中 | 为什么交易员在意 |
| --- | --- | --- |
| 平今 / 平昨（close_today/close_yesterday） | **0** | CTP 上期所/能源中心强制区分，平今手续费常高出数倍 |
| 涨跌停板 | **0** | 停板时订单行为、风控判定、被动单策略全变 |
| 保证金率盘中调整 | **0** | 临近交割/停板后交易所会盘中提保证金，直接影响可用资金 |
| 强平（交易所/期货公司） | **0** | 系统必须能识别并处理"不是我下的平仓单" |
| 结算价 | **0** | 盯市盈亏、日损口径的基准 |
| 合约换月 / rollover | **0**（唯一 1 处是 permit rollover，语义无关） | 期货策略最日常的运维动作 |
| 行权 / 到期日 | **0** | 仓库有 3 个期权 example |
| 合约乘数 / instrument master | **0** | 名义金额、保证金、最小变动价位计算的根 |
| 期权 | **0** | `014_1`/`014_2`/`015` + 7 个 `ctp_options_simnow_*.py` 在范围内 |

### 2.1 CTP 业务细节

[迁移矩阵](迁移矩阵.md) 把 `007_ctp`、`013_1`、`013_2`、`013_3`、`014_*`、`015` 都列入了迁移范围，
这些都是 CTP 场景，但计划对 CTP 的处理只到"TradingDay/夜盘边界"这一层。缺的都是会直接
造成实盘损失的东西：

1. **平今/平昨**。`ExecutionIntent` 只有 `position effect` 和 `reduce-only`，
   没有 `offset flag`（开/平/平今/平昨）。CTP 的 `OffsetFlag` 是**必填字段**，
   填错会被柜台拒单；而"平今 vs 平昨"还直接影响手续费和可用持仓。
   更关键的是：**这个决策属于执行层还是策略层？** 计划没有回答。
   我的建议是执行层根据账户实际持仓（今仓/昨仓）自动解析，并把它记入 `ChildIntent`，
   因为策略层通常不该关心这个。但**必须显式决定并写下来**。

2. **涨跌停**。停板时：
   - 市价单可能无法成交或被拒；
   - 被动单（`passive`）挂在停板价上会一直不成交；
   - 风控的"名义金额"用停板价还是最新价计算？
   - 停板打开时的滑点会极大。
   计划有 `immediate/passive/slice` 三种 policy，但没有一条提到停板。

3. **保证金盘中变化与强平**。交易所盘中提高保证金比例后，本地 risk ledger 的
   "可用额度"会与柜台不一致。以及：柜台强平产生的成交**不在本地 journal 里**，
   `UNKNOWN → reconcile` 能否识别并正确处理？这是对账逻辑最容易漏的 case。

4. **合约换月**。主力合约切换时，持仓、行情订阅、策略状态、风险额度都要迁移。
   计划完全没有这个概念。至少要明确：**换月是策略责任还是平台责任？**
   如果是策略责任，README 合同里应该要求说明；如果是平台责任，需要 contract。

5. **结算价 vs 最新价**。"日损"和"名义金额"用哪个价格算？计划没定义。

### 2.2 期权专项（014_1 / 014_2 / 015）

这三个 example 是期权策略（`015` 的 fixture 里明确有 `call`/`put`/`strike` 结构），
但计划全文 **"期权"命中 0 次**。期权交易有一批期货没有的硬约束：

- **到期日与行权**：到期日的持仓怎么办？自动行权还是必须提前平仓？被行权后变成期货持仓，
  系统能不能识别并接管？到期日当天能不能开新仓？
- **合约元数据**：行权价、到期日、合约乘数、最小变动价位——名义金额和保证金算错的直接来源。
- **流动性断层**：虚值期权流动性极差，`immediate` policy 可能吃到极端价格。
- **组合保证金**：如果策略是价差组合，保证金算法与单腿完全不同。

**建议：** 至少新增一节"期权专项约束"，明确到期/行权/元数据/流动性四件事的处理责任方；
如果本轮确实不做，必须在"明确非范围"里**显式声明**，而不是留白——留白会让实施者
以为默认行为是安全的。

### 2.3 instrument master 缺失

`ExecutionScope` 有"instrument canonical identity"，`FillAllocation` 有"舍入 remainder"，
但**没有任何地方定义合约元数据（乘数、最小变动价位、涨跌停、保证金率、到期日）从哪来、
谁校验、什么时候刷新**。没有它：

- "名义金额"算不出来（期货名义 = 价格 × 乘数 × 手数）；
- 舍入没有基准（价格必须对齐最小变动价位）；
- 保证金占用算不出来。

**建议：** 新增 `InstrumentMetadata` contract 与来源（provider 查询？静态文件？两者校验？），
并明确**元数据缺失时 fail-closed**。这是风控数字正确性的前提，不能留给实现者自由发挥。

## 3. 可观测性缺口：只监控"健康"，不监控"赚亏"

计划有非常完整的 health read model（WP41-D2：心跳、MD/TD、行情新鲜度、writer lease、
磁盘、队列、未知订单、对账滞后、风险预算、clock skew），这部分很好。

但作为交易员，我每天要回答的问题，计划**一个都没接**：

1. **我今天赚了多少？** —— 全文"权益曲线/equity/PnL"命中 0。没有 durable 的
   权益/盈亏时间序列。journal 里有成交和费用，但没有聚合出 PnL 的 contract。
2. **我的策略是不是按预期在跑？** —— 没有"策略信号 vs 实际下单"的对账。
   实盘最经典的故障是"信号发了但单没下"，或者"下重复了"。`FillAllocation` 回灌能支撑
   这个对账，但没有把它定义成一个交付物。
3. **我的成交质量怎么样？** —— 计划有"滑点约束"字段，但**没有 TCA（交易成本分析）**：
   滑点（相对到达价/中间价）、实现落差、被动单成交率、拒单率、部分成交率。
   这些是判断"策略衰减是因为 alpha 没了还是因为执行变差了"的唯一依据。
4. **回测和实盘差多少？** —— 没有 backtest-vs-live 的一致性对账。这是量化交易员
   最核心的反馈闭环。计划把"成本研究"划出范围（[迭代计划](迭代计划.md) §5），
   这作为**范围控制**是合理的，但连"留个接口/留个数据出口"都没做，就过头了。

**建议：** 不要求本轮做分析产品，但要求**数据出口**：

1. 定义 `AccountSnapshot`（权益、保证金占用、可用、持仓、当日已实现/未实现盈亏）
   的 durable 快照，作为 monitor read model 的一部分。注意：`LifecycleCheckpoint`
   已有 "account snapshot freshness" 字段，但那只表示"快照新不新"，不是快照本身。
2. 定义 `ExecutionQualityRecord`：每个 child 记录到达价、成交均价、滑点、费用、耗时。
   数据从 `FillAllocation` + 行情天然可得，成本极低。
3. 在 README 最小内容合同里增加一项：**如何回答"今天赚了多少、执行质量如何"**。
   如果答案是"自己写脚本解析 journal"，也要写明。

## 4. 其他需要补齐的契约

### 4.1 风控指标的**口径**未定义（会直接导致实盘事故）

FR41-05 / WP41-C4 列了一串风险维度："频率、每日次数、撤单、仓位、名义金额、保证金、损失、
紧急额度"。全文检索"口径"：**0 命中**。这些词每一个都有多种算法，不定义就会出现
"风控以为没超、柜台以为超了"：

| 指标 | 需要定义的口径 |
| --- | --- |
| 名义金额 | 绝对值还是净额？用最新价/结算价/委托价？期权用名义还是权利金？ |
| 损失 | 已实现、含浮亏、还是含手续费？起点是交易日 00:00 还是开盘？ |
| 每日次数 | 自然日、交易日、还是 rolling 24h？跨夜盘怎么算？ |
| 频率 | 每秒/每分钟？窗口滑动还是固定桶？ |
| 仓位 | 手数、名义、还是保证金占用？净额还是 gross？ |
| 保证金 | 交易所口径还是期货公司口径（后者通常更高）？ |

**建议：** 在 [需求文档](需求文档.md) 或 [设计文档](设计文档.md) 新增
"风险指标计算口径表"，逐项冻结定义、价格基准和时区/日界。这是**验收 AC41-14 的前提**——
没有口径，AC41-14 无法判定通过与否。

### 4.2 幂等键的派生规则与重启语义

`ExecutionIntent` 有 `idempotency key`，E1 有"intent 去重"，但**没有定义键怎么派生**。
这直接决定一个经典事故：**策略进程重启后重新生成同一个信号，会不会重复下单？**

需要明确：
- 键的组成（strategy_id + 交易日 + bar 时间 + 信号序号？）
- 重启后能否重建出**同一个**键（需要策略状态持久化配合，见 4.3）
- 键的保留窗口（当日有效？TradingDay 内？永久？）
- 跨进程/跨重启去重发生在哪一层（execution journal？risk？）

**建议：** 在 contracts 里冻结幂等键的派生规则，并补一条负向测试：
"重启后重放同一信号，provider write count 为 0"。

### 4.3 策略自身状态的恢复（不只是订单状态）

计划的 Recovery 全部围绕**订单/执行状态**（WP41-E2、AC41-22、
[迁移矩阵](迁移矩阵.md) Recovery 行）。但 Backtrader 策略有自己的内部状态：
指标缓存、状态机（"我正在第三条腿的执行中间"）、冷却计时器。

进程崩溃重启后：
- 指标需要重新预热（minperiod 内不能交易）；
- "三腿价差执行到一半"这种状态怎么恢复？F5 提到把 014_1/014_2 的本地
  coordinator/journal 下沉，但那是**特例**，不是通用 contract。

**建议：** 明确策略层状态恢复的**责任边界**：
(a) 平台提供通用 checkpoint contract，策略自行实现 `save/load`；或
(b) 明确声明"策略重启后从零状态开始，由 execution 层保证不重复下单"。
两者都可以，但必须**显式选一个**并写进 README 合同。

### 4.4 对账容差与告警可操作性

1. **对账容差**：全文"tolerance"命中 0。本地 journal 与柜台持仓差 1 手算正常吗？
   差多久算异常？需要定义容差表（按品种/账户）和超差动作。
2. **告警分级**：D3 有"告警去重、升级"，但没有**分级**。交易员需要知道
   "哪条告警需要我立刻起床、哪条明天看就行"。建议引入明确分级
   （如 P1 立即人工介入 / P2 当日处理 / P3 记录），并规定每级的通知渠道与响应时限。
3. **`manual_intervention` 的触发清单**：什么情况下系统会进入 `manual_intervention`、
   通知谁、期望多久内响应、超时怎么办——都没有。

### 4.5 性能预算缺失

全文"latency"命中 0。managed 路径新增了 journal 持久化、outbox、跨进程 risk reservation
加锁、monitor consumer。交易员会问：**"这条链路给我的下单增加了多少延迟？"**

**建议：** 增加 NFR：明确 managed 路径的 order-path 延迟预算
（例如 p99 端到端 < X ms，不含网络与柜台），并**明确声明该架构不适用于哪一类延迟敏感策略**
（`015` 是 HFT 观测，正好是边界案例）。没有这个声明，实施者可能默认它适合一切场景。

### 4.6 零写 shadow 的强制机制

AC41-36 要求 shadow/replay 的收据证明 "0 provider write"。但**拦截点在哪一层没有定义**：
是 Store 层、provider 层，还是靠配置约定？如果策略代码绕过 Store 直接调 provider 呢？

**建议：** 定义 shadow 模式的**强制拦截点**（建议在 provider adapter 最内层做硬拒绝 +
write counter），并明确"shadow 模式下 provider write 计数器必须为 0，否则该次运行判定 FAIL"。
只靠收据事后断言不够，要有机制保证。

## 5. 易用性审阅（针对"简洁易用"这一诉求）

初始需求第 1 条就是："当前 examples 中实现的实盘策略有架构问题；**每个策略重复配置大量前置条件**，
不适合实际长期运行。" 计划的响应是引入 5 个插件 + 2 个拓扑维度 + schema-v3 配置。
这在工程上是合理的解耦，但**从操作者视角看，配置负担并没有明显下降**。具体问题：

### 5.1 `required` + `enabled` 双布尔，与"减少前置条件"的初衷相悖

[模板](templates/config.example.yaml) 里每个插件都有两个布尔：

```yaml
plugins:
  execution: {enabled: false, required: false, config: {...}}
  risk:      {enabled: false, required: false, config: {...}}
  monitor:   {enabled: false, required: false, config: {...}}
  gateway:   {enabled: false, required: false, config: {...}}
  transport_zmq: {enabled: false, required: false, config: {...}}
```

**10 个布尔**，而 `required: true && enabled: false` 又是非法组合
（[设计文档](设计文档.md) §3.1）。也就是说 `required` 只能取 `false`，
或与 `enabled: true` 同时出现——**它表达的是"这个部署 profile 强制要求该插件"，
那为什么不直接由部署 profile 决定，而要策略配置再写一遍？**

**建议：** 二选一：
- (a) 删掉 `required`，只保留 `enabled`；"强制要求"由部署 profile 或顶层
  `runtime.strict_profile: true` 表达；
- (b) 保留 `required`，但让它**蕴含** `enabled`（`required: true` 即视为启用），
  消灭非法组合。

无论哪种，都能把每个插件的配置项从 3 个降到 2 个。考虑到 5 个插件，
这是 5 行配置的差别，也是心智负担的差别。

### 5.2 六种合法组合，但没有"我该选哪个"的决策树

[设计文档](设计文档.md) §3.1 的组合表列了 6 行合法组合。对实施者清晰，对**操作者**
是负担。交易员想要的是：

```text
我只是想跑个策略，不想出事       → 无 config，direct_provider（零配置）
我想限制下单/撤单次数           → + risk
我还想有人盯着，出事能停        → + monitor
我要多策略共用一个账户          → + gateway_client + transport_zmq
我要聚合拆单、对账、恢复        → + managed_execution
```

**建议：** 新增一页"**操作者决策树 / 推荐路径**"，把这 6 种组合压缩成 3~4 条
命名路径（如 `basic` / `guarded` / `shared-account` / `managed`），并给出
每种路径的**最小配置片段**。文档已经很好地区分了"能做什么"，缺的是"**我该做什么**"。

### 5.3 缺 Quickstart、Runbook 和校验工具

- **没有 Quickstart**：一个新人拿到这个计划，不知道"最小可运行的一套是什么"。
- **没有 Runbook**：计划里 `freeze`/`drain`/`manual_intervention`/`resume` 出现了几十次，
  但**没有一份操作手册**告诉 operator 每一步具体敲什么、看什么、确认什么。
  [迁移矩阵](迁移矩阵.md) §5 要求 README 写启动/停止/freeze/drain 命令，但那是
  逐 example 的要求，不是统一 runbook。
- **没有配置校验工具**：计划只提到 `--strategy-dir <dir>`。缺少
  `validate` / `doctor` 这类命令——在 fail-closed 的架构里，**一个能明确告诉我
  "第 37 行 `plugins.risk.config.strategy_limits.max_notional` 必须是正整数" 的工具
  比一百页文档有用**。

**建议新增交付物：**
1. `操作者快速上手.md`（Quickstart，含决策树 + 最小配置 + 三条命令跑通）；
2. `运行手册.md`（Runbook：启动、观察、freeze、drain、恢复、进程死亡处置、告警响应）；
3. 一个配置校验 CLI（`validate` / `doctor`），并把**错误信息的可操作性**列为验收项：
   每条拒绝必须指出**具体文件、行号/字段路径、期望类型/取值**。

### 5.4 错误信息的可操作性没有被验收

计划反复强调 fail-closed，但**"失败得让人看得懂"从未被列为要求**。
在 5 个插件 × 6 种组合 × 多层 schema 校验下，一个模糊的 "config invalid"
会让 operator 排查数小时。

**建议：** 在 AC41-41/42 增加子项：**每个负向用例必须断言错误信息包含字段路径与原因**，
而不只是断言"非零退出"。这既是可用性要求，也是可测试的。

### 5.5 无渐进采用路径的说明

schema 允许任意组合，但文档没有明确告诉操作者：**"我可以先只上 risk，跑两周稳定后再加
monitor 吗？加的时候要不要停机？"**（[设计文档](设计文档.md) 说了配置变更必须
`freeze → drain → 新 preflight → restart`，但这散落在多处。）

**建议：** 在 Quickstart 里明确"**渐进采用阶梯**"，并说明每一级增加的保障、
需要重启还是可热加（当前答案是"必须重启"，因为 permit 不能沿用）、以及回退方式。

### 5.6 迁移工作量没有估算

[迁移矩阵](迁移矩阵.md) 列了 **14 个迁移单元**，每个都要 8 节 README + `config.example.yaml`
+ route 归责 + 测试 + 证据。[迭代计划](迭代计划.md) 有 M41-0～M41-4 里程碑，但**没有任何
工作量/周期估算**。业务方最关心的问题——"**我什么时候能用上？**"——无法回答。

**建议：** 给出每个工作包的人日量级估算，并明确 **M41-x 各自解锁了什么实际能力**
（当前里程碑表只说了"能得出什么结论"，没说"能做什么事"）。

## 8. 给计划的"交易员问题清单"

建议把这 12 个问题作为**需求的追问清单**附在 [需求文档](需求文档.md) 末尾。
一份实盘执行架构如果答不上来，交易员就不敢把钱交给它：

1. 我的策略今天赚了多少、亏了多少？在哪看？
2. 我的策略现在有多少敞口、多少保证金占用？在哪看？
3. 我的策略能下多大？这个额度是谁定的、怎么改？
4. 三个策略共用一个账户时，它们会不会互相抢资金？
5. 策略进程崩了，我手上的仓位谁来管？
6. 半夜出事，我会被叫醒吗？被什么叫醒？我要做什么？
7. 系统怎么判断"策略行为异常"而不只是"进程还活着"？
8. 我的成交质量怎么样？滑点、拒单、部分成交率是多少？
9. 回测和实盘的差距，是因为 alpha 衰减还是执行变差？
10. 我改了风控参数，需要停机吗？旧的授权会不会继续生效？
11. CTP 的平今/平昨、停板、保证金盘中调整，系统处理了吗？
12. 期权到期那天，我的持仓会怎样？

计划目前能明确回答的是 **6、10**（部分），其余要么留白，要么只能靠操作者自己写脚本。
**这不一定要求本轮全部实现**——但**每一项都必须显式回答"本轮做 / 不做 / 谁负责"**，
不能沉默。沉默在实盘系统里等于"默认不安全"。

---

## 9. 结语

这份计划的**安全设计水平明显高于它的业务完备度**。它像一座守备森严的堡垒：
谁都不能越权写入、所有动作都有 journal、所有能力都要 receipt、所有失败都 fail-closed。
这些都是对的，而且难得。

但堡垒里缺的是**厨房和卧室**——交易员日常要看的数字、要按的按钮、出事时的手册、
以及"我这个策略到底能用多少钱"这个最基本的问题。

我的建议不是推翻设计，而是**在不放松任何安全边界的前提下，补齐三件事**：

1. **业务语义**（P0-4/5/6、P1-7/8/15、P2-16）：CTP 与期权的真实约束、风险指标口径、
   instrument metadata。这些是数字算对的前提。
2. **兜底主体**（P0-2、P1-11）：进程死亡后谁执行 drain、交易员在哪看盈亏。
   这是"敢不敢真上"的前提。
3. **操作者体验**（P0-1、P1-12/13、P2-20）：命名不冲突、配置更少、有决策树、
   有 runbook、有 validate 工具、错误信息能看懂。这是"愿不愿意长期用"的前提。

第 3 点尤其重要，因为它直接对应初始需求第 1 条——**"每个策略重复配置大量前置条件，
不适合实际长期运行"**。当前的 schema-v3 在解耦上是对的，但如果不在易用性上再收一轮，
很可能只是把"重复配置前置条件"换成了"重复配置 10 个布尔 + 学习 6 种组合"。

**架构的安全性决定了它能不能上；架构的易用性决定了它会不会被绕过。**
一个用起来太麻烦的系统，最终一定会有人写脚本绕过它——那才是最大的风险。
