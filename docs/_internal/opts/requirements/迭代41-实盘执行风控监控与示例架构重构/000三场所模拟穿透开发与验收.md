# 000 三场所模拟穿透开发与验收

日期：2026-09-30。范围：`examples/000_live_certification/` 下的 Binance、OKX、SimNow 三个套件。本文是本轮开发与验收计划增补，不是 provider 准入凭据，也不是已通过的验收报告。

## 1. 目标、配置范围与当前状态

用户已确认 Binance 的产品范围为 **USDⓈ-M futures**，OKX 为 **永续合约（SWAP）**，并要求三个场所各完成全部 33 个案例，合计 99 个案例；不是只交付最小报撤单样例。每个场所保留 33 个独立案例入口。目标是在对应真实模拟账户环境中完成请求、场所回报、独立查询、风险约束与最终清理的全链路验证。离线源码、fake provider、配置校验和脚本启动结果分别记录，不能计入真实案例 PASS。

| 场所 | 目标目录 | 待绑定的运行范围 | 本计划建立时的真实验收状态 |
| --- | --- | --- | --- |
| Binance | `binance_penetration/` | 已确认 USDⓈ-M futures；实际模拟账户、标的、精确 REST/WS 端点与权限待绑定；现有示例的 `demo/sandbox` 标签不能替代实际绑定 | 33 个案例全部必需；真实结果 `NOT_RUN`，实际执行前仍须接受 adapter 与环境绑定 |

## 2. 本轮直连与可选能力要求的合同变更

用户本轮要求覆盖直连，并允许按需选用 gateway、ZMQ、execution、risk、monitor。原[实施计划 §0.3](迭代计划.md#03-必需配置与三模式交付合同)和[插件与 ZMQ 架构 §2](插件与ZMQ架构.md#2-三模式预设与派生拓扑)要求 sandbox/live 写入强制 execution+risk+monitor，并把 `legacy_direct` 限定为零外部写入。两项要求存在明确差异，不能把新组合描述成已经满足旧合同。

本轮以三套件的模拟环境为范围，开发可审查的直连及可选能力组合。每种组合必须有明确配置、固定的实际路由和独立验收记录；是否使用共享网关与是否使用 execution 分别记录。直接连接 provider 不自动等于使用 execution，也不自动获得 risk/monitor 保障。新增配置合同须与实际入口一致，不得仅添加未消费的插件字段。

此计划增补不开放生产交易、不删除 CTP 现有关闭门、不把未实现的能力标为启用，也不允许能力初始化失败后静默改走其他路由。现有 schema-v2 场所认证配置与 Iter41 schema-v4 registry/preset 是不同入口合同；适配或迁移必须显式实现并验证，不能只因字段名称相似就宣称已进入受管运行时。未来若提供无 execution 的 SimNow 写入路线，须先提交并验证等效的订单标识、持久状态和不确定结果处理合同；当前 G5/G6-S 等前置缺口仍阻断写入。

## 3. 组合矩阵

下表是待实现、待验收的组合，不是当前可启动清单。除表内强制依赖外，可选组件仅在显式选择时加载；报告逐项列出启用状态与实际消费的接口。每个允许组合均须验证关闭的组件没有被隐式导入、初始化或启动线程/socket。

| 组合 | 必须验证的行为 | 限定结论 |
| --- | --- | --- |
| direct，全部可选组件关闭 | 唯一 provider owner、明确环境、精确订单关联、请求限额、独立回报、UNKNOWN 冻结与限定清理 | 只证明该直接路线的案例行为，不宣称 execution/risk/monitor 保障 |
| direct+risk | 风险检查在 provider 写入之前执行；拒绝、额度占用与释放、重复请求有可核验证据 | 只证明已启用的风险规则，不宣称不存在的 execution 账本 |
| direct+monitor | 事件来源、持久消费/游标、滞后、断线恢复与声明的控制行为；monitor 不成为第二 writer | 观测或控制范围必须按实际实现列出 |
| direct+execution | 持久 intent/command 关联、去重、恢复、UNKNOWN 对账；只有一个发送权威 | execution 不隐式代表 risk/monitor 已启用 |
| direct+execution+risk+monitor | 三组件联合的派发前检查、持久结果、故障恢复和监控控制 | 可申请对应受管路线验收，但仍需场所/账户/配置范围证据 |
| gateway+ZMQ，叠加所选 execution/risk/monitor | gateway 与 transport 成对；server 持有唯一 provider owner，client 不持有 provider 凭据；各选用组件在实际 owner 侧生效 | 每个实际支持的组件组合单独列记录，不从 direct 结果推导 gateway PASS |

`risk+monitor` 等组合也必须由同一配置校验与组合合同覆盖。不得为了凑满组合数运行不支持的组合；不支持时输出明确 `BLOCKED` 原因并保留待交付项。gateway 关闭而 ZMQ 开启、gateway 开启而缺少相应 transport、组件声明启用却不可导入/不可绑定、client/server 环境或配置摘要不匹配，均须在 provider 写入前拒绝。

gateway 验收继续对应 AC41-46：至少两个独立 client、同一账户/标的一次 upstream 订阅、扇出隔离、订单归属、防冒用取消/查询、认证和 ACL、断线 snapshot/cursor/replay、timeout 到 UNKNOWN 和禁止本地 provider fallback。单进程 fake topology 不替代真实跨进程 transport 验收。

## 4. 开发顺序与验收门

| 阶段 | 交付物 | 通过条件 | 当前状态 |
| --- | --- | --- | --- |
| P0 范围与基线 | 三场所环境/产品绑定、99 案例清单、组合清单、代码与包身份 | 范围无歧义；每个案例和组合有明确依赖/阻断原因 | Binance USDⓈ-M、OKX SWAP 和全部 99 例已确认；精确端点/账户、OKX 地区、SimNow 合约/前置待绑定 |
| P1 配置与入口 | 显式环境、产品、route、组件组合、预算与证据目标；逐案固定入口 | 错配、缺失、非法组合和占位配置在 provider 写入前拒绝；关闭组件不加载 | Binance/OKX 已增加显式 topology 的先行关闭检查；direct 和可选组件实际路线仍 `NOT_ACCEPTED`，SimNow 未接入 |
| P2 场所 adapter 只读 | 真实会话身份、产品规格、参考价、账户/订单/成交/持仓完整查询 | 环境/账户/标的/会话绑定一致；分页终态与来源可验证；写入计数为零 | `NOT_RUN / BLOCKED` |
| P3 最小报撤单 | 一笔受限限价单、独立订单确认、精确撤余量、最终回查 | 请求与独立回报对应；不存在不明敞口或扩大清理范围；不确定结果不重发 | `NOT_RUN / BLOCKED` |
| P4 全部案例 | 各场所 33 例逐例运行与证据 | 每例满足自身动作、风险和证据合同；前置不足明确 BLOCKED | 99 个真实案例 `NOT_RUN` |
| P5 可选能力组合 | 已支持组合的正常、拒绝、崩溃、重连与恢复结果 | 证明组件实际生效；一次 writer；组合间证据不混用 | `NOT_RUN` |
| P6 独立验收与交付 | 最终代码/包/配置摘要、运行清单、逐例结论与复核记录 | 所有声明均可追溯；未完成项保留；不能以源码测试关闭真实场所门 | `NOT_RUN` |

P2/P3 只在实际所需 adapter、账户、环境和前置能力齐备后执行。P4 先完成只读、普通写入和可靠清理，再按案例需要执行危险场景。CLI 确认、配置 grants 与每案范围必须同时匹配；整个迭代的开发授权不能被运行器转换成任意账户、任意合约或无限预算的操作许可。

现有 Binance/OKX C01 校验把认证、登录和 `provider_session_id` 要求为同一个会话 ID，并要求独立事件引用这次只读检查的 provider 请求/响应；现行只读窗口还要求前后订单、仓位、余额、成交和流水快照稳定。签名 REST 账户查询的 HTTP 200 本身不提供这些事实，不能在检查旧认证证据时伪造一个新的 provider 登录事件。P2 应先建立版本化的场所认证观察 profile，区分 provider connection ID、客户端请求 ID、采集 ID 和本地派生摘要；由独立只读采集器保存原始事实并验证账户身份与完整快照，只对 C01 的只读检查语义作有测试约束的调整，写入路径继续保持现有事件关联要求。

按现有[Binance 官方 WS API](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/websocket-api-general-info)，`session.logon` 需要 Ed25519 凭据，不能由当前 HMAC Demo key 推定支持；REST profile 应只声称签名账户读取，不能虚构登录 session。按[OKX 官方 WS 登录](https://www.okx.com/docs-v5/zh/#overview-websocket-login)和[账户配置](https://www.okx.com/docs-v5/en/#trading-account-rest-api-get-account-configuration)，私有 WS 登录回执的 `connId` 是连接标识，账户配置的 `uid` 才用于账户身份核对；不得将 `connId` 同时当作两个独立认证事件和账户 ID。两种 profile 的实际 collector、原始回执和独立性尚未实现，C01 保持 `NOT_RUN`。

## 5. SimNow 的既有边界

CTP 当前状态以[当前验收矩阵](ctp-current-acceptance-matrix.md)的最新日期段落为准，历史测试数和 marker 不作为新运行凭据。000 入口不得借用旧 007/013 脚本绕过缺失 runner 或 native 生命周期门。

SimNow 写入之前逐项核对：G1 的制品与受监督进程清理；G2 的 TD 身份和终态只读查询；G3 的 MD 身份、匹配订阅 ACK 与首 tick；G4 的同一会话 Join/Release/观察线程退出；G5 的唯一持久 OrderRef/ActionRef/command 映射；G6-S 的本机写者约束、逐动作窗口、结算就绪和 UNKNOWN 不重派。G7-S 先取得仍有余量的限价单撤单正例，再扩展成交与已验证的平仓路径。

用户已取消整条 CLI 必须 0.8 秒完成的旧要求；不得重新将该数字列为当前硬门。可验证的终止、资源回收和明确超时行为仍须实现。进程退出、Job 空或客户端 `stop()` 返回，均不能代替 native close 的正面证据。

G6-P/G7-P 的跨主机账户 fence 和同版本完整快照属于严格 F14/production 的额外门。未来 G7-S 只可记录限定账户和操作窗口的 SimNow 操作性结果，并明确这些外部保证尚未证明，不能升级为生产准入。当前仍为 `NO_WRITE / LIVE_NO_GO`。

## 6. 不可覆盖的证据与判定

每次运行创建新的独立 evidence 目录；不得复用已完成目录或覆盖旧结果。运行清单至少绑定 suite/case、产品/环境、route、各组件状态、代码提交及脏树差异摘要、包版本和来源、配置摘要、账户伪名、开始/结束时间、运行 ID 与会话代次。凭据、token、原始私有配置不入证据。

逐案保存请求关联、provider 同步结果、独立回调/查询来源、完整分页终态、执行前后订单/成交/持仓/余额快照、适用的风险判定与执行账本、精确清理目标和最终残留。形成内容哈希索引；复核结论写入新记录并引用旧摘要，不回写原始事实。哈希链只能证明记录之间的完整性，不能认证恶意 backend 自造的事实；adapter 来源、部署和独立观察必须另验。

| 结果 | 必须满足的含义 |
| --- | --- |
| `NOT_RUN` | 尚未执行相应真实场所案例或组合 |
| `BLOCKED` | 前置、范围、能力、来源或证据缺失；记录具体缺口，不等于案例通过 |
| `FAILED` | 已观察违反合同、不一致、越界或未完成清理；记录残留与后续处理 |
| `PASS` | 此精确案例、环境、产品、账户范围、路由和组合的全部适用条件有真实证据，并完成最终对账 |

仅清理本次授权且身份精确匹配的订单；不得因 provider 产生重复 ID、外来订单或回报未知而扩大撤单/平仓权限。出现 UNKNOWN、未完成分页、过期证据、身份错配或清理不确定，不能记 PASS，不能自动重试下单。场所不具备某案例所需能力时单独记录原因与待决范围，不能用 N/A 静默减少 33 例分母。

以下是环境识别和 adapter 实现的主来源，不是本次账户可用性或实际连接的证明。实际运行仍绑定精确配置和当次 provider 事实。

- [Binance USDⓈ-M Futures General Info](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/general-info)：本轮查阅的官方文档将 testnet REST 与 WebSocket 基地址分别列为 `https://demo-fapi.binance.com`、`wss://demo-fstream.binance.com`；使用前须核对实际接口类别，不能把行情流地址当成所有 WS API 的统一地址。文档明确部分超时响应代表执行状态 UNKNOWN，应先通过订单查询或回报核验，防止重复下单。
