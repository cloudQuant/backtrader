## 0. 审阅结论摘要

这份计划的**单个需求写得很密**：FR/NFR/AC 三层都有可观察条件，负向情形清单详尽，
"不得"类约束的措辞精度高。作为需求文档的单篇质量，高于常见水平。

但从需求工程的全过程看，它缺的是**管理层**：

| 维度 | 评价 |
| --- | --- |
| 需求条目质量（可观察完成条件） | 强。FR→AC 的映射经手工重建后内容大体闭合 |
| 安全/负向需求覆盖 | 强。与前两份审阅结论一致，不重复 |
| **审阅意见的裁决机制** | **缺失。四份审阅 60+ 条修订项无人裁决、无模板、无时限；AC41-47～55 已被交易员与 AI 架构师两份审阅重复分配（第 10.1 节实证）** |
| **需求可追溯性** | **缺失。初始需求 13 条 → FR → WP → AC 无追溯矩阵；初始需求 1/3/4 无法闭环验收** |
| **需求基线与变更控制** | **缺失。schema v1→v2→v3 同日三变，无 changelog、无基线声明** |
| **迁移矩阵完备性** | **有实证缺口。`ctp_options_simnow_*` 实际 11 个文件，P1-B 只枚举 6 个；6 个 examples 目录未出现在矩阵任何位置** |
| 优先级管理 | 不足。FR 无优先级标注；WP41-D（monitor）P1 与初始需求 3 的用户优先级错位，未经知情确认 |
| 里程碑质量门 | 不足。M41-0～4 未绑定 AC 子集，"达成"无判定标准 |

一句话：**前两份审阅证明这份计划"答错了什么"，本审阅证明它"没有机制保证答错之后
能被纠正"——31 条修订意见目前悬置在没有任何裁决流程的真空里。**

## 2. 需求管理流程缺口（本审阅的核心增量）

### 2.1 【严重】F1：两份审阅、31 条修订项，悬置在没有裁决流程的真空里

README 已如实登记：两份审阅意见"尚未并入本计划的强制范围，需由计划 owner 逐条裁决
`采纳 / 部分采纳 / 不采纳`"。但计划**没有定义裁决流程本身**：

1. **owner 是谁？** "计划 owner"一词被两份审阅合计点名十余次（交易员"问题清单"、
   技术经理"裁决问题清单"第 1～8 条），但全部 8 份文档没有任何一处定义这个角色的
   人选、权限或与策略研究方/operator/库维护者的分工。没有 RACI，"需 owner 裁决"
   等于"无人裁决"。
2. **裁决时限挂在未定义的事件上。** 技术经理要求 R1/R2/R3 在"计划冻结前"裁决，
   但"计划冻结"这个事件本身没有定义：没有日期、没有触发条件、没有由谁宣布。
   当前的现实风险是：`PLANNED / NO-GO` 状态可以无限期持续，裁决被无限推迟，
   而修订项（如 config.yaml 改名）的成本随时间单调上升。
3. **无裁决记录模板。** 31 条修订项（交易员 P0×6 + P1×9 + P2×5，技术经理 R1～R11）
   中至少 4 组实质重叠：
   - 性能预算：交易员 P2-18 ↔ 技术经理 R3/R4（技术经理已升级为 P0/P1）；
   - 证据自动化/validate CLI：交易员 P1-13 ↔ 技术经理 R8；
   - config.yaml 命名：交易员 P0-1 ↔ 技术经理第 4 节"升级为冻结前置条件"；
   - drain executor：交易员 P0-2 ↔ 技术经理裁决问题 5。

   两张独立清单 + 两份"建议验收条件"（AC41-47～55 与 AC41-56～60，编号已自觉错开）
   如果不合并为**一张统一裁决表**（条目、来源、重叠关系、裁决、理由、影响文档、
   落实工作包），并入过程必然漏项或重复施工。

**建议：** 新增《审阅裁决记录》文档（或并入 README），包含：owner 任命与替补、
统一裁决表（全部审阅条目）、"计划冻结"事件的定义与裁决截止规则。
这是 RA1，**建议列为计划冻结前的强制前置**。

> **2026-09-21 第二轮更新：** 第四份审阅（AI 系统架构师）已提交，其建议 AC 编号
> AC41-47～55 与交易员审阅的 AC41-47～55 **完全冲突**——本条预言的编号漂移已实际发生，
> 实证见第 10.1 节。统一裁决表与编号命名空间（RA13）已从"建议"变为硬前提。

### 2.2 【高】F2：需求基线与变更日志缺失 —— schema 一日三变而无记录

本迭代的需求在同一天（2026-09-21）经历了三次架构修订：schema-v1（`modules`，
WP41-A7 标记"已废弃、不实施、不验收"）→ schema-v2（`plugins.zmq`，废弃，仅允许
显式 v2→v3 迁移工具）→ schema-v3（`plugins` + `runtime.account_access`）。
变更本身合理，且各文档头部的"架构修订"注记做得不错；但：

- 没有**变更日志**：v1/v2 的哪些内容进入了 v3、哪些被废弃、废弃影响了哪些
  FR/AC/WP，只能靠读者跨 5 份文档自行 diff；
- 没有**需求基线声明**：当前文档集合是"第几版基线"？后续修订（例如并入两份
  审阅的 31 条）将以什么版本号、什么评审动作固化？
- WP41-A5 承诺的 ADR-41-01～06 尚不存在，而后续 ADR 编号已用到 08
  （[插件与ZMQ架构](插件与ZMQ架构.md)）。A 阶段交付时若无 ADR 索引页，编号必然漂移。

**建议（RA2）：** 建立需求基线声明（当前为 baseline-0，并入审阅裁决后冻结为
baseline-1）+ 变更日志（每次修订记录：变更点、动因、影响的 FR/NFR/AC/WP/模板）+
ADR 索引页。成本极低，缺失的代价在 31 条修订项并入时会立即显现。

**缺口（逐条展开）：**

**建议（RA3）：** 建立追溯矩阵（初始需求 → FR → WP → AC → 证据），随 baseline-1

### 2.4 【中】F4：假设与依赖未登记

计划的关键假设散落在各处，没有一条被当作"假设"管理（验证方式、失效影响、复审节点）：

| 假设 | 现状 | 失效时的影响 |

## 3. 需求质量缺口（初始需求层）

### 3.1 【严重】Q1：初始需求 1（"减少每个策略的前置条件"）没有任何可验收形式

初始需求第 1 条是本迭代的立项动因："每个策略重复配置大量前置条件，不适合实际
长期运行。"但：

- **没有基线**：当前每个策略的"前置条件"是多少？（环境变量数、配置文件数、
  手工步骤数、启动命令数、需记忆的参数数）——全文无一处统计；
- **没有目标**：迁移后降到多少算"减少"？schema-v3 引入 5 插件 × (enabled,
  required, config) + 2 个拓扑维度后，配置项**数量上可能不降反升**
  （交易员审阅 5.1 已指出 10 个布尔问题）；
- **没有任何 AC 能判定这条初始需求达成与否**。FR41-14 只规定了"如何组装"，
  没有规定"组装后比原来简单"。

后果：迭代可以全部 46 条 AC 通过，同时初始需求 1 事实上恶化——而无人能判定。

**建议（RA4）：** WP41-A inventory 为每个迁移单元增加"前置条件基线"字段
（至少：必填环境变量数、配置文件数及行数、启动命令步数、手工准备动作清单）；
完成定义增加"迁移后的命名路径配置不劣于基线，目标路径达到约定降幅"；
新增 AC41-61（见第 6 节）。

### 3.2 【严重】Q2：评估类需求被预设结论替代，评估过程无交付物

初始需求第 3、4 条是**评估/决策类**需求：

- 需求 3："需要判断 Backtrader 的 TradeLogger 是否足以替代 monitor"；
- 需求 4："需要评估 Backtrader 和 `bt_api_py` 已有 execution 能力，以及订单聚合
  下单应处于哪个框架层"。

计划的处理方式是**直接预设结论**：完成定义第 4 条断言"TradeLogger 不是其替代品"；
D41-01 决定新建 execution 包；D41-05 决定聚合表达在 execution 层。
这些结论很可能都是对的——但**评估过程没有任何交付物**：

- WP41-A5 的 ADR-41-01～06 主题清单（journal、risk reservation、monitor command、
  数据保留、回滚、submodule/optional extras/版本兼容）**不包含这两项评估**；
- 需求文档 §4 对 risk/monitor/execution 现状有描述，但那是"集成约束"陈述，
  不是"TradeLogger vs monitor 能力对比"或"聚合层次备选方案权衡"的评估记录；
- 后果一：结论缺乏依据链，未来有人翻案（例如"其实 TradeLogger 加两个字段就够了"）
  时无据可考；后果二：如果评估真的展开后结论与预设相反，计划没有回退路径。

**建议（RA5）：** 新增两份评估 ADR（编号从 ADR-41-09 起，因 08 已被
[插件与ZMQ架构](插件与ZMQ架构.md)占用）：TradeLogger-vs-monitor 能力对比与裁决；
execution 能力盘点与聚合层次裁决（含"兼容迁移 `_ExecutionSession`"的可行性评估，
与技术经理 R5 衔接）。作为 WP41-A 交付物，owner 签收，新增 AC41-62。

### 3.3 【高】Q3："完善 bt_api_risk/monitor" 的存量处置边界未定义

初始需求第 8 条要求"完善 `bt_api_risk`、`bt_api_monitor`"。技术经理实测
`bt_api_risk/src` 6,584 行中**约 2,100 行是 ML 模型代码**（ensemble_model 732 +
anomaly_detector 914 + ml_base 482）。计划对 risk 的范围只写了"修复 fail-open/频率/
额度/halt 缺口 + durable reservation/permit"（WP41-C），对这批 ML 代码**只字未提**：

- 保留为分析能力？那么其依赖（可能的 sklearn/numpy 等）是否进入 risk 包安装依赖、
  是否违背"risk 在写前 hard-gate 热路径"的性能定位（技术经理 3.3）？
- 隔离为可选 extra？删除？这些决定影响 C1 的"补齐声明依赖/导出一致性"的验收口径。
- monitor 的 Prometheus/Grafana/ELK exporter（3,376 行存量）同理：保留范围需确认。

**建议（RA6）：** WP41-C/D 动工前，owner 对两个存量包逐模块裁决
"保留/隔离/删除"，写入各自 WP 的任务表；这是"完善"一词的完成边界，
否则实施者自由发挥的余地过大。

### 3.4 【高】Q4：managed 路径的最小真实 consumer 集未定义

完成定义第 1 条允许每个 example 落到 `DIRECT`、`MANAGED`、`DISABLED` 或
`NOT_APPLICABLE` 中的任何一个。逻辑上自洽，但存在**退化完成形态**：
所有 example 全部保留 `legacy_direct` 或 `DISABLED`，迭代仍可宣告完成——
此时 execution 包的"隔离 consumer 验收"（AC41-39）只有 fake provider 和
contract test，聚合/恢复/生命周期从未被真实策略负载检验过。

初始需求第 6 条要求"重构所有可写 examples"，`DISABLED` 确实是一种合法处置；
但一个没有真实 managed consumer 的 execution 架构，`ARCHITECTURE_ACCEPTED`
的证明力存疑。

**建议（RA9）：** 完成定义增加下限："至少 N 个代表性迁移单元（建议 013_3
与 P1-B 中至少各一）完成 `managed_execution` 迁移并通过 L2 验收，
否则最终裁决不得为 `ARCHITECTURE_ACCEPTED`"。新增 AC41-64。
（gateway 侧已有类似下限：G6 要求一个 server + 至少两个 strategy client，
此条是把同样思路补到 managed 侧。）

## 4. 一致性与完整性发现（文档层）

### 4.1 【高】C1：迁移矩阵枚举不完整（实证）

矩阵自述"WP41-A 的机器可读 inventory 是最终权威"，但作为**需求文档**，矩阵当前版本

1. **P1-B 枚举 6/11。** `ctp_options_simnow_*` 实际 11 个文件，矩阵只列 6 个。

   （保留 examples / 迁入 SDK / 退役）没有工作包覆盖，恰好是最需要归责的一类。
   `common.py` 同理未枚举。
2. **NOT_APPLICABLE 清单以"等"字收尾。** 实测 examples 下 21 个目录中，
   002/003/006/011/016/017 六个目录未出现在矩阵任何位置。我逐一核验了写能力：
   002/003/006/011 无 provider 写标记，016/017 的 `live` 仅为 `order.alive()`——
   **NOT_APPLICABLE 的判断方向全部正确**，但"判断正确"与"枚举完整"是两回事：
   未来任何人新增 writer 时，无法回答"这个目录当初是谁判定不适用、依据是什么"。
   且 016/017 各有一个**已跟踪的 `config.yaml`**（参数文件），与交易员 P0-1 的
   11 文件处置清单直接相关，矩阵却只字未提。

**建议（RA7）：** 矩阵改为**完整枚举**：21 个目录 + 根目录散列文件逐一给出分类
（迁移批次 / NOT_APPLICABLE + 一句话依据）；`ctp_options_simnow_*` 按文件粒度
补全 approval_issuer、common 与两个 `.md`；消除所有"等"字。新增 AC41-63：
机器可读 inventory 与矩阵逐目录一致，每个目录恰好一个分类。

### 4.2 【高】C2：FR 无优先级标注，monitor 的 P1 与用户诉求优先级错位

WP 层有 P0/P1/P2，但 FR41-01～17 没有任何优先级/必要性标注。两个后果：

1. 技术经理 R1 的"砍范围"裁决（加人/拆分/砍范围三选一）发生时，**无法从需求层

   （独立监控）与第 2 条（账户级风控，WP41-C 为 P0）在用户原始诉求中**并列**。
   这个错位可能有充分理由（D 依赖 B 的 outbox），但**未经 owner 知情确认**
   就是隐性决策。

与 WP 优先级对齐；monitor 的 P1 排序写入裁决记录，由 owner 知情确认。

### 4.3 【中】C3：里程碑无质量门

### 4.4 【中】C4：迭代中止/回滚处置缺失

NO-GO 防止的是"错误发布"，但如果迭代在 WP41-E/G 阶段中止（按技术经理估算，

### 4.5 【低】C5：AC41-37 永久 BLOCKED 的复审机制

## 9. 结语

三份审阅看同一份计划，看到的是三个不同的它：交易员看到"堡垒缺厨房"，
技术经理看到"做不完、没限速"，而需求分析师看到的是——**这座堡垒的图纸上，
有 31 处已被指出的修改意见，却没有规定由谁、在什么时间、以什么形式
把这些意见画回图纸。**

这份计划最可贵的资产是它的安全纪律，而最脆弱的地方是它的需求管理：
初始需求 1 无法验收、两条评估类需求被结论替代、迁移矩阵有实证枚举缺口、
31 条修订意见悬置。这些问题在 `PLANNED` 阶段修复的成本接近于零——
它们全部是文档级工作；一旦进入实施，每一个都会变成跨仓返工。

建议顺序：先 RA1（任命 owner + 统一裁决表），再 RA2/RA3（基线 + 追溯矩阵），
然后在同一次裁决会上把四份审阅的修订项一次性裁完，冻结 baseline-1。
**这份计划值得被冻结——但应该先被管理起来，再被冻结。**

  "capability 不伪造"纪律同构，是把同一原则延伸到 AI 产物；
- **AD-AI-04**（AI 发起的部署只能进入 `managed_execution`）点出了计划的真实漏洞：
  计划 §0 规定"无 `config.yaml` 即合法 `legacy_direct`"，这对人类操作者是兼容性设计，
  但对 AI-produced strategy 是一条**可携带凭据的逃逸默认**——AI artifact 缺 config 时
  会静默落入有凭据的直连路径，现有 NO-GO 清单未覆盖该组合；
- **语义完整性门**（`semantics=review_required` 的 artifact 不得进入受管写入）与本审阅
  Q2 同构：评估/语义状态必须成为可验证 contract，而不是文档自述。

另有两条与本审阅直接呼应，建议合并执行：其"非 AI 专属问题"第 2 条（`D:/` 盘符路径
不得作为跨平台权威定位，改用 repo URL + logical path + pin + 本机 resolved checkout
四项）并入 RA11 假设登记；其"canonical route matrix 放计划首页"与 RA3 追溯矩阵、
RA10 里程碑质量门方向一致。

### 10.3 范围管理：WP41-I 使 R1 的估算进一步失真

AI 审阅新增 WP41-I（I1～I7）与三个新 Git 身份（agent/mcp/skills），核心 Git 身份从

### 10.5 状态词汇表不一致

四份审阅使用三套状态词：计划本身 `PLANNED / NO-GO`；交易员/技术经理/本审阅
`REVIEW / 建议修订`；AI 审阅 `REVIEWED / PLAN_AMENDMENT_RECOMMENDED /
NO-GO FOR AI-LIVE-INTEGRATION`。含义相近但不可机械比较、无法按状态过滤。
建议并入 RA2 的基线工作：为审阅文档定义统一的状态枚举。

### 10.6 小结

AI 审阅的内容方向（AI 作为不可信主体、三层凭证不可复用、AI 强制 managed route、
语义完整性门）**建议采纳**；但它同时是 F1/F2 的活样本：编号冲突、状态词漂移、
范围扩大而无人重算估算。四份审阅合计 60+ 条修订项、29 条建议验收条件、1 个新工作包
（WP41-I）——**统一裁决表、基线与编号命名空间（RA1/RA2/RA13）已从"建议"变成
"不做就无法安全并入任何一份审阅"的硬前提。**
