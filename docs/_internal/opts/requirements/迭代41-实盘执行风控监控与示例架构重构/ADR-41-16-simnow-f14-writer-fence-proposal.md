# ADR-41-16 (PROPOSED): SimNow F14 writer-fence boundary and waiver option

**Status:** `PROPOSED` — this is the sole F14 SimNow writer-fence decision ADR. Its option B is the only proposed bounded SimNow operational path; it is not implemented, registered, or a write authorization. The current Iteration 41 decision remains `SIMNOW_WRITE_NO_GO / PRODUCTION_LIVE_NO_GO`. The [two-level feasibility review](evidence/ctp-f14-two-level-acceptance-review-2026-09-25.md) is non-normative evidence, not another ADR.
**Date:** 2026-09-25
**Scope:** whether a narrowly bounded SimNow simulated order/cancel test can proceed when public CTP interfaces do not establish broker-side, account-wide cross-host writer exclusion or a coherent account snapshot.

## Decision recorded by this proposal

Keep the strict F14 gate in force. The current plan requires an independently verifiable account-wide writer fence and complete account-state evidence; neither a local lease nor operator confirmation satisfies that requirement. If the account owner later wants to accept a narrowly scoped operational-risk exception for a dedicated SimNow account, option B below requires a separately approved change to the plan and acceptance labels before implementation or use. This ADR does not make that change or select option B.

The alternatives are recorded so that a future decision has explicit boundaries:

| Option | Meaning | Status in this proposal |
| --- | --- | --- |
| A. Strict F14 gate | Require externally verifiable account-wide writer exclusion and a defensible complete/coherent account view. Keep SimNow writes and production live closed while either is missing. | **Current governing decision; retain.** |
| B. SimNow operational-attestation waiver | Consider one minimal simulated order/cancel exercise on a dedicated SimNow account under named owner/operator attestations, exclusive credential custody, one designated host/user, a local cooperating-process lease, exact native correlation, and conservative reconciliation. This is an operational control with residual risk, not a broker fence. | **Unapproved alternative only.** It cannot be enabled by this document or by code/config changes. Requires an explicit plan/AC change and named sign-off. |
| C. Credential-owning execution gateway | Consider a trusted gateway as the only credential holder and only network path capable of CTP writes; serialize and journal all actions there, and block direct clients at the credential/network boundary. | **Alternative for future design review.** It can address writer routing only if exclusivity is demonstrated; it does not by itself provide an atomic account snapshot. |

## Evidence and limits

The current [F14 feasibility record](evidence/ctp-accountwide-control-feasibility-2026-09-23.md) documents that the native query certificate binds individual query completions to a client, account, TradingDay and connection generation, but does not establish one shared snapshot version, full-account open-order coverage or exclusion of other clients. The local `CtpAccountFlowLease` in `backtrader_runtime/ctp_simulation_execution.py` coordinates cooperating processes using the same host, OS user and state root. The module itself says it does not fence another user, host or SDK process and requires an injected external account-wide fence. `ctp_simulation_query_evidence.py` also states that it does not provide a writer fence, atomic multi-query snapshot or durable cancel history after restart.

The published [SimNow CTPIIMini API v1.2](https://www.simnow.com.cn/DocumentDown/api_3/5_2_4/CTPIIMini_API_Ver1.2.pdf) and [SFIT CTP Mini API v1.7](https://www.simnow.com.cn/DocumentDown/api_3/5_2_4/SFIT%2BCTP%2BMini%2BAPI-V1.7.0.pdf) describe request-level submissions, queries and callbacks. In the inspected public manuals, no account lease, cross-host writer lock or common version for the separate order/trade/position queries was found. This is a bounded statement about those published interfaces, not proof that no broker-specific control service exists. Obtain and review such a service if the strict gate is to be satisfied.

The [official SimNow product page](https://www.simnow.com.cn/product.action) describes its 7x24 environment as an API test environment without clearing/settlement services. Therefore neither option B nor C may claim clearing, settlement, production readiness, or equivalence to a production account control.

## Option B: bounded SimNow operational-attestation test (not approved)

This option is a candidate for a separately authorized **simulation-only test**, not a way to report F14 as passed. Its risk claim is narrow: the named account owner attests that, for a declared test window, no other person or process will write to the dedicated SimNow account, and the runtime enforces one cooperating local writer. The attestation is procedural evidence. It does not technically exclude an undisclosed client and must not be represented as a broker-issued or cross-host fence.

If separately approved, all of the following are prerequisites:

1. **Explicit change control.** The account owner, execution maintainer, risk owner and independent QA approve a written waiver with account scope, test window, residual-risk statement, expiry and revocation procedure. The plan and ACs are amended first. The result is labeled `SIMNOW_OPERATIONAL_ATTESTATION_TESTED` (or another reviewed label), never `F14_PASS` or `ACCOUNT_WIDE_FENCE_VERIFIED`.
2. **Dedicated account and custody.** The account is reserved for this test; the named owner confirms no other CTP API client, terminal, manual operator, scheduled job or remote host will use it during the window. Credentials remain in the approved protected source and are held only by the designated host/operator. No secret values go into the ADR, receipt or evidence bundle. Any uncertainty or withdrawal ends the test and freezes new writes.
3. **One local writer.** Use one designated host and OS user, a local supported filesystem and the account-keyed `CtpAccountFlowLease` continuously from before native client construction through worker drain, native close and journal close. A second cooperating process must fail before client construction. This only covers participants that honor the same local lock; it cannot prove cross-host, other-user or external-client exclusion.
4. **Exact, short-lived admission.** Keep the runtime on the registered `simulation/sandbox` scope and exact sealed account/front/contract identity. Require the reviewed artifact and native SDK pins, trusted one-use approval, bounded expiry, one instrument, one contractually valid lot, one non-marketable limit order and one exact cancel target. Enforce a pre-approved maximum notional/exposure and a maximum of one live test order. No config edit, route flag or operator attestation may add code capability.
5. **Readiness and baseline.** Require exact TD/MD identity, matching TradingDay and connection generation, successful required subscription/tick evidence where applicable, and current-account/TradingDay settlement-confirmation query evidence before writing. Query funds, orders, trades and all positions to terminal native callbacks before the test; bind each response to its exact request and account/session. Run a second quiet baseline pass, explain ordinary changing fields, and reject any unexplained exposure, unrelated open order, missing callback, unknown coverage, or identity mismatch. Repeated reads are only an `UNVERSIONED_QUIESCENCE_CHECK`; they are not an atomic snapshot certificate. If the configured front lacks settlement service, including the official 7×24 API-test environment, stop at zero writes; the operator may edit the same protected `config.yaml` and repeat every applicable gate, without time/set-based fallback.
6. **Correlated insert and cancel.** Persist the intent, unique OrderRef mapping, approval consumption and command claim before dispatch in the single reviewed authority. A native return code of zero means only local `QUEUED`. Require the exact insert response/order callback before targeting the order. Cancel only by the verified native target tuple; a cancel response or queue result is not a canceled order. Require the exact terminal order state and reconcile all trade and position changes against the same intent. If any fill occurs, account for its exact quantity and resulting position before closing the test; do not assume the test order remained unfilled.
7. **Fail closed.** Any timeout, callback/request mismatch, lease loss, session/day/generation change, foreign order, differing query results, uncertain close, or `UNKNOWN` freezes further insert/cancel dispatch. Never automatically retry an action with unknown dispatch outcome. Do not use cancel-all or a second client as a recovery path. Recovery requires independently reviewed exact reconciliation and a new explicit approval.
8. **Evidence and stop condition.** Preserve redacted native callback/query provenance, ledger transitions, order/trade/position reconciliation, approval and artifact/config digests, local-lock owner identity, test window, and named operator/QA sign-off. Do not store credentials or raw private config. An unresolved order, callback or close prevents a clean completion receipt and prevents any later writer from starting. Start with a cancelable-remainder insert→native order confirmation→exact cancel→terminal order/readback use case. A fully filled order cannot count as a successful cancel. Treat a positive fill as a separate later use case, only after a reviewed closing/flattening path exists; the current managed request contract permits `OPEN` only and cannot safely close a test fill by itself. Crash-cut and forced-termination recovery remain mandatory offline fault tests, but a real forced crash with an unresolved account order is not a prerequisite for this minimal provider exercise.

Credential rotation/revocation where supported, a dedicated VM, application control, and full egress/host-flow audit strengthen option B evidence. They are not public CTP API primitives and are not automatic prerequisites for a bounded SimNow exercise. A dedicated account, one declared host/operator window, no **known** parallel writer, and explicit risk-owner acceptance of the unproven cross-host/manual-writer exclusion remain required. If the owner knows another client is writing, stop; if external exclusion cannot be technically proved, record it as residual risk instead of setting `account_writer_exclusive=true`. Production never inherits this exception.

Even if every item passes, the claim is limited to the attested test window and the exact SimNow account. It does not prove a common atomic account snapshot; a query sequence can race with an unobserved writer. If the account cannot be kept operationally quiescent or a complete baseline cannot be defended, option B is unsuitable and strict NO_GO remains.

## Option C: trusted credential-owning gateway (alternative)

A gateway could provide a stronger customer-controlled writer boundary if it is the sole holder of usable CTP credentials, all application actions pass through one durable serialized command authority, and network/OS policy prevents every other host, user, terminal or process from reaching the CTP write interface with those credentials. Its lease generation must cover approval, command claim, native dispatch, callback capture, drain and restart recovery. Break-glass access must revoke/fence the gateway generation before any manual client is allowed to connect.

Acceptance must independently prove credential custody, complete egress coverage, no alternate credential or terminal path, competing-client rejection, gateway crash/restart fencing, durable no-resend behavior for unknown dispatch, and auditability. A gateway that merely proxies calls while another client can use the same account does not establish exclusivity. Nor does a gateway create a common snapshot across CTP query streams. Option C satisfies the writer-fence part only if the deployment evidence proves the boundary; complete account-state coverage remains a separate gate. Until those controls and tests exist, the gateway is only a design alternative and writes remain NO_GO.

## Production boundary

Production does not inherit option B, its operator attestation, SimNow account history, test receipt, artifact approval or risk limits. Production must use the same registered CTP runner and execution implementation under a separately admitted live mode/preset. It still requires separately accepted production artifact, account identity, credential custody, broker/account-level writer control (or a reviewed gateway that truly excludes every other writer), complete account-state/reconciliation contract, trusted approval and expiry/revocation, risk/monitor gates, incident procedure and production-specific QA; do not create a separate production runner or writer. The shared protected `config.yaml` and canonical `ctp:` fields are configuration shape only; switching mode/preset or replacing account/front/contract fields grants no execution authority.

## Executable acceptance and decision gates

| Gate | Required evidence | Failure disposition |
| --- | --- | --- |
| Current strict gate | Broker/clearing-side or independently reviewed equivalent fence is bound to exact account and validity window; proves all writer paths are excluded. Query contract demonstrates full account coverage and a coherent point-in-time view or a separately approved equivalent. Independent QA exercises expiry, revoke, competing host/client, query mutation, disconnect and restart. | Keep `SIMNOW_WRITE_NO_GO / PRODUCTION_LIVE_NO_GO`; no native write. |
| Option B waiver approval | Signed account-owner/operator statement plus execution, risk and QA approvals; dedicated account, custody, host/user, test window, limits, revocation and residual risk specified; plan/AC and receipt label updated before route implementation. | Waiver remains unavailable; strict NO_GO unchanged. |
| Option B offline implementation | Fake tests cover second local process rejection, every dispatch/callback/query failure, unknown no-retry, exact target cancel, fill reconciliation, forced termination/lease poisoning and zero native calls before all gates. Static route audit proves no CLI/default registration or production fallback. | Reject implementation; no provider test. |
| Option B supervised SimNow test | Re-run all prerequisites and signed operator attestations immediately before the declared window; one approved one-lot non-marketable insert and exact cancel; correlated native callbacks; terminal order and trade/position reconciliation; clean shutdown; zero unexplained state; redacted independent QA receipt. Count every native insert/cancel and settlement call. | Any ambiguity freezes the account. No further writer starts until exact independent reconciliation. No retries. |
| Option C gateway | Prove sole credential custody and network reachability boundary, durable serialization and single state authority; run cross-host, direct-client, gateway crash, lost callback, revoke and recovery adversarial tests; separately satisfy complete account-state gate. | Gateway is not an accepted fence; strict NO_GO unchanged. |
| Production | Separate production artifact/account/session and risk acceptance; independently demonstrate the production fence and complete state contract; no dependency on SimNow waiver receipts. | Live route remains unavailable and `LIVE_NO_GO`. |

For all options, reject any claim that a local file lock proves cross-host exclusivity, that repeated query responses establish atomicity, that `bIsLast` alone proves full account coverage, that a native immediate return/queue receipt is an exchange acknowledgement, or that the official 7x24 SimNow environment provides clearing/settlement. `UNKNOWN` is not success and must not be retried automatically.
