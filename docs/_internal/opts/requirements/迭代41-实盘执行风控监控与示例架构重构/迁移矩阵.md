# 迭代 41：可写 Examples 迁移矩阵

状态：`PLANNED`。本矩阵以“能够直接或经配置发起 provider 下单、撤单、改单、平仓，或作为真实写入
认证运行器”为范围，而不是只按目录名称是否包含 `live` 判断。WP41-A 的机器可读 inventory 是最终
权威：任何未出现在本表但扫描到的可写入口必须先加入 inventory，再决定迁移或禁用。

## 1. 共同行为要求

每个迁移单元必须同时选择并记录两个互不替代的维度：

- `runtime.order_route`：订单语义是保留既有的 `legacy_direct`，还是使用 `managed_execution`；
- `runtime.account_access`：策略进程直接持有 provider 接入（`direct_provider`），还是作为共享账户网关的
  `gateway_client`。

网关是账户连接、订阅汇聚、状态/命令路由的拓扑能力，不是 execution 准入、风险许可或第二套 OMS；因此接入
网关不会把 direct 路径自动变成 managed execution。目标组合如下（均为迭代 41 的合同，不表示现有 example
已实现）：

| `order_route` | `account_access` | 进入条件 | 写入行为与可作出的声明 |
| --- | --- | --- | --- |
| `legacy_direct` | `direct_provider` | 无 `config.yaml` 的默认，或本地 schema-v3 config 明确选择该组合且未启用 execution。 | Strategy 保留现有 Backtrader Broker/Store 到 provider 的调用。无 config/no plugins/all-disabled 且均 `required:false` 时不启动 runtime plugins；启用的 risk/monitor 仍须分别实际 hard-gate 写入、经 Broker control gate 执行 freeze/drain。它不获得 aggregation、journal 或 managed 准入。 |
| `legacy_direct` | `gateway_client` | canonical config 明确选择，且 `plugins.gateway` 与 `plugins.transport_zmq` 成对启用。 | Strategy 通过 gateway client 使用共享账户连接和路由，但订单仍是 legacy direct 语义；不得声称 execution plan、allocation、journal 或 managed 准入。策略 config 不得含 provider 凭据。 |
| `managed_execution` | `direct_provider` | canonical config 明确选择 `managed_execution`，并启用 execution。 | 只通过 `bt_api_py` 已锁定的 integration adapter 调用 `bt_api_execution` 提交 intent/plan；provider port 由本地 integration 持有。适用 execution capability/preflight 及所选可选插件合同。 |
| `managed_execution` | `gateway_client` | canonical config 明确选择，启用 execution，并启用 gateway 与 transport_zmq。 | intent/plan 仍由 execution boundary 决定；gateway 只提供共享账户的会话、路由与状态通道。若宣称账户级强制 risk/execution 准入，该授权必须在 gateway/provider 写入边界服务端执行，不能仅依赖策略客户端。 |

具体要求如下：

> 当前目标配置为 **schema-v3**。历史 schema-v2 的 `plugins.zmq` 不是兼容别名：迁移时必须把
> `plugins.zmq.config.role` 显式映射为 `plugins.gateway.config.role`，把 endpoint/security 等传输字段显式映射为
> `plugins.transport_zmq.config`，随后重新 preflight 并重启。v2 配置必须被明确拒绝，不能猜测或静默迁移。
> 完整规则见[插件、网关与传输架构](插件与ZMQ架构.md)。

1. 每个 writer、cancel/close 路径、test 子进程和 operator runner 都在 inventory/README 中标明 `order_route`、
   `account_access`、owner、当前状态和选择方式。既有 direct writer 是合法 `legacy_direct`，不是自动旁路错误；但
   managed 的 config/schema/package/preflight 失败绝不能自动回退 direct，也不得将 direct 写成 managed/已准入；
2. 只有无 config/no plugins/all-disabled 且全为 `required:false` 的 `legacy_direct + direct_provider` 进程跳过
   plugin 校验。存在 config 的 runtime 都只从其运行目录读取 canonical `config.yaml`，并严格验证
   `config_schema_version: 3`、`strategy.id`、`runtime.{order_route,account_access}`、
   `plugins.{execution,risk,monitor,gateway,transport_zmq}.{enabled,required,config}`、路径 containment 和**实际
   enabled plugin**的 package/pin/schema/attach/profile/capability preflight。`gateway_client` 必须成对启用 gateway
   与当前唯一已规划 transport_zmq；`direct_provider` 禁止这两个插件；`transport_zmq` 不得单独启用。策略 client
   只能声明 `strategy_client` 角色且不得含 provider 凭据，gateway server 使用独立受管部署配置。direct+enabled
   risk/monitor 必须 attach 到真实 write/control gate；managed 另必须启用 execution。若 config/route/access/
   required/plugin 无效则零 I/O 拒绝，不得静默改走 direct；
3. 每个支持 plugin 配置的目录提交无 secret、默认五项 plugin `enabled=false, required=false` 的
   `config.example.yaml`，并用 `.gitignore` 忽略同目录本地 `config.yaml`。操作者复制模板后可选择 route、
   account access 和插件；`direct_provider` 的本地 config 可保存 provider 凭据，`gateway_client` 的策略 config
   不可保存它们。gateway server 的凭据、ACL 与 provider 配置由独立部署配置管理，不能下沉到 example YAML；模板
   不是运行时 fallback。若 schema 允许 runtime-local artifact 路径，必须相对该目录并通过 realpath containment；
   managed 账户级 journal/risk ledger/writer lease 不能由 example YAML 指定；loader、日志、receipt 和 scanner
   必须脱敏本地 config，同时扫描模板、git index 与所有输出，阻止凭据泄露；
4. `managed_execution` 保留策略专属信号和经济约束，但账户级额度、writer lease、journal、unknown/recovery、日界
   与进程健康移交公共层。`legacy_direct` 保留现有 Broker/Store 语义及 provider 原生认证/协议要求；使用
   `gateway_client` 只改变连接/路由拓扑，不因此获得上述公共层保障；
5. 每个写入型 test 使用隔离账户/合约范围、清理和最终对账。managed test 使用受限 `TestExecutionProfile`；
   direct test 必须显式标为 `legacy_direct` 并验证其 native provider 或 gateway-client 前提，不能借 test 身份
   伪装为 managed；
6. README 写明策略逻辑、参数、两种订单路由和两种账户接入的模式/启动方式、managed 与 direct 的保障差异、
   deployment profile、启动/停止/冻结/恢复、输出证据和不能得出的结论；
7. `simnow`/`production` 的 `managed_execution` 写入只能由已显式启用的 execution 经统一 boundary 发起。risk 与
   monitor 可以按合同独立启用或关闭；gateway client 则必须使用 gateway+transport_zmq 成对组合，二者不能单独
   启动：`required:true` 必须同时 enabled；direct+enabled risk 必须 veto native writer，direct+enabled monitor
   必须经 Broker control gate freeze/drain；gateway/transport 本身不能授权写入。direct 的 risk/monitor 不生成
   execution `RiskPermit`、journal、allocation 或 managed receipt/准入声明；gateway client 的客户端 risk/monitor
   也不能声称账户级权威。已启用 plugins 通过自身的 schema/pin/profile/capability/preflight 校验；本地被忽略的
   `config.yaml` 仅在 direct_provider 场景可以含 provider 凭据，但模板、git index、日志、receipt、metrics 与
   异常输出不得含 secret。

examples 只依赖 Backtrader 与 SDK public facade；`bt_api_execution`、`bt_api_risk`、`bt_api_monitor`、
`bt_api_gateway` 与 `bt_api_transport_zmq` 五个可选能力包的具体安装、版本、pin 和组合由 deployment profile
与 `bt_api_py` integration 管理。example 不得 vendor contracts、直连能力包的私有对象，或以存在本地 checkout
作为可写模式前提。`bt_api_gateway` 是已创建但尚未接入的独立仓库；`bt_api_transport_zmq` 是近期实现目标，
不能被本矩阵表述为已交付能力。`bt_api_transport_nats` 与 `bt_api_transport_redis` 只保留为未来候选；在各自
独立通过 transport port、认证/ACL、重连/序列缺口和 fan-out 合同前，不能作为本迭代的可选配置或迁移出口。

## 4. 单例迁移检查表

| Scope/profile | 配置存在时，运行目录 `config.yaml` 有 schema-v3、strategy identity、`runtime.{order_route,account_access}`、五项 `plugins.*.enabled/required/config`、resolved descriptor/distribution/pin/schema、attach result 和 redacted configuration fingerprint。无 config 只允许 `legacy_direct + direct_provider`，但仍必须记录 route/access 和 provider 原生认证/协议前提；gateway client 必须有 config。 |
| Configuration composition | 提交的 `config.example.yaml` 默认五项 all-disabled、`required:false` 且无 secret；本地 `config.yaml` 被忽略。无 config 是合法 `legacy_direct + direct_provider`，不加载模板或 plugins。存在 config 时，所有 enabled plugins 经严格 schema、组合规则和 runtime-local path containment 校验，`required:true && enabled:false` 拒绝；`gateway_client` 必须启用 gateway+transport_zmq，`direct_provider` 禁止二者，transport 不能单独启用。策略 gateway client 不得保存 provider 凭据，gateway server 使用独立部署配置；`simnow`/`production` 的 managed 写入仅 execution 能请求 provider。direct+enabled risk/monitor 分别真实 gate/control，但不伪造 execution journal/permit。认证账户的 managed journal/risk ledger/writer lease 不得按 strategy config 分裂；配置变更必须形成新 scope/preflight。 |
| Attribution | managed 的每个 framework order/strategy intent 与 plan/child/fill allocation 可双向查询；direct 的 native 或 gateway-routed order 必须可按 route/access、`strategy_id` 与 `client_order_id` 归责，但不得伪装为 plan/allocation，也不得允许跨策略伪造归属。 |

## 5. README 最小内容合同

每份已迁移 example 的 README 必须有下列小节，不能仅复制通用部署说明：

1. 策略目的、信号/持仓/退出逻辑和不适用市场；
2. 参数表，区分 signal 参数、无 config 的 `legacy_direct + direct_provider` 行为、`config.yaml`/`config.example.yaml` 的 schema/version、`runtime.{order_route,account_access}`、每个 plugin 的 enabled/required/config、execution/risk/monitor/gateway/transport_zmq 参数，以及默认关闭和允许组合；
