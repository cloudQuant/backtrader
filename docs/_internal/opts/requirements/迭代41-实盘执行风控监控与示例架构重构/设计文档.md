# 迭代 41 设计文档

状态：`PLANNED`。本设计只定义模块边界与验收合同；具体 API 名称、存储后端和发布版本必须在
WP41-A 的 ADR 中冻结后才可实现。

> **架构修订（2026-09-21）：** schema-v3 的权威配置根是 `plugins`；`runtime.order_route` 与
> `runtime.account_access` 分别表达执行路由和账户接入拓扑。direct+enabled risk/monitor 必须是真实
> hard-gate/control，不是 advisory/telemetry。旧 `modules`、schema-v2 `plugins.zmq` 输入一律拒绝；以
> [插件、网关与传输架构](插件与ZMQ架构.md)及 D41-13～17 为准。

## 1. 目标架构

```text
legacy_direct + direct_provider
    Backtrader Strategy → BtApiBroker/BtApiStore → bt_api_py/provider → provider
                                    ├─ optional enabled risk: real write gate
                                    └─ optional enabled monitor: Broker control gate
    (no config / all capabilities disabled and required:false is the zero-plugin subset)

gateway_client (one shared account gateway)
    Strategy A/B/C → Broker/Store → bt_api_py integration → bt_api_gateway client
                                                              │
                                                        transport_zmq
                                                              ⇅
                                                   bt_api_gateway server
                                                              │ one provider session and
                                                              │ one market subscription union
                                                              ▼
                                                          provider

managed_execution is orthogonal to account access
    Broker adapter → bt_api_execution → provider dispatch port
                         ├─ optional RiskGate/RiskPermit
                         ├─ durable journal + outbox
                         └─ immutable event → bt_api_monitor
```

`TradeLogger` 位于左侧，是 Backtrader adapter 可选的 telemetry source；它不得成为 durable journal、
风险许可权威、远端对账来源或 monitor 的唯一输入。

五个能力包是 `bt_api_execution`（初始仓为空）、`bt_api_risk`、`bt_api_monitor`、
[`bt_api_gateway`](https://github.com/cloudQuant/bt_api_gateway)（已创建但尚未 package/submodule）与近期拟建的
`bt_api_transport_zmq`。它们保留各自的 Python distribution 和版本；`bt_api_py` superproject 维护 pin，并用明确的
optional dependency 与 integration adapter 组装运行时。它们不是 `bt_api_py` 的 Python 子包、vendor copy 或 provider
子仓的替代品；NATS/Redis adapter 不属于当前交付。

## 3. 公共 contracts

下列模型是**受管执行路径**的 contracts，必须不可变、版本化、canonical-serializable，且默认不含凭据、
原始账户 ID、capability secret 或 provider 私有对象。既有 direct 路径继续使用其当前 provider/SDK 对象和
协议，不假装产生这些模型、permit 或 journal：

| 模型 | 最少字段/语义 |
| --- | --- |
| `ExecutionScope` | provider、environment、account fingerprint、strategy/candidate、instrument canonical identity、TradingDay 或 rolling epoch、connection generation、policy/config/code hash。 |
| `ExecutionIntent` | intent ID、strategy attribution、scope、side、position effect、quantity/unit、price/TIF、deadline、reduce-only、idempotency key、risk tags。 |
| `RiskDecision` | `allowed`、原因码、policy hash、投影风险、拒绝/告警信息；不能单独授权 I/O。 |
| `RiskPermit` / `RiskReservation` | 一次性/受限 capability，绑定 scope、permit ID、额度、child/action 限制、issued/expiry、fencing/version 与撤销状态。 |
| `ExecutionPlan` / `ParentExecution` | 聚合规则、atomicity level、所有源 intent、目标净额、execution policy、routing policy、状态和 plan hash。 |
| `ChildIntent` | parent ID、child ID、provider capability、client ID、具体写入动作、deadline、状态、幂等键和 reconciliation identity。 |
| `FillAllocation` | child fill 到每个 source intent/framework order 的数量、价格、费用、funding、舍入 remainder 和分配版本。 |
| `ExecutionEvent` | journal/outbox sequence、scope、entity、状态迁移、时间、脱敏错误码、相关 hash。 |
| `LifecycleCheckpoint` | session/epoch、MD/TD 健康、account snapshot freshness、reconcile 状态、risk 状态、writer lease、heartbeat、stop-latch。 |
| `ControlCommand` | `freeze_new_entries`、`drain`、`manual_intervention`；带 scope、原因、签名/授权、TTL、序列和审计 ID。 |
| `ProviderCapabilityReceipt` | provider/version/environment、native OCO/batch/slice/basket/recovery 等声明、约束、证据 hash、有效期。 |

`bt_api_execution` 发布 contracts 的兼容版本；`bt_api_risk` 和 `bt_api_monitor` 只能声明并测试其兼容
范围，不能 import execution 的 provider adapter 或反向要求 execution import 自身。`bt_api_py` 的 managed
integration adapter 是受管路径的 concrete composition root：它按锁定版本加载 execution、注入可选 risk gate、
向可选 monitor 暴露 outbox/checkpoint reader，并绑定现有 provider adapter。它不取代 `BtApiBroker/BtApiStore`
已有的 direct provider 调用链。

### 3.1 策略运行目录 `config.yaml` 合同

本节定义计划中的 schema-v3 装配规则，**不是创建任何 example 的实际配置文件**。唯一权威的细节和模板位于
[插件、网关与传输架构](插件与ZMQ架构.md)及[模板](templates/config.example.yaml)：

1. `<strategy-runtime-dir>/config.yaml` **不存在**、没有 `plugins`，或全部插件 disabled 且均为 `required: false` 时，
   runner 保留既有 `legacy_direct + direct_provider` 链路；不导入五个运行时 capability、不创建 execution
   journal，也不运行 plugin composition 校验。
2. 文件存在时，runner 对规范化的 `<dir>/config.yaml` 执行 schema-v3 校验；若 `runtime.order_route=legacy_direct`，
   execution 必须 disabled。risk/monitor 可独立启用，并在 attach 成功后分别在 provider write / Broker control
   boundary 作真实 hard-gate、freeze/drain。`account_access=gateway_client` 必须启用 gateway+transport_zmq；它们
   改变账户接入拓扑，不能授予写权限。
3. `runtime.order_route=managed_execution` 必须同时启用 execution。任何 enabled plugin 的 descriptor、pin/version、
   schema、构造、attach 或 preflight 失败都在 provider I/O 前失败，且不得暗中落回 direct。`required: true` 同时
   `enabled: false` 也是配置错误。

选择第 2 或第 3 项时，runner 接受明确的 strategy runtime directory（例如 `--strategy-dir <dir>`），对路径做
realpath/canonicalization 后仅加载 `<dir>/config.yaml`。同一目录必须提交无秘密的 `config.example.yaml`；迁移工作
须用项目 `.gitignore` 忽略实际 `config.yaml`，而不忽略 template。plugin loader 绝不读取 template 作为实际配置，
也不允许 `--config`、CWD、父目录搜索或自动发现改变这条规则。YAML `!include`、任意环境变量插值、任意 Python
object/class/import 与未锁定的外部文件/URL 均不支持。`strategy.id` 必须与 WP41-A inventory 中的 runtime identity
一致。显式给出的 plugin 配置若格式无效，必须拒绝该配置化启动，不能把“risk/monitor 已启用”的错误配置静默当作
直连成功。

如 schema 将来允许 runtime-local artifact（例如脱敏 report、checkpoint 或 operator evidence）指定目录，
它必须是相对 `<strategy-runtime-dir>` 的路径，经过 resolve/realpath 后仍位于该目录内；绝对路径、`..`、符号
链接逃逸和任意共享路径一律拒绝。execution journal、risk ledger、writer lease 的**账户级权威位置**反而不能由
该 YAML 指定：SDK 必须在认证得到 account fingerprint 后派生共享、加锁的 account scope，防止两个策略目录
各自建立计数器而绕过账户总额度。

目标 schema 至少有下列字段类别；字段名、枚举和版本迁移在本设计中作为建议 contract，最终由 WP41-A ADR 与
版本化 schema vectors 冻结：

| 字段类别 | 规则 |
| --- | --- |
| `config_schema_version: 3`、`strategy.id`、`runtime.mode` | 配置文件存在时严格验证。mode 只能是冻结的 replay/shadow/test/simnow/production 枚举；不得由环境变量覆盖。没有 `config.yaml` 的 direct 路径沿用其已有的启动/模式语义。 |
| `runtime.order_route` / `runtime.account_access` | 配置文件存在时必填：route 为 `legacy_direct` 或 `managed_execution`，access 为 `direct_provider` 或 `gateway_client`。无文件时隐式为 `legacy_direct + direct_provider`。execution 与 managed 成对；gateway client 与 gateway+transport_zmq 成对；不能由 CLI、环境变量或凭据源改写。 |
| `plugins.{execution,risk,monitor,gateway,transport_zmq}` | 每项结构固定为 `enabled`、`required`、`config`。默认 `enabled:false, required:false`；`required:true && enabled:false` 拒绝。enabled 后才解析该 capability config / import factory；即使 `required:false`，enabled capability 任一校验或 attach 失败仍 fail-closed。 |
| `plugins.execution` | 仅能与 `managed_execution` 配对，提供 aggregation/journal/recovery/final dispatch；其 disabled 不阻止 direct。 |
| `plugins.risk` | direct 和 managed 均可启用；必须在真实 pre-submit/pre-cancel boundary 作允许/拒绝。managed 另提供 durable reservation/permit/settlement；direct 不伪造这些 execution 事实。 |
| `plugins.monitor` | direct 和 managed 均可启用；消费各自事件源并仅经 Broker control gate 实施 freeze/drain/manual intervention。不得普通开仓或自动 resume。 |
| `plugins.gateway` | 选择中间件无关的 shared account gateway core；strategy config 只能是 `strategy_client`，不能起 gateway server 或自行授权账户。 |
| `plugins.transport_zmq` | 首个 GatewayTransport adapter；仅在 gateway client 启用时允许，负责 endpoint/security/framing，不拥有 provider client 或账户真相。 |
| `connection.provider_profile`、`connection.credentials` | 受管 profile 是 allowlist 的逻辑标识。`credentials` 可以是被选 profile 严格定义的本地 inline 字段，也可以是 `.env`、OS secret store 或等价 secret provider 的结构化引用；不得是任意对象、import、URL/path 或未声明字段。凭据只能在被 Git 忽略的本地 provider/gateway-server config 中出现，绝不能出现在 template、日志或证据中。gateway client config 只能保存 endpoint/profile 引用，不能保存 provider credential。 |
| runtime-local artifact | 仅在 schema 明确允许时使用相对路径，并必须 realpath containment 在策略运行目录内；它不得指定账户级 execution/risk journal、ledger 或 writer lease。 |

每个策略目录提交的唯一模板是 [templates/config.example.yaml](templates/config.example.yaml)。它使用
`config_schema_version: 3` 和默认 all-disabled 的 `plugins`；不得在 README 或 example 中复制、修改为旧 `modules`
或 v2 `plugins.zmq` 层级。复制为策略侧 `config.yaml` 后可把 `REPLACE_*` 占位符换成本地 direct-provider
凭据；gateway server 的 provider 凭据属于独立受管部署配置，不能放进 strategy client config。仅将 `enabled`
改为 `true` 不构成交易授权。

禁用 plugin 可省略或保留 inert `config`；它不得携带会触发 I/O、自动 resume 或放宽账户级限制的 active-only
字段。`config.example.yaml` 中的 `REPLACE_*` 必须被 template scanner 识别为占位符；任何真实 credential、完整账户
ID、token、DSN、capability 或恢复 token 都令 CI/secret scan 失败。实际 `config.yaml` 可以包含 provider schema
允许的 inline credentials，但 loader 必须立即隔离，之后只使用认证后派生的 account fingerprint。

`config.yaml` 缺失不是错误，而是 direct route。配置存在时，loader 拒绝不支持的 schema version、未知/重复 key、
错误类型、无效单位/范围、runtime-local path 的绝对/上跳/符号链接逃逸、route/execution/account-access 不匹配、
`required:true && enabled:false`、disabled plugin 的 active-only 参数和不兼容的 profile/capability/pin；只有结构和
组合校验后才能解析实际 credential source。任何 enabled direct risk/monitor 的 schema 或 attach 失败也必须失败关闭，
不能把错误配置伪装成“插件未启用”。secret 绝不能进入 exception、metric、receipt、report 或日志。启用插件的
descriptor/pin/schema、attach result、实际 gate/control/transport state 与 canonical redacted config fingerprint 必须进入
receipt/evidence。影响写入的配置变化必须 `freeze → drain/stop → 新 preflight → restart`，不能热加载沿用旧 scope。

插件组合是可选能力，不是“所有实盘下单必须安装五个包”的限制；但有配置的 direct 路径也必须验证它实际启用的
plugins。它仍不能绕过 provider 原生认证、会话、协议或交易所/venue 规则：

| route / account access | execution | risk / monitor | gateway / transport | 实际路径、能力与缺口 |
| --- | --- | --- | --- | --- |
| 无 config、无 plugins 或 all-disabled 且均 `required:false` | off | off | off | `legacy_direct + direct_provider`；不导入 capability，不形成 execution journal。 |
| `legacy_direct + direct_provider` | off | off | off | 保留既有 provider path。 |
| `legacy_direct + direct_provider` | off | risk and/or monitor on | off | risk 在 provider I/O 前真实允许/拒绝；monitor 经 Broker control gate freeze/drain；不声称 execution permit/journal/recovery。 |
| `legacy_direct + gateway_client` | off | risk/monitor 可选 | gateway + transport_zmq on | 保留 direct execution 语义，但命令/事件经已部署 shared account gateway；gateway server 独立写入授权，client 不携带 provider credential。 |
| `managed_execution + direct_provider` | on | risk/monitor 各可选 | off | execution 负责 intent/plan/journal/recovery；risk/monitor 的实际 enabled state 决定相应 gate/control。 |
| `managed_execution + gateway_client` | on | risk/monitor 各可选 | gateway + transport_zmq on | execution route 与共享账户拓扑叠加；gateway server 的 provider write 再经过所需 risk/execution admission。 |

execution/risk/monitor/gateway 是可独立选择的能力，transport_zmq 是 gateway 的成对实现：execution 提供受管耐久
写入口/恢复，risk 提供真实写前决策，monitor 提供健康/告警/受限控制，gateway 提供共享账户路由。最高保障组合
可以同时启用，但不是 direct 写入的前提。任何 managed provider 写入仍须单独通过
execution package/pin、provider capability receipt、身份、账户、日历/时段、研究/审批和 provider-specific preflight；
plugin 组合或 credentials 本身不签发权限。`replay`/`shadow` 无论选择哪条路径，仍遵循各 runner 的零写合同。
`simnow` / `production` 的 direct 路径仍须 provider 原生认证、连接/会话与协议；direct+enabled risk/monitor 只声明
其实际 gate/control，不虚报 execution journal/aggregation/recovery。

`.env`、OS secret store 或等价 secret provider 是 inline credentials 的可选替代；只能在 core/plugin schema 校验成功后
按 `connection.provider_profile` 解析，且不能覆盖 YAML 的 `order_route`、`account_access`、`plugins.*.enabled`、mode、profile 或风险上限。
risk/monitor 均不是 provider writer、普通开仓者或自动恢复授权者。

## 4. 状态与事务规则

### 4.1 受管 Child 写入状态机

```text
DRAFT
  → RISK_RESERVED
  → JOURNALED
  → DISPATCHING
  → ACKED / PARTIALLY_FILLED / FILLED / REJECTED
  → CANCEL_REQUESTED / CANCELLED
  → UNKNOWN → RECONCILING → TERMINAL
```

本状态机只适用于 `runtime.order_route=managed_execution`。每次状态迁移必须有 journal event。任何发送后的
timeout、连接断开、回执丢失或进程崩溃均为 `UNKNOWN`，不能“再发一次看看”。只有远端查询、私有流或有证据的
本地 reservation-only 恢复可将其推进为终态。既有 direct 路径继续按当前 provider/SDK 的订单状态和恢复语义
处理，不得伪造 `ChildIntent`/journal 覆盖它。

### 4.2 受管风险 reservation 规则

1. `RiskDecision` 不是 `bool`；只有持久化成功的 `RiskPermit` 可进入 child dispatch。
2. 额度按普通开仓、普通撤单、replace、紧急减仓/保护撤单分别记账；replace 必须声明是一个逻辑
   行为还是 provider 的 cancel + new 两次写入。
3. 在确认未发生 provider I/O 前可释放 reservation；一旦结果不确定，不退款、冻结新开仓并等待对账。
4. 风险 scope 同时包含账户级硬上限和策略/候选分配；净额化不能使任何原始 gross intent 绕过限制。
5. risk ledger 与 execution journal 必须由同一事务性存储/同一 writer lease 协调；不得维护两份独立的
   “成功计数器”。

以上 durable reservation 规则只在 managed route 且 `plugins.risk.enabled=true` 时适用。direct+enabled risk 仍须
在 `BtApiBroker/BtApiStore` 的 provider I/O 前作真实允许/拒绝，但它不伪造 `RiskPermit`、execution journal 或
managed reconciliation；risk plugin 故障同样 fail-closed。

### 4.3 聚合与 atomicity

v1 只允许下列字段全部兼容时合并：provider、environment、account、instrument、position mode、side、
position effect、reduce-only、TIF、价格/滑点约束、deadline、lifecycle profile 和 risk scope。否则保持
独立 plan 或明确拒绝。

每个 plan 必须标记下列之一：

| 标记 | 允许含义 |
| --- | --- |
| `native_atomic` | provider capability 和实际回执均证明原子语义。 |
| `native_algo` | provider 接受一个具备独立查询/取消/恢复语义的 algo child；仍不是跨 provider 原子性。 |
| `sequential_non_atomic` | 多个 child 依次发送，必须有部分成交、补偿与 UNKNOWN 方案。 |
| `basket_best_effort` | 多腿计划；必须显式披露非原子，并要求每腿可恢复。 |

没有 capability receipt 时，`parent`、`oco`、`transmit`、batch、slice 和 basket 一律拒绝；不得静默拆成
普通订单后宣称同等保护。

## 5. 打包与依赖方向

```text
bt_api_base                          shared typed contracts; no transport dependency
       ▲
bt_api_gateway                       middleware-neutral shared-account core
       ▲
bt_api_transport_zmq                 first GatewayTransport implementation; owns pyzmq
       ▲
bt_api_py[gateway-zmq]               optional integration extra; injects provider ports
       │
       └── provider adapters / ports ── Backtrader adapter

bt_api_execution / bt_api_risk / bt_api_monitor
       └── compatible public contracts only; never a concrete transport dependency
```

`bt_api_py` 应提供明确命名的 extras 或等价锁定 profile（至少 execution、risk、monitor、gateway、gateway-zmq、
完整受管 execution）。仅在 configuration 启用对应 capability 后，启动才解析它的 wheel 版本、submodule pin、
contracts compatibility、schema/attach 和 provider capability。没有 execution extra/profile、匹配 execution
版本/pin，或发现 managed route/插件组合不一致时，受管启动必须拒绝；不得静默改走 direct。无 config/no plugins/
all-disabled 且均 `required:false` 时不加载 runtime-plugin extras/pin。direct+enabled risk/monitor 只加载并验证
实际 enabled 的 plugin；`gateway_client` 则只加载成对的 gateway + selected transport。未启用 capability 不得被
隐式导入或冒充已经提供其控制。`pyzmq` 只能随 `bt_api_transport_zmq` 安装；gateway/core/direct runtime 的 import
不得要求它。不得从 checkout、环境中已安装的未锁定包或 Python import 副作用获得能力。

## 7. 生命周期策略

### CTP

受管 `TradingDaySessionPlan` 必须绑定 account/profile/TradingDay、审核过的 schedule/calendar hash、
session end、connection generation 和 policy hash。会话结束前执行 `freeze → drain/approved hold →
reconcile → sealed terminal manifest`。下一 TradingDay 必须重新 preflight 和授权，不能由旧 permit 自动 rollover。
direct CTP 路径继续由已有 Store/provider 的登录、交易日与会话协议驱动，不能把未启用的受管 lifecycle 当成
其必需启动校验。

### Crypto

受管 `ContinuousLifecyclePlan` 使用 rolling epoch、耐久 heartbeat 和 checkpoint；健康时不按小时/天重启。
行情陈旧、连接/流守恒异常、未知订单、journal/risk/monitor 故障均使其 `freeze → reconcile →
manual_intervention`。direct crypto 路径保留其已有连续会话逻辑，不能因没有 execution/risk/monitor 而被本计划
强制重启。当前被研究拒绝的 012 候选只能接入零写 shadow 版本。

## 8. Backtrader 兼容性

1. `BtApiBroker` 在 managed route 接受 framework order 后可以创建 virtual/order projection，但不能在 SDK
   未创建 plan 前假装远端已接受；direct route 保持当前 Broker/Store/provider 的确认与通知语义。
2. managed `FillAllocation` 回灌必须保持各 strategy 的 `notify_order`、`notify_trade`、仓位和费用守恒；
   具体通知顺序以冻结的 adapter contract 测试为准。direct route 不伪造 allocation。
3. 回测 `BackBroker` 的 bracket/OCO 仅为模拟行为；它不自动扩展到 `BtApiBroker`。
4. migration 前的 `parent/oco/transmit` real-live 提交必须显式失败关闭，并报告 provider capability
   缺失，而不是分三笔立即写入。
5. TradeLogger 的 snapshot 可进入 monitor telemetry bridge，但 snapshot 缺失、observer 崩溃或文件
   logging 关闭绝不能影响 managed execution/risk 状态；direct telemetry 缺失也不能改变既有下单链路。
6. `runtime.order_route=managed_execution` 的 runner 必须在创建 Store/Broker/provider client 前完成其策略运行
    目录 `config.yaml` 的 strict validation；execution 未打包、`runtime.order_route`/`runtime.account_access` 与
    `plugins.{execution,risk,monitor,gateway,transport_zmq}.{enabled,required}` 组合不一致、profile/
   pin 不匹配时必须在零 provider I/O 前失败。risk 或 monitor 被显式关闭本身不是 managed schema 错误，但必须
   保留对应缺口声明且不得被当作已启用。无 `config.yaml` 或 `legacy_direct` 的 runner 可创建既有 Store/Broker/
   provider client 并直接下单，不运行这套新增校验；它仍受 provider 原生认证、会话和协议约束。
