## 1. 目标架构

```text
every Iter41 runtime:
    mandatory config.yaml → strict mode/preset validation → trusted registry
                          → immutable effective config → selected adapters

backtest / simulation.replay:
    historical/fixture data → local broker/adapter → explicitly hypothetical results
    (no provider client, no network, no external writes)

simulation.paper / simulation.shadow:
    approved read-only market data → local paper/observation adapter
    (no provider writer; paper hypothetical fills and shadow zero fills are distinct)

simulation.sandbox default:
    authenticated isolated demo/SimNow → private-read port → observation/preflight
    (external writes=0; receipt alone cannot upgrade this read-only profile)

simulation.sandbox with write admission / live:
    Backtrader adapter → SDK composition → ONE execution authority → admitted provider
                                      ├─ mandatory risk/permit
                                      ├─ durable journal/outbox + writer lease
                                      └─ mandatory monitor/control confirmation

live.managed_live_gateway:
    SDK managed client → authenticated gateway server → ONE execution/risk authority
    (intent + opaque IDs only; no client-side account journal or provider credential)
```

`managed_live_direct` 的 direct 是账户直接接入 provider 的拓扑，仍经过 execution/risk/monitor；
它不恢复 `legacy_direct`。历史 SDK/Broker direct API 作为兼容合同保留并回归，不作为新的 Iter41
runtime preset，更不能因配置缺失或预检失败取得写入能力。live 的账户 owner 与策略进程隔离；gateway profile
由 server 持有该 owner，non-gateway profile 由独立 execution supervisor 持有，不创建第二 writer。

`TradeLogger` 位于左侧，是 Backtrader adapter 可选的 telemetry source；它不得成为 durable journal、
风险许可权威、远端对账来源或 monitor 的唯一输入。

五个能力包是 `bt_api_execution`（初始仓为空）、`bt_api_risk`、`bt_api_monitor`、
[`bt_api_gateway`](https://github.com/cloudQuant/bt_api_gateway)（已挂载、仅 README、尚未 package）与近期拟建的
`bt_api_transport_zmq`。它们保留各自的 Python distribution 和版本；`bt_api_py` superproject 维护 pin，并用明确的
optional dependency 与 integration adapter 组装运行时。它们不是 `bt_api_py` 的 Python 子包、vendor copy 或 provider
子仓的替代品；NATS/Redis adapter 不属于当前交付。

## 3. 公共 contracts

下列是目标合同：intent/plan/child/allocation为**受管执行**领域模型；其余跨路由共享DTO按D41-02放base。
它们必须不可变、版本化、canonical-serializable，且默认不含凭据、
原始账户 ID、capability secret 或 provider 私有对象。既有 direct 路径继续使用其当前 provider/SDK 对象和
协议，不假装产生execution intent/plan/permit/journal；实际启用risk/monitor仍使用共享decision/control合同：

| 模型 | 最少字段/语义 |
| --- | --- |
| `ExecutionScope` | mode/preset/registry/effective-config digest、provider/environment/account fingerprint、strategy/candidate/runtime identity、instrument canonical identity、metadata version/hash、TradingDay或rolling epoch、connection generation、policy/config/code hash；deployment另绑定evidence/receipt/actor digest。 |
| `ExecutionIntent` | intent ID、signal event identity、strategy attribution、scope、side、position effect（含 CTP OPEN/CLOSE_TODAY/CLOSE_YESTERDAY/CLOSE）、quantity/unit、price/TIF、deadline、reduce-only 请求、idempotency key、risk tags。server 用实际库存、挂单和 provider 语义推导 effect，不能信任客户端 `reduce_only=true`。 |
| `RiskDecision` | `allowed`、原因码、policy hash、投影风险、拒绝/告警信息；不能单独授权 I/O。 |
| `RiskPermit` / `RiskReservation` | 一次性/受限 capability，绑定 scope、permit ID、额度、child/action 限制、issued/expiry、fencing/version 与撤销状态。 |
| `ExecutionPlan` / `ParentExecution` | 聚合规则、atomicity level、所有源 intent、目标净额、execution policy、routing policy、状态和 plan hash。 |
| `ChildIntent` | parent ID、child ID、provider capability、client ID、具体写入动作、deadline、状态、幂等键和 reconciliation identity。 |
| `FillAllocation` | provider trade identity、child fill 到每个 source intent/framework order 的数量、价格、费用及 currency、资金费状态/证据、舍入 remainder 和分配版本；`unknown/not_applicable/pending/complete` 必须区分，不把缺 funding 填成 0。 |
| `ExecutionEvent` | schema/event ID、account journal/outbox sequence、scope、entity、前后 revision、状态迁移、源时间/接收时间、脱敏原因码、actor/receipt/intent/permit/config/code/plugin digest 和前一事件 hash。 |
| `LifecycleCheckpoint` | session/epoch、MD/TD 健康、account snapshot freshness、reconcile 状态、risk 状态、writer lease、heartbeat、stop-latch。 |

`bt_api_execution` 发布领域contracts兼容版本；risk/monitor的core只依赖base共享surface，其managed adapter按显式
启用加载execution兼容合同，不能import execution provider adapter或反向要求execution import自身。`bt_api_py` 的 managed

必选能力的权限。SDK/Broker旧direct API只保留兼容，不作为新的Iter41运行入口。

### 3.1 必需的三模式配置合同

schema-v4 是本次有意的破坏性配置升级；现有源代码中的 v2/v3、`--mode` 和参数 YAML 不是它的实现。
每个 Iter41 runtime 必须加载 canonical `<strategy-runtime-dir>/config.yaml`，包括回测、模拟、shadow、
AI-assisted 与实盘。文件缺失统一 `CONFIG_REQUIRED`，策略构造、网络、provider credential 读取、外部写均为零；
空文件、未知字段、重复 key、类型错误、旧版本与不相容 mode/preset 同样失败，不回退任何路径。

用户最小配置如下；正式候选、dataset、入口与默认参数的 hash 来自已登记 runtime，不从工作目录猜测：

```yaml
config_schema_version: 4
strategy:
  id: example.strategy-id
runtime:
  mode: backtest
  preset: local_backtest
```

| 用户字段 | 验证和易用性规则 |
| --- | --- |
| `config_schema_version: 4` | 必填；v3 及更旧 schema 只经显式迁移工具生成新文件，loader 不猜测兼容。 |
| `strategy.id` | 必填，绑定受信 runtime registry、真实策略制品与 candidate/data/parameter schema；错目录、缺登记或 hash 变化拒绝。 |
| `runtime.mode` | 只允许 `backtest/simulation/live`；由配置独占，不由 CLI、环境、secret、receipt 或模型选择。 |
| `runtime.preset` | 必须符合[唯一映射矩阵](插件与ZMQ架构.md#2-三模式预设与派生拓扑)；backtest→local_backtest，simulation→replay/paper/shadow/sandbox，live→managed_live_direct/managed_live_gateway。 |
| `parameters`（可选） | 只接受已登记策略参数与可收紧的 risk-limit 字段；缺省使用带版本/hash 的冻结默认值。未知 key、越界/单位错误拒绝；不能包含 route/access/plugins、环境、任意文件路径或扩权字段。 |
| `secrets_ref`（可选） | 普通 profile 只接受不透明 secret registry 引用，不能含凭据原值或任意 path/URL/import/env interpolation。受限 CTP SimNow `simulation/sandbox` 使用固定值 `config_yaml`，认证字段仅存在本地未跟踪、受保护的同一 `config.yaml` 顶层 canonical `ctp:` 块中；SimNow 与未来 production 共用此配置文件和字段结构，但该引用不能选择 front、live mode、写权限或 production authority。当前同一 CTP runner 的 live-mode dispatch/write admission 尚未实现或接线，模式/字段变更本身不能开启交易。当前 backtest/replay/paper/shadow 预设不接收 provider trading secret；gateway client 不持 provider credential。 |

`runtime.order_route/account_access`、`plugins.*` 和 provider connection 不再是用户字段，提交这些字段
返回 `CONFIG_SCHEMA_UNSUPPORTED`（reason=`field_not_allowed`）。它们属于受信 preset 展开的 `EffectiveRuntimeConfig`：绑定 config hash、
preset version/hash、artifact/candidate/data、mode/environment、execution adapter、route/access、所选能力
及其 required state、账户 policy、secret 引用指纹和 read/write policy。导出结果只供审阅与机器验证，不再作为
第二种用户输入。registry 更新、参数/配置变化使旧 seal/receipt 失效，不能悄悄改预设后沿用旧准入。

本地 backtest/replay、paper/shadow 不具有 provider order route 或账户接入，effective 中为 null，分别注入
本地 broker/fixture/paper/observation adapter；不能用 null 推导 direct writer。paper/shadow 的在线数据必须经
只读port，无provider submit/cancel能力。sandbox默认是认证的隔离测试账户私有只读，order_route=null、
account_access按registry固定；不因需要读取私有状态就强制加载三能力。可写sandbox/live强制
`managed_execution`与execution+risk+monitor；
gateway 预设再强制 gateway+transport_zmq。缺包、错误 pin、无效 policy、控制未 attach 或 receipt 不足都拒绝，
不得把关掉能力的配置当作“简化启动”。不适用能力仍不 import/init，零插件本地回测不是无配置启动。

#### 模式语义与零写判据

- **backtest**：只读已登记本地历史数据，零网络、零外部 provider write；允许 BackBroker 模拟成交和历史假设 PnL。
- **simulation/replay**：离线 fixture，零网络/零外部写；公式验算、状态机模拟和策略回放各有 evidence kind，
  是否生成假设成交由 fixture 合同冻结，不能把 replay 输出冒充实盘事实。
- **simulation/paper、shadow**：仅可用受信 profile 允许的公共只读行情，外部 submit/cancel/cancel-all 全部为零。
  paper 允许明确标记的假设成交/PnL；shadow 不产生 fill，不报告实际盈利。
- **simulation/sandbox**：默认是认证的demo/SimNow私有只读，external write=0，可支持014/015的隔离观察与准备。
  registry默认`write_policy=deny`；只有operator显式登记的`receipt_required`沙盒write profile，以及独立receipt、
  账户/会话/provider admission和三能力就绪后才可sandbox write，production write始终=0。缺receipt拒绝write profile，
  不降级只读；只读profile不会因发现receipt升级写入。目标环境无法证明为sandbox时ENVIRONMENT_MISMATCH拒绝。
  用户parameters/CLI不能切write_policy；两profile同属simulation/sandbox但绑定不同registry/effective hash，
  变更要停止会话并重新preflight，不能绕研究门或自动切live。
- **live**：只允许两种 managed_live 预设，强制 execution/risk/monitor、独立存活 owner、正式环境审批、
  研究/策略准入、metadata/session/calendar、capability、reconcile 和逐 child permit。点击确认或收到 token 只批准
  已固定配置，不能选择 mode/切换环境/降低风险。gateway 能力尚不支持的 provider 仍保持拒绝，不回退 direct。

报告至少区分 `external_write_count`（等于 sandbox+production 写数）、`sandbox_write_count`、
`production_write_count`、`hypothetical_fill_count`、evidence kind 和 PnL 完整性；模拟成交非零与外部写为零
可以同时成立。所有写门必须在最终dispatcher测试，而不只通过monkeypatch CLI/策略方法证明零写。
write count统计实际provider dispatch调用，包含发送后被provider拒绝的请求，不以ACK成功或最终成交数代替。

#### 两步运行、doctor 与迁移

默认用户主线是“bootstrap 生成配置，之后 run 自动重验配置和 preset policy 并调度 runner”。当前源码已交付这两项以及 validate/doctor；
`bootstrap` 只用审核模板生成，不连接 provider，不覆盖已有文件，已有文件返回CONFIG_EXISTS且字节不变；并发创建仅
一个成功，原子创建失败保留原文件，未选mode/preset不生成 live 默认值。批量 bootstrap 只接受审核的 runtime-set，
先预检全体目标，冲突时不写入其余缺失配置。`run --strategy-dir <dir>`
只选择目录，内部按 `validate → registry resolve → runner dispatch` 执行，不接受 `--mode/--preset/--config`
或环境变量覆写。这里的校验不等于 provider/account preflight；CTP 只读 provider preflight 是单独显式命令，
当前默认 registry 已登记 CTP SimNow `simulation/sandbox` 私有只读 binding，但无 runner/写能力；受保护私有 `config.yaml` 已存在。以下 F/G/H2 SDK/query 观察属于较早设计验证快照，不代表当前 I2：H2 与 I1 均曾在 TD query 完成后因 native Join shutdown incomplete 被拒绝，独立 MD-only request-ID mismatch 仍未根因化。当前 I2 TD retry、I2 MD-only strict-reject 与 runtime/SDK 测试见[验证汇总](evidence/validation-summary-2026-09-24.md)。managed 第三 `bt_api_py` parent pin、共享 CTP runner 的 live dispatch/default route 与写入授权仍缺；SimNow read-only pin 不构成生产准入。

validate/doctor 默认静态、零网络和零外部 secret-store 访问；CTP 私有路径需在文件权限预检后读取本地
`config.yaml` 并始终脱敏。doctor 还输出 mode、目的地、外部写/PnL 边界和下一条安全命令；普通路径缺配置
提示 bootstrap，CTP 私有路径提示一次性准备受保护的配置。两者输出稳定原因码、错误 field path、脱敏值/允许值、具体修复动作。
preflight 才按已固定 preset 进行允许的只读连接/身份检查，始终零 provider write；backtest/replay 的 preflight
仍零网络。run 显示 mode、preset、provider environment、是否可能外部写与实际能力，随后独立校验有效 receipt；
显示或确认不替代配置和授权。不可用功能标 `BLOCKED/NOT_IMPLEMENTED`，不能偷偷降级运行。

#### 同目录 CTP 的 mode/preset 路由合同（默认生产路由与 runner 尚未接入）

SimNow 与未来 production 的 operator-facing 配置目标是同一个受保护的
`examples/013_3_sa_midfreq_simnow/runtime-ctp-private/config.yaml`，并共用 canonical `ctp:` 字段。
共享 `ctp:` 解析及纯 scope binding 已实现；该文件中的 sealed `runtime.mode`/`runtime.preset`
只表达请求的运行路径，不签发 route 或 authority。
受信 route dispatcher 必须根据 loader seal、精确的 mode/preset 与 code-owned registration，选择互不混用的
SimNow sandbox 或 production live authority contract；任何缺失或不匹配都在凭据解析、SDK 导入、socket、runner
和最终 dispatch 前失败。

当前 `RuntimeRegistry` 对每个规范化目录只允许一个 registration。013_3 私有目录目前只绑定
`simulation/sandbox` 的只读 registration，`sandbox_write_policy=deny`，无 runner、execution/risk/monitor
capability 或写入 receipt。因此不能给同一目录追加第二条 `RegisteredRuntime`，也不能放宽当前只读 registration
来“顺便支持”写入。只改该文件到 `live/managed_live_direct` 当前必须 fail closed；不复制配置目录、不把旧
`runtime-production/` 作为第二条 operator 路径。

未来 production 准入必须有单独审阅的 production approval、账户/前置候选集/合约/制品 pin、风险和 monitor
capability、账户级 writer fence、session/reconciliation 及逐请求授权合同。代码应在同一目录、同一受管 CTP runner
和一个受信 registration 下，由 mode-aware dispatcher 选择模式专属准入并验证各自 seal；不建立 production 专用
runner，也不得通过 YAML、共享 registration 或继承 SimNow receipt 获得生产权限。只有共享 runner 的两模式路由
和各自审批均已安装、验收后，operator 的操作才可简化为编辑原文件。
旧 `runtime-production/` 与 `ctp_production:` parser/helper 保持 legacy/deferred；退休 CLI 不得再创建第二份
配置，兼容 parser 的存在不代表可运行或可授权。

注册的运行目录提交无secret `config.example.yaml`，实际 `config.yaml` 目录级精确ignore。既有 tracked 参数文件
保持原义与 Git tracking；冲突例子使用独立 runtime-dir，registry 固定其参数 artifact/hash，不依赖 cwd或父目录
搜索。不得全仓ignore/覆盖旧 config，更不能让保留下来的参数文件豁免必需启动配置。严格安全打开及平台seal见§11。

旧 runner mode、CLI开关、.env profile覆盖逐例进入迁移清单：显式工具生成 v4候选与差异报告，无法确定mapping/
environment就 `MIGRATION_REVIEW_REQUIRED`，重新preflight/授权，不复制旧receipt。旧受限候选仍受原研究状态，
不能因为生成配置或切到sandbox/paper而解除禁止。影响写入的配置变化统一
`freeze → drain/stop → 新config/registry seal → 新preflight/receipt → restart`，禁止运行中热切实盘。

## 4. 状态与事务规则

### 4.1 受管 Child 写入状态机

```text
DRAFT
  → PENDING_DISPATCH   [one durable commit: child + claim + optional risk reservation + outbox]
  → DISPATCHING
  → ACKED → PARTIALLY_FILLED → FILLED
     ├─────────────────────→ CANCELLED
     └─────────────────────→ REJECTED [only where provider facts permit]

any dispatched nonterminal state → UNKNOWN → RECONCILING
    → authoritative open/partial/filled/cancelled/rejected state, or remain UNKNOWN

cancel action: REQUESTED → DISPATCHING → CONFIRMED / REJECTED / UNKNOWN
    (separate action state; never erase the child's known fills)
```

本状态机只适用于派生 `effective_order_route=managed_execution`。每次状态迁移必须有 journal event。任何发送后的
timeout、连接断开、回执丢失或进程崩溃均为 `UNKNOWN`，不能“再发一次看看”。只有远端查询、私有流或有证据的
本地 reservation-only 恢复可将其推进为终态。既有 direct 路径继续按当前 provider/SDK 的订单状态和恢复语义
处理，不得伪造 `ChildIntent`/journal 覆盖它。

省略ACK的fill可在充分provider证据下直接进入partial/filled；本地绝不能凭发送成功补ACK/fill。
`FILLED/CANCELLED/REJECTED`终态禁止被晚到ACK倒退；取消与成交竞争通过独立cancel action和累计filled quantity归并。
schema必须约束每个允许迁移及数量单调性，遇到冲突事实冻结对账；不能把上述图画成所有箭头可任意互转。

### 4.2 受管风险 reservation 规则

1. `RiskDecision`不是bool；可写sandbox/live只有持久化且dispatch时仍有效的RiskPermit可授权child。
   execution单包的零写单元fixture可不注入risk，但没有受管外部写准入，不制造“risk passed”或虚假permit。
2. 额度按普通开仓、普通撤单、replace、紧急减仓/保护撤单分别记账；replace 必须声明是一个逻辑
   行为还是 provider 的 cancel + new 两次写入。
3. 在确认未发生 provider I/O 前可释放 reservation；一旦结果不确定，不退款、冻结新开仓并等待对账。
4. 风险 scope 同时包含账户级硬上限和策略/候选分配；净额化不能使任何原始 gross intent 绕过限制。
5. risk ledger、intent/dispatch claim 与 outbox 在 §10 的同库事务提交，账户 writer lease/fence 是额外互斥，
   不能单靠“持有同一锁”声称两个独立文件原子提交。provider 网络动作不在数据库事务内；发送后不确定性必须保守恢复。

以上是v4可写sandbox/live强制的managed+risk规则。旧SDK direct+risk兼容合同仍在provider I/O前原子占用同一耐久账户
authority 的次数/额度、保留未知结果的占用，不能按进程各算一次；它不伪造 execution permit/journal/aggregation。
两个本地 direct writer 必须加入同一 authority 服务或因独占 lease 被拒绝；跨主机多 writer 不在 v1 支持范围。
这些路径仍须记录实际已发送计数；reserve 失败的“0 write”断言不适用于已经发送后的 UNKNOWN 故障。

### 4.3 聚合与 atomicity

v1 只允许下列字段全部兼容时合并：provider、environment、account、instrument、position mode、side、
position effect、reduce-only、TIF、价格/滑点约束、deadline、lifecycle profile 和 risk scope。否则保持
独立 plan 或明确拒绝。

每个 plan 必须标记下列之一：

| 标记 | 允许含义 |
| --- | --- |
| `native_atomic` | provider capability 和实际回执均证明原子语义。 |
| `native_algo` | provider 接受一个具备独立查询/取消/恢复语义的 algo child；仍不是跨 provider 原子性。 |
| `sequential_non_atomic` | 多个 child 依次发送，必须有部分成交、补偿与 UNKNOWN 方案。 |
| `basket_best_effort` | 多腿计划；必须显式披露非原子，并要求每腿可恢复。 |

没有 capability receipt 时，`parent`、`oco`、`transmit`、batch、slice 和 basket 一律拒绝；不得静默拆成
普通订单后宣称同等保护。

## 5. 打包与依赖方向

```text
bt_api_base                          shared typed contracts; no transport dependency
       ▲
bt_api_gateway                       middleware-neutral shared-account core
       ▲
bt_api_transport_zmq                 first GatewayTransport implementation; owns pyzmq
       ▲
bt_api_py[gateway-zmq]               optional integration extra; injects provider ports
       │
       └── provider adapters / ports ── Backtrader adapter

bt_api_execution / bt_api_risk / bt_api_monitor
       └── compatible public contracts only; never a concrete transport dependency
```

`bt_api_py` 应提供明确命名的 extras 或等价锁定 profile（至少 execution、risk、monitor、gateway、gateway-zmq、
完整受管 execution）。仅在必需配置经受信preset展开并选定capability后，启动才解析其wheel版本、submodule pin、
contracts compatibility、schema/attach 和 provider capability。没有 execution extra/profile、匹配 execution
版本/pin，或发现managed route/能力组合与mode/preset不一致时必须拒绝，不得静默改走direct。缺配置立即
CONFIG_REQUIRED；合法local_backtest/replay预设不加载五能力，可写sandbox/live加载且验证三能力，gateway预设再
加载成对gateway+selected transport。未选capability不得被隐式导入或冒充生效。
`pyzmq`只能随`bt_api_transport_zmq`安装；gateway core、本地模式、non-gateway SDK import
不得要求它。不得从 checkout、环境中已安装的未锁定包或 Python import 副作用获得能力。

现有risk ML训练/推理能力保留在独立`ml` extra，core hard-gate不训练或推理，不要求安装ML重依赖；
monitor保留metrics/collector/health并适配durable read model，exporter/backend按extras加载。
`bt_api_monitoring`旧导入别名只委托一个consumer实例，不复制监控线程/游标。这些裁剪是依赖隔离，不删除已有产品能力。

## 7. 生命周期策略

### CTP

受管 `TradingDaySessionPlan` 必须绑定 account/profile/TradingDay、审核过的 schedule/calendar hash、
session end、connection generation 和 policy hash。会话结束前执行 `freeze → drain/approved hold →
reconcile → sealed terminal manifest`。下一 TradingDay 必须重新 preflight 和授权，不能由旧 permit 自动 rollover。
v4可写sandbox中的SimNow与live正式CTP都必须通过各自环境的上述生命周期；sandbox只读会话验证环境身份、
连接代次与查询完整性但不能报单，不需要伪造RiskPermit。历史回测使用冻结日历而不连接CTP。
旧Store/provider登录协议是实现基础，不构成v4免配置或跳过受管写入生命周期的入口。

### Crypto

受管 `ContinuousLifecyclePlan` 使用 rolling epoch、耐久 heartbeat 和 checkpoint；健康时不按小时/天重启。
行情陈旧、连接/流守恒异常、未知订单、journal及实际enabled的risk/monitor故障均使其 `freeze → reconcile →
manual_intervention`。可写sandbox/live的execution/risk/monitor必须全部生效；paper/shadow仅保持公共行情读取与本地
模拟/观察，不持provider writer。当前被研究拒绝的012候选仅准许其既定零写观察/明确研究测试路径，三模式配置
不能自动解除原来的paper/demo准入限制。

## 8. Backtrader 兼容性

1. `BtApiBroker` 在 managed route 接受 framework order 后可以创建 virtual/order projection，但不能在 SDK
   未创建 plan 前假装远端已接受；direct route 保持当前 Broker/Store/provider 的确认与通知语义。
2. managed `FillAllocation` 回灌必须保持各 strategy 的 `notify_order`、`notify_trade`、仓位和费用守恒；
   具体通知顺序以冻结的 adapter contract 测试为准。direct route 不伪造 allocation。
3. 回测 `BackBroker` 的 bracket/OCO 仅为模拟行为；它不自动扩展到 `BtApiBroker`。
4. migration 前的 `parent/oco/transmit` real-live 提交必须显式失败关闭，并报告 provider capability
   缺失，而不是分三笔立即写入。
5. TradeLogger 的 snapshot 可进入 monitor telemetry bridge，但 snapshot 缺失、observer 崩溃或文件
   logging 关闭绝不能影响 managed execution/risk 状态；direct telemetry 缺失也不能改变既有下单链路。
6. 所有Iter41 runner在创建策略/Store/Broker/provider client前验证必需config；mode/preset/effective route与
   能力组合不一致、profile/pin不匹配时零provider I/O拒绝。可写sandbox/live关闭risk/monitor为
   PRESET_POLICY_VIOLATION，不能记录“缺口”后继续写。本地预设不创建provider writer；AI额外语义门见§12。

## 9. 线程、账户控制与恢复合同

### 9.1 谁可以改变状态

| 上下文 | 可以做 | 不可以做 |
| --- | --- | --- |
| provider callback / SDK worker / transport I/O 线程 | 校验 envelope、复制成不可变事件、附 generation/sequence、投递有界 mailbox。 | 调用策略 `notify_*`、改变 Backtrader order/position/cash、取得第二执行 lease。 |
| 账户 authority owner | 顺序消费私有事实，在事务中去重、更新 execution/risk projection/outbox；同步检查 dispatch gate。 | 在持数据库事务锁时等 provider 网络、模型或告警服务。 |
| Cerebro 线程 | 在 `BtApiBroker.next()` / idle 周期 drain mailbox，按 allocation/event revision 更新 framework projection，再送通知。 | 将 REST/transport ACK 当成交；从旧 generation 回调恢复已冻结权限。 |
| monitor / AI read-model consumer | 读取 checkpoint/outbox，发受限控制请求/人工待办。 | 直接改风险账本、调用 provider writer、在 producer 失联后伪造新鲜状态。 |

每账户 owner 串行写，消费者各有 cursor；重复 trade ID/事件 revision 只应用一次，冲突重复必须冻结并对账。
私有事件/控制 mailbox 满时禁止丢弃后继续交易：先原子 latch `EVIDENCE_BACKLOG`，停止增加风险，保留已提交
outbox 后从 cursor 重放；没有 durable source 的 direct event 丢失须强制 provider 完整对账。行情队列只能在
schema 明确为完整快照且消费者接受 latest-only 时合并；增量盘口/逐笔不得任意抽样并声称连续。
`notify_order/notify_trade` 的顺序冻结为 adapter vectors，包含部分成交、cancel/fill race、重复/晚到回调与重启；
不修改 `getcash()`/`getvalue()` 的兼容语义，新的只读 `StrategyAllocation` 独立用于 sizing。

### 9.2 Freeze、drain 与进程死亡

账户 owner 持久保存按 issuer/reason/scope 分组的 freeze latch：**freeze 取 OR**，任何有效未解除原因都阻止
增加风险；**resume 取 AND**，全部原因解除、账户/行情/对账恢复、scope/fence 新鲜且新的人工审批通过才解锁。
某组件恢复健康不能清除其他组件的 latch。自动解除、自动重新授权与由模型批准 resume 均不支持。

control port 先持久提交 `(command_id, issuer sequence, receipt digest, expected revision, target generation)`，
再按 scope/policy 执行。相同 key+相同内容返回原结果，相同 key+不同内容拒绝；重复 drain 复用同一处置计划。
`RECEIVED` 仅表示接收，`APPLIED` 表示 gate 已变更，`COMPLETED` 必须有订单/仓位对账证据与最终 checkpoint。
目标没有回复或已死亡时，在该 profile 的 `ack_deadline` 后标 `UNCONFIRMED` 并升级 `MANUAL_INTERVENTION_REQUIRED`，
不得把请求已发出写成 drain 完成。参考验收 profile 固定 `ack_deadline=5s`、失联检测 `heartbeat_timeout=5s`，
provider 清理 deadline 由具名 venue/session profile 给出，过期保持冻结。

需要“策略进程死亡仍能处置”保障的受管 deployment，由独立 **execution supervisor** 持有唯一账户 lease、
provider session 与已授权处置计划，Backtrader 只作为 client；它是 SDK 部署/组装方式，不是第六种 plugin。
gateway 阶段 supervisor 与 gateway server 的账户 owner 合并，不能各持一个 writer。策略死亡后存活 owner
可按已预授权的范围做撤单/减仓，仍必须通过真实 dispatch gate；monitor 只提交请求。若 authority 本身死亡、
连接不可用或处置范围不确定，保持冻结并交人工。嵌入式 managed 或原 local direct 在 owner 与策略一起死亡时
明确**没有自动 drain 保障**，不能以增加 timeout 掩盖这一缺口。

控制动作由账户事实分类为 `INCREASE`、`REDUCE`、`CANCEL` 或 `UNKNOWN_EFFECT`：

- 普通损失/保证金开仓门阻断 `INCREASE`，不能误杀已授权撤单；撤单有独立次数/频率预算和已知 order identity。
- `REDUCE` 必须验证真实持仓侧、已挂减仓量、CTP 平今/平昨或 venue reduce-only 能力，并使用独立 emergency budget；
  不允许用 `reduce_only` 字符串绕过风险或制造反向开仓。
- `UNKNOWN_EFFECT` 保持冻结并人工核对。空 book、无有效价格、无法确认成交/持仓时不盲目市价平仓；不能承诺一定平仓。
- 期权/篮子先按已冻结组合风险和逐腿清理优先级执行；缺 Greeks/metadata/库存时不得以净名义额等价代替，能力缺失拒绝。

### 9.3 三层恢复与确定性重放

启动顺序固定为 `freeze → authority/lease校验 → provider完整查询/执行对账 → 策略状态恢复/行情warmup → 新preflight`。
execution checkpoint 证明账户/订单事实；strategy checkpoint 证明决策状态；market watermark 证明数据连续性，三者
互不替代。策略只能恢复明确列入 schema 的信号、持仓目标、计时器、窗口与最后 signal ID；实际仓位总由对账覆盖。
无法校验旧 code/config/metadata hash 的 checkpoint 必须拒绝使用，按具名 cold-start/warmup 策略保持零增加风险。

signal identity 必须源自稳定 `source event ID + strategy runtime/candidate + decision version + action ordinal`，
canonical hash 得到 intent/idempotency key；不能每次进程启动随机生成同一信号的全新 key。账户 namespace、
环境/TradingDay epoch 与 request fingerprint 同时绑定，但重启不改变已发 intent 的原 key。未知请求只查询同一
identity，不因重连/generation 变化新建订单。信号可靠交接使用策略checkpoint内的pending outbox：先原子保存完整
pending signal payload+stable key+待处理source watermark，再向execution提交；只有收到并校验绑定原key/digest的
durable admission ACK后，才能在本地事务将该signal标成已处理并推进acknowledged cursor。禁止先推进“已处理”
游标再提交intent，否则崩溃会永久漏信号。

重启先恢复pending outbox并按原key查询唯一execution authority：已存在则join原状态并回补ACK/cursor；仅当同一
权威、正确generation且完整journal查询证明不存在该key，才可重送**同一payload/key**，不能生成新intent。
query timeout、authority更换而未完成迁移、或结果UNKNOWN均保持pending并冻结。必须在pending保存前/后、提交前/后、
admission ACK前/后与cursor提交前/后分别杀进程，证明无丢失信号且每个逻辑信号至多一次provider写入；未发送的
pending被恢复后允许完成唯一一次发送，不能把该情形误验为所有恢复都0 write。

去重记录覆盖全部 nonterminal intent 及已冻结回放窗口；过期数据无法
证明“未执行”时拒绝自动重播。确定性 fixture 重放同一信号必须新增 provider write=0。

行情 gap 按数据类型恢复：完整快照可替换；增量 book 必须取 snapshot sequence S、校验并连续应用 S 之后的增量，
缺序则重新同步；bar/逐笔 warmup 必须有来源、时间区间、校验和与重复去除。对齐前 alpha 禁止增加风险，
已授权 CANCEL/可证明 REDUCE 仍走独立处置规则。交易日/元数据/连接 generation 变化必须失效旧 readiness。
gateway 的 snapshot barrier 细节见[插件 ADR §6](插件与ZMQ架构.md#6-zmq-的可靠性安全与-ctp-边界)。

## 10. ADR-41-11：事务存储、迁移与灾难恢复

**v1 决策：本机 SQLite，WAL，`synchronous=FULL`，单账户 authority owner，禁止 network filesystem。**
这是待实现并待性能验证的选择，不是现有 `_ExecutionSession` 的事实。无持久化/关闭 fsync 的模式只能作为
零 provider I/O 的测试 profile，不能以性能不足为由进入真实写入。数据库文件位置由认证后的账户 namespace
派生，策略 YAML 不得自建 ledger 路径。SQLite 事务 unit-of-work port 与无 I/O DTO 放 `bt_api_base`；execution、
risk 各持有其表语义，SDK integration 注入同一 backend，禁止 concrete 相互 import。

1. 接收 intent 后，在同一事务验证当前 scope/fence/freeze、唯一幂等键与账户预算，写 intent/child 的待发送
   claim、risk reservation（若启用）、必需 outbox record，然后 durable commit；完成前不允许 provider I/O。
2. dispatch port 在网络调用前复核 claim、scope/fence、expiry 与 config seal；复核和命令领取由唯一 owner
   串行化。未发送且可证明的 abort 可释放预留；出现过 dispatch claim 后崩溃/超时而无法证明未发送则按 UNKNOWN，
   不能自动重新 dispatch。不能承诺数据库与外部 provider 的跨系统 exactly-once。
3. 回执/成交在下一事务按 provider trade/order identity 去重，结算 reservation 并写 outbox；一次 fill 可对应
   多条 allocation，但总量/费用守恒。provider ACK 只改接受状态。outbox 发布、read-model checkpoint 与 telemetry
   可以异步批量，但唯一原始outbox记录不能只在内存。仅零外部写的execution单包fixture可关闭risk且不虚构permit；
   v4可写sandbox/live禁止关闭risk。旧direct+risk兼容测试在同authority记录action/reservation/outcome，不造execution parent。
4. monitor 的 sink/消费 cursor 可以单独存储，但只有处理事务提交后才推进 cursor；丢失 cursor 可由 durable
   outbox 重建。slow consumer 超出保留期必须 snapshot/reconcile，不能把新 cursor 当已处理全部历史。
5. v1 不支持活跃多主、NFS 锁或跨主机双 writer。多策略共享 owner；第二 owner 的 lease 竞争必须拒绝。
   同一账户 direct/managed 混用只有都加入同一 authority 且 scope/policy兼容才可运行，否则拒绝并发。

旧 JSONL 与 forwarding ack/private-event 数据迁移分两类：前者迁移**写入权威**，后者迁移**交付投影**。
迁移工具必须保留公开 `migrate_execution_journal` 的兼容入口，输出 old/new schema、源/目标 hash、账户 fingerprint、
最后 event sequence、unknown/open set、fence 与工具版本，不能复制 credential/恢复 capability。
流程是 `冻结 → 旧owner完成对账 → 持迁移独占锁备份 → 导入/守恒校验 → 停旧writer → 原子切active authority/fence
→ 新preflight`；旧写 lease 释放后，迁移锁仍覆盖切换窗口。每步都可故障注入，未提交切换允许安全恢复旧权威，
已提交后只能前滚或显式反向迁移并新授权，不准复制文件启动旧 writer。旧 `_ExecutionSession` shim 不再持 journal、
lease、dispatch/recovery 状态，只懒导入委托新公开 integration。删除旧领域实现与 consumer 测试是交付条件。

durable receipt 的 RPO=0 限于“已确认提交的数据在进程崩溃/机器重启且存储介质仍完好”的声明；全盘损坏/丢失
不在此承诺内。默认每 5 分钟以 SQLite backup API 生成一致性备份，校验 hash/恢复可读性；账户凭据与授权不入备份。
备份/保留策略在 ADR-41-05 固定并记录实际恢复点。恢复 1,000,000 个事件的本地 fixture，在 §11 平台上恢复
到“冻结、可读、可开始对账”RTO≤10 分钟；这不承诺 10 分钟恢复交易，provider 查询/人工重新授权仍是独立门。
数据库损坏/磁盘满时停止新 dispatch，不能清库重试；备份恢复必须更换 fence 并验证未知订单、额度和 sequence。

## 11. ADR-41-13：平台、性能与资源预算

以下是工程验收阈值，**尚未测量**。任何平台不通过即相应项 `FAIL/BLOCKED`，不得用删 risk、降低 durability、
改为无锁或放宽研究门来满足预算；需要调整数值时必须先审阅变更 ADR，并重跑整组结果。

| 验收 profile | 测量方法与门槛 |
| --- | --- |
| 平台 | Windows x64 与至少一种 Linux x64；Python 3.11、本地 SSD，记录 CPU/RAM/磁盘/OS/Python/wheel/SQLite/libzmq 版本。源码兼容 Python 3.8–3.13 另做 import/contract CI，不能用一个版本性能代表全部版本。 |
| managed+risk 同步开销 | 单账户 fake provider，20 intent/s，包含 durable reserve/intent/outbox 到可 dispatch 的增加成本 p99≤20ms，不含 provider 网络；启用 direct+risk 同一 authority 路径也≤20ms。 |
| 账户吞吐 | 2 clients/1 account，持续≥50 intent/s，至少30分钟；无丢事件、无重复写、risk额度与allocation守恒，队列不持续增长。 |
| 旧SDK direct兼容微基准 | 仅对保留的低层API用fake provider回归，不是Iter41运行入口；同硬件submit/cancel的p50/p99回归≤5%，5轮配对取新/旧比值中位数。有效local_backtest/replay预设的零capability import/worker/socket另验；缺配置拒绝，不能运行此benchmark伪装成功runtime。 |
| gateway | 本地已认证 ZMQ、20 intent/s，新增本地 request→durable ACK 往返 p99≤50ms；最终 fill 延迟另报，不作为网络延迟的替代。 |
| monitor | 20 events/s、30分钟，独立进程CPU≤单核5%、RSS≤256MiB、consumer lag p99≤1s、压缩前持久增量≤1GiB/日；实际 event大小/保留天数/容量必须进入报告。 |

基准使用 warmup、冻结随机种子、单独串行进程，禁止 xdist/coverage、同机并发重负载；提供原始样本、分位数、
队列高水位、fsync/commit延迟、drop/UNKNOWN/拒绝计数及已知硬件差异。性能验收覆盖 Store/Broker adapter，不只测
孤立 planner。指标是中低频基础设施门槛，不构成 013_2/015 HFT 准入；高频 profile 超预算须保持 disabled/shadow
或现有明确分类 direct，并保留性能缺口。

配置文件在 POSIX 用 regular file、owner/mode、no-follow open 与同一 FD 校验；Windows 必须用 handle identity、
reparse-point拒绝、文件共享/替换约束、ACL验证的等价实现，不能因无 `O_NOFOLLOW` 而跳过。preflight seal 绑定
实际读取字节、file identity 和 canonical redacted fingerprint；每次 dispatch 验证当前 seal/策略制品未被替换，
秘密值不进 receipt。无法提供该平台等价检查的 protected profile 为 `BLOCKED`。ZMQ Windows 默认
`tcp-loopback-curve-v1`，POSIX IPC 仅在安全/权限 fixture通过后使用，不把 `ipc:///` 写成所有平台通用。

## 13. 交易、预算与经济事实合同

本节是 FR18～21 的规范来源；[验收用例与基准](验收用例与基准.md) TC48/50/52/53/55 是其确定性
oracle，修改任何一方必须同步。以下为目标实现，不能把现有分析模型的输出当作已实现的权威风险门。

### 13.1 风险指标计算口径表

所有计算输入需含 source/version/as-of/completeness/currency/unit；Decimal 有限值或最小单位整数，
禁止 NaN/Infinity/静默默认 multiplier=1。元数据/价格/账户事实缺失或过期拒绝 INCREASE；CANCEL
不因缺估值而被普通开仓额度误杀，但仍检查身份、目标活单、撤单预算、模式与允许的执行主体。

| 指标 | v1 规范 | 状态、日界与边界 |
| --- | --- | --- |
| 原生数量/持仓 | long/short、CTP今/昨及已被close占用数量分桶；available_close=权威已知持仓-活动减仓保留量 | 数量容差0；未知数量不能当0；账户/策略各自限制；reduce_only由库存推导，不能只信任flag |
| 名义金额 | 已验证线性合约 abs(native_qty) × multiplier × conservative_price；同时约束gross及signed net | conservative_price为受限订单价格与新鲜mark的较保守风险金额；市场单必须有保护价格上限；inverse/特殊产品无版本化公式即不支持，不套线性公式 |
| 保证金 | 已验证provider产品公式/权威margin snapshot + 未成交worst-case reservation；fixture仅线性notional×rate | 不默认跨腿抵消或组合保证金优惠；盘中rate/metadata revision改变使旧permit失效；预估不足阻断新风险 |
| 策略配额 | allocation ceiling、used、reserved、available和revision；available=min(strategy ceiling-used-reserved, account free) | 配额是受账户总限额约束的逻辑上限，不是隔离资金所有权；多策略ceiling可重叠，但真实占用总和不可超account cap |
| 日损/损失 | max(0, equity_baseline + signed_external_net_cashflow - equity_current)，同币种、同账户、同来源完整区间 | >=loss_limit触发锁存，权益回升不自动解除；CTP由verified TradingDay/结算来源建立基线，crypto冻结UTC日界；rolling checkpoint不重置日损 |
| 普通submit次数 | child实际dispatch-attempt前耐久预占slot；发送后计入，UNKNOWN保持；最终证明未发送才释放预占 | 本地写前拒绝不消耗实际dispatch次数；provider拒绝仍消耗已发次数；同幂等请求不重复计数；日次数按上行日界 |
| 撤单/replace | CANCEL独立预算，replace按cancel+new分别计数；紧急预算有独立上限与授权 | 日损或新仓margin不足不直接拒绝合法CANCEL；风险插件/authority失效时不得生成新permit；mode=simulation且preset=shadow/replay/paper始终零外部写 |
| 频率 | authority以monotonic clock维护滑动窗口(t-window,t]；TC50-E用window=1s、cap=2 | 窗口边界剔除t-window；进程恢复基于耐久记录保守重建，墙钟回拨不延长许可；不能各进程本地计数 |
| 额度阈值 | projected_count/notional/margin <= cap才可通过；loss >= limit则阻断 | 必须同时通过账户与策略限制；不能只比较当前值而漏掉本次预占 |
| 金额差异 | 按currency minor unit及已冻结rounding mode（fixture CNY 0.01、ROUND_HALF_EVEN）计算 | 只有完整事实的已知舍入差<=1 minor unit可容忍；缺费用/funding/FX不是舍入误差 |

时间字段区分 exchange event time、ingest UTC 和 authority monotonic，连接代次变化不篡改历史TradingDay。
多币种指标保留原币种；缺完整FX source/as-of不得直接相加。外部手动交易/强平/行权是账户事实，
必须对账及重新投影风险，不能捏造策略intent归因。亏损/异常可冻开仓，不能任意新建相反腿补偿。

### 13.2 StrategyAllocation 与 sizer

公开只读 `get_strategy_allocation(strategy_id)`（目标API，由SDK port/Backtrader薄适配暴露）返回
`scope/currency/allocated/used/reserved/available/revision/as_of/completeness/reason`。
`BtApiBroker.getcash/getvalue` 保持账户级缓存语义；新增allocation-aware sizer显式选择，先按
metadata的保证金/风险单位将available换算原生quantity，再向下对齐lot。查询只是建议，不能替代
写前原子reserve。配额不足区分STRATEGY_ALLOCATION_EXHAUSTED/ACCOUNT_LIMIT_EXHAUSTED；
旧revision许可返回ALLOCATION_VERSION_MISMATCH。缩减配额不能抹去现有占用；若已有风险超过新额，
冻结新风险并走受控处置，不能把used/reserved截断为新上限。

### 13.3 部分成交、费用与余量

固定算法 `remaining_pro_rata_v1`：每个被接受的provider fill按server已排序的事件序列分配，权重为
各source intent当前剩余可分数量。先算fill_units×remaining_i/sum(remaining)，取整数floor；余下
单位按小数余数降序、相同按稳定intent_id字节序逐一分配，任何分配不得超过该source的remaining。
事务内同时更新source filled/remaining、child cumulative filled和event dedupe；输入fill超过child
remaining即CONFLICT_RECONCILE，不能截掉差额而报成功。只合并同一原生quantity lattice的intent。

总量、逐source上限和每次非负三者同时断言。例：S1=2、S2=1、S1 ID先于S2，三次fill1分为
S1、S1、S2，总数2:1；不能三次固定用初始2:1将全部成交给S1。同样输入、排序和版本可重放；
不同fill分片可能改变成交价格归属，必须如实记录，不承诺对任意分片方式经济结果相同。

每个fill的fee按其实际数量分配比例，以currency最小单位、同一余数/intent_id规则分配；sum(source_fee)
精确等于该fill fee。费用修订/返佣作为独立、具身份的signed event，不覆盖或重复累计旧事件。
迟到fee按其引用fill的原allocation分摊；无法关联则费用unknown并对账，不随便分给当前持仓。
funding按账户现金流和持仓覆盖期间分配，未得到完整事实为pending/unknown，不填0。

### 13.4 AccountSnapshot 与 ExecutionQualityRecord

`AccountSnapshot` 最小字段为account fingerprint、environment、generation、TradingDay/epoch、
source/as_of/currency、equity/cash/available/margin、realized/unrealized/fee/funding/net_cashflow、
每字段completeness和覆盖区间/来源引用。provider equity若已含fee不得重复扣除；只读缓存与权威
observation必须明确区分。完整funding账本尚缺时，不发布完整realized-net PnL或解除生产阻断。

`ExecutionQualityRecord` 关联signal/intent/child/order/trade opaque IDs，记录arrival bid/ask/mid及
时间/新鲜度、side、native qty/multiplier、VWAP、signed fee、slippage amount/bps、各阶段monotonic
耗时和拒绝原因。buy滑点=(fill-arrival_mid)×qty×multiplier，sell反向；arrival缺失则null，不造0。
跨机未校准时钟不能相减声称端到端延迟。monitor提供有界查询/导出，TradeLogger bridge消费这些
事实而不再计算第二套账户账本。TC53-A给出净/毛费用和滑点的明确数值回归。

### 13.5 紧急能力兼容边界

managed v1或direct+enabled Iter41 risk在durable authority不可用时不新签permit，不自动dispatch
submit/reduce/cancel；已有UNKNOWN不丢弃，升级人工。SDK原legacy执行会话已有的degraded cancel
