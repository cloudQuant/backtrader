## 0. 审阅结论摘要

这份计划的**安全设计纪律是一流的**：双路径显式归责、fail-closed、无自动回退、capability 不伪造、
46 条验收几乎全部可执行。方向正确，不建议推翻。

但从可行性角度看，它有一个致命的结构问题，和一组性能上的**空白**：

| 维度 | 评价 |
| --- | --- |
| 安全边界与归责设计 | 强。无需修订 |
| 范围/体量 vs "一个迭代" | **不可行。这是项目群（program）级范围，却按一个迭代立项，且无任何工作量估算** |
| 性能预算与热路径设计 | **空白。全文无延迟/吞吐指标；受管路径的 fsync 链在 Windows/CTP 上有可预见的延迟问题** |
| 关键路径与验收耦合 | 有风险。gateway/ZMQ（WP41-G）阻塞最终裁决，但它与本迭代核心价值耦合度最低 |
| 迁移源退役路径 | 缺口。B2 的兼容迁移对象（8.8k 行 `_ExecutionSession`）自身没有退役工作包 |
| 平台约束显式化 | 缺口。CTP 实盘在 Windows，但 Windows 未被列为交付/验收平台约束；模板 `ipc:///` 在 Windows 上不可用 |
| 证据/验收自动化 | 缺口。46 条 AC × 14 迁移单元的证据采集无自动化设计 |

一句话：**计划把"不能出事"设计到了极致，但把"做不做得完"和"跑得快不快"留白了。**
前者是设计问题，这份计划已经证明了团队有能力解决；后两者是管理问题，是技术经理必须现在拦下来的。

## 2. 可行性发现

### 2.1 【严重】范围超载：这不是一个迭代，是一个项目群

计划包含 8 个工作包（A–H）、**7 个核心 Git 身份**、5 个从零或半成品起步的能力包、46 条验收条件
（若并入量化交易员建议的 9 条则为 55 条）、14 个迁移单元。而**全文没有一行工作量估算、人力假设或
周期承诺**。里程碑表（§3）只定义"能得出什么结论"，没有回答"需要多少资源、什么时候"。

基于第 1 节的实测体量，我给出粗粒度人日估算（±50%，供立项决策用，不作为承诺）：

| 工作包 | 主要体量依据 | 估算（人日） |
| --- | --- | --- |
| A 基线/inventory/ADR | 扫描规则 + 7 份 ADR | 5–10 |
| B contracts + execution spine | **空仓从零 + 兼容迁移 8,857 行 `_ExecutionSession`** | 30–50 |
| C risk hard-gate | 修复 6,584 行存量 + durable ledger + 跨进程预留 | 20–30 |
| D monitor control plane | 3,376 行存量改造 + durable consumer + 命令通道 | 15–25 |
| E 聚合/parent-child/lifecycle | 全新状态机 + 两种 lifecycle supervisor | 25–40 |
| F Backtrader adapter + 14 迁移单元 | 落在 8.4k + 15.9k 行核心文件上的双路径改造 | 20–35 |
| G gateway + ZMQ transport | **一整套消息中间件**（CurveZMQ/ZAP、HWM、snapshot/replay、幂等） | 30–50 |
| H 验收/证据/文档 | 46–55 条 AC × 跨 7 仓证据 | 15–25 |
| **合计** | | **160–265 人日** |

单人执行约需 **8–13 个月**。即便 2–3 人并行（B→C/D 已有并行设计），也是 4–6 个月的全力投入。
这个数字必须摆在立项决策面前，由 owner 明确裁决：要么加人，要么拆分，要么砍范围。
**"按一个迭代静默开工、靠 NO-GO 兜底"是最差的选择** —— NO-GO 状态能防止错误发布，
但防止不了 6 个月后一个半成品架构卡在 E 和 G 之间。

### 2.2 【严重】WP41-G（gateway/ZMQ）阻塞最终裁决，但耦合度最低

依赖图上 G 排在 F 之后，H 要求逐子仓复核 gateway/transport_zmq（H6），M41-4 = G + H。
也就是说：**gateway 或 ZMQ transport 的任何延误都会扣住整个迭代的 `ARCHITECTURE_ACCEPTED`**。

但看内容：G4/G5/G6 是中间件产品级工作（wire protocol、CurveZMQ/ZAP、ACL、背压、
snapshot/cursor/replay、命令幂等、多租户验收）。它服务的场景——多策略共享账户——**在迁移矩阵的
P0 批次里没有任何一个单元是必须的**（P0 各单元的目标状态都是 `direct_provider` 或 managed，
`gateway_client` 全部是"可选"）。本迭代的核心业务价值（初始需求 1/2/3：减少前置条件、账户风控、
独立监控）在 A/B/C/D/F 就能全部达成。

**建议（对应修订项 R2）：** 将 WP41-G 拆出为独立迭代（如迭代 42），或至少把 M41-4 拆成两个
独立裁决点——execution/risk/monitor/adapter 可先行 `ARCHITECTURE_ACCEPTED`，不等待 gateway。
这不取消初始需求第 12/13 条，只是承认它是独立交付物，不该和核心风控绑死在同一张验收单上。

### 2.3 【高】B2 的迁移源没有退役路径 —— 计划给自己留了最忌讳的口子

计划最强调的就是"不得有第二真相源"（NO-GO 第 1 条：第二账户 ledger；D41-10：禁止第二 writer）。
但 B2 要求把 8,857 行的 `bt_api_py/_execution_session.py` **兼容迁移**到新的
`bt_api_execution` 包——这意味着迁移期内 SDK 私有 session 和公开 execution 包**并存**。
计划管住了 examples 的迁移（迁移矩阵），却没有一个工作包回答：

- 迁移期内 `bt_api_py` 内部调用点走旧 session 还是新包？双写期多长？
- 旧 `_ExecutionSession` 何时删除、以什么证据删除？
- 谁保证新路径上线后没有代码路径仍落在旧 session 上（这正是 inventory 扫描该覆盖的，但 A2 的
  inventory 范围是 examples/runner/writer，未明确包含 SDK 内部调用点）？

**建议：** 在 WP41-B 增加任务"B8：`_ExecutionSession` 退役计划"——定义调用点切换清单、双写期
退出条件、旧路径删除的验收证据；A2 的 inventory 扫描范围明确包含 `bt_api_py` 包内对
`_execution_session` 的所有引用。

### 2.4 【高】Windows 是 CTP 的目标平台，但计划没有把它当作平台约束

三条具体证据：

1. **模板 `ipc:///` 在 Windows 上不可用。** ZeroMQ 的 ipc:// 传输（Unix domain socket）在
   Windows 上长期不受支持（pyzmq 文档将其标记为 POSIX-only；libzmq 的 named-pipe 实现一直
   未稳定落地）。而 CTP 实盘恰恰运行在 Windows（迭代 27 已登记 Windows CTP 运行时问题），
   `security_profile: local-ipc-v1` 及三个 `ipc:///` endpoint 在首选部署平台上直接无法工作。
   应改为 `tcp://127.0.0.1:<port>` + CurveZMQ/ZAP 的本机 profile，或至少把 Windows 可用性
   验证列为 G5 的前置条件。
2. **fsync 成本。** `_ExecutionSession` 的 journal 是 JSONL + 每写 `os.fsync`。Windows/NTFS
   的 fsync 单次成本通常在毫秒级且抖动大，直接决定受管路径的延迟下限（详见 3.2）。
   `_execution_session.py` 已有 `msvcrt`/`fcntl` 双平台锁分支，说明团队有跨平台意识，但性能
   验收不能只在一个平台上做。
3. **验收等价物。** H2 的 fault-injection 列表含"磁盘满、时钟回拨、writer lease 争抢"——这些
   在 Windows 上的触发方式、语义与 POSIX 不同（如文件被占用时的删除/锁行为）。验收文档没有
   指定执行平台矩阵。

**建议：** 在 WP41-A 基线中显式声明交付平台矩阵（至少 Windows + 一种 POSIX），所有性能验收
（见第 3 节）必须在 Windows 上执行，因为那才是 CTP 的生产平台。

### 2.5 【中】46 条 AC × 14 迁移单元的证据采集没有自动化设计

验收文档要求每个 PASS 保存 7 个 Git 身份的 commit/pin/wheel hash、JUnit、脱敏指纹、零写计数。
`evidence/README.md` 只定义了**命名规则**，没有任何"如何生成"的设计。按 46 条 AC × 14 迁移单元
的量级，人工收集证据会吞掉 H 阶段的大部分工时，并且必然出现证据缺失/过期导致的返工。

**建议：** 在 WP41-A 或 H 中新增交付物：`evidence collector` 脚本/CI job——一条命令生成符合
命名规范的脱敏 receipt（身份、pin、hash、命令、结果自动嵌入），跨仓 CI matrix 在每次 pin 变更
时自动重跑受影响的 consumer 验收。这应是 A 阶段就交付的工具，而不是 H 阶段的手工活。

### 2.6 【中】与本仓开发纪律的衔接缺失

- `BtApiBroker`/`BtApiStore` 在 **Backtrader 核心包**（不是 examples），改动影响全部 SDK 用户。
  本仓 CLAUDE.md 明确要求：动 broker/clock 逻辑必须跑 `make test-strategies`（1,271 个回归测试）。
  计划 AC41-27 只说"回测既有回归不倒退"，没有指名测试集。**建议明确写入：WP41-F 的每个变更
  必须通过 `make test-strategies` 全量 + 该 example 的 replay 回归，作为 PR 合并门槛。**
- 新增的 fault/multi-process/contract 测试体量大，需要并入本仓 tiered pytest 体系
  （`make test-fast`/`test-slow`），否则会破坏日常 3.5 分钟的快速反馈回路。建议 F8/H2 交付时
  同步登记 `tests/functional/strategies/.test_durations.json`（用
  `scripts/refresh_strategy_durations.py` 刷新），把慢测试自动归入 slow 档。

### 2.7 【中】direct 路由的账户级限额在多进程下语义不明（正确性×性能交叉点）

NO-GO 只要求 **managed** 额度 durable（"本应 durable 的 managed 额度在重启/多进程下归零/竞争"）。
direct 路由启用 risk 时，若多个策略进程以 `direct_provider` 共享账户（计划允许此组合），
每个进程内的 risk plugin 实例各自持有计数器，"账户级 max_new_entries_per_epoch" 实际是
**每进程**的——限额被静默放大 N 倍。要让它真 durable，就要付跨进程锁 + fsync 的延迟成本
（见 3.2），而计划没有为此定价。

**建议（对应修订项 R6）：** 显式二选一并写进设计文档：
(a) 声明 direct 路由的限额为进程内语义，多进程共享账户必须走 gateway（server-side 强制）或
managed（durable permit）——这是推荐项，把性能成本和保障等级清晰挂钩；
(b) direct 限额也 durable 化，同时接受其延迟代价并纳入性能预算。

## 3. 性能专项审查（技术经理核心意见）

**本 fork 的立身之本就是性能**（CLAUDE.md 第一句即 performance-oriented fork，且明文要求
"热路径最小化 isinstance/hasattr/len"）。而这份计划全文**没有出现任何延迟、吞吐或资源预算**。
量化交易员审阅 4.5 已指出此点但归为 P2——**我不同意这个优先级。对这个仓库而言性能预算是 P0/P1，
理由如下。**

### 3.1 受管路径每单成本：可预见的 fsync 链

计划的受管写入序列（B/C/E 段）为：

```text
intent 持久化 → RiskPermit 预留（durable）→ journal 写入 → dispatch → outbox 事件
```

现状证据（第 1 节）：`_ExecutionSession` 的 journal 是 JSONL + 每写 `os.fsync`（10 处调用），
且计划 B2 要求"兼容迁移"而非重写。C3 又要求"risk reservation 与 execution journal 使用同一
事务边界或同一 writer lease 协调"——若两者是独立文件（journal JSONL + risk ledger），一次下单
就是 **2 次独立 fsync + 2 次锁获取**，加上 intent/outbox 可达 3–5 次同步磁盘写。
Windows/NTFS 单次 fsync 毫秒级且抖动大，**受管路径每单固定成本可预估在 5–30ms 量级**，
这是结构性的，不是调优能消除的。

结论与建议：

1. **冻结存储后端选型 ADR（WP41-A5 现有 ADR 清单里没有这一项）。** 候选：单一 SQLite（WAL
   模式，journal 与 risk ledger 同库同事务 = 每单一次 commit fsync，WAL 在 Windows 上表现良好）
   vs 现状 JSONL+fsync×N。这是 B 段动工前必须做的决定，否则 C3 的"同一事务边界"没有实现载体。
2. **定义 durability 分层。** intent + permit 必须 dispatch 前 durable（可合并为单事务单 fsync）；
   outbox/checkpoint/telemetry 允许 group-commit 或异步批量。不是所有事件都值得一次 fsync。
3. **把延迟预算写成 NFR + AC**（见第 6 节 AC41-56/57 建议）：受管路径每单新增同步开销
   （不含网络与柜台）p99 ≤ X ms，X 由 ADR 冻结；超出即验收失败，而不是"上线后再调优"。

### 3.2 013_2（高频日历套利）不应默认上 managed rail

迁移矩阵 P0-F 把 013_2 的目标定为"与 013_1 同一 managed execution rail"。按 3.1 的分析，
受管路径的毫秒级固定成本对"高频日历套利"很可能是**不可用**而非"略慢"。计划对 015（HFT）明确
保持了观测边界，却没有对 013_2 做同样的适配性声明——这是遗漏。

**建议：** P0-F 的目标状态修改为三选一并由该候选的研究政策裁决：保留 `legacy_direct`（+
risk/monitor）、shadow/观测接入、或迁入 managed rail **但必须先通过 3.1 的延迟预算验证**。
不要让迁移矩阵隐含"managed 适用于一切策略"的默认。

### 3.3 legacy_direct 零开销承诺需要量化，否则必然回归

计划承诺"无 config 时不 import 插件、direct submit/cancel 行为不变"（AC41-44）。但"行为不变"
不等于"性能不变"：`BtApiBroker.submit()` 已经是 8,376 行文件里串行 10+ 道校验的热路径，本迭代
还要在其上叠加 route 判断、risk gate、monitor control gate 三类新入口检查。本仓
`btapistore.py` 热路径里已存在多处 `getattr(self.store, "get_symbol_routes", None)` 反射模式
——**不能再用这个模式实现 route/gate 挂接**。

**建议（对应修订项 R4）：**

1. F1/G2 的实现合同：route、risk、monitor 在 `__init__` 期一次性解析为**扁平 gate 链**
   （一次构建、按序调用），禁止 per-submit 的 dict 查找、`getattr` 反射和 try/except 包裹；
   未启用的 gate 必须从链中**物理缺席**，而不是运行时跳过。
2. 新增微基准验收（挂入本仓已有的 `tests/performance/`/`tests/bench/` 基础设施）：
   无插件 direct 路径 `submit()` 相对当前基线的延迟回归 ≤ 阈值（建议 ≤5%，随 ADR 冻结）。
   该基准进 CI，防止后续迭代无声地磨慢直连路径。

### 3.4 共享账户的吞吐上限要写成容量声明

writer lease + 单一 durable ledger 意味着**账户级串行化**：同账户所有策略的下单在 ledger 写入点
排队。按 3.1 的每单成本，单账户吞吐上限约在每秒几十至几百单。对当前策略集（低频/中频）足够，
但必须写下来，原因有二：

1. gateway（G6）会把多策略命令**汇聚到单一 server**，server-side admission 又要过 risk/execution
   gate——server 既是吞吐单点又是延迟单点。G5 有 transport 层的 HWM/backpressure，但
   **admission 层没有吞吐预算**。
2. 不写容量声明，未来一定会有人把延迟敏感策略塞进来，然后抱怨"框架慢"。

**建议：** H2 增加固定的账户级 order-path 吞吐/延迟基准（fake provider、多策略并发），每版本
记录数据防止倒退；README 模板增加"本架构的适用频率范围"一节。

### 3.5 monitor 的资源预算缺失

monitor 是 7×24 常驻进程（crypto 场景）。计划定义了它观察什么，没定义它自己消耗什么：
消费滞后阈值（"对账滞后"有字段无阈值）、checkpoint 频率与磁盘占用上限、内存/CPU 上限、
alert 风暴的抑制规则（D3 有去重/升级，无速率上限）。一个监控进程泄漏一个月就是实盘事故。

**建议：** D 段新增 NFR：monitor 空载 CPU/RSS 上限、outbox 消费最大滞后（如 ≤ N 秒，超限自告警）、
checkpoint/retention 磁盘占用上限。ADR-41-05 的 retention ADR 把这些数字一并冻结。

### 3.6 Backtrader 框架层隔离：runonce/runnext parity 必须点名

F2 的 managed allocation 回灌改变 `notify_order`/`notify_trade` 的产生方式。本仓已知最高发的
bug 类正是 runonce（向量化）与 runnext（事件驱动）的 clock/对齐分歧（见 CLAUDE.md
"Indicator registration & multi-data clocks"节与 `docs/DEV_REGRESSION_FAILURES.md`）。
计划 AC41-27 只说"回测既有回归不倒退"，**没有点名 runonce/runnext 双模 parity**。

**建议：** AC41-27 增加子项：adapter 的 allocation 回灌与 route 投影必须在 runonce 与 runnext
两种模式下产出一致（以既有 branch-compare 工具 + TradeLogger 比对），防止只在一种模式下"看起来对"。

## 8. 结语

这份计划的安全设计水平，坦率地说，高于我见过的大部分实盘系统——**方向完全正确，一条安全边界
都不应该放松**。我的修订建议没有一条是"降低标准"，全部是三类：

1. **把"做得完"变成显式决策**（R1/R2/R5/R8）：估算、拆分、退役路径、证据自动化；
2. **把"跑得快"变成显式合同**（R3/R4/R6/R10）：存储后端、durability 分层、延迟/吞吐预算、
   热路径实现纪律、容量声明；
3. **把平台现实变成显式约束**（R7）：Windows 是 CTP 的生产平台，不是配角。

安全边界决定这套架构**能不能上**；性能与可行性决定它**上去了会不会被绕过、能不能按时上**。
一个每单多花 30ms 的受管路径，和一个 8 个月后只交付一半的迭代，最终都会把用户推回
`legacy_direct` —— 那才是对这套安全设计最大的辜负。

请在冻结前完成 R1/R2/R3 的裁决。其余修订项可随各工作包动工节点落实，但 owner 的裁决意图
需要现在记录进计划。
