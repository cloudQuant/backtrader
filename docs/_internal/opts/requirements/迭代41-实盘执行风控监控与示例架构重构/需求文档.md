# 迭代 41 需求文档

状态：`PLANNED`。本文件把用户提出的“减少每个实盘策略的前置条件、建立账户级风控和运行监控、
重构所有可写 examples”转为可验证需求。它不替代各候选的研究、审批或真实交易验收合同。

## 1. 术语

| 术语 | 定义 |
| --- | --- |
| `ExecutionIntent` | 策略产生的、尚未向 provider 写入的交易意图；必须含策略归因、账户范围、有效期与风险标签。 |
| `ParentExecution` | 由一个或多个兼容 intent 形成的耐久执行计划，不表示 provider 已原子接受。 |
| `ChildIntent` | 实际映射到一个 venue/provider 写入、撤单、replace 或 native algo 的最小可对账动作。 |
| `RiskPermit` | 风控在原子预留成功后发给 execution 的不可伪造能力；绑定 scope、policy、额度、有效期和 fencing。 |
| `ExecutionScope` | provider、environment、account fingerprint、账户/策略、TradingDay 或 rolling epoch、连接 generation 的组合身份。 |
| `freeze` | 禁止新的风险增加型动作；不等同于遗忘已知挂单或拒绝必要的 reduce-only 清理。 |
| `drain` | 冻结开仓后，在明确定义的 deadline 内撤单、降低风险、对账并形成终态证据的过程。 |
| `monitor` | 独立于策略主循环的控制面观察者；消费耐久 execution/risk 事件和 heartbeat，不拥有普通开仓权限。 |
| 能力子仓 | `bt_api_execution`、`bt_api_risk`、`bt_api_monitor`、[`bt_api_gateway`](https://github.com/cloudQuant/bt_api_gateway)、`bt_api_transport_zmq` 分别作为独立 Python 包，挂载、已创建待打包或拟挂载为 `D:/bt_api_py/bt_api/` 下的 Git submodule；它们不是 `bt_api_py` 的复制源码目录。NATS/Redis transport 不在本轮创建范围。 |
| SDK integration | `bt_api_py` superproject 中显式版本化的 optional dependency、adapter 与 provider wiring；它组装能力包，不隐式导入、vendor 或重新实现其领域状态。 |
| `LegacyDirectPath`（既有直连路径） | Backtrader `Strategy → BtApiBroker/BtApiStore → bt_api_py/provider` 的既有下单链路。运行目录没有 `config.yaml`、没有 `plugins`、所有插件 disabled 且均为 `required:false`，或有效配置显式 `runtime.order_route=legacy_direct` 且 `plugins.execution.enabled=false` 时保留此路径；它不创建 execution 的 `ExecutionIntent`、parent/child journal 或 allocation。后者仍必须加载、验证并 attach 任一显式 enabled plugin。若 risk/monitor 被启用并 attach 成功，它们仍分别在真实写入/控制边界执行 hard gate、freeze/drain；它仍受 provider 原生认证、会话、协议字段、交易所/venue 规则及该既有 runner 自身条件约束。 |
| `ManagedExecutionPath`（受管执行路径） | 仅在本地 `config.yaml` 显式 `plugins.execution.enabled=true` 且 `runtime.order_route=managed_execution` 时选择的 Iter41 链路：framework order 映射为 intent/plan，随后由 `bt_api_execution` 负责 journal、capability、reconcile 和可选的 risk/monitor 集成。显式请求该路径却缺包、pin 或配置不兼容时必须 fail-closed，不得暗中回退为直连。 |
| `StrategyRuntimeConfig` | 对 execution、risk、monitor、gateway、transport_zmq 五个可选能力的本地 `config.yaml` 合同；它声明 schema 版本、strategy identity、运行模式、`order_route`、`account_access`、凭据来源/本地凭据和插件启用/参数。该文件必须被 Git 忽略；仓库只提交无秘密的 `config.example.yaml` 模板。它不是账户级额度、订单事实或 provider 权限的真相来源，也不是既有直连路径的必需前置条件。 |
| 插件组合 | 已提供 `config.yaml` 时，`plugins.{execution,risk,monitor,gateway,transport_zmq}` 的显式启用组合及其控制边界。execution 仅在 managed route 接管订单编排；risk/monitor 可以在 direct 或 managed route 生效，且在 direct 中也是实际 hard gate/control；gateway 选择共享账户拓扑，transport_zmq 仅实现该 gateway transport。插件可独立选择，但 gateway client 与恰一个 transport 必须成对；loader 绝不隐式补齐、降级或把某组合误标为受管。 |

> **2026-09-21 架构修订：** 本迭代的配置根为 `plugins`（schema v3），不是旧草案中的
> `modules` 或 schema-v2 的 `plugins.zmq`。`legacy_direct` 中已启用并 attach 成功的 risk/monitor 是实际
> hard-gate/control，不是 advisory/telemetry。`bt_api_gateway` 与 `bt_api_transport_zmq` 分层，完整加载、
> 路由与安全边界见[插件、网关与传输架构](插件与ZMQ架构.md)。

## 2. 功能需求

| ID | 需求 | 可观察完成条件 |
| --- | --- | --- |
| FR41-01 | 建立可选的 provider-neutral managed execution 入口 | 显式 `plugins.execution.enabled=true` 的 example 经 `bt_api_execution` 发出 child；在该受管路径中，策略、Backtrader observer、monitor 均不能直接调用 provider writer。不得删除或把既有 `Strategy → BtApiBroker/BtApiStore → provider` 直连路径强制迁入 execution：无 `config.yaml` 或 execution disabled 时该路径保持可用。 |
| FR41-02 | 支持受管的带归因订单聚合 | managed execution 合并前保存每个 intent 的策略、候选、风险和价格/时效约束；相反或不兼容 intent 不得静默合并。既有直连订单继续按其当前 provider 映射运行。 |
| FR41-03 | 支持受管 parent/child 执行和成交分配 | managed parent、每个 child、部分成交、费用、funding、未知状态与 `FillAllocation` 均可重放和对账；直连路径不被要求制造这些受管对象。 |
| FR41-04 | 支持受管的明确执行模式 | 每个 managed plan 显式标记 `immediate`、`passive`、`slice`、`native_algo`、`basket_best_effort` 或 provider-native atomic；不支持即拒绝。 |
| FR41-05 | 建立可选的账户级硬风控 | 启用 risk 时，无论 direct 或 managed，普通开仓、普通撤单、replace、紧急撤单/减仓都在真实 Broker/Store 写入边界被评估并可拒绝；涵盖次数、频率、名义金额、仓位、保证金、损失、未知订单和账户冻结。managed 另做 durable reservation/permit/settlement。 |
| FR41-06 | 将风控与 dispatch 原子衔接 | managed 的 child 在 transport 前必须验证未过期 `RiskPermit`；direct 的单笔写入必须经过同一 risk plugin 的 hard decision。持久化/插件故障、scope 不一致、未知订单或 permit 无效均 fail-closed，且 provider write count 为零。 |
| FR41-07 | 建立可选的 durable monitoring 控制面 | monitor 可读取 managed execution outbox 或 direct Store/Broker runtime event、风险状态和 heartbeat，生成告警与 `freeze_new_entries`、`drain`、`manual_intervention` 请求；这些请求只能经 Broker control gate 生效，monitor 不得普通开仓或自动 resume。 |
| FR41-08 | 监控策略进程之外的运行状态 | monitor 检测进程/心跳失活、行情陈旧、连接代次、队列、磁盘、对账滞后、风险额度与 TradingDay/rolling epoch 漂移；启用 direct monitor 时其 freeze/drain 也必须真正拦截对应 Broker writer。 |
| FR41-09 | 提供双路径 Backtrader 薄适配 | `BtApiStore/BtApiBroker` 在 `plugins.execution.enabled=true` 时映射 framework order 到 intent/plan 并以 allocation 回灌；无 execution 时保留既有 framework order 到 provider 的直连映射和通知语义，但对已启用 risk/monitor 挂接真实 hook/control gate。 |
| FR41-10 | 受管路径拒绝不支持的 bracket/OCO/basket | `execution=true` 时，未协商 provider capability 的 `parent`、`oco`、`transmit`、native batch、slice 等请求不能退化为多笔普通写入。既有直连路径继续遵循其现有 BtApiBroker/provider 语义，不得因 Iter41 补写一套“已验证原子性”的声明。 |
| FR41-11 | 按市场分离受管长期生命周期 | 受管 CTP 以审核过的交易时段和 TradingDay 边界 drain/reconcile；受管 crypto 采用 7×24 rolling checkpoint，不因健康 checkpoint 杀死会话。既有直连路径保留现有 provider session 行为，不因未启用模块而被强加 Iter41 lifecycle gate。 |
| FR41-12 | 分类迁移所有可写 examples | 每个写入入口被分类为“保留既有直连”“迁入受管 execution”“禁用”或“不适用”，并完成 README、双路径回归和无意外回退验证。迁入受管路径不得在失败时回退直连；保留直连路径不得被强制要求任一运行时插件或 `config.yaml`。 |
| FR41-13 | 实际实现并发布五个能力包与两个 adapter | execution、risk、monitor、gateway、transport_zmq 五个能力包必须各自在对应 Git submodule 中有真实源码、测试、版本化制品与 consumer 验收；`bt_api_py` 必须提交其 pin、optional dependency/integration adapter，Backtrader adapter 也必须有真实源码与测试。当前空 execution pin `2700cb5`，新建但尚未 package 的 gateway repo，以及近期拟建 transport_zmq 子仓，在有完整 package skeleton/wheel/pin 前都必须维持 `NOT_PACKAGED`/strict 非零且无 PyPI fallback。不得以文档、mock、vendor copy 或 example 内复制代码替代。 |
| FR41-14 | 以策略运行目录 `config.yaml` 可选地组装插件与凭据 | 仅从规范化后的 `<strategy-runtime-dir>/config.yaml` 加载 schema-v3、strategy identity、运行模式、`runtime.order_route`、`runtime.account_access`、连接/凭据和 `plugins.{execution,risk,monitor,gateway,transport_zmq}` 的 `enabled`/`required`/`config`。无文件、无 `plugins` 或 all-disabled 且均为 `required:false` 时不 import/init 插件且保持 direct provider。每个迁移目录提交无秘密 `config.example.yaml`，本地 `config.yaml` 被局部 `.gitignore` 忽略；loader 永不把 template 当运行时回退，也不得由 CLI/环境变量/CWD/父目录隐式开启插件。 |
| FR41-15 | 校验路由、账户访问、插件组合与配置授权边界 | execution/risk/monitor/gateway 可按合同独立启用；execution 仅在 `managed_execution` 接管 provider 写入，risk/monitor 可在两条路由真实工作；`gateway_client` 必须启用 gateway 和恰一个 transport，本轮仅支持 transport_zmq。已启用包的 package/pin/schema/attach 任一失败必须零 I/O fail-closed；未启用包不得 ambient import。gateway client 不得携带 provider credential 或伪造 account/strategy 权限。 |
| FR41-16 | 建立运行时插件与 transport 管理器 | `bt_api_py` 以独立 `bt_api.runtime_plugins` entry point、descriptor、pin/version/schema 校验和生命周期管理只加载 enabled execution/risk/monitor/gateway/transport_zmq；`GatewayTransportRegistry` 只在 gateway 启用且账户接入为 `gateway_client` 后加载所选 transport_zmq。不得复用会加载全部 exchange adapter 的 `bt_api.plugins`。所有插件必须经受限 lifecycle hooks attach 到唯一 Broker/Store/execution write boundary。 |
| FR41-17 | 实现中间件无关 gateway 与首个 ZMQ transport adapter | `bt_api_gateway` 提供共享账户会话、订阅并集/fan-out、strategy/order correlation、snapshot/replay 与 command admission contracts；`bt_api_transport_zmq` 提供 versioned ZMQ wire、server-side write gate、auth/ACL、backpressure、sequence/gap、command idempotency/unknown/reconcile。两者不能形成第二 OMS/risk/account truth；在 CTP gateway 完成单独端到端验收前，不得将 CTP gateway 写入标为支持。 |

## 3. 非功能需求与不变量

| ID | 不变量 |
| --- | --- |
| NFR41-01 | `bt_api_execution` 是**受管路径**的唯一写入编排权威；既有 direct REST/CTP/provider wrapper 仍可由现有 `BtApiBroker/BtApiStore` 链路调用，不能被新增模块强制移除。受管路径不得绕过 execution 直接写 provider，也不得在 execution 失败时暗中改走直连。 |
| NFR41-02 | 受管耐久状态按 `ExecutionScope` fencing；账户、TradingDay/epoch、环境、connection generation、policy hash 或代码/配置身份变化均不能继承旧 permit。既有直连路径不伪造或消费该 permit，其 provider-side order/session identity 继续按原有协议处理。 |
| NFR41-03 | 受管路径不得将 provider-native 多请求、顺序多腿或批量撤单表述为原子 basket/OCO，除非 capability 与远端回执共同证明。直连路径也不得因 Iter41 而新增未经 provider 证明的原子性承诺。 |
| NFR41-04 | 受管且启用 risk 时，风险降低型动作有独立、有限的紧急额度；普通撤单/开仓不能耗尽其清理能力，未知状态下不自动重试开仓。direct+enabled risk 也必须在 provider write 前真实作出允许/拒绝，direct+enabled monitor 也必须通过 Broker control gate 真正 freeze/drain；但 direct 不会因此伪造 execution 的 durable reservation、journal 或 recovery 保证。 |
| NFR41-05 | 本地、被 Git 忽略的 strategy `config.yaml` 可以在严格的 provider-specific credential schema 中保存凭据；仓库中的 `config.example.yaml`、`TradeLogger`、metrics、报告、README、receipt、异常消息和日志则绝不得泄露凭据、完整账户标识、capability 或恢复 token。对**显式插件配置**的 loader 必须在解析后立即将凭据隔离/脱敏，且 managed public config fingerprint 只能基于 canonical redacted projection（不得以可离线猜测秘密的原始配置 hash 代替）。`.env`、OS secret store 或等价受管注入仍是可选来源；它们不能把直连路由隐式切换为 managed execution。 |
| NFR41-06 | 受管 `PASS` 绑定 Backtrader、`bt_api_py` superproject 和**已启用**能力 submodule（含 gateway 与 selected transport）的 commit/wheel/hash、submodule pin、解释器、命令、脱敏证据和运行模式；直连兼容性 `PASS` 绑定实际 Backtrader/SDK/provider 版本、`order_route`/`account_access` 选择及其 provider-native 条件，且不得伪造未启用能力已经生效。本地、replay、shadow、SimNow、production 结论严格分开。 |
| NFR41-07 | 五个能力包按公共 contracts 的兼容版本发布；`bt_api_py` 的 integration 必须声明并锁定其兼容范围。显式请求某 capability 而对应包缺代码/测试/consumer 证据时，依赖方不得用私有对象、monkey patch、vendor 或 example-local copy 替代，并且该 capability 请求必须 fail-closed；这不删除未选择插件的既有直连能力。 |
| NFR41-08 | `StrategyRuntimeConfig` 是**显式插件配置**的安全相关参数声明层：环境变量、`.env`、CLI、默认工作目录或 Python import 副作用均不得覆盖 `order_route`、`plugins.*.enabled`、mode、profile、risk/lifecycle/execution/transport policy。每次 managed 解析形成不含秘密的 canonical redacted config fingerprint，并进入 `ExecutionScope`/evidence；任何影响写入的插件配置变更必须 freeze、drain 或停止后以新 preflight/identity 启动，不能静默热加载沿用旧 permit。无 `config.yaml` 的既有直连路径不是此 loader 的失败条件。 |
| NFR41-09 | `config.yaml` 的 plugin `config` 参数只可由版本化、allowlist 的 execution/risk/monitor/gateway/transport_zmq schema 解释；不得接受任意文件路径、Python object/class、未锁定 URL、未声明 profile 或会放宽账户级 hard limit 的 override。允许的 runtime-local artifact 路径必须是相对路径，realpath 后仍位于 strategy runtime 内；受管账户级 journal/ledger 仅能由认证后的 SDK account scope 派生、跨策略共享并受 writer lease 保护。未安装、空仓、pin/version 不匹配或 schema 不兼容的**显式插件**一律 fail-closed；`plugins.execution.enabled=true` 失败时绝不静默改走直连。 |

## 4. 已知能力包基线与集成约束

`bt_api_risk` 将作为 `D:/bt_api_py/bt_api/bt_api_risk` Git submodule 使用。它可复用 policy authoring、
limit calculation、风险事件和分析模型，但当前默认分支的
`check_order_risk()` 未将部分 limits/policy 拒绝可靠合并为最终拒绝，频率状态也未形成耐久账户级
计数；它必须先完成 WP41-C，不能直接成为实盘写入门。

`bt_api_monitor` 将作为 `D:/bt_api_py/bt_api/bt_api_monitor` Git submodule 使用。它可复用 metrics、
health probe、Prometheus/Grafana/ELK exporter，但当前指标历史和健康循环是进程内能力；它必须在 WP41-D
接入 execution outbox、durable checkpoint 和控制命令。

`bt_api_execution` 将作为 `D:/bt_api_py/bt_api/bt_api_execution` Git submodule 新建；初始子仓为空，不能把
`bt_api_py` 私有 `_ExecutionSession` 的存在误报为该包已经实现。它可在兼容迁移中复用 SDK 的稳定机制，
但必须有自己的公开 contracts、版本、测试和 consumer 证据。

[`bt_api_gateway`](https://github.com/cloudQuant/bt_api_gateway) 已创建为 public repository，但在 package skeleton、
独立 wheel、pin 与 consumer 测试完成前保持 `NOT_PACKAGED / NOT_ATTACHED`。它只依赖无 transport 的 shared
contracts（位于 `bt_api_base` 或单独 contracts 包），并通过受限 provider port 接收 SDK integration adapter；
不得依赖 `bt_api_py`。`bt_api_transport_zmq` 将作为首个独立 Git submodule 新建，只依赖 gateway/shared contract，
拥有 socket/security/generic relay 与 `pyzmq`；不得依赖 `bt_api_py`，以避免循环。provider-aware router、
execution/risk 真相与兼容 facade 留在 SDK integration 层。

五个包在运行时只经显式 dependency/integration adapter 连接：`bt_api_execution` 提供最小 execution contracts 和
`RiskGate` protocol，`bt_api_risk`/`bt_api_monitor` 可依赖兼容 contracts 版本，gateway 依赖 shared contracts，
transport_zmq 依赖 gateway/shared transport contract；execution 不得反向导入它们的 concrete 实现。`bt_api_py`
负责选择、注入和锁定可选组合；
provider 子仓不得承担 risk/monitor/execution/transport 的领域状态。

选择新增模块的策略 runner 必须通过 SDK integration 的 `StrategyRuntimeConfig` loader 读取本运行目录的
`config.yaml`，而不是自行解析五个包的配置。相邻、受版本控制的 `config.example.yaml` 只用于复制和校验模板，
绝不可被 loader 当成运行时回退。配置可选择受管 provider/credential profile，也可在该 profile 的严格字段中
保存本地凭据；风险 policy/profile、monitor profile 和 strategy-level tightening parameters 仍由 schema 限定。
账号 identity、批准根及受管 provider client 只能在受管预检/认证后派生或创建。gateway client config 不得包含
provider credential；它只能选择已认证 gateway endpoint/profile。**没有 `config.yaml` 时 runner
必须保留既有 `BtApiBroker/BtApiStore/provider` 直连路径，而不是报错或尝试加载任一 runtime capability。**当前 execution 子仓为空时，
任何 `plugins.execution.enabled=true` 的配置都必须以 `NOT_PACKAGED` 拒绝，绝不回退到私有 `_ExecutionSession`、ambient
editable 包、PyPI 或既有直连路径；这不影响明确未启用 execution 的直连运行。

## 5. 明确非范围

- 不因为本迭代而批准任何 `RESEARCH_REJECTED`、`RESEARCH_NOT_ESTABLISHED` 或 `NOT_ADMITTED` 候选交易；
- 不把 SimNow credentials、期货公司 production credentials、审批根或账户原件写入仓库、
  `config.example.yaml`、日志或验收证据；它们可以只保存在被 `.gitignore` 忽略的本地 `config.yaml` 或受管
  secret provider 中；
- 不承诺交易盈利、成交质量、CTP 官方前置写入或 production CTP 接入已经通过；
- 不用 Backtrader 的回测 `BackBroker` bracket/OCO 行为为实盘 provider 语义背书；
- 不以删除门禁、扩大 timeout、伪造 TradingDay/日历或重试未知订单来达到“长期运行”。
- 不把五个能力包 vendor 到 `bt_api_py`、Backtrader 或 examples，也不以未 pin 的 submodule、ambient editable
  import 或隐式 extras 代替受控集成。
- 不以 Iter41 取消既有 Backtrader `Strategy → BtApiBroker/BtApiStore → provider` 直连能力，或把缺少
  `config.yaml` 本身视为直连策略的启动错误；直连仍须遵循其 provider 原生认证、会话和协议条件。
