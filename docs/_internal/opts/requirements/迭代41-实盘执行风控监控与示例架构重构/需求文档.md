修订基线：`baseline-4 / 2026-09-23`。四份审阅与后续配置合同更新的处理见[审阅裁决记录](审阅裁决记录.md)，

不表示代码已经实现、人员已承诺工期或测试已经 PASS。

**必要性与顺序：** FR41-01～16、18～22、25 为核心阶段 Must；FR41-17 为 gateway 阶段 Must；
FR41-23～24 为 AI 互操作阶段 Must。FR41-13 的五包完整交付属于全架构完成门，核心阶段只验其
execution/risk/monitor 和两个 adapter 子集。阶段是交付顺序，不是删除需求；monitor 的运行健康、
告警及 control gate 属于核心 Must，与 risk 同级，丰富 exporter 为 Should。
高级执行模式按 capability 声明验收，不支持的模式必须有明确拒绝用例，不能虚构支持。

**配置作用域（基线 3）：** 每个 inventory 显式登记的 runtime directory 必须有且只能有一个本地、被精确忽略的
`config.yaml`，并以 schema v4 作为启动唯一入口；同目录受版本控制的 `config.example.yaml` 是其可审阅模板。文件缺失、未登记、schema v3 或更旧、非法 mode/preset 都必须在
初始化 provider 或插件前拒绝。历史无秘密参数文件须通过显式迁移生成 v4；不得因同名自动解释、取消跟踪、忽略或保留
无配置启动兼容入口。普通 profile 可继续以 `secrets_ref` 引用被忽略的 `secrets.yaml` 或操作系统 secret store；CTP SimNow 私有 profile 则按使用者更新要求，在不被 Git 跟踪且权限受限的 `config.yaml` 中配置成对的 `md_front`/`td_front`、合约范围和认证字段。两类配置均不得允许模式、能力或审批提升，也不得把秘密写入模板、日志或公开摘要。
用户不手工选择插件组合：版本化 preset registry 从 mode/preset 推导只读 effective route/access/capability 合同，
高级参数只能收紧已声明限制，不能增加写入权限。

**2026-09-24 CTP configuration direction (supersedes earlier separate-production-schema clauses):** the active and future operator contract uses one physical `examples/013_3_sa_midfreq_simnow/runtime-ctp-private/config.yaml` path and one canonical `ctp:` field shape for SimNow and production. SimNow is the active first phase. The protected file currently contains SimNow values; do not prefill production account/front values or request production credentials now. After implementation and separate acceptance, the intended operator action is to edit only this same file: set `runtime.mode: live`, `runtime.preset: managed_live_direct`, and replace account/front/contract parameters. This config-only switch is a target workflow, not current capability: the shared CTP execution runner live dispatch and mode-specific write admission are not wired to the default registry, so changing values alone must fail closed. Existing `ctp_production` parser, second `runtime-production/` path, and production prepare helper are legacy/deferred migration code/test evidence, not required operator flow. Canonical shared parser/helper/private-config migration is implemented; pure same-path production admission contracts exist but remain unregistered.

## 1. 术语

| 术语 | 定义 |
| --- | --- |
| `ExecutionIntent` | 策略产生的、尚未向 provider 写入的交易意图；必须含策略归因、账户范围、有效期与风险标签。 |
| `ParentExecution` | 由一个或多个兼容 intent 形成的耐久执行计划，不表示 provider 已原子接受。 |
| `ChildIntent` | 实际映射到一个 venue/provider 写入、撤单、replace 或 native algo 的最小可对账动作。 |
| `RiskPermit` | 风控在原子预留成功后发给 execution 的不可伪造能力；绑定 scope、policy、额度、有效期和 fencing。 |
| `ExecutionScope` | provider、environment、account fingerprint、账户/策略、TradingDay 或 rolling epoch、连接 generation 的组合身份。 |
| `freeze` | 禁止新的风险增加型动作；不等同于遗忘已知挂单或拒绝必要的 reduce-only 清理。 |
| `drain` | 冻结开仓后，在明确定义的 deadline 内撤单、降低风险、对账并形成终态证据的过程。 |
| `monitor` | 独立于策略主循环的控制面观察者；消费耐久 execution/risk 事件和 heartbeat，不拥有普通开仓权限。 |
| 能力子仓 | `bt_api_execution`、`bt_api_risk`、`bt_api_monitor`、[`bt_api_gateway`](https://github.com/cloudQuant/bt_api_gateway)、`bt_api_transport_zmq` 分别作为独立 Python 包，挂载、已创建待打包或拟挂载为 `D:/bt_api_py/bt_api/` 下的 Git submodule；它们不是 `bt_api_py` 的复制源码目录。NATS/Redis transport 不在本轮创建范围。 |
| SDK integration | `bt_api_py` superproject 中显式版本化的 optional dependency、adapter 与 provider wiring；它组装能力包，不隐式导入、vendor 或重新实现其领域状态。 |
| `LegacyDirectPath`（既有直连适配） | Backtrader `Strategy → BtApiBroker/BtApiStore → bt_api_py/provider` 的既有映射代码。它可由某些 v4 `simulation` preset 作为受写入封锁的内部 adapter 使用，也可作为 `managed_live_direct` 的连接侧适配；不能由无配置、CLI flag 或手写 `order_route` 直接选择。它不伪造 execution 的 `ExecutionIntent`、parent/child journal 或 allocation；任何被 preset 启用的 risk/monitor 仍须在真实写入/控制边界硬拦截。 |
| `ManagedExecutionPath`（受管执行路径） | v4 preset 为已获准写入的 sandbox profile 或 live 解析出的 Iter41 链路：framework order 映射为 intent/plan，随后由 `bt_api_execution` 负责 journal、capability、reconcile 和 risk/monitor 集成。sandbox 私有只读 profile 不是此路径。所需包、pin、审批、账户能力或配置不兼容时必须 fail-closed，不得暗中变为直连或只读。 |
| `StrategyRuntimeConfig` | 所有纳入 inventory 的 runtime 必备的本地 schema-v4 `config.yaml` 合同；它被精确忽略，同目录受版本控制 `config.example.yaml` 是其审阅模板。它声明 strategy identity、`runtime.mode`、`runtime.preset`、策略参数和 `secrets_ref`。普通 profile 不含本地凭据；受限的 CTP SimNow `simulation/sandbox` 私有扩展可在本地 config 中包含 CTP MD/TD 地址、合约范围和认证字段。操作者可填写一组成对的 `md_front`/`td_front`，也可提供至多 8 组成对且无重复的 `front_pairs`；不得与旧单对字段并用。单对直接使用；多对只在这份显式配置的候选中按有界、无凭据 TCP 探测结果选择。地址不受静态官方前置 allowlist 限制。旧 profile/selection/calendar 选择字段拒绝；配置仍不得授予插件、审批或写权限。版本化 preset registry 独占解析 route、account access、审批 receipt 绑定与 execution/risk/monitor/gateway/transport 能力。它不是账户额度、订单事实、provider 权限或审批本体的真相来源。 |
| 有效能力组合 | `StrategyRuntimeConfig` 经 allowlist preset registry 解析出的只读 `EffectiveRuntimeConfig`。execution 只在 sandbox write/live managed 合同接管订单编排；sandbox private-read 不加载三能力；risk/monitor 在任何允许写入的合同中均为真实 hard gate/control；gateway 和 transport 仅在 `managed_live_gateway` 的成对合同中加载。loader 不得补齐、降级或将用户输入误标为受管。 |

> 用户可编辑 `plugins` 根和此前无配置启动约定。`legacy_direct` 仅是受 preset 约束的适配代码，不是运行选择。
> `bt_api_gateway` 与 `bt_api_transport_zmq` 继续分层；完整加载、路由与安全边界见

## 2. 功能需求

| ID | 需求 | 可观察完成条件 |
| --- | --- | --- |
| FR41-01 | 建立可选的 provider-neutral managed execution 入口 | v4 sandbox write/live preset 的 example 经 `bt_api_execution` 发出 child；在该受管路径中，策略、Backtrader observer、monitor 均不能直接调用 provider writer。不得删除既有 `Strategy → BtApiBroker/BtApiStore → provider` 映射代码，但每个用户可启动 runtime 都必须先通过 `config.yaml`，不得因 execution 缺失或失败而无配置回退。 |
| FR41-02 | 支持受管的带归因订单聚合 | managed execution 合并前保存每个 intent 的策略、候选、风险和价格/时效约束；相反或不兼容 intent 不得静默合并。既有直连订单继续按其当前 provider 映射运行。 |
| FR41-03 | 支持受管 parent/child 执行和成交分配 | managed parent、每个 child、部分成交、费用、funding、未知状态与 `FillAllocation` 均可重放和对账；直连路径不被要求制造这些受管对象。 |
| FR41-04 | 支持受管的明确执行模式 | 每个 managed plan 显式标记 `immediate`、`passive`、`slice`、`native_algo`、`basket_best_effort` 或 provider-native atomic；不支持即拒绝。 |
| FR41-05 | 建立可选的账户级硬风控 | 启用 risk 时，无论 direct 或 managed，普通开仓、普通撤单、replace、紧急撤单/减仓都在真实 Broker/Store 写入边界被评估并可拒绝；涵盖次数、频率、名义金额、仓位、保证金、损失、未知订单和账户冻结。两条 risk-enabled 路由均做 durable reservation/settlement；managed 另将 permit 绑定 execution journal/child，direct 不建立 OMS。 |
| FR41-06 | 将风控与 dispatch 原子衔接 | 启用 risk 的 managed child 在 transport 前必须验证未过期 `RiskPermit`；启用 risk 的 direct 写入经过同一 durable risk authority 的 reserve/decision/settle。risk disabled 不制造 permit，但 managed 仍执行 journal、身份与 dispatch admission。持久化/插件故障、scope 不一致、未知订单或 permit 无效均 fail-closed，且 provider write count 为零。 |
| FR41-07 | 建立可选的 durable monitoring 控制面 | monitor 可读取 managed execution outbox 或 direct Store/Broker runtime event、风险状态和 heartbeat，生成告警与 `freeze_new_entries`、`drain`、`manual_intervention` 请求；这些请求只能经当前账户唯一owner（embedded Broker、独立execution supervisor或gateway server）的control port生效，Broker是其适配端，monitor 不得普通开仓或自动 resume。 |
| FR41-08 | 监控策略进程之外的运行状态 | monitor 检测进程/心跳失活、行情陈旧、连接代次、队列、磁盘、对账滞后、风险额度与 TradingDay/rolling epoch 漂移；启用 direct monitor 时其 freeze/drain 也必须经对应账户owner真正拦截writer，目标死亡无确认时升级人工。 |
| FR41-09 | 提供双路径 Backtrader 薄适配 | `BtApiStore/BtApiBroker` 在 v4 preset 解析出 managed execution 时映射 framework order 到 intent/plan 并以 allocation 回灌；其他允许的 preset 可保留既有 framework order 映射和通知语义，但 risk/monitor 必须在任何允许写入合同中挂接真实 hook/control gate。 |
| FR41-10 | 受管路径拒绝不支持的 bracket/OCO/basket | `execution=true` 时，未协商 provider capability 的 `parent`、`oco`、`transmit`、native batch、slice 等请求不能退化为多笔普通写入。既有直连路径继续遵循其现有 BtApiBroker/provider 语义，不得因 Iter41 补写一套“已验证原子性”的声明。 |
| FR41-11 | 按市场分离受管长期生命周期 | 受管 CTP 以审核过的交易时段和 TradingDay 边界 drain/reconcile；受管 crypto 采用 7×24 rolling checkpoint，不因健康 checkpoint 杀死会话。既有直连路径保留现有 provider session 行为，不因未启用模块而被强加 Iter41 lifecycle gate。 |
| FR41-12 | 分类迁移所有可写 examples | 每个写入入口被分类为“v4 preset 内的既有适配”“迁入受管 execution”“禁用”或“不适用”，并完成 README、模式回归和无意外回退验证。所有可启动入口都必须迁入必需 `config.yaml`；受管路径失败不得回退为直连。 |
| FR41-13 | 实际实现并发布五个能力包与两个 adapter | execution、risk、monitor、gateway、transport_zmq 五个能力包必须各自在对应 Git submodule 中有真实源码、测试、版本化制品与 consumer 验收；`bt_api_py` 必须提交其 pin、optional dependency/integration adapter，Backtrader adapter 也必须有真实源码与测试。当前空 execution pin `2700cb5`，新建但尚未 package 的 gateway repo，以及近期拟建 transport_zmq 子仓，在有完整 package skeleton/wheel/pin 前都必须维持 `NOT_PACKAGED`/strict 非零且无 PyPI fallback。不得以文档、mock、vendor copy 或 example 内复制代码替代。 |
| FR41-14 | 强制 schema-v4 `config.yaml` 并唯一决定运行模式 | 每个 `<strategy-runtime-dir>/config.yaml` 必须存在、精确 Git 忽略且含 schema-v4、strategy identity、mode/preset 与允许参数；同目录模板不含秘密。当前 CTP SimNow `simulation/sandbox` 使用共享顶层 `ctp:` 块，单对 `md_front`/`td_front` 或 1–8 组有序唯一 `front_pairs` 二选一，并在同块提供合约/交易所/HedgeFlag/账号认证字段；多对只在显式候选中做有界无凭据 TCP 选择，不按时间/set/日历切档或发现/回退外部地址。未来 production CTP 使用同一注册 runtime 路径和同一 `ctp:` 字段结构，只有用户启动该阶段后才更改 mode/preset 为经审阅的 live contract 并替换 account/front/instrument 参数；shared canonical parser/helper/private-config contract 已实现；live 仍因共享 CTP runner 的 live dispatch 与 mode-specific admission 未接入默认 registry 而 fail closed，当前文件保持 SimNow 值，不预填或索取生产账号/前置地址。未来目标是在共享 CTP runner 的 live dispatch 与 mode-specific admission 实现并验收后，只编辑同一文件将 runtime.mode 设为 live、runtime.preset 设为 managed_live_direct，并替换账号/前置/合约字段。现有 `ctp_production`/`runtime-production/`/prepare helper 为 legacy/deferred，不是当前 operator flow。mode/config 不能提升 route、权限或能力；SimNow 与 production 的凭据、receipt、pin 与审批分开。任何缺配置、旧 schema、非法 mode/preset/scope 或不安全路径都必须在 provider/SDK 初始化前稳定拒绝，0 network、0 provider write。 |
| FR41-15 | 用密封 preset 解析路由、账户访问与能力合同 | 版本化 allowlist preset registry 唯一把 mode/preset 解析为 route、account access、execution/risk/monitor/gateway/transport 能力和写入边界。`backtest`、`replay` 为 0 网络/0 外部写；`shadow`/`paper` 为 0 provider write；`sandbox` 默认是隔离环境私有只读，只有 registry 预登记 `write_policy=receipt_required` 且 receipt 有效时才可受管写隔离账户，缺 receipt 必须拒绝而不降级；`live` 仅允许 `managed_live_direct` 或 `managed_live_gateway` 并要求 execution/risk/monitor、审批、指纹与确认。CLI、环境变量、CWD、AI 产物或参数不得覆盖、升级或放宽该合同。 |
| FR41-16 | 建立配置优先的 runtime 管理器 | `bt_api_py` 以独立 `bt_api.runtime_plugins` entry point、schema/preset/pin/version 校验和生命周期管理生成 `EffectiveRuntimeConfig`，只加载该有效合同允许的能力；gateway transport 只由 `managed_live_gateway` 的成对合同加载。不得复用会加载全部 exchange adapter 的 `bt_api.plugins`。所有能力必须经受限 lifecycle hooks attach 到唯一 Broker/Store/execution write boundary，且不允许 ambient import。 |
| FR41-17 | 实现中间件无关 gateway 与首个 ZMQ transport adapter | `bt_api_gateway` 提供共享账户会话、订阅并集/fan-out、strategy/order correlation、snapshot/replay 与 command admission contracts；`bt_api_transport_zmq` 提供 versioned ZMQ wire、server-side write gate、auth/ACL、backpressure、sequence/gap、command idempotency/unknown/reconcile。两者不能形成第二 OMS/risk/account truth；在 CTP gateway 完成单独端到端验收前，不得将 CTP gateway 写入标为支持。 |
| FR41-18 | 保留并统一 instrument/CTP/期权交易语义 | InstrumentMetadataSnapshot 绑定 provider/instrument/version/as-of/TTL、原生单位、乘数、tick/lot、交易币种、日历、费用与保证金来源；过期/缺失/冲突拒绝新增风险。CTP open/close_today/close_yesterday 在 ChildIntent 中显式表达，保留现有 offset/期权乘数和费用校验；期权到期、行权与换月边界按 §6 限定。 |
| FR41-19 | 共享账户策略预算及风险口径 | 提供只读 StrategyAllocation，包含 allocated/reserved/used/available/revision/as-of；getcash/getvalue 保持原账户含义，新增预算感知 sizer/查询入口。所有 risk-enabled writer 共用 durable account authority，禁止进程本地计数冒充账户限额；策略资金、账户限额耗尽有独立原因码。详见设计风险口径表及 AC41-48/50。 |
| FR41-20 | 控制、失联与恢复责任可判定 | freeze 取所有来源的 OR；resume 要求所有阻断解除 AND 新授权。command 持久化去重、目标确认、截止升级。每个拓扑登记进程死亡后的 executor 或 NO_AUTOMATIC_TAKEOVER；无 executor 不宣称自动平仓。策略 checkpoint、历史预热、重复信号键和已知仓位对账完成前不恢复开仓。 |
| FR41-21 | 输出可解释的账户与执行质量事实 | AccountSnapshot/ExecutionQualityRecord 标明来源、时间、单位、覆盖区间与 complete/partial/unknown；费用、funding、已实现/未实现 PnL、滑点与延迟可追溯，不完整不得补零。保持 PRODUCTION_BLOCKED_ACTUAL_FUNDING_CASHFLOW_LEDGER 边界。 |
| FR41-22 | 降低重复准备负担并提供配置优先运维工具 | 每个迁移单元有前后手工步骤/必填参数/配置文件/启动命令基线；选定两个参考入口的日常流程收敛为首次 `bootstrap`、日常 `run`（内置配置/schema/preset policy 校验）和可选只读 `doctor`，重复手工准备步骤至少减少 30%（向上取整）。真实 provider/account `preflight` 必须另行显式执行，不由 `run` 或 `doctor` 代办。`bootstrap` 拒绝覆盖已有配置；`run` 不接受 mode/preset override；错误含字段路径、原因码、修复步骤。独立审批/研究/账户条件不得削减。 |
| FR41-23 | AI 研究证据和部署权限分离 | shared contracts 定义 StrategyDeploymentEvidence、DeploymentAdmissionReceipt、ActorContext、PrincipalPolicy；evidence 不授权，人工/受信部署 receipt 不替代逐 child RiskPermit。受信部署入口强制使用 v4 live managed preset；不得只信任可由输入删改的 producer.kind。语义 review_required 的产物在独立代码审阅或机械映射校验前不许写入。 |
| FR41-24 | 三个 AI 产品独立、离线兼容及只读互操作 | WP41-I 分别在 `D:/source_code/backtrader-agent`、`D:/source_code/backtrader-skills`、`D:/source_code/backtrader-mcp` 实现 opt-in evidence exporter/consumer 契约并记录其版本、commit、wheel 和来源；三者不互相导入、不持有 provider 凭据、不进入交易热路径。只读 observer 默认读取脱敏导出，禁止向 AI producer/tool 暴露私有 CTP `config.yaml` 的原文、password、AuthCode 或可重建信息；在线访问必须独立 profile、认证和有界游标；不改变既有 P0 禁网络/禁 live 的边界。AI 失效不影响执行/risk/monitor，AI 不执行 freeze/drain/resume，只能提出待审批建议。 |
| FR41-25 | 固定插件、部署、配置和账户身份的信任边界 | distribution/hash/module/entry-point、preset registry 和 AI 产物来源均受 allowlist 约束；配置校验后 seal 绑定 dispatch，替换/权限异常失效。CTP 私有 `config.yaml` 的账号、认证和配置端点只能在本地受限文件中使用，AI/MCP 入口不能读取、返回或修改该文件，也不能通过直接/别名 `BtApiStore` 构造绕过 v4 runtime、sealed configured-front candidate membership 或能力门；配置不能替代受信 provider-environment policy、正式 SDK artifact provenance、账户/session admission、审批或 risk permit。其他 runtime 的 `secrets_ref` 同样不能赋予 route 或模式。已登记同账户 writer 只能共用同一 lease/risk authority，否则拒绝并发；隔离生产与 SimNow 凭据、限制 server-side principal，不以客户端 account/route 声明授权。任意外部程序或同机管理员不在 SDK 的强制隔离保证内。 |

## 3. 非功能需求与不变量

| ID | 不变量 |
| --- | --- |
| NFR41-01 | `bt_api_execution` 是**受管路径**的唯一写入编排权威；既有 direct REST/CTP/provider wrapper 可继续由已批准 preset 的 `BtApiBroker/BtApiStore` 适配调用，但不能被作为无配置用户入口。受管路径不得绕过 execution 直接写 provider，也不得在 execution 失败时暗中改走直连。 |
| NFR41-02 | 受管耐久状态按 `ExecutionScope` fencing；账户、TradingDay/epoch、环境、connection generation、policy hash 或代码/配置身份变化均不能继承旧 permit。既有直连路径不伪造或消费该 permit，其 provider-side order/session identity 继续按原有协议处理。 |
| NFR41-03 | 受管路径不得将 provider-native 多请求、顺序多腿或批量撤单表述为原子 basket/OCO，除非 capability 与远端回执共同证明。直连路径也不得因 Iter41 而新增未经 provider 证明的原子性承诺。 |
| NFR41-04 | 受管且启用 risk 时，风险降低型动作有独立、有限的紧急额度；普通撤单/开仓不能耗尽其清理能力，未知状态下不自动重试开仓。direct+enabled risk 也必须在 provider write 前真实作出允许/拒绝，direct+enabled monitor 也必须通过 账户owner control port（Broker为适配端） 真正 freeze/drain；direct 有 risk 的 durable reservation，但不会因此伪造 execution OMS、journal 或 recovery 保证。 |
| NFR41-05 | 受版本控制的 `config.example.yaml` 永远无真实秘密；CTP SimNow 的实际账号、密码、AppID/AuthCode 可按使用者要求写在**仅本机使用、被 Git 精确忽略且权限受限**的 `config.yaml`，其他 runtime 仍可用被 Git 忽略的 `secrets.yaml` 或 OS secret store。`TradeLogger`、metrics、报告、README、receipt、异常消息和日志绝不得泄露凭据、完整账户标识或恢复 token；`repr`、doctor 与错误 payload 也必须脱敏。公开 config projection/摘要不含秘密；私有 seal 必须比较认证字段且变更后重新预检，任何跨进程公开绑定秘密的摘要必须由独立密钥 HMAC 生成，不得把低熵账号/密码的裸 SHA 当成公开凭据指纹。仓库/CI Git-index hygiene gate 必须拒绝被追踪的 active `config.yaml` 或 `secrets.yaml`；runtime loader 还要拒绝 CTP 私有配置的不安全文件位置/权限。 |
| NFR41-06 | `PASS` 绑定 Backtrader、`bt_api_py` superproject、有效 preset 及其已加载能力包（含 gateway 与 selected transport）的 commit/wheel/hash、submodule pin、解释器、命令、脱敏证据和运行模式；既有 direct-adapter 兼容性也绑定实际 Backtrader/SDK/provider 版本和 preset 合同，且不得伪造未加载能力已经生效。backtest、simulation 各 preset 和 live 结论严格分开。 |
| NFR41-07 | 五个能力包按公共 contracts 的兼容版本发布；`bt_api_py` 的 integration 必须声明并锁定其兼容范围。显式请求某 capability 而对应包缺代码/测试/consumer 证据时，依赖方不得用私有对象、monkey patch、vendor 或 example-local copy 替代，并且该 capability 请求必须 fail-closed；这不删除未选择插件的既有直连能力。 |
| NFR41-08 | `StrategyRuntimeConfig` 是每个 runtime 必备的安全相关声明层：环境变量、`.env`、CLI、默认工作目录、AI 产物或 Python import 副作用均不得覆盖 `mode`、`preset`、route、账户访问、能力集合、risk/lifecycle/execution/transport policy。每次解析形成不含秘密的 canonical redacted config fingerprint，并进入 `ExecutionScope`/evidence；任何影响写入的变更必须 freeze、drain 或停止后以新 preflight/identity 启动，不能静默热加载沿用旧 permit。 |
| NFR41-09 | `config.yaml` 仅可由版本化、allowlist 的 schema-v4 和 preset registry 解释；不得接受任意文件路径、Python object/class、未锁定 URL、未声明 profile 或会放宽账户级 hard limit 的 override。允许的 runtime-local artifact 路径必须是相对路径，realpath 后仍位于 strategy runtime 内；受管账户级 journal/ledger 仅能由认证后的 SDK account scope 派生、跨策略共享并受 writer lease 保护。缺失文件、未安装/空仓/pin/version 不匹配能力、schema 不兼容或非法 preset 一律 fail-closed，且绝不静默改走直连。 |
| NFR41-10 | 核心 managed submit 本地新增 p99 ≤20ms、无插件 direct submit/cancel 回归 ≤5%、同账户两个独立 client 持续 50 intents/s 的候选容量必须在 Windows 与 Linux 串行实测；gateway 本地端到端 p99 ≤50ms。精确定义、样本量、总延迟与差值算法见《验收用例与基准》，这些是待测门槛，不是现有性能声明；变更需基线变更记录，不得见失败后删样本或放松 durability。013_2 未通过自身延迟预算不得默认迁入 managed。 |
| NFR41-11 | 首发 managed/CTP 验收平台为 Windows x64 CPython 3.11 与 Linux x64 CPython 3.11；框架原有兼容性保持。Windows 文件锁/flush/reparse point/ACL、进程强杀与 tcp loopback 必须有平台原生验证；POSIX 的 mode/O_NOFOLLOW/ipc socket 不能当 Windows 证据。其余平台或解释器组合在通过前为 NOT_VALIDATED。 |
| NFR41-12 | permit/reservation、intent、dispatch-attempt、freeze/command、lease fence 必须 durable 后才能产生相应副作用；telemetry 可异步但有界，未确认 outbox 不可按普通日志保留期删除。monitor 的 CPU/RSS、积压、磁盘保留与 HWM 按验收附录预算执行；ML/exporter/通知/模型调用不进入 submit 热路径。 |
| NFR41-13 | 扫描只能证明已登记入口和假设范围，不能声称静态扫描穷尽任意 Python writer；inventory 按 Git 跟踪文件集合与显式入口发现规则做覆盖，并结合受限 fake-provider 运行捕获。无网络、0 external provider writes 与 fake adapter 调用计数分别报告，正向 fake 执行不能被错误要求 0 fake calls。 |
| NFR41-14 | 每个验收结论绑定 baseline、FR/WP/AC、代码/制品身份、适用 scope、预期与实际值、证据哈希和复审人；NOT_RUN/BLOCKED 不作 PASS。阶段回滚默认冻结当前 route，禁止 managed 故障后自动 direct；外部阻断每个里程碑或最多 30 天复审，过期为 NOT_RUN。 |

## 4. 已知能力包基线与集成约束

`bt_api_risk` 将作为 `D:/bt_api_py/bt_api/bt_api_risk` Git submodule 使用。它可复用 policy authoring、
limit calculation、风险事件和分析模型，但当前默认分支的
`check_order_risk()` 未将部分 limits/policy 拒绝可靠合并为最终拒绝，频率状态也未形成耐久账户级
计数；它必须先完成 WP41-C，不能直接成为实盘写入门。

`bt_api_monitor` 将作为 `D:/bt_api_py/bt_api/bt_api_monitor` Git submodule 使用。它可复用 metrics、
health probe、Prometheus/Grafana/ELK exporter，但当前指标历史和健康循环是进程内能力；它必须在 WP41-D
接入 execution outbox、durable checkpoint 和控制命令。

`bt_api_execution` 将作为 `D:/bt_api_py/bt_api/bt_api_execution` Git submodule 新建；初始子仓为空，不能把
`bt_api_py` 私有 `_ExecutionSession` 的存在误报为该包已经实现。它可在兼容迁移中复用 SDK 的稳定机制，
但必须有自己的公开 contracts、版本、测试和 consumer 证据。

[`bt_api_gateway`](https://github.com/cloudQuant/bt_api_gateway) 已在 SDK 挂载，pin 为 `44fd2fe26b51f1d8b573c84415a6cff660f33dea`，当前只有 README。
在 package skeleton、独立 wheel 与 consumer 测试完成前保持 `ATTACHED / NOT_PACKAGED`；
当前 `.gitmodules` 缺少 `installable=false`，该安装门修复列入 A6，不能声称已通过。它只依赖无 transport 的 shared
contracts（本版固定为 `bt_api_base` 的无 I/O contract surface），并通过受限 provider port 接收 SDK integration adapter；
不得依赖 `bt_api_py`。`bt_api_transport_zmq` 将作为首个独立 Git submodule 新建，只依赖 gateway/shared contract，
拥有 socket/security/generic relay 与 `pyzmq`；不得依赖 `bt_api_py`，以避免循环。provider-aware router、
execution/risk 真相与兼容 facade 留在 SDK integration 层。

五个包在运行时只经显式 dependency/integration adapter 连接：`bt_api_execution` 提供 intent/plan/child/allocation 领域 contracts；
跨路由 `RiskGate`、decision/reservation/permit/control/transaction ports 和 deployment/gateway DTO 固定在
`bt_api_base` 的无 I/O shared surface。risk/monitor 的 core 只依赖 base，managed adapter 在显式启用时才加载
execution contracts，避免 direct+risk 因导入 protocol 意外 import execution；gateway/transport 依赖 base/gateway
合同。execution 不得反向导入任何能力的 concrete 实现。`bt_api_py`
负责选择、注入和锁定可选组合；
provider 子仓不得承担 risk/monitor/execution/transport 的领域状态。

所有策略 runner 必须通过 SDK integration 的 `StrategyRuntimeConfig` loader 读取本运行目录的 schema-v4
`config.yaml`，而不是自行解析能力包配置。相邻、受版本控制的 `config.example.yaml` 只用于复制和校验模板，绝不可被
loader 当成运行时回退。config 选择 mode/preset 和策略参数；CTP 私有 profile 还在同一份未跟踪且权限受限的配置中填写一组 `md_front`/`td_front`，或可选的有序多组 `front_pairs`、合约查询范围与认证字段。单组原样使用；多组只在配置中显式列出的候选之间，以有界且无凭据的 TCP RTT 探测选择较低延迟的一组，平分按配置顺序，失败组排除、全失败则拒绝。不得按时间、日历、TradingDay、服务时段、endpoint discovery 或未列出的地址选择；旧 selection/profile/calendar 字段拒绝。内部 provider environment 固定为受信 `simnow`，不从地址推导 set1/set2。其他 provider 可保留 opaque credential selector。preset registry 仍独占 route、能力组合、风险/监控 profile 和可收紧的参数范围；配置不能授予写权。账号 identity、批准根及 provider client 只能在预检/认证后
派生或创建；gateway client 配置不得包含 provider credential。**任何 runner 缺少有效 `config.yaml` 时都必须在导入
runtime capability 和连接 provider 前拒绝。**当前 execution 子仓为空时，任何解析为 execution 的 sandbox write/live 合同都必须以
`NOT_PACKAGED` 拒绝，绝不回退到私有 `_ExecutionSession`、ambient editable 包、PyPI 或既有直连路径。

## 5. 明确非范围

下列条款的验证类型、责任工作包和证据见[追溯矩阵](追溯矩阵.md)；治理声明不是可执行测试的替代。

- 不因为本迭代而批准任何 `RESEARCH_REJECTED`、`RESEARCH_NOT_ESTABLISHED` 或 `NOT_ADMITTED` 候选交易；
- 不把 SimNow 或期货公司 production credentials、审批根或账户原件写入 Git、`config.example.yaml`、日志或验收证据；CTP SimNow 当前参数及未来 production 阶段替换后的参数均由使用者放在同一个被 Git 忽略、受本机权限保护的 runtime `config.yaml` 中，mode/preset 字段选择声明的运行模式，但不授予权限。共享 CTP runner 的 live dispatch 须与 production-specific 账户/session/制品准入及逐笔审批独立实现和验收；不维护第二份生产 operator config。其他 provider 可继续使用被忽略的 `secrets.yaml` 或受管 secret provider；
- 不承诺交易盈利、成交质量、CTP 官方前置写入或 production CTP 接入已经通过；
- 不用 Backtrader 的回测 `BackBroker` bracket/OCO 行为为实盘 provider 语义背书；
- 不以删除门禁、扩大 timeout、伪造 TradingDay/日历或重试未知订单来达到“长期运行”。
- 不把五个能力包 vendor 到 `bt_api_py`、Backtrader 或 examples，也不以未 pin 的 submodule、ambient editable
  import 或隐式 extras 代替受控集成。
- 不以 Iter41 删除既有 Backtrader `Strategy → BtApiBroker/BtApiStore → provider` 映射能力；但缺少
  `config.yaml` 必须是所有 strategy runtime 的启动错误，既有适配只能由允许的 v4 preset 调用并继续遵循其
  provider 原生认证、会话和协议条件。

## 6. 本版范围裁决与存量处置

1. **期权：** 本轮实施合约元数据、到期/最后交易时段、乘数/费用、平今平昨、涨跌停及外部强平事件的
   校验与对账；到期或资料不全时禁止开仓。自动行权/放弃行权、自动组合保证金优惠、复杂 Greeks
   组合优化不实施，相关请求返回 `CAPABILITY_UNSUPPORTED`。已有期权策略只能按迁移矩阵声明支持范围，
   不能因非范围而省略到期保护或把未测请求转普通单。换月信号/新旧合约经济决策属于策略，execution
   只执行显式归因 intent；平台不自动换月。
2. **risk 存量：** `core/{risk_manager,limits_manager,policy_engine}` 保留公共兼容入口并修复最终拒绝
   汇总与耐久计数；`risk_calculator/risk_assessor/containers` 保留分析及只读模型，权威输入必须带来源。
   `ml_models/{ml_base,ensemble_model,anomaly_detector}` 保留为可选 `ml` extra，依赖按实际 import graph
   迁出核心 hard gate；不删除算法，不在逐单路径训练/推理，不允许模型自动放宽 hard limit。
   当前 risk pyproject 仍强依赖 numpy/scikit-learn，隔离是 WP41-C 交付，不是现状。
3. **monitor 存量：** `metrics/collector/exchange_health/system_metrics/config` 保留并适配有界 read model；
   `prometheus/grafana/elk` 保留为可选 exporter，按真实依赖分别声明 extra、懒加载，异常不阻塞账本；
   `decorators` 仅兼容遥测。`bt_api_monitoring` 兼容命名继续提供过渡导出，不另建第二 consumer。
   durable checkpoint、独立 heartbeat 和 command ledger 是新增能力，不能把进程内 deque 当耐久记录。
4. **AI：** 纳入交接 schema、安全边界、三产品 exporter 与只读适配，独立阶段交付；不纳入运行时 LLM
   决策、自由文本即时编译、模型交易权限、自动 resume 或既有 P0 网络能力扩张。先完成核心交易设施，
   AI 阶段未通过时明确 `AI_INTEROP_NOT_ACCEPTED`。三产品改动只在各自仓库提交。
5. **交付：** 核心、gateway、AI 分阶段解锁，完整范围仍须最终逐项验收。首个核心版本至少使 013_3 与
   P1-B mechanical rail 两个实际 runner 通过 managed L2 集成，使用 fake provider/录制输入，
   不依赖真实交易授权。真实 CTP gateway 写入、funding 完整现金流与候选研究门维持独立 BLOCKED。

基线代码定位、TradeLogger 能否替代 monitor、现有执行能力的保留/迁移选择见
[能力评估与 ADR 索引](能力评估与ADR索引.md)。
