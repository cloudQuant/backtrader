# SimNow / CZCE 日历来源审计（2026-09-23）

> **历史材料，选择合同已废弃。** 本文审计的是此前 Iteration 41 以日历自动选择 SimNow set1/set2 的方案；baseline-4 已改为私有 `config.yaml` 明确成对填写 `md_front`/`td_front`，按配置直连，失败不回退。本文不构成当前 runtime 的日历前置条件或自动选档依据。文中官方地址/服务时间来源仍可供 allowlist 与操作说明复核。Iteration 22 的策略合约日历逻辑独立保留。

## 判定

`set2_7x24` 是代码与配置中的 profile 名称，不能解释为任何时刻都可用的 24 小时服务。SimNow 官方产品页给出了第二套的服务时间窗，但没有 2026 年逐段维护状态，也没有该环境在每段的实际 CTP `TradingDay` 语义。CZCE 的交易规则足以支持 SA 的常规交易时段和夜盘归属参考，不能单独签发与 SimNow 路由绑定的 v2 日历。当前结论仍为 `CALENDAR_ARTIFACT_NOT_ADMITTED`；本审计没有生成或修改日历、配置、账号资料，也没有连接任何账户。

## 与本地 v2 合同和选择规则的差异

`backtrader_runtime/ctp_trading_day_evidence.py` 要求制品绑定精确交易所和合约，声明来源、生成/复核/失效时间及完整覆盖范围，并以无间隙、无重叠的上海时间半开区间逐段给出 `trading_day`（或来源明确的 `null`）和 `session_route`。历史模板行为（当时将合约设为待复核占位符、要求日历独立 SHA，并预设受控枚举 `set2_7x24`）不再是 Iteration 41 的当前 operator contract。当前规范使用同一受保护 `config.yaml` 中的 canonical `ctp:` 直接地址字段或显式 `front_pairs`，不要求日历 SHA，也不按 set、时间或日历选择前置；本节只保留旧交易日证据设计审计。

`backtrader_runtime/ctp_session_selector.py` 对 `set1_open` 要求明确的 CTP TradingDay，并返回私有配置中的 set1 Group1/Group2；`set2_open` 会选 set2，即使 `is_trading_day` 为 false。selector 不自行验证官方来源，也不判断当前服务器可达。因此，不能仅从 profile 名称、自然日、常规小时或网络可达性造出 `set2_open` 区间。旧 Iteration 22 日期清单也不含 v2 要求的逐段 route/TradingDay 证据。

## 尚缺证据与边界

- SimNow 对 Group1、Group2 及第二套在 2026 逐段服务/维护时间的当前一手确认，特别是节假日边界、无夜盘日和恢复日。
- 要绑定的账户当前实际 SA InstrumentID、CZCE exchange 身份，以及账户配置与允许使用的前置组。模板中的 `SA` 示例和历史 `SA610` 均不能代替此核验。
- 同一账户、所选 front 和连接代次下的实际 `OnRspUserLogin.TradingDay` 读数，以及 set2 非结算用途下该字段如何变化的依据。官方手册指出应读取登录响应字段，但当前审计没有连接；未来需要在获准的实时只读会话中采集并审阅，不能用日历推算或本次研究代替。
- 覆盖期内 CZCE 对应合约的官方节假日/夜盘变更通知、来源归档与独立复核记录，才能形成有明确有效期和独立 SHA pin 的 v2 制品。

上述缺口未补齐前，不建立制品、不登记 CTP binding，也不连接 SimNow；真实账户登录及原生 TradingDay 查询只应在后续独立获准的只读验收中进行。
