# R9 native Win32 boundary supplement — 2026-09-27

## Disposition

This is an inert local Windows API supplement for the R9 design. It establishes a normal direct `CreateProcessW` measurement and successful Job cleanup in the measured runs, plus a local caller-death/pending-I/O ownership scenario. It does **not** inject a kernel stall, prove a whole-command hard deadline, verify P14 failure/hang handling, install SCM, or accept G1. Production/default CTP routing remains unchanged and G1 remains CLOSED.

No CTP SDK/provider, credentials, account, network connection, or default route was used. The helper uses only local inert child processes, shared memory/events, one local named pipe, and Windows Job/handle APIs.

## Win32 helper results

The helper was compiled with the recorded VS 2022 x64 environment (`vcvars64` exit 0; `cl` exit 0, final build produced no compiler warnings). Final direct run and reproducibility replay both exited 0; the source SHA stayed constant and no helper process remained after either run. Raw JSON-lines are preserved under `run\native-boundary-run-final.log` and `run\native-boundary-replay-02.log` (see their exit files).

- **Before-call control (P02-like only):** the in-Job worker signals entry, then sleeps in user mode before calling `CreateProcessW`. At D=1,200 ms, there is no call start/return and no child; the monitor's Job count is 1 before termination and 0 afterward. Worker wait is signaled. This is a pre-call hold, not a kernel wait.
- **Direct CreateProcessW / post-call hold (P03-like only):** the helper worker invokes `CreateProcessW(CREATE_SUSPENDED)` directly. In both runs the call succeeded and returned in 63 ms; the child was in the worker's Job before D (ActiveProcesses=2). The worker then stayed in user-mode sleep until the monitor killed the Job at D. Both worker and child handles became signaled and Job ActiveProcesses reached 0. This proves ordinary call completion and containment for this inert child. It does not simulate a `CreateProcessW` call that remains blocked inside the OS.
- **P14 adjacent rights-negative and normal Job-empty readback:** on a live one-process Job, a query-only handle's `TerminateJobObject` and a terminate-only handle's `QueryInformationJobObject` each failed with `ERROR_ACCESS_DENIED` (5); the owner handle still read ActiveProcesses=1. The owner then terminated the process and a successful query observed ActiveProcesses=0. This is ordinary API evidence and a bad-rights negative only. It does not inject `TerminateJobObject` failure/hang, correct-rights query failure/hang, or `CloseHandle` failure/hang. P14 fault handling remains untested.
- **Caller death with pending overlapped write and retained Job handle:** in both runs, a local named-pipe 2 MiB overlapped write submit tick equaled the request-start tick at millisecond resolution; it remained pending at the D kill cut. Outer Job ActiveProcesses=2 (caller + I/O broker), nested caller Job=1. A query-only duplicate of the outer Job handle was successfully duplicated and queried while the caller lived. At D+3 ms the monitor terminated the caller Job; caller process signaled, caller Job became empty, and a post-death `DuplicateHandle` attempt failed with Win32 error 5. Record this only as the remote handle no longer being duplicable; do not relabel error 5 as `ERROR_INVALID_HANDLE`. The monitor's separately retained outer Job handle remained queryable with ActiveProcesses=1 and the broker's OVERLAPPED write remained pending after caller death. After cancellation, `CancelIoEx` succeeded and final `GetOverlappedResult` reported 995 (`ERROR_OPERATION_ABORTED`); broker exited and the outer Job reached 0. The sampled termination was at/after D (ticks are in the raw log), so this is cleanup/ownership evidence, not an on-time caller API result.

## Limits

User-mode code here cannot deterministically force the kernel to hang inside synchronous `CreateProcessW`, `TerminateJobObject`, `QueryInformationJobObject`, `DuplicateHandle`, or `CloseHandle`. A real kernel/fault-injection mechanism would be needed to exercise those wedges safely and repeatably. The logs therefore cannot prove a hard whole-command deadline or survival of a persistent service/reaper if that custodian itself wedges. SCM/startup-before-D, P14 fault handling, real SDK/native calls, G4, F14, and production acceptance remain untested/closed.
