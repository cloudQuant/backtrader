## Exact V21 seams

- `store.py:6189` persists a logical account-family generation (`family_generation`, owner intent, writer owner/token, callback owner, handoff id). `store.py:6145` has a permanent family row with `ACTIVE`/`POISONED`; these are store ownership generations, not OS process generations. `acquire_ctp_account_family_owner()` at `:3193` reuses `CLAIMED`/`ACTIVE` only with the exact handle issued by that open Store. After reopen, an ACTIVE owner is not reconstructed; the test at `tests/test_ctp_dispatch_commands.py:3656` expects acquisition to fail.
- `store.py:6772` callback-session rows bind family generation, writer owner/fencing token, SDK source/API/SPI identities and connection/login session facts. They contain no OS process generation, process creation identity, Job identity, or supervisor receipt.
- `store.py:6470` command rows persist account/scope/day/operation and CTP target/correlation data. Claim provenance is `claimed_owner_id`, `claimed_fencing_token`, `callback_owner_intent_id`, `status`, and `native_call_inflight` (`:6516`). The command's `session_generation_id` is protocol/session correlation; it is not a process generation. There is no durable process-generation field to match a death receipt against.
- `claim_ctp_dispatch_command()` (`:10799`) runs its injected authority verification before the write transaction, then rechecks admission under the Store transaction. Its READY→CLAIMED write records owner/token and callback owner and sets `native_call_inflight` (`:11147`). That claim is the needed atomic seam for adding a process-generation binding before an external Req can occur. `_transaction()` uses `BEGIN IMMEDIATE` (`:13798`).
- `recover_claimed_ctp_dispatch_commands()` (`:13713`) is **not process-death recovery**. It scans account-wide CLAIMED rows under a newly valid writer lease and treats a differing `claimed_owner_id`/fencing token as the recovery condition. It has no supervisor/process/Job verifier; it sets `UNKNOWN` and a writer-change reason, but does not poison the callback/family owner or clear `native_call_inflight`. The `test_unresolved_command_fences_other_scopes_account_wide` (`:3685`) expires a writer lease in the same live Store, obtains another lease, and exercises this method; it does not kill a process or prove Job emptiness. Lease expiry/change cannot establish that the prior process stopped sending.
- `complete_poisoned_ctp_dispatch_unknown_for_session()` (`:11723`) is a same-Store finalizer: it needs exact issued callback-owner handle, matching writer lease/family generation, already-poisoned rows, and an exact UNKNOWN receipt. It does not recreate those capabilities after process death. `complete_ctp_account_owner_handoff()` (`:3481`) is an issuer-verified clean close/drain successor path, not a crash proof.
- G5 r1 models the missing contract: fake supervisor state binds owner + process-generation + job; it issues a one-use object only after process-exit, Job-empty, controls-released, and sealed-Job facts. `recover_stale_owner()` rechecks both family and session generation in `BEGIN IMMEDIATE`, transitions claimed rows to UNKNOWN/inflight=0, poisons both owners, and appends a recovery record. The session-generation mismatch regression is at G5 `test_recovery_contract.py:155`. These are fake booleans and in-memory identity checks, not Windows evidence.

## Missing trusted binding

Before the V21 path could safely do `CLAIMED + inflight → UNKNOWN` because the old process died, a trusted supervisor capability must match persisted data at least by journal incarnation, account/family key, family generation and owner intent, callback owner id, writer owner/fencing token, and a distinct `process_generation_id`. Every claim recovered must be joined to that same process generation. OS evidence must come from retained trusted handles: exact process object observed signaled, exact sealed Job observed empty, and process/Job/control handles released under the supervisor's bounded protocol. PID text alone is insufficient because it can be reused. Receipt identity/nonce must be one-shot and supervisor-issued; caller booleans or a constructible dataclass are not proof. A service restart that lost the relevant handles must fail closed unless an independently trusted supervisor can re-establish the same exact evidence.

The existing V21 writer-change helper's UNKNOWN transition also needs an explicit `native_call_inflight` meaning decision. G5 clears it only after proved process exit; V21's writer-change helper leaves it set. Do not silently equate those paths.

## Schema/version hazards

V21 sets `_SCHEMA_VERSION = 21` (`store.py:2189`) and existing-store validation accepts only exact V20 or current V21 shapes (`:2574–2618`), with frozen table/trigger/index contracts. A new persisted process-generation/proof audit therefore needs a new schema version and an explicit exact V21 migration branch (plus the already-supported V20 path). Do not widen the accepted version set or route V21 through the V20 digest. Existing V21 CLAIMED rows have no process-generation proof binding: preserve them fenced/legacy-unbound and do not infer a generation from `session_generation_id`, writer token, lease expiry, or callback generation. Add migration tests for both supported source shapes, including active claims and mismatch/rollback cases.

## Minimal safe integration sequence

1. Have the trusted Windows supervisor mint/bind a unique process-generation id to the exact family generation, callback owner and writer token before resuming a suspended child; persist that binding. Include the same generation in each command's atomic claim write.
2. Keep the process and sealed Job handles in the trusted supervisor. Issue a non-public, one-shot exit capability only after exact process signaled + Job empty + controls released; no PID-only or caller-supplied proof.
3. Add a dedicated recovery entry that accepts only that verifier-issued capability. In one `BEGIN IMMEDIATE`, reread and compare the persisted account/family/callback/writer/process-generation identities and all matching CLAIMED/no-receipt commands; consume the proof once, mark those commands UNKNOWN, apply the defined in-flight flag semantics, poison the old session/family generation, and append immutable recovery evidence. On any mismatch or rollback, leave the account fenced. Do not issue a successor owner or permit replay as part of crash recovery.
4. Keep UNKNOWN behind the existing independent reconciliation fence. Add fake transaction tests first, then inert Windows supervisor/Job tests. No provider/native test can substitute for proving the OS process/Job boundary.

**Residual: no trusted process-death proof or safe post-crash reacquisition path is present in this V21 source snapshot.** The accepted G5 result remains a local fake-model contract only.
