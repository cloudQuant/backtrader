# Limitations and acceptance boundary

`LOCAL_TYPED_CONTRACT_ONLY / NO_WRITE / NO_AUTHORITY / NOT A MIGRATION TOOL`.

This validator is pure in-memory logic over typed caller-provided evidence. It does not inspect a real database, establish snapshot provenance/completeness, authorize cutover, modify historical rows, allocate `max()+1`, renumber, delete, or merge identities. It cannot be registered in the main runtime because it is isolated under `D:\temp` and has no runtime adapter.


The r1 contract requires both snapshots to declare the same boundary identifier and requires every matched action's source status to be exactly equal (`READY`, `CLAIMED`, or `COMPLETED`). It rejects `UNKNOWN` and state mismatch. The boundary identifier itself is caller-supplied and unauthenticated; the exporter/service must establish a genuinely shared quiesced boundary. Input classes and contained row/metadata fields are exact types, validated before canonical hashing/comparison; this guards Python callbacks but does not authenticate the exporter.
Before any operational offline cutover can be designed, the owner must provide an authenticated, read-only exporter contract for the actual deployed old G5 database and the exact V21 Store package/database version. The exporter must bind a verified account identity, source digests, high-water evidence, complete command-to-allocation joins, all UNKNOWN outcomes, and its snapshot boundary. Current G5 verifier SHA `7caed2a…3f681c66` does not define the old reservation schema; the old schema only appears in a separate SDK candidate SHA `8e7abdd…35f647d`. V21 r3 allocation rows need a command/correlation join to populate shared identity fields, while the old allocation table has no command ID or state. No compatibility or migration rule can be inferred safely from those sources alone.

Even successful offline consistency is not account authority. Separate external requirements remain: authenticated native account ActionRef floor evidence; explicit conflict-preserving inventory and reconciliation of every old writer/database; service-owned account-wide exclusive writer epoch across processes/hosts/store generations; sticky fencing for UNKNOWN, stale epoch, missing/unreadable source or identity conflict; package/API/schema rollout barriers; and independently authorized provider acceptance. Default runtime disposition remains NO_WRITE / LIVE_NO_GO.
