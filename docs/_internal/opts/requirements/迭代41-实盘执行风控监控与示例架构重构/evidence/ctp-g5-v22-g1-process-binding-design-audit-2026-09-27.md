## What the current seams establish

V22 generates `process_generation_id` as a random UUID in `SqliteExecutionStore.create_ctp_callback_session_owner()` (`store.py:4142–4253`). One transaction writes it to the callback-session owner and its family generation; the claim path checks that pair and copies the value to each claimed command (`store.py:11294`, `11731`). The crash verifier request binds journal incarnation, account/family, family generation and owner IDs, writer owner/fence, CTP `session_generation_id`, process-generation UUID, exact claim IDs, and claim-set digest (`store.py:14264–14355`). Recovery asks the injected verifier outside the write transaction, re-reads the exact request under `BEGIN IMMEDIATE`, then atomically moves claims to UNKNOWN, poisons callback/family owners, and appends audit evidence (`store.py:14458–14600`). No replay or successor is added.

That UUID is **not currently an OS process identity**. V22 does not persist a binding from it to a Windows process handle, PID plus creation time, Job object, OS token/session, supervisor instance, or sealed artifact digest. The recovery audit table records PID, creation time, exit code, Job-empty/control booleans and verifier IDs, but the table cannot establish that those values came from a retained OS handle.

G1 has useful OS primitives, but no Store-generation bridge. The output channel binds a suspended child using a process handle, checks PID and creation time, and validates the peer (`worker_output_channel.py:569–674`, `871–953`). The Job backend observes launcher exit, Job emptiness and control release (`windows_job_backend.py:466–510`, `650–683`); the outer watchdog records bounded containment facts (`outer_watchdog.py:158–165`). The G1 service starts coordinator/writer stages and binds channels/handles (`windows_guardian_service.py:3838–3910`, `4018–4045`). These facts do not currently identify a V22 `process_generation_id`.

The coordinator’s typed output contains generic process/job booleans and a redacted read-only observation with `connection_generation`; it contains no V22 process-generation UUID or Store owner identity (`readonly_request_coordinator.py:48–110`, `300–390`). The fixed worker dispatches registered read-only preflight (`readonly_preflight_worker.py:18–31`); it does not create or recover the V22 execution Store. The G1 dependency seal’s only import roots are `yaml`, `bt_api_base`, and `bt_api_ctp` (`ctp_i13_worker_dependency_seal.py:52`), so `bt_api_execution` is not in the current sealed dependency closure. The V22 candidate remains source-only package version `0.2.0`; it has not been consumed as an accepted G1 dependency artifact.

The parent’s outer Job facts describe the coordinator process. Worker facts arriving inside coordinator JSON are not an independent substitute for the service retaining and querying the **native-owner worker’s** process and Job handles. If a coordinator creates the native-owner worker, the service must hold verified duplicates of that child’s process and Job handles (or directly launch/supervise that worker); a coordinator’s statement that the worker exited is insufficient for G5.

## Minimum safe binding design

Keep `process_generation_id` as the Store-generated local correlation ID; do not overload it with PID, CTP connection generation, CTP session generation, or Windows SessionId. Add a distinct immutable OS binding, created before any CTP API construction or native call:

1. **G1 service launch record.** The trusted G1 service creates the direct native-owner worker suspended, assigns it to the fixed Job before resume, and retains non-inheritable process, Job, channel, and token/control handles. It records the process PID and creation FILETIME by querying the retained process handle, not by reopening a PID. The handle/Job custody must outlive a coordinator failure. The worker is the process that owns the CTP API/SPI callbacks; coordinator and receipt-writer PIDs are different roles and cannot be substituted.
2. **Store owner registration.** Inside the fixed sealed worker, V22 creates the account-family/callback-session owner and obtains its random process-generation ID. Before constructing `TraderApi`/registering SPI/Init, the worker sends a registration request over the service-created, peer-PID-bound pipe. It carries Store facts (journal incarnation, account/family keys and generation/owner IDs, callback owner, writer owner/fence, process-generation UUID, and separately named CTP session generation when available). The G1 service binds that UUID to its already retained worker PID+creation time, Job identity, owner SID/AuthId/Windows SessionId and the exact deployment hashes; pipe-supplied PID fields are ignored. A failed or timed-out binding poisons/fences the owner and no CTP API is constructed.
3. **Persist-before-native gate.** Append one immutable Store binding row and a service-authenticated attestation digest, keyed by `(journal_incarnation_id, account_key, process_generation_id)`. It references family/callback owner IDs, writer fence, CTP session identity, Windows PID+creation FILETIME, an opaque supervisor/Job instance ID, owner/service identities, and the exact descriptor/source/runtime/dependency/Python/bootstrap/worker digest set. Do not persist HANDLE values as authority. Every native claim must require the committed binding row and copy its binding digest with `process_generation_id` in the same claim transaction. Native start and claim paths must reject a missing, stale, mismatched, or legacy binding.
4. **Exit attestation.** Only the external, protected G1 supervisor that retained the process and Job handles may attest death. It independently observes the exact process handle signaled and exit code, the same Job active-process count at zero, successful cleanup/release of required controls, and the same PID+creation FILETIME previously bound. It verifies the original Job assignment-before-resume, no breakaway, exact worker/bootstrap/deployment seals, and the challenge/claim-set binding. Timeout, successful TerminateJobObject call alone, coordinator exit, a worker JSON boolean, PID-only lookup, or a nonempty/unknown Job never yields proof. If service restart loses the retained handles, preserve the UNKNOWN fence; do not reconstruct proof by reopening a PID.
5. **Trusted Store commit.** Preserve V22’s good two-phase shape: take a consistent request snapshot; call the external verifier without holding SQLite’s writer transaction; then re-read the exact context under `BEGIN IMMEDIATE`; atomically mark only exact claims UNKNOWN, poison the exact callback/family generation, and append the signed proof/binding digest. UNKNOWN remains non-replayable and account-poisoned. The proof is evidence of process death only; it does not prove an order’s provider-side result.

A V23 schema should add an immutable `ctp_owner_process_bindings` row/table and reference its digest from session-owner/claim/recovery records. Keep separate field names for `process_generation_id`, `ctp_session_generation_id`, `windows_session_id`, and `windows_process_creation_time_100ns`. Bind the full artifact set using a canonical deployment digest plus the individual component hashes needed for audit. Add a proof key ID and verifiable signature over the canonical request, binding digest, retained-handle observations, process exit, Job-empty and control-release facts; a plain `proof_sha256` over booleans is not an authenticity check.

V22→V23 migration must **not** infer OS binding from the V22 UUID. Any V22 active/prepared callback owner or claimed/in-flight row lacks G1 binding and must remain permanently fenced: convert unresolved claims to UNKNOWN and poison owners/family with a specific `g1_process_binding_missing` reason. Preserve the old process UUID/audit facts for diagnosis, but do not issue or accept a V23 proof for those rows. V20/V21 behavior remains fail-closed as already recorded.

## Verifier trust boundary and constructor injection

The current `_CtpProcessExitVerifier` is a Python `Protocol`, the capability is a private dataclass, and `SqliteExecutionStore.__init__` accepts `_ctp_process_exit_verifier` (`store.py:2469`). Those names/types do not create a permission boundary; any code with in-process execution can implement or monkeypatch them and produce matching hashes. V22 deliberately defaults the verifier to `None`, and the inspected candidate has no production Windows verifier or pin.

For G5, remove arbitrary verifier-object injection from the normal Store constructor/factory and keep recovery out of caller-controlled API/config/wire paths. The proof must be issued by the protected G1 service or a dedicated service-SID broker that owns the retained handles and is independent of the crashed owner worker. The service-side signing key must be inaccessible to the owner worker; a pinned public-key verifier in the sealed Store/recovery code can validate the signed, challenge-bound proof. Alternatively, the service itself can perform the Store transaction under an ACL that grants it the required journal access. Never accept a caller-built dataclass or bool/PID bundle as proof. If untrusted strategy code can execute in the process holding the verifier or mutate its objects, the permission boundary is still absent; keep route closed until the process/SID/ACL separation is enforced.

## Required adversarial tests and independent acceptance

- Owner registration positive: generated UUID maps to the exact retained child handle’s PID+creation time, Job, CTP owner/session, SID/AuthId/SessionId, and sealed artifact digests; no CTP API constructor or claim runs before binding is persisted.
- Reject mismatches for journal, account/family key and generation, family/callback owner, writer owner/fence, process-generation UUID, CTP session generation, PID, creation FILETIME, Job instance, supervisor instance, token SID/AuthId/Windows SessionId, channel nonce/request, and every deployment/source/runtime/dependency/bootstrap/worker hash. All failures leave no native start/claim and no recovery audit.
- OS proof negatives: PID reuse/creation-time mismatch; process still alive; owner process signaled but Job nonempty; Job empty without exact owner process exit; TerminateJobObject success without final empty observation; controls/pipe/token handles not released; timeout; coordinator exits while worker remains; service restart without retained handles. Each preserves UNKNOWN/fence and cannot mint proof.
- Proof negatives: caller bool/PID-only data, unsigned/rehashed fake capability, wrong challenge/claim-set digest, old process generation/supervisor key, duplicate/replayed signature, malformed exact-int/bool confusion, and tampered signature all reject before writes.
- Store atomics: claim blocked until binding is persisted; exact account-wide claims snapshot; verification happens outside the DB writer lock; new owner/claim remains blocked during verification; rollback injection leaves claim/poison/audit unchanged; successful signed proof transitions only matching claims to UNKNOWN and poisons owner/family once; no replay/successor route.
- Real Windows inert conformance: pinned service/worker/helper origins; service creates a suspended synthetic child, binds its actual handle to Job and pipe, the sealed worker registers a synthetic in-flight Store claim then blocks before any native/provider call; terminate it from the supervisor, observe process signal + exit code, Job-empty and control release through retained handles, verify signed proof and atomic UNKNOWN/poison. Repeat the mismatch and cleanup negatives above. This proves only the OS boundary under test, not CTP behavior or provider acknowledgement.

**Acceptance boundary:** the G1 worker remains a read-only preflight and the G5 candidate remains a fake-verifier Store model. Adding `bt_api_execution` to the sealed dependency closure, building/pinning its wheel, binding the direct native-owner process to G1 handles, and installing a service-authenticated verifier are external integration gates. Until those gates and independent Windows inert conformance pass, G5 stays closed.
