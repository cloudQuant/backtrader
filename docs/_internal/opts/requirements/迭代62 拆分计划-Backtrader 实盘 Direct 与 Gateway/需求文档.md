## 1. 背景、用户已确认边界与决定登记表

### 1.1 用户已确认边界（2026-11-22）与范围/非目标

**用户已确认的核心边界（引自 v1 §1）**：

- 实盘只允许**两种互斥路径**：
  1. **Direct 模式**：Backtrader 策略进程通过 `bt_api_py` 统一 SDK 直连交易所（provider）；
  2. **Gateway 模式**：Backtrader 策略进程接入 **Gateway、Execution、Risk、Monitor、Runtime** 五个微服务组件构成的服务体系。
- **不保留混合实盘路径**（例如 Direct SDK + 远端 Execution、或 Gateway MarketHub 行情 + Direct 下单）。
- **组件全备不等于五者串行转发每笔订单**（Monitor 为旁路观测，Runtime 为外部策略进程监督器，不进入下单关键路径）。

**范围与非目标**：

- **目标**：消除 `BtApiStore` / `BtApiFeed` / `BtApiBroker` / `live_state` 中的模式职责交叉与隐式选路；将实盘架构整理为“薄 Base + Direct/Gateway 两套独立实现”；实现启动前不可变模式绑定与 fail-closed 边界；清晰剥离非实盘工具。
- **非目标**：
  - 不承诺性能提速（仅设离线最小回归守门，防止吞吐/延迟显著劣化，见 [验收文档](验收文档.md) `S-11`）；
  - 不改动 Backtrader 核心调度（`Cerebro`）、指标计算与回测撮合语义，不替[迭代 71](../迭代71-代码缺陷修复与工程质量治理/迭代计划.md)清账，不将[迭代 70](../迭代70-单账户多策略回测持仓与账户/迭代计划.md)离线多策略账本混入实盘双模式；
  - 不重写[迭代 67](../迭代67-交易日历数据文件化与每日更新/迭代计划.md)交易日历规则，不把[迭代 69](../迭代69-bt_api统一Web页面/迭代计划.md)统一 Web 设为交易放行依赖；
  - 本轮仅完成需求/设计/开发计划/验收预案修订，**不实施代码修改、不启动服务、不执行测试、不登录账户或发出指令**；任何实盘/模拟账户接入、部署与切换须另行授权与验证。

## 2. 术语表与概念边界

为彻底消除跨仓同名异义（尤其是 `direct` 一词在 Backtrader 架构层与 Gateway RPC 层含义完全相反的问题），本计划冻结以下术语，**所有负例校验与文档表述必须严格遵守，禁止按子串 `"direct"` 粗暴匹配**：

| 术语 | 精确定义 | 归属边界 / 禁用误解 |
| --- | --- | --- |
| **Direct 模式（`mode: direct`）** | Backtrader 策略进程经 `bt_api_py` 统一 SDK（`DirectWriteCoordinator` + `live_state`）直连 provider（交易所）的实盘路径 | 不连接 Gateway/Risk/Execution/Monitor/Runtime 微服务；不加载这些子包 |
| **Gateway 模式（`mode: gateway`）** | Backtrader 策略进程接入部署级五组件（Gateway/Execution/Risk/Monitor/Runtime）服务体系的实盘路径 | 策略进程不加载 provider 原生交易客户端模块、不持有直连 TD 会话 |
| **Gateway `direct.*` 操作与端口** | Gateway 服务自身的操作名与挂载点：`direct.reserve`、`direct.dispatch`、`direct.release`、`direct.cancel`、`direct.control.*`、`direct.delegated_*`、`broker.direct_write`、`application.direct_write` | **属于 Gateway 模式内部契约，与 Direct 模式完全无关**；S-01 负例不得误伤 Runtime 的 `application.direct_write` 等合法 Gateway 绑定 |
| **Execution `DIRECT_PATH`** | SDK `ExecutionOrderRouter`（`bt_api_py/execution_routing.py`）对未命中执行路由规则的订单返回的枚举值 `ExecutionRoutingOutcome.DIRECT_PATH`，意为“不进 Execution 母单，改走 Gateway 侧既定直通/Risk 委托路径” | **属于 Gateway 模式内部路由语义，绝不是切回 Direct 模式** |
| **部署级五组件全备** | 运维与预检视角：同一实盘账户环境下 Gateway、Execution、Risk、Monitor、Runtime 五服务均已部署、版本兼容、健康运行，且 Gateway 启用 `monitor_required=true`、策略进程受 Runtime 监督 | 不等于 `GatewayBtApiStore` 在策略进程内建立 5 个 RPC 客户端 |
| **策略进程绑定** | `GatewayBtApiStore` 在策略进程内实际装配的客户端句柄集合（按已确认的 `D62S-01` 方案 A + `D62S-05` 方案 A2：Gateway 客户端负责行情/账本/delegated_cancel/就绪证明 + Execution 客户端为唯一订单提交入口；可选只读 Risk 状态客户端不作绕过下单旁路） | Monitor 凭 Gateway 就绪证明快照核验，Runtime 凭外部受管启动合同核验 |
| **模式（`mode`）** | 仅 `direct` / `gateway` 二选一，启动时由组合根求值并写入 `live_state` 的不可变会话状态 | `market_data_only` / `write_admission=False` 是可叠加的**写权限状态**，`local_replay` 是 **Feed 来源**，均**不是**第三/第四种模式 |
| **实盘只读预演态** | 在完整 Direct 或 Gateway 实盘拓扑上关闭写入（Direct：`write_admission=False`；Gateway：`market_data_only=True`），用于上线前验证行情、日历、账本、风控与监控链路 | 两种模式均合法（`D62S-08`），绝不产生任何交易所写操作 |
| **非实盘工具** | 离线回测、`local_replay` 回放、`ServiceReadProxy` 只读观察及无 SDK 预置数据夹具 | 独立导出，不携带账户写能力，不混入实盘 Base |
| **互斥粒度** | 四层强制互斥（`D62S-09a` 已确认）：① **策略目录层**（`state/identity.json` 冻结不可变 `mode`）；② **对象图/组合根层**（Store/Feed/Broker 共享同一不可伪造运行绑定）；③ **账户作用域层**（同账户 × 场所 × route 下严禁 Direct 与 Gateway 混跑）；④ **进程层**（默认单进程单模式，保证严格模块零交叉加载） | — |

### 6.2 Gateway 订单与数据流（已确认方案：D62S-01 方案 A + D62S-05 方案 A2）

- **行情流**：`交易所 → provider → Gateway MarketHub → GatewayMarketAdapter（MarketSourcePort）→ BaseBtApiFeed → 策略`；
- **下单流（全量必经 Execution → Risk → Gateway，无旁路）**：`策略 → GatewayBtApiBroker（本地预检 + live_state W1 落盘）→ Execution 服务（唯一上游受理入口）`：
  - **普通单（含限价、及轨道二扩展后的市价/条件单）**：经 Execution `PASS` 透传受理 → 先持久化不可变记录（W2 起点）→ Risk 校验与预留 → 受权 Risk 代理 principal 调 Gateway 交易 owner（W3 起点：`DISPATCHING` 落盘）→ 原生报单；
  - **切片/轧差母单**：经 Execution `SLICE`/`TWAP` 或反向轧差编排 → 先持久化母单（W2 起点）→ Risk 母单预留与子单风控 → 受权 Risk 代理提交 Gateway 交易 owner（W3 起点：`DISPATCHING` 落盘）→ 原生报单；
  - **双层防绕过**：严格 Gateway 模式下禁止 `ExecutionOrderRouter` 返回 `DIRECT_PATH` 未命中直通旁路（`D62S-05`），且 Gateway 服务端默认不授予策略 principal `SUBMIT`/`RESERVE` 权限（`D62S-03`），策略进程不存在任何绕过 Execution 或 Risk 直接向 Gateway 下单的通道；
- **撤单流**：策略保留经 Gateway `direct.delegated_cancel` 的受权委派撤单（Risk 或 Execution 不可用时仍可对已入场委托撤单），已入场母单子单按原归属/运营 DRAIN 处理；
- **观测与监督**：Monitor 旁路接收事件与心跳，Gateway 凭 `monitor_required=true` 实施账户级 `STOP_NEW`；Runtime 作为外部父进程监督策略启停与退出码。

> **派发前授权核对点（具名冻结，SPLIT-00b 输出字段级 Schema）**：
> - **BT → Execution**：核对 `mode=gateway`、不可变运行绑定、意图身份（`request_key` / `idempotency_key`）、合约规则与行情资格（拒绝任何 `DIRECT_PATH` 旁路）；
> - **Execution → Risk**：核对不可变母单/透传意图已持久化、`account_scope/strategy_scope/route/run_id`、`risk_operation_id` 与有效期（`valid_until_ns`）；
> - **Risk 代理 → Gateway 交易 owner**：核对调用方为受权 Risk 代理 principal（非被撤权的策略 principal）、作用域与代次有效、无 `FREEZE`/`DRAIN`/适用 `STOP_NEW`、已落盘 `DISPATCHING`。任一证据缺失或过期 → 拒绝派发或保持 `UNKNOWN`，绝不回退 Direct。

## 7. 关键不变量与持久化故障窗口

1. **单写者（严格限定于协作进程边界）**：
   - Direct 模式（`D62-05` 单策略独占账户）：策略目录级本地 `state/run.lock` 防止同目录双启；
   - Gateway 模式：账户级单写者由每账户唯一 Gateway 实例（`D63-02/08`）+ 本机 SQLite lease / `HostAccountRegistry`（跨主机以 SDK `account_writer_authority` TTL 租约为候选，SPLIT-00b 选型冻结）保证；策略级单写者由 Gateway 服务端租约 + 本地 `state/run.lock` 保证（2026-11-14 同账户同策略禁双活决定维持）；Execution 每账户一进程（`D65-13`）。
   - **明确残余边界声明**：所有本地锁与同库 SQLite lease **仅约束协作进程**；同账户在其他主机、未接入本系统的手工客户端或第三方终端的外部写入属于**操作层残余风险**（靠账户权限、运营规程与交易所限制管控），不以 fake 测试冒充全局防线。多策略共享会话的作用域为账户级 Gateway 交易 owner，严禁误设为“每策略一个 TD writer”。
2. **唯一订单意图、UNKNOWN 不可变性与 W1/W2/W3 正确次序窗口**：
   - 任何外部派发前须先持久化唯一命令身份与绑定；超时、断连、重启产生的结果不明一律保持 `UNKNOWN`，**严禁标为 `Rejected`、清空 pending 行、重置账本、自动重发或切回 Direct**；
   - 必须按真实安全次序分别验收三个高危持久化窗口（修正 v1 将 W2 顺序写反的错误）：
     - **W1（`BT ↔ Execution/Risk`）**：策略 `live_state` 已落盘意图并外发请求，但回复丢失或策略进程崩溃；
     - **W2（`Execution ↔ Risk`）**：Execution **必须先持久化不可变母单**，再调用 Risk `reserve`；验收“母单已落盘、Risk 已预留额度但回执未落盘到 Execution”时的原 `risk_operation_id` 查证、继续或释放，防止额度泄漏；
     - **W3（`Risk/Gateway ↔ Provider`）**：Gateway 已写 `DISPATCHING`（或 Risk 已 claim）并调用原生报单，但回复丢失/进程崩溃 → `UNKNOWN` 阻断并仅沿原身份查询对账。
   - 不以单次正常下单冒充跨组件原子性，不承诺未经证明的端到端 exactly-once。
3. **不跨模式热切换与空仓迁移（`D63-12`）**：
   - 首期跨模式迁移**只允许空仓**（`D63-12`）：先阻止新意图 → 停写 → 保存并核验无活动委托与未决/UNKNOWN 记录 → 原路径对账完成 → 旧会话标记停止并留下所有权交接审计证据 → 由获授权人员使用新绑定（及新目录或显式升级后的目录）人工启动新模式；**带仓迁移明确排除**。
   - 任何运行期回退到 Direct 均为禁止行为；版本回滚属于离线发布操作。
4. **可观测性与脱敏**：
   - 所有诊断与拒绝事件记录 `mode`、不可逆脱敏的 session/strategy correlation（如 `account_hash` / `strategy_uuid`）、状态码与故障分类（区分网络不可达、认证失败、版本不兼容、业务拒单、数据掉队与时钟异常），**绝不输出账户密钥、密码、私钥路径内容或原始凭据**。
5. **存量清退红线**：
   - 旧混合路由的 `state/execution_routing.sqlite` 与历史 `pending.json` 中的未决/UNKNOWN 记录是唯一可读审计证据；清退动作限定为“**只读导出 CLI + 审计日志 + fail-closed 拒绝新写入**”，绝不删库、删历史状态或篡改日志；处置审批人由用户指定。

## 8. 分期路线与双轨解耦策略

为避免 Backtrader 侧 37,000+ 行实盘单体拆分被 SDK 侧外部数据前置（如 `R-05` 真实切点数据、`gateway_api._risk_reserve` v2、`risk_parent_port` 子单派发、Windows B 类安全门）无限期死锁，本计划采用**“协议先行、双轨推进、联合合龙”**策略：

- **轨道一（Backtrader 仓，离线可完整验收）**：完成模式边界、组合根、薄 Base + Direct/Gateway 拆分、`live_state` 模式印记、存量清退与 22 个示例迁移，通过 `S-01`、`S-02`、`S-06`、`S-07`、`S-09`、`S-10`、`S-11`、`S-12` 及基于冻结契约替身的 `S-03`、`S-04`、`S-05`、`S-08`。
- **轨道二（`D:/bt_api_py` 及各子仓，承接迭代 63–68 剩余门）**：按“**子仓 → SDK 父仓 gitlink → Backtrader**”顺序补齐 strict Gateway 配置载体、principal 权限默认、`GatewayReadinessProof`、`_risk_reserve` v2、`reserve_child/dispatch_child` 真实现、`AtomicIntakeService` 接 `risk_port`、**Execution `PASS` 市价/条件单透传扩展（`D62S-05`）**、`R-05` 共同切点与五组件联合健康快照。
- **合龙红线**：在轨道二完成真实五组件联合闭环、且迭代 66（Runtime 监督启停）与迭代 68（Monitor 告警）关键门禁通过前，**Gateway 模式对真实/模拟账户写入整体保持 `NO-GO`**。
