## 2. 阻塞项（P0，SPLIT-00 冻结前必须关闭）

### R62S-01　以“用户确认”取代多条既有用户决定，却没有新的决定登记

需求文档 §1 以“用户确认：实盘只允许两种互斥路径”为总前提，§3/§4/§8 进一步要求：

- Gateway 模式必须同时具备 Gateway、Execution、Risk、Monitor、Runtime 五组件；
- Risk 是 Gateway 的必配组件；
- Execution 是新策略订单意图的唯一上游受理和编排入口；
- 五组件部分接入、缺关键证据时拒绝启动/写入。

这与下列已登记的用户决定直接冲突，而文档没有给出新的决定编号、日期和原话：

| 既有决定 | 内容 | 证据 |

| D63-29（2026-11-06） | runtime 是独立微服务，不受 S-09 限制，负责策略启停；不是 Gateway 的写入前置 | 同上 `:603`、`:692` |
| D63-17 / INV63-10、D65-18（2026-11-06） | Gateway 不检查风控批准；用户明确更正“启动 Gateway 时也可以接受没有风控批准的订单” | `迭代63-.../迭代计划.md:613`；`迭代65-.../迭代计划.md:645` |

### R62S-02　“五组件均必须配置”没有可承载的配置/合同载体

需求文档 §3 的目标是“五组件均必须配置并完成统一预检；部分接入、绑定错配、版本不兼容或缺关键证据拒绝启动/写入”。但当前实际只有两份互不相干的配置面：

- **每策略 Gateway 配置**：`bt_api_py/gateway_strategy_config.py` 的 `GatewayStrategyConfig`，`schema_version` 固定为 1（L448），只接受 `gateway`、`risk`（值可为 `"none"`）和可选 `execution`（可为 `"none"`）；没有 Monitor、Runtime 字段。
- **部署服务清单**：`bt_api_py/service_config.py` 的 `_COMPONENT_PORTS`（L271）才定义了 gateway/execution/risk/runtime/monitor 五类组件及其角色/端口，并用 `service_config_schema_version`（L587）、组件必填（L600-606）、`MONITOR_CONTROL_RETIRED`（L617-625）做校验。
- **Backtrader 侧**：`btapistore.py:605` 只根据 `config` 中是否存在 `gateway_strategy` 选择 Gateway 模式；L650-675 只调用 `parse_gateway_strategy_config`，从不读取 `service_config`。

**影响**：

- “缺任一服务拒绝启动”在 BT 进程内没有判定对象：Runtime/Monitor 不出现在每策略配置里，BT 也没有读取部署清单的入口。
- “版本不兼容”没有定义版本字段；两份配置的版本字段（1 与 1/6）语义不同，不能直接比较。
- “统一预检”没有定义谁调用、调用哪个端点、什么算健康证据。S-01 的“缺任一服务”负例无法落地，S-03 的“五端口各验身份、版本、健康”没有合同来源。

**要求**：

1. 在 SPLIT-00 冻结“五组件”的权威载体：是每策略配置引用一份部署清单（按 `service_id/instance_id/scope_ref`），还是 BT 新增只读预检适配器读取 `service_config`，或是 SDK 在 `GatewayStrategyConfig` 中增加 strict 模式与组件引用。三者不能并存而不规定优先级。
2. 定义版本协商字段、健康证据格式、超时/不可达/认证失败的区别，以及“已确认不兼容”与“暂时不可达”的不同处理（后者不能伪装成前者，反之亦然）。
3. 明确 strict 校验由谁实现：SDK 的 `parse_gateway_strategy_config` 增加严格模式，还是 BT 在构造 Store 前做包装校验。文档已正确要求“不能把导入成功当就绪、不默认破坏 SDK 其他用途”，但尚未给出归属。

### R62S-03　把 Execution 设为唯一受理入口，与当前拓扑和 SDK 现状冲突；且遗漏了 child dispatch 硬阻断

**当前拓扑**：

- Gateway 模式的 BT Broker 在 `_btapi_gateway_stream.py:547` 直接构造 `OrderRequest` 与 Gateway 意图，再经 SDK facade 提交；选 Risk 时走 Risk，未选时走 Gateway（D64-01，同文件 L698 注释）。这条路径没有独立的 Execution 服务 intake。
- 独立的 Execution 路由只存在于 `_configure_execution_routing` 的 direct SDK + 远端 parent port 组合（`btapistore.py:1186-1262`），而且该组合的三个构造参数（`service_client_config`、`gateway_client_config`、`execution_parent_port`，`btapistore.py:492-494`）在仓库内没有被任何生产组合调用；它是一条“已暴露、已单测、未接线”的构造路径，不是当前实盘流量。

**SDK 侧还有一处文档未列出的硬阻断**：

- `bt_api_py/risk_parent_port.py:126-137`：即使父单已预留，`reserve_child()` 与 `dispatch_child()` 都硬编码返回 `{"status": "UNKNOWN", "code": "risk_parent_child_unavailable"}`。
- 因此，迭代 64–68 剩余门计划里“把 `RiskParentPort` 传入 `ParentSubmitService`”的第 3 项（`迭代63-Gateway统一转发与多策略共享会话/迭代64-68剩余门工程实施计划-2026-11-19.md:106`）只能解决“父单有没有 risk_port”，仍不能产生可用的子单派发。
- 需求文档 §7 已正确指出 `AtomicIntakeService` 未接 risk_port、`ParentSubmitService` 仅在测试中使用、Gateway 另有 risk_client 装配；但未把“child reserve/dispatch 恒 UNKNOWN”列入阻塞清单。

**影响**：

- §4 的“Execution 作为新策略订单意图的唯一上游受理和编排入口”在现有 SDK 上无法实现；S-03 的“上游 Execution 受理/编排、按合同核对 Risk 证据，只有 Gateway 交易 owner 发往假场所”会直接失败。
- 如果按 §4 强行实施，当前可工作的 Gateway 直连 + Risk 路径反而会被判定为不合规；这与 D65-10/D65-15 的既有决定冲突（见 R62S-01）。
- 文档 §1 的“组件全备不是说五者串行转发每笔订单”与 §4/S-03 的“每笔订单先 Execution、再 Risk、再 Gateway”在字面上不一致；读者无法判断到底哪些订单可以直达 Gateway。

**要求**（二选一，并登记决定）：

- **方案 A（与既有决定相容）**：保留当前“Gateway 直连 + 可选 Risk”为基线；Execution 只对有明确执行路由的订单生效；未命中/不可用按 D65-10 处理。此时 §4 的“唯一上游受理”必须删除或降级为“有路由命中的订单由 Execution 受理”，S-03 相应拆分。
- **方案 B（改变拓扑）**：由用户明确登记“Gateway 模式下所有策略订单意图必须经 Execution 受理”。此时必须新增 SDK 工作项：`AtomicIntakeService` 接 risk_port、`ParentSubmitService` 生产宿主、`reserve_child`/`dispatch_child` 的真实实现、执行证据与 Gateway 回执的关联合同；并把它们列为 SPLIT-00 的阻塞依赖，而不是放在 §7 一句“重点补齐”里。

**要求**：把 §7 风险改写为“ParamsMixin/lifecycle 与 MRO/参数覆盖”，S-06 改为验证 `params` 字典、`p`/`params` 别名、`donew/doinit/dopostinit` 顺序、`_owner`/`_clock` 解析，而不是验证一个不存在的 metaclass。

### R62S-06　Monitor/Runtime“必配”与既有默认可选/独立定位冲突，且故障语义未冻结

- Monitor：D63-21/INV63-11 规定缺省可选；只有显式 `monitor_required` 时，Gateway 才按自身观察对账户施加 STOP_NOW。D68-02 还区分“确认旧版不兼容”（启动拒绝）与“暂时不可达/认证失败”（按原宽限合同）。需求文档却把 Monitor 列为 Gateway 必配，并在 §4 写“服务不足、过期或无法证明授权时，至少禁止新开仓”。
- Runtime：D63-29 明确 runtime 不受 S-09 限制，是独立微服务；迭代 66 当前整体 `IN_PROGRESS / NO-GO`，受保护的 007 只跑过一次 30 秒只读运行且由独立 runner 启动，未由 Runtime 监督。把 Runtime 设为 Gateway 写入前置，等于让 Gateway 验收被 66 的未完成状态阻塞。

**影响**：

1. Monitor 是遥测组件，若其不可达就禁止交易，会把“可观测性”变成“可用性单点”；这与 Monitor README 的“只记录遥测、无交易/风控/暂停/撤单权”定位不一致。
2. Runtime 失联时，至少撤单/平仓不应被一并阻断；文档 §4 只说“至少禁止新开仓”，S-05 又把“平仓/撤单按冻结政策”留到后面，冻结前没有可执行矩阵。
3. 五组件必配会让 S-03 事实上依赖 66/68 的验收；文档 §11 已承认这一点，但 §3/S-03 没有把依赖写进门禁。

**要求**：增加“组件必配/可选 × 动作（新开/加仓/减仓/平仓/撤单）× 故障类型（未启动/不可达/认证失败/版本不兼容/失联超时）”矩阵；明确 Monitor/Runtime 的缺失到底是启动拒绝、禁止新开、还是仅告警。若确实要把它们变成写入前置，必须先登记取代 D63-21/D63-29/U64-8 的新用户决定。

### R62S-07　单写者不变量大于可验证边界，且未覆盖多策略共享会话

- 文档 §6 不变量 1 要求“同一允许写入的作用域同一时间只有一个被证明有权的写入路径；进程锁、generation/fencing、账户身份和 provider 会话一致”。
- `bt_api_gateway/README.md` 明确：SQLite lease 只协调“cooperating processes on the configured database”，不能排除手工写入、其他主机、不查询该库的 provider 会话；`bt_api_execution/README.md` 也明确“不提供外部账户级写栅栏”。
- S-04 只测试“两运行实例争同一范围、过时代次、丢锁、重启”，没有手工/外部写者，也没有覆盖 provider 会话不协作的场景。把不变量写成“唯一写入路径”会超出证据能力。

此外，Gateway 的核心目标是“多策略共享同一账户会话”，但文档只在 §9 问题 3 问“共享账户/多个策略如何授权”，正文没有说明单写者作用域与多策略的关系。若把作用域误设为“策略”，就可能退化成每策略一个 writer，破坏共享会话；若设为“账户 × 场所 × route”，则多个策略共享一个 Gateway 交易 owner 才是正确模型。

**要求**：

1. 把不变量限定为“协作进程之间”；对“外部/手工写者”单列为残余风险，要求操作层控制（账户权限、运营规程、provider 侧限制）而不是 fake 测试门禁。
2. 明确写作用域元组（至少账户、场所、route；策略范围另列），并说明多策略共享会话下只允许一个 Gateway 交易 owner。
3. S-04/S-08 增加“两个策略共享同一账户会话”“一个策略换代次、另一个仍持有旧会话”“Direct 与 Gateway 同时存在但作用于不同账户/场所”的用例，或明确声明后者被禁止。

### R62S-08　“薄 Base + 两套实现”没有冻结类图与 mixin 归属

文档 §5 提出 `BaseBtApiStore` / `DirectBtApiStore` / `GatewayBtApiStore`、`BaseBtApiFeed` 等，并说“现有 mixin 可先继续由各自实现使用；拒绝多继承带来的 MRO/参数覆盖变化”。但当前结构是：

- `BtApiStore(StoreManagedExecutionBridgeMixin, StoreReconciliationBridgeMixin, LiveStoreBase)`（`btapistore.py:438`）；
- `BtApiFeed(LiveBarCohortFeedMixin, LiveFeedBase)`（`btapifeed.py:665`）；
- `BtApiBroker` 有 9 个 mixin（`btapibroker.py:179-190`），其中 Direct 逻辑已在 `_btapi_direct_mode.py`（6,363 行），Gateway 逻辑已在 `_btapi_gateway_stream.py`（2,123 行）。

也就是说，代码已经“按模式分文件”，真正要做的是**组合根、所有权和兼容壳的提取**，而不是从零拆两个类。新增 `BaseBtApiBroker` 到底是：

- 放在 9 个 mixin 之上、之下，还是替换其中某个？
- 由 Base 持有 `store`/`start`/`stop`，还是继续由 mixin 各自处理？
- 参数声明放在 Base、具体类，还是两边都放？

文档没有回答。SPLIT-02/03 无法据此评审，且一次提交同时重排 MRO 和搬模块的风险很高。

**要求**：在 SPLIT-00 输出一张“现有类/mixin → Base/Direct/Gateway”归属表，并冻结以下约束：

1. `BtApiStore`/`BtApiFeed`/`BtApiBroker` 的公开 import 和类名保留；
2. 新增 Base 不改变 `ParamsMixin` 参数收集顺序和 `Strategy` 直接子类的初始化例外；
3. Direct/Gateway 各自拥有自己的写路径 mixin，Base 不吸收授权模型；
4. 每个阶段单独提交，禁止“搬模块 + 改执行语义”同提交。

### R62S-09　跨仓工作项、版本 pin 与提交顺序缺失

需求文档的新合同至少需要 SDK 侧改动：strict Gateway 配置、五组件清单/版本、child dispatch、Risk 证据合同、可能的 intake 宿主。但文档没有：

- S-07 只说“隔离 wheel 导入与依赖闭包”，没有给出五个子包的版本矩阵和 SDK 侧合同测试。

**要求**：增加“SPLIT-0S SDK 合同项”（或等价工作流），列出每个子包的版本/SHA、需要新增或修改的合同、验收测试和证据等级；按仓库约定执行“子仓 → SDK 父仓 gitlink → Backtrader”的提交顺序。S-01/S-03 不得只靠 BT 侧改动通过。
