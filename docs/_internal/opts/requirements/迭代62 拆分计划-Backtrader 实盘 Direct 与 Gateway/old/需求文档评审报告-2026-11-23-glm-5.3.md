## 4. 发现的问题与建议

按影响排序。均为合同/计划层缺口，不影响文档作为 SPLIT-00 输入的资格。

### P-1（中）live_state 状态所有权未进入拆分形态与待确认清单

§5 只定义了 Base/Direct/Gateway 的 Store、Feed、Broker 三类形态，但实盘状态的持久层已经按模式分化：`backtrader/live_state/` 中 `identity/sequence/pending/snapshot/state_dir/audit` 为公共层，而 `gateway_pending.py`、`gateway_execution_state.py`、`gateway_order_state.py`、`gateway_execution_route.py`、`gateway_initialization.py` 为 Gateway 专属（btapistore.py L652–672 证实 Gateway 模式绑定 `GatewayPendingHost` 与 `StrategyStateDir`）。Direct 的"对账、持久化、停止"（§3 目标行 1）落在 live_state v2 快照。拆分时这一层的归属（公共 Base 持有哪些、Direct/Gateway 各持哪些、`gateway_*` 模块是否随 GatewayBtApiStore 走）是和 MRO 同级的结构决策，§9 待确认清单未列。**建议：在 §5 增加第四行"状态持久层"形态，或在 §9 增补待确认项。**

### P-2（中）"五组件必配"的 BT 侧预检合同缺口与 SPLIT-00 退出条件存在先后矛盾

§3 要求 Gateway"五组件均必须配置并完成统一预检"，S-01/S-03 依赖该预检。但现状是：SDK `gateway_strategy_config.py` 的策略配置只有 Risk/Execution 两个可选组件字段（L494–495），无 Monitor/Runtime 字段；`service_config.py` 的 runtime/monitor 角色校验属于服务清单（manifest）层，不是策略配置层。也就是说五端口身份/版本/健康预检是**全新合同**，而它被放在 §9.2（待确认）。SPLIT-00 的退出条件（"有逐项 owners、证据等级、依赖图"）并未要求闭合 §9.2，但 SPLIT-01 的"组合根和故障配置断言"必须先有配置 schema 才能写负例。**建议：把 §9.2 的五组件绑定格式/健康证明明确提升为 SPLIT-00 退出条件之一，否则 SPLIT-01 会带着未冻结的 schema 开工。**

### P-3（中）Execution 唯一受理模型与现行意图路径的差距应作为显式依赖项

§4 建议"Execution 作为新策略订单意图的唯一上游受理和编排入口"。现状：Gateway 模式的实际下单走 `_gateway_submit_order` → `bt_api_py.gateway_direct_client.build_gateway_order_intent`（gateway_direct_client.py L261），**不经 Execution**；生产 `execution_parent_service_host.py` 的 AtomicIntakeService 无 risk_port；ParentSubmitService 的 risk_port 证据限于测试（均经核实，文档 SPLIT-00 段亦如实记载）。文档已承认差距，但只作为"重点补齐契约"的叙述，未列为 SPLIT-00 的显式依赖/阻塞项。另有一个需要调和的模型冲突：`gateway_strategy_config._risk`（L332–337）现行语义是"经 Risk 的委托命令（delegated command/status/cancel）"，而 §4 目标是"Execution 验证 Risk 证据后派发"——两种 Risk 参与模型不同，冻结合同时必须二选一或明确共存边界。**建议：SPLIT-00 增加显式依赖行"Execution intake 接入生产 host + risk 证据链"，并把两种模型的取舍列为 SPLIT-00 必须冻结的决策。**

### P-4（低-中）双 SDK checkout 的权威性未指定

文档正确区分了 D:/bt_api_py（dev）与 D:/source_code/bt_api_py（code-optimization，排除），但未指定哪一个是拆分工作的权威基线。跨仓提交顺序规则（子仓 → SDK parent gitlink → Backtrader）要求唯一权威 checkout，否则 SPLIT-00 的"盘点本地与对应 SDK/五组件提交"结论无法复现。**建议：SPLIT-00 记录权威 checkout 路径、各子仓 dev 提交哈希与 gitlink 状态。**

### P-5（低）单写者机制盘点可引用既有候选，减少空白感

§9.3 把锁实现列为待确认（正确，不指定技术）。但 SDK 已存在 `bt_api_py/account_writer_authority.py`（跨主机 TTL 写者租约、派发租约、接管/撤销证据）与本机 `account_coordination`/同文件 SQLite lease 两套既有机制（职责规范亦有记载）。§6.1 的作用域矩阵若在 SPLIT-00 盘点中列出这些候选及其证明等级，冻结会更快；当前表述容易让读者以为完全从零设计。

### P-6（低）基线冻结建议记录文件哈希

文档行号引用在当前 HEAD 仍有效（P-2 核对段），但 SPLIT-00 若只记提交号，后续任何触及这五个文件的提交都会使行号证据失准。**建议：SPLIT-00 冻结提交号 + 五个关键文件的哈希（与仓库"guard 变更需 hash 校验"的既有纪律一致）。**

### P-7（低）示例迁移面未显式列入 SPLIT-04

`examples/live/007_ctp/` 现有 30 个目录，含 `_direct`/`_gateway` 成对示例。SPLIT-04 的"旧混合写入口和文档从正式支持面移除"只在字面上覆盖写入口；示例是用户可见的支持面，且是 §7 风险表"公共 import/示例回归"的具体载体。**建议：SPLIT-04 迁移表显式包含示例清单及其目标模式归类。**

### P-8（低）建议为热路径加最小守门基准

"目标不是提速承诺"正确，但拆分会改变 submit/cancel/_load 的分发路径（现 btapibroker.py L2310–2338 的顺序分支会被模式化）。若完全无基准，"架构验收不依赖某次时延更好"可能反向掩盖真实回归。**建议：S-06/S-07 中加一条离线最小基准（同数据下事件吞吐/延迟分位数对照），只作回归守门，不作提速指标。**
