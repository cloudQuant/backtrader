### P0-2 订单链拓扑和已实现的 D64-02、D65-01 不一致

文档 §4 提出：订单意图 → Execution 受理 → “约定的授权组件”核对 Risk 证据 → Gateway 交易 owner 派发。Risk 在这个模型里是签发**证据**的一方。

现有决定和源码是另一种拓扑：

- **D64-02（Risk 是带内委托提交者）**：`gateway_strategy_config.py:332` 写明 “PLACE never goes to the Gateway directly while Risk is selected”。选了 Risk 后，策略不能持有 `direct.reserve/dispatch`，必须持有 `direct.delegated_*`。BT 侧 `_btapi_gateway_stream.py` 有完整的 delegated command 记录和恢复（L216、L844、L1033–1193），撤单固定走 “delegated Gateway operations, never via Risk”（L1103）。
- **D65-01**：“Execution → 可选 Risk → Gateway 登记”。
- **SDK `ExecutionOrderRouter`**：结果包含 `DIRECT_PATH`（NO_MATCH 时保持原路径，`execution_routing.py:647–656`）。BT 在 `DIRECT_PATH` 时按 `risk_routed` 改走 Risk 委托或直达 Gateway（`_btapi_gateway_stream.py:747–763`）。

所以当前 Gateway 模式实际上有 4 种子拓扑：仅 Gateway、Gateway+Risk 委托、Gateway+Execution（NO_MATCH 直达 Gateway）、Gateway+Execution+Risk（NO_MATCH 走 Risk 委托）。文档要定的是：

1. Risk 用**证据模型**（Execution 或 Gateway 验证许可）还是**委托模型**（Risk 代为提交）？两者的持久化窗口、UNKNOWN 归属、撤单路径和 BT pending state 版本（v7 delegated 记录）都不同。选证据模型就要删掉 SDK 的 delegated 路径并迁移 BT pending state；选委托模型，§4 的消息流就要改写。
2. “约定的授权组件”到底是谁？11-11 决定和 D63-37 都明确 **Gateway 不检查风控批准**。如果由 Execution 验证，Execution 就会成为 Risk 证据的权威验证者，这需要新的用户决定。
3. **D65-07：Execution 首期只支持限价母单**，不支持的订单明确拒绝。Execution 一旦成为唯一入口，Gateway 模式下的市价单、止损/条件单和平仓单都会被拒，现有 11 个 `_gateway` 示例也可能失效。文档要么规定一个 PASS 透传方法（D65-08 已有 PASS）覆盖哪些订单类型，要么接受这个功能收缩并写进迁移说明。
4. 撤单的受理入口：撤单也经 Execution，还是保留现有的 delegated cancel 直达 Gateway？Execution 不可用时撤单是否放行（迭代 63 分析 S-05a 和 11-11 决定都放行撤单）？

### P0-3 “五组件必配”目前只在客户端检查，没有服务端强制

文档把“必须接入五组件”写成 Backtrader/SDK 启动校验（S-01、S-03），但旁路就在服务端：

- D63-37 默认**保留策略 principal 的 SUBMIT**。一个配置了五组件的 BT 进程，和另一个只连 Gateway 的进程（或改过配置的同一进程），在 Gateway 看来都是合法提交者。11-11 决定 §1 原文是：“独立持有 SUBMIT 权限的客户端仍可能绕过 Risk……不把 SDK 的启动校验说成 Gateway 的强制保障。”
- SDK 仍然接受 `risk: "none"` 和 `execution: "none"`；`ExecutionOrderRouter` 仍会返回 `DIRECT_PATH`。

**要求**：

1. 把“Gateway 模式 = 五组件”定义成**服务端可验证的不变量**：Gateway 账户配置里策略 principal 不持有 SUBMIT/RESERVE，只有绑定的 Execution（代理 principal）持有。这一条要作为新决定，取代 D63-37 的默认值。
2. BT 自己连不到 Monitor、Runtime（SDK `_create_api` 不装配二者），所以 BT 能检查的只有“Gateway 给出的、带代次的就绪证明”。证明里要包含 Risk/Execution 绑定、`monitor_required` 状态和 Runtime 监督身份。不要设计成 BT 自己去连五个端点探活，否则又会出现“可达 ≠ 有权”的问题。
3. S-03 的“无 Direct 场所写客户端”要改成可检验的说法：例如 Gateway 模式的策略进程不加载 provider 交易客户端模块，也不持有场所 TD 会话（参考迭代 63 的 C-7 模块探测）。

### P0-4 现状盘点漏了一条现存写路径和多处服务入口

`BtApiBroker.submit`（L2310–2420）的实际分支顺序是：market-data-only → Gateway stream → `_direct_active()` → `factor_execution_coordinator` 拒绝 → **旧的 SDK 托管/服务执行分支**。最后这个分支包括 `ServiceExecutionSession` 写者范围、`_consume_approval_operation`、`execution_recovery` 的 recovery_exit、`startup_preflight` 等，**既不是 Direct，也不是 Gateway**。此外还有：

- Store 构造参数 `managed_execution_adapter`、`execution_authorization`、`settlement_authorization`（`btapistore.py:655–657、682–686`），以及 `backtrader/service/service_execution_session.py`、`_store_managed_bridge.py`、`examples/service_execution_session/run.py`；
- Direct 下的 `execution_config` / `DIRECT_EXECUTION_CONFIG_KEYS`（`order_journal`、`account_maximum_loss_bps`、`account_risk_max_age_seconds` 等，`direct_api_assembly.py:31–44`）。一旦配置了这些键，`_direct_write_mode` 就会变成 False（`btapistore.py:741–756`），订单转入上面那个旧分支；
- SDK `BtApi` 的 `market_runtime_factory`（服务行情）、`execution_order_routing`（Execution 加 Gateway intent）；
- `event_batch_handoff` 与 execution 配置的互斥。

这些都要进入 §2 的模块表和 §3 的配置矩阵，并逐项归类：Direct 保留（例如 `order_journal` 是否就是 Direct 的“订单身份/持久化”）、Gateway 吸收、按 D65-11 退役，或作为非实盘工具保留。否则 S-01 的“配置笛卡尔负例”会缺一大块，SPLIT-04 也无法证明“旧混合写入口全部移除”。

### P0-5 “Direct”一词在不同层含义不同，没有术语表

在 SDK/Gateway 语境里，`direct.reserve`、`direct.dispatch`、`direct.control.*`、`direct.delegated_*` 是 **Gateway 服务的操作名**；`broker.direct_write`、`application.direct_write` 是 Gateway 端口；`ExecutionRoutingOutcome.DIRECT_PATH` 指“绕过 Execution，直接走 Gateway/Risk”。这些都属于 Gateway 模式，和本计划所说的“Direct 模式”（BT 经 SDK 直连 provider）不是一回事。文档 §11 中“新 Gateway 禁止不命中回原 Direct”就有歧义：按 SDK 语义，“原 Direct”其实是 Gateway 的 `direct.*` 路径。

**要求**：增加术语表，至少区分 `Direct 模式`、`Gateway direct.* 操作`、`Execution DIRECT_PATH` 三者。S-01 负例规则只针对 BT 层的模式标签，不能按字符串 “direct” 误杀 Runtime 的 `application.direct_write` 绑定。

## 4. 重要问题（P1：SPLIT-00 冻结时必须处理）

**P1-1 场所 × 模式适用矩阵缺失。** D63-10 规定 Gateway 首期只交付 CTP，OKX/Binance Gateway 后续再接，现有 direct 不取消。所以“实盘只有两种互斥路径”在 OKX/Binance 上实际只有 Direct。§9 Q5 只问了“第一批交易所”，应补一张“场所 × 模式 × 证据等级”表。

**P1-2 迁移规则应引用已有决定。** D63-12（Q40）已经规定：direct 迁入 Gateway 首期只允许策略**空仓**迁移，旧策略停止且没有活动或未决订单；带仓迁移以后再做；外部基线不自动归属策略。§6 不变量 3 和 S-08 只写了泛化的“停写、对账、交接”，应直接采用 D63-12 作为首期边界，带仓迁移明确排除在外。

**P1-3 Feed parity 前提不成立的部分。** Gateway 行情路径现在拒绝 backfill、history、cohort 和 `orderbook_as_ticks`（`btapifeed.py:1029`），所以两套 Feed 的能力不对等。“用同一规范化数据做逐条事件 parity”只能覆盖交集。要补一张 Feed 能力矩阵，并说明同一策略在两种模式间“可复用”的边界（AGENTS.md 也说跨模式复用只是目标）。

**P1-4 Monitor “必配”的语义。** 要映射到现有合同：是不是等于账户级 `monitor_required=true`？如果是，就要沿用 D68-02（确认旧版不兼容时拒绝启动）、D63-36/Q34（运行中失联 → STOP_NEW，恢复后默认自动解除该原因），并承认它和迭代 63 分析 P4（“monitor 挂掉不影响下单”）的取舍已经改变。§4 写的“运行期故障域/降级策略待确认”其实大部分已有决定，应引用，不要重开。

**P1-5 Runtime 必配的可验证性和进度后果。** D66-02 规定 Runtime 首期只监督策略进程，迭代 66 当前是 NO-GO（007 runner 未纳管，UNKNOWN/OBSERVATION_ONLY）。Runtime 必配意味着 **Gateway 实盘要等 66 的“监督启停”验收通过后才能放行**。文档应明确写出这个进度依赖，并定义 BT 如何证明“本进程由 Runtime 监督”（例如 Runtime 下发的带代次的启动凭据，经 Gateway 就绪证明转交）。

**P1-6 单写者应复用现有边界，不必重新选型。** Direct 是单策略独占账户（D62-05）；Gateway 是每账户一个独立实例、唯一交易 owner（D63-02、D63-08）；Execution 是每账户一个进程（D65-13）；65 计划写明同一账户同一策略不允许两个主体同时运行。§9 Q3 “Redis/本地锁/服务选主”的提法过宽，应先把这些已定作用域填进单写者矩阵，只把真正的空白（例如跨主机 Gateway 实例互斥、E095 守护对账命令的接管证明）留作待决。

**P1-7 跨仓工作项没有进入分期。** 落实本计划需要的 SDK/Gateway 改动有：删除 `risk: "none"`、改掉 `DIRECT_PATH` 语义、决定 Risk delegated 路径的去留、Gateway principal 权限默认值、就绪证明、Direct facade 拒收 `market_runtime_factory`/`execution_order_routing`/`execution_config`。这些都不在 BT 仓。§7 的 SPLIT-01 写的是“模式分类和负例测试通过”，但很多负例的判定在 SDK 里。建议增加 **SPLIT-00b：SDK/Gateway 合同变更**，写明 owner 仓、提交顺序（子包 → 父仓 gitlink，按 AGENTS.md）和对应决定编号；SPLIT-01 依赖它。

**P1-8 Broker 拆分的共享状态先盘点。** 9 个 mixin 共享 `BrokerBase` 的 `orders`、通知队列、持仓字典、`_startup_ready` 等状态，Gateway 分支和 Direct 分支对同一字段的语义不一定相同（例如 `order.info` 中 `gateway_*` 和 direct 字段）。抽 Base 之前，要先产出“字段 × 读写方 × 模式”的共享状态清单，作为 SPLIT-03 的入口条件。这一项还要先解决 P0-1 中“`BtApiBroker` 源码不变”的冲突。
