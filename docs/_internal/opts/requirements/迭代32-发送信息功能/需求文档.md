## 1. 目标与决策

目标是让策略在回测与实盘中把消息**推送到人和团队真正会看的终端**（飞书/微信/QQ/Telegram/邮件等），并且这件事**绝不能影响交易**：异步投递、失败隔离、默认静默、零新增第三方依赖、离线可全量验证。

**核心决策（用户 2026-09-17 已裁决，本文档锁定）：**

- **D32-A 渠道范围 = 三类并集。** 三类全部纳入本次迭代，落地顺序为"一/二类（M2）→ 三类（M3）"：
  1. **无状态推送**（一个 webhook URL 或 bot token 即可单向推送）：钉钉自定义机器人、企业微信群机器人、飞书自定义机器人、Telegram Bot、邮件 SMTP、通用 Webhook、Slack、Discord、ntfy、Gotify、Bark。
  2. **账户型推送**（需先换 token 再发）：企业微信应用消息（corpid + corpsecret + agentid）。
  3. **会话锚定推送**（必须先收到过用户的一条消息才能回推）：**微信 ClawBot（iLink Bot API）**、**QQ 机器人开放平台**。
  逆向个人微信协议（wechaty / PC hook / WeChatPadPro 等）**明确排除**：微信已于 2026-03 通过 ClawBot 官方开放个人微信 Bot 通道，没有再走灰色协议的理由。
- **D32-B 零新第三方依赖。** HTTP 走仓库既有的标准库 shim `backtrader/utils/py3.py:57 urlopen`（默认 30s 超时），邮件走标准库 `smtplib` + `email`。**不使用 `requests`**：它虽在 `requirements.txt` 中，但**不在 `setup.py install_requires` 里**，对 `pip install` 用户是新增运行时依赖，与本仓库"核心功能零第三方依赖"的既有约束冲突（详见设计文档 D32-02）。
- **D32-C 接入方式 = `Strategy` 便捷方法。** 主入口为策略内的 `self.send_message(...)`，自动注入策略名/数据名/回测时间上下文；底层能力以 `bt.configure_notifications()` + `bt.send_message()` 形式导出，供非策略场景使用。**不引入** `cerebro.addnotifier()` 自动事件推送、不引入 `NotificationObserver`、不把通知挂成 logging handler。
- **D32-D 默认异步、参数可切同步。** 默认由**每渠道一个后台 worker 线程 + 每渠道有界队列**投递（主循环只做非阻塞入队；同渠道串行保序，跨渠道互不阻塞）；`self.send_message(..., wait=True)` 走同步直发并返回逐渠道真实结果。不引入 asyncio。
- **D32-E 测试口径 = 离线 mock 为门禁 + 真实凭据仅本地手动冒烟。** 全部渠道的 URL/签名/请求体/限流/重试在离线假传输层上断言；真实发送脚本 `scripts/notify_smoke.py` 默认不联网、不入 CI。
- **D32-F 边界 = 只做框架能力 + 文档。** 不接入 `examples/` 任何示例与实盘工程（CTP 穿透式测试、SA 模拟盘等），示例侧接入另立需求。
- **D32-G 不改引擎热路径。** 本轮唯一触及既有文件的改动是 `Strategy` 新增一个便捷方法 + 包导出；**不在 `_cerebro/` 引擎循环中新增任何调用**。"run 返回即已送达"由用户显式调用 `bt.flush_notifications()` 或进程 `atexit` 保证（权衡见设计文档 D32-11）。

### 2.4 渠道事实与证据等级

**会话锚定的含义（本迭代最关键的约束）**：`wechat_clawbot` 与 `qq_bot` **不是"填个 token 就能推"** 的通道。微信侧需要一条入站消息带来的 `context_token`（只知道 `to_user_id` 不足以投递，缺 `context_token` 时接口可能返回 200 但消息静默丢弃）；QQ 侧需要事件里的 `user_openid`/`group_openid`（按 bot 隔离）。因此这两条通道必须配套**绑定流程**（用户先给机器人发一条消息 → 框架记录绑定凭据 → 之后可主动推送），且必须允许"绑定未完成"这一正常状态，用**明确失败**而不是静默丢弃来暴露它。

**M0 复核结论（2026-09-17，`evidence/channel-facts.json`）**：钉钉/企微群/飞书/Telegram/邮件/企微应用/Slack/Discord/ntfy/Gotify/Bark 的端点与限流按官方来源冻结；三处事实更正已回写本表（飞书纯文本、ntfy 与 bark 用 JSON publish）。仍未确认的两类事实：① 未给出内容长度上限的渠道（钉钉/飞书/ntfy/gotify/bark/webhook）**不做截断**，避免按猜测的字节数切错；② 微信 ClawBot 的 iLink 协议细节（端点/请求头/必填字段/token 有效期/单实例互斥）为等级 B/C 证据，实现按隔离常量落地，真实送达待灰度账号实测。

**原始证据缺口（留存备查）**：

1. 微信 ClawBot / iLink 的端点、请求头（`AuthorizationType: ilink_bot_token`、`X-WECHAT-UIN`）、`context_token` 与 `client_id`/`message_type`/`message_state`/`base_info.channel_version` 的必要性，均来自第三方对官方 npm 包 `@tencent-weixin/openclaw-weixin` 的反推与社区实测（等级 B/C）；官方文档站未公开该协议。灰度状态、iOS 8.0.70+ 限制、单 bot 绑定单微信用户等描述同样来自第三方。
2. 钉钉加签（`timestamp\nsecret` + HmacSHA256 + base64 + urlencode）与飞书签名（`timestamp\nsecret` 作密钥、空串作数据 + HmacSHA256 + base64）需用官方示例向量在 M1 锁定，防止实现轮写反。
3. Telegram 的 30 条/秒与 20 条/分/群为社区 wiki 数值，Telegram 官方未承诺；设计取保守值并只对 `429 retry_after` 做强契约。

## 4. 功能需求

| ID | 需求及可判定边界 |
| --- | --- |
| FR32-01 | 配置入口 `bt.configure_notifications(**options)`：opt-in，接受渠道列表（每项含 `channel` id 与凭据）、`default_wait`（默认 `False`）、队列容量、`rate_limit_scale`（本地限流余量系数，默认 0.75）、`dedup_cooldown`（默认 0）、`workers`（`"silent"`/`"send"`，默认 `"silent"`）、`logger` 开关。未调用该函数时：**零渠道、零网络、零线程创建**；`send_message` 返回"未配置"结果并经 stderr 提示一次（复用 `_warn_once` 语义），绝不抛异常。重复调用为幂等替换（替换渠道集与队列，不产生重复投递）。未知渠道 id、缺少必需凭据、非法参数（容量 ≤0、cooldown <0）→ `ValueError`，且**失败时保留原配置不被破坏**（沿用 `log_message.configure_logging` 的"先构建后替换"事务语义）。 |
| FR32-02 | `Strategy.send_message(text, *, title=None, level="info", channels=None, wait=None, timeout=None, dedup_key=None)`：策略内主入口，自动注入上下文（策略类名、`data._name`、回测时间 `self.datetime.datetime()`，而非 wall clock；时间不提供覆盖参数）：三者渲染为**标题下的独立上下文行**，且策略名已出现在标题中时不重复输出（1.3 明确；1.2 之前 `data._name` 实际未进入消息）。`channels=None` 走全局配置；给定则为本次调用的渠道子集（未知 id → `ValueError`；合法但**未配置**的 id → 该渠道返回 `error_category="not_configured"`，其余渠道照常，不视为编程错误）。`wait=None` 取配置的 `default_wait`；`wait=True` 同步直发并返回逐渠道结果（多渠道串行，总延迟 ≈ Σ 各渠道（重试×超时+退避），**仅建议在 `stop()` 等低频路径使用**）；`wait=False` 非阻塞入队立即返回。`timeout` 仅在 `wait=True` 时生效，覆盖该次调用的单请求超时，默认取配置 `request_timeout`。**不得抛出任何发送相关异常**，返回值统一为 `SendResult`（`accepted`、`mode`、`outcomes`、`dropped`；async 模式下 `outcomes` 给出逐渠道入队结果）。`send_message` 名称与框架保留的 `notify_*` 前缀无冲突，不新增 `notify_*` 方法。 |
| FR32-03 | 无状态 HTTP 渠道（`dingtalk`/`wecom_bot`/`feishu_bot`/`telegram`/`webhook`/`slack`/`discord`/`ntfy`/`gotify`/`bark`）：请求方法、URL、查询参数、请求头、请求体、成功判定全部可被离线断言；签名类渠道（钉钉、飞书）在配置时校验 secret 存在，签名参数每次发送重新计算（时间戳不得缓存）。`webhook` 渠道支持自定义 URL/method/headers/body 模板与成功判定表达式（模板占位符 `{text}`/`{title}`/`{level}`）。企业微信机器人 URL 中的 key 与钉钉 `access_token` **不得出现在任何日志或 `repr` 中**。 |
| FR32-04 | 账户型渠道：`email`（标准库 `smtplib`，支持 465 SSL 与 587 STARTTLS，收件人多值，主题含等级与标题，超时显式设置，认证失败给出可判定错误）；`wecom_app`（`gettoken` 换取 access_token 并**缓存至 `expires_in` 前 5 分钟**，到期或 `errcode 40014/42001` 时刷新一次并重试）。token 缓存不得跨进程共享，不得写入磁盘。 |
| FR32-05 | 会话锚定渠道：`wechat_clawbot` 与 `qq_bot`。提供**绑定流程**：读取入站消息事件（微信 `getupdates` 长轮询 / QQ `WebSocket` 或 `Webhook` 回调）→ 提取并持久化锚定凭据（微信 `bot_token` + `context_token`；QQ appid 对应的 `user_openid`/`group_openid`）→ 之后允许主动推送。**未绑定时 `send_message` 必须返回可判定的失败（`outcome.error` 明确标识"未绑定/锚点缺失"）且不重试**，不得静默丢弃、不得伪装成功。微信 `context_token` 需按 `(bot, user)` 维度缓存并在收到新入站消息时刷新；QQ 需处理 access_token 过期刷新。两条通道的"主动推送受限"事实（微信需周期性入站刷新、QQ 用户可关闭主动消息）必须在返回结果中可区分（限流/权限/未绑定三类）。 |
| FR32-06 | 同步/异步模型：默认异步（**每渠道实例一个 daemon worker 线程 + 每渠道实例一个有界队列**，单渠道 `maxsize` 默认 1000；同渠道内串行保序，**跨渠道互不阻塞**——单渠道限流等待或重试退避不得拖住其他渠道）。入队为 `put_nowait` 语义，**绝不阻塞主循环**；某渠道队列满时按 `overflow` 策略处理（`drop_newest` 默认 / `drop_oldest`），仅影响该渠道，丢弃计数入统计并经 `throttled_warning` 提示。`bt.flush_notifications(timeout=5.0)` 等待**全部渠道队列**排空并返回是否排空；`atexit` 注册一次自动 flush（atexit 期间任何异常静默容错，不得在解释器关闭期抛错）；`wait=True` 时不经过队列直接发送。`bt.reset_notifications()` 关闭全部 worker、**丢弃**剩余队列（丢弃数入统计）、清空绑定缓存与统计（测试与长驻进程用）；flush 超时后调用 reset 安全、无死等。 |
| FR32-07 | 限流、重试与去重：每渠道实例维护本地滑动窗口限流器（分/秒双窗口，按渠道官方阈值与口径声明），阈值按官方阈值的 `rate_limit_scale`（默认 0.75）折算，命中时该渠道 worker 侧**等待窗口恢复后继续投递**（不丢消息、不阻塞主循环、不阻塞其他渠道），等待超时（默认 30s）则记录失败。重试仅针对可恢复错误：`429`（Telegram 按 `retry_after` 精确等待）、`5xx`（归 `error_category="server"`）、连接/超时错误；默认最多重试 2 次，指数退避 + 抖动。`4xx`（含鉴权/参数错误）**不重试**，直接记录失败并计数（错误类型可区分）。`dedup_key` 给定时，同一 `(渠道实例, key)` 在 `dedup_cooldown` 秒内只实际投递一次，被抑制的调用返回可判定结果（`error_category="deduped"`）。 |
| FR32-08 | 消息适配：按渠道声明长度上限做**超长截断并追加省略标记**（各渠道上限的**数值与"按字符还是按 UTF-8 字节"口径一律以 M0 官方文档复核冻结为准**，本文档不预设；字节口径渠道须按 UTF-8 安全切分、不切碎多字节字符），截断事件计数；按渠道声明富文本能力（`markdown`/`plain`），不支持 markdown 时降级为纯文本（去除标记而非原样发送）；`level` 大小写归一后映射为统一前缀（`[INFO]/[WARNING]/[ERROR]/[CRITICAL]`），`critical` 在支持的渠道附加 `@所有人` 类提醒（钉钉/企微 `mentioned_list`/`<@all>`，默认关闭，需显式开启）。空消息与仅空白消息 → `ValueError`（编程错误，不静默丢弃）。 |
| FR32-09 | 失败隔离与可观测：任何渠道异常、网络异常、队列异常都不得传播到策略或回测；`SendResult.outcomes` 逐渠道给出 `channel`、`ok`、`error_category`、`attempts`、`elapsed_ms`。`error_category` 的**唯一权威集合**见设计 D32-05（`network`/`timeout`/`tls`/`server`/`auth`/`rate_limit`/`permission`/`not_bound`/`not_configured`/`bad_request`/`deduped`/`dropped`/`worker_silent`/`unknown`；5xx 归 `server`），需求与验收只引用不另立清单。所有日志经统一入口（`get_logger`），URL 与凭据脱敏（只保留 `scheme://host/path`，查询串中的 token/key 替换为 `***`）。提供只读统计 `bt.notification_stats()`（各渠道 发送成功/失败/重试/丢弃/去重/限流等待 计数），供运维与验收断言。 |
| FR32-10 | 多进程与 fork 安全：`multiprocessing.parent_process() is not None` 时默认**不外发**（`workers="silent"`），命中调用返回 `error_category="worker_silent"`，避免 `cerebro.run(maxcpus>1)` 参数优化把通知变成轰炸；显式 `workers="send"` 可开启（用户自担风险，文档说明）。`os.register_at_fork(after_in_child=...)` 重建锁与队列状态（线程不跨 fork 复用），子进程不得继承父进程的 worker 线程状态与统计。 |
| FR32-11 | 测试：新增 `tests/unit/notifications/` 覆盖全部渠道的请求构造、签名向量、限流、重试、去重、队列、配置校验、默认静默、多进程静默、会话锚定失败语义；新增 `tests/integration/test_notifications_lifecycle.py` 用真实小型回测 + 假传输层验证策略内 `send_message` 全链路。**离线**为门禁；真实凭据仅由 `scripts/notify_smoke.py` 在本地手动执行（默认不联网、不入 CI、不读仓库内凭据）。 |
| FR32-12 | 文档：新增 `docs/NOTIFICATIONS_GUIDELINES.md`（渠道配置清单、凭据管理、限流与去重语义、会话锚定绑定流程、失败排查、与迭代29 日志体系的分工）；`AGENTS.md` 增加通知能力段落（与 `## Logging (iteration 29)` 并列）；渠道阈值以"M1 冻结值"标注来源与复核日期。 |

## 5. 非功能需求

## 6. 渠道清单与优先级

| 优先级 | 渠道 | 理由 |
| --- | --- | --- |
| M2 必须 | `dingtalk`、`wecom_bot`、`feishu_bot`、`telegram`、`email` | 用户点名；覆盖国内群告警、个人手机、邮件留档；接入成本最低 |
| M2 必须 | `wecom_app` | 用户点名；额度宽松且消息直达个人微信 |
| M2 必须 | `webhook`、`slack`、`discord`、`ntfy`、`gotify`、`bark` | 用户点名；与首批声明式渠道同属一个实现模式，增量成本近零，不单独延后 |
| M3 | `wechat_clawbot`、`qq_bot` | 用户点名；需额外绑定流程与锚点凭据管理，工程量最大，放在无状态渠道打通之后 |
| M4 可选 | 附件/图片/语音/文件、模板卡片 | 依赖 Media 上传能力（微信需 CDN + AES、企微/飞书需素材上传），非首批必需 |
| 评估后不做 | 微信公众号/服务号模板消息 | 需要**认证服务号**（企业主体，个人不可申请），与"个人可用"目标不符 |
| 评估后不做 | 企业微信智能机器人（aibot，WebSocket 长连接 + Bot ID/Secret） | 面向对话交互（流式回复、模板卡片、事件回调），需常驻长连接；作为单向告警通道的复杂度远高于企微群机器人/应用消息，留待后续独立需求 |
| 评估后不做 | 逆向个人微信协议（wechaty / PC hook / WePadPro） | 违反服务协议、有封号风险、随客户端更新失效；ClawBot 官方化后已无必要 |
| 明确不做 | Apprise 等第三方通知库 | 与 D32-B 冲突；且国内渠道（钉钉加签/企微/ClawBot）语义需自行拼接，排错困难 |
| 明确不做 | 通知挂成 logging handler 自动外发 ERROR、`cerebro.addnotifier` 自动事件、`NotificationObserver` | 用户裁决为范围外；这三项都会改变默认行为或侵入引擎，噪音与回归风险另立需求评估 |

## 7. 未决条件（设计文档裁决，不阻塞 M0/M1）

1. `SendResult` / `ChannelOutcome` 的字段是否为公开契约（影响兼容性承诺深度）——设计文档 D32-05 给出结论，验收按结论断言。
2. 会话锚定凭据的默认存储位置——**已由设计 D32-09 裁定**：默认 `~/.backtrader/notifications/<channel>.json`、权限 `0600`、须加入 `.gitignore`；评审确认即可，不再悬置。
3. 微信 ClawBot 与 QQ 机器人若在实现轮被证实不具备稳定主动推送能力（证据等级 B/C），降级为"仅本地记录、不承诺送达"还是移出首批——由 **M3** 实测结论决定（假传输框架测试在 M3 先行），验收文档给出对应分支判据。
4. `level` 与"@所有人"的默认关系（默认关闭已定；是否提供 `critical` 自动开启由 M3 评审决定）。
