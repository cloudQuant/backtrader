## 2. D32-02：传输层与依赖策略

支撑 NFR32-04、NFR32-05、D32-B。

| 方案 | 收益与代价 | 决策 |
| --- | --- | --- |
| 标准库 `py3.urlopen`（`urllib.request`）+ `smtplib`/`email` | 对 `pip install` 用户真零新依赖；与 `setup.py install_requires` 现状一致；`py3.urlopen` 已带 30s 默认超时且已被测试锁定；代价：需自行处理 header/body 编码与 SSL 上下文 | **采用** |
| `requests` | API 更省事；但**不在 `install_requires`**，等于给 `pip install backtrader` 用户新增运行时依赖，且与"核心功能零第三方依赖"冲突 | 不采用 |
| `requests` 可选加速（探测到才用） | 双路径意味着双份测试与行为差异；本场景发送频次低，性能无收益 | 不采用 |
| `aiohttp`/`httpx`（异步） | 与"不引入 asyncio"冲突（D32-06），且都是新依赖 | 不采用 |

**关键抽象：可注入传输层。** 所有出站请求经过一个极小接口，测试用进程内假传输实现同一个接口，从而在**不联网、不 monkeypatch 第三方库**的前提下断言完整请求：

```python
# backtrader/notifications/transport.py
class HttpRequest:      # method, url, headers: dict, body: bytes|None, timeout: float
class HttpResponse:     # status: int, headers: dict, body: bytes, elapsed_ms: float
class HttpTransport(Protocol):
    def send(self, request: HttpRequest) -> HttpResponse: ...
class UrllibTransport:  # 生产实现：包装 py3.urlopen；超时显式传入；不跟随跨域重定向
```

设计合同：

1. `UrllibTransport` 是唯一生产实现，内部只用 `backtrader.utils.py3` 的 `urlopen`/`Request`/SSL 上下文相关符号（若缺失则在 `py3.py` 补充导出，不直接 `import urllib` 散落各处）。
2. 响应体一律按 UTF-8 解码，非 UTF-8 用 `errors="replace"`；`HttpResponse.body` 与 `status` 供渠道层判定成功。
3. 网络异常（`URLError`/`socket.timeout`/`ssl.SSLError`/`OSError`）在传输层归一为 `TransportError(kind=network|timeout|tls)`，上抛给渠道层分类，不得泄漏原始异常类型给调用方。
4. 传输层**不重试**（重试策略集中在核心，见 D32-07），不打印、不记录（日志由调用方负责），保证"一层只做一件事"。
5. **SMTP 同样有可注入缝**：`SmtpSender` 协议（`send(envelope) -> None`，异常归一为 `SmtpError(auth|timeout|network)`），生产实现包装 `smtplib.SMTP`/`SMTP_SSL`（465）与 STARTTLS（587），超时显式传入；测试注入假实现（不启动真实 SMTP 服务、不 monkeypatch `smtplib`）。HTTP 与 SMTP 两条缝是 NFR32-05"不 monkeypatch 第三方库内部实现"的全部支撑。

                   reset_notifications / notification_stats / SendResult / ChannelOutcome /
                   CHANNELS（渠道 id 常量与能力表）
  core.py          Notifier（渠道解析、队列、worker 线程、同步直发、统计、去重、重试编排）

**为什么不是"每渠道一个模块"。** 钉钉、企微群、飞书、Slack、Discord、ntfy、Gotify、Bark、通用 webhook 的差异**只在**URL 形态、请求体 schema、签名、成功判定、限流阈值、长度与富文本能力五处，属同一模式（`POST` 一次 JSON 看返回码）。为它们各写一个模块会产生大量样板与重复测试。而邮件（SMTP）、Telegram（`429 retry_after` 强语义）、企微应用（token 生命周期）、ClawBot/QQ（会话锚点）形态确有本质差异，单列。这是"按机制分组、按差异分层"而非"按厂商铺文件"。

## 4. D32-04：配置 API 与默认静默合同

支撑 FR32-01、NFR32-02。

```python
bt.configure_notifications(
    channels,                       # 见下
    *,
    default_wait=False,             # False=异步入队；True=同步直发
    queue_size=1000,
    rate_limit_scale=0.75,          # 本地限流阈值 = 渠道官方阈值 × 该系数
    dedup_cooldown=0.0,             # >0 时，同 dedup_key 在窗口内只投递一次
    workers="silent",               # "silent"（默认，子进程不外发）| "send"
    max_retries=2,
    retry_backoff=0.5,              # 秒，指数退避基数
    request_timeout=10.0,
    at_all=False,                   # critical 是否 @所有人（默认关闭）
    log_events=True,                # 经 get_logger 输出投递事件；受迭代29约束——未 configure_logging 时日志仍零输出
)
```

`channels` 的**唯一必测写法**是显式字典：

```python
[{"channel": "dingtalk", "access_token": "...", "secret": "..."},
 {"channel": "telegram", "bot_token": "...", "chat_id": "..."},
 {"channel": "email", "host": "smtp.qq.com", "port": 465, "ssl": True,
  "user": "...", "password": "...", "to": ["a@b.com"], "sender": "..."}]
```

**URL 风格简写（Apprise 式，如 `"dingtalk://?access_token=...&secret=..."`）降级为 M4 待定可选项**：它引入第二个解析器与第二组测试，用户需求未点名，1.0 曾把它列为必测属范围膨胀；裁决为"不做"之前，实现与验收只覆盖字典写法（见迭代计划 R4 一并评审）。

**默认静默合同（硬约束，逐条测试）：**

1. 不调用 `configure_notifications` → 无渠道、无 worker 线程、无队列、无文件与目录创建、零网络。
2. 未配置时调用 `send_message` → 返回 `SendResult(accepted=False, outcomes=(), reason="not_configured")`，经 `_warn_once` 语义在 stderr 提示一次，**不抛异常**。
3. 未配置时 `flush_notifications()` → 立即返回 `True`（无等待）；`reset_notifications()` → 幂等空操作。
4. 配置失败（未知渠道/缺凭据/非法参数）→ `ValueError`，且**旧配置与旧 worker 保持不变**（先构建、后替换，与 `configure_logging` 一致）。
5. 重复配置 → 幂等替换：新建渠道集合后优雅停止旧 worker（等待至多 `request_timeout`），不产生重复投递。

**环境变量。** 默认**不**读取环境变量（避免隐式网络行为）。提供 `bt.configure_notifications_from_env(prefix="BT_NOTIFY_")` 作为显式可选入口，约定 `BT_NOTIFY_<ID>_<FIELD>`（如 `BT_NOTIFY_TELEGRAM_BOT_TOKEN`、`BT_NOTIFY_DINGTALK_ACCESS_TOKEN`），并允许 `BT_NOTIFY_CHANNELS="dingtalk,telegram"` 指定启用集。是否纳入首批由 M2 评审（见迭代计划风险 R4）。

**边界情况裁定（1.1 评审补充，验收有对应子项）：**

1. `channels=[]`（空列表）→ 合法，等价"配置了空渠道集"：`send_message` 返回 `reason="no_channels"`，不告警不报错（区别于"从未配置"的 `not_configured`）。
2. 同一渠道 id 多条实例 → **合法**（典型：`qq_bot` 同时配单聊与群聊、多个钉钉群机器人）；实例按出现顺序编号（`dingtalk#1`/`dingtalk#2`），**统计、限流、队列、去重键均按实例隔离**。
3. 调用方请求**合法但未配置**的渠道 id → 不是编程错误：该渠道 `ChannelOutcome(error_category="not_configured")`，其余渠道正常投递。
4. `overflow="drop_oldest"` 挤掉的消息若携带未消费的去重窗口 → 窗口状态不回滚（该 key 视为"未投递"，窗口内再次调用仍被抑制直至过期；丢弃计数已可见）。
5. `flush_notifications` 超时返回 `False` 后调用 `reset_notifications()` → reset **丢弃**剩余消息（丢弃数先入统计），二者组合无死等。
6. `atexit` 自动 flush 期间的任何发送/关闭异常一律静默吞掉（解释器关闭期无可靠输出通道）。
7. fork 后子进程的统计计数器随 `_after_fork` **一并清零**（父进程计数不含子进程副本）。
8. `wecom_app` 的 token **刷新请求自身**网络失败 → 归 `network`、可重试，重试预算与发送共享 `max_retries`；刷新得到鉴权类错误 → 归 `auth` 不重试。

## 5. D32-05：公开对象契约与 `Strategy` 集成

支撑 FR32-02、FR32-09。

```python
@dataclass(frozen=True)
class ChannelOutcome:
    channel: str                 # 实例名（含多实例编号，如 "dingtalk#2"）
    ok: bool
    error_category: str | None   # 唯一权威集合 ERROR_CATEGORIES：
                                 # network|timeout|tls|server|auth|rate_limit|permission|
                                 # not_bound|not_configured|bad_request|deduped|dropped|
                                 # worker_silent|unknown   （5xx → server）
    error: str | None            # 已脱敏、可读；不含 URL query 与凭据
    attempts: int
    elapsed_ms: float

@dataclass(frozen=True)
class SendResult:
    accepted: bool               # 至少一个目标渠道接受（入队成功或同步已尝试）
    mode: str                    # "async" | "sync"
    outcomes: tuple[ChannelOutcome, ...]
                                 # sync：逐渠道发送结果；
                                 # async：逐渠道**入队**结果（ok=入队成功；error_category 可为
                                 #   dropped/not_configured/worker_silent/deduped）
    dropped: bool                # 至少一个目标渠道因队列满被丢弃
    reason: str | None           # not_configured | no_channels | queue_full | ok | ...
```

契约裁定（回答需求文档第 7 节未决项 1）：**`SendResult`/`ChannelOutcome` 为公开契约**，字段只增不减；`error_category` 的取值集合为公开枚举常量（`bt.notifications.ERROR_CATEGORIES`），新增类别属于向后兼容变更，删除/改名属于破坏性变更，需另立需求。理由：这是用户唯一能看到"消息到底发出去没有"的接口，若不定为契约则无法写稳定的验收断言。**本节集合是全文档唯一权威定义**：需求 FR32-09 与验收各 AC 只引用此处，不得另立第二份清单（1.0 版曾出现三处清单不一致，1.1 收敛于此）。

`Strategy` 新增方法（唯一触及既有文件的改动）：

```python
def send_message(self, text, *, title=None, level="info", channels=None,
                 wait=None, timeout=None, dedup_key=None):
    """发送一条通知（默认异步）。上下文自动注入策略名/数据名/回测时间。"""
```

设计要点：

1. **上下文注入**：`title` 缺省为 `f"{self.__class__.__name__}"`；时间固定取 `self.datetime.datetime()`（回测时间，**不提供覆盖参数**——1.0 的 `at` 参数与 `at_all` 语义撞车且无人需要，1.1 删除）；`strategy`/`data_name` 由 `context_line()` 渲染成**标题之下的独立上下文行**（例：`2026-09-18 09:00:00 strategy=Pair data=RB889`），且**当 `strategy` 已出现在 `title` 中时不重复输出**（`Strategy.send_message` 的标题默认就是类名，因此那里只补 `data=`）——1.2 之前这两个字段被赋值但从不进入消息，属复核轮发现的死字段。不注入 wall clock，避免回测中时间语义混乱。`timeout` 仅在 `wait=True` 时生效（覆盖该次单请求超时，默认取 `request_timeout`）；**`wait=True` 多渠道串行，总延迟 ≈ Σ 各渠道（重试×超时+退避），只建议用于 `stop()` 等低频路径**。
2. **无异常承诺**：方法体包在单一 `try/except Exception` 中，任何意外都归为 `ChannelOutcome(error_category="unknown", ok=False)`，并 `throttled_error` 记录一次；**绝不向 `next()` 抛出**。
3. **`self.data` 缺失时**（多数据/未绑定）不报错，静默省略数据名。
4. **返回值**：`wait=False` → `outcomes` 为逐渠道**入队**结果（`ok=True` 或 `error_category="dropped"/"not_configured"/"worker_silent"`），`accepted`=至少一渠道入队成功，`dropped`=至少一渠道被队列满丢弃（多渠道部分接受状态由此可表达）；`wait=True` → `outcomes` 为逐渠道**发送**结果（全渠道失败时 `accepted=False`）。
5. **不改 `Strategy.__init__`、不改 `_notify`、不改 `stop()`**：通知器通过进程级单例（`config.get_notifier()`）获取，策略实例不持有引用——这样 optimize 子进程、派生策略、pickle 场景都不会把线程/队列带进策略状态。

## 6. D32-06：异步模型

支撑 FR32-06、NFR32-01。

```text
主循环 (next/notify_*)
   └─ Strategy.send_message(wait=False)
        └─ Notifier.enqueue(message)   # 对每个目标渠道实例 put_nowait；满则按 overflow 丢弃该渠道
             ├─ queue[dingtalk#1] ── worker(dingtalk#1) ── 渠道内串行：限流等待→发送→重试→统计
             ├─ queue[telegram#1] ─ worker(telegram#1) ─ ……
             └─ queue[email#1]    ─ worker(email#1)    ─ ……
```

| 设计项 | 取值与理由 |
| --- | --- |
| 并发模型 | **每渠道实例一个 daemon worker 线程 + 每渠道实例一个有界队列**（实例数 ≤14，线程开销可忽略）。同渠道内严格串行（保序、限流、重试都在该线程内完成，不自我并发触发渠道限流）；**跨渠道互不阻塞**。1.0 的"单 worker"设计存在队头阻塞：一个渠道的限流等待（最长 `rate_limit_wait_timeout`）或重试退避会挡住其后**所有其他渠道**的消息，违背 FR32-09 的隔离承诺，1.1 废弃。 |
| 主循环阻塞 | 仅各目标渠道 `Queue.put_nowait`；无锁竞争热点（`Queue` 内部锁，纳秒级）。`send_message` 不组装请求体（延迟到各 worker），确保热路径零格式化开销。 |
| 队列满策略 | 按渠道实例独立判定：`drop_newest` 默认（保留先到的、丢弃最新的，符合"最初的异常最有价值"）；`drop_oldest` 可选。**仅影响该渠道**，其他渠道照常入队；计数与 `throttled_warning` 按渠道实例。 |
| 关闭语义 | `flush_notifications(timeout=5.0)`：对**全部渠道队列**轮询排空，返回是否全部排空（未排空保留计数，可再次 flush 或 reset）。`atexit` 注册一次，但**必须内联发送而非等 worker**：CPython 在跑 atexit 回调前就冻结了 daemon 线程，等 worker 只会耗尽超时后照样丢消息（复核轮实证：改前普通脚本 3/4、子进程 0/4）。因此 `drain_and_deliver()` 先置停止位并投递哨兵、`join(≤1s)` 让 worker 退休，再补发"在途消息"（worker 已取出但未完成的条，由 `_inflight` 交还而非丢弃），最后在剩余预算内排空队列 inline 发送；atexit 期间任何异常静默吞掉。`reset_notifications()`：丢弃剩余队列（丢弃数先入统计，含交还的在途消息）、停全部线程、清绑定缓存与统计；flush 超时后调用安全，无死等。语义为**不丢优先、允许极小窗口重复**（worker 已发完但未及清 `_inflight`），与"尽力而为"定位一致。 |
| 为什么不用 asyncio | 回测引擎是同步单线程，混入事件循环需要 `run_until_complete` 或自建 loop 线程，反而比一个 worker 线程更脆弱（用户已裁决 D32-D）。`wait=True` 同步直发已覆盖"我要立刻知道结果"的场景。 |
| 为什么不在引擎里自动 flush | 用户裁决 D32-F/G：不侵入引擎。代价是"`cerebro.run()` 返回时消息可能仍在队列中"（通常 <1s 即排空）。文档明确推荐长驻进程在 run 之后显式 `bt.flush_notifications()`；`atexit` 兜底脚本退出。此权衡登记为已知取舍，验收文档 AC32-14 断言"显式 flush 后必达"。 |
| 线程安全 | `enqueue`/`flush`/`reset`/`stats` 由内部锁保护，多策略、多线程并发调用语义与单线程一致（NFR32-01）。fork 后锁重建、队列内容与统计一并重置（`_after_fork`，同迭代29 `log_message` 先例）。 |

**多进程与 fork（FR32-10）：**

- `workers="silent"`（默认）：`multiprocessing.parent_process() is not None` 时 `send_message` 返回 `error_category="worker_silent"`，**不投递**（optimize 会跑成百上千参数组合，通知会变轰炸；且子进程各自持凭据与队列无意义）。判据与 `log_message._mp_log_suffix` 同源。
- `os.register_at_fork(after_in_child=_after_fork)`：子进程内重建锁、丢弃继承的队列内容与 worker 引用（线程不跨 fork 存活，残留引用会导致"看似有 worker 实则永不投递"）。
- 主进程配置快照不自动传播到 spawn 子进程（除非用户显式 `workers="send"` 且在子进程内再次 `configure_notifications`）；此行为在文档显式声明。

**限流（本地前置，避免撞渠道硬限流）：**

```python

# 结构：(per_minute, per_second)，None = 该维度不限；两窗口同时生效，任一命中即等待
_CHANNEL_RATE_LIMITS = {
    "dingtalk":   (20, None),   # 20/分 → 本地 15/分
    "wecom_bot":  (20, None),   # 20/分 → 本地 15/分

                                # （1.0 注误写"15/分"：100×0.75=75，已修正）
    "telegram":   (20, 1),      # 每会话 20/分 且 1/秒（保守，不依赖未承诺的全局 30/s）
    "discord":    (None, 2.5),  # 5 次/2 秒 → 2.5/秒
    "slack":      (None, 1.0),
    "wecom_app":  (30, None),   # 每成员 30/分 → 本地 22/分
    "email":      (None, None), # 不限流（由服务商约束）
    # wechat_clawbot / qq_bot：见 D32-09，在协议侧窗口之上再叠加本表

```

命中限流时 worker **等待**到窗口可用（`time.monotonic` 计时，monkeypatch 可注入时钟），累计等待时长入统计；等待超过 `rate_limit_wait_timeout`（默认 30s）记 `rate_limit` 失败并继续处理后续消息（防止队头阻塞）。不做跨进程共享限流器（多进程本就是 silent）。

**重试（只对可恢复错误）：**

| 情形 | 处理 |
| --- | --- |
| `429` / 微信企业侧限流 `errcode 45009` / 飞书 `11232` / QQ `40034100` | 可恢复；Telegram 用响应 `parameters.retry_after` 精确等待（+0.2s 抖动）；其他用退避 |
| `5xx`（归 `error_category="server"`）、`TransportError(network/timeout/tls)` | 可恢复；指数退避 `retry_backoff * 2**n` + 抖动，`n ≤ max_retries` |
| `401/403/400`、`errcode` 鉴权类（如企微 `40014/42001`、钉钉 `300001`、飞书 `19001`） | **不重试**；`error_category="auth"`；企微应用渠道允许一次 token 刷新后重试（唯一例外，见 FR32-04） |
| `not_bound`（ClawBot/QQ 锚点缺失） | **不重试**（重试不会让用户先发消息） |
| `deduped` | 不重试；不算失败 |

**去重（`dedup_key` + `dedup_cooldown`）：** 键为 `(channel, dedup_key)`，窗口内只实际投递一次；被抑制的调用返回 `error_category="deduped"`（`ok=False` 但分类不视为故障，统计单列）。设计上刻意与迭代29 的 `throttled_*` 区分：`throttled_*` 管**日志**量，本机制管**外发**量与渠道额度（Server酱类服务有每日额度，超发会烧掉当天配额）。

## 8. D32-08：消息适配

支撑 FR32-08。

```python
# 内部统一消息对象（ChannelSpec.build 的输入；Strategy.send_message 的上下文在此组装）
@dataclass(frozen=True)
class Notification:
    text: str
    title: str | None

@dataclass(frozen=True)
class ChannelSpec:
    id: str
    endpoint: str
    requires: tuple[str, ...]        # 必需凭据字段名
    optional: tuple[str, ...]        # 可选字段（如 secret、mentioned_list）
    build: Callable[[Notification, dict, Signer], HttpRequest]

```

| 渠道 | max_length（**建议值；数值与"字符/字节"口径一律以 M0 冻结为准**） | markdown | @所有人 | 成功判定要点 |
| --- | --- | --- | --- | --- |
| dingtalk | ~2000（口径待 M0） | ✅ | ✅（`isAtAll`） | `errcode == 0`；`310000`（关键词/加签不匹配）→ `auth` |

| feishu_bot | 未确认（不截断） | ❌（本期纯文本，M0 更正） | ❌（无 @all 语义） | `code/StatusCode == 0`；`11232` → `rate_limit` |
| telegram | 4096 字符 | ✅（MarkdownV2 需转义） | ❌ | `ok == True`；`429` 读 `parameters.retry_after` |
| email | 无硬限（按服务商） | HTML | ❌ | SMTP 无异常即成功 |
| wecom_app | 2048 字节 | ✅ | ✅ | `errcode == 0` |
| discord | 2000 字符 | ✅ | ❌ | HTTP 204/2xx |
| slack | 无硬限（建议 4000） | mrkdwn | ❌ | HTTP 200 且 body == `ok` |

| webhook | 用户声明（`max_length`） | 模板决定 | 模板决定 | 用户声明（默认 2xx）；`body_json` 由 JSON 序列化保证转义 |
| wechat_clawbot | ~2000（公开实现） | ❌ | ❌ | `ret == 0`？公开实现无错误码，需以"HTTP 200 且后续可观测"弱判定，文档标注不确定性 |
| qq_bot | 按接口（`40054007` 长度超限） | ✅（需模板权限） | ❌ | `code == 0` |

**处理规则：**

1. **超长**：按渠道声明值截断（按字符数；字节限制的渠道按 UTF-8 字节安全切分，不切碎多字节字符），追加 `…（已截断 N 字符）`，计入 `truncated` 统计。截断是**有损但显式**的行为，禁止静默丢尾。
2. **富文本降级**：`markdown=False` 的渠道把 `**x**`/`##`/`` ` `` 等标记去除为纯文本（而非原样发出 `## 标题`）；Telegram 开启 markdown 时对 `_*[]()~\`` 做 MarkdownV2 转义（转义缺失会导致 400，是最高频的失败原因之一）。
3. **等级前缀**：统一 `[LEVEL] title`，等级取 `info/warning/error/critical`（大小写不敏感，非法值 `ValueError`）。
4. **空消息**：`text` 非字符串或去空白后为空 → `ValueError`（编程错误，立即暴露，不入队）。
5. **一次调用多渠道**：逐渠道独立构造请求（长度/markdown 适配各自进行），单渠道失败不影响其他渠道（FR32-09 的失败隔离）。

## 10. D32-10：失败隔离与脱敏

支撑 FR32-09、NFR32-04。

1. **不外抛**：`send_message`（无论同步/异步）、`flush_notifications`、渠道适配器内部均不得抛出到调用方；唯一例外是**编程错误**（未知渠道 id、缺必需凭据、空消息、非法 level）在**配置/调用参数校验阶段**抛 `ValueError`——早失败优于静默。
2. **错误分类**：所有异常在渠道层归一为 `error_category` 枚举（D32-05），避免调用方解析字符串。
3. **脱敏**：`security.mask_url` 只保留 `scheme://host/path`，query 中 `access_token`/`key`/`token`/`sign`/`secret` 一律 `***`；`mask_text` 处理 `Authorization: Bearer`、`"password": "..."` 等形态（语义对齐 `log_message._SECRET_VALUE`/`_BEARER_VALUE`/`_URL_PASSWORD`）。`SendResult`/`ChannelOutcome` 的 `error` 字段一律经过脱敏；`repr(Notifier)` 不打印渠道凭据。
4. **统计**：`notification_stats()` 返回只读快照 `{channel: {sent, failed, retried, dropped, deduped, rate_waited_ms, truncated}}`，用于验收断言与运维观测；线程安全（加锁拷贝）。
5. **日志**：投递事件用 `get_logger("notifications")`，成功 `debug`、可恢复失败 `warning`、鉴权/权限失败 `error`；重复失败走 `throttled_*`。`log_events=False` 时全部静默（只留统计）。

### 15.1 停机排空（复核轮新增，属实现级正确性要点）

`atexit` 里调用 `flush_notifications()`（等 worker）**不足以**兜底：CPython 在 atexit 前已冻结 daemon 线程。实证对比：

| 做法 | 普通脚本退出 | spawn 子进程退出 |
| --- | --- | --- |
| 无 atexit（1.2 实现） | 送达 0/4 | 0/4 |
| atexit + `flush`（等 worker） | 仍会丢（worker 已取出） | 仍会丢 |
| atexit + 内联排空 + 在途交还（1.3 实现） | 4/4 | 4/4（子进程需 `workers="send"`，否则按设计根本不入队） |

约束：`drain_and_deliver` 必须先让 worker 退休再内联发送，否则两个发送方争抢同一队列会**同时造成重复与丢失**（复核轮实测出现过 `m0,m0,m2,m3`）。
