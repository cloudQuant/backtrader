## 2. 发现清单

### F1（P1）`atexit` 自动 flush 未实现 —— 四处文档承诺与实现不符，且验收从未覆盖

需求 FR32-06、设计 D32-04 边界裁定第 6 条与 D32-06「关闭语义」、`AGENTS.md` 通知段、用户指南第 150 行，四处都写明"脚本退出由 `atexit` 兜底 flush"。实现中 `backtrader/notifications/` **没有任何 `atexit` 注册**（全包 grep 零命中）。worker 是 daemon 线程，因此异步入队后进程正常退出即丢弃未发送消息。

实证（本地 loopback HTTP 服务，handler 每条耗时 0.25s，5 条异步消息后直接退出）：

```text
进程退出时刻      server 收到 0 条      ← 消息全部丢失
若再存活 2 秒     server 收到 5 条      ← 证明发送逻辑本身正常，丢在退出时机
```

影响面正是**最常见的使用场景**：脚本跑完回测 → `send_message` → 进程退出 → 用户什么也收不到，而文档告诉他"有 atexit 兜底"。用户指南虽另有一行提示"长驻进程请显式 flush"，但没有说**短脚本也必须 flush**。

验收缺口：AC32-14「重试与 flush 必达」用**显式** `flush_notifications()` 测得，全文（含验收文档任何一节）**未出现 `atexit`** → 该承诺从未进入验证清单，属于"承诺—实现—验证"三处同时缺失的漏网项，而非单纯笔误。

建议：二选一并保持一致 —— ①按承诺实现 atexit 钩子（`atexit.register` + 关闭期异常静默，参照 `log_message.py` 已有的 `atexit.register(flush_throttle_summary)` 先例），并补一条"不显式 flush 也能送达"的测试；②若判定不该引入 atexit 网络 I/O，则删除四处承诺，并在指南中把"脚本结束前显式 `bt.flush_notifications()`"提升为**必须**（含示例代码）。任一方案都需回填验收文档新增 AC。

### F2（P1）`data_name` / `strategy` 上下文被注入但从未进入消息 —— 死字段 + 假公开参数

需求 FR32-02 承诺"自动注入上下文（策略类名、`data._name`、回测时间）"。实现里：

- 策略类名可用：`Strategy.send_message` 把 `title` 缺省设为类名，[compose_text](backtrader/notifications/channels.py:234) 会渲染 `title`；
- 回测时间可用：`at_time` 被 `compose_text` 渲染；
- **`data_name` 与 `strategy` 从未被任何渠道读取** —— 仅在 [channels.py:63](backtrader/notifications/channels.py:63) 定义、在 [config.py:500](backtrader/notifications/config.py:500) 赋值，全包无第三处引用。

后果：多数据/跨品种策略（本仓库的主力场景，如跨所套利、CTP 多合约）里，收到的通知**无法区分是哪个 feed 触发的**；同时 `bt.send_message(..., strategy=..., data_name=...)` 这两个公开参数是"传了也没用"的假接口，用户只能自己拼进正文。

建议（小改动，不扩范围）：在 `compose_text` 的上下文行里带上 `data_name`（例如同步渲染 `[INFO] 标题 / 2006-01-03 / data=RB889`），并让 `strategy` 在 `title` 缺省时参与；或反向收敛——删除这两个字段与公开参数并同步修正 FR32-02 与 D32-05 措辞。**不应保持现状**（文档承诺一项未兑现的能力）。

### F3（P2）`configure_notifications_from_env` 零测试覆盖，却被记为"已交付"

[config.py:319](backtrader/notifications/config.py:319) 的公开入口没有任何测试（`tests/` 全文零命中），而迭代计划 1.2 把风险 R4 写成"按评审采纳（`configure_notifications_from_env` 已交付）"。

本轮手工验证：以假 HTTP 传输注入后，`BT_NOTIFY_CHANNELS=email,dingtalk` + 各 `BT_NOTIFY_<ID>_<FIELD>` 能正确建实例，`port` 强转 int、`to` 逗号串强转 list 均生效（`instance_names=('email','dingtalk')`，dingtalk 发送成功）。**功能可用，但完全未验证**，且其中的类型强转分支（`_ENV_INT_FIELDS`、`to`、`ssl/starttls/sandbox/html` 布尔）与"缺必填 → ValueError"都是易回归的边界。

### F7（P3）`scripts/notify_smoke.py` 依赖私有符号

### F8（记录，非本迭代范围）`.env` 代理变量污染测试进程 —— 既有缺陷仍在

`examples/013_1|013_2/ctp_example_support.py` 在**模块导入期**调用 `load_dotenv(REPO_ROOT/.env)`，把开发者本机 `HTTP_PROXY/HTTPS_PROXY/SOCKS_PROXY/PROXY_HOST` 注入 worker 的 `os.environ` 且不还原，导致同进程后续任何 urllib/requests 请求走一个不存在的本地代理（实测 `ConnectionRefusedError [Errno 61]`，原始 socket 却正常）。

本迭代只加固了自己的测试（`isolated_opener` 用 `ProxyHandler({})` 显式无代理），**未修根因**，判定为范围外是正确的；但它是一颗仍在影响他人的地雷：任何后续新增的、走真实 HTTP 的测试都可能偶发失败。建议另立需求：在根 `conftest.py` 加 session 级 autouse fixture 保存并清除 `*_PROXY` 环境变量，或把两处导入期的 `load_dotenv_if_available()` 改为显式调用。
