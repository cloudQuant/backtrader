# 迭代 32：发送信息（通知外发）功能迭代计划

版本：1.2；修订日期：2026-09-17；状态：`IMPLEMENTED`。M0–M5 已执行完毕：需求见[需求文档](./需求文档.md)（1.2），技术方案见[设计文档](./设计文档.md)（1.2），判定标准与执行记录见[验收文档](./验收文档.md)（2.0 第 6/7 节）。原始诉求见[初始需求](./初始需求.md)。1.1 修订（评审轮）：异步模型改为"每渠道实例独立 worker + 队列"（消除跨渠道队头阻塞）；`transports.py` 更名 `adapters.py`；R1 应对的实测节点修正为 M3；新增 R8（ClawBot 单实例互斥）。1.2 修订（实现轮）：M0 事实冻结与回写完成（`evidence/channel-facts.json`）；M1–M4 交付完成；M5 门禁全绿——`make test-fast` 5,144 passed、`make test-strategies` 1,271/1,271、`black/ruff/mypy/bandit` 全过；R1/R2 的真实渠道送达因缺灰度账号与 QQ 沙箱凭据仍为 `BLOCKED`（框架侧已通过），R4 环境变量入口按评审采纳（`configure_notifications_from_env` 已交付），M4 附加项（附件/模板卡片）未做、保持待评审。

## 1. 一句话目标

让策略在回测与实盘中把消息推送到飞书/微信/QQ/Telegram/邮件等终端，**默认异步、失败不影响交易、零新增第三方依赖、离线可全量验证**；本轮先完成方案与验收口径，开发在下一轮进行。

## 2. 范围边界

**做：**

- 新增 `backtrader/notifications/` 包（传输层 + 配置 + 核心队列 + 声明式渠道 + 账户型渠道 + 会话锚定渠道 + 脱敏）。
- `Strategy` 新增 `send_message(...)`；`backtrader/__init__.py` 新增导出。
- 新增单元测试（`tests/unit/notifications/`）、集成测试（`tests/integration/test_notifications_lifecycle.py`）、本地冒烟脚本（`scripts/notify_smoke.py`）。
- 新增 `docs/NOTIFICATIONS_GUIDELINES.md` 与 `AGENTS.md` 段落。
- 渠道覆盖：`dingtalk` / `wecom_bot` / `feishu_bot` / `telegram` / `email` / `wecom_app` / `webhook` / `slack` / `discord` / `ntfy` / `gotify` / `bark` / `wechat_clawbot` / `qq_bot`（共 14 条）。

**不做（本轮已与用户确认或经评估排除）：**

- 不改引擎（`_cerebro/`、`cerebro.py`、broker/feed）任何一行；不提供 `cerebro.addnotifier`。
- 不提供 `NotificationObserver`；不把通知挂成 logging handler 自动外发 ERROR。
- 不引入 asyncio；不引入任何新第三方依赖（含 Apprise）。
- 不做微信公众号/服务号模板消息、企业微信智能机器人（aibot）、逆向个人微信协议。
- 不做附件/图片/语音/文件与模板卡片（列为 M4 可选）。
- 不接入 `examples/` 任何示例与实盘工程（另立需求）。

## 5. 决策记录（用户 2026-09-17 裁决，已锁定）

| ID | 决策 | 影响 |
| --- | --- | --- |
| D32-A | 渠道范围 = 无状态渠道 + 企微应用消息 + **微信 ClawBot + QQ 官方机器人**；排除逆向个人微信协议 | 覆盖面从"群机器人"扩展到个人微信/QQ 官方通道；带来会话锚定设计与绑定流程（设计 D32-09） |
| D32-B | 零新第三方依赖：标准库 HTTP（`py3.urlopen`）+ `smtplib` | **不使用 `requests`**（不在 `setup.py install_requires`）；测试改用可注入传输层而非 `requests-mock` |
| D32-C | 接入方式 = `Strategy.send_message`（不引入 `cerebro.addnotifier` / Observer / logging handler） | 改动面极小（1 个方法 + 导出）；引擎零改动 |
| D32-D | 默认异步（**每渠道实例一个后台 worker 线程 + 每渠道有界队列**，同渠道串行、跨渠道互不阻塞），参数可切同步 | 主循环零阻塞且单渠道限流/重试不拖累其他渠道；代价是"run 返回不保证已送达"，需显式 flush（设计 D32-06/D32-11 已记录取舍） |
| D32-E | 测试口径 = 离线 mock 门禁 + 真实凭据仅本地手动冒烟 | 验收可判定、CI 可复现；真实送达不作断言 |
| D32-F | 边界 = 只做框架能力 + 文档，示例后续迭代再接 | 不触碰 `examples/` 与实盘工程，范围可控 |

**由本次调研追加的两项结论（需在评审时确认）：**

1. **D32-B 的强化**：`requests` 不在 `setup.py install_requires`，故"零新依赖"实现为**标准库 HTTP**；这与最初问题选项里"用 requests-mock 测试"的措辞有偏差，偏差已登记在设计文档 D32-02，测试改以传输层注入实现（能力等价且更强）。
2. **微信通道选型修正**：微信侧采用 **ClawBot（iLink）官方个人微信 Bot** 而非公众号模板消息（后者需认证服务号、企业主体）；企业微信**智能机器人 aibot** 评估后不纳入本轮（面向对话、需常驻长连接），企业微信侧仍走群机器人与应用消息。

## 6. 风险与应对

| ID | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| R1 | **微信 ClawBot 协议证据等级低**：端点与字段来自社区对官方 npm 包 `@tencent-weixin/openclaw-weixin` 的反推，官方文档站未公开；功能灰度、iOS 8.0.70+；存在"主动推送窗口"约束 | M3 可能无法按预期交付 | M3 先以假传输实现并按 AC32-17 断言框架行为，真实实测紧随其后（沙箱/灰度环境）；若不成立则**降级为"仅本地记录"或移出首批**，并回写需求文档未决项 3 与验收 AC32-17（不得写成 PASS） |
| R2 | QQ 机器人需主体认证、提审上线、IP 白名单（新增机器人默认启用） | 正式环境不可用，只能沙箱验证 | AC32-18 只在沙箱语义下判定；文档明确列出上线前置条件（白名单、提审、认证类型对应的频控差异） |
| R3 | 渠道阈值与错误码会变（平台政策） | 本地限流阈值或错误分类失效 | 阈值集中声明在 `channels.py` 一处；`rate_limit_scale` 留余量；错误分类对未知错误码退化为 `unknown` 而非崩溃；`NOTIFICATIONS_GUIDELINES.md` 标注复核日期 |
| R4 | 环境变量入口是否纳入首批未定 | 可能出现"文档有、代码无" | 评审时二选一：纳入（M2 交付 + AC32-03 增子项）或明确不做（文档不写） |
| R5 | 通知失败被误当"可用于生产告警" | 用户以为消息必达 | 文档与 `AGENTS.md` 明确：这是**尽力而为**的通知能力，不提供送达保证、不做持久化队列；关键告警需多通道冗余 |
| R6 | 多进程 optimize 场景消息轰炸 | 渠道被封或额度耗尽 | 默认 `workers="silent"`（子进程不外发）；`workers="send"` 需显式开启并在文档警示 |
| R7 | 会话锚定凭据落盘带来泄露风险 | 凭据文件被提交 | 默认路径 `~/.backtrader/notifications/*.json`、权限 `0600`、文档要求加入 `.gitignore`；日志与 `repr` 全量脱敏 |
| R8 | ClawBot **单 bot 同时只能连一个 agent 实例**（第三方证据，等级 C）：backtrader 占用长轮询后，该 ClawBot 无法同时接 OpenClaw 等其他助手，反之亦然 | 用户既有助手被挤掉或刷新中断，表现为"莫名收不到/不刷新" | 指南显著说明该互斥并建议为交易通知**单独创建一个 ClawBot**；M3 实测确认 |

## 7. 前置条件与依赖

- **M1 无需任何外部依赖**（纯代码 + 离线测试），可立即开始。
- **M3 需要**：可用的微信 ClawBot 灰度账号（iOS 微信 8.0.70+）与 QQ 开放平台账号（个体开发者可人脸认证入驻）及其沙箱环境。若暂时不可得，M3 可先交付"框架侧 + 假传输测试"，真实实测顺延，验收状态记 `BLOCKED` 而非 `PASS`。
- **M2 需要**：无外部依赖；若希望做真实发送验证，由用户在本地用 `scripts/notify_smoke.py` 自备凭据执行（结果可选落 `evidence/smoke/`）。

## 8. 建议评审顺序

1. 先审[需求文档](./需求文档.md)第 1、6 节（范围与渠道优先级）——确认渠道取舍与"不做"清单无异议。
2. 再审[设计文档](./设计文档.md)第 2、6、9 节（依赖策略、异步模型、会话锚定）——这三节决定实现形态与主要风险。
3. 最后审[验收文档](./验收文档.md)第 3、6 节（具名用例与风险对验收的影响）——确认可判定性与 `BLOCKED` 分支可接受。
4. 评审通过后，把需求/设计/验收文档状态由 `PLANNING` 改为 `APPROVED`，再启动 M0/M1。
