## 1. 决策与范围

用户确认：实盘只允许两种互斥路径。Direct 通过 bt_api_py 统一 SDK 直连交易所；Gateway 必须接入 Gateway、Execution、Risk、Monitor、Runtime 五个微服务组件。不保留混合实盘路径。组件全备不是说五者串行转发每笔订单。

本计划建议：业务实现采用薄 Base + Direct/Gateway 两套，先冻结模式和状态所有权，再迁移代码；保留原导入兼容面到迁移完成的建议不等于批准永久兼容。Replay、回测和若保留的只读观察是非实盘工具，不携带下单、撤单、替换、结算等账户写能力。本轮只写设计文档，不实现、不启动服务、不执行测试、不登录账户或发出指令。实盘、模拟账户接入、部署和切换均须另行授权和验证。

目标不是提速承诺：先减少职责交叉和隐式选路，架构验收不依赖某次时延更好。现有 Backtrader 核心调度、指标和回测撮合语义不在迁移范围；后续单独测队列、每笔事件开销、回调时序和恢复耗时。

## 4. 目标职责与服务合同

| 所有者 | 必须提供的合同 / 不应承担的事 |
| --- | --- |
| Backtrader | Cerebro 和策略生命周期、Feed 时间线及 bar 投递、BT Order/Position/Trade 和通知投影。保存框架需要的身份和因果映射；不另造 SDK venue 协议或服务的授权真相。 |
| 统一 SDK 与 provider | SDK 负责统一 facade、route 和会话装配；provider 负责场所原生登录、行情、协议映射、写入和回报。Direct 仅经这一条场所链路；Gateway 根据已冻结服务合同使用 SDK/provider，BT 不直接旁路写入。SDK 包被依赖不等于 BT 有场所写权限。 |
| Gateway | 策略/账户/venue 绑定、可验证会话代次、统一连接和分发、行情/回报的流和恢复证据。沿用 63 的既有边界：Gateway 交易 owner 是唯一场所派发者、场所会话与权威台账的所有者；最终绑定/作用域校验留在 Gateway，不假定由它校验 Risk 准入。 |
| Execution | 订单意图的身份、持久化接受、幂等和唯一派发权、撤单关联、结果未知及对账；向 BT 提供可关联的状态证据。不将请求超时等同为拒单。建议作为新策略订单意图的唯一上游受理和编排入口，由 Gateway 交易 owner 进行场所派发；Execution 自身不得另开场所写入会话。具体准入验证和持久回执合同在 SPLIT-00 冻结。 |
| Risk | 按绑定范围提供可验证、有版本和有效期的风险准入；提供明确的允许、拒绝、不可用证据。Execution 验证与订单意图对应的证据，再决定能否派发。BT 展示结果，不替代有权的风控决定。 |
| Monitor | 只读采集健康、代次、延迟、流缺口和异常，告警可关联到路线和命令。不是交易门禁的替代凭证，不下单或补发。组件必配；运行期故障域/降级策略待确认。 |
| Runtime | 核对组件和配置，协调启动、停止、恢复、预检及诊断；保管运行所有权或按冻结合同分配。不是 second broker、不接管订单或风控真相，也不驱动 Cerebro 指标。 |

Gateway 建议的消息流：行情从 Gateway 市场订阅进入 Feed；订单意图进入已绑定的 Execution 执行入口，经约定的授权组件核对 Risk 证据后交给 Gateway 交易 owner 唯一派发；成果沿原绑定回报，再由 Broker 投影。Monitor 旁路观测，Runtime 控制和协调。服务实际调用顺序、持久化点、开仓/平仓/撤单策略以跨仓合同和下一轮证据冻结为准，不在此把设计当作交付现状。服务不足、过期或无法证明授权时，至少禁止新开仓；不暗示退出或撤单可绕过风控/所有者规则。

## 5. 模块形态：薄 Base，两套实现

- BaseBtApiStore：框架注册、工厂契约、公共状态/错误接口；`DirectBtApiStore` 管统一 SDK 自有会话和回收；`GatewayBtApiStore` 管五组件端口绑定和 Gateway 会话。模式装配集中在单一显式 factory / composition root，不在 Feed/Broker 反复读取同一堆开关。
- BaseBtApiFeed：回调与 bar 投递顺序、聚合/数据线、生命周期信号和通用质量投影；Direct 和 Gateway 各提供来源端口或薄类。只读和回放另行导出，不塞进 live Base。用同一规范化数据做逐条事件 parity，不能为共用接口牺牲时间语义。
- BaseBtApiBroker：框架对象、队列及经过对照证实的投影；Direct Broker 使用 Direct SDK 准入、回报与本地恢复，Gateway Broker 使用绑定的 Execution/Risk/回报流。现有 mixin 可先继续由各自实现使用；拒绝多继承带来的 MRO/参数覆盖变化。禁止把不同场所/服务的未知状态含义统一简化成 rejected。
- 名称和文件数非验收项。建议暂保留 BtApiStore、`BtApiFeed`、`BtApiBroker` 的公开 import/注册作为薄兼容壳，再视迁移证据决定公开两个工厂或公开类。保持 getdata/getbroker、类参数、规范化返回、Order/Position 身份与 live/replay 隔离可验证。

## 6. 关键不变量

1. 单写者：同一允许写入的作用域（至少账户、场所、route；策略范围与多策略共享由合同定）同一时间只有一个被证明有权的写入路径。进程锁、generation/fencing、账户身份和 provider 会话一致；重复启动、锁丢失和过时代次拒绝写入。不得用配置默认值或重试绕过。
2. 唯一订单意图与结果未知：在任何外部派发前生成持久、可追踪的命令身份，把原模式、绑定和能力记录持久化。超时、断线、重启的未知不标成失败/拒单，不自动切模式或再发。只沿原路径读证据、去重和对账；证据不完整保持 UNKNOWN/人工处理。撤单、部分成交、重复/乱序回报和终态冲突分别对账，并区分本地明确拒绝、已提交、回报未知和可证实的终态。
3. 不跨模式热切换：先阻止新意图、停写、保存未决、按原路对账，将旧会话标记停止且有明确所有权交接证据，再由获授权人员启动新配置。若不能证明停止、不知道交易所状态或有未决污染，暂停切换。回退是隔离的版本/发布操作，不是在运行中回退 Direct。
4. 可观测性：诊断记录 mode、不可逆脱敏的 session/strategy correlation、状态和失败边界，不能写入账户秘钥或真实配置。状态误报、告警缺口、回放时钟/前视及数据掉队与业务拒单分类记录。

## 9. 需确认与未验证事项

1. 公开 API 最终是原三类加两个工厂，还是另外公开六个薄具体类？旧名称支持期及诊断错误安置何处？

3. 单写者锁的作用域，在共享账户/多个策略如何授权，请冻结 Redis/本地锁/服务选主等实现边界和切换证明，不在此指定技术。
4. 历史混合配置还有哪些使用者、是否存在持有的未决订单/数据库、如何隔离和只读导出；旧日志保留及迁移的审批者。无授权不得处置这些状态。
5. Direct 借用/自有 SDK facade 的支持界线；只读/Replay 是独立工具还是保留研究接口；接受的第一批交易所、操作和证据等级。不能从文档提到 CTP/OKX/Binance 推出全部已上线。
6. Gateway 五组件各自配套合同在当前工作树未作完整启动和行为验证；迭代 63–71 仍以各自证据和门禁为准，不能因这里全组件必配而宣布已经通过。
