# 迭代50：通用基础设计与实施计划

初稿：2026-10-23；联合修订：2026-10-24；版本：v0.2。
状态：**设计稿，未实现、未运行验收**。分工见 [README](README.md)，验收唯一入口见 [验收方案](验收方案.md)。

## 1. 目标、分层与边界

目标是同一份因子定义通过正常Cerebro生命周期用于研究、回测和实时普通bar策略。实时可由合格历史预热，也可从真实闭合bar逐格积累；策略读取当前快照，经既有BtApi执行链送单、收回报并受控恢复。

- **50-A**：先完成Alpha003所需的严格装配、history/tick/direct-bar输入合同、同期交付、缓存、因果回测、订单关联/恢复和安装profile。不是只完成构图或少量单测。
- **50-B**：在同一实现上扩到全101合成字段、逐节点数值、不同buffer、缺格、派生/外部字段和多因子长稳。它是50最终交付要求，但不阻塞已通过50-A的51示例集成。
- **50-C**：在51唯一示例上完成真实行情/账户证明，按对应AC复用原始运行证据，不独立发起一套重复交易。

支持单品种及epoch内静态多品种集合、同频同格、native/build、有限迟到/缺格/重建和有界内存。单品种使用相同cohort合同，但不保证横截面因子在单资产上有有效值。

不包含未闭合bar反复修订、逐tick分钟因子重算、`cerebro.replaydata/resampledata`、任意混合频率、运行中动态增删目标、跨账户原子组合、在线训练或新交易服务拓扑。示例CLI的 `--replay` 表示历史交易回测，并非Cerebro replay时钟。51主力换月使用停新决策、对账、重建epoch，而非绕过静态绑定合同。

接收49及后续优化的已提交基线；追加优化未完成不阻止规划、fixture和主力工作。修改共用热点前明确归属，每次接收新基线只复测受影响合同，不能混用不同版本的数值或性能证据。

## 4. 最小公开接口与共享绑定

暂保留以下拟议名称，R0可按既有接口收敛；没有第二套live公式API。

| 接口 | 职责与约束 |
|---|---|
| `LiveFactorPlan` | 不可变targets/groups、FactorSpec、日历/频率/字段合同、预热/迟到/容量；不包含凭证、账户或交易策略规则 |
| `LiveFactorSet.bind(plan, datas)` | 在普通Strategy的OwnerContext中使用共享绑定，保留mode、图、target/input身份；也支持有限历史交易回测 |
| `LiveFactorSet.snapshot()` | 原引擎完成本批次后读当前不可变value/status/input identity，不计算、不推进、不发单 |
| `LiveBarCohort` | 取得/验证/暂存bar及整批可见性，未就绪及时返回；不是因子调度器 |

普通 `bt.Strategy` 组合因子集合，并继续调用 `buy/sell/cancel`，是必须验证的用法。`LiveFactorStrategy/on_factors` 只有出现真实重复需求时才作可选薄便利层；不强制继承，不新增必经 `submit_factor_order`，不强迫使用managed身份体系。决策有效性由共用前置检查和所选执行适配绑定，最终仍由原Broker/Store准入控制。

提取一个内部共享装配接点（必要时 `_binding.py`），共用FactorSpec字段解析、分组、命名辅助输入、参数/mode和严格上下文。研究入口提供有限grid，普通策略提供有限或开放式bar合同；不让 `ResearchSpec.end=None` 或伪造无限DataFrame。

单个Cerebro首版只允许一个cohort；所有驱动时钟的目标和辅助Feed都须属于它，不能靠额外Feed反复触发旧因子。公式group可以是其子集。额外输入不自动加入输出或横截面池。oldsync、cheat-on-open/close、改时戳filter、channel mode及多cohort等不支持模式应在资源接管前拒绝。

因子membership是公式资格，present是当前数据是否有效；两者分别绑定，数学有效成员按原profile组合，不能把业务membership直接替换成present。源字段值随时间因果更新不等于改变字段定义/组/目标；定义变化须新epoch并保留交易连续性。

## 5. 输入与时间：统一合同，分开来源

### 5.1 不可变bar envelope

复用现有BarEvent/BarEvidence，入队时保留：actual instrument/feed、来源/连接generation/序号、bucket_start/end、available_at、TradingDay/session/时区/clock domain、OHLCV/附加字段、complete/quality/present、原始bar ID与history/live角色。

- 历史文件、tick-built和direct-bar分别有来源适配与正反例，不把history伪装成实时quote revision；50-A覆盖三种合同，首个实际路由只需支持其使用的来源，不扩张全部provider。
- 原始payload进入 `_normalize_bar` 或LineBuffer之前检查字段存在、类型、非有限值、OHLC/volume口径。INF、错误类型或缺字段不能被容错变0。NaN只能伴随明确缺失语义。
- 流式strict必须绑定真实Feed/字段和其交付记录；一个 `validated=True` 或 `factor_name=None` 不构成准入。错误继续经FactorComputationContext传播。
- 这些是业务数据合同，不新建多代源码pin/进程证明基础设施。模块/依赖版本、调用与数据来源须可核对，但不额外要求第三方签章。

### 5.2 grid时间不等于可交易时间

因子profile使用UTC `bucket_end/close_time` 为grid，保留start与available_at；普通未启用Feed保持原标签。生成bar、封存截面、决策、提交与成交的可用时点分别记录，任何后续步骤不得回标为先前可用。

研究可按close_time展示结果；回测和COMPOSITION同样必须遵守available_at。例如10:00截面到10:00:02才齐，不得按10:00:00的下一分钟open成交。tick/quote回测只能匹配提交之后可用的事件；仅分钟数据时，首个开端不早于提交可用时点的后续bar才是最早匹配候选，仍须满足限价规则。未记录接收时间的历史源须声明自己的可用性假设；不能宣称复现真实网络延迟。

历史、回测、实时使用相同频率、日历、价格与成交量单位。CTP累计成交量转增量、首tick/首半桶、日切/重连基线及无效源时间由实际Feed适配验证；本机时间不能替代缺失事件时间。无成交/无tick不能靠墙钟造完整bar。

### 5.3 附加字段

Alpha003基础仅需open/volume与输入完整性；未知字段须明确拒绝。50-B扩展既有field_bindings、ADV/VWAP、命名benchmark、市值与行业数据，保留生效/可用时间和freshness。没有真实VWAP不能用OHLC均价冒充，额外数据不扩大公式pool。

全101可用完整合成字段验证数学；真实市场能力按实际来源列出可用字段/因子及拒绝原因，不能称每个市场都可跑101。递归自定义因子也不能只凭一个H值获得有限重放资格。

## 6. 在指标之前同步

### 6.1 原循环的最小接点

在 `_runnext` 的feed advance前，显式cohort有预算地 `prepare_round()`，准备最早未消费的不可变batch；所有Feed完成该batch的line交付后、任何indicator/Strategy/业务bar回调之前核对时间/成员/序号/次数。

- cohort是成员行情取数、历史队列消费、闭合与暂存的唯一协调入口。成员 `_load` 只交付已封存的本成员envelope，否则立即None；`_check` 不得偷消费、闭合或派发事件。重试、全None、single-data和EOF均遵守。
- 每成员每批交付一次；半批失败即停止epoch并重建，不继续计算或手工回滚指标。来源结束先排尽完整batch并处理尾部缺格，不能某成员提前EOF让别的成员丢尾部。
- `notify_bar` 在整批可见后派发，使用仍有效的原证据关系；封存后不接受后续tick改写该bar。
- **暂停发布不等于停收行情**：coordinator可继续按预算接收并暂存后续事件，但不能推进下一批line；执行行情缓存按原职责更新。闭合bar的quote证据保持不可变，提交使用独立的新鲜执行报价；二者不能相互冒充。
- 来源与pending有界；等待过久/溢出冻结而非无限积压。各来源合法generation可以不同，应分别验证连续性，不能机械要求跨Feed值相等。
- 现有2～3腿MultiLegBarBarrier可复用类型/失败分类，但不是任意资产的line交付器，不硬扩其原合同。

期间继续 `_storenotify/_datanotify`、Broker无bar轮询、查询/回报和 `notify_idle`。每轮prepare按事件数/单调时间双预算及时返回；空轮完成订单工作后统一有界等待，行情/停止/Store通知可唤醒，防丢失唤醒。不能每Feed叠加sleep、阻塞等所有腿或忙轮询；等待上限不越过订单轮询/已配置续租的下一期限。

### 6.2 日历、缺格与profile能力

grid来自明确计划日历，而非已到达bar集合；未来日历不足时停止新决策。51可用全组共同交易分钟，休市不生成gap；日历中应有但缺失的分钟才是gap。窗口跨休市是否保留由同一profile固定，流批一致。

- 未封存格允许有界乱序暂存；相同重复数据去重；封存后迟到不回写，冲突停止epoch。
- 迟到到期依据单调预算，只能证明等待结束，不能虚称provider watermark推进。
- 缺格首先进入 **09a：冻结并全组重建**，原grid仍留缺失记录，不用“最后N个收到的bar”压缩掉它。
- **09b：显式gap推进** 需要当前因子profile在NaN/present、membership、所有滚动子节点与Broker无效价格处理上独立通过；通过Alpha003的09b即可供51使用，不必等待全101。未验证因子仍冻结，50-B再完成全101的09b。
- 全cohort输入缺失时本批不产生新风险决策。继续计算其余有限成员不代表允许在残缺截面交易；缺口退出依赖窗口后还需就绪检查。gap不能成为报价、估值有效性或成交证据。

09a先验收再09b，取消“R2退出先要求R3全101已通过”的倒置。profile能力是已有验收事实的明确登记，不是允许绕过检查的运行开关。

## 7. 预热、因子状态与计算重建

| 状态 | 计算与交易 |
|---|---|
| INITIALIZING | 绑定、源/配置校验，禁止因子下单 |
| WARMUP | 同图处理合格历史或实际积累bar，禁止历史信号下单 |
| CATCHING_UP | 处理切换/重连积压，禁止旧格补单 |
| LIVE_READY | 同批输入、窗口、时间和执行准入均合格才允许业务决策 |
| DEGRADED / RECONCILING | 停新风险，保留查询/回报及获准风险处置 |
| STOPPING / STOPPED | 停新批次/决策，按既有生命周期收尾 |

就绪不能仅看 `data.LIVE` 或最终值有限；复用 `_window_is_complete` 的字段/当前格/窗口完整性，live用有限状态实现。

- **无历史冷启动**：建立源基线、排除首不完整桶，积累完整实时截面到minperiod/预热要求，再以新的合格live格解锁。51默认30格；通用模块不写死30。
- **历史加速预热**：明确来源、相同口径，cohort自首条预热起生效；重叠去重、处理积压，所有成员共同越过cutover。CTP基础接口没有历史bar不应导致冷启动永远不可用。
- **重建**：先对账原订单/持仓与UNKNOWN，恢复交易去重边界，再重建因子。Alpha101只有在依赖跨度被证明时才能有限重放；EMA等从固定genesis重放或用另行验收状态恢复。不得pickle任意Strategy/Indicator。
- 新计算epoch不等于新交易逻辑运行。需要更新目标/字段/日历时先停止新风险、对账再绑定；51的主力政策决定何时换月，50只提供静态epoch重建合同。

## 8. 目标、订单与所选执行路由

### 8.1 数学有效、策略目标、执行就绪分层

当前快照包含batch/close_time/available_at、版本与mode、每资产value及真实可追溯reason。无reason的NaN记OUTPUT_UNAVAILABLE，不臆造READY。

因子集合只提供计算状态；Strategy结合显式direction/规则/交易子集产生信号目标，再结合账户/在途/权限/元数据/报价产生子订单。相同因子不保证不同账户状态下订单相同，测试须分这两层固定完整输入。研究评价/训练不进入实时循环，因子本身也不携带账户或order逻辑。

### 8.2 最小持久决策关联

同一逻辑运行的业务key为 `(account_scope, strategy_scope, logical_run_id, cohort_id, close_time, decision_kind)`；子意图加入instrument/side/position_effect/leg。config/mode/主力清单版本属于不可变payload绑定，generation/进程/计算epoch不是去重key。修改配置不得重新交易已封存同格，同key不同内容是冲突。

新的logical_run_id只能由明确的新会话准入建立，并核对既有订单/持仓及cutover，不能在恢复时自动生成。跨运行也不能靠改ID接管未知单或重播旧信号。

先持久固定决策（包括无操作）及子意图内容，再调用原提交。优先复用所选路由的现有存储/所有权/查询接口：ServiceExecutionRecoveryJournal仅在已配置service路由上使用；非service路由若缺决策记录，只补最小的提交前关联及唯一key，不复制订单/成交/余额权威状态。

必须验证持久化、派发、ACK、callback间的故障窗口：仅可证明未发送者可续原意图；不确定者保留原ID查询，不新ID重发。恢复只提供冻结而不能恢复新交易的路由，可作为中间诊断交付，但不能通过50-A完整恢复/51最终恢复项。所选路由必要缺口必须修复，不能强制安装全部服务来规避。

每资产最多一个未决因子意图；partial fill、重复/乱序回报与撤单后成交只累计一次。多资产独立提交不是原子组合。风险减少/撤单依原授权和当前执行状态，不因没有新因子而一概禁止，也不能借机扩大授权。

### 8.3 单一路由与最小接入

R0与51共同选择一条实际可用SimNow路由，优先核实既有 `RegisteredSimStore/Wrapper`；普通CTP直写限制保持，明确的registered-sim准入不是全局开写。ServiceExecutionSession为可选已配置路由，ServiceReadProxy继续只读，不允许自动fallback。

普通Strategy的buy/sell/cancel必须经BtApiBroker/Store；在原提交前补当前decision/owner/batch/有效窗口关联，保留原资金/权限/风险/UNKNOWN检查，未配置普通策略行为不变。不要为新的下单API改所有Broker。

51负责验证实际多合约arm/排队/撤单目标，若需要改SDK或共享Store则在其归属模块修复。没有合格路线可先完成source/shadow诊断，但不能将真实交付目标改成shadow或宣称账户通过；同样不为此另建Gateway/Actor平台。

## 9. 有界存储与性能

live使用 `runonce=False, preload=False`，只采用经过验证的exactbars/qbuffer配置。value与reason按各自逻辑时点读取，不用target物理索引直接索引不同容量deque。优先在研究适配修复，实证需要才改LineBuffer并扩大回归。

调用时间保留计数及有限样本，离线仍可有完整诊断。bar pending、日志、决策缓冲、line、终结订单缓存均有上限；活动/UNKNOWN/未完成callback不能淘汰。若无安全归档，就显式限制会话并通过已验收重建接续，不称无限长稳。

50-A先测20资产单Alpha003的100,000格；50-B保留20资产六代表因子长流、两小时墙钟及全101buffer检查。51另测真实全目标池；只有实际负载和判据均覆盖时才能共享结果，单Alpha003不能替代六因子负载。批研究性能继续按49冻结方法验证受影响热路径，不增加第二个五倍优化项目。
