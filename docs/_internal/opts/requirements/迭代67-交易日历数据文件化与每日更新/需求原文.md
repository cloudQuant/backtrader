本文件只保存用户原话和同一讨论中的决定，不包含设计结论；设计见[迭代计划](迭代计划.md)。

## 3. 解读说明（起草人注，非用户原话）

- 原话 2 中“这个存放的位置”指 I62-04 的交付物。I62-04 的文字是“BT 内置的版本化数据文件”，实际代码是 `bt_api_ctp` 包内的 Python 常量（STATIC，见计划 §1.2）。两者都随安装包固定，用户不满意的是“固定在包里、不能按系统指定位置、不能每天更新”这一点；计划按此理解。
- 原话 2 中的“config.yaml”：计划理解为运行 CTP 会话的进程所读的配置文件，即 007 示例每个策略文件夹的 `config.yaml`（direct），以及迭代 63 账户级 Gateway 文件夹的配置（Gateway）；每日更新工具也读同一个键。键名和未配置时的缺省是计划的候选决定（D67-01）。
- 原话 2 中“放到一个calendars的文件夹中，ctp的日期数据放到ctp的单独文件夹中”：计划理解为 `<calendars 根>/ctp/`，根目录由 `config.yaml` 指定；以后若有其他场所的日历，各自一个子文件夹。
- 原话 1 中“每个交易日都更新一下”：日历的大部分内容一年只变几次（节假日公告、夜盘时间调整、临时休市），每天要做的是核对与发布：读入当天经人工核对的公告、从 CTP 取得品种与合约清单、校验、发布新版本或确认“无变化”。计划按“每个交易日收盘后运行一次更新工具”设计，不按“每天从网上自动抓取”设计（计划 §3.6）。
- 原话 1 中“方便策略使用”：计划理解为策略经 SDK 的统一接口查询时段，不自己读文件（计划 §3.9）。
- 职责归属：场所日历事实归 provider `bt_api_ctp`（[仓库职责规范](../../../../source/developer-guide/repository-responsibilities_zh.md):121 已写 `bt_api_ctp.trading_session_schedule` 为 provider 拥有的版本化日历）。“写在 `config.yaml` 里的路径”只是位置配置，不改变归属。
- 迭代 62 的 I62-04 中“2027 年节假日在官方公布前标为未知（待核验），不推测”继续有效，本迭代沿用。

## 4. 主会话归纳的目标（非用户原话，供审阅核对）

- CTP 交易日历从包内常量改为 `<calendars 根>/ctp/` 下的版本化数据文件，根目录由 `config.yaml` 指定，三个平台路径规则一致；包内保留一份种子版本。
- 每个交易日收盘后运行更新工具：节假日取自经人工核对的官方公告（国务院与各交易所），品种与合约清单取自 CTP，校验后原子发布新版本并保留历史；失败时告警并保留旧版本。
- 运行时在启动和每次交易日切换时加载最新的有效版本；覆盖范围之外为 UNKNOWN，休市待发单不派发（同 I62-04 的 fail-closed）；与 CTP 实时合约状态交叉核对，紧急情况下以实时状态为准。
- 策略经 SDK 查询时段，不读文件。
- 迭代 62 的内置 2026 年日历在本迭代交付前保持不变。
