## 1. 背景与现状（STATIC，2026-11-06）

### 1.1 为什么有本迭代

- 用户要求：日历从本地文件读取、每个交易日更新；根目录写在 `config.yaml`，放在 `calendars` 文件夹，CTP 数据在其中的 `ctp` 子文件夹；Windows 11、Ubuntu、macOS 都能用（U67-1、U67-2）。迭代 62 的内置 2026 年日历保持不变，新做法写进本迭代（U67-3）。

### 1.3 缺口

1. 数据在代码里，更新要发版；没有可由运营指定的位置（U67-2）。
2. 只覆盖 2026 年，2027-01-01 起全部 UNKNOWN（§1.1）。
3. 没有版本历史，事后无法知道某个判断用的是哪一版数据；BT 待发单记录也不存 `calendar_ref`（§1.2 第 15 项）。
4. 没有每日流程：公告录入、核对、发布、告警都不存在。
5. 两份日历分叉：时段日历含夜盘与集合竞价，预期日历只有日盘；节假日常量只在后者；两者都不含临时休市。
6. 实时合约状态未使用，紧急停市（台风、熔断、临时停牌）只能靠场所拒单发现。
7. 策略没有查询入口：BT 只在 Broker 内部使用日历（`dm:1648-1655`），SDK 只返回端口对象。
8. 日历只在启动时取一次（`dm:538-540`）；长期运行的进程跨年后不会换数据。

## 2. 目标、非目标与新增规则

### 2.1 目标

1. **数据文件化。** CTP 的交易日、假日、临时休市、节前无夜盘日期、各交易所与品种的时段模板（含夜盘结束时间与集合竞价）写成版本化 JSON 文件，放在 `<calendars 根>/ctp/`（U67-2）；包内带一份种子版本。
2. **位置可配置、三平台一致。** 根目录由 `config.yaml` 指定，路径规则在 Windows 11、Ubuntu、macOS 上相同（§3.3）。
3. **每日更新工具。** 每天晚上运行，使用可用 AKShare 接口与明确标识的 mock 输入，完成校验、比较、无变化记录和按 D67-23 配置的自动／人工审核发布；记录各范围来源及失败。未来切换 Opendata 不要求策略重写。
4. **运行时。** 启动时与每次交易日切换时加载最新的有效版本；覆盖之外为 UNKNOWN，休市待发单不创建、不派发（同 I62-04）；时段答案带版本（§3.7）。
5. **实时状态交叉核对。** CTP 合约状态推送投影为中立状态，与日历合成；紧急停市以实时状态为准（§3.8）。
6. **策略查询。** 策略经 SDK 接口（BT 的 Feed/Store 投影）查询时段，不读文件（§3.9）。
7. **验收。** UNIT/FAKE 与 INTEGRATION_SIM 覆盖发布、并发读取、损坏恢复与日切加载；PACKAGE 在三平台分别记录；SimNow 观察一次收盘后发布与跨夜盘日切。

### 2.2 非目标

- 不改迭代 62 的内置 2026 年日历（U67-3）；本迭代交付并经用户验收前，62 的行为不变。
- 不让策略、SDK 或 Gateway 运行时依赖外部采集网络；独立更新进程可为实现 D67-14 联网采集，来源、覆盖及解析以实际验证为准。
- 不改 D62-30、D62-34～36 与 R-3 的派发语义；日历不成为立即派发订单的前置（D62-36：日历与行情不能证明没有临时停牌，场所按实际规则处理）。
- 不实现 Gateway 侧（Gateway 进程读取日历根目录、向策略转发合约状态）：按 U63-4 提交迭代 63（§3.10）。
- 不做 OKX、Binance 的日历（7x24）；CFFEX、GFEX 仍属本期六所功能范围，使用可用 AKShare 或明确 mock 场景验证，不要求直接解析交易所网页。
- 不做调度器：用操作系统的计划任务；迭代 66 的 runtime 不做定时任务（66 §2.2）。
- 不做回测数据的日历重放；D67-09 A 已决定保留全部历史，并提供按时点查询已发布版本。

### 3.2 行业做法与取舍（参考来源见文末，本次未打开原文核对）

- QuantConnect LEAN 用一个 JSON 文件（market-hours database）描述各市场与品种的交易时间：按“证券类型-市场-代码”分条目，可用通配条目作市场缺省；每条有交易所时区、按星期的时段段（盘前、盘中、盘后），以及显式列出的假日、提前收盘、推迟开盘；随数据仓库一起版本化 [R1]。
- exchange_calendars、pandas_market_calendars 用 Python 代码描述规则并按年推导 [R2][R3]——这正是现状，每次变化都要发版。
- 中国期货：国务院办公厅发布次年节假日安排；各交易所发布休市安排与节前夜盘安排通知，夜盘与集合竞价时间以交易所公布的交易时间为准（来源已列于 `ctp: futures_expected_calendar_provider.py:67-123`）。
- 取舍：发布物用 JSON；按 D67-03 分开表达交易日、品种时间模板和例外，交易日和已确认例外显式列出，查询时按模板组合；版本不可变加指针，自动采集并按配置决定是否人工确认。

- 路径规则与 `ctp.catalog_cache_dir` 相同（`ex: run.py:160-175`）：相对路径相对 `config.yaml` 所在目录；允许绝对路径；`~` 展开为用户主目录；不展开环境变量；不依赖当前工作目录。Windows 的盘符、UNC 路径、大小写不敏感与超过 260 字符的长路径在 67.01 定处理方式，67.09 在 Windows 11 上实测。
- 根目录建议放在本地磁盘：网络共享盘上的重命名与文件锁语义较弱（§6.1）。同一主机的多个策略可以指向同一个根目录（运行时只读，INV67-02）。
- **D67-01（2026-11-11，用户已决定 C）**：Gateway 模式或 direct 写入准入开启时必须显式配置 `calendars.root`；未配置拒绝启动并报告 `calendar_root_unconfigured`。可显式指定 `root: package_seed` 使用包内种子；状态和报告必须标记 `package_seed`，不能将其表述为每日更新。离线 `--dry-run` 只报告配置问题。旧行为在本迭代交付并验收前保持不变；非 Gateway 且未开启 direct 写入准入的未配置行为不由此决定，67.01 另行冻结。
- 验收覆盖：Gateway 与 direct 写入场景分别验证缺失时拒绝、显式外部路径按配置文件位置解析、显式种子的状态标记、离线 `--dry-run` 只报告；67.08 为 007 示例补充相应配置，67.09 覆盖三个平台和安装包。此决定不改变日历覆盖不足时的 UNKNOWN，也不授予账户操作。
- 配置经 Store 的 SDK 选项传入（新增可选项 `trading_calendar`，与 `market_clock_verification` 同一路径，§1.2 第 21 项），再由 SDK 交给 provider 工厂；不使用进程级环境变量（避免同一进程内不同 route 互相影响）。

### 3.4 文件格式（D67-02 A；schema v1 在 67.01 冻结）

**D67-02（2026-11-11，用户已决定 A）**：日历发布物使用 JSON；需要人工补充公告信息时可使用 YAML。AKShare 自动采集不要求人工编辑 JSON 或 YAML；人工审核模式下由审核人核对差异并按 D67-13b 确认。发布数据的字段、YAML 输入的校验及编解码细节在 67.01 冻结，跨平台与安装包行为分别验证。

**D67-03（2026-11-11，用户确认三层设计）**：交易所交易日逐日明确列出，品种交易时间按生效期保存模板，休市、停夜盘及其他例外按明确范围单独表达；查询时将三层组合。已确认的具体例外逐项列出，不以工作日或统一节假日公式替代交易所事实。模板供日期查询时组合，无须每天为每个品种物化所有窗口。

| 逻辑层 | 目标数据与边界 |
| --- | --- |
| 交易所交易日 | 各交易所逐日列出的交易日、覆盖范围与来源；查询必须明确数据环境与覆盖；mock 开闭市只表示模拟，真实开闭市仍需真实依据。交易所开市不证明每个品种或合约均可交易。 |
| 品种交易时间 | 按交易所、合约类型（期货/期权）、品种及生效区间选择模板，区分集合竞价、连续交易、休息和跨午夜；期权与期货是否共用模板须有适用来源，如有合约差异须明确范围，无法解析时为 UNKNOWN。 |
| 例外安排 | 按交易所、品种或合约，以及自然日、交易日和时段明确适用范围，表达节假日、临时停市、取消夜盘等；不能用范围不明的例外覆盖其他品种。 |
| 共同元数据 | 版本、覆盖、来源、时区、内容摘要及局限；具体 schema、来源和摘要字段在 67.01 冻结。窗口输出为 UTC 半开区间，同时保留交易所本地时间与交易日归属。 |

晚间时段的自然日期与所属交易日可不同，跨午夜也须正确表达；例如周五夜盘是否归属周一，真实数据须有该交易所适用安排的依据，模拟数据按明确声明的 mock 映射测试，均不由“前一天”或统一周末公式推断。缺少任一必要层或相应环境下的归属依据时，相关范围为 UNKNOWN。有效 CTP 实时状态是独立观察，按 D67-08 B 处理已知日历冲突，不改写计划数据，也不推导未来窗口。

交易所日期、时段、例外和来源以一个组合版本发布；任何组成部分发生实质变化时，整体差异按 D67-23 配置处理后形成新版本，无实质变化不生成版本。指针 `CURRENT.json` 候选指向不可变发布记录，发布记录引用整个版本和摘要；67.01 冻结 schema、文件拆分、完整性和可恢复发布合同，不把预写时间当作真实提交时刻。

67.01 提供严格校验的合成示例：六所分别覆盖期货／期权，并包含不同时段、跨午夜、休息间断、节前停夜盘、临时休市及自然日与交易日映射。旧代码与历史规则可能有差异，记录为真实数据缺口；本期不以逐条解析官网为测试前提。

### 3.5 校验（工具发布前与运行时加载用同一个校验器）

1. 结构：schema 名与版本；未知键拒绝；类型、日期与时间格式；必填字段缺失即拒绝，不补缺省值。
2. 完整性：分别验证 `content_sha256` 与其规范化内容、指针摘要与其声明的摘要输入；两者输入可不同，不能要求摘要值必然相等。具体字段与规范化规则在 67.01 冻结。
3. 引用：每个假日、休市、例外、品种都引用存在且适用的来源；记录来源标识、可用的 URL、获取时间及其校验结果；人工审核模式按 D67-13b 另记核对人和时间，自动模式记录系统处理，不伪造人工审核；品种引用的模板存在。
4. 一致性：校验交易所、品种、日期、时段、夜盘归属和例外的结构一致性；AKShare 与 mock 来源及覆盖分别记录。mock 只用于模拟，不以调休、缺失记录或其他市场日历推断真实安排；真实来源核验归后续 Opendata 工作。
5. 时间有效性：按当前数据环境声明的规则检查窗口、跨午夜及相互关系；mock 规则只证明模拟行为，不证明实际场所规则；窗口应结束晚于开始，重叠或竞价与连续时段的关系按对应规则校验，不强加未经验证的通用假设。
6. 覆盖：每个交易所分别声明真实已核实覆盖与 mock 测试覆盖区间；D67-31 按北京时间自然日检查覆盖终点，默认提前 30 天预警（可配置）。真实运行的预警只使用已发布真实数据的覆盖，缺失时为 UNKNOWN；mock 覆盖仅用于隔离环境的模拟预警，不能推迟或消除真实预警。预警本身不阻止有效候选发布；区间缺失或不完整的处理按实际覆盖和既有合同，不因预警推断数据可用。
7. 与上一版本比较（只在工具中）：发布时刻之前的交易日与时段不得改变；确需更正时标 `correction` 并带来源，报告列出（保护时点查询）。

### 3.6 每日更新工具

- **入口**：独立更新命令由 SDK 装配版本仓和 CTP 采集/校验能力；CLI 名称及安装方式在 67.01 冻结。候选子命令：`status`、`refresh-products`、`build`、`validate`、`diff`、`publish`、`history`、`verify`；按 D67-36 B，人工补充文件由正常更新流程读取，不要求独立导入子命令。有限退出码：0 已发布；10 无变化；20 校验失败、未发布；30 需要人工核对（新品种、公告缺来源或确有冲突）；40 写入失败（提交状态另报）；50 锁被占用；新增的已提交后处理未完及提交状态 UNKNOWN 的退出码待冻结。
- **时间（D67-19，用户已决定）**：默认每天北京时间 **20:30（Asia/Shanghai）**由操作系统计划任务启动一次检查，周末和节假日也运行，部署时可配置时间；不能用可能陈旧的本地日历决定是否触发。由 cron 或 systemd timer、launchd、Windows 任务计划程序调度，67.08 提供样例并按平台验证上海时区与非上海主机时区；不新增应用内调度器。20:30 是检查触发时间，不证明来源已更新、审核在夜盘前完成或当前已发生交易日切换；请求日期和夜盘归属在 67.01 冻结。D67-05 B 的持续进程下次可信交易日切换生效、同日重启可重新绑定仍不变。
- **D67-20（2026-11-11，用户已决定 A）**：对可判定为临时性故障的公开只读采集请求（如网络超时、临时服务故障），首次失败后最多再试 2 次，默认每次间隔 10 分钟；重试次数、间隔可配置，请求超时与总运行时间须有上限。间隔从前一次尝试结束计算；遵守来源限流和明确的重试等待要求，超过本次时限则停止并报告。结构变化、解析错误、来源冲突等须报告核查，不能通过重试当作校验成功。逐来源/交易所记录尝试及最终结果；失败范围不记成功，部分成功按 D67-18。重试产生的候选或差异变化时，人工模式的原确认失效；内容变化按 D67-23 选择自动发布或人工审核。采集重试不授权登录 CTP 或发送邮件，不适用于发布结果不明：提交 UNKNOWN 按同一发布 ID 核验，无法证明时停止自动重试，遵守 §3.6 失败合同。
- **步骤**：
  1. 由 SDK 版本仓取单写者锁（候选 POSIX `flock`、Windows `msvcrt.locking`；具体实现和平台行为待验证，不依赖 BT 的 `live_state`）。
  2. 读当前版本。
  3. 按 D67-35/37 使用可用 AKShare 获取交易日、品种时段及例外候选；缺失或不适用的范围使用明确标识的 mock 进行功能开发和测试。记录来源类型、请求／生成状态、范围与缺口；不把接口失败、空结果或 mock 描述为真实采集成功。本期不编写交易所网页、公告或 PDF 解析器，不依赖 Opendata。
  4. 品种与合约清单：优先读取符合要求的 CTP 合约目录缓存或使用 AKShare 可用信息；D67-07：缓存缺失时仅在显式开启且获授权后可进行 CTP 只读查询，否则报告未更新并继续。真实清单不完整的功能场景使用 mock 标识；CTP 目录不证明时段。
  5. 可选：读取前一交易日记录的合约状态观察（§3.8），与日历比对，不一致项写入报告供人工核对，不自动修改日历。
  6. 在 `staging/` 生成新版本，用运行时的同一加载器与校验器加载。
  7. 与当前版本比较：成功检查的范围无内容变化时记录该范围成功，不产生新日历版本；失败或未覆盖的范围不能报告成功或“已核实无变化”，仅抓取时间、检查时间或运行号变化不构成日历内容变化。有变化生成差异；自动模式校验通过后发布，人工模式等待确认，确认绑定完整候选内容摘要与差异，候选发生变化须重新确认（D67-23）。有效覆盖、交易日/时段及来源依据等有实质变化时须报告，具体比较字段在 67.01 冻结。
  8. 发布：须以真正的排他创建/无替换机制保护不可变版本，不能用会覆盖目标的 `os.replace` 实现同名拒绝；候选的 CURRENT 单点提交、提交链、平台持久性和 UNKNOWN 恢复见[设计文档 §3](设计文档.md#3-发布恢复和时点查询建议修订-d67-0609)，待 67.01 冻结。
  9. 已处理的输入移入 `inbox/archive/`，写报告，释放锁。
- **失败**：提交前、提交后与结果不确定分别处理（INV67-04）；报告和退出码须区分未提交、已提交但后处理未完及 UNKNOWN。清理残留前验证不属于可恢复的同一发布操作；具体有限退出码在 67.01 冻结。
- **D67-18（2026-11-11，用户已决定 A）**：允许在部分交易所本次检查失败时，将已核验的其他交易所变化并入完整候选版本，按 D67-23 配置自动发布或经人工确认后整体发布；失败场所仅在上次已发布数据仍在有效覆盖内且未发现明确冲突时沿用，不将来源不可用当作本次已核实无变化。按交易所分别记录本次成功/失败、原因、最近成功检查时间、覆盖及告警；不能用部分成功刷新失败场所的成功时间或报告整批成功。已发现冲突或受影响范围无法确认时须报告并按既有覆盖/UNKNOWN 合同处理，不能以旧数据冒充已核实。跨交易所依赖、候选完整性或安全性无法证明时不得发布；发布后仍是单个不可变组合版本和单点切换，人工审核绑定整个候选；自动模式记录系统发布主体。D67-10 的两交易日告警按受影响交易所分别计算，计数来源不可证明时报告不确定；更细到品种或来源的计数在 67.01 冻结。
- **边界**：独立采集/更新进程按 D67-14 使用网络；日历运行时只读本地。AKShare 采集不要求账户登录；如选择启用可选 CTP 查询，仍须按 D67-07 和另行授权建立只读会话。未来 Opendata 接管采集不成为本迭代依赖；候选接口/来源元数据应便于迁移，但不得假称现有跨项目接口已实现。

### 3.8 与 CTP 实时合约状态交叉核对

- **投影（bt_api_ctp）**：把 `OnRtnInstrumentStatus` 的 InstrumentStatus（§1.2 第 19 项）映射为 base 的中立枚举；扩充安全字段，读取 EnterTime、EnterReason（自动、手动、熔断）与 TradingSegmentSN；附接收时刻、会话代际与交易日。状态的粒度（合约、品种还是交易所）、登录时是否推送当前状态、QUICK 模式下能否收到，都在 67.01 用 SimNow 捕获确认（需授权）；确认前只对字段完全匹配的合约或品种生效。
- **合成（SDK，中立；D67-08 B，2026-11-11 用户已决定）**：与已知日历冲突时，仅对当前 route、可信来源、匹配范围、当前会话代际和交易日且有效的 CTP 状态，以实时状态作为当前合成结果；日历与观察仍分开记录并报告冲突。精确状态/原因映射与有效期在 67.01 核实，未知、过期、旧代际或范围不能证明的观察不得用于放宽。

| 日历 | 实时状态（当前会话代际、当前交易日、未过期） | 结果 |
| --- | --- | --- |
| CONTINUOUS 或 AUCTION | 有效 NoTrading、Closed 或明确的熔断停止 | 当前按实时非交易状态；相应待发单不派发，按原有效期限和目标处理；记录冲突 |
| CLOSED | 有效 Continous | 当前按实时连续交易状态，可进入待发单的既有资格检查；不因这一状态自动延长期限、改写原目标、跳过其他检查或证明订单可成交；记录并告警日历过时 |
| CLOSED | 有效集合竞价类状态 | 当前按实时集合竞价状态；不当作连续交易，记录并告警日历冲突 |
| UNKNOWN | 任意 | 用户认为交易所日历正常覆盖时不需另设此业务场景；如发生缺覆盖、读取或校验故障，沿用 INV67-05 的 UNKNOWN 边界，不因实时观察推断未来窗口或变更既有待发单语义。 |
| 任意 | 与日历一致，或确实没有状态 | 一致时使用状态；确无观察时沿用日历并报告没有实时观察，不假称现场已验证。相关但失效、来源或范围不明的其他观察如何降级另行冻结，不能用无效观察本身放宽 |

**D67-16（2026-11-11，用户已决定 A）**：此前收到适用且可信的暂停交易状态，后来状态来源断开、该观察已被证明失效，基础会话与回报恢复等既有条件均已满足，当前日历显示连续交易，且尚无新的有效合约状态时，不把旧暂停状态当作当前事实；待发单可按日历进入既有资格检查，同时报告当前没有有效实时状态。仍须满足原目标、行情、授权等原有条件和 D67-15，不自动派发、改期或证明场所实际交易。基础会话未恢复或恢复证据不足时不得派发；有效的新实时状态仍按 D67-08 B 处理。状态可能是变化事件，不能仅凭一段时间没有新推送就断言失效；有效性、断线代际和恢复证据在 67.01 核实。此决定只针对所述场景，不预决所有范围不明或未知枚举的处理，也不改变立即单 D62-36。

- 立即派发的订单不受影响：`_direct_route` 在 UNKNOWN 时不转为待发，仍按行情资格派发、由场所处理（`dm:1616-1621`）；本迭代不改。
- 观察记录：provider 可把每个交易日的状态观察写入一个只追加文件，供次日工具比对（§3.6 第 5 步）；写入位置不在 `<calendars 根>` 内（INV67-02），67.01 决定（候选：合约目录缓存的同级目录）。
- Gateway 模式下策略进程没有本地 CTP 交易会话，状态须由 Gateway 转发（迭代 63，§3.10）；转发实现之前只用日历。
- **跨迭代冲突待协调**：63 [实施合同补充 §7](../迭代63-Gateway统一转发与多策略共享会话/实施合同补充.md)此前写“冲突不得扩大可交易范围”和“仅收紧不凭观察放宽”，与本次 D67-08 B 的有效实时冲突优先相抵触。此处记录用户新决定；应与 63 负责人对齐、更新其合同与联合测试，未完成前相关 Gateway 扩展为 GAP，不声称已实现或已验收。

### 3.9 策略怎样查询
