## 1. 背景与现状（STATIC，2026-11-06）

### 1.1 为什么有本迭代

- 用户要求：日历从本地文件读取、每个交易日更新；根目录写在 `config.yaml`，放在 `calendars` 文件夹，CTP 数据在其中的 `ctp` 子文件夹；Windows 11、Ubuntu、macOS 都能用（U67-1、U67-2）。迭代 62 的内置 2026 年日历保持不变，新做法写进本迭代（U67-3）。
- 现有日历是 `bt_api_ctp` 包内的 Python 常量，只覆盖 2026 年。按现有代码推断（STATIC，未运行）：**从 2027-01-01 起，所有 CTP 品种的时段查询都返回 UNKNOWN**，休市待发单不能创建（`target_session_unknown`）也不会派发，R-3 的日历核对结果为 `unknown`。2026 年最后几个交易日收盘后创建的待发单同样拿不到下一时段。见 §1.2 与 D67-12。
- 新年份、临时休市、夜盘时间调整都要改代码、发版、重装；两份日历（时段日历与预期交易日历）分别维护。

### 1.3 缺口

1. 数据在代码里，更新要发版；没有可由运营指定的位置（U67-2）。
2. 只覆盖 2026 年，2027-01-01 起全部 UNKNOWN（§1.1）。
3. 没有版本历史，事后无法知道某个判断用的是哪一版数据；BT 待发单记录也不存 `calendar_ref`（§1.2 第 15 项）。
4. 没有每日流程：公告录入、核对、发布、告警都不存在。
5. 两份日历分叉：时段日历含夜盘与集合竞价，预期日历只有日盘；节假日常量只在后者；两者都不含临时休市。
6. 实时合约状态未使用，紧急停市（台风、熔断、临时停牌）只能靠场所拒单发现。
7. 策略没有查询入口：BT 只在 Broker 内部使用日历（`dm:1648-1655`），SDK 只返回端口对象。
8. 日历只在启动时取一次（`dm:538-540`）；长期运行的进程跨年后不会换数据。

## 2. 目标、非目标与新增规则

### 2.1 目标

1. **数据文件化。** CTP 的交易日、假日、临时休市、节前无夜盘日期、各交易所与品种的时段模板（含夜盘结束时间与集合竞价）写成版本化 JSON 文件，放在 `<calendars 根>/ctp/`（U67-2）；包内带一份种子版本。
2. **位置可配置、三平台一致。** 根目录由 `config.yaml` 指定，路径规则在 Windows 11、Ubuntu、macOS 上相同（§3.3）。
3. **每日更新工具。** 每个交易日收盘后运行：读入人工核对的公告、从 CTP 合约目录取得品种与合约清单、校验、原子发布新版本、保留历史；失败时告警并保留旧版本（§3.6）。
4. **运行时。** 启动时与每次交易日切换时加载最新的有效版本；覆盖之外为 UNKNOWN，休市待发单不创建、不派发（同 I62-04）；时段答案带版本（§3.7）。
5. **实时状态交叉核对。** CTP 合约状态推送投影为中立状态，与日历合成；紧急停市以实时状态为准（§3.8）。
6. **策略查询。** 策略经 SDK 接口（BT 的 Feed/Store 投影）查询时段，不读文件（§3.9）。
7. **验收。** UNIT/FAKE 与 INTEGRATION_SIM 覆盖发布、并发读取、损坏恢复与日切加载；PACKAGE 在三平台分别记录；SimNow 观察一次收盘后发布与跨夜盘日切。

### 2.2 非目标

- 不改迭代 62 的内置 2026 年日历（U67-3）；本迭代交付并经用户验收前，62 的行为不变。
- 不自动抓取或解析网页公告；公告由人工核对后录入（INV67-06）。
- 不改 D62-30、D62-34～36 与 R-3 的派发语义；日历不成为立即派发订单的前置（D62-36：日历与行情不能证明没有临时停牌，场所按实际规则处理）。
- 不实现 Gateway 侧（Gateway 进程读取日历根目录、向策略转发合约状态）：按 U63-4 提交迭代 63（§3.10）。
- 不做 OKX、Binance 的日历（7x24）；数据格式支持 CFFEX、GFEX，但它们的时段模板要另行核对来源后再录入（§6.2 第 7 项）。
- 不做调度器：用操作系统的计划任务；迭代 66 的 runtime 不做定时任务（66 §2.2）。
- 不做回测数据的日历重放；只提供按时点选版本的查询（D67-09）。

### 2.3 本迭代新增规则

| ID | 规则 |
| --- | --- |
| INV67-01 | 场所日历事实只由 provider（`bt_api_ctp`）声明；SDK、BT、Gateway 只读取与投影，不自行推断节假日或时段。 |
| INV67-02 | 运行时只读：策略进程、Gateway、SDK 从不写 `<calendars 根>`；唯一的写者是更新工具，靠单写者锁互斥。 |
| INV67-03 | 发布原子、版本不可变：已发布的版本文件不改写、不覆盖；“当前版本”只经原子替换指针文件切换；读者只会看到完整的旧版本或新版本。 |
| INV67-04 | 失败保留旧版本：任何校验或写入失败都不改变指针；运行中的进程继续使用已加载的版本，并报告失败。 |
| INV67-05 | 未知即未知：覆盖之外、品种无模板、数据不可读、校验失败、实时状态与日历冲突，一律回答 UNKNOWN 并带有限原因码，不推测为开市或休市；UNKNOWN 不创建也不派发休市待发单（I62-04、D62-34）。 |
| INV67-06 | 公告须人工核对：假日、临时休市、交易时间调整只来自人工准备的公告输入（来源 URL、留存原件的 SHA-256、核对人与时间）；工具不从网页发现或解析公告。 |
| INV67-07 | 同一交易日内版本固定：一个进程在一个交易日内只用一个版本；新版本在下一次交易日切换或进程重启时生效；紧急情况只经实时合约状态覆盖（§3.8）。 |
| INV67-08 | 判断可追溯：每个时段答案带含版本号的 `calendar_ref`，BT 的待发单记录与对账报告保存它。 |
| INV67-09 | 策略不读文件：文件格式和路径不是公开 API；策略只用 SDK 的查询接口及其 BT 投影。 |

### 3.2 行业做法与取舍（参考来源见文末，本次未打开原文核对）

- QuantConnect LEAN 用一个 JSON 文件（market-hours database）描述各市场与品种的交易时间：按“证券类型-市场-代码”分条目，可用通配条目作市场缺省；每条有交易所时区、按星期的时段段（盘前、盘中、盘后），以及显式列出的假日、提前收盘、推迟开盘；随数据仓库一起版本化 [R1]。
- exchange_calendars、pandas_market_calendars 用 Python 代码描述规则并按年推导 [R2][R3]——这正是现状，每次变化都要发版。
- 中国期货：国务院办公厅发布次年节假日安排；各交易所发布休市安排与节前夜盘安排通知，夜盘与集合竞价时间以交易所公布的交易时间为准（来源已列于 `ctp: futures_expected_calendar_provider.py:67-123`）。
- 取舍：发布物用 JSON（可比对、可哈希、标准库可读）；数据显式列出，规则只在工具中使用并由校验器复核（D67-03）；版本不可变加指针（支持回滚与时点查询）；人工录入公告（INV67-06）。

### 3.3 位置与配置

```yaml
# config.yaml（策略文件夹；Gateway 账户配置与更新工具使用同一个键）
calendars:
  root: ../calendars        # 相对本文件所在目录；也可写绝对路径
```

- 键名在 67.01 冻结（候选 `calendars.root`）；CTP 子目录固定为 `<root>/ctp/`（U67-2）。
- 路径规则与 `ctp.catalog_cache_dir` 相同（`ex: run.py:160-175`）：相对路径相对 `config.yaml` 所在目录；允许绝对路径；`~` 展开为用户主目录；不展开环境变量；不依赖当前工作目录。Windows 的盘符、UNC 路径、大小写不敏感与超过 260 字符的长路径在 67.01 定处理方式，67.09 在 Windows 11 上实测。
- 根目录建议放在本地磁盘：网络共享盘上的重命名与文件锁语义较弱（§6.1）。同一主机的多个策略可以指向同一个根目录（运行时只读，INV67-02）。
- 未配置时怎么办由用户决定（D67-01）。
- 配置经 Store 的 SDK 选项传入（新增可选项 `trading_calendar`，与 `market_clock_verification` 同一路径，§1.2 第 21 项），再由 SDK 交给 provider 工厂；不使用进程级环境变量（避免同一进程内不同 route 互相影响）。

目录布局：

```text
<calendars 根>/
  ctp/
    CURRENT.json             # 指针：当前版本文件名与 SHA-256（只经原子替换更新）
    manifest.jsonl           # 只追加：版本、发布时间、SHA-256、上一版本、变更摘要、工具运行号
    versions/
      ctp-20261106-001.json  # 已发布版本，不可变
    inbox/                   # 人工准备的公告输入（YAML）；处理后移入 inbox/archive/
    sources/                 # 人工留存的公告原件（PDF/HTML），文件名含 SHA-256
    staging/                 # 工具工作目录；运行时从不读取
    reports/                 # 每次运行的报告与差异（JSON）
    .lock                    # 更新工具的单写者锁
```

包内种子：`bt_api_ctp` 包数据 `data/calendars/ctp/` 下一份 2026 年版本，内容与现有常量等价（67.03 用金标准测试证明），随 wheel 发行，只读。

### 3.5 校验（工具发布前与运行时加载用同一个校验器）

1. 结构：schema 名与版本；未知键拒绝；类型、日期与时间格式；必填字段缺失即拒绝，不补缺省值。
2. 完整性：`content_sha256` 与指针中的 `sha256` 都一致。
3. 引用：每个假日、休市、例外、品种都引用存在的来源；来源有 URL、核对人、核对时间；品种引用的模板存在。
4. 一致性：`trading_days` = 覆盖内工作日 − 假日 − 全天休市；`no_night_session_dates` 与规则一致，不一致处必须是带来源的例外。
5. 无重叠：同一交易日的窗口排序后不重叠、结束晚于开始；相邻交易日不重叠（夜盘结束早于次日集合竞价）；集合竞价紧接其连续交易段。
6. 覆盖：每个交易所的覆盖是连续区间。工具另检查覆盖终点距今的交易日数，不足阈值时照常发布但报告告警（D67-10）。
7. 与上一版本比较（只在工具中）：发布时刻之前的交易日与时段不得改变；确需更正时标 `correction` 并带来源，报告列出（保护时点查询）。

### 3.6 每日更新工具

- **入口**：`bt_api_ctp` 的命令行（候选名 `bt-api-ctp-calendar`，67.01 冻结）。子命令：`status`、`ingest <输入>`、`refresh-products`、`build`、`validate`、`diff`、`publish`、`history`、`verify`。有限退出码：0 已发布；10 无变化；20 校验失败、未发布；30 需要人工核对（新品种、公告缺来源、国务院与交易所不一致）；40 写入失败、未发布；50 锁被占用。
- **时间**：每个交易日收盘后运行一次，建议北京时间 15:30～20:00，在当晚夜盘集合竞价（20:55）之前完成，使下一交易日的版本在日切前就绪；周末和节前另各运行一次。由操作系统计划任务调度（cron 或 systemd timer、launchd、Windows 任务计划程序），67.08 给样例。
- **步骤**：
  1. 取单写者锁（POSIX `flock`、Windows `msvcrt.locking`，在 provider 内实现，不依赖 BT 的 `live_state`）。
  2. 读当前版本。
  3. 读 `inbox/` 中的公告输入：类型、年份、日期段、交易所、品种、来源 URL、标题、发布日、`sources/` 中留存原件的文件名（工具计算 SHA-256）、核对人与时间。交易所的休市通知是假日的直接依据，国务院安排用于交叉核对；二者不一致时退出码 30，不发布（INV67-06）。
  4. 品种与合约清单：读取当日 CTP 合约目录缓存（I62-12 的 `instrument_catalog_cache`，含品种、到期日与 IsTrading），没有缓存时按 D67-07。用途：发现 CTP 上有而模板没有的品种（报告“需核对”，运行时它们仍是 UNKNOWN）、已下市品种、合约最后交易日（供预期日历的合约到期叠加）。CTP 不提供交易时间，时段仍以交易所公布为准。
  5. 可选：读取前一交易日记录的合约状态观察（§3.8），与日历比对，不一致项写入报告供人工核对，不自动修改日历。
  6. 在 `staging/` 生成新版本，用运行时的同一加载器与校验器加载。
  7. 与当前版本比较：无变化只写报告，退出码 10。
  8. 发布：版本文件写入并 fsync 后，以 `os.replace` 移入 `versions/`（同名已存在即失败，INV67-03），fsync 目录；再用临时文件加 `os.replace` 替换 `CURRENT.json` 并 fsync；追加 `manifest.jsonl`。
  9. 已处理的输入移入 `inbox/archive/`，写报告，释放锁。
- **失败**：任何一步失败都不改指针（INV67-04），写报告和日志，用非零退出码让计划任务告警（D67-13）；`staging/` 的残留在下次运行时清理。
- **边界**：工具不访问网页、不读凭据文件内容。需要自己做 CTP 只读查询时（D67-07 b），凭据按示例的方式传入（环境变量或 `--env-file` 路径），并需用户授权。

### 3.7 运行时加载与版本固定

- provider 的时段日历与预期日历改为读同一份已加载数据（`expected_trading_days` 不再用常量，`ctp: futures_expected_calendar_provider.py:198-215`），消除两份日历分叉。
- 加载：读指针 → 读版本文件 → 校验 → 建内存索引；记录加载状态（版本、`calendar_ref`、来源、覆盖、加载时刻）。
- 启动时指针损坏或版本无效（D67-06）：推荐取 `versions/` 中最新的有效版本并报告 `calendar_pointer_invalid`；没有有效版本时全部回答 UNKNOWN（`calendar_unavailable`）。配置了根目录时不退回包内种子，避免悄悄用旧数据。
- 版本固定（INV67-07）：交易日切换时重读指针。SDK 在日历自身判定的交易日变化后的第一次查询时检查（不依赖 BT，Gateway 与工具进程同样适用）；BT 在 R-3 日切完成时（`dm:3031` `_direct_complete_day_switch`）再请求一次；两者幂等（D67-05）。重读失败时继续用已加载版本，报告 `calendar_reload_failed`（INV67-04）。
- 答案：`TradingSessionState.calendar_ref` 改为带版本的引用；原因码沿用 `calendar_coverage_unavailable`、`product_session_unknown`，新增 `calendar_unavailable`、`venue_status_halt:<状态>`、`calendar_venue_conflict`（§3.8）。
- BT：待发单记录的 `target_session` 增加 `calendar_ref`（`dm:2372-2376`）；`get_direct_reconcile_report()` 增加日历状态（版本、来源、覆盖终点、陈旧标记、最近一次重读结果）；派发语义不变（`dm:1616-1621`、`:2541-2561`）。
- 时点查询（D67-09）：SDK 提供按时点选版本的只读查询（`published_at_utc` 不晚于给定时刻的最新版本），供回测复核与事后审计；实时路径永远用当前交易日已固定的版本。

### 3.8 与 CTP 实时合约状态交叉核对

- **投影（bt_api_ctp）**：把 `OnRtnInstrumentStatus` 的 InstrumentStatus（§1.2 第 19 项）映射为 base 的中立枚举；扩充安全字段，读取 EnterTime、EnterReason（自动、手动、熔断）与 TradingSegmentSN；附接收时刻、会话代际与交易日。状态的粒度（合约、品种还是交易所）、登录时是否推送当前状态、QUICK 模式下能否收到，都在 67.01 用 SimNow 捕获确认（需授权）；确认前只对字段完全匹配的合约或品种生效。
- **合成（SDK，中立；D67-08 推荐 a）**：

| 日历 | 实时状态（当前会话代际、当前交易日、未过期） | 结果 |
| --- | --- | --- |
| CONTINUOUS 或 AUCTION | NoTrading、Closed，或进入原因为熔断 | UNKNOWN `venue_status_halt:<状态>`：待发单不派发，目标时段结束时照常过期——**紧急情况以实时状态为准** |
| CLOSED | Continous 或集合竞价类状态 | UNKNOWN `calendar_venue_conflict`：不派发，告警，进入次日工具报告，由人工核对日历 |
| UNKNOWN | 任意 | 仍为 UNKNOWN：实时状态不能补出日历没有的时段 |
| 任意 | 与日历一致，或没有状态 | 以日历为准；没有状态不等于开市或休市（D62-36） |

- 立即派发的订单不受影响：`_direct_route` 在 UNKNOWN 时不转为待发，仍按行情资格派发、由场所处理（`dm:1616-1621`）；本迭代不改。
- 观察记录：provider 可把每个交易日的状态观察写入一个只追加文件，供次日工具比对（§3.6 第 5 步）；写入位置不在 `<calendars 根>` 内（INV67-02），67.01 决定（候选：合约目录缓存的同级目录）。
- Gateway 模式下策略进程没有本地 CTP 交易会话，状态须由 Gateway 转发（迭代 63，§3.10）；转发实现之前只用日历。

### 3.9 策略怎样查询

- **SDK 公开只读接口**（名称 67.01 冻结）：`BtApi.trading_session_state(exchange_name, instrument_id, at_utc=None)`、`trading_windows(exchange_name, instrument_id, start_utc, end_utc)`、`trading_calendar_status(exchange_name)`；返回 base 的中立类型。现有的 `trading_session_schedule(exchange_name)` 保留不变（`SDK: bt_api.py:4293-4305`）。
- **BT 投影**（D67-11 推荐 a）：`BtApiFeed.trading_session(at=None)` 与 `trading_windows(start, end)`，与现有 `trade_qualification()`（`BT: backtrader/feeds/btapifeed.py:932`）同一风格，委托 Store → SDK；Store 提供 `trading_calendar_status()`。策略写 `self.data0.trading_session()`。
- 不向策略提供文件路径或内容（INV67-09）。没有 SDK 会话时（例如普通回测）这些方法返回明确的不可用结果，不读包内种子冒充。

**Monitor 时段消费者（D68-10，用户已决定）**：迭代 68 的行情中断告警只累计可证明的连续交易时段，跨休市段累计，集合竞价不计，按交易所与品种分别统计，同品种多个合约合并展示。67 已规划本地文件化日历与 SDK 中立查询，67.01 与 63/68 冻结消费者所需范围、时间区间、交易日/时区、coverage、来源、版本与更正/重启语义；63 §3.22 提供 Gateway 对应配置和观察接线。数据缺失或无法证明时返回 UNKNOWN，不能根据固定窗口或单个会话/结算事件构造有效时段。68 对该项用替身可先推进，真实时段告警须对应接口与真实组件联调，不要求等待迭代 67 整体验收；不据此声称文件日历或未来年份已交付。

### 6.2 未决问题（UNKNOWN）

1. 2027 年国务院节假日安排与各交易所休市安排的发布时间。
2. CTP 合约状态推送的粒度、登录时是否推送当前状态、QUICK 模式下能否收到（62 计划:296）。

5. Windows 上 `os.replace` 与杀毒软件、同步盘目录的交互。
6. 版本文件大小与加载耗时（41 个品种、一年数据，67.03 实测）。
7. CFFEX、GFEX 时段模板的来源核对（现有时段日历未收录这两个交易所）。
