## 1. 目标、边界和使用场景

1. CTP 日历由配置指定 `<calendars.root>/ctp/`，包含可版本化的交易日和品种时段数据；更新工具每天晚上自动采集和检查一次，内容无变化仅记录检查、不生成新版本，内容变化按 D67-23 配置自动发布或人工确认后发布。
2. 策略、Gateway 和 SDK 只读；更新工具是日历目录唯一写者，可获取 AKShare 数据并使用明确标识的 mock。CTP 合约目录仅用于识别线索，不证明交易时间；交易所网页解析及 Opendata 真实采集对接留待后续。
3. 运行时提供有版本和覆盖范围的查询。日历是**预期安排**，不证明交易所实际交易日、订单可成交、账户结算、授权、时钟或可平容量。
4. 按 D62-36，日历 UNKNOWN 时不创建或派发**休市待发单**；立即单继续按既有行情资格和场所处理，不在本迭代改为因日历 UNKNOWN 一律拒单。实时状态合成的范围与其对立即单的影响也不得被误称为全局急停。
5. 开发过程中编写并运行发布、并发读取、恢复、跨日切换、安装及平台适配的相应用例；整体功能验收在合并 `dev` 后另行组织。替身、源码存在或历史运行不替代真实组件和账户证据。

### 1.1 系统关系和职责

```text
CTP 数据适配 / 校验：可用 AKShare + 明确标识的 mock + 可选合约目录缓存
            │
SDK 更新入口：差异报告 → 自动发布 / 人工确认 → SDK 版本仓发布 → CURRENT / 不可变版本
                                                        │ 只读
                      SDK 版本仓校验、版本绑定与装配 ←───┘
                              │ 注入中立只读数据或端口
                      CTP provider 场所语义与窗口计算
                              │
                SDK 中立查询 / 状态合成 ↔ Gateway（迭代 63）
                              │                  配置、日切、观察转发
                       BT Store / Feed / Broker
                              │
                          策略 / 65 / 68
```

## 2. 配置、数据和查询合同

### 2.1 配置和目录

候选键 `calendars.root` 在各自读取的 `config.yaml` 中解析：相对配置文件所在目录，支持绝对路径和 `~`，不展开环境变量、不依赖进程当前工作目录。Gateway 仅保存和使用自己的服务器侧路径，不向客户端公开；客户端自己的路径不等于服务器路径。不同策略/账户是否指向同一目录须由运营显式配置。Windows 盘符、UNC、长路径、大小写和符号链接按平台能力明确测试；网络共享盘、同步盘不得凭本地磁盘测试宣称支持。

哈希需区分：`content_sha256` 计算规范化 JSON 且排除自身字段；版本文件字节摘要计算完整实际字节；发布记录与 CURRENT 引用的是哪个摘要必须逐字段声明。规范化编码、数字和 Unicode 规则、允许的最大文件/条目数量、路径穿越及重复 JSON 键处理由 67.01 冻结，未知 schema 和不合法输入拒绝。哈希只能检测内容不一致，不能证明作者、公告真伪或写入方身份。

## 3. 发布、恢复和时点查询（建议修订 D67-06/09）

### 3.1 提交点

建议以**原子替换 `CURRENT`** 作为唯一可见性提交点。一个发布操作具有稳定 `publication_id`、单调序号、前序已提交发布引用、目标版本和字节摘要；回滚是指向旧内容的新发布事件，不能倒退或删除历史。不可变内容与不可变发布记录先写完整、校验并按平台支持能力持久化，只有随后 CURRENT 指向该发布记录，才构成可见发布。预写的版本或记录可能是孤儿，不能单独被当成已发布。`manifest.jsonl` 若保留，只能是可重建的诊断索引，不得单独作为提交真值；发布记录链的校验、截断及权限边界须在 67.01 冻结。

| 时点 | 操作结果 | 恢复和重试 |
| --- | --- | --- |
| 替换 CURRENT 前已确定失败 | `NOT_COMMITTED`；原指针不变 | 保留或安全清理孤儿；同一操作 ID 可幂等重试 |
| 替换成功且读回匹配 | 可见性 `COMMITTED`，返回发布 ID/版本；持久性另计 | 归档、报告或索引失败标 `POST_COMMIT_INCOMPLETE`；补做后处理，不再生成第二次发布。读回不证明断电后持久 |
| 替换结果或持久性无法确认 | `COMMIT_UNKNOWN` | 在同一锁和同一发布 ID 下读回验证；若无法证明，停止自动重试，明确报告待核；不得声称未发布或盲目另建发布 |

可见性与持久性是两维状态：`COMMITTED` 只证明调用者在当前运行中读回了已切换指针；持久性另报 `CONFIRMED_FOR_DECLARED_FAILURE_MODEL`、`UNCONFIRMED` 或 `FAILED`，只可在对应平台和故障模型有证据时确认。无法判定替换是否发生时，可见性为 `COMMIT_UNKNOWN`；能够读回当前指针只澄清当下可见性，不自动证明断电持久或已经过覆盖的历史。不得把 `COMMITTED` 简写为所有失败模型均已持久。

读者只从一次读取的指针及其引用加载和校验完整快照；读取期间指针变化不拼接新旧记录。版本同名不可覆盖：使用真正的排他创建/无替换机制，不能用会覆盖目标的 `os.replace` 模拟“同名失败”。测试发布前后中断、读回异常、重复执行、并发写者、部分记录和报告/归档失败。

### 3.2 持久性与跨平台

`os.replace` 的 Python 文档将成功重命名的原子性表述为 POSIX 要求，且目标存在时会替换；不能把这一表述直接扩大为 Windows 或网络文件系统的已验收保证。文件 flush/fsync、目录元数据持久化、Windows 文件占用及断电语义须分别设计并在目标平台取证；不支持或未取证的保证标 GAP。进程级故障注入能验证进程崩溃路径，**不能证明断电持久性**。参考 [Python os.replace 文档](https://docs.python.org/3.13/library/os.html#os.replace)、[Python os.fsync 文档](https://docs.python.org/3.13/library/os.html#os.fsync)和 [Microsoft 文件移动与替换文档](https://learn.microsoft.com/en-us/windows/win32/fileio/moving-and-replacing-files)。

### 3.3 指针损坏和历史时点

**D67-06（2026-11-11，用户已决定 A）**：启动时指针损坏或版本无效，只有能证明版本已发布、内容完整且是应恢复的版本时，才自动恢复并告警；不能证明时返回 UNKNOWN、报告并由运营处理。不静默回退包内种子。原“取 versions 中最新有效文件”可能误选 CURRENT 切换前的孤儿或旧回滚内容；单凭目录、文件名、mtime、有效 JSON 或预写发布时间均不是提交证明。CURRENT 完全丢失时，候选独立提交回执或可信检查点可证明其明确覆盖的历史发布，但未必包含最后一次发布；不能将较旧检查点当作最新版本自动恢复，无法证明最新状态即 UNKNOWN。回执本身依赖受信写者和受保护存储，哈希不是身份认证；具体证明、恢复权威与故障处理在 67.01 冻结。

**D67-09（2026-11-11，用户已决定 A）**：保留全部历史日历版本并提供按时点查询已发布版本；每日例行检查无日历内容变化时不生成新版本，抓取时间、检查时间和运行号单独记录。能够查询某时刻的已发布版本不等于知道某进程实际使用了哪版；后者须读取该进程的绑定记录。有效覆盖、交易日/时段及来源依据的实质变化须报告并按 D67-23 配置处理，具体比较字段在 67.01 冻结。

时点查询建议顺着已提交发布链查询，不扫描候选文件；同一内容的多次发布/回滚是不同事件，按发布序号消歧。预写 `published_at_utc` 早于指针切换，不能冒充精确可见时间。建议分别存储：预写不可变发布记录记录切换前 UTC 下界，切换后另写不可变回执，绑定发布 ID、记录摘要、读回结果及切换后 UTC 上界。回执在切换成功且读回后创建，不回写预写记录；时点查询同时核验指针/链、回执和来源。此方案假设发布者及其时钟可信、UTC 在区间内不回拨；校验不能证明绝对时钟正确。时点落在无法确定的区间、发布后崩溃导致上界或回执缺失、时钟倒拨或历史链不完整时，返回 `HISTORY_UNCERTAIN`，而不是猜版本。后续恢复不能伪造事发时刻；具体时间可信性、单调时钟跨进程限制、回执持久性和可否补证在 67.01 冻结。

## 4. 版本绑定与日切（D67-05 已决定 B）

**用户决定 B（2026-11-11）**：每天晚上采集更新；变化按 D67-23 所配置模式发布后，持续运行的进程在下一次可信交易日切换时加载新版本。同一交易日进程重启时，可重新加载当时已发布的最新有效版本；尚未发布的候选不能作为已发布版本加载。

建议绑定作用域至少为 `(SDK 实例, route, 来源会话代际, 可信交易日)`，并记录 `calendar_ref`、内容摘要、绑定时间和原因。一次运行中同一绑定不因后台发布而换版；进程重启可以重新绑定，所以不能声称整个账户或所有策略同日必然同版。Gateway 与策略需比较版本及覆盖；不一致或信息不全时，相关待发/扩展按已有合同保持不可证明，不能以其中一方版本代替另一方。

把“探测候选版本”和“激活交易日绑定”分开：

1. SDK 可有界读取和校验 CURRENT 作为候选；探测不修改当前绑定、不建立账户日切或写入许可。
2. 激活应以 provider/会话来源绑定的可信日切事件或 BT R-3/Gateway 既有可信生命周期为触发，并检查 route、来源代际、交易日及顺序；SDK 独立只读场景通过显式中立通知或只读查询候选，不靠旧日历宣布账户日切。实际事件格式和签发方与 63 在 67.01 联合冻结。
3. 同一事件重复幂等；旧代际、倒退交易日、并发查询及重连竞态不得把新绑定覆盖回旧绑定。加载失败保留当前完整快照并报告；旧版覆盖之外仍 UNKNOWN。
4. 即便旧版覆盖截止、无法从其推导下一交易日，新版仍可被探测；没有可信日切时不得激活为账户当前交易日。日历自身的预期交易日与场所事实不一致时，须报告不一致，不能由日历完成今转昨或解除 UNKNOWN。

**D67-15（2026-11-11，用户已决定 A）**：待发单保存创建时的 `calendar_ref` 和原目标以供审计；版本实际切换后，对已创建但尚未发送的休市待发单重新核验原目标。若无法确认原目标仍有效，暂停派发并以既有通知/状态报告提示，不自动改期、延长期限或改变订单身份。恢复证据后，仅当原目标仍有效且其他原有准入条件满足时继续按原目标处理；能可信证明原目标已结束且订单未发送时，按 D62-30 结束并通知。若无法证明原目标是否结束，不只凭旧截止时间擅自终结；发送与否不明时按原身份核验，不重复发送。已发送或已受理订单按真实订单和恢复合同管理。

实时状态按 D67-08 B 决定当前合成状态；实时连续交易本身不证明原计划目标仍有效，也不改变原目标。旧记录缺 `calendar_ref` 时，不得捏造创建版本；需要的历史证据、通知去重、状态持久化与恢复方式在 67.01 对齐 62/63 并冻结。外部邮件是否启用仍由 D67-13a 的通知程序显式配置，本决定不自动发邮件。以上是目标合同，当前实现及行为验收均待完成。

## 5. 实时状态合成（D67-08 已决定 B）

provider 原始状态 `0`～`7` 的具体含义、粒度、推送范围和时效需经公开协议与获授权观察核实；未经验证的映射标 UNKNOWN，不猜测品种或交易所范围。观察至少绑定 route、原生明确的合约/范围、会话代际、可信交易日、接收时刻、时钟可信条件、来源和顺序/序号（可证明时）。订阅断连、乱序、旧交易日、旧代际、超时、范围不明、未知枚举或无法证明新鲜度时，不作为扩大可交易范围的依据。

**用户决定 B（2026-11-11）**：日历可能过时；当有效且匹配当前合约、会话及交易日的实时状态与已知日历冲突时，当前状态以实时观察为准。日历显示可交易而实时显示停市时，按实时状态暂停相应待发单；日历显示休市而实时显示连续交易时，按实时状态进入待发单的既有资格检查，并记录和告警冲突。实时竞价不等于连续交易；不因为状态冲突自动延长订单期限、改写原目标、跳过其他检查或证明订单必然成交。原日历和实时观察分别保留，不自动改写已发布日历；采集变化仍按 D67-23 所配置模式发布。

确实未收到任何观察时，计划状态仍可用于 D62 既有日历行为，但必须报告“无可用观察”，不得称为现场已证明交易。对于已收到但失效、旧代际、未知枚举或范围不明的观察，不能笼统当成“从未收到”：若能证明与查询范围无关，忽略并记录诊断；特定已失效暂停观察按 D67-16 处理，其余相关或关联范围不能判清的情形及恢复条件在 67.01 冻结，未经验证的观察本身不能用于放宽。用户认为交易所日历正常覆盖时无需另设“日历 UNKNOWN 但实时状态有效”的业务场景；若实际发生覆盖缺失、数据损坏或读取失败，继续按既有 UNKNOWN 合同处理，不用实时观察补造未来窗口，也不由此修改 D62-36 的立即单行为。竞价与连续状态不一致、BeforeTrading、NoTrading、AuctionOrdering/Balance/Match、Closed、TransactionProcessing、未知状态、熔断原因逐项建表；该表须在 67.01 冻结，不以此草案代替实际 CTP 行为验收。

**D67-16（2026-11-11，用户已决定 A）**：曾收到可信暂停状态，之后状态来源断开且该观察经证明失效；当基础会话与回报恢复等既有条件已经满足、日历显示连续交易、尚无新有效状态时，旧状态不再充当当前事实。待发单可按日历进入既有资格检查，并报告缺少有效实时状态；原目标和行情、授权等条件仍不可跳过。基础连接或恢复证据不足不能发送，新有效状态按 D67-08 B；这也不证明场所当前一定交易。状态可能只在变化时推送，不能单凭长时间没有新推送判失效。具体有效性、代际与恢复证据待核实，本决定不预决所有其他无效状态情形，也不改变立即单规则。

Gateway 的状态由 63 按认证和授权作用域转发，必须带来源、范围、交易日、代际、接收时间、完整性和版本；不能把一次有状态的观察延伸至全部合约，也不能将服务器路径或凭据发给策略。63 [实施合同补充 §7](../迭代63-Gateway统一转发与多策略共享会话/实施合同补充.md)的“冲突不得扩大可交易范围/仅收紧”与新决定 B 不一致，需由 63 负责人对齐并同步合同、联合测试；完成前 Gateway 相关扩展记 GAP。

## 6. 兼容、迁移和回滚

迭代 62 的现有内置 2026 及旧默认行为保持至合并 `dev` 后整体验收通过且具备明确启用条件：必须设计显式新旧选择及默认值，不能仅因合并或安装新版 wheel 自动切换到文件方案。D67-01 已决定配置缺失处理和显式使用包内种子；组件间兼容测试覆盖旧 SDK/新 provider、新 SDK/旧 provider、direct/Gateway 及缺少新能力，不能静默冒充成功。67.08 相应更新 007 示例，67.04/67.09 编写缺失、显式路径、显式种子及报告的测试。

67.03 比较原算法和文件数据的交易日、phase、窗口与边界；新版 `calendar_ref` 是刻意变化，单独核对，不要求对象字节完全相同。旧算法等价不等于符合交易所规则：日盘竞价条件与上期能源交易细则可能存在差异，须核对生效日期、适用品种与实现，差异未核实时标 GAP，不用等价测试掩盖。旧 `live_state` 可能没有版本字段：用真实旧格式 fixture 验证读取、恢复、缺版本报告、回滚及待发单安全处理；迁移后旧程序能否读取、不可逆变更和回退步骤必须明确，不以重建空状态代替迁移。根目录与业务账本分离；版本回滚只能恢复预期日历，不得回滚真实订单、账户日切或持仓事实。

**D67-17（2026-11-11，用户已决定 A）**：旧待发记录支持受控迁移，不要求先等待全部订单结束。迁移保留原订单身份、参数、原目标和有效期；无法证明创建时的 `calendar_ref` 则标记未知，按 D67-15 核验，不用当前日历冒充历史版本。迁移前保留可核验备份，迁移中断须能安全恢复，不遗漏或重复发送；真实旧格式 fixture 覆盖解析与重启。回退前须验证旧程序能安全读取**当前最新状态**；不得以升级前备份覆盖升级后发生的订单、成交或账户事实，无法安全回退时保留新版本并人工处理。现有启动、账户对账和写入准入不因迁移放宽；备份存储、迁移提交与崩溃恢复的具体方法在 67.01 冻结，旧程序可读与否须实测，尚无验收证据。
