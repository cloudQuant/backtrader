# 迭代45-46优化

版本：**v0.2，运行时统一float64**；日期：**2026-10-22**。状态：**计划已建立，优化实施尚未开始，正式验收项全部 NOT_RUN**。

本计划针对迭代45的原生因子研究链路、迭代46的 Alpha101 native 算子，以及 fincore 因子报告链路进行性能优化。用户当前的主要场景是运行025、026、027的 `run.py`，约500只股票，并开启 `--report`。本次仅形成计划、保留诊断证据；不包含生产代码、测试实现或依赖安装变更。

**2026-10-22数值决策：用户明确只需与Backtrader一致的float。后续生产因子算子统一使用Python float / NumPy float64，移除滚动相关/协方差运行时的Fraction和120位Decimal，不增加高精度运行模式或选择开关。高精度可保留在独立测试参考中。当前生产算子尚未修改。**

## 1. 目标与归属

在统一float64数值策略和既有公式、接口合同下，缩短“读取数据 → 原生因子计算及采集 → ResearchDataset封存 → 报告 → 研究评价/导出”的等待时间，降低重复计算、临时对象和不必要的内存峰值，并提供明确的阶段进度。

| 责任仓库 | 本轮优化范围 | 主要位置 |
|---|---|---|
| Backtrader | 输入可用性采集、数据集校验与封存、内容哈希、原生滚动算子、报告取数适配、示例阶段日志 | `backtrader/research/`、`examples/backtest/025_factor_single/`、`026_factor_multi/`、`027_alpha003_panel_acceptance/` |
| fincore | 因子分析中的权重/收益/持仓复用、分组计算、报告模型按需装配，以及基线恢复后实证发现的研究评价热点 | `fincore/factor_analysis/`、`fincore/report/factor/` |

Backtrader负责公式计算、原生调度与原始面板采集；标签、IC、组合分析和报告数学继续归属fincore。允许在两个仓库分别实施优化，不在Backtrader复制fincore统计算法。

本计划是45/46已交付能力的后续优化，不覆盖或重写历史验收结论，也不占用迭代47/48的build实现。公式、窗口、PIT和生命周期约束继续引用[四迭代路线与对齐合同](../迭代45-Indicator因子研究与多因子合成/四迭代路线与对齐合同.md)、[迭代45计划](../迭代45-Indicator因子研究与多因子合成/迭代计划.md)、[迭代46计划](../迭代46-Alpha101原生因子实现/迭代计划.md)。其中要求生产运行时保留Fraction/120位Decimal、与旧实现逐位一致的条款，由本次用户确认的float64策略替代；实施数值迁移时同步相关profile、指南、45–48数值条款和测试，不以历史高精度条款阻止迁移。

### 2.2 已确认的热点

1. **快照构建昂贵。** 025/026中，ResearchDataset构建约占原生采集时间的69%/73%。availability校验逐行`iterrows()`，再逐格`.at`读取原始值；窗口输入时间戳逐条规范化并转成字符串；字段表还有逐行校验与防御性复制。
2. **未保存也执行完整内容序列化。** `compute_dataset_id()`调用`_payloads_and_descriptors()`，编码全部表、计算摘要并暂存payload。仅计算ID时这些payload随后丢弃；以后显式保存还可能重新编码。
3. **输入窗口被重复扫描。** `_classify_output()`按字段调用`input_availability()`，后者每次扫描全部字段；`_input_times()`再次扫描同一窗口。026的20只样本有14,580个因子单元、38,709次`input_availability()`调用。
4. **报告分析重复构建中间结果。** 20只样本中，025/027每份报告调用11次`factor_weights()`、4次`factor_positions()`；026三份合计33次、12次。`analyze_factor()`占报告剖析累计时间约91%–95%。同参数权重在收益、累计收益、持仓和组合输入路径中存在复用机会，分组后的`.loc`赋值也是热点。不同参数的调用不能一概合并。
5. **Alpha003滚动相关成本高。** 每个窗口重新构造Fraction、重算精确矩，再做120位Decimal开方。20只样本中，相关算子的`_evaluate()`累计约4.65秒，Cerebro累计约9.30秒；该比例来自剖析，不能当作普通运行绝对耗时。
6. **runonce没有自动消除Python逐bar循环。** 只实现`next()`的节点通过`once_via_next()`逐bar执行；027 quick入口固定使用`runonce=False`。目前没有runonce/runnext速度对照证据。
7. **缺少阶段可见性。** 示例在较长的采集、封存、报告期间缺少进度和分阶段耗时，用户难以判断程序正在哪一步。

当前数据类型本身已经与Backtrader一致：LineBuffer使用`array('d')`，ResearchDataset原始因子和价格表使用`float64`；高精度对象只存在于相关/协方差内部计算。上面的剖析属于旧数值实现，不能作为float64改造后的速度或误差证据。

## 3. 必须保持的合同

1. **结果与可用性。** 完整时间/资产/因子索引、窗口H、PIT/formula-universe、缺bar/缺字段和未来扰动合同保持不变。除独立记录的数值迁移差异外，NaN/finite mask、reason、ready/valid及首个有效时点保持既有合同。不得通过删行、缩短窗口、填0、减字段或跳过校验获得加速。
2. **数值语义。** 运行时统一float64，移除相关/协方差的Fraction/Decimal路径。Pearson相关、总体协方差`ddof=0`、完整窗口及常量输入/数学域错误的NaN+DOMAIN_ERROR规则保留。采用稳定的浮点算法，例如中心化、缩放、`math.fsum`和`math.sqrt`；避免直接以两个巨大且接近的原始矩相减。允许与旧高精度结果存在正常舍入差异，不要求逐位一致；rank仍按实际float64精确相等分组，不引入epsilon强行还原旧并列。独立float64参考的数值门槛在实施前冻结；高精度参考用于诊断误差，不强制生产复现其每一位。
3. **生命周期。** Cerebro仍是唯一推进者，保留owner注册、原生子指标、clock、minperiod和runonce/runnext行为；不引入第二套面板调度或手动重复调用`next()`。缓存必须按实例/研究运行隔离。
4. **快照及身份。** 保持公开不可变性、防御性复制、存储schema、规范编码与内容哈希合同。同一内容和同一元数据的固定fixture应保持dataset ID和规范序列化字节；实现摘要合法变化造成的ID差异按ALN-08说明，不要求跨实现提交的ID无条件相等。输入值、来源或PIT元数据改变必须继续改变身份。
5. **fincore统计。** 保持NaN、零权重、退化分组、标签期、组中性、等权/因子权重、重叠持有期、索引/列顺序、公开返回模型及`result_fingerprint`合同。不合并参数、样本池或数据身份不同的计算，不跨运行保留可变全局缓存。
6. **可见结果。** 默认股票数、日期、因子、评价期和报告内容保持现有配置。正式前后配对使用相同输出范围；纯HTML试验与完整评价/图表试验分别标识。

数值迁移须单独记录新旧连续值误差、近并列导致的rank/分支变化，以及受影响的mask/reason。新实现分别对独立float64参考验收，再与旧高精度结果做差异说明；不能只把旧断言改成新输出。旧`alpha101-v1`包含高精度实现合同，本计划将新的float64策略登记为`alpha101-v2`，实施时统一切换生产默认值和来源元数据，只保留一个float64生产路径，不增加精度开关。已保存的旧快照继续按原身份读取，不自动改写。输入、实际因子值或实现身份改变后dataset ID及下游报告指纹可能随之变化，不伪造旧ID；对内容完全相同的快照，编码/身份合同仍须保持。

## 6. 性能测量与候选目标

### 6.1 场景矩阵

| 层次 | 规模 / 配置 | 用途 |
|---|---|---|
| 小样本诊断 | 20/50只、完整243日网格，025/026/027；报告开/关分别记录 | 定位具体函数和验证单个工作包，不代替500只退出门 |
| 用户主场景 | 500只、完整243日、默认因子与1/5/20评价期、`--report`；025/026原有默认模式，027原有runnext模式 | 本迭代主要端到端性能验收 |
| 语义对照 | 同一冻结合成fixture的runonce/runnext、资产重排、未来扰动、缺bar和PIT边界 | 证明优化没有改变结果和生命周期 |
| 保存/离线 | 同一数据集显式保存、加载、离线复评 | 验证封存/编码优化没有转移成本或破坏身份 |
| 安装集成 | 仓外安装精确版本的BT/fincore产物后运行既有研究集成入口 | 验证实际导入来源与公开API，不以editable测试替代 |

500只样本固定资产清单、manifest/日历及输入文件摘要。前后配对不得重新抽样、删掉慢资产、更换评价期或减少输出；登记有效值/缺失原因计数，避免全NaN或退化分析造成虚假加速。浮点迁移单列精度策略及输出差异；快照/fincore工作包另用相同输入表配对，区分算法复用收益与输入数值改变的影响。

### 6.2 记录方法

- 同一台机器、相同解释器与依赖、串行测量；记录系统、CPU、内存及会影响结果的后台负载。前后使用相同I/O与文件缓存口径。
- 基线和候选分别用新进程；先预热，再交替顺序进行至少3组配对普通计时，保存原始轮次、median和范围。波动明显时先定位噪声再扩展轮次，不能只选最快一次。
- 分开记录导入、读取、对齐/装配、Cerebro、feed表收集、ResearchDataset校验、内容编码/哈希、CSV、每因子HTML、研究评价、评价图表导出、完整进程wall及CPU。
- 测量进程树峰值RSS，并记录封存临时编码量、报告数量及文件大小。父子阶段的累计时间不能重复相加，CPU百分比注明核数口径。
- cProfile用于归因，普通计时用于性能判断；性能测试串行运行，不与xdist、coverage追踪或其他重型基准混跑。
- 每次记录代码/配置/输入哈希、两仓提交、依赖版本、模块`__file__`、是否dirty、命令、输出目录和失败原因。正式对比绑定干净提交或明确冻结的源文件集合。

## 9. 开发记录与风险处理

后续在本目录新增`开发与验收记录.md`和`验收结果.md`，每轮记录范围、两仓提交、命令、输入/源摘要、正确性与性能结果、失败定位、下一步。若采用与本初稿不同的算法或指标门槛，先在对应轮次说明依据。

主要风险及处理：

- **缓存旧状态或误合并配置：** 采用分析调用/实例局部缓存，明确身份和失效规则，用改变bindings、period、PIT时刻及输入值的反例验证。
- **浮点舍入或增量漂移改变近并列排序：** 优先稳定的中心化/缩放浮点算法，再评估增量化；对独立float64参考验证rank和离散分支，另列旧高精度差异，不用epsilon或保留生产Decimal来强行匹配历史逐位结果。
- **序列化优化破坏历史兼容：** 优先保留schema及规范字节；确有格式变更需求时单独版本化、设计迁移和验收，不夹带进提速小批。
- **只把成本移到另一阶段：** 同时检查封存、保存、报告和端到端wall/RSS；不以局部更快替代整体结果。
- **当前环境与历史验收版本不一致：** R0记录实际导入与能力，恢复明确配套产物后补测，不凭历史文档推定当前模块存在。
- **基线噪声或样本差异：** 固定资产和有效性计数、配对串行采样，必要时扩展轮次；差异来源未解释时保持GAP。

fincore可复用`benchmarks/bench_factor_analysis.py`等现有设施并增加报告/持仓场景；保留其已有基准治理，不以本计划覆盖全仓历史性能门槛。初稿核对期间fincore HEAD已从诊断时的`7679c71a…`更新到所观察的`68162a814dec665aefd2b5ebb51d4ea4093e6df5`，正式实施仍需重核版本、目标源码及环境，不把归档诊断直接套作新HEAD的基线。
