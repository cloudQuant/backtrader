# 分析：迭代 62 中“行情连续无缺口”的界定（供用户决策）

- 日期：2026-11-06。作者：实施者（Claude，分析子任务）。用户原话：“行情连续无缺口这个是怎么界定的？因为正常情况下，k线行情有可能是可以变化的”；“感觉这个连续性的定义可能有点问题”。
- 性质：**只做分析，不改代码，也不改计划**。文中的“建议”都等用户决定；凡涉及已确认决定（D62-xx）的，以“计划修改建议”的形式提出。
- 证据等级：源码阅读为 **STATIC**；现场事实引自 [SimNow 实测记录](SimNow实测记录-2026-11-05.md)（SIMNOW）和 [OKX/Binance demo 记录](OKX-Binance-demo实测记录-2026-11-05.md)（DEMO）。本文没有运行测试，没有连接任何环境，不证明真实账户或生产能力。
- 代码基准：backtrader `74c48c7e3`，SDK `e063e561`，bt_api_ctp `9d1f13a`，bt_api_okx `6bd5958`，bt_api_binance `f9bfe34`。
- 路径缩写：`CTP:` = `bt_api_py/bt_api/bt_api_ctp/src/bt_api_ctp/`；`OKX:`、`BN:`、`BASE:` 分别对应 `bt_api_okx`、`bt_api_binance`、`bt_api_base` 的同一结构；`SDK:` = `bt_api_py/bt_api_py/`；`BT:` = `backtrader/backtrader/`；`EX:` = `backtrader/examples/live/007_ctp/`。

## 0. 结论摘要

1. 用户的怀疑成立。CTP 路径上的“连续性”完全由成交量核算推出：只有“累计量→增量”的换算完整且为 CONTINUOUS 时，`continuity_status` 才是 `continuous`（`CTP:containers/ctp/ctp_ticker.py:228-241`）。它既不度量消息是否丢失（CTP 行情没有序号），也不度量价格是否新鲜。
2. 这一个字段同时决定三件事：SDK 是否允许用它下单（`SDK:clock_verification.py:386`），BT Feed 处于 LIVE 还是 DELAYED（`BT:feeds/btapifeed.py:2397-2416`），以及 bar 能否进入数据线（`BT:feeds/btapifeed.py:2133,2259`）。结果是，“首笔 tick 没有上一笔可减”这样一个纯记账问题，变成了“行情非实时、拒单、K 线少一根”。
3. 应该把它拆成五个互相独立的维度：价格新鲜度、消息/连接连续性、成交量核算完整性、bar 构建与修订、交易时段。参与下单门禁的只应是新鲜度、消息/连接连续性、报价有效性和交易时段；成交量核算和 bar 修订只用来标注 bar 和诊断。
4. 另有三项风险与本问题强相关，但不属于“定义”本身（都是 STATIC 推断，未实测）：涨跌停导致单边盘口时，报价被判为无效，Feed 进入 DELAYED，订单被拒（§4.13）；direct 路径的 MD 重连后，tick 通道可能停在 RECOVERY_REQUIRED，而 BT 不会自动恢复（§4.2）；拒单原因只保留前 3 个（§4.3）。
5. 需要用户决定的事项见 §6.2（决策 1～9），参数配置见 §6.4。

## 2. 现行定义（逐路径、逐层）

### 2.1 CTP provider（direct 与 Gateway 共用 `CtpQuoteV2MarketProvider`）

每次行情回调依次执行：

1. **readiness 丢弃**：订阅确认集齐后，第 1 笔回调只用来证明“源已流动”，随即丢弃（`live_ctp_feed.py:3446-3449`）。
2. **记录接收**：在回调内采集本机接收时间和单调时钟，并执行 `ingest_seq += 1`（`3470-3476`）。
3. **确定来源时间**：由 ActionDay + UpdateTime + UpdateMillisec 按 UTC+8 解析。字段缺失时退回本机接收时间，并打上 `AMBIGUOUS_EVENT_DATE` 或 `INVALID_EVENT_TIME` 标记（`containers/ctp/ctp_ticker.py:243-265`）。只有 `event_time_source == "action_day"` 时，投影才给出来源时间（`market_tick_projection.py:85-100`）。
4. **报价校验**（`live_ctp_feed.py:844-875`）：
   - 无效：LAST/BID/ASK 不为正或不小于 DBL_MAX/2；量为负；bid > ask（CROSSED_BOOK）。
   - 只打标记、不判无效：bid == ask（`LOCKED_BOOK`）；任一侧量为 0（`ZERO_DEPTH`）。
5. **成交量换算**：无效报价走 `apply_volume_delta(0, complete=False, quality="INVALID_QUOTE")`，且不更新跟踪器（`3521-3525`）；有效报价进入 `CtpVolumeDeltaTracker.apply`（`1071-1109`），按顺序匹配下表：

| 条件（按顺序匹配） | volume_quality | delta | volume_complete | continuity |
| --- | --- | --- | --- | --- |
| 该合约第一次出现 | BASELINE | 0 | False | gap |
| 范围键变化（重连、订阅代际、交易日） | CONNECTION_OR_TRADING_DAY_RESET | 0 | False | gap |
| `ingest_seq` ≤ 上一笔 | OUT_OF_ORDER（另加标记，不更新状态） | 0 | False | gap |
| 累计量 < 上一笔 | VOLUME_RESET（另加 `VOLUME_GAP`） | 0 | False | gap |
| 其他 | CONTINUOUS | 差值 | True | continuous |

6. **得出 continuity**：`continuity_status` 为 `continuous`，当且仅当 `volume_complete` 为真且 `volume_quality == CONTINUOUS`（`ctp_ticker.py:235-239`）。此外：
   - 容器的 `execution_eligible` 恒为 False（`ctp_ticker.py:136-137,240`）；
   - 类型化投影把一切非 `continuous` 都映射成 `gap`，同时设置 freshness UNAVAILABLE、`execution_eligible=False`（`market_tick_projection.py:225-227,263-266`）。
7. **重连**：
   - 本地连接代际和订阅代际递增（`live_ctp_feed.py:2694-2723`）；
   - provider 内部重建源后要求新的 epoch（`market_provider.py:925-937`）；
   - direct 适配器遇到这种情况直接抛错，交给 SDK owner 进入恢复（`market_stream_provider.py:233-237`）；
   - tick 通道的 `resync` 一律拒绝，注释写的是“改为重新订阅”（`261-267`）。

### 2.2 OKX（`OKX:market_tick_stream.py`，6bd5958）

- **报价 tick（tickers）**：delta 为 0；锚定之前记为 `baseline`，之后记为 `continuous`、complete（`240-275`）。
- **成交 tick（trades）**：这是聚合成交，`tradeId` 是 `count` 笔中最后一笔的编号（`153-174,278-327`）。
  - 首笔为 baseline，delta 为 0，**首笔成交自身的 sz 被丢弃**；
  - `tradeId == 上一笔 + count` 时为 continuous；
  - 其他向前跳的编号记为 `discontinuous`：本行 sz 照报，`volume_complete=False`，但**不再算 gap**；
  - 重复或更旧的编号直接丢弃。
- **continuity**：每个绑定的第一笔、以及坏帧之后的第一笔为 gap，其余为 continuous（`gap_pending`：`142,584,594`）。重连、断开或入口溢出时，通道转入恢复（文件头 `46-50`）。

### 2.3 Binance（`BN:market_tick_stream.py`，f9bfe34）

- 报价来自 bookTicker，成交来自 aggTrade，规则同 OKX 旧版：`a == 上一个 + 1` 为连续；跳号时既记 `discontinuous`，**也把 continuity 设为 gap**（`178-193,258`）。
- 没有使用 bookTicker 的更新号 `u`，也没有使用 aggTrade 的 `f`/`l`（首、末成交号）。
- demo 记录显示，两家都曾因成交号缺口出现短暂 DELAYED（DEMO 记录第 54、73 行）。

### 2.4 SDK

- **owner 分发**（`SDK:service_market_stream_owner.py:535-552`；Gateway 路径为 `service_market_stream.py:532-552`）：
  - provider 游标必须逐一递增，否则记 `MARKET_CURSOR_DISCONTINUITY`，通道进入 RECOVERY_REQUIRED；消费队列溢出时同样处理；
  - 这是 provider 到 owner 之间的**本地**消息连续性，也是目前唯一真正度量“丢消息”的检查；
  - 恢复必须由调用方以 `acknowledge_data_loss=True` 显式 resync；没有找到自动恢复路径。
- **时钟资格** `qualify_market_tick_event`（`clock_verification.py:342-399`）：
  - 前提：NTP 证据有效，且与场所时钟的核对一致；否则原样返回，时钟质量保持 UNKNOWN（`358`）；
  - 延迟 = 经 NTP 校正的接收时间 − 来源时间。不超过 `max_latency_seconds` 为 FRESH；超过为 STALE（`EVENT_TIME_STALE`）；来源时间超前且超出误差时为 UNAVAILABLE（`371-377`）；
  - `execution_eligible = FRESH 且 continuity_status == "continuous"`（`386`）。
- **场所时钟核对**（`SDK:bt_api.py:4297-4335`）：CTP 用登录回报里的交易所时间，容差 = 粒度 1000 ms + 误差界 + `max_latency_seconds`，按（交易所、场所、连接代际）缓存；场所缺少时间时借用 SHFE 的时间（`4319`）。
- **更严格的其他消费方**：多腿 cohort 要求 continuous、不得有任何 quality flag、volume complete（`market_cohort.py:432-460`）；CTP quote v2 执行投影要求 continuous、不得有 flag、买卖双边量 > 0、价格在涨跌停之内（`CTP:quote_v2_projection.py:137-181`）。

### 2.5 BT Feed（类型化 SDK tick；D62-27 规定的“数据与下单资格分离”路径）

- **接收与资格**：`ingest_market_tick_event`（`BT:feeds/market_tick_adapter.py:289-336`）。
  - 缺少时间：丢弃并计数；
  - 资格条件：两种时钟都为 VERIFIED、FRESH、SDK 判定可执行、`接收 − 来源 ≤ event_time_max_age`（默认 2.0，`btapifeed.py:280`）；
  - 原因码集合见 `market_tick_adapter.py:213-225`；资格保存为 `_tick_trade_state`（`btapifeed.py:1215-1240`）。
- **`_prepare_tick`**（`1914-2113`）先收集各类 flag：
  - 来源：provider 的 `quality_flags`、SDK 报价检查（`BID/ASK_PRICE_INVALID`、`*_DEPTH_ZERO`、`CROSSED_BOOK`，见 `SDK:market_tick_contracts.py:437-458`）、价格网格、`OUT_OF_ORDER_EVENT_TIME`（`1992`）、迟到、范围变化；
  - 除 `LEGACY_SCHEMA`、`NO_TRADE`、`VOLUME_BASELINE` 外，全部算作阻断（`2050-2058`）；
  - `VOLUME_INCOMPLETE` 在 continuity 为 continuous 时只标 bar（74c48c7e3，`2064-2075`）；
  - 资格类标记只阻断下单，其余标记阻断数据（`2078-2080`）；
  - `bar_eligible` 要求没有数据阻断且 delta > 0（`2101`）。
- **状态切换** `_handle_event_health`（`2374-2425`）：
  - 数据质量不为 GOOD，或 continuity ∈ {gap, stale, disconnected, checksum_failed, out_of_order, invalid} 时：发出 DELAYED，并设 `_live_notified=False`、`_continuity_degraded=True`；
  - 之后出现一笔 continuity ∈ {ok, continuous, recovered, snapshot} 的健康 tick，即回到 LIVE。
- **bar**：桶内只要有任何 flag，bar 就是 `complete=False`（`2133`），只通过 notify_bar 通知，**不进入数据线**（`2259`）；provider 尚未完成的 bar 不发布（`883`）；同一时间点已发布过的 bar 若出现不同的值，记为 `revisions_refused`，不改写（`909`）。
- **`trade_qualification()`**（`787-848`）要求同时满足：Feed 处于 LIVE 且未降级；之后没有接收错误；最近一笔 tick 的资格原因为空；距该笔的本机接收时间不超过 `receive_time_max_age`（默认 2.0）。

### 2.6 Broker direct 下单门（`BT:brokers/_btapi_direct_mode.py:1525-1551`）

依次检查，命中即返回：

1. 历史预热中：`target_feed_warming_up`；
2. 没有资格接口：`target_data_unqualified`；
3. 可信休市或集合竞价：`wait`（D62-30/34）；
4. Feed 非 LIVE：`target_feed_not_live`；
5. 其他不合格：`target_data_not_tradable:` 加上**前 3 个原因**（`1550`）。

休市待发单在派发前会重新核验；不合格时继续等待（`2364-2370`）。

## 3. 被混在一起的五个概念

| 概念 | 回答什么问题 | 现在由谁承载 | 应否参与下单门禁 | 建议 |
| --- | --- | --- | --- | --- |
| 价格新鲜度 | 这个价格是不是“刚才”的 | SDK 的 FRESH/STALE（来源到接收）+ BT 的接收后停留时间 | 是 | 阈值可按场所、按合约配置 |
| 消息/连接连续性 | 有没有可能丢了消息；数据是否来自当前连接 | 本地游标、连接/订阅代际、队列溢出；CTP 没有交易所序号 | 是：不属于当前代际的数据不能用 | 当前代际的首笔快照应视为连续 |
| 成交量核算完整性 | 累计量能否正确分摊到每笔、每根 bar | CTP 的 `volume_quality`；OKX/Binance 的成交号 | 否 | 只标注 bar；另设可选的严格模式 |
| bar 构建与修订 | bar 是否收齐，是否会被修改 | Feed 水位线、`bar_final`、`revisions_refused` | 否 | 只影响 bar 的交付和标注 |
| 交易时段/阶段 | 现在能否交易 | 交易日历（D62-30/34/36） | 是，但由时段门禁负责，不由数据门禁负责 | 竞价 tick 是数据，不应使 Feed 进入 DELAYED |
| （附加）报价有效性 | 价格本身是否合理 | provider 校验 + SDK 报价标记 | 是，但须区分“无效”和“涨跌停单边” | 分级处理 |

关键事实：CTP 的 L1 是全状态快照，每笔都包含最新价、买卖一、日内累计量和持仓量。因此：

- 丢失一笔，不会让下一笔的价格变错；
- 下一笔的累计量已经包含丢失那笔的成交，所以成交量只会被记到下一笔所在的 bar，不会丢；
- 反过来，现行规则也检测不到真正丢失的快照。

可见，现行的“连续性”既不是丢消息的证据，也不是价格可用的条件。

## 4. 具体问题场景（按现行规则）

每条依次给出现象、影响和证据等级。

**4.1 订阅后首笔。**
- 现象：第 2 笔回调为 BASELINE（gap），Feed 进入 DELAYED，订单被拒为 `target_feed_not_live`，要到第 3 笔才回到 LIVE。
- 事实：SimNow 实测显示，这笔 tick 的来源到接收延迟为 1.0–1.2 s，`VERIFIED/FRESH`，“首笔为成交量基线（continuity=gap）”（SIMNOW 记录第 43 行）。OKX/Binance 同样是“首笔为 gap”（DEMO 记录第 43-44 行）。
- 影响：活跃合约约损失 1 s；稀疏合约可能是几十秒到几分钟。这一笔的价格本可使用。

**4.2 重连后首笔。**
- 规则上：重连后的首笔为 gap，与 4.1 相同。
- 更严重的问题（STATIC 推断）：direct 路径在 MD 重连后，provider 重建源，适配器抛错，SDK 把通道置为 RECOVERY_REQUIRED；CTP tick 通道的 resync 本身拒绝（`market_stream_provider.py:261-267`）；BT 的 `accept_market_stream_resync`（`BT:stores/btapistore.py:2119`）没有任何调用方；Store 只把该合约标为 stale/gap，并丢弃后续事件（`BT:stores/_market_delivery_state.py:192-222`）。
- 若推断成立：重连后连 gap 首笔都不会送达，目标合约将一直不可交易，直到进程重启。
- 现场：SimNow 在 2026-11-06 16:01 观察到 MD 断线（原因 4097），观察结论待补（SIMNOW 记录 §2h）。在核验之前，“重连后首笔可交易”无从谈起（决策 7）。

**4.3 稀疏合约。**
- 现象：超过 2 s 没有新 tick 就触发 `RECEIVE_TIME_STALE`；首次可交易还要再等两笔回调。
- 实测（SIMNOW）：
  - hc2701 有一笔订单被 `FRESHNESS_STALE` 拒绝（SIMNOW 记录第 117 行）；
  - Gateway 版 tickbroker_5s_pair_arbitrage 两腿共被拒 4 次，原因 `FRESHNESS_STALE,UPSTREAM_EXECUTION_INELIGIBLE,EVENT_TIME_STALE`（第 168 行）。
- 分析：这三个代码都源自同一个事实，即这笔 tick 在接收时来源到接收已超过 2 s。由于原因只保留前 3 个（`_btapi_direct_mode.py:1550`），排在后面的 `RECEIVE_TIME_STALE` 可能被截掉。第二例中 rb2701 那条腿也被拒，所以真因到底是上游延迟还是合约冷清，从现有记录无法区分。
- 业界视角：冷清不等于陈旧。前置在快照不变时可能不推送（需核验）。

**4.4 累计量下降。**
- 现象：VOLUME_RESET 使这一笔为 gap，出现一次 DELAYED 抖动并拒单；跟踪器随后重新锚定。
- 可能来源：SimNow 回放、交易日字段口径（见 4.10），或极少见的更正。
- 影响：价格不受影响。这正是用户所说的“行情可能变化”的一种情形。

**4.5 乱序。**
- CTP 跟踪器的 OUT_OF_ORDER 在实时路径上不可达（见 §1）。
- 交易所时间倒退由 BT 判为数据阻断，一笔倒退（例如前置重复投递）就会引起一次 DELAYED。时间相等不算倒退。

**4.6 只有报价变化、没有成交。**
- CTP：delta 为 0，CONTINUOUS，可以交易，并刷新接收时间；delta 为 0 时不进入 bar，这是合理的。OKX tickers、Binance bookTicker 相同。
- 结论：现规则下这一项没有问题。

**4.7 集合竞价 tick。**
- 现象：竞价结果快照常常缺一侧盘口（STATIC，需实测），从而成为 INVALID_QUOTE（gap）；又因为交易日变化，跟踪器会重置，竞价成交量落入基线，于是第一根 bar 少了这部分量。
- 影响：
  - 下单方面：竞价阶段本来就不派发（D62-34，`_btapi_direct_mode.py:1540`），影响不大；
  - 数据方面：Feed 在开盘时出现一次 DELAYED 抖动；首根 bar 的成交量与常见数据商（把竞价量并入首根分钟线）不一致，回测与实盘因此不一致。

**4.8 每秒约 2 笔的快照与突发到达。**
- 快照本身就是合并后的状态，丢失不可见，而累计量保证成交量换算正确。
- 停顿后突发到达时：前几笔判为 STALE，进入数据线但不用于下单；最新一笔判为 FRESH，可用于下单。行为正确，与连续性无关。

**4.9 Gateway 路径。**
- provider 语义与 direct 相同（同一 provider，同样丢弃第 1 笔）；资格判定在 BT 进程中完成（`service_market_stream.py:546-552`）。
- 接收时间取自 Gateway 进程，所以 Gateway 到 BT 这一跳只体现在“接收后停留”里，前提是两进程在同一主机、共用单调时钟。
- Gateway 重启或租约续订后要重新订阅，又会出现一次 BASELINE。

**4.10 交易日切换。**
- 规则上：`trading_day` 在范围键里，切换后首笔为 gap；实际中切换往往与前置断线重连同时发生，见 4.2。
- 风险（未核验）：社区常报告 DCE、CZCE 夜盘的 ActionDay/TradingDay 口径与自然日不一致。如果 ActionDay 报成下一交易日，现规则会判“来源时间超前”（UNAVAILABLE），整个夜盘都不可交易。现有示例只覆盖 SHFE 和 CZCE（SA701）的日盘。

**4.11 OKX 聚合成交。**
- 6bd5958 之后，成交号跳号不再导致 DELAYED 或拒单（74c48c7e3）。
- 但跳号所在的 bar 仍然 `complete=False`，只通过 notify_bar 通知，**K 线数据线少一根**。demo 上跳号较频繁，指标窗口会错位，而回测中没有这种空洞。

**4.12 Binance 聚合成交号。**
- 跳号仍算 gap，导致 DELAYED 并拒单，与 OKX 的决定不一致。
- aggTrade 跳号是否意味着推送丢失，尚未证明；可以用 `f`/`l` 核对。

**4.13 涨跌停单边盘口（STATIC，高影响，未实测）。**
- 现象：涨停时卖一为 DBL_MAX、卖量为 0，`_validate_ctp_quote` 判为无效（`live_ctp_feed.py:848-855`），于是 INVALID_QUOTE、gap，BT 的 `ASK_DEPTH_ZERO` 等标记又构成阻断，结果 Feed 进入 DELAYED、不生成 bar、拒绝一切订单。
- 影响：被拒的订单里包括按场所规则本可受理的订单（例如涨停时卖出平多）。行情被锁板期间，策略既看不到价格，也无法下单。

**4.14 提示类标记被当作阻断。** provider 只标记不判无效的 `LOCKED_BOOK`、`ZERO_DEPTH`，在 BT 里却成为阻断，同样导致 DELAYED（`btapifeed.py:2050-2058`）。

## 5. 业界做法

**5.1 增量数据依靠序号判断缺口。**
- 典型例子：CME MDP 3.0（通道包序号 + 合约级 RptSeq），Nasdaq TotalView-ITCH/MoldUDP64（包序号与补发），FIX（MsgSeqNum + ResendRequest），Binance 差量深度（U/u，期货另有 pu），OKX books（seqId/prevSeqId 与 checksum）。
- 共同点：这些都是“增量”数据，漏一条后本地订单簿就是错的。所以发现缺口后，标记该合约的簿无效，用快照重建，恢复之前不在该合约下单。

**5.2 L1 快照与合并（conflated）行情不依赖序号。**
- 每条消息都是完整状态，例如 CTP DepthMarketData、Binance bookTicker、OKX tickers。漏一条只是少看到一个中间状态，下一条照样正确。
- 对这类数据通常只做“时效”和“合理性”检查，不会因为“此前没有消息”而拒绝第一条。
- CTP 方面：`CThostFtdcDepthMarketDataField` 没有序号字段；交易所按固定节拍推送快照（上期所等约 500 ms，各所与前置以实测为准），前置还可能再做合并。

**5.3 陈旧按时间判断，并按合约区分。**
- 阈值依据合约活跃度（典型更新间隔的高分位数）和交易阶段来设。
- 用连接心跳，或同一连接上其他合约的推送，来区分“只是冷清”和“已经断了”；只看“距上一笔多久”，在冷门合约上会大量误报。
- CTP 的 SPI 虽有 `OnHeartBeatWarning`，但一般认为不可依赖（需核验）。

**5.4 “行情够不够格下单”的常见检查组合**（常见组合，不是某一家的规范）：连接正常且数据属于当前代际；时效在阈值内；价格合理（为正，在涨跌停或价格带内，不过度偏离参考价，买卖不交叉，部分场所允许锁盘）；交易阶段允许；可选的跨源核对（第二个前置，或关联合约、指数）；行情中断时的停单开关。监管方面，如 MiFID II RTS 6 要求算法交易具备价格带、最大单量等事前控制。

**5.5 成交量重建出现缺口，通常不阻断交易。**
- 成交量用于 bar、VWAP、量能信号；出现缺口时，把相关 bar 标为不完整，或事后用官方数据修复。
- 交易门禁看价格类数据；依赖量能的策略可以显式选择严格模式。

## 6. 建议

### 6.1 修订后的定义（提议）

对每笔 tick 产生四个互相独立的事实，各有固定用途：

1. **范围有效**：tick 属于当前连接代际和订阅代际，且本代际开始以来没有发生本地丢消息（游标断裂、队列溢出、坏帧）。代际内的首笔快照也属有效。用于下单门禁和 LIVE 判断。
2. **新鲜度**：来源到接收的延迟（D62-21/37），以及下单时的接收后停留时间（D62-28）；阈值可按场所、按合约配置。用于下单门禁。
3. **报价可用性**：分三级——
   - `INVALID`：非正数、哨兵值、交叉、价格不在涨跌停内，拒单；
   - `LIMIT_LOCKED`：与同一快照的涨跌停价严格相等的单边盘口，视为有效并打标记；
   - `LOCKED`/`ZERO_DEPTH`：提示级。
4. **成交量核算**：BASELINE、RESET、JUMP、CONTINUOUS。只标注 bar；另设可选的严格模式。

交易时段由日历门禁负责；bar 的完成与修订由 Feed 处理。这两者都不读 tick 的连续性。

**LIVE 的定义**：Feed 正在投递当前代际的实时 tick。只在历史数据或回补中、断线或恢复中、范围失效、时间或价格出现数据完整性缺陷时发出 DELAYED；BASELINE、成交号跳号、累计量下降都不再导致 DELAYED。

**承载方式**：沿用现有词汇，不另造新字段——
- 首笔快照记为 `continuity_status="snapshot"`。BT 的健康集合和 SDK 的 `_ACTIVE_CONTINUITY` 已经包含这个值（`btapifeed.py:2418-2423`、`service_market_stream_owner.py:50`）；`BASE:market_tick_protocol.py:207` 中该字段为 str。
- `gap` 只表示“可能丢了消息”。
- SDK 资格改为：FRESH，且 continuity ∈ {continuous, snapshot}。

### 6.2 决策项

**决策 1：采用分层定义（§6.1）。**
- 推荐：采纳。
- 与已确认决定的关系：I62-09 中“连续性无缺陷”需要改义（详见 §6.3）。
- 归属（按职责规范）：中立词汇和资格归 BASE/SDK（`market_tick_protocol`、`market_tick_contracts`、`clock_verification`）；各场所的映射归各 provider；BT 只改状态切换、bar 消费和原因报告。

**决策 2：订阅后、重连后、日切后的首笔，价格能否用于交易。**
- 选项：
  - A1：维持现状，首笔不可交易；
  - **A2（推荐）**：同时满足范围有效、新鲜、报价可用时即可交易；成交量仍为基线（delta 为 0，只标 bar）；CTP 保留 readiness 丢弃第 1 笔（防订阅时推送的旧缓存，新鲜度检查也能挡住）；
  - A3：等到第 N 笔或 T 秒之后。
- 预期效果：SimNow 上首笔引起的 DELAYED 和 `target_feed_not_live` 拒单消失。

**决策 3：成交量类缺陷不再算作连续性缺口。**
- 范围：CTP 的 VOLUME_RESET 和交易日基线、OKX 跳号（已按 2026-11-06 的用户决定处理）、Binance 跳号。
- 选项：
  - 3a：维持现状；
  - 3b：统一为只标 bar；
  - 3c：在 3b 基础上，按策略提供可选的 `strict_volume_continuity`，为真时恢复现行门禁。
- 推荐：3b + 3c，开关默认关闭。
- 需确认：Binance 是否与 OKX 对齐（OKX 的决定原文只针对 OKX）。

**决策 4：成交量不完整的 bar 是否进入数据线。**
- 选项：
  - 4a：维持现状，只走 notify_bar，数据线少一根，回测中没有这种空洞；
  - 4b：进入数据线，并带 `volume_complete=False` 标记；
  - 4c：按策略配置。
- 需注意：由逐笔成交构建的 bar 在漏成交时，最高价、最低价也可能不准；而 CTP 的快照 bar 本身就是近似。
- 推荐：4c，默认保持 4a；先实测空洞频率，再定默认值。OKX 可评估改订 `trades-all`（逐笔、不聚合；需核验）。

**决策 5：新鲜度阈值。**
- 现状：SDK 的 `max_latency_seconds` 是全局值；BT 的 `event_time_max_age`、`receive_time_max_age` 按 Feed 设置，但示例里所有合约共用一份。两个延迟上限各自生效，实际取较小者。
- 选项：
  - **5b（推荐）**：两类阈值都支持“场所默认值 + 合约覆盖”；BT 侧只能收紧 SDK 的上限；由同一个配置键下发；默认值仍为 2 s（D62-28）；
  - 5c：已证明连接存活时，对冷清合约放宽停留上限。这需要新的活性证据合同，而 CTP 目前缺少可靠的心跳，暂不推荐。

**决策 6：涨跌停单边盘口与提示类标记。**
- 选项：
  - 6a：维持现状；
  - **6b（推荐）**：provider 用同一快照的 Upper/LowerLimitPrice 识别 `LIMIT_LOCKED_UP/DOWN`；最新价照常进入 bar；订单交由场所按规则处理；`LOCKED_BOOK`、`ZERO_DEPTH` 降为提示级，不再导致 DELAYED；
  - 6c：只放行与锁板方向相反的平仓单。
- 与已确认决定的关系：6b 与 D62-33（不增加前置拒绝，由场所处理并如实反馈）的精神一致。
- 推荐先用录制的快照（FAKE）验证，再等待真实涨跌停时观察。

**决策 7：MD 重连恢复。**
- 先在 SimNow 交易时段做一次受控断线（只读、不下单），核验 direct 和 Gateway 能否恢复。
- 若确认会停在 RECOVERY_REQUIRED：由 SDK owner 或 provider 提供重新订阅，BT Store 提供显式的数据丢失确认和 bar 作废。
- 在完成核验之前，决策 2 对重连这一场景不能宣称生效。

**决策 8：乱序。**
- 推荐：删除 CTP 跟踪器中按 `ingest_seq` 判乱序的分支（实时路径不可达，容易误导）。
- 交易所时间倒退的单笔 tick：不进入 bar，不覆盖最近一次资格判定，也不导致降级；连续多笔倒退时才降级。这一点需用户确认。

**决策 9：拒单原因。**
- 拒单只报主因（第一个失败的维度），完整原因记入订单 info 和日志；同一个事实不再拆成三个代码重复表达。
- 这是机械性改动。

### 6.4 config.yaml 参数

**现状（数据流已在源码中核实）：**

- **SDK 时钟资格**：
  - 数据流：`direct.market_clock_verification`（模板中为 `true`）→ `run.py` 原样传入 `BtApiStore(market_clock_verification=...)`（例如 `EX:tickbroker_single_symbol_direct/run.py:152`）→ Store 把它并入 `_api_kwargs`（`BT:stores/btapistore.py:381-386`）→ `DirectApiAssembly.from_options` 选取（`SDK:direct_api_assembly.py:104-131`）→ `BtApi`（`SDK:bt_api.py:750,888-903`）。

## 7. 测试、验收影响与风险

**7.1 UNIT/FAKE**（每项都必须在旧代码上失败，并做变异检查）：

- **CTP**：订阅后首笔有效快照为 snapshot，volume_quality 为 BASELINE，delta 为 0；VOLUME_RESET 不再是 gap，带 `VOLUME_GAP`；单边涨停有效并带 `LIMIT_LOCKED_UP`；交叉盘口或双边哨兵值仍为 INVALID。
- **Binance**：跳号时 continuity 为 continuous，volume_quality 为 discontinuous（参照 OKX 6bd5958 的测试）。
- **SDK**：FRESH + snapshot 可执行；FRESH + gap、STALE + snapshot、未知 continuity 均不可执行；按合约阈值生效。
- **BT**：首笔不发出 DELAYED 且 `trade_qualification().ok` 为真；已退役代际的 tick 仍被拒；单笔时间倒退不降级、不覆盖资格；按合约的 `receive_time_max_age` 生效；拒单原因完整保留；打开严格模式时恢复现行行为。
- **cohort 与 quote v2**：明确是否接受 snapshot，不能默认放宽。

**7.2 SimNow/demo**（交易时段；证据等级 SIMNOW/DEMO）：从订阅到首次可交易的时间（改动前后对比）；每小时 DELAYED 次数与拒单主因分布；rb2701 与 hc2701 对比；夜盘 20:59/21:00 日切；受控断线后的恢复（决策 7）；DCE、CZCE 夜盘日期字段的只读观察；OKX、Binance 跳号频率与 bar 空洞数。

**7.3 风险：**

- **首笔放行**：订阅时推送的旧缓存，若恰好在 2 s 以内也会被采用。但它是近期的真实价格，可以接受；不同前置之间的数据差异不在本定义范围内。
- **语义变更面**：增加 snapshot 值、成交量缺陷不再降级，会影响 cohort、quote v2、Gateway 等消费方，以及现有断言 DELAYED 的测试。这些须逐项更新，并作为行为变更记录在案；依赖量能的策略需要显式打开严格模式。
- **涨跌停识别**：若把损坏的报价误判为锁板，就会放行订单。因此只在与同一快照的涨跌停价严格相等时才识别。
- **阈值配置**：合约级阈值可能被配得过大，建议设置上限，并在启动时打印生效值。
