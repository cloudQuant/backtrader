## 4. 仍归迭代 62 的 direct 问题

1. **成交缺口可被漏掉：本次 UNIT/FAKE 已复现。** 成交回报先到、超过匹配窗口后被记录为 unmatched 并移出缓冲；之后可信关联的订单累计成交为 1，本地已应用成交和多仓仍为 0，而活跃订单使审计跳过该合约，新订单仍可提交。证据：[缓冲和释放](../../../../../backtrader/brokers/_btapi_direct_mode.py)（`_direct_expire_buffered_trades`、`_direct_unmatched_trade`、`_direct_audit`）；测试 `test_direct_trade_rematch.py` 第 92–108 行本身覆盖了过期后不再认领，但未检查随后本单累计成交出现缺口。独立复现命令及结果见 §6。不要把未匹配成交自动认领为本策略，也不能用累计成交伪造逐笔成交；需要为已可靠关联订单的未应用成交建立可持续、可恢复的阻断与对账合同。只加进程内标志不足：现有快照无逐单已应用成交，恢复工作单的累计基数与 UNKNOWN 的解除均需一并设计。
2. **查询查不到原身份的处置与文档不一致。** 当前代码在完整同日查询查无时标 `not_found_at_venue`；待发单恢复还把它作为可重发依据。用户本次明确确认 **D63-38**：完整当日查询查不到时标 Rejected 并解除阻断，但不自动重发；休市待发单取消并通知策略。查询不完整或旧交易日仍按计划保持 UNKNOWN。应在 62 实现并同步 62 计划及修改记录，不能把“查询查无”表述为已证明请求从未发出。查询覆盖、前置拒单与成交的否定证据仍未证明；策略自行决定是否重下时仍可能存在重复业务意图的风险。原先 62 计划 §5.3 的“查询不到保持 UNKNOWN”与新决定存在明确冲突，须注明后者的适用范围及覆盖关系，不应伪称两个文本一致。

   本次尝试了待发单从 DISPATCHING 原子转 CANCELLED，并用离线测试验证不自动重发，但审查发现仍有三个未闭环的问题：持久取消后、通知前崩溃时通知无法重放；普通订单查无后的 Rejected 通知缺乏可安全恢复的原订单参数；同日 UNKNOWN 标记仍不能按该规则解决。另缺少 provider 按 route 声明可用于查询比较的身份合同：CTP 本地客户端号不能冒充原生身份，而对所有 route 一律禁用客户端号会改变 OKX/Binance 已有恢复行为。**试验性代码已撤回，当前代码仍未实现此决定。** 建议在 Base/provider、SDK 和 BT 之间确定查询身份、原子终态及可恢复通知合同，覆盖上述崩溃点和跨场所回归后再实施。
3. **账户事实查询期间会话变化。** 现有 CTP `account_facts` 在查询前读会话，查询后缺少可信同源复核；`_query_blocker` 对缺少代际的结果采用当前代际，Feed 期间可能替换 Trader。静态证据见 [63 计划 §1.5](../迭代63-Gateway统一转发与多策略共享会话/迭代计划.md) 第 104 行和 CTP provider 的 `account_facts` / `_query_blocker`。本次有界修复核查发现，仅比较查询前后整数代际不能排除中途换源后恢复的 ABA；现有密封查询 scope/source 的适用范围、过滤和有效期尚需与 direct 合同对齐。应先冻结可信同一来源、请求范围、代际、交易日与时效，发生变化或证明缺失时拒绝完整事实，再用真实 TraderClient + fake native SPI 覆盖重连、换源 ABA、日切与正常路径。当前**未修复**。
4. **回报丢失与重连补查。** CTP provider 有界队列满时丢最旧并计数，但现有 direct 消费链未读取计数；投影异常及出队到宿主持久化之间也存在损失窗口。同日 QUICK 重连后 direct 没有明确的完整委托/成交补查闭环。应在 62 建立缺口信号、可证明来源与按类型补查/去重，无法补齐时保留受影响范围的 UNKNOWN 或阻断，并覆盖溢出、投影异常、出队后崩溃、断线窗口和补查不完整。不能假设查询可补齐所有前置拒单。
5. **SDK 弱身份键及跨交易日去重。** 计划记载 SDK 关联器使用 `(交易日, OrderRef)` 弱键；处理记录更正指出 BT direct 另有强身份匹配，因此不能称已证明外部成交记入本策略。用户此前决定 SDK 关联器修复仍留 62，Gateway 侧强身份设计归 63。本次另以假 CTP 回报复现同一 coordinator 中不同交易日使用完全相同去重字段时，第二条被丢弃（§6）；实际场所是否重用该组合尚未证实。修复须按可信 route/交易日作用域处理，保留 OKX/Binance GTC 跨日重放的去重语义，不能简单全局加日期。

上述第 3–5 项中的部分是源码风险或假数据反例，不等于已在真实账户发生。各项均需独立变更、针对性检查和逐层证据，完成前保持未关闭状态。

### 5.3 新发现及建议

- **63.05/63.06 的行为验收存在顺序环风险。** 63.05 要求三客户端的 BT Feed 在 Gateway 断线后 DELAYED→LIVE；对应 BT resync 放在依赖 63.05 的 63.06。建议 63.05 验收 SDK 健康信号及可控客户端，完整 BT Feed 链在 63.06 验收；或明确提前交付的独立子项。见 63 计划第 592–593、613–614 行。
- **静默窗口不自动证明共同切点。** 63 计划 §3.8 以查询前后代际、账本版本和已接收回报序号不变作为可比较条件；但场所成交回报可能还在传输或队列中，尚未改变 Gateway 序号。应证明查询与回报覆盖及延迟边界，或维持 NOT_COMPARABLE；不能仅由本地期间未看到回报推断场所没有发生变化。迭代 60 计划 §9.5 明记三家尚无可证明的共同水位，63 的方案需要新的能力与证据。
- **D63-38 的说明须统一。** 63 计划 §3.7 同时写无法补齐保持 UNKNOWN 与前置拒单按 D63-38；62 计划 §5.3 仍写查不到保持 UNKNOWN。建议把新决定适用的完整同日查询、范围/身份证明、旧日和不完整查询分支写成单一表，并显式更新 62 的决定、验收和变更记录。用户已明确选择 D63-38，不将原报告的不同建议当作现行决定。
- **monitor 文字要区分配置。** 63 计划 §3.14 一处写 monitor 缺失或变慢不影响交易，另一处规定 `monitor_required` 超时施加 STOP_NEW；前一句应限定未启用 required。D63-36 所称 monitor 不发控制命令，与心跳 ACK 是两件事；应明确 ACK 的回传途径、来源绑定、新鲜度和重启语义，不要写成完全没有反馈。
- **已决定内容的旧表述需要清理。** 63 计划 D62 适用表仍有“resync 方式待 D63-39”；处理记录同一文件中也有“direct 问题所在迭代待定”和之后已决定留 62 的并存。保留历史时明确时间和后续决定，避免误读为当前未决。
