## 4. 建议新增的待决事项

### N-1 CTP direct 模式下 BT 的持仓模式

**证据**

- BtApiBroker 的 `position_mode` 默认为 `net`（`backtrader/brokers/btapibroker.py:124`），`examples/live/007_ctp` 的配置和 `run.py` 都没有另行设置。
- 净持仓模式下：
  - `getposition(side=...)` 会直接报错（`btapibroker.py:1952-1954`）；
  - 持仓审计只比较净数量。
- 改用 `dual_side` 也走不通：
  - `sdk_preflight` 默认开启（`btapibroker.py:125`）；
  - `_run_sdk_preflight` 要求 `store.get_account_config()` 证明交易权限和账户持仓模式（`btapibroker.py:610-638`）；
  - CTP 没有注册 `account_config_read_aliases` 和 `position_mode_*` 入口（见 `bt_api_ctp/pyproject.toml`），OKX、Binance 都注册了；
  - 此前 SimNow 联调只能用 `sdk_preflight=False` 绕过。

**影响**

- 以下三项都要求本地按多空方向分别记账，净持仓模式下表示不了：
  - D62-22 按多空方向对账；
  - D62-24 平仓与反向开仓同时在途，中间可能短暂锁仓；
  - R-1 按方向提供的可平视图。
- 改成双向持仓，又过不了预检。

**建议**

- 定为：CTP direct 使用 `dual_side`。
- 由 CTP provider 把"期货账户为双向持仓"和交易权限作为场所事实提供给 SDK，用来替代 `get_account_config` 预检，而不是关闭预检。
- 示例配置同步修改。
- 测试覆盖短暂锁仓时的记账与对账。

### N-2 未指定开平时的默认规则

**证据**

- `sa_dual_ma` 在金叉时先发平空单、再发开多单，两笔都没有指定开平（`examples/live/007_ctp/sa_dual_ma/sa_dual_ma_strategy.py:163-179`）。
- D62-18 规定只有"明确的 OPEN 订单"才按 D62-24 判断（计划第 151 行）。
- §5.3b R-1 只写了"未指定开平时由框架基于可信数据和 D62-18 判定"，没有给出具体规则。

**影响**：第二笔下单时，空头持仓已被第一笔平仓冻结，两种判法都有问题：

- 判为平仓：可平量为 0，按 D62-18 被拒。
- 判为开仓：如果第一笔随后被撤或被拒，账户会留下锁仓。

规则不定，实现和示例都无法确定预期行为。

**建议**

- 明确规则：有反向持仓且未指定开平时，一律按平仓处理；扣除冻结后可平量不足即拒绝，并给出原因码。
- 需要与平仓同时在途的反向开仓，必须显式写 `offset="open"`。
- 62.07 按此修改 `sa_dual_ma`，并为两笔订单分别保存引用。

### N-3 没有时间资格的实时行情能否进入策略数据线

**证据**

- §5.3b R-5（计划第 221 行）写的是"未知/无资格实时数据如何进入观察或策略数据线、如何防止污染后续交易决策需另定实际合同"，但 §5.2 没有列出这一项。
- 现在 BtApiFeed 遇到不合格的 typed tick 会直接抛异常（`backtrader/feeds/btapifeed.py:1022-1027`）。

**影响**：在某个场所实现 D62-21 的时间资格之前，该场所的 tick 一律没有资格，CTP direct 示例连 bar 都生成不了。

**建议**：列为待决事项，有两个选项：

- **(a)** 无资格 tick 可以生成 bar 供指标计算，但标记为不可交易；下单时按 D62-21 单独核验。
- **(b)** 资格实现前一律丢弃。

评审倾向 (a)，同时要求 bar 带资格标记，并且不放松 Gateway 路径现有的资格校验。

### N-4 D62-21 的默认阈值

**证据**：D62-21 和 §5.3b R-9 都要求按场所、按交易时段定义允许延迟和静默期处理，但没有给出默认值。D62-06b 的 60 秒/5 分钟是现成的先例。

**影响**：示例和测试没有可用的默认值，验收时也无法判断行情是否"新鲜"。

**建议**：在 62.01 之前定好以下默认值，并允许策略配置覆盖：

- 来源时间与接收时间之间的最大差；
- 最后一笔 tick 的最大年龄；
- 休市、集合竞价、开盘第一笔这几种情况的处理方式。

### N-5 Gateway 带持仓、带挂单重启是否属于本迭代的支持范围

**证据**

- CTP 对账 authority 按设计只输出未解决的观察，从不签发安全回执（`bt_api_ctp/reconciliation_authority.py:1-7`）。
- 计划 §5.3b R-6/7 写明"缺证据时保持不可用"。
- 但 §7 的"Gateway"行和"复审闭环与状态隔离"行都标为"必需"，62.08 的完成判据也包含带仓、挂单重启的验证（计划第 505 行）。

**影响**

- 如果带仓重启需要 CTP authority 提供新能力，这是一项计划中没有排期的工作。
- 不先声明支持范围，这个必需项只能记为 GAP 或 NOT_RUN，迭代无法收口。

**建议**：在 62.01 之前二选一：

- 本迭代 Gateway 示例声明支持带仓、挂单重启，并为 authority 补齐所需证据排期；
- 只声明支持空仓启动，带仓重启保持不可用，并写进 README。

## 5. 计划中的执行缺口与文档问题

### N-6 人工核验 UNKNOWN 没有交付物

**证据**

- 计划中"人工"共出现 8 次（第 180、182、217、440、452、463、469 行）。
- §5.3b R-3 依赖"经授权的人工核验和可审计恢复"来收尾。
- 但 62.01～62.09 的交付列里，没有对应的工具或流程。

**影响**：按 D62-14 和 INV62-05，出现无法查清的 UNKNOWN 后，写入会一直被禁止。没有具体的解除手段，策略只能一直停着。

**建议**

- 62.06 交付人工处理工具或固定流程，分三步：
  1. 展示未决标记及已有的查询证据；
  2. 由操作者确认结论；
  3. 写入带操作者和时间的审计记录后解除阻断。
- 62.07 的 README 写明操作步骤。
- 验收覆盖"人工解除后恢复写入"和"错误操作被拒绝"。

### N-7 结算单确认与 UNKNOWN 写入阻断的先后关系

**证据**

- §5.3b R-10 的启动时序（计划第 233 行）先"查询结算状态、如需写确认先通过 SDK 准入"，之后才"完整查询……本地未决"。
- INV62-05（计划第 97 行）规定结果不明时"不放行写入"。

**影响**：本地有 UNKNOWN 时，结算单确认这次写操作仍会先执行，与"UNKNOWN 不放行写入"的字面规定冲突。

**建议**：二选一并写明：

- 结算单确认不改变持仓敞口，豁免 UNKNOWN 阻断；
- 或者把结算单确认移到本地未决检查之后。

### N-8 "固定状态入口"与"日志按运行分目录"在实现上冲突

**证据**

- TradeLogger 把快照写在与日志相同的 `log_dir` 下（`backtrader/observers/trade_logger.py:2990`）。
- §5.3b R-8 要求重启状态入口固定、普通日志可以按运行分目录；D62-05 以 `logs/current_position.yaml` 作为默认入口。
- 示例默认的日志目录是 `logs/<配置名>/<时间戳>/`（如 `examples/live/007_ctp/bbroker_5s_single_symbol/run.py:114`）。

**影响**：按现有参数，这两项要求只能满足一项。

**建议**：在 62.05 或 62.07 中二选一写明实现方式：

- 给 TradeLogger 增加独立的快照（状态）路径参数；
- 把状态写入拆成独立组件，TradeLogger 只负责写日志。
