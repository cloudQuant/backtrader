## 3. 本轮发现的实质问题

### R-1 D62-18 要求策略"分别提交"，但策略看不到今昨仓，示例又写死了平今

**证据**

- 10 个非 SA 示例的平仓开平方向都默认 `close_today`：
  - 策略参数：`examples/live/007_ctp/bbroker_5s_single_symbol/single_symbol_ma_strategy.py:113`，其余 9 个同值；
  - 配置文件：例如 `bbroker_5s_pair_arbitrage/config.yaml:28`。
- 平仓数量取整个持仓（`single_symbol_ma_strategy.py:762`）。
- 策略能用的持仓接口只给方向总量：
  - `Strategy.getaccountposition(data, side=...)`（`backtrader/strategy.py:4662-4670`）转调 `BtApiBroker.getposition(data, side=...)`（`backtrader/brokers/btapibroker.py:1948-1954`），`side` 只在双向持仓模式下可用；
  - 没有今仓、昨仓，也没有在途平仓冻结的数量。
- Broker 交给 SDK 规则判定的持仓事实里，今昨数量固定为 `None`（`btapibroker.py:3736-3739`）。
- `sa_dual_ma` 在同一根 bar 里先发"平空"再发"开多"，两笔都没有指定开平（`examples/live/007_ctp/sa_dual_ma/sa_dual_ma_strategy.py:161-179`）。

**影响**

- **跨交易日后平仓被拒**：按 D62-22，跨交易日后今仓会转为昨仓。螺纹、热卷属于上期所，用 `close_today` 平昨仓会被拒绝。
- **今昨混合时平不掉**：持仓今昨混合时，D62-18 会拒绝整笔平仓，而策略不知道该怎么拆。结果是持仓无法平掉，策略可能反复下单、反复被拒。
- **同 bar 先平后开可能被误拒**：判定第二笔"开多"的开平时，如果不扣除第一笔在途平仓冻结的数量，可能被判成超量平仓而拒绝。

**建议**（Q1）：以下建议都在 D62-18"需要拆单就拒绝"的框架内，不引入自动拆单。

- 向策略提供每个方向的可平今、可平昨数量（扣除在途平仓），以及 D62-18 拒单的可读原因码。
- 策略不指定开平时，由框架按可信事实判定，只有需要拆单才拒绝；策略指定的开平与事实冲突时直接拒绝，不静默改写。
- 62.07 的示例去掉写死的 `close_today`，需要时分两笔分别平今、平昨。
- 测试覆盖三种情况：
  - 跨交易日重启后平仓；
  - 今昨混合平仓；
  - 同一根 bar 先平后开。

### R-2 在同一策略目录跑回测，会覆盖实盘的对账快照

**证据**

- D62-04b2 规定：同一策略目录的回测与实盘共用局部序号。这意味着默认会在实盘策略目录里跑回测。
- D62-05 与 §5.3a 第 6 条，以策略目录下的 `logs/current_position.yaml` 作为对账快照的默认入口。
- TradeLogger 默认写快照（`backtrader/observers/trade_logger.py:201`，`log_position_snapshot: True`），并且每次 `next()` 都覆盖写入（`trade_logger.py:2379-2410,2954-3000`）。
- 回测示例同样挂了 TradeLogger（如 `examples/backtest/007_ctp/bbroker_5s_single_symbol/run.py`）。

**影响**

- 改成固定快照路径后，在实盘目录里跑回测会把实盘快照覆盖掉。
- 如果未决标记也放在同一处，会被覆盖或混入回测数据。
- 下一次实盘启动时，会拿回测的持仓去和账户对账。

**建议**（Q2）

- 状态文件记录运行模式（live/backtest），以及账户和 route 绑定。
- 回测只共享序号分配器，不写实盘对账快照和未决标记。
- 实盘启动时，发现快照的模式或账户不符即拒绝。
- 测试覆盖"同一目录先跑回测、再重启实盘"。

### R-3 跨交易日的运行与恢复缺少合同

**证据**

- CTP feed 只接受 GFD 委托（`bt_api_ctp/feeds/live_ctp_feed.py:1899-1902`）。
- 夜盘属于下一个交易日。进程从日盘一直运行到夜盘时，会依次遇到：
  1. 前置断开后重连，产生新会话（FrontID、SessionID 改变）；
  2. 新交易日需要重新确认结算单（D62-20）；
  3. 运行中的持仓审计需要做今转昨（D62-22 只写了重启时的对账）；
  4. 合约目录缓存要切换到新交易日（D62-11b、11c）；
  5. GFD 委托在日终失效。
- §5.3 已经写明"CTP 特定查询存在交易日与完整性边界，未查到不能视为未发送"，但没有给出解决办法。CTP 的委托和成交查询通常只返回当前交易日的数据，需要在 62.03 用 SimNow 核实。
- provider 没有封装结算单查询：原生绑定里有 `ReqQrySettlementInfo`（`bt_api_ctp/ctp/ctp_trader_api.py:984`），但 `TraderClient`（`bt_api_ctp/ctp/client.py`）没有使用。

**影响**

- **UNKNOWN 标记无法清除**：日终前崩溃留下的 UNKNOWN 标记，换交易日后无法再按原身份查清。按 D62-14 规则，写入会被永久禁止，只能人工处理。
- **日切处理无序**：长时间运行跨入夜盘时，结算确认、今转昨、缓存切换、会话切换这几件事的处理顺序没有合同约束。

**建议**（Q3）

1. 在 §5.3a 增加"运行中跨交易日"合同，按以下顺序执行：
   1. 检测到交易日变化；
   2. 暂停写入；
   3. 重新确认结算单；
   4. 切换目录缓存；
   5. 核对今转昨后的持仓；
   6. 恢复写入。
2. 增加跨交易日未决标记的解决规则：
   - 只有 GFD 委托，所以上一交易日的订单到下一交易日一定已终结，只剩成交量未知；
   - 成交量用该交易日的结算单（含成交明细，需新增封装）加持仓变化来确定；
   - 无法确定时由人工确认，并留下记录。

### R-4 派发前持久化由谁负责仍有矛盾

**证据**

- §5.3a 第 4 条（计划第 202 行）写的是：SDK/provider 在内部依次完成"原生关联号及会话预留 → 持久提交最小未决标记 → 核验绑定后派发"。
- D62-14 规定：未决标记存放在 BT 侧的 TradeLogger 相关本地记录中。
- §5.3a 第 3 条要求 62.01 按实际 owner 登记职责。

**影响**

- SDK 不应直接写 BT 的状态文件。
- 一次 `make_order` 调用内部，BT 没有机会在"预留"和"派发"之间写盘。
- 这一点不定下来，D62-04a1（provider 分配原生号）与 D62-14（派发前持久化）就无法同时满足。

**建议**（Q4），二选一，并写进职责规范：

- **(a) 推荐**：SDK 定义一个中立的"派发前提交"端口，由 BT 注入实现（基于本地状态文件）。`make_order` 在预留之后、原生调用之前调用它，提交失败就不派发。
- **(b)**：拆成"预留"和"派发"两次调用。

两种做法都保留 `make_order` 作为公共入口，D62-03 本来就允许"必要时在 SDK 内调整接口"。

### R-5 BT Feed 的"行情可见"与"交易资格"拆分没有归到具体步骤

**证据**

- BtApiFeed 收到不合格的 typed tick 时，会冻结行情源并抛出异常（`backtrader/feeds/btapifeed.py:1022-1027`；校验逻辑在 `backtrader/feeds/market_tick_adapter.py:77-100`）。
- `execution_eligible is False` 会触发 DELAYED：tick 不进入 bar，也不发出 LIVE（`btapifeed.py:2123-2180`）。
- §5.3a 第 1 条写了"展示、行情可见性和交易资格可分别表达"，但没有步骤负责改 Feed：
  - 62.03、62.04 交付的是 SDK/provider；
  - 62.05（计划第 475 行）的交付清单里没有 Feed 改造。
- 这段 Feed 代码 Gateway 路径也在用。

**影响**

- 没有步骤负责，§7"CTP 直连"中的"tick 到达 BT 数据线"就无法通过。
- 改动时如果不加回归测试，可能削弱 Gateway 路径现有的资格检查。

**建议**：在 62.05（或 62.03 的 BT 子项）中明确以下交付：

- tick 的可见性与交易资格分离；
- 按目标 data 计算 LIVE（D62-15）和下单时的时间资格（D62-21）；
- Gateway 行情路径的回归测试。

### R-6 Gateway 版示例的启动对账走哪条路径没有写

**证据**

- SDK 模式下，Broker 启动时如果不走 service recovery 分支，有两道检查：
  - 要求远端没有挂单（`backtrader/brokers/btapibroker.py:376-381`）；
  - 要求 `get_reconcile_snapshot()` 证明账户干净且空仓（`btapibroker.py:426-431`），而这个快照恒为不完整（`backtrader/stores/btapistore.py:3955-3958`）。
- service recovery 分支走的是受管恢复（`btapibroker.py:399-420`）。
- CTP 对账 authority 按设计不签发安全回执（`bt_api_ctp/reconciliation_authority.py:1-7`）。

**影响**

- 62.08 没有写 Gateway 示例使用哪套启动和恢复合同；如果走普通 SDK 启动分支，会直接启动失败。
- 账户有持仓时能否重启、README 怎么说明，都没有定义。

**建议**（Q5）

- 62.08 写明 Gateway 示例的启动和恢复路径（service recovery）、有持仓或挂单时的行为，以及与 direct 对账的区别，并写进 README。
- 验收覆盖"带持仓重启"。

### R-8 示例的日志目录与验证账户的前提

**证据**

- 11 个实盘示例的 `run.py` 在没有配置 `log_dir` 时，都会使用带时间戳的新目录（如 `bbroker_5s_single_symbol/run.py:114`，`sa_dual_ma/run.py:113`），而所有 `config.yaml` 都没有设置 `log_dir`。§5.3 第 1 条写的是"可能按时间戳生成日志目录"，现在已经确认确实如此。
- D62-13 要求首次启动时全账户空仓且无挂单；D62-19 规定停止时只撤单、不平仓。
- 22 个示例在同一个 SimNow 账户上共用 rb2701、hc2701、SA701。此前在 SimNow 上的探测也可能留下了持仓或挂单。

**影响**

- 不改日志目录，重启时永远找不到上次的快照。
- 不先清理账户，多数示例的首次启动都会被拒绝。

**建议**（Q7）：62.07 的交付中明确以下内容，62.08 同样适用。

- 把 `log_dir` 和状态文件路径改为固定路径，不带时间戳。
- 制定运行规程：
  - 首次启动前清空账户（手工处理，或由策略自身的退出逻辑平仓，不由框架自动平仓）；
  - 示例依次运行；
  - 记录每次运行前后的账户状态。

### R-9 D62-21 需要具体阈值和各场所的时间细节

**证据**

- CTP 登录回报 `CThostFtdcRspUserLoginField` 带有各交易所的时间 `SHFETime`、`DCETime`、`CZCETime` 等（`bt_api_ctp/ctp/ctp_structs_common.py:77,114-124`），`TraderClient` 目前没有使用。
- CTP 行情投影用 `ActionDay + UpdateTime + UpdateMillisec` 构造事件时间（`bt_api_ctp/market_tick_projection.py:88-118`）。

**建议**

- **阈值**：
  - 盘中休市、集合竞价，以及冷门合约长时间没有 tick 时，"最后一笔 tick 已经很旧"并不说明来源时钟不可信。
  - 需要按交易时段定义阈值，以及没有新 tick 时的处理方式；否则在 bar 边界下单的策略会被频繁阻断。
- **时钟偏差**：交易所时间与本机时间对比之前，要先估计本机时钟偏差。可以用登录回报里的交易所时间做初始校准，并记录偏差。
- **场所差异**：社区报告过一些 CTP 行情时间字段的差异，需要在 SimNow 实测核实后写进场所合同。示例涉及上期所（rb、hc）和郑商所（SA）。
  - 大商所夜盘的 `ActionDay` 可能等于交易日；
  - 郑商所的毫秒字段可能恒为 0；
  - 郑商所夜盘的 `TradingDay` 可能是自然日。

**建议**：在 §5.3 之后增加一张时序表，每一步写明失败时的行为：
