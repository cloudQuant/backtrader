## 4. 实测发现并已修复的缺陷

1. `CtpDirectWriteProvider.settlement_status` 把“完整查询但无当日确认”误判为 UNKNOWN（实际状态码为 failed/unknown 等）；改为按查询结果完整性判定 UNCONFIRMED。
2. 撤单使用去掉空格的 OrderSysID，CTP 按原始右对齐字符串匹配；改为优先用原会话 FrontID/SessionID/OrderRef，否则用原始 `order_sys_id_raw`。
3. Store 启动在 direct 模式仍执行 SDK 执行日志恢复（无日志，报 unproven）和托管余额读取；direct 模式改由 Broker 的账户事实与 live_state 负责。
4. SimNow 路由在 SDK 中的环境标签为 `demo`，示例 `MarketInstrumentKey` 用 `simnow` 时订阅报 `MARKET_STREAM_ROUTE_UNAVAILABLE`。
5. BT 行情订阅的身份检查只接受旧版 tick 身份类型，SDK provider 会话 owner 返回中立 `MarketStreamIdentityReceipt`；合同改为两者都按同一键与状态校验。
6. Feed 缺少合约最小变动价位时把每笔行情标为 `PRICE_TICK_UNKNOWN`（数据缺陷），保持 DELAYED、不生成 bar；示例配置增加 `contracts`（交易所、price_tick、乘数）写入 Store 合约元数据。
7. direct 订单缺少 `comminfo`，成交通知时 BT Trade 记账崩溃；提交时补齐。
8. 场所时间核对容差过窄：SimNow 登录返回的交易所时间比 NTP 校正后的本机时间约晚 2.1 s（整秒截断加传输延迟），原容差（粒度+误差界+0.5 s）判为不一致导致全部行情不可交易；容差改为粒度+误差界+已配置的延迟上限（默认 2 s），逐笔延迟仍按 D62-37 直接比较。
9. CTP 行情投影没有原生规则标识（`rules_hash` 为空），而合同要求可交易行情必须带质量合同引用；改为由 SDK 时钟资格策略在 provider 未提供时写入自己的策略引用（I62-09），连续性缺陷的行情仍不可交易。
10. CTP 行情客户端以原生 Join 观察线程启动，停止永远无法证明完成，Gateway 关闭报告 `UNSUBSCRIPTION_UNCERTAIN`/`CLOSE_FAILED`；改为无 Join 观察线程（I62-11）。交易客户端同类问题暂未修改（GAP，见 I62-11）。
11. Gateway 双合约示例第二个合约订阅失败（客户端 `CONTROL_OUTCOME_UNKNOWN`，服务端 `MARKET_SOURCE_DESCRIPTOR_UNAVAILABLE`）：CTP 行情 provider 对第一个合约等待认证与订阅确认，
    对后加入的合约发出订阅请求后立即返回；Gateway MarketHub 在同一次订阅调用里要求来源描述，而真实前置的订阅确认是异步到达的（SimNow 约 0.2 s），
    直连会话因自己轮询 `describe_source` 未暴露该问题。改为后加入合约等到前置确认（以连接超时为界）才算取得，确认缺失或被拒按原有路径使共享会话失效关闭
    （bt_api_ctp `052a93e`；同步/异步确认两种替身的 Gateway 集成测试，异步替身在修复前复现该失败）。
12. 修复 11 后双合约 Gateway 示例在 `BtApiStore.subscribe` 崩溃 `cannot pickle 'mappingproxy' object`：运行时事件脱敏遍历配置的秘密来源（含 Gateway 行情运行时），
    对 dataclass 使用 `dataclasses.asdict` 深拷贝，遇到行情客户端保存的启动快照（载荷为 mappingproxy）失败；是否出现取决于订阅时 Hub 是否已有快照，单合约也可能触发。
    改为原地遍历字段（覆盖范围不变、不复制）（backtrader `83c692fc3`）。
13. 恢复的待发单在开盘派发时被 SDK 本地拒绝 `ctp_direct_exchange_id_required`：空仓重启时 Broker 不知道合约交易所，CTP provider 在下单路径内解析交易所，触发当日全量合约目录查询（D62-11b/11c 实现），SimNow 上全量 `ReqQryInstrument` 60 s 不到 2000 行（全量超过 1 万），超出构建预算；其回报继续占用会话唯一的查询通道，单合约回退也被拒，Broker 在该调用内阻塞约 46 s。修复：BT direct 模式先使用配置的合约交易所（backtrader `8d219ad23`）；provider 下单路径不再启动全量查询，只用已有/已发布目录或单合约查询（0.3 s），全量改由显式预热接口执行（bt_api_ctp `cca6753`，I62-12a）。
14. 交易时段 RESTART 私有流使启动查询排在当日私有回报重放之后（SimNow 约 10 条/秒，20～90 s 以上），启动账户事实 10 s 超时后在途查询使后续查询全部 `-2`，示例启动被拒。修复：示例默认 QUICK，RESTART 可选；direct 启动恢复由当日委托/成交/持仓查询覆盖（backtrader `f02c9e2b2`，I62-01a）。遗留（GAP）：任一查询超时后在途期间同一会话的后续查询仍会 `-2`，客户端未在提交前等待在途查询结束（12:05 由 I62-14 关闭：新查询等待在途查询结束，等不到返回 `query_slot_busy`，bt_api_ctp `091c96e`）。
15. 示例策略在逐笔回调（`notify_tick`）里用 `data.close[0]` 定限价，而该回调发生在行情 Feed 载入下一行、数值尚未写入时（`close[0]` 读到 0），或 Feed 尚无任何行时取到占位数据（收盘价 0）：买单以 0+2 跳报出被场所拒。修复：价格取策略跟踪的该合约最新逐笔价，其次 `close[0]`、`close[-1]`，都无效时跳过并记录（backtrader `a61fc872b`、`fc3178bce`；第一次修复只回退到 `close[-1]`，使开局强制开仓被跳过且不重试，第二次修复改为优先最新逐笔价）。
16. 无效限价（-2.0）使 SDK `OrderRequest` 在 `broker.sell()` 内抛 `ValueError`、整个运行崩溃。修复：direct 预检对非有限或非正的限价、数量本地拒绝（`limit_price_invalid`、`order_size_invalid`），SDK 请求对象构造失败转为本地拒绝（`request_unrepresentable:…`），不预留、不发送（backtrader `3f40425f2`）。
17. SDK 时钟校验：一次 SNTP 交换丢失时 `refresh` 清除仍在有效期内的证据，后台线程再等满 300 s 才重测，而逐笔路径不会即时刷新，导致最长 5 分钟逐笔全部未校验、Broker 拒绝全部订单（一次 3 分钟运行 415 次本地拒绝）。修复：重测失败保留仍有效的证据（过期仍生效），失败后按 2、4、8… 秒重试（SDK `8c62d051`）。该次运行的直接证据（失败原因）未留存，按机制与现象推断；同时刻探测 SNTP 正常、场所时间核对一致（-1.5 s，容差 3.05 s）。
18. 验收工具（会话临时目录 `flatten_simnow.py`）取行情失败时未平仓，且以不完整的查询结果显示为空仓，下一示例首启空仓校验正确拒绝；改为重试取价并以完整查询核实空仓、最多三轮。
