1. 门禁这个设置不合理，应该是在bt_api_py里面设置，而不是在相应的接口里面设计，需要把门禁功能从bt_api_ctp, bt_api_okx, bt_api_binance等子包里面移动到bt_api_py里面

CTP 本身能下单吗？

  - 原生层面能。 bt_api_ctp 的 TraderClient 封装了 CTP 原生的报单和撤单。
  - 但每次写入都有门禁。 live_ctp_feed.py:1547 的 _ensure_execution_permitted 要求两件事：一是持有 SDK
    核心签发的执行能力，二是按合约一次性 arm。官方 SimNow 前置原来一律拒绝。这是迭代 22–41 为真实账户默认 fail-closed
    加的治理。
  - 我加的 simnow_direct_writes 开关让 feed 能在冻结白名单里的模拟前置上自己 arm。不过执行能力目前仍要靠 SDK
    执行会话来安装，所以不开执行会话时，CTP 还是写不了。


2. bt的下单流程需要修复一下，bt_api_execution是可选组件，并不是必须组件

BT 的 BtApiStore 在 SDK 模式下设了两道硬要求：
  - 必须配置 SDK 执行会话：启动时要做订单日志恢复（store_lifecycle.py:609），没有会话就拒绝启动。
  - 下单必须走"关联下单合同"（btapistore.py:749、2923），不调用 make_order。

  而 BtApi 一旦有执行会话，关联下单就自动走托管路由（bt_api.py:3934），需要发号器和 provider 运行时上下文；对 CTP
  来说就是整套托管执行运行时。结果就是 execution 在 BT 里成了必选项，层次正好反过来了。

3. 应该先实现一个基础的直连工作

 应不应该先有直连、再叠加组件？

  应该。合理的分层是：
  - 基础层：provider 加 bt_api_py 直连，包括行情订阅、账户/持仓/委托查询、下单撤单。不依赖任何可选组件就能工作。
  - 可选组件：execution（持久订单日志、托管执行）、risk（风控门）、monitor（监控）、gateway（跨进程、多策略共享连接）。
    按配置叠加，不配就不启用。

## 已确认的决策（2026-11-05）

以上三条为原始需求，保持原文。以下是后续讨论中已经确认的决定，实施计划见[迭代计划](迭代计划.md)。

| 编号 | 决定 |

| D62-01 写入准入范围 | 准入不区分模拟账户和实盘账户。写入由显式配置开启，开启后对所有环境的行为一致；把模拟账号（及对应前置）替换成实盘账号，就可以直接交易。准入层不做模拟/实盘判断，也不依赖模拟前置白名单。 |

| D62-04b2 回测和实盘共用序号 | 同一策略目录/UUID 下，回测与实盘共用同一条局部订单序列，重启后继续递增；并发运行统一协调以避免重号，回测不因此连接实盘账户。 |
| D62-04c1 策略身份区分 | 用户最新明确：策略 UUID 按独立策略目录实例生成并持久保存；同一目录的源码或参数变化不自动换号。需要区分的并发策略或不同参数组合使用独立目录。 |
| D62-04c2 账户区分 | 相同策略逻辑和参数运行于不同账户时也分配不同策略 ID；目标是在统一编号范围内区分订单，相同账户下并发实例按 D62-04c3。 |
| D62-04c3 独立实例区分 | 即使策略逻辑、参数及账户完全相同，同时启动的独立实例也使用不同策略 ID；同一目录实例重启仍须恢复原 ID，实例按 D62-04c4 的独立策略目录区分。 |
| D62-04c4 实例目录 | 每个策略实例有独立的策略目录；同一目录实例重启后继续使用原策略 ID，不同独立实例使用不同 ID。身份记录首次初始化、复制和迁移在设计时确定。 |
| D62-04c5 多机策略 UUID | 用户提出每个策略实例首次启动随机生成 UUID，保存在策略目录，重启读取原值，以适应多机器运行；UUID 版本和订单整数编码待设计确认。 |
| D62-04c6 历史策略迁移 | 已有策略的旧账本和关联记录迁移到策略 UUID；迁移须验证原身份归属、保存历史追溯、处理未决命令并完成对账，详细迁移与恢复规则见计划 §5.13。 |
| D62-04c7 目录身份不变 | 同一策略目录首次生成 UUID 后继续使用原 UUID，源码或参数变化不自动换号；策略版本、账户绑定和执行授权仍需依相应合同核验。 |

| D62-06b 默认刷新间隔 | direct 和启用 execution 均使用同一策略默认间隔：资金刷新 60 秒、持仓审计 5 分钟；可按策略显式配置，按场所限流与查询耗时调整并记录数据新鲜度。 |

| D62-31 待发单 DAY 有效期 | 策略指定 DAY 时从目标交易时段实际提交时按场所规则计算；绝对截止时间保持原值，不静默延长。 |
| D62-32 BT 真实验证前置 | BT direct 真实下单验证需等待 05e 跨时段待发与 62.06 恢复合同完成；62.03 已授权 SDK 隔离验证不证明 BT 放行。 |
| D62-33 订单类型 | 由策略选择订单类型；不新增非限价单框架统一拒绝规则。可按场所协议正确表达的如实透传、场所回报如实反馈；现有 SDK 无法表达时明确报告，不伪称场所拒绝或静默改变订单类型。 |
| D62-34 集合竞价 | 休市待发单默认等待对应连续交易开始且该目标有合格行情后再派发；不能在集合竞价结束时提前当作目标时段过期。 |
| D62-35 待发单顺序 | 同一策略多笔到期待发单按策略局部序号安排实际发送，不必等待前单成交；撤单和对账可优先处理。 |
| D62-36 待发时段判断 | 使用已核验交易日历与目标行情判断待发时段，不强制合约状态推送；连接异常的业务风控后续由可选 risk 处理，SDK/provider 保留真实连接和报单结果，不能假称已发送。 |
| D62-37 延迟阈值判断 | 来源到接收延迟按测得值比较阈值，不把时钟误差上界叠加作最坏情况判断；来源与接收时间的可信性、接收后年龄及其他条件仍分别核验。 |
| D62-10 editable 元数据 | CTP 先备份并定点刷新入口点元数据，独立进程校验实际安装来源及插件发现，失败恢复并评估重装。 |
| D62-12 示例目录命名 | 实盘策略目录使用 `_direct`、`_gateway` 后缀区分两种接入，保持自包含。 |
| D62-07 OKX、Binance | 补齐 direct 基础层（行情流、账户/持仓/委托查询、下单撤单），并用 demo/testnet 账户验证。 |
