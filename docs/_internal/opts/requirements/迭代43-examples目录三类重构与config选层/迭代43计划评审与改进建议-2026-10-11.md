## 实施前必须修订的问题

### P1 01 config 默认值与 CLI 覆盖规则存在冲突

**计划定位：** 第 13、157、166、169 行。

“CLI 显式覆盖”与“冲突取更保守方”不是同一个规则。例如 config 缺省为 dry 时，旧命令 `--live` 应继续进入 live；如果把缺省 dry 也当成限制上限，则旧命令会被降成 dry，违反向后兼容。config 明确写 backtest、CLI 写 live 时，静默改跑 backtest 也容易让操作人误判实际执行通道。现有入口还没有 `--dry`，用户无法用明确参数覆盖一个 `tier: live` 的配置。

**建议：** 把“选层意图”和“写授权”分开，删除含糊的排序规则，先固定如下契约，再实现 dispatcher。下表是建议的冲突策略，保留方案 B 的无 flag 行为。

| config entry.tier | 无模式参数 | `--dry` 新增 | `--replay` | `--live` |
| --- | --- | --- | --- | --- |
| 缺省 | dry | dry | replay | live |
| dry | dry | dry | BLOCKED 配置冲突 | BLOCKED 配置冲突 |
| backtest | replay 兼容别名 | dry | replay | BLOCKED 配置冲突 |
| live | live 只读观察 | dry | replay | live |

这里的 `backtest → replay` 必须按下文明确其能力范围。非法值、错误类型、`entry: null`、配置解析失败应在产生 provider 副作用前 BLOCKED；不能回落到 live。CLI 模式参数互斥，未知参数继续拒绝。

`--allow-write` 独立于模式参数：它不选择 live，也不因出现在离线命令中而启用写。有效通道为 live 时，仍须满足原来的写授权、环境、候选准入与有界操作条件。证据至少记录 config 请求通道、CLI 请求通道、最终通道、选择原因和写授权结果。

**验收补充：** 分派测试断言实际调用了哪个 handler、未调用哪些 handler，以及是否发生 provider 初始化；不能只断言 exit code。还要单独覆盖 `--allow-write`、`--mechanical-smoke`、`--drill`、冲突 flag 和非法配置，4×4 表不能代替这些维度。分派结果只决定处理函数，不能预先保证业务结果 PASS。

### P1 02 六个现有 live 入口没有计划承诺的无写观察路径

**计划定位：** 第 13、157、160、170 行。

公开代码已明确区分两种入口：

| 示例 | 当前无 allow-write 的 live 行为 | 源码定位 |
| --- | --- | --- |
| 012_1、012_2 | `write_consent_missing`，返回 BLOCKED | 两个 `run.py:167`、`:168` 起的 `run_live` |
| 013_1、013_2、013_3 | 在进入实际运行前要求写授权 | 各 `run.py:510`、`:511`、`:472` 起的 `run_live` |

因此，把 `tier: live` 直接映射到现有 `run_live`，前六个示例仍然 BLOCKED；去掉原授权判断则改变了写门禁。两种做法都不满足草案承诺。

**建议：** 将 R5 拆成两个可验收的小轮次：先增加严格选层与配置兼容；再给缺少能力的示例补无写观察处理函数。已有写 drill 继续保留原入口和授权条件，观察函数不能调用该写函数后依赖“没有信号”来避免下单。暂时不支持观察的示例必须明确返回 `live_observation_unavailable`，不能宣称该例的 config-live 功能已经完成。

**验收补充：** 观察路径在真实生产加载方式下，使用 fake provider 叶子验证连接、订阅或查询、超时与正常关闭，并用写调用陷阱证明 submit/cancel 均未进入。离线默认与显式 `--dry` 必须在 provider 导入或初始化前完成。实际 provider 观察验收与这些源码测试分别登记，不借此重复历史已通过的账户用例。

### P1 04 搬迁后的路径修复与旧 manifest SHA 不变无法同时成立

**计划定位：** 第 88、121、128、143 至 145 行。

这里需要区分“业务语义不变”与“源码字节不变”：

- `012_1/run.py:27`、`012_2/run.py:28` 用 `HERE.parents[1]` 定位仓库根；加一层 unified 后会定位到 examples，必须修复运行源码中的根路径计算。其他 013 至 015 入口也有同类定位。
- `012_1/legacy_runner.py:136` 从 `HERE.parent` 找根 manifest；C 类先搬而根 manifest 到 R4 才搬，会产生两个连续路径状态，必须分别可运行。
- `scripts/refresh_cross_exchange_local_manifests.py:78` 已把 folder-local 的 `resolved_example_path` 设置为 `.`；它不是简单插入 unified 前缀。`:79` 至 `:88` 则把实际 `run.py` 字节哈希写入 candidate 并重算指纹。
- 根 manifest 的 `resolved_example_path` 当前从 examples 根解析；移动至 `_support` 后，基准目录再次改变。`strategy_candidate_approval.py:32` 也钉住 canonical manifest 路径。

因此，修正了 `run.py` 的字节，再要求 folder-local manifest 重算后仍等于旧 SHA，是不可实现的门禁。只保住旧 SHA 又会留下错误的根路径。

**建议：** R2 明确允许“必要路径适配”，同时显式重绑受影响的 runner hash、candidate hash 与 canonical/folder-local manifest。未修改 payload 才要求字节一致；发生适配的 payload 记录旧路径、新路径、旧 SHA、新 SHA 与改动原因。保持 strategy ID、风险配置、准入状态和授权语义不变，新的指纹不继承旧签名授权。

R2 与 R4 的 manifest 定位依赖必须一起设计：可以提前准备支持文件的最终定位，或保留明确的过渡定位并在 R4 再受控重绑；每个提交都应可运行。不能把 R2 的失败拖到 R4 才补齐。

### P1 06 自包含测试会把整个类别误当成一个示例

**计划定位：** 第 116、126、145、176 行。

`tests/unit/test_examples_self_contained.py:116` 只枚举 `EXAMPLES.iterdir()`；`:129` 将该目录下递归找到的所有 Python 模块视为本地模块。搬迁后参数会变成 backtest、live、unified，而不再是每个示例叶子。结果可能把同一类别内的跨示例依赖当成本地依赖，弱化目前的自包含边界；按 folder.name 配置的可选依赖与兼容例外也会失效。

### P2 08 按可运行能力归类并区分 replay 与 backtest

草案第 59 行的 import 关键词只能辅助发现，不能证明 live 能力。被封死的 007 legacy 入口即使导入 CTP，也不能因加了 config 分派而恢复为可运行 live；sample 与 L2 fixture 也不应因为有离线路径就被宣称为统一双通道示例。已由上述 source managed L2 退役提交删除的示例条目，应从最终搬迁清单移除，不重新创建。

建议每个示例登记离线入口、在线入口、写能力、当前是否可用与最小启动命令。这是轻量清单，可复用旧新路径映射，不需要再造一套运行框架。缺能力的条目保留明确 BLOCKED 状态或归为支持 fixture，不能为了符合三类模型扩展原本关闭的路由。

`012_1/legacy_runner.py:1006` 起的 replay 是公式与冻结 fixture 验证，并不等同于历史行情驱动的完整策略回测。若继续使用 `tier: backtest` 作为别名，README 与 evidence 必须明确 `effective_mode: replay` 及证据级别；更清晰的配置词是 replay，未来真正 backtest 再另行支持。A 类的“零 broker 写”也应改成“零 provider 网络与真实账户写”，模拟 Broker 的买卖撮合属于正常回测。

### P2 09 四件套应定义核心入口而非强制只剩四个文件

现有 C 类需要 `legacy_runner.py`、本地支持副本、manifest 和测试 fixture；002/003/011 有多个教学入口，017 还有 models 与 reports 等材料。“保留核心四件套”可实施，“目录只能有四个文件”会破坏现有能力。

建议定义核心四件套及允许的支持目录，主 README 列明可运行入口与数据依赖。R6 中“未被其他目录引用就删除”也不适合 CLI 脚本、notebook 和模型样本；这些文件本来可能没有 Python import 引用。删除应依据公开入口清单、用途、可重建性与实际依赖，而不是零引用计数。

根散落脚本四件套化、下载工具改造与过时 writer collector 的处置，均可能改变行为。将它们拆成后续小轮次，避免作为收口杂项混入搬迁；不恢复 collector，也不把旧 inventory 文档当成当前验收事实。数据移动若影响消费者，应与对应路径修复同轮交付，不能让前一轮示例暂时失效。

### P2 10 补齐私有文件迁移与历史引用的边界

`.gitignore` 先加新规则的做法正确，但只能证明路径被忽略，不能证明私有配置已迁移、ACL 未变、加载器没有回退到错误输入。`git mv` 的跟踪面清单也覆盖不了本地忽略文件。

建议每轮分别登记跟踪文件、忽略的私有文件与可重建产物。公共评审和普通迁移脚本只处理公开材料与必要元数据；私有配置的路径迁移由原受控流程处理，验证新路径访问规则、缺文件时拒绝及旧路径不被隐式尝试。不得为了搬迁把私有 config 加入 Git，也不读取或输出其内容。

不要把 `logs/`、`evidence/`、模型或 journal 统称垃圾后递归删除。已消耗的 claim、generation、结果与保留 host 均遵循原限制；目录重组不能清理它们以便重跑。

草案第 85、91 行还要求改冻结 oracle 与冻结 Root 激活脚本，和历史材料保持不变的原则有张力。引用清单应标注活跃源码、活跃文档、冻结测试材料、历史证据四种角色：活跃引用随迁移修正；冻结材料保留旧字节，通过新适配器或新版本承接；旧路径扫描只要求活跃范围零悬空引用。历史 AGENTS 段落也宜追加现状说明，而非统一改写当时的事实。

| R1 | A 类搬迁、必要根路径与数据路径适配、自包含叶子发现修复 | 已有入口在规定 cwd 与离线输入下可运行；相关策略回归通过；无边界放宽 |
| R2 | C 类搬迁、注册引用和属性更新、012_x 必要 manifest 重绑 | 业务语义不变；每个受影响 payload 的字节变化可解释；注册冒烟无新增回归 |
| R3 | 000 整体搬迁及列明的根定位适配，optional16 保持内部相邻关系 | 99 case ID 与判据不变；三套路径定位、私有配置拒绝条件、矩阵 dry 均符合基线 |
| R4 | `_support` 与公共 data 归位，权威 manifest 定位最终收敛 | 本地示例独立性和批准状态不变；没有跨轮悬空路径 |
| R5a | 严格入口配置、确定性 dispatcher、CLI dry 覆盖、旧配置兼容 | 分派与副作用矩阵通过；未知字段拒绝与 runtime 授权边界不变 |
| R5b | 逐例补齐缺少的无写观察能力，独立登记验收 | 无写生命周期有证据；不支持项明确 BLOCKED；不冒充实际账户通过 |
| R6 | 索引、活跃引用扫描、文档与针对性收口检查 | 已完成范围可复现；遗留项有归属；不混入新策略、旧工具修复和无依据删除 |

A 类搬迁影响 016/017 的策略回归时，保留一次完整策略验收；其余轮次优先运行路径与行为受影响的检查，最终做一次约定的整体回归。没有新变更或新风险时，不为了交付重复已经通过的全套验收。`make lint/format-check` 若有既有全仓失败，按同一冻结基线验证本轮增量，不能顺手格式化历史钉死材料。

回滚需要按依赖关系处理：R5b 依赖 R5a，后续路径提交依赖前面的搬迁提交，不能在后续轮次落地后随意单独 revert 早期搬迁。私有配置位置和运行产物也不由 Git revert 自动恢复，应另列对应恢复步骤。

## 通过修订的判据

1. 唯一映射表覆盖全部公开条目，optional16 新路径不再矛盾，轮次编号和引用一致。
2. 明确 config 与 CLI 的确定性真值表、缺省兼容、非法输入拒绝和写授权关系。
3. 承认并拆出缺失的观察路径与严格 schema 适配，不把它们当成单纯改 dispatch。
4. 将“所有旧 SHA 不变”改成未修改字节保持、必要适配受控重绑，认证根路径有专项测试。
5. 更新叶子级自包含测试与活跃范围守卫，冻结可重现的失败基线并要求无新增回归。
6. 四件套、私有迁移、历史材料及后续清理的范围清楚，每轮可以独立审阅和提交。

满足以上条件后，这个迭代可以按现有 dev 小轮次流程实施。目录重组本身不需要扩展 SDK、注册 live runner 或重新执行历史已消耗的账户调用。
