## 2. 核心判断

### 2.1 当前最高优先级不是新功能，而是基线收口

项目已有大量高价值能力：实盘 broker/store、HFT/midfreq、指标迁移、报告与可视化、CI 工具链、3000+ 测试。但当前本地工作区有 316 个未提交变更，且核心包 lint/format/security 已出现小回流。继续叠加功能会让验收边界变得不可靠。

### 2.2 迭代13 的代码迁移已落地，但验证债仍未完全关闭

迭代13 文档显示功能测试内联指标迁移已完成，`bt.indicators.Xxx` 统一入口已建立。但本次检查发现：

- 核心包新增/改动文件仍有 ruff、black、isort 问题。
- 功能策略测试目录仍有大量 lint 问题，尤其 `F821 undefined-name` 需要优先确认是否为迁移副作用。
- 迭代13 台账中 `M6-c 全量本地验收`、`M6-d 远端 CI/CD 验收`仍是待执行项。

### 2.3 安全基线整体健康，但 Bandit Low 回流需要立刻修

当前 High/Medium 仍为 0，说明迭代12 的安全主线基本有效。但 `backtrader/indicators/contrib/moving_average_fn_indicator.py:74` 出现 `B112 try/except/continue`，与迭代12 “未 triage Low 基线=0”的 CI 看板冲突。

### 2.4 类型检查策略需要重新定锚

项目配置仍声明 `mypy.python_version = "3.8"`，CI 矩阵也包含 Python 3.8。但本地 mypy 1.20.2 已不接受 `python_version=3.8`。当前 CI 里安装的是未固定版本的 `mypy`，未来很容易因为工具版本漂移导致 lint 作业不稳定。

建议二选一：

1. 若继续支持 Python 3.8：固定 mypy 到仍支持 `python_version=3.8` 的版本，并记录工具链上限。
2. 若准备放弃 Python 3.8：先做产品/兼容性决策，再同步 CI matrix、README、setup/pyproject 和用户迁移说明。

在没有明确产品决策前，保守选择是继续支持 Python 3.8，并固定 mypy。

### 2.5 高复杂度函数不能直接重构，必须先补 golden/性能基线

`TickBroker.process_orderbook` 当前 CC=161，是最高复杂度热点；`Cerebro._runnext`、line system、plot 旧同步路径也属于高复杂度区域。这些代码多半承载历史兼容行为，直接拆分风险高。应先建立行为基线和性能基线，再做小步拆分。

## 3. 改进方向分级

### P0：立即收口项

1. 修复核心包当前 lint/format/security 回流：
   - `backtrader/indicators/supertrend.py` 的 2 个 `PIE790`
   - `backtrader/stores/btapistore.py` 的 2 个 `RET501`
   - `backtrader/brokers/hft/__init__.py` black 格式
   - `backtrader/utils/get_metrics.py` black/isort
   - `backtrader/indicators/contrib/moving_average_fn_indicator.py:74` Bandit B112
2. 固定或调整 mypy 工具链，消除 `python_version=3.8` 与 mypy 1.20+ 的冲突。
3. 重新跑核心质量门禁，确认 CI lint 不会红。

### P1：验证债收口

1. 完成迭代13 的本地验收：
   - 迁移影响的指标测试全量通过。
   - `tests/functional/strategies` 不再出现内联 `Indicator` 子类定义。
   - 代表性指标做逐 bar 等价验证，补入 `指标迁移矩阵.md`。
2. 对 316 个未提交变更做分组：
   - 指标迁移
   - HFT / tickbroker / midfreq
   - BtApiStore / live broker
   - 示例与穿透式认证脚本
   - 测试与工具脚本
3. 每组变更独立跑最小验收，避免一个大提交同时承载多个风险面。

### P2：稳定性与实盘可靠性

1. 对实盘路径建立订单生命周期一致性检查：
   - submit / accepted / partial / completed / canceled / rejected
   - 本地 order ref 与外部 order id 映射
   - broker/store/feed 断线重连后的状态恢复
2. 对 `BtApiStore`、`BtApiBroker`、`TickBroker` 做可观测性补强：
   - runtime event schema 固化
   - 异常日志上下文标准化
   - 关键状态变化可追踪
3. 对 live/sandbox 测试做凭证隔离和跳过策略复核，确保无凭证时 collection 不失败，有凭证时能跑认证场景。

### P3：复杂度、覆盖率与性能

1. 给高风险模块补 fresh coverage baseline：
   - `backtrader/brokers/tickbroker.py`
   - `backtrader/brokers/hft/*`
   - `backtrader/stores/btapistore.py`
   - `backtrader/feeds/btapifeed.py`
   - `backtrader/indicators/*_ext.py` 与 `contrib`
2. 对 `TickBroker.process_orderbook` 先补 golden replay，再拆分撮合阶段：
   - 输入标准化
   - 队列位置更新
   - 成交判定
   - 手续费/滑点/延迟
   - 状态记录
3. 对 HFT/midfreq 建立性能基线：
   - replay 耗时
   - peak memory
   - event throughput
   - 与 hftbacktest 对齐误差

### P4：仓库与文档治理

1. 修复 BMAD help 缺失：
   - 恢复 `_bmad/core/tasks/help.md`，或更新 `.windsurf/workflows/bmad-help.md` 指向当前实际任务文件。
2. 更新 `PROJECT_STATUS.md`，把 2026-06-13 的真实测试数量、覆盖率、质量门禁状态写入。
3. 清理或忽略本地构建/缓存产物：
   - `build/`
   - `dist/`
   - `htmlcov/`
   - `__pycache__/`
   - `.coverage`
4. 明确功能策略测试的 lint 策略：
   - 如果它们是生成/迁移资产，应单独建立有限 lint profile。
   - 但 `F821 undefined-name` 应作为 correctness 类问题优先清零。

## 7. 风险与边界

- 当前存在大量未提交改动，任何计划执行前都应先确认这些变更是否属于同一作者/同一任务。
