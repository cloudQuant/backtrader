## 0. 结论

- 计划和设计对信任边界的处理是谨慎的：身份由服务端注入，scope 绑定，游标做完整性校验；不声称 exactly-once；队列有界；“未采集”与“零”分开表示。这些都与“monitor 只观察”一致。
- 但它的重心在合同与管道，缺少运营真正需要的几样东西：
  - 第一版告警目录；
  - 至少一个推送出口；
  - 按交易时段生效的规则；
  - 对监控本身的存活监督。
- 另外两点：心跳 ACK 的文字冲突需要给出解法（建议采用设计 §5 的候选 1）；68 没有需求原文。
- 本轮共 9 条：P1 2 条，P2 6 条，P3 1 条。

## 2. 发现与建议

### RV68-01（P1）心跳 ACK 的文字冲突：建议以“中继推送请求的响应”作为 ACK（设计 §5 候选 1）

- **定位**：设计 §5；计划 §3.4；63 计划 §3.14 与 §4.0 D63-36 之间的冲突。
- **建议**：采用候选 1。
  - Gateway 中继经一条与业务事件分开的优先通道，向 monitor 持久入口推送心跳；
  - monitor 在同一条认证连接上返回**响应**，确认该心跳“已持久接收（事务已提交）”；
  - 中继据此推进 ACK 进度，并把“最近确认的心跳的发出时间”交给 Gateway 的存活判定器。
- **为什么这能解决冲突**：monitor 从不主动发起连接或消息，符合 D63-36“monitor 完全被动”的字面；确认又绑定了 monitor 的 principal、中继代际和心跳 ID，满足 63 §3.14 的要求。
- **确认点**：取“持久提交之后”，不取“已收到”。否则 monitor 磁盘写满时仍会被判为存活。
- **理由**：“推送 + 响应确认”是 Prometheus remote-write、Kafka 生产者 acks 等系统的常见做法。候选 2（monitor 主动确认）需要 monitor 持有一条通往 Gateway 的写通道，与“只观察”的定位不符，也多了一个需要认证的方向。
- **附带建议（D68-02）**：在 required 模式下，如果 monitor 版本提供不了这种带绑定的确认，Gateway 直接拒绝启动，而不是启动后等宽限期结束再施加 STOP_NEW。（问题 Q68-01）

### RV68-02（P1）缺少告警目录和推送出口：只做本地记录，运营几乎得不到通知

- **定位**：计划 §3.3、§2（“外部通知通道……不默认纳入”）、D68-04（建议首轮只做本地告警记录）。
- **问题**：监控的核心价值，是在需要人介入时通知到人。68 目前定义了指标、规则框架和本地告警记录，但缺两样东西：第一版必须覆盖的告警清单，以及任何推送出口。

**建议 1：告警目录 v1。** 在 68.01 冻结（新增候选 D68-06）。每条告警写明来源、条件、持续时长（`for`）、级别和处置手册链接。下表数值只是示例，实际由运营配置：

| 级别 | 告警 | 条件示例 | 来源 |
| --- | --- | --- | --- |
| P1 | Gateway 交易 owner 不可用 | 交易时段内 `session_status` 不可达超过 15 s | Gateway 心跳 / runtime |
| P1 | TD 会话断开或回报中断 | 断开或 `stream_gap` 持续超过 10 s | Gateway |
| P1 | 存在 UNKNOWN 订单 | UNKNOWN 数 > 0，持续超过 30 s | Gateway |
| P1 | 账户合计对账为 SHORTFALL 或 UNEXPLAINED_SURPLUS | 任一合约 | Gateway |
| P1 | 急停生效 | 出现任一 FREEZE 或 DRAIN 原因 | Gateway |
| P1 | 策略进程 CRASHED、KILLED 或 LOST | — | runtime |
| P2 | 行情 DELAYED | 交易时段内超过 10 s | Gateway MarketHub |
| P2 | risk 越限锁存，或 risk 不可用 | — | risk |
| P2 | 母单冻结，或子单 UNKNOWN | — | execution |
| P2 | 报撤单计数接近阈值 | 达到阈值的 80% | risk / Gateway |
| P2 | 中继积压或游标 gap | — | Monitor |
| P3 | 磁盘水位、时钟偏差、密钥或证书即将到期 | — | 主机 |

**建议 2：推送出口。**

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| a | 只做本地记录（D68-04 的建议） | 最简单 | 没有人会被通知 |
| **b** | Monitor 内置一个最小 webhook 出口：HTTP POST，带重试、限速和去重键；用模板生成企业微信、钉钉、飞书、Telegram、Slack 兼容的消息格式 | 一个出口覆盖常用即时通讯工具 | 要处理网络失败；webhook URL 要按秘密保管 |
| c | 导出到 Prometheus Alertmanager，由它负责分组、静默、抑制和路由 [S11] | 成熟、功能全 | 运营要部署整套 Prometheus |

- **建议**：b，c 作为可选。注意：Monitor 不能导入 backtrader，所以不能直接复用 `backtrader/notifications`，只能借鉴其消息格式设计。（问题 Q68-02）

### RV68-03（P2）规则要区分交易时段，否则休市时会大量误报

- **定位**：§3.3 阈值规则（窗口、时区等）；“67 日历事件仅为未来可选来源，不作为前置”。
- **问题**：行情陈旧、主循环停滞、Gateway 心跳这类规则，在午休、日夜盘之间、周末和节假日都会误报。告警一多，真正的告警反而容易被忽略。
- **建议**：
  1. Gateway 按合约或交易所发布 `session_state` 事件（交易中/休市），规则可设为“仅在交易时段生效”；
  2. 67 交付之前，支持运营手工配置固定时间窗和静默窗口（维护窗口）；
  3. 67 交付之后，改用日历数据。

### RV68-04（P2）谁来监控监控：不开 required 时，monitor 失联没人会发现

- **问题**：D63-36 的存活判定只在打开 `monitor_required` 时由 Gateway 使用。它缺省是关闭的，这时 monitor 停了也没人知道，运营还以为告警链路一切正常。
- **建议**：
  1. Gateway 的 `session_status` 始终公布“monitor 最近一次确认距今多久”（RV63-10），并在 runtime 的 `status` 中显示；
  2. Monitor 定期向推送出口发一条低级别的“看门狗”心跳，或由外部服务在心跳缺失时告警（dead man's switch）；
  3. 由 runtime 监督 monitor 进程（RV66-02 的服务单元）。

### RV68-05（P2）告警卫生：分组、抑制、静默、持续时长

- **建议**在 D68-04 中写明以下规则：
  - 同源告警按（规则、范围）分组；
  - “Gateway 不可用”生效时，抑制它的下游告警（行情陈旧、回报中断等），参照 Alertmanager 的 inhibition [S11]；
  - 运营可设置静默（维护窗口）；
  - 每条规则都有持续时长（`for`），避免抖动 [S12]；
  - 恢复通知可选。

### RV68-06（P2）保留与清理（D68-03）：建议按交易日分区

- **建议**：
  - 持久事件按交易日分区，每天一个 SQLite 文件或一个分区表；
  - 保留 N 个交易日后归档或删除，当日分区只追加；
  - 磁盘水位和 WAL 大小单独告警。
- **好处**：保留期与清理都简单、可审计，不必在大表上做删除和 VACUUM。

### RV68-07（P2）指标与导出采用通用标准，不自建时序库

- **建议**：
  - 指标的命名和类型遵循 OpenTelemetry/Prometheus 的约定 [S27][S12]；
  - Monitor 自己的 SQLite 只存交易事件和审计记录；
  - 时序存储和看板交给 Prometheus/Grafana（可选）；
  - 不在 68 内实现时序聚合和查询语言。

### RV68-08（P3）68 没有需求原文

- 63、64、65、66 都有需求原文，68 没有；与 monitor 相关的用户原话（S-10、S-20、D63-36）分散在 63 的需求原文里。
- **建议**：新建 68 需求原文，逐条链接原话的出处（RVX-07）。

### RV68-09（P2）最小事件集 v1 应与 63.12 共同冻结成一张表

- **定位**：计划 §3.1：“最小来源包含 63.12 确认的命令结果和拒绝码、UNKNOWN、会话/回报、日切、急停状态、对账摘要、配额和中继健康”。
- **建议**：在合同注册表（RVX-02）中给出一张事件类型表：类型名、owner、字段白名单、序号与 epoch、是否持久、对应的告警。把它作为 63.12 与 68.03 共同的验收依据，否则两边会各写各的。
