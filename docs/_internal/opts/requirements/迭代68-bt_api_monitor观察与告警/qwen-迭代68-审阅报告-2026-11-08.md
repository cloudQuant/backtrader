## 4. 发现与建议

### QW68-01（P1）告警目录 v1 仍未冻结成表（RV68-02 遗留）

- **定位**：计划 §3.3（D68-08 段、行情中断告警段、D63-48/49 段）、§7 D68-04；设计 §6；复核清单 §6 M4。
- **问题**：通知渠道与投递合同已由 D68-08 写全，但复核清单 M4 点名的告警类别（资金/数据未知、服务失活、队列/磁盘、UNKNOWN、母单冻结、行情恢复/最终失败）仍散落在三处散文段落；没有表格，没有级别模型（“高优先级”仅计划行情告警一句），没有 `for` 持续时长列，没有处置手册链接列；D68-04 仍写“目录待冻结”。目录缺表使 68.04 的验收无法逐行对应，服务失活、队列/磁盘等类别存在漏实现（漏报）风险。
- **建议**：68.01 冻结告警目录 v1 草表（建议沿用 11-07 报告的新增候选编号 D68-06），列：告警名｜来源事件/指标｜条件（数值一律写“显式配置”，不发明阈值）｜`for`｜级别｜恢复条件｜处置手册链接｜对应验收步骤。行集合至少覆盖：Monitor 失联 cause（required，Q34）、Gateway 行情恢复超时/恢复/最终失败（D68-07）、UNKNOWN 产生/解决（D63-04）、D63-48 差额告警、D63-49 拒单展示（不误报为差额）、母单冻结/子单 UNKNOWN（65）、中继积压/游标 gap、队列/磁盘/WAL 水位、认证失败、导出与 Webhook 投递失败、服务失活。
- **理由**：RV68-02 建议 1 与复核清单 M4 均要求具体目录；无目录则“必需事件目录、保留期和容量预算”（D68-04）没有验收载体；`for`/pending→firing 是防告警抖动的通行做法 [S12]。
- **验收**：68.01 交付物含该表且表内无发明数值；每行映射到 68.04/68.05 的测试用例或显式标 NOT_RUN；63.12 与 68.03 共同引用。

### QW68-02（P2）规则模型缺 `for`、级别、静默窗口与通用恢复通知语义（RV68-05 遗留）

- **定位**：设计 §6 规则冻结清单（“版本、窗口与时区、最少样本、迟到/乱序、触发/恢复、抑制、去重键和上限”）；计划 §3.3。
- **问题**：清单没有 pending→firing 的 `for` 持续时长（“窗口”不蕴含滞回）；没有静默/维护窗口配置；恢复通知是否逐规则可选未定义；级别字段缺失，导致行情告警只能用孤立的“高优先级”措辞。
- **建议**：68.01 规则 schema 增加：`for`（允许显式 0）、级别枚举、静默窗口（运营显式配置，与交易日历语义分开，见 QW68-03）、恢复通知开关；抑制沿用现有要求并写明引用关系（哪条告警抑制哪些下游告警）。
- **理由**：Alertmanager 的分组/抑制/静默/路由语义 [S11]、Prometheus `for` [S12]；缺静默窗口时维护期告警会淹没真实告警。
- **验收**：规则 schema 冻结文档含上述字段；UNIT 覆盖 `for` 未满不触发、期满触发、中途恢复不触发、静默窗口内抑制、恢复通知开/关。

### QW68-03（P2）“交易时段”的真值来源未定义（RV68-03 遗留）

- **定位**：计划 §3.3 行情中断告警“建议按交易时段计”；§3.1“67 日历事件仅为未来可选来源，不作为前置”。
- **问题**：67 不是前置且未交付，正文没有说明规则里“交易时段”从哪来。复核清单 §7 明确“不把固定时间窗冒充有效交易日历”，11-07 建议的“手工固定时间窗”过渡方案不能照搬。缺会话来源时，午休、日夜盘间隙与节假日会误报，或规则被迫整体关闭。
- **建议**：明确时段条件来源的优先次序：(1) Gateway 会话/结算/日切事件（63.12 最小集已含“会话与结算、日切”）；(2) 67 交付后接日历；(3) 两者皆不可用时，该规则的时段条件显式标为不可用/`not_collected`，规则退化为全天计时须显式配置并告警文案注明，不静默冒充。运营静默窗口（QW68-02）只用于维护场景。
- **理由**：M1 同源原则——不能用弱证据冒充强语义；68 正文自身“失效、重启、规则过期或来源缺失不得默认为健康”。
- **验收**：告警目录（QW68-01）每行含“时段来源”列；FAKE 覆盖休市时段规则不触发、时段来源缺失时显式不可用。

### QW68-04（P2）非 required 模式下 Monitor 自身无监督机制（RV68-04 遗留）

- **定位**：设计 §6“满盘或自身故障可能连本地失败记录都无法写入，必要时使用独立外部观察”；计划 §2“66 首期不监督这些服务”。
- **问题**：`monitor_required=false`（缺省）时 Monitor 失活无人发现，运营会误以为告警链路正常；正文只有一句散文，无机制、无决定项。runtime 监督路径已被 D66-02 关闭，不应重开。

- **理由**：常燃 Watchdog 告警是 kube-prometheus 生态验证告警链路端到端可用的通行做法 [S29]；RV68-04 原建议 1/2 在本轮文档中均未落地。
