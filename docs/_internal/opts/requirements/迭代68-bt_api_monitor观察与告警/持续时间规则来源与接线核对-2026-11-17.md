# 持续时间规则：来源与接线核对（2026-11-17）

状态：**本地来源与认证转发已通过限定验证 / 完整持续时间未验收**。本文记录公开源码、已实现切片和后续边界；不构成实际来源认证证明或新增用户决定。主任务仍是 63–68 五组件联合验收；D68-10 的持续时间功能尚未完成，现有正数 `for_seconds` 拒绝保护保持。

## 已确认的产品缺口

1. SDK `monitor_service_host` 只装配 `events.append` 与 heartbeat 两个监听；没有装配 `AlertCatalogRouter`、持久持续计时或 evaluator 工作线程。接收 ACK 只证明事件入库，不证明告警已经计算。
2. Monitor `AlertSourceAdapter` 目前只是本地扩展点。注册和可用标志不是远端认证或完整时间覆盖。已发现并修复 `poll()` 未约束 adapter 与规则来源对应的问题；具体版本和验证见[联合记录](../迭代63-Gateway统一转发与多策略共享会话/迭代63-68联合验收与修复记录-2026-11-16.md)。
3. Gateway 行情 Hub 是有界内存回放；`ServiceMarketMonitorRelay` 是 best-effort。连续序号和两个相同快照不能证明中间一直成立，重启、队列丢失或缺失样本不能补成正常或异常时间。
4. 现有 `calendar.windows.v1` 只支持明确的模拟范围合同，且当前服务只授权 STRATEGY_CLIENT；不能让 Monitor 冒用策略身份或把 `COMPLETE`、`DEPLOYMENT_DECLARED_UNVERIFIED` 当作真实日历权威。

## 实际来源位置与可证明范围

核对 CTP `fdd3f82` 的 `src/bt_api_ctp/market_provider.py` 与 `feeds/live_ctp_feed.py`，以及 SDK `gateway_owner_market.py`。完整原生回调、provider 状态机、Hub epoch 和最终客户端交付没有共同的单一锁或现成持久日志。

可实施的保守计时起点是 owner 线程实际进入 `_begin_source_recovery` 的观察时刻；状态定义为 **owner 持有恢复栅栏，Gateway 尚不能从该 provider 读取**。它不是物理网络断开的精确起点，也不覆盖 owner 尚未观察到的时间。`reset_pending` 仍属于该状态，不能沿用 `source_recovery_state == None` 推断恢复。

必须覆盖的变更点：

| 入口/变化 | 持续区间处理 |
| --- | --- |
| `_begin_source_recovery` | 新 episode；在完整范围、owner/进程代际和时钟可比较时开始记录，不追溯原生断线起点。 |
| `_start_next_source_recovery_attempt` | 仅更换尝试对象；仍为同一 episode，重试不能清零累计或伪造恢复。 |
| `reset_pending` 再断线，临时清空再同步重入 | 连续异常或 UNKNOWN；中间的临时 None 不能输出 RECOVERED。 |
| `acknowledge_source_epoch_reset` | 最后一个 handle ACK 本身仍不足以证明恢复；需要同一时点核对新 scope、代际、完整目标成员和可读性。 |
| `_unsubscribe_during_recovery` | 成员集合改变；被退订范围为 UNKNOWN/停止观察，不能把剩余成员满足 ACK 当成原完整范围恢复。 |
| `_reset_active_stream`、close、最后退订 | 结束可证明覆盖，保留未决异常；不自动恢复。 |
| begin 前的失败关闭、回调协议失败 | 不能从“尚未创建 recovery 对象”推断正常；独立最终失败事实或 UNKNOWN。 |

`_check_owner` 约束状态机写入线程。native callback 和异步 stop/start worker 不会自行清空 `_source_recovery`，因而在上述 owner 序列边界之间记录“已观察恢复栅栏持续存在”的下界是可行的。实际 native failure 可能先发生、后被 owner 观察，事件只能陈述 owner 观察到的范围，不能冒称已覆盖真实终态发生时刻。

恢复时逐个查询 handle 不构成全成员共同切点；callback 可在两次读取之间撤销 scope。需要在适用现有 native 锁边界内获取一次完整的恢复观察，离开该边界后持久化，失败则保持 UNKNOWN；禁止把阻塞 fsync 放进原生 callback 锁。恢复事实仅代表那个时点，不承诺随后持续健康。

## 必须连成的实现路径

1. **Provider / Base**：中立、有界恢复观察合同，绑定完整成员及 source/owner/进程代际、episode、序列和可比较时钟。Provider 负责真实状态与来源；不能由 Monitor 或任意配置 `verified=true` 生成。源记录失败、重启、范围改变或时钟不可比较产生明确缺口。
2. **Gateway / SDK**：由正式 owner 装配持久源日志与有界 relay；可信 source 绑定、首个完整切点、`covered_through` 水位、缺口和认证代际必须一起传递。不能只把通用事件 journal 的序号当成完整时间覆盖。Monitor 故障不控制交易，也不能令 producer 声称未观察时段已完整。
3. **Monitor ingress**：沿用认证 `events.append` 外壳和 producer 封装，为新 event type 单独授权；规则配置精确绑定可信 producer、scope、stream、显式阈值与容量。未选时不增加默认依赖；普通 Runtime 或其他服务不能代报 Gateway recovery。
4. **Monitor 计算**：独立有界 worker 消费同库持久事件。接收 ACK 与计算分开；一次事务保存本地消费水位、pending/firing/unknown、累计量、来源和日历版本、生命周期事件及通知 outbox。不能通过先 ACK 再算、重新开库或新 episode 丢弃 UNKNOWN。
5. **日历**：显式授权的固定范围接口；只取可证明恢复区间与半开 `continuous` 窗口的交集，auction/午休不计。跨休市还需证明是同一 episode，范围不齐、版本冲突或缺口为 UNKNOWN，不能用自然时间补足。
6. **Host 生命周期**：worker 不在 heartbeat owner 中执行慢计算，独立连接、有限锁等待和有界队列；启动失败及关闭不明时保留原资源。Webhook 慢路径不能饿死 heartbeat。当前 Host 清理保留修复只是这一接线的前置，不表示 evaluator 已存在。

旧 `AlertCatalogRouter.record()` 的正数持续时间保护不能直接删除。只有正式装配、来源覆盖和持久计算都完成的新入口才可接受对应配置；不能添加一个只供测试构造的 helper 后宣称功能完成。

## 必须覆盖的验收场景

- 使用真实 ServiceHost/CURVE、SQLite 与子进程；provider 和日历可显式模拟。验证 receiver ACK 与计算水位分离、同事务崩溃前后、重放去重、同 ID 不同内容拒绝和原状态重开。
- 合成阈值 600 秒：同一 outage 覆盖上午 11:24–11:30、午休以及下午 13:00–13:04；只累计 6+4 分钟。恰好阈值一次触发，恢复仅凭合格恢复事件；午休、收盘或 UNKNOWN 不自动恢复。
- owner retry/reset_pending 保持累计；退订、scope 变化、重入异常、native 回调竞态、丢失/乱序/旧 epoch、缺口与时钟变化不得错误恢复或重复累计。
- 同品种多合约按 exchange/product 合并，同时保留完整受影响范围证据；不能从一条 tick 推断全部合约恢复。不同品种/交易所独立计时。
- 满队列、磁盘/事务失败、工作线程异常、慢 Webhook 与关闭未知不影响 heartbeat 的有限服务行为；恢复原记录时不盲重发。
- D67-37 允许明确 mock 完成本期功能验证。模拟日历必须在输出保留来源类型，真实日历全量和 Opendata 不是本期 mock 功能前置；模拟闭环也不自动成为实际账户告警通过。

本记录未修改真实配置、journal、进程或账户，未放宽任何交易写入门禁。实现完成后还需更新矩阵并逐项验收。
