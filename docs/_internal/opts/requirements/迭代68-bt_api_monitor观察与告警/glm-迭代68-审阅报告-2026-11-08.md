### GL68-02(边界)[新发现] 活性判定的"可信来源时间及延迟上界"由谁提供未定义

- **定位**:迭代计划.md:61(§3.3"只有可信来源时间及延迟上界或经过验证的因果请求/响应才能支持来源活性判断,否则为 `unknown`")。
- **问题**:心跳有因果请求/响应路径(D63-43)可证明活性;但普通遥测/事件流里"可信来源时间"需要来源时钟可信——这又回到时钟证据问题(迭代 62 的 SNTP/场所时间核对是 direct 行情时钟资格的机制,见职责规范 SDK `clock_verification` 行)。计划没有写"可信"的判定来源:是复用 SDK 时钟核对证据、只认心跳因果路径、还是由来源服务自报时间加配置延迟上界。
- **建议**:68.01 冻结时明确:首期活性判断**仅**心跳因果路径;普通遥测一律"近期收包"语义(标 fresh 仅指收包新鲜),不因其载荷时间戳升级为活性。若未来要扩展,单独立 D68-xx 并指定时钟证据来源,不在本迭代默认引入。
- **影响**:不定义则各来源(63/64/65/66)各自声称"我的时间戳可信",活性判断退化为载荷自报,重放/积压旧数据可再次被误读为存活——M1 修了心跳,M1 的措辞却在遥测路径留了这个口子。

### GL68-03(边界)[新发现] 行情中断告警"建议按交易时段计"与"67 非前置、63 无日历条目"冲突

- **定位**:迭代计划.md:77(§3.3"行情恢复中超过显式配置的时长(**建议按交易时段计**)时告警一次");:43(§3.1"67 日历事件仅为未来可选来源,不作为本计划任何必需步骤的前置");:170(§7"迭代 67 不是前置")。
- **问题**:按交易时段计需要交易日历事实;Monitor 明确不引入日历(67 非前置),而 63 计划当前也没有任何日历条目(见[glm-迭代67-审阅报告](../迭代67-交易日历数据文件化与每日更新/glm-迭代67-审阅报告-2026-11-08.md) GL67-02)。"按交易时段计"在首期交付里没有可实现的事实来源(Gateway 若用 62 的 2026 内置常量,2027 年起失效)。
- **建议**:首期把告警时长改为**纯显式配置的固定时长**(运营按品种时段自行配置),括注的"按交易时段计"标注为"后续增强,依赖 63/67 交付后的会话感知超时(事件载荷可携带来源会话标记)";或直接删去该建议。

### GL68-04(对抗)[新发现] 持仓恒等式告警缺"观察流长期陈旧/停止"的升级告警类目

- **定位**:迭代计划.md:67(§3.3 持仓恒等式告警段)、:71(告警归组/顺序段)、:165(D68-04)。
- **问题**:恒等式告警"仅对新鲜、完整、水位可比且差额非零的观察产生不匹配告警;缺失、过期或水位不齐为 unknown/未能核对,不当作零或健康"——显示语义完备,但**观察流本身长时间不达或持续陈旧**时,只有页面上的 unknown/stale 标记,没有告警类目(对比同节行情中断告警有"超过显式时长告警一次"的机制)。风控上"对账观察失明"本身是应通知运营的事件(参照 §3.3 阈值规则"来源缺失不得默认为健康"的原则)。
- **建议**:D68-04 的必需事件目录中增加"对账/恒等式观察持续陈旧或中断"告警类目(阈值显式配置,与行情中断告警同模式:触发一次、恢复一次);68.04 测试矩阵补一行。
- **影响**:Gateway 恒等式观察静默停止(例如中继故障)时,页面长期 unknown 无人被告知,恒等式告警事实上失效。

### GL68-09(对抗)[新发现] `heartbeat_timeout_seconds` 的配置归属有歧义

- **定位**:迭代计划.md:117(§4 示例把 `heartbeat_timeout_seconds` 放在 `monitor:` 段)与 :85(§3.4"63 的 D63-36 判断依据是……发出时间在配置时长内",判活主体是 **Gateway**)。
- **问题**:心跳超时是 Gateway 判活(D63-36)用的参数,判活与 `monitor_required` STOP_NEW 都归 63;示例却把它放在 `monitor:` 配置段。若 Monitor 侧配置它而 Gateway 侧另有值,同一超时两处配置可能分叉(运营改了 Monitor 配置以为生效,Gateway 仍用旧值)。
- **建议**:68.01 与 63.01 联合冻结时明确:判活超时归 Gateway 账户配置(`gateway:` 段),Monitor 段不重复该键;或明确"Monitor 侧仅为展示用的只读镜像"。§4 示例相应调整。
- **影响**:两处配置分叉导致存活判定与运营认知不一致,`monitor_required=true` 下可能出现"Monitor 认为健康、Gateway 已 STOP_NEW"的告警噪音。
