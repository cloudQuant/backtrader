## 0. 立项结论

本迭代建设一个可单独使用的 `backtrader-skills` 技能套件。用户在已有 Backtrader
运行时上只安装 `backtrader-skills`，不安装、不启动、甚至不存在
`backtrader-mcp` 和 `backtrader-agent` 时，AI 也必须能完成以下完整闭环：

```text
理解策略需求
  -> 检查、登记并加载本地数据
  -> 检索本地策略语料
  -> 形成结构化策略规格
  -> 选择当前 fork 合规模板
  -> 生成单文件测试或 Python 三件套
  -> 预览并落盘
  -> 静态与安全校验
  -> 受控回测和测试
  -> 分析失败并修复
  -> 输出指标、证据和报告
```

这里的“Skills”不只是几份提示词。完整能力必须由
`SKILL.md + references + templates + scripts + tests` 自己提供。提示词负责指导 AI，
确定性的索引、渲染、校验、执行和报告必须由技能包自带脚本实现。

`backtrader-mcp` 和 `backtrader-agent` 仅可作为未来可选互操作对象，不能成为本
迭代的安装依赖、运行依赖、测试依赖或验收条件。

结论：两套语料是“同源、互补的证据库”，不是两份完全相同的模板库。

### 1.5 必须按对象类型治理初始化

再次核验当前 fork 源码后，原先“所有 Strategy 必须先调用
`super().__init__()`”的结论不成立。`Strategy.__new__()` 先建立参数、broker、
analyzers 等状态，`Strategy.__init__()` 再建立 `datas/data0/_clock`，随后才显式调用
直接策略子类的用户 `__init__()`。因此仓库中直接继承 `bt.Strategy` 且不调用
`super().__init__()` 的主流写法是当前有效契约，不是待治理缺陷。

Validator 必须按继承关系分类：

- 直接继承 `bt.Strategy`：允许不调用 `super().__init__()`，不得据此报错；
- 继承自带自定义 `__init__()` 的策略基类或 cooperative mixin：若依赖父类初始化，
  必须按 MRO 调用 `super().__init__()`，并检查调用顺序；
- Indicator、Analyzer、Feed 等其他对象：按各自构造管线验证，不能套用 Strategy
  特例；
- 旧语料仍只能作为逻辑和装配参考；AI 输出必须重新经过当前 API、时钟、数据、
  look-ahead 和执行验收，但不能仅因没有 `super()` 而失败。

## 2. 用户场景

### 2.1 核心场景

1. 用户用自然语言描述单品种均线、突破、均值回归等策略，AI 生成可运行策略。
2. 用户给出一个或多个本地 CSV、Pandas fixture 或仓库测试数据，AI 能检查 schema、
   时间范围、排序、重复值、缺失值、时区和 feed 映射，生成可复现数据清单后加载。
3. 用户描述多指标组合，AI 能解释指标关系、参数和最小周期。
4. 用户描述多资产配置，AI 能生成多 feed 装配和再平衡逻辑。
5. 用户描述多周期策略，AI 能正确处理 secondary clock 和 runonce/runnext。
6. 用户描述配对/价差策略，AI 能生成多数据对齐和仓位管理。
7. 用户描述止损、止盈、限价、括号单或风险预算，AI 能生成受支持的订单逻辑。
8. 用户描述预计算信号或机器学习特征，AI 能声明可选依赖和 feed lines。
9. 用户给出失败策略，AI 能读取结构化诊断、修复并重新验证。
10. 用户选择输出为一个功能测试文件，或选择完整 Python 三件套。
11. 用户要求解释回测结果，AI 能关联策略规格、代码版本、数据 hash 和指标。

### 2.2 首版不覆盖

- 实盘 broker/store、实盘下单和模拟连接真实交易账户；
- 凭据、交易所 API key、外部 CCXT/Yahoo 等网络行情；
- HTTP 服务、远程多租户和权限系统；
- 自动优化参数、自动选出“收益最好”的策略；
- 把 1,035 个旧策略批量改写或复制进当前仓库；
- 用历史 `py_result.json` 自动批准新策略基线；
- 把本地子进程描述为完整安全沙箱。

## 6. 版本化契约

### 6.1 `StrategySpec v1`

至少包含：

- `spec_version`、策略名称、slug、类别和目标 archetype；
- 目标产物 `single_test | python_bundle`；
- 数据源数量、名称、symbol、timeframe、字段和固定 fixture；
- 指标/特征、参数、默认值、类型与约束；
- 入场、加仓、减仓、退出、止损、止盈和风险规则；
- 订单类型、Sizer、commission、cash；
- Analyzer 和期望输出；
- `runonce/runnext` 要求；
- 可选依赖和允许的 import；
- 明确非目标与尚未决定项。

为使两个 renderer 可确定性地产生同一策略语义，Schema 必须定义受限 IR：

- `Expression`：typed constant/parameter/data line/indicator reference，以及 allowlisted
  boolean、comparison、arithmetic、cross 和 rolling operator；
- `Action`：`buy/sell/close/cancel/set_stop/set_target` 及 typed order/risk 参数；
- `StateRule`：阶段、触发 Expression、Action 列表、priority 和 mutually-exclusive
  group；
- 指标 DAG、warm-up/minperiod、feed/clock 引用和 state variables。

宿主 AI 负责把自然语言变成该 IR；renderer 只渲染并拒绝不支持的 operator，不能让
AI 为 `single_test` 与 `python_bundle` 各写一份可能分叉的策略。Repair 修改 IR 或
受限模板参数后重渲染。

禁止在未澄清数据、交易方向、仓位和退出规则时直接生成最终产物。

### 6.2 `DatasetManifest v1`

本地数据先登记、后绑定、再运行。清单至少包含：

`DataSpec` 不是第八份公共 Schema，而是
`dataset-manifest-v1.schema.json#/$defs/DataSpec` 中的 typed request 定义；它继承
DatasetManifest v1 版本，拥有独立 `spec_hash` 和正反 fixture。DataSpec 记录用户请求
的 feed、受控路径引用、列映射、时间窗口、transform 和 alignment；DatasetManifest
在其基础上增加实际解析事实与 provenance。

- `dataset_id`、schema/spec/semantic-manifest hash、产品/Backtrader/parser
  provenance 和创建时间；semantic hash 排除产品名、产品版本、创建时间和本机显示路径
  等非数据语义字段；
- 受控数据根 ID 与根内相对路径，禁止把用户绝对路径写入可移植产物；
- 每个 feed 的唯一名称、symbol、execution/signal/benchmark/hedge/cash_proxy 角色与
  tradable 标记；
- 来源类型：`local_file | materialized_dataframe`，以及 allowlisted format/adapter；
- 每个文件的 SHA-256、字节数、行数、首末时间和扫描证据；
- feed 顺序、master feed、`intersection | left | explicit_asof` 对齐策略和最低重叠；
- timeframe、compression、timezone、交易日历和 session；
- datetime/open/high/low/close/volume/openinterest 以及自定义 lines 的列映射、dtype、
  datetime format、分隔符和编码；
- `fromdate/todate`、resample/replay、预处理函数或 feature artifact 的相对引用和 hash；
- 排序、重复时间戳、空值、非有限值、OHLC 合法性、频率间隔和缺口检查结果；
- 数据许可/敏感性标签、是否允许写入派生产物和可审计 provenance；
- manifest hash、实际加载摘要和与 StrategySpec 的兼容性状态。

P0 只支持已配置数据根中的离线本地数据。`dataset_id` 是后续 StrategySpec、
ValidationReport、validation token 和 RunManifest 的稳定引用；源文件、映射、时间范围
或预处理 hash 改变后，旧验证和运行批准必须失效。

### 6.3 `CorpusManifest v1`

至少包含：

- `canonical_id=category/full_directory_name`；
- adapter 和 schema 版本；
- 源仓库、branch、commit、dirty-scope、扫描时间；
- 源相对路径、主 runner import、主 module/class 和每个文件 SHA-256；
- config ID/name 别名、参数和类型；
- 数据文件、feed 数、lines、周期和特征预处理函数；
- 指标、订单 API、风险/退出钩子、Sizer、commission、Analyzer；
- 依赖标签和最低运行环境；
- 对应测试、映射方法、映射状态和差异摘要；
- 历史结果 schema，但不把历史结果标成当前验收。

### 6.4 `StrategyArtifactManifest v1`

记录目标 profile、受限输出根、文件相对路径、文件角色、内容 hash、来源规格/模板/
语料引用、预览 diff、覆盖策略和批准状态。它不能承载绝对路径或可执行命令。

### 6.5 `ValidationReport v1`

每条诊断必须有稳定错误码、严重级别、文件、位置、规则、说明和修复建议。报告分层：

1. 规格和 Schema；
2. Python 语法/AST；
3. 当前 fork API；
4. 安全/路径/依赖；
5. import/collection；
6. smoke 回测；
7. runonce/runnext；
8. 目标测试；
9. master/dev 基线；
10. 产物完整性。

### 6.6 `RunManifest/RunResult v1`

记录：

- StrategySpec、候选文件、数据和环境 hash；
- Backtrader import path、version、branch、commit；
- 固定命令、cwd、允许的环境变量、开始/结束时间和超时；
- Analyzer、11 个兼容指标及 nullable 语义；
- stdout/stderr 摘要和结构化诊断；
- JSON/Markdown/HTML 等产物引用；
- 审批、基线来源和比较容差。

### 6.7 `ComparisonProfile v1`

该 profile 是七份契约引用的版本化策略文件，不新增第八种产物 Schema。默认规则必须
由三个产品各自实现和测试：

- 交易/订单/bar/win/loss 等整数计数、状态、布尔、枚举、ID、hash：精确相等；
- 浮点指标：`math.isclose(rel_tol=1e-7, abs_tol=1e-9)`；
- 金额等确需专属容差的字段：以明确 metric key 覆盖，禁止全局模糊放宽；
- `null` 只可出现在 schema 声明 nullable 的字段，且只与 `null` 相等；
- NaN、Infinity 和缺失必需字段：直接失败；
- runonce/runnext：计数精确、浮点按默认规则、交易事件序列按规范化字段比较；
- master/dev：默认同上；每个覆盖必须记录 metric、原/新容差、理由、批准人、时间和
  profile hash。

S1 必须冻结 `comparison-profile-v1.json` 及正反 fixture。未经审计的临时容差不能
产生“通过”结论。

### 6.8 Canonical JSON、ID、token 与批准状态

三个产品各自内置但共用 golden fixture 的 `canonical-json-v1`：UTF-8、Unicode NFC、
object key 排序、无多余空白、稳定 JSON number/null/bool 表示，禁止 NaN/Infinity。
`spec_hash/artifact_hash/manifest_hash/report_hash = sha256(canonical_bytes)`；
`dataset_id = "ds_" + semantic_manifest_hash`，volatile 的产品名、时间和显示路径在计算
semantic hash 前按 Schema 明确排除。

跨产品 public import/export 冻结以下核心字段；产品私有状态只能进入版本化
`extensions`：

- StrategySpec：`spec_version/name/slug/category/archetype/output_profile/dataset_id/
  feeds/parameters/entry/exit/sizing/risk/run_modes/allowed_imports`；
- DatasetManifest：`schema_version/dataset_id/spec_hash/semantic_hash/manifest_hash/feeds/
  master_feed/alignment/status/diagnostics/transforms/provenance`；
- CorpusManifest：`schema_version/corpus_id/mode/entries/snapshot_hash/provenance`；
- StrategyArtifactManifest：`schema_version/artifact_id/spec_hash/dataset_id/output_profile/
  files/artifact_hash`；
- ValidationReport：`schema_version/validation_id/artifact_hash/dataset_id/status/diagnostics/
  evidence/validation_hash`；
- RunManifest：`schema_version/run_id/artifact_hash/dataset_id/engine/environment_hash/
  run_profile/approval_id/manifest_hash`；
- RunResult：`schema_version/run_id/status/metrics/diagnostics/artifacts/result_hash`。

`dataset_id` 固定为 `ds_` + 完整 64 位 semantic hash；七类 archetype 枚举在三产品
中逐字一致。各产品运行时不得 import sibling，但仓库级 parity fixture 必须证明一个
产品的 public artifact 能被另一个产品重新登记和验证。

validation/change/run token 使用 256-bit 随机句柄或 HMAC，不使用可重算的裸内容
hash；持久化时只保存 token digest，并绑定 token type、artifact revision、spec/data/
engine/environment/policy hash、目标及 preimage（适用时）、workspace subject、签发/
过期时间和 nonce。状态固定为 `ISSUED -> CONSUMED | REVOKED | EXPIRED`，内容变化立即
revoked；change approval 与 run approval 分开，preview 本身不构成批准。相同
idempotency key 只能重放同一结果。上述字节、ID、过期、漂移和重放均有正反 fixture。

### 6.9 `RunResult` 11 项指标语义

标准 runner 总是装配对应 Analyzer，并规范化为：

| 字段 | 类型/单位 | nullable |
| --- | --- | --- |
| `bar_num` | integer，实际处理 bar 数 | 否 |
| `buy_count` / `sell_count` | integer，long/short trade 计数 | 否 |
| `win_count` / `loss_count` | integer，已结束盈利/亏损 trade 计数 | 否 |
| `trade_num` | integer，总 trade 计数 | 否 |
| `final_value` | finite number，账户计价货币单位 | 否 |
| `sharpe_ratio` | finite number，无量纲 | 是，样本/方差不足时为 null |
| `annual_return` | finite number，年化小数收益，`0.10 = 10%` | 是，无足够期间时为 null |
| `max_drawdown` | finite number，百分比，`10 = 10%` | 否 |
| `return_rate` | finite number，百分比，`10 = 10%` | 否 |

Analyzer 缺失是 runner/config 错误，不得把计数字段写成 null。交易/订单规范化事件另存
并生成 `event_trace_hash`；branch-compare 中 `Returns.rtot` 不得冒充这里的
`return_rate`。

## 7. 本地数据接入与加载设计

### 7.1 受控数据根

- 用户先把一个或多个目录登记为只读数据根，系统向外只暴露 opaque root ID；
- 所有输入路径必须规范化后位于登记根内，并拒绝 `..`、绝对路径、编码绕过与软链接
  逃逸；
- `inspect_dataset` 只读抽样和统计，不 import 策略、不执行用户预处理代码；
- `register_dataset` 在同一次受控读取中校验并复制为产品自有 content-addressed
  immutable canonical CSV/CAS，再生成 manifest；更新必须产生新版本/hash，runner
  只读 CAS，原路径只保留 provenance，避免 check-open 间 TOCTOU；
- `materialize_dataset` 只把已批准的仓库 fixture/产品内 tabular artifact 规范化为
  UTF-8 canonical CSV（显式列序、ISO-8601 时间、稳定数值/null、无隐式 index），
  不接受 pickle、任意反序列化或用户 callable；
- `preview_dataset` 仅返回受限行数、列摘要和质量诊断，避免把完整行情塞入模型上下文；
- `feed_factory` 只接受已验证 manifest 和允许的 feed/profile，不接受任意 Python
  callable 或动态 import。

### 7.2 P0 数据类型

| 类型 | P0 能力 | 明确限制 |
| --- | --- | --- |
| `generic_csv` | `GenericCSVData`，显式列位置、日期格式和缺失列 | 不下载、不回写源文件 |
| `backtrader_csv` | 固定 Backtrader CSV 格式 | 本地只读 |
| `yahoo_csv` | 已下载的 Yahoo CSV | 不调用在线下载 |
| `mt5_csv` | 逗号/Tab、列归一化、日期切片和 bar shift | mtime/size 只用于缓存，不能替代内容 hash |
| `pandas` | 可信调用方先把 DataFrame 物化为 canonical CSV，再由 runner 构造 `PandasData` | 不跨进程传 Python 对象，不接受 pickle |
| `pandas_custom_lines` | 产品模板拥有的扩展 `PandasData` | 不动态 import 用户 feed |
| 仓库测试数据 | 解析现有测试 loader 和固定相对路径，生成可复用 manifest | 不把测试源码路径当长期数据 ID |
| 多数据/多周期 | 多 manifest 绑定、角色、对齐、resample/replay 声明 | 不静默 forward-fill 或改变日历 |
| 自定义 lines | 显式列映射、dtype 与预处理产物 hash | 未声明列直接失败 |

网络行情、数据库连接、API key、实时流、实盘 store、自动下载和任意用户 Python
loader 均不属于 P0。后续即使增加 Provider，也必须在独立安全迭代中保留可复现快照。

### 7.3 数据验收

固定正反 fixture 至少覆盖：正常 OHLCV、乱序、重复时间戳、时区缺失、缺列、空值、
NaN/Infinity、非法 OHLC、多 feed 时间不对齐、resample/replay、custom lines 和源文件
被修改。相同文件和映射应得到相同 manifest hash；manifest 变化必须使旧 token 失效。

## 10. 校验与安全

### 10.1 静态门禁

- YAML 可解析、公共字段完整、扩展字段位于允许 namespace；
- runner import 唯一解析到本包主策略；
- 存在正确的 `bt.Strategy` 子类；
- 直接 `bt.Strategy` 不强制 `super()`；自定义父策略/mixin 的 cooperative init
  按 MRO 正确调用；
- config 参数与策略参数兼容；
- Python compile/AST 通过；
- import 位于 allowlist，可选依赖已声明且已安装；
- 禁止 `exec`、`eval`、`compile`、`__import__`、动态 import；
- 禁止 `subprocess`、`os.system`、socket 和未批准网络库；
- 禁止硬编码凭据、绝对数据路径和目录穿越；
- 禁止 live broker/store；
- 对未来数据访问和 look-ahead 进行 AST/对象语义检查；
- 输出路径必须位于草稿/产物根，拒绝软链接逃逸。

### 10.2 运行门禁

- 只有已落盘且静态通过的候选可运行；
- validation token 绑定策略、配置、数据和环境 hash；
- 任一文件变化后 token 失效；
- 使用固定参数数组，不拼 shell；
- 本仓库验收使用用户 Anaconda base：
  `/Users/yunjinqi/opt/anaconda3/bin/conda run -n base python ...`；
- distribution 由 doctor 登记 interpreter/conda env ID 和环境 hash，公开安装文档不
  硬编码本机路径；
- 固定 cwd、最小环境变量、已知网络 API 拒绝策略、超时、输出和产物配额；
- 捕获并脱敏错误，不回传绝对路径、环境变量或完整 traceback；
- 写入批准和执行批准分开；
- 首版明确声明：子进程隔离不等于完整 OS 沙箱；
- AI 生成代码仍是不可信输入；P0 只执行本产品生成、验证且用户批准的候选，来源不明
  的第三方代码仅做静态校验；产品 action 门禁不声称能阻止宿主自身 Bash/Edit 旁路。

## 16. 风险与控制

| 风险 | 控制 |
| --- | --- |
| Skill 只有提示词、无真实能力 | 索引、渲染、校验、运行和报告全部要求自带脚本验收 |
| 复制旧策略导致生命周期错误 | 当前 fork 模板 + 分对象初始化/时钟 AST 规则 |
| 两套语料同源但行为已漂移 | 双来源、hash、差异状态和 current-test 优先证据 |
| ID/类名重复选错策略 | canonical path key + runner import |
| YAML 变体被刚性 schema 拒绝 | 公共核心 + 受控扩展 namespace |
| 未来数据或 look-ahead | AST/对象语义检查 + 双模式/行为测试 |
| 历史结果被误当新基线 | fresh master/dev 审批门禁 |
| 子进程仍可访问主机 | 明示安全边界；高风险代码后续增加容器 |
| Skills 暗中依赖 MCP | 无 MCP 的隔离安装和文件访问审计 |
| Skills 暗中依赖 Agent | 无 Agent 的隔离安装和文件访问审计 |
| 数据路径泄漏或数据漂移 | opaque root ID、相对路径、DatasetManifest、内容 hash 和 token 失效 |
| 数据质量问题被策略错误掩盖 | 登记前排序/重复/空值/非有限值/OHLC/时区/对齐门禁 |
| clean install 暗中依赖 sibling corpus | 随包 snapshot/模板/精选片段 + 显式 source-attached 模式 |
| “禁网”承诺不可验证 | P0 只承诺静态网络 API 拒绝和人工批准；强隔离留给容器后端 |
