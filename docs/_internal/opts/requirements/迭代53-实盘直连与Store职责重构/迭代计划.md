## 1. 目标与边界

Backtrader 在不安装、不启动 `bt_api_gateway`、`bt_api_risk`、`bt_api_execution`、`bt_api_monitor`、`bt_api_runtime` 时，仍可通过标准 `Store` / `Feed` / `Broker` 接口，使用 `bt_api_py` 与明确选择的交易所包直连该包真实支持的外部账户。能力需由对应 SDK / 交易所包实际提供并逐项验收；本计划不宣称现有 CTP、Binance、OKX 或其他交易所的真实账户已经可用。

插件是显式选择的增强能力。插件被配置启用后，缺包、初始化失败、准入失败、调用异常、未知执行状态或清理失败都必须明确报错并保留状态；不能悄悄切换到 Store 直连、其他插件、另一账户、另一环境或重新生成订单。插件未选择时，核心 Store 不得仅因插件未安装而拒绝 SDK 有原生能力的 direct 请求。

首要垂直切片是普通 CTP `direct` Store / Broker / Feed → `bt_api_py` → `bt_api_ctp`。保留真实会话认证、账户和环境绑定、原生字段校验、请求/回报关联、交易所限制、幂等身份、撤单身份、未知状态与资源收尾要求。不能为恢复直连而绕过身份、认证、账户作用域、隐私边界或已有有效安全检查。

长期目标是同一适用策略代码经配置和 Feed、Broker、Store 装配，覆盖 backtest、`replay`、`shadow`、`paper`（外部模拟账户）和 `live`（生产账户）。迭代52只实现、使用、验收 `paper` 与 `live`；`replay`、`shadow`、旧本地模拟能力只盘点并研究后续归属，本轮不运行、不验收。该兼容性是目标，不宣称现有策略均已支持。

## 4. 目标职责与运行拓扑

### 4.1 必选基础直连路径

    Strategy / Cerebro
      → Backtrader Broker（BT Order、状态机、通知）
      → Backtrader Store / Feed（标准 API、生命周期、BT 数据投影）
      → bt_api_py（统一连接门面与 bt_api_base 中立协议）
      → 显式选择的交易所包（bt_api_ctp / bt_api_binance / bt_api_okx / 经能力审计的其他包）
      → 对应 provider

Backtrader 保持通用 `Order`、`OrderData`、成交位、Feed / Broker / Store 生命周期、策略通知与通用状态映射。`bt_api_base` 定义中立数据合同；`bt_api_py` 负责统一配置、客户端门面、会话调用与插件发现；`bt_api_ctp` 等交易所包独占本交易所字段、原生请求、回报、序号、交易日、产品限制和错误解释。不得在 Backtrader 中维护第二套 CTP 字段真值，也不得把 Backtrader 继承链整体搬入 SDK。若调用方未选择可选插件且按原 API 正常注入 SDK/client，则兼容既有 Store 默认 direct 路径，不要求增加 `direct` 显式开关；路由明确选择插件后，该插件失败必须 fail closed。

核心路径自身执行必需的账户 / provider / environment 身份匹配、会话检查、订单与交易所限制校验、client identity、请求-回报关联、幂等投影、UNKNOWN 保留及收尾。它们是协议正确性与连接安全，不是可选 risk / execution 服务。未选择插件时按原 Store 与 SDK/client 注入方式走 direct；不得要求新显式 direct 标志。不得从连接失败推测并改连另一 provider。

### 4.2 显式选择的插件

- `bt_api_execution`：可选可靠执行与持久化；长期目标包括注册策略信号聚合和冲突处理、大单拆分、算法状态、子单路由及恢复。处理已生成的策略 intent；不生成策略信号、不选股、不拥有 Alpha / 因子政策。现有多腿支持不等同多策略信号聚合；完整新聚合/算法能力是长期目标，不是 direct 恢复或旧包移除的前置，也不视为已实现。
- `bt_api_risk`：可选业务风险政策。未选择时 direct 基础路径仍可用；选择后准入、超时或执行错误一律 fail closed，不绕过、不回退。
- `bt_api_gateway`：可选共享账户会话、行情分发与远程接入。只有显式选择 gateway 才走 gateway；不得自动接管或替代 direct 的账户身份。
- `bt_api_monitor`：可选观察、指标、告警与审计投影；不拥有下单、撤单、账户状态真值或 execution journal 写权限。
- `bt_api_runtime`：可选的 SDK 共享部署组合、依赖装配、服务生命周期与配置校验；不得成为普通 direct Store 的隐式前置条件。它与 Backtrader 内旧可安装包 `backtrader_runtime` 是不同项目/边界。旧包能力迁移、调用方切换及最终移除属于迭代53，不等待迭代52；`bt_api_runtime` 仍是可选依赖。

当配置显式选择 execution 等插件路由时，在构造 Broker / Store 前校验所需包、版本、路由、能力与作用域；失败立即返回有限错误。未选择插件时，标准 Store 配合正常注入的 SDK/client 使用既有默认 direct。插件已执行时发生不确定结果，不得重发或转 direct；按原订单身份查询、对账并保留 UNKNOWN。

### 4.3 Execution 聚合、拆分与风控顺序

以下是未来完整聚合与算法执行能力显式启用时的目标合同，并非现有插件能力的现状：

1. 校验 intent 的 strategy id、注册版本、account / provider / environment、instrument、side、position effect、数量、价格、有效期、幂等 key 和来源；信号生成与选股属于策略。
2. 只在显式 registry scope 内聚合，范围至少含账户、provider、环境、策略组、品种、方向 / 持仓效果、执行周期；不同范围不得混单。
3. 按版本化冲突政策合并、净额、排序或拒绝。相反方向、超时和重复信号不得静默丢弃；输出可复算决策、数量分配与拒绝原因。
4. 若启用 risk，聚合后、拆单前检查父 intent；每个子单生成后、dispatch 前再次检查数量、总量、价格、速率、暴露和品种规则。任一拒绝按明确合同暂停或拒绝相关父单 / 剩余量，禁止超限子单。未启用 risk 时只执行必需的基础与 provider 限制校验，不声称业务风控通过。
5. 大单拆分 / 算法产生父子订单树，记录来源策略、聚合决策、分配、拆分原因、时间表、参数、子单 client id、provider id、尝试和回报。可暂停、撤销、恢复；重启只恢复已持久化状态。
6. 先写唯一权威 journal 的 intent / reservation / dispatch-pending，再调用 provider；事件以 provider event id / client id / order id 幂等归并。BT Broker 只投影并通知，不能成为第二个 journal 写者。
7. 超时、断线、崩溃或撤单竞争均保留 UNKNOWN，用原 client id 查询确认；未确认终态前禁止生成新身份、自动补发或误报父单完成。partial、迟到 fill、duplicate event 和 cancel/fill race 必须可重放归并。

聚合分配满足来源数量守恒；子单累计成交不超过 parent；parent 剩余、撤单量、成交量、费用和事件顺序可从 journal 复算。策略政策与算法由显式注册配置选择，不嵌入 Store 默认路径。若父/子两级风险政策均启用，父级只占用一次总额度；子级仅在父级预留额内分配，不再重复占用账户额度。确认成交时按实际风险消耗归属；确认拒绝、撤销或最终未成交剩余量时幂等释放对应额度；UNKNOWN 或未对账 partial 不释放相关预留。

## 6. 实施阶段与每轮 Gate

每轮只在对应现有 `dev` checkout 小步实施；验收通过立即提交再开始下一轮。失败继续修本轮，不用源码或 fake 测试宣称 paper / live 通过。不另建开发 worktree。

### R53-0：源码、历史、dirty 与 worktree 清点

- 固定 Backtrader、`bt_api_py` 父仓与相关子仓 HEAD、branch、status、包版本、依赖 metadata、Gitlink、worktree 和测试入口；核对本计划目标路径。
- 逐一核对历史 worktree 中与 Store、CTP direct、execution、risk、gateway、monitor、runtime 相关的提交、文件、测试和证据级别；只迁移证明仍缺失且适用于当前 dev 的改动。
- 对照用户提供的 AGENTS 摘要、A0 R3 索引及后续可复核的逐案登记，保留99 case 与 Optional16 原 ID、状态、权限、历史 / retained-host / consumed-invocation 关联，不重编号、不清历史、不重跑已验收 QA。只使用获准公开审计索引；信息不足则记 OPEN / UNVERIFIED。
- 交付源码调用图、owner 表、依赖 / 版本矩阵、dirty/worktree 保留清单和阻塞清单。Gate：没有未解释覆盖、双 owner、包循环或误标的历史接受。

### R53-1：中立 Store / Broker / SDK 合同

- 定义 `bt_api_base` 中立订单意图、撤单请求、账户 / 会话 / provider / environment identity、client id、订单 / 成交事件、UNKNOWN / 终态合同和 schema 版本。
- 固定 BT Order ↔ neutral DTO ↔ provider event 的字段、顺序、时间 / 数量单位、时钟及错误码映射；CTP、Binance、OKX 原生字段分开。
- 按实际实现确认 callback、队列、Broker 通知与 journal 的 owner 线程；同进程只允许一个 journal 写者与一份执行真值。
- Gate：Backtrader 与至少一个交易所包可独立消费合同；无插件的 import graph 不触发 service/runtime；兼容和错误路径测试通过。

### R53-2：普通 CTP direct 恢复（首要交付）

- 逐跳追踪 `BtApiStore.submit_order` / `cancel_order` / `_submit_order_legacy`、Broker、`bt_api_py` facade / SimNow profile 和 `bt_api_ctp` 原生 submit / cancel。分类每个拒绝点是协议要求、认证 / 环境身份、交易所限制、明确写权限还是 optional managed/risk/service policy；不得未审先删身份 / 账户保护。
- 实现不依赖 RegisteredSimStore 的普通 BtApiStore CTP direct route。Order mapping 留 BT，中立 API 经 facade 到 CTP SDK；CTP 字段不再由 Store 保持第二份真值。RegisteredSimStore 保持显式兼容桥。
- 兼容标准 Store 的默认 direct：调用方不选可选插件、按原 API 注入 SDK/client 即可使用；direct 按已有配置明确绑定 provider / environment / account session。认证成功，instrument 与账户一致，请求和回报绑定同一 session generation。身份/route 不可证明即拒绝，不猜测 fallback。
- fake SDK/native leaf 覆盖 insert、cancel、回报、错误码、partial、撤单回报、重复 callback 和异常收尾；不构造真实账户身份，不发送 provider 请求。
- 身份认证、账户作用域、私有输入保护及有效订单/交易所约束继续执行；不得把 service/risk/execution 插件门禁误判为协议必需条件，也不得以恢复直连为由绕过真实安全校验。
- Gate：全新隔离环境只安装 Backtrader、`bt_api_py`、`bt_api_base`、`bt_api_ctp` 及必要原生依赖；不安装 gateway/risk/execution/monitor/runtime；标准 Store / Feed / Broker 能通过合成客户端完成订单状态机。此 Gate 仅证明源码与组合，不等于 SimNow / 真实账户通过。

### R53-3：非 CTP direct 分批审计

- 对每个 exchange package 核对真实 submit/cancel、client id、provider id、partial、UNKNOWN 查询、断线恢复和能力合同。分级记录源码存在、mock 合同、隔离安装、external paper、live read-only、live write；不得越级。
- 按策略实际需要逐交易所交付。unsupported / incomplete 需精确拒绝，不伪造状态、不改连另一 package。
- Gate：每条宣称支持的 direct route 都有不装可选服务的 wheel 与完整 fake 状态机；矩阵未完成的包不得宣称可实盘。

### R53-4：可选 bt_api_execution

- 对当前旧路径中已经存在且属于可靠执行的行为做最小迁移，先定义单一 intent、dispatch、fill、UNKNOWN 与恢复事实 owner；不能为迁移而整文件照搬耦合 BT 的 journal。
- 记录 execution 长期合同：注册策略信号聚合/冲突处理、来源追溯/分配、大单拆分、算法执行状态、子单路由与恢复。明确注册 scope 至少包含账户、provider、环境、策略组、instrument、方向/持仓效果与周期；策略生成信号、选股和 Alpha/因子政策仍属 Strategy/research。
- full 多策略聚合、拆单算法的新实现是后续可选 execution 能力，不是本轮恢复 direct 或移除旧 `backtrader_runtime` 的前置；只对实际迁移部分验收，不宣称现有多腿等于聚合或相关目标已实现。
- 若本轮触及已有双层风控路径，父级额度只预留一次、子级仅从父级额度分配，不重复占用；成交转为实际消耗，确认拒绝/撤单/最终剩余量按幂等规则释放，UNKNOWN/未对账 partial 保留预留。未选 risk 时不影响 direct；显式选中后错误 fail closed。
- Gate：本轮迁移的执行状态可追溯、事务单写、UNKNOWN 不自动重发且无第二次 provider 调用；完整聚合/算法矩阵属于标记为未实现的长期目标，不阻塞 I53。

### R53-5：可选插件分离

- 为 risk / gateway / monitor / runtime 定义独立依赖、版本合同、显式开关、装配错误和关闭合同；direct 无包仍能启动。
- risk 仅执行被选政策；gateway 只提供选定共享服务；monitor 只读观察；runtime 只装配显式选择的 managed composition。
- 构造前校验路由恰为一个。未选不导入 / 连接；已选失败给出有限错误与 BLOCKED / FAILED，禁止“插件失败后继续普通 Store dispatch”。
- Gate：逐插件注入缺包、坏版本、初始化异常、断连、拒绝、超时和错误关闭；direct 未被改变，选中插件也未被绕过。

### R53-6：schema、线程、版本和 wheel

- 确定 journal owner 后做版本化 schema 迁移。用无账户临时 DB 验证升级、恢复、回滚、旧版本拒写；禁止直接改写生产数据或受保护数据库。
- 明确 callback、Broker、Store、journal 的线程、锁序、队列与退出。并发事件由唯一事务序列归并；无 Store / execution 双写或 monitor 改状态。
- Backtrader、`bt_api_py` 与 SDK 包分别定义 base dependencies、插件 extras 和兼容矩阵。direct CTP 仅装 facade / base / CTP 与必要原生依赖，不要求 `bt_api_runtime` 或其他可选服务。
- Gate：源码与 wheel 各建全新隔离环境，检查 metadata、import origins、依赖树、API、Python 范围和 `pip check`；不得借用开发环境残留包。隔离环境至少包含不装插件 direct 与显式选择插件两类；后者注入失败证明不回退。

### R53-7：迁移并移除 Backtrader 旧 `backtrader_runtime`

- 按 §5.1 的31项逐一完成调用方映射、唯一 owner、兼容方案和测试；调用方包含 BT 源码、SDK facade、生产入口、CLI、setup/发行元数据、公开 examples 与 tests。未迁完则不删对应能力。
- 切换活跃 production source callsites、`examples/live` 与 `examples/unified` 中仍活跃的 paper/live 路径、公开生产 API、测试 imports、setup/pyproject 包列表、入口点、依赖及安装验证；历史 evidence、replay/shadow 源码和 fixture 保留在不随新 wheel 安装的归档/测试位置，不保留可偷偷导回旧 runtime 的 fallback。
- 逐包运行 targeted source/fake checks 和全新隔离 wheel consumer。direct 默认路径、RegisteredSimStore 薄桥、CTP/非 CTP 已宣称能力、显式插件失败语义及版本合同通过后，再移除 `backtrader_runtime` 目录、入口、依赖和打包声明。删除动作单独提交并有回滚点。
- 迭代53完成不依赖实际 external paper / production live 账户验收；该证据由迭代52及各自正式 acceptance entrypoint 另行处理。源码、fake、wheel 完成只代表工程边界与组合完成，不代表真实账户可用。
- Gate：新位置承接所有必需能力，活跃调用完成切换，源码与隔离安装检查通过，安装产物不含旧包/引用，延迟模式的源代码与历史证据留存但不能触发回退。此 Gate 不要求 paper/live 账号登录或下单。

### R53-8：交接迭代52的 paper / live

- I53 工程门槛关闭后，I52 从已提交的 direct 基线继续 external `paper` / `live`；I52 不是 R53-7 删除旧包的先决条件，避免53→52→53循环。

测试报告必须记录证据等级、环境、repo/package HEAD、wheel hash、stub 或实际账户边界、运行 / 调用次数与限制。默认零计数不能解释成“没有发生”。fake 结果不能写成真实账户证据。测试只在后续获准实施回合运行；创建本文档不运行测试。
