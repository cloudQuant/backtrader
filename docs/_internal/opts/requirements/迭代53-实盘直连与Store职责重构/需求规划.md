# 迭代 53 需求规划

状态：进行中。本文定义需求，不代表实现、安装组合或账户验收已通过。执行顺序见[迭代计划](迭代计划.md)，实现边界见[设计文档](设计文档.md)，验收见[验收文档](验收文档.md)。

## 目标

1. 保留标准 Backtrader `Store` / `Feed` / `Broker` 用户接口，通过 `bt_api_py` 统一接口连接明确选择的交易所；同一个非单例 Store 实例可按实际 SDK 能力管理多个 route/交易所，不预设所有组合已可用。
2. 普通 direct 只依赖 Backtrader、`bt_api_py`、`bt_api_base` 和所选 provider；不能强制安装或启动 Gateway、Risk、Monitor、Execution、Runtime。显式选中插件后，缺包、错误、超时、未知结果或关闭失败必须明确失败，不静默降级。
3. 首要贯通普通 CTP direct 的行情、账户、下单、撤单、回报和关闭：会话/账户/环境、真实订单身份、单次派发、回报及撤单关联由 SDK/provider 给出。UNKNOWN 不自动换 ID 重发或伪造终态。其他 provider 按已声明能力逐项核查，不为每个交易所新建 BT adapter。
4. 将 `service/`、`stores/`、`execution/`、`factor_execution/`、Broker、Feed 和旧 runtime 按函数、状态及生命周期拆分到相应 owner；可破坏旧内部接口。BT 保留框架对象与生命周期，SDK 负责中立接口及跨包工作流，provider 负责交易所原生事实。
5. 清点并承接受支持的 `backtrader_runtime` 能力、切换活跃调用和发行声明后退役旧包；归档不是运行时回退。可选多策略聚合、算法与拆单是目标能力，不以代码名称充当完成证据。
6. 同一适用策略长期目标是通过配置与 Feed/Broker/Store 装配切换 backtest、replay、shadow、paper、live；当前不宣称所有模式或策略兼容。迭代 52 继续负责其 paper/live 验收，不能将静态或 fake 证据提升为真实账户结果。

## 约束与完成条件

- 保持 Provider 的真实会话、账户、环境、交易日、权限、单位、时间来源、订单身份及回报边界；缺少可信来源时标记 unavailable，不从配置或回放时钟推断权威。
- 多账户/多币种信息按 route 明确暴露；不能把无权威估值的余额和持仓简单加总成单一值。BT 的本地 attribution 不等同交易所账户账本。
- 每项功能有唯一状态 owner、明确线程/锁/事务与关闭责任。execution journal 有单一写者，保留 schema、幂等与恢复语义；迁移时不能形成双写或第二套队列。
- 全部相关结构迁移、生产调用及发行路径收口后冻结结构，再集中执行测试、修复和隔离安装验收。各仓使用既有 dev checkout，小轮明确范围、记录证据、子仓先提交、父仓更新 gitlink、最后交付 BT；保留无关改动。
- 真实 paper/live read/write 按实际有效授权和对应正式入口单独记录；缺权限或条件记 NOT_RUN/BLOCKED，不由本需求授予真实操作权限。
